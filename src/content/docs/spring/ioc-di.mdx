:::tip[한 줄 요약]
IoC(제어의 역전)는 객체를 만들고 서로 연결하는 제어권이 내 코드에서 스프링 컨테이너로 넘어간 것이고, DI(의존성 주입)는 그 방법으로 필요한 객체를 직접 `new` 하지 않고 생성자 등으로 넣어 받는 거예요. 스프링은 필수 의존성은 생성자로 받으라고 권장해요.
:::

## 쉽게 이해하기

스프링이 처음이라면 먼저 이것만 기억하세요. **스프링**(Spring)은 자바로 서버를 만들 때 가장 많이 쓰는 프레임워크(뼈대 코드 묶음)이고, 그 한가운데에 "객체를 대신 만들어 주고 이어 주는 관리자"가 있어요. 이 관리자를 **스프링 컨테이너**라고 불러요.

식당으로 비유해 볼게요. 요리사가 요리를 하려면 칼, 도마, 재료가 필요해요. 요리사가 매일 직접 시장에 가서 칼을 사 오고 재료를 고르면, 납품처 하나 바꾸는 데도 요리사의 하루가 흔들려요.

그래서 식당은 **매니저**를 둬요. 요리사는 "칼 하나, 양파 한 박스 필요해요"라고 적어 두기만 하고, 매니저가 출근 전에 다 준비해서 자리에 놓아 줘요. 무엇을 누구에게 줄지 정하는 권한이 요리사에서 매니저로 넘어갔죠. 이게 **제어의 역전**이에요. 매니저가 물건을 요리사 자리에 놓아 주는 행동이 **의존성 주입**이고요.

단, 실제로는 매니저(컨테이너)가 "무엇을 줄지"를 혼자 정하지 않아요. 개발자가 **어노테이션**(annotation, 클래스나 메서드 위에 붙이는 `@Service` 같은 표시)이나 설정 클래스로 알려 준 정보(설정 메타데이터)를 보고 그대로 만들고 연결해요.

## 제대로 알기

### 1. 먼저 용어 세 개

- **빈**(Bean, 스프링 컨테이너가 만들고 관리하는 객체): 내가 `new`로 만든 객체가 아니라 컨테이너가 만들어서 들고 있는 객체예요.
- **의존성**(dependency, 내 객체가 일하려면 필요한 다른 객체): `OrderService`가 결제를 하려면 `Pay`가 필요하면, `Pay`가 `OrderService`의 의존성이에요.
- **컨테이너**(container, 빈을 만들고 연결하고 보관하는 스프링의 관리자): 코드로는 `ApplicationContext`라는 이름으로 만나요.

DIP(원칙), DI(기법), IoC(개념)가 어떻게 다른지는 [SOLID 원칙의 "DIP, DI, IoC는 어떻게 다른가"](../../oop/solid/)에 정리해 뒀어요. 여기서는 스프링 컨테이너가 실제로 **어떻게** 그 일을 하는지에 집중해요.

### 2. IoC가 없을 때 vs 있을 때

```java
// IoC 없이: 내가 직접 만들고 고름
class OrderService {
    private final Pay pay = new KakaoPay(); // 토스로 바꾸려면 이 줄을 고쳐야 함
}

// DI: 필요하다고 선언만 하고, 누가 넣어 줄지는 신경 안 씀
@Service
class OrderService {
    private final Pay pay;
    OrderService(Pay pay) { this.pay = pay; } // 컨테이너가 Pay 빈을 넣어 줌
}
```

위쪽은 `OrderService`가 "결제하기"에 더해 "어떤 결제사를 쓸지 고르고 만들기"까지 떠안고 있어요. 아래쪽은 만들고 고르는 일을 컨테이너에 넘겼어요. 테스트할 때도 `new OrderService(가짜Pay)`처럼 가짜 객체를 쉽게 넣을 수 있어요.

스프링 문서는 이걸 "빈이 스스로 의존 객체를 만드는 것의 **반대(inverse)**"라서 제어의 역전이라 부른다고 설명해요.

### 3. 컨테이너: BeanFactory와 ApplicationContext

| 구분 | BeanFactory | ApplicationContext |
|---|---|---|
| 관계 | 가장 기본 인터페이스 | BeanFactory를 상속한 하위 인터페이스 |
| 하는 일 | 빈 설정·생성·관리 | 위 기능 + AOP(로깅처럼 여러 곳에 공통으로 끼우는 기능) 통합, 메시지(다국어), 이벤트 발행, 웹용 컨텍스트 등 |
| 실무 | 직접 쓸 일 거의 없음 | 거의 항상 이걸 씀 |

컨테이너가 일하는 방식은 단순해요. **입력**은 내가 만든 평범한 자바 클래스(POJO, 특별한 상속 없는 일반 객체)와 설정 정보(어노테이션, `@Configuration` 자바 설정, 옛날 방식인 XML)예요. **출력**은 바로 쓸 수 있게 연결이 끝난 빈들이에요.

기본적으로 빈은 **싱글톤**(컨테이너 하나당 객체 하나)이에요. 같은 컨텍스트에서 `getBean`을 두 번 불러도 같은 객체가 나와요. 그리고 `ApplicationContext`는 싱글톤 빈을 **시작할 때 미리**(eager) 다 만들어요. 시작이 조금 느려지고 메모리를 먼저 쓰지만, 설정이 잘못됐으면 앱이 뜨는 순간 바로 알 수 있어요. 필요하면 지연(lazy) 생성으로 바꿀 수도 있어요.

<Aside type="caution" title="싱글톤 빈에 요청별 값을 필드로 두지 마세요">
빈 하나를 여러 요청이 동시에 같이 쓰는 구조라서, 서비스 빈 필드에 "현재 사용자" 같은 값을 저장하면 요청끼리 값이 섞이는 동시성 버그로 이어질 수 있다고 흔히 경고해요. 스코프는 [빈 생명주기와 스코프](../bean-lifecycle-scope/)에서 더 다뤄요.
</Aside>

또 "싱글톤 빈"은 디자인 패턴의 싱글톤(private 생성자로 JVM 전체에 하나)과 같은 말이 아니에요. 스프링 빈은 **컨테이너당 하나**라는 뜻으로 보통 설명해요. 패턴 쪽은 [생성 패턴](../../oop/patterns-creational/)을 보세요.

### 4. 빈 등록 방법 2가지

#### 컴포넌트 스캔: `@Component`

클래스에 `@Component`를 붙이면 컨테이너가 지정된 패키지를 훑어서(스캔) 찾아 빈으로 등록해요. 역할에 따라 이름만 다른 특수화 버전이 있어요.

| 어노테이션 | 보통 붙이는 곳 |
|---|---|
| `@Controller` | 웹 요청을 받는 클래스 |
| `@Service` | 비즈니스 로직 |
| `@Repository` | DB 접근 (DB 예외를 스프링 예외로 바꿔 주는 대상이 됨) |
| `@Component` | 그 밖의 일반 부품 |

Spring Boot의 `@SpringBootApplication`에는 `@ComponentScan`이 들어 있고, 기본 스캔 범위는 **이 클래스가 있는 패키지와 그 하위 패키지**로 알려져 있어요. 그래서 메인 클래스를 가장 위 패키지에 두라고들 해요. 자세한 건 [스프링 부트 자동 설정](../boot-autoconfig/)에서 봐요.

#### 직접 등록: `@Configuration` + `@Bean`

```java
@Configuration
class AppConfig {
    @Bean // 반환한 객체가 빈으로 등록됨
    ObjectMapper objectMapper() {
        return new ObjectMapper(); // 소스를 내가 못 고치는 라이브러리 객체
    }
}
```

`@Bean`은 내가 소스를 고칠 수 없는 외부 라이브러리 객체(클래스에 `@Component`를 못 붙이니까)나, 만드는 과정이 복잡한 객체를 등록할 때 주로 써요.

| | `@Component` | `@Bean` |
|---|---|---|
| 붙이는 곳 | 클래스 | `@Configuration` 클래스의 메서드 |
| 주로 쓰는 대상 | 내가 만든 클래스 | 외부 라이브러리 객체, 생성 로직이 복잡한 객체 |
| 등록 방식 | 스캔으로 자동 | 메서드가 반환한 객체 |

#### `@Bean` 메서드를 두 번 부르면 객체가 두 개?

`@Configuration` 클래스는 시작할 때 **CGLIB**(클래스를 상속한 대리 클래스를 실행 중에 만들어 주는 라이브러리)으로 하위 클래스가 만들어져요. 그래서 `@Bean` 메서드끼리 서로 호출해도 매번 새 객체가 아니라 **컨테이너에 있는 그 싱글톤**을 돌려줘요.

```java
@Configuration
class AppConfig {
    @Bean ClientDao clientDao() { return new ClientDao(); }
    @Bean ClientService s1() { return new ClientService(clientDao()); }
    @Bean ClientService s2() { return new ClientService(clientDao()); }
    // s1, s2는 같은 ClientDao 객체를 공유함
}
```

반대로 `@Bean`을 `@Component` 클래스 안에 두거나 `@Configuration(proxyBeanMethods = false)`로 쓰면 이 가로채기가 없어요. 그때 `clientDao()` 호출은 그냥 자바 메서드 호출이라 **새 객체**가 생겨요. 이럴 땐 의존 빈을 메서드 파라미터로 받아야 해요. 같은 이유로 `@Configuration` 클래스는 `final`이면 안 돼요(상속이 안 되니까).

### 5. 주입 방식 3가지

`@Autowired`는 "여기에 맞는 빈을 넣어 줘"라고 컨테이너에 알리는 표시예요. **setter**는 `setNotifier(...)`처럼 필드 값을 넣는 `set`으로 시작하는 메서드고요.

```java
@Service
class OrderService {
    private final Pay pay;           // ① 생성자 주입
    OrderService(Pay pay) { this.pay = pay; }

    private Notifier notifier;       // ② setter 주입 (선택 의존성)
    @Autowired(required = false)
    void setNotifier(Notifier n) { this.notifier = n; }

    @Autowired
    private Coupon coupon;           // ③ 필드 주입
}
```

| 방식 | 장점 | 단점 |
|---|---|---|
| 생성자 | `final` 가능(불변), 필수 의존성이 null 아님 보장, 완전히 초기화된 객체 | 인자가 많으면 길어짐(사실 그게 설계 신호) |
| setter | 기본값이 있는 **선택** 의존성에 적합, 나중에 다시 넣을 수 있음 | 기본값이 없으면 쓰는 곳마다 null 확인 필요 |
| 필드 | 코드가 가장 짧음 | `final` 불가, 스프링 없이 `new`로 테스트할 때 넣을 방법이 없음, 의존성이 생성자에 드러나지 않음 |

스프링 공식 문서의 DI 장이 정식으로 다루는 건 **생성자 방식과 setter 방식 두 가지**예요. 필드 주입은 `@Autowired` 설명에서 "필드에도 붙일 수 있다" 정도로만 나와요. 위 표의 필드 주입 단점은 공식 문서 문구라기보다, 생성자 주입 권장 이유에서 자연스럽게 나온 **업계 통설**에 가까워요.

스프링 팀의 규칙은 간단해요. **필수 의존성은 생성자, 선택 의존성은 setter.** 생성자 인자가 너무 많아지면 그 클래스가 책임을 너무 많이 지고 있다는 냄새로 봐요([SRP](../../oop/solid/)).

알아 두면 좋은 세부 규칙도 있어요.

- 생성자가 **하나뿐이면 `@Autowired`를 생략**해도 돼요(Spring 4.3부터로 알려져 있어요). 생성자가 여러 개이고 기본 생성자가 없으면 최소 하나에는 붙여야 해요.
- 선택 의존성은 `@Autowired(required = false)`, `Optional<T>`, `@Nullable`로 표현해요.
- 같은 타입 빈 **전부**를 `List<T>`나 `Map<String, T>`로 받을 수 있어요. Map의 키는 빈 이름이에요. 순서는 `@Order` 등으로 정하고, 없으면 등록 순서예요.

### 6. 같은 타입 빈이 여러 개일 때

`Pay` 구현이 `kakao`, `toss` 두 개인데 `Pay pay` 하나만 달라고 하면, 컨테이너는 뭘 줘야 할지 몰라서 시작할 때 실패해요.

```
NoUniqueBeanDefinitionException:
expected single matching bean but found 2: kakao,toss
```

컨테이너는 아래 순서로 하나를 골라요.

| 순서 | 확인하는 것 | 뜻 |
|---|---|---|
| 1 | `@Qualifier("kakao")` | 후보를 좁히는 **필터**. 붙어 있으면 그걸로 |
| 2 | `@Primary` | "여럿이면 나를 기본으로". 후보 중 딱 하나면 그것 |
| 3 | 이름 일치 | 파라미터·필드 이름(`Pay kakao`)과 빈 이름이 같으면 그것 |
| 4 | 그래도 없음 | `NoUniqueBeanDefinitionException` |

- **`@Qualifier`가 `@Primary`보다 우선**이에요. `toss`에 `@Primary`가 있어도 `@Qualifier("kakao") Pay p`라고 쓰면 kakao가 들어와요(로컬 실행으로 확인).
- `@Qualifier` 값은 빈의 고유 ID가 아니에요. 여러 빈이 같은 qualifier 값을 가질 수 있고, 그러면 `List`로 받을 때 모두 들어와요.
- Spring 6.2부터는 `@Fallback`도 있어요. `@Primary`의 반대로, "더 나은 후보가 없을 때만" 쓰이는 빈이에요.
- 이름 일치를 쓸 때, 6.1부터는 파라미터 이름을 읽으려면 `-parameters` 컴파일 옵션이 필요해요. Boot의 Gradle·Maven 플러그인은 기본으로 켜 줘요.

#### `@Autowired` vs `@Resource`

| | `@Autowired` (스프링) | `@Resource` (Jakarta 표준) |
|---|---|---|
| 먼저 찾는 기준 | **타입** → 못 찾으면 이름 | **이름** → 못 찾으면 타입 |
| 붙일 수 있는 곳 | 생성자·setter·필드 | 필드, 인자 하나인 setter (생성자 불가) |
| 이름으로 고르려면 | `@Qualifier`와 함께 | 그 자체로 이름 지정 |

옛날 책이나 글에는 `javax.annotation.Resource`로 나오지만, Spring 6 / Boot 3 이후는 패키지가 `jakarta.annotation.Resource`로 바뀌었어요.

### 7. 순환 참조

**순환 참조**(circular reference)는 A가 B를 필요로 하고 B도 A를 필요로 하는 상황이에요. 닭이 먼저냐 달걀이 먼저냐 문제예요.

```java
@Service class A { A(B b) {} }
@Service class B { B(A a) {} }
// A를 만들려면 B가 있어야 하고, B를 만들려면 A가 있어야 함
```

| 상황 | 결과 |
|---|---|
| 생성자 주입, 순수 Spring | 시작할 때 `BeanCurrentlyInCreationException` |
| 필드/setter 주입, 순수 Spring | 기본으로 **해결해 줌**(덜 만든 객체 참조를 먼저 넘기는 방식) |
| 아무 주입 방식, **Spring Boot 2.6+** 기본 설정 | 시작 실패. 순환 참조가 **기본 금지** |
| Boot에서 `spring.main.allow-circular-references=true` | 필드/setter 순환은 다시 허용(2.5 동작). 생성자 순환은 여전히 불가 |

그래서 "필드 주입이면 순환 참조가 해결된다"는 말은 **순수 스프링 기준**이에요. 요즘 Boot 프로젝트에서는 주입 방식과 상관없이 기본으로 앱이 안 떠요. Boot 4.1에서도 이 기본값이 유지되는 걸 로컬에서 확인했어요.

스프링 문서도 setter 주입으로 순환을 푸는 방법을 언급하지만 **권장하지 않는다**고 적어요. 근본 해결은 설계를 고치는 거예요. 흔히 쓰는 방법은 이래요.

- 둘이 같이 쓰는 로직을 **제3의 클래스**로 빼기
- **이벤트**(`ApplicationEventPublisher`)로 한쪽 방향 호출을 끊기
- 한쪽을 `@Lazy`나 `ObjectProvider<T>`로 **나중에** 가져오기(임시방편 성격)

생성자 주입은 순환이 생기면 시작하자마자 드러나서, 설계 문제를 숨기지 않는다는 점이 장점이에요.

### 8. 책 예제와 요즘 방식

『스프링 입문을 위한 자바 객체 지향의 원리와 이해』 7장은 운전자–자동차–타이어 예제로 "직접 `new` → 생성자 주입 → setter 주입 → XML 설정 → `@Autowired` → `@Resource`" 순서로 발전시켜요. 흐름을 이해하기엔 좋지만 XML 설정 중심이라 옛날 방식이에요. 지금은 **어노테이션 + 생성자 주입**이 표준이에요.

## 면접 질문

<details>
<summary>Q. IoC와 DI가 뭔가요? 둘은 어떻게 다른가요?</summary>

**답변(30초)** IoC는 객체를 만들고 연결하는 제어권이 내 코드에서 프레임워크로 넘어간 것을 말해요. DI는 IoC를 구현하는 방법으로, 객체가 필요한 의존성을 직접 `new` 하지 않고 생성자나 setter로 밖에서 받는 거예요. 스프링에서는 컨테이너가 빈을 만들면서 생성자 파라미터 타입을 보고 맞는 빈을 넣어 줘요. 그래서 구현체를 바꿀 때 쓰는 쪽 코드를 안 고쳐도 되고 테스트에 가짜 객체를 넣기도 쉬워요.

**꼬리질문**
- Q. DIP와는 어떻게 다른가요? → DIP는 "추상화에 의존하라"는 설계 원칙이에요. DI로 주입받아도 받는 타입이 구체 클래스면 DIP는 안 지켜져요.
- Q. 왜 "역전"인가요? → 원래 객체가 스스로 의존 객체를 만들던 것과 반대로, 컨테이너가 만들어 넣어 주기 때문이에요.
</details>

<details>
<summary>Q. BeanFactory와 ApplicationContext의 차이는?</summary>

**답변(30초)** 둘 다 스프링 컨테이너 인터페이스예요. BeanFactory가 빈을 만들고 관리하는 기본 기능을 가지고, ApplicationContext는 BeanFactory를 상속해서 AOP 통합, 다국어 메시지, 이벤트 발행, 웹 컨텍스트 같은 기능을 더한 상위 집합이에요. 실무에서는 거의 항상 ApplicationContext를 써요. 또 ApplicationContext는 싱글톤 빈을 시작 시점에 미리 만들어서 설정 오류를 앱이 뜰 때 바로 알 수 있어요.

**꼬리질문**
- Q. 미리 만드는 게 단점은 없나요? → 시작 시간과 메모리를 먼저 써요. 필요하면 지연(lazy) 초기화로 바꿀 수 있어요.
</details>

<details>
<summary>Q. @Component와 @Bean은 어떻게 다르고 언제 무엇을 쓰나요?</summary>

**답변(30초)** `@Component`는 클래스에 붙여 컴포넌트 스캔으로 자동 등록하고, `@Bean`은 `@Configuration` 클래스의 메서드에 붙여 그 메서드가 반환한 객체를 등록해요. 내가 만든 클래스는 보통 `@Service`, `@Repository` 같은 `@Component` 계열로 등록해요. 소스를 고칠 수 없는 외부 라이브러리 객체나 생성 로직이 복잡한 객체는 `@Bean`으로 등록해요.

**꼬리질문**
- Q. `@Configuration`에서 `@Bean` 메서드를 두 번 호출하면 객체가 두 개 생기나요? → 아니요. CGLIB 하위 클래스가 호출을 가로채서 컨테이너의 싱글톤을 돌려줘요. 단 `@Component` 클래스 안의 `@Bean`이나 `proxyBeanMethods = false`면 새 객체가 생겨요.
- Q. `@Repository`만의 특징은? → DB 접근 계층 예외를 스프링 예외로 바꿔 주는 대상이 돼요.
</details>

<details>
<summary>Q. 의존성 주입 방식 3가지와 생성자 주입을 권장하는 이유는?</summary>

**답변(30초)** 생성자 주입, setter 주입, 필드 주입이 있고 스프링 팀은 생성자 주입을 권장해요. 생성자 주입은 필드를 `final`로 둘 수 있어 불변이고, 필수 의존성이 없으면 객체가 아예 안 만들어지니 null이 아님이 보장돼요. 또 스프링 없이도 `new`로 가짜 객체를 넣어 단위 테스트하기 쉬워요. 그래서 필수는 생성자, 기본값이 있는 선택 의존성은 setter로 받는 게 기본 규칙이에요.

**꼬리질문**
- Q. 필드 주입은 왜 피하나요? → `final`을 못 쓰고, 스프링 없이 테스트할 때 의존성을 넣을 방법이 없고, 무엇에 의존하는지 생성자에 드러나지 않는다는 점이 흔히 꼽혀요.
- Q. 생성자 파라미터가 10개면? → 책임이 너무 많다는 신호라 클래스를 나눌지 검토해요.
- Q. `@Autowired`를 꼭 붙여야 하나요? → 생성자가 하나뿐이면 생략할 수 있어요.
</details>

<details>
<summary>Q. 같은 타입 빈이 두 개면 어떻게 되나요?</summary>

**답변(30초)** 아무 구분 수단이 없으면 시작할 때 `NoUniqueBeanDefinitionException`으로 실패해요. 해결은 주입 지점에 `@Qualifier`로 어떤 빈인지 지정하거나, 기본으로 쓸 빈에 `@Primary`를 붙이는 거예요. 둘이 같이 있으면 `@Qualifier`가 우선해요. 표시가 전혀 없으면 파라미터 이름과 빈 이름이 같은 걸 골라요. 전부 필요하면 `List`나 `Map<String, T>`로 받으면 돼요.

**꼬리질문**
- Q. `@Autowired`와 `@Resource` 차이는? → `@Autowired`는 타입으로 먼저 찾고, `@Resource`는 이름으로 먼저 찾아요. `@Resource`는 생성자에는 못 써요.
- Q. `@Qualifier` 값은 빈 이름인가요? → 아니요, 후보를 좁히는 필터 값이에요. 다만 지정이 없으면 빈 이름이 기본 qualifier 역할을 해요.
</details>

<details>
<summary>Q. 순환 참조가 뭐고, 스프링은 어떻게 처리하나요?</summary>

**답변(30초)** 두 빈이 서로를 의존하는 상황이에요. 생성자 주입이면 서로가 먼저 있어야 해서 시작할 때 `BeanCurrentlyInCreationException`이 나요. 순수 스프링은 필드나 setter 순환은 덜 만든 객체를 먼저 넘겨서 풀어 주지만, Spring Boot 2.6부터는 순환 참조가 기본 금지라 주입 방식과 상관없이 앱이 안 떠요. 설정으로 다시 허용할 수 있지만, 근본적으로는 공통 로직을 분리하거나 이벤트로 방향을 끊어 설계를 고쳐야 해요.

**꼬리질문**
- Q. 생성자 주입이 순환 참조에 유리하다는 건? → 순환이 생기면 시작하자마자 드러나서 설계 문제를 숨기지 않기 때문이에요.
- Q. 급할 때 임시 해결은? → `spring.main.allow-circular-references=true`나 한쪽을 `@Lazy`로 받는 방법이 있지만 문제를 덮는 것이라 후속 수정이 필요해요.
</details>

## 서술형 연습

<details>
<summary>상황: Spring Boot 2.5에서 2.6 이상으로 버전을 올렸더니 "The dependencies of some of the beans form a cycle" 오류로 서버가 뜨지 않습니다. 오늘 안에 배포해야 합니다. 어떻게 하겠습니까?</summary>

**상황 파악**
코드는 그대로인데 버전만 올렸더니 시작이 실패해요. 원래 있던 순환 참조가 2.5까지는 필드/setter 주입 덕분에 조용히 넘어갔고, 2.6부터 순환 참조가 기본 금지가 되면서 드러난 거예요.

**원인 후보**
1. 서비스 A와 B가 서로를 필드 주입으로 참조(가장 흔함)
2. A → B → C → A처럼 여러 단계를 거친 순환
3. 설정 클래스의 `@Bean` 메서드끼리 엮인 순환

오류 메시지에 순환에 걸린 빈 목록이 나오니 그걸 보고 어느 경우인지 먼저 확인해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `spring.main.allow-circular-references=true` | 설정 한 줄, 바로 2.5 동작으로 복구 | 설계 문제를 그대로 덮음, 생성자 순환은 못 품 |
| B. 한쪽 주입을 `@Lazy`로 | 코드 수정 범위가 작음 | 실제 호출 시점까지 문제가 숨고, 프록시(진짜 객체 대신 끼워 두는 대리 객체)가 끼어 동작을 추적하기 어려움 |
| C. 공통 로직을 제3의 클래스로 분리하거나 이벤트로 한쪽 방향 끊기 | 근본 해결, 의존 방향이 한쪽으로 정리됨 | 시간이 들고 테스트 범위가 넓어짐 |

**내가 고를 방법**
오늘 배포가 급하니 A로 먼저 서버를 살리고, 순환 목록을 이슈로 남겨 다음 작업에서 C로 고쳐요. A는 전역 설정이라 새 순환이 또 생겨도 못 잡으니, C가 끝나면 설정을 다시 꺼서 기본 금지 상태로 돌려요. 고칠 때는 생성자 주입으로 바꿔 두면 이후 순환이 생겨도 시작 시점에 바로 드러나요.

**채점 포인트**: Boot 2.6 순환 참조 기본 금지, 필드 주입이 순환을 숨겨 왔다는 진단, `allow-circular-references`의 임시성, 설계 수정(분리·이벤트), 생성자 주입으로 재발 방지, 임시 조치 후 되돌리기 계획.
</details>

<details>
<summary>상황: 주 DB와 리포트용 DB, DataSource 두 개를 @Bean으로 등록했더니 서버가 NoUniqueBeanDefinitionException으로 뜨지 않습니다.</summary>

**상황 파악**
`DataSource` 타입 빈이 두 개인데, 이걸 하나만 받는 곳(내 코드나 라이브러리 설정)이 어느 쪽을 줘야 할지 몰라서 실패한 거예요.

**원인 후보**
1. 두 빈에 아무 구분 표시가 없음
2. 내 코드의 주입 지점 이름이 빈 이름과 달라 이름 일치로도 못 고름
3. 라이브러리 쪽 자동 설정이 `DataSource` 하나를 기대함(내 코드에서 고칠 수 없는 주입 지점)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 주 DB에 `@Primary`, 리포트 쪽은 쓰는 곳마다 `@Qualifier("reportDataSource")` | 대부분 코드와 라이브러리는 그대로 주 DB를 받음 | 리포트 DB를 쓰는 곳에 `@Qualifier`를 빠뜨리면 조용히 주 DB를 씀 |
| B. `@Primary` 없이 모든 주입 지점에 `@Qualifier` | 어느 DB인지 코드에 항상 명시됨 | 내가 못 고치는 라이브러리 주입 지점은 해결이 안 됨 |
| C. 파라미터 이름을 빈 이름과 맞춰 이름 일치에 기대기 | 어노테이션이 줄어듦 | 이름 변경(리팩터링) 한 번에 다른 빈이 들어가거나 깨질 수 있음 |

**내가 고를 방법**
A를 써요. 주 DB가 "기본값"이라는 의미가 실제와 맞고, 라이브러리처럼 내가 못 고치는 주입 지점도 `@Primary`로 해결돼요. 리포트 DB를 쓰는 곳은 몇 군데 안 되니 `@Qualifier`로 명시하고, 실수를 막으려고 리포트 전용 리포지토리 설정을 한곳에 모아 둬요.

**채점 포인트**: `NoUniqueBeanDefinitionException` 원인, `@Primary`와 `@Qualifier` 역할 차이, `@Qualifier`가 우선한다는 점, 라이브러리 주입 지점 고려, 이름 일치의 취약함.
</details>

## 필기 포인트

- IoC는 **개념**, DI는 **구현 기법**, DIP는 **설계 원칙**.
- ApplicationContext는 BeanFactory의 **하위** 인터페이스(기능은 상위 집합).
- 싱글톤 빈은 ApplicationContext가 **시작 시 미리(eager)** 생성. "기본이 lazy"는 오답.
- 기본 스코프는 **singleton**.
- `@Autowired`는 **byType** 우선, `@Resource`는 **byName** 우선.
- 생성자가 하나면 `@Autowired` **생략 가능**.
- `@Qualifier`가 `@Primary`보다 **우선**.
- Spring Boot **2.6+**는 순환 참조 **기본 금지**.
