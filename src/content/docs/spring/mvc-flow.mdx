:::tip[한 줄 요약]
스프링 MVC는 `DispatcherServlet` 하나가 모든 요청을 먼저 받는 프론트 컨트롤러 구조예요. 요청은 필터를 지나 DispatcherServlet에 들어오고, HandlerMapping이 컨트롤러를 찾고, HandlerAdapter가 실행하고, `@RestController`면 HttpMessageConverter가 반환값을 JSON으로 바꿔 바로 응답해요.
:::

:::note[처음이라면 여기까지]
① 모든 요청은 DispatcherServlet이라는 접수 창구 하나를 먼저 거쳐요.

② 창구가 담당 컨트롤러를 찾아 실행하고, 결과를 JSON이나 화면으로 돌려줘요.

③ 요청 하나는 처음부터 끝까지 스레드(일하는 직원) 하나가 처리해요.

④ 면접에선 질문 1·2번을 먼저 연습하세요.
:::

## 쉽게 이해하기

큰 병원을 떠올려 보세요. 환자는 의사 진료실로 바로 들어가지 않아요. 건물 입구에서 보안 검색과 체온 측정을 먼저 받고(**필터**), 1층 **접수 데스크**로 가요(**DispatcherServlet**).

접수 직원은 증상을 보고 "내과 3번 방"처럼 어느 의사에게 보낼지 안내판에서 찾아요(**HandlerMapping**). 의사마다 진료 방식이 달라서, 통역사 같은 진행 담당이 그 의사에 맞게 차트를 준비하고 진료를 진행시켜요(**HandlerAdapter**). 진료실 문 앞에서는 간호사가 "예약하셨죠?"를 한 번 더 확인해요(**인터셉터**).

진료가 끝나면 결과를 처방전(JSON)으로 바로 주거나, 설명 자료(화면)로 만들어 줘요. 그리고 환자는 들어왔던 입구를 거꾸로 지나 나가요.

단, 실제로는 이 모든 일을 **직원 한 명(스레드 하나)** 이 환자 한 명을 입구부터 출구까지 데리고 다니며 처리해요. 병원처럼 창구마다 사람이 따로 있는 게 아니에요.

## 제대로 알기

### 1. 먼저 용어 몇 개

- **서블릿**(Servlet, 자바로 HTTP 요청을 받아 응답을 만드는 표준 객체): 자바 웹의 기본 단위예요.
- **서블릿 컨테이너**(servlet container, 서블릿을 띄우고 요청을 넘겨 주는 프로그램): 대표가 **톰캣**(Tomcat)이에요. 스프링 부트는 톰캣을 앱 안에 넣어서(내장 서블릿 컨테이너) 같이 띄워요.
- **핸들러**(handler, 요청을 실제로 처리하는 대상): 보통 `@GetMapping`이 붙은 컨트롤러 메서드예요.
- **프론트 컨트롤러 패턴**(front controller, 모든 요청을 입구 하나가 먼저 받는 구조): 공통 처리를 입구에 모아 두고, 실제 일은 뒤쪽 부품에 나눠 맡겨요.

### 2. DispatcherServlet은 왜 있나

컨트롤러마다 "URL 해석, 요청 바디 읽기, JSON 만들기, 예외 처리"를 각자 하면 같은 코드가 수십 번 반복돼요. 그래서 스프링 MVC는 `DispatcherServlet`이라는 서블릿 **하나**가 모든 요청을 받아 정해진 순서를 지키고, 각 단계의 실제 일은 바꿔 끼울 수 있는 부품(빈)에게 맡겨요.

`DispatcherServlet`도 결국 평범한 서블릿이라 톰캣에 등록돼야 해요. 스프링 부트는 이걸 자동으로 해 주고, 빈으로 등록된 서블릿이 하나뿐이면 `/`에, 필터는 `/*`에 매핑해요.

DispatcherServlet이 일을 맡기는 부품들이에요.

| 부품 | 하는 일 |
|---|---|
| `HandlerMapping` | 요청 URL로 처리할 핸들러를 찾고, 함께 걸 **인터셉터 목록**도 돌려줌 |
| `HandlerAdapter` | 핸들러 모양이 무엇이든 DispatcherServlet이 똑같이 실행할 수 있게 해 줌 |
| `HandlerExceptionResolver` | 처리 중 난 예외를 응답으로 바꾸는 전략 |
| `ViewResolver` | 컨트롤러가 돌려준 문자열 뷰 이름을 실제 화면(View)으로 바꿈 |
| 기타 | `LocaleResolver`(언어), `MultipartResolver`(파일 업로드), `FlashMapManager`(리다이렉트 사이 값 전달) |

### 3. 요청 하나가 지나가는 순서

1. 톰캣이 연결을 받고 **워커 스레드** 하나를 배정해요.
2. **서블릿 필터** 체인을 지나요. 인코딩, 보안(Spring Security), 로깅 같은 일이에요.
3. `DispatcherServlet`에 도착해요.
4. `HandlerMapping`이 URL에 맞는 컨트롤러 메서드와 인터셉터 목록을 찾아요.
5. 인터셉터 `preHandle`이 실행돼요. `false`를 돌려주면 여기서 멈춰요.
6. `HandlerAdapter`가 메서드 인자를 준비해요. `@RequestBody`면 JSON을 객체로 바꾸고, `@Valid`가 있으면 검증해요.
7. 컨트롤러가 실행되고 서비스, 리포지토리를 불러요. `@Transactional` 같은 **AOP 프록시**는 이 호출 경계에서 걸려요([AOP](../aop/)).
8. 반환값 처리
   - `@RestController`: HttpMessageConverter가 객체를 JSON으로 바꿔 **어댑터 안에서 바로 응답을 써요**. 화면 렌더링은 없어요.
   - `@Controller` + 뷰 이름: `ViewResolver`가 화면을 찾아 렌더링해요.
9. 인터셉터 `postHandle` → `afterCompletion` 순으로 불려요.
10. 필터를 거꾸로 지나 응답이 나가고, 스레드는 풀로 돌아가요.

### 심화: 4. 왜 HandlerAdapter가 따로 있나

컨트롤러의 모양은 하나가 아니에요. `@RequestMapping` 메서드도 있고, `HttpRequestHandler`를 구현한 클래스도 있고, 함수형 라우터도 있어요. DispatcherServlet이 이걸 전부 직접 알면 새 종류가 생길 때마다 DispatcherServlet을 고쳐야 해요.

그래서 중간에 **어댑터**를 둬요. DispatcherServlet은 어댑터들에게 `supports(handler)`로 "이거 실행할 줄 알아?"를 묻고, 맞는 어댑터의 `handle()`만 불러요. 새 핸들러 종류가 생기면 어댑터만 추가하면 돼요. 디자인 패턴의 [어댑터 패턴](../../oop/patterns-structural/) 사례이고, 확장에는 열리고 수정에는 닫힌 OCP 구조예요.

| 어댑터 | 실행하는 핸들러 |
|---|---|
| `RequestMappingHandlerAdapter` | `@RequestMapping` 계열 메서드(우리가 거의 항상 쓰는 것) |
| `HttpRequestHandlerAdapter` | `HttpRequestHandler` 구현체 |
| `SimpleControllerHandlerAdapter` | 옛날식 `Controller` 인터페이스 구현체 |
| `HandlerFunctionAdapter` | 함수형 엔드포인트 |

### 5. @RestController와 JSON은 누가 만드나

`@RestController`는 `@Controller`와 `@ResponseBody`를 합친 것일 뿐이에요. `@ResponseBody`가 붙으면 반환값을 뷰 이름으로 보지 않고 **HttpMessageConverter**(자바 객체와 HTTP 바디를 서로 바꿔 주는 변환기)로 바디에 바로 써요.

| | `@Controller` (뷰) | `@RestController` |
|---|---|---|
| 반환값의 뜻 | 화면 이름(예: `"home"`) | 응답 바디에 쓸 데이터 |
| 거치는 부품 | ViewResolver → View 렌더링 | HttpMessageConverter |
| 응답이 써지는 곳 | 핸들러 실행 뒤 렌더링 단계 | HandlerAdapter 안에서 바로 |

어떤 변환기를 쓸지는 헤더로 정해요.

- 요청을 읽을 때(`@RequestBody`): 보통 **Content-Type** 헤더(내가 보내는 바디의 형식)를 봐요.
- 응답을 쓸 때: 보통 **Accept** 헤더(클라이언트가 받고 싶은 형식)를 봐요.

JSON은 Jackson 기반 변환기가 맡아요. 스프링 부트가 기본으로 넣어 주고, 문자열 기본 인코딩은 UTF-8이에요.

<Aside type="note" title="버전에 따라 클래스 이름이 달라요">
Spring 7 / Boot 4는 Jackson 3를 쓰고 변환기 이름이 `JacksonJsonHttpMessageConverter`예요. Spring 6 / Boot 3는 Jackson 2 기반 `MappingJackson2HttpMessageConverter`로 알려져 있어요. 면접에서는 "Jackson 기반 JSON 메시지 컨버터"라고만 말해도 충분해요.
</Aside>

`@RequestBody`는 JSON 같은 바디를 읽을 때 써요. HTML 폼 데이터는 `@RequestParam`으로 읽어야 해요. 서블릿이 파라미터를 꺼내면서 바디를 이미 읽어 버려서 다시 못 읽기 때문이에요.

### 6. 필터 vs 인터셉터 vs AOP

셋 다 "앞뒤에 공통 코드 끼우기"라서 헷갈려요. 가장 큰 차이는 **어디에 서 있느냐**예요. 필터는 DispatcherServlet **바깥**(톰캣 레벨), 인터셉터는 DispatcherServlet **안**(스프링 MVC 레벨), AOP는 빈 메서드 호출 경계예요.

| 구분 | 서블릿 필터 | 핸들러 인터셉터 | 스프링 AOP |
|---|---|---|---|
| 소속 | 서블릿 표준 | 스프링 MVC | 스프링 코어(프록시) |
| 위치 | DispatcherServlet 앞 | DispatcherServlet 안, 컨트롤러 앞뒤 | 빈 메서드 호출 경계 |
| 적용 단위 | URL 패턴(`/*`) | 핸들러 경로 패턴 | 포인트컷(패키지, 어노테이션) |
| 받는 정보 | 요청·응답 객체 | 요청·응답 + 핸들러 객체 | 메서드 정보·인자 |
| 요청·응답 객체 바꿔치기 | 가능 | 불가 | 해당 없음 |
| 흐름 멈추기 | `chain.doFilter()` 안 부름 | `preHandle`에서 `false` | 예외 또는 `proceed()` 안 부름 |
| `@ControllerAdvice`로 예외 처리 | 안 됨 | 됨 | 컨트롤러·서비스 안이면 됨 |
| 대표 용도 | 인증(Spring Security), 인코딩, CORS, 요청 로깅 | API 공통 로깅, 실행 시간 측정 | 트랜잭션, 메서드 로깅, 캐싱 |

로컬에서 필터 1개, 인터셉터 1개, 서비스에 거는 AOP 1개를 두고 찍어 본 실제 순서예요. 모든 로그가 **같은 스레드 이름**으로 찍혔어요.

```
Filter before → preHandle → Controller → AOP before → Service → AOP after
→ postHandle → afterCompletion → Filter after
```

**필터 쓰는 법.** `doFilter(req, res, chain)` 안에서 요청을 보고, 필요하면 요청·응답을 감싸고, `chain.doFilter()`로 다음에 넘겨요. 안 넘기면 거기서 끝나요. 부트에서 순서가 필요하면 필터 **클래스**에 `@Order`를 붙이거나 `FilterRegistrationBean.setOrder()`를 써요. `@Bean` 메서드에 `@Order`를 붙이는 건 효과가 없어요.

**인터셉터 쓰는 법.** `WebMvcConfigurer.addInterceptors()`로 등록하고 메서드 3개를 구현해요.

| 메서드 | 언제 | 주의 |
|---|---|---|
| `preHandle` | 핸들러 실행 전 | `false`면 핸들러를 안 부름. 응답은 인터셉터가 직접 써야 함 |
| `postHandle` | 핸들러 실행 후 | 예외가 나면 **안 불림**. `@ResponseBody`면 응답이 **이미 커밋**된 뒤 |
| `afterCompletion` | 요청이 완전히 끝난 뒤 | **항상** 불림. 정리 작업은 여기서 |

**커밋**(commit)은 응답 헤더가 이미 클라이언트로 출발해서 더는 못 바꾸는 상태를 말해요. `@RestController`는 어댑터 안에서 응답을 다 써 버리기 때문에, `postHandle`에서 헤더를 추가해도 안 붙어요. 로컬 실험에서도 `postHandle` 시점에 `response.isCommitted()`가 `true`였어요. 이럴 땐 `ResponseBodyAdvice`나 필터를 써요.

인터셉터가 여러 개면 `preHandle`은 등록 순서대로, `postHandle`·`afterCompletion`은 역순으로 불려요. 로컬에서 A, B 두 개를 등록해 보니 A.pre → B.pre → (컨트롤러) → B.post → A.post → B.after → A.after 순이었어요.

<Aside type="caution" title="인증은 인터셉터보다 필터에서">
스프링 공식 문서는 인터셉터가 컨트롤러 경로 매칭과 어긋날 수 있어서 **보안 계층으로는 적합하지 않다**고 해요. Spring Security처럼 서블릿 필터 체인에 붙는 방식을 가능한 한 앞에서 쓰라고 권해요. 그래서 "Spring Security는 필터 기반"이라고 흔히 설명해요([Spring Security](../spring-security/)).
</Aside>

### 7. 예외는 어떻게 처리되나

컨트롤러나 서비스에서 예외가 나면 DispatcherServlet은 `HandlerExceptionResolver`들에게 차례로 물어봐요. 각 리졸버는 "내가 처리함" 또는 "모르겠음(null)"을 돌려주고, 모르면 다음 리졸버로 넘어가요.

| 리졸버 | 하는 일 |
|---|---|
| `ExceptionHandlerExceptionResolver` | 컨트롤러나 `@ControllerAdvice`의 `@ExceptionHandler` 메서드 호출 |
| `ResponseStatusExceptionResolver` | `@ResponseStatus`가 붙은 예외를 그 상태 코드로 |
| `DefaultHandlerExceptionResolver` | 스프링 MVC 내부 예외를 알맞은 HTTP 상태 코드로 |
| `SimpleMappingExceptionResolver` | 예외 클래스 이름을 에러 화면 이름에 매핑 |

**전역 예외 처리**는 `@RestControllerAdvice`(= `@ControllerAdvice` + `@ResponseBody`) 클래스에 `@ExceptionHandler`를 모아 두는 방식이 보통이에요. 기본으로 모든 컨트롤러에 적용되고, `annotations`, `basePackages`, `assignableTypes`로 범위를 좁힐 수 있어요.

```java
@RestControllerAdvice
class GlobalErrorHandler {
    @ExceptionHandler(IllegalStateException.class)
    ResponseEntity<String> handle(IllegalStateException e) {
        // 상태 코드를 직접 정해야 함. 안 정하면 200으로 나감
        return ResponseEntity.status(409).body(e.getMessage());
    }
}
```

알아 둘 규칙이에요.

- 컨트롤러 안에 있는 `@ExceptionHandler`가 먼저, 전역(`@ControllerAdvice`) 것이 그다음이에요.
- 리졸버가 끝까지 못 풀면 예외는 톰캣으로 올라가고, 톰캣이 에러 페이지 경로(예: `/error`)로 **다시 디스패치**해요. 스프링 부트는 `/error`에 `BasicErrorController`를 등록해 두고, 브라우저엔 whitelabel HTML, API 클라이언트엔 JSON을 줘요.
- 로컬 실험에서 예외가 나면 `postHandle`은 건너뛰고 `afterCompletion`은 불렸어요. 리졸버가 처리했으면 `afterCompletion`의 예외 인자는 `null`이었어요.
- **필터에서 던진 예외는 `@ControllerAdvice`가 못 잡아요.** 필터는 DispatcherServlet 바깥이라 리졸버 체인을 안 거치고 톰캣의 `/error`로 가요.

표준 에러 형식(RFC 9457 Problem Details)을 쓰고 싶으면 `spring.mvc.problemdetails.enabled=true`로 켤 수 있어요.

### 8. @Valid 검증이 실패하면

`@RequestBody`나 `@ModelAttribute` 파라미터에 `@Valid`(또는 `@Validated`)를 붙이면 객체 안의 `@NotBlank` 같은 규칙을 검사해요. 실패하면 `MethodArgumentNotValidException`이 나고 기본 응답은 **400 Bad Request**예요. 바로 뒤에 `BindingResult` 파라미터를 두면 예외 대신 컨트롤러 안에서 직접 처리할 수 있어요.

Spring 6.1부터는 `@RequestParam @Min(1) int page`처럼 파라미터에 제약을 직접 달면 **메서드 검증**이 돌고, 실패 시 `HandlerMethodValidationException`이 나요. 그래서 요즘은 두 예외를 **둘 다** 전역 처리해야 응답 형식이 통일돼요. 이 내장 메서드 검증을 쓰려면 컨트롤러 클래스에 붙은 `@Validated`는 빼야 해요(그게 있으면 AOP 프록시 방식으로 검증해요).

### 심화: 9. 톰캣 스레드 풀과 thread-per-request

스프링 MVC는 **요청 하나당 스레드 하나**(thread-per-request) 모델이에요. 톰캣 워커 스레드(`http-nio-8080-exec-N`) 하나가 필터부터 응답까지 전부 처리해요. 그래서 트랜잭션 정보, 로그인 정보(SecurityContext), 로그 추적값(MDC)처럼 **ThreadLocal**(스레드마다 따로 갖는 저장 칸)에 담는 기능이 요청 단위로 동작한다고 설명해요.

스프링 부트 4.1 기본값이에요(부트 3에서도 같다고 알려져 있어요).

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `server.tomcat.threads.max` | 200 | 요청을 처리하는 워커 스레드 최대 수 |
| `server.tomcat.threads.min-spare` | 10 | 놀고 있어도 유지하는 최소 스레드 |
| `server.tomcat.max-connections` | 8192 | 동시에 받아 두는 연결 수 |
| `server.tomcat.accept-count` | 100 | 연결이 꽉 찼을 때 OS가 더 받아 두는 대기열 길이 |
| `spring.threads.virtual.enabled` | false | `true`면 가상 스레드 사용(이때 `threads.max`는 효과 없음) |

**연결 수(8192)와 스레드 수(200)는 달라요.** 연결은 많이 붙잡아 둘 수 있지만, 실제로 동시에 일하는 건 스레드 200개예요. 200개가 모두 느린 외부 호출 같은 데서 기다리고 있으면 새 요청은 줄을 서고, 결국 지연과 타임아웃이 나요. 스레드 풀 자체는 [스레드 풀](../../java/thread-pool/)에서 더 다뤄요.

<details>
<summary>Q. 스프링 MVC의 요청 처리 흐름을 설명해 주세요.</summary>

**답변(30초)** 요청이 오면 톰캣이 워커 스레드 하나를 배정하고, 서블릿 필터를 지나 프론트 컨트롤러인 DispatcherServlet에 도착해요. DispatcherServlet은 HandlerMapping으로 처리할 컨트롤러 메서드와 인터셉터를 찾고, 인터셉터 preHandle 뒤에 HandlerAdapter로 컨트롤러를 실행해요. `@RestController`면 HttpMessageConverter가 반환 객체를 JSON으로 바꿔 어댑터 안에서 바로 응답을 쓰고, 뷰 컨트롤러면 ViewResolver가 화면을 렌더링해요. 그 뒤 postHandle, afterCompletion을 거쳐 필터를 거꾸로 지나 응답이 나가요.

**꼬리질문**
- Q. DispatcherServlet이 컨트롤러를 직접 호출하나요? → 아니요, HandlerAdapter를 통해 호출해요. 그래서 컨트롤러 형태가 달라도 DispatcherServlet은 바뀌지 않아요.
- Q. 예외가 나면요? → HandlerExceptionResolver 체인으로 넘어가고, 보통 `@ControllerAdvice`의 `@ExceptionHandler`가 처리해요. 못 풀면 톰캣이 `/error`로 다시 보내요.
</details>

<details>
<summary>Q. DispatcherServlet의 역할과 프론트 컨트롤러 패턴이 무엇인가요?</summary>

**답변(30초)** 프론트 컨트롤러 패턴은 모든 요청을 입구 하나가 먼저 받아 공통 처리를 하고, 실제 일은 뒤쪽 부품에 나눠 맡기는 구조예요. 스프링 MVC에서는 DispatcherServlet이 그 입구예요. DispatcherServlet은 처리 순서만 쥐고 있고, 핸들러 찾기는 HandlerMapping, 실행은 HandlerAdapter, 예외는 HandlerExceptionResolver, 화면은 ViewResolver에 맡겨요. 이 부품들이 빈이라서 교체나 확장이 쉬워요.

**꼬리질문**
- Q. DispatcherServlet도 서블릿인가요? → 네, 표준 서블릿이라 톰캣에 등록돼야 해요. 부트는 내장 톰캣을 띄우면서 자동으로 등록해 줘요.
</details>

<details>
<summary>Q. @Controller와 @RestController의 차이는? JSON은 누가 만드나요?</summary>

**답변(30초)** `@RestController`는 `@Controller`에 `@ResponseBody`를 합친 거예요. `@Controller`는 반환값을 화면 이름으로 보고 ViewResolver가 렌더링하지만, `@RestController`는 반환값을 HttpMessageConverter가 바디로 직렬화해요. JSON은 Jackson 기반 메시지 컨버터가 만들고, 어떤 컨버터를 쓸지는 응답 땐 Accept 헤더, 요청 바디를 읽을 땐 Content-Type 헤더를 보고 골라요.

**꼬리질문**
- Q. `@RestController`도 ViewResolver를 거치나요? → 아니요. 어댑터 안에서 바디를 바로 쓰고 뷰 렌더링은 없어요.
- Q. 폼 데이터를 `@RequestBody`로 받을 수 있나요? → 폼 데이터는 `@RequestParam`으로 읽어야 해요. 서블릿이 파라미터를 꺼낼 때 바디를 이미 읽어 버려요.
</details>

<details>
<summary>Q. 필터와 인터셉터의 차이는? 각각 언제 쓰나요?</summary>

**답변(30초)** 가장 큰 차이는 위치예요. 필터는 서블릿 표준이라 DispatcherServlet 바깥, 톰캣 레벨에서 돌고, 인터셉터는 스프링 MVC 기능이라 DispatcherServlet 안에서 컨트롤러 앞뒤로 돌아요. 그래서 필터는 요청·응답 객체를 감싸 바꿀 수 있고 정적 리소스까지 걸리지만 `@ControllerAdvice` 예외 처리 대상이 아니에요. 인터셉터는 어떤 핸들러가 처리하는지 알 수 있어요. 인증·인코딩·CORS는 필터, API 공통 로깅이나 실행 시간 측정은 인터셉터에 주로 둬요.

**꼬리질문**
- Q. AOP와는 어떻게 다른가요? → 필터·인터셉터는 HTTP 요청 단위, AOP는 빈 메서드 호출 단위예요. 트랜잭션처럼 서비스 메서드에 거는 건 AOP예요.
- Q. Spring Security는 필터인가요, 인터셉터인가요? → 서블릿 필터 체인에 붙어요. 공식 문서도 인터셉터는 경로 매칭이 어긋날 수 있어 보안 계층으로 적합하지 않다고 해요.
</details>

<details>
<summary>Q. 전역 예외 처리는 어떻게 하나요?</summary>

**답변(30초)** `@RestControllerAdvice` 클래스에 `@ExceptionHandler` 메서드를 모아 둬요. 예외가 나면 DispatcherServlet이 HandlerExceptionResolver 체인에 넘기고, 그중 `ExceptionHandlerExceptionResolver`가 맞는 `@ExceptionHandler`를 찾아 실행해요. 컨트롤러 안의 핸들러가 먼저고 전역 핸들러가 그다음이에요. 상태 코드를 직접 정하지 않으면 200이 나가니 `ResponseEntity`나 `@ResponseStatus`로 명시해야 해요.

**꼬리질문**
- Q. 필터에서 던진 예외도 잡히나요? → 아니요. 필터는 DispatcherServlet 바깥이라 톰캣의 `/error`로 가요.
- Q. 아무도 못 잡으면? → 톰캣이 `/error`로 다시 디스패치하고, 부트의 `BasicErrorController`가 기본 에러 응답을 줘요.
</details>

<details>
<summary>Q. HandlerMapping과 HandlerAdapter는 어떻게 다르고, 어댑터는 왜 필요한가요?</summary>

**답변(30초)** HandlerMapping은 "누가 처리할지 찾는" 역할이고, HandlerAdapter는 "찾은 걸 어떻게 실행할지" 맡는 역할이에요. 핸들러는 `@RequestMapping` 메서드, `HttpRequestHandler` 구현체, 함수형 엔드포인트처럼 모양이 여러 가지예요. 어댑터가 `supports()`로 실행 가능 여부를 답하고 `handle()`로 실행해 주니, DispatcherServlet은 핸들러 종류를 몰라도 돼요. 새 종류가 생겨도 어댑터만 추가하면 되는 어댑터 패턴이자 OCP 사례예요.

**꼬리질문**
- Q. 우리가 쓰는 `@GetMapping` 메서드는 어떤 어댑터가 실행하나요? → `RequestMappingHandlerAdapter`예요. 인자 준비, `@RequestBody` 변환, 반환값 처리도 여기서 해요.
</details>

<details>
<summary>Q. preHandle, postHandle, afterCompletion의 차이는? postHandle에서 헤더 추가가 안 되는 이유는?</summary>

**답변(30초)** preHandle은 핸들러 전에 불리고 `false`를 돌려주면 핸들러를 실행하지 않아요. postHandle은 핸들러 실행 후, afterCompletion은 요청이 완전히 끝난 뒤에 불려요. 그런데 `@ResponseBody`나 `ResponseEntity` 메서드는 HandlerAdapter 안에서 응답이 이미 써지고 커밋된 뒤에 postHandle이 불려서, 그때 헤더를 넣으면 늦어요. 그래서 응답을 바꾸려면 `ResponseBodyAdvice`나 필터를 써요.

**꼬리질문**
- Q. 예외가 나면 셋 중 무엇이 불리나요? → postHandle은 건너뛰고 afterCompletion은 항상 불려요. 그래서 정리 작업은 afterCompletion에 둬요.
</details>

<details>
<summary>Q. 톰캣 스레드 풀 기본 크기는? 요청이 몰리면 어떻게 되나요?</summary>

**답변(30초)** 스프링 부트 기본 톰캣 워커 스레드 최대는 200개이고, 요청 하나를 스레드 하나가 끝까지 처리해요. 200개가 모두 바쁘면 새 연결은 대기하고, 연결 수 한도(8192)와 OS 대기열(accept-count 100)까지 차면 연결이 거부되거나 타임아웃이 나요. 그래서 느린 외부 호출이 스레드를 오래 붙잡으면 전체 서비스가 멈춘 것처럼 보일 수 있어요.

**꼬리질문**
- Q. 스레드를 늘리면 해결되나요? → 일시적으로는 도움이 되지만 메모리와 컨텍스트 스위칭 비용이 늘고, 병목이 DB 커넥션 풀 같은 하류 자원으로 옮겨가요. 타임아웃과 격리가 먼저예요.
</details>

## 서술형 연습

<details>
<summary>상황: 모든 API 응답에 X-Request-Id 헤더를 넣으려고 인터셉터 postHandle에 코드를 넣었는데, @RestController 응답에 헤더가 붙지 않습니다.</summary>

**상황 파악**
코드는 실행되는데 결과가 응답에 반영되지 않아요. "실행 시점"이 문제일 가능성이 커요.

**원인 후보**
1. `@RestController`는 HandlerAdapter 안에서 HttpMessageConverter가 바디를 쓰고 응답을 커밋해요. postHandle은 그 **뒤**라서 헤더를 바꿔도 반영되지 않아요.
2. 인터셉터 경로 패턴에 해당 URL이 빠져 있을 수 있어요.
3. 예외가 난 요청이면 postHandle 자체가 안 불려요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 서블릿 필터에서 `chain.doFilter()` **전에** 헤더 설정 | 커밋 전이라 확실히 붙음, 예외 응답·정적 리소스에도 붙음, 같은 스레드라 MDC에 같이 넣기 좋음 | 모든 요청에 걸려서 필요 없는 요청에도 적용됨 |
| B. 인터셉터 `preHandle`에서 헤더 설정 | MVC 안이라 핸들러 정보 활용 가능 | 필터보다 늦게 시작해서 필터 단계 로그엔 ID가 없음 |
| C. `ResponseBodyAdvice` | 바디가 써지기 직전에 개입, 바디 수정도 가능 | 바디가 있는 MVC 응답에만 적용, 필터 단계 에러 응답엔 안 붙음 |

**내가 고를 방법**
A를 골라요. 요청 ID는 요청이 들어오는 가장 앞에서 만들어서 로그(MDC)와 응답 헤더에 같이 쓰는 게 목적에 맞아요. 요청 하나를 스레드 하나가 끝까지 처리하니까 필터에서 넣은 MDC 값이 컨트롤러·서비스 로그까지 이어져요. 요청이 끝나면 필터의 `finally`에서 MDC를 비워서 스레드가 재사용될 때 값이 섞이지 않게 해요.

**채점 포인트**: `@ResponseBody`는 어댑터 안에서 커밋, postHandle은 커밋 이후, 예외 시 postHandle 미호출, 필터/ResponseBodyAdvice 대안과 적용 범위 차이, thread-per-request와 MDC, MDC 정리.
</details>

<details>
<summary>상황: 외부 결제 API가 느려지자 결제와 상관없는 API까지 전부 응답하지 않습니다. 스레드 덤프를 보니 http-nio-8080-exec 스레드 200개가 모두 소켓 읽기에서 대기 중입니다.</summary>

**상황 파악**
결제 한 기능의 지연이 서비스 전체 장애로 번졌어요. 스레드 200개가 전부 같은 외부 호출에서 멈춰 있으니 **스레드 풀 고갈**이에요.

**원인 후보**
1. 스프링 MVC는 요청 하나당 톰캣 워커 스레드 하나를 쓰고, 기본 최대가 200개예요. 결제 요청이 스레드를 붙잡고 안 놓아요.
2. 외부 호출에 타임아웃이 없거나 너무 길어요.
3. 결제 호출과 일반 API가 같은 스레드 풀을 나눠 써서, 한쪽이 막히면 다른 쪽도 같이 막혀요. 스레드가 다 차면 새 요청은 처리되지 못한 채 쌓이고, 연결 한도(8192)와 OS 대기열(accept-count 100)까지 차면 거부·타임아웃돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 외부 호출에 연결·읽기 타임아웃, 서킷 브레이커 | 느린 호출이 스레드를 오래 못 잡음, 장애가 계속되면 바로 실패시켜 빨리 회복 | 타임아웃 값 조정이 필요, 실패 응답 처리 로직 필요 |
| B. 결제 호출을 별도 스레드 풀로 격리(벌크헤드) | 결제가 막혀도 다른 API 스레드는 살아 있음 | 풀 크기 설계와 비동기 처리 코드가 늘어남 |
| C. `threads.max` 증설 | 설정 한 줄로 당장 여유 생김 | 메모리·컨텍스트 스위칭 비용 증가, 근본 원인은 그대로, DB 커넥션 풀이 다음 병목 |
| D. 가상 스레드(`spring.threads.virtual.enabled=true`) | 기다리는 스레드 비용이 작아 많이 버팀 | 하류 자원(DB 커넥션, 외부 API 한도)이 병목으로 옮겨감, 도입 검증 필요 |

**내가 고를 방법**
당장은 A로 결제 호출에 짧은 타임아웃과 서킷 브레이커를 걸어 스레드가 묶이지 않게 해요. 이어서 B로 결제 호출을 별도 풀로 떼어 다른 API가 같이 쓰러지지 않게 해요. C나 D는 대기 시간을 늘려 줄 뿐 느린 호출 자체를 막지 못해서, A·B를 먼저 하고 부하 테스트로 필요할 때만 검토해요.

**채점 포인트**: thread-per-request, 톰캣 기본 200 스레드 고갈, accept-count 대기열, 타임아웃, 서킷 브레이커, 벌크헤드(격리), 스레드 증설의 한계, 커넥션 풀로 병목 이동.
</details>

<details>
<summary>상황: JWT 검증 실패 시 필터에서 예외를 던졌는데, @RestControllerAdvice에 만든 공통 에러 형식이 아니라 기본 에러 JSON이 나갑니다.</summary>

**상황 파악**
같은 "인증 실패"인데 응답 형식이 팀 규칙과 달라요. 예외가 어디서 났는지가 핵심이에요.

**원인 후보**
1. 필터는 DispatcherServlet **바깥**이라 HandlerExceptionResolver 체인을 안 거쳐요. 그래서 `@RestControllerAdvice`가 이 예외를 볼 기회가 없어요.
2. 처리되지 않은 예외가 톰캣으로 올라가 `/error`로 다시 디스패치되고, 부트의 `BasicErrorController`가 기본 JSON을 만들어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 필터 안에서 예외를 잡아 직접 응답 작성 | 단순하고 흐름이 명확 | 에러 형식 코드가 advice와 필터 두 곳에 중복 |
| B. Spring Security의 `AuthenticationEntryPoint`에서 응답 작성 | 보안 실패 처리의 정해진 자리, 401 처리가 일관됨 | Spring Security 구조를 알아야 하고, 역시 형식 코드가 따로 있음 |
| C. 필터에 `HandlerExceptionResolver`를 주입해 예외를 넘김 | 기존 `@RestControllerAdvice`를 그대로 재사용해 형식 통일 | 필터가 MVC 부품에 의존하게 됨, 동작을 아는 사람만 이해 |

**내가 고를 방법**
Spring Security를 쓰고 있다면 B를 골라요. 인증 실패는 보안 계층이 책임지는 게 자연스럽고, 응답 형식은 공통 에러 객체를 만드는 코드를 함께 써서 advice와 맞춰요. 직접 만든 필터라면 C로 advice를 재사용하는 것도 괜찮아요.

**채점 포인트**: 필터는 DispatcherServlet 바깥, `@ControllerAdvice`는 MVC 안의 예외만 처리, 톰캣 `/error` 재디스패치와 BasicErrorController, AuthenticationEntryPoint, 에러 형식 통일 방법.
</details>

## 필기 포인트

- 스프링 MVC는 **프론트 컨트롤러** 패턴, 그 입구는 `DispatcherServlet`.
- 핸들러를 **찾는** 건 HandlerMapping, **실행하는** 건 HandlerAdapter. 인터셉터 목록은 HandlerMapping이 같이 돌려줌.
- `@RestController` = `@Controller` + `@ResponseBody`. ViewResolver를 **거치지 않음**.
- 메시지 컨버터 선택: 읽기는 **Content-Type**, 쓰기는 **Accept**.
- `postHandle`은 예외 시 **호출 안 됨**, `afterCompletion`은 **항상** 호출.
- 필터는 서블릿 표준(컨테이너 레벨), 인터셉터는 스프링 MVC 레벨. 필터 예외는 `@ControllerAdvice`가 못 잡음.
- 부트 톰캣 기본: `threads.max` **200**, `accept-count` **100**, `max-connections` **8192**.
- `@Valid` 실패 기본 응답은 **400**.
