:::tip[한 줄 요약]
**N+1**은 목록을 1번 조회한 뒤, 결과 N개마다 연관 데이터를 1번씩 더 조회해서 SQL이 **1+N번** 나가는 문제예요. 지연 로딩이든 즉시 로딩이든 생기고, 연관은 전부 LAZY로 둔 뒤 필요한 곳에서만 **fetch join·@EntityGraph·batch size·DTO 조회**로 한 번에(또는 몇 번에) 가져와서 해결해요.
:::

:::note[처음이라면 여기까지]
① 목록을 한 번 가져온 뒤, 항목마다 연결된 데이터를 한 번씩 더 가져와서 DB에 SQL이 1+N번 나가는 문제예요.

② "필요할 때 가져오기"(지연 로딩)로 미뤄도 횟수는 그대로예요.

③ 해결은 처음부터 같이 가져오기(fetch join)나 묶어서 가져오기(batch size)예요.

④ 면접에선 질문 1·2·3번을 먼저 연습하세요.
:::

## 쉽게 이해하기

반 학생 30명의 부모님 연락처가 필요하다고 해 봐요. 먼저 교무실에서 "우리 반 명단"을 한 번 받아요(1번). 그런데 연락처는 명단에 없어서, 학생 한 명씩 행정실에 가서 "이 학생 부모님 번호요" 하고 30번 따로 물어봐요(N번). 총 31번 왕복이에요. 이게 **N+1**이에요.

처음부터 "명단이랑 부모님 연락처 같이 주세요"라고 한 번에 부탁하면 1번이면 끝나요. 이게 **fetch join**이에요. "30명 번호 한꺼번에 주세요"라고 묶어서 물어보면 2번이면 끝나요. 이게 **batch size**예요.

**지연 로딩**은 "연락처는 진짜 필요할 때 물어볼게요"라고 미뤄 두는 방식이에요. 미뤄 둔다고 왕복 횟수가 줄지는 않아요. 물어보는 시점만 늦어질 뿐이에요.

단, 실제로는 "왕복"이 DB로 보내는 **SQL 한 번**이에요. 한 번 한 번은 빨라도, 목록이 1000건이면 SQL이 1001번 나가서 응답이 눈에 띄게 느려져요.

## 제대로 알기

### 1. 즉시 로딩과 지연 로딩

엔티티끼리 연결된 걸 **연관관계**(association, 예: 회원이 속한 팀, 팀에 속한 회원들)라고 해요. 연관 데이터를 **언제** 가져올지 정하는 게 fetch 전략이에요. 연관관계 매핑 자체는 [연관관계 매핑](../jpa-relations/)에서 다뤄요.

- **즉시 로딩**(EAGER): 엔티티를 가져올 때 연관도 바로 같이 가져와요.
- **지연 로딩**(LAZY): 일단 가짜를 넣어 두고, 연관에 처음 접근할 때 가져와요.

JPA 표준 기본값은 이래요.

| 애너테이션 | 기본 fetch |
|---|---|
| `@ManyToOne` | EAGER |
| `@OneToOne` | EAGER |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

"**~ToOne은 즉시, ~ToMany는 지연**"으로 외우면 돼요.

### 2. 프록시: 지연 로딩의 가짜 객체

LAZY 연관에는 진짜 객체 대신 **대리 객체**가 들어가요.

- 단일 엔티티(예: `member.team`)에는 **Hibernate 프록시**가 들어가요. 클래스 이름을 찍어 보면 `Team$HibernateProxy` 같은 모양이에요.
- 컬렉션(예: `team.members`)에는 Hibernate가 만든 **래퍼 컬렉션**(`PersistentBag` 등)이 들어가요.

이 대리 객체는 getter나 `size()`로 **처음 내용을 건드리는 순간** SQL을 보내 자기를 채워요. 이걸 "초기화"라고 해요.

초기화하려면 **영속성 컨텍스트**(엔티티를 관리하는 1차 캐시 겸 작업 공간)가 열려 있어야 해요. 영속성 컨텍스트 자체는 [영속성 컨텍스트](../jpa-persistence-context/)에서 다뤄요. 여기서는 "닫힌 뒤엔 지연 로딩이 안 된다"만 기억하면 돼요.

### 3. N+1은 왜 생기나

N+1의 정체는 "**연관을 행마다 따로 SELECT하는 것**"이에요. Hibernate 문서도 연관마다 별도 SELECT로 읽는 방식을 흔히 N+1이라고 부른다고 설명해요.

**LAZY여도 생겨요.** 팀 3개를 조회하고 루프에서 `team.getMembers().size()`를 부르면, 팀마다 회원 조회 SQL이 하나씩 나가요.

```java
List<Team> teams = em.createQuery("select t from Team t", Team.class)
        .getResultList();               // SQL 1: 팀 목록
for (Team t : teams) {
    t.getMembers().size();              // 팀마다 SQL 1개씩 (3개)
}
// 합계 SQL 4개 = 1 + N(3)
```

**EAGER여도 JPQL에서는 생겨요.** JPQL(엔티티 대상으로 쓰는 JPA 쿼리 언어)은 쓴 그대로 SQL로 바뀌어요. `select m from Member m`은 회원 테이블만 조회하고, 그다음에 EAGER인 `team`을 채우려고 팀을 따로 조회해요. 서로 다른 팀이 3개면 SQL이 4개(회원 1 + 팀 3) 나가요.

반면 `em.find(Member.class, id)`처럼 id로 한 건을 찾을 때는 EAGER 연관을 조인 한 번으로 가져와요. 그래서 "EAGER로 바꾸면 해결된다"는 **틀린 말**이에요. 목록 조회에서는 추가 쿼리가 나중이 아니라 바로 나갈 뿐이고, 그 연관이 필요 없는 화면에서도 항상 끌려와요.

<Aside type="tip" title="실무 기본 규칙">
연관은 **전부 LAZY**로 두고, 필요한 화면에서만 한 번에 가져와요. `@ManyToOne`·`@OneToOne`은 기본이 EAGER라서 `fetch = FetchType.LAZY`를 **직접 적어야** 해요. Hibernate 가이드 예제도 이렇게 써요.
</Aside>

```java
@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)  // 기본 EAGER라 꼭 명시
    private Team team;
}
```

### 4. 해결 1: fetch join

JPQL에 `join fetch`를 쓰면, 연관의 LAZY 설정을 무시하고 **SQL 조인 한 번**으로 같이 가져와요.

```java
// SQL 1개: team join member
List<Team> teams = em.createQuery(
        "select t from Team t join fetch t.members", Team.class)
        .getResultList();
```

알아 둘 점이에요.

- `join fetch`는 **inner join**이에요. 회원이 한 명도 없는 팀은 결과에서 빠져요. 다 가져오려면 `left join fetch`를 써요.
- 팀 3개 × 회원 2명이면 SQL 결과 행은 6개예요. 같은 팀이 여러 줄에 걸쳐 나오는데, **Hibernate 6부터는 중복 부모 엔티티를 자동으로 제거**해서 팀 3개가 돌아와요. Hibernate 5까지는 `distinct`를 붙여야 했어요. 옛 블로그 글에서 "DISTINCT 필수"라고 하는 건 이 때문이에요. Spring Boot 3는 Hibernate 6 이상을 써요.

### 5. 해결 2: @EntityGraph

**엔티티 그래프**(entity graph)는 "이 조회에서는 이 연관까지 같이 가져와"를 JPQL 밖에서 지정하는 JPA 표준 기능이에요(JPA 2.1). Spring Data JPA에서는 리포지토리 메서드에 붙여요.

```java
public interface TeamRepository extends JpaRepository<Team, Long> {
    @EntityGraph(attributePaths = {"members"})  // members를 같이 로딩
    List<Team> findAll();
}
```

- 이름 붙인 `@NamedEntityGraph`를 엔티티에 정의하고 `@EntityGraph("이름")`으로 참조할 수도 있어요.
- 엔티티 그래프는 **left outer join** SQL 1개로 나가요. 그래서 회원이 없는 팀도 결과에 남아요.
- `type`은 두 가지예요.

| type | 그래프에 적은 속성 | 적지 않은 속성 |
|---|---|---|
| `FETCH` | 즉시 로딩 | LAZY로 취급 |
| `LOAD` | 즉시 로딩 | 매핑에 적힌 기본값을 따름 |

**fetch join vs @EntityGraph**

| 구분 | fetch join | @EntityGraph |
|---|---|---|
| 쓰는 곳 | JPQL 문자열 안 | 리포지토리 메서드 애너테이션 |
| 조인 종류 | `join fetch`는 inner, `left join fetch`는 outer | outer join |
| 장점 | 조건·조인을 자유롭게 씀 | JPQL 없이 메서드에 애너테이션만 붙임 |

### 6. 해결 3: batch size

**배치 페치**(batch fetching)는 조인 대신, 아직 안 채워진 프록시·컬렉션 여러 개를 **`IN (?, ?, ...)` 한 번**으로 묶어 채우는 방식이에요.

- 필드나 엔티티 클래스에 `@BatchSize(size = 100)`
- 또는 전역 설정 `hibernate.default_batch_fetch_size`. Spring Boot에서는 `spring.jpa.properties.hibernate.default_batch_fetch_size=100`처럼 넘겨요.
- 전역 설정은 **기본값이 없어요.** 안 켜면 `@BatchSize`를 붙인 곳만 배치로 읽어요.

팀 3개에서 루프를 돌리면 SQL이 2개(팀 1 + `member where team_id in (...)` 1)로 줄어요. 정확히는 **1+N이 1+⌈N/size⌉로** 줄어요. 팀이 1000개이고 size가 100이면 1 + 10 = 11번이에요. 쿼리가 1개가 되는 건 아니에요.

### 7. 해결 4: DTO로 직접 조회

엔티티 대신 화면에 필요한 컬럼만 담은 **DTO**(Data Transfer Object, 데이터를 나르기만 하는 객체)로 바로 받는 방법이에요.

```java
// JPQL 생성자 표현식: 필요한 컬럼만 SELECT
List<TeamDto> list = em.createQuery(
    "select new com.example.TeamDto(t.id, t.name) from Team t", TeamDto.class)
    .getResultList();
```

Spring Data JPA의 **인터페이스 프로젝션**으로도 같은 일을 할 수 있어요. 엔티티가 아니라서 프록시도, 지연 로딩도 없어요. 대신 영속성 컨텍스트가 관리하지 않으니 값을 바꿔도 **변경 감지**(dirty checking)로 UPDATE가 나가지 않아요. 조회 전용 화면에 잘 맞아요.

### 8. 해결 방법 한눈에 비교

| 방법 | SQL 수(팀 N개) | 장점 | 주의 |
|---|---|---|---|
| 아무것도 안 함 | 1 + N | - | N이 크면 매우 느림 |
| fetch join | 1 | 가장 확실하게 1번 | 컬렉션이면 페이징 문제, 컬렉션 2개 동시 불가 |
| @EntityGraph | 1 | JPQL 없이 메서드에 붙임 | outer join 고정, 컬렉션이면 fetch join과 같은 페이징 문제 |
| batch size | 1 + ⌈N/size⌉ | 페이징과 같이 써도 안전, 설정 한 줄 | 쿼리가 1개는 아님 |
| DTO 조회 | 1 | 필요한 컬럼만, 지연 로딩 없음 | 변경 감지 안 됨, 화면마다 DTO 필요 |

### 심화: 9. fetch join과 페이징을 같이 쓰면

**페이징**(paging, 목록을 10개씩 끊어 가져오기)은 SQL의 `LIMIT`/`OFFSET`으로 해요. 그런데 **컬렉션(일대다)을 fetch join**하면 행이 부모 수보다 많아져요. 팀 3개 × 회원 2명이면 6행이라서, DB에서 "처음 2행"을 자르면 "팀 2개"가 아니라 "팀 1개와 회원 2명"이 돼 버려요.

그래서 흔히 알려진 동작(Hibernate 5~6, Spring Boot 3.x 기준)은 이래요.

- Hibernate가 SQL에 LIMIT를 넣지 않고 **전부 읽어 온 뒤 메모리에서 잘라요.**
- 로그에 경고 `HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory`가 찍혀요.
- 데이터가 많으면 메모리를 크게 쓰고 느려져요. Hibernate 문서도 성능이 아주 나빠질 수 있으니 피하라고 해요.
- `hibernate.query.fail_on_pagination_over_collection_fetch=true`(5.2.13부터, 기본 false)로 켜면 이 경우 경고 대신 **예외**를 던져서 실수를 빨리 잡을 수 있어요.

<Aside type="caution" title="버전에 따라 다를 수 있어요">
위 동작은 널리 알려진 Hibernate 5~6 기준이에요. 최신 Hibernate에서는 처리 방식이 달라졌을 수 있으니, 쓰는 버전에서 실제 SQL과 경고 로그를 직접 확인해요.
</Aside>

**페이징이 필요할 때 실무에서 흔히 쓰는 조합**
- **ToOne 관계만** fetch join해요. 다대일은 행 수가 안 늘어나서 LIMIT가 정상으로 걸려요.
- **컬렉션은 LAZY + batch size**로 채워요.
- 또는 **ID만 먼저 페이징 조회**하고, `where t.id in :ids` + fetch join으로 다시 가져와요.

### 심화: 10. 컬렉션 두 개를 동시에 fetch join하면: MultipleBagFetchException

순서도 인덱스도 없는 `List` 컬렉션을 Hibernate는 **bag**(가방, 중복 허용·순서 없음)이라고 불러요. bag 두 개를 한 쿼리에서 같이 fetch join하면 Hibernate가 아예 거부해요.

```
MultipleBagFetchException: cannot simultaneously fetch multiple bags:
[Team.members, Team.tags]
```

이유는 두 일대다를 동시에 조인하면 행이 **곱**으로 불어나기 때문이에요(**카테시안 곱**, 회원 2명 × 태그 3개 = 팀 하나에 6행). bag은 어느 행이 진짜 중복인지 구별할 수 없어요. JPA API로 호출하면 `IllegalArgumentException`으로 감싸져 나오고, SQL은 하나도 안 나가요.

해결은 두 가지예요.
- **하나만 fetch join**하고 나머지는 batch size로 채워요. 보통 이쪽을 권해요.
- `List`를 `Set`으로 바꿔요. 예외는 사라지지만 **행 폭증(카테시안 곱)은 그대로** 남아요.

### 심화: 11. LazyInitializationException

영속성 컨텍스트가 **닫힌 뒤에** 초기화 안 된 프록시·컬렉션을 건드리면 나는 예외예요.

```
Cannot lazily initialize collection of role 'Team.members'
with key '1' (no session)
```

보통 서비스 메서드(`@Transactional`)가 끝난 뒤, 즉 **컨트롤러나 JSON 직렬화** 단계에서 터져요. 엔티티를 그대로 응답으로 내보내면 JSON 변환기가 getter를 부르다가 지연 로딩을 시도하기 때문이에요.

해결은 "서비스 안에서 필요한 건 다 로딩하고 나온다"예요. fetch join이나 엔티티 그래프로 가져오고, 서비스에서 DTO로 바꿔 반환해요. 트랜잭션 범위는 [@Transactional](../transactional/)에서 다뤄요.

### 심화: 12. OSIV(Open Session In View)

**OSIV**(Open Session/EntityManager In View)는 영속성 컨텍스트를 **요청 시작부터 응답 끝까지** 열어 두는 기능이에요. 그래서 컨트롤러나 뷰에서도 지연 로딩이 돼요.

- Spring Boot는 웹 앱이면 **기본으로 켜요**(`OpenEntityManagerInViewInterceptor` 등록). 설정을 안 적으면 켜진 것으로 동작해요.
- 명시하지 않으면 기동할 때 `spring.jpa.open-in-view is enabled by default ...`로 시작하는 WARN 로그가 찍혀요(Boot 2.0부터).
- 끄려면 `spring.jpa.open-in-view=false`.

| | OSIV 켬(기본) | OSIV 끔 |
|---|---|---|
| 지연 로딩 가능 범위 | 요청 끝(컨트롤러·뷰·JSON 직렬화)까지 | 트랜잭션 안에서만 |
| DB 커넥션 | 요청 끝까지 붙잡고 있을 수 있음 | 트랜잭션 끝나면 반납 |
| 장점 | LazyInitializationException이 잘 안 남 | 커넥션을 짧게 써서 트래픽에 강함 |
| 단점 | 트래픽이 몰리면 **커넥션 풀 고갈** 위험, 컨트롤러에서 숨은 N+1이 나가도 눈치채기 어려움 | 필요한 연관을 서비스 안에서 전부 로딩해야 함 |

커넥션을 오래 쥐는 게 왜 위험한지는 [@Transactional의 외부 API 호출 부분](../transactional/)과 같은 이야기예요.

### 13. N+1을 어떻게 찾아내나

- 개발 환경에서 SQL 로그를 켜고 목록 API를 한 번 불러 봐요. **모양이 같고 id만 다른 SELECT**가 줄줄이 나오면 N+1이에요.
- "목록 1건짜리 API에서 SQL이 몇 개 나가는지" 세는 습관이 가장 확실해요.

## 면접 질문

<details>
<summary>Q. N+1 문제가 뭔가요? 왜 생기나요?</summary>

**답변(30초)** 목록을 1번 조회한 뒤, 결과 N개마다 연관 데이터를 1번씩 더 조회해서 SQL이 1+N번 나가는 문제예요. 원인은 연관을 행마다 따로 SELECT하기 때문이에요. 예를 들어 팀 3개를 조회하고 루프에서 각 팀의 회원 목록에 접근하면 팀 조회 1번에 회원 조회 3번, 총 4번이 나가요. 팀이 1000개면 1001번이라 응답이 크게 느려져요.

**꼬리질문**
- Q. 로그에서 어떻게 알아보나요? → id만 다르고 모양이 같은 SELECT가 반복해서 찍히면 N+1이에요.
- Q. 쿼리 하나하나는 빠른데 왜 문제죠? → SQL마다 DB 왕복 비용이 들고, N이 데이터 양에 비례해 커지기 때문이에요.
</details>

<details>
<summary>Q. 지연 로딩을 쓰면 N+1이 안 생기나요? EAGER로 바꾸면요?</summary>

**답변(30초)** 둘 다 생겨요. 지연 로딩은 쿼리 시점을 "처음 접근할 때"로 미룰 뿐이라, 루프에서 연관에 접근하면 행마다 SQL이 나가요. EAGER도 JPQL 목록 조회에서는 JPQL에 적은 테이블만 먼저 조회한 뒤 연관을 채우려고 추가 SELECT를 바로 보내요. 그래서 실무에서는 연관을 전부 LAZY로 두고, 필요한 화면에서만 fetch join이나 엔티티 그래프로 한 번에 가져와요.

**꼬리질문**
- Q. 왜 `@ManyToOne`에 `fetch = LAZY`를 직접 적나요? → ToOne 관계는 JPA 기본값이 EAGER라서, 안 적으면 필요 없는 곳에서도 항상 끌려오고 N+1이 숨어서 나가요.
- Q. `em.find()`로 한 건 찾을 때 EAGER는요? → id로 한 건을 찾을 때는 조인 한 번으로 같이 가져와요. 문제는 JPQL 목록 조회예요.
</details>

<details>
<summary>Q. N+1 해결 방법을 아는 대로 말하고 장단점을 비교해 보세요.</summary>

**답변(30초)** 네 가지를 써요. fetch join은 JPQL에 `join fetch`를 써서 SQL 1번으로 가져오는데, 컬렉션이면 페이징과 같이 못 쓰고 컬렉션 두 개를 동시에 못 가져와요. `@EntityGraph`는 같은 일을 애너테이션으로 하고 outer join으로 나가요. batch size는 `IN` 절로 묶어 1+N을 1+N/size로 줄이고 페이징과도 잘 맞아요. DTO 조회는 필요한 컬럼만 가져와 지연 로딩 자체가 없지만 변경 감지가 안 돼요.

**꼬리질문**
- Q. 하나만 고르라면? → 기본은 LAZY + 전역 batch size로 깔아 두고, 성능이 중요한 화면은 fetch join이나 DTO 조회로 따로 최적화해요.
- Q. batch size로 쿼리를 1개로 만들 수 있나요? → 아니요. 1+⌈N/size⌉개예요. 1개가 필요하면 fetch join이에요.
</details>

<details>
<summary>Q. fetch join과 @EntityGraph는 뭐가 다른가요?</summary>

**답변(30초)** 둘 다 연관을 조인으로 한 번에 가져와 N+1을 없앤다는 점은 같아요. fetch join은 JPQL 문자열 안에 쓰고, `join fetch`는 inner join이라 연관이 없는 부모가 빠지며 `left join fetch`로 바꿀 수 있어요. `@EntityGraph`는 리포지토리 메서드에 애너테이션으로 붙이고 left outer join으로 나가요. JPQL을 직접 안 써도 된다는 게 장점이에요.

**꼬리질문**
- Q. FETCH 그래프와 LOAD 그래프 차이는? → 둘 다 적은 속성은 즉시 로딩해요. FETCH는 나머지를 LAZY로, LOAD는 나머지를 매핑 기본값대로 다뤄요.
- Q. 컬렉션 fetch join 결과가 중복되면 DISTINCT가 필요한가요? → Hibernate 6부터는 중복 부모를 자동으로 없애서 필요 없어요. 5까지는 필요했어요.
</details>

<details>
<summary>Q. 컬렉션을 fetch join하면서 페이징하면 어떻게 되나요?</summary>

**답변(30초)** 일대다를 조인하면 행이 부모 수보다 많아져서, DB에서 LIMIT로 자르면 부모 기준 페이징이 안 맞아요. 그래서 흔히 알려진 Hibernate 5~6 동작은 LIMIT 없이 전부 읽어 온 뒤 메모리에서 자르고 `HHH90003004` 경고를 남기는 거예요. 데이터가 많으면 메모리가 터질 수 있어요. 버전에 따라 동작이 다를 수 있으니 실제 SQL을 확인하고, 보통은 ToOne만 fetch join하고 컬렉션은 batch size로 채워요.

**꼬리질문**
- Q. 실수를 미리 막을 방법은? → `hibernate.query.fail_on_pagination_over_collection_fetch=true`로 켜면 이 경우 예외를 던져요.
- Q. ToOne fetch join은 페이징해도 되나요? → 다대일은 행 수가 안 늘어나서 괜찮아요.
</details>

<details>
<summary>Q. 컬렉션 두 개를 한 번에 fetch join하면요?</summary>

**답변(30초)** 둘 다 `List`면 `MultipleBagFetchException`이 나요. 두 일대다를 동시에 조인하면 행이 곱으로 불어나는데, 순서 없는 `List`인 bag은 진짜 중복을 구별할 수 없어서 Hibernate가 거부해요. 하나만 fetch join하고 나머지는 batch size로 채우는 게 보통이에요. `Set`으로 바꾸면 예외는 사라지지만 행 폭증은 그대로라서 근본 해결은 아니에요.

**꼬리질문**
- Q. 카테시안 곱이 뭐죠? → 두 집합의 모든 조합이에요. 회원 2명 × 태그 3개면 팀 하나에 6행이 나와요.
</details>

<details>
<summary>Q. LazyInitializationException은 언제 나고 어떻게 해결하나요?</summary>

**답변(30초)** 영속성 컨텍스트가 닫힌 뒤에 초기화 안 된 프록시나 컬렉션에 접근하면 나요. 보통 서비스 트랜잭션이 끝난 뒤 컨트롤러나 JSON 직렬화에서 엔티티의 LAZY 연관을 건드릴 때예요. 해결은 서비스 안에서 fetch join이나 엔티티 그래프로 필요한 데이터를 미리 가져오고, 엔티티 대신 DTO로 바꿔 반환하는 거예요. OSIV를 켜면 증상은 사라지지만 커넥션을 오래 쥐는 대가가 있어요.

**꼬리질문**
- Q. 프록시가 뭔가요? → 지연 로딩 대상 자리에 진짜 객체 대신 넣어 두는 대리 객체예요. 처음 내용을 건드릴 때 SQL을 보내 자기를 채워요.
</details>

<details>
<summary>Q. OSIV가 뭐고, 켜 두는 게 좋나요?</summary>

**답변(30초)** 영속성 컨텍스트를 요청 시작부터 응답 끝까지 열어 두는 기능이고, Spring Boot 웹 앱은 기본으로 켜져 있어요. 켜면 컨트롤러와 뷰에서도 지연 로딩이 돼 편하지만, DB 커넥션을 요청 끝까지 쥘 수 있어 트래픽이 몰리면 커넥션 풀이 고갈될 수 있고 숨은 N+1도 찾기 어려워요. 그래서 트래픽이 큰 API 서버는 `spring.jpa.open-in-view=false`로 끄고 서비스에서 필요한 데이터를 다 로딩해 DTO로 넘기는 편이에요.

**꼬리질문**
- Q. 기본값이 켜짐인지 어떻게 알 수 있나요? → 설정을 명시하지 않으면 기동할 때 "open-in-view is enabled by default"라는 WARN 로그가 찍혀요.
- Q. 끄면 무엇이 불편해지나요? → 컨트롤러에서 LAZY 연관을 쓰면 LazyInitializationException이 나서, 서비스에서 미리 로딩하는 코드가 늘어나요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 목록 API(한 페이지 20건, 주문마다 회원·배송·주문상품 목록 표시)의 응답이 1초가 넘게 걸립니다. SQL 로그에 모양이 같은 SELECT가 수십 개 찍혀 있습니다.</summary>

**상황 파악**
모양이 같고 id만 다른 SELECT가 반복되면 전형적인 N+1이에요. 주문 20건을 1번 조회한 뒤, 주문마다 회원·배송·주문상품을 따로 조회해서 1 + 20 × 3 = 61번 가까이 나갔을 수 있어요. 페이징은 유지해야 해요.

**원인 후보**
1. 회원·배송(ToOne)이 LAZY이고, 응답을 만들면서 주문마다 getter를 불러 N+1이 났어요.
2. ToOne이 기본값 EAGER로 남아 있어 JPQL 목록 조회 직후 추가 SELECT가 바로 나갔어요.
3. 주문상품(컬렉션)도 주문마다 따로 조회됐어요. 그 안의 상품 엔티티까지 건드리면 더 늘어나요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 회원·배송만 fetch join + 주문상품은 LAZY + batch size | 페이징이 DB에서 정상으로 걸림. SQL이 주문 1 + 주문상품 IN 1 정도로 줄어듦 | 쿼리가 1개는 아님. batch size 설정 필요 |
| B. 주문상품까지 모두 fetch join | 쿼리 수가 가장 적음 | 컬렉션 fetch join이라 페이징이 메모리에서 일어나 위험. 컬렉션이 둘 이상이면 MultipleBagFetchException |
| C. 화면 전용 DTO 조회 | 필요한 컬럼만 가져와 가장 가벼움. 지연 로딩 없음 | 쿼리·DTO 코드가 늘고, 컬렉션은 결국 따로 조회해 조립해야 함 |

**내가 고를 방법**
A를 골라요. 페이징을 지키면서 쿼리 수를 상수 수준으로 줄이는 가장 무난한 조합이에요. 먼저 모든 ToOne에 `fetch = LAZY`를 명시하고, 전역 `default_batch_fetch_size`를 깔아 둬요. 그래도 느리면 이 화면만 C로 바꿔요. 바꾼 뒤 SQL 로그로 개수가 실제로 줄었는지 확인해요.

**채점 포인트**: N+1 진단(같은 모양 SELECT 반복), SQL 개수 추정, ToOne은 fetch join·컬렉션은 batch size, 컬렉션 fetch join과 페이징 충돌, LAZY 명시, 해결책 2개 이상의 트레이드오프, 적용 후 SQL 개수 검증.
</details>

<details>
<summary>상황: 게시글 목록 페이징 API에 댓글을 join fetch로 붙였더니 쿼리 수는 1개로 줄었는데, 서버 메모리 사용량이 급증했고 로그에 HHH90003004 경고가 찍힙니다.</summary>

**상황 파악**
쿼리 수는 줄었지만 메모리가 늘었어요. 경고 내용이 "컬렉션 fetch에 페이징이 지정돼 메모리에서 적용한다"는 뜻이라, DB가 아닌 애플리케이션에서 페이징하고 있다는 신호예요.

**원인 후보**
1. **컬렉션 fetch join + 페이징**: 게시글 × 댓글로 행이 불어나서 Hibernate가 SQL에 LIMIT를 넣지 않고, 조건에 맞는 게시글·댓글을 전부 읽은 뒤 메모리에서 잘랐어요. 게시글이 많을수록 메모리가 커져요.
2. 정렬 조건이 없거나 넓어서 읽어 오는 범위가 더 커졌을 수도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 댓글 fetch join 제거 + LAZY + batch size | 게시글은 DB에서 LIMIT로 정상 페이징. 댓글은 IN으로 묶어 1~2번에 채움 | 쿼리가 2개 이상이 됨 |
| B. ID 먼저 페이징 → `where id in :ids` + 댓글 fetch join | 페이징 정확, 댓글은 한 번에 가져옴 | 쿼리 2번, 코드가 조금 복잡함 |
| C. 목록에는 댓글 수만 DTO로 내려주고 댓글은 상세에서 조회 | 목록이 가장 가벼움 | 화면·API 요구사항을 바꿔야 함 |

**내가 고를 방법**
A를 골라요. 설정 위주라 바꿀 코드가 적고 페이징이 DB에서 정확히 걸려요. 재발을 막으려고 `hibernate.query.fail_on_pagination_over_collection_fetch=true`를 켜서, 같은 실수가 생기면 경고 대신 예외로 바로 드러나게 해요. 쓰는 Hibernate 버전에서 실제로 어떤 SQL이 나가는지도 로그로 확인해요. 버전에 따라 처리 방식이 다를 수 있기 때문이에요.

**채점 포인트**: 컬렉션 fetch join은 행 수 증가, 메모리 페이징과 HHH90003004, ToOne과 컬렉션 구분, batch size, ID 먼저 페이징, fail_on_pagination 설정, 버전 차이 확인.
</details>

<details>
<summary>상황: 트래픽 피크 때 HikariCP "Connection is not available" 타임아웃이 쏟아집니다. OSIV는 기본값(켜짐)이고, 컨트롤러에서 서비스 호출 뒤 외부 추천 API를 부르고 엔티티를 그대로 JSON으로 반환합니다.</summary>

**상황 파악**
커넥션 풀 고갈이에요. 쿼리 자체보다 "커넥션을 쥐고 있는 시간"이 길어진 게 의심돼요. OSIV가 켜져 있어 요청 끝까지 커넥션을 쥘 수 있는 구조예요.

**원인 후보**
1. **OSIV + 컨트롤러의 외부 API 호출**: 영속성 컨텍스트가 응답 끝까지 열려 있고, 이미 커넥션을 얻은 상태에서 외부 API를 기다리는 동안 커넥션이 묶여 있어요.
2. **숨은 N+1**: 엔티티를 그대로 JSON으로 바꾸면서 LAZY 연관에 접근해, 컨트롤러 단계에서 추가 SQL이 줄줄이 나가 커넥션 점유가 더 길어져요.
3. 외부 API 타임아웃이 없거나 길어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `spring.jpa.open-in-view=false` + 서비스에서 fetch join으로 로딩 후 DTO 반환 | 커넥션을 트랜잭션 동안만 써서 근본 해결. 숨은 N+1도 사라짐 | 컨트롤러·뷰에서 지연 로딩하던 곳에 LazyInitializationException이 나서 전부 고쳐야 함 |
| B. OSIV는 유지하고 외부 API 타임아웃 설정 + 풀 크기 증설 | 바로 적용 가능 | 구조 문제는 남음. 풀을 키우면 DB 부하만 늘 수 있음 |

**내가 고를 방법**
B로 당장 피해를 줄이고, A로 구조를 고쳐요. 끄기 전에 테스트로 LazyInitializationException이 나는 곳을 찾아, 서비스에서 필요한 연관을 fetch join이나 DTO 조회로 가져오게 바꿔요. 엔티티를 응답으로 직접 내보내지 않는 규칙도 함께 세워요.

**채점 포인트**: OSIV 기본 켜짐, 커넥션 점유 시간, 커넥션 풀 고갈, 엔티티 직렬화 중 숨은 N+1, OSIV 끄면 LazyInitializationException, DTO 반환, 외부 API 타임아웃, 해결책 2개 이상의 트레이드오프.
</details>

## 필기 포인트

- 기본 fetch: `@ManyToOne`·`@OneToOne` = EAGER, `@OneToMany`·`@ManyToMany` = LAZY.
- N+1 = 1(목록) + N(행마다 연관 조회). LAZY·EAGER 둘 다 생김.
- EAGER는 `em.find()`에선 조인, JPQL 목록에선 추가 SELECT.
- `join fetch`는 inner join, `left join fetch`는 outer join. `@EntityGraph`는 outer join.
- Hibernate 6+: fetch join 중복 부모 자동 제거, DISTINCT 불필요.
- batch size: `IN`으로 묶어 1 + ⌈N/size⌉. 전역 기본값 없음.
- 컬렉션 fetch join + 페이징: (흔히 알려진 동작) 메모리 페이징 + `HHH90003004` 경고.
- bag(`List`) 두 개 동시 fetch join → `MultipleBagFetchException`.
- 세션 닫힌 뒤 지연 로딩 → `LazyInitializationException`.
- Spring Boot OSIV 기본 켜짐, 끄려면 `spring.jpa.open-in-view=false`.
