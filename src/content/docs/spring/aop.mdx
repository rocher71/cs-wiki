:::tip[한 줄 요약]
AOP(관점 지향 프로그래밍)는 로깅·트랜잭션·보안처럼 여러 클래스에 반복되는 **횡단 관심사**를 핵심 로직에서 떼어 **Aspect** 하나에 모으는 방법이에요. "어디에(Pointcut)" "언제·무엇을(Advice)" 끼울지 선언하면, 스프링이 **런타임에 프록시**를 만들어 스프링 빈의 메서드 실행 앞뒤에 그 코드를 끼워 넣어요.
:::

## 쉽게 이해하기

아파트 모든 집에 "외출할 때 가스 잠그기, 문 잠그기"를 집주인이 매번 직접 한다고 해 볼게요. 집마다 같은 일을 반복하고, 깜빡하는 집도 생겨요.

그래서 관리실이 규칙을 하나 정해요. "**어느 집이든**(어디에) **나갈 때**(언제) **가스·문을 점검한다**(무엇을)." 집주인은 자기 생활(핵심 로직)만 하고, 공통 점검은 관리실이 알아서 끼워 넣어요. 이 규칙 묶음이 **Aspect**예요.

관리실 직원은 현관 앞에 서 있다가 드나드는 순간을 가로채요. 스프링에서 이 직원 역할을 하는 게 **프록시**(진짜 객체 앞에 선 대리 객체)예요.

단, 실제로는 관리실이 집 **안**에서 일어나는 일은 못 봐요. 스프링 AOP는 프록시를 통과하는 **바깥에서 들어온 메서드 호출**만 가로채고, 객체가 자기 메서드를 직접 부르는 건 놓쳐요.

## 제대로 알기

### 1. 왜 AOP가 필요한가

서비스 메서드마다 이런 코드가 복붙돼 있다고 해 볼게요.

```java
public void order(long id) {
    long start = System.currentTimeMillis();   // 공통: 시간 측정 시작
    // ... 주문 핵심 로직 ...
    log.info("걸린 시간 {}ms", System.currentTimeMillis() - start); // 공통
}
```

이렇게 여러 기능에 가로로 걸쳐 반복되는 일을 **횡단 관심사**(cross-cutting concern)라고 해요. 로깅, 실행 시간 측정, 트랜잭션, 권한 검사가 대표예요. 복붙하면 바꿀 때 전부 찾아 고쳐야 하고, 핵심 로직이 잘 안 보여요.

AOP는 이 공통 코드를 **Aspect**라는 한 클래스로 옮겨요. 그러면 서비스에는 핵심 로직만 남아요. DI가 "객체를 넣어 주는 것"이라면, AOP는 "로직을 끼워 넣어 주는 것"이에요.

### 2. 용어 다섯 개

| 용어 | 한 줄 뜻 | 아파트 비유 |
|---|---|---|
| **JoinPoint** | 공통 코드를 끼울 수 *있는* 지점. 스프링 AOP에서는 항상 **메서드 실행** | 모든 집의 모든 현관문 |
| **Pointcut** | JoinPoint 중 실제로 적용할 곳을 *고르는* 조건 (어디에) | "101동만" 같은 조건 |
| **Advice** | 그 지점에서 할 일과 시점 (언제 + 무엇을) | "나갈 때 가스 점검" |
| **Aspect** | Advice와 Pointcut을 묶은 모듈. `@Aspect` 클래스 | 관리실 규칙집 |
| **Advisor** | 스프링 고유 용어. Advice 1개 + Pointcut 1개 | 규칙 한 줄 |

여기에 세 가지가 더 나와요.
- **Target**(타깃): Advice가 적용되는 진짜 객체예요.
- **AOP 프록시**: 타깃을 감싼 대리 객체예요. JDK 동적 프록시 또는 CGLIB으로 만들어요.
- **위빙**(Weaving, 엮기): Aspect를 타깃에 연결하는 일이에요. 컴파일 시점, 클래스 로드 시점, 런타임에 할 수 있는데 **스프링 AOP는 런타임 위빙**이에요.

한 줄로 묶으면 **Aspect = 어디에(Pointcut) + 언제·무엇을(Advice)** 이에요. JoinPoint와 Pointcut이 헷갈리면 "후보 전체"와 "그중 고른 것"으로 기억하면 돼요.

프록시를 어떻게 만드는지(JDK 동적 프록시와 CGLIB 차이, Boot는 CGLIB이 기본)는 [구조 패턴: 프록시](../../oop/patterns-structural/)에서 다뤄요.

### 3. 어드바이스 5종

| 애너테이션 | 언제 실행 | 기억할 점 |
|---|---|---|
| `@Before` | 메서드 실행 전 | 예외를 던지지 않는 한 실행을 막을 수 없어요 |
| `@AfterReturning` | **정상** 반환 후 | `returning`으로 반환값을 받아 볼 수 있지만, 다른 객체로 바꿔치기는 못해요 |
| `@AfterThrowing` | **예외**로 끝났을 때 | `throwing`으로 예외를 받아요. 예외를 삼키지 못하고 계속 전파돼요 |
| `@After` | 어떻게 끝나든 | `finally`처럼 정상·예외 둘 다 실행. 자원 정리에 써요 |
| `@Around` | 전후를 감쌈 | 가장 강력해요. 실행할지, 언제, 몇 번 할지 정해요 |

`@Around`는 규칙이 있어요.
- 첫 파라미터는 `ProceedingJoinPoint`, 반환형은 `Object`로 해요.
- 본문에서 **`proceed()`를 불러야** 진짜 메서드가 실행돼요. 안 부르면 원본이 아예 안 돌아요.
- Around가 돌려준 값이 호출자가 받는 값이에요. 반환형을 `void`로 하면 호출자는 늘 `null`을 받아요.

```java
@Aspect
@Component   // @Aspect만으로는 빈 등록이 안 돼요
public class TimingAspect {
    @Around("@annotation(com.example.LogExecutionTime)")
    public Object measure(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();            // 진짜 메서드 실행, 결과를 그대로 반환
        } finally {                          // 예외가 나도 시간은 남김
            log.info("{} {}ms", pjp.getSignature(),
                     (System.nanoTime() - start) / 1_000_000);
        }
    }
}
```

<Aside type="tip" title="가장 약한 어드바이스를 고르세요">
스프링 공식 문서의 권장이에요. 반환값을 보고 캐시만 갱신하면 되는 일이면 `@Around`보다 `@AfterReturning`이 나아요. 더 단순하고, `proceed()`를 빠뜨리는 같은 실수가 생길 여지가 없어요.
</Aside>

### 4. 실행 순서

**한 Aspect 안**에서 종류별 우선순위는 `@Around` > `@Before` > `@After` > `@AfterReturning` > `@AfterThrowing` 순이에요. 다만 `@After`는 실제로는 같은 Aspect의 `@AfterReturning`/`@AfterThrowing` **뒤에** 실행돼요. 그래서 체감 순서는 이래요.

- 정상: Around(proceed 전) → Before → **진짜 메서드** → AfterReturning → After → Around(proceed 후)
- 예외: Around(proceed 전) → Before → **진짜 메서드** → AfterThrowing → After → Around가 proceed에서 예외를 받음

같은 종류 어드바이스가 한 Aspect에 두 개 있으면 둘의 순서는 **정해져 있지 않아요**. 하나로 합치거나 Aspect를 나눠요.

**Aspect끼리**는 **양파 껍질**처럼 동작해요. 우선순위가 높은 Aspect가 들어갈 때 먼저, 나올 때 마지막에 실행돼요.
- 우선순위는 Aspect **클래스**에 `@Order`를 붙이거나 `Ordered`를 구현해서 정해요. 어드바이스 메서드에 붙이는 게 아니에요.
- **숫자가 작을수록 우선순위가 높아요**(바깥 껍질).
- 순서를 안 정한 두 Aspect가 같은 메서드에 걸리면 실행 순서는 **정의되지 않아요**. 등록 순이나 이름 순이 아니에요.
- `@Transactional`의 트랜잭션 어드바이스도 Aspect의 하나이고, 기본 순서는 `Ordered.LOWEST_PRECEDENCE`(우선순위 가장 낮음 = 가장 안쪽)예요.

### 5. 포인트컷 표현식 읽기

스프링은 **AspectJ**(자바용 본격 AOP 도구)의 포인트컷 문법을 빌려 써요. 가장 많이 쓰는 건 두 가지예요.

**`execution`**: 메서드 모양으로 고르기

```text
execution(접근제어자? 반환타입 선언타입?메서드이름(파라미터) throws?)
```

`?`가 붙은 건 생략 가능하고, **반환타입·메서드이름·파라미터** 세 개는 꼭 써요.

| 기호 | 뜻 |
|---|---|
| `*` | 아무거나(반환타입, 이름 일부 `set*`, 타입 하나) |
| 패키지의 `..` | 그 패키지와 하위 패키지 전부 |
| `(..)` | 파라미터 0개 이상 |
| `()` | 파라미터 없음 |
| `(*)` | 아무 타입 파라미터 1개 |
| `(*,String)` | 파라미터 2개, 두 번째는 String |

| 예 | 고르는 것 |
|---|---|
| `execution(public * *(..))` | 모든 public 메서드 |
| `execution(* set*(..))` | 이름이 set으로 시작하는 메서드 |
| `execution(* com.xyz.service.AccountService.*(..))` | `AccountService`의 모든 메서드 |
| `execution(* com.xyz.service..*.*(..))` | service 패키지와 하위 패키지의 모든 메서드 |

**`@annotation`**: 애너테이션이 붙은 메서드만 고르기. 위 예처럼 `@LogExecutionTime` 같은 커스텀 애너테이션을 만들어 원하는 메서드에만 붙이는 방식이 실무에서 흔해요. 범위가 코드에 바로 보여서 실수가 적어요.

그 밖에 알아 두면 좋은 것이에요.
- `within`(타입·패키지 범위), `args`(인자 타입), `bean(이름패턴)`(스프링 전용) 같은 지시자도 있어요.
- `&&`, `||`, `!`로 조합해요.
- `@Pointcut("...")`을 붙인 빈 `void` 메서드로 이름을 지어 재사용해요.
- `call`, `get`, `set` 같은 AspectJ 지시자는 스프링 AOP가 지원하지 않아서 쓰면 `IllegalArgumentException`이 나요.

### 6. 스프링 AOP의 한계와 AspectJ

스프링 AOP는 순수 자바로 만들어져서 **특별한 컴파일 과정이 필요 없어요**. 목표는 완전한 AOP가 아니라 스프링 컨테이너와 잘 붙는 실용적인 AOP예요. 그래서 할 수 있는 범위가 좁아요.

| | 스프링 AOP | AspectJ |
|---|---|---|
| 위빙 시점 | 런타임(프록시) | 컴파일 시점 또는 클래스 로드 시점 |
| 가로채는 지점 | 메서드 실행만 | 메서드 실행·호출, 필드 읽기/쓰기, 생성자 등 |
| 적용 대상 | 스프링 빈만 | 모든 객체 |
| 같은 클래스 내부 호출 | 안 걸림 | 걸림 |
| 준비물 | 없음 | AspectJ 컴파일러 또는 로드 타임 위버 |

프록시 방식이라 생기는 제약이에요.
- **자기 호출**(self-invocation): 객체 안에서 `this.other()`로 부르면 프록시를 안 거쳐서 Advice가 안 걸려요. 자세한 원리는 [구조 패턴: 자기 호출 함정](../../oop/patterns-structural/)에서 다뤄요.
- JDK 동적 프록시는 인터페이스의 public 메서드만, CGLIB은 public·protected(필요하면 package-private)까지 가로채요. private 메서드는 안 돼요.
- `new`로 직접 만든 객체는 스프링 빈이 아니라서 적용되지 않아요.

공식 문서 기준으로 AspectJ가 필요한 경우는 두 가지예요. ① 스프링이 관리하지 않는 객체(보통 도메인 객체)에 적용할 때, ② 필드 접근처럼 메서드 실행이 아닌 지점을 가로챌 때. 스프링 빈의 메서드에만 적용하면 되면 스프링 AOP가 더 단순해요.

<Aside type="note" title="import가 org.aspectj인데 AspectJ 아닌가요?">
`@Aspect`, `@Before` 등은 `org.aspectj.lang.annotation` 패키지에서 가져와요. 하지만 스프링은 AspectJ의 **애너테이션과 포인트컷 문법만** 빌리고, 실제로 끼워 넣는 건 자기 프록시로 해요. AspectJ 컴파일러를 쓰는 게 아니에요.
</Aside>

### 7. 등록과 설정

- `@Aspect`만 붙이면 컴포넌트 스캔 대상이 아니에요. **`@Component`를 함께** 붙이거나 `@Bean`으로 등록해요.
- Aspect 자신은 다른 Aspect의 적용 대상이 되지 않아요.
- Spring Boot는 AOP 스타터를 추가하면 자동 설정이 AOP를 켜 줘서 `@EnableAspectJAutoProxy`를 따로 안 붙여도 돼요. 기본은 CGLIB 프록시이고, JDK 프록시를 원하면 `spring.aop.proxy-target-class=false`로 바꿔요.
- 앱이 뜰 때 컨테이너가 빈마다 Pointcut에 맞는 메서드가 있는지 보고, 있으면 원본 대신 프록시를 빈으로 등록해요. 이 시점은 [빈 생명주기](../bean-lifecycle-scope/)에서 이어져요.

### 8. 실무 예: 재시도 Aspect

스프링 공식 문서에 나오는 예예요. DB 데드락 같은 일시적 실패(`PessimisticLockingFailureException`)가 나면 `@Around`에서 `proceed()`를 루프로 다시 불러요. 최대 횟수를 넘으면 마지막 예외를 다시 던져요.

여기서 중요한 건 두 가지예요.
1. **순서**: 재시도 Aspect의 order를 트랜잭션보다 작게(우선순위 높게) 둬요. 재시도가 바깥, 트랜잭션이 안쪽이 돼서 **재시도할 때마다 새 트랜잭션**으로 돌아요.
2. **범위**: 여러 번 실행해도 결과가 같은 **멱등**(idempotent) 연산에만 안전해요. 그래서 `@Idempotent` 같은 표시용 애너테이션을 만들고 `@annotation`으로 범위를 좁혀요.

스프링이 직접 AOP 프록시로 만든 기능도 많아요. [`@Transactional`](../transactional/)이 대표이고, `@Cacheable`, `@Async`, 메서드 보안의 `@PreAuthorize`도 프록시 기반이에요. 그래서 이 기능들도 자기 호출에서는 안 먹어요.

**답변(30초)** AOP는 로깅·트랜잭션·보안처럼 여러 모듈에 반복되는 횡단 관심사를 핵심 로직에서 분리해 Aspect 한곳에 모으는 프로그래밍 방식이에요. 공통 코드를 복붙하지 않아도 되고, 바꿀 때 한곳만 고치면 돼요. 서비스 코드에는 핵심 로직만 남아 읽기 쉬워져요. 스프링에서는 `@Transactional`이 대표적인 AOP 적용 예예요.

- Q. DI와 AOP의 관계는? → DI는 객체를 넣어 주고 AOP는 로직을 끼워 넣어요. 프록시를 빈으로 주입할 수 있는 것도 DI 덕분이에요.
</details>

<details>
<summary>Q. Aspect, Advice, Pointcut, JoinPoint의 차이는?</summary>

**답변(30초)** JoinPoint는 공통 코드를 끼울 수 있는 지점으로, 스프링 AOP에서는 메서드 실행이에요. Pointcut은 그 JoinPoint 중 실제로 적용할 곳을 고르는 조건, 즉 "어디에"예요. Advice는 그 지점에서 "언제, 무엇을" 할지이고, 이 둘을 묶은 모듈이 Aspect예요.

**꼬리질문**
- Q. Advisor는요? → 스프링 고유 용어로 Advice 하나와 Pointcut 하나를 묶은 거예요. Aspect는 이런 묶음 여러 개를 가질 수 있어요.
- Q. 위빙은요? → Aspect를 타깃에 연결하는 일이에요. 스프링 AOP는 런타임에 프록시로 해요.
</details>

<details>
<summary>Q. 어드바이스 종류와 실행 순서, @After와 @AfterReturning의 차이는?</summary>

**답변(30초)** `@Before`, `@AfterReturning`, `@AfterThrowing`, `@After`, `@Around` 다섯 가지예요. `@AfterReturning`은 정상 반환일 때만, `@After`는 `finally`처럼 정상이든 예외든 항상 실행돼요. 한 Aspect 안에서 정상 흐름은 Around 전반, Before, 메서드, AfterReturning, After, Around 후반 순이에요. Aspect끼리는 `@Order` 값이 작은 쪽이 바깥에서 감싸요.

**꼬리질문**
- Q. `@AfterThrowing`으로 예외를 처리할 수 있나요? → 예외를 받아 볼 수는 있지만 삼키지 못하고 계속 전파돼요. 바꾸려면 `@Around`에서 try/catch 해요.
- Q. `@Order`를 안 붙이면요? → 같은 메서드에 걸린 두 Aspect의 순서는 정의되지 않아요. 순서가 중요하면 반드시 지정해요.
</details>

<details>
<summary>Q. @Around를 쓸 때 주의할 점은?</summary>

**답변(30초)** `proceed()`를 반드시 불러야 진짜 메서드가 실행되고, 그 반환값을 그대로 돌려줘야 해요. 반환형을 `void`로 하면 호출자는 항상 `null`을 받아요. 가장 강력한 만큼 실수 여지도 커서, 공식 문서는 요구사항을 만족하는 가장 약한 어드바이스를 쓰라고 권해요.

**꼬리질문**
- Q. 실행 시간 측정은 어떻게 짜나요? → `proceed()` 앞에서 시작 시각을 재고 `finally`에서 로그를 남겨요. 그래야 예외가 나도 측정돼요.
- Q. `proceed()`를 여러 번 부를 수 있나요? → 네. 공식 재시도 예제가 루프 안에서 여러 번 불러요.
</details>

<details>
<summary>Q. 스프링 AOP의 한계는? AspectJ와 무엇이 다른가요?</summary>

**답변(30초)** 스프링 AOP는 런타임 프록시 방식이라 스프링 빈의 메서드 실행만 가로채요. 필드 접근, 생성자, private 메서드, 같은 클래스 안의 자기 호출에는 적용되지 않아요. AspectJ는 컴파일이나 클래스 로드 시점에 바이트코드에 직접 엮어서 이런 지점도 가로채고, 스프링 빈이 아닌 객체에도 적용돼요. 대신 별도 컴파일러나 위버를 빌드에 넣어야 해요.

**꼬리질문**
- Q. 왜 같은 클래스 내부 호출은 안 걸리나요? → `this`는 프록시가 아니라 진짜 객체를 가리켜서 프록시를 안 거치기 때문이에요. → [구조 패턴](../../oop/patterns-structural/)
- Q. 스프링 AOP도 `org.aspectj` 애너테이션을 쓰잖아요? → 애너테이션과 포인트컷 문법만 빌려 쓰고, 적용은 스프링 프록시가 해요.
</details>

<details>
<summary>Q. execution(* com.example..*Service.*(..))를 읽어 보세요.</summary>

**답변(30초)** 반환타입은 아무거나(`*`), `com.example` 패키지와 그 하위 패키지(`..`)에서 이름이 `Service`로 끝나는 타입(`*Service`)의 모든 메서드(`.*`)를, 파라미터 개수·타입 상관없이(`(..)`) 고른다는 뜻이에요. 접근제어자는 생략돼서 제한이 없어요.

**꼬리질문**
- Q. 파라미터 없는 메서드만 고르려면? → `(..)` 대신 `()`를 써요.
- Q. 범위가 너무 넓으면 뭐가 문제죠? → 모든 호출에 Advice가 걸려 오버헤드와 로그가 늘어요. 애너테이션 방식으로 좁히는 게 안전해요.
</details>

## 서술형 연습

<details>
<summary>상황: 데드락 재시도 Aspect를 만들었는데, 재시도해도 계속 실패해요.</summary>

**상황 파악** 주문 서비스에서 가끔 데드락(`PessimisticLockingFailureException`)이 나서, `@Around`로 최대 3번 재시도하는 Aspect를 만들었어요. 그런데 재시도가 성공한 적이 없어요.

**원인 후보**
1. **순서 문제**: 재시도 Aspect가 트랜잭션 *안쪽*에 있어요. 순서를 안 정했거나 트랜잭션보다 낮은 우선순위라면, 실패한 같은 트랜잭션 안에서 다시 시도하게 돼요. 이미 롤백될 트랜잭션이라 다시 해도 소용없어요.
2. **적용 안 됨**: `@Component` 누락, 자기 호출, 포인트컷 오타로 Aspect가 아예 안 걸렸을 수 있어요.
3. **재시도 간격 없음**: 바로 다시 부르면 같은 충돌이 또 날 수 있어요.

**해결책**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 재시도 Aspect에 `@Order`로 트랜잭션보다 높은 우선순위 부여 | 재시도마다 새 트랜잭션. 스프링 공식 예제와 같은 구조 | Aspect를 직접 관리해야 하고, 순서가 코드에 잘 안 보임 |
| B. 재시도를 트랜잭션 메서드를 부르는 바깥 빈에서 직접 루프 | 흐름이 코드에 그대로 보임 | 재시도가 필요한 곳마다 반복 코드가 생김 |
| C. `@Retryable` 사용 (Spring 7은 내장 `org.springframework.resilience`, 그 전엔 Spring Retry 라이브러리) | 횟수·간격(백오프) 설정이 쉬움 | 이것도 프록시라 순서·자기 호출 주의 |

**내가 고를 방법** A예요. 재시도가 필요한 곳이 여러 군데라 Aspect로 모으는 게 맞고, `@Order`만 트랜잭션보다 작게 주면 "재시도 바깥, 트랜잭션 안쪽"이 보장돼요. 그리고 `@Idempotent` 애너테이션이 붙은 메서드로만 범위를 좁혀요. 돈이 두 번 빠지는 것처럼 반복하면 결과가 달라지는 연산은 재시도하면 안 되니까요.

**채점 포인트**: `@Order` 값이 작을수록 바깥, 트랜잭션 기본 order는 가장 낮은 우선순위, 재시도마다 새 트랜잭션, 멱등 연산만 재시도, 최대 횟수, 해결책 2개 이상과 트레이드오프.
</details>

<details>
<summary>상황: 로깅 Aspect를 만들었는데 특정 메서드에서만 로그가 안 찍혀요.</summary>

**상황 파악** 서비스 메서드 실행 시간을 남기는 `@Around` Aspect를 만들었어요. 대부분 찍히는데 몇몇 메서드는 안 찍혀요.

**원인 후보**
1. **자기 호출**: 같은 클래스의 다른 메서드가 `this`로 부른 경우. 프록시를 안 거쳐요.
2. **private 메서드**: 프록시가 가로챌 수 없어요.
3. **스프링 빈이 아님**: `new`로 직접 만든 객체라면 프록시가 없어요.
4. **포인트컷 범위 밖**: 패키지 오타, 하위 패키지인데 `..` 대신 `.`을 쓴 경우.
5. (전부 안 찍힌다면) `@Aspect`만 붙이고 `@Component`를 빠뜨린 경우.

**해결책**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 대상 메서드를 다른 빈으로 분리해 외부 호출로 바꿈 | 프록시를 확실히 거침. 가장 흔한 해법 | 클래스가 늘어남 |
| B. 포인트컷을 `@annotation(LogExecutionTime)` 방식으로 바꿈 | 어디에 걸리는지 코드에 보임, 패키지 오타 걱정 없음 | 메서드마다 애너테이션을 붙여야 함 |
| C. AspectJ 위빙으로 전환 | 자기 호출·private도 가로챔 | 빌드 설정이 복잡해짐 |

**내가 고를 방법** 먼저 원인을 확인해요. 안 찍히는 메서드가 같은 클래스 안에서 불리는지, private인지 봐요. 자기 호출이면 A로 빈을 분리하고, 포인트컷 문제면 B로 바꿔요. C는 이 정도 문제엔 과해요.

**채점 포인트**: 프록시 기반이라 외부 호출만 가로챔, self-invocation, private 불가, 스프링 빈만 대상, `@Component` 필요, 포인트컷 `..` 의미, 해결책 2개 이상과 트레이드오프.
</details>
