상속은 부모 클래스의 내부 구현에 자식이 의존하게 만들어서, 부모가 바뀌면 자식이 조용히 깨질 수 있어요. 그래서 코드 재사용이 목적이라면 기존 객체를 필드로 갖고 일을 넘기는 조합(has-a)을 먼저 고려하고, 상속은 진짜 "~의 한 종류"이고 상속용으로 설계된 클래스일 때만 써요.
:::

:::note[처음이라면 여기까지]
- 상속은 남의 집을 통째로 물려받아 고치는 것과 같아서, 부모 속이 바뀌면 자식이 조용히 깨질 수 있어요.

- 그래서 코드를 빌려 쓰는 게 목적이면, 부품(객체)을 필드로 들고 일을 넘기는 조합을 먼저 생각해요.

- 상속은 진짜 "~의 한 종류"이고 상속용으로 만든 클래스일 때만 써요.

- 면접에선 질문 1·2번을 먼저 연습하세요.

## 쉽게 이해하기

**상속**은 **남의 집을 통째로 물려받아 리모델링하는 것**과 비슷해요. 배관이 벽 속에서 어떻게 이어져 있는지 모르는 채로 수도꼭지 하나를 바꿨는데, 알고 보니 그 배관이 보일러와 연결돼 있어서 온수가 두 번 데워지는 식이에요. 원래 집주인이 배관을 바꾸면 내 리모델링도 같이 망가져요.

**조합**은 **가전제품을 사서 내 집에 들이는 것**이에요. 세탁기 내부가 어떻게 돌아가는지 몰라도 "빨래해" 버튼만 누르면 돼요. 마음에 안 들면 다른 회사 세탁기로 바꿔 끼우면 끝이에요.

그래서 흔히 상속은 "**~의 한 종류다**(is a kind of)", 조합은 "**~을 가지고 있다**(has-a)"로 구분해요. 자동차는 엔진을 *가지고* 있지, 엔진의 한 종류가 아니에요.

단, 실제로는 상속이 나쁜 게 아니에요. 문제는 다른 사람이 만든 구체 클래스를 "코드 좀 빌려 쓰려고" 상속하는 경우예요.

## 제대로 알기

### 1. 상속은 원래 재사용 + 확장 도구예요

Java에서 `extends`로 다른 클래스를 물려받는 클래스를 **하위 클래스**(subclass), 물려주는 쪽을 **상위 클래스**(superclass)라고 해요. `Object`를 빼면 모든 클래스는 상위 클래스가 딱 하나예요(**단일 상속**). 아무것도 안 쓰면 `Object`를 상속해요.

- 하위 클래스는 상위의 `public`, `protected` 멤버를 물려받아요. 같은 패키지면 패키지 접근 멤버도 받아요.
- `private` 멤버와 생성자는 물려받지 않아요.
- Oracle 공식 튜토리얼도 상속을 "이미 있는 코드를 다시 짜지 않고 재사용하는 방법"으로 소개해요.

"부모/자식"이라는 말 때문에 가족 관계(계층도)로 오해하기 쉬운데, 객체지향 상속은 **분류도**예요. 위로 갈수록 일반적(동물), 아래로 갈수록 구체적(펭귄)이에요. 그래서 "상위/하위 클래스"라는 표현이 더 정확하고, 키워드도 `inheritance`가 아니라 `extends`(확장)예요.

### 2. is-a와 has-a

| 구분 | 상속 (is-a) | 조합 (has-a) |
|---|---|---|
| 문장 | 펭귄은 동물의 **한 종류**다 | 자동차는 엔진을 **가진다** |
| 코드 | `class Penguin extends Animal` | `class Car { private final Engine engine; }` |
| 만드는 관계 | 타입 관계 | 부품 관계 |
| 정해지는 시점 | 컴파일할 때 고정 | 실행 중 바꿔 끼울 수 있음 |
| 개수 | 하나만 | 여러 개 가능 |

"is-a"를 그대로 쓰면 "뽀로로는 펭귄이다"(객체와 클래스 관계)와 헷갈릴 수 있어요. 그래서 "**하위 클래스 is a kind of 상위 클래스**"(펭귄은 동물의 한 종류)라고 말하는 게 더 정확해요.

**조합**(composition)은 다른 객체를 필드로 가지고, 그 객체에게 일을 시키는 구조예요. 면접에서 말하는 "composition over inheritance"의 조합은 이렇게 넓은 뜻이에요.

### 3. 상속이 캡슐화를 깨는 이유: HashSet 실험

**캡슐화**(encapsulation, 내부 구현을 숨기고 겉으로 약속한 기능만 보여주는 것)가 깨진다는 게 무슨 뜻인지 실제 JDK 코드로 볼게요.

`HashSet`에 원소가 몇 번 추가됐는지 세고 싶어서 상속으로 만들어 봐요.

```java
class InstrumentedHashSet<E> extends HashSet<E> {
    int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;                    // 하나 넣을 때 +1
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();          // 여러 개 넣을 때 +개수
        return super.addAll(c);
    }
}

var s = new InstrumentedHashSet<String>();
s.addAll(List.of("a", "b", "c"));
System.out.println(s.addCount);       // 기대: 3, 실제: 6
```

JDK 17, 21에서 실행하면 **6**이 나와요. 원인은 이래요.

1. 재정의한 `addAll`이 먼저 3을 더해요.
2. `super.addAll(c)`를 부르는데, `HashSet`은 `addAll`을 직접 구현하지 않고 상위인 `AbstractCollection.addAll`을 물려받아 써요.
3. 그 `addAll`은 원소마다 `add(e)`를 하나씩 호출해요.
4. 실제 객체가 `InstrumentedHashSet`이라 **재정의된 `add`**가 불려요([동적 바인딩](../overloading-overriding/)). 여기서 3이 또 더해져요.

이렇게 public 메서드가 내부에서 재정의 가능한 다른 메서드를 부르는 걸 **self-use**(자기 사용)라고 해요. 하위 클래스는 상위의 이 숨은 구현까지 알아야 제대로 동작해요. 이게 "상속은 캡슐화를 깬다"는 말의 뜻이에요.

<Aside type="caution" title="addAll 재정의만 지우면 해결?">
지금은 3이 맞게 나와요. 하지만 그 정답은 "상위 `addAll`이 내부에서 `add`를 부른다"는 **현재 구현**에 기댄 거예요. 다음 버전에서 상위가 `add`를 안 부르게 바뀌면 이번엔 카운트가 0이 돼요. 반대로 `addAll`을 직접 처음부터 다시 짜면 상위 코드를 베끼는 셈이고, private 필드가 필요하면 아예 불가능해요.
</Aside>

**생성자 함정**도 있어요. `new HashSet<>(컬렉션)` 생성자는 내부에서 `addAll`을 불러요. 그래서 하위 클래스의 `super(c)`가 실행되는 동안 아직 초기화되지 않은 하위 클래스의 `addAll`, `add`가 먼저 불려요. 실제로 원소 2개를 넣으면, 필드를 `int addCount;`로 두면 4(이중 카운트), `int addCount = 0;`으로 두면 **0**이 나와요. 상위 생성자가 센 값을 하위 필드 초기화가 덮어써 버리거든요. Oracle 튜토리얼도 "생성자에서 부르는 메서드는 보통 final로 두라"고 권해요.

### 4. 상속의 다른 문제들

**취약한 기반 클래스**(fragile base class, 상위 클래스를 고치면 하위가 깨지기 쉬운 상태)
- 상위에 새 메서드가 추가되면, 하위가 지키던 규칙(예: "넣을 때마다 검증")을 피해 가는 새 통로가 생길 수 있어요.
- 하위가 우연히 같은 이름의 메서드를 갖고 있었다면 의도치 않게 재정의되거나, 반환 타입이 달라 컴파일이 깨져요.
- 상위 하나를 고치면 모든 하위를 다시 확인해야 해요.

**강한 결합**
- `extends`는 컴파일할 때 부모가 정해지고, 실행 중에 바꿀 수 없어요.
- 단일 상속이라 한 번 쓰면 다른 클래스는 상속할 수 없어요.

**필요 없는 기능까지 물려받음**. JDK에도 실패 사례가 있어요.

| 클래스 | 상속 관계 | 생기는 문제 |
|---|---|---|
| `Stack` | `extends Vector` | `push(1)`, `push(2)` 뒤 `add(0, 99)` 하면 `[99, 1, 2]`. 스택 바닥에 끼워 넣기가 돼요. javadoc도 `Deque`(예: `ArrayDeque`)를 쓰라고 권해요. |
| `Properties` | `extends Hashtable<Object,Object>` | `put("k", 123)`이 돼요. 그런데 `getProperty("k")`는 `null`, `get("k")`는 `123`. javadoc이 `put` 사용을 강하게 말려요. |

### 5. 해결: 조합 + 전달

기존 클래스를 상속하지 않고 **`private final` 필드로 갖고**, 내 메서드에서 그 필드의 메서드를 그대로 불러 줘요. 이렇게 일을 넘기는 걸 **전달**(forwarding)이라 하고, 실무에선 보통 **위임**(delegation)이라고도 불러요.

```java
class InstrumentedSet<E> {
    private final Set<E> inner;            // 상속 대신 필드로 가짐
    int addCount = 0;

    InstrumentedSet(Set<E> inner) { this.inner = inner; }

    public boolean add(E e) {
        addCount++;
        return inner.add(e);               // 일은 inner에게 넘김
    }
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return inner.addAll(c);            // inner 안에서 add가 불려도 inner 자신의 add
    }
}
// new InstrumentedSet<>(new HashSet<>()).addAll(List.of("a","b","c")) → 3
```

이번엔 **3**이 정확히 나와요. `inner.addAll`이 내부에서 `add`를 부르더라도 그건 `inner`(그냥 `HashSet`)의 `add`이지 래퍼의 `add`가 아니거든요. 내부 구현이 어떻게 바뀌어도 래퍼는 영향을 받지 않아요.

덤으로 유연해져요. 같은 래퍼에 `HashSet`을 넣어도, `TreeSet`을 넣어도 똑같이 동작해요. 상속으로 만들었다면 Set 종류마다 클래스를 하나씩 만들어야 했을 거예요.

래퍼가 `Set` 인터페이스를 구현하게 하면 기존 Set 자리에 그대로 쓸 수 있어요. 이렇게 같은 인터페이스로 감싸서 기능을 덧붙이는 구조가 [데코레이터 패턴](../patterns-structural/)이에요. 전달 메서드만 모아 둔 `ForwardingSet`을 따로 만들어 두면(Guava에도 있어요) 재사용이 쉬워요.

**조합의 단점**도 알아 두세요.
- 인터페이스 메서드마다 전달 코드를 써야 해서 코드가 길어져요.
- 내부 객체가 콜백용으로 자기 자신(`this`)을 다른 곳에 넘기면, 래퍼가 아니라 내부 객체가 넘어가서 래퍼를 건너뛰어요(**SELF 문제**).
- 객체 수가 조금 늘어요. 성능·메모리 영향은 대부분 무시할 만해요.

### 6. 그럼 상속은 언제 쓰나

- 하위가 상위의 **진짜 한 종류**이고, 상위 자리에 하위를 넣어도 문제없을 때(아래 LSP).
- 상위와 하위를 **같은 팀·같은 패키지**에서 함께 관리할 때.
- 상위 클래스가 **상속용으로 설계되고 문서화**됐을 때. 어떤 메서드가 어떤 재정의 가능 메서드를 부르는지 javadoc에 밝혀 둔 경우예요. `AbstractCollection.addAll` 문서의 `@implSpec`, [골격 구현](../abstract-interface/) `AbstractList`가 그 예예요.
- "전체 흐름은 상위가 정하고 일부 단계만 하위가 채운다"가 의도인 **템플릿 메서드 패턴**. 같은 걸 조합으로 하면 전략 패턴이에요([행위 패턴](../patterns-behavioral/)).

상속용으로 설계하지 않은 클래스는 막아 두는 게 좋아요.
- `final class`: 아예 상속 금지. `String` 같은 불변 클래스에 써요.
- `sealed class ... permits A, B`(Java 17+): 허용한 클래스만 상속 가능.

### 심화: 7. LSP와 연결

**LSP**(리스코프 치환 원칙, Liskov Substitution Principle)는 "하위 타입은 언제나 상위 타입 자리에 넣어도 문제없어야 한다"는 원칙이에요.

- `동물 뽀로로 = new 펭귄();` 자연스러워요. 펭귄은 동물의 한 종류니까요.
- `아버지 춘향이 = new 딸();` 이상해요. 딸에게 아버지 역할을 기대할 수 없어요. 가족 관계(계층도)를 상속으로 만든 오용이에요.

문법상 `extends`가 된다고 끝이 아니에요. 상위가 약속한 **동작**을 하위가 지켜야 해요. 유명한 예가 **정사각형 extends 직사각형**이에요.

```java
Rectangle r = new Square();   // 정사각형은 직사각형의 한 종류...?
r.setWidth(5);
r.setHeight(10);              // 정사각형이라 가로도 10으로 바뀜
r.area();                     // 직사각형이라 믿은 코드는 50을 기대, 실제 100
```

수학적으로는 is-a처럼 보이지만, "가로와 세로를 따로 바꿀 수 있다"는 직사각형의 약속을 깨요. `Stack extends Vector`도 "위에서만 넣고 뺀다"는 스택 약속을 Vector 메서드가 깨는 셈이에요.

결론은 한 문장이에요. **is-a처럼 보여도 LSP를 못 지키면 상속하지 말고 조합하세요.** LSP 세부 규칙은 [SOLID](../solid/)에서 다뤄요.

### 심화: 8. 스프링에서의 조합

스프링은 클래스 상속보다 **인터페이스 + 의존성 주입**(DI, 필요한 객체를 밖에서 넣어 주는 것)을 기본으로 써요. 서비스가 리포지토리를 필드로 갖고 호출하는 구조가 바로 has-a + 위임이에요. `@Transactional` 같은 AOP 프록시도 대상 객체를 감싸서 호출을 넘기는 구조예요.

<summary>Q. is-a와 has-a의 차이를 설명해 주세요.</summary>

**답변(30초)** is-a는 상속 관계로 "하위가 상위의 한 종류"라는 뜻이고, has-a는 조합 관계로 "다른 객체를 부품처럼 가진다"는 뜻이에요. 펭귄은 동물의 한 종류라 is-a, 자동차는 엔진을 가지니 has-a예요. is-a는 타입 관계를 만들고 컴파일할 때 고정되지만, has-a는 필드에 들어갈 객체를 실행 중에 바꿀 수 있어요.

**꼬리질문**
- Q. 정사각형은 직사각형을 상속해도 되나요? → 수학적으론 is-a지만, 가로만 바꿨는데 세로도 바뀌어서 직사각형을 기대한 코드가 틀린 넓이를 받아요. LSP 위반이라 상속하면 안 돼요.
</details>

<details>
<summary>Q. 상속보다 조합을 쓰라는 이유가 뭔가요?</summary>

**답변(30초)** 상속은 하위 클래스가 상위 클래스의 내부 구현에 의존하게 만들어서 캡슐화가 깨지기 때문이에요. 상위 구현이 바뀌면 하위 코드를 안 고쳤는데도 동작이 틀어질 수 있어요. 또 부모가 컴파일할 때 고정되고 하나만 상속할 수 있어 유연하지 않아요. 조합은 객체를 필드로 갖고 일을 넘기기만 해서 내부 구현과 무관하고, 실행 중에 다른 구현으로 바꿔 끼울 수도 있어요.

**꼬리질문**
- Q. 조합의 단점은? → 전달 메서드를 일일이 써야 해서 코드가 길어지고, 내부 객체가 `this`를 넘기는 콜백 구조에선 래퍼가 우회돼요.
- Q. 그럼 상속은 쓰지 말라는 건가요? → 아니요. 진짜 하위 타입이고 상속용으로 설계·문서화된 클래스이거나 같은 팀이 관리하면 괜찮아요. 문제는 남의 구체 클래스를 재사용만 하려고 상속하는 거예요.
</details>

<details>
<summary>Q. 상속이 캡슐화를 깬다는 게 무슨 뜻인지 예를 들어 설명해 주세요.</summary>

**답변(30초)** 하위 클래스가 상위의 숨은 구현까지 알아야 제대로 동작한다는 뜻이에요. 예를 들어 `HashSet`을 상속해서 `add`와 `addAll`을 둘 다 재정의해 추가 횟수를 세면, 원소 3개를 `addAll` 했을 때 3이 아니라 6이 나와요. 상위 `addAll`이 내부에서 `add`를 하나씩 부르는데, 그게 재정의된 `add`로 가서 두 번 세지기 때문이에요. 이런 내부 호출 관계는 겉으로 드러나지 않아서 상위가 바뀌면 또 깨질 수 있어요.

**꼬리질문**
- Q. `addAll` 재정의를 지우면 되지 않나요? → 지금은 맞지만 "상위 `addAll`이 `add`를 부른다"는 현재 구현에 기대는 거라, 상위 구현이 바뀌면 다시 틀려요.
- Q. 생성자에서 재정의 가능한 메서드를 부르면? → 하위 필드가 초기화되기 전에 하위 메서드가 실행돼요. `HashSet(Collection)` 생성자가 `addAll`을 불러서, 필드 초기화식이 있으면 카운트가 0으로 덮어써져요.
</details>

<details>
<summary>Q. LSP란 무엇이고 상속과 어떤 관계인가요?</summary>

**답변(30초)** 하위 타입은 언제나 상위 타입 자리에 넣어도 문제없이 동작해야 한다는 원칙이에요. 상속 문법이 허용돼도 상위가 약속한 동작을 하위가 깨면 위반이에요. 그래서 상속을 쓸지 판단하는 기준이 돼요. is-a처럼 보여도 LSP를 못 지키면 상속 대신 조합을 써야 해요.

**꼬리질문**
- Q. JDK에서 상속을 잘못 쓴 예는? → `Stack extends Vector`는 `add(0, x)`로 바닥에 끼워 넣을 수 있고, `Properties extends Hashtable`은 문자열이 아닌 값을 `put`할 수 있어요. 둘 다 javadoc이 대안을 권해요.
- Q. 상속을 막고 싶으면? → `final`로 막거나, Java 17부터는 `sealed`로 허용한 하위만 지정해요.
</details>

<details>
<summary>Q. 스프링에서 조합은 어디에 쓰이나요?</summary>

**답변(30초)** 의존성 주입 자체가 조합이에요. 서비스가 리포지토리 같은 다른 빈을 생성자로 받아 필드로 갖고, 필요한 일을 그 객체에 넘겨요. 인터페이스에 의존하니 테스트에서 가짜 구현으로 바꾸기도 쉬워요. `@Transactional` 같은 AOP 프록시도 실제 객체를 감싸서 앞뒤로 기능을 붙이고 호출을 넘기는 조합 구조예요.

**꼬리질문**
- Q. 데코레이터 패턴과는 무슨 관계예요? → 같은 인터페이스를 구현한 래퍼가 내부 객체를 감싸 기능을 덧붙이는 게 데코레이터예요. 조합 + 전달의 대표 활용이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 모든 서비스가 공통 BaseService를 상속해 로깅·권한 체크·저장 헬퍼를 씁니다. BaseService의 save()가 내부에서 validate()를 부르도록 바뀐 뒤, 일부 서비스에서 저장이 실패합니다.</summary>

**상황 파악**
하위 서비스 코드는 한 줄도 안 바뀌었는데 상위 변경 하나로 여러 서비스가 깨졌어요. 전형적인 **취약한 기반 클래스** 문제예요.

**원인 후보**
1. 몇몇 하위 서비스가 `validate()`를 다른 의미(예: 조회 조건 검사)로 이미 재정의해 두었고, 새 `save()`가 그 재정의된 메서드를 부르게 됐어요(self-use).
2. BaseService가 어떤 메서드가 어떤 재정의 가능 메서드를 부르는지 문서화하지 않아, 하위 개발자가 알 수 없었어요.
3. 로깅·권한·저장처럼 성격이 다른 기능이 한 상위 클래스에 몰려 있어 변경 영향 범위가 넓어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. BaseService를 상속용으로 정리: 재정의 지점을 템플릿 메서드 몇 개로 한정하고 나머지는 `final`, 호출 관계를 문서화 | 변경량이 적고 기존 구조 유지 | 상속 결합은 그대로, 앞으로도 상위 변경 시 전체 점검 필요 |
| B. 공통 기능을 `Validator`, `AuditLogger` 같은 별도 컴포넌트로 분리해 주입(조합), 로깅·권한 같은 횡단 관심사는 AOP | 서비스끼리 독립, 기능별 교체·테스트 쉬움 | 리팩터링 비용이 크고 서비스마다 의존성 주입 코드가 생김 |

**내가 고를 방법**
당장은 A로 `save()`를 `final`로 막고 재정의 지점을 명확히 해서 장애를 멈춰요. 그다음 B로 점진적으로 옮겨요. 새 서비스부터 컴포넌트 주입 방식을 쓰고, 기존 서비스는 수정할 때마다 BaseService 의존을 줄여요. 장기적으로 공통 기능을 상속이 아닌 조합으로 받아야 상위 변경이 모든 서비스로 번지지 않아요.

**채점 포인트**: 취약한 기반 클래스, 구현 세부 의존(self-use), 캡슐화 깨짐, final/상속용 설계·문서화, 템플릿 메서드, 조합(DI)으로 분리, AOP, 해결책 2개의 트레이드오프.
</details>

<details>
<summary>상황: 외부 라이브러리의 HTTP 클라이언트 클래스를 상속해 요청 횟수를 측정했는데, 라이브러리 마이너 버전 업 후 메트릭이 2배로 찍힙니다.</summary>

**상황 파악**
우리 코드는 그대로인데 라이브러리 업그레이드 후 숫자만 두 배가 됐어요. `InstrumentedHashSet`이 6을 세는 것과 같은 구조예요.

**원인 후보**
1. 새 버전에서 `execute()`가 내부적으로 `executeAsync()`를 부르도록 바뀌었고, 우리가 둘 다 재정의해 카운트하고 있어 이중 집계돼요.
2. 상속은 라이브러리의 내부 호출 관계에 의존하는데, 그건 공개 약속이 아니라 언제든 바뀔 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 재정의를 하나만 남겨 맞춤 | 고치기 가장 쉬움 | 또 현재 내부 구현에 기댐. 다음 업그레이드에서 다시 깨질 수 있음 |
| B. 클라이언트 인터페이스를 구현하는 래퍼(데코레이터)로 감싸 카운트 후 전달 | 내부 구현과 무관, 어떤 구현체든 감쌀 수 있음 | 전달 메서드를 써야 하고, 인터페이스가 없으면 적용 어려움 |
| C. 라이브러리가 공식 제공하는 인터셉터/훅 사용 | 라이브러리가 약속한 지점이라 업그레이드에 안전 | 라이브러리가 그런 기능을 제공해야 함 |

**내가 고를 방법**
C가 있으면 C를 써요. 공식 확장 지점이라 가장 안전해요. 없으면 B로 바꿔서 라이브러리 내부 구현에서 벗어나요. A는 급한 불 끄기용으로만 쓰고, 근본 해결은 상속을 걷어내는 거예요.

**채점 포인트**: 상위(라이브러리) 내부 구현 의존, self-use로 인한 이중 호출, 조합 + 전달, 데코레이터, 공식 확장 지점 활용, 업그레이드 안정성.
</details>

<details>
<summary>상황: CardPayment, PointPayment가 Payment를 상속하고 있는데, "카드 + 포인트 복합 결제"를 추가해 달라는 요구가 왔습니다.</summary>

**상황 파악**
복합 결제는 카드이면서 포인트예요. 자바는 클래스를 하나만 상속할 수 있어서 상속 구조로는 자연스럽게 표현할 수 없어요.

**원인 후보**
1. 결제 수단을 "타입"(is-a)으로 고정해서, 실행 중에 조합하는 경우를 담을 수 없어요.
2. 수단이 늘 때마다 조합 수만큼 하위 클래스가 늘어날 위험이 있어요(카드+포인트, 카드+쿠폰, ...).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `CardPointPayment extends Payment`를 새로 만들어 카드·포인트 코드를 복사 | 빠르게 추가 | 코드 중복, 조합마다 클래스 폭증 |
| B. `PaymentMethod` 인터페이스를 두고, 결제가 `List<PaymentMethod>`를 가지며(has-a) 각 수단에 금액을 나눠 위임 | 실행 중 어떤 조합이든 가능, 새 수단은 구현체 하나만 추가 | 부분 실패 시 취소 처리 등 조율 로직이 필요 |

**내가 고를 방법**
B를 골라요. 결제 수단을 부품으로 바꾸면 복합 결제는 리스트에 둘을 넣으면 끝이에요. 대신 카드는 성공했는데 포인트가 실패하는 경우를 대비해 앞서 성공한 결제를 취소하는 보상 로직을 함께 설계해요.

**채점 포인트**: 단일 상속 제약, 클래스 폭증, 조합(has-a)으로 런타임 조합, 인터페이스 의존(전략), 부분 실패 처리, 트레이드오프 비교.
</details>
