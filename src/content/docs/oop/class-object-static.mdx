:::tip[한 줄 요약]
클래스는 객체가 가질 상태(필드)와 행동(메서드)을 정의한 분류이고, 객체(인스턴스)는 `new`로 힙에 만들어진 실체예요. 인스턴스 필드는 객체마다 따로 생기지만, static 필드는 클래스에 딱 하나만 있어서 모든 객체가 공유해요.
:::

:::note[처음이라면 여기까지]
- 클래스는 "학생" 같은 분류이고, 객체는 `new`로 만든 실제 철수·영희예요.

- 인스턴스 필드는 각자의 공책이라 객체마다 따로 있고, static 필드는 교실 칠판 하나라 모두가 같이 봐요.

- 그래서 static은 객체를 안 만들어도 `클래스명.이름`으로 바로 쓸 수 있어요.

- 면접에선 질문 1·2번을 먼저 연습하세요.
:::

## 쉽게 이해하기

"학생"이라는 말은 **개념(분류)**이에요. 이름, 학번, 점수를 가진다는 약속만 있고, 실제로 교실에 앉아 있는 건 아니에요. 교실에 앉아 있는 김철수, 이영희가 **실체**예요. 자바에서 "학생"이 **클래스**, 김철수와 이영희가 **객체**예요.

교실에는 **각자의 공책**과 **앞쪽 칠판 하나**가 있어요. 철수가 자기 공책에 쓴 건 영희 공책에 안 보여요. 이게 **인스턴스 필드**예요. 칠판은 반 전체에 하나라서, 누가 고치든 모두가 같은 내용을 봐요. 이게 **static 필드**예요.

칠판은 학생이 한 명도 없어도 교실에 걸려 있어요. 그래서 static 멤버는 객체를 만들지 않아도 `클래스명.이름`으로 바로 쓸 수 있어요.

단, 흔히 쓰는 "클래스 = 붕어빵 틀, 객체 = 붕어빵" 비유는 조금 어긋나요. 틀은 붕어빵을 **찍어 내는 도구**지, 붕어빵이 **무엇인지 나타내는 분류**가 아니거든요. "클래스 : 객체 = 분류 : 실체"(펭귄 : 동물원의 그 펭귄)로 기억하는 편이 더 정확해요. 헷갈리면 "몇 살이야?(물건이면 언제 만들었어?)"라고 물어 보세요. 답할 수 있으면 객체, 답할 수 없으면 클래스예요.

## 그림으로 보기

<ClassObjectMemory />

그림에 쓰인 코드는 이거예요.

```java
class Counter {
    static int total = 0;   // 클래스에 딱 1개
    int mine = 0;           // 객체마다 1개씩

    void inc() { mine++; total++; }
}

// main 안에서
Counter a = new Counter();
Counter b = new Counter();
a.inc();
b.inc();
// a.mine == 1, b.mine == 1, Counter.total == 2
```

## 제대로 알기

### 1. 클래스, 객체, 인스턴스

- **클래스**(class): 같은 종류의 객체가 가질 **상태(필드)**와 **행동(메서드)**을 적어 둔 정의예요.
- **객체**(object): 그 정의대로 실제로 만들어진 실체예요.
- **인스턴스**(instance): 객체와 **같은 대상**이에요. 다만 "어느 클래스에서 나왔는지" 관계를 강조할 때 써요. "`mickey`는 `Mouse` 클래스의 인스턴스"처럼요.

`new Mouse()`가 실행되면 **힙**(heap, `new`로 만든 객체가 사는 메모리 구역)에 객체가 생기고, 변수에는 객체 자체가 아니라 그 객체를 가리키는 **참조**(reference, 객체가 있는 위치 정보)가 담겨요.

```java
Mouse mickey = new Mouse();
// mickey(변수)에는 참조가, Mouse 객체는 힙에 있어요
```

### 심화: 2. 코드가 돌 때 무엇이 어디에 생기나

처음 배울 때는 메모리를 세 칸으로 나눠 생각하면 편해요.

| 칸 | 무엇이 들어가나 | 언제 생기고 사라지나 | 스레드 |
|---|---|---|---|
| 스태틱 영역 | 클래스 정보, static 필드 | 클래스가 처음 쓰일 때 생김 | 모두 공유 |
| 스택 | 메서드 호출마다 쌓이는 **프레임**(지역변수·매개변수) | 메서드 시작에 생기고 끝나면 사라짐 | 스레드마다 따로 |
| 힙 | `new`로 만든 객체와 그 인스턴스 필드 | `new` 때 생기고, 아무도 안 가리키면 GC가 치움 | 모두 공유 |

- static 필드는 클래스가 올라올 때 **한 칸만** 생겨요.
- 인스턴스 필드는 클래스에 이름만 적혀 있고, 실제 칸은 **객체를 만들 때마다 객체 안에** 따로 생겨요.
- 클래스는 프로그램 시작 때 한꺼번에 올라오지 않아요. **처음 사용될 때**(객체 생성, static 메서드 호출, 상수가 아닌 static 필드 사용 등) 직전에 초기화돼요.

<Aside type="caution" title="버전 주의: '스태틱 영역'은 학습용 이름">
위 세 칸은 이해를 돕는 단순화예요. 실제 HotSpot JDK 8 이상에서는 클래스 메타데이터는 Metaspace, **static 변수 값은 힙**에 있어요. "static 변수는 Metaspace에 있다"는 틀린 말이에요. 자세한 버전별 위치는 [JVM 구조와 GC](../../java/jvm-gc/)를 보세요.
</Aside>

### 3. static 멤버 vs 인스턴스 멤버

| 구분 | static(클래스) 멤버 | 인스턴스(객체) 멤버 |
|---|---|---|
| 개수 | 클래스에 1개 | 객체마다 1개 |
| 객체 없이 접근 | 가능 | 불가 |
| 권장 접근법 | `클래스명.이름` | `참조변수.이름` |
| 한쪽이 바꾸면 | 모두에게 보임 | 그 객체만 바뀜 |

- 부르는 이름이 여러 개예요. 클래스 멤버 = static 멤버 = 정적 멤버, 객체 멤버 = 인스턴스 멤버. 필드, 속성, 멤버 변수도 거의 같은 뜻으로 섞어 써요.
- `a.total`처럼 객체 참조로 static 필드에 접근해도 컴파일은 돼요. 하지만 여전히 클래스에 있는 그 한 칸이에요. static인 게 코드에서 안 드러나서 권하지 않아요.

### 4. static 메서드에서 인스턴스 멤버를 못 쓰는 이유

| 어디서 | static 멤버 | 인스턴스 멤버 | `this` |
|---|---|---|---|
| 인스턴스 메서드 | 직접 사용 가능 | 직접 사용 가능 | 사용 가능 |
| static 메서드 | 직접 사용 가능 | 객체 참조를 통해서만 | **사용 불가** |

static 메서드는 객체 없이 불릴 수 있어요. 그러면 "어느 객체의 `mine`을 말하는 거지?"에 답할 객체가 없어요. 같은 이유로 `this`(지금 메서드를 실행 중인 객체를 가리키는 참조)도 쓸 수 없어요.

`main()`이 static인 이유도 같아요. 프로그램이 막 시작될 때는 객체가 하나도 없으니까, 객체 없이 부를 수 있어야 해요.

### 5. static을 쓰기 좋은 곳

- **모든 객체가 같은 값을 가지는 속성**: 원주율처럼 객체마다 다를 이유가 없는 값.
- **객체 상태가 필요 없는 유틸리티 메서드**: `Math.max()`처럼 입력만 보고 결과를 내는 함수.
- **상수**: `static final`. 다시 대입하면 컴파일 에러가 나고, 이름은 `MAX_SIZE`처럼 대문자와 밑줄로 써요.

<Aside type="note" title="컴파일 타임 상수의 함정">
기본형이나 String으로 된 `static final` 값이 컴파일 시점에 정해지면, 컴파일러가 그 값을 **사용하는 쪽 코드에 직접 박아 넣어요**. 그래서 상수 값을 바꾸면 그 상수를 쓰는 다른 클래스도 다시 컴파일해야 새 값이 반영돼요.
</Aside>

### 6. static을 조심해야 하는 이유

| 문제 | 왜 생기나 | 대안 |
|---|---|---|
| 추적 어려움 | 바꿀 수 있는 static 필드는 사실상 **전역 변수**라 어디서 바뀌었는지 찾기 어려움 | 읽기 전용 공유(`static final` 상수)만 static으로 |
| 동시성 버그 | static 필드는 모든 스레드가 공유. `count++`는 한 번에 끝나는(원자적) 연산이 아님 | 불변 객체, `AtomicInteger`·`ConcurrentHashMap`, 동기화 |
| 테스트 어려움 | static 상태가 테스트 사이에 남아 순서에 따라 결과가 달라짐. static 메서드는 가짜 객체로 바꾸기 어려움 | 인스턴스 메서드 + 의존성 주입(DI). Mockito `mockStatic`은 차선책 |
| 메모리 누수 | static 컬렉션에 넣기만 하면 GC가 영영 못 치움 | 크기 제한·만료 있는 캐시. 자세한 건 [JVM 구조와 GC](../../java/jvm-gc/) |

스프링 빈도 기본이 **싱글톤**(애플리케이션 전체에 객체 하나)이라, 여러 요청이 같은 객체를 함께 써요. 빈의 필드에 요청마다 다른 값(사용자 ID 등)을 저장하면 static과 똑같은 공유 상태 문제가 생겨요. 그래서 빈은 **무상태**(stateless, 요청별 값을 필드에 두지 않음)로 만들어요.

static 메서드는 **오버라이딩되지 않고 숨겨져요**(hiding). 자식 클래스에 같은 시그니처로 선언해도, 어떤 메서드가 불릴지는 참조 변수의 선언 타입으로 정해져요. 자세한 건 [오버로딩과 오버라이딩](../overloading-overriding/)에서 다뤄요.

### 심화: 7. 초기화 규칙과 static 블록

- **필드**(인스턴스·static)는 값을 안 넣어도 기본값이 있어요: 숫자 0, `0.0`, `false`, 참조는 `null`.
- **지역변수**는 기본값이 없어요. 값을 넣기 전에 읽으면 **컴파일 에러**예요.
- **static 블록**(`static { ... }`)은 클래스가 초기화될 때 **딱 한 번** 실행돼요. 안에서는 static 멤버만 쓸 수 있어요. 실행 시점은 클래스가 처음 쓰일 때예요.

```java
class Config {
    static final Map<String, String> DEFAULTS;
    static {   // 클래스 초기화 때 한 번만 실행
        DEFAULTS = Map.of("lang", "ko");
    }
}
```

### 8. 생성자와 this

**생성자**(constructor)는 객체를 처음부터 **쓸 수 있는 올바른 상태**로 만드는 특별한 메서드예요. 클래스 이름과 같고, 반환 타입이 없고, `new`로 불려요. 꼭 필요한 값을 생성자 인자로 받으면 "반쯤 만들어진 객체"를 막을 수 있어요.

- 생성자를 **하나도 안 쓰면** 컴파일러가 인자 없는 **기본 생성자**를 넣어 줘요.
- 인자 있는 생성자를 **하나라도 만들면** 기본 생성자는 자동으로 생기지 않아요. 그래서 `new Animal()`이 컴파일 에러가 나요.
- 기본 생성자는 부모 클래스의 인자 없는 생성자를 불러요. 부모에 그게 없으면 컴파일 에러예요. 부모를 안 적으면 `Object`가 부모예요.

```java
class Animal {
    String name;

    Animal(String name) {
        this.name = name;      // this.name = 필드, name = 매개변수
    }

    Animal() {
        this("이름없음");       // 같은 클래스의 다른 생성자 호출
    }
}
```

- `this`: 지금 실행 중인 객체를 가리키는 참조예요. 매개변수 이름이 필드와 같으면 매개변수가 필드를 **가려서**(shadowing), 필드를 쓰려면 `this.name`이라고 써야 해요. static 필드는 `클래스명.이름`으로 써요.
- `this(...)`: 같은 클래스의 **다른 생성자**를 부르는 문법이에요(생성자 체이닝). 인자 개수와 타입으로 어떤 생성자인지 정해져요.

<Aside type="caution" title="버전 주의: this()/super()는 첫 줄?">
Java 24까지는 `this(...)`나 `super(...)`가 생성자의 **첫 문장**이어야 했어요. **Java 25(JEP 513)**부터는 그 앞에 인자 검증 같은 문장을 둘 수 있어요. 단, 그 앞부분에서는 아직 다 만들어지지 않은 `this`를 읽거나 메서드를 부를 수 없어요(필드에 값을 넣는 건 허용). 면접·필기에서는 "원래 첫 줄 규칙이고, Java 25부터 완화됐다"고 말하면 충분해요.
</Aside>

## 면접 질문

<details>
<summary>Q. 클래스와 객체(인스턴스)의 차이는 무엇인가요?</summary>

**답변(30초)** 클래스는 객체가 가질 상태와 행동을 정의한 분류이고, 객체는 그 정의대로 `new`를 통해 힙에 만들어진 실체예요. 변수에는 객체 자체가 아니라 객체를 가리키는 참조가 담겨요. 인스턴스는 객체와 같은 대상인데, "어느 클래스의 것인지" 관계를 강조할 때 쓰는 말이에요.

**꼬리질문**
- Q. 붕어빵 틀 비유는 정확한가요? → 틀은 붕어빵을 만드는 도구에 가까워서 조금 어긋나요. "펭귄 : 그 펭귄"처럼 분류와 실체 관계로 보는 게 더 정확해요.
- Q. `Mouse m = new Mouse()`에서 `m`에 객체가 들어 있나요? → 아니요. 객체는 힙에 있고 `m`에는 그 위치를 가리키는 참조가 있어요.
</details>

<details>
<summary>Q. static 변수와 인스턴스 변수의 차이를 설명해 주세요.</summary>

**답변(30초)** static 변수는 클래스에 하나만 있어서 모든 객체가 공유하고, 인스턴스 변수는 객체마다 따로 있어요. static 변수는 클래스가 처음 쓰일 때 생기고 객체 없이 `클래스명.변수`로 접근해요. 인스턴스 변수는 `new`로 객체를 만들 때 그 객체 안에 생겨요. 그래서 한 객체가 static 변수를 바꾸면 다른 모든 객체에도 바뀐 값이 보여요.

**꼬리질문**
- Q. static 변수는 JVM 어디에 있나요? → HotSpot JDK 8 이상에서는 힙이에요. Metaspace에는 클래스 메타데이터만 있어요.
- Q. 클래스는 프로그램 시작 때 전부 로딩되나요? → 아니요. 객체 생성이나 static 메서드 호출처럼 처음 쓰일 때 초기화돼요.
</details>

<details>
<summary>Q. static 메서드에서 인스턴스 변수나 this를 쓸 수 없는 이유는?</summary>

**답변(30초)** static 메서드는 객체 없이도 호출되기 때문이에요. 인스턴스 변수는 객체마다 따로 있으니 "어느 객체의 변수인지" 정해야 하는데, static 메서드에는 그 기준이 되는 객체가 없어요. `this`도 같은 이유로 쓸 수 없어요. 인스턴스 멤버가 필요하면 객체 참조를 받아서 그 참조로 접근해야 해요.

**꼬리질문**
- Q. `main`은 왜 static인가요? → 프로그램이 시작될 때는 객체가 하나도 없어서, 객체 없이 부를 수 있어야 하기 때문이에요.
- Q. 반대로 인스턴스 메서드에서 static 변수는 쓸 수 있나요? → 네, 클래스에 하나 있는 값이라 어디서든 직접 쓸 수 있어요.
</details>

<details>
<summary>Q. static은 언제 쓰고, 남용하면 어떤 문제가 있나요?</summary>

**답변(30초)** 모든 객체가 같은 값을 갖는 상수나, 객체 상태가 필요 없는 유틸리티 메서드에 써요. 바꿀 수 있는 static 필드는 사실상 전역 변수라 값이 어디서 바뀌었는지 추적하기 어렵고, 모든 스레드가 공유하니 동시성 버그가 생기기 쉬워요. 또 static 상태는 테스트 사이에 남고, static 메서드는 가짜 객체로 바꾸기 어려워 테스트가 힘들어져요. 그래서 공유는 `static final` 상수 위주로 하고, 나머지는 인스턴스와 의존성 주입으로 풀어요.

**꼬리질문**
- Q. 스프링 싱글톤 빈과 static은 뭐가 비슷한가요? → 둘 다 객체 하나를 여러 요청이 공유해요. 그래서 빈 필드에 요청별 상태를 두면 static처럼 값이 섞여요. 빈을 무상태로 만드는 이유예요.
- Q. static 메서드는 오버라이딩되나요? → 아니요, 숨겨져요(hiding). 어떤 메서드가 불릴지는 참조 변수의 선언 타입으로 정해져요.
</details>

<details>
<summary>Q. 기본 생성자는 언제 생기나요? 생성자를 추가했더니 new X()가 에러 나는 이유는?</summary>

**답변(30초)** 생성자를 하나도 작성하지 않았을 때만 컴파일러가 인자 없는 기본 생성자를 넣어 줘요. 인자 있는 생성자를 하나라도 만들면 기본 생성자는 자동으로 생기지 않아서, `new X()`가 컴파일 에러가 나요. 필요하면 인자 없는 생성자를 직접 써야 해요.

**꼬리질문**
- Q. 부모 클래스와는 무슨 관계가 있나요? → 기본 생성자는 부모의 인자 없는 생성자를 불러요. 부모에 그게 없으면 자식도 컴파일 에러가 나요.
- Q. 생성자의 역할은 뭔가요? → 객체를 처음부터 올바른 상태로 만드는 거예요. 필수 값을 인자로 강제하면 반쯤 만들어진 객체를 막을 수 있어요.
</details>

<details>
<summary>Q. this와 this()의 차이는?</summary>

**답변(30초)** `this`는 지금 실행 중인 객체를 가리키는 참조이고, 주로 매개변수와 이름이 같은 필드를 구분할 때 `this.name`처럼 써요. `this()`는 같은 클래스의 다른 생성자를 부르는 문법이에요. 생성자끼리 중복 코드를 줄일 때 쓰고, 인자 개수와 타입으로 어떤 생성자인지 정해져요.

**꼬리질문**
- Q. `this()`는 꼭 첫 줄이어야 하나요? → Java 24까지는 그랬어요. Java 25(JEP 513)부터는 그 앞에 인자 검증 같은 문장을 둘 수 있지만, 그 부분에서 `this`를 읽거나 메서드를 부를 수는 없어요.
</details>

<details>
<summary>Q. 지역변수는 왜 초기화해야 하고 필드는 안 해도 되나요?</summary>

**답변(30초)** 필드는 객체나 클래스가 만들어질 때 0, `false`, `null` 같은 기본값이 자동으로 들어가요. 지역변수는 기본값이 없어서, 값을 넣기 전에 읽으면 컴파일러가 에러를 내요. 그래서 지역변수는 쓰기 전에 반드시 값을 넣어야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 번호를 static long seq에 seq++로 만들었는데, 트래픽이 몰리면 번호가 중복됩니다.</summary>

**상황 파악**
평소엔 괜찮다가 **동시에 요청이 많을 때만** 중복이 난다는 점이 핵심이에요. 여러 스레드가 같은 값을 동시에 건드릴 때 생기는 문제를 먼저 의심해요.

**원인 후보**
1. static 필드는 모든 스레드가 공유하는데, `seq++`는 "읽기 → 1 더하기 → 쓰기" 세 단계라 원자적이지 않아요. 두 스레드가 같은 값을 읽으면 같은 번호가 나와요.
2. 서버가 여러 대라면 static 변수는 **서버(JVM)마다 따로** 있어요. 각 서버가 1부터 세니 동기화를 해도 서버끼리 번호가 겹쳐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `AtomicLong.incrementAndGet()` | 코드 한 줄, 빠름, 한 JVM 안에서 중복 없음 | 서버가 여러 대면 소용없음. 재시작하면 처음부터 다시 셈 |
| B. `synchronized`로 감싸기 | 이해하기 쉬움 | 락 대기로 느려질 수 있고, 다중 서버 문제는 그대로 |
| C. DB 시퀀스나 Redis `INCR`로 번호 발급 | 서버 여러 대여도 하나의 출처에서 발급. 앱 서버를 재시작해도 번호가 이어짐 | 번호마다 네트워크 왕복이 생기고 DB·Redis가 장애 지점이 됨. Redis는 영속성(RDB·AOF)을 안 켜면 Redis 재시작 때 값이 날아감 |

**내가 고를 방법**
운영 서버는 보통 여러 대라서 C를 골라요. JVM 안의 static은 서버 한 대 안에서만 공유된다는 한계가 있으니, 번호처럼 전체에서 유일해야 하는 값은 공용 저장소에서 받아야 해요. 서버가 한 대뿐이고 재시작 후 이어질 필요가 없다면 A로 충분해요.

**채점 포인트**: static은 모든 스레드 공유, `count++`는 비원자적(경쟁 상태), `AtomicLong`, 서버가 여러 대면 static은 서버별이라 무의미, DB 시퀀스나 Redis `INCR`, 해결책 2개 이상의 트레이드오프.
</details>

<details>
<summary>상황: 서비스 코드가 static 유틸(DateUtil.now(), 외부 API static 클라이언트)을 직접 불러서 단위 테스트를 쓸 수가 없습니다.</summary>

**상황 파악**
테스트에서 "지금 시각"이나 "외부 API 응답"을 원하는 값으로 바꿔야 하는데, 코드가 static 메서드를 직접 부르고 있어서 끼어들 틈이 없어요.

**원인 후보**
1. static 메서드는 인터페이스 뒤로 숨길 수 없어서, 가짜 구현으로 바꿔 끼울 수 없어요.
2. static 상태가 있다면 테스트 사이에 값이 남아, 실행 순서에 따라 결과가 달라질 수도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 의존성 주입으로 전환(시간은 `Clock` 주입, 외부 API는 인터페이스 + 구현 빈) | 테스트에서 가짜 객체를 자유롭게 넣음, 설계가 유연해짐 | 기존 코드를 고쳐야 하고 호출부가 많으면 작업량이 큼 |
| B. Mockito `mockStatic`으로 static 호출을 가로채기 | 프로덕션 코드를 안 고쳐도 됨 | 테스트 코드가 복잡해지고, 근본적인 결합은 그대로 남음 |

**내가 고를 방법**
새로 쓰거나 자주 바뀌는 코드는 A로 바꿔요. 테스트하기 쉬운 구조가 곧 바꾸기 쉬운 구조라서예요. 당장 고치기 어려운 레거시는 B로 테스트를 먼저 붙여 안전망을 만든 뒤, 점진적으로 A로 옮겨요.

**채점 포인트**: static 메서드는 다형성·대체 불가, static 상태가 테스트 간 공유됨, 의존성 주입, `Clock` 주입, `mockStatic`은 차선책, 두 방법의 트레이드오프.
</details>

<details>
<summary>상황: 스프링 서비스 빈의 필드에 현재 사용자 ID를 저장했더니, 가끔 다른 사람 정보가 응답에 섞입니다.</summary>

**상황 파악**
"가끔"이고 "다른 사람" 정보가 섞인다는 건, 여러 요청이 같은 값을 공유하고 있다는 신호예요.

**원인 후보**
1. 스프링 빈은 기본이 싱글톤이라 모든 요청이 **같은 객체 하나**를 써요. 그 객체의 필드는 static 필드처럼 사실상 공유 상태가 돼요.
2. 요청 A가 필드에 ID를 쓰고 읽기 전에, 요청 B가 같은 필드를 덮어쓰면 A가 B의 ID로 처리돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 빈을 무상태로: 사용자 ID를 필드가 아니라 메서드 매개변수·지역변수로 전달 | 지역변수는 스레드마다 스택에 따로 있어 근본적으로 안전 | 메서드 시그니처를 고쳐야 함 |
| B. 빈 스코프를 요청 단위로 바꾸기(`@RequestScope`, HTTP 요청마다 새 빈) | 필드 사용 방식을 유지 | 요청마다 객체가 생기고, 싱글톤 빈에 주입하려면 스코프 프록시가 필요해 구조가 복잡해짐 |

**내가 고를 방법**
A를 골라요. 싱글톤 빈은 static과 같은 "공유 객체"라서 요청별 값을 담으면 안 된다는 원칙을 지키는 게 가장 단순하고 안전해요.

**채점 포인트**: 싱글톤 빈 = 모든 요청이 공유하는 객체, static과 같은 공유 상태 문제, 무상태 설계, 지역변수는 스레드별 스택이라 안전, 대안과 트레이드오프.
</details>

## 필기 포인트

- 클래스는 **처음 사용될 때** 초기화돼요. "프로그램 시작 시 모든 클래스 로딩"은 틀린 보기예요.
- static 메서드 안에서 `this` 사용, 인스턴스 필드 직접 접근은 **컴파일 에러**예요.
- 인자 있는 생성자만 있는 클래스에 `new X()`는 **컴파일 에러**예요.
- 지역변수를 초기화하지 않고 읽으면 **컴파일 에러**, 필드는 기본값(0, `false`, `null`)이 있어요.
- `객체.static필드`도 문법상 허용되지만 가리키는 건 클래스의 그 한 칸이에요.
- static 블록은 클래스 초기화 때 **한 번만** 실행돼요.
- static 메서드는 오버라이딩이 아니라 **hiding**이에요.
- JDK 8+ HotSpot에서 static 변수는 **힙**, 클래스 메타데이터는 **Metaspace**예요.
