:::note[처음이라면 여기까지]
- SOLID는 객체지향 설계 원칙 다섯 개(SRP·OCP·LSP·ISP·DIP)의 앞 글자예요. 식당 주방 비유로 하나씩 떠올리면 돼요.

- 다섯 개가 노리는 건 하나예요. 바뀌는 부분을 떼어 내고, 특정 가게 대신 규격(추상화)에 기대서, 바뀌어도 한 곳만 고치기.

- 면접에선 질문 1·2번을 먼저 연습하세요.
:::

## 쉽게 이해하기

식당 주방을 떠올려 보세요. 요리사 한 명이 주문 받기, 요리, 계산, 배달을 다 하면 배달 방식만 바꾸려 해도 그 사람의 하루 전체가 흔들려요. 그래서 역할을 나눠요(**SRP**).

새 메뉴가 생길 때마다 주방을 뜯어고치면 곤란해요. 레시피 카드만 한 장 더 꽂으면 되게 만들어 두는 게 좋아요(**OCP**).

"요리사"로 뽑은 사람이 막상 칼을 못 쓴다면 요리사 자리에 앉힐 수 없어요. 이름만 같은 게 아니라 기대한 일을 해내야 해요(**LSP**).

설거지 담당에게 "요리·계산·배달 매뉴얼 전부"를 외우게 할 필요는 없어요. 자기 일에 필요한 매뉴얼만 주면 돼요(**ISP**).

사장이 "○○상회 양파"만 쓰겠다고 정해 두면 그 가게가 문을 닫는 순간 끝이에요. "규격에 맞는 양파"라는 기준에만 의존하면 납품처는 언제든 바꿀 수 있어요(**DIP**).

단, 실제로는 다섯 원칙이 따로 노는 게 아니라 한 가지 해결책 안에 여러 원칙이 함께 들어 있는 경우가 많아요. 아래 결제 예시에서 그걸 확인해 볼게요.

## 제대로 알기

### 0. SOLID가 노리는 것: 낮은 결합도, 높은 응집도

먼저 두 단어부터 알아야 해요.

- **결합도**(coupling, 모듈끼리 서로 얼마나 엮여 있는지): **낮을수록** 좋아요. 한쪽을 고쳤을 때 다른 쪽이 덜 흔들리니까요.
- **응집도**(cohesion, 한 모듈 안의 요소들이 얼마나 같은 목적으로 모여 있는지): **높을수록** 좋아요.

SOLID는 이 오래된 원칙을 객체지향 언어로 구체화한 거예요. 원칙들은 Robert C. Martin(일명 Uncle Bob)이 2000년 논문에서 정리했고, SOLID라는 약어는 2004년 무렵 Michael Feathers가 붙였어요.

| 글자 | 원칙 | 한 줄 뜻 |
|---|---|---|
| S | 단일 책임 원칙(SRP) | 클래스를 바꿀 이유는 하나뿐이어야 한다 |
| O | 개방 폐쇄 원칙(OCP) | 확장에는 열려 있고, 수정에는 닫혀 있어야 한다 |
| L | 리스코프 치환 원칙(LSP) | 하위 타입은 상위 타입 자리에 넣어도 문제없어야 한다 |
| I | 인터페이스 분리 원칙(ISP) | 안 쓰는 메서드에 의존하게 강요하지 마라 |
| D | 의존 역전 원칙(DIP) | 구체 클래스 말고 추상화에 의존하라 |

### 1. SRP: 단일 책임 원칙

**정의**: 어떤 클래스를 **변경해야 하는 이유는 하나**뿐이어야 해요.

여기서 많이들 오해해요. "메서드 하나만", "한 가지 일만"이라는 뜻이 아니에요. 기준은 **누가 바꿔 달라고 하는가**예요. Martin은 변경 이유가 코드가 아니라 **사람(이해관계자)**에게서 나온다고 설명해요. 그의 예시에서 `Employee` 클래스에 급여 계산(재무 조직), 근무시간 보고(운영 조직), 저장(기술 조직)이 함께 있으면, 급여 규칙을 고치다가 근무시간 보고서가 깨질 수 있어요. 이후 『클린 아키텍처』에서는 "하나의 모듈은 하나의 **액터**(actor, 변경을 요청하는 사람이나 집단)만 책임진다"는 식으로 다시 표현한 것으로 알려져 있어요.

> 같은 이유로 바뀌는 것은 모으고, 다른 이유로 바뀌는 것은 떼어 놓는다.

```java
// 위반: 결제 정책, 저장 방식, 알림 문구가 바뀔 때마다 이 클래스를 고침
class OrderService {
    void order(Order o) {
        // 1) 카드사 API 직접 호출
        // 2) JDBC로 직접 저장
        // 3) SMTP로 메일 전송, 문구 하드코딩
    }
}

// 개선: OrderService는 흐름만 조율하고, 각 책임은 협력 객체가 맡음
class OrderService {
    private final PaymentGateway payment;  // 결제 책임
    private final OrderRepository repo;    // 저장 책임
    private final Notifier notifier;       // 알림 책임

    OrderService(PaymentGateway p, OrderRepository r, Notifier n) {
        this.payment = p; this.repo = r; this.notifier = n;
    }
    void order(Order o) { payment.pay(o); repo.save(o); notifier.send(o); }
}
```

SRP 위반을 알아채는 신호도 있어요.

- **상황에 따라 의미가 달라지는 필드**: 토지면 "면적", 건물이면 "층수"를 담는 필드가 있으면 코드 곳곳에 `if`가 생겨요.
- **메서드 안의 타입 분기 `if`**: `if (수컷) ... else (암컷) ...`처럼 분기하는 메서드는 추상 메서드로 두고 하위 클래스로 나누는 게 나아요.
- **생성자 인자가 너무 많음**: 스프링 문서도 생성자 주입 인자가 많으면 책임이 과하다는 신호라고 말해요.

DB 테이블 **정규화**(중복을 없애려고 테이블을 쪼개는 것)도 테이블·컬럼 수준에서 SRP를 적용한 거라고 볼 수 있어요.

### 2. OCP: 개방 폐쇄 원칙

**정의**: 클래스·모듈·함수는 **확장에는 열려 있고, 수정에는 닫혀 있어야** 해요. 쉽게 말해 "기능을 추가할 때 기존 코드를 고치지 않아도 되게" 만들라는 뜻이에요.

용어는 Bertrand Meyer가 1988년에 처음 썼어요. 원래는 상속 기반이었는데, 1990년대에 Martin 등이 "인터페이스 + 다형성"으로 다시 풀었고, 지금은 이 뜻으로 통해요.

```java
// 위반: 결제 수단이 늘 때마다 이 if문을 고쳐야 함 → 기존 카드 결제까지 회귀(멀쩡하던 기능이 다시 깨짐) 위험
if (type.equals("CARD")) { /* ... */ }
else if (type.equals("KAKAO")) { /* ... */ }

// 개선: 인터페이스를 두고, 새 수단은 구현 클래스만 추가
interface PaymentGateway {
    boolean supports(String type);
    void pay(Order o);
}
class CardGateway implements PaymentGateway { /* ... */ }
class KakaoPayGateway implements PaymentGateway { /* ... */ }
// TossPayGateway를 추가해도 기존 코드는 그대로
```

교과서적인 예는 **JDBC**(자바에서 DB에 접속하는 표준 인터페이스)예요. 애플리케이션은 JDBC 인터페이스에만 의존해서, DB를 오라클에서 MySQL로 바꿔도 접속 설정 말고는 코드가 안 바뀌어요. JVM도 비슷해요. 같은 `.class` 파일이 OS가 바뀌어도 그대로 돌아가요.

<Aside type="note" title="OCP는 '절대 수정 금지'가 아니에요">
모든 변경을 미리 예측할 수는 없어요. **자주 바뀔 지점**을 추상화로 감싸서, 그 지점이 늘어날 때만큼은 기존 코드를 안 건드리게 하는 거예요.
</Aside>

### 3. LSP: 리스코프 치환 원칙

**정의**: **하위 타입은 언제나 상위 타입으로 바꿔 넣을 수 있어야** 해요. 상위 타입 변수에 하위 객체를 넣어도, 그 변수를 쓰는 코드가 아무 문제 없이 돌아가야 한다는 뜻이에요.

Barbara Liskov가 1987년에 제시했고, 1994년 논문으로 형식화됐어요. 핵심은 **문법이 아니라 행위(약속)**예요. 컴파일이 되고 "A는 B다"처럼 들려도, 상위 타입을 쓰는 쪽의 기대를 깨면 위반이에요.

#### 고전 예시: 정사각형은 직사각형인가?

수학적으로 정사각형은 직사각형이에요. 그래서 `Square extends Rectangle`로 만들고, 정사각형은 너비와 높이가 같아야 하니 `setWidth`가 높이도 함께 바꾸도록 오버라이드했다고 해 볼게요.

```java
void check(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    // 직사각형을 쓰는 사람은 당연히 20을 기대함
    assert r.area() == 20;
}
check(new Rectangle()); // 20, 통과
check(new Square());    // 너비·높이가 모두 4가 되어 16, 실패
```

`Square`를 `Rectangle` 자리에 넣었더니 결과가 달라졌어요. **치환할 수 없으니 LSP 위반**이에요. 해결 방향으로는 흔히 두 가지가 거론돼요.

- 둘 다 `Shape` 인터페이스를 구현하는 **형제**로 두고 `area()`만 공통으로 둬요. 크기 바꾸는 setter는 상속하지 않아요.
- **불변 객체**로 만들어요. 크기를 바꾸면 새 객체를 돌려주니 "너비만 바꿨는데 높이도 바뀌는" 일이 없어요.

#### 형식 조건 (면접에서 한 단계 더)

**사전조건**(메서드를 부르기 전에 만족해야 할 조건)과 **사후조건**(메서드가 끝난 뒤 보장하는 결과)으로 말하면 이래요.

| 규칙 | 뜻 |
|---|---|
| 사전조건을 강화하면 안 됨 | 부모는 받던 입력을 자식이 거부하면 안 돼요 |
| 사후조건을 약화하면 안 됨 | 부모가 약속한 결과를 자식이 덜 지키면 안 돼요 |
| 불변조건 유지 | 부모가 늘 지키던 성질(예: 잔액 ≥ 0)을 자식도 지켜야 해요 |
| 새 예외 금지 | 부모에 없던 종류의 예외를 던지면 안 돼요 |

실무에서 자주 보는 위반은 "자식이 지원 안 하는 메서드에서 예외를 던지는" 경우예요.

```java
class Payment { void refund() { /* 환불 */ } }
class PointPayment extends Payment {
    void refund() { throw new UnsupportedOperationException(); } // 환불 불가
}
// Payment 목록을 돌며 환불하는 배치가 PointPayment에서 터짐 → 치환 불가
// 개선: 환불 기능을 Refundable 인터페이스로 분리(ISP와 함께 해결)
```

자바 표준 라이브러리에도 논쟁적인 사례가 있어요. `Collections.unmodifiableList()`가 돌려준 `List`에 `add()`를 하면 `UnsupportedOperationException`이 나요. `List` 문서에서 `add`를 "선택적 연산"으로 적어 두긴 했지만, LSP 관점에서 자주 도마에 오르는 예예요.

<Aside type="tip" title="쉽게 외우기: 분류도 vs 조직도">
상속 관계는 "~의 한 종류다"(is a kind of)로 읽혀야 해요. `동물 ← 펭귄`은 자연스럽지만 `아버지 ← 딸`은 어색하죠. 다만 이건 단순화한 설명이라, 면접에서는 "상위 타입의 약속(사전·사후조건)을 지켜야 한다"까지 말하면 좋아요.
</Aside>

### 4. ISP: 인터페이스 분리 원칙

**정의**: 클라이언트(그 인터페이스를 가져다 쓰는 쪽)는 **자기가 쓰지 않는 메서드에 의존하도록 강요받으면 안 돼요.**

```java
// 위반: SMS 알림 하나 만들려는데 이메일·푸시까지 구현해야 함
interface Notifier { void sendEmail(); void sendSms(); void sendPush(); }
class SmsNotifier implements Notifier {
    public void sendEmail() { throw new UnsupportedOperationException(); } // 억지 구현
    public void sendSms() { /* 실제 구현 */ }
    public void sendPush() { throw new UnsupportedOperationException(); }
}

// 개선: 채널과 상관없는 작은 인터페이스 하나
interface Notifier { void send(Message m); }
class SmsNotifier implements Notifier { public void send(Message m) { /* ... */ } }
```

위반 코드의 억지 예외는 앞에서 본 LSP 위반으로도 이어져요. 인터페이스를 잘게 나누면 두 문제가 같이 풀려요.

**SRP와 ISP의 차이**도 자주 물어요. 둘 다 "한 클래스가 너무 많은 걸 떠안은" 문제의 처방이에요.

| | SRP | ISP |
|---|---|---|
| 무엇을 쪼개나 | **클래스** 자체를 나눔 | 클래스는 두고 **인터페이스**를 역할별로 나눔 |
| 예 | 주문·결제·알림 클래스 분리 | 한 클래스가 `남자친구`, `아들`, `사원` 인터페이스를 각각 구현하고, 상대마다 자기 인터페이스로만 접근 |

함께 기억할 말이 있어요. **"상위 클래스는 풍성할수록, 인터페이스는 작을수록 좋다."** 인터페이스는 `Runnable`, `AutoCloseable`처럼 "~할 수 있다"(is able to) 단위로 작게 만드는 게 정석이에요. 자세한 비교는 [추상 클래스 vs 인터페이스](../abstract-interface/)에 있어요.

### 5. DIP: 의존 역전 원칙

**정의**는 두 문장이에요.

1. **고수준 모듈**(업무 흐름을 정하는 쪽, 예: 주문 서비스)은 **저수준 모듈**(세부 기술, 예: 카카오페이 API 클라이언트)에 의존하면 안 돼요. 둘 다 **추상화**에 의존해야 해요.
2. 추상화가 세부사항에 의존하면 안 되고, 세부사항이 추상화에 의존해야 해요.

더 짧게는 "**자기보다 자주 바뀌는 것에 의존하지 마라**"예요.

```java
// 위반: 고수준(OrderService)이 저수준 구체 클래스를 직접 new
class OrderService {
    private final KakaoPayClient client = new KakaoPayClient();
}

// 개선: 추상화(PaymentGateway)에 의존하고, 구현체는 밖에서 넣어 줌
@Service
class OrderService {
    private final PaymentGateway gateway;
    OrderService(PaymentGateway gateway) { this.gateway = gateway; }
}
```

**왜 "역전"인가요?** 원래는 `OrderService → KakaoPayClient`처럼 화살표가 고수준에서 저수준으로 내려가요. 인터페이스를 사이에 두면 `KakaoPayGateway → PaymentGateway`처럼 **저수준 구현이 고수준이 정한 약속을 향해** 의존하게 돼요. 아무것에도 의존하지 않던 저수준 쪽이 이제 위를 바라보니, 화살표 방향이 뒤집힌 거예요.

<Aside type="caution" title="인터페이스만 만든다고 DIP가 아니에요">
인터페이스를 저수준 쪽(예: PG사(결제대행사) SDK 패키지)에 두고 그 SDK의 요청·응답 타입을 그대로 노출하면, 이름만 인터페이스일 뿐 고수준이 여전히 저수준 세부에 묶여 있어요. 추상화는 **쓰는 쪽(고수준)의 필요**에 맞춰 정의하는 게 원래 취지예요.
</Aside>

눈치챘겠지만 DIP 설명은 OCP와 거의 같아요. 인터페이스 하나를 두는 해결책 안에 OCP(확장해도 수정 없음)와 DIP(추상화에 의존)가 함께 들어 있어요. 이렇게 여러 원칙이 한 설계에 겹쳐 있는 경우가 많아요.

### 심화: 6. DIP, DI, IoC는 어떻게 다른가

면접 단골이에요. 세 가지는 층위가 달라요.

| 용어 | 정체 | 한 줄 뜻 |
|---|---|---|
| **DIP**(의존 역전 원칙) | 설계 **원칙** | 무엇에 의존할까? → 추상화에 |
| **DI**(Dependency Injection, 의존성 주입) | 구현 **기법** | 의존 객체를 내가 `new` 하지 않고 밖에서 넣어 받음 |
| **IoC**(Inversion of Control, 제어의 역전) | 더 넓은 **개념** | 객체를 만들고 연결하는 제어권이 내 코드에서 프레임워크로 넘어감 |

스프링 문서는 DI를 IoC의 한 형태로 설명해요. 객체는 생성자 인자나 setter로 "이게 필요해요"라고 **선언만** 하고, **IoC 컨테이너**(스프링이 객체를 만들고 관리하는 공간)가 그 객체(빈)를 만들 때 필요한 것을 넣어 줘요. 객체가 직접 `new` 하는 것과 반대라서 "제어의 역전"이라 불러요.

주의할 점은 **DI를 써도 DIP를 지키지 않을 수 있다**는 거예요. 스프링이 주입해 줘도 받는 타입이 `KakaoPayClient` 같은 구체 클래스면 여전히 구체에 묶여 있어요.

스프링 팀은 **생성자 주입**을 권장해요. 필드를 `final`로 만들 수 있고, 필수 의존성이 `null`이 아님을 보장하며, 완전히 초기화된 객체가 만들어지기 때문이에요. 생성자가 하나뿐이면 `@Autowired`를 생략해도 돼요(Spring 4.3부터로 알려져 있어요).

또 스프링에서는 같은 인터페이스의 빈 여러 개를 `List<PaymentGateway>`나 `Map<String, PaymentGateway>`(키는 빈 이름)로 한꺼번에 주입받을 수 있어요(스프링 문서 "Using @Autowired"). 결제 수단을 추가할 때 구현 빈만 하나 더 만들면 되는 OCP 구조에 자주 쓰여요. 하나만 골라야 할 땐 `@Primary`나 `@Qualifier`를 써요.

### 심화: 7. 과하게 적용하면 생기는 문제

SOLID를 따르면 파일 수가 늘어나는 경향이 있어요. 대개는 이해·유지보수가 쉬워지는 이점이 더 크지만, 지나치면 이런 부작용이 흔히 지적돼요.

- **구현체가 하나뿐인 인터페이스 남발**: `XxxService`와 `XxxServiceImpl`을 1:1로 기계적으로 만드는 경우예요.
- **코드 추적이 어려워짐**: 호출을 따라가면 인터페이스만 나오고, 실제 구현을 찾으려면 몇 단계를 더 들어가야 해요.
- **과설계**(YAGNI 위반, "필요할 때 만들어라"를 어김): 오지 않을 미래를 대비한 추상화가 쌓여요.
- **너무 잘게 쪼갬**: 오히려 관련된 코드가 흩어져 응집도가 떨어져요.

그래서 "두 번째 구현이 실제로 생길 때 인터페이스를 뽑아낸다"는 실용적인 기준이 많이 쓰여요. 다만 외부 결제사, 메일 서버처럼 **바깥 시스템과 맞닿은 경계**는 교체와 테스트를 위해 처음부터 추상화해 두는 편이 이득인 경우가 많아요. 테스트에서 가짜 객체(목)로 바꾸려고 인터페이스를 두기도 하는데, 요즘 Mockito 같은 도구는 구체 클래스도 목으로 만들 수 있어서 이 이유만으로 인터페이스를 강제할 필요는 줄었다는 의견도 있어요.

<details>
<summary>Q. SRP에서 말하는 "책임"이란 무엇인가요?</summary>

**답변(30초)** 책임은 "변경 이유"예요. 메서드가 하나여야 한다는 뜻이 아니라, 그 클래스를 바꿔 달라고 요청하는 주체가 하나여야 한다는 뜻이에요. 예를 들어 주문 서비스에 결제 호출, DB 저장, 메일 발송 코드가 다 있으면 결제팀·DB 담당·마케팅팀이 각자 이유로 같은 클래스를 고치게 돼요. 그래서 결제, 저장, 알림을 별도 객체로 나누고 주문 서비스는 흐름만 조율하게 해요.

**꼬리질문**
- Q. SRP 위반을 어떻게 알아채나요? → 타입에 따라 갈리는 `if` 분기, 상황마다 의미가 바뀌는 필드, 생성자 인자가 지나치게 많은 경우가 신호예요.
- Q. 너무 잘게 나누면? → 관련 코드가 흩어져 오히려 응집도가 떨어지고 추적이 어려워져요.
</details>

<summary>Q. OCP를 지킨 예를 들어 주세요.</summary>

**답변(30초)** 대표적인 예는 JDBC예요. 애플리케이션이 JDBC 인터페이스에만 의존해서 DB를 오라클에서 MySQL로 바꿔도 설정 말고는 코드가 안 바뀌어요. 실무에서는 결제 수단을 `if-else`로 분기하던 코드를 `PaymentGateway` 인터페이스와 수단별 구현체로 바꾸는 게 흔한 예예요. 새 결제 수단은 구현 클래스만 추가하면 되고 기존 코드는 건드리지 않아요.

**꼬리질문**
- Q. 스프링에서는 어떻게 구현하나요? → 같은 인터페이스 구현 빈들을 `Map<String, PaymentGateway>`나 `List`로 주입받아 골라 쓰는 방식이 흔해요.
- Q. 모든 코드를 OCP로 만들어야 하나요? → 아니요. 모든 변경을 예측할 수 없으니 실제로 자주 바뀌는 지점에만 추상화를 둬요.

<details>
<summary>Q. LSP 위반 예를 들어 주세요. 정사각형이 직사각형을 상속하면 왜 문제인가요?</summary>

**답변(30초)** LSP는 하위 타입을 상위 타입 자리에 넣어도 사용하는 코드가 똑같이 동작해야 한다는 원칙이에요. 정사각형이 직사각형을 상속하면 너비를 바꿀 때 높이도 같이 바뀌어야 해요. 그래서 "너비 5, 높이 4로 설정하면 넓이 20"을 기대하는 코드에 정사각형을 넣으면 16이 나와요. 수학적으로는 is-a 관계지만, 상위 타입이 약속한 행위를 깨기 때문에 위반이에요.

**꼬리질문**
- Q. 어떻게 고치나요? → 둘을 `Shape`의 형제로 두고 setter를 상속하지 않거나, 불변 객체로 만들어 크기 변경 시 새 객체를 돌려줘요.
- Q. LSP를 형식적으로 말하면? → 하위 타입은 사전조건을 강화하거나 사후조건을 약화하면 안 되고, 불변조건을 지키며, 부모에 없던 예외를 던지면 안 돼요.
- Q. 자식 메서드에서 `UnsupportedOperationException`을 던지면? → 부모 타입으로 쓰던 코드가 터지니 대표적인 LSP 위반 신호예요. 그 기능을 별도 인터페이스로 분리해요.
</details>

<details>
<summary>Q. ISP와 SRP는 어떻게 다른가요?</summary>

**답변(30초)** 둘 다 한 클래스가 너무 많은 걸 떠안은 문제를 푸는 원칙이에요. SRP는 클래스 자체를 책임별로 나누고, ISP는 클래스는 그대로 두되 그 클래스를 쓰는 쪽이 보는 인터페이스를 역할별로 작게 나눠요. ISP를 지키면 구현 클래스가 안 쓰는 메서드를 억지로 구현하며 예외를 던지는 일이 없어져요. 인터페이스는 `Runnable`처럼 "~할 수 있다" 단위로 작게 만드는 게 좋아요.

**꼬리질문**
- Q. 둘 중 무엇을 먼저 고려하나요? → 보통은 클래스를 나누는 SRP를 먼저 보고, 하나의 객체가 여러 역할을 해야 할 때 ISP로 역할별 인터페이스를 나눠요.
</details>

<details>
<summary>Q. DIP란 무엇이고, DI·IoC와는 어떻게 다른가요?</summary>

**답변(30초)** DIP는 고수준 모듈이 저수준 구체 클래스에 의존하지 말고 둘 다 추상화에 의존하라는 설계 원칙이에요. DI는 그 원칙을 실현하는 기법으로, 의존 객체를 직접 `new` 하지 않고 생성자 등으로 밖에서 넣어 받는 거예요. IoC는 더 넓은 개념으로, 객체 생성과 연결의 제어권이 프레임워크로 넘어간 걸 말해요. 스프링 컨테이너는 DI로 IoC를 구현한 도구이고, DI를 써도 구체 클래스를 주입받으면 DIP는 지켜지지 않아요.

**꼬리질문**
- Q. 왜 "역전"인가요? → 원래 고수준이 저수준을 향하던 의존 화살표가, 인터페이스를 두면 저수준 구현이 고수준이 정한 추상화를 향하게 뒤집히기 때문이에요.
- Q. 인터페이스만 만들면 DIP인가요? → 아니요. 인터페이스가 저수준 세부(예: SDK 타입)를 그대로 드러내면 의미가 없어요. 쓰는 쪽 필요에 맞춰 정의해야 해요.
</details>

<details>
<summary>Q. 스프링은 왜 생성자 주입을 권장하나요?</summary>

**답변(30초)** 생성자 주입을 쓰면 의존 필드를 `final`로 둘 수 있어 불변이 되고, 필수 의존성이 빠지면 객체 자체가 안 만들어지니 `null`이 아님이 보장돼요. 또 객체가 완전히 초기화된 상태로만 만들어져요. 테스트에서도 생성자에 가짜 객체를 넣기만 하면 돼서 편해요. 필수 의존성은 생성자, 선택 의존성은 setter로 받는 게 일반적이에요.

**꼬리질문**
- Q. 생성자 인자가 10개가 넘으면? → 스프링 문서도 이를 책임 과다 신호로 봐요. SRP 관점에서 클래스를 나눌지 검토해요.
</details>

<details>
<summary>Q. SOLID를 과하게 적용하면 어떤 문제가 있나요? 구현체가 하나뿐인데도 인터페이스를 만들어야 하나요?</summary>

**답변(30초)** 과하면 구현체가 하나뿐인 인터페이스가 넘쳐나고, 간접 단계가 늘어 코드 흐름을 따라가기 어려워지며, 오지 않을 미래를 위한 과설계가 돼요. 그래서 교체 가능성이 낮은 내부 로직은 구체 클래스로 시작하고, 두 번째 구현이 생길 때 인터페이스를 뽑는 편이 실용적이라고 생각해요. 다만 결제사나 메일 서버처럼 외부 시스템 경계는 교체와 테스트 때문에 처음부터 추상화하는 게 이득인 경우가 많아요.

**꼬리질문**
- Q. 테스트를 위해 인터페이스가 꼭 필요한가요? → 인터페이스가 있으면 가짜 구현을 넣기 쉽지만, Mockito 같은 도구는 구체 클래스도 목으로 만들 수 있어서 그 이유만으로 강제할 필요는 줄었다는 의견도 있어요.
</details>

## 서술형 연습

<details>
<summary>상황: 카드 결제만 있던 PaymentService에 카카오페이·토스페이·포인트가 추가되면서 if-else가 길어졌고, 수정할 때마다 기존 카드 결제에서 회귀 버그가 납니다. 어떻게 개선할까요?</summary>

**상황 파악**
결제 수단이 늘 때마다 같은 메서드의 `if-else`를 고치고 있어요. 새 수단을 넣는 작업이 기존 수단 코드를 건드리니, 테스트 범위가 매번 전체로 커지고 회귀 버그가 나요. "확장할 때 기존 코드를 수정하는" 구조, 즉 OCP 위반이에요.

**원인 후보**
1. 결제 수단별 로직이 한 메서드에 섞여 있어 서로 간섭함(SRP·OCP 위반)
2. 서비스가 각 결제사 클라이언트 구체 클래스를 직접 의존함(DIP 위반)
3. 포인트처럼 환불이 안 되는 수단이 같은 메서드 흐름에 억지로 끼어 있음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `if-else`를 `switch`로 정리하고 수단별 private 메서드로 분리 | 변경량이 작고 바로 적용 가능 | 수단을 추가할 때 여전히 이 클래스를 고침, 회귀 위험은 그대로 |
| B. `PaymentGateway` 인터페이스 + 수단별 구현 클래스, 스프링 `Map<String, PaymentGateway>` 주입 | 새 수단은 클래스만 추가(OCP), 수단별로 따로 테스트 가능, 서비스는 추상화에만 의존(DIP) | 클래스 수가 늘고 처음 구조를 잡는 비용이 있음 |
| C. B에 더해 `Refundable` 인터페이스를 분리 | 환불 불가 수단이 `refund()`에서 예외를 던지는 LSP 위반을 막음(ISP) | 타입이 하나 더 늘고 환불 흐름에서 타입 확인이 필요 |

**내가 고를 방법**
B를 기본으로 하고, 포인트처럼 환불이 안 되는 수단이 있으니 C까지 적용해요. 결제 수단은 앞으로도 늘어날 게 분명한 "자주 바뀌는 지점"이라 추상화 비용을 치를 가치가 있어요. 환불 배치는 `Refundable`만 받게 해서, 포인트 결제가 섞여도 실행 중에 터지지 않게 해요. A는 당장은 깔끔해 보여도 근본 문제(수정해야 확장됨)를 못 풀어요.

**채점 포인트**: OCP 위반 진단, 인터페이스 + 구현체 분리, DIP(서비스는 추상화에 의존), 스프링 `Map`/`List` 빈 주입, 환불 불가 수단의 LSP 위반과 ISP로 분리, 클래스 수 증가라는 트레이드오프.
</details>

<details>
<summary>상황: 주문 완료 알림을 이메일에서 카카오 알림톡으로 바꿔 달라는 요청이 왔는데, OrderService 안에 SMTP 코드가 박혀 있어 주문 로직까지 다시 테스트·배포해야 합니다.</summary>

**상황 파악**
알림 채널만 바꾸면 되는 요청인데 주문 로직 전체가 영향을 받아요. 주문 클래스가 "알림 방식"이라는 다른 변경 이유까지 품고 있어서(SRP 위반), 그리고 SMTP라는 구체 기술에 직접 묶여 있어서(DIP 위반) 생긴 문제예요.

**원인 후보**
1. 주문과 알림이라는 서로 다른 책임이 한 클래스에 있음
2. 알림을 추상화 없이 구체 기술(SMTP)로 바로 호출함

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `Notifier` 인터페이스로 분리하고 생성자 주입, 구현은 `KakaoAlimtalkNotifier` | 채널 교체가 구현체 교체로 끝남, 주문 로직 재배포 불필요, 테스트 시 가짜 알림 주입 | 주문과 알림이 여전히 같은 흐름에서 동기로 실행돼 알림 실패가 주문에 영향을 줄 수 있음 |
| B. 주문 완료 이벤트를 발행(`ApplicationEventPublisher`)하고 알림은 이벤트를 받아 처리 | 주문은 알림의 존재조차 모름(결합도 최소), 알림을 비동기로 돌려 주문 응답에 영향 없음 | 흐름이 코드에서 바로 안 보여 추적이 어려움, 트랜잭션 커밋 후 발송·실패 재시도를 따로 고민해야 함 |

**내가 고를 방법**
당장은 A로 알림 책임을 떼어 내요. 변경이 작고 효과가 바로 나요. 알림 채널이 더 늘거나 알림 실패가 주문을 막는 일이 생기면 B로 넘어가서, 주문 트랜잭션이 커밋된 뒤에 알림을 보내도록 해요. 처음부터 B로 가면 구조가 복잡해지는 비용이 있어서, 문제가 보일 때 도입하는 게 낫다고 봐요.

**채점 포인트**: SRP(변경 이유 분리), DIP(`Notifier` 추상화), 생성자 주입, 이벤트 기반 분리의 장단점(동기/비동기, 커밋 후 발송), 단계적 도입 판단.
</details>

<details>
<summary>상황: 신입 개발자가 모든 클래스에 XxxService 인터페이스와 XxxServiceImpl을 1:1로 만들어 PR이 매우 커졌습니다. 리뷰어로서 어떻게 피드백할까요?</summary>

**상황 파악**
"DIP를 지키려면 인터페이스가 있어야 한다"는 생각으로 기계적으로 만든 것 같아요. 구현체가 하나뿐이고 교체될 가능성도 낮다면, 파일만 늘고 코드 추적은 어려워져요. 원칙을 목적 없이 적용한 과설계예요.

**원인 후보**
1. 원칙을 "인터페이스를 만드는 규칙"으로 이해함
2. 테스트에서 목을 쓰려면 인터페이스가 필요하다고 생각함
3. 팀에 언제 추상화할지 기준이 없음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 모두 유지 | 일관된 구조, 나중에 구현을 바꾸기 쉬움 | 구현 하나짜리 인터페이스가 넘침, 탐색 비용 증가 |
| B. 모두 제거하고 구체 클래스만 | 코드가 단순하고 흐름이 바로 보임 | 외부 시스템 경계까지 구체에 묶이면 교체·테스트가 어려움 |
| C. 기준을 세워 선별: 외부 시스템 경계(PG사, 메일, 외부 API)는 인터페이스, 내부 로직은 구체 클래스로 시작 | 꼭 필요한 곳에만 추상화, 두 번째 구현이 생기면 그때 추출 | 팀원이 기준을 이해하고 판단해야 함 |

**내가 고를 방법**
C로 피드백해요. 결제사·메일처럼 바뀔 가능성이 크고 테스트에서 가짜로 바꿔야 하는 경계는 인터페이스를 남기고, 나머지는 구체 클래스로 바꾸자고 제안해요. 목 때문이라면 Mockito가 구체 클래스도 목으로 만들 수 있다는 점도 알려 줘요. 인터페이스는 나중에 IDE로 쉽게 뽑을 수 있으니 필요할 때 만드는 게 낫다고 설명해요.

**채점 포인트**: 과설계(YAGNI), 구현 하나짜리 인터페이스의 비용, "두 번째 구현이 생길 때 추출" 기준, 외부 경계는 예외적으로 처음부터 추상화, 테스트 도구로 구체 클래스 목 가능.
</details>

## 필기 포인트

- SOLID 순서: **S**RP → **O**CP → **L**SP → **I**SP → **D**IP.
- 결합도는 **낮게**, 응집도는 **높게**. 반대로 쓴 보기는 오답.
- OCP: 확장에 **열림**, 수정(변경)에 **닫힘**. "확장에 닫힘"은 오답.
- LSP: 하위 타입은 사전조건 **강화 금지**, 사후조건 **약화 금지**.
- ISP: "클라이언트는 사용하지 않는 메서드에 의존하지 않아야 한다."
- DIP: 고수준·저수준 **모두 추상화에** 의존. "저수준이 고수준 구체 클래스에 의존"이 아님.
- DIP는 원칙, DI는 기법, IoC는 제어권이 프레임워크로 넘어간다는 개념.
