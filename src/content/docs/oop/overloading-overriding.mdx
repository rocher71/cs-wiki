:::tip[한 줄 요약]
오버로딩은 이름은 같고 매개변수가 다른 메서드를 여러 개 두는 것으로, 컴파일러가 선언 타입을 보고 미리 골라요. 오버라이딩은 상속받은 메서드를 자식이 같은 시그니처로 다시 정의하는 것으로, 실행할 때 실제 객체를 보고 골라져요. 이 오버라이딩과 동적 바인딩 덕분에 부모 타입 하나로 여러 자식을 다루는 다형성이 가능해요.
:::

## 쉽게 이해하기

카페 키오스크를 떠올려 볼게요. "주문하기" 버튼이 하나인데, 메뉴 이름만 넣으면 기본 사이즈로, 메뉴와 사이즈를 같이 넣으면 그 사이즈로 주문돼요. 이름은 같은데 **넣는 재료(매개변수)에 따라 다른 버튼처럼** 동작하죠. 이게 **오버로딩**이에요. 같은 층에 비슷한 버튼을 옆으로 나란히 실어 둔 모습이에요.

이번엔 프랜차이즈 본사 매뉴얼에 "인사하기: 안녕하세요"라고 적혀 있다고 해요. 제주 지점이 자기 매뉴얼에 "인사하기: 혼저옵서예"라고 덮어 적었어요. 손님이 "지점 직원"이라는 이름표만 보고 인사를 청해도, 실제로 제주 지점 직원이면 제주 인사가 나와요. 본사 문구 **위에 올라타서 가린 것**, 이게 **오버라이딩**이에요.

**다형성**(polymorphism, 같은 호출이 실제 객체에 따라 다르게 동작하는 성질)은 이 두 번째 그림에서 나와요. "지점 직원"이라는 이름표 하나로 서울·제주·부산 직원을 다 부를 수 있고, 각자 자기 방식으로 인사해요.

단, 실제로는 "누구를 부를지"가 두 번에 나눠 정해져요. 어떤 버튼(시그니처)을 누를지는 **코드를 컴파일할 때** 이름표만 보고 정하고, 그 버튼을 누구의 매뉴얼로 처리할지는 **실행할 때** 실제 직원을 보고 정해요.

## 제대로 알기

### 1. 먼저 용어 세 개

- **시그니처**(signature, 메서드를 구별하는 이름표): 메서드 이름 + 매개변수 타입 목록이에요. **반환 타입은 들어가지 않아요.**
- **선언 타입**(컴파일 타임 타입): 변수를 만들 때 적은 타입이에요. `Animal an = new Dog();`에서 `an`의 선언 타입은 `Animal`이에요.
- **실제 타입**(런타임 타입): 변수가 실제로 가리키는 객체의 클래스예요. 위 예에선 `Dog`예요.

### 2. 한눈에 비교

| | 오버로딩(overloading) | 오버라이딩(overriding) |
|---|---|---|
| 한국어(필기 용어) | 중복 정의 | 재정의 |
| 어디서 | 한 클래스 안(상속받은 메서드 포함) | 부모와 자식 사이 |
| 시그니처 | 이름 같고 매개변수가 달라야 함 | 이름·매개변수가 같아야 함 |
| 반환 타입 | 상관없음(단, 반환 타입만 다르면 에러) | 같거나 하위 타입(공변 반환) |
| 언제 정해지나 | 컴파일 시점(정적 바인딩) | 실행 시점(동적 바인딩) |
| 무엇을 보고 | 인자의 선언 타입 | 실제 객체의 클래스 |
| 이점 | 호출하는 쪽이 이름 하나만 기억하면 됨 | `instanceof`나 형변환 없이 자식 구현이 자동 호출 |

### 3. 오버로딩: 컴파일러가 미리 고른다

```java
void m(int x) { }
int  m(int x) { return x; }   // 컴파일 에러: 이미 정의됨 (반환 타입만 다름)

void p(Object o) { System.out.println("p(Object)"); }
void p(String s) { System.out.println("p(String)"); }

Object o = "str";
p(o);     // p(Object)  ← 실제 객체는 String이지만 선언 타입 Object 기준
p(null);  // p(String)  ← 둘 다 되면 더 구체적인 쪽
```

컴파일러는 인자의 **개수와 선언 타입**으로 후보를 찾는데, 3단계로 나눠서 찾아요. 앞 단계에서 하나라도 맞으면 뒤 단계는 보지도 않아요.

| 단계 | 허용하는 변환 | 예시 |
|---|---|---|
| 1단계 | 정확히 일치, 넓히기(`int` → `long`) | `q(long)`, `q(Integer)`, `q(int...)` 중 `q(5)` → `q(long)` |
| 2단계 | 박싱/언박싱(`int` ↔ `Integer`) | `r(Integer)`, `r(long...)` 중 `r(5)` → `r(Integer)` |
| 3단계 | 가변인자(`int...`) | 앞에서 못 찾았을 때만 |

후보가 여럿인데 어느 쪽이 더 구체적인지 못 정하면 `reference to f is ambiguous` 컴파일 에러가 나요. 예를 들어 `f(Integer, long)`과 `f(long, Integer)`가 있을 때 `f(1, 1)`이 그래요.

<Aside type="caution" title="실무 함정: List.remove(1)">
`List<Integer>`에 `[1, 2, 3]`이 있을 때 `list.remove(1)`은 **값 1이 아니라 인덱스 1**을 지워서 `[1, 3]`이 돼요. 1단계에서 `remove(int)`가 바로 맞기 때문이에요. 값 1을 지우려면 `list.remove(Integer.valueOf(1))`처럼 써요.
</Aside>

### 4. 오버라이딩: 실행할 때 실제 객체를 본다

**오버라이딩**은 자식 클래스의 인스턴스 메서드가 부모 인스턴스 메서드와 **같은 시그니처**를 가질 때 일어나요. 시그니처 단위라서, 부모에 같은 이름 오버로드가 두 개 있고 자식이 하나만 재정의하면 나머지 하나는 부모 것이 그대로 상속돼요.

메서드 호출은 **두 단계**로 정해져요.

1. **컴파일 시점**: 선언 타입(`Animal`)만 보고 "어떤 시그니처를 부를지" 고정해요. 바이트코드에 `invokevirtual Animal.speak()`처럼 박혀요.
2. **실행 시점**: JVM이 실제 객체의 클래스(`Dog`)부터 위로 올라가며 그 시그니처의 구현을 찾아요. 이걸 **동적 디스패치**(dynamic dispatch) 또는 **동적 바인딩**이라고 해요.

```java
class Animal {
    void speak()        { System.out.println("Animal.speak"); }
    void eat(Object o)  { System.out.println("Animal.eat(Object)"); }
}
class Dog extends Animal {
    @Override void speak() { System.out.println("Dog.speak"); }
    void eat(String s)  { System.out.println("Dog.eat(String)"); } // 재정의 아님! 새 오버로드
}

Animal an = new Dog();
an.speak();             // Dog.speak            ← 실제 객체 기준
an.eat("hi");           // Animal.eat(Object)   ← 함정
((Dog) an).eat("hi");   // Dog.eat(String)
```

`an.eat("hi")`가 왜 Animal 것일까요? 컴파일러는 `Animal`만 보고 `eat(Object)`를 골랐어요. 그런데 Dog의 `eat(String)`은 매개변수 타입이 달라서 `eat(Object)`를 재정의한 게 아니라 **새 오버로드**예요. 실행 시점에 Dog에서 `eat(Object)` 재정의를 찾아봐도 없으니 Animal 것이 실행돼요.

부모 메서드 안에서 `this.speak()`를 불러도 실제 객체가 Dog면 Dog의 `speak()`가 실행돼요. 부모가 흐름을 짜고 자식이 단계만 채우는 템플릿 메서드 패턴이 이 성질을 이용해요.

### 5. 다형성: 업캐스팅과 다운캐스팅

**업캐스팅**(upcasting)은 자식 객체를 부모 타입 변수에 담는 거예요. 형변환을 안 적어도 자동으로 돼요.

```java
Animal a = new Dog();   // 업캐스팅, 자동
a.speak();              // Dog.speak (실제 객체의 구현)
a.fetch();              // 컴파일 에러: Animal에는 fetch()가 없음

Dog d = (Dog) a;        // 다운캐스팅, 명시 필요. 실제 객체가 Dog라 성공
Dog x = (Dog) new Animal(); // 컴파일은 통과, 실행 시 ClassCastException

if (a instanceof Dog dog) { // Java 16+ 패턴 매칭: 확인과 캐스팅을 한 번에
    dog.fetch();
}
```

- 부모 타입 변수는 **리모컨**과 비슷해요. 리모컨에 있는 버튼(부모에 선언된 메서드)만 누를 수 있지만, 누르면 실제 기계(자식 객체)가 자기 방식으로 동작해요.
- **다운캐스팅**(downcasting)은 부모 타입 변수를 자식 타입으로 바꾸는 거예요. 실제 객체가 그 타입이 아니면 실행 중에 `ClassCastException`이 나요. 그래서 `instanceof`로 먼저 확인해요.
- `Dog p = new Animal();`처럼 캐스팅 없이 부모 객체를 자식 변수에 넣는 건 컴파일 에러예요.

다형성의 진짜 이점은 **분기문이 사라진다**는 거예요. `Animal[]`에 Dog, Cat, Penguin을 담고 반복문에서 `animals[i].speak()`만 부르면 각자 알맞게 울어요. `if (a instanceof Dog) ... else if (a instanceof Cat) ...` 같은 코드가 필요 없어요.

<Aside type="note" title="자식 객체 안에 부모 객체가 따로 있나요?">
아니에요. `new Dog()`를 하면 힙에 **객체가 딱 하나** 생기고, 그 안에 부모(Animal)에서 물려받은 필드와 Dog 자신의 필드가 함께 들어 있어요. 부모 객체가 별도로 하나 더 만들어지는 게 아니에요.
</Aside>

### 6. super 키워드

- `super.speak()`는 **바로 위 부모 클래스의 구현**을 불러요. 동적 조회를 하지 않아요(바이트코드 `invokespecial`).
- 주로 재정의한 메서드 안에서 "부모 동작은 그대로 하고 조금 덧붙이기"에 써요.
- `super`는 부모 객체를 따로 가리키는 게 아니에요. **같은 객체, 즉 this**에 대해 부모 클래스에 정의된 구현이나 필드를 지정하는 표현이에요.
- `super.super.speak()`는 문법 에러예요. 조부모 구현을 직접 부르는 방법은 없어요.
- 생성자 첫 줄의 `super(...)`는 부모 생성자 호출로, 용도가 달라요.

```java
class Dog extends Animal {
    @Override void speak() {
        super.speak();                  // Animal.speak 먼저
        System.out.println("멍멍");     // 덧붙이기
    }
}
```

### 7. @Override는 왜 붙이나

`@Override`는 "부모 메서드를 재정의하려는 거예요"라고 컴파일러에게 알리는 표시(애너테이션)예요. 실제로 재정의가 아니면 `method does not override or implement a method from a supertype` 에러를 내요.

위의 `eat(String)` 같은 사고, 즉 **매개변수 타입을 잘못 적어서 오버라이딩 대신 오버로딩이 되는 실수**를 컴파일할 때 바로 잡아 줘요. 안 붙여도 규칙만 맞으면 오버라이딩은 성립하지만, 붙이는 게 권장돼요. static 메서드나 private 메서드에 붙이면 에러가 나요.

### 8. 오버라이딩 규칙 (어기면 컴파일 에러)

| 항목 | 규칙 | 예 |
|---|---|---|
| 반환 타입 | 기본형은 완전히 같아야 함. 참조형은 같거나 **하위 타입** 가능(공변 반환, Java 5+) | `Animal self()` → `Dog self()` OK, `int` → `long` 에러 |
| 접근 제어자 | **같거나 더 넓게**만 | `protected` → `public` OK, `public` → (default) 에러 |
| checked 예외 | 부모보다 **더 많거나 넓게** 던질 수 없음. 같거나 좁거나 아예 안 던지기는 OK | 없던 `throws Exception` 추가 에러. unchecked(`RuntimeException` 계열)는 제한 없음 |
| final 메서드 | 재정의 불가 | final 클래스는 상속 자체가 불가 |
| private 메서드 | 상속이 안 되니 재정의 대상이 아님 | 자식에 같은 시그니처를 만들면 그냥 별개 메서드 |
| static ↔ 인스턴스 | 섞으면 에러 | 부모 static을 자식 인스턴스 메서드로(또는 반대로) 만들 수 없음 |

접근 제어자를 좁힐 수 없는 이유는 간단해요. 부모 타입 변수로 부를 수 있던 메서드가 자식 객체에선 갑자기 못 부르게 되면, "부모 자리에 자식을 넣어도 된다"는 약속이 깨지기 때문이에요.

생성자는 클래스의 멤버가 아니라서 상속되지 않고, 따라서 **오버라이딩도 안 돼요.** 오버로딩(매개변수가 다른 생성자 여러 개)만 가능해요.

### 9. 다형성이 없는 것: static 메서드와 필드

**static 메서드**는 자식에 같은 시그니처를 만들어도 오버라이딩이 아니라 **숨김**(hiding)이에요. 어떤 게 불릴지는 선언 타입으로 정해져요(`invokestatic`).

**필드**도 마찬가지예요. 자식이 같은 이름 필드를 선언하면 부모 필드를 가릴 뿐이고, 객체 안에는 두 필드가 **모두** 있어요. 필드 접근은 참조 변수의 타입만 봐요.

```java
class Animal { String name = "animal-field"; static String kind() { return "Animal.static"; } }
class Dog extends Animal { String name = "dog-field"; static String kind() { return "Dog.static"; } }

Animal an = new Dog();
an.name;          // "animal-field"  ← 선언 타입 기준
((Dog) an).name;  // "dog-field"
an.kind();        // "Animal.static" ← 선언 타입 기준 (경고 대상, 클래스명으로 부르는 게 정석)
Dog.kind();       // "Dog.static"
```

실무에서는 필드 숨김을 피하고, 타입별로 값이 달라야 하면 **getter를 오버라이드**해요.

<Aside type="caution" title="생성자에서 오버라이드 가능한 메서드 호출 금지">
부모 생성자에서 `init()`을 부르고 자식이 `init()`을 재정의하면, **자식 필드가 아직 초기화되기 전에** 자식 `init()`이 실행돼요. 자식 필드 `int v = 7;`이 있어도 이때는 `0`으로 보이고, 참조 필드라면 `null`이라 NPE가 날 수 있어요.
</Aside>

### 10. 오버로딩도 다형성일까?

교과서에서는 다형성의 기본 형태로 오버라이딩과 오버로딩을 함께 소개하기도 하지만, 오버로딩을 다형성으로 볼지는 의견이 갈려요. 면접에서 "자바의 다형성"을 물으면 **부모 타입 참조 + 오버라이딩 + 동적 바인딩**을 중심으로 답하는 게 안전해요.

<summary>Q. 오버로딩과 오버라이딩의 차이를 설명해 주세요.</summary>

**답변(30초)** 오버로딩은 한 클래스 안에서 이름은 같고 매개변수가 다른 메서드를 여러 개 두는 것이고, 오버라이딩은 상속받은 메서드를 자식이 같은 시그니처로 다시 정의하는 거예요. 가장 큰 차이는 결정 시점이에요. 오버로딩은 컴파일러가 인자의 선언 타입으로 미리 고르고, 오버라이딩은 실행할 때 실제 객체의 클래스를 보고 구현을 골라요.

**꼬리질문**
- Q. 반환 타입만 다르게 오버로딩할 수 있나요? → 안 돼요. 반환 타입은 시그니처에 없어서 "이미 정의됨" 컴파일 에러가 나요.
- Q. 생성자는 오버라이딩되나요? → 안 돼요. 생성자는 멤버가 아니라 상속되지 않아요. 오버로딩만 돼요.
- Q. `Object o = "str"; p(o);`에서 `p(Object)`와 `p(String)` 중 뭐가 불리나요? → `p(Object)`예요. 오버로딩은 실제 객체가 아니라 선언 타입으로 골라요.
</details>

<details>
<summary>Q. 다형성이란 무엇이고 자바에서 어떻게 구현되나요?</summary>

**답변(30초)** 다형성은 같은 호출이 실제 객체에 따라 다르게 동작하는 성질이에요. 자바에서는 부모 타입 변수에 자식 객체를 담는 업캐스팅, 자식의 오버라이딩, 그리고 실행 시점에 실제 객체의 구현을 찾는 동적 바인딩으로 구현돼요. 덕분에 `instanceof` 분기나 형변환 없이 부모 타입 하나로 여러 구현을 다룰 수 있어서, 새 타입을 추가해도 호출하는 코드를 고치지 않아도 돼요.

**꼬리질문**
- Q. 정적 바인딩과 동적 바인딩의 차이는? → 정적은 컴파일 시점에 선언 타입으로 정해지고(오버로딩, static 메서드, 필드, `super.`, private), 동적은 실행 시점에 실제 객체로 정해져요(인스턴스 메서드 오버라이딩).
- Q. 필드도 다형성이 적용되나요? → 아니요. 필드는 숨김(hiding)이라 참조 변수의 선언 타입 기준으로 접근돼요.
- Q. 다운캐스팅은 언제 위험한가요? → 실제 객체가 그 타입이 아니면 컴파일은 통과해도 실행 중 `ClassCastException`이 나요. `instanceof`로 먼저 확인해요.
</details>

<details>
<summary>Q. 오버라이딩할 때 지켜야 할 규칙은?</summary>

**답변(30초)** 시그니처는 같아야 하고, 반환 타입은 같거나 하위 타입이어야 해요(공변 반환). 접근 제어자는 같거나 더 넓게만 바꿀 수 있고, checked 예외는 부모보다 더 넓게 던질 수 없어요. final 메서드는 재정의할 수 없고, private 메서드는 상속되지 않아서 재정의 대상이 아니에요. 이 규칙들은 부모 자리에 자식을 넣어도 문제없이 쓸 수 있게 하려는 거예요.

**꼬리질문**
- Q. static 메서드는 오버라이딩되나요? → 안 돼요. 같은 시그니처를 만들면 숨김(hiding)이고, 선언 타입 기준으로 불려요.
- Q. 접근 제어자를 왜 좁힐 수 없나요? → 부모 타입으로 부를 수 있던 메서드를 자식에서 못 부르게 되면 다형성이 깨지기 때문이에요.
- Q. unchecked 예외도 제한되나요? → 아니요. `RuntimeException` 계열은 제한이 없어요.
</details>

<details>
<summary>Q. @Override는 왜 붙이나요?</summary>

**답변(30초)** 재정의하려는 의도를 컴파일러에게 알려서 실수를 막으려고 붙여요. 매개변수 타입을 잘못 적으면 오버라이딩이 아니라 새 오버로드가 되는데, 이러면 부모 타입으로 호출할 때 내 메서드가 안 불려요. `@Override`가 있으면 이런 경우를 컴파일 에러로 바로 잡아 줘요. 안 붙여도 오버라이딩은 되지만 붙이는 게 권장돼요.

**꼬리질문**
- Q. 대표적인 사고 예시는? → `equals(Object)`를 `equals(MyType)`으로 정의하면 재정의가 아니라 오버로드라서 `HashSet` 같은 컬렉션이 내 `equals`를 쓰지 않아요.
- Q. static 메서드에 붙이면? → `static methods cannot be annotated with @Override` 컴파일 에러예요.
</details>

<details>
<summary>Q. super 키워드는 무엇이고, super.super도 쓸 수 있나요?</summary>

**답변(30초)** `super.메서드()`는 바로 위 부모 클래스의 구현을 호출해요. 주로 재정의한 메서드 안에서 부모 동작을 재사용하고 덧붙일 때 써요. 별도의 부모 객체가 있는 게 아니라 같은 객체에 대해 부모 클래스의 구현을 지정하는 거예요. `super.super`는 문법 에러라서 조부모 구현을 직접 부를 수는 없어요.

**꼬리질문**
- Q. `super.speak()`도 동적 바인딩되나요? → 아니요. 부모 구현으로 고정돼요(`invokespecial`).
- Q. 생성자의 `super(...)`와는 뭐가 다른가요? → 그건 부모 생성자 호출이고, 생성자 첫 줄에서만 쓸 수 있어요.
</details>

<details>
<summary>Q. 생성자에서 오버라이드 가능한 메서드를 호출하면 어떻게 되나요?</summary>

**답변(30초)** 실제 객체가 자식이면 자식의 재정의 메서드가 실행되는데, 그 시점엔 자식 필드가 아직 초기화되지 않았어요. 그래서 기본형 필드는 0, 참조형 필드는 null로 보이고, NPE 같은 버그가 생길 수 있어요. 그래서 생성자에서는 오버라이드할 수 없는 private이나 final 메서드만 부르는 게 안전해요.

**꼬리질문**
- Q. 왜 자식 필드가 초기화 전인가요? → 자식 생성자는 부모 생성자부터 실행한 뒤에 자기 필드를 초기화하기 때문이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제 수단이 늘 때마다 if-else 분기를 고치다가 배포 장애가 났습니다. 구조를 어떻게 바꾸겠습니까?</summary>

**상황 파악**
`if (type == CARD) ... else if (type == TOSS_PAY) ...` 같은 분기가 결제·환불·수수료 계산 등 여러 곳에 흩어져 있어요. 새 결제 수단을 추가할 때마다 모든 분기를 찾아 고쳐야 하고, 한 군데라도 빠뜨리면 장애가 나요. 문제의 본질은 "타입별로 다른 동작"을 호출하는 쪽이 직접 판단하고 있다는 거예요.

**원인 후보**
1. 결제 수단별 동작이 한 클래스의 조건문에 몰려 있음
2. 새 수단 추가가 "기존 코드 수정"을 요구하는 구조(변경에 닫혀 있지 않음)
3. 분기 누락을 컴파일러가 잡아 주지 못함

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `PaymentMethod` 인터페이스 + 수단별 구현 클래스, 호출부는 `method.pay()`만 부름(오버라이딩 + 다형성) | 새 수단은 클래스 추가만 하면 됨. 호출 코드 수정 없음(OCP) | 클래스 수가 늘어나고, 흐름이 여러 파일에 흩어져 처음 읽기 어려울 수 있음 |
| B. 분기는 유지하되 한 곳(enum + switch)으로 모으기 | 구조 변경이 작고 한눈에 보임 | 수단이 늘수록 switch가 커지고, 결국 기존 코드 수정은 계속 필요 |

**내가 고를 방법**
결제 수단은 계속 늘어날 가능성이 높고 수단마다 결제·환불·수수료 동작이 다르니 A를 고르겠어요. 호출하는 쪽은 부모 타입(인터페이스)만 알고, 실제 동작은 실행 시점에 각 구현체의 오버라이딩된 메서드가 맡아요. 구현체에는 `@Override`를 꼭 붙여 시그니처 실수를 막아요. 수단이 두세 개로 고정이고 늘 계획이 없다면 B로도 충분해요.

**채점 포인트**: 다형성(부모 타입 참조), 오버라이딩, 동적 바인딩, OCP(확장에 열림·변경에 닫힘), 클래스 수 증가 트레이드오프, `@Override`, 대안 비교.
</details>

<details>
<summary>상황: equals를 구현했는데 HashSet에 같은 데이터가 중복으로 들어갑니다.</summary>

**상황 파악**
같은 값을 가진 객체를 두 번 넣었는데 중복 제거가 안 돼요. 컬렉션은 `equals(Object)`를 호출하는데, 내가 만든 메서드가 실제로 그걸 재정의했는지부터 의심해야 해요.

**원인 후보**
1. `equals(Object)`가 아니라 `equals(MyType)`으로 정의해서 **재정의가 아니라 오버로드**가 됨. 컬렉션은 `Object` 타입으로 부르므로 내 메서드는 안 불리고 `Object.equals`(주소 비교)가 실행됨
2. `equals`는 맞게 재정의했지만 `hashCode`를 재정의하지 않음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 매개변수를 `Object`로 고치고 `@Override`를 붙임. `hashCode`도 함께 재정의 | 근본 해결, 같은 실수를 컴파일러가 잡아 줌 | 기존 클래스마다 점검이 필요 |
| B. 정적 분석 도구나 IDE 검사로 `@Override` 누락·`equals` 오버로드를 경고 | 팀 전체에 같은 실수를 미리 막음 | 도구 도입·규칙 설정 비용, 경고 무시 위험 |

**내가 고를 방법**
당장은 A로 고치고, 재발 방지를 위해 B로 팀 규칙을 만들어요. 원리를 말하면, 오버로딩은 컴파일 시점에 선언 타입(`Object`)으로 시그니처가 정해지고 실행 시점에는 그 시그니처의 재정의만 찾기 때문에, 매개변수 타입이 다른 메서드는 절대 불리지 않아요.

**채점 포인트**: 오버로딩 vs 오버라이딩 구분, 컴파일 시점 시그니처 결정, `@Override`, `equals`와 `hashCode` 함께 재정의, 재발 방지책.
</details>

<details>
<summary>상황: 이벤트 처리기에서 운영 중 ClassCastException이 터졌습니다.</summary>

**상황 파악**
`Event`를 받아 `(OrderEvent) event`로 다운캐스팅하는 코드가 있었는데, 새 이벤트 타입이 추가된 뒤 그 이벤트가 같은 처리기로 들어와 장애가 났어요. 다운캐스팅은 컴파일을 통과해도 실제 객체가 그 타입이 아니면 실행 중에 터져요.

**원인 후보**
1. 타입 확인 없이 다운캐스팅
2. 처리 로직이 이벤트 클래스 밖(처리기)에 있어서 타입마다 캐스팅이 필요한 구조

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `if (event instanceof OrderEvent e)` 패턴 매칭으로 확인 후 처리, 모르는 타입은 로그·무시 | 수정 범위가 작고 즉시 적용 가능 | 타입이 늘면 분기가 계속 늘어남 |
| B. 처리 로직을 이벤트 쪽 다형 메서드(`event.handle()`)로 옮김 | 캐스팅 자체가 사라짐, 새 타입은 구현만 추가 | 이벤트 클래스에 로직이 붙어 책임이 커질 수 있음 |

**내가 고를 방법**
장애 대응으로 먼저 A를 적용해 터지지 않게 막아요. 이후 타입별 처리가 계속 늘어날 구조라면 B로 옮겨 캐스팅을 없애요.

**채점 포인트**: 다운캐스팅은 런타임 검사, `ClassCastException`, `instanceof`(패턴 매칭), 다형 메서드로 분기 제거, 즉시 조치와 구조 개선 구분.
</details>

## 필기 포인트

- **출력 문제 공식**: `Parent p = new Child();`일 때 `p.method()`는 **Child**, `p.field`와 `p.staticMethod()`는 **Parent**.
- "반환 타입만 다르면 오버로딩 가능" → **X**(매개변수가 달라야 함).
- "오버라이딩 시 접근 제어자를 더 좁게 할 수 있다" → **X**(같거나 넓게만).
- "static 메서드는 오버라이딩된다" → **X**(숨김).
- "private 메서드를 자식에서 재정의할 수 있다" → **X**(상속 안 되므로 별개 메서드).
- 오버로딩 선택 우선순위: **정확/넓히기 > 박싱 > 가변인자**.
- 정보처리기사 용어: 오버로딩 = **중복 정의**, 오버라이딩 = **재정의**.
