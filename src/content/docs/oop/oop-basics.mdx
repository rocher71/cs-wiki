## 쉽게 이해하기

자판기를 떠올려 보세요. 자판기 안에는 돈통, 음료 재고, 거스름돈 계산 장치가 들어 있어요. 우리는 그 속을 열지 않고 **버튼**만 눌러요. 자판기는 "돈이 모자라면 안 내준다" 같은 규칙을 스스로 지켜요.

객체지향은 프로그램을 이런 자판기 여러 대로 짜는 방식이에요. 각 자판기(**객체**)는 자기 물건(**데이터**)과 버튼(**기능**)을 함께 가지고, 다른 자판기와는 버튼으로만 대화해요.

반대로 예전 방식은 창고 하나에 돈과 재고를 쌓아 두고, 여러 직원이 각자 창고에 들어가 직접 꺼내 가는 모습이에요. 직원이 적을 땐 편하지만, 많아지면 누가 돈을 잘못 꺼냈는지 찾기 어려워요.

단, 실제로는 객체도 버튼 안쪽은 순서대로 실행되는 코드예요. 차이는 "코드를 어떤 단위로 나누고, 규칙을 누가 책임지느냐"에 있어요.

## 제대로 알기

### 1. 절차지향 vs 객체지향

**절차지향**(procedural, 순서대로 실행할 명령을 함수로 나눠 짜는 방식)에서는 데이터(변수)와 그 데이터를 다루는 함수를 따로 만들어요.

**객체지향**(object-oriented, 데이터와 기능을 한 덩어리로 묶는 방식)에서는 둘을 **객체**로 묶어요. 자바 공식 튜토리얼은 객체가 **상태**(state)와 **행위**(behavior)를 가진다고 설명해요. 상태는 **필드**(객체가 가진 변수)에, 행위는 **메서드**(객체가 가진 함수)에 담아요.

사람은 세상을 하나하나가 아니라 "강아지", "자동차"처럼 **분류**해서 이해해요. 이 분류가 **클래스**(class, 객체를 만드는 설계도)이고, 분류에 속하는 구체적인 하나가 **객체**(object)예요. 클래스와 객체, static은 [클래스·객체·static](../class-object-static/)에서 자세히 다뤄요.

| 구분 | 절차지향 | 객체지향 |
|---|---|---|
| 나누는 단위 | 함수(할 일 순서) | 객체(데이터 + 기능) |
| 데이터 위치 | 함수 바깥, 여럿이 공유 | 객체 안, 메서드로만 접근 |
| 잘 맞는 곳 | 짧은 스크립트, 단순 계산 | 크고 자주 바뀌는 프로그램 |

절차지향이 나쁜 게 아니에요. 짧은 계산은 절차형이 더 간단해요. 객체지향은 프로그램이 커지고 **변경이 잦을 때** 고칠 곳을 좁히는 데 강해요.

### 2. 캡슐화: 내부는 숨기고 버튼만 보여 준다

**캡슐화**(encapsulation)는 객체의 데이터를 밖에서 직접 못 건드리게 숨기고, 메서드를 통해서만 다루게 하는 거예요. **정보 은닉**(information hiding)이라고도 불러요. 이렇게 하면 객체가 "이 값은 이런 규칙으로만 바뀐다"를 스스로 지킬 수 있어요.

```java
class Account {
    private long balance;              // 밖에서 직접 못 바꿈
    void withdraw(long amount) {
        if (amount <= 0 || amount > balance)
            throw new IllegalArgumentException("잔액 부족");
        balance -= amount;             // 규칙 검사 후에만 변경
    }
    long getBalance() { return balance; }
}
```

자바에서는 **접근 제어자**(access modifier, 누가 이 필드·메서드를 볼 수 있는지 정하는 키워드)로 캡슐화를 해요. **패키지**(package)는 관련 클래스를 모아 둔 폴더 같은 묶음이고, **UML**은 클래스 구조를 그림으로 그리는 표준 표기법이에요.

| 접근 제어자 | 볼 수 있는 범위 | UML 기호 |
|---|---|---|
| `private` | 같은 클래스 안 | `-` |
| (default, 아무것도 안 씀) | 같은 패키지 | `~` |
| `protected` | 같은 패키지 + 하위 클래스 | `#` |
| `public` | 어디서나 | `+` |

<Aside type="caution" title="private + getter/setter = 캡슐화?">
수단일 뿐이에요. 필드를 private으로 막아 놓고 모든 필드에 setter를 열면, 밖에서 아무 값이나 넣을 수 있어서 public과 거의 같아져요. 핵심은 "규칙 검사와 상태 변경을 객체 안에서 한다"예요.
</Aside>

### 3. 상속: 공통 부분을 물려받는다

**상속**(inheritance)은 한 클래스가 다른 클래스의 필드와 메서드를 물려받는 거예요. 물려주는 쪽을 **상위 클래스**(superclass, 부모), 받는 쪽을 **하위 클래스**(subclass, 자식)라고 해요. 자바에서는 `extends`로 써요.

```java
class Animal { void breathe() { System.out.println("숨쉬기"); } }
class Dog extends Animal { void bark() { System.out.println("멍"); } }
// new Dog().breathe();  // Animal에서 물려받은 메서드
```

- 자바 클래스는 부모를 **하나만** 가질 수 있어요(단일 상속). 인터페이스(아래 4번에서 설명)는 여러 개 구현할 수 있어요.
- 상속은 "하위 클래스는 상위 클래스의 **한 종류다**"(is a kind of)가 성립할 때 써요. 개는 동물의 한 종류예요.
- 코드 재사용만 보고 상속하면 자식이 부모 구현에 강하게 묶여요. 그래서 "상속보다 조합"이라는 원칙이 있어요. [상속보다 조합](../inheritance-composition/)에서 이어서 봐요.

### 4. 추상화: 필요한 핵심만 남긴다

**추상화**(abstraction)는 문제에 필요한 핵심만 남기고 나머지는 빼는 거예요. 같은 "사람"이라도 병원 프로그램은 혈액형을, 은행 프로그램은 계좌를 남겨요. 클래스를 설계하는 일 자체가 추상화예요.

코드에서는 **인터페이스**(interface, 몸체 없는 메서드 목록으로 "무엇을 할 수 있는지"만 정한 계약)나 **추상 클래스**로 "무엇을 하는지"만 정하고 "어떻게 하는지"는 숨겨요. 공식 튜토리얼은 인터페이스를 TV 버튼에 비유해요. 우리는 전원 버튼이 무엇을 하는지만 알고, 안의 회로는 몰라도 돼요.

```java
interface Payment { void pay(long amount); }  // 무엇을 하는지만 정함
```

클래스가 `implements`로 인터페이스를 따르겠다고 해 놓고 메서드를 다 구현하지 않으면 컴파일 에러가 나요. 계약을 컴파일러가 지켜 줘요. 둘의 차이는 [추상 클래스 vs 인터페이스](../abstract-interface/)에서 다뤄요.

<Aside type="tip" title="추상화와 캡슐화, 뭐가 달라요?">
표준 정의가 딱 정해진 건 아니지만, 보통 관점으로 나눠 말해요. 추상화는 "바깥에 **무엇을 보여 줄지**" 정하는 설계 관점이고, 캡슐화는 "나머지를 **어떻게 숨기고 지킬지**" 정하는 구현 관점이에요. 둘은 짝으로 쓰여요.
</Aside>

### 5. 다형성: 같은 호출, 다른 동작

**다형성**(polymorphism)은 같은 타입의 변수로 여러 종류의 객체를 다루고, 같은 메서드를 불러도 **실제 객체에 따라 다르게 동작**하는 거예요.

```java
class Card implements Payment { public void pay(long a) { System.out.println("카드 " + a); } }
class Toss implements Payment { public void pay(long a) { System.out.println("토스 " + a); } }

Payment p = new Toss();   // 변수 타입은 Payment
p.pay(1000);              // 실제 객체(Toss)의 pay 실행 → "토스 1000"
```

`p`에 `new Card()`를 넣으면 같은 `p.pay(1000)`이 카드 결제를 해요. 부르는 코드는 한 글자도 안 바뀌어요. 자바는 실행할 때 실제 객체를 보고 **오버라이딩**(overriding, 자식이 부모 메서드를 다시 정의하는 것)된 메서드를 골라요. 이걸 **동적 바인딩**(dynamic binding)이라고 해요.

**오버로딩**(overloading, 이름은 같고 매개변수가 다른 메서드를 여러 개 두는 것)도 다형성으로 묶어 설명하기도 해요. 다만 오버로딩은 컴파일할 때 정해지니까, 면접에서는 "다형성의 핵심은 상위 타입 참조 + 오버라이딩"이라고 말하고 오버로딩은 정적 다형성으로 따로 구분하는 편이 안전해요. [오버로딩 vs 오버라이딩과 다형성](../overloading-overriding/)에서 자세히 봐요.

| 특징 | 한 줄 뜻 | 자바 도구 | 자세히 |
|---|---|---|---|
| 캡슐화 | 내부를 숨기고 메서드로만 다룸 | `private`, 메서드 | [클래스·객체·static](../class-object-static/) |
| 상속 | 공통 코드를 물려받음 | `extends` | [상속보다 조합](../inheritance-composition/) |
| 추상화 | 핵심만 계약으로 남김 | `interface`, `abstract` | [추상 클래스 vs 인터페이스](../abstract-interface/) |

### 심화: 7. 응집도와 결합도: 좋은 설계의 잣대

네 가지 특징을 왜 쓰는지 한 문장으로 말하면 "응집도는 높이고 결합도는 낮추려고"예요.

- **응집도**(cohesion): 한 클래스 안의 요소들이 하나의 목적에 얼마나 모여 있는지예요. **높을수록** 좋아요.
- **결합도**(coupling): 클래스끼리 서로에게 얼마나 기대고 있는지예요. **낮을수록** 좋아요. 결합도가 높으면 하나를 고칠 때 다른 곳도 줄줄이 고쳐야 해요.

| 특징 | 응집도·결합도에 주는 영향 |
|---|---|
| 캡슐화 | 관련 데이터와 규칙을 한곳에 모아 응집도↑, 내부를 숨겨 결합도↓ |
| 추상화·다형성 | 구체 클래스 대신 인터페이스에 기대게 해서 구현을 바꿔도 결합도↓ |
| 상속 | 부모와 자식을 강하게 묶어서 잘못 쓰면 결합도↑ |

이 생각을 원칙 다섯 개로 정리한 게 [SOLID 원칙](../solid/)이에요. 자주 쓰이는 설계 모양을 모아 둔 디자인 패턴은 [생성 패턴: 싱글톤·팩토리·빌더](../patterns-creational/)부터 시작해요.

<summary>Q. 객체지향 프로그래밍이란 무엇이고, 절차지향과 어떻게 다른가요?</summary>

**답변(30초)** 객체지향은 데이터와 그 데이터를 다루는 기능을 객체 하나로 묶어서 프로그램을 짜는 방식이에요. 절차지향은 데이터와 함수를 따로 두고 함수가 공유 데이터를 직접 다뤄요. 객체지향은 데이터를 객체 안에 숨기고 메서드로만 다루게 해서, 프로그램이 커지고 자주 바뀔 때 고칠 곳을 좁혀요. 다만 짧은 계산 같은 일은 절차형이 더 단순할 수 있어서, 어느 쪽이 항상 낫다기보다 문제 크기와 변경 빈도에 따라 골라요.

**꼬리질문**
- Q. 자바는 완전히 객체지향인가요? → 코드를 클래스 단위로 나누지만, 메서드 안은 위에서 아래로 순서대로 실행되는 절차형이에요. 차이는 코드를 나누는 단위와 책임을 두는 위치예요.
- Q. 클래스와 객체의 차이는? → 클래스는 설계도(분류)이고, 객체는 그 설계도로 만든 실제 하나예요.
</details>

<details>
<summary>Q. 객체지향의 4대 특징을 설명해 주세요.</summary>

**답변(30초)** 캡슐화, 상속, 추상화, 다형성이에요. 캡슐화는 내부 데이터를 숨기고 메서드로만 다루게 하는 것, 상속은 상위 클래스의 필드와 메서드를 물려받는 것이에요. 추상화는 필요한 핵심만 인터페이스 같은 계약으로 남기는 것, 다형성은 같은 상위 타입 변수로 여러 객체를 다루고 같은 호출이 실제 객체에 따라 다르게 동작하는 것이에요. 결국 네 가지 모두 응집도를 높이고 결합도를 낮춰서 변경에 강한 코드를 만들려는 도구예요.

**꼬리질문**
- Q. 넷 중 가장 중요하다고 생각하는 건? → 정답은 없지만 다형성을 꼽기 좋아요. 호출하는 쪽이 인터페이스에만 의존하게 해서 구현을 바꾸거나 추가해도 기존 코드를 안 고치게 해 주기 때문이에요.
- Q. 자바는 다중 상속이 되나요? → 클래스는 부모를 하나만 가질 수 있고, 인터페이스는 여러 개 구현할 수 있어요.
</details>

<details>
<summary>Q. 캡슐화는 왜 필요한가요? 필드를 private으로 하고 getter/setter를 만들면 캡슐화인가요?</summary>

**답변(30초)** 캡슐화는 객체가 자기 상태를 스스로 지키게 하려고 필요해요. 예를 들어 잔액을 private으로 두고 `withdraw()` 안에서만 줄이게 하면 "잔액은 음수가 될 수 없다" 같은 규칙을 한곳에서 지킬 수 있어요. 그래서 모든 필드에 setter를 기계적으로 여는 건 캡슐화가 아니에요. 밖에서 아무 값이나 넣을 수 있어 사실상 public과 비슷해지고, 규칙 검사가 객체 밖으로 새어 나가요.

**꼬리질문**
- Q. 접근 제어자 범위를 말해 보세요. → private은 클래스 안, default는 같은 패키지, protected는 같은 패키지와 하위 클래스, public은 어디서나예요.
- Q. 캡슐화의 이점은? → 객체를 따로 만들고 고칠 수 있고(모듈성), 문제가 생긴 객체만 갈아 끼우기 쉬워요.
</details>

<details>
<summary>Q. 다형성을 예시로 설명하고, 그게 왜 좋은지 말해 주세요.</summary>

**답변(30초)** 다형성은 같은 호출이 실제 객체에 따라 다르게 동작하는 거예요. 예를 들어 `Payment` 인터페이스를 `Card`와 `Toss`가 구현하면, `Payment p` 변수에 무엇을 넣느냐에 따라 같은 `p.pay()`가 카드 결제도 되고 토스 결제도 돼요. 호출하는 코드는 `Payment`만 알면 되니까, 새 결제 수단을 추가해도 기존 코드를 고칠 필요가 없어요. 그래서 결합도가 낮아져요.

**꼬리질문**
- Q. 오버로딩도 다형성인가요? → 넓게는 그렇게 부르기도 하지만, 컴파일 시점에 정해지는 정적 다형성이에요. 보통 다형성의 핵심은 실행 시점에 정해지는 오버라이딩이에요.
- Q. 실행할 메서드는 언제 정해지나요? → 실행 시점에 실제 객체 타입을 보고 정해요(동적 바인딩).
</details>

<details>
<summary>Q. 추상화와 캡슐화는 어떻게 다른가요?</summary>

**답변(30초)** 둘은 관점이 달라요. 추상화는 바깥에 무엇을 보여 줄지 정하는 설계 관점이고, 캡슐화는 나머지 내부를 어떻게 숨기고 보호할지 정하는 구현 관점이에요. 예를 들어 `Payment` 인터페이스에 `pay()`만 두는 건 추상화이고, `Card` 안의 카드번호와 한도를 private으로 막는 건 캡슐화예요. 둘은 보통 짝으로 함께 써요.

**꼬리질문**
- Q. 자바에서 추상화는 어떻게 하나요? → 인터페이스나 추상 클래스로 "무엇을 하는지"만 정하고, 구현은 하위 클래스에 맡겨요.
</details>

<details>
<summary>Q. 높은 응집도, 낮은 결합도란 무엇인가요?</summary>

**답변(30초)** 응집도는 한 클래스 안의 요소가 하나의 목적에 얼마나 모여 있는지이고, 높을수록 좋아요. 결합도는 클래스끼리 서로에게 얼마나 의존하는지이고, 낮을수록 좋아요. 응집도가 높고 결합도가 낮으면 하나를 고쳐도 영향이 그 클래스 안에서 끝나요. 캡슐화로 관련 로직을 모으고, 인터페이스에 의존하게 만들어서 이 상태를 만들어요.

**꼬리질문**
- Q. 상속은 결합도에 어떤 영향을 주나요? → 자식이 부모 구현에 묶여서 결합도를 높일 수 있어요. 그래서 is-a 관계가 아니면 조합을 먼저 고려해요.
</details>

## 서술형 연습

<details>
<summary>상황: PaymentService가 if (type == CARD) ... else if (type == BANK) ... 로 결제 수단을 분기합니다. 토스페이를 추가하려니 서비스 코드 여러 곳을 고쳐야 하고, 기존 결제가 깨질까 걱정됩니다. 어떻게 바꾸겠어요?</summary>

**상황 파악**
결제 수단을 아는 코드가 서비스 곳곳에 퍼져 있어요. 수단이 하나 늘 때마다 분기문을 전부 찾아 고쳐야 하고, 그 과정에서 카드·계좌 결제 코드까지 건드리게 돼요. 서비스와 결제 수단 사이의 결합도가 높은 상태예요.

**원인 후보**
1. 결제 수단마다 다른 부분(실제 결제 호출)과 공통 부분(결제를 요청한다는 사실)이 나뉘어 있지 않아요.
2. 서비스가 "어떤 수단인지"를 직접 알고 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. if/else 분기 유지, 토스 분기만 추가 | 지금 당장 가장 빠름, 클래스가 안 늘어남 | 수단이 늘수록 분기가 여러 곳에서 커지고, 수정할 때마다 기존 결제가 깨질 위험 |
| B. `Payment` 인터페이스 + 수단별 구현 클래스(다형성) | 서비스는 `Payment.pay()`만 호출, 새 수단은 클래스 하나 추가로 끝 | 클래스 수가 늘고, 구조를 처음 보는 사람은 흐름을 따라가기 조금 어려움 |
| C. B + 수단 타입으로 구현체를 찾는 Map(또는 스프링 빈 목록) | 분기문이 아예 사라지고 등록만 하면 됨 | 등록 누락 시 실행 중에야 발견, 설정이 한 단계 늘어남 |

**내가 고를 방법**
수단이 이미 세 개이고 앞으로도 늘 것 같으니 B를 기본으로, 고르는 부분은 C로 가요. 결제사마다 다른 부분은 각 구현 클래스 안에 캡슐화하고, 서비스는 `Payment` 인터페이스에만 의존하게 해요. 그러면 토스페이 추가는 `TossPayment` 클래스 하나와 등록 한 줄로 끝나고, 기존 카드·계좌 코드는 건드리지 않아요. 이게 SOLID의 개방-폐쇄 원칙(OCP, 기능 추가에는 열려 있고 기존 코드 수정에는 닫혀 있어야 한다는 원칙)이에요. 다만 수단이 두 개뿐이고 늘 계획이 없다면 A의 if문이 더 단순하다는 점도 같이 말해요.

**채점 포인트**: 추상화(공통 `pay` 계약), 다형성, 인터페이스에 의존, 결합도 낮추기, 변경 범위 축소, OCP, 해결책 2개 이상의 트레이드오프(클래스 증가 vs 분기 증가).
</details>

<details>
<summary>상황: 여러 곳에서 account.setBalance(account.getBalance() - x)를 호출하다가, 검사가 빠진 경로로 잔액이 음수가 됐습니다. 어떻게 고치겠어요?</summary>

**상황 파악**
"잔액은 음수가 될 수 없다"는 규칙이 객체 밖, 호출하는 쪽마다 흩어져 있어요. 한 곳이라도 검사를 빼먹으면 규칙이 깨져요. 필드는 private이지만 setter가 열려 있어서 캡슐화가 사실상 무너진 상태예요.

**원인 후보**
1. setter가 열려 있어 누구나 아무 값이나 넣을 수 있어요.
2. 출금 규칙이 `Account`가 아니라 호출부에 있어서 응집도가 낮아요.
3. (별개 문제) 동시에 두 요청이 같은 잔액을 읽고 빼면 검사를 해도 음수가 될 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 호출하는 곳마다 검사 코드 추가 | 구조 변경이 없어 빠름 | 새 호출부가 생길 때마다 또 빼먹을 수 있음, 같은 검사가 여러 곳에 중복 |
| B. setter 제거, `withdraw(amount)` 안에서 검사 후 차감 | 규칙이 한곳에만 있어 빼먹을 수 없음, 응집도↑ | 기존 setter 호출부를 모두 바꿔야 함 |
| C. B + DB 쪽 보호(조건부 UPDATE, 락) | 동시 요청까지 막음 | DB 설계와 성능을 함께 고려해야 함 |

**내가 고를 방법**
B를 먼저 해요. `setBalance`를 없애고 `withdraw()`가 금액과 잔액을 검사한 뒤에만 줄이게 해서, 규칙을 객체가 스스로 지키게 만들어요. 동시에 여러 요청이 들어오는 서비스라면 객체 안 검사만으로는 부족하니 C처럼 DB 수준 보호를 따로 더해요. A는 지금은 빠르지만 같은 사고가 다시 날 구조예요.

**채점 포인트**: 캡슐화, setter 남용, 불변식(항상 지켜야 할 규칙)을 객체 안으로, 응집도, 동시성 문제는 별도로 구분, 해결책 2개 이상의 트레이드오프.
</details>

## 필기 포인트

- 객체 = 상태(필드) + 행위(메서드). 클래스는 설계도, 객체는 실체.
- 자바 클래스는 **단일 상속**만 가능, 인터페이스는 여러 개 구현 가능.
- 접근 제어자 범위 좁은 순: `private` → (default) → `protected` → `public`. UML 기호는 `-`, `~`, `#`, `+`.
- 상속은 "하위는 상위의 한 종류"(is a kind of)일 때.
- 다형성의 핵심은 오버라이딩(실행 시점 결정). 오버로딩은 컴파일 시점 결정.
- **응집도는 높게, 결합도는 낮게.** 방향을 거꾸로 고르는 함정이 자주 나와요.
- 정보처리기사·컴퓨터일반 필기 암기 순서
  - 응집도 강 → 약(높을수록 좋음): 기능 → 순차 → 교환(통신) → 절차 → 시간 → 논리 → 우연. 줄여서 "기순교절시논우"
  - 결합도 약 → 강(낮을수록 좋음): 자료 → 스탬프 → 제어 → 외부 → 공통 → 내용. 줄여서 "자스제외공내"
