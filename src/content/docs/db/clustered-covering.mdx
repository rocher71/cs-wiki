:::tip[한 줄 요약]
InnoDB 테이블은 **PK 순서로 정렬된 B+트리 그 자체**이고, 이걸 **클러스터드 인덱스**라고 해요. 세컨더리 인덱스는 행 주소 대신 **PK 값**을 들고 있어서 행을 읽으려면 클러스터드 인덱스를 **한 번 더** 찾아가요. 쿼리에 필요한 컬럼이 인덱스에 다 있으면 그 왕복을 건너뛰는데, 이걸 **커버링 인덱스**라고 해요.
:::

<Aside type="note" title="이 페이지의 기준">
설명은 MySQL 8.0 기준 책과 MySQL 8.4 공식문서를 바탕으로 했어요. 실험은 **MySQL 9.6.0**(InnoDB, 16KB 페이지, 노트북 1회 실행)이라 숫자는 "경향"으로만 봐 주세요. 이 주제의 동작은 8.0~9.x에서 달라진 게 없어요. B+트리·페이지·페이지 분할 같은 기초는 [인덱스와 B+트리](../index-btree/)에서 먼저 보고 오면 좋아요.
</Aside>

## 쉽게 이해하기

도서관을 떠올려 봐요. 책장 자체가 **청구기호 순서대로** 꽂혀 있어요. 청구기호만 알면 책장으로 바로 걸어가서 책을 꺼낼 수 있어요. 이 "책장 = 정렬 기준"이 **클러스터드 인덱스**예요.

그런데 "저자 이름"으로 찾고 싶으면 따로 만든 **저자 카드 목록**을 봐요. 카드에는 저자 이름과 **청구기호**만 적혀 있어요. 그래서 카드에서 청구기호를 읽고, 다시 책장으로 걸어가야 책을 꺼내요. 이게 **세컨더리 인덱스**로 찾을 때 두 번 걷는 이유예요.

만약 알고 싶은 게 "이 저자 책의 청구기호"뿐이라면? 카드만 보고 끝나요. 책장까지 갈 필요가 없죠. 이게 **커버링 인덱스**예요.

단, 실제로는 카드 목록도 책장도 둘 다 B+트리라서, "걸어간다"는 건 트리를 루트부터 리프까지 다시 내려가는 일이에요.

## 제대로 알기

### 1. 클러스터드 인덱스: 테이블 = PK 인덱스

"클러스터링"은 비슷한 것끼리 묶어 둔다는 뜻이에요. InnoDB에서는 **PK 값이 비슷한 행끼리 붙어서 저장되도록, PK 값으로 행의 저장 위치를 정해요.** 이걸 **클러스터드 인덱스**(clustered index, 행 데이터 자체를 PK 순서로 정렬해 저장하는 방식)라고 해요.

그래서 클러스터드 인덱스는 "테이블과 따로 있는 인덱스"가 아니에요. 모양은 일반 B+트리와 같은데, **리프에 그 행의 모든 컬럼**이 들어 있어요. 테이블 자체가 하나의 커다란 PK 인덱스인 셈이에요.

| 구분 | 리프에 들어 있는 것 |
|---|---|
| 클러스터드 인덱스(PK) | **행 전체**(모든 컬럼) |
| 세컨더리 인덱스 | **인덱스 컬럼 값 + 그 행의 PK 값** |

몇 가지 따라오는 성질이 있어요.

- 일반 인덱스도 키 순서로 정렬돼 있지만 클러스터링이라고 부르지 않아요. **테이블 행이 PK 순서로 정렬 저장될 때만** 클러스터링이라고 해요.
- **PK 값을 바꾸면 행의 물리적 위치도 바뀌어요.** 사실상 "지우고 다른 자리에 다시 넣기"라서 비싸요.
- 클러스터드 인덱스는 InnoDB가 지원하는 방식이에요. MyISAM·MEMORY 엔진은 지원하지 않아요.

### 2. PK를 안 만들면? InnoDB가 고르는 순서

InnoDB 테이블에는 클러스터드 인덱스가 **항상** 있어요. PK를 안 만들면 InnoDB가 알아서 정해요.

1. PK가 있으면 PK.
2. 없으면 **모든 컬럼이 NOT NULL인 첫 번째 UNIQUE 인덱스**.
3. 그것도 없으면 숨은 인덱스 `GEN_CLUST_INDEX`를 만들어요. 6바이트짜리 **row ID** 컬럼을 몰래 추가하고, 행이 들어올 때마다 1씩 늘려요. 그래서 행이 삽입 순서대로 저장돼요.

3번의 row ID는 SELECT나 WHERE에 쓸 수 없어요. 공간은 차지하는데 쓸모가 없죠. 그래서 책과 공식문서 모두 **PK를 꼭 직접 정하라**고 권해요. 마땅한 값이 없으면 auto_increment 컬럼을 하나 추가하라는 게 공식 권고예요.

책은 이유를 하나 더 들어요. ROW 기반 복제나 InnoDB Cluster 환경에서는 모든 테이블에 PK가 있어야 복제 성능이 정상적으로 나와요. **복제**(replication)는 원본 DB의 변경을 다른 DB에 똑같이 옮겨 적는 거예요.

### 3. 세컨더리 인덱스는 왜 주소 대신 PK를 들고 있나

**세컨더리 인덱스**(secondary index)는 클러스터드 인덱스가 아닌 모든 인덱스예요. 리프에는 **인덱스 컬럼 + PK 값**이 있고, InnoDB는 이 PK 값으로 클러스터드 인덱스를 다시 검색해서 행을 찾아요.

왜 "행이 있는 주소"를 바로 적어 두지 않을까요?

- MyISAM은 행이 처음 저장된 자리가 바뀌지 않아요. 그래서 인덱스에 주소(ROWID)를 적어도 괜찮아요.
- InnoDB는 PK가 바뀌거나 **페이지 분할**(꽉 찬 페이지를 둘로 쪼개는 일)이 일어나면 행 위치가 바뀌어요. 세컨더리에 주소를 적었다면 **그때마다 모든 세컨더리 인덱스를 고쳐야** 해요.
- 그래서 PK 값을 적어 두는 거예요. 페이지 분할로 행 위치가 바뀌어도 PK 값은 그대로라 세컨더리는 손댈 필요가 없어요.

대가는 조회 단계가 하나 늘어난다는 거예요. `ix_first_name`이 있는 상태에서 `SELECT * ... WHERE first_name = 'Aamer'`를 하면 이렇게 돼요.

| 엔진 | 찾아가는 길 |
|---|---|
| MyISAM | 인덱스 → 주소 → 행 |
| InnoDB | 세컨더리 인덱스 → **PK 값** → 클러스터드 인덱스를 다시 내려감 → 행 |

책은 한 단계가 늘어도 클러스터링으로 얻는 이점이 더 커서 크게 걱정할 일은 아니라고 봐요.

<Aside type="tip" title="실험에서 본 덤">
`ix_age(age)` 하나만 있는데 `WHERE age = 30 ORDER BY id`가 별도 정렬(filesort) 없이 처리됐어요. 세컨더리 항목이 실험상 (age, id) 순서로 정렬된 것처럼 동작했다는 뜻이에요. 이 정렬 순서를 못 박은 공식문서 문장은 찾지 못해서, "실험에서 그렇게 동작했다" 정도로만 알아 두세요.
</Aside>

### 4. 장단점: 읽기는 빠르고 쓰기는 느리다

| 장점 | 단점 |
|---|---|
| PK로 찾기, 특히 **PK 범위 검색**이 아주 빠름(이웃한 행이 같은 페이지나 옆 페이지에 있음) | 세컨더리 인덱스가 PK를 들고 있어서 **PK가 크면 모든 세컨더리 인덱스가 커짐** |
| 세컨더리 인덱스에 PK가 붙어 있어서 **인덱스만으로 끝나는(커버링) 경우가 많음** | 세컨더리로 찾으면 PK로 **한 번 더** 찾아가야 함 |
| | INSERT 때 PK로 저장 위치를 정해야 해서 느림. PK 변경은 삭제+삽입이라 더 느림 |

책 저자의 경험상 웹 서비스는 쓰기와 읽기 비율이 대략 2:8~1:9라서, 쓰기를 조금 내주고 읽기를 얻는 이 구조가 보통 이득이에요.

### 5. 커버링 인덱스: 인덱스만 보고 끝내기

**커버링 인덱스**(covering index)는 **쿼리에 필요한 컬럼이 전부 한 인덱스 안에 있어서, 행을 읽으러 클러스터드 인덱스까지 가지 않는 경우**를 말해요.

핵심은 이게 **인덱스의 종류가 아니라 쿼리와 인덱스의 관계**라는 점이에요. 같은 `ix_age`도 어떤 쿼리에는 커버링이고 어떤 쿼리에는 아니에요.

InnoDB 세컨더리 리프에는 PK가 붙어 있으니, **PK 컬럼까지 SELECT해도 커버링이 깨지지 않아요.** `SELECT id, age ... WHERE age = ?`는 `ix_age(age)` 하나로 끝나요.

실험(30만 행 회원 테이블, `ix_age(age)`, age=30이 6,000행)이에요.

| 쿼리 | 사용 인덱스 | EXPLAIN Extra | 실제 시간 |
|---|---|---|---|
| `SELECT id, age ... WHERE age=30` | ix_age | **Using index** | 약 0.43ms |
| `SELECT id, email ... WHERE age=30` | ix_age | (비어 있음) | 약 3.66ms |

두 번째 쿼리도 인덱스는 탔어요. 다만 email이 인덱스에 없어서 **6,000행마다 클러스터드 인덱스를 다시 내려갔고**, 약 8배 느렸어요. 데이터가 전부 메모리에 올라와 있던 상태라, 디스크 읽기가 섞이면 차이는 더 커질 수 있어요.

**EXPLAIN에서 확인하는 법** ([EXPLAIN](../explain/)에서 자세히)

- `Extra`에 **`Using index`** 가 있으면 커버링이에요. `EXPLAIN FORMAT=TREE`에서는 `Covering index lookup`으로 나와요.
- `Extra`가 비어 있어도 **인덱스를 안 탔다는 뜻이 아니에요.** 실제로 쓴 인덱스는 `key` 컬럼을 봐야 해요.
- **`Using index condition`은 커버링이 아니에요.** 인덱스로 조건을 먼저 걸러 보고 필요한 행만 읽는 별개 최적화(ICP)예요.

### 6. 커버링이 안 되면: 인덱스에 컬럼 더하기

`SELECT id, email WHERE age = 30`을 커버링으로 만들려면 email도 인덱스에 넣으면 돼요. 실험에서 `ix_age_email(age, email)`을 추가하고 그 인덱스를 강제로 쓰게 했더니 `Covering index lookup`이 나왔고 약 0.51ms였어요(ix_age 강제 시 약 3.67ms).

<Aside type="caution" title="만들었다고 옵티마이저가 쓰는 건 아니에요">
같은 실험에서 아무 힌트 없이 실행하면 옵티마이저(실행 방법을 고르는 MySQL 내부 부품)는 **스스로 ix_age를 골랐어요.** 통계로 비용을 추정한 결과예요. 커버링 인덱스를 만든 뒤에는 꼭 EXPLAIN으로 실제로 쓰이는지 확인해요. 여러 컬럼 인덱스의 순서 설계는 [복합 인덱스](../composite-index/)에서 다뤄요.
</Aside>

`SELECT *`를 피하라는 말도 여기서 나와요. 컬럼을 다 달라고 하면 어떤 세컨더리 인덱스도 커버할 수 없어서, 행마다 클러스터드 인덱스를 왕복해요.

덤으로, `SELECT COUNT(*) FROM member`는 실험에서 PK가 아니라 **가장 작은 세컨더리 인덱스(ix_age)를 처음부터 끝까지 읽었어요**(`type=index`, `Using index`). 클러스터드 인덱스는 리프에 모든 컬럼이 있어 크니까, 행 수만 셀 때는 작은 인덱스를 읽는 게 싸요.

### 7. PK 설계 ①: 크기 — PK는 모든 세컨더리에 복사된다

공식문서도 **PK가 길면 세컨더리 인덱스가 공간을 더 쓰니 짧은 PK가 유리하다**고 해요.

책의 계산으로는 세컨더리 인덱스 5개, 100만 건일 때 PK가 10바이트면 세컨더리 인덱스가 약 47MB 늘고, 50바이트면 약 238MB 늘어요. 1,000만 건이면 차이가 1.9GB예요. 인덱스가 커지면 같은 성능을 내는 데 메모리가 더 필요해요.

책이 "무조건 auto_increment"를 권하는 건 아니에요. 조건이 있어요.

- PK로 검색(특히 범위)하는 일이 많으면, 좀 크더라도 **업무적으로 행을 대표하는 값**을 PK로.
- 세컨더리 인덱스도 필요하고 PK도 길다면 **auto_increment 인조 키**(surrogate key, 업무 의미 없이 식별만 하는 번호)로.
- 로그처럼 **INSERT 위주** 테이블도 auto_increment로.

### 8. PK 설계 ②: 순서 — 랜덤 PK는 페이지를 찢는다

InnoDB는 키가 **순서대로** 들어오면 페이지를 약 15/16까지 채우고, **무작위 순서**면 1/2~15/16만 채워요. 순차 키는 항상 맨 오른쪽 끝에 붙어요. 랜덤 키는 이미 꽉 찬 중간 페이지에 끼어들어야 해서 페이지 분할이 자주 일어나요. 쓸 페이지가 여기저기 흩어져서 메모리 캐시(버퍼 풀) 효율도 떨어져요.

실험(100만 행, 세컨더리 `ix_email` 1개, 한 문장으로 일괄 INSERT, 1회 실행)이에요.

| PK | INSERT 시간 | PK 크기 | 리프 페이지 | ix_email 크기 |
|---|---|---|---|---|
| BIGINT auto_increment (8B, 순차) | 3.6s | 147.7MB | 9,425 | 51.6MB |
| BINARY(16), 시간 정렬 UUID | 3.7s | 155.8MB | 9,901 | 64.8MB |
| BINARY(16), 완전 랜덤 | **8.5s** | **250.0MB** | 13,897 | 64.8MB |
| CHAR(36) UUID 문자열, 랜덤 순서 | (참고 불가*) | 290.0MB | 16,156 | 92.0MB |

\* 이 행은 랜덤 순서를 만드는 정렬 비용이 시간에 섞여서 크기만 봐요.

읽는 법이에요.

- 같은 16바이트끼리 **순서만 랜덤으로 바꿔도** INSERT는 약 2.3배, PK 크기는 약 1.6배가 됐어요. 페이지 분할로 덜 찬 페이지가 늘어난 결과예요.
- `ix_email` 크기는 PK 크기를 따라가요(8B → 51.6MB, 16B → 64.8MB, 36자 문자열 → 92.0MB). **PK가 커지면 세컨더리가 같이 커진다**는 걸 숫자로 보여 줘요.

### 9. UUID를 PK로 쓸 때의 함정

**UUID**(Universally Unique IDentifier)는 서버 여러 대가 따로 만들어도 겹치지 않는 128비트(16바이트) ID예요. 만드는 방식에 따라 버전이 나뉘어요.

| 만드는 곳 | 버전 | 성질 |
|---|---|---|
| MySQL `UUID()` | **버전 1**(시간 기반) | 시간에 따라 바뀜. 단, 문자열 맨 앞이 **가장 빨리 바뀌는 시간 부분**이라 그대로는 정렬 순서가 어긋나요 |
| Java `UUID.randomUUID()` | 버전 4(난수 기반)로 알려져 있어요 | 완전 랜덤 → 위 표의 "완전 랜덤" 행 |
| 버전 7 | 앞부분이 밀리초 타임스탬프 | 시간순으로 정렬돼요. 앱에서 만들어요 |

<Aside type="caution" title="'MySQL UUID()는 랜덤이라 느리다'는 오해">
MySQL `UUID()`는 **버전 1, 시간 기반**이에요. 실험에서 한 문장 안에서 연달아 만들었더니 맨 앞 묶음이 `473d6916-…`, `473d6917-…`처럼 1씩 늘었어요. 그래서 CHAR(36)에 정렬 없이 넣었을 때는 랜덤 손해가 거의 안 보였고 **키가 긴 손해만** 보였어요(4.2s, 179MB). 실제 서비스에서 문제가 되는 건 보통 **애플리케이션이 만든 랜덤 UUID(v4)** 를 PK로 쓸 때예요.
</Aside>

MySQL 쪽 해결 도구는 `UUID_TO_BIN(uuid, 1)`이에요.

- 결과가 16바이트 바이너리라 36자 문자열보다 절반 이하로 작아요.
- 두 번째 인자 `1`(swap_flag)은 시간의 빨리 바뀌는 부분과 느리게 바뀌는 부분을 맞바꿔, **빨리 바뀌는 부분을 뒤로 보내요.** 그래서 값이 시간순에 가깝게 정렬돼 인덱스에 유리해요. 이 맞바꿈은 **버전 1 UUID에서만 의미가 있어요.**
- 되돌릴 땐 `BIN_TO_UUID(x, 1)`처럼 **같은 플래그**를 써야 원래 값이 나와요.

```sql
-- 시간 정렬된 16바이트 UUID를 PK로
CREATE TABLE member (
  id BINARY(16) PRIMARY KEY,
  email VARCHAR(100) NOT NULL
);
INSERT INTO member VALUES (UUID_TO_BIN(UUID(), 1), 'a@ex.com');

-- 사람이 읽을 땐 같은 플래그로 되돌리기
SELECT BIN_TO_UUID(id, 1) AS id, email FROM member;
```

앱에서 ID를 만들어야 한다면 시간순으로 정렬되는 **UUID 버전 7**이 대안으로 쓰여요. 2024년 UUID 표준(RFC 9562)에 들어간 버전이고, MySQL `UUID()`는 v1만 만들어서 v7은 앱에서 생성해요.

## 면접 질문

<details>
<summary>Q. 클러스터드 인덱스와 세컨더리 인덱스의 차이는요?</summary>

**답변(30초)** 클러스터드 인덱스는 테이블 행 자체를 PK 순서로 정렬해 저장한 B+트리라서, 리프에 행의 모든 컬럼이 있어요. InnoDB에선 테이블이 곧 PK 인덱스예요. 세컨더리 인덱스는 그 밖의 인덱스로, 리프에 인덱스 컬럼과 PK 값만 있어요. 그래서 세컨더리로 찾으면 PK를 얻은 뒤 클러스터드 인덱스를 한 번 더 내려가 행을 읽어요.

**꼬리질문**
- Q. 클러스터드 인덱스는 테이블에 몇 개까지 있나요? → 행을 저장하는 정렬 순서가 하나뿐이라 한 개예요. 나머지는 전부 세컨더리예요.
- Q. PK를 바꾸면 무슨 일이 일어나요? → 행의 물리적 위치가 바뀌어서 사실상 삭제 후 다른 자리에 삽입이에요. 그래서 PK는 바뀌지 않는 값이 좋아요.
</details>

<details>
<summary>Q. InnoDB 테이블에 PK를 안 만들면 어떻게 되나요?</summary>

**답변(30초)** PK가 없는 테이블이 되는 게 아니라, InnoDB가 클러스터드 인덱스를 알아서 정해요. NOT NULL인 첫 UNIQUE 인덱스가 있으면 그걸 쓰고, 그것도 없으면 숨은 6바이트 row ID를 추가해 클러스터드 인덱스를 만들어요. 그런데 이 row ID는 쿼리에서 쓸 수 없어서 공간만 차지해요. 그래서 PK는 꼭 직접 정하고, 마땅한 값이 없으면 auto_increment를 둬요.

**꼬리질문**
- Q. PK 없는 테이블이 운영에서 문제를 일으키는 예는요? → 책은 ROW 기반 복제나 InnoDB Cluster에서 PK가 있어야 복제 성능이 정상적으로 나온다고 해요.
</details>

<details>
<summary>Q. 세컨더리 인덱스는 왜 행 주소 대신 PK를 저장하나요?</summary>

**답변(30초)** InnoDB는 PK가 바뀌거나 페이지 분할이 일어나면 행 위치가 바뀌기 때문이에요. 주소를 저장했다면 그때마다 모든 세컨더리 인덱스를 고쳐야 해요. PK 값을 저장하면 위치가 바뀌어도 세컨더리는 그대로예요. 대신 세컨더리로 찾을 때 클러스터드 인덱스를 한 번 더 내려가야 하고, PK가 크면 모든 세컨더리 인덱스가 커지는 단점이 있어요.

**꼬리질문**
- Q. MyISAM은요? → 행이 처음 저장된 자리가 안 바뀌어서 인덱스에 주소(ROWID)를 바로 저장해요.
- Q. PK가 크면 왜 문제죠? → PK가 모든 세컨더리 인덱스에 복사돼요. 실험에서도 PK가 8바이트에서 36자 문자열로 커지자 email 인덱스가 51.6MB에서 92.0MB로 커졌어요.
</details>

<details>
<summary>Q. 커버링 인덱스가 뭐고, 실행 계획에서 어떻게 확인하나요?</summary>

**답변(30초)** 쿼리에 필요한 컬럼이 전부 한 인덱스 안에 있어서 클러스터드 인덱스까지 가지 않고 인덱스만으로 끝내는 경우예요. 인덱스 종류가 아니라 쿼리와 인덱스의 관계예요. EXPLAIN의 Extra에 `Using index`가 나오면 커버링이에요. InnoDB는 세컨더리에 PK가 붙어 있어서 PK 컬럼을 같이 SELECT해도 커버링이 유지돼요. 실험에서 같은 인덱스로 커버링이면 0.43ms, 아니면 3.66ms였어요.

**꼬리질문**
- Q. `Using index condition`도 커버링인가요? → 아니에요. 인덱스로 조건을 먼저 걸러 보고 필요한 행만 읽는 ICP라는 별개 최적화예요.
- Q. Extra에 `Using index`가 없으면 인덱스를 안 탄 건가요? → 아니에요. `key` 컬럼에 인덱스가 있으면 탄 거예요. 행을 읽으러 한 번 더 갔을 뿐이에요.
- Q. `SELECT *`를 피하라는 이유를 인덱스 관점에서 말해 보세요. → 모든 컬럼을 커버하는 세컨더리 인덱스는 없어서, 행마다 클러스터드 인덱스를 왕복해야 해요.
</details>

<details>
<summary>Q. PK를 auto_increment로 할까요, UUID로 할까요?</summary>

**답변(30초)** 핵심은 PK의 크기와 순서예요. PK는 모든 세컨더리 인덱스에 복사되니 작을수록 좋고, 순서대로 들어와야 페이지 분할이 적어요. 단일 DB라면 BIGINT auto_increment가 둘 다 만족해요. UUID가 필요하면 36자 문자열 대신 BINARY(16)으로, 그리고 랜덤 v4가 아니라 시간순 UUID(v7이나 `UUID_TO_BIN(UUID(), 1)`)를 써요. 실험에서 같은 16바이트라도 완전 랜덤이면 INSERT가 약 2.3배 느렸어요.

**꼬리질문**
- Q. MySQL `UUID()`도 랜덤이라 느린가요? → MySQL `UUID()`는 시간 기반 v1이에요. 랜덤 문제는 보통 앱에서 만든 v4에서 생겨요.
- Q. auto_increment 값을 외부 API에 그대로 노출하면요? → 번호로 데이터 규모를 추정당할 수 있어요. 내부 PK는 숫자로 두고 외부엔 별도 UUID 컬럼을 노출하는 방법이 있어요.
</details>

## 서술형 연습

<details>
<summary>상황: 회원 테이블 PK를 앱에서 만든 랜덤 UUID 문자열(CHAR(36))로 설계했습니다. 데이터가 늘면서 가입 INSERT가 점점 느려지고, 디스크와 메모리 사용량이 예상보다 크게 늘었습니다.</summary>

**상황 파악**
쓰기 지연과 공간 증가가 같이 왔고, 둘 다 데이터가 늘수록 심해져요. InnoDB에서 PK는 행 저장 위치를 정하고 모든 세컨더리 인덱스에 복사되니, PK 설계를 먼저 의심해요.

**원인 후보**
1. **랜덤 순서**: 새 키가 B+트리 중간의 꽉 찬 페이지에 끼어들어 페이지 분할이 자주 나요. 덜 찬 페이지가 늘어 테이블이 커지고, 쓸 페이지가 흩어져 버퍼 풀 효율도 떨어져요.
2. **큰 키**: 36자 문자열 PK가 모든 세컨더리 인덱스에 복사돼 인덱스 전체가 커져요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 내부 PK는 BIGINT auto_increment, 외부 노출용 UUID는 별도 UNIQUE 컬럼 | PK가 8바이트·순차라 삽입과 세컨더리 크기 모두 유리 | UNIQUE 인덱스가 하나 늘어요. 외부 UUID 조회는 세컨더리 → PK → 행 2단계 |
| B. 시간순 UUID(v7 또는 `UUID_TO_BIN(UUID(), 1)`) + BINARY(16) | 분산 환경에서도 ID를 따로 만들 수 있고 순서가 거의 순차 | 사람이 바로 못 읽어서 `BIN_TO_UUID` 필요. v7은 생성 시각이 ID에 드러나요. 여전히 8바이트보다 큼 |
| C. CHAR(36)를 BINARY(16)으로만 바꿈 | 키 크기 손해는 줄어요 | 랜덤 순서 문제는 그대로 남아요 |

**내가 고를 방법**
단일 DB라면 A를 골라요. 실험에서도 8바이트 순차 PK가 삽입 시간과 PK·세컨더리 크기에서 모두 가장 작았어요. auto_increment 번호가 밖으로 새면 규모를 추정당할 수 있으니 외부에는 UUID만 내보내요. 여러 서버가 DB 없이 ID를 만들어야 한다면 B로 가요. C만으로는 근본 원인(랜덤 순서)이 안 풀려서 단독으론 부족해요. 바꾼 뒤엔 테이블·인덱스 크기와 INSERT 시간을 다시 재서 확인해요.

**채점 포인트**: 클러스터드 인덱스(PK가 저장 위치 결정), 랜덤 삽입 → 페이지 분할·채움률 저하, PK가 세컨더리에 복사됨, BINARY(16) vs CHAR(36), 시간순 UUID(v7 / swap_flag), MySQL `UUID()`는 v1, 내부 PK·외부 ID 분리와 보안, 적용 후 측정.
</details>

<details>
<summary>상황: 주문 목록 API `SELECT * FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20`이 느립니다. `user_id` 인덱스는 이미 있습니다.</summary>

**상황 파악**
인덱스가 있으니 풀 스캔은 아닐 가능성이 커요. EXPLAIN에서 `key`는 user_id 인덱스인데 Extra에 `Using index`가 없고 `Using filesort`가 있다면, 행마다 클러스터드 인덱스를 왕복하고 그 결과를 다시 정렬하고 있는 거예요.

**원인 후보**
1. `SELECT *`라 커버링이 안 돼요. 그 사용자의 주문이 많을수록 클러스터드 인덱스 왕복이 늘어요.
2. 인덱스에 `created_at`이 없어 정렬을 따로 해요. 20건만 필요해도 그 사용자의 주문을 다 읽고 정렬해야 해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `(user_id, created_at)` [복합 인덱스](../composite-index/) | 정렬이 인덱스 순서로 해결돼 20건만 읽고 멈출 수 있어요 | 인덱스가 하나 늘어 주문 INSERT 비용·공간 증가 |
| B. 필요한 컬럼만 SELECT하고 그 컬럼을 인덱스에 포함해 커버링 | 클러스터드 왕복 자체가 사라져요 | 컬럼이 늘면 인덱스가 커지고, 화면 요구가 바뀔 때마다 인덱스도 손봐야 해요 |
| C. 인덱스로 PK 20개만 먼저 뽑고(커버링) 그 PK로 행을 조인 | `SELECT *`를 유지하면서 왕복을 20번으로 줄여요 | 쿼리가 복잡해지고 ORM으로 쓰기 번거로워요 |

**내가 고를 방법**
먼저 A로 정렬과 불필요한 읽기를 없애요. 이것만으로 왕복이 20번 정도로 줄어서 대부분 충분해요. 그래도 부족하고 화면에 필요한 컬럼이 적고 고정적이라면 B를 더해요. 컬럼이 많아 커버링이 어렵다면 C를 써요. 인덱스를 만든 뒤에는 옵티마이저가 실제로 새 인덱스를 골랐는지 EXPLAIN으로 확인해요.

**채점 포인트**: EXPLAIN의 key·Extra 읽기, 세컨더리 → 클러스터드 왕복, `SELECT *`와 커버링, 정렬(filesort)을 인덱스로 제거, 복합 인덱스, 인덱스 추가의 쓰기·공간 비용, 옵티마이저 선택 확인.
</details>

## 필기 포인트

- InnoDB 클러스터드 인덱스 = **테이블 자체**. 리프에 행 전체. 테이블당 하나.
- 세컨더리 인덱스 리프 = **인덱스 컬럼 + PK 값**(물리 주소 아님). MyISAM은 주소(ROWID).
- PK가 없을 때 클러스터드 인덱스: PK → **NOT NULL인 첫 UNIQUE 인덱스** → 숨은 6바이트 row ID(`GEN_CLUST_INDEX`).
- 커버링 = 인덱스만으로 처리. EXPLAIN Extra **`Using index`**. `Using index condition`은 ICP라 다른 것.
- InnoDB 세컨더리는 PK를 포함하므로 PK 컬럼을 SELECT해도 커버링 유지.
- PK는 짧을수록 좋음(모든 세컨더리에 복사). 순차 삽입 시 페이지 약 15/16, 랜덤이면 1/2~15/16.
- MySQL `UUID()` = 버전 1(시간 기반). `UUID_TO_BIN(x, 1)`은 시간 부분을 맞바꿔 정렬 효율을 높이고 16바이트로 줄임.
