:::tip[한 줄 요약]
**JOIN**은 두 테이블의 행을 조건에 맞춰 **옆으로 이어 붙이는** 연산이에요. INNER JOIN은 짝이 있는 행만 남기고, LEFT JOIN은 왼쪽 행을 전부 남긴 뒤 짝이 없으면 오른쪽 칸을 NULL로 채워요. SQL은 **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT** 순서로 처리된다고 생각하면 대부분의 함정이 풀려요.
:::

:::note[처음이라면 여기까지]
① **JOIN**은 두 테이블의 행을 조건에 맞춰 옆으로 이어 붙여요.

② INNER JOIN은 짝이 있는 행만 남기고, LEFT JOIN은 왼쪽 행을 다 남긴 뒤 짝이 없으면 빈칸(NULL)으로 채워요.

③ SQL은 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY 순서로 처리된다고 기억하면 함정 대부분이 풀려요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

</Aside>

## 쉽게 이해하기

동아리 회원 명단 한 장과 주문 영수증 묶음이 있다고 해 봐요. "누가 뭘 샀는지" 보려면 영수증에 적힌 회원 번호를 보고 명단에서 이름을 찾아 **옆에 나란히 붙여** 써야 해요. 이게 JOIN이에요.

이때 두 가지 방식이 있어요. 영수증이 있는 회원만 적는 방식(INNER JOIN), 그리고 명단의 회원은 전부 적되 영수증이 없으면 "없음"이라고 비워 두는 방식(LEFT JOIN)이에요.

한 회원이 영수증을 두 장 냈다면 그 회원은 결과에 **두 줄**로 나와요. JOIN은 행을 이어 붙이는 거라 행 수가 늘 수도 있어요.

단, 실제 DB는 사람처럼 한 줄씩 손으로 대조하지 않아요. 옵티마이저(쿼리를 어떻게 실행할지 고르는 DB 내부 부품)가 인덱스(책 뒤의 찾아보기처럼 원하는 행을 빨리 찾게 해 주는 자료) 등을 보고 가장 싼 방법을 골라요. 우리가 알아야 하는 건 **결과가 어떤 모양이 되느냐**예요.

## 제대로 알기

### 1. SELECT 한 줄 읽는 법

SQL(Structured Query Language, DB에 질문하는 언어)의 기본 모양은 이래요.

```sql
SELECT name, city        -- 어떤 칸(컬럼)을 보여 줄지
FROM member              -- 어느 테이블에서
WHERE city = 'seoul'     -- 어떤 행만 남길지
ORDER BY name;           -- 어떤 순서로 (기본은 오름차순 ASC)
```

결과는 이름순으로 choi, kim 두 행이에요. 자주 쓰는 부품도 같이 알아 두세요.

- `SELECT DISTINCT city`: 중복을 뺀 값만. 아무것도 안 쓰면 `ALL`(중복 허용)이 기본이에요.
- `AS`: 결과 칸에 **별칭**(alias, 임시 이름)을 붙여요. `amount * 2 AS dbl`.
- `LIKE 'k%'`: `%`는 0글자 이상 아무거나, `_`는 딱 한 글자예요.

### 2. JOIN 종류와 결과 행 수

위 예제에 각 JOIN을 돌린 결과예요(실험으로 확인한 행 수).

| 조인 | 남는 행 | 예제 결과 |
|---|---|---|
| **INNER JOIN** | ON 조건에 맞는 짝이 있는 행만 | 3행 |
| **LEFT JOIN** | 왼쪽 전부 + 짝 없으면 오른쪽 칸 NULL | 5행 (3 + park, choi) |
| **RIGHT JOIN** | 오른쪽 전부 + 짝 없으면 왼쪽 칸 NULL | 5행 (3 + 주문 13, 14) |
| **CROSS JOIN** | 모든 조합(카테시안 곱) | 20행 (4 × 5) |

```sql
SELECT m.name, o.id, o.amount
FROM member m                        -- m, o는 테이블 별칭
LEFT JOIN orders o ON o.member_id = m.id;
-- kim 10 5000 / kim 11 3000 / lee 12 7000 / park NULL NULL / choi NULL NULL
```

꼭 알아 둘 점이 있어요.

- **LEFT JOIN이 왼쪽 행 수를 유지하는 건 아니에요.** kim은 주문이 2건이라 2행이 됐어요. "최소한 왼쪽 행은 다 남는다"가 정확한 표현이에요.
- **RIGHT JOIN**은 LEFT JOIN의 좌우만 바꾼 거예요. MySQL 문서는 다른 DB로 옮기기 쉽도록 RIGHT 대신 LEFT JOIN을 쓰라고 권해요.
- **FULL OUTER JOIN**(양쪽 전부 남기기)은 MySQL 문법에 없어요. 필요하면 LEFT JOIN 결과와 RIGHT JOIN 결과를 `UNION`(두 결과를 위아래로 이어 붙이고 중복 행을 빼는 연산)으로 합쳐 흉내 내요.
- **카테시안 곱**(Cartesian product)은 두 테이블 행의 모든 조합이에요. MySQL에서는 `JOIN`, `INNER JOIN`, `CROSS JOIN`이 문법상 같아서, ON을 빼먹어도 오류 없이 20행이 나와요. 실제 운영 테이블이면 행이 폭발해요.

<Aside type="caution" title="벤 다이어그램 그림은 반쯤만 맞아요">
JOIN을 원 두 개가 겹친 그림으로 설명하는 글이 많아요. 그런데 그 그림은 교집합·합집합 같은 **집합 연산**처럼 보이게 해요. JOIN은 행을 이어 붙이는 연산이라, 짝이 여러 개면 행이 늘어나요. 행 수로 생각하는 습관을 들이세요.
</Aside>

### 심화: 3. 셀프 조인과 짝 없는 행 찾기

**셀프 조인**(self join)은 같은 테이블을 별칭 두 개로 조인하는 거예요. 따로 있는 문법이 아니에요. 회원-추천인, 사원-관리자, 하위-상위 카테고리처럼 한 테이블 안에서 서로를 가리킬 때 써요.

```sql
SELECT m.name, r.name AS referrer
FROM member m
LEFT JOIN member r ON m.referrer_id = r.id;
-- INNER면 3행(추천인 없는 kim 빠짐), LEFT면 4행(kim의 referrer는 NULL)
```

**짝 없는 행 찾기**(안티 조인, anti join)는 LEFT JOIN의 NULL 성질을 이용해요. "주문이 한 번도 없는 회원"은 이렇게 찾아요.

```sql
SELECT m.name
FROM member m
LEFT JOIN orders o ON o.member_id = m.id
WHERE o.id IS NULL;        -- 결과: park, choi
```

### 4. LEFT JOIN에서 ON과 WHERE의 차이

면접 단골이에요. "결제 완료(PAID) 주문을 회원 옆에 붙이되, 회원은 전부 보여 줘"를 두 가지로 써 봤어요.

| 조건 위치 | 의미 | 예제 결과 |
|---|---|---|
| `ON o.member_id = m.id AND o.status = 'PAID'` | **짝을 고르는 조건**. 안 맞으면 NULL이 붙고 왼쪽 행은 남음 | 4행 (kim-10, lee-12, park-NULL, choi-NULL) |
| `ON o.member_id = m.id` + `WHERE o.status = 'PAID'` | 조인이 **끝난 뒤** 거르는 조건 | 2행 (kim, lee) |

WHERE 쪽에서 park, choi가 사라진 이유는 그 행의 `o.status`가 NULL이라 `= 'PAID'`가 참이 아니기 때문이에요. 결과적으로 INNER JOIN과 같아져요.

- **INNER JOIN에서는 ON에 두든 WHERE에 두든 결과가 같아요.** 차이는 외부 조인(LEFT/RIGHT)에서만 생겨요.
- 콤마 조인(`FROM a, b`)과 `JOIN`을 섞으면 우선순위 때문에 `Unknown column ... in 'on clause'` 오류가 날 수 있어요. JOIN 문법으로 통일하세요.

### 5. NULL: 모르는 값

**NULL**은 "값을 모름/없음"이에요. 빈 문자열 `''`이나 숫자 0과 달라요. NULL에는 특별한 규칙이 있어요.

**NULL과 비교하면 참이 안 돼요.** NULL끼리도요. `NULL = NULL`의 결과는 참도 거짓도 아닌 NULL(UNKNOWN, 모름)이에요. SQL은 이렇게 참·거짓·모름 세 가지를 쓰는데, 이걸 **3값 논리**라고 해요. 그리고 **WHERE는 참인 행만 남겨요.** 모름은 거짓처럼 버려져요.

| 쿼리 | 결과 | 이유 |
|---|---|---|
| `WHERE city = NULL` | 0행 (오류도 안 남) | 비교 결과가 늘 UNKNOWN |
| `WHERE city IS NULL` | 1행 (park) | NULL은 `IS NULL`로 찾음 |
| `WHERE city <> 'seoul'` | 1행 (lee만) | park의 NULL은 비교 결과가 UNKNOWN이라 빠짐 |

MySQL에는 NULL끼리도 같다고 보는 **NULL-safe 비교** `<=>`가 있어요. `NULL <=> NULL`은 1(참)이에요.

**NOT IN에 NULL이 섞이면 결과가 0행이 돼요.** 가장 위험한 함정이에요.

```sql
-- "주문 안 한 회원" 찾기. orders.member_id에 NULL(주문 13)이 있음
SELECT name FROM member
WHERE id NOT IN (SELECT member_id FROM orders);   -- 0행!
```

`id NOT IN (1, 1, 2, NULL, 9)`는 `id <> 1 AND id <> 2 AND id <> NULL AND id <> 9`와 같아요. `id <> NULL`이 늘 UNKNOWN이라 전체가 참이 될 수 없어요. 고치는 방법은 세 가지예요(셋 다 실험에서 park, choi 2행).

1. `NOT EXISTS (SELECT 1 FROM orders o WHERE o.member_id = m.id)`로 바꾸기
2. 3번 절의 `LEFT JOIN ... WHERE o.id IS NULL` 쓰기
3. 서브쿼리에 `WHERE member_id IS NOT NULL` 붙이기

`IN`은 일치하는 값이 하나라도 있으면 참이라 NULL 영향이 적어요(`1 IN (1, NULL)`은 1).

**NULL끼리 같이 묶이는 곳도 있어요.** DISTINCT, GROUP BY, ORDER BY에서는 NULL을 한 값처럼 다뤄서 한 그룹으로 묶어요. MySQL에서 오름차순 정렬이면 NULL이 맨 앞, 내림차순이면 맨 뒤에 와요.

### 6. 집계 함수와 COUNT의 차이

**집계 함수**(aggregate function)는 여러 행을 하나의 값으로 줄이는 함수예요. COUNT, SUM, AVG, MIN, MAX 등이 있고, 따로 적힌 경우가 아니면 **NULL을 무시해요.**

member 테이블(4행, city 중 하나가 NULL)로 세 가지 COUNT를 비교하면 이래요.

| 식 | 세는 것 | 결과 |
|---|---|---|
| `COUNT(*)` | 행 수 (NULL 상관없음) | 4 |
| `COUNT(city)` | city가 NULL이 아닌 행 수 | 3 |
| `COUNT(DISTINCT city)` | NULL이 아닌 서로 다른 값 수 | 2 (seoul, busan) |

`COUNT(1)`은 `COUNT(*)`와 같아요. 둘 다 행 수를 세요.

**대상 행이 0개면** COUNT는 0이지만 SUM, AVG, MAX, MIN은 **NULL**을 돌려줘요. 앱에서 0을 기대하면 `COALESCE(SUM(amount), 0)`처럼 바꿔 줘요.

**LEFT JOIN 뒤 COUNT(*)는 함정이에요.** 회원별 주문 수를 셀 때를 보세요.

```sql
SELECT m.name, COUNT(*) AS a, COUNT(o.id) AS b
FROM member m LEFT JOIN orders o ON o.member_id = m.id
GROUP BY m.id, m.name;
-- kim a=2 b=2 / lee a=1 b=1 / park a=1 b=0 / choi a=1 b=0
```

park은 주문이 없는데 `COUNT(*)`는 1이에요. NULL로 채운 행 1개를 셌기 때문이에요. 오른쪽 테이블의 컬럼(`o.id`)으로 세야 0이 나와요.

### 7. GROUP BY와 HAVING

**GROUP BY**는 같은 값끼리 행을 묶어 그룹당 1행으로 줄여요. 거르는 시점이 두 군데예요.

| 구분 | 언제 거르나 | 집계 함수 사용 |
|---|---|---|
| **WHERE** | 묶기 **전**, 개별 행을 | 불가 |
| **HAVING** | 묶은 **후**, 그룹을 | 가능 |

- `WHERE SUM(amount) > 5000`은 `ERROR 1111 Invalid use of group function`이에요. 그룹 조건은 HAVING에 써요.
- HAVING은 거의 마지막에 최적화 없이 적용돼요. 그래서 그룹과 상관없는 조건은 WHERE에 두라고 MySQL 문서가 권해요.
- **ONLY_FULL_GROUP_BY**(MySQL 5.7.5부터 기본으로 켜진 모드): SELECT 목록에 GROUP BY에 없고 집계도 아닌 컬럼이 있으면 거부해요. `SELECT member_id, amount ... GROUP BY member_id`는 `ERROR 1055`예요. 그룹 안에 amount가 여러 개인데 뭘 보여 줄지 정할 수 없으니까요. 아무 값이나 괜찮으면 `ANY_VALUE(amount)`를 써요.

### 8. 논리적 실행 순서

SQL은 쓰는 순서(SELECT가 맨 앞)와 **처리되는 순서**가 달라요.

| 순서 | 절 | 하는 일 |
|---|---|---|
| 1 | FROM, JOIN, ON | 테이블을 가져와 이어 붙임 |
| 2 | WHERE | 행 거르기 |
| 3 | GROUP BY | 묶기 |
| 4 | HAVING | 그룹 거르기 |
| 5 | (윈도 함수) | 행마다 계산 결과 붙이기 |
| 6 | SELECT | 보여 줄 값 계산, 별칭 생성 |
| 7 | DISTINCT | 중복 제거 |
| 8 | ORDER BY | 정렬 |
| 9 | LIMIT | 개수 자르기 |

예제 쿼리 하나가 단계마다 어떻게 줄어드는지 보세요.

```sql
SELECT member_id, SUM(amount) AS total
FROM orders
WHERE status = 'PAID'
GROUP BY member_id
HAVING SUM(amount) >= 2000
ORDER BY total DESC
LIMIT 2;
-- 결과: (2, 7000), (1, 5000)
```

이 쿼리에는 윈도 함수와 DISTINCT가 없어서, 아래 그림은 표의 9단계 중 그 둘을 뺀 7단계만 보여 줘요.

<LogicalOrder />

이 순서로 설명되는 현상이 많아요.

- **WHERE에서 SELECT 별칭을 못 써요.** `WHERE dbl > 5000`은 `Unknown column 'dbl' in 'where clause'` 오류예요. WHERE(2단계) 때는 별칭(6단계)이 아직 없으니까요.
- MySQL은 GROUP BY, HAVING, ORDER BY에서는 별칭을 허용해요. 다만 HAVING·GROUP BY 별칭은 MySQL 확장이라 다른 DB에선 안 될 수 있어요.
- **윈도 함수 결과도 WHERE에서 못 써요.** 바깥 쿼리로 한 번 감싸서 걸러요(9번 절).

<Aside type="caution" title="'논리적' 순서예요">
이건 결과의 **의미**를 정하는 순서예요. 실제 실행 순서는 옵티마이저가 결과만 같다면 바꿔요. 예를 들어 인덱스로 정렬을 미리 끝내거나, 조건을 조인 전에 먼저 걸기도 해요. 실제로 어떻게 도는지는 [EXPLAIN](../explain/)으로 확인해요.
</Aside>

### 심화: 9. 서브쿼리와 윈도 함수 맛보기

**서브쿼리**(subquery)는 쿼리 안에 넣은 쿼리예요. 바깥 테이블을 참조하는 서브쿼리를 **상관 서브쿼리**(correlated subquery)라고 하고, 개념상 바깥 행마다 다시 평가돼요.

- **EXISTS**는 서브쿼리가 행을 하나라도 돌려주면 참이에요. 무슨 컬럼을 고르는지는 안 봐서 `SELECT 1`이든 `SELECT *`든 같아요.
- "서브쿼리는 무조건 JOIN보다 느리다"는 옛날 이야기예요. MySQL 8.0 이후 옵티마이저는 IN/EXISTS를 세미 조인(짝이 있는지만 확인하고 왼쪽 행을 한 번씩만 남기는 조인)으로, NOT IN/NOT EXISTS를 안티 조인(짝이 없는 행만 남기는 조인)으로 바꿔 처리할 수 있어요. 어느 쪽이 빠른지는 실행 계획으로 확인하는 게 답이에요.

**윈도 함수**(window function, MySQL 8.0+)는 여러 행을 보고 계산하지만 GROUP BY와 달리 **행을 합치지 않고 각 행에 결과를 붙여요.**

```sql
SELECT * FROM (
  SELECT id, member_id, amount,
         SUM(amount) OVER (PARTITION BY member_id) AS member_total,
         ROW_NUMBER() OVER (PARTITION BY member_id ORDER BY id DESC) AS rn
  FROM orders
) t
WHERE rn = 1;   -- 회원별 최근 주문 1건. 안쪽 WHERE에선 rn을 못 씀
```

`OVER (PARTITION BY member_id ...)`는 "member_id가 같은 행끼리 나눠서 계산해"라는 뜻이에요. 안쪽 쿼리만 돌리면 주문 5행이 그대로 5행이고, 각 행에 회원별 합계와 순번이 붙어요.

## 면접 질문

<details>
<summary>Q. INNER JOIN과 LEFT JOIN의 차이는요?</summary>

**답변(30초)** INNER JOIN은 ON 조건에 맞는 짝이 있는 행만 남기고, LEFT JOIN은 왼쪽 테이블 행을 전부 남기면서 짝이 없으면 오른쪽 컬럼을 NULL로 채워요. 회원 4명, 주문 5건 예제에서 INNER는 3행, LEFT는 주문 없는 회원 2명이 더해져 5행이었어요. 그래서 "주문 없는 회원도 보여 줘야 하는 목록"이면 LEFT JOIN을 써요. 단, 오른쪽에 짝이 여러 개면 왼쪽 행이 그만큼 늘어나요.

**꼬리질문**
- Q. 주문 없는 회원만 뽑으려면요? → `LEFT JOIN` 후 `WHERE o.id IS NULL`, 또는 `NOT EXISTS`를 써요.
- Q. MySQL에서 FULL OUTER JOIN은요? → 지원하지 않아요. LEFT JOIN과 RIGHT JOIN 결과를 UNION으로 합쳐 흉내 내요.
- Q. ON을 빼먹으면요? → MySQL은 JOIN과 CROSS JOIN이 문법상 같아서 오류 없이 카테시안 곱(4×5=20행)이 나와요.
</details>

<details>
<summary>Q. WHERE와 HAVING의 차이는요?</summary>

**답변(30초)** WHERE는 GROUP BY로 묶기 전에 개별 행을 거르고, HAVING은 묶은 뒤 그룹을 걸러요. 그래서 SUM, COUNT 같은 집계 함수 조건은 WHERE에 못 쓰고 HAVING에 써요. 반대로 그룹과 상관없는 조건은 WHERE에 둬야 해요. HAVING은 거의 마지막에 최적화 없이 적용돼서, 일찍 걸러 낼 행을 늦게까지 끌고 가기 때문이에요.

**꼬리질문**
- Q. `WHERE SUM(amount) > 5000`을 쓰면요? → MySQL은 `ERROR 1111 Invalid use of group function`을 내요.
- Q. GROUP BY에 없는 컬럼을 SELECT에 쓰면요? → ONLY_FULL_GROUP_BY 모드(5.7.5부터 기본)에서 `ERROR 1055`예요. 그룹 안에 값이 여러 개라 뭘 보여 줄지 정할 수 없어서예요.
</details>

<details>
<summary>Q. COUNT(*)와 COUNT(컬럼)의 차이는요?</summary>

**답변(30초)** `COUNT(*)`는 NULL과 상관없이 행 수를 세고, `COUNT(컬럼)`은 그 컬럼이 NULL이 아닌 행만 세요. `COUNT(DISTINCT 컬럼)`은 NULL을 뺀 서로 다른 값의 수예요. 실무에서 차이가 크게 나는 곳은 LEFT JOIN 뒤예요. 주문 없는 회원도 NULL 행이 하나 붙으니 `COUNT(*)`는 1이 되고, `COUNT(o.id)`로 세야 0이 나와요.

**꼬리질문**
- Q. COUNT(1)은요? → `COUNT(*)`와 같아요. 둘 다 행 수예요.
- Q. 대상 행이 0개면 SUM은요? → NULL이에요. COUNT만 0이에요. 0이 필요하면 `COALESCE(SUM(x), 0)`.
</details>

<details>
<summary>Q. SQL의 실행 순서와, SELECT 별칭을 WHERE에서 못 쓰는 이유는요?</summary>

**답변(30초)** 논리적 처리 순서는 FROM과 JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT 순이에요. 별칭은 SELECT 단계에서 생기는데 WHERE는 그보다 먼저 평가되니까 아직 그 이름을 몰라요. 반대로 ORDER BY는 SELECT 뒤라 별칭을 쓸 수 있어요. 다만 이건 의미상 순서이고, 실제 실행 순서는 옵티마이저가 결과가 같은 범위에서 바꿔요.

**꼬리질문**
- Q. 윈도 함수 결과로 거르려면요? → 윈도 함수도 WHERE 뒤에 계산되니, 서브쿼리나 CTE(`WITH 이름 AS (...)`로 이름 붙인 임시 결과)로 감싸 바깥 WHERE에서 걸러요.
- Q. HAVING에서는 별칭이 되나요? → MySQL은 허용하지만 확장 기능이라 다른 DB에선 안 될 수 있어요.
</details>

<details>
<summary>Q. LEFT JOIN에서 조건을 ON에 두는 것과 WHERE에 두는 것은 어떻게 다른가요?</summary>

**답변(30초)** ON의 조건은 "짝을 고르는 조건"이라 안 맞아도 왼쪽 행은 남고 NULL이 붙어요. WHERE의 조건은 조인이 끝난 뒤 행을 거르는 거라, NULL이 붙은 행은 비교가 참이 안 돼서 사라져요. 그래서 오른쪽 테이블 조건을 WHERE에 쓰면 LEFT JOIN이 사실상 INNER JOIN이 돼요. 예제에서도 PAID 조건을 ON에 두면 4행, WHERE에 두면 2행이었어요.

**꼬리질문**
- Q. INNER JOIN에서도 차이가 있나요? → 없어요. 결과가 같아요. 차이는 외부 조인에서만 생겨요.
- Q. WHERE에 꼭 둬야 한다면요? → `WHERE (o.id IS NULL OR o.status = 'PAID')`처럼 NULL 행을 살리는 조건을 함께 써요.
</details>

<details>
<summary>Q. NULL을 =로 비교하면 어떻게 되나요? NOT IN에 NULL이 섞이면요?</summary>

**답변(30초)** NULL은 "모르는 값"이라 어떤 값과 비교해도 참이 아니라 UNKNOWN이 나와요. WHERE는 참인 행만 남기니 `= NULL`은 오류 없이 0행이고, NULL을 찾을 땐 `IS NULL`을 써요. NOT IN은 목록의 모든 값과 `<>` 비교를 AND로 묶는 거라, 목록에 NULL이 하나라도 있으면 전체가 참이 될 수 없어 결과가 0행이 돼요. 그래서 NOT EXISTS나 LEFT JOIN IS NULL을 쓰거나 서브쿼리에 IS NOT NULL을 붙여요.

**꼬리질문**
- Q. `city <> 'seoul'`은 NULL인 행을 돌려주나요? → 안 돌려줘요. 비교 결과가 UNKNOWN이라 빠져요.
- Q. NULL끼리 같다고 비교하고 싶으면요? → MySQL은 `<=>` 연산자가 있어요. `NULL <=> NULL`은 참이에요.
</details>

<details>
<summary>Q. 서브쿼리와 JOIN 중 무엇이 더 빠른가요?</summary>

**답변(30초)** 한쪽이 항상 빠르다고 말할 수 없어요. 예전 MySQL에선 서브쿼리가 느린 경우가 많았지만, 8.0 이후 옵티마이저는 IN·EXISTS를 세미 조인으로, NOT IN·NOT EXISTS를 안티 조인으로 바꿔 처리할 수 있어요. 그래서 버전과 데이터에 따라 달라지고, 실행 계획을 보고 판단해요. 저는 읽기 쉬운 쪽으로 쓰고 EXPLAIN으로 확인하는 편이에요.

**꼬리질문**
- Q. 상관 서브쿼리가 뭐예요? → 바깥 쿼리의 테이블을 참조하는 서브쿼리예요. 개념상 바깥 행마다 다시 평가돼요.
- Q. GROUP BY와 윈도 함수 차이는요? → GROUP BY는 그룹당 1행으로 합치고, 윈도 함수는 행을 그대로 두고 각 행에 계산 결과를 붙여요.
</details>

## 서술형 연습

<details>
<summary>상황: 관리자 대시보드의 "회원별 주문 수"에서 주문을 한 번도 안 한 회원이 1건으로 표시된다는 문의가 들어왔습니다.</summary>

**상황 파악**
주문 없는 회원도 목록에 나와야 하니 LEFT JOIN을 쓰고 있을 거예요. 0이어야 할 값이 정확히 1이라는 점이 단서예요. 주문이 있는 회원의 숫자는 맞는지도 확인해요.

**원인 후보**
1. LEFT JOIN 뒤 `COUNT(*)`로 셌어요. 주문 없는 회원에도 오른쪽 칸이 NULL인 행이 1개 붙으니 1로 세져요.
2. 이 쿼리에 다른 1:N 테이블(예: 주소)까지 조인해서 행이 불어났을 수도 있어요. 이건 1이 아니라 2배, 3배로 틀린 숫자가 나와요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `COUNT(o.id)`로 변경 | 한 단어 수정, 바로 0이 나옴 | 다른 조인으로 행이 불어난 문제는 못 고침 |
| B. 주문을 먼저 회원별로 집계(서브쿼리)한 뒤 LEFT JOIN + `COALESCE(cnt, 0)` | 다른 테이블을 더 붙여도 숫자가 안 불어남 | 쿼리가 길어지고 실행 계획을 다시 봐야 함 |

**내가 고를 방법**
원인이 1뿐이면 A로 고쳐요. 쿼리에 다른 1:N 조인이 섞여 있다면 B로 바꿔 집계 단위를 분명히 해요. 수정 후 주문 0건, 1건, 여러 건인 회원으로 결과를 검증해요.

**채점 포인트**: LEFT JOIN은 짝 없으면 NULL 행 1개, `COUNT(*)`는 NULL 행도 셈, `COUNT(컬럼)`은 NULL 제외, 1:N 조인의 행 증가, 조인 전 집계, 경계값(0건) 검증.
</details>

<details>
<summary>상황: 게스트 주문(회원 번호 NULL) 기능을 출시한 뒤, "주문 안 한 회원에게 쿠폰 발송" 배치가 매일 0명을 반환해 아무에게도 쿠폰이 안 갑니다.</summary>

**상황 파악**
코드는 그대로인데 데이터에 NULL이 생긴 시점부터 깨졌어요. 오류 없이 0명이 나와서 알림도 안 왔을 거예요. 배치 쿼리를 먼저 봐요.

**원인 후보**
1. `WHERE id NOT IN (SELECT member_id FROM orders)`를 쓰고 있어요. 서브쿼리 결과에 NULL이 하나라도 있으면 `id <> NULL`이 UNKNOWN이라 모든 행이 걸러져요.
2. 다른 조건에서 `= NULL`처럼 NULL을 등호로 비교하고 있을 수도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `NOT EXISTS`로 교체 | NULL과 상관없이 의도대로 동작. 옵티마이저가 안티 조인으로 처리할 수 있음 | 쿼리 모양이 바뀌어 리뷰·테스트 필요 |
| B. `LEFT JOIN ... WHERE o.id IS NULL` | 같은 결과, 많이 쓰는 관용구 | JOIN 조건을 잘못 쓰면 행이 불어날 수 있음 |
| C. 서브쿼리에 `WHERE member_id IS NOT NULL` 추가 | 가장 작은 수정 | 비슷한 NOT IN 쿼리마다 같은 실수를 반복할 수 있음 |

**내가 고를 방법**
당장은 A로 바꿔요. NULL이 생겨도 의미가 변하지 않는 방식이라 같은 사고가 다시 안 나요. 그리고 다른 배치에 같은 NOT IN 패턴이 있는지 찾아보고, "결과 0명이면 알림" 같은 감시를 붙여요. 게스트 주문이 정말 NULL이어야 하는지, 스키마 설계도 같이 검토해요.

**채점 포인트**: NULL 비교는 UNKNOWN(3값 논리), WHERE는 참만 남김, NOT IN + NULL = 0행, NOT EXISTS·LEFT JOIN IS NULL·IS NOT NULL 대안, 오류 없이 조용히 틀리는 문제, 재발 방지(패턴 점검, 결과 감시).
</details>

## 필기 포인트

- **논리적 처리 순서**: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. WHERE에서 SELECT 별칭 사용 불가.
- **집계 조건은 HAVING**. `WHERE SUM(...)`은 틀림. WHERE = 그룹 전 행, HAVING = 그룹 후.
- GROUP BY를 쓰면 SELECT에는 **GROUP BY에 적은 컬럼이나 집계 함수**만.
- **NULL 비교**: `= NULL`이 아니라 `IS NULL` / `IS NOT NULL`. `NULL = NULL`은 참이 아님.
- **COUNT(*)** = NULL 상관없이 전체 행 수. **COUNT(컬럼)** = NULL 제외. 나머지 집계 함수도 NULL 무시.
- 대상 행 0개면 COUNT는 0, SUM·AVG는 NULL.
- `SELECT`의 기본은 **ALL**(중복 허용), 중복 제거는 DISTINCT. ORDER BY 기본은 **ASC**.
- `LIKE`: `%` = 0글자 이상, `_` = 정확히 1글자.
- 관계대수 조인 용어(필기용, 내 말로 요약)
  - **동등 조인**: `=`로 조인. 공통 속성이 결과에 두 번 나옴.
  - **세타 조인**: `=`뿐 아니라 `<`, `>` 같은 비교 연산자로 일반화한 조인.
  - **자연 조인**: 공통 속성 값이 같은 것끼리 조인하고 공통 속성은 한 번만 남김.
  - **세미 조인**: 한쪽을 조인 속성으로 추린 뒤 자연 조인. 교환법칙이 성립하지 않음.
  - **외부 조인**: 자연 조인에서 빠지는 튜플(행)도 NULL로 채워 포함.
- SQL의 `NATURAL JOIN`은 이름이 같은 컬럼 전부로 자동 조인해요. 컬럼이 추가되면 결과가 바뀔 수 있어 실무에선 잘 안 써요.
