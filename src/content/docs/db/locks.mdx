:::tip[한 줄 요약]
InnoDB는 **행이 아니라 인덱스 레코드**에 락을 걸어요. 그래서 인덱스 없이 UPDATE하면 훑은 행 전부가 잠겨요. 재고 차감 같은 동시 수정은 **원자적 조건부 UPDATE**, **비관적 락**(`SELECT ... FOR UPDATE`), **낙관적 락**(version 컬럼) 중 충돌 빈도에 맞게 골라서 막아요.
:::

<Aside type="note" title="이 페이지의 기준">
설명은 MySQL 8.4 공식문서와 MySQL 8.0 기준 책을 바탕으로 했어요. 직접 돌린 실험은 **MySQL 9.6.0**(InnoDB, 기본 격리 수준 REPEATABLE READ)이에요. 이 페이지에 나온 행 락·갭 락·데드락 동작은 8.0·8.4와 같은 영역이에요. 실험 중에는 기다리는 시간을 줄이려고 타임아웃을 1~3초로 낮췄어요.
</Aside>

## 쉽게 이해하기

공유 오피스 회의실을 예약한다고 해 봐요. 두 사람이 동시에 "비어 있네" 하고 같은 시간을 잡으면 겹쳐요. 그래서 문에 **자물쇠**를 걸어요. 먼저 건 사람이 쓰는 동안 다음 사람은 문 앞에서 줄을 서요.

DB의 **락**(lock, 데이터에 거는 자물쇠)도 같아요. 두 주문이 동시에 "재고 1개 남았네" 하고 둘 다 팔면 재고가 -1이 돼요. 락을 걸면 한 명씩 차례로 처리돼서 이런 사고가 안 나요.

자물쇠를 거는 단위가 중요해요. 회의실 하나만 잠그면 다른 회의실은 자유롭게 쓸 수 있어요. 그런데 "3층 어딘가에 있는 회의실"이라고만 알면 3층을 다 돌며 문마다 자물쇠를 걸게 돼요. 인덱스 없이 UPDATE하는 게 딱 이 상황이에요.

단, 실제로는 "보기만 하는 사람"은 줄을 안 서요. InnoDB의 일반 `SELECT`는 자물쇠와 상관없이 미리 찍어 둔 사진(스냅숏)을 보기 때문이에요.

## 제대로 알기

### 1. 왜 락이 필요한가: 갱신 분실

재고 차감 코드를 흔히 이렇게 짜요.

1. `SELECT stock FROM product WHERE id = 1` → 10을 읽음
2. 앱에서 `10 - 1 = 9`를 계산
3. `UPDATE product SET stock = 9 WHERE id = 1`

두 요청이 동시에 1번을 하면 둘 다 10을 읽고 둘 다 9를 써요. 두 개 팔았는데 재고는 하나만 줄었어요. 이걸 **갱신 분실**(lost update, 한쪽 수정이 다른 쪽 수정에 덮여 사라지는 문제)이라고 해요.

MySQL 기본 격리 수준인 REPEATABLE READ에서도 이 문제가 생겨요. 일반 SELECT는 락을 안 걸기 때문이에요. 자세한 실험은 [격리 수준](../isolation-levels/)에 있어요. 이 페이지는 이걸 **락으로 어떻게 막느냐**를 다뤄요.

### 2. 공유 락과 배타 락

행에 거는 락은 두 종류예요.

| 락 | 뜻 | 거는 문장 |
|---|---|---|
| **공유 락**(S, Shared) | "읽는 중이니 바꾸지 마" | `SELECT ... FOR SHARE` |
| **배타 락**(X, Exclusive) | "내가 바꾸는 중이니 아무도 손대지 마" | `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE` |

호환 관계는 이래요.

| 이미 걸린 락 → 새로 요청 | S 요청 | X 요청 |
|---|---|---|
| S | 같이 잡음 | 기다림 |
| X | 기다림 | 기다림 |

S끼리만 같이 잡을 수 있고, X는 누구와도 같이 못 잡아요. 락은 `COMMIT`이나 `ROLLBACK` 때 풀려요.

`FOR SHARE`는 8.0부터 생긴 문법이고, 옛 이름은 `LOCK IN SHARE MODE`예요.

**인텐션 락**(intention lock, IS/IX)도 있어요. "이 테이블의 어떤 행에 S/X를 걸 거예요"라고 **테이블에 붙이는 표시**예요. `FOR UPDATE`나 `UPDATE`는 행에 X를 걸기 전에 테이블에 IX부터 걸어요. IX끼리는 서로 막지 않아서 행 락끼리의 동시 처리를 방해하지 않아요. `LOCK TABLES ... WRITE`처럼 테이블 전체를 잠그려는 요청만 막아요.

### 3. 일반 SELECT는 락을 안 걸어요

| 문장 | 락 | 읽는 값 |
|---|---|---|
| `SELECT ...` | 안 걸음 | 트랜잭션이 찍어 둔 스냅숏 |
| `SELECT ... FOR UPDATE` | X | 최신 커밋 값 |
| `SELECT ... FOR SHARE` | S | 최신 커밋 값 |

그래서 누가 `FOR UPDATE`로 행을 잡고 있어도 일반 SELECT는 기다리지 않아요. 실험에서 A가 `FOR UPDATE`로 잡고 있는 동안 일반 SELECT는 약 0.0002초 만에 끝났어요. (SERIALIZABLE 격리 수준은 예외예요.)

8.0부터는 잠금 읽기에 옵션도 붙일 수 있어요.

- `NOWAIT`: 잠겨 있으면 기다리지 않고 바로 에러
- `SKIP LOCKED`: 잠긴 행은 건너뛰고 나머지만 가져옴

### 4. InnoDB는 인덱스 레코드를 잠가요

여기가 이 페이지에서 가장 중요한 부분이에요. InnoDB는 **행 자체가 아니라 인덱스 레코드**에 락을 걸어요. 인덱스가 하나도 없는 테이블도 InnoDB가 내부에서 만든 숨은 클러스터드 인덱스를 잠가요. ([클러스터드 인덱스](../clustered-covering/)는 PK 순서로 정렬된 테이블 자체예요.)

그리고 잠금 읽기·UPDATE·DELETE는 **검색하며 훑은 인덱스 레코드 전부**를 잠가요. WHERE 조건에 안 맞아서 결과에서 빠지는 행도, 훑었다면 잠겨요.

실험(1000행 `item` 테이블)으로 확인했어요.

| 조건 | 바뀐 행 | 걸린 락 | 다른 세션의 id=999 UPDATE |
|---|---|---|---|
| `WHERE code='C500'` (code 인덱스 없음) | 1 | **1003개** (1000행 + 끝 표시 3개) | 대기 후 1205 에러 |
| `WHERE id=500` (PK) | 1 | 1개 | 바로 성공 |
| `WHERE code='C500'` (code 인덱스 추가 후) | 1 | 3개 | 바로 성공 |

인덱스가 없을 때는 다른 세션의 **INSERT까지** 막혔어요. 끝 표시 3개는 InnoDB가 페이지마다 두는 "마지막 레코드 뒤" 가짜 레코드(supremum)예요.

책의 예도 같아요. `first_name` 인덱스만 있는 30만 행 테이블에서 `first_name='Georgi' AND last_name='Klassen'`을 UPDATE하면 1건만 바뀌지만, first_name이 Georgi인 253건이 모두 잠겨요. 인덱스가 아예 없으면 30만 건 전체가 잠겨요.

그래서 공식문서도 **UPDATE·FOR UPDATE의 조건 컬럼에 좋은 인덱스를 만들라**고 해요. 인덱스는 조회 속도만이 아니라 **락 범위**도 정해요. ([인덱스와 B+트리](../index-btree/))

### 5. 레코드 락, 갭 락, 넥스트 키 락

인덱스 값이 10, 20, 30으로 정렬돼 있다고 해 봐요. 값과 값 사이에는 빈 **틈**이 있어요.

| 락 | 잠그는 것 | 목적 |
|---|---|---|
| **레코드 락**(record lock) | 인덱스 레코드 하나 | 그 행 수정 막기 |
| **갭 락**(gap lock) | 레코드 사이의 빈 틈 (첫 값 앞, 마지막 값 뒤 포함) | 그 틈에 **INSERT 막기** |
| **넥스트 키 락**(next-key lock) | 레코드 락 + 그 레코드 **앞쪽** 틈 | 둘 다 |

넥스트 키 락 구간은 (−∞, 10], (10, 20], (20, 30], (30, +∞)처럼 "앞 틈 + 자기 자신"이에요.

**왜 틈까지 잠그나요?** REPEATABLE READ에서 **팬텀**(phantom, 같은 조건으로 다시 조회했더니 없던 행이 새로 보이는 현상)을 막으려고요. 범위를 잠금 읽기했는데 그 사이에 누가 새 행을 넣으면 결과가 달라지니까, 틈 자체를 막아 둬요. InnoDB는 RR에서 검색·인덱스 스캔에 기본으로 넥스트 키 락을 써요.

실험(`k` 컬럼에 일반 인덱스, 값 10·20·30)에서 A가 `SELECT * FROM t WHERE k=20 FOR UPDATE`를 했어요.

| B의 작업 | 결과 |
|---|---|
| `INSERT k=5` | 성공 |
| `INSERT k=15` | **막힘** (10~20 틈) |
| `INSERT k=25` | **막힘** (20~30 틈) |
| `INSERT k=35` | 성공 |
| `UPDATE ... WHERE k=30` | 성공 (갭 락은 레코드 30 자체는 안 잠금) |

실제로 읽은 건 1행인데 앞뒤 틈에 INSERT가 막혔어요. 같은 행을 **PK로**(`WHERE id=2 FOR UPDATE`) 잠그면 레코드 락 하나뿐이라 k=15 INSERT도 성공했어요. PK나 유니크 인덱스로 **있는** 한 행을 정확히 찾으면 틈은 안 잠가요. (찾는 행이 없으면 그 자리 틈에 갭 락이 걸려요. 아래 출석 서술형이 이 경우예요.)

갭 락에서 헷갈리는 점 두 가지예요.

- **갭 락끼리는 충돌하지 않아요.** 두 트랜잭션이 같은 틈에 갭 락을 동시에 잡을 수 있어요. 갭 락이 막는 건 오직 INSERT예요.
- INSERT는 넣기 전에 **인서트 인텐션 락**(insert intention lock)이라는 특수한 갭 락을 걸어요. 같은 틈이라도 넣는 위치가 다르면 서로 안 기다려요. 하지만 그 틈에 누가 갭 락을 잡고 있으면 기다려요.

<Aside type="tip" title="READ COMMITTED로 바꾸면">
READ COMMITTED에서는 검색용 갭 락을 쓰지 않아요(외래 키·중복 키 검사에만 써요). 실험에서도 RC에서 같은 `k=20 FOR UPDATE`는 레코드 락만 걸었고 k=15 INSERT가 성공했어요. 대신 팬텀을 락으로 막아 주지 않아요.
</Aside>

책은 갭·넥스트 키 락이 의외로 데드락과 대기를 자주 만든다고 짚어요. 이 락은 원래 STATEMENT 형식 바이너리 로그 복제 결과를 맞추려는 목적이 커서, 바이너리 로그를 ROW 형식(8.0 기본값)으로 쓰면 줄일 수 있다고 권해요.

### 6. AUTO_INCREMENT 락

`AUTO_INCREMENT` 번호를 받을 때도 잠깐 락을 걸어요. 테이블 수준이지만 트랜잭션 끝까지가 아니라 **번호를 받는 순간만** 잡아요. `innodb_autoinc_lock_mode` 기본값은 8.0부터 2(5.7까지는 1)예요.

그래서 INSERT가 롤백돼도 이미 받은 번호는 돌아가지 않아요. id에 **구멍**이 생기는 이유예요.

### 7. 락 대기와 타임아웃 (ERROR 1205)

락을 기다리는 최대 시간은 `innodb_lock_wait_timeout`이에요. 기본 **50초**이고, 세션·전역 모두 실행 중에 바꿀 수 있어요. 넘으면 이 에러가 나요.

```
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

<Aside type="caution" title="1205는 문장만 롤백돼요">
실험(MySQL 9.6, `innodb_rollback_on_timeout` 기본값 OFF)에서 1205가 나도 **그 문장만** 취소되고 트랜잭션은 열린 채 남았어요. 앞에서 성공한 UPDATE도 살아 있었고, 직접 `ROLLBACK`해야 되돌아갔어요. 그래서 앱은 1205를 받으면 직접 롤백하거나 재시도해야 해요. (이 동작을 설명한 공식문서 원문은 이번에 직접 확인하지 못했고, 서버 기본값과 실험으로 확인했어요.)
</Aside>

### 8. 데드락 (ERROR 1213)

**데드락**(deadlock, 교착 상태)은 둘 이상의 트랜잭션이 서로 상대가 가진 락을 기다려서 아무도 못 나아가는 상태예요. 주로 여러 행을 **반대 순서로** 잠글 때 생겨요.

실험에서 A는 id 1 → 2 순서로, B는 id 2 → 1 순서로 재고를 차감했어요.

1. A가 id=1, B가 id=2를 잠가요.
2. A가 id=2를 요청 → B를 기다려요.
3. B가 id=1을 요청 → A를 기다려요. 서로 기다리는 원이 생겨요.
4. InnoDB가 원을 찾아서 B를 롤백했어요. A는 정상 커밋했어요.

**InnoDB의 처리 방식**

- `innodb_deadlock_detect`(기본 ON)가 켜져 있으면, InnoDB가 "누가 누구를 기다리나" 그래프에서 원을 찾아요.
- 원을 찾으면 **희생자** 하나를 롤백해요. 바꾼 행 수가 적은(=되돌릴 게 적은) 작은 트랜잭션을 고르려 해요.
- 희생자는 아래 에러를 받고, **트랜잭션 전체**가 롤백돼요. 실험에서도 B가 먼저 성공했던 id=2 차감까지 사라졌어요.

```
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

| 구분 | 1205 (타임아웃) | 1213 (데드락) |
|---|---|---|
| 원인 | 너무 오래 기다림 | 서로 기다리는 원 |
| 롤백 범위 | 기본은 **그 문장만** | **트랜잭션 전체** |
| 앱 처리 | 직접 ROLLBACK 후 재시도 | 트랜잭션 처음부터 재시도 |

**원인 찾기**

- `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK`에 **마지막 1건**이 나와요. 각 트랜잭션이 가진 락(`HOLDS THE LOCK(S)`), 기다리던 락(`WAITING FOR THIS LOCK TO BE GRANTED`), 롤백된 쪽(`WE ROLL BACK TRANSACTION (2)`)이 보여요.
- 모든 데드락을 에러 로그에 남기려면 `innodb_print_all_deadlocks=ON`(기본 OFF)으로 켜요.
- 지금 걸린 락과 대기 관계는 `performance_schema.data_locks`, `data_lock_waits`로 봐요(8.0).

**줄이는 법** (공식문서 권장)

- 트랜잭션을 짧게 유지해요.
- 여러 행·테이블은 **항상 같은 순서로** 잠가요. 예: id 오름차순.
- `FOR UPDATE`·`UPDATE ... WHERE` 조건 컬럼에 인덱스를 만들어 잠기는 범위를 줄여요.
- `LOCK TABLES` 대신 트랜잭션을 써요.
- 그리고 **로직이 맞아도 데드락은 날 수 있으니 재시도 처리를 꼭 넣어요.**

공식문서는 격리 수준이 데드락 발생 여부와 상관없다고 해요. 데드락은 읽기가 아니라 쓰기·잠금에서 생기기 때문이에요. 다만 RC는 갭 락을 안 쓰니 **갭 락 때문에 생기는 데드락**은 줄어든다는 점은 구분해 두세요.

<Aside type="note" title="Java 데드락과 비교">
"서로 상대가 가진 자원을 기다린다"는 구조는 Java 스레드 데드락과 같아요. InnoDB는 원을 **스스로 찾아 한쪽을 롤백**해 줘요. 데드락이 생기는 조건을 Java 쪽과 나란히 보려면 → [Java 동기화](../../java/synchronization/)
</Aside>

동시 접속 스레드가 아주 많으면 데드락 감지 자체가 느려질 수 있어요. 이럴 때 감지를 끄고(`innodb_deadlock_detect=OFF`) 타임아웃을 50초보다 훨씬 짧게 잡는 선택지도 있어요.

### 9. 재고 차감 해결책 3가지

갱신 분실을 막는 대표 방법은 세 가지예요.

**① 원자적 조건부 UPDATE**

읽고-계산하고-쓰는 과정을 SQL 한 문장에 넣어요. **원자적**(atomic, 중간에 끼어들 틈 없이 한 번에)이라는 뜻이에요.

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ? AND stock >= 1;
-- 바뀐 행 수(affected rows)가 0이면 품절 처리
```

UPDATE가 X 락을 잡고 **최신 값 기준으로** 조건을 확인하니 틈이 없어요. 실험에서 재고 1에 세 세션이 동시에 실행하자 바뀐 행 수가 1, 0, 0이었고 최종 재고는 0이었어요. 음수가 안 됐어요.

**② 비관적 락** (pessimistic lock, "충돌이 날 거라 보고 먼저 잠근다")

```sql
BEGIN;
SELECT stock FROM product WHERE id = ? FOR UPDATE;  -- X 락, 다른 요청은 줄 섬
-- 앱에서 재고 확인·계산
UPDATE product SET stock = ? WHERE id = ?;
COMMIT;  -- 락 풀림
```

실험에서 A가 `FOR UPDATE`로 잡고 2초 뒤 재고를 9로 커밋하자, B는 약 1.5초 기다렸다가 **A가 바꾼 9**를 읽었어요. 차례로 줄을 서서 처리돼요.

**③ 낙관적 락** (optimistic lock, "충돌이 드물 거라 보고 잠그지 않는다")

```sql
-- 읽을 때 version도 같이 읽음 (예: version = 0)
UPDATE product
SET stock = ?, version = version + 1
WHERE id = ? AND version = 0;
-- 바뀐 행 수가 0이면 그 사이 누가 먼저 바꾼 것 → 다시 읽고 재시도하거나 실패 응답
```

실험에서 두 요청이 모두 version=0을 읽고 차례로 실행하자 바뀐 행 수가 1, 0이었어요. JPA는 `@Version` 필드로 이 SQL을 자동으로 만들어 줘요. 바뀐 행이 0이면 낙관적 락 예외를 던지는데, 자세한 건 Spring/JPA 쪽에서 다뤄요.

**비교**

| 방법 | 장점 | 단점 | 잘 맞는 곳 |
|---|---|---|---|
| ① 원자적 UPDATE | 가장 간단하고 빠름. 트랜잭션을 짧게 끝내면 락 보유도 짧음 | 조건을 SQL 한 줄로 표현할 수 있을 때만 가능. 인기 상품 한 행에 요청이 몰리면 그 행에서 줄을 섬 | 재고·포인트 같은 단순 증감 |
| ② 비관적 락 `FOR UPDATE` | DB가 순서를 보장. 복잡한 검증 로직도 넣을 수 있음 | 대기 증가, 트랜잭션 동안 DB 커넥션 점유, 여러 행이면 데드락 위험 | 충돌이 잦고, 읽은 뒤 복잡한 계산이 필요한 경우 |
| ③ 낙관적 락 version | 읽고 고민하는 동안 락이 없어 가벼움 | 충돌이 잦으면 재시도가 폭주, 재시도 코드 필요 | 충돌이 드문 수정 (게시글 편집, 설정 변경) |

선택 기준은 보통 **충돌 빈도**예요. 인기 상품 선착순처럼 충돌이 잦으면 재시도가 쌓이는 낙관적 락보다 ①이나 ②가 나은 경우가 많아요. 충돌이 드물면 ③이 대기 없이 가벼워요.

<Aside type="caution" title="낙관적 락도 순간적으로는 X 락을 잡아요">
버전 조건 UPDATE도 실행되는 순간엔 X 락을 걸어요. "읽고 고민하는 동안" 잠그지 않을 뿐이에요.
</Aside>

**서버가 여러 대라면?** DB 락은 DB 한 곳에서 걸리니 서버가 몇 대든 통해요. 반면 Java `synchronized`는 서버 1대(JVM 하나) 안에서만 효과가 있어요. 트래픽이 아주 커서 DB 앞단에서 미리 걸러야 할 때 쓰는 **Redis 분산 락**과 Redis 원자 연산은 Redis 섹션에서 다뤄요.

## 면접 질문

<details>
<summary>Q. 공유 락과 배타 락의 차이는요?</summary>

**답변(30초)** 공유 락(S)은 읽을 권리, 배타 락(X)은 수정·삭제할 권리예요. S끼리는 여러 트랜잭션이 같이 잡을 수 있지만, X는 S와도 X와도 같이 못 잡아요. `SELECT ... FOR SHARE`가 S, `FOR UPDATE`와 UPDATE·DELETE가 X를 걸어요. 둘 다 커밋이나 롤백 때 풀려요.

**꼬리질문**
- Q. 누가 FOR UPDATE로 잡은 행을 일반 SELECT로 읽을 수 있나요? → 네. 일반 SELECT는 스냅숏을 읽어서 락을 안 기다려요. 막히는 건 잠금 읽기와 UPDATE·DELETE예요.
- Q. 인텐션 락은 뭐예요? → 행에 락을 걸 거라고 테이블에 붙이는 표시예요. IX끼리는 호환이라 행 락을 방해하지 않고, 테이블 전체 락 요청만 막아요.
</details>

<details>
<summary>Q. 레코드 락, 갭 락, 넥스트 키 락을 설명해 주세요.</summary>

**답변(30초)** 레코드 락은 인덱스 레코드 하나를, 갭 락은 레코드 사이의 빈 틈을, 넥스트 키 락은 레코드와 그 앞 틈을 함께 잠가요. 갭을 잠그는 이유는 그 틈에 새 행이 INSERT되는 걸 막아 REPEATABLE READ에서 팬텀을 막기 위해서예요. 그래서 InnoDB는 RR에서 기본으로 넥스트 키 락을 써요. PK나 유니크 인덱스로 한 행을 정확히 찾으면 레코드 락만 걸어요.

**꼬리질문**
- Q. 갭 락끼리는 충돌하나요? → 안 해요. 갭 락이 막는 건 INSERT뿐이에요. 그래서 두 트랜잭션이 같은 틈을 잡고 둘 다 INSERT하려다 데드락이 나기도 해요.
- Q. READ COMMITTED에선요? → 검색용 갭 락을 안 써서 틈에 INSERT가 가능해요. 대신 팬텀을 락으로 막지 않아요.
</details>

<details>
<summary>Q. 인덱스가 없는 컬럼으로 UPDATE하면 어떻게 되나요?</summary>

**답변(30초)** 테이블의 거의 모든 행이 잠길 수 있어요. InnoDB는 행이 아니라 검색하며 훑은 인덱스 레코드에 락을 거는데, 인덱스가 없으면 전체를 훑으니까요. 실험에서 1000행 테이블에 1건만 바꾸는 UPDATE가 1003개의 락을 걸었고, 다른 행 UPDATE와 INSERT까지 타임아웃이 났어요. 그래서 UPDATE 조건 컬럼에 인덱스를 거는 건 속도뿐 아니라 락 범위 문제예요.

**꼬리질문**
- Q. 보조 인덱스로 찾아서 UPDATE하면 뭐가 잠겨요? → 보조 인덱스 레코드와 그 행의 PK(클러스터드) 레코드가 함께 잠겨요.
- Q. 잠긴 락은 어떻게 확인해요? → `performance_schema.data_locks`와 `data_lock_waits`로 봐요.
</details>

<details>
<summary>Q. 데드락이 뭐고, InnoDB는 어떻게 처리하나요?</summary>

**답변(30초)** 데드락은 두 트랜잭션이 서로 상대가 가진 락을 기다려 둘 다 멈춘 상태예요. 보통 여러 행을 반대 순서로 잠글 때 생겨요. InnoDB는 대기 그래프에서 원을 찾아, 바꾼 행이 적은 작은 트랜잭션을 롤백하고 1213 에러를 줘요. 예방은 잠금 순서 통일, 짧은 트랜잭션, 조건 컬럼 인덱스이고, 그래도 날 수 있어서 재시도 로직을 꼭 넣어요.

**꼬리질문**
- Q. 원인은 어떻게 찾나요? → `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK`에 마지막 1건이 나와요. 전부 남기려면 `innodb_print_all_deadlocks`를 켜요.
- Q. 1205와 1213은 뭐가 달라요? → 1205는 타임아웃이고 기본적으로 그 문장만 취소돼서 직접 롤백해야 해요. 1213은 데드락이고 트랜잭션 전체가 롤백돼요.
</details>

<details>
<summary>Q. 낙관적 락과 비관적 락은 언제 쓰나요?</summary>

**답변(30초)** 비관적 락은 충돌을 예상하고 `FOR UPDATE`로 먼저 잠가서 차례로 처리해요. 순서는 확실하지만 대기와 데드락 위험이 있어요. 낙관적 락은 잠그지 않고 version 조건으로 UPDATE해서, 바뀐 행이 0이면 충돌로 보고 재시도해요. 그래서 충돌이 잦은 선착순 재고엔 비관적 락이나 원자적 UPDATE를, 충돌이 드문 게시글 수정엔 낙관적 락을 보통 써요.

**꼬리질문**
- Q. 서버가 여러 대면 synchronized로 안 되나요? → synchronized는 JVM 하나 안에서만 통해요. DB 락은 DB에서 걸려서 서버 대수와 상관없이 통해요.
- Q. 낙관적 락은 DB 락을 전혀 안 쓰나요? → UPDATE 실행 순간엔 X 락을 잡아요. 읽고 계산하는 동안 잠그지 않을 뿐이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 재고 100개 한정판에 주문이 몰렸는데 재고가 -7이 됐습니다. 코드는 findById로 상품을 읽고, stock이 0보다 크면 stock을 1 줄여 save합니다.</summary>

**상황 파악**
판 수량이 실제 재고보다 많아요. 동시 요청이 같은 재고 값을 읽고 각자 차감한 갱신 분실 문제예요. 돈과 직결되는 정합성 문제라 우선순위가 높아요.

**원인 후보**
1. `findById`는 일반 SELECT라 락이 없어요. 여러 요청이 같은 재고를 동시에 읽어요.
2. "읽기 → 앱에서 확인 → 쓰기" 사이에 틈이 있어요. REPEATABLE READ여도 이 틈은 안 막혀요.
3. 서버가 여러 대라면 앱 코드의 `synchronized`로도 못 막아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 원자적 UPDATE `SET stock = stock - 1 WHERE id = ? AND stock >= 1` + 바뀐 행 수 확인 | 가장 간단·빠름. 음수가 구조적으로 불가능 | 차감 전후에 복잡한 검증을 넣기 어려움 |
| B. 비관적 락 `FOR UPDATE` | 순서 보장, 복잡한 로직도 가능 | 인기 상품에 대기가 몰림, 트랜잭션 동안 커넥션 점유 |
| C. 낙관적 락 `@Version` | 락 대기 없음 | 충돌이 몰리면 재시도 폭주, 실패 응답 증가 |

**내가 고를 방법**
A를 골라요. 선착순은 충돌이 아주 잦아서 C는 맞지 않고, 재고 차감은 SQL 한 줄로 표현돼서 B만큼 길게 잠글 필요가 없어요. 바뀐 행 수가 0이면 품절로 응답해요. 트랜잭션은 짧게 유지해서 락 보유 시간을 줄여요. 트래픽이 DB가 감당 못 할 만큼 커지면 Redis로 앞단에서 거르는 방법을 함께 검토해요.

**채점 포인트**: 일반 SELECT는 락 없음, 갱신 분실, 원자적 조건부 UPDATE와 affected rows 확인, 비관적·낙관적 트레이드오프, 충돌 빈도에 따른 선택, 재시도, 짧은 트랜잭션, 다중 서버에서 synchronized 한계.
</details>

<details>
<summary>상황: 운영 중 만료 주문 정리 배치(기준 시각보다 오래된 주문의 status를 EXPIRED로 바꾸는 UPDATE, 조건 컬럼은 created_at)를 돌렸더니, 주문 생성 API가 수십 초씩 멈추다 Lock wait timeout 에러가 쏟아졌습니다.</summary>

**상황 파악**
배치 하나 때문에 새 주문 INSERT까지 막혔어요. 바꾸려던 행과 상관없는 INSERT가 막혔다는 게 단서예요. 기본 타임아웃이 50초라 그만큼 멈췄다가 1205가 났을 거예요.

**원인 후보**
1. `created_at`에 인덱스가 없어 풀 스캔 → 훑은 모든 행과 틈이 잠겨 INSERT도 막혀요.
2. 배치가 한 트랜잭션으로 아주 많은 행을 바꿔서 락을 오래 쥐고 있어요.
3. 1205는 기본적으로 문장만 취소돼서, 앱이 롤백을 안 하면 트랜잭션이 열린 채 남아 락이 더 오래 갈 수 있어요.

확인은 `performance_schema.data_locks`로 배치 트랜잭션이 몇 개의 락을 잡고 있는지 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `created_at`에 인덱스 추가 | 조건에 맞는 범위만 잠가 락 범위가 크게 줄어듦 | 주문 INSERT마다 인덱스 갱신 비용, 운영 중 인덱스 추가 작업 부담 |
| B. PK 범위로 잘게 나눠 짧은 트랜잭션 반복 (예: 1000건씩 커밋) | 락 보유 시간이 짧아 API가 잠깐씩만 기다림 | 배치 전체 시간 증가, 중간 실패 시 이어서 처리하는 로직 필요 |
| C. 트래픽 적은 시간에 실행 | 코드 변경 없음 | 근본 해결이 아님, 데이터가 늘면 다시 문제 |

**내가 고를 방법**
A와 B를 함께 해요. 인덱스로 잠기는 범위를 줄이고, 잘게 나눠 커밋해서 잠그는 시간도 줄여요. C는 보조 수단으로만 써요. 1205를 받으면 앱에서 롤백하도록 처리도 확인해요.

**채점 포인트**: InnoDB는 인덱스 레코드를 잠금, 인덱스 없는 UPDATE의 락 확대, 갭 락으로 INSERT 차단, data_locks로 확인, 트랜잭션 쪼개기, 1205 후 롤백.
</details>

<details>
<summary>상황: 포인트 이체 기능에서 A→B, B→A 이체가 동시에 들어오면 가끔 Deadlock found 에러(1213)가 납니다.</summary>

**상황 파악**
두 이체가 각각 두 계좌 행을 잠그는데, 잠그는 순서가 반대예요. 가끔만 나는 건 두 요청이 거의 동시에 올 때만 원이 생기기 때문이에요.

**원인 후보**
1. 이체 T1은 A → B 순서로, T2는 B → A 순서로 잠가서 서로를 기다려요.
2. 트랜잭션 안에 외부 호출 같은 느린 작업이 있어 락 보유 시간이 길면 겹칠 확률이 올라가요.

확인은 `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK`에서 두 트랜잭션이 각자 어느 행을 쥐고 무엇을 기다렸는지 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 항상 작은 계좌 ID부터 잠그기 | 반대 순서 원이 구조적으로 안 생김 | 모든 코드 경로가 같은 규칙을 지켜야 함 |
| B. 1213 받으면 트랜잭션 전체 재시도 | 어떤 데드락에도 안전망 | 재시도 중 지연 증가, 재시도 횟수 제한 필요 |
| C. 트랜잭션을 짧게 (외부 호출은 밖으로) | 겹칠 확률 자체가 줄어듦 | 구조 변경이 필요할 수 있음 |

**내가 고를 방법**
A로 원인을 없애고, B를 안전망으로 같이 둬요. 공식문서도 로직이 맞아도 데드락은 날 수 있으니 재시도를 넣으라고 해요. 1213은 트랜잭션 전체가 롤백되니 이체 전체를 처음부터 다시 실행해요. C도 함께 적용해 겹칠 확률을 줄여요.

**채점 포인트**: 반대 순서 잠금이 원인, 잠금 순서 통일, InnoDB의 자동 감지와 희생자 롤백, 1213은 트랜잭션 전체 롤백이라 전체 재시도, LATEST DETECTED DEADLOCK으로 확인, 짧은 트랜잭션.
</details>

<details>
<summary>상황: "회원당 하루 1회 출석"을 SELECT ... FOR UPDATE로 오늘 기록이 없는지 확인한 뒤 INSERT하도록 만들었는데, 같은 회원의 동시 요청에서 데드락이 납니다.</summary>

**상황 파악**
잠금 읽기로 중복을 막으려 했는데 오히려 데드락이 났어요. 찾는 행이 **아직 없다**는 게 핵심이에요.

**원인 후보**
1. 없는 행을 `FOR UPDATE`하면 레코드가 없으니 그 자리 **틈에 갭 락**이 걸려요(RR 기준).
2. 갭 락끼리는 충돌하지 않아서 두 요청이 같은 틈을 동시에 잡아요.
3. 둘 다 INSERT하려 하면, INSERT는 상대의 갭 락에 막혀요. 서로 기다리는 원이 생겨요.

실험(MySQL 9.6, `(member_id, day)` 일반 인덱스)에서 그대로 재현됐어요. A와 B가 같은 회원·같은 날짜를 `FOR UPDATE`로 조회(0행)한 뒤 둘 다 INSERT하자 B가 1213을 받고 A만 커밋됐어요. `LATEST DETECTED DEADLOCK`에는 두 트랜잭션 모두 `locks gap before rec`(갭 락)를 쥔 채 `insert intention waiting`(인서트 인텐션 대기)으로 서로를 기다린 기록이 남았어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. (회원, 날짜)에 유니크 제약 + 그냥 INSERT하고 중복 키 에러를 "이미 출석"으로 처리 | DB가 중복을 확실히 막음, 잠금 읽기 불필요 (실험: 동시 INSERT에서 뒤 요청은 앞 요청 커밋을 기다렸다가 1062 중복 키 에러, 데드락 없음) | 중복 키 에러를 정상 흐름으로 다루는 코드 필요 |
| B. `INSERT ... ON DUPLICATE KEY UPDATE` (유니크 제약 필요) | 한 문장으로 끝남 | 이미 있을 때 무엇을 할지 SQL로 정해야 함 |
| C. 격리 수준을 READ COMMITTED로 | 검색용 갭 락이 없어짐 | 중복 방지 수단이 사라짐(유니크 제약이 여전히 필요), 다른 쿼리 동작도 바뀜 |

**내가 고를 방법**
A를 골라요. "중복 금지"는 앱의 확인 로직보다 DB 제약이 확실해요. 잠금 읽기가 필요 없어지니 갭 락 데드락도 사라져요. B는 기존 행을 갱신해야 하는 경우에 써요.

**채점 포인트**: 없는 행에 대한 FOR UPDATE는 갭 락, 갭 락끼리는 호환, INSERT는 갭 락에 막힘, 유니크 제약으로 중복 방지, 중복 키 에러 처리.
</details>

## 필기 포인트

- InnoDB는 **인덱스 레코드**를 잠금. 인덱스 없는 UPDATE는 훑은 행 전부 잠김.
- S끼리만 호환. X는 S·X 모두와 충돌. IX끼리는 호환.
- 넥스트 키 락 = 레코드 락 + **앞쪽** 갭 락. RR 기본. 목적은 팬텀 방지.
- 갭 락끼리는 충돌 안 함. 막는 건 INSERT뿐.
- RC는 검색용 갭 락 없음.
- 일반 SELECT는 락 없음(SERIALIZABLE 제외).
- `innodb_lock_wait_timeout` 기본 50초, 1205. 데드락은 1213, 트랜잭션 전체 롤백.
- AUTO_INCREMENT 번호는 롤백돼도 돌아가지 않음. `innodb_autoinc_lock_mode` 8.0 기본 2.
- 격리 수준은 데드락 발생 여부와 무관(공식문서).
