:::tip[한 줄 요약]
**트랜잭션**은 여러 변경을 "**전부 반영(COMMIT) 아니면 전부 취소(ROLLBACK)**"로 묶는 작업 단위예요. 이 묶음이 지켜야 할 성질이 **ACID**(원자성·일관성·격리성·지속성)이고, MySQL InnoDB는 **undo 로그로 되돌리고 redo 로그로 커밋된 변경을 지켜요.**
:::

<Aside type="note" title="이 페이지의 기준">
설명은 MySQL 8.4 공식문서와 Real MySQL 8.0을 바탕으로 했어요. 직접 돌린 실험은 **MySQL 9.6.0**(InnoDB, 기본 격리 수준 REPEATABLE READ, 노트북)이에요. 숫자는 "경향"으로 봐 주세요.
</Aside>

## 쉽게 이해하기

내 통장(A)에서 친구 통장(B)으로 30만 원을 보낸다고 해 봐요. 은행은 두 가지 일을 해요. A에서 30만 원을 빼고, B에 30만 원을 더해요.

그런데 A에서 돈을 뺀 직후 서버가 꺼지면 어떻게 될까요? 내 돈은 빠졌는데 친구는 못 받았어요. 30만 원이 허공으로 사라진 거예요.

그래서 DB는 이 두 일을 **한 묶음**으로 취급해요. 둘 다 끝나면 "확정(COMMIT)"하고, 중간에 문제가 생기면 둘 다 "없던 일(ROLLBACK)"로 돌려요. 이 묶음이 **트랜잭션**(transaction, 쪼갤 수 없는 작업 묶음)이에요.

은행이 믿을 만하려면 네 가지가 필요해요. 반만 처리되는 일이 없어야 하고(원자성), 이체 전후로 잔액 규칙이 깨지지 않아야 하고(일관성), 동시에 일어나는 다른 이체가 내 중간 상태를 보면 안 되고(격리성), "이체 완료" 문자를 받았으면 정전이 나도 기록이 남아야 해요(지속성). 이 네 가지의 영어 첫 글자가 **ACID**예요.

단, 실제 DB는 "되돌리기"와 "완료 기록 지키기"를 각각 다른 장부로 해요. 되돌리기용이 **undo 로그**, 완료 기록용이 **redo 로그**예요. 아래에서 자세히 봐요.

## 제대로 알기

### 1. 트랜잭션이 없으면 생기는 일

트랜잭션의 핵심은 **부분 반영**(partial update, 일부만 저장되는 것)을 막는 거예요. 쿼리가 하나든 여러 개든 마찬가지예요.

MySQL의 MyISAM·MEMORY 엔진은 트랜잭션을 지원하지 않아요. 그래서 INSERT 세 개 중 세 번째가 실패하면 앞의 두 개는 그대로 남아요. 개발자가 그걸 찾아서 직접 지워야 해요. InnoDB는 트랜잭션을 지원하니 실패하면 ROLLBACK 한 번으로 끝나요.

```sql
-- 계좌 이체: 둘 다 되거나, 둘 다 안 되거나
START TRANSACTION;
UPDATE acct SET bal = bal - 300 WHERE id = 1;  -- A 출금
UPDATE acct SET bal = bal + 300 WHERE id = 2;  -- B 입금
COMMIT;      -- 문제 생기면 대신 ROLLBACK;
```

실험(MySQL 9.6)에서 id1=900, id2=1000인 상태로 위 이체를 COMMIT하니 600 / 1300이 됐어요. 합계 1900이 그대로예요. 출금만 한 상태에서 ROLLBACK하니 900 / 1000으로 돌아왔어요.

### 2. ACID 네 글자

| 글자 | 뜻 | 계좌 이체로 말하면 |
|---|---|---|
| **A**tomicity(원자성) | 전부 되거나 전부 안 되거나 | 출금만 되고 입금이 안 되는 일은 없어요 |
| **C**onsistency(일관성) | 트랜잭션 전후로 데이터가 올바른 상태 | 아래에서 두 가지 정의를 따로 봐요 |
| **I**solation(격리성) | 동시에 도는 트랜잭션끼리 서로의 중간 상태를 안 봄 | 이체 도중의 잔액을 다른 조회가 보지 않아요 |
| **D**urability(지속성) | 커밋된 건 장애가 나도 남음 | "이체 완료" 후 정전이 나도 기록이 살아 있어요 |

**격리성은 정도를 조절할 수 있어요.** 얼마나 엄격하게 막을지를 **격리 수준**(isolation level)으로 정해요. MySQL 기본값은 REPEATABLE READ예요. 자세한 건 [격리 수준](../isolation-levels/)에서 다뤄요.

### 3. 일관성(C)은 정의가 두 가지예요

C는 출처마다 설명이 달라서 헷갈리기 쉬워요.

| 관점 | 설명 |
|---|---|
| **교과서(DB 이론)에서 흔한 설명** | 트랜잭션 전후로 **제약조건**(PK, FK, CHECK 같은 DB 규칙)과 **업무 규칙**(예: 이체 전후 잔액 합계가 같다)이 지켜지는 것 |
| **MySQL 공식문서** | 크래시가 나도 데이터가 깨지지 않게 하는 내부 장치. **doublewrite buffer**와 **크래시 복구**(crash recovery)를 C 항목에 넣어요 |

면접에서는 보통 교과서 쪽인 "제약조건과 규칙이 깨지지 않는 상태를 유지한다"를 먼저 말해요. 여기에 "MySQL 문서는 크래시 보호 장치를 C로 분류하기도 한다"를 덧붙이면 깊이가 보여요.

### 4. MySQL은 ACID를 무엇으로 지키나

MySQL 공식문서가 각 글자에 대응시키는 InnoDB 기능이에요.

| 글자 | InnoDB 쪽 장치 |
|---|---|
| A | autocommit 설정, COMMIT, ROLLBACK |
| C | doublewrite buffer, 크래시 복구 |
| I | autocommit, 격리 수준(`SET TRANSACTION`), InnoDB 잠금 |
| D | doublewrite buffer, `innodb_flush_log_at_trx_commit`, `sync_binlog` 등 설정, 그리고 디스크 캐시·fsync·UPS 같은 하드웨어 쪽 요소 |

지속성은 DB 설정만으로 끝나지 않고 **디스크와 OS까지** 협조해야 한다는 점이 눈에 띄어요.

### 5. autocommit: 문장 하나가 곧 트랜잭션

**autocommit**(자동 커밋)은 새 연결마다 **기본 ON**이에요. ON이면 SQL 문장 하나하나가 각자 트랜잭션이 되고, 에러가 없으면 실행 직후 바로 커밋돼요.

- 여러 문장을 묶고 싶으면 `START TRANSACTION`(또는 `BEGIN`)으로 열고 `COMMIT`/`ROLLBACK`으로 닫아요.
- `SET autocommit=0`이면 세션에 **항상 트랜잭션이 열려 있어요.** COMMIT이나 ROLLBACK을 하면 곧바로 다음 트랜잭션이 시작돼요.
- autocommit=0 세션이 COMMIT 없이 끝나면 MySQL은 **마지막 트랜잭션을 롤백**해요.

실험(MySQL 9.6)에서 확인한 내용이에요.

| 실험 | 결과 |
|---|---|
| autocommit ON, 세션 A가 잔액을 900으로 UPDATE | 세션 B가 **즉시** 900을 봤어요 |
| autocommit OFF, A가 500으로 UPDATE 후 대기 | A는 500, B는 여전히 900. 열린 트랜잭션이 1개 보였어요 |
| 그 상태로 A가 COMMIT 없이 연결 종료 | B가 다시 보니 900. **자동 롤백**됐어요 |

COMMIT은 변경을 영구화하고 다른 세션에 보이게 해요. COMMIT과 ROLLBACK 둘 다 트랜잭션 동안 잡은 **잠금**(lock, 다른 트랜잭션이 같은 행을 못 건드리게 거는 표시)을 풀어요. 잠금은 [락](../locks/)에서 다뤄요.

### 6. undo 로그: 되돌리기 장부

**undo 로그**(undo log)는 "바꾸기 전 값"을 적어 두는 장부예요. 트랜잭션이 데이터를 바꿀 때마다, 그 변경을 되돌리는 방법이 undo 레코드로 남아요.

쓰임새는 두 가지예요.

1. **롤백**: ROLLBACK하면 undo에 적힌 옛 값으로 되돌려요. → **원자성**
2. **옛 버전 읽기**: 다른 트랜잭션이 아직 커밋 안 된(또는 자기 시작 이후 바뀐) 데이터 대신 변경 전 값을 읽게 해 줘요. 이걸 **MVCC**(Multi-Version Concurrency Control, 여러 버전을 두고 읽기와 쓰기가 서로 덜 막히게 하는 방식)라고 해요. → **격리성**

### 7. redo 로그: 다시 하기 장부

**redo 로그**(redo log)는 "무엇을 바꿨는지"를 적는 디스크 장부예요. 서버가 비정상 종료돼서 데이터 파일에 미처 못 쓴 변경이 있으면, 재시작할 때 **연결을 받기 전에** redo 로그를 보고 자동으로 다시 적용해요. → **지속성**

여기서 중요한 사실이 있어요. **커밋할 때 데이터 파일에 바로 쓰지 않아요.**

1. UPDATE를 하면 메모리(**버퍼 풀**, buffer pool, 디스크 페이지를 캐시해 두는 메모리 영역)의 페이지만 바뀌어요. 디스크에 아직 안 쓴 이런 페이지를 **더티 페이지**(dirty page)라고 해요.
2. COMMIT하면 **redo 로그만 디스크에 확실히 써요**(flush). 그다음 클라이언트에 "완료"를 알려요.
3. 더티 페이지는 나중에 백그라운드에서 데이터 파일로 옮겨요.

왜 이렇게 할까요? 데이터 파일은 여기저기 흩어진 페이지를 고쳐야 해서 느려요. redo 로그는 끝에 이어 쓰기만 하면 돼요. 그래서 "로그 먼저, 데이터는 나중에"로 커밋을 빠르게 하면서도, 죽으면 로그로 복구해요.

| 구분 | undo 로그 | redo 로그 |
|---|---|---|
| 적는 것 | 바꾸기 **전** 값(되돌리는 방법) | 바꾼 내용(다시 하는 방법) |
| 주 용도 | 롤백, MVCC 옛 버전 읽기 | 크래시 후 커밋된 변경 재적용 |
| ACID | 원자성, 격리성 | 지속성 |
| 한 줄로 | 없던 일로 | 했던 일 다시 |

**크래시 복구 순서**는 이래요. 재시작하면 깨진 페이지를 doublewrite에서 복원하고, redo 로그를 마지막 **체크포인트**(checkpoint, "여기까지는 데이터 파일에 반영됨" 표시)부터 다시 적용해요. 그다음 커밋 안 된 트랜잭션은 undo로 되돌려요.

<Aside type="caution" title="흔한 오해: redo는 롤백용?">
반대예요. **redo는 커밋된 걸 다시 하기**(지속성), **undo는 되돌리기와 옛 버전 읽기**(원자성·MVCC)예요. 이름 그대로 re-do(다시 하기), un-do(되돌리기)로 기억하세요.
</Aside>

### 8. doublewrite buffer: 반쯤 쓰인 페이지 대비

더티 페이지를 디스크에 쓰다가 중간에 전원이 나가면, 페이지가 반만 새 값인 **깨진 페이지**(torn page)가 생길 수 있어요. 그래서 InnoDB는 페이지를 실제 위치에 쓰기 **전에** doublewrite 파일에 먼저 한 번 써요. 복구 때 깨진 페이지가 있으면 거기서 온전한 사본을 가져와요.

두 번 쓰지만 I/O가 두 배가 되진 않아요. doublewrite 쪽은 큰 덩어리로 순서대로 쓰고 fsync(디스크에 확실히 쓰라는 OS 명령)를 한 번만 하기 때문이에요. 기본값은 켜짐이에요(`innodb_doublewrite`).

### 9. 커밋을 얼마나 확실히 쓸까: `innodb_flush_log_at_trx_commit`

커밋마다 redo 로그를 디스크에 flush하는 건 안전하지만 비용이 들어요. 이 설정으로 조절해요(기본값 1, 실행 중 변경 가능).

| 값 | 동작 | 크래시 때 |
|---|---|---|
| **1**(기본) | 커밋마다 로그를 쓰고 디스크에 flush | 커밋된 건 안 잃어요. **완전한 ACID에 필요한 값** |
| 2 | 커밋마다 OS 캐시까지 쓰고, flush는 약 1초마다 | flush 안 된 트랜잭션은 잃을 수 있어요 |
| 0 | 약 1초마다 쓰고 flush | flush 안 된 트랜잭션은 잃을 수 있어요 |

- "1초"는 보장값이 아니에요(`innodb_flush_log_at_timeout`, 기본 1초).
- 어느 값이든 **크래시 복구 기능 자체는 동작**해요. 잃을 수 있는 건 "마지막 순간 커밋들"이에요.
- 값 2는 MySQL 프로세스만 죽으면 OS 캐시에 남아 있어 괜찮고, OS가 죽거나 정전이면 약 1초분을 잃을 수 있다고 흔히 설명해요. 다만 공식문서는 이렇게 나눠 말하진 않고 "크래시 시 유실 가능"이라고만 써요.

<Aside type="note" title="둘은 함께 맞춰요">
Real MySQL은 redo 로그를 커밋마다 동기화하지 않는 설정(값 1이 아님)에서 doublewrite만 켜 두는 건 어울리지 않는 조합이라고 지적해요. 지속성은 두 장치를 같이 맞춰야 의미가 있어요.
</Aside>

### 10. 에러가 나면 자동으로 롤백될까?

**아니요, 항상은 아니에요.** InnoDB는 에러 종류에 따라 "문장 하나만" 또는 "트랜잭션 전체"를 롤백해요.

| 에러 | 롤백 범위 |
|---|---|
| **데드락**(deadlock, 두 트랜잭션이 서로의 잠금을 기다리며 멈춤) | 트랜잭션 **전체** → 처음부터 재시도해야 해요 |
| 락 대기 타임아웃 | 기본은 그 **문장만** (`--innodb-rollback-on-timeout`을 켜면 전체) |
| 중복 키(duplicate key), 행이 너무 김 | 그 **문장만** |

그래서 애플리케이션이 에러를 잡아서 **직접 ROLLBACK**해야 해요.

실험(MySQL 9.6)에서 `START TRANSACTION` → id1 잔액 UPDATE → 중복 키 INSERT를 했더니 에러가 났어요. 이 실험에서는 에러 직후 클라이언트가 종료됐고, 다시 보니 id1은 원래 값이었어요. 중복 키 에러는 그 문장만 되돌리고, 앞의 UPDATE는 **연결이 끊기면서** 전체 롤백된 거예요. 연결이 살아 있었다면 UPDATE는 열린 트랜잭션에 그대로 남아 있었을 거예요.

### 11. DDL은 롤백이 안 돼요

**DDL**(CREATE/ALTER/DROP TABLE처럼 테이블 구조를 바꾸는 문장)은 실행 **전에** 열린 트랜잭션을 몰래 커밋해요. 이걸 **암묵적 커밋**(implicit commit)이라고 해요. 대부분 실행 후에도 커밋해요.

실험(MySQL 9.6)에서 `START TRANSACTION` → id2 잔액을 0으로 UPDATE → `CREATE TABLE` → `ROLLBACK`을 했더니 id2는 **0 그대로**였어요. CREATE TABLE이 앞의 UPDATE를 커밋해 버렸기 때문이에요.

### 12. 트랜잭션은 짧게

트랜잭션을 길게 잡으면 여러 가지가 동시에 나빠져요.

- **잠금을 오래 쥐어요.** 같은 행을 건드리려는 다른 요청이 기다려요.
- **DB 커넥션을 오래 쥐어요.** 커넥션은 개수가 정해진 자원이라 다른 요청이 커넥션을 못 얻어요([커넥션 풀](../connection-pool-query/)).
- **undo가 안 지워져요.** 아래에서 자세히 봐요.

특히 메일 발송, 외부 API 호출, 파일 전송 같은 **네트워크 작업을 트랜잭션 안에 두면** 상대 서버가 느려질 때 DB까지 같이 위험해져요. 트랜잭션은 꼭 필요한 DB 작업만 감싸고, 단순 조회나 성격이 다른 작업은 분리해요. 데드락·락 타임아웃은 바쁜 서버에선 정상적으로 일어나는 일이라, 공식문서도 **재시도 로직**을 두고 첫 변경부터 커밋까지를 짧게 하라고 권해요.

**긴 트랜잭션과 History list**

InnoDB는 DELETE한 행이나 옛 버전을 바로 지우지 않아요. 그 undo가 롤백에도, 누군가의 옛 버전 읽기에도 더 이상 필요 없을 때 백그라운드의 **purge**(정리 작업)가 지워요. 아직 정리 못 한, 커밋된 트랜잭션의 undo 목록을 **History list**라고 하고, 그 길이는 `SHOW ENGINE INNODB STATUS`의 `History list length`로 볼 수 있어요. 보통은 수천 이하로 낮아요.

REPEATABLE READ에서는 트랜잭션이 **시작 시점의 데이터**를 계속 보여줘야 해요. 그래서 오래 열린 트랜잭션이 하나라도 있으면, **읽기만 하더라도** 그동안 쌓인 옛 버전을 purge가 못 지워요.

실험(MySQL 9.6, 1만 행 테이블)에서 다른 세션들이 303개 트랜잭션씩 UPDATE·COMMIT을 반복했어요.

| 상황 | History list length |
|---|---|
| 긴 트랜잭션 없음 | 라운드 직후 301 수준, purge가 정리하며 유지 |
| 아무것도 안 하는 트랜잭션을 열어 둔 채 3라운드 | 303 → 606 → 909, 5초 더 지나도 910 (정리 불가) |
| 그 트랜잭션 COMMIT | 직후 910, 5초 후 **0** |

그 사이 열어 둔 트랜잭션은 시작 시점 합계(81300)를 계속 봤고, 실제 현재 합계는 172200이었어요. undo로 옛 버전을 읽고 있다는 증거예요.

History list가 커지면 purge가 밀리고 undo 저장 공간이 커질 수 있어요. 흔한 원인은 IDE에서 autocommit을 끄고 SELECT만 한 뒤 방치한 세션, 동시 쓰기가 많을 때 도는 `mysqldump --single-transaction` 같은 경우예요.

## 면접 질문

<details>
<summary>Q. 트랜잭션이 뭔가요? ACID를 설명해 주세요.</summary>

**답변(30초)** 트랜잭션은 여러 변경을 전부 반영하거나 전부 취소하는 하나의 작업 단위예요. 계좌 이체에서 출금만 되고 입금이 안 되는 부분 반영을 막아요. ACID는 원자성(전부 아니면 전무), 일관성(전후로 제약조건과 규칙 유지), 격리성(동시 트랜잭션끼리 중간 상태를 안 봄), 지속성(커밋된 건 장애 후에도 남음)이에요. InnoDB에선 원자성은 undo 로그, 지속성은 redo 로그가 핵심이에요.

**꼬리질문**
- Q. 일관성은 정확히 뭘 보장하죠? → 보통은 PK·FK·CHECK 같은 제약조건과 업무 규칙이 트랜잭션 전후로 깨지지 않는 걸 말해요. MySQL 문서는 doublewrite와 크래시 복구 같은 크래시 보호 장치를 C로 분류하기도 해요.
- Q. 격리성과 일관성은 어떻게 다르죠? → 일관성은 트랜잭션 하나가 끝났을 때 데이터가 규칙에 맞느냐이고, 격리성은 동시에 도는 트랜잭션끼리 얼마나 서로를 안 보느냐예요. 격리성은 격리 수준으로 정도를 조절해요.
</details>

<details>
<summary>Q. redo 로그와 undo 로그의 차이는?</summary>

**답변(30초)** undo는 되돌리기, redo는 다시 하기예요. undo 로그는 바꾸기 전 값을 담아서 ROLLBACK할 때 원래대로 돌리고, 다른 트랜잭션이 옛 버전을 읽는 MVCC에도 쓰여요. redo 로그는 바꾼 내용을 담아서, 커밋했지만 데이터 파일에 아직 못 쓴 변경을 크래시 후 재시작할 때 다시 적용해요. 그래서 undo는 원자성과 격리성, redo는 지속성을 맡아요.

**꼬리질문**
- Q. 크래시 복구 때 둘은 어떤 순서로 쓰이나요? → redo를 체크포인트부터 다시 적용해 커밋된 변경을 살리고, 커밋 안 된 트랜잭션은 undo로 되돌려요.
- Q. 임시 테이블의 undo도 redo로 기록하나요? → 아니요. 임시 테이블 undo는 크래시 복구에 필요 없어서 redo 로깅을 안 해요.
</details>

<details>
<summary>Q. 커밋하면 데이터 파일에 바로 쓰나요? 그런데 크래시 후에도 데이터가 남는 이유는요?</summary>

**답변(30초)** 바로 쓰지 않아요. 커밋 시점엔 redo 로그만 디스크에 flush하고 완료를 알려요. 데이터 페이지는 메모리에서 바뀐 채로 있다가 나중에 백그라운드에서 써요. 그 사이 서버가 죽어도 재시작할 때 redo 로그를 보고 변경을 다시 적용하니 커밋된 데이터가 남아요. 흩어진 데이터 페이지 대신 순서대로 쓰는 로그만 확실히 쓰니 커밋이 빨라요.

**꼬리질문**
- Q. `innodb_flush_log_at_trx_commit` 0/1/2 차이는요? → 1은 커밋마다 flush해서 완전한 ACID, 2는 커밋마다 OS 캐시까지 쓰고 flush는 약 1초마다, 0은 약 1초마다 쓰고 flush해요. 0과 2는 빠르지만 크래시 때 마지막 커밋들을 잃을 수 있어요.
- Q. doublewrite buffer는 왜 있죠? → 페이지를 쓰다 중간에 죽어 반쯤 쓰인 깨진 페이지를 복구하려고요. 실제 위치 전에 사본을 먼저 써 둬요.
</details>

<details>
<summary>Q. autocommit이 뭔가요? 끄면 어떻게 되나요?</summary>

**답변(30초)** autocommit은 SQL 문장 하나하나를 각자 트랜잭션으로 보고 실행 직후 자동 커밋하는 모드로, MySQL은 연결마다 기본 ON이에요. 여러 문장을 묶으려면 START TRANSACTION과 COMMIT을 써요. 끄면 세션에 항상 트랜잭션이 열려 있어서 직접 COMMIT해야 다른 세션에 보여요. 커밋 없이 연결이 끊기면 마지막 트랜잭션은 롤백돼요.

**꼬리질문**
- Q. 끄고 SELECT만 하고 두면 괜찮나요? → 트랜잭션이 계속 열려 있어서 purge가 옛 버전을 못 지우고 History list가 커져요.
</details>

<details>
<summary>Q. 트랜잭션 중 에러가 나면 자동으로 롤백되나요?</summary>

**답변(30초)** 항상은 아니에요. InnoDB는 데드락이면 트랜잭션 전체를 롤백하지만, 중복 키 에러나 기본 설정의 락 대기 타임아웃은 그 문장만 롤백해요. 앞에서 성공한 변경은 열린 트랜잭션에 그대로 남아요. 그래서 애플리케이션이 에러를 잡아서 직접 ROLLBACK해야 해요.

**꼬리질문**
- Q. DDL도 롤백되나요? → MySQL에서 DDL은 실행 전에 열린 트랜잭션을 암묵적으로 커밋해서, 그 뒤 ROLLBACK은 앞의 DML도 못 되돌려요.
- Q. 스프링에선요? → `@Transactional`이 이 COMMIT/ROLLBACK을 대신 관리해요. [스프링 @Transactional](../../spring/transactional/)에서 다뤄요.
</details>

<details>
<summary>Q. 트랜잭션을 길게 가져가면 어떤 문제가 있나요?</summary>

**답변(30초)** 잠금과 커넥션을 오래 쥐고, undo가 쌓여요. 잠금을 오래 쥐면 같은 행을 쓰려는 요청이 기다리고, 커넥션을 오래 쥐면 풀이 고갈될 수 있어요. 또 REPEATABLE READ에선 열린 트랜잭션이 시작 시점 데이터를 봐야 해서, 읽기만 해도 purge가 옛 버전을 못 지워 History list가 커져요. 그래서 트랜잭션은 꼭 필요한 DB 작업만 짧게 감싸고, 외부 API 호출 같은 네트워크 작업은 밖으로 빼요.

**꼬리질문**
- Q. 긴 트랜잭션은 어떻게 찾아요? → `information_schema.innodb_trx`에서 `trx_started`가 오래된 트랜잭션을 찾아요.
</details>

## 서술형 연습

<details>
<summary>상황: 회원가입 API가 트랜잭션 안에서 회원을 저장하고 환영 메일 API를 호출합니다. 메일 서버가 느려진 날, 회원가입뿐 아니라 다른 API까지 전부 타임아웃이 났습니다.</summary>

**상황 파악**
메일 서버 응답을 기다리는 동안 트랜잭션이 안 끝나요. 그 시간 내내 DB 커넥션과 잠금을 쥐고 있어요. 가입 요청이 몰리면 커넥션 풀이 바닥나고, 커넥션이 필요한 다른 API까지 줄을 서다 타임아웃이 나요.

**원인 후보**
1. 트랜잭션 범위 안에 외부 네트워크 호출(메일 API)이 들어 있어요.
2. 외부 호출에 짧은 타임아웃이 없어 오래 붙잡혀요.
3. 커넥션 풀 크기 대비 트랜잭션 보유 시간이 길어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 메일 호출을 커밋 **후**로 옮김(커밋 후 이벤트 등) | 트랜잭션이 DB 작업만 감싸 짧아짐. 메일이 느려도 DB는 무사 | 커밋 후 메일이 실패하면 가입은 됐는데 메일이 안 감. 재발송 처리가 필요 |
| B. 가입 트랜잭션에서 "보낼 메일"을 테이블에 같이 저장하고, 별도 작업이 읽어서 발송(아웃박스 방식) | 가입과 "메일 보낼 예정" 기록이 한 트랜잭션이라 유실이 없음 | 테이블과 발송 작업을 따로 만들어야 하고, 메일이 조금 늦게 감 |
| C. 메일 호출 타임아웃만 짧게 | 수정이 가장 적음 | 트랜잭션 안에 외부 호출이 남아 근본 해결이 아님 |

**내가 고를 방법**
A를 기본으로 해요. 환영 메일은 가입의 본질이 아니라서, 가입 커밋과 묶을 이유가 없어요. 메일 유실이 문제 되는 서비스라면 B로 가요. C는 어느 쪽이든 같이 적용하는 보조책이에요. 적용 후 트랜잭션 보유 시간과 커넥션 대기 지표가 줄었는지 확인해요.

**채점 포인트**: 트랜잭션 안 네트워크 호출의 위험, 커넥션·잠금 보유 시간, 커넥션 풀 고갈, 트랜잭션 범위 최소화, 커밋 후 처리와 실패 시 재처리, 아웃박스 같은 대안, 적용 후 검증.
</details>

<details>
<summary>상황: 계좌 이체 코드에서 출금 UPDATE 후 입금 INSERT가 중복 키 에러로 실패했습니다. 개발자는 "에러 났으니 DB가 알아서 롤백했겠지" 하고 예외만 로그로 남긴 뒤 커넥션을 풀에 돌려줬습니다.</summary>

**상황 파악**
중복 키 에러는 InnoDB에서 **그 문장만** 롤백해요. 앞의 출금 UPDATE는 열린 트랜잭션 안에 그대로 있어요. 이 커넥션이 풀로 돌아가면 출금 변경과 그 행의 잠금이 남은 채로 다른 요청에 재사용될 수 있어요.

**원인 후보**
1. "에러 = 자동 전체 롤백"이라는 오해로 catch에서 ROLLBACK을 안 했어요.
2. 트랜잭션 경계를 코드가 직접 관리해서 빠뜨리기 쉬웠어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. catch에서 반드시 ROLLBACK (finally에서 정리) | 원인을 정확히 고침, 구조가 단순 | 모든 코드 경로에서 사람이 챙겨야 함 |
| B. 프레임워크 트랜잭션 관리(스프링 `@Transactional`)에 맡김 | 예외가 나면 롤백이 자동, 빠뜨릴 일이 줄어듦 | 어떤 예외에서 롤백하는지 규칙을 알아야 함 |

**내가 고를 방법**
B를 기본으로 쓰고, 롤백 규칙을 팀이 이해하게 해요. 직접 관리하는 코드가 남아 있다면 A 패턴으로 바꿔요. 데드락은 트랜잭션 전체가 롤백되니 처음부터 다시 시도하는 재시도 로직도 함께 둬요.

**채점 포인트**: 중복 키는 문장 단위 롤백, 데드락은 전체 롤백, 앱의 명시적 ROLLBACK, 커넥션 재사용 시 열린 트랜잭션 위험, 프레임워크 트랜잭션 관리, 재시도.
</details>

<details>
<summary>상황: 쓰기 처리량을 올리려고 `innodb_flush_log_at_trx_commit`을 1에서 2로 바꾸자는 제안이 나왔습니다.</summary>

**상황 파악**
값 2는 커밋마다 디스크 flush를 하지 않아 빨라지지만, 크래시 때 마지막 순간 커밋들을 잃을 수 있어요. "커밋 완료"라고 응답한 데이터가 사라질 수 있다는 뜻이라 지속성(D)을 일부 내주는 결정이에요.

**원인 후보(왜 느린가)**
1. 커밋마다 디스크 flush 비용이 병목이에요.
2. 아주 작은 트랜잭션을 너무 자주 커밋하고 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 값 2로 변경 | 설정 하나로 처리량 향상 | 크래시 시 약 1초분 커밋 유실 가능(1초는 보장값도 아님) |
| B. 값 1 유지, 작은 쓰기를 적당히 묶어 커밋 | 지속성 유지 | 코드 수정이 필요, 묶은 만큼 실패 시 다시 할 양이 커짐 |

**내가 고를 방법**
결제·원장처럼 커밋된 돈 기록을 잃으면 안 되는 DB는 1을 유지하고 B로 풀어요. 잃어도 다시 만들 수 있는 로그성 데이터 DB라면 A를 허용할 수 있어요. 데이터의 성격을 먼저 정하고 고르는 게 핵심이에요.

**채점 포인트**: 0/1/2 동작 차이, 값 1이 완전한 ACID, 유실 가능 범위, 데이터 성격별 선택, 처리량과 지속성의 트레이드오프.
</details>

## 필기 포인트

- ACID = **A**tomicity(원자성), **C**onsistency(일관성), **I**solation(격리성), **D**urability(지속성).
- C의 교과서 설명은 "제약조건·규칙 유지". MySQL 문서는 doublewrite·크래시 복구를 C로 분류해요.
- undo = 되돌리기(원자성, MVCC). redo = 다시 하기(지속성, 크래시 복구). 헷갈리는 함정 단골이에요.
- 커밋 시점엔 **redo 로그만** flush하고 데이터 페이지는 나중에 써요.
- MySQL autocommit 기본 **ON**. 끄면 항상 트랜잭션이 열려 있고, 커밋 없이 종료하면 롤백.
- DDL은 **암묵적 커밋** → ROLLBACK으로 못 되돌려요.
- 에러 시 롤백 범위: 데드락 = 전체, 중복 키·락 타임아웃(기본) = 문장만.
- `innodb_flush_log_at_trx_commit` 기본 **1** = 완전한 ACID.
