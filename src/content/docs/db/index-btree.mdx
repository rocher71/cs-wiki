:::tip[한 줄 요약]
**인덱스**는 컬럼 값을 **정렬해서 따로 저장해 둔 목차**예요. MySQL InnoDB는 이걸 **B+트리 계열 구조**로 저장해서, 수억 건 테이블에서도 페이지를 3~4번만 읽고 원하는 행을 찾아요. 대신 INSERT·UPDATE·DELETE가 느려지고 저장 공간을 더 쓰는 **트레이드오프**(하나를 얻는 대신 다른 하나를 내주는 관계)가 있어요.
:::

:::note[처음이라면 여기까지]
① **인덱스**는 컬럼 값을 정렬해 따로 저장한 찾아보기예요. 덕분에 처음부터 다 훑지 않고 원하는 행으로 바로 가요.

② 여러 층으로 된 나무(트리) 모양이라, 행이 아주 많아도 몇 번만 내려가면 찾아요.

③ 대신 데이터를 넣고 고칠 때마다 인덱스도 같이 고쳐야 해서 쓰기가 느려지고 공간을 더 써요. 그래서 많이 만든다고 좋은 게 아니에요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

<Aside type="note" title="이 페이지의 기준">
설명은 MySQL 8.0 기준 책과 MySQL 8.4 공식문서를 바탕으로 했어요. 직접 돌린 실험은 **MySQL 9.6.0**(InnoDB, 30만 행 회원 테이블, 노트북 1회 실행)이라 숫자는 "경향"으로만 봐 주세요. 8.0과 기본값이 다른 설정은 따로 표시했어요.
</Aside>

## 쉽게 이해하기

두꺼운 전공책에서 "교착 상태"가 나오는 쪽을 찾는다고 해 봐요. 첫 장부터 한 장씩 넘기면 오래 걸려요. 그래서 책 뒤에는 **찾아보기(색인)** 가 있어요. 단어가 가나다순으로 정렬돼 있어서 금방 찾고, 옆에 적힌 쪽 번호로 본문에 바로 가요.

DB도 똑같아요. **테이블**(엑셀 시트처럼 행과 열로 된 데이터 묶음)에서 이메일이 `a@b.com`인 회원을 찾을 때, 찾아보기가 없으면 첫 행부터 끝 행까지 다 봐야 해요. 이걸 **풀 테이블 스캔**(full table scan)이라고 해요. 찾아보기 역할을 하는 게 **인덱스**(index)예요.

찾아보기에도 대가가 있어요. 책에 새 내용을 넣으면 찾아보기도 가나다 순서에 맞게 끼워 넣어야 해요. 그래서 인덱스가 많을수록 **읽기는 빨라지고 쓰기는 느려져요.**

단, 실제 인덱스는 한 줄짜리 목록이 아니라 **여러 층으로 된 나무 모양**(트리)이에요. 목차의 목차를 따라 내려가는 구조라서, 행이 수억 개여도 몇 번만 내려가면 돼요.

## 제대로 알기

### 1. 인덱스는 왜 빠른가

인덱스는 "**컬럼 값 → 그 행이 있는 곳**" 쌍을 **컬럼 값 순서로 정렬해서** 테이블과 따로 저장한 자료구조예요. 정렬돼 있으니 처음부터 훑지 않고 원하는 위치로 바로 찾아갈 수 있어요.

비유하면 이래요.

| 구분 | 비슷한 것 | 특징 |
|---|---|---|
| 테이블 데이터 | 넣은 순서대로 쌓이는 리스트 | 쓰기 쉬움, 찾기 느림 |
| 인덱스 | 항상 정렬 상태를 지키는 리스트 | 찾기 빠름, 쓰기 때마다 정렬 위치 유지 |

실험(MySQL 9.6, 30만 행)에서 `WHERE email = 'user123456@ex.com'`은 인덱스가 없을 때 30만 행을 다 읽고 1건을 돌려주며 약 46ms가 걸렸어요. email 인덱스를 만든 뒤에는 1행만 읽고 약 0.007ms였어요.

인덱스는 역할에 따라 이렇게 불러요.

- **프라이머리 키**(Primary Key, PK): 행을 하나로 딱 집어내는 값. NULL(값 없음)도, 중복도 안 돼요.
- **세컨더리 인덱스**(secondary index): PK가 아닌 나머지 인덱스 전부.
- 중복을 허용하느냐에 따라 **유니크**(unique) / **논유니크**로도 나눠요.

### 2. 페이지: DB가 디스크를 읽는 단위

DB는 디스크를 한 줄씩 읽지 않고 **페이지**(page, 일정 크기의 데이터 덩어리) 단위로 읽고 써요. 메모리에 캐시해 두는 단위도 페이지예요. InnoDB의 페이지 기본 크기는 **16KB**예요(`innodb_page_size`, 4KB~64KB 중 DB를 처음 만들 때 정함). 실험 환경에서도 `@@innodb_page_size = 16384`였어요.

DB 성능은 결국 **디스크를 몇 번 읽느냐**에 달려 있어요. 디스크를 읽고 쓰는 일을 **I/O**(Input/Output, 입출력)라고 하고, 읽는 방식은 두 가지예요.

- **랜덤 I/O**: 원하는 위치를 찾아가서 읽기. 인덱스 탐색이 주로 이쪽이에요.
- **순차 I/O**: 붙어 있는 위치를 쭉 읽기. 풀 테이블 스캔이 주로 이쪽이에요.

SSD가 좋아졌어도 랜덤 I/O가 순차 I/O보다 비싸요. 이 사실이 뒤에 나올 "인덱스가 있어도 안 쓰는 경우"의 이유예요.

### 3. B-트리와 B+트리 구조

MySQL의 PK, UNIQUE, 일반 INDEX는 대부분 **B-트리**(B-tree) 구조로 저장돼요.

- **B는 Binary(이진)가 아니라 Balanced(균형)** 로 이해하면 돼요. 이진 트리는 자식이 최대 2개지만, B-트리 노드 하나는 자식을 **수백 개** 가질 수 있어요.
- 균형이라는 건 루트에서 어느 리프까지 가든 **깊이가 같다**는 뜻이에요.

모양은 3층이에요.

| 층 | 들어 있는 것 |
|---|---|
| **루트 노드**(root, 맨 위 1개) | 키 + 자식 페이지 번호 |
| **브랜치 노드**(branch, 중간) | 키 + 자식 페이지 번호 |
| **리프 노드**(leaf, 맨 아래) | 실제 레코드(=행) 또는 레코드를 찾아갈 값 |

노드 하나가 페이지 하나예요. 그리고 **리프끼리 옆으로 연결**돼 있어서, 범위 조회 때는 리프를 따라 옆으로 읽어 나가요.

**B-트리 vs B+트리** (교과서 정의, 면접용)

| 구분 | B-트리 | B+트리 |
|---|---|---|
| 데이터 위치 | 모든 노드에 있을 수 있음 | **리프에만** |
| 내부 노드 | 키 + 데이터 | **키만** → 한 페이지에 키가 더 많이 들어가 트리가 낮아짐 |
| 범위 조회 | 트리를 위아래로 오가며 순회 | **연결된 리프만 옆으로** 따라가면 됨 |

<Aside type="caution" title="'B+트리'는 업계 통칭이에요">
MySQL 공식문서는 InnoDB 인덱스를 **"B-tree"** 라고 부르고, "고전 B-tree에 없는 개선이 들어간 **변형**"이라고만 설명해요. 'B+tree'라는 이름은 쓰지 않아요. 면접에서 "InnoDB 인덱스는 B+트리 계열이에요"라고 말해도 되지만, "공식문서 표현은 B-tree의 변형"이라는 점을 알아 두면 안전해요. 리프가 서로 연결돼 있다는 점은 책 그림으로 확인했고, 그 연결 방식(예: 양방향인지)을 못 박은 공식문서 문장은 찾지 못했어요.
</Aside>

예외도 있어요. 공간(지도 좌표) 인덱스는 **R-트리**, MEMORY 엔진은 **해시 인덱스**, InnoDB의 FULLTEXT(전문 검색) 인덱스는 **역색인**(inverted list)을 써요.

### 심화: 4. 왜 B+트리인가: 낮은 높이

한 페이지에 들어가는 자식 수를 **팬아웃**(fan-out)이라고 해요. 팬아웃은 **키 크기**로 정해져요.

| 키 크기 | 한 페이지(16KB)에 들어가는 키 | 깊이 3이면 담는 키 수 |
|---|---|---|
| 16바이트 (+자식 주소 12바이트) | 약 585개 | 585³ ≈ **약 2억 개** |
| 32바이트 (+자식 주소 12바이트) | 약 372개 | 372³ ≈ 약 5천만 개 |

그래서 수억 건 테이블도 **페이지 3~4번**만 읽으면 원하는 키에 닿아요. 대용량이어도 깊이가 5 이상 되는 일은 드물어요.

이진 탐색 트리와 비교하면 차이가 커요. 자식이 2개뿐이면 2억 건을 담으려면 깊이가 약 28(2²⁸ ≈ 2.7억)이 돼요. 층마다 페이지를 읽는다면 디스크 읽기가 28번이에요. B+트리는 한 번 읽을 때 수백 갈래 중 하나를 고르니 3~4번이면 끝나요.

**키는 작을수록 좋아요.** 키가 크면 한 페이지에 들어가는 키가 줄어 트리가 깊어지고, 인덱스 전체가 커져서 메모리에 덜 올라가요.

### 심화: 5. InnoDB에서 행을 찾아가는 길

InnoDB는 **테이블 자체가 PK 순서로 정렬된 B+트리**예요. 이걸 **클러스터드 인덱스**(clustered index)라고 해요. PK 인덱스의 리프에 행 데이터가 통째로 들어 있어요.

세컨더리 인덱스의 리프에는 행의 물리 주소가 아니라 **PK 값**이 들어 있어요. 그래서 세컨더리 인덱스로 찾으면 두 번 내려가요.

1. email 인덱스를 타고 내려가 **PK 값**을 얻어요.
2. 그 PK로 클러스터드 인덱스를 다시 타고 내려가 **행**을 읽어요.

(MyISAM 엔진은 리프에 레코드 주소를 바로 갖고 있어요.) 클러스터드 인덱스와 "두 번 안 내려가는" **커버링 인덱스**는 [클러스터드·커버링 인덱스](../clustered-covering/)에서 자세히 다뤄요.

### 6. 인덱스의 비용: 쓰기와 공간

**쓰기가 느려져요.**

- **추가**: 정렬 위치를 찾아 리프에 끼워 넣어요. 리프가 꽉 차면 페이지를 둘로 쪼개는 **페이지 분할**(page split)이 일어나고, 위층 노드까지 영향이 갈 수 있어요.
- **삭제**: 리프에 "삭제됨" 표시만 해서 비교적 간단해요.
- **변경**: 키 값은 제자리에서 못 바꿔요. 정렬 위치가 바뀌니까 **삭제 후 새로 추가**해요.
- 책 저자의 경험치로는, 행 추가 비용을 1이라 하면 인덱스 하나당 대략 1.5가 더 들어요. 비용 대부분은 CPU가 아니라 **디스크에서 인덱스 페이지를 읽고 쓰는 시간**이에요.

실험(MySQL 9.6)에서 30만 행을 한 번에 넣는 데 세컨더리 인덱스가 0개면 0.62초, 3개면 1.64초가 걸렸어요(1회 실행이라 경향으로만 봐 주세요).

**공간도 먹어요.** 같은 실험에서 PK가 17.5MB였고, 세컨더리 인덱스 3개가 약 28.6MB를 더 썼어요(email 17.6MB, created_at 5.5MB, gender 5.5MB). email 인덱스가 PK만큼 큰 건, 리프에 email 값과 PK 값이 같이 들어가기 때문이에요.

**쓰기 순서도 공간에 영향을 줘요.** InnoDB는 페이지의 1/16을 나중 수정용으로 비워 둬요. 키가 순서대로 들어오면 페이지가 약 15/16까지 차지만, **무작위 순서**로 들어오면 분할이 잦아 1/2~15/16만 차요. PK를 랜덤 UUID로 쓸 때 테이블이 커지는 이유예요.

<Aside type="note" title="버전에 따라 다른 기본값">
InnoDB는 세컨더리 인덱스 변경을 **체인지 버퍼**(change buffer)에 모았다가 나중에 반영할 수 있어요(PK·유니크 인덱스는 중복 검사 때문에 바로 반영). 이 기능을 켜는 `innodb_change_buffering` 기본값이 **8.0은 `all`, 8.4부터는 `none`** 으로 바뀌었어요.
</Aside>

### 7. 인덱스를 쓸 수 있는 조건

B-트리 인덱스는 이런 조건에 쓸 수 있어요.

- `=`, `>`, `>=`, `<`, `<=`, `BETWEEN`, `IS NULL`
- **앞부분이 정해진** `LIKE 'abc%'`

못 쓰는 대표 경우예요.

- `LIKE '%abc'`: 앞이 정해지지 않으면 정렬된 순서에서 시작점을 못 잡아요.
- **컬럼에 함수·연산을 씌운 비교**: `UPPER(email) = '...'`처럼 바꾼 값은 인덱스에 저장돼 있지 않아요.

실험(MySQL 9.6)에서도 `LIKE 'user12345%'`는 인덱스 범위 스캔, `LIKE '%12345@ex.com'`과 `UPPER(email) = ...`는 풀 테이블 스캔이었어요. 여러 컬럼을 묶은 인덱스와 "못 타는 경우" 전체는 [복합 인덱스](../composite-index/)에서 다뤄요.

<Aside type="caution" title="UPDATE·DELETE도 인덱스를 써요">
UPDATE·DELETE도 바꿀 행을 찾으려고 먼저 인덱스를 검색해요. 그리고 InnoDB는 **검색에 쓴 인덱스 레코드에 잠금**을 걸어요. 조건 컬럼에 쓸 인덱스가 없으면 훑은 행을 잔뜩 잠그고, 최악엔 테이블 전체 행이 잠겨요. 자세한 건 [락](../locks/)에서 다뤄요.
</Aside>

### 8. 카디널리티: 어떤 컬럼에 인덱스를 거나

**카디널리티**(cardinality, 기수성)는 컬럼에 들어 있는 **서로 다른 값의 개수**예요. **선택도**(selectivity)와 거의 같은 뜻으로 써요. 값 종류가 많을수록(중복이 적을수록) 인덱스 한 번에 걸러지는 행이 적어서 효율이 좋아요.

예를 들어 1만 행에서 `country = 'KOREA' AND city = 'SEOUL'`(실제 1건)을 country 인덱스로 찾는다고 해 봐요.

| country 값 종류 | 인덱스로 읽는 행 | 버리는 행 |
|---|---|---|
| 10개 | 약 1,000건 | 999건 |
| 1,000개 | 약 10건 | 9건 |

결과는 같은데 카디널리티가 높은 쪽이 훨씬 덜 읽어요. 성별처럼 값이 두세 개뿐인 컬럼은 단독 검색용으로는 비효율적이에요. 다만 정렬·그룹핑이나 복합 인덱스의 일부로는 쓸모가 있을 수 있어요.

### 9. 인덱스가 있어도 안 쓰는 경우

인덱스로 행 1건을 읽는 건 테이블을 직접 1건 읽는 것보다 **4~5배 비싸다**고 옵티마이저(쿼리 실행 방법을 고르는 MySQL 내부 부품)는 추정해요. 인덱스 탐색에 랜덤 I/O까지 더해지니까요. 그래서 읽을 행이 전체의 **약 20~25%를 넘으면** 인덱스를 버리고 테이블을 쭉 읽는 게 낫다고 판단해요. 이 기준은 비용 설정에 따라 달라져요.

실험(MySQL 9.6, 30만 행, `created_at` 인덱스) 결과예요.

| 조건 | 해당 행 | 옵티마이저 선택 |
|---|---|---|
| `created_at < '2024-01-02'` | 1,439행 (약 0.5%) | 인덱스 범위 스캔 (`type=range`) |
| `created_at < '2024-03-01'` | 86,399행 (약 29%) | 풀 스캔 (`type=ALL`) |

**카디널리티는 추정치예요.** InnoDB는 일부 페이지만 표본으로 읽어 통계를 만들어요(`innodb_stats_persistent_sample_pages` 기본 20). 실험에서 M/F가 반반인 `gender` 인덱스의 카디널리티가 `1`로 나왔고, 옵티마이저는 절반을 읽는 `gender = 'M'`에 그 인덱스를 골랐어요. 실제로는 인덱스 쪽 74ms, 인덱스를 무시하게 한 풀 스캔 39ms로 **인덱스가 약 2배 느렸어요.** 통계가 틀리면 옵티마이저도 나쁜 선택을 할 수 있다는 예예요. 실행 계획을 읽는 법은 [EXPLAIN](../explain/)에서 다뤄요.

### 심화: 10. 해시 인덱스와 비교

**해시 인덱스**는 값을 **해시 함수**(입력을 정해진 크기의 숫자로 바꾸는 함수)로 바꿔 저장해요. 등호 비교는 아주 빠르지만 할 수 있는 게 적어요.

| 구분 | B-트리 인덱스 | 해시 인덱스 |
|---|---|---|
| `=` 조회 | 가능 | 가능, 매우 빠름 |
| 범위(`<`, `BETWEEN`) | 가능 | 불가 |
| `ORDER BY` 최적화 | 가능 | 불가 |
| `LIKE 'abc%'` | 가능 | 불가 |
| 키 일부(왼쪽부터)로 검색 | 가능 | 키 전체로만 |
| 엔진 | InnoDB·MyISAM은 BTREE만 | MEMORY 엔진(기본값) |

InnoDB에서 `INDEX ... USING HASH`라고 써도 지원하지 않는 타입이라 **BTREE로 만들어져요.** 실험(MySQL 9.6)에서도 `SHOW INDEX`의 Index_type이 BTREE로 나왔어요. MEMORY 테이블의 해시 인덱스는 `k = 500`에는 쓰였지만 `BETWEEN`은 풀 스캔, `ORDER BY k`는 따로 정렬(`Using filesort`)했어요.

<Aside type="note" title="어댑티브 해시 인덱스 기본값 주의">
**어댑티브 해시 인덱스**(Adaptive Hash Index, AHI)는 자주 조회되는 인덱스 페이지에 InnoDB가 메모리에 알아서 해시 인덱스를 만들어 등호 조회를 빠르게 하는 기능이에요. 사용자가 만드는 인덱스가 아니에요. 기본값이 **8.0은 ON, 8.4부터는 OFF**예요. 실험한 9.6에서도 `@@innodb_adaptive_hash_index = 0`이었어요. 오래된 글은 ON 기준이에요.
</Aside>

## 면접 질문

<details>
<summary>Q. 인덱스가 무엇이고 왜 조회가 빨라지나요?</summary>

**답변(30초)** 인덱스는 컬럼 값과 그 행의 위치를 값 순서로 정렬해 따로 저장한 자료구조예요. 책 뒤 찾아보기처럼 정렬돼 있어서, 테이블 전체를 훑지 않고 원하는 위치로 바로 찾아가요. InnoDB는 이걸 B+트리 계열 구조로 저장하는데, 노드 하나에 자식이 수백 개라 트리가 낮아요. 그래서 수억 건이어도 페이지 3~4번만 읽으면 돼요.

**꼬리질문**
- Q. 인덱스가 없으면 어떻게 찾나요? → 첫 행부터 끝 행까지 다 읽는 풀 테이블 스캔을 해요. 테이블이 클수록 느려져요.
- Q. 수억 건에서도 빠른 이유를 숫자로 말해 보세요. → 16KB 페이지에 키가 수백 개 들어가서, 깊이 3이면 약 585³ ≈ 2억 개 키를 담아요. 그래서 3~4번 읽으면 끝나요.
</details>

<details>
<summary>Q. 인덱스는 많이 만들수록 좋은가요?</summary>

**답변(30초)** 아니에요. 인덱스는 읽기 속도를 얻는 대신 쓰기 성능과 저장 공간을 내주는 트레이드오프예요. INSERT·UPDATE·DELETE마다 모든 인덱스의 정렬 위치를 맞춰야 하고, 리프가 꽉 차면 페이지 분할도 일어나요. 인덱스마다 디스크와 메모리도 따로 차지해요. 그래서 자주 쓰는 조회 조건 위주로, 카디널리티가 높은 컬럼에 골라서 만들어요.

**꼬리질문**
- Q. 키 값을 바꾸면 인덱스에선 무슨 일이 일어나요? → 제자리 수정이 안 돼서, 기존 키를 지우고 새 정렬 위치에 다시 넣어요.
- Q. 인덱스 키 크기는 왜 중요하죠? → 키가 크면 한 페이지에 들어가는 키가 줄어 트리가 깊어지고, 인덱스가 커져 메모리에 덜 올라가요.
</details>

<details>
<summary>Q. 인덱스가 있는데도 안 쓰이는 경우는요?</summary>

**답변(30초)** 크게 세 가지예요. 첫째, 컬럼에 함수를 씌우거나 `LIKE '%abc'`처럼 앞이 정해지지 않으면 인덱스에서 시작점을 못 잡아요. 둘째, 읽을 행이 전체의 약 20~25%를 넘으면 옵티마이저가 풀 스캔이 더 싸다고 판단해요. 인덱스 경유는 랜덤 I/O라 1건당 비용이 더 크기 때문이에요. 셋째, 통계가 추정치라서 옵티마이저가 잘못 고르기도 해요.

**꼬리질문**
- Q. 성별 컬럼에 인덱스를 걸면요? → 값이 두 종류라 카디널리티가 낮아 단독 검색엔 비효율적이에요. 실험에서도 성별 인덱스를 탄 쿼리가 풀 스캔보다 약 2배 느렸어요.
- Q. 그럼 FORCE INDEX로 강제하면 되나요? → 많은 행을 읽는 경우엔 강제해도 이득이 없어요. 먼저 조건과 인덱스 설계, 통계를 봐요.
</details>

<details>
<summary>Q. B-트리와 B+트리의 차이, DB가 B+트리를 쓰는 이유는요?</summary>

**답변(30초)** B-트리는 모든 노드에 데이터가 있을 수 있고, B+트리는 데이터를 리프에만 두고 리프끼리 연결해요. 내부 노드에 키만 있으니 한 페이지에 키가 더 많이 들어가 트리가 낮아지고, 디스크 읽기 횟수가 줄어요. 범위 조회는 시작 리프를 찾은 뒤 옆 리프로만 따라가면 돼요. 참고로 MySQL 공식문서는 이 구조를 "B-tree의 변형"이라고 부르고, B+트리는 업계에서 쓰는 이름이에요.

**꼬리질문**
- Q. B-트리의 B는 무슨 뜻이에요? → Binary가 아니라 Balanced로 이해하면 돼요. 어느 리프든 깊이가 같고, 노드 하나의 자식이 수백 개예요.
- Q. 이진 탐색 트리는 왜 안 쓰나요? → 자식이 2개라 트리가 너무 깊어요. 층마다 디스크를 읽으면 2억 건에 약 28번이 필요해요.
</details>

<details>
<summary>Q. 해시 인덱스와 B-트리 인덱스를 비교해 주세요.</summary>

**답변(30초)** 해시 인덱스는 등호 조회가 매우 빠르지만 범위 검색, 정렬, `LIKE 'abc%'` 같은 앞부분 일치를 못 해요. 정렬된 순서가 없기 때문이에요. B-트리는 등호와 범위, 정렬을 다 지원해서 범용으로 써요. MySQL에선 MEMORY 엔진이 해시를 지원하고, InnoDB는 사용자가 해시 인덱스를 만들 수 없어 `USING HASH`라고 써도 BTREE가 돼요.

**꼬리질문**
- Q. 어댑티브 해시 인덱스는요? → InnoDB가 자주 쓰는 페이지에 메모리 해시를 알아서 만드는 기능이에요. 8.0은 기본 ON, 8.4부터 기본 OFF예요.
</details>

## 서술형 연습

<details>
<summary>상황: 회원 수가 수십만에서 수천만으로 늘면서, 로그인 때 쓰는 `WHERE email = ?` 조회가 수백 ms로 느려졌습니다.</summary>

**상황 파악**
데이터가 늘수록 비례해서 느려졌다면 행을 전부 훑고 있을 가능성이 커요. 로그인은 호출이 많은 경로라 개선 효과가 커요. 먼저 실행 계획([EXPLAIN](../explain/))으로 확인해요.

**원인 후보**
1. email 컬럼에 인덱스가 없어 풀 테이블 스캔(`type=ALL`)을 하고 있어요.
2. 인덱스는 있지만 `LOWER(email) = ?`처럼 컬럼에 함수를 씌워서 못 타고 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. email에 UNIQUE 인덱스 | 조회가 수 페이지 읽기로 끝남. 중복 가입도 DB가 막아 줌 | 가입(INSERT)마다 인덱스 갱신 비용, 디스크 공간 증가. email이 길면 인덱스도 커짐 |
| B. 일반(논유니크) 인덱스 | 기존 데이터에 중복이 있어도 바로 만들 수 있음 | 중복 방지는 앱 코드에 맡겨야 함 |
| C. 쿼리에서 함수 제거(저장할 때 소문자로 정규화) | 인덱스를 그대로 탈 수 있음 | 기존 데이터 정리와 저장 로직 수정이 필요 |

**내가 고를 방법**
원인이 1이면 A를 골라요. email은 회원마다 달라 카디널리티가 높고, 로그인은 읽기가 압도적으로 많아서 쓰기 비용을 감수할 만해요. 원인이 2면 C로 쿼리를 고쳐 인덱스를 타게 해요. 적용 후 실행 계획이 `ALL`에서 인덱스 조회(`ref` 등)로 바뀌었는지, 응답 시간이 줄었는지 확인해요.

**채점 포인트**: 실행 계획으로 풀 스캔 확인, 카디널리티가 높은 컬럼, 함수 적용 시 인덱스 미사용, 인덱스의 쓰기·공간 비용, UNIQUE의 무결성 이점, 적용 후 검증.
</details>

<details>
<summary>상황: `status`(값의 90%가 'ACTIVE')에 인덱스를 걸었는데 `WHERE status = 'ACTIVE'` 조회가 빨라지지 않았고, 오히려 주문 INSERT가 느려졌습니다.</summary>

**상황 파악**
인덱스가 조회를 못 돕고 쓰기 비용만 늘린 상황이에요. 값 종류가 적고 한 값이 90%를 차지하는 컬럼이라는 게 핵심이에요.

**원인 후보**
1. **선택도가 낮음**: 90%를 읽는 조건은 인덱스를 경유하면 랜덤 I/O가 많아져요. 옵티마이저가 풀 스캔을 고르거나, 인덱스를 골라도 더 느릴 수 있어요.
2. **통계가 추정치**: 옵티마이저가 인덱스를 잘못 골랐을 수 있어요.
3. 인덱스가 하나 늘어 INSERT마다 갱신할 B+트리가 늘었어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. status 단독 인덱스 삭제 | 쓰기 비용과 공간이 돌아옴 | 드문 값(예: 'CANCELED')을 찾는 조회는 느려질 수 있음 |
| B. 자주 함께 쓰는 조건과 묶은 [복합 인덱스](../composite-index/)로 교체 | 실제 걸러내는 조건이 있으면 효과가 큼 | 컬럼 순서 설계가 필요, 인덱스가 커짐 |
| C. `ANALYZE TABLE`로 통계 갱신 후 실행 계획 재확인 | 잘못된 선택이 통계 때문이면 바로 해결 | 선택도 자체가 낮은 문제는 그대로 |

**내가 고를 방법**
먼저 C로 통계 문제인지 확인하고, 그래도 이득이 없으면 A로 단독 인덱스를 지워요. 'ACTIVE' 목록을 날짜순으로 보는 화면처럼 다른 조건이 같이 붙는다면 B로 바꿔요. 인덱스는 "만들면 끝"이 아니라 비용이 계속 드는 것이라, 효과를 측정해서 남길지 정해요.

**채점 포인트**: 카디널리티·선택도, 약 20~25% 이상 읽으면 풀 스캔이 유리, 랜덤 I/O vs 순차 I/O, 통계는 추정치, 인덱스의 쓰기 비용, 복합 인덱스 대안, 실행 계획으로 검증.
</details>

## 필기 포인트

- B-트리의 B = **Balanced**(균형). Binary 아님. 노드 하나의 자식이 수백 개.
- B+트리: 데이터는 **리프에만**, 리프끼리 연결 → 범위 조회 유리, 트리 높이 낮음.
- InnoDB 페이지 기본 **16KB**. 노드 1개 = 페이지 1개.
- B-트리 인덱스 사용 가능: `=`, 범위 비교, `BETWEEN`, `IS NULL`, `LIKE 'abc%'`. 불가: `LIKE '%abc'`, 컬럼에 함수 적용.
- 해시 인덱스: 등호만. 범위·정렬·앞부분 일치 불가. InnoDB는 `USING HASH`여도 BTREE.
- 카디널리티 = 서로 다른 값의 개수. 높을수록 인덱스 효율 좋음.
- 키 변경 = 삭제 + 추가. 리프가 꽉 차면 페이지 분할.
- 버전 차이: AHI 기본값 8.0 ON → 8.4 OFF, `innodb_change_buffering` 8.0 `all` → 8.4 `none`.
