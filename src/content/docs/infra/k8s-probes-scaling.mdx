:::tip[한 줄 요약]
**liveness**는 실패하면 컨테이너를 **재시작**하고, **readiness**는 재시작 없이 **트래픽만 끊고**, **startup**은 앱이 다 뜰 때까지 나머지 둘을 **미뤄요**. 종료는 엔드포인트 제거와 SIGTERM이 **동시에** 일어나서 preStop sleep으로 틈을 메우고, **HPA**는 request 대비 사용률로 Pod 수를 계산해요.
:::

<Aside type="note" title="이 페이지의 기준">
kubernetes.io와 Spring Boot 공식 문서(2026-11 조회)를 바탕으로 했어요. 클러스터에서 직접 돌려 본 결과가 아니라 문서 근거로 정리했고, 표의 HPA 숫자는 공식 계산식에 넣어 직접 계산한 값이에요.
</Aside>

## 쉽게 이해하기

Pod를 **편의점 알바생**이라고 해 봐요. 매니저(kubelet, 각 서버에서 컨테이너를 돌보는 관리 프로그램)가 주기적으로 상태를 확인해요.

- **startup 확인**: "출근 준비 끝났어요?" 옷 갈아입는 중엔 다른 질문을 안 해요.
- **liveness 확인**: "정신은 있어요?" 서서 졸고 있으면(데드락) 깨워서 다시 시작시켜요.
- **readiness 확인**: "지금 손님 받을 수 있어요?" 물건 정리 중이면 계산대만 잠깐 닫아요. 사람은 그대로예요.

퇴근(종료)할 땐 문제가 하나 있어요. 매니저가 "퇴근하세요"라고 말하는 것과 입구에 "이 계산대 닫음" 팻말을 거는 게 **동시에** 일어나요. 팻말이 늦게 걸리면 퇴근 중인 알바생에게 손님이 와서 헛걸음해요. 그래서 "팻말 걸릴 때까지 10초만 더 서 있기"(preStop sleep)를 넣어요.

**HPA**(HorizontalPodAutoscaler, Pod 수를 자동으로 늘리고 줄이는 기능)는 점장이에요. 알바생들이 평균적으로 얼마나 바쁜지 보고 "목표보다 1.5배 바쁘니 1.5배로 뽑자"처럼 계산해요.

단, 실제로 "바쁜 정도"는 사람 체감이 아니라 **처음에 신청한 자원(request) 대비 실제 CPU 사용량**이에요. 신청서가 없으면 점장은 계산을 못 해요.

## 제대로 알기

### 1. Probe가 왜 필요한가

프로세스가 **살아 있다고 일을 하고 있는 건 아니에요.** 데드락(스레드들이 서로를 기다리며 멈춘 상태)에 걸린 Java 앱은 프로세스는 멀쩡해 보여도 요청을 하나도 처리 못 해요. 막 뜬 앱은 캐시를 채우는 중이라 아직 요청을 받으면 안 될 수도 있어요.

**Probe**(프로브, 진단 검사)는 kubelet이 컨테이너에 주기적으로 던지는 질문이에요. 방법은 네 가지예요.

| 방식 | 성공 조건 |
|---|---|
| `httpGet` | 응답 상태코드 200 이상 400 미만 |
| `tcpSocket` | 포트 연결 성공 |
| `exec` | 컨테이너 안에서 명령 실행 후 종료코드 0 |
| `grpc` | gRPC 헬스 체크 응답 |

### 2. 세 가지 probe 비교

| | startupProbe | livenessProbe | readinessProbe |
|---|---|---|---|
| 묻는 것 | 다 떴나? | 살아서 일하나? | 손님 받을 수 있나? |
| 언제 도나 | 시작할 때만, 성공하면 끝 | startup 성공 후 계속 | startup 성공 후 **수명 내내** 계속 |
| 실패하면 | 컨테이너 **종료 → 재시작** | 컨테이너 **재시작** | **재시작 안 함.** Ready=false, Service 엔드포인트에서 빠짐 |
| 회복하면 | - | - | 다시 엔드포인트에 들어가 트래픽 받음 |
| 쓰는 곳 | 기동이 느린 앱 | 데드락처럼 복구 불가능한 상태 | 기동 직후 준비 중, 일시 과부하 |

- startupProbe가 있으면 **성공할 때까지 liveness·readiness를 아예 안 돌려요.**
- liveness와 readiness는 서로 기다리지 않아요. 각자 따로 돌아요.
- 재시작이 반복되면 kubelet은 10초, 20초, 40초… 식으로 기다리는 시간을 늘려요(최대 5분). 이 상태가 **CrashLoopBackOff**예요. 10분 동안 문제없이 돌면 대기 시간이 초기화돼요.

<Aside type="caution" title="liveness는 '정말 고칠 방법이 재시작밖에 없을 때'만">
쿠버네티스 문서는 liveness를 잘못 만들면 **연쇄 장애**(cascading failure)가 난다고 경고해요. 부하가 높을 때 컨테이너가 재시작되면 실패 요청이 늘고, 남은 Pod에 부하가 몰려 그 Pod도 쓰러지는 식이에요. 앱이 문제가 생기면 스스로 죽는 구조라면 liveness가 없어도 restartPolicy가 재시작해 줘요.
</Aside>

### 3. Probe 숫자 설정

| 필드 | 기본값 | 뜻 |
|---|---|---|
| `initialDelaySeconds` | 0 | 컨테이너 시작 후 첫 검사까지 대기 |
| `periodSeconds` | 10 | 검사 간격 |
| `timeoutSeconds` | **1** | 응답을 기다리는 시간. 넘으면 실패 |
| `failureThreshold` | 3 | 연속 몇 번 실패해야 "실패"로 볼지 |
| `successThreshold` | 1 | liveness·startup은 반드시 1 |

기본값 그대로면 liveness는 **10초 간격으로 3번 연속 실패하면** 재시작돼요. 첫 실패 시점에 따라 대략 20~30초 안에 판정 나요(직접 계산한 값).

`timeoutSeconds` 기본값이 **1초**라는 점이 함정이에요. 긴 GC 멈춤(Stop-the-World)이나 스레드 풀 고갈로 헬스 응답이 1초를 넘기면 실패로 세요.

**기동이 느린 앱**은 liveness 간격을 늘리지 말고 startupProbe를 따로 둬요. 문서 기준으로 기동 시간이 `initialDelaySeconds + failureThreshold × periodSeconds`보다 길면 startupProbe를 쓰라고 해요. 공식 예시는 `failureThreshold: 30` × `periodSeconds: 10` = **최대 300초**까지 기동을 기다려 줘요.

### 4. Spring Boot Actuator와 연결

Spring Boot는 쿠버네티스 환경에서 probe용 엔드포인트를 **자동으로** 켜요.

- `/actuator/health/liveness`: 앱 내부 상태(LivenessState: CORRECT / BROKEN)
- `/actuator/health/readiness`: 트래픽 수용 여부(ReadinessState: ACCEPTING_TRAFFIC / REFUSING_TRAFFIC)

이 두 그룹에는 **DB 같은 외부 시스템 체크가 기본으로 안 들어가요.** Spring 문서도 "liveness는 외부 시스템 상태에 의존하면 안 된다. DB나 외부 API가 죽으면 모든 인스턴스가 재시작돼 연쇄 장애가 날 수 있다"고 경고해요.

readiness에 외부 시스템을 넣을지는 **선택**이에요. 넣으면 외부 장애 때 앱이 서비스에서 빠지는 걸 감수하고, 빼면 호출하는 쪽의 **서킷 브레이커**(실패가 계속되는 대상 호출을 잠시 끊는 장치) 같은 걸로 처리해요.

기동과 종료 때 상태는 이렇게 바뀌어요.

| 시점 | Liveness | Readiness |
|---|---|---|
| 기동 중 | BROKEN | REFUSING_TRAFFIC |
| 컨텍스트 준비 완료 | CORRECT | REFUSING_TRAFFIC |
| 시작 작업까지 끝 | CORRECT | ACCEPTING_TRAFFIC |
| 우아한 종료 중 | CORRECT | REFUSING_TRAFFIC |

### 5. 우아한 종료: Pod는 어떤 순서로 죽나

롤링 배포나 스케일 다운으로 Pod가 지워질 때 순서예요.

1. Pod 삭제 요청. **유예 시간**(terminationGracePeriodSeconds, 기본 30초) 타이머 시작.
2. **preStop 훅**(종료 직전에 실행하는 명령)이 있으면 kubelet이 실행.
3. 컨테이너의 1번 프로세스에 **SIGTERM**(정상 종료 요청 신호) 전송.
4. 유예 시간이 끝났는데 아직 살아 있으면 **SIGKILL**(즉시 강제 종료).

여기서 핵심은 **1번과 동시에** 컨트롤 플레인이 이 Pod를 **EndpointSlice**(Service가 트래픽을 보낼 Pod IP 목록)에서 빼는 작업을 시작한다는 거예요. 그런데 kube-proxy나 Ingress가 바뀐 목록을 반영하는 데는 시간이 걸려요. **SIGTERM이 먼저 도착하면** 앱은 이미 새 요청을 거부하는데 Ingress는 아직 요청을 보내서 502나 connection refused가 나요. → [Service와 Ingress](../k8s-service-ingress/)

그래서 Spring Boot 문서는 **preStop에 sleep을 넣으라고** 권해요. sleep 동안 라우팅 반영이 끝나고, 그다음에 SIGTERM이 와요.

- 유예 시간에는 **preStop 시간 + 앱 종료 시간이 모두 포함**돼요. preStop 10초 + 앱 종료 최대 30초면 기본 30초로는 모자라요.
- preStop이 유예 시간을 넘기면 kubelet이 **딱 한 번 2초**를 더 줘요. 그래도 모자라면 유예 시간을 늘려야 해요.
- 쿠버네티스 1.32 이상은 셸 없이 `preStop.sleep.seconds`를 쓸 수 있어요. 그 전에는 `sh -c "sleep 10"`인데, 셸이 없는 이미지(distroless 등)에선 안 돼요.

### 6. Spring Boot 설정 예

**Spring Boot 3.4부터 우아한 종료가 기본으로 켜져 있어요**(`server.shutdown` 기본값 `graceful`). 3.3 이하는 기본이 `immediate`라서 직접 넣어야 했어요. 켜져 있으면 내장 서버(Tomcat 등)가 새 요청을 멈추고 처리 중인 요청을 마칠 시간을 줘요.

```yaml
# application.yml
server:
  shutdown: graceful            # 3.4+는 기본값. 3.3 이하는 꼭 명시
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 종료 단계별 최대 대기(기본 30s)
```

```yaml
# Deployment의 Pod 템플릿 일부
spec:
  terminationGracePeriodSeconds: 45   # preStop 10 + 앱 종료 30 + 여유
  containers:
    - name: app
      startupProbe:
        httpGet: { path: /actuator/health/liveness, port: 8080 }
        failureThreshold: 30          # 30 × 10초 = 최대 300초 기동 허용
        periodSeconds: 10
      livenessProbe:
        httpGet: { path: /actuator/health/liveness, port: 8080 }
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }
      lifecycle:
        preStop:
          sleep: { seconds: 10 }      # K8s 1.32+. 그 전엔 exec로 sleep
```

<Aside type="caution" title="graceful만 켜면 무중단 배포 끝? 아니에요">
Spring 문서도 우아한 종료 기간에만 기대지 말라고 해요. SIGTERM 이후 Spring은 새 요청을 거부하는데, 그 순간에도 아직 요청이 들어올 수 있어서 preStop이 따로 필요해요. IDE에서 앱을 멈추면 SIGTERM이 제대로 안 가서 바로 꺼질 수도 있어요.
</Aside>

### 7. HPA: Pod 수를 어떻게 계산하나

HPA는 기본 **15초마다** 메트릭을 보고 이 식으로 원하는 Pod 수를 정해요.

```
원하는 Pod 수 = ceil( 현재 Pod 수 × 현재 메트릭 ÷ 목표 메트릭 )
```

`ceil`은 올림이에요. 예시를 직접 계산해 보면 이래요.

| 현재 Pod | 평균 사용률 | 목표 | 비율 | 계산 | 결과 |
|---|---|---|---|---|---|
| 4 | 90% | 60% | 1.5 | ceil(6.0) | 6개로 증가 |
| 3 | 90% | 50% | 1.8 | ceil(5.4) | 6개로 증가 |
| 3 | 70% | 50% | 1.4 | ceil(4.2) | 5개로 증가 |
| 10 | 40% | 50% | 0.8 | ceil(8.0) | 8개 권고, 단 5분 안정화 뒤 감소 |
| 4 | 63% | 60% | 1.05 | 허용오차 0.1 안 | 변화 없음 |

**사용률은 노드 CPU가 아니라 Pod의 request 대비 비율이에요.** **request**는 컨테이너가 "최소 이만큼은 필요해요"라고 신청한 자원이에요. → [설정과 리소스](../k8s-config/)

- CPU request 500m(0.5코어)에 실제 400m를 쓰면 80%예요. request를 1000m로 잡으면 같은 사용량이 40%로 보여서 늘어나지 않아요.
- 컨테이너 중 하나라도 **request가 없으면** 그 Pod의 사용률을 계산할 수 없고, HPA는 그 메트릭으로 아무것도 안 해요.
- CPU·메모리 메트릭은 보통 **Metrics Server**가 제공하는데, **따로 설치**해야 해요.

들쭉날쭉(flapping)을 막는 장치도 있어요.

| 장치 | 기본값 | 효과 |
|---|---|---|
| 허용오차 | 0.1(10%) | 비율이 0.9~1.1이면 아무것도 안 함 |
| 스케일 업 | 안정화 0초, 15초마다 현재의 100% 또는 4개 중 큰 쪽까지 추가 | 급증엔 빠르게 |
| 스케일 다운 | 안정화 **300초**, 최근 5분 권고 중 **가장 큰 값** 사용 | 잠깐 줄었다고 바로 안 줄임 |

메트릭이 없는 Pod나 아직 Ready가 아닌 Pod는 일단 빼고 계산한 뒤, 스케일 업이면 그 Pod가 0%를 쓴다고 보수적으로 가정해 폭을 줄여요. 막 뜬 JVM의 워밍업 CPU 때문에 과하게 늘어나는 걸 어느 정도 막아 줘요.

## 면접 질문

<details>
<summary>Q. liveness, readiness, startup probe의 차이는 무엇인가요?</summary>

**답변(30초)** 실패했을 때 하는 일이 달라요. liveness는 실패하면 컨테이너를 재시작하고, readiness는 재시작 없이 Service 엔드포인트에서만 빼서 트래픽을 끊어요. startup은 앱이 다 뜰 때까지 나머지 두 probe를 미뤄서, 기동이 느린 앱이 기동 중에 liveness에 걸려 죽지 않게 해요. readiness는 시작할 때만이 아니라 수명 내내 돌아요.

**꼬리질문**
- Q. readiness가 실패하면 재시작되나요? → 아니에요. Ready만 false가 되고 엔드포인트에서 빠져요. 회복하면 다시 트래픽을 받아요.
- Q. initialDelaySeconds를 크게 잡으면 startupProbe 없이도 되지 않나요? → 되긴 하지만 기동이 빨리 끝나도 그 시간 동안 이상을 못 잡고, 기동이 더 느려지면 재시작 루프에 빠져요. 그래서 startupProbe를 권해요.
</details>

<details>
<summary>Q. liveness probe에 DB 헬스 체크를 넣으면 안 되는 이유는요?</summary>

**답변(30초)** DB 하나가 잠깐 죽으면 모든 Pod의 liveness가 동시에 실패해서 전부 재시작되기 때문이에요. 재시작해도 DB 문제는 안 풀리고, 오히려 모든 Pod가 한꺼번에 다시 떠서 DB에 연결을 몰아붙여 복구가 늦어져요. 쿠버네티스와 Spring 문서 모두 이런 연쇄 장애를 경고해요. liveness는 앱 내부 상태만 보고, DB 상태는 필요하면 readiness에 넣거나 서킷 브레이커로 처리해요.

**꼬리질문**
- Q. readiness에 DB를 넣으면 문제는 없나요? → 재시작은 안 되지만 DB 장애 때 모든 Pod가 엔드포인트에서 빠져 서비스 전체가 응답을 못 해요. 그걸 감수할지 판단해야 해요.
</details>

<details>
<summary>Q. Pod가 종료되는 과정을 설명해 주세요.</summary>

**답변(30초)** 삭제 요청이 오면 기본 30초 유예 시간이 시작되고, preStop 훅이 있으면 먼저 실행해요. 그다음 컨테이너에 SIGTERM을 보내 앱이 스스로 정리하게 하고, 유예 시간이 끝났는데도 살아 있으면 SIGKILL로 강제 종료해요. 이와 동시에 컨트롤 플레인은 Pod를 Service 엔드포인트에서 빼요. 이 두 작업이 동시에 일어나서 preStop sleep으로 순서를 맞춰 줘요.

**꼬리질문**
- Q. 유예 시간은 SIGTERM 이후부터 세나요? → 아니에요. preStop 실행 시간까지 포함한 전체 시간이에요.
- Q. preStop이 유예 시간을 넘기면요? → kubelet이 2초를 딱 한 번 더 줘요. 그래도 모자라면 유예 시간을 늘려야 해요.
</details>

<details>
<summary>Q. HPA는 어떻게 Pod 수를 정하나요? CPU 목표 50%에 Pod 3개가 평균 90%면 몇 개가 되나요?</summary>

**답변(30초)** 현재 Pod 수에 "현재 메트릭 ÷ 목표 메트릭"을 곱하고 올림해요. 3 × 90 ÷ 50 = 5.4라서 올림해 6개가 돼요. 이때 사용률은 노드 CPU가 아니라 각 Pod의 CPU request 대비 비율이에요. 그래서 request가 없으면 HPA가 CPU 기준으로 동작하지 않아요.

**꼬리질문**
- Q. 부하가 줄면 바로 줄어드나요? → 아니에요. 스케일 다운은 기본 5분 안정화 동안 최근 권고 중 가장 큰 값을 써서 천천히 줄여요. 스케일 업은 바로 해요.
- Q. 63%인데 목표 60%면요? → 비율 1.05로 허용오차 0.1 안이라 아무것도 안 해요.
</details>

<details>
<summary>Q. CrashLoopBackOff가 무엇인가요?</summary>

**답변(30초)** 컨테이너가 계속 죽고 재시작되는 상태에서, kubelet이 재시작 사이 대기 시간을 10초, 20초, 40초처럼 늘려 가는 상태예요. 최대 5분까지 늘어나고, 10분 동안 문제없이 돌면 초기화돼요. 앱이 기동 중 에러로 죽는 경우도 있지만, 기동이 느린데 liveness가 너무 빨리 검사해서 죽이는 경우도 흔해요.

**꼬리질문**
- Q. 원인을 어떻게 찾나요? → 이전 컨테이너의 로그와 Pod 이벤트에서 probe 실패인지, 앱 에러인지, OOM 같은 강제 종료인지 먼저 구분해요. → [컨테이너와 VM](../container-vs-vm/)
</details>

## 서술형 연습

<details>
<summary>상황: 결제 API 서버의 DB가 페일오버로 30초간 응답하지 않았습니다. 그런데 DB가 돌아온 뒤에도 수 분간 장애가 이어졌고, 그 사이 모든 Pod가 재시작된 기록이 있습니다.</summary>

**상황 파악**
DB 장애는 30초였는데 장애가 길어졌고, 그동안 **모든 Pod가 동시에 재시작**됐어요. DB 문제가 앱 재시작으로 번진 거라서, "누가 Pod를 재시작시켰나"부터 봐요. Pod 이벤트에서 liveness probe 실패 기록을 확인해요.

**원인 후보**
1. liveness가 DB 상태까지 보는 엔드포인트를 쓰고 있어요. 예를 들어 `/actuator/health/liveness` 대신 전체 `/actuator/health`를 liveness로 걸면, 앱 설정에 따라 DB 상태도 함께 반영돼요.
2. 기본값(10초 × 3회)이면 30초짜리 DB 장애로 충분히 liveness가 실패해요. 모든 Pod가 같은 DB를 보니 동시에 재시작돼요.
3. 모든 Pod가 한꺼번에 다시 뜨면서 커넥션 풀을 새로 채우느라 DB에 연결이 몰리고, JVM 워밍업 동안 처리량도 낮아요. 그래서 DB가 돌아온 뒤에도 회복이 늦어져요(일반적인 연쇄 장애 패턴).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. liveness를 `/actuator/health/liveness`로 분리해 앱 내부 상태만 보게 함 | DB 장애로 재시작이 안 일어남. 근본 원인 제거 | 앱이 DB 없이 떠 있는 동안 요청은 실패함 |
| B. DB 상태를 readiness에 넣음 | DB 장애 때 트래픽을 받지 않아 실패 요청이 줄어듦 | 모든 Pod가 엔드포인트에서 빠져 서비스 전체가 응답 불가. 재시작은 안 함 |
| C. DB는 probe에서 빼고 서킷 브레이커·타임아웃으로 빠르게 실패 | Pod는 계속 트래픽을 받으며 DB와 무관한 기능은 살아 있음 | 앱 코드에 장애 처리 로직이 필요함 |

**내가 고를 방법**
A는 반드시 해요. 재시작으로 DB 장애가 풀리지 않으니 liveness에서 DB를 빼는 게 근본 해결이에요. 그다음 결제처럼 DB 없이는 아무것도 못 하는 API라도 B보다는 C를 골라요. 응답 불가로 빠지는 것보다 빠르게 에러를 돌려주는 편이 클라이언트가 재시도·안내를 하기 쉬워요. 적용 후 DB 장애 훈련에서 Pod 재시작 횟수가 0인지, DB 복구 직후 에러율이 바로 떨어지는지 확인해요.

**채점 포인트**: liveness 실패 = 재시작, 외부 의존성을 liveness에 넣지 않음(공식 경고), 모든 Pod 동시 재시작 → 연쇄 장애, 재시작 시 커넥션 몰림·워밍업, liveness/readiness 엔드포인트 분리, readiness에 DB를 넣을 때의 트레이드오프, 서킷 브레이커, 적용 후 검증.
</details>

<details>
<summary>상황: 롤링 배포를 할 때마다 몇 초 동안 502 에러가 몇 건씩 납니다. 배포가 끝나면 사라집니다.</summary>

**상황 파악**
배포 중에만, 몇 초만 나는 에러라면 **Pod가 바뀌는 순간**의 문제예요. 새 Pod가 준비 안 된 채 트래픽을 받았거나, 꺼지는 Pod로 트래픽이 갔거나 둘 중 하나예요. 502가 언제 나는지(새 Pod 투입 시점인지, 옛 Pod 종료 시점인지)를 로그 시간으로 맞춰 봐요.

**원인 후보**
1. **엔드포인트 제거와 SIGTERM의 경합**: Pod 삭제 시 EndpointSlice 제거와 SIGTERM 전송이 동시에 일어나요. Ingress·kube-proxy 반영이 늦으면 이미 새 요청을 거부하는 Pod로 요청이 가요.
2. 우아한 종료가 꺼져 있어요. Spring Boot 3.3 이하는 기본이 `immediate`라 처리 중인 요청까지 끊겨요.
3. readiness probe가 없거나 너무 가벼워서 새 Pod가 준비 전에 트래픽을 받아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. preStop sleep(5~15초) 추가 | 라우팅 반영이 끝난 뒤 SIGTERM이 가서 경합 해소 | Pod 종료가 그만큼 느려져 배포 시간이 늘어남. 적정 시간은 환경마다 다름 |
| B. `server.shutdown=graceful` 확인 | 처리 중인 요청을 마치고 종료 | 이것만으로는 경합을 못 막음 |
| C. 유예 시간을 preStop + 앱 종료 시간 이상으로 늘림 | SIGKILL로 중간에 잘리는 것 방지 | 정말 멈춘 Pod도 그만큼 늦게 치워짐 |
| D. readiness를 `/actuator/health/readiness`로 설정 | 새 Pod가 준비된 뒤에만 트래픽을 받음 | 기동 시간만큼 배포가 느려짐 |

**내가 고를 방법**
A~D를 함께 적용해요. 핵심은 A예요. graceful shutdown은 "들어온 요청을 끝내는 것"이고, preStop은 "새 요청이 그만 오게 기다리는 것"이라 역할이 달라요. 예를 들어 preStop 10초, 앱 종료 최대 30초라면 유예 시간은 기본 30초에서 45초 정도로 늘려요. 배포 시간이 조금 늘어나는 건 결제 같은 서비스에서 에러보다 훨씬 싸요. 적용 후 배포 중 502 건수가 0이 되는지 확인하고, 아직 남으면 sleep 시간을 늘려요. → [로드밸런서와 프록시](../../web/load-balancer-proxy/)

**채점 포인트**: 엔드포인트 제거와 SIGTERM이 동시 진행(순서 보장 없음), preStop sleep, 유예 시간에 preStop 시간 포함, Spring Boot 3.4+ 기본 graceful(이전 버전은 immediate), graceful만으로는 부족, readiness probe, 배포 시간 증가 트레이드오프, 배포 중 에러율 검증.
</details>

<details>
<summary>상황: 새로 띄운 Spring 서버가 Running이 되었다가 계속 재시작되며 결국 CrashLoopBackOff가 됩니다. 로컬에서는 약 90초 걸려 정상 기동합니다.</summary>

**상황 파악**
로컬에선 뜨는데 쿠버네티스에서만 재시작된다면 앱 에러보다 **쿠버네티스가 죽이고 있을** 가능성이 커요. Pod 이벤트에서 liveness probe 실패 기록이 있는지, 재시작 시점이 기동 후 일정 시간인지 봐요.

**원인 후보**
1. liveness가 기동이 끝나기 전에 검사를 시작해요. 예를 들어 `initialDelaySeconds: 30`에 기본값(10초 × 3회)이면 약 60초 안에 판정이 나는데 기동은 90초 걸려서, 뜨는 도중에 재시작돼요. 매번 처음부터 다시 뜨니 영원히 못 떠요.
2. 컨테이너 CPU가 로컬보다 적게 잡혀 있어 기동이 더 오래 걸려요.
3. 정말 앱이 기동 중 에러로 죽는 경우(설정 누락 등). 이건 앱 로그로 구분해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. liveness `initialDelaySeconds`를 120초로 늘림 | 설정 하나로 해결 | 기동이 빨리 끝나도 그 시간 동안 이상을 못 잡음. 기동이 더 느려지면 같은 문제 재발 |
| B. startupProbe 추가(예: 10초 × 30회 = 최대 300초) | 기동이 끝나는 순간부터 liveness가 정상 간격으로 동작. 기동 시간 변동에 강함 | 정말 기동에 실패한 경우 판정이 최대 5분 늦어짐 |
| C. 기동 시간 자체를 줄임(불필요한 초기화 제거, CPU request 상향) | 배포·스케일 아웃도 빨라짐 | 시간이 들고 비용이 늘 수 있음 |

**내가 고를 방법**
B를 골라요. 쿠버네티스 문서도 오래 뜨는 앱엔 liveness 간격을 늘리지 말고 startupProbe를 따로 두라고 권해요. startup이 성공할 때까지 liveness·readiness가 안 도니, liveness는 기본값처럼 짧게 유지할 수 있어요. 여유는 기동 시간의 2~3배 정도로 잡고, 길게 보면 C로 기동 시간을 줄여요. 적용 후 재시작 횟수가 0인지, 실제 기동 시간이 startupProbe 한도보다 충분히 짧은지 확인해요.

**채점 포인트**: 재시작 주체가 kubelet(liveness)인지 확인, CrashLoopBackOff(지수 백오프, 최대 5분), 기동 중 liveness 실패, startupProbe가 성공할 때까지 liveness·readiness 미실행, initialDelaySeconds만 늘리는 방법의 한계, failureThreshold × periodSeconds 계산, 기동 시간 단축.
</details>

<details>
<summary>상황: 이벤트로 트래픽이 평소의 3배가 됐는데 HPA를 걸어 둔 Deployment의 Pod 수가 늘지 않습니다. 응답은 점점 느려지고 있습니다.</summary>

**상황 파악**
HPA가 아예 안 늘어난 건지, 늦게 늘어나는 건지부터 구분해요. `kubectl describe hpa`에서 현재 메트릭 값이 `<unknown>`으로 나오는지, 이벤트에 메트릭을 못 가져왔다는 경고가 있는지 봐요.

**원인 후보**
1. **CPU request 미설정**: 사용률은 request 대비 비율이라, request가 없는 컨테이너가 있으면 계산이 안 되고 HPA가 아무것도 안 해요.
2. **Metrics Server 미설치·장애**: CPU·메모리 메트릭을 줄 곳이 없어요.
3. **request가 너무 큼**: request 1000m에 실제 400m면 40%로 보여서 목표 60%를 못 넘어요. 실제로는 바쁜데 HPA 눈엔 한가해요.
4. **병목이 CPU가 아님**: DB 커넥션이나 외부 API 대기라면 CPU는 낮아서 늘어나지 않아요. 늘려도 해결되지 않을 수 있어요.
5. **이미 maxReplicas에 닿음**.
6. 늘고는 있는데 **느림**: 15초 주기, 메트릭 지연, 새 Pod의 JVM 기동·readiness 시간이 쌓여요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. CPU request를 실제 사용량에 맞게 설정, Metrics Server 확인 | HPA가 정상 계산함. 근본 해결 | request를 크게 잡으면 노드에 덜 들어가 비용 증가 |
| B. 지금 당장 replicas를 수동으로 늘리거나 minReplicas 상향 | 즉시 효과 | 사람이 개입해야 함. 이벤트 뒤 되돌리지 않으면 비용 낭비 |
| C. 목표 사용률을 낮춤(예: 70% → 50%) | 더 일찍 늘어나 급증에 여유 | 평소에도 Pod가 많아 비용 증가 |
| D. 병목에 맞는 메트릭(요청 수 등) 사용 | 실제 부하를 반영 | 커스텀 메트릭 수집 구성이 필요 |

**내가 고를 방법**
지금은 B로 Pod를 수동으로 늘려 급한 불을 꺼요. 그다음 `describe hpa`로 원인을 확정하고, request 미설정이나 Metrics Server 문제라면 A로 고쳐요. 이벤트처럼 미리 아는 급증은 HPA가 따라잡기엔 늦을 수 있어서, 시작 전에 minReplicas를 올려 두고 끝나면 내려요. 스케일 다운은 기본 5분 안정화가 있으니 이벤트 직후 Pod가 급히 줄어들 걱정은 덜어요. 적용 후 부하 테스트에서 메트릭이 제대로 잡히고 Pod 수가 계산대로 늘어나는지 확인해요.

**채점 포인트**: 사용률 = request 대비 비율, request 없으면 HPA 동작 안 함, Metrics Server 별도 설치, request 과대 설정 문제, 병목이 CPU가 아닐 가능성, 15초 주기·기동 시간으로 인한 지연, 사전 minReplicas 상향, 비용 트레이드오프, 스케일 다운 5분 안정화.
</details>

## 필기 포인트

- 재시작하는 건 **liveness·startup**뿐. readiness 실패는 **엔드포인트에서 제외**만.
- startupProbe가 성공할 때까지 liveness·readiness는 **실행 안 됨**.
- probe 기본값: period 10초, timeout **1초**, failureThreshold 3, initialDelay 0, successThreshold 1.
- httpGet 성공 = 상태코드 **200 이상 400 미만**.
- 종료 순서: preStop → SIGTERM → (유예 시간 초과 시) SIGKILL. 유예 시간 기본 **30초**, preStop 시간 **포함**.
- CrashLoopBackOff: 10초부터 2배씩, 최대 **300초**. 10분 정상이면 초기화.
- Spring Boot **3.4+** `server.shutdown` 기본 `graceful`(이전 `immediate`), `timeout-per-shutdown-phase` 기본 30s.
- HPA: `ceil(현재 수 × 현재값 ÷ 목표값)`, 주기 15초, 허용오차 0.1, 스케일 다운 안정화 300초.
- HPA 사용률 = **request 대비**. request 없으면 동작 안 함. Metrics Server 별도 설치.
