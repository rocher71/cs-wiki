**이미지**는 앱 실행에 필요한 파일을 **읽기 전용 레이어**로 쌓은 꾸러미이고, **Dockerfile**은 그 레이어를 어떤 순서로 쌓을지 적은 레시피예요. 잘 안 바뀌는 것을 위에 두면 **빌드 캐시**로 빌드가 빨라지고, **멀티 스테이지 빌드**로 결과물만 옮기면 이미지가 작아져요.
:::

## 쉽게 이해하기

**Dockerfile은 요리 레시피**예요. "냄비를 꺼낸다 → 육수를 붓는다 → 면을 넣는다"처럼 순서대로 적혀 있어요.

**이미지는 그 레시피대로 만들어 둔 밀키트**예요. 재료가 손질된 채로 칸칸이 포장돼 있어서, 어느 집에서 뜯어도 똑같은 맛이 나요. 밀키트의 칸 하나하나가 **레이어**예요.

**컨테이너는 밀키트를 뜯어서 실제로 요리하는 것**이에요. 밀키트 자체는 그대로 두고, 내 냄비 위에서 조리해요. 냄비를 치우면(컨테이너를 지우면) 조리 흔적도 같이 사라져요.

레시피를 고칠 때 요령도 있어요. "육수 끓이기"처럼 오래 걸리는 단계는 앞에, "고명 올리기"처럼 자주 바꾸는 단계는 뒤에 두면, 고명만 바꿀 때 육수는 어제 끓인 걸 그대로 써요. 이게 **빌드 캐시**예요.

단, 실제로는 밀키트처럼 칸이 옆으로 나란히 있는 게 아니라 **위로 겹겹이 쌓여요**. 아래 칸이 바뀌면 그 위 칸은 전부 다시 만들어야 해요. 이 점이 빌드 속도를 가르는 핵심이에요.

## 제대로 알기

### 1. 이미지는 레이어를 쌓은 것

**이미지**(image)는 앱과 라이브러리, 설정 파일을 묶어 둔 **읽기 전용** 꾸러미예요. 커널은 들어 있지 않아요. 커널은 호스트 것을 함께 써요. → [컨테이너와 VM](../container-vs-vm/)

이미지는 **레이어**(layer, 파일 변경분 한 겹)를 아래에서 위로 쌓아서 만들어요.

- Dockerfile에서 **파일을 바꾸는 명령**(`RUN`, `COPY`, `ADD`)이 레이어를 하나씩 만들어요.
- `CMD`, `ENV`, `EXPOSE`처럼 **설정만 바꾸는 명령**은 크기 0B짜리 기록만 남겨요.
- 레이어는 내용으로 계산한 **digest**(다이제스트, `sha256:...` 형태의 내용 지문)로 저장돼요. 그래서 내용이 같은 레이어는 한 번만 저장되고 여러 이미지가 나눠 써요. 같은 베이스 이미지를 쓰는 이미지 10개가 있어도 베이스 레이어는 한 벌만 있어요.
- 레지스트리에 올리거나 받을 때도 레이어 단위로 주고받아요. 이미 있는 레이어는 다시 보내지 않아요.

실험에서 만든 이미지를 `docker history`로 보면 이렇게 쌓여 있어요(위가 최신).

```text
CMD ["python" "app.py"]                       0B      ← 설정만, 크기 0
COPY . .                                      16.4kB
RUN /bin/sh -c pip install --no-cache-dir …   13.5MB
COPY requirements.txt .                       12.3kB
WORKDIR /app                                  8.19kB
CMD ["python3"]                               0B      ← 여기부터 베이스 이미지 레이어
```

내가 쓴 명령 다섯 줄이 베이스 이미지(`python:3.12-slim`, 약 203MB) 위에 그대로 얹혀서 약 221MB가 됐어요.

**컨테이너를 띄우면** 이 읽기 전용 레이어들 위에 **얇은 쓰기 레이어**가 하나 붙어요. 컨테이너 안에서 쓰는 파일은 전부 여기로 가요. 아래 레이어의 파일을 고치면, 그때 처음 위로 복사해서 고쳐요. 이걸 **copy-on-write**(쓸 때 복사)라고 해요. 그래서 컨테이너 안에서 파일을 고쳐도 이미지는 그대로이고, 컨테이너를 지우면 고친 내용도 사라져요.

여러 레이어를 겹쳐 하나의 파일시스템처럼 보여 주는 방식을 **유니온 파일시스템**이라고 하고, 리눅스 Docker의 대표 구현이 OverlayFS를 쓰는 `overlay2`예요.

### 2. Dockerfile 주요 명령

| 명령 | 하는 일 | 레이어 |
|---|---|---|
| `FROM 이미지[:태그][@digest] [AS 이름]` | 베이스 이미지를 고르고 새 스테이지를 시작 | 베이스 레이어를 가져옴 |
| `RUN 명령` | **빌드할 때** 명령을 실행하고 결과를 저장 | 만듦 |
| `COPY 원본 대상` | 빌드 컨텍스트(또는 다른 스테이지)에서 파일 복사 | 만듦 |
| `ADD 원본 대상` | COPY + 원격 URL·Git 받기, 로컬 tar 자동 압축 해제 | 만듦 |
| `WORKDIR 경로` | 이후 명령의 작업 폴더(없으면 만듦) | 만듦 |
| `ENV 키=값` | 컨테이너 실행 중에도 남는 환경 변수 | 설정만 |
| `ARG 이름` | **빌드할 때만** 쓰는 변수 | 설정만 |
| `EXPOSE 8080` | "이 포트를 쓴다"는 **문서용 표시**. 포트를 실제로 열지 않음 | 설정만 |
| `CMD` | 컨테이너 시작 시 기본 명령(또는 ENTRYPOINT의 기본 인자) | 설정만 |
| `ENTRYPOINT` | 컨테이너를 실행 파일처럼 고정하는 명령 | 설정만 |

헷갈리기 쉬운 세 가지예요.

- **COPY와 ADD**: ADD는 tar를 알아서 풀거나 URL에서 받는 등 기능이 더 많아요. 그만큼 의도치 않은 동작이 생길 수 있어서, 공식 권장은 보통 COPY이고 그 기능이 꼭 필요할 때만 ADD예요.
- **EXPOSE**: 써도 포트가 열리지 않아요. 밖에서 접속하게 하려면 `docker run -p 8080:8080`처럼 실행할 때 열어요.
- **ENV와 ARG**: ENV는 이미지에 남아서 실행 중에도 보이고 `docker run --env`로 덮어써요. ARG는 빌드가 끝나면 쓰이지 않아요.

### 3. CMD와 ENTRYPOINT

둘 다 "컨테이너가 시작될 때 무엇을 실행할까"를 정해요. 차이는 **`docker run 이미지 인자...`로 인자를 줬을 때** 드러나요.

- **CMD**는 run 인자가 오면 **통째로 바뀌어요**.
- **ENTRYPOINT**는 **그대로 남고**, run 인자가 그 뒤에 붙어요. ENTRYPOINT까지 바꾸려면 `--entrypoint`를 써요.
- 그래서 같이 쓰면 **ENTRYPOINT = 고정 실행 파일, CMD = 바꿀 수 있는 기본 인자**가 돼요.

`alpine:3.20`으로 실험한 결과예요.

| Dockerfile | 실행 | 출력 |
|---|---|---|
| `CMD ["echo","default-cmd"]` | `docker run img` | `default-cmd` |
| 〃 | `docker run img echo override` | `override` (CMD 전체가 바뀜) |
| 〃 | `docker run img hello` | 오류: `hello`라는 실행 파일 없음 (인자가 명령 자리로 감) |
| `ENTRYPOINT ["echo","ep:"]` + `CMD ["default-arg"]` | `docker run img` | `ep: default-arg` |
| 〃 | `docker run img hello world` | `ep: hello world` (CMD만 바뀜) |
| 〃 | `docker run --entrypoint date img` | 날짜 출력 (ENTRYPOINT 교체) |
| `ENTRYPOINT echo shell-form-ep` | `docker run img ignored-arg` | `shell-form-ep` (인자 무시) |

#### exec form과 shell form

명령을 쓰는 방식이 두 가지예요.

| | exec form | shell form |
|---|---|---|
| 모양 | `["java","-jar","app.jar"]` (JSON 배열) | `java -jar app.jar` |
| 실행 방식 | 셸 없이 바로 실행 | `/bin/sh -c "..."`로 감싸서 실행 |
| `$VAR` 치환 | 안 함 | 셸이 해 줌 |
| PID 1 | 앱 자신 | `sh`가 PID 1, 앱은 그 자식 |
| 종료 신호 | 앱이 `docker stop`의 SIGTERM을 받음 | 앱이 SIGTERM을 못 받을 수 있음 |
| ENTRYPOINT로 쓸 때 | CMD·run 인자가 뒤에 붙음 | CMD·run 인자를 무시 |

**PID 1**은 컨테이너 안에서 맨 처음 뜬 프로세스예요. `docker stop`은 이 프로세스에게 **SIGTERM**(정상 종료해 달라는 신호)을 보내요. shell form이면 `sh`가 신호를 받고 앱에는 안 넘겨 줄 수 있어서, 앱이 정리할 기회 없이 기다리다 강제 종료될 수 있어요. 그래서 **ENTRYPOINT와 CMD는 exec form**을 권장하고, 시작 스크립트를 쓴다면 마지막 줄을 `exec java ...`로 써서 앱이 PID 1이 되게 해요.

### 4. 빌드 캐시: 순서가 속도를 정한다

`docker build`는 명령을 한 줄씩 실행하면서 매번 **"이전 레이어 + 이 명령"이 전에 만든 것과 같은가?**를 확인해요. 같으면 다시 실행하지 않고 저장해 둔 레이어를 써요(`CACHED`).

캐시가 깨지는 조건은 명령마다 달라요.

- **RUN**: **명령 문자열**만 비교해요. 그래서 `RUN apt-get update`만 따로 두면, 문자열이 같으니 며칠 전 받은 오래된 목록이 계속 캐시돼요. 시간이 지났다고 캐시가 없어지지도 않아요. `apt-get update && apt-get install ...`처럼 같은 RUN에 묶어요.
- **COPY / ADD**: 복사할 **파일 내용과 권한**으로 체크섬을 만들어 비교해요. 수정 시각은 안 봐서 `touch`만으로는 캐시가 안 깨져요.

그리고 가장 중요한 규칙은 이거예요. **한 레이어의 캐시가 깨지면 그 아래 명령은 전부 다시 실행돼요.**

```dockerfile
# 나쁜 순서: 소스 한 글자만 고쳐도 의존성 설치를 다시 함
COPY . .
RUN pip install -r requirements.txt

# 좋은 순서: 의존성 목록이 그대로면 설치는 CACHED
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

실험에서 `app.py` 한 글자만 고치고 다시 빌드해 봤어요.

| 순서 | 다시 실행된 것 | 재빌드 시간 |
|---|---|---|
| 나쁜 순서 | `COPY . .` → `RUN pip install` | 약 1.78초 |
| 좋은 순서 | `COPY . .`만 (`pip install`은 CACHED) | 약 0.22초 |

의존성이 `requests` 하나뿐이라 차이가 1.5초 정도지만, 실제 프로젝트는 의존성 설치가 수십 초에서 수 분이라 그만큼 차이가 커져요.

**`.dockerignore`**도 같이 써요. 빌드할 때 Docker는 현재 폴더의 파일 묶음(**빌드 컨텍스트**)을 빌더로 보내는데, `.dockerignore`에 적은 파일은 빼고 보내요. `.git`, `.env`, `build/`, `node_modules` 같은 걸 빼면 빌드가 빨라지고, 상관없는 파일 변경이 `COPY . .` 캐시를 깨는 일도 막고, 비밀 파일이 이미지에 들어가는 사고도 막아요.

반대로 캐시를 일부러 무시하려면 `--no-cache`(전체 새로 빌드), 베이스 이미지를 새로 받으려면 `--pull`을 써요. 공식 문서는 보안 패치를 반영하려고 이 둘로 **주기적으로 다시 빌드**하길 권해요.

### 5. 멀티 스테이지 빌드: 결과물만 옮긴다

자바나 Go 앱을 빌드하려면 컴파일러와 빌드 도구가 필요해요. 그런데 **실행할 때는 필요 없어요**. 이걸 그대로 이미지에 두면 크기만 커지고, 공격자가 쓸 수 있는 도구도 늘어나요.

**멀티 스테이지 빌드**(multi-stage build)는 `FROM`을 여러 번 써서 단계를 나누고, **앞 단계의 결과물만** 마지막 이미지로 가져오는 방법이에요.

- `FROM ... AS build`로 단계에 이름을 붙여요.
- `COPY --from=build 경로 경로`로 그 단계에서 만든 파일만 가져와요.
- 최종 결과는 **이미지 하나**예요. 앞 단계는 빌드 재료로만 쓰이고 최종 이미지에 레이어가 남지 않아요.

Go hello world로 실험한 결과예요.

| 방식 | 최종 이미지 | 크기 |
|---|---|---|
| 단일 스테이지 | `golang:1.23-alpine`에서 빌드하고 그대로 실행 | 약 407MB (베이스만 365MB) |
| 멀티 스테이지 | 빌드는 golang, 실행은 `scratch`(아무것도 없는 빈 이미지)에 바이너리만 복사 | 약 3.41MB |

약 120배 차이예요. 멀티 스테이지 이미지의 `docker history`에는 바이너리 COPY(2.17MB)와 CMD(0B) 두 줄만 있었어요.

### 6. 스프링 부트 이미지 만들기

스프링 부트 실행 jar 안에는 `layers.idx`라는 목록이 있어서, 내용을 **바뀌는 빈도** 순으로 네 묶음으로 나눠요.

1. `dependencies` (외부 라이브러리, 거의 안 바뀜)
2. `spring-boot-loader` (jar 실행기)
3. `snapshot-dependencies` (개발 중인 SNAPSHOT 라이브러리)
4. `application` (내 코드, 자주 바뀜)

jar를 이 묶음대로 풀어서 **따로 COPY**하면, 코드만 고쳤을 때 라이브러리 레이어는 캐시를 그대로 써요. 4번의 레이어 순서 원리를 jar 안까지 적용한 거예요.

```dockerfile
# 1단계: JDK로 빌드 (예시 태그. 실제로는 버전·digest를 고정)
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY gradlew settings.gradle build.gradle ./
COPY gradle/ gradle/
# 의존성만 먼저 받아 캐시
RUN ./gradlew dependencies --no-daemon
COPY src/ src/
RUN ./gradlew bootJar --no-daemon && cp build/libs/myapp-0.0.1.jar app.jar \
 && java -Djarmode=tools -jar app.jar extract --layers --destination /extracted

# 2단계: 실행에는 JRE만
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /extracted/dependencies/ ./
COPY --from=build /extracted/spring-boot-loader/ ./
COPY --from=build /extracted/snapshot-dependencies/ ./
# 자주 바뀌는 건 맨 아래
COPY --from=build /extracted/application/ ./
# exec form → JVM이 PID 1
ENTRYPOINT ["java", "-jar", "app.jar"]
```

<Aside type="caution">
Dockerfile의 `#` 주석은 **줄 맨 앞**에서만 주석이에요. `ENTRYPOINT [...]  # 설명`처럼 뒤에 붙이면 JSON 배열로 읽히지 않아 shell form이 되고, `COPY a b  # 설명`은 `#`도 복사할 파일 이름으로 읽혀요.
</Aside>

`cp` 줄의 jar 이름은 프로젝트 이름·버전에 따라 달라요. 빌드 후 `build/libs`에 생긴 실행 jar 이름에 맞춰 고쳐 쓰고, 풀기 전에 `app.jar`로 이름을 바꿔 두면 마지막 줄을 고정할 수 있어요.

Dockerfile을 직접 안 쓰는 방법도 있어요. `./gradlew bootBuildImage`(Gradle)나 `mvn spring-boot:build-image`(Maven)를 실행하면 **Cloud Native Buildpacks**(Paketo)가 알아서 OCI 이미지를 만들어 줘요. → [스프링 부트 자동 설정](../../spring/boot-autoconfig/)

### 7. 이미지 이름, 태그, digest

이미지 이름의 전체 모양은 `[호스트[:포트]/]네임스페이스/저장소[:태그]`예요. 생략하면 호스트는 `docker.io`, 네임스페이스는 `library`, 태그는 `latest`가 붙어요. 그래서 `redis`는 사실 `docker.io/library/redis:latest`예요.

| | 태그 (`:3.12-slim`, `:latest`) | digest (`@sha256:...`) |
|---|---|---|
| 정체 | 사람이 붙인 **이름표** | 내용으로 계산한 **지문** |
| 바뀌나 | 바뀔 수 있음. 게시자가 같은 태그를 새 이미지로 옮김 | 안 바뀜. 내용이 다르면 digest도 다름 |
| 용도 | 읽기 쉬운 이름 | 정확히 같은 이미지를 보장 |

**`latest`는 "최신 버전"이라는 뜻이 아니에요.** 태그를 안 쓰면 자동으로 붙는 기본 이름일 뿐이에요. 그래서 같은 `latest`라도 언제 받았느냐에 따라 다른 이미지일 수 있어요. 정확히 같은 이미지를 쓰려면 `FROM alpine:3.21@sha256:...`처럼 digest로 고정해요.

### 8. 이미지 크기 줄이기 정리

- **작은 베이스 이미지**: `slim`, `alpine`, 셸도 없는 distroless, 아예 빈 `scratch`. 단, 셸이 없으면 `docker exec`로 들어가 디버깅하기 어려워요.
- **멀티 스테이지**: 컴파일러·빌드 도구는 최종 이미지에서 빼요.
- **설치와 정리는 같은 RUN에서**: 앞 레이어에서 만든 파일은 뒤 레이어에서 지워도 앞 레이어에 그대로 남아요. 그래서 `apt-get install ... && rm -rf /var/lib/apt/lists/*`처럼 한 줄에 써요. 단, 모든 RUN을 무조건 한 줄로 합치면 캐시를 덜 쓰게 되니 **바뀌는 빈도가 같은 것끼리** 묶어요.
- **`.dockerignore`**와 **필요 없는 패키지 설치 금지**.

## 면접 질문

<details>
<summary>Q. Docker 이미지와 컨테이너의 차이는 무엇인가요?</summary>

**답변(30초)** 이미지는 앱 실행에 필요한 파일을 읽기 전용 레이어로 쌓은 꾸러미이고, 컨테이너는 그 이미지 위에 쓰기 레이어를 하나 얹어서 실제로 실행한 프로세스예요. 클래스와 객체 관계처럼 이미지 하나로 컨테이너를 여러 개 띄울 수 있어요. 컨테이너 안에서 파일을 고쳐도 쓰기 레이어만 바뀌고 이미지는 그대로예요. 그래서 컨테이너를 지우면 그 변경도 사라져요.

**꼬리질문**
- Q. 컨테이너 안에서 고친 파일은 어떻게 처리되나요? → 아래 레이어 파일을 고치면 그때 쓰기 레이어로 복사해서 고쳐요(copy-on-write). 이미지 레이어는 건드리지 않아요.
- Q. 이미지에 OS가 들어 있나요? → 라이브러리·셸 같은 유저 공간 파일만 있고 커널은 없어요. 커널은 호스트 것을 함께 써요.
</details>

<details>
<summary>Q. 이미지 레이어란 무엇이고, 왜 레이어로 나누나요?</summary>

**답변(30초)** 레이어는 Dockerfile 명령 하나가 만든 파일 변경분 한 겹이에요. RUN, COPY, ADD가 레이어를 만들고, CMD나 ENV는 설정 기록만 남겨요. 레이어는 내용의 digest로 저장돼서 같은 레이어는 한 번만 저장하고 여러 이미지가 나눠 써요. 그래서 디스크를 아끼고, 레지스트리에 올리고 받을 때도 바뀐 레이어만 주고받고, 빌드할 때도 안 바뀐 레이어는 캐시로 재사용해요.

**꼬리질문**
- Q. 앞 레이어에서 만든 파일을 뒤 RUN에서 지우면 이미지가 작아지나요? → 아니에요. 앞 레이어에 그대로 남아요. 설치와 정리는 같은 RUN에서 해요.
</details>

<details>
<summary>Q. Docker 빌드 캐시는 언제 깨지고, 빌드를 빠르게 하려면 어떻게 하나요?</summary>

**답변(30초)** 각 명령은 이전 레이어와 명령이 같으면 캐시를 써요. RUN은 명령 문자열을, COPY는 파일 내용을 비교해요. 한 번 캐시가 깨지면 그 아래 명령은 전부 다시 실행돼요. 그래서 잘 안 바뀌는 의존성 목록을 먼저 COPY해서 설치하고, 자주 바뀌는 소스는 나중에 COPY해요. 실험에서 이 순서만 바꿔도 소스 한 글자 수정 후 재빌드가 약 1.78초에서 0.22초로 줄었어요.

**꼬리질문**
- Q. `RUN apt-get update`를 따로 두면 왜 문제죠? → 명령 문자열이 같아서 오래된 패키지 목록이 계속 캐시돼요. install과 같은 RUN에 묶어요.
- Q. `.dockerignore`는 왜 쓰나요? → 빌드 컨텍스트에서 `.git`·`.env` 같은 파일을 빼서 빌드를 빠르게 하고, 상관없는 변경이 캐시를 깨거나 비밀 파일이 이미지에 들어가는 걸 막아요.
</details>

<details>
<summary>Q. CMD와 ENTRYPOINT의 차이는 무엇인가요?</summary>

**답변(30초)** 둘 다 컨테이너 시작 명령을 정하지만, `docker run`에 인자를 줬을 때 다르게 동작해요. CMD는 인자가 오면 통째로 바뀌고, ENTRYPOINT는 그대로 남은 채 인자가 뒤에 붙어요. 그래서 보통 ENTRYPOINT에 고정 실행 파일을, CMD에 바꿀 수 있는 기본 인자를 둬요. ENTRYPOINT까지 바꾸려면 `--entrypoint` 옵션을 써요.

**꼬리질문**
- Q. exec form을 권장하는 이유는요? → shell form은 `/bin/sh -c`로 감싸서 sh가 PID 1이 돼요. 그러면 `docker stop`의 SIGTERM이 앱에 안 갈 수 있어서 정상 종료를 못 할 수 있어요.
- Q. shell form ENTRYPOINT에 run 인자를 주면요? → 인자가 무시돼요. 실험에서도 인자를 줘도 원래 출력만 나왔어요.
</details>

<details>
<summary>Q. 멀티 스테이지 빌드란 무엇이고 왜 쓰나요?</summary>

**답변(30초)** Dockerfile에서 FROM을 여러 번 써서 빌드 단계와 실행 단계를 나누고, `COPY --from`으로 빌드 결과물만 최종 이미지에 가져오는 방법이에요. 컴파일러나 빌드 도구는 실행에 필요 없으니 최종 이미지에서 빠져요. 실험에서 Go 앱이 단일 스테이지 407MB에서 멀티 스테이지 3.41MB로 줄었어요. 크기가 작아지면 배포가 빨라지고, 이미지 안 도구가 적어 공격 표면도 줄어요.

**꼬리질문**
- Q. 멀티 스테이지면 이미지가 여러 개 생기나요? → 최종 이미지는 하나예요. 앞 스테이지는 빌드 재료로만 쓰여요.
- Q. 스프링 부트는 어떻게 하나요? → JDK 단계에서 jar를 빌드하고 레이어별로 풀어서, JRE 단계로 dependencies부터 application 순서로 COPY해요. 또는 `bootBuildImage`로 Dockerfile 없이 만들어요.
</details>

<details>
<summary>Q. 태그와 digest의 차이는 무엇이고, 운영 배포에 latest를 쓰면 왜 위험한가요?</summary>

**답변(30초)** 태그는 사람이 붙인 이름표라서 게시자가 다른 이미지로 옮길 수 있고, digest는 내용으로 계산한 지문이라 바뀌지 않아요. latest는 "최신"이라는 뜻이 아니라 태그를 안 쓰면 붙는 기본 이름일 뿐이에요. 그래서 latest로 배포하면 언제 받았느냐에 따라 다른 이미지가 뜰 수 있고, 어떤 버전이 돌고 있는지 추적하기도 어려워요. 운영에서는 버전 태그를 쓰고, 정확히 고정하려면 digest를 써요.

**꼬리질문**
- Q. digest로 고정하면 단점은요? → 베이스 이미지 보안 패치가 자동으로 안 들어와요. 갱신을 일부러 해 줘야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 코드 한 줄만 고쳤는데도 CI에서 Docker 이미지 빌드가 매번 5분씩 걸립니다. Dockerfile은 `COPY . .` 다음에 `./gradlew build`를 실행합니다.</summary>

**상황 파악**
코드 한 줄 수정인데 매번 오래 걸린다면, 빌드 캐시가 거의 안 쓰이고 있다는 신호예요. 먼저 빌드 로그(`--progress=plain`)에서 어느 단계가 `CACHED`이고 어느 단계가 다시 실행되는지 봐요. 보통 의존성 다운로드 단계가 다시 돌고 있어요.

**원인 후보**
1. **레이어 순서**: `COPY . .`가 먼저라서 소스 한 글자만 바뀌어도 이 레이어 캐시가 깨지고, 그 아래 `./gradlew build`(의존성 다운로드 포함)가 전부 다시 실행돼요.
2. **빌드 컨텍스트**: `.dockerignore`가 없어서 `.git`이나 `build/` 같은 상관없는 파일 변경도 `COPY . .` 캐시를 깨요.
3. **CI 환경**: CI 러너가 매번 새 머신이면 로컬 캐시 자체가 없어서, 순서를 고쳐도 처음부터 빌드해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 의존성 파일(`build.gradle`, `settings.gradle`, `gradle/`)을 먼저 COPY해서 의존성만 받고, 소스는 나중에 COPY | Dockerfile 몇 줄만 바꾸면 됨. 소스만 바뀌면 의존성 단계는 CACHED | 의존성이 바뀌면 여전히 다시 받음 |
| B. 스프링 부트 layered jar로 풀어서 `dependencies` → `application` 순으로 COPY | 실행 이미지에서도 라이브러리 레이어가 그대로라 push·pull 양이 줄어듦 | Dockerfile이 조금 길어짐 |
| C. CI에서 레지스트리에 빌드 캐시를 저장하고 다시 불러오기(`--cache-from`, `--cache-to`) | 새 머신에서도 캐시를 씀 | 캐시 저장 공간 비용. 캐시가 오래되면 보안 패치가 빠질 수 있음 |

**내가 고를 방법**
A부터 해요. 원인이 순서라면 가장 적은 변경으로 가장 큰 효과가 나요. `.dockerignore`도 함께 추가해요. CI 러너가 매번 새 머신이라 그래도 느리면 C를 더해요. 캐시가 오래되는 문제는 주기적으로 `--pull --no-cache` 빌드를 돌려서 막아요. 적용 후 빌드 로그에서 의존성 단계가 `CACHED`로 나오는지, 빌드 시간이 줄었는지 확인해요.

**채점 포인트**: 빌드 로그로 CACHED 여부 확인, 한 레이어 캐시가 깨지면 아래는 전부 재실행, 잘 안 바뀌는 것 위·자주 바뀌는 것 아래, 의존성 파일 먼저 COPY, `.dockerignore`, CI 러너의 캐시 부재와 원격 캐시, 오래된 캐시의 보안 패치 문제와 주기적 재빌드.
</details>

<details>
<summary>상황: 스프링 부트 서비스의 운영 이미지가 1GB가 넘어서 배포할 때 이미지를 받는 데 오래 걸리고, 서버 디스크도 금방 찹니다.</summary>

**상황 파악**
스프링 부트 jar 자체는 보통 수십 MB라서, 1GB가 넘는다면 jar 말고 **다른 게 이미지에 많이 들어 있다**는 뜻이에요. `docker history`로 어느 레이어가 큰지 먼저 봐요.

**원인 후보**
1. **빌드 도구가 그대로 남음**: JDK와 Gradle 캐시, 소스가 든 단계에서 빌드하고 그 이미지를 그대로 실행해요. 실행에는 JRE와 jar만 있으면 돼요.
2. **큰 베이스 이미지**: 패키지가 잔뜩 든 일반 OS 이미지를 베이스로 써요.
3. **불필요한 파일**: `.dockerignore`가 없어 `.git`, `build/` 같은 게 들어가거나, 설치 후 정리를 다른 RUN에서 해서 앞 레이어에 파일이 남아 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 멀티 스테이지: 빌드는 JDK 단계, 실행은 JRE 단계에 jar(또는 풀어 둔 레이어)만 COPY | 빌드 도구가 통째로 빠져 크기가 크게 줌. 공격 표면도 줄어듦 | Dockerfile이 길어짐 |
| B. 더 작은 베이스 이미지(slim, alpine, distroless) | 베이스 크기 자체가 줄어듦 | 셸이 없는 이미지는 `docker exec`로 들어가 디버깅하기 어려움. 일부 라이브러리 호환성을 확인해야 함 |
| C. `.dockerignore` 추가, 설치와 정리를 같은 RUN에 | 작은 변경으로 쓸데없는 파일 제거 | 단독으로는 효과가 제한적 |

**내가 고를 방법**
A를 먼저 해요. 1GB의 대부분은 실행에 필요 없는 빌드 도구일 가능성이 커서 효과가 가장 커요. C는 비용이 거의 없으니 같이 해요. B는 그다음에, 셸 없이도 운영할 수 있는지(로그·모니터링으로 충분한지) 팀과 확인한 뒤 적용해요. 적용 후 `docker images`로 크기를 다시 재고, 배포 시간이 줄었는지 봐요. 레이어별로 COPY해 두면 코드만 바뀔 때 서버가 받는 양도 작아져요.

**채점 포인트**: `docker history`로 큰 레이어 확인, 빌드 환경과 실행 환경 분리(멀티 스테이지, JDK 대 JRE), `COPY --from`, 작은 베이스 이미지와 디버깅 트레이드오프, 뒤 레이어에서 지워도 앞 레이어에 남음, `.dockerignore`, 레이어 재사용으로 pull 양 감소.
</details>

<details>
<summary>상황: `myapp:latest`로 서버 여러 대에 배포했더니, 서버마다 다른 버전의 앱이 돌고 있습니다.</summary>

**상황 파악**
같은 이름으로 배포했는데 결과가 다르다면, **이름은 같지만 가리키는 이미지가 달랐던 것**이에요. 서버마다 실제로 돌고 있는 이미지의 digest를 비교해서 정말 다른 이미지인지부터 확인해요.

**원인 후보**
1. **태그가 움직임**: `latest`는 "최신"이라는 뜻이 아니라 이름표일 뿐이고, 새 이미지를 올리면 같은 태그가 새 이미지를 가리켜요. 서버마다 이미지를 받은 시점이 다르면 서로 다른 이미지를 갖게 돼요.
2. **이미 받아 둔 이미지를 씀**: 어떤 서버는 예전에 받은 `latest`가 남아 있어 새로 받지 않고 그걸 실행했을 수 있어요.
3. **추적 불가**: 태그만으로는 어떤 커밋으로 만든 이미지인지 알 수 없어서 문제를 늦게 알아챘어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 빌드마다 고유한 태그(버전 번호나 커밋 해시)를 붙이고 그 태그로 배포 | 읽기 쉽고, 어떤 커밋인지 바로 앎. 롤백할 때도 태그만 바꾸면 됨 | 태그도 이름표라 누가 같은 태그를 덮어쓰면 다시 달라질 수 있음 |
| B. digest(`@sha256:...`)로 배포 | 내용 지문이라 모든 서버가 정확히 같은 이미지를 받음 | 사람이 읽기 어려움. 태그와 digest를 함께 기록해 둬야 함 |

같은 원리로 Dockerfile의 `FROM`도 digest로 고정하면 "어제와 같은 Dockerfile인데 오늘 빌드한 이미지가 다르다"는 문제도 막을 수 있어요. 대신 베이스 이미지 보안 패치가 자동으로 안 들어오니, 갱신은 일부러 해 줘야 해요.

**내가 고를 방법**
A와 B를 같이 써요. CI가 빌드할 때마다 커밋 해시 태그를 붙여 올리고, 배포에는 그 이미지의 digest를 기록해서 사용해요. 사람은 태그로 읽고, 서버는 digest로 정확히 같은 이미지를 받는 구조예요. 운영 배포에서는 `latest`를 쓰지 않아요. 적용 후 모든 서버에서 실행 중인 이미지의 digest가 같은지 확인해요.

**채점 포인트**: latest는 기본 태그 이름일 뿐 최신을 보장하지 않음, 태그는 옮겨질 수 있음, digest는 내용 기반이라 불변, 서버마다 받은 시점 차이, 고유 버전 태그로 추적·롤백, digest 고정, 베이스 이미지 고정 시 보안 패치 갱신 필요.
</details>

## 필기 포인트

- 레이어를 만드는 명령: `RUN`, `COPY`, `ADD`. `CMD`·`ENV`·`EXPOSE`는 설정 기록만(0B).
- `RUN`은 **빌드할 때**, `CMD`·`ENTRYPOINT`는 **컨테이너 시작할 때** 실행.
- `CMD`가 여러 개면 **마지막 것만** 유효.
- `docker run` 인자는 **CMD를 대체**, ENTRYPOINT 뒤에 붙음. ENTRYPOINT 교체는 `--entrypoint`.
- exec form = JSON 배열, 셸 없음, `$VAR` 치환 안 함. shell form = `/bin/sh -c`로 실행.
- `EXPOSE`는 문서용. 실제 포트 연결은 `-p`.
- `ADD`는 로컬 tar 자동 해제·URL 다운로드 가능. 보통은 `COPY` 권장.
- `ENV`는 실행 중에도 남음, `ARG`는 빌드할 때만.
- RUN 캐시는 명령 문자열 비교, COPY 캐시는 파일 내용·권한 비교(수정 시각 무시).
- 태그 생략 시 `latest`, 레지스트리 생략 시 `docker.io`, 네임스페이스 생략 시 `library`.
