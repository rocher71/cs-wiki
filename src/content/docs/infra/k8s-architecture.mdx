쿠버네티스는 **컨트롤 플레인**(클러스터 전체를 결정하는 두뇌)과 **노드**(실제 컨테이너가 도는 서버)로 나뉘어요. 내가 "이 앱을 3개 띄워 줘"라고 **원하는 상태**를 적으면, 컨트롤러들이 현재 상태와 비교해 차이를 계속 메우는 **조정 루프**로 동작해요.
:::

## 쉽게 이해하기

컨테이너 하나는 [컨테이너와 VM](../container-vs-vm/)에서 본 것처럼 가볍게 띄울 수 있어요. 그런데 서버가 수십 대, 컨테이너가 수백 개가 되면 "어디에 띄우지?", "죽으면 누가 다시 띄우지?"를 사람이 다 챙길 수 없어요.

쿠버네티스는 **프랜차이즈 회사**라고 생각하면 쉬워요.

- **본사(컨트롤 플레인)**: "매장 직원은 지점마다 3명"처럼 목표를 정하고, 어느 지점에 사람을 보낼지 결정해요. 본사는 직접 커피를 만들지 않아요.
- **장부(etcd)**: 본사가 정한 목표와 각 지점 현황을 적어 두는 공식 장부예요. 장부가 사라지면 회사가 뭘 하고 있었는지 아무도 몰라요.
- **지점(노드)**: 실제로 커피를 만드는 곳이에요. 지점마다 **점장(kubelet)**이 있어서 "본사가 우리 지점에 배정한 일"이 제대로 돌아가는지 챙겨요.
- **창구(API 서버)**: 본사의 모든 연락은 이 창구 하나를 거쳐요. 누구도 장부에 직접 손대지 않고 창구에 요청해요.

핵심은 본사가 "직원 3명이 있어야 한다"는 **목표**만 장부에 적어 둔다는 점이에요. 한 명이 그만두면 누가 시키지 않아도 "3명이어야 하는데 2명이네" 하고 1명을 새로 뽑아요.

단, 실제로는 본사 담당자들이 한 명의 사장에게 순서대로 지시받는 구조가 아니에요. 담당자 여럿이 각자 맡은 일만 보면서 장부를 보고 따로따로 움직여요. 이게 아래에서 볼 **조정 루프**예요.

## 제대로 알기

### 1. 왜 쿠버네티스 같은 게 필요할까

서버 몇 대에 `docker run`으로 컨테이너를 직접 띄우면 이런 일을 사람이 해야 해요.

- 컨테이너가 죽으면 알아채고 다시 띄우기
- 새 버전을 배포할 때 서버마다 들어가서 하나씩 교체하기
- 트래픽이 몰리면 컨테이너 늘리기, 어느 서버에 여유가 있는지 계산하기
- 컨테이너 주소가 바뀔 때마다 다른 서비스에 알려 주기

쿠버네티스는 이런 일을 여러 서버에 걸쳐 자동으로 해 줘요. 공식 문서가 꼽는 기능은 다음과 같아요.

| 기능 | 뜻 |
|---|---|
| 자가 치유 | 죽은 컨테이너를 재시작하고, 헬스체크에 실패한 컨테이너를 교체해요 |
| 자동 롤아웃·롤백 | 원하는 버전을 적으면 정해진 속도로 바꾸고, 문제가 있으면 되돌려요 |
| 자동 빈 패킹 | 컨테이너가 필요한 CPU·메모리를 보고 알맞은 노드에 배치해요 |
| 서비스 발견·로드밸런싱 | 컨테이너를 DNS 이름이나 IP로 노출하고 트래픽을 나눠요 |
| 수평 스케일 | 명령이나 CPU 사용량에 따라 개수를 늘리고 줄여요 |
| 설정·Secret 관리 | 이미지를 다시 빌드하지 않고 설정과 비밀값을 바꿔요 |

반대로 쿠버네티스가 **하지 않는 것**도 있어요. 소스 코드를 빌드하는 일(CI/CD는 바깥 도구 몫), DB·캐시 같은 서비스를 기본 제공하는 일, 서버 머신 자체를 관리하는 일은 하지 않아요. 공식 문서는 쿠버네티스를 완성된 플랫폼이 아니라 "빌딩 블록"이라고 불러요.

### 2. 클러스터 = 컨트롤 플레인 + 노드

**클러스터**(cluster, 하나로 묶여 관리되는 서버 무리)는 두 부분으로 나뉘어요.

- **컨트롤 플레인**(control plane): 스케줄링 같은 클러스터 전체 결정을 내리고, "Pod가 모자라다" 같은 이벤트에 대응해요.
- **노드**(node, 워커 노드): 실제 앱이 도는 서버예요. 앱을 돌리려면 노드가 최소 1대 있어야 해요.

**Pod**(파드)는 쿠버네티스가 컨테이너를 띄우는 가장 작은 단위예요. 지금은 "컨테이너 1개 이상을 감싼 포장"으로 생각하면 충분해요. → [Pod와 Deployment](../k8s-pod-deployment/)

설치 도구는 보통 컨트롤 플레인 구성요소를 앱 컨테이너를 돌리지 않는 머신 한 대에 모아 둬요. 운영 환경에서는 컨트롤 플레인을 여러 머신에 나눠 두어 한 대가 죽어도 버티게 해요(**고가용성**, high availability).

### 3. 구성요소 한눈에 보기

| 위치 | 구성요소 | 비유 | 하는 일 |
|---|---|---|---|
| 컨트롤 플레인 | **kube-apiserver** | 창구 | 쿠버네티스 API를 여는 핵심 서버. 사용자·구성요소·외부 도구가 모두 여기로 통신해요 |
| 컨트롤 플레인 | **etcd** | 장부 | 클러스터의 모든 데이터를 담는 키-값 저장소. 원본 데이터라 백업이 필수예요 |
| 컨트롤 플레인 | **kube-scheduler** | 인사 배치 담당 | 아직 노드가 안 정해진 Pod에 알맞은 노드를 골라 줘요 |
| 컨트롤 플레인 | **kube-controller-manager** | 목표 관리 담당들 | 컨트롤러들을 돌려 원하는 상태를 맞춰요 |
| 컨트롤 플레인 | cloud-controller-manager (선택) | 외부 업체 담당 | AWS·GCP 같은 클라우드와 연동해요. 로컬에선 없을 수 있어요 |
| 노드 | **kubelet** | 점장 | 자기 노드에 배정된 Pod의 컨테이너가 실제로 돌고 있는지 챙겨요 |
| 노드 | kube-proxy (선택) | 전화 교환 규칙 | 노드의 네트워크 규칙을 유지해 Service를 구현해요 |
| 노드 | **컨테이너 런타임** | 실제 직원 | 컨테이너를 실제로 실행해요. 예: containerd, CRI-O |

몇 가지만 더 짚을게요.

- **kube-apiserver**: `kubectl`(쿠버네티스 명령줄 도구)도 결국 이 API를 HTTP로 부르는 클라이언트예요. API 서버는 여러 개 띄워 부하를 나눌 수 있어요.
- **kube-scheduler**는 Pod를 **실행하지 않아요.** "이 Pod는 3번 노드"라는 결정만 API 서버에 기록해요. 고르는 순서는 **필터링**(못 돌리는 노드 빼기) → **스코어링**(남은 노드 점수 매기기) → 최고점 노드에 **바인딩**(배정 기록)이에요. 맞는 노드가 하나도 없으면 Pod는 **Pending**(대기) 상태로 남고 계속 다시 시도해요.
- **컨트롤러**도 컨테이너를 직접 띄우지 않아요. "Pod를 만들어라/지워라"를 API 서버에 요청할 뿐이에요.
- **컨테이너 런타임**은 **CRI**(Container Runtime Interface, kubelet과 런타임이 대화하는 표준 규격)를 지켜야 해요. 예전에 쿠버네티스 안에 있던 Docker 연동 코드(**dockershim**)는 v1.24에서 제거됐어요. Docker Engine을 쓰려면 cri-dockerd라는 어댑터를 거쳐야 해요. → [컨테이너 런타임](../docker-runtime/)
- **kube-proxy**가 "선택"인 이유는 일부 네트워크 플러그인이 그 일을 대신하기 때문이에요. → [Service와 Ingress](../k8s-service-ingress/)

<Aside type="tip" title="etcd는 왜 3대, 5대처럼 홀수로 둘까">
etcd는 **Raft**라는 합의 알고리즘(여러 서버가 같은 값에 동의하는 방법)을 써요. 전체 n대 중 과반((n/2)+1대)이 동의해야 쓰기가 돼요. 3대면 1대, 5대면 2대가 죽어도 버텨요. 4대는 과반이 3대라 3대와 똑같이 1대까지만 버텨서, 짝수는 서버만 늘고 이득이 없어요. 공식 FAQ는 7대 이하를 권장해요. Raft 자체는 분산 섹션에서 따로 다룰 예정이에요.
</Aside>

### 4. 모두 API 서버를 거친다 (허브-앤-스포크)

스케줄러, 컨트롤러, kubelet은 **서로 직접 말하지 않아요.** 노드에서 나가는 모든 API 요청은 API 서버에서 끝나고, 다른 컨트롤 플레인 구성요소는 바깥에 서비스를 열지 않도록 설계돼 있어요. 바퀴 가운데 축(허브)에 살(스포크)이 다 모이는 모양이라 **허브-앤-스포크**(hub-and-spoke)라고 불러요.

그럼 구성요소들은 변화를 어떻게 알까요? 계속 "바뀐 거 있어?" 하고 묻는(**폴링**, polling) 대신, API의 **watch**로 변경 내용을 흐름(스트림)으로 받아요. "새 Pod가 생기면 알려 줘"라고 구독해 두는 셈이에요.

반대 방향(API 서버 → kubelet) 연결도 있어요. `kubectl logs`, `kubectl exec`, `kubectl port-forward`처럼 특정 노드의 컨테이너를 들여다볼 때 쓰여요.

### 5. kubectl apply부터 컨테이너 실행까지

`replicas: 3`(복제본 3개)짜리 앱을 배포하는 흐름이에요. 위 첫 번째 그림과 같은 순서예요.

1. 개발자가 `kubectl apply -f deploy.yaml`을 실행 → kubectl이 API 서버에 요청해요.
2. API 서버가 요청자가 누구인지, 권한이 있는지, 내용이 올바른지 확인한 뒤 **etcd에 저장**해요.
3. controller-manager 안의 컨트롤러들이 watch로 새 오브젝트를 감지해요. 정확히는 Deployment 컨트롤러가 먼저 **ReplicaSet**(Pod 개수를 지키는 오브젝트)을 만들고, ReplicaSet 컨트롤러가 "Pod 3개 필요, 현재 0개"를 보고 Pod 3개 생성을 API 서버에 요청해요. 이때 Pod에는 아직 노드가 정해지지 않았어요. (ReplicaSet 세부는 [Pod와 Deployment](../k8s-pod-deployment/)에서 봐요.)
4. 스케줄러가 "노드 미정 Pod"를 감지 → 필터링·스코어링으로 노드를 골라 API 서버에 기록해요.
5. 그 노드의 kubelet이 "내 노드에 배정된 Pod"를 감지 → CRI로 컨테이너 런타임에 실행을 맡겨요. 런타임이 이미지를 받아 컨테이너를 띄워요.
6. kubelet이 Pod 상태를 API 서버에 보고하고, 그 상태가 etcd에 저장돼요.

**결정하는 쪽(스케줄러·컨트롤러)과 실행하는 쪽(kubelet·런타임)이 나뉘어 있고, 둘은 API 서버에 적힌 기록으로만 이어져요.**

### 6. 선언형과 조정 루프

#### spec과 status

쿠버네티스의 **오브젝트**(object, Deployment·Pod처럼 클러스터에 저장되는 기록 하나)는 "이 상태를 유지해 달라"는 **의도의 기록**이에요. 오브젝트에는 두 칸이 있어요.

- **spec**: 원하는 상태. 내가 적어요. (예: replicas 3)
- **status**: 현재 상태. 쿠버네티스가 채우고 갱신해요.

`kubectl create deployment web --image=nginx:1.27 --replicas=3 --dry-run=client -o yaml`로 서버에 보내지 않고 YAML만 뽑아 보면, 끝에 `status: {}`가 비어 있어요. status는 내가 아니라 클러스터가 채운다는 걸 볼 수 있어요.

```yaml
apiVersion: apps/v1   # 어떤 API 버전인지
kind: Deployment      # 어떤 종류의 오브젝트인지
metadata:
  name: web           # 이름
spec:                 # 원하는 상태 (내가 쓴다)
  replicas: 3
  # ... (selector, template 생략)
status: {}            # 현재 상태 (쿠버네티스가 채운다)
```

`apiVersion`, `kind`, `metadata`, `spec` 네 개는 매니페스트(오브젝트를 적은 YAML 파일)의 필수 최상위 필드예요.

#### 조정 루프(control loop)

**컨트롤러**(controller)는 **조정 루프**를 도는 프로그램이에요. 공식 문서는 온도조절기에 비유해요. 설정 온도(원하는 상태)와 실내 온도(현재 상태)를 비교해서, 차이가 나면 난방을 켜거나 꺼요. 그리고 이 비교를 끝없이 반복해요.

1. **관찰**: 현재 상태를 본다 (Pod 2개)
2. **비교**: 원하는 상태와 비교한다 (3개여야 함 → 1개 부족)
3. **조치**: 차이를 줄이도록 API 서버에 요청한다 (Pod 1개 생성)
4. 다시 1로

그래서 `kubectl delete pod`로 Pod를 지워도 곧바로 새 Pod가 생겨요. 정말 줄이려면 spec의 replicas를 바꿔야 해요.

설계 원칙도 알아 두면 좋아요.

- 거대한 루프 하나 대신, **한 가지 일만 맡는 단순한 컨트롤러 여러 개**가 돌아요.
- 컨트롤러는 **실패할 수 있다는 전제**로 만들어요. 다시 살아나면 그때의 현재 상태를 보고 이어서 맞추면 되니까요.
- 클러스터가 끝내 완벽한 안정 상태에 닿지 않아도 괜찮아요. 컨트롤러가 살아서 계속 차이를 줄이고 있으면 돼요.

<Aside type="note" title="오케스트레이션이 아니라고요?">
공식 문서는 쿠버네티스가 "단순한 오케스트레이션 시스템이 아니다"라고 말해요. 여기서 오케스트레이션은 A → B → C처럼 정해진 순서를 실행하는 걸 뜻해요. 쿠버네티스는 중앙 지휘자 없이, 독립된 컨트롤러들이 각자 현재 상태를 원하는 상태로 몰아가요. 그래서 하나가 잠깐 멈춰도 전체가 깨지지 않고 확장하기 쉬워요. 면접에서 "컨테이너 오케스트레이터"라고 불러도 되지만, 동작 원리를 설명할 땐 "조정 루프"라고 말하는 게 정확해요.
</Aside>

### 7. 명령형 vs 선언형: apply는 뭐가 다를까

| 방식 | 예 | 특징 | 권장 |
|---|---|---|---|
| 명령형 커맨드 | `kubectl create deployment nginx --image nginx` | 한 줄로 빠름. 리뷰·기록·원본 파일이 없음 | 개발·실습 |
| 명령형 오브젝트 설정 | `kubectl create -f`, `replace -f`, `delete -f` | 파일을 쓰지만 "만들어라/바꿔라"를 내가 정함 | 운영 |
| 선언형 오브젝트 설정 | `kubectl diff -f configs/` → `kubectl apply -f configs/` | 만들지·고칠지·지울지 kubectl이 판단 | 운영 |

- YAML을 쓴다고 다 선언형은 아니에요. `create -f`, `replace -f`는 명령형이에요.
- `replace`는 spec 전체를 덮어써서, 파일에 없는 필드(클러스터가 따로 쓰는 값)를 날려요.
- `apply`는 전체를 바꾸지 않고 **차이만 패치**해요. 그래서 다른 쪽에서 바꾼 필드도 지켜요. 권장 순서는 `diff`로 먼저 보고 `apply`예요.
- **한 오브젝트는 한 방식으로만** 관리해야 해요. 섞으면 동작이 정해져 있지 않아요.
- 선언형 파일을 Git에 두면 누가 언제 무엇을 바꿨는지 리뷰·기록이 남아요. GitOps(Git을 배포의 기준으로 삼는 방식)의 토대예요.

## 면접 질문

<details>
<summary>Q. 쿠버네티스는 왜 필요한가요? Docker만으로는 뭐가 부족한가요?</summary>

**답변(30초)** Docker는 컨테이너 하나를 한 서버에서 띄우는 도구라서, 서버가 여러 대가 되면 배치·복구·배포·확장을 사람이 해야 해요. 쿠버네티스는 이걸 여러 서버에 걸쳐 자동화해요. 죽은 컨테이너를 다시 띄우는 자가 치유, 무중단 롤아웃과 롤백, 자원에 맞춘 노드 배치, 서비스 발견과 로드밸런싱, 수평 스케일을 해 줘요. 저는 "원하는 상태를 적으면 그 상태를 계속 지켜 주는 시스템"이라고 이해하고 있어요.

**꼬리질문**
- Q. 쿠버네티스가 안 해 주는 건요? → 소스 빌드·CI/CD, DB 같은 앱 서비스 제공, 서버 머신 관리는 하지 않아요. 빌딩 블록이에요.
- Q. 작은 서비스에도 꼭 써야 하나요? → 운영 복잡도와 학습 비용이 커서, 서버 몇 대 규모면 매니지드 서비스나 더 단순한 도구가 나을 수 있어요.
</details>

<details>
<summary>Q. 쿠버네티스 아키텍처를 설명해 주세요.</summary>

**답변(30초)** 컨트롤 플레인과 워커 노드로 나뉘어요. 컨트롤 플레인에는 모든 요청의 창구인 API 서버, 클러스터 데이터를 저장하는 etcd, Pod를 둘 노드를 고르는 스케줄러, 원하는 상태를 맞추는 컨트롤러 매니저가 있어요. 노드에는 배정된 Pod를 실제로 띄우는 kubelet, Service 네트워크 규칙을 관리하는 kube-proxy, 컨테이너를 실행하는 런타임이 있어요. 구성요소끼리는 직접 통신하지 않고 모두 API 서버를 거쳐요.

**꼬리질문**
- Q. kubelet과 kube-proxy 차이는요? → kubelet은 Pod의 컨테이너가 제대로 도는지 챙기고, kube-proxy는 Service로 가는 트래픽의 네트워크 규칙을 관리해요.
- Q. etcd에 직접 접근하는 건 누구죠? → etcd는 API 서버의 저장소예요. 다른 구성요소는 API 서버를 통해 상태를 읽고 써요.
</details>

<details>
<summary>Q. kubectl apply 후 Pod가 뜨기까지 무슨 일이 일어나나요?</summary>

**답변(30초)** kubectl이 API 서버에 요청하면, API 서버가 인증·인가·검증을 하고 etcd에 저장해요. 컨트롤러가 watch로 이를 감지해 필요한 Pod 생성을 요청하고, 스케줄러가 노드가 안 정해진 Pod에 노드를 골라 기록해요. 그 노드의 kubelet이 자기에게 배정된 Pod를 보고 컨테이너 런타임에 실행을 맡겨요. 마지막으로 kubelet이 상태를 API 서버에 보고해요.

**꼬리질문**
- Q. 스케줄러가 컨테이너를 띄우나요? → 아니에요. 노드만 정해서 API 서버에 기록하고, 실행은 kubelet과 런타임이 해요.
- Q. Pod가 계속 Pending이면요? → 스케줄러가 조건에 맞는 노드를 못 찾은 경우가 많아요. `kubectl describe pod`의 Events에서 이유를 봐요. 요청한 CPU·메모리가 너무 큰지 확인해요.
</details>

<details>
<summary>Q. 선언형과 조정 루프(reconciliation)를 설명해 주세요.</summary>

**답변(30초)** 선언형은 "어떻게 할지" 대신 "어떤 상태여야 하는지"를 적는 방식이에요. 오브젝트의 spec에 원하는 상태를 적으면, 쿠버네티스가 현재 상태를 status에 채워요. 컨트롤러는 둘을 끝없이 비교해서 차이를 줄이는 조정 루프를 돌아요. 그래서 replicas가 3인데 Pod 하나가 죽으면 누가 시키지 않아도 하나를 새로 만들어요.

**꼬리질문**
- Q. `kubectl apply`와 `create`/`replace` 차이는요? → create·replace는 내가 동작을 정하는 명령형이고, replace는 전체를 덮어써요. apply는 kubectl이 생성·패치를 판단하고 차이만 패치해요.
- Q. Pod를 delete했는데 다시 생겨요. → 조정 루프가 원하는 개수를 맞춘 거예요. 줄이려면 replicas를 바꿔야 해요.
</details>

<details>
<summary>Q. etcd는 무엇이고, 왜 홀수 대로 구성하나요?</summary>

**답변(30초)** etcd는 클러스터의 모든 상태를 담는 키-값 저장소라서, 백업이 꼭 필요한 클러스터의 원본 데이터예요. Raft 합의 알고리즘을 써서 과반이 동의해야 쓰기가 돼요. 3대는 1대, 5대는 2대 장애를 견디는데, 4대는 과반이 3대라 3대와 똑같이 1대까지만 견뎌요. 그래서 짝수는 비용만 늘어 홀수를 권장해요.

**꼬리질문**
- Q. 많이 둘수록 좋나요? → 아니에요. 공식 FAQ는 7대 이하를 권장해요. 보통 3대나 5대로 둬요.
</details>

## 서술형 연습

<details>
<summary>상황: 서버 30대에 서비스 컨테이너 수십 개를 docker run으로 직접 배포하고 있습니다. 새벽에 서버 한 대가 죽으면 당직자가 수동으로 다른 서버에 띄우고, 배포 때마다 ssh로 한 대씩 교체하며, 트래픽이 몰리면 손으로 늘립니다. 어떻게 개선하겠습니까?</summary>

**상황 파악**
문제는 사람이 "현재 상태를 보고 원하는 상태로 맞추는 일"을 손으로 하고 있다는 점이에요. 서버가 늘수록 장애 복구가 느려지고, 배포 중 실수가 나고, 어느 서버에 뭐가 떠 있는지 기록이 흩어져요.

**원인 후보**
1. 죽은 컨테이너를 감지하고 다시 띄우는 자동화가 없어요(자가 치유 부재).
2. 배포가 서버별 수작업이라 순서·속도·롤백이 사람에게 달려 있어요.
3. 어느 서버에 자원이 남았는지 사람이 계산해서 배치해요.
4. 컨테이너 위치가 바뀌면 다른 서비스가 새 주소를 알 방법이 없어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 스크립트·설정 관리 도구로 현재 방식을 자동화 | 지금 구조를 크게 안 바꿈, 도입이 빠름 | 장애 감지·재배치·롤백을 직접 다 만들어야 하고, 스크립트가 계속 불어남 |
| B. 쿠버네티스 도입 (가능하면 클라우드 매니지드) | 원하는 상태를 선언하면 조정 루프가 자가 치유, 자원 기준 배치, 롤링 배포·롤백, 서비스 발견, 수평 스케일을 해 줌. YAML을 Git에 두어 변경 기록이 남음 | 학습 비용과 운영 복잡도가 큼. 컨트롤 플레인·etcd 운영(직접 설치 시)과 백업 부담 |
| C. 더 단순한 매니지드 컨테이너 서비스 | 쿠버네티스보다 배우기 쉬움 | 기능과 확장성이 제한적이고 특정 클라우드에 묶이기 쉬움 |

**내가 고를 방법**
서버 30대, 컨테이너 수십 개 규모라면 B를 골라요. 지금 사람이 하는 일이 바로 쿠버네티스 조정 루프가 하는 일이라서, 수작업을 "원하는 상태 선언"으로 바꾸는 게 근본 해결이에요. 컨트롤 플레인 운영 부담은 매니지드 서비스로 줄이고, 매니페스트는 Git에 두고 `diff` 후 `apply`하는 흐름으로 바꿔요. 한 번에 다 옮기지 않고 상태가 없는 서비스부터 옮기면서, 서버 한 대를 꺼도 Pod가 다른 노드에서 다시 뜨는지 확인해요. 규모가 훨씬 작다면 C도 충분해요.

**채점 포인트**: 수작업 = 현재 상태를 원하는 상태로 맞추는 일, 자가 치유, 롤링 배포·롤백, 자원 기준 스케줄링, 서비스 발견, 수평 스케일, 선언형 설정과 Git 기록, 도입 비용·운영 복잡도 트레이드오프, 매니지드로 컨트롤 플레인 부담 감소, 단계적 이전과 검증.
</details>

<details>
<summary>상황: 운영 중인 쿠버네티스 클러스터에서 컨트롤 플레인이 응답하지 않습니다(kubectl 명령이 전부 실패). 지금 서비스 사용자에게 어떤 영향이 있을지, 어떻게 대응하겠습니까?</summary>

**상황 파악**
먼저 "결정하는 쪽"과 "실행하는 쪽"을 나눠서 생각해요. 컨테이너를 실제로 돌리는 건 각 노드의 kubelet과 컨테이너 런타임이고, 스케줄링·자가 치유·스케일은 컨트롤러와 스케줄러가 API 서버를 거쳐 하는 일이에요. 이 구조에서 일반적으로 추론하면, 이미 노드에서 돌던 컨테이너는 곧바로 멈추지는 않을 가능성이 커요. 대신 **새로 결정해야 하는 일**이 멈춰요. 다만 정확한 영향은 클러스터 구성과 네트워크 플러그인, 장애가 얼마나 길어지는지에 따라 달라서 단정하지 않고 확인부터 해요.

**원인 후보와 영향 추정**
1. API 서버 장애: 모든 구성요소가 API 서버를 거치므로 배포·스케일·Pod 교체 같은 변경이 막혀요. kubelet도 상태를 보고하지 못해요.
2. etcd 장애나 과반 상실(예: 3대 중 2대 다운): 쓰기가 안 되어 클러스터 상태를 바꿀 수 없어요.
3. 컨트롤 플레인 머신이 1대뿐인 구성: 그 한 대가 죽으면 위 기능이 통째로 멈춰요.
4. 이 상태에서 Pod가 죽거나 노드가 죽으면, 원래라면 조정 루프가 다시 띄웠을 텐데 그 복구가 일어나지 않을 수 있어요. 트래픽이 몰려도 자동으로 늘어나지 않아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 당장: 사용자 트래픽이 실제로 실패하는지부터 확인하고 변경(배포) 동결, 컨트롤 플레인 복구 | 실제 영향 범위를 확인하고, 상황을 더 꼬이게 하지 않음 | 복구 전까지 자가 치유·스케일이 없어서 그 사이 장애가 겹치면 위험 |
| B. etcd 백업으로 복원 | 상태가 깨졌을 때 되돌릴 유일한 방법 | 백업 이후 변경은 사라짐. 백업이 없으면 쓸 수 없음 |
| C. 재발 방지: 컨트롤 플레인과 etcd를 여러 머신(etcd는 3·5대 홀수)으로 다중화, 또는 매니지드 컨트롤 플레인 사용 | 한 대가 죽어도 계속 동작 | 머신 비용과 운영 복잡도 증가 |

**내가 고를 방법**
먼저 A로 사용자 영향을 실제로 확인하고 배포를 멈춘 뒤 컨트롤 플레인 복구에 집중해요. 데이터가 손상됐다면 B로 etcd를 복원해요. 근본 대책은 C예요. 운영 클러스터라면 컨트롤 플레인과 etcd를 홀수 대로 다중화하고, etcd 백업과 복원 연습을 정기적으로 해요. 직접 운영할 여력이 없다면 매니지드 컨트롤 플레인을 써서 이 부담을 클라우드에 넘기는 것도 좋은 선택이에요.

**채점 포인트**: 실행(kubelet·런타임)과 결정(스케줄러·컨트롤러) 분리, 모든 통신이 API 서버 경유, 새 스케줄링·자가 치유·스케일이 멈출 수 있음, 영향은 단정하지 않고 확인, etcd 과반(Raft)과 홀수 대수, etcd 백업, 컨트롤 플레인 고가용성, 장애 중 변경 동결.
</details>

## 필기 포인트

- 클러스터 = **컨트롤 플레인** + **노드**. 앱 Pod는 노드에서 돈다.
- 컨트롤 플레인: kube-apiserver, etcd, kube-scheduler, kube-controller-manager, (선택) cloud-controller-manager.
- 노드: **kubelet**, (선택) kube-proxy, 컨테이너 런타임.
- 스케줄러는 노드만 정한다(필터링 → 스코어링 → 바인딩). 실행은 kubelet.
- **spec** = 원하는 상태(사용자), **status** = 현재 상태(시스템).
- 매니페스트 필수 필드: apiVersion, kind, metadata, spec.
- 컨트롤러 = 조정 루프(control loop). 비유는 온도조절기.
- etcd는 Raft, 과반 동의. 3대 → 1대 장애, 5대 → 2대 장애 견딤. 홀수 권장.
- dockershim은 **v1.24**에서 제거. 런타임은 CRI 준수(containerd, CRI-O).
- `apply` = 선언형(차이만 패치), `create`/`replace -f` = 명령형 오브젝트 설정.
