:::tip[한 줄 요약]
**관측성**은 서버 안을 직접 들여다보지 않고도, 서버가 내보내는 **메트릭·트레이스·로그**만으로 "왜 이런 일이 생겼나"를 알아낼 수 있는 성질이에요. 메트릭으로 **이상을 알아채고**, 트레이스로 **어디서 느린지** 찾고, 로그로 **그 요청에 무슨 일이 있었는지** 확인하며, 셋을 **traceId**로 이어 붙이는 게 핵심이에요.
:::

<Aside type="note" title="이 페이지의 기준">
OpenTelemetry·Prometheus·W3C Trace Context·Google SRE 책·Spring Boot 4.2 공식 문서를 바탕으로 했어요(2026-11 조회). 평균과 p99 비교는 파이썬으로 가짜 응답 시간 1000개를 한 번 만들어 계산해 본 예시예요.
</Aside>

## 쉽게 이해하기

서버를 **입원한 환자**라고 해 봐요. 의사는 환자 몸속을 직접 열어 볼 수 없으니, 밖으로 나오는 정보로 판단해요.

- **체온계·혈압계 = 메트릭.** 숫자 몇 개를 시간마다 기록해요. "38도 넘었다"처럼 **뭔가 이상하다는 걸 빨리** 알려 줘요. 하지만 왜 열이 나는지는 몰라요.
- **동선 추적 = 트레이싱.** 환자가 접수 → 검사실 → 영상의학과를 거치며 **어디서 얼마나 기다렸는지** 보여 줘요. "영상의학과에서 40분 막혔다"를 찾아내요.
- **진료 기록 = 로그.** 그 순간 무슨 일이 있었는지 **글로 자세히** 남겨요. "조영제 투여 후 알레르기 반응" 같은 구체적인 사실이 여기 있어요.

셋을 잇는 건 **환자 번호**예요. 번호 하나로 체온 기록, 동선, 진료 기록을 한꺼번에 찾을 수 있어야 해요. 서버에서는 이 번호가 **traceId**예요.

단, 실제로는 메트릭이 환자 한 명이 아니라 **요청 수천 개를 합친 숫자**예요. "결제 API 전체의 응답 시간 분포"처럼 묶어서 봐요. 요청 하나하나를 따라가는 건 트레이스와 로그의 몫이에요.

## 제대로 알기

### 1. 모니터링과 관측성은 뭐가 다를까

**모니터링**(monitoring)은 요청 수, 에러 수, 처리 시간 같은 숫자를 실시간으로 모으고 보여 주는 거예요. 모니터링은 두 가지 질문에 답해야 해요.

- **무엇이** 고장 났나? (증상) 예: 결제 API가 500 에러를 내요.
- **왜** 고장 났나? (원인) 예: DB 연결이 거부됐어요.

**관측성**(observability)은 한 걸음 더 나가요. 미리 대시보드를 만들어 두지 않은 **처음 보는 문제**도, 밖으로 나온 데이터만으로 물어보고 답할 수 있는 성질이에요. 그러려면 문제가 생긴 뒤에 코드를 고치는 게 아니라, **앱이 평소에 신호를 내보내고 있어야** 해요.

시스템이 내보내는 이런 데이터를 **텔레메트리**(telemetry)라고 하고, 대표 신호가 메트릭·트레이스·로그 세 가지예요.

### 2. 세 신호 비교

| | 메트릭 | 트레이스 | 로그 |
|---|---|---|---|
| 비유 | 체온계 | 동선 추적 | 진료 기록 |
| 정체 | 숫자를 시간 단위로 집계 | 요청 하나가 지나간 경로 | 시각이 찍힌 메시지 |
| 답하는 질문 | 뭔가 이상한가? | 어디서 느린가? | 그 요청에 무슨 일이? |
| 예 | 초당 요청 수, 에러율, p99 지연 | 게이트웨이 → 주문 → 결제 → DB 각 구간 시간 | 예외 스택, "잔액 부족" 메시지 |
| 비용 | 싸요(숫자 몇 개) | 중간(보통 일부만 샘플링) | 비싸요(양이 많음) |
| 사용자 ID 같은 값 | 넣으면 안 돼요 | 넣어도 돼요 | 넣어도 돼요 |

세 신호는 서로를 대신하지 못해요. 보통 순서는 **메트릭으로 알아채고 → 트레이스로 위치를 좁히고 → 로그로 원인을 확인**하는 거예요.

### 3. 메트릭: 무엇을 셀까

#### Prometheus는 어떻게 모으나

**Prometheus**(프로메테우스)는 오픈소스 모니터링·알림 도구예요. 데이터를 **시계열**(time series, 시각과 값의 쌍이 줄줄이 이어진 데이터)로 저장해요. 시계열 하나는 **메트릭 이름 + 레이블**(label, 키=값 꼬리표)로 구분돼요.

```text
http_requests_total{method="POST", uri="/payments", status="200"}
```

모으는 방식은 **pull**(당겨 오기)이에요. Prometheus 서버가 앱의 HTTP 주소를 주기적으로 찾아가서 숫자를 **긁어 와요**(scrape). 금방 끝나서 긁기 전에 사라지는 배치 작업만 예외로, **Pushgateway**라는 중간 저장소에 직접 밀어 넣어요(push).

```text
앱(/actuator/prometheus) ← Prometheus가 주기적으로 긁어 감
  → 시계열 DB에 저장 → PromQL로 조회(Grafana 대시보드)
  → 규칙 위반 시 Alertmanager → 슬랙·전화로 알림
```

Prometheus는 데이터가 100% 정확한 것보다 **장애 중에도 계속 동작하는 것**을 택했어요. 그래서 요청 단위 과금처럼 하나도 빠지면 안 되는 데이터에는 맞지 않아요.

#### 메트릭 타입 4가지

| 타입 | 특징 | 예 |
|---|---|---|
| **Counter** | 올라가기만 함(재시작 시 0) | 요청 수, 에러 수 |
| **Gauge** | 오르내리는 현재값 | 메모리 사용량, 동시 접속 수 |
| **Histogram** | 값을 구간(bucket)별로 셈. 분위수는 조회할 때 계산 | 응답 시간 |
| **Summary** | 분위수를 앱이 미리 계산해서 보냄 | 응답 시간 |

- Counter 값을 그대로 그래프로 그리면 계속 올라가기만 해요. **`rate()`** 함수로 "초당 몇 개씩 늘었나"로 바꿔 봐야 의미가 있어요. `rate()`는 재시작으로 0이 된 것도 알아서 보정해요.
- Histogram은 인스턴스(서버) 여러 대의 구간별 개수를 **먼저 합친 다음** 분위수를 계산할 수 있어요. 분위수끼리 평균을 내면 전체 분위수가 아니에요.

```text
# 결제 API 전체의 p99 응답 시간(최근 5분)
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))
# le = 구간 경계 레이블. 합칠 때 le는 남겨야 해요
```

#### 레이블에 사용자 ID를 넣으면 안 되는 이유

레이블 값 조합 하나하나가 **새 시계열**이에요. 사용자 ID나 이메일처럼 값이 끝없이 늘어나는 걸 레이블로 쓰면 시계열이 사용자 수만큼 생겨요. 이걸 **카디널리티**(cardinality, 서로 다른 값의 개수) 폭발이라고 하고, Prometheus 메모리가 감당하지 못해요. 같은 이유로 URL도 `/orders/123` 같은 실제 경로가 아니라 `/orders/{id}` 같은 **템플릿**으로 남겨야 해요. 사용자 한 명을 따라가는 건 로그와 트레이스가 해요.

이름 규칙도 있어요. 단위는 `_seconds`처럼 복수형으로 붙이고, 누적 카운터는 `_total`로 끝내요(`http_requests_total`).

### 4. 무엇을 볼까: 골든 시그널 4개

Google SRE 책은 사용자에게 서비스하는 시스템이라면 **이 4개만은 꼭 보라**고 해요.

| 신호 | 뜻 | 주의할 점 |
|---|---|---|
| **Latency**(지연) | 요청 처리 시간 | 성공과 실패를 나눠 봐요. 느린 에러는 빠른 에러보다 나빠요 |
| **Traffic**(트래픽) | 수요. 예: 초당 HTTP 요청 수 | 갑자기 늘었는지 줄었는지 |
| **Errors**(에러) | 실패한 요청 비율 | 500만 에러가 아니에요. 200인데 내용이 틀리거나, 1초 목표를 넘긴 것도 정책상 실패 |
| **Saturation**(포화) | 얼마나 꽉 찼나. 가장 부족한 자원 기준 | 100%가 되기 전에 이미 느려지니 목표 사용률을 정해 둬요 |

비슷한 체크리스트가 두 개 더 있어요.

- **USE**(Brendan Gregg 제안): 모든 **자원**(CPU, 디스크 등)마다 Utilization(바쁜 시간 비율), Saturation(밀려서 기다리는 일의 양), Errors(에러 수)를 봐요. 서버·인프라 쪽 병목 찾기용이에요.
- **RED**: **요청** 관점에서 Rate(초당 요청 수), Errors(실패), Duration(지연 분포)을 봐요. 공식 명세 문서가 있는 건 아니고 업계에서 널리 쓰는 정리예요.

대략 USE는 "기계가 힘든가", RED는 "요청이 잘 처리되나"를 봐요.

### 5. 평균은 느린 요청을 숨긴다

응답 시간 1000개를 만들어 계산해 봤어요. 980개는 50ms 근처, 20개(2%)는 2초에서 5초 사이로요.

| 지표 | 값 |
|---|---|
| 평균 | 119.6ms |
| p50(중앙값) | 50.0ms |
| p90 | 64.2ms |
| p95 | 69.4ms |
| **p99** | **3330ms** |
| 최대 | 4855ms |

**p99**(99번째 백분위수)는 "응답 시간을 빠른 순으로 줄 세웠을 때 99% 지점의 값"이에요. 즉 100명 중 가장 느린 1명 정도가 겪는 시간이에요.

- 평균 119.6ms만 보면 "괜찮네" 하고 넘어가요.
- 그런데 대다수는 50ms로 그보다 빠르고, 2%는 2초에서 5초나 기다려요. **평균은 어느 쪽도 대표하지 못해요.**
- 같은 실험에서 느린 비율을 1%로 줄이자 p99가 87ms로 나왔어요. 느린 요청이 딱 경계에 걸리면 p99에도 안 잡힐 수 있어서, 필요하면 **p99.9**까지 봐요.

꼬리는 커지기도 해요. 페이지 하나가 백엔드 여러 개를 부르면, 그중 하나라도 느리면 페이지 전체가 느려져요. 그래서 **백엔드의 p99가 프런트의 중앙값**이 될 수도 있어요.

### 6. 트레이스: 요청 하나를 따라가기

#### span과 trace

- **Span**(스팬): 작업 한 단위예요. 이름, 시작·끝 시각, 속성을 가져요. 예: "결제 서비스의 DB 조회".
- **Trace**(트레이스): 요청 하나가 여러 서비스를 지나간 전체 경로예요. 맨 위 **루트 span** 하나와 그 아래 자식 span들로 이뤄지고, 보통 위 그림 같은 **폭포**(waterfall) 모양으로 봐요.

**traceId는 요청 전체에 하나**, **spanId는 구간마다 달라요.**

#### 서비스 사이에 traceId를 어떻게 넘길까

서비스 A가 B를 부를 때, HTTP 헤더에 traceId와 자기 spanId를 실어 보내요. B는 그걸 꺼내서 **같은 trace 안에** 새 span을 만들고, A의 span을 부모로 삼아요. 이걸 **컨텍스트 전파**(context propagation)라고 해요. 헤더 형식의 표준이 W3C **Trace Context**이고, 핵심 헤더가 `traceparent`예요.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └ flags: 01 = 기록 대상(sampled)
             │  │                                └ parent-id: 16자, 부른 쪽 span
             │  └ trace-id: 32자, 요청 전체에서 같음
             └ version: 00
```

- 모두 소문자 16진수이고, 0으로만 채운 ID는 무효예요.
- 벤더별 추가 정보는 `tracestate` 헤더에 따로 실어요.
- OpenTelemetry(관측 신호를 만들고 보내는 오픈소스 표준 도구 모음)도 기본으로 이 형식을 써요.

### 7. 로그: 사람이 아니라 검색을 위해 찍기

#### 로그 레벨

`TRACE < DEBUG < INFO < WARN < ERROR` 순으로 심각해요. Spring Boot는 기본으로 ERROR·WARN·INFO만 콘솔에 찍고, `logging.level.패키지명=debug`처럼 패키지별로 바꿀 수 있어요.

#### 구조화 로그와 traceId

로그를 문장으로만 찍으면 grep으로 찾기 힘들어요. **구조화 로그**(structured log)는 JSON 같은 키-값으로 찍어서 "traceId가 이것인 로그만", "userId가 이것인 에러만"처럼 **필드로 검색**할 수 있게 해요.

```json
{"level":"ERROR","traceId":"4bf92f35...","userId":"u-81","msg":"PG 응답 시간 초과"}
```

- 로그에는 userId 같은 값이 많은 필드를 넣어도 괜찮아요. 메트릭 레이블과 다른 점이에요.
- 대신 카드 번호·주민번호 같은 **민감정보는 가려서(마스킹)** 찍어야 해요. 금융 서비스에서 특히 중요해요.

#### 쿠버네티스에서 로그는 어디로 가나

컨테이너 앱은 파일 대신 **stdout/stderr**(표준 출력, 화면에 찍는 출력)으로 로그를 써요. 컨테이너 런타임이 이걸 노드의 파일로 저장하고, `kubectl logs`로 읽어요.

- 파일은 kubelet이 돌려 가며 지워요(기본 10Mi짜리 5개). `kubectl logs`는 최신 파일 하나만 보여 줘요.
- 파드가 쫓겨나거나(evict) 노드가 죽으면 로그도 사라져요. 재시작 직전 컨테이너 로그는 `kubectl logs --previous`로 볼 수 있어요.
- 쿠버네티스는 클러스터 전체 로그 저장소를 기본으로 주지 않아요. 노드마다 **로깅 에이전트**를 두거나, 파드 안에 **사이드카**(옆에 붙여 띄우는 보조 컨테이너)를 두거나, 앱이 직접 보내는 방식으로 **중앙 저장소**에 모아야 해요.

### 8. Spring Boot에서는

| 하는 일 | 도구 | 포인트 |
|---|---|---|
| 메트릭 | **Micrometer** | 로깅의 SLF4J처럼 "창구"예요. 코드는 Micrometer로 기록하고, `micrometer-registry-prometheus` 같은 의존성으로 보낼 곳이 정해져요 |
| 메트릭 노출 | **Actuator** | 기본으로 HTTP에는 `health`만 열려요. `management.endpoints.web.exposure.include=health,info,prometheus`로 추가. 외부에 열면 보안 설정 필수 |
| 트레이싱 | **Micrometer Tracing** | 백엔드는 OpenTelemetry 또는 Brave(Zipkin). 기본 샘플링 10%(`management.tracing.sampling.probability=0.1`) |
| 로그 연결 | MDC | 로그에 traceId·spanId를 기본으로 넣어 줘요 |

**MDC**(Mapped Diagnostic Context)는 "지금 이 요청을 처리하는 스레드"에 붙여 두는 꼬리표 저장소예요. 여기 traceId가 들어 있으면 그 요청 중에 찍는 모든 로그에 자동으로 붙어요.

<Aside type="caution" title="직접 new로 만든 HTTP 클라이언트는 trace가 끊겨요">
다음 서비스로 traceId가 넘어가려면 Spring이 자동 구성해 준 `RestClient.Builder`나 `WebClient.Builder`를 주입받아 써야 해요. 클라이언트를 직접 `new`로 만들면 `traceparent` 헤더가 안 붙어서, 다음 서비스에서 새 trace가 시작돼요.
</Aside>

Spring MVC 요청 메트릭은 `http.server.requests`라는 이름으로 쌓이고, method·uri(템플릿)·status 같은 태그가 붙어요. → [스프링 부트 자동 구성과 Actuator](../../spring/boot-autoconfig/)

### 9. 알림은 증상 기준으로

**알림**(alert)은 "사람을 깨우는 것"이에요. Google SRE 책의 원칙은 이래요.

- 모든 알림은 **사람이 할 일이 있어야** 해요. 기계적으로 처리할 수 있으면 알림이 아니라 자동화 대상이에요.
- **증상 기준**으로 알려요. "결제 p99가 1초를 5분 넘게 초과", "5xx 비율 1% 초과"처럼 사용자가 실제로 겪는 것 기준이에요.
- **원인 기준**("CPU 80%")은 확실하고 곧 닥칠 문제일 때만 써요. CPU가 높아도 사용자가 멀쩡하면 사람을 깨울 이유가 없어요.
- 급한 알림이 너무 많으면 사람들이 지쳐서 무시하게 돼요(**알림 피로**).

기준을 정할 때 쓰는 말이 SLI와 SLO예요. **SLI**(Service Level Indicator)는 서비스 상태를 재는 값(가능하면 사용자 관점, 예: 응답 시간)이고, **SLO**(Service Level Objective)는 거기에 붙인 목표(예: "p99 1초 이내")예요.

## 면접 질문

<details>
<summary>Q. 관측성의 세 신호(로그·메트릭·트레이스)는 각각 무엇이고 언제 쓰나요?</summary>

**답변(30초)** 메트릭은 이상을 알아채고, 트레이스는 위치를 찾고, 로그는 원인을 확인하는 데 써요. 메트릭은 에러율이나 p99 지연처럼 숫자를 시간 단위로 집계한 거라 싸고 알림에 좋아요. 트레이스는 요청 하나가 여러 서비스를 지나간 경로를 span 단위로 보여 줘서 어느 구간이 느린지 알려 줘요. 로그는 그 순간의 상세 메시지라 예외 내용을 확인할 때 써요. 셋을 traceId로 이어야 메트릭에서 이상을 보고 바로 해당 요청의 트레이스와 로그로 넘어갈 수 있어요.

**꼬리질문**
- Q. 모니터링과 관측성은 뭐가 달라요? → 모니터링은 미리 정한 지표로 알려진 문제를 지켜보는 거고, 관측성은 처음 보는 문제도 밖으로 나온 신호만으로 물어보고 답할 수 있는 성질이에요. 그래서 앱이 평소에 신호를 충분히 내보내야 해요.
- Q. 메트릭 레이블에 userId를 넣으면요? → 레이블 값 조합마다 시계열이 생겨서 사용자 수만큼 늘어나요(카디널리티 폭발). 사용자 단위 추적은 로그·트레이스로 해요.
</details>

<details>
<summary>Q. 평균 응답 시간 대신 p99를 보는 이유는요?</summary>

**답변(30초)** 평균은 소수의 아주 느린 요청을 숨기기 때문이에요. 응답 시간 1000개 중 98%가 50ms, 2%가 2초에서 5초 사이인 예를 계산하면 평균은 119.6ms로 정상처럼 보이지만 p99는 3330ms예요. 사용자 100명 중 한두 명은 3초 넘게 기다린다는 뜻이에요. 그래서 지연은 히스토그램으로 분포를 모으고 p50, p99를 함께 봐요.

**꼬리질문**
- Q. 서버 3대의 p99를 평균 내면 전체 p99인가요? → 아니에요. 분위수끼리는 평균 낼 수 없어서, 히스토그램의 구간별 개수를 먼저 합친 뒤 `histogram_quantile`로 계산해요.
- Q. p99로도 부족할 때는요? → 느린 요청 비율이 1% 근처면 p99 경계에 걸려 안 보일 수 있어요. 그럴 땐 p99.9까지 봐요.
</details>

<details>
<summary>Q. Four Golden Signals를 설명해 주세요.</summary>

**답변(30초)** Google SRE 책이 사용자용 시스템이라면 꼭 보라고 한 네 가지예요. Latency는 처리 시간인데 성공과 실패를 나눠 봐요. Traffic은 초당 요청 수 같은 수요, Errors는 실패 비율인데 200이어도 내용이 틀리거나 목표 시간을 넘으면 실패로 쳐요. Saturation은 가장 부족한 자원이 얼마나 꽉 찼는지예요. 100% 전에 이미 느려지니 목표 사용률을 둬요.

**꼬리질문**
- Q. USE와 RED는요? → USE는 CPU·디스크 같은 자원마다 사용률·포화·에러를 보는 인프라 관점이고, RED는 요청의 비율·에러·지연을 보는 서비스 관점이에요.
</details>

<details>
<summary>Q. MSA에서 요청 하나를 여러 서비스에 걸쳐 어떻게 추적하나요?</summary>

**답변(30초)** 분산 트레이싱으로 추적해요. 첫 서비스가 traceId를 만들고, 다음 서비스를 부를 때 W3C 표준 `traceparent` 헤더에 traceId와 자기 spanId를 실어 보내요. 받는 쪽은 같은 traceId로 새 span을 만들고 보낸 쪽 span을 부모로 삼아요. 각 서비스가 span을 수집기로 보내면 traceId로 묶여서 폭포 그림이 돼요.

**꼬리질문**
- Q. Spring에서 trace가 중간에 끊기면 뭘 보나요? → HTTP 클라이언트를 직접 `new`로 만들었는지 봐요. 자동 구성된 `RestClient.Builder`·`WebClient.Builder`를 주입받아야 헤더가 붙어요.
- Q. 로컬에서 trace가 일부만 보여요. → Spring Boot 기본 샘플링이 10%라 정상이에요.
</details>

<details>
<summary>Q. Prometheus는 어떻게 메트릭을 모으나요? Counter와 Gauge는 뭐가 달라요?</summary>

**답변(30초)** Prometheus는 pull 방식이에요. 서버가 앱의 HTTP 엔드포인트, Spring이라면 `/actuator/prometheus`를 주기적으로 긁어 와서 시계열로 저장해요. 금방 끝나는 배치 작업만 Pushgateway에 push해요. Counter는 요청 수처럼 올라가기만 하는 값이라 `rate()`로 초당 증가율을 봐야 하고, Gauge는 메모리 사용량처럼 오르내리는 현재값이에요.

**꼬리질문**
- Q. Histogram과 Summary 차이는요? → Histogram은 구간별 개수를 보내고 분위수는 조회할 때 계산해서 여러 서버를 합칠 수 있어요. Summary는 앱이 분위수를 미리 계산해서 보내요.
</details>

<details>
<summary>Q. 쿠버네티스에서 로그는 어떻게 수집하나요?</summary>

**답변(30초)** 앱은 stdout으로 로그를 쓰고, 컨테이너 런타임이 노드 파일에 저장해서 `kubectl logs`로 볼 수 있어요. 하지만 파일은 회전되며 지워지고, 파드가 쫓겨나거나 노드가 죽으면 로그도 사라져요. 쿠버네티스는 클러스터 단위 로그 저장소를 기본으로 주지 않아서, 노드마다 로깅 에이전트를 두거나 사이드카, 또는 앱이 직접 보내는 방식으로 중앙 저장소에 모아요.

**꼬리질문**
- Q. 재시작된 컨테이너의 직전 로그는요? → `kubectl logs --previous`로 봐요. 근본적으로는 중앙 수집이 있어야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: "결제 API가 가끔 3초 넘게 걸린다"는 고객 문의가 들어왔습니다. 그런데 대시보드의 평균 응답 시간은 120ms로 정상입니다. 원인을 어떻게 찾겠습니까?</summary>

**상황 파악**
평균이 정상인데 "가끔" 느리다면, 소수 요청만 느린 **꼬리 지연**일 가능성이 커요. 평균은 이런 요청을 숨겨요. 먼저 결제 API의 **p99·p99.9 지연**을 확인해서 문의가 실제 현상인지, 언제부터인지, 어느 엔드포인트인지(uri 태그) 좁혀요.

**원인 후보**
1. DB의 특정 쿼리가 일부 조건에서만 느려요(데이터가 많은 사용자, 인덱스를 못 타는 조건 등).
2. 외부 **PG사**(결제대행사) 호출이 가끔 늦게 응답하고, 타임아웃이 길게 잡혀 있어요.
3. DB 커넥션 풀이나 스레드 풀이 순간적으로 꽉 차서(포화) 요청이 줄 서서 기다려요.
4. GC 멈춤 같은 서버 내부 지연이 가끔 끼어들어요.

**해결 순서와 방법**
찾는 순서는 **p99 → 트레이스 → 로그**예요.

1. **메트릭**: p99가 언제 튀는지, 트래픽 증가·포화(커넥션 풀 사용률)와 시점이 겹치는지 봐요.
2. **트레이스**: 느린 요청의 trace를 몇 개 골라 폭포 그림에서 어느 span이 길게 늘어났는지 찾아요. DB span인지, PG 호출 span인지, 아니면 span 사이 빈 시간(대기)인지 구분돼요.
3. **로그**: 그 traceId로 로그를 검색해서 예외, 재시도, 타임아웃 메시지를 확인해요.

원인별 해결책은 트레이드오프가 있어요.

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 느린 쿼리 개선(인덱스, 쿼리 수정) | 근본 해결, 다른 요청도 빨라짐 | 분석·배포 시간이 걸리고, 인덱스는 쓰기 비용이 늘어남 |
| B. PG 호출 타임아웃 단축 + 실패 시 재시도 또는 빠른 실패 | 사용자가 오래 기다리지 않음 | 결제는 중복 처리 위험이 있어 재시도에 멱등성 보장이 필요함 |
| C. 커넥션 풀 크기 조정 / 서버 늘리기 | 포화가 원인이면 바로 효과 | DB가 병목이면 풀만 키워도 DB 부담만 커짐 |

**내가 고를 방법**
추측으로 바로 C(서버 증설)부터 하지 않아요. 트레이스로 **어느 span이 느린지 먼저 확정**하고 그 원인에 맞는 방법을 골라요. DB span이면 A, PG span이면 B가 우선이에요. 그리고 같은 일이 다시 묻히지 않게, 평균이 아니라 **p99 기준 알림**("결제 p99가 1초를 5분 넘게 초과")을 걸어 둬요. 고친 뒤엔 p99 그래프가 내려왔는지로 확인해요.

**채점 포인트**: 평균이 꼬리를 숨김, p99·p99.9 확인, 히스토그램, 메트릭 → 트레이스 → 로그 순서, 느린 span 특정, traceId로 로그 검색, 포화(커넥션 풀) 확인, 외부 PG 타임아웃, 결제 재시도는 멱등성 필요, 증상 기준 알림, 적용 후 p99로 회복 확인.
</details>

<details>
<summary>상황: 서비스가 주문 → 재고 → 결제 3개로 나뉘어 있습니다. 로그는 서비스마다 엄청 많이 쌓이는데, 특정 고객의 요청 하나가 어디서 실패했는지 따라가지 못하고 있습니다.</summary>

**상황 파악**
로그 **양**이 문제가 아니라, 서비스마다 흩어진 로그를 **같은 요청끼리 묶을 열쇠**가 없는 게 문제예요. 사람이 시각을 맞춰 가며 세 서비스 로그를 grep하는 건 동시 요청이 많으면 불가능해요.

**원인 후보**
1. 로그에 요청을 식별하는 ID(traceId)가 없어요.
2. 있더라도 서비스 사이에 전파되지 않아서 서비스마다 다른 ID가 찍혀요(예: HTTP 클라이언트를 직접 `new`로 생성).
3. 로그가 자유 문장이라 필드로 검색이 안 되고, 서비스별 서버에 흩어져 있어 한곳에서 못 찾아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 분산 트레이싱 도입(Micrometer Tracing + OpenTelemetry) + `traceparent` 전파 + MDC로 로그에 traceId 자동 기록 | 표준 방식이라 서비스 언어가 달라도 이어짐. 폭포 그림으로 위치까지 보임 | 수집기·저장소 운영 비용. 샘플링하면 모든 요청의 trace가 남진 않음 |
| B. 게이트웨이에서 요청 ID를 직접 만들어 헤더로 넘기고 로그에 찍기 | 단순하고 빨리 적용 | 서비스마다 직접 구현해야 하고 빠뜨리기 쉬움. 구간별 시간은 안 보임 |
| C. 로그를 JSON 구조화 로그로 바꾸고 중앙 저장소에 모으기 | traceId·userId·orderId 필드로 한 번에 검색 | 저장 용량 증가, 민감정보 마스킹 필요 |

**내가 고를 방법**
A와 C를 함께 해요. 트레이싱으로 traceId가 서비스를 건너 자동으로 이어지게 하고, 로그는 JSON으로 찍어 traceId를 필드로 넣은 뒤 중앙 저장소에서 검색해요. HTTP 클라이언트는 자동 구성된 `RestClient.Builder`를 주입받아 쓰게 고쳐서 전파가 끊기지 않게 해요. 샘플링 때문에 trace가 없는 요청도 **로그의 traceId는 남으니** 로그 검색은 항상 가능해요. 카드 번호 같은 민감정보는 로그에서 마스킹해요. 적용 후 실제 실패 요청 하나를 traceId로 세 서비스 끝까지 따라가 보는 걸로 확인해요.

**채점 포인트**: 로그 양이 아니라 상관관계 ID 부재가 문제, traceId·spanId, W3C `traceparent` 컨텍스트 전파, MDC로 로그에 자동 기록, 구조화(JSON) 로그와 필드 검색, 중앙 로그 수집, 직접 생성한 클라이언트는 전파 끊김, 샘플링 트레이드오프, 민감정보 마스킹.
</details>

<details>
<summary>상황: 모니터링 알림이 하루 수십 건씩 슬랙에 와서, 팀원들이 이제 알림을 거의 보지 않습니다. 지난주엔 진짜 장애 알림도 놓쳤습니다.</summary>

**상황 파악**
**알림 피로**예요. 대부분의 알림이 "봐도 할 일이 없는" 알림이라, 사람들이 알림 전체를 무시하게 됐어요. 먼저 지난 몇 주 알림을 모아서 "이 알림을 받고 실제로 누가 뭘 했나"를 분류해요.

**원인 후보**
1. **원인 기준 알림**이 많아요. "CPU 80%", "디스크 70%"처럼 사용자에게 영향이 없을 때도 울려요.
2. 임계값이 너무 민감하거나, 순간 튐에도 바로 울려요(지속 시간 조건이 없음).
3. 사람이 판단할 필요 없이 매번 같은 조치(재시작 등)를 하는 알림이 있어요.
4. 긴급(전화)과 참고(티켓)가 구분 없이 같은 채널로 와요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. **증상 기준**으로 바꾸기: 에러율, p99 지연처럼 사용자가 겪는 것을 SLO로 정하고 "5분 이상 지속" 조건 | 진짜 영향이 있을 때만 울림 | 원인은 알림 뒤에 대시보드·트레이스로 따로 찾아야 함 |
| B. 반복 조치는 **자동화**(자동 재시작, 오토스케일링) | 사람을 안 깨워도 됨 | 자동화가 진짜 문제를 가릴 수 있어 자동 조치 횟수도 지켜봐야 함 |
| C. 원인 기준 지표는 알림 대신 **대시보드·업무 시간 티켓**으로 강등 | 정보는 잃지 않으면서 소음은 줄어듦 | 곧 터질 문제(디스크 가득 참 임박 등)를 놓치지 않게 일부는 남겨야 함 |

**내가 고를 방법**
A를 중심으로 B와 C를 함께 해요. 사람을 부르는 알림은 "사용자가 지금 피해를 보고 있고, 사람이 판단할 일이 있는 것"으로만 줄여요. 원인 기준 알림은 디스크가 곧 가득 차는 것처럼 **확실하고 임박한 경우**만 남기고 나머지는 대시보드로 내려요. 알림마다 "받으면 무엇을 할지"를 적어 두고, 할 일을 못 적는 알림은 지워요. 적용 후엔 주당 알림 수와, 알림 없이 사용자 신고로 먼저 알게 된 장애가 있는지를 같이 봐요.

**채점 포인트**: 알림 피로, 모든 알림은 행동 가능해야 함(actionable), 증상 기준 대 원인 기준, SLI·SLO, 지속 시간 조건, 반복 조치 자동화, 긴급도 분리, 원인 지표는 대시보드로, 놓친 장애로 알림 품질 점검.
</details>

## 필기 포인트

- 관측 신호 3가지: **메트릭**(집계된 숫자), **트레이스**(요청 경로), **로그**(시각 찍힌 메시지).
- Golden Signals: **Latency, Traffic, Errors, Saturation**.
- USE = 자원별 **U**tilization·**S**aturation·**E**rrors. RED = 요청의 **R**ate·**E**rrors·**D**uration.
- Prometheus = **pull**(scrape). 짧은 배치 작업만 Pushgateway로 push.
- Counter는 증가만(재시작 시 0) → `rate()`로 봄. Gauge는 오르내림.
- Histogram은 분위수를 조회 시 계산(서버 합산 가능), Summary는 앱이 미리 계산.
- `traceparent` = `version-traceid-parentid-flags`. trace-id 32자, parent-id 16자, 소문자 16진수.
- traceId는 요청 전체 공통, spanId는 구간마다 다름.
- Spring Boot 트레이싱 기본 샘플링 **10%**. Actuator 기본 HTTP 노출은 **health**만.
- 쿠버네티스 로그: stdout → 노드 파일(기본 10Mi × 5개 회전). 클러스터 로그 저장소는 기본 제공 안 함.
