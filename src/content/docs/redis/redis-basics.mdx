:::tip[한 줄 요약]
**Redis**는 데이터를 **메모리**에 두는 키-값 저장소라 아주 빠르고, 명령 실행은 **한 스레드가 하나씩 순서대로** 처리해서 명령 하나는 다른 명령에 끼어들림 없이 끝나요(원자적). 대신 `KEYS *`처럼 오래 걸리는 명령 하나가 들어오면 **다른 모든 요청이 줄 서서 기다려요.**
:::

:::note[처음이라면 여기까지]
① Redis는 데이터를 디스크가 아니라 **메모리**에 둬서 아주 빨라요.

② 명령은 한 줄로 서서 **하나씩 순서대로** 처리돼요. 그래서 명령 하나가 실행되는 도중에 다른 명령이 끼어들지 않아요.

③ 대신 `KEYS *`처럼 오래 걸리는 명령 하나가 들어오면 뒤에 선 요청이 전부 기다려요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

<Aside type="note" title="이 페이지의 기준">
설명은 redis.io 최신 공식 문서(2026-11 조회)를 바탕으로 했어요. 직접 돌린 실험은 **Redis 8.x**(Docker 공식 이미지, 노트북 1회 실행)라서 숫자는 "이 정도 차이가 난다"는 경향으로만 봐 주세요. 7.x와 다른 설정은 따로 표시했어요.

## 쉽게 이해하기

동네에 **계산대가 딱 하나뿐인 편의점**이 있다고 해 봐요. 직원 한 명이 손님을 한 명씩 계산해요. 그런데 이 편의점은 물건이 전부 **계산대 바로 옆 선반**에 있어서, 직원이 창고(디스크)에 갈 일이 거의 없어요. 그래서 손님 한 명 계산이 눈 깜짝할 새에 끝나고, 줄이 길어도 금방 빠져요.

계산대가 하나라서 좋은 점도 있어요. 두 직원이 같은 물건을 동시에 집다가 엉키는 일이 없어요. 한 손님 계산이 끝나야 다음 손님으로 넘어가니까요.

문제는 **"이 가게 물건 전부 목록으로 뽑아 주세요"** 하는 손님이 올 때예요. 직원이 그 목록을 다 뽑을 때까지 뒤 손님은 우유 하나 사려고 해도 기다려야 해요. Redis에서는 `KEYS *`가 바로 그 손님이에요.

단, 실제로는 직원이 혼자인 건 **계산(명령 실행)** 뿐이에요. 문 열어 주기(네트워크 읽고 쓰기)나 쓰레기 버리기(디스크 저장, 큰 데이터 삭제)는 다른 직원(백그라운드 스레드)이 돕기도 해요. 그래서 정확히는 "**대부분** 싱글 스레드"라고 불러요.

## 제대로 알기

### 1. Redis는 무엇인가

**Redis**는 **RE**mote **DI**ctionary **S**erver의 줄임말이에요. "원격에 있는 사전"이라는 뜻 그대로, 이름(**키**, key)을 주면 값(**밸류**, value)을 돌려주는 **키-값 저장소**(key-value store)예요.

공식 문서는 Redis를 **데이터베이스, 캐시, 스트리밍 엔진, 메시지 브로커**로 쓸 수 있다고 소개해요. 실제로는 이렇게 많이 써요.

| 쓰임새 | 한 줄 설명 | 자세히 |
|---|---|---|
| 캐시 | 느린 DB 앞에 자주 읽는 값을 잠깐 둬요 | [캐시 패턴](../cache-patterns/) |
| 세션·처리율 제한 | 로그인 상태, "1분에 100번까지" 같은 카운터 | [Redis 실무 활용](../redis-practice/) |
| 랭킹·좋아요·방문자 수 | 정렬된 셋, 셋 같은 자료구조로 바로 계산 | [자료구조](../data-structures/) |
| 분산 락 | 서버 여러 대가 "지금 내가 쓴다"를 나눠 가짐 | [분산 락](../distributed-lock/) |
| 메시지 | 실시간 알림, 작업 큐 | [Pub/Sub와 Streams](../pubsub-streams/) |

다른 키-값 저장소와 가장 다른 점은 **값이 자료구조**라는 거예요. 값이 그냥 문자열만이 아니라 **리스트**(순서 있는 목록), **해시**(필드-값 묶음), **셋**(중복 없는 모음) 등이 될 수 있어요. 그리고 "리스트 끝에 하나 넣기" 같은 자료구조별 연산이 **원자적**(atomic, 중간에 다른 명령이 끼어들 수 없이 한 번에 끝남)으로 정의돼 있어요.

### 2. 인메모리: 왜 빠르고, 무엇을 포기했나

**인메모리**(in-memory)는 데이터를 디스크가 아니라 **메모리**(RAM, 전원이 꺼지면 지워지지만 아주 빠른 저장 공간)에 두고 읽고 쓴다는 뜻이에요.

Redis의 설계는 "**메모리에서 서빙하고, 디스크는 저장용**"이에요.

- 읽기·쓰기는 전부 메모리에서 해요. 그래서 빨라요.
- 디스크에는 꺼졌을 때를 대비해 **RDB**(스냅숏)나 **AOF**(명령 기록) 형식으로 저장해요. 그래서 "인메모리라 껐다 켜면 다 날아간다"는 틀린 말이에요. 단, 설정에 따라 잃을 수 있는 범위가 달라요. → [영속성](../persistence/)
- 대가는 **데이터가 메모리보다 클 수 없다**는 거예요. 공식 FAQ는 데이터를 RAM보다 크게 담는 디스크 백엔드를 만들 계획이 없다고 밝혀요.

메모리를 얼마나 쓰는지 감을 잡아 볼게요(공식 FAQ, 64비트 기준).

| 상황 | 메모리 |
|---|---|
| 빈 인스턴스 | 약 3MB |
| 작은 문자열 키 100만 개 | 약 85MB |
| 필드 5개짜리 해시 100만 개 | 약 160MB |

실험(Redis 8.x)에서는 값이 더 짧은 문자열 키 100만 개가 약 53MB였어요. 키는 한 인스턴스에 최대 2^32개까지 넣을 수 있고 2억5천만 개 이상 테스트됐지만, 실제 한계는 메모리예요.

메모리가 꽉 차면 어떻게 될까요? `maxmemory`(Redis가 쓸 메모리 상한)에 닿으면 **쓰기 명령은 에러, 읽기는 계속** 받아요. 대신 **퇴출 정책**(eviction, 꽉 차면 어떤 키를 지울지 정한 규칙)을 설정하면 키를 지워서 자리를 만들어요. → [만료와 퇴출](../expire-eviction/)

### 3. 싱글 스레드: 명령은 한 줄로 선다

**스레드**(thread)는 프로그램 안에서 일을 실제로 하는 "일꾼" 단위예요. Redis는 **명령을 실행하는 일꾼이 하나**예요. 어느 순간이든 요청 하나만 처리하고, 요청은 **순서대로** 실행돼요. 공식 문서는 이걸 Node.js와 비슷하다고 직접 비유해요.

그럼 손님(클라이언트) 수천 명은 어떻게 상대할까요? **I/O 멀티플렉싱**(multiplexing, 한 일꾼이 여러 연결을 동시에 지켜보다가 "데이터 왔음" 신호가 온 연결만 골라 처리하는 방식) 덕분이에요. 리눅스에서는 **epoll**이라는 기능을 써요(실험 서버의 `INFO`에서도 `multiplexing_api:epoll`로 나왔어요).

흐름은 이래요.

1. 클라이언트 A, B, C가 각자 연결로 명령을 보내요.
2. 메인 스레드의 **이벤트 루프**(계속 돌면서 "준비된 일 있나?" 확인하는 반복문)가 데이터가 도착한 연결을 알아내요.
3. 메인 스레드가 명령을 **하나씩 순서대로** 실행해요.
4. 결과를 응답 버퍼에 넣고 **소켓**(socket, 프로그램이 네트워크 연결로 데이터를 주고받는 창구)으로 보내요.

**싱글 스레드인데 왜 빠를까요?**

- 데이터가 메모리에 있어서 명령 하나 처리가 아주 짧아요. 일반 명령은 마이크로초(100만분의 1초) 미만 수준이에요.
- 소켓 읽기·쓰기에서 **블로킹**(기다리느라 멈춰 서는 것)이 일어나지 않게 설계됐어요.
- 공식 FAQ는 Redis에서 CPU가 병목인 경우는 드물고, 보통 **메모리나 네트워크가 병목**이라고 해요.
- 일꾼이 하나라 일꾼끼리 자원을 두고 다투거나 서로 기다리게 할 **락**(lock, "내가 쓰는 중" 표시)이 명령 실행에는 필요 없어요. (이건 순차 실행에서 따라 나오는 결론이고, 문서에 이 문장이 그대로 있지는 않아요.) 락 개념은 [DB 락](../../db/locks/)에서 볼 수 있어요.

**싱글 스레드라서 얻는 것**은 명령 단위 원자성이에요. `INCR` 같은 명령 하나는 실행 도중 다른 명령이 끼어들 수 없어요.

### 심화: 4. "대부분" 싱글 스레드인 이유

"Redis는 스레드가 1개다"는 틀린 말이에요. 한 스레드인 건 **명령 실행**이고, 느린 일은 다른 스레드가 거들어요.

| 버전 | 추가된 것 | 하는 일 |
|---|---|---|
| 2.4+ | 백그라운드 스레드 | 디스크 I/O 같은 느린 작업 |
| 4.0+ | lazy free | 큰 데이터 삭제를 뒤에서 처리(예: `UNLINK`) |
| 6.0+ | **I/O 스레드**(`io-threads`) | 소켓 읽기·쓰기와 명령 해석을 나눠 맡음 |

여기서 면접에 자주 나오는 함정이 있어요. **6.0부터 멀티스레드가 됐으니 명령이 병렬로 실행된다? 틀려요.** I/O 스레드는 "손님 말 받아 적기와 영수증 건네기"만 나눠 하고, **명령 실행은 여전히 메인 스레드 하나**예요. 그래서 원자성은 그대로예요.

`io-threads`의 기본값은 1(메인 스레드만)이라 꺼져 있어요. 켜는 방법은 버전마다 조금 달라요.

| | 7.2 | 8.2 |
|---|---|---|
| 기본 동작(켰을 때) | 쓰기만 스레드화 | 쓰기 + 읽기·해석 |
| 읽기 스레드화 | `io-threads-do-reads yes`로 따로 켬 | 옵션이 없어지고 같이 켜짐 |
| 권장 개수 | 4코어면 2~3개, 8코어면 6개 | 4코어면 3개, 8코어면 7개 |

두 버전 공통 권고는 "4코어 이상일 때, 코어 하나는 남겨 두고, **실제로 CPU가 병목일 때만**" 켜라는 거예요. 7.2 설정 파일은 8개 넘게는 별 도움이 안 되고, `CONFIG SET`으로 실행 중에 바꿀 수 없다고 적어 둬요.

실험(Redis 8.x)으로 확인해 보면, 기본 설정에서도 `bio_close_file`, `bio_aof`, `bio_lazy_free` 같은 백그라운드 스레드가 이미 있어요. `io-threads 4`로 띄우면 `INFO threads`에 I/O 스레드가 추가로 보여요.

곁가지로, 디스크 스냅숏은 **fork**(지금 프로세스를 복제해 자식 프로세스를 만드는 것)한 자식이 만들어요. 그런데 fork 자체는 메인 스레드가 해서, 메모리가 큰 인스턴스에선 이 순간에 지연이 생길 수 있어요.

### 5. 싱글 스레드의 대가: 느린 명령 하나가 모두를 막는다

명령이 한 줄로 서니까, **오래 걸리는 명령 하나가 있으면 뒤의 모든 클라이언트가 기다려요.**

- `GET`, `SET`, `LPUSH`는 **상수 시간**(데이터가 많아져도 걸리는 시간이 거의 같음)이라 괜찮아요.
- `SORT`, `LREM`, `SUNION`, 큰 셋의 교집합처럼 원소를 많이 다루는 명령은 오래 걸릴 수 있어요.
- 공식 문서는 운영 환경에서 쓰는 **`KEYS`** 를 느린 명령 지연의 "매우 흔한 원인"으로 꼽아요.

모든 명령 문서에는 **시간 복잡도**(데이터 양이 늘 때 걸리는 시간이 어떻게 늘어나는지)가 적혀 있어요. 낯선 명령은 쓰기 전에 확인하는 습관을 들이라고 권해요.

#### KEYS vs SCAN

`KEYS pattern`은 DB의 **모든 키**를 한 번에 훑어요. 시간 복잡도는 O(N)(N = 전체 키 수)이에요. 공식 문서는 디버깅 같은 특수 작업용이고, 일반 앱 코드에는 쓰지 말고 **SCAN**이나 **Set**을 쓰라고 경고해요.

`SCAN cursor [MATCH 패턴] [COUNT 개수]`는 키를 **조금씩 나눠서** 훑어요. 호출할 때마다 일부 키와 **커서**(다음에 어디서부터 이어 볼지 표시한 책갈피 번호)를 돌려주고, 커서가 0으로 돌아오면 끝이에요.

실험(Redis 8.x)에서 재 본 서버 내부 실행 시간이에요.

| 상황 | 결과 |
|---|---|
| 10만 키, `KEYS *` 1회 | 약 3.5ms 동안 서버를 붙잡음 |
| 10만 키, `SCAN ... COUNT 100` 전체 순회 | 996번 호출, 합계 약 6.7ms, **1회 최대 21µs** |
| 100만 키, `KEYS *` | 약 61ms 실행 |
| 그동안 다른 연결의 `PING` | 실행은 3µs인데 **응답까지 약 50ms** (줄 서서 기다림) |

핵심은 **SCAN이 총 일을 줄여 주는 게 아니라는 것**이에요. 전체를 다 훑으면 SCAN도 O(N)이에요. 차이는 한 번에 서버를 붙잡는 시간이 100배 넘게 짧아서, **호출 사이사이에 다른 요청이 끼어들 수 있다**는 거예요.

SCAN에도 알아 둘 한계가 있어요.

- 순회 내내 있던 키는 **적어도 한 번은** 나와요. 대신 **같은 키가 두 번 나올 수 있어서** 앱이 중복을 처리해야 해요.
- 순회 도중 추가·삭제된 키는 나올 수도, 안 나올 수도 있어요.
- `COUNT`는 "이번에 이 정도 일 해 줘"라는 **힌트**일 뿐이에요(기본 10). 정확히 그 개수가 오지 않아요.
- `MATCH`는 키를 가져온 **뒤에** 걸러요. 그래서 빈 결과가 와도 커서가 0이 아니면 계속 불러야 해요.

키 목록이 자주 필요하다면 애초에 Set으로 "이런 키들이 있다"는 목록을 따로 관리하는 설계가 더 나아요.

### 6. 지연을 줄이는 습관

공식 지연 가이드가 권하는 것들이에요.

- **연결을 오래 유지해요.** 요청마다 연결을 새로 맺고 끊지 않아요(**커넥션 풀**, 미리 맺어 둔 연결을 돌려 쓰는 방식).
- **왕복 횟수를 줄여요.** `MSET`/`MGET` 같은 묶음 명령 > **파이프라이닝**(pipelining, 응답을 기다리지 않고 명령 여러 개를 연달아 보내는 것) > 하나씩 왕복 순으로 좋아요. 앞 결과를 다음 명령 입력으로 써야 하면 **Lua 스크립트**(Redis 서버 안에서 여러 명령을 한 번에 실행하는 작은 프로그램)를 써요.
- 실험(Redis 8.x, `redis-benchmark`, 같은 머신 안)에서 `GET`이 초당 약 33만 건이었는데, 16개씩 파이프라이닝하니 초당 약 417만 건이 나왔어요. 가상 머신 위라 절대값보다는 "왕복을 줄이면 크게 달라진다"는 경향만 봐 주세요.
- 느린 명령은 **SLOWLOG**(오래 걸린 명령 기록), `LATENCY` 모니터, `redis-cli --latency`로 찾아요.
- 같은 초에 키가 한꺼번에 많이 만료되는 것도 메인 스레드를 막는 원인이에요. → [만료와 퇴출](../expire-eviction/)
- 여러 CPU 코어를 쓰고 싶으면 한 머신에 인스턴스를 여러 개 띄우거나 **샤딩**(데이터를 여러 서버에 나눠 담기)해요. → [복제와 클러스터](../replication-cluster/)

## 면접 질문

<details>
<summary>Q. Redis는 왜 빠른가요?</summary>

**답변(30초)** 크게 세 가지예요. 첫째, 데이터를 메모리에 두고 읽고 써서 디스크를 기다리지 않아요. 둘째, 한 스레드가 I/O 멀티플렉싱으로 여러 연결을 지켜보며 블로킹 없이 처리하고, 명령 하나가 마이크로초 미만으로 끝나요. 셋째, 명령 실행이 한 스레드라 락 경쟁이나 스레드끼리 다툴 일이 없어요. 그래서 Redis에서는 CPU보다 메모리나 네트워크가 먼저 병목이 돼요.

**꼬리질문**
- Q. 메모리에 두면 꺼질 때 데이터가 다 날아가지 않나요? → RDB 스냅숏이나 AOF 명령 기록으로 디스크에 영속화할 수 있어요. 다만 설정에 따라 잃을 수 있는 범위가 달라요.
- Q. 인메모리의 단점은요? → 데이터가 메모리보다 클 수 없어요. `maxmemory`에 닿으면 쓰기가 에러 나거나, 퇴출 정책에 따라 키가 지워져요.
</details>

<details>
<summary>Q. 싱글 스레드인데 동시에 들어오는 요청은 어떻게 처리하나요?</summary>

**답변(30초)** I/O 멀티플렉싱과 이벤트 루프로 처리해요. 메인 스레드가 리눅스의 epoll 같은 기능으로 수많은 연결을 한꺼번에 지켜보다가, 데이터가 도착한 연결만 골라 명령을 읽어요. 그리고 그 명령들을 한 줄로 세워 하나씩 실행해요. 명령 하나가 아주 짧게 끝나서, 순서대로 처리해도 사용자 입장에선 동시에 처리되는 것처럼 보여요.

**꼬리질문**
- Q. 비슷한 구조를 가진 다른 기술은요? → 공식 문서가 Node.js와 비슷하다고 비유해요. 한 스레드가 이벤트를 돌며 처리해요.
</details>

<details>
<summary>Q. 싱글 스레드라서 생기는 문제와 주의할 점은요?</summary>

**답변(30초)** 오래 걸리는 명령 하나가 메인 스레드를 붙잡으면 다른 모든 요청이 기다려요. 대표적인 게 운영 환경의 `KEYS *`예요. 실험에서 100만 키에 `KEYS *`가 61ms 걸리는 동안, 3µs면 끝날 `PING`이 응답까지 50ms 기다렸어요. 그래서 명령의 시간 복잡도를 확인하고, 전체 키 순회는 SCAN으로 나눠 하고, 큰 키 삭제는 `UNLINK`처럼 뒤에서 지우는 방법을 써요.

**꼬리질문**
- Q. 느린 명령은 어떻게 찾아요? → SLOWLOG로 오래 걸린 명령을 보고, `LATENCY` 모니터나 `redis-cli --latency`로 지연을 재요.
- Q. GET도 위험한가요? → GET, SET, LPUSH는 상수 시간이라 괜찮아요. 원소를 많이 다루는 SORT, SUNION 같은 명령이 위험해요.
</details>

<details>
<summary>Q. Redis는 싱글 스레드인가요? 6.0 이후는요?</summary>

**답변(30초)** 명령 실행은 지금도 싱글 스레드예요. 다만 "스레드가 하나"는 아니에요. 2.4부터 디스크 I/O 같은 느린 일은 백그라운드 스레드가, 4.0부터 큰 데이터 삭제는 lazy free가 맡아요. 6.0에 생긴 I/O 스레드도 소켓 읽기·쓰기와 명령 해석만 나눠 하고, 실행은 메인 스레드가 해요. 그래서 명령 단위 원자성은 그대로 유지돼요.

**꼬리질문**
- Q. io-threads는 언제 켜요? → 기본은 꺼져 있어요. 4코어 이상이고, 코어 하나는 남겨 두고, 네트워크 처리 때문에 CPU가 실제로 병목일 때만 켜라고 설정 파일이 권해요.
- Q. 멀티코어를 제대로 쓰려면요? → 한 머신에 인스턴스를 여러 개 띄우거나 클러스터로 샤딩해요.
</details>

<details>
<summary>Q. KEYS 대신 SCAN을 쓰는 이유와 SCAN의 한계는요?</summary>

**답변(30초)** KEYS는 모든 키를 한 번에 훑어서 그동안 서버가 다른 요청을 못 받아요. SCAN은 커서를 주고받으며 조금씩 나눠 훑어서, 호출 사이사이에 다른 요청이 끼어들 수 있어요. 다만 전체를 훑는 총 비용은 SCAN도 O(N)으로 같아요. 그리고 같은 키가 중복으로 나올 수 있고, 순회 중 바뀐 키는 나올 수도 안 나올 수도 있어서 앱이 이걸 감안해야 해요.

**꼬리질문**
- Q. COUNT 100이면 100개가 오나요? → 아니에요. 한 번에 할 일의 힌트일 뿐이에요. MATCH를 쓰면 빈 결과가 와도 커서가 0이 아니면 계속 불러야 해요.
- Q. 더 나은 방법은요? → 키 목록이 자주 필요하면 Set으로 목록을 따로 관리해서 처음부터 전체 순회를 안 하게 설계해요.
</details>

## 서술형 연습

<details>
<summary>상황: 배포 후 매시 정각마다 Redis 응답이 수십~수백 ms로 튀고 API 타임아웃이 납니다. 조사해 보니 매시 도는 배치가 `KEYS session:*`로 오래된 세션을 찾아 지우고 있었습니다.</summary>

**상황 파악**
평소엔 멀쩡하다가 **정해진 시각에만** 모든 API가 느려진다면, 그 시각에 도는 작업이 Redis를 붙잡고 있을 가능성이 커요. Redis는 명령 실행이 싱글 스레드라, 한 명령이 오래 걸리면 다른 요청이 전부 줄 서서 기다려요. 먼저 SLOWLOG로 그 시각에 오래 걸린 명령이 `KEYS`인지 확인해요.

**원인 후보**
1. `KEYS session:*`가 전체 키를 O(N)으로 훑으면서 메인 스레드를 수십 ms 이상 붙잡아요. 세션이 늘수록 더 길어져요.
2. 찾은 세션을 한꺼번에 `DEL`하면서 삭제도 메인 스레드를 오래 써요.
3. 같은 시각에 대량 만료가 겹쳐 지연을 키웠을 수도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `KEYS`를 `SCAN MATCH session:* COUNT n` 반복으로 교체, 삭제는 `UNLINK` | 코드 수정이 작음. 한 번에 서버를 붙잡는 시간이 아주 짧아져 다른 요청이 끼어듦 | 전체 순회 시간은 오히려 길어질 수 있음. 중복 반환·순회 중 변경 키 누락 가능 → 앱이 처리해야 함 |
| B. 세션 키에 **TTL**(만료 시간)을 걸어 Redis가 알아서 지우게 함 | 배치 자체가 필요 없어짐. 가장 단순 | 기존 세션 키에 TTL을 붙이는 이관 작업 필요. 만료가 한 시각에 몰리지 않게 시간을 흩어야 함 |
| C. 세션 키 목록을 Set으로 따로 관리하고 그 Set만 순회 | 전체 키를 훑을 일이 사라짐 | 세션 생성·삭제마다 Set도 같이 고쳐야 해서 코드가 늘고, 둘이 어긋날 위험 |

**내가 고를 방법**
당장 장애를 멈추려면 A로 바꿔요. 변경이 작고, 서버를 붙잡는 시간이 호출당 마이크로초 단위로 줄어요. 그다음 근본 해결로 B를 적용해 "오래된 세션 지우기"라는 일 자체를 Redis 만료에 맡겨요. 적용 후 정각의 SLOWLOG와 API **p99 지연**(요청 100개 중 가장 느린 1개 정도의 응답 시간)이 평소 수준으로 돌아왔는지 확인해요.

**채점 포인트**: 싱글 스레드 명령 실행, KEYS의 O(N)과 운영 사용 금지, SLOWLOG로 확인, SCAN의 커서·중복·누락, SCAN도 총 비용은 O(N), DEL 대신 UNLINK, TTL로 배치 제거, 적용 후 지연 검증.
</details>

<details>
<summary>상황: 트래픽이 늘어 Redis 한 대가 버거워졌습니다. 응답 지연이 늘고 CPU 사용률이 높습니다.</summary>

**상황 파악**
"버거움"의 원인이 무엇인지부터 나눠요. 트래픽이 평소 수준인데 CPU가 높다면 **느린 명령**을 먼저 의심해요. 트래픽이 정말 늘었다면 **왕복 횟수**, **네트워크 처리**, **데이터 양** 중 어디가 병목인지 봐요.

**원인 후보**
1. O(N) 명령(**빅키**(원소가 아주 많은 키)에 `HGETALL`, `LRANGE 0 -1`, `SMEMBERS` 등)이 메인 스레드를 오래 써요.
2. 한 요청에서 `GET`을 수십 번 따로 보내 왕복이 많아요. 요청마다 연결을 새로 맺는 코드도 원인이 돼요.
3. 연결 수와 데이터 송수신이 많아 네트워크 읽기·쓰기 자체가 CPU를 써요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 느린 명령 정리 + `MGET`/파이프라이닝 + 커넥션 풀 | 코드만 고쳐서 바로 효과. 실험에서도 파이프라이닝이 처리량을 크게 올림 | 원인이 데이터 양이면 한계가 있음 |
| B. `io-threads` 켜기 | 네트워크 처리가 병목이면 설정만으로 개선 | 4코어 이상 필요, 명령 실행은 여전히 한 스레드라 느린 명령 문제는 못 풂. 실행 중 변경 불가 |
| C. **레플리카**(원본을 복사해 두는 서버)로 읽기 분산 | 읽기 부하를 여러 대로 나눔 | 복제가 기본적으로 **비동기**(원본이 복사본 반영을 기다리지 않음)라 방금 쓴 값이 레플리카에 아직 없을 수 있음 |
| D. **Cluster**(키를 여러 서버에 나눠 담는 Redis 구성)로 샤딩 | 메모리와 처리량을 여러 대로 늘림 | 운영이 복잡해지고, 여러 키를 한 번에 다루는 명령은 키들이 같은 **해시 슬롯**(키가 배정되는 칸)에 있을 때만 됨 |

**내가 고를 방법**
먼저 SLOWLOG와 코드 리뷰로 A를 해요. 가장 싸고 원인을 직접 없애요. 그래도 네트워크 처리 때문에 CPU가 병목이면 B를, 읽기가 대부분이면 C를 더해요. 데이터가 한 대 메모리에 안 들어갈 만큼 커질 때 D로 가요. 각 단계 후에 지연과 CPU를 다시 재서 다음 단계가 필요한지 판단해요.

**채점 포인트**: 원인부터 구분(느린 명령/왕복/네트워크/용량), 명령 실행은 싱글 스레드라 io-threads로 느린 명령 해결 불가, 파이프라이닝·MGET·커넥션 풀, 레플리카 복제 지연, 클러스터 샤딩의 복잡도, 적용 후 측정.
</details>

## 필기 포인트

- Redis = **RE**mote **DI**ctionary **S**erver. 키-값 저장소, 값이 자료구조.
- **명령 실행**은 싱글 스레드. 백그라운드 스레드(2.4+), lazy free(4.0+), I/O 스레드(6.0+)는 있음.
- 6.0 I/O 스레드: 소켓 읽기·쓰기·해석만. **명령 병렬 실행 아님**. 기본값 `io-threads 1`(꺼짐).
- `maxmemory` 도달 시 기본은 **쓰기 에러, 읽기 가능**. 퇴출 정책 설정 시 키 삭제.
- `KEYS`: O(N), 운영 금지. `SCAN`: 호출 1번 O(1), 전체 순회 O(N), 중복 반환 가능, COUNT는 힌트(기본 10).
- 디스크 저장 형식: RDB(스냅숏), AOF(명령 기록).
