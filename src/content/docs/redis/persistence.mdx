:::tip[한 줄 요약]
Redis 영속성은 **RDB**(정해진 간격으로 메모리 전체를 찍어 두는 스냅숏)와 **AOF**(쓰기 명령을 로그로 이어 붙여 재시작 때 다시 실행)가 있어요. RDB는 파일이 작고 재시작이 빠르지만 **비정상 종료 때 마지막 스냅숏 이후를 잃고**, AOF는 기본 설정(everysec)에서 **최대 약 1초치**만 잃어요. 그래서 둘을 같이 켜는 걸 공식 문서가 권해요.
:::

:::note[처음이라면 여기까지]
① Redis는 데이터를 메모리에 두니 그냥 꺼지면 날아가요. 그래서 디스크에 남기는 방법이 두 가지 있어요.

② **RDB**는 "정해진 간격으로 사진 찍기", **AOF**는 "쓰기 명령을 일기처럼 계속 적기"예요.

③ RDB는 마지막 사진 이후를, AOF는 기본 설정에서 약 1초치를 잃을 수 있어요. 그래서 둘을 같이 켜는 걸 권해요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

하루 동안 있었던 일을 남기는 방법이 두 가지 있다고 해 봐요.

**사진 찍기(RDB)** 는 한 시간에 한 번 방 전체를 사진으로 찍어 두는 거예요. 사진 한 장만 보면 그때 방이 어땠는지 바로 알 수 있고, 앨범도 얇아요. 대신 사진을 찍은 뒤에 방이 바뀌었는데 갑자기 집에 불이 나면, 마지막 사진 이후의 변화는 기록이 없어요.

**일기 쓰기(AOF)** 는 "컵을 책상에 놓음", "책을 꺼냄"처럼 한 일을 하나하나 적는 거예요. 일기를 처음부터 다시 따라 하면 방을 그대로 되살릴 수 있고, 잃는 건 마지막 몇 줄 정도예요. 대신 일기장이 점점 두꺼워지고, 처음부터 다시 따라 하는 데 시간이 걸려요. 그래서 가끔 "지금 방 상태"만 요약해서 일기장을 새로 써요(**rewrite**).

똑똑한 방법은 둘을 섞는 거예요. 일기장 첫 장에 방 사진을 붙이고, 그 뒤로 바뀐 것만 적어요. Redis의 **하이브리드 영속성**이 바로 이 모양이에요.

단, 실제로는 사진을 찍는 동안 방 주인(메인 프로세스)이 멈춰 있지 않아요. 분신(자식 프로세스)을 만들어 분신이 사진을 찍고, 주인은 계속 손님을 받아요. 이 분신을 만드는 순간과 그 뒤 메모리 사용이 운영에서 문제가 되기도 해요.

## 제대로 알기

### 1. 왜 영속성이 필요한가

Redis는 데이터를 **메모리**(RAM, 빠르지만 전원이 꺼지면 지워지는 저장 공간)에 둬요. 그래서 프로세스가 죽거나 서버가 재부팅되면 메모리 내용은 사라져요. **영속성**(persistence, 데이터를 디스크 같은 오래 남는 곳에 기록해 재시작 후에도 되살리는 것)은 이걸 막는 장치예요.

공식 문서가 꼽는 선택지는 네 가지예요.

| 선택지 | 한 줄 설명 |
|---|---|
| RDB만 | 정해진 간격으로 시점 스냅숏 저장 |
| AOF만 | 쓰기 명령을 로그로 남기고 재시작 때 재실행 |
| 둘 다 | RDB와 AOF를 동시에 켬 |
| 끔 | 디스크에 아무것도 안 남김(순수 캐시 용도) |

**기본 설정** Redis는 RDB만 켜져 있어요(`appendonly no`). 그래서 "인메모리라 껐다 켜면 다 날아간다"는 말은 기본 설정 기준으로는 틀려요. 아래 실험에서 볼 거예요.

### 2. RDB: 사진 찍기

**RDB**(Redis Database)는 어느 한 시점의 메모리 전체를 압축된 파일 하나(`dump.rdb`)로 저장해요.

**언제 저장하나**

- `save <초> <변경 수>` 조건을 걸어 두면 자동으로 저장해요. 설정 파일에 따로 없을 때 기본값은 세 줄이에요.
  - 3600초(1시간) 안에 1건 이상 변경
  - 300초(5분) 안에 100건 이상 변경
  - 60초 안에 1만 건 이상 변경
- 셋 중 하나라도 맞으면 저장해요. `save ""`로 완전히 끌 수 있어요.
- 수동으로는 `BGSAVE`(백그라운드 저장)를 써요. `SAVE`는 메인 스레드에서 직접 저장해서 끝날 때까지 **모든 요청이 막혀요.** 운영에서는 쓰지 않아요.

**어떻게 저장하나 (BGSAVE)**

1. 메인 프로세스가 **fork**(지금 프로세스를 복제해 자식 프로세스를 만드는 것)해요.
2. 자식이 메모리 내용을 **임시 파일**에 써요. 부모는 계속 요청을 받아요.
3. 다 쓰면 임시 파일 이름을 `dump.rdb`로 바꿔 기존 파일을 한 번에 교체해요(rename, 중간 상태가 없는 원자적 교체).

그래서 RDB 파일은 만들어진 뒤 고쳐지지 않아요. 서버가 도는 중에 복사해도 안전해서, cron으로 주기적으로 다른 곳에 백업하기 좋아요.

**copy-on-write가 왜 중요한가**

fork하면 자식이 부모 메모리를 통째로 복사할 것 같지만, 그러면 너무 느리고 메모리도 두 배로 들어요. 실제로는 **copy-on-write**(COW, 처음엔 같은 메모리를 같이 보다가 누군가 고칠 때 그 부분만 복사하는 방식)를 써요.

- fork 직후 부모와 자식은 같은 메모리 페이지를 공유해요.
- 부모가 키를 바꾸면 **그 페이지만** 복사돼요.
- 자식은 계속 fork 시점의 모습을 봐서, 일관된 스냅숏을 쓸 수 있어요.

이 말은 거꾸로, **저장하는 동안 쓰기가 많을수록 복사되는 페이지가 늘어 메모리 사용이 커진다**는 뜻이에요. 쓰기가 아주 많으면 최악에는 데이터 크기의 두 배 가까이 늘 수 있다고 흔히 말해요. 다만 이 배수는 COW 원리에서 나오는 일반적인 설명이고, 공식 문서에 정확한 수치로 적혀 있지는 않아요.

**RDB의 장단점**

| 장점 | 단점 |
|---|---|
| 파일 하나, 압축됨 → 백업·원격 보관에 좋음 | **비정상 종료**(정전, `kill -9`) 시 마지막 스냅숏 이후 유실 |
| 디스크 쓰기는 자식이 함 → 부모 성능 영향 적음 | 보통 간격이 몇 분 이상이라 "최근 몇 분"을 잃을 각오 필요 |
| 큰 데이터에서 AOF보다 재시작이 빠름 | 저장마다 fork 필요 → 데이터가 크고 CPU가 약하면 수 ms~최대 1초 정도 응답이 멈출 수 있음 |

<Aside type="caution" title="저장 실패하면 쓰기가 멈춰요">
`stop-writes-on-bgsave-error yes`가 기본이에요. save 조건이 걸려 있는데 마지막 BGSAVE가 실패하면(예: 디스크 가득 참) Redis가 **쓰기 명령을 거부**해요. 저장이 다시 성공하면 자동으로 풀려요.
</Aside>

### 3. AOF: 일기 쓰기

**AOF**(Append Only File)는 쓰기 명령을 받을 때마다 파일 끝에 덧붙여요. 형식은 Redis가 네트워크로 주고받는 프로토콜(RESP)과 같아서 사람이 읽을 수 있어요. 재시작하면 이 명령들을 처음부터 다시 실행해 데이터를 되살려요.

**appendfsync: 언제 디스크에 확정하나**

파일에 "썼다"고 바로 디스크에 들어가는 건 아니에요. 운영체제는 일단 메모리(페이지 캐시)에 모아 뒀다가 나중에 디스크로 내려요. **fsync**는 "지금 당장 디스크에 내려라"라는 시스템 호출이에요. 이걸 얼마나 자주 하느냐가 유실 범위를 정해요.

| 옵션 | 동작 | 속도 | 장애 시 유실 |
|---|---|---|---|
| `always` | 명령을 붙일 때마다 fsync. 동시에 온 명령은 한 번에 모아 fsync(그룹 커밋) | 매우 느림 | 거의 0 |
| `everysec` (기본, 권장) | 1초마다 fsync. 백그라운드 스레드가 함 | 빠름 | 최대 약 1초 |
| `no` | fsync를 OS에 맡김. 리눅스는 보통 약 30초마다 | 가장 빠름 | 수십 초 |

**AOF의 장단점**

| 장점 | 단점 |
|---|---|
| 내구성이 훨씬 높음 | 같은 데이터면 RDB보다 파일이 큼 |
| 덧붙이기만 해서 정전에도 손상 위험이 적음. 끝 명령이 잘려도 복구 가능 | fsync 정책에 따라 RDB보다 느릴 수 있음 |
| 실수로 `FLUSHALL` 해도 rewrite 전이면 마지막 명령을 지우고 되살릴 수 있음 | 쓰기가 아주 많을 때 최대 지연 보장은 RDB가 나음 |

**rewrite: 일기장 다시 쓰기**

카운터를 100번 `INCR`하면 AOF에는 100줄이 쌓여요. 하지만 필요한 건 "최종값 100" 하나예요. **AOF rewrite**는 **현재 메모리 데이터**를 기준으로, 그 상태를 만드는 최소한의 내용으로 파일을 새로 써요. 기존 AOF 파일을 읽어서 줄이는 게 아니에요.

- 수동: `BGREWRITEAOF`
- 자동(기본): 마지막 rewrite 때보다 크기가 100% 커지고(`auto-aof-rewrite-percentage 100`) 64MB 이상이면(`auto-aof-rewrite-min-size 64mb`)
- rewrite도 fork해서 백그라운드로 하므로 서비스는 멈추지 않아요.
- BGSAVE와 rewrite는 동시에 돌지 않아요. 스냅숏 중에 `BGREWRITEAOF`를 요청하면 예약해 두고 스냅숏이 끝난 뒤 시작해요.

실험에서 `INCR c`를 100번 하니 incr 파일이 2123바이트였어요. `BGREWRITEAOF` 뒤에는 base 파일 99바이트와 빈 incr 파일로 바뀌었고, `GET c`는 그대로 100이었어요.

### 심화: 4. Redis 7.0+의 multi-part AOF

7.0부터 AOF는 파일 하나가 아니라 **디렉터리**(기본 `appendonlydir`)에 여러 파일로 나뉘어요.

| 파일 | 역할 |
|---|---|
| base 파일 (최대 1개) | rewrite 시점의 전체 스냅숏 |
| incr 파일 (여러 개 가능) | base 이후 바뀐 명령 |
| manifest 파일 | 어떤 파일을 어떤 순서로 읽을지 적은 목록 |

rewrite 흐름은 이래요.

1. fork → 자식이 새 base를 임시 파일에 써요.
2. 그동안 부모는 **새 incr 파일**을 열어 새 쓰기를 계속 기록해요.
3. 자식이 끝나면 부모가 "새 base + 새 incr"로 임시 manifest를 만들고 원자적으로 교체해요.
4. 옛 base와 incr를 지워요.

중간에 실패해도 옛 base + 옛 incr + 새 incr로 데이터가 온전해요.

<Aside type="note" title="7.0 미만은 달라요">
예전에는 `appendonly.aof` 파일 하나였고, rewrite 중 들어온 쓰기를 **메모리 버퍼**에 쌓았다가 마지막에 붙였어요. 그래서 메모리를 많이 쓰고, 같은 쓰기가 디스크에 두 번 기록되고, 끝에서 멈칫할 수 있었어요. 블로그 글이 옛 방식을 설명하고 있을 수 있으니 버전을 확인하세요.
</Aside>

### 5. 하이브리드: 사진 붙인 일기장

`aof-use-rdb-preamble yes`(기본)면 rewrite할 때 base 파일을 **RDB 형식**으로 써요. 7.0+에서는 파일 이름이 `appendonly.aof.N.base.rdb`가 돼요.

- 앞부분(base)은 RDB라 로드가 빨라요.
- 뒷부분(incr)은 AOF라 최근 변경까지 남아요.

설정 파일 주석은 RDB 형식 쪽이 항상 빠르고 효율적이며, 이 옵션을 끄는 건 하위 호환용이라고 설명해요.

### 6. 세 방식 한눈에 비교

| | RDB | AOF | 하이브리드 (AOF + RDB preamble) |
|---|---|---|---|
| 저장하는 것 | 시점 스냅숏 | 쓰기 명령 로그 | base는 스냅숏, 이후는 명령 로그 |
| 장애 시 유실 | 마지막 스냅숏 이후 (몇 분 단위) | everysec면 최대 약 1초 | AOF와 같음 |
| 파일 크기 | 작음 | 큼 | AOF보다 작음 |
| 재시작 속도 | 빠름 | 느림 (명령 재실행) | base는 빠르게, incr만 재실행 |
| fork 빈도 | 저장할 때마다 | rewrite 때만 | rewrite 때만 |
| 백업 | 파일 하나 복사로 쉬움 | 디렉터리 단위 | 디렉터리 단위 |
| 기본값 | 켜짐 | 꺼짐 (`appendonly no`) | AOF를 켜면 자동 적용 |

**재시작하면 무엇으로 복원하나**

1. AOF가 켜져 있으면 AOF(manifest 순서대로 base → incr)로 복원해요. 가장 완전한 데이터라서예요.
2. AOF가 꺼져 있고 `dump.rdb`가 있으면 RDB로 복원해요.
3. 둘 다 없으면 빈 상태로 시작해요.

즉 "둘 다 켜면 RDB로 빨리 올라온다"는 틀려요. AOF를 써요. 다만 하이브리드 덕분에 base가 RDB 형식이라 빨라요.

**공식 권장**

- PostgreSQL 수준의 안전이 필요하면 **둘 다** 켜요.
- 몇 분 유실을 감수할 수 있으면 **RDB만**.
- **AOF만** 쓰는 건 권하지 않아요. 백업, 빠른 재시작, AOF 엔진 버그 대비용으로 RDB가 있는 게 좋다고 해요.

### 심화: 7. 실험: 정말 날아가나?

키 1개를 쓰고 Redis를 재시작한 뒤 키 개수(`DBSIZE`)를 봤어요. 정상 종료는 `docker restart`(SIGTERM, "이제 꺼 주세요" 신호), 강제 종료는 `docker kill`(SIGKILL, 즉시 죽이기, 정전과 비슷)로 했어요.

| 설정 | 정상 종료 후 재시작 | 강제 종료 후 재시작 |
|---|---|---|
| 영속성 끔 (`save ""`, AOF 끔) | **유실** (0개, 디스크에 파일 없음) | **유실** (0개, 디스크에 파일 없음) |
| RDB만 (기본 save, AOF 끔) | **복원** (1개) | **유실** (0개) |
| AOF만 (`save ""`, everysec) | **복원** (1개, INCR 값도 유지) | **복원** (쓰고 2초 뒤 kill, 쓰자마자 kill 모두 1개) |

**RDB만 켰는데 정상 종료는 왜 남았을까요?** Redis는 SIGTERM을 받으면, save 조건이 설정돼 있을 때 꺼지기 직전에 RDB를 한 번 저장해요. 로그에도 "Saving the final RDB snapshot before exiting." → "DB saved on disk"가 찍혔고, 재시작 뒤 "Done loading RDB, keys loaded: 1"이 나왔어요.

**강제 종료는 왜 날아갔을까요?** SIGKILL은 저장할 틈을 주지 않아요. 게다가 키 1개만 썼으니 "1시간 안에 1건" 조건을 아직 못 채워 자동 저장도 없었어요.

**AOF는 강제 종료도 버텼어요.** 쓰고 2초가 지나 everysec의 fsync가 이미 끝났기 때문이에요. 로그에 base 파일(`appendonly.aof.1.base.rdb`)을 읽고 incr 파일(`appendonly.aof.1.incr.aof`)을 이어 읽었다고 나왔어요. 사실 쓰자마자 kill 해 봐도 남았어요. 프로세스만 죽으면 이미 write()한 내용은 OS 페이지 캐시에 있어서 OS가 디스크로 내려 주거든요. everysec의 "최대 약 1초" 유실은 OS나 전원까지 꺼져 페이지 캐시가 사라질 때의 이야기예요.

정리하면 "RDB만 켜면 재시작 때 날아간다"가 아니라 **"RDB만 켜면 비정상 종료 때 마지막 스냅숏 이후가 날아간다"** 가 정확해요.

### 8. 운영에서 알아 둘 것

- **fork 지연 확인**: `INFO stats`의 `latest_fork_usec`(마지막 fork에 걸린 마이크로초)를 봐요. `INFO persistence`가 아니라 `INFO stats`에 있어요. 실험(키 20만 개, RDB 약 3.7MB)에서는 227µs였어요. 데이터가 작아서 짧게 나온 거예요.
- **COW 메모리 확인**: `INFO persistence`의 `rdb_last_cow_size`가 마지막 저장 때 COW로 복사된 메모리예요. 같은 실험에서 약 400KB였어요.
- **저장 상태 확인**: `rdb_last_bgsave_status`가 `ok`인지 모니터링해요.
- **잘린 AOF**: 쓰다가 죽어 끝이 잘렸으면 `aof-load-truncated yes`(기본)라 마지막 불완전한 명령만 버리고 올라와요. **중간**이 손상됐으면 시작을 거부하고, `redis-check-aof --fix`로 고쳐야 해요. 이때 손상 지점 이후는 버려질 수 있어요.
- **RDB → AOF 전환 함정**: 설정 파일만 `appendonly yes`로 고치고 재시작하면, Redis가 **빈 AOF**로 시작해서 데이터가 사라질 수 있어요. 운영 중에 `CONFIG SET appendonly yes`로 켜서 AOF를 만들게 하고, 완료를 확인한 뒤 `CONFIG REWRITE`로 설정 파일에 반영해요.
- **영속성은 고가용성이 아니에요**: 파일은 그 서버 디스크에 있어서 서버가 통째로 죽으면 같이 못 써요. 서버 장애 대비는 [복제와 클러스터](../replication-cluster/)에서 다뤄요.

## 면접 질문

<details>
<summary>Q. Redis는 인메모리인데 데이터를 어떻게 보존하나요? RDB와 AOF 차이는요?</summary>

**답변(30초)** RDB와 AOF 두 가지로 디스크에 남겨요. RDB는 정해진 간격으로 메모리 전체를 스냅숏 파일 하나로 저장해서 파일이 작고 재시작이 빠르지만, 비정상 종료 때 마지막 스냅숏 이후 데이터를 잃어요. AOF는 쓰기 명령을 로그로 덧붙이고 재시작 때 다시 실행해서, 기본값 everysec 기준 최대 약 1초치만 잃어요. 대신 파일이 크고 재시작이 느려서, 공식 문서는 둘을 같이 쓰는 걸 권해요.

**꼬리질문**
- Q. 기본 설정이면 재시작할 때 데이터가 날아가나요? → 기본은 RDB만 켜져 있고, 정상 종료 때는 꺼지기 직전에 RDB를 저장해서 남아요. 유실은 kill -9나 정전 같은 비정상 종료 때 생겨요.
- Q. 둘 다 켜면 재시작 때 뭘로 복원해요? → AOF로 복원해요. 더 완전한 데이터라서예요.
</details>

<details>
<summary>Q. 캐시 용도의 Redis에도 영속성을 켜야 하나요?</summary>

**답변(30초)** 원본이 DB에 있는 순수 캐시라면 꺼도 돼요. 끄면 fork와 디스크 쓰기가 없어져 가볍고, 데이터가 날아가도 DB에서 다시 채우면 돼요. 다만 재시작 직후 캐시가 비어 요청이 전부 DB로 몰리는 콜드 스타트가 생겨요. 그게 부담이면 RDB만 켜서 재시작 때 캐시를 빠르게 되살리는 절충을 써요.

**꼬리질문**
- Q. 영속성을 켜면 고가용성도 되나요? → 아니에요. 파일은 그 서버에 있어서 서버가 죽으면 같이 못 써요. 장애 대비는 복제와 Sentinel이 맡아요.
</details>

<details>
<summary>Q. appendfsync 옵션별 차이와 유실 범위는요?</summary>

**답변(30초)** fsync, 즉 디스크에 확정하는 시점을 정하는 옵션이에요. `always`는 명령마다 fsync해서 유실이 거의 없지만 매우 느려요. 기본값 `everysec`는 1초마다 백그라운드 스레드가 fsync해서 빠르고, 최대 약 1초치를 잃을 수 있어요. `no`는 OS에 맡겨서 가장 빠르지만 리눅스 기준 보통 수십 초치를 잃을 수 있어요.

**꼬리질문**
- Q. always면 절대 안 잃나요? → 디스크와 OS가 fsync를 정직하게 해 준다는 전제에서 거의 0이에요. 처리량이 크게 떨어져서 잘 안 써요.
- Q. always는 매 명령 fsync면 너무 느리지 않나요? → 동시에 들어온 명령들을 한 번 쓰고 한 번 fsync하는 그룹 커밋으로 비용을 줄여요.
</details>

<details>
<summary>Q. AOF 파일이 계속 커지면 어떻게 하나요?</summary>

**답변(30초)** AOF rewrite로 줄여요. 현재 메모리 데이터를 기준으로, 그 상태를 만드는 최소한의 내용으로 파일을 새로 써요. 예를 들어 INCR 100번은 최종값 하나로 줄어요. 기본 설정에서는 마지막 rewrite보다 두 배로 커지고 64MB 이상이면 자동으로 하고, fork해서 백그라운드로 하니 서비스는 안 멈춰요.

**꼬리질문**
- Q. Redis 7에서 뭐가 바뀌었나요? → AOF가 base, incr, manifest 파일로 나뉜 multi-part AOF가 됐어요. rewrite 중 쓰기를 메모리 버퍼에 쌓지 않고 새 incr 파일에 바로 써서, 메모리 낭비와 이중 쓰기가 없어졌어요.
- Q. 하이브리드 영속성이 뭐예요? → `aof-use-rdb-preamble`로 base를 RDB 형식으로 쓰는 거예요. 앞은 빠르게 로드하고 뒤는 최근 변경을 남겨요. 기본으로 켜져 있어요.
</details>

<details>
<summary>Q. RDB 저장 때 fork를 하는데, 왜 문제가 될 수 있나요?</summary>

**답변(30초)** BGSAVE는 fork로 자식 프로세스를 만들어 자식이 파일을 쓰게 해요. 그런데 fork 자체는 메인 스레드에서 일어나서, 데이터가 크면 그 순간 수 ms에서 최대 1초 정도 응답이 멈출 수 있어요. 또 copy-on-write라 부모가 키를 바꿀 때마다 그 페이지가 복사돼서, 저장 중 쓰기가 많으면 메모리가 크게 늘어요. fork 시간은 `INFO stats`의 `latest_fork_usec`로 확인해요.

**꼬리질문**
- Q. copy-on-write가 뭐예요? → fork 직후 부모와 자식이 같은 메모리를 공유하다가, 한쪽이 고칠 때 그 페이지만 복사하는 방식이에요. 덕분에 자식은 fork 시점 상태를 그대로 보고 일관된 스냅숏을 써요.
- Q. SAVE와 BGSAVE 차이는요? → SAVE는 메인 스레드에서 직접 저장해서 끝날 때까지 모든 요청이 막혀요. BGSAVE는 fork해서 백그라운드로 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 같은 회사에 Redis가 두 대 있습니다. 하나는 상품 조회 결과를 담는 캐시(원본은 MySQL), 다른 하나는 로그인 세션 저장소입니다. 두 대의 영속성 설정을 각각 어떻게 하시겠습니까?</summary>

**상황 파악**
영속성 설정은 "이 데이터를 잃으면 무슨 일이 생기나"로 정해요. 캐시는 원본이 DB에 있어서 잃어도 다시 만들 수 있어요. 세션은 Redis가 사실상 원본이라 잃으면 사용자가 강제로 로그아웃돼요.

**원인 후보(따져 볼 점)**
1. 잃었을 때의 피해: 캐시는 DB 부하 증가, 세션은 사용자 경험 손상.
2. 영속성 비용: fork 순간 지연, COW 메모리 증가, AOF 디스크 쓰기.
3. 기본 설정의 함정: 기본은 RDB만이라, 세션 서버를 그대로 두면 비정상 종료 때 최근 최대 몇십 분~1시간치(쓰기가 적을 때)를 잃을 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| 캐시 A. 영속성 끔 (`save ""`, AOF 끔) | fork·디스크 쓰기 없음, 가장 가벼움. 저장 실패로 쓰기가 막힐 일도 없음 | 재시작 직후 캐시가 비어 DB로 요청 폭증(콜드 스타트) |
| 캐시 B. RDB만 | 재시작 때 캐시를 빠르게 되살려 DB 부하 완화 | 저장 때 fork 지연·메모리 증가. 디스크 가득 차면 쓰기 거부 가능 |
| 세션 C. AOF everysec + RDB (하이브리드) | 장애 시 최대 약 1초만 유실. RDB로 백업·빠른 재시작 | 디스크 쓰기와 파일 관리 부담, rewrite 때 fork |
| 세션 D. AOF always | 유실이 거의 없음 | 처리량이 크게 떨어짐. 로그인마다 느려질 수 있음 |

**내가 고를 방법**
캐시는 **B(RDB만)** 를 고르겠어요. 캐시를 잃는 것 자체보다 재시작 직후 DB가 무너지는 게 더 위험하기 때문이에요. 캐시가 작아 금방 다시 차거나 DB가 충분히 버티면 A로 더 가볍게 가요. A를 고르면 재시작 직후 몰리는 부하를 [캐시 문제들](../cache-problems/)에서 다루는 방법으로 같이 대비해요.

세션은 **C(AOF everysec + RDB)** 를 고르겠어요. 1초 유실이면 극소수 사용자가 다시 로그인하는 정도라 감수할 만하고, always는 그 정도 이득에 비해 처리량 손해가 커요. 세션 서버가 아예 죽는 경우까지 대비하려면 영속성만으로는 부족해서 레플리카를 함께 둬요. 그리고 기존 RDB 전용 서버를 AOF로 바꿀 때는 설정 파일만 고쳐 재시작하지 않고, `CONFIG SET appendonly yes`로 켠 뒤 `CONFIG REWRITE`로 반영해요.

**채점 포인트**: 데이터를 잃었을 때 영향으로 판단(원본이 어디 있나), 기본값은 RDB만, RDB는 비정상 종료 때 마지막 스냅숏 이후 유실, everysec 최대 약 1초 유실, always의 처리량 손해, 캐시 콜드 스타트, 공식 권장(둘 다 켜기, AOF 단독 비권장), 영속성 ≠ 고가용성(복제), RDB→AOF 전환은 CONFIG SET.
</details>

<details>
<summary>상황: 평소엔 멀쩡한 Redis가 주기적으로 p99 응답 지연이 수백 ms로 튀고, 그 시각에 서버 메모리 사용량도 같이 치솟습니다. 느린 명령(SLOWLOG)에는 특별한 게 없습니다.</summary>

**상황 파악**
느린 명령이 없는데 **주기적으로** 지연과 **메모리**가 함께 튄다면, Redis가 주기적으로 하는 백그라운드 작업을 의심해요. RDB 저장(BGSAVE)과 AOF rewrite는 둘 다 fork를 하고, fork는 지연과 메모리 증가를 함께 일으킬 수 있어요.

**원인 후보**
1. **fork 지연**: fork는 메인 스레드에서 일어나서 데이터가 클수록 그 순간 요청이 멈춰요. `INFO stats`의 `latest_fork_usec`로 확인해요.
2. **COW 메모리 증가**: 저장 중 쓰기가 많으면 복사되는 페이지가 늘어 메모리가 크게 늘어요. `INFO persistence`의 `rdb_last_cow_size`로 봐요. 메모리가 모자라 **스왑**(메모리 대신 디스크를 쓰는 것)이 일어나면 지연이 훨씬 커져요.
3. **트리거 확인**: 튀는 시각이 save 조건 충족 시점이나 자동 rewrite 시점과 맞는지 로그로 맞춰 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 저장 주기 조정 (save 조건 완화, 트래픽 적은 시간에 BGSAVE) | 설정만으로 fork 횟수를 줄임 | 저장 간격이 길어져 비정상 종료 때 유실 범위가 커짐 |
| B. 마스터는 저장을 끄고 레플리카에서만 RDB 저장 | 서비스 트래픽을 받는 쪽에 fork가 없어짐 | 레플리카 운영 필요. 마스터 재시작 절차를 조심해야 함 |
| C. 메모리 여유 확보 (COW 증가분을 감당할 만큼) | 스왑을 막아 큰 지연을 없앰 | 비용 증가 |
| D. 샤딩으로 인스턴스당 데이터를 줄임 | fork 시간과 COW 크기가 같이 줄어듦 | 운영 복잡도 증가, 여러 키 명령 제약 |

**내가 고를 방법**
먼저 `latest_fork_usec`, `rdb_last_cow_size`, 로그 시각으로 원인이 fork인지 확정해요. 맞다면 바로 할 수 있는 **C(메모리 여유 확보)로 스왑부터 막고**, 레플리카가 있다면 **B로 저장을 레플리카에 넘겨요.** 마스터에 fork가 없어지니 지연 원인을 직접 없애요. 데이터가 계속 커질 예정이면 D를 계획해요. A는 유실 범위가 커지는 대가가 있어서, 데이터를 잃어도 되는 경우에만 써요. 적용 후 같은 시각의 p99 지연과 메모리를 다시 확인해요.

**채점 포인트**: BGSAVE·AOF rewrite 모두 fork, fork는 메인 스레드에서 일어남, copy-on-write로 저장 중 쓰기만큼 메모리 증가, 스왑 위험, `INFO stats`의 `latest_fork_usec`, `rdb_last_cow_size`, 레플리카에서 저장, 저장 주기와 유실 범위의 트레이드오프, 적용 후 측정.
</details>

<details>
<summary>상황: 디스크가 가득 찬 뒤로 Redis의 모든 쓰기 요청이 MISCONF 에러로 실패합니다. 읽기는 됩니다.</summary>

**상황 파악**
읽기는 되고 쓰기만 막혔다면 Redis가 일부러 쓰기를 거부하고 있는 거예요. `stop-writes-on-bgsave-error yes`(기본)라서, save 조건이 걸려 있는데 마지막 BGSAVE가 실패하면 쓰기를 막아요. 디스크가 차서 RDB 파일을 못 쓴 거예요.

**원인 후보**
1. 디스크 가득 참으로 BGSAVE 실패 (`rdb_last_bgsave_status`가 `err`).
2. 디스크를 같이 쓰는 다른 파일(로그, 오래된 백업)이 공간을 차지함.
3. AOF를 켜 뒀다면 AOF 쓰기 실패로도 같은 MISCONF가 나요. 이때는 `aof_last_write_status`를 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 디스크 공간 확보 후 BGSAVE 재시도 | 원인을 직접 해결. 저장이 성공하면 쓰기가 자동으로 풀림 | 공간 확보에 시간이 걸릴 수 있음 |
| B. `stop-writes-on-bgsave-error no` | 저장이 실패해도 쓰기는 계속됨 | 저장 실패를 모르고 지나가면, 나중에 장애 때 데이터가 하나도 없을 수 있음 |

**내가 고를 방법**
기본은 **A**예요. 데이터를 지키려고 만든 안전장치라 끄지 않아요. 다만 원본이 DB에 있는 순수 캐시 Redis라면 저장 실패보다 쓰기 중단이 더 큰 피해라서 B나 아예 영속성 끄기를 고려해요. 어느 쪽이든 `rdb_last_bgsave_status`와 디스크 사용량에 알람을 걸어 재발을 막아요.

**채점 포인트**: stop-writes-on-bgsave-error 기본 yes, 저장 성공 시 자동 해제, rdb_last_bgsave_status 모니터링, 캐시 용도면 끄는 선택지, 끌 때의 위험.
</details>

## 필기 포인트

- 기본 설정: **RDB 켜짐**(`save 3600 1 300 100 60 10000`), **AOF 꺼짐**(`appendonly no`), `appendfsync everysec`, `aof-use-rdb-preamble yes`.
- RDB 유실은 **비정상 종료** 때. 정상 종료(SIGTERM)는 종료 직전 저장함.
- `SAVE` = 메인 스레드 동기 저장(막힘), `BGSAVE` = fork 후 백그라운드.
- appendfsync: always ≈ 0 유실 / everysec 최대 약 1초 / no는 OS 의존(리눅스 보통 약 30초).
- 둘 다 켜져 있으면 재시작 시 **AOF**로 복원.
- AOF rewrite는 **현재 메모리** 기준으로 새로 씀. 자동 조건: 100% 증가 + 64MB 이상.
- 7.0+ multi-part AOF: `appendonlydir/` 안에 base(1개) + incr(여러 개) + manifest.
- `latest_fork_usec`는 **INFO stats**, `rdb_last_cow_size`·`rdb_last_bgsave_status`는 **INFO persistence**.
- 설정 파일만 `appendonly yes`로 바꾸고 재시작 → 빈 AOF로 시작해 유실 가능. `CONFIG SET` 먼저.
