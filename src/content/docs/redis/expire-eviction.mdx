:::tip[한 줄 요약]
Redis는 만료된 키를 **접근할 때 지우는 수동 방식**과 **주기적으로 무작위 샘플을 뽑아 지우는 능동 방식**을 함께 써요. 메모리가 `maxmemory`에 닿으면 **퇴출 정책**(eviction policy)에 따라 키를 지우는데, 기본값은 **noeviction**이라 아무것도 지우지 않고 **쓰기를 에러로 거절**해요.
:::

:::note[처음이라면 여기까지]
① 키에 유효기간(**TTL**)을 붙이면 시간이 지나 사라져요. Redis는 누가 그 키를 찾을 때, 그리고 주기적으로 조금씩 골라서 지워요.

② **만료**(시간이 다 됨)와 **퇴출**(메모리가 꽉 차서 강제로 지움)은 다른 이야기예요.

③ 메모리 상한(`maxmemory`)에 닿으면 기본 설정은 아무것도 안 지우고 **쓰기를 에러로 거절**해요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

편의점 냉장고에 유통기한이 붙은 우유가 가득하다고 해 봐요. 직원은 유통기한 지난 우유를 두 가지 방법으로 치워요. 하나는 **손님이 집어 들었을 때** 날짜를 보고 "아, 지났네" 하고 버리는 거예요. 다른 하나는 **10분마다 아무 칸이나 몇 개 집어서** 날짜를 확인하고, 지난 게 많이 나오면 몇 번 더 뒤져 보는 거예요. 냉장고 전체를 매번 다 뒤지면 계산을 못 하니까요.

그런데 냉장고가 꽉 찼는데 새 우유가 들어오면 어떻게 할까요? 가게마다 규칙이 달라요. "더는 안 받아요"(noeviction), "제일 오래 안 팔린 걸 빼요"(LRU), "제일 안 팔리는 걸 빼요"(LFU), "유통기한 붙은 것 중에서만 빼요"(volatile) 같은 규칙이에요.

단, 실제로는 유통기한 지난 우유는 손님 눈에 **바로 안 보여요**. 아직 냉장고에 남아 있어도 손님이 집으면 "없음"이 나와요. 물리적으로 치우는 시점만 늦을 뿐이에요.

## 제대로 알기

### 1. TTL: 키에 수명 붙이기

**TTL**(Time To Live, 남은 수명)은 "이 키는 몇 초 뒤에 사라져라"는 표시예요. 수명이 붙은 키를 공식 문서는 **volatile 키**(휘발성 키)라고 불러요.

| 명령 | 하는 일 |
|---|---|
| `EXPIRE key 60` | 60초 수명 붙이기. 성공 1, 키가 없거나 조건 때문에 못 붙이면 0 |
| `SET key v EX 60` | 값과 수명을 한 번에(원자적으로) |
| `TTL key` | 남은 초. 수명 없음 -1, 키 없음 -2 |
| `PERSIST key` | 수명 없애기 |
| `EXPIRE key 60 NX/XX/GT/LT` | 조건부(7.0+). 수명 없을 때만 / 있을 때만 / 더 길 때만 / 더 짧을 때만 |

헷갈리기 쉬운 규칙이 있어요. **값을 통째로 덮어쓰거나 지우는 명령만 TTL을 없애요.**

- TTL이 사라지는 명령: `DEL`, `SET`, `GETSET`, `*STORE` 계열
- TTL이 그대로인 명령: `INCR`, `LPUSH`, `HSET`처럼 값을 고치기만 하는 명령
- `RENAME`하면 TTL이 새 이름으로 따라가요.
- 0 이하 값으로 `EXPIRE`하면 만료가 아니라 **즉시 삭제**돼요.

실험에서 `INCR c` → `EXPIRE c 100` → `INCR c` 후 TTL은 100 그대로였고, 이어서 `SET c 5`를 하자 TTL이 -1(수명 없음)이 됐어요.

만료 시각 오차는 Redis 2.6부터 0~1ms 수준이에요.

### 2. 만료된 키는 언제 실제로 지워지나

만료 시각이 지나면 키는 **논리적으로 바로 사라져요**(조회하면 없다고 나와요). 하지만 **메모리에서 지우는 시점**은 따로예요. Redis는 두 방식을 같이 써요.

| | 수동 만료 (passive, lazy) | 능동 만료 (active) |
|---|---|---|
| 언제 | 클라이언트가 그 키에 접근할 때 | 백그라운드에서 주기적으로 |
| 방법 | 만료 시각이 지났으면 그 자리에서 삭제 | 만료가 걸린 키 중 일부를 무작위로 뽑아 검사 |
| 약점 | 아무도 안 건드리는 키는 계속 남음 | 샘플링이라 전부 바로 잡지는 못함 |

수동만 쓰면 다시는 안 읽히는 키가 메모리를 계속 차지해요. 능동만 쓰면 전체를 훑느라 서버가 멈춰요. 그래서 둘을 섞어요.

#### 심화: 능동 만료 세부 (10%와 25%를 구분하세요)

이 부분은 공식 문서 본문이 아니라 **소스 코드(`expire.c`)와 설정 파일(`redis.conf`) 기준**이에요.

1. 서버 타이머 `hz`(기본 10 = 초당 10번)에 맞춰 사이클이 돌아요.
2. DB마다 만료가 걸린 키 **20개**를 무작위로 뽑아 만료된 걸 지워요.
3. 뽑은 것 중 만료된 비율이 **10%를 넘으면** 그 자리에서 다시 뽑아요.
4. 이 반복이 CPU를 독차지하지 않게 **CPU 시간의 25%** 를 넘지 않는 시간 제한이 있어요.

<Aside type="caution" title="25%는 만료 비율이 아니에요">
오래된 블로그나 옛 설명은 "만료된 키가 **25%** 이상이면 반복한다"고 써 있어요. 현재 소스는 반복 기준이 **10%**(`ACCEPTABLE_STALE 10`)이고, **25는 CPU 시간 상한**(`SLOW_TIME_PERC 25`)이에요. 면접에서는 "샘플을 뽑아 만료 비율이 기준을 넘으면 반복하고, CPU 시간 제한이 있다"로 말하고, 숫자를 묻는다면 최신 소스 기준 10%라고 답하면 돼요.
</Aside>

`active-expire-effort`(기본 1, 최대 10)를 올리면 더 많이 샘플링해서 남아 있는 만료 키 비율을 낮춰요. 대신 CPU를 더 써요. 설정 파일 표현도 만료 키가 10% 넘게 남지 않도록 "노력"한다는 거라, **바로 지워진다는 보장은 없어요.**

실험에서 `SET tmp:n v EX 2`로 10만 개를 넣고 아무도 접근하지 않았더니, 3초 뒤 키는 1개만 남았고 지워진 10만 개는 전부 능동 만료로 처리됐어요.

#### 심화: 레플리카와 AOF

키가 만료되면 Redis는 **AOF**(명령 기록 파일)와 모든 **레플리카**(복사본 서버)에 `DEL` 명령을 만들어 보내요. 레플리카는 스스로 만료 삭제를 하지 않고 **마스터의 DEL을 기다려요.** 만료 정보는 갖고 있어서, 레플리카가 마스터로 승격되면 그때부터 직접 지워요. → [복제와 클러스터](../replication-cluster/)

### 3. 만료(expire)와 퇴출(eviction)은 다르다

| | 만료 | 퇴출 |
|---|---|---|
| 이유 | TTL이 다 됨 | 메모리 상한에 닿음 |
| 지우는 키 | 수명이 끝난 키 | **아직 살아 있는** 키 |
| 메모리 여유와 관계 | 없음 | 있음 |
| 통계(`INFO stats`) | `expired_keys` | `evicted_keys` |

### 4. maxmemory: 메모리 상한

`maxmemory`는 Redis가 데이터에 쓸 메모리 상한이에요. **기본값은 0 = 제한 없음**(64비트 기준)이에요. 그래서 아무 설정도 안 하면 Redis는 알아서 지우지 않고 OS 메모리가 바닥날 때까지 늘어나요. 캐시로 쓰려면 `maxmemory`와 정책을 **둘 다** 직접 정해야 해요.

```bash
# 실행 중에도 바꿀 수 있어요
CONFIG SET maxmemory 100mb
CONFIG SET maxmemory-policy allkeys-lru
```

동작 순서는 이래요. 데이터를 늘리는 쓰기 명령이 올 때마다 메모리를 확인하고, 상한을 넘었으면 정책대로 키를 지워 상한 아래로 돌려요. 큰 값 하나를 쓰면 순간적으로 상한을 꽤 넘을 수 있어요.

주의할 점이 하나 더 있어요. **레플리카로 보내는 출력 버퍼와 AOF 버퍼는 maxmemory 계산에서 빠져요**(`INFO memory`의 `mem_not_counted_for_evict`). 그래서 실제 프로세스 메모리는 maxmemory보다 커요. 복제나 영속성을 쓰면 maxmemory를 실제 RAM보다 여유 있게 잡으라고 공식 문서가 권해요.

### 5. 퇴출 정책 (8.6+ 기준 10가지)

면접에서 흔히 "8가지"라고 말하는 건 **Redis 8.6 이전 기준**이에요. 8.6부터 LRM 정책 2개가 추가돼 **10가지**가 됐어요(실험한 8.10에서 `allkeys-lrm` 설정 성공).

| 정책 | 대상 키 | 지우는 기준 |
|---|---|---|
| **noeviction** (기본) | 지우지 않음 | 데이터를 늘리는 쓰기는 에러, 읽기는 정상 |
| allkeys-lru | 전체 | 가장 오래 **안 읽은/안 쓴** 키 |
| allkeys-lfu | 전체 | 가장 **덜 자주** 쓴 키 (4.0+) |
| allkeys-random | 전체 | 무작위 |
| volatile-lru | TTL 있는 키만 | LRU |
| volatile-lfu | TTL 있는 키만 | LFU (4.0+) |
| volatile-random | TTL 있는 키만 | 무작위 |
| volatile-ttl | TTL 있는 키만 | 남은 TTL이 가장 짧은 키 |
| allkeys-lrm | 전체 | 가장 오래 **수정** 안 된 키 (8.6+) |
| volatile-lrm | TTL 있는 키만 | LRM (8.6+) |

용어를 풀면 이래요.

- **LRU**(Least Recently Used): 마지막으로 쓴 지 가장 오래된 것부터 지워요.
- **LFU**(Least Frequently Used): 쓰인 횟수가 가장 적은 것부터 지워요.
- **LRM**(Least Recently Modified): 마지막으로 **수정**된 지 가장 오래된 것부터 지워요. 읽기는 셈에 넣지 않아요.

외우는 요령은 **"범위(allkeys / volatile) × 기준(lru / lfu / lrm / random)" + volatile-ttl + noeviction**이에요.

<Aside type="caution" title="volatile-* 함정">
volatile-* 정책인데 TTL 붙은 키가 하나도 없으면, 지울 후보가 없어서 **noeviction처럼 쓰기 에러**가 나요.
</Aside>

#### noeviction에서 메모리가 차면

쓰기는 이런 **OOM**(Out Of Memory, 메모리 부족) 에러를 받아요.

```text
OOM command not allowed when used memory > 'maxmemory'.
```

실험에서 `maxmemory 2mb` + noeviction으로 `SET`을 5만 번 보냈더니 **44,213건이 에러**였고, 이미 들어간 키를 `GET`하는 건 정상이었어요. 지워진 키(`evicted_keys`)는 0이었어요.

같은 상태에서 `allkeys-lru`로 바꾸고 5만 번 더 썼더니 **에러 0건**, 대신 51,036개 키가 퇴출됐어요. 상한 안에서 키가 계속 갈아 끼워진 거예요.

### 심화: 6. Redis의 LRU·LFU는 "근사"다

**정확한 LRU**를 하려면 모든 키를 사용 순서대로 줄 세운 목록을 유지해야 해요. 키가 수백만 개면 이 목록 자체가 메모리를 많이 먹어요.

그래서 Redis는 **근사 LRU**를 써요. 키를 몇 개(`maxmemory-samples`, 기본 5) 무작위로 뽑아서 그중 가장 오래 안 쓴 키를 지워요. 진짜 가장 오래된 키가 안 뽑힐 수도 있어요. Redis 3.0부터 좋은 후보를 모아 두는 **eviction pool**을 써서 정확도를 높였어요. 샘플 수를 늘리면 더 정확해지지만 CPU를 더 써요.

**LFU**(4.0+)는 키마다 작은 **확률적 카운터**로 접근 빈도를 어림해요.

- 실제 횟수가 아니라 **로그 스케일**이에요. 실험에서 새 키는 카운터 5에서 시작했고, `GET`을 1000번 해도 17이었어요(`OBJECT FREQ`로 확인).
- `lfu-decay-time`(기본 1분)마다 카운터가 줄어서, **예전에 인기 있던 키가 영원히 남지 않아요.**
- `lfu-log-factor`(기본 10)는 카운터가 얼마나 천천히 오를지 정해요.

**LRU와 LFU 중 무엇을?** 최근에 쓴 게 다시 쓰일 가능성이 크고 인기 키가 자주 바뀌면 LRU, 꾸준히 인기 있는 키가 정해져 있으면 LFU가 잘 맞아요.

### 7. 빅키와 핫키

**빅키**(big key)는 값이 아주 큰 키예요. 긴 문자열이나 원소가 수백만 개인 Hash·List·Set·ZSet을 말해요. 공식 문서에 "빅키"라는 전용 정의는 없고, 업계에서 흔히 쓰는 말이에요.

빅키를 `DEL`로 지우는 게 왜 문제일까요? Redis는 명령을 한 스레드가 순서대로 실행해요. → [Redis란?](../redis-basics/) 설정 파일은 원소가 수백만 개인 키를 `DEL`하면 **서버가 몇 초 동안 멈출 수 있다**고 직접 설명해요. 그동안 다른 요청이 전부 줄 서서 기다려요.

| 대책 | 설명 |
|---|---|
| `UNLINK key` | 키를 키 목록에서 바로 떼어 내고, 메모리 해제는 **다른 스레드가 뒤에서** 해요 |
| `FLUSHALL ASYNC` | 전체 삭제도 뒤에서 |
| `MEMORY USAGE key` | 키 하나가 차지하는 바이트 확인(4.0+) |
| `redis-cli --bigkeys` | 타입별로 가장 큰 키 찾기. SCAN을 써서 운영 중에도 돌릴 수 있고 `-i`로 속도 조절 |
| `redis-cli --memkeys` | 메모리 기준으로 큰 키 찾기 |

**핫키**(hot key)는 소수의 키에 요청이 몰리는 거예요. 클러스터에서는 그 키가 있는 노드 하나만 과부하가 걸려요. Redis 블로그는 `redis-cli --hotkeys`로 찾으라고 하는데, 이건 **LFU 정책일 때만** 동작해요. 실험에서 allkeys-lru로 돌리면 "LFU 정책이 선택되지 않았다"는 에러가 났고, allkeys-lfu로 바꾸니 핫키를 찾았어요. 대책으로 흔히 앱 서버의 로컬 캐시, 키를 여러 개로 복제해 나눠 읽기, 레플리카로 읽기 분산을 써요.

<details>
<summary>Q. Redis에서 만료된 키는 어떻게 삭제되나요?</summary>

**답변(30초)** 두 방식을 같이 써요. 하나는 수동 만료로, 클라이언트가 키에 접근했을 때 만료됐으면 그 자리에서 지워요. 다른 하나는 능동 만료로, 초당 10번 정도 만료가 걸린 키 20개를 무작위로 뽑아 지우고, 만료된 비율이 높으면 CPU 시간 제한 안에서 반복해요. 그래서 만료된 키는 바로 안 보이지만, 메모리에서는 잠깐 남아 있을 수 있어요.

**꼬리질문**
- Q. 왜 전체를 다 훑지 않나요? → 키가 많으면 전체 검사 동안 싱글 스레드가 멈춰 다른 요청을 못 받아요. 샘플링으로 비용을 제한해요.
- Q. 반복 기준이 25% 아닌가요? → 옛 설명이에요. 현재 소스는 만료 비율 10%가 반복 기준이고, 25%는 CPU 시간 상한이에요.
- Q. 레플리카는 각자 만료시키나요? → 아니에요. 마스터가 만료 시 보내는 DEL을 받아서 지워요.
</details>

<details>
<summary>Q. 만료와 퇴출(eviction)의 차이는요?</summary>

**답변(30초)** 만료는 TTL이 다 된 키를 지우는 거라 메모리 여유와 상관없어요. 퇴출은 메모리 상한에 닿아서 아직 살아 있는 키를 정책에 따라 지우는 거예요. 통계도 `expired_keys`와 `evicted_keys`로 따로 잡혀요. 그래서 `evicted_keys`가 늘고 있다면 메모리가 부족하다는 신호예요.

**꼬리질문**
- Q. INCR하면 TTL이 초기화되나요? → 아니에요. 값을 고치기만 하는 명령은 TTL을 유지하고, SET처럼 통째로 덮어쓰면 TTL이 사라져요.
</details>

<details>
<summary>Q. 메모리가 꽉 차면 Redis는 어떻게 동작하나요? 정책 종류는요?</summary>

**답변(30초)** `maxmemory`에 닿으면 `maxmemory-policy`에 따라 동작해요. 기본값은 noeviction이라 아무것도 지우지 않고 데이터를 늘리는 쓰기를 OOM 에러로 거절해요. 읽기는 계속 돼요. 다른 정책은 범위(전체 키 allkeys / TTL 있는 키 volatile)와 기준(LRU, LFU, random)을 조합하고, volatile-ttl이 더 있어서 흔히 8가지라고 해요. Redis 8.6부터는 수정 시각 기준인 LRM 2개가 추가돼 10가지예요.

**꼬리질문**
- Q. maxmemory 기본값은요? → 0, 즉 제한 없음이에요. 캐시로 쓰려면 상한과 정책을 둘 다 직접 정해야 해요.
- Q. volatile-lru인데 TTL 있는 키가 없으면요? → 지울 후보가 없어서 noeviction처럼 쓰기 에러가 나요.
</details>

<details>
<summary>Q. 빅키는 왜 문제이고 어떻게 다루나요?</summary>

**답변(30초)** Redis는 명령을 한 스레드로 실행해서, 빅키를 통째로 읽거나 `DEL`로 지우는 동안 다른 요청이 전부 기다려요. 설정 파일도 원소 수백만 개짜리 키 DEL은 서버를 몇 초 멈출 수 있다고 해요. 그래서 삭제는 메모리 해제를 뒤 스레드에 맡기는 `UNLINK`를 쓰고, `redis-cli --bigkeys`나 `MEMORY USAGE`로 미리 찾아 키를 나눠요.

**꼬리질문**
- Q. 핫키는요? → 소수 키에 요청이 몰리는 거예요. `--hotkeys`로 찾는데 LFU 정책일 때만 돼요. 로컬 캐시나 키 복제 분산으로 풀어요.
</details>

<details>
<summary>Q. Redis의 LRU는 정확한 LRU인가요?</summary>

**답변(30초)** 아니에요, 근사 LRU예요. 정확한 LRU는 모든 키를 사용 순서로 줄 세운 목록이 필요해서 메모리를 많이 먹어요. Redis는 키 5개(`maxmemory-samples`)를 무작위로 뽑아 그중 가장 오래 안 쓴 키를 지우고, 3.0부터는 후보 풀을 둬서 정확도를 높였어요. 샘플 수를 늘리면 정확해지지만 CPU를 더 써요.

**꼬리질문**
- Q. LFU와 차이는요? → LRU는 "마지막으로 언제 썼나", LFU는 "얼마나 자주 썼나"를 봐요. Redis LFU는 로그 스케일 확률 카운터이고 시간이 지나면 줄어들어요.
- Q. 언제 LFU를 고르나요? → 꾸준히 인기 있는 키가 정해져 있을 때요. 인기 키가 자주 바뀌면 LRU가 나아요.
</details>

## 서술형 연습

<details>
<summary>상황: 캐시로 쓰던 Redis에서 갑자기 "OOM command not allowed when used memory > 'maxmemory'" 에러가 나며 쓰기가 실패합니다. 읽기는 됩니다.</summary>

**상황 파악**
에러 문구가 maxmemory 초과이고, 쓰기만 실패하고 읽기는 된다면 **퇴출이 일어나지 않는 상태**예요. 먼저 `CONFIG GET maxmemory-policy`, `INFO memory`, `INFO stats`의 `evicted_keys`, `INFO keyspace`의 `keys`와 `expires` 수를 봐요.

**원인 후보**
1. maxmemory만 걸고 정책은 기본값 **noeviction** 그대로예요. `evicted_keys`가 0이에요.
2. 정책은 volatile-lru인데, TTL을 빠뜨린 키만 쌓여서 지울 후보가 없어요. `expires`가 `keys`보다 훨씬 적어요.
3. 실제로 데이터가 늘어서 상한이 모자라졌어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 정책을 `allkeys-lru`/`allkeys-lfu`로 변경 (`CONFIG SET`, 재시작 없이) | 즉시 쓰기 에러가 멈춤. 순수 캐시면 지워져도 DB에서 다시 채우면 됨 | TTL 없는 중요 키도 지워질 수 있음. 퇴출이 잦으면 캐시 적중률이 떨어져 DB 부하 증가 |
| B. TTL 누락 키를 찾아 TTL을 붙이고 코드에서 `SET ... EX`로 강제 | 근본 원인 제거. 만료로 메모리가 자연히 비워짐 | 키를 찾고 고치는 데 시간이 걸림. 당장의 장애는 못 막음 |
| C. maxmemory 증설(메모리 큰 인스턴스) | 코드·정책 변경 없음 | 비용 증가. 원인이 그대로면 또 찬다. 복제·AOF 버퍼는 계산에서 빠지니 RAM 여유도 같이 봐야 함 |

**내가 고를 방법**
용도가 **순수 캐시**라면 먼저 A로 쓰기 실패를 멈춰요. 캐시는 지워져도 원본 DB가 있으니까요. 그다음 B로 TTL 누락을 고쳐 재발을 막고, `evicted_keys`가 계속 많이 늘면 C를 검토해요. 반대로 이 Redis에 지워지면 안 되는 데이터가 섞여 있다면 A 대신 C와 B를 먼저 해요.

**채점 포인트**: 기본 정책 noeviction, 쓰기만 실패·읽기 정상, `evicted_keys`/`keys` vs `expires` 확인, volatile-*인데 TTL 키 없음, allkeys-* 변경의 트레이드오프, TTL 누락 수정, 복제·AOF 버퍼가 maxmemory에서 빠짐.
</details>

<details>
<summary>상황: 비용을 아끼려고 로그인 세션과 상품 캐시를 한 Redis에 같이 두려고 합니다. 어떤 퇴출 정책을 고를까요?</summary>

**상황 파악**
두 데이터의 성격이 달라요. 상품 캐시는 지워져도 DB에서 다시 읽으면 돼요. 세션은 지워지면 **사용자가 로그아웃돼요**. 그러니 질문은 "메모리가 찼을 때 무엇을 먼저 희생할까"예요.

**원인 후보(고려할 점)**
1. allkeys-* 정책은 세션과 캐시를 구분하지 않아요. 오래 안 쓴 세션이 먼저 지워질 수 있어요.
2. volatile-* 정책은 TTL 있는 키만 지워요. 그런데 세션에도 보통 TTL(예: 30분)을 걸기 때문에 세션도 후보가 돼요.
3. volatile-*에서 TTL 있는 키가 없으면 noeviction처럼 쓰기 에러가 나요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `volatile-lru` + 캐시에만 TTL, 세션은 TTL 없이 앱이 직접 삭제 | 세션은 퇴출 대상에서 빠짐 | 세션 정리를 앱이 해야 함. 정리 누락 시 세션이 쌓여 캐시 자리가 줄고, 결국 캐시가 다 지워지면 쓰기 에러 |
| B. `volatile-ttl` + 캐시 TTL을 세션보다 짧게 | 남은 수명이 짧은 캐시부터 지워짐 | 세션 TTL이 다 되어 가는 키가 캐시보다 먼저 지워질 수 있음. TTL 설계에 의존 |
| C. Redis를 둘로 분리(세션용 noeviction + 여유 메모리, 캐시용 allkeys-lru) | 정책을 용도마다 따로 정함. 장애가 서로 번지지 않음 | 인스턴스 비용과 운영 대상이 늘어남 |

**내가 고를 방법**
세션 유실이 사용자 경험에 직접 닿으니 **C를 권해요**. 비용 때문에 꼭 한 대여야 한다면 A를 고르고, 세션 수와 `keys` 대비 `expires` 비율을 모니터링해서 캐시 키가 바닥나기 전에 증설해요. 순수 캐시만 있었다면 allkeys-lru/lfu가 맞지만, 섞어 쓸 땐 volatile-*로 "지우면 안 되는 키"를 TTL 없이 보호하는 게 핵심이에요.

**채점 포인트**: 데이터별 유실 영향 구분, allkeys-*는 TTL 무관하게 지움, volatile-*는 TTL 있는 키만, TTL 있는 키가 없으면 쓰기 에러, 세션에도 TTL이 있으면 보호 안 됨, 인스턴스 분리 트레이드오프, 모니터링 지표.
</details>

<details>
<summary>상황: 랭킹 ZSet 하나에 멤버가 수백만 개 쌓였고, 시즌이 끝나 이 키를 DEL로 지웠더니 몇 초간 모든 API가 타임아웃났습니다.</summary>

**상황 파악**
Redis는 명령 실행이 싱글 스레드라, `DEL` 한 번이 원소 수백만 개의 메모리를 해제하는 동안 다른 요청이 전부 기다려요. 설정 파일도 이런 키의 DEL이 서버를 몇 초 멈출 수 있다고 설명해요. 먼저 SLOWLOG에 그 시각 `DEL`이 찍혔는지 확인해요.

**원인 후보**
1. 빅키를 동기 삭제(`DEL`)해서 메인 스레드가 멈췄어요.
2. 평소에도 그 키에 전체 조회(`ZRANGE 0 -1`)를 하고 있었다면 지연이 이미 있었을 수 있어요.
3. 빅키에 TTL을 걸어 두었다면, 만료로 지워질 때도 같은 일이 생길 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `DEL` 대신 `UNLINK` | 키는 바로 떼어 내고 메모리 해제는 뒤 스레드가 함. 코드 한 줄 변경 | 해제가 끝날 때까지 메모리가 잠깐 남음 |
| B. 키를 나눠 저장(시즌·구간별 여러 ZSet) | 키 하나의 크기가 작아져 삭제·조회 모두 가벼움 | 전체 랭킹을 합쳐 볼 때 로직이 복잡해짐 |
| C. 정기적으로 `--bigkeys`·`MEMORY USAGE`로 빅키 탐지 | 사고 전에 미리 발견 | 탐지일 뿐, 고치는 건 A·B가 해야 함 |

**내가 고를 방법**
당장은 A로 삭제를 전부 `UNLINK`로 바꿔요. 바로 효과가 나고 변경이 작아요. 재발을 막으려면 B로 키 설계를 나누고, C를 정기 점검에 넣어 빅키가 다시 자라는지 봐요.

**채점 포인트**: 싱글 스레드 명령 실행, 빅키 DEL이 서버를 멈춤, SLOWLOG 확인, UNLINK(메모리 해제를 뒤 스레드로), 키 분할, `--bigkeys`/`MEMORY USAGE` 탐지.
</details>

## 필기 포인트

- 만료 삭제 = **수동(접근 시) + 능동(주기적 샘플링)**. 능동: `hz` 10, 20개 샘플, 만료 비율 **10%** 초과 시 반복, **25%는 CPU 시간 상한**.
- `TTL` 반환: 수명 없음 **-1**, 키 없음 **-2**.
- `INCR`/`HSET`은 TTL 유지, `SET`/`DEL`/`GETSET`은 TTL 제거.
- `maxmemory` 기본 **0(무제한)**, `maxmemory-policy` 기본 **noeviction**.
- 정책: 8.6 이전 **8가지**, 8.6+ **10가지**(allkeys-lrm, volatile-lrm 추가). LFU 4.0+.
- volatile-*인데 TTL 키 없음 → noeviction처럼 쓰기 에러.
- LRU는 **근사**(`maxmemory-samples` 기본 5). LFU 카운터는 로그 스케일, 시간에 따라 감소.
- 레플리카는 만료를 직접 안 하고 마스터의 DEL을 받음. 기본적으로 maxmemory도 무시.
