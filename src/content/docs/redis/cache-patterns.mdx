:::tip[한 줄 요약]
가장 흔한 캐시 전략은 **Cache-Aside**예요. 읽을 때 캐시에 없으면 DB에서 읽어 캐시에 넣고, 데이터를 고칠 때는 **DB를 먼저 갱신하고 그다음 캐시를 지워요.** 이렇게 해도 캐시와 DB가 잠깐 어긋날 수 있어서, 모든 캐시 값에 **TTL**을 걸어 어긋남이 언젠가는 풀리게 해요.
:::

<Aside type="note" title="이 페이지의 범위">
여기서는 캐시를 "언제 채우고 언제 지우나"만 다뤄요. 인기 키가 만료되는 순간 DB로 요청이 몰리는 **캐시 스탬피드**, 없는 키를 계속 찌르는 **캐시 관통**, 한꺼번에 만료되는 **캐시 눈사태**는 [캐시 문제들](../cache-problems/)에서 따로 봐요.
</Aside>

## 쉽게 이해하기

학교 앞 분식집에 **메뉴판 사진을 붙인 게시판**이 있다고 해 봐요. 손님은 가게 안 주방(DB)에 들어가 묻는 대신 게시판(캐시)을 보고 가격을 확인해요. 게시판이 가까워서 훨씬 빨라요.

게시판에 없는 메뉴는 주방에 물어보고, 들은 김에 게시판에 적어 둬요. 이게 **Cache-Aside**예요. 가격이 바뀌면 주방 장부를 먼저 고치고, 게시판의 옛 가격은 떼어 버려요. 다음 손님이 주방에 다시 물어보고 새 가격을 붙이게요.

순서를 거꾸로 하면 문제가 생겨요. 게시판부터 떼었는데 장부를 고치기 직전에 손님이 와서 주방에 물으면, 손님은 **옛 가격**을 듣고 게시판에 다시 붙여요. 장부는 새 가격인데 게시판은 옛 가격인 상태가 한참 가요.

그래서 게시판 종이마다 "이 날짜까지만 유효" 도장(**TTL**)을 찍어 둬요. 뭔가 꼬여도 그 날짜가 지나면 종이가 떨어지고 새로 붙어요.

단, 실제로는 손님(요청)이 1초에 수천 명이고 여러 명이 동시에 게시판과 주방을 오가요. 그래서 "누가 먼저 했나"가 밀리초 단위로 뒤섞이는 게 핵심 문제예요.

## 제대로 알기

### 1. 왜 "전략"이 필요한가

**캐시**(cache)는 느린 원본(DB) 앞에 자주 읽는 값을 복사해 두는 빠른 저장소예요. Redis가 가장 많이 쓰이는 곳이 이거예요. → [Redis란?](../redis-basics/)

복사본을 두는 순간 질문이 두 개 생겨요.

- **언제 채우나?** 처음 읽을 때? 쓸 때마다?
- **원본이 바뀌면 복사본은 어떻게 하나?** 같이 고치나? 지우나? 나중에 반영하나?

이 두 질문에 대한 답의 조합이 캐시 전략이에요. 답에 따라 "얼마나 빠른가"와 "얼마나 자주 옛 값이 보이나"가 달라져요. 옛 값을 **stale**(상한, 원본과 달라진 오래된 값) 데이터라고 불러요.

### 2. 패턴 5종 한눈에 보기

| 패턴 | 읽기/쓰기 | DB를 부르는 주체 | 한 줄 동작 | 장점 | 단점 | 어울리는 곳 |
|---|---|---|---|---|---|---|
| **Cache-Aside** (Lazy loading) | 읽기 | 앱 | 캐시 확인 → 없으면 DB 읽고 캐시에 넣기 | 요청된 것만 캐시. 캐시가 죽어도 느려질 뿐 동작 | miss 때 왕복 3번. stale 가능 | 읽기가 많은 대부분의 조회 |
| **Read-Through** | 읽기 | 캐시(라이브러리) | 앱은 캐시만 부르고, 캐시가 없으면 스스로 DB에서 채움 | 앱 코드가 단순 | 그런 기능을 가진 캐시가 필요 | Caffeine `LoadingCache` 같은 로컬 캐시 |
| **Write-Through** | 쓰기 | 앱(또는 캐시) | DB와 캐시를 같은 쓰기에서 함께 갱신, 둘 다 성공해야 응답 | 쓴 직후 읽어도 새 값 | 쓰기 느려짐. 안 읽힐 값도 캐시에 쌓임 | 쓰고 바로 다시 읽는 경로 |
| **Write-Behind** (Write-Back) | 쓰기 | 캐시(비동기) | 캐시에만 쓰고 즉시 응답, DB는 나중에 묶어서 반영 | 쓰기가 아주 빠름. DB 부하 감소 | 반영 전에 캐시가 죽으면 유실 | 조회수·좋아요처럼 몇 건 잃어도 되는 값 |
| **Write-Around** | 쓰기 | 앱 | DB에만 쓰고 캐시는 건드리지 않음(또는 지움) | 안 읽힐 값으로 캐시를 낭비하지 않음 | 쓴 직후 첫 읽기는 miss | 쓰고 한동안 안 읽는 데이터 |

<Aside type="caution" title="이름 헷갈림 주의">
**Write-Behind와 Write-Back은 같은 말**이에요. 이름이 비슷한 **Write-Around**는 정반대로 캐시를 건너뛰는 방식이에요. Write-Around는 공식 정의 문서를 찾기 어려워서, 업계에서 흔히 쓰는 이름 정도로 알아 두면 돼요.
</Aside>

### 3. 읽기: Cache-Aside와 Read-Through

**Cache-Aside**는 앱이 캐시 옆(aside)에서 직접 오가며 채운다는 뜻이에요. **Lazy loading**(게으른 적재, 필요할 때만 채움)이라고도 불러요. Redis 공식 페이지도 Redis를 캐시로 쓰는 가장 흔한 방식으로 이걸 꼽아요.

```java
Product getProduct(long id) {
    String key = "product:" + id;
    Product cached = redis.get(key);          // 1. 캐시 먼저
    if (cached != null) return cached;        // hit: 바로 반환

    Product p = productRepository.findById(id); // 2. miss: DB 조회
    redis.set(key, p, Duration.ofMinutes(10));   // 3. 캐시에 넣기 + TTL
    return p;
}
```

- **좋은 점**: 실제로 요청된 데이터만 캐시에 들어가요. 대부분의 데이터는 거의 안 읽히니 메모리를 아껴요. 캐시 서버가 죽고 빈 서버로 바뀌어도 DB에서 다시 채우며 계속 동작해요(느려질 뿐이에요).
- **나쁜 점**: **miss**(캐시에 없음) 한 번에 캐시 조회 → DB 조회 → 캐시 쓰기로 왕복 3번이 들어요. 이걸 **miss penalty**(miss 벌금)라고 해요. 그리고 DB가 바뀌어도 캐시는 모르니 stale이 남을 수 있어요.

**Read-Through**는 흐름이 거의 같은데 **DB를 부르는 주체가 캐시**예요. 앱은 캐시에게만 "줘"라고 하고, 없으면 캐시가 알아서 원본에서 가져와요. 예를 들어 Java 로컬 캐시 라이브러리 **Caffeine**의 `LoadingCache`는 "없을 때 값을 만드는 함수"를 등록해 두면 없는 키를 요청할 때 캐시가 직접 채워요. Redis 서버에는 기본으로 이런 기능이 없어서, Redis에서는 보통 앱이 Cache-Aside로 같은 효과를 내요.

### 4. 쓰기: 4가지 길

**Write-Through**는 DB에 쓸 때 캐시도 같은 작업 안에서 함께 갱신하고, 둘 다 성공해야 응답해요. 그래서 쓰자마자 읽어도 새 값이 보여요. 대신 쓰기마다 왕복이 늘어요. AWS 문서는 사용자가 읽기 지연보다 쓰기 지연을 더 잘 참는다고 설명해요.

문제는 두 가지예요. 새로 투입된 캐시 서버에는 아무것도 없고, 한 번도 안 읽힐 값까지 캐시에 쌓여요(**cache churn**, 쓸모없는 값으로 캐시가 계속 들끓는 것). 그래서 Azure 문서는 Write-Through를 "쓰고 나서 바로 읽어야 하는, 읽기 많은 경로"에만 쓰라고 권해요.

**Write-Behind**는 캐시에만 쓰고 바로 응답한 뒤, DB에는 나중에 **비동기**(기다리지 않고 따로)로 반영해요. Write-Through가 동기, Write-Behind가 비동기라고 대비하면 외우기 쉬워요. 쓰기가 몰리는 값을 묶어서 한 번에 반영할 수 있어 DB 부하가 크게 줄어요. 대신 DB에 반영되기 전에 캐시가 죽으면 그 쓰기가 사라질 수 있어요. 그래서 결제·잔액처럼 잃으면 안 되는 값에는 흔히 쓰지 않고, 조회수·좋아요처럼 몇 건 잃어도 괜찮은 값에 흔히 써요.

**Write-Around**는 DB에만 쓰고 캐시는 그대로 두거나 지워요. 다음 읽기가 miss 나면서 Cache-Aside로 채워져요.

**실무 기본 조합**은 **읽기 Cache-Aside + 쓰기는 DB 갱신 후 캐시 삭제**예요. Azure의 Cache-Aside 문서가 이 방식을 기본으로 설명해요. 이걸 **쓰기 시 무효화**(invalidate on write)라고도 불러요. Write-Around와 사실상 같은 쓰기 경로예요.

### 5. 갱신 순서별 불일치 타임라인

여기가 면접과 토스 서술형에서 가장 많이 묻는 부분이에요. 모든 예시는 **처음에 DB=10, 캐시=10이고, 새 값은 20**이에요. 굵은 칸이 어긋난 순간이에요.

#### 5-1. 캐시 먼저 삭제 → DB 갱신 (나쁨)

| 시점 | 쓰기 A | 읽기 B | 캐시 | DB |
|---|---|---|---|---|
| t1 | 캐시 DEL | | 없음 | 10 |
| t2 | | 캐시 GET → miss | 없음 | 10 |
| t3 | | DB 읽기 → 10 | 없음 | 10 |
| t4 | DB 갱신 → 20 | | 없음 | 20 |
| t5 | | 캐시 SET 10 | **10 (stale)** | 20 |

A가 캐시를 지우고 DB를 고치기 전, 그 짧은 틈에 B가 끼어들어 옛 값을 다시 캐시에 넣어요. 이제 TTL이 끝날 때까지 모두가 10을 봐요. Azure 공식 문서도 **DB를 먼저 갱신하고 그다음 캐시를 지우라**고 명시해요.

#### 5-2. DB 갱신 → 캐시 갱신(SET), 동시 쓰기 2개 (나쁨)

| 시점 | 쓰기 A (값 20) | 쓰기 B (값 30) | 캐시 | DB |
|---|---|---|---|---|
| t1 | DB ← 20 | | 10 | 20 |
| t2 | | DB ← 30 | 10 | 30 |
| t3 | | 캐시 ← 30 | 30 | 30 |
| t4 | 캐시 ← 20 (늦게 도착) | | **20 (stale)** | 30 |

DB에는 나중 값(30)이 남았는데, 캐시에는 먼저 출발했지만 늦게 도착한 값(20)이 남아요. 게다가 "갱신"은 아무도 안 읽을 값도 매번 계산해서 넣어요. 그래서 캐시는 **갱신보다 삭제**를 흔히 권해요. 지우면 다음 읽기가 DB의 최신 값을 가져오니까요.

#### 5-3. DB 갱신 → 캐시 삭제 (권장, 그래도 드문 구멍)

| 시점 | 쓰기 A | 읽기 B | 캐시 | DB |
|---|---|---|---|---|
| t0 | | (캐시가 TTL로 막 만료됨) | 없음 | 10 |
| t1 | | 캐시 GET → miss | 없음 | 10 |
| t2 | | DB 읽기 → 10 | 없음 | 10 |
| t3 | DB 갱신 → 20 | | 없음 | 20 |
| t4 | 캐시 DEL (지울 게 없음) | | 없음 | 20 |
| t5 | | 캐시 SET 10 | **10 (stale)** | 20 |

B가 "DB 읽기"와 "캐시 SET" 사이에 머무는 아주 짧은 시간 안에, A의 "DB 쓰기 + 삭제"가 **통째로** 끼어야 생기는 일이에요. 읽기는 보통 쓰기보다 훨씬 빨라서 드물어요. 드물지만 0은 아니라서 아래 보완책을 같이 써요.

같은 구멍이 더 쉽게 열리는 경우도 있어요. 읽기를 **복제본**(replica, 원본 DB를 따라 복사하는 DB)에서 하면, A가 원본을 고치고 캐시를 지운 뒤에도 복제본에는 아직 옛 값이 남아 있을 수 있어요. 그 틈에 B가 복제본에서 옛 값을 읽어 캐시에 넣으면 같은 stale이 생겨요. 또 캐시 삭제를 DB **커밋**(commit, 트랜잭션 확정) 전에 하면, 다른 요청은 아직 확정 전의 옛 값을 읽으니 사실상 5-1과 같은 순서가 돼요.

#### 5-4. 남은 구멍을 줄이는 방법

| 방법 | 어떻게 | 한계 |
|---|---|---|
| **TTL 보험** | 모든 캐시 값에 만료 시간을 걸어요 | stale을 막진 못하고, stale이 남는 **최대 시간**만 정해요 |
| **지연 이중 삭제**(delayed double delete) | 캐시 삭제 → DB 갱신 → 잠깐(읽기 한 번 걸리는 시간보다 조금 길게) 기다렸다가 캐시 한 번 더 삭제 | 기다릴 시간을 정하기 애매하고 완전한 보장은 아니에요 |
| **삭제 재시도 큐** | 캐시 삭제가 네트워크 오류로 실패하면 큐에 넣어 다시 시도해요 | 큐라는 부품이 하나 늘어요 |
| **CDC 기반 삭제** | DB 변경 기록(MySQL binlog 등)을 구독해서 바뀐 행의 캐시를 지워요. **CDC**(Change Data Capture)는 DB 변경을 이벤트로 뽑아내는 방식이에요 | 구성이 복잡하고, 삭제가 약간 늦게 일어나요 |
| **lease** | miss 때 캐시가 토큰을 주고, 그 사이 삭제가 오면 토큰을 무효로 해서 늦은 SET을 거절해요. Facebook의 memcache 논문에 소개된 방식이에요 | 캐시나 클라이언트에 기능을 직접 넣어야 해요 |

지연 이중 삭제·재시도 큐·CDC는 공식 표준이 아니라 업계에서 흔히 쓰는 방법이에요.

<Aside type="tip" title="외우는 법">
"**DB 먼저, 캐시는 지운다, TTL은 꼭.**" 이 세 마디가 정합성 질문의 뼈대예요.
</Aside>

### 6. TTL은 어떻게 정하나

**TTL**(Time To Live)은 키가 사라질 때까지 남은 시간이에요. 만료된 키는 없는 것처럼 취급돼서 다음 읽기가 DB를 다시 읽어요. → [만료와 퇴출](../expire-eviction/)

- **너무 짧으면** 계속 DB를 다시 읽어서 캐시 효과가 줄어요.
- **너무 길면** stale이 오래 남을 위험이 커져요.
- 캐시는 **잘 안 바뀌거나 자주 읽히는 데이터**에 가장 잘 맞아요.
- AWS 문서는 **모든 쓰기에 TTL을 붙이면** Lazy loading과 Write-Through의 장점을 함께 얻는다고 해요.
- 만료가 없거나 길면 메모리가 차서 **eviction**(퇴출, 꽉 찼을 때 오래 안 쓴 키 등을 지우는 것)이 일어나요.
- 일부 캐시는 **절대 만료**(넣은 뒤 N분)와 **슬라이딩 만료**(마지막 접근 뒤 N분)를 둘 다 지원해요. Caffeine의 `expireAfterWrite`와 `expireAfterAccess`가 그 예예요.

TTL을 고를 때는 "이 데이터가 옛 값으로 **몇 분까지** 보여도 괜찮은가?"를 먼저 정하고, 그걸 상한으로 잡는 방법을 흔히 써요.

### 7. 캐시가 죽어도 서비스는 살아야 한다

Cache-Aside는 DB와 캐시가 항상 같다고 **보장하지 않아요.** 예를 들어 다른 프로그램이 DB를 직접 고치면 캐시는 다시 채워질 때까지 몰라요. 그래서 송금 직후 잔액처럼 **틀리면 안 되는 값은 원본(DB)에서 읽는** 것이 원칙이에요.

또 캐시는 보조 장치라서, 캐시 서버가 죽어도 앱은 **DB로 바로 넘어가서**(폴백, fallback) 계속 동작해야 해요. 캐시 응답을 하염없이 기다리다 멈추면 안 되니 짧은 타임아웃을 둬요.

동시에 여러 요청이 같은 값을 고치는 경우엔 **낙관적 방식**(고치기 전에 그사이 값이 바뀌었는지 확인)이나 **비관적 방식**(읽을 때 잠금, 짧은 작업에만)을 써요. Redis는 `WATCH` + `MULTI/EXEC`로 낙관적 트랜잭션을 지원해요.

### 8. 로컬 캐시 vs Redis(분산 캐시)

| | 로컬 캐시 (Caffeine 등) | 분산 캐시 (Redis 등) |
|---|---|---|
| 위치 | 서버 프로세스의 메모리 안 | 별도 서버, 네트워크로 접근 |
| 속도 | 가장 빠름(네트워크 없음) | 로컬보다 느림(네트워크 왕복) |
| 크기 | 서버 메모리에 묶임 | 캐시 서버를 늘려 확장 |
| 서버 여러 대일 때 | **서버마다 복사본이 따로** 있어 값이 다를 수 있음 | 모든 서버가 같은 값을 봄 |
| 무효화 | 서버마다 따로 지워야 함 | 한 곳만 지우면 됨 |
| 운영 부담 | 라이브러리 하나 | 서비스 하나를 따로 운영 |

**Caffeine**은 Java용 고성능 인메모리(로컬) 캐시 라이브러리예요. 꽉 차면 "얼마나 자주, 얼마나 최근에 쓰였나"를 함께 보고 지워요.

둘을 합친 **2단계 캐시**도 있어요. 로컬 → Redis → DB 순으로 찾아요. 가장 뜨거운 값은 로컬에서 바로 나오고, Redis가 잠깐 죽어도 로컬이 버텨 줘요. 대신 로컬 값이 너무 오래 묵지 않게 로컬 TTL을 짧게 잡아요. 서버마다 로컬 캐시를 지우라고 알려야 할 때는 Redis Pub/Sub으로 "이 키 지워" 메시지를 뿌리는 방법을 흔히 써요. → [Pub/Sub와 Streams](../pubsub-streams/)

Redis 자체도 **클라이언트 사이드 캐싱**(client-side caching)을 제공해요. 서버가 각 연결이 읽은 키를 기억해 두었다가, 그 키가 바뀌면 "지워" 메시지를 보내 줘요. 연결이 끊기면 클라이언트는 로컬 캐시를 통째로 비워요. Jedis 5.2.0+, redis-py 5.1.0+ 같은 클라이언트가 지원해요. 카운터처럼 자주 바뀌는 값은 무효화 비용이 더 커서 캐시 없이 쓰라고 권해요.

### 9. 스프링에서는: @Cacheable, @CachePut, @CacheEvict

스프링은 애노테이션 하나로 Cache-Aside를 붙일 수 있게 해 줘요.

| 애노테이션 | 하는 일 | 알아 둘 점 |
|---|---|---|
| `@Cacheable` | 결과를 캐시에 저장. 같은 인자로 다시 부르면 메서드를 실행하지 않고 캐시 값 반환 | 키 기본값은 메서드 인자. `key` 속성으로 지정 |
| `@CachePut` | 항상 메서드를 실행하고 결과를 캐시에 넣음 | `@Cacheable`과 같은 메서드에 같이 쓰는 건 강하게 비권장 |
| `@CacheEvict` | 캐시 항목 삭제 | 기본은 메서드가 **성공한 뒤** 삭제(예외면 삭제 안 함). `allEntries=true`면 전부 비움 |
| `@Cacheable(sync = true)` | 같은 키 miss에 동시 호출이 오면 한 번만 계산, 나머지는 대기 | 스탬피드 완화. → [캐시 문제들](../cache-problems/) |

```java
@Cacheable(cacheNames = "product", key = "#id")
public Product getProduct(long id) { ... }        // 읽기: Cache-Aside

@Transactional
@CacheEvict(cacheNames = "product", key = "#id")  // 메서드 성공 후 삭제
public void changePrice(long id, int price) { ... }
```

함정 세 가지예요.

- `@CacheEvict(beforeInvocation = true)`는 메서드 **실행 전에** 지워요. 이건 5-1의 "캐시 먼저 삭제" 순서와 같아서 같은 stale 문제가 생길 수 있어요.
- 스프링 캐시는 **프록시**(진짜 객체 앞에서 호출을 가로채는 대리 객체)로 동작해요. 그래서 **같은 클래스 안에서 자기 메서드를 직접 부르면** 캐시가 적용되지 않아요(self-invocation). public 메서드에만 적용돼요. → [스프링 AOP](../../spring/aop/)
- `@Transactional`과 `@CacheEvict`를 같은 메서드에 붙이면, 두 프록시가 어떤 순서로 감싸느냐에 따라 **커밋 전에** 캐시가 지워질 수 있어요. 그러면 커밋 전 틈에 옛 값이 다시 캐시돼요. 캐시 매니저를 트랜잭션 인식(transaction-aware) 모드로 두면 삭제가 커밋 뒤로 미뤄져요.

## 면접 질문

<details>
<summary>Q. Cache-Aside 패턴을 설명하고 장단점을 말해 주세요.</summary>

**답변(30초)** Cache-Aside는 앱이 먼저 캐시를 읽고, 없으면 DB에서 읽어 캐시에 넣은 뒤 돌려주는 방식이에요. 캐시와 DB를 오가는 일을 앱 코드가 직접 해요. 장점은 실제로 요청된 데이터만 캐시에 들어가고, 캐시가 죽어도 DB로 동작한다는 거예요. 단점은 miss 때 왕복이 3번이라 느리고, DB가 바뀌어도 캐시는 몰라서 옛 값이 남을 수 있다는 거예요. 그래서 쓰기 때 캐시를 지우고 TTL을 함께 걸어요.

**꼬리질문**
- Q. Read-Through와 뭐가 달라요? → 흐름은 거의 같고, DB를 부르는 주체가 달라요. Cache-Aside는 앱이, Read-Through는 캐시(라이브러리)가 불러요.
- Q. 캐시 서버가 죽으면요? → 앱은 DB로 폴백해서 계속 동작해야 해요. 대신 DB 부하가 갑자기 늘어서 짧은 타임아웃과 부하 대비가 필요해요.
</details>

<details>
<summary>Q. Write-Through와 Write-Behind는 어떻게 다르고, 각각 언제 쓰나요?</summary>

**답변(30초)** 둘 다 쓸 때 캐시를 거치는데, Write-Through는 DB와 캐시를 **동기**로 함께 쓰고 둘 다 성공해야 응답해요. 그래서 쓴 직후 읽어도 새 값이 보이지만 쓰기가 느려져요. Write-Behind는 캐시에만 쓰고 바로 응답한 뒤 DB에는 **비동기**로 나중에 반영해요. 쓰기가 빠르지만 반영 전에 캐시가 죽으면 쓰기가 사라질 수 있어요. 그래서 Write-Through는 쓰고 바로 읽는 경로에, Write-Behind는 조회수처럼 몇 건 잃어도 되는 값에 써요.

**꼬리질문**
- Q. Write-Through의 단점은 더 없나요? → 안 읽힐 값까지 캐시에 쌓이고, 새 캐시 서버는 비어 있어요. TTL과 Lazy loading을 같이 쓰면 줄어요.
- Q. Write-Around는요? → DB에만 쓰고 캐시는 건너뛰거나 지워요. 쓰고 한동안 안 읽는 데이터에 캐시를 낭비하지 않아요.
</details>

<details>
<summary>Q. 캐시와 DB 정합성은 어떻게 맞추나요? 캐시를 먼저 지우면 왜 안 되나요?</summary>

**답변(30초)** DB를 먼저 갱신하고 그다음 캐시를 지워요. 캐시를 먼저 지우면, DB를 고치기 전 틈에 다른 요청이 miss를 내고 옛 DB 값을 읽어 캐시에 다시 넣어요. 그러면 DB는 새 값인데 캐시는 TTL이 끝날 때까지 옛 값이에요. DB 먼저 갱신해도 드물게 어긋날 수 있어서 TTL을 보험으로 걸고, 필요하면 삭제 재시도나 DB 변경 로그 기반 삭제를 더해요.

**꼬리질문**
- Q. DB 먼저 갱신해도 생기는 경우는요? → 읽는 쪽이 옛 값을 읽어 둔 뒤, 쓰는 쪽이 DB 갱신과 삭제를 다 끝내고, 그다음 읽는 쪽이 옛 값을 SET하면 생겨요. 읽기가 보통 더 빨라서 드물어요.
- Q. 지연 이중 삭제는요? → 삭제, DB 갱신 뒤 잠깐 기다렸다 한 번 더 지워서 그 사이 들어간 옛 값을 치우는 방법이에요. 기다릴 시간을 정하기 애매하고 완전한 보장은 아니에요.
</details>

<details>
<summary>Q. 데이터를 고친 뒤 캐시를 갱신(SET)하는 것과 삭제(DEL)하는 것 중 뭐가 낫나요?</summary>

**답변(30초)** 보통 삭제를 권해요. 갱신은 동시 쓰기 두 개의 순서가 뒤집히면, DB에는 나중 값이 남았는데 캐시엔 늦게 도착한 옛 값이 남아 TTL까지 틀린 값을 보여 줘요. 또 아무도 안 읽을 값도 매번 계산해서 넣어요. 삭제하면 다음 읽기가 DB의 최신 값을 가져오니 순서 꼬임에 강해요. 대신 삭제 직후 첫 읽기는 miss가 나요.

**꼬리질문**
- Q. 그럼 갱신은 언제 써요? → 쓰고 바로 다시 읽는 일이 많아 miss를 피하고 싶을 때(Write-Through)예요. 이때도 TTL은 걸어요.
- Q. 스프링에선 각각 뭐예요? → 갱신은 `@CachePut`, 삭제는 `@CacheEvict`예요.
</details>

<details>
<summary>Q. 로컬 캐시와 Redis 같은 분산 캐시는 어떻게 다른가요?</summary>

**답변(30초)** 로컬 캐시는 서버 프로세스 메모리 안에 있어서 네트워크가 없어 가장 빨라요. 대신 서버가 여러 대면 서버마다 복사본이 따로 있어 같은 조회가 서버마다 다른 값을 낼 수 있어요. Redis 같은 분산 캐시는 모든 서버가 같은 값을 보고 지울 때도 한 곳만 지우면 되지만, 네트워크를 거쳐 느리고 운영할 서비스가 하나 늘어요. 둘을 합쳐 로컬, Redis, DB 순으로 찾는 2단계 캐시도 써요.

**꼬리질문**
- Q. 로컬 캐시를 서버 여러 대에서 맞추려면요? → 로컬 TTL을 짧게 잡거나, Redis Pub/Sub으로 무효화 메시지를 뿌리는 방법을 흔히 써요. Redis의 클라이언트 사이드 캐싱처럼 서버가 무효화를 알려 주는 기능도 있어요.
</details>

<details>
<summary>Q. @Cacheable이 안 먹는 경우가 있다던데요?</summary>

**답변(30초)** 스프링 캐시는 프록시가 메서드 호출을 가로채서 동작해요. 그래서 같은 클래스 안에서 `this.getProduct()`처럼 자기 메서드를 부르면 프록시를 거치지 않아 캐시가 적용되지 않아요. 또 public 메서드에만 적용돼요. 해결은 캐시 메서드를 다른 빈으로 분리해서 바깥에서 부르게 하는 거예요.

**꼬리질문**
- Q. @CacheEvict는 언제 지워요? → 기본은 메서드가 성공적으로 끝난 뒤예요. 예외가 나면 안 지워요. `beforeInvocation = true`면 실행 전에 지우는데, 이건 "캐시 먼저 삭제"와 같은 순서라 stale이 생길 수 있어요.
</details>

## 서술형 연습

<details>
<summary>상황: 관리자가 상품 가격을 10,000원에서 8,000원으로 바꿨는데, 일부 사용자에게 몇 분 동안 옛 가격 10,000원이 보인다는 문의가 들어왔습니다.</summary>

**상황 파악**
"일부 사용자에게, 몇 분 동안"이 핵심 단서예요. 모두에게 영원히 틀리면 DB 저장 실패를 먼저 보지만, 일부에게 잠깐이라면 **캐시가 옛 값을 들고 있다가 결국 풀리는** 그림이에요. 풀리는 시간이 캐시 TTL과 비슷한지부터 확인해요. 그리고 상품 조회 경로에 어떤 캐시가 몇 겹 있는지(로컬 캐시, Redis, 그 밖의 HTTP 캐시) 그려 봐요.

**원인 후보**
1. **삭제 순서**: 가격 변경 코드가 캐시를 먼저 지우고 DB를 고쳐요(`@CacheEvict(beforeInvocation = true)` 포함). 그 틈에 들어온 조회가 옛 가격을 다시 캐시에 넣었어요.
2. **갱신(SET) 경합**: 가격을 캐시에 직접 SET하는데, 동시에 들어온 다른 쓰기와 순서가 뒤집혀 옛 값이 남았어요.
3. **삭제 실패**: DB는 바뀌었는데 Redis 삭제가 네트워크 오류로 실패했고, 재시도가 없어요.
4. **로컬 캐시**: 서버마다 Caffeine 같은 로컬 캐시가 있어서, 변경 요청을 받은 서버만 지워지고 나머지 서버는 TTL까지 옛 값을 줘요. "일부 사용자"라는 증상과 특히 잘 맞아요.
5. **DB 밖에서 변경**: 관리자 도구가 DB를 직접 고쳐서 앱의 캐시 삭제 코드가 아예 안 탔어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 순서를 "DB 갱신 → 커밋 후 캐시 DEL"로 고치고, SET 대신 DEL | 코드 수정이 작고 원인 1·2를 직접 없앰 | 드문 경합(읽기가 옛 값을 늦게 SET)은 남음. 삭제 실패는 못 막음 |
| B. 삭제 실패 시 재시도 큐 + 짧은 TTL 보험 | 원인 3을 막고, 최악에도 TTL 안에 바로잡힘 | 큐 부품이 늘고, TTL을 줄이면 DB 읽기가 늘어남 |
| C. 로컬 캐시 무효화 전파(Redis Pub/Sub) 또는 가격은 로컬 캐시에서 제외 | 원인 4 해결. 서버 간 값이 맞춰짐 | 메시지 유실 시 일부 서버가 놓칠 수 있음. 제외하면 Redis 왕복이 늘어남 |
| D. DB 변경 로그(CDC) 구독으로 캐시 삭제 | 원인 5까지 포함해 어떤 경로로 바뀌어도 지워짐 | 구성이 복잡하고 삭제가 약간 늦어요 |

**내가 고를 방법**
먼저 A와 B를 바로 적용해요. 가격은 돈과 연결돼서 "틀린 값이 얼마나 오래 보일 수 있나"의 상한이 중요하니, TTL을 몇 분 이내로 짧게 잡아 보험을 걸어요. 로컬 캐시가 있다면 C로 가격 같은 민감한 값은 로컬에서 빼거나 무효화를 전파해요. 관리자 도구가 DB를 직접 고친다면 그때 D를 검토해요. 그리고 **주문 시점에는 캐시가 아니라 DB의 가격으로 다시 확인**해서, 화면에 옛 가격이 잠깐 보여도 결제 금액은 틀리지 않게 해요. 적용 후 가격 변경 뒤 옛 가격 노출 시간을 다시 재서 확인해요.

**채점 포인트**: DB 먼저 갱신 후 캐시 삭제, 캐시 먼저 삭제 시 stale 재적재, SET보다 DEL, 삭제 실패 재시도, TTL은 상한일 뿐, 로컬 캐시 서버별 불일치, 결제 시 원본 재확인, 적용 후 측정.
</details>

<details>
<summary>상황: 상품 상세 API는 초당 수천 번 호출되지만 상품 정보는 하루에 몇 번 바뀝니다. DB 부하를 줄이려고 Redis 캐시를 설계하세요(키, TTL, 무효화 포함).</summary>

**상황 파악**
읽기가 압도적으로 많고 쓰기는 드물어요. 캐시가 가장 잘 맞는 모양이에요. 설계에서 정할 것은 ① 어떤 전략으로 채울지 ② 키를 어떻게 지을지 ③ TTL을 얼마로 할지 ④ 바뀔 때 어떻게 지울지 ⑤ 캐시가 죽거나 인기 키가 만료될 때 어떻게 버틸지예요.

**원인 후보(설계 시 생길 위험)**
1. 상품 수정 후 옛 정보가 오래 보이는 stale.
2. 인기 상품 키가 만료되는 순간 수천 요청이 동시에 DB로 몰리는 스탬피드.
3. Redis 장애 시 API 전체가 멈추는 것.
4. 같은 시각에 넣은 키가 한꺼번에 만료돼 DB가 한 번에 맞는 것.

**해결책과 트레이드오프**

| 결정 | 선택지 1 | 선택지 2 |
|---|---|---|
| 채우기 | **Cache-Aside**: 요청된 상품만 캐시, 장애에 강함. 첫 요청은 느림 | **Write-Through**: 수정 시 캐시도 갱신, miss 적음. 안 보는 상품도 쌓이고 동시 쓰기 순서 꼬임 위험 |
| 무효화 | **DB 갱신 후 DEL**: 순서 꼬임에 강함. 직후 첫 읽기 miss | **DB 갱신 후 SET**: miss 없음. 동시 쓰기 시 옛 값 남을 수 있음 |
| TTL | **짧게(수 분)**: stale 상한이 작음. DB 읽기가 늘어남 | **길게(수 시간)**: 적중률 높음. 삭제 실패 시 오래 틀림 |

키는 `product:{id}`처럼 대상과 ID를 담아요.

**내가 고를 방법**
읽기는 **Cache-Aside**, 수정은 **DB 커밋 후 DEL**로 해요. 쓰기가 드물어서 삭제 직후 miss 한 번은 부담이 작아요. TTL은 "옛 상품 정보가 최대 얼마까지 보여도 되나"로 정해요. 하루 몇 번 바뀌는 정보라면 수십 분 정도를 상한으로 두고, 만료가 한 시각에 몰리지 않게 키마다 TTL을 조금씩 다르게 주는 방법을 흔히 써요. 인기 키 스탬피드는 `@Cacheable(sync = true)`나 락으로 한 요청만 DB를 읽게 막아요([캐시 문제들](../cache-problems/)). Redis 호출에는 짧은 타임아웃을 두고, 실패하면 DB로 폴백해요. 재고나 가격처럼 결제에 쓰는 값은 주문 단계에서 DB로 다시 확인해요. 적용 후 캐시 적중률과 DB QPS, API p99 지연을 보고 TTL을 조정해요.

**채점 포인트**: Cache-Aside 선택 이유(읽기 많음), 키 설계, TTL의 기준(허용 stale 시간)과 무작위 분산, DB 먼저 후 DEL, 스탬피드 대비, Redis 장애 시 폴백·타임아웃, 민감 값은 원본 재확인, 지표로 검증.
</details>

<details>
<summary>상황: 서버 10대가 같은 서비스를 돌립니다. 자주 읽는 데이터를 캐시하려는데, 로컬 캐시(Caffeine)와 Redis 중 무엇을 쓸지 정해야 합니다.</summary>

**상황 파악**
판단 기준은 세 가지예요. ① 데이터가 얼마나 자주 바뀌고, 서버마다 값이 잠깐 달라도 되는가 ② 데이터 크기가 서버 메모리에 들어가는가 ③ 네트워크 왕복 비용이 문제가 될 만큼 호출이 많은가.

**원인 후보(각 선택의 위험)**
1. 로컬 캐시만 쓰면 서버 10대가 각자 복사본을 가져서, 값이 바뀐 뒤 서버마다 다른 값을 줄 수 있어요. 지울 때도 10대를 다 지워야 해요.
2. 로컬 캐시는 서버 메모리를 나눠 써서, 데이터가 크면 앱 메모리를 압박해요. 서버 10대가 각자 DB에서 채우니 DB 읽기도 10배 가까이 늘 수 있어요.
3. Redis만 쓰면 모든 호출이 네트워크를 타고, Redis가 장애 나면 캐시 전체가 사라져요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 로컬 캐시 + 짧은 TTL | 가장 빠르고 구성이 단순 | 서버 간 불일치가 TTL만큼 남음. 크기 제한 |
| B. Redis 하나로 공유 | 모든 서버가 같은 값, 삭제는 한 곳 | 네트워크 왕복, 운영할 서비스 추가, Redis 장애 영향 |
| C. 2단계(로컬 → Redis → DB) + Pub/Sub 무효화 | 뜨거운 값은 로컬에서, 나머지는 Redis에서. Redis 장애 시 로컬이 버팀 | 구성이 가장 복잡. 무효화 메시지를 놓치면 그 서버만 옛 값 |

**내가 고를 방법**
데이터 성격으로 나눠요. 코드 목록·설정값처럼 **거의 안 바뀌고 작으며 잠깐 달라도 되는** 데이터는 A로 로컬 캐시에 둬요. 상품 정보처럼 **바뀌면 서버 모두가 같은 값을 봐야 하는** 데이터는 B로 Redis에 둬요. 측정해 봤더니 Redis 왕복 자체가 병목인 극소수 인기 키만 C로 로컬을 앞에 얹고, 로컬 TTL은 아주 짧게 잡고 변경 시 Pub/Sub으로 지워요. 처음부터 C로 가면 복잡도만 늘 수 있어서, 지표로 필요가 확인될 때 도입해요.

**채점 포인트**: 로컬=빠름·서버별 불일치·메모리 제한, Redis=일관성·네트워크 비용·운영 부담, 데이터 성격(변경 빈도·허용 불일치)으로 선택, 2단계 캐시와 무효화 전파, Redis 장애 대비, 측정 후 도입.
</details>

## 필기 포인트

- **Cache-Aside = Lazy loading**: 앱이 캐시 확인 → miss면 DB 읽고 캐시 SET. miss 시 왕복 3번.
- **Read-Through**: miss 때 **캐시가** DB에서 채움(Cache-Aside는 **앱이**).
- **Write-Through = 동기**(DB·캐시 둘 다 성공 후 응답), **Write-Behind = Write-Back = 비동기**(유실 위험).
- **Write-Around**: DB에만 쓰고 캐시는 건너뜀. Write-Back과 혼동 주의.
- 쓰기 순서: **DB 갱신 → 캐시 삭제**. 캐시 먼저 삭제하면 옛 값이 다시 캐시됨.
- TTL은 stale을 **막지 못하고 상한만** 정함.
- `@CacheEvict` 기본은 **메서드 성공 후** 삭제. `@Cacheable`은 같은 클래스 내부 호출에 안 먹음(프록시).
