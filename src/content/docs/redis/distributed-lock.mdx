:::tip[한 줄 요약]
Redis 분산 락은 `SET key 토큰 NX PX 시간` 한 명령으로 **없을 때만, 만료와 함께** 잡고, **값이 내 토큰일 때만** 지우는 방식으로 풀어요. 다만 TTL이 지나면 저절로 풀리는 "시간제 락"이라, 데이터 정확성이 꼭 필요한 곳에서는 **펜싱 토큰이나 DB 제약**을 최종 방어선으로 함께 둬요.
:::

<Aside type="note" title="이 페이지의 기준">
설명은 redis.io 공식 문서(2026-11 확인)와 Redisson 문서를 바탕으로 했어요. 직접 돌린 실험은 **Redis 8.10.2**예요. `DELEX`, `SET ... IFEQ`는 **Redis 8.4+** 기능이라 7.x에서는 Lua 스크립트로 해제해요. 실험 시간 값은 한 번 재 본 예시라 상대 비교로만 보세요.
</Aside>

## 쉽게 이해하기

공용 화장실 열쇠가 하나 있다고 해 봐요. 열쇠를 가진 사람만 들어갈 수 있으니 한 번에 한 명만 써요. 이게 **락**(lock, 한 번에 하나만 쓰게 하는 자물쇠)이에요.

그런데 건물이 세 동이고 동마다 열쇠를 따로 걸어 두면, 세 명이 동시에 같은 화장실에 들어가요. 서버 3대가 각자 `synchronized`를 거는 게 이 상황이에요. 그래서 **모든 동이 함께 보는 안내 데스크**(Redis)에 열쇠를 하나만 두는 게 **분산 락**이에요.

안내 데스크는 열쇠를 빌려줄 때 "30초 뒤엔 자동 반납"이라는 조건을 붙여요. 빌린 사람이 쓰러져도 열쇠가 영원히 사라지지 않게요. 그리고 반납할 때 "이거 당신이 빌린 열쇠 맞죠?" 하고 이름표를 확인해요.

단, 실제로는 자동 반납 때문에 새 문제가 생겨요. 안에서 오래 머문 사람은 열쇠가 이미 반납된 줄 모르고 계속 써요. 그 사이 다음 사람이 들어오면 둘이 겹쳐요. 이 페이지 후반의 **펜싱 토큰**이 그 문제를 다뤄요.

## 제대로 알기

### 1. 왜 분산 락이 필요한가

자바의 `synchronized`는 **JVM 하나 안에서만** 통해요. 서버가 2대 이상이면 각 서버가 자기 자물쇠만 보니, 서버 밖에 모두가 함께 보는 잠금 장소가 필요해요. ([Java 동기화](../../java/synchronization/))

실험으로 확인했어요. 재고 100개를 두고 스레드 10개가 20번씩 "재고 읽기 → 1ms 로직 → 재고-1 쓰기"를 했어요.

| 방식 | 판매 성공으로 센 수 | 남은 재고 | 걸린 시간(예시) |
|---|---|---|---|
| 락 없음 | **200** | 80 | 약 0.06초 |
| `SET NX PX` + 토큰 해제 | **100** | 0 | 약 0.45초 |

락이 없으면 100개뿐인데 200건이 팔렸어요. 여러 요청이 같은 재고를 읽고 각자 덮어쓴 **갱신 분실**(lost update)이에요. 락을 걸면 정확히 100건만 팔렸어요. 대신 한 명씩 처리하니 시간이 늘었어요. 이게 락의 비용이에요.

redis.io는 분산 락이 지켜야 할 최소 조건을 세 가지로 정리해요.

| 조건 | 뜻 |
|---|---|
| **안전성**(safety) | 어느 순간이든 락을 가진 클라이언트는 하나 |
| **데드락 없음**(liveness A) | 락을 쥔 쪽이 죽거나 네트워크가 끊겨도 결국 다시 잡을 수 있음 |
| **장애 허용**(liveness B) | Redis 노드 과반이 살아 있으면 잡고 풀 수 있음 |

### 2. 안전한 락의 3조건: NX · TTL · 토큰 확인 해제

단일 Redis에서 올바른 락은 세 가지를 모두 갖춰야 해요.

```text
# 잡기: 없을 때만(NX) + 30초 뒤 자동 만료(PX) + 값은 나만의 토큰
SET lock:item 8f3a...c1 NX PX 30000
# 성공 → OK / 누가 이미 잡음 → (nil), 잠시 뒤 재시도
```

```lua
-- 풀기 (Redis 8.4 미만): 값이 내 토큰일 때만 삭제
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
-- 실행: EVAL <스크립트> 1 lock:item 8f3a...c1
-- Redis 8.4+: DELEX lock:item IFEQ 8f3a...c1 한 명령
```

**① NX: 없을 때만 만든다**
`NX`는 키가 없을 때만 설정해요. 이미 있으면 아무것도 안 바꾸고 nil을 돌려줘요. "비었는지 확인"과 "내 것으로 표시"가 한 번에 일어나요.

**② TTL: 반드시 같은 명령에서 만료를 건다**
**TTL**(Time To Live, 자동으로 사라지기까지 남은 시간)이 없으면 락을 쥔 서버가 죽을 때 락이 영원히 남아요. `SETNX` 후 `EXPIRE`를 따로 보내도 위험해요. 두 명령 사이에 서버가 죽으면 만료 없는 락이 남거든요. 실험에서도 `SETNX` 직후 TTL이 `-1`(만료 없음)이었어요. 공식 문서도 `SETNX`·`SETEX` 같은 옛 명령은 SET 옵션으로 대체돼서 앞으로 없어질 수 있다고 적어요.

**③ 토큰 확인 해제: 내 락만 지운다**
값에는 **요청마다 유일한 랜덤 값**(토큰)을 넣어요. 해제할 때 "이 락이 내가 건 게 맞나"를 확인하는 이름표예요. 그냥 `DEL`하면 위의 첫 번째 그림처럼 **남의 락을 지울 수** 있어요.

실험에서 그대로 재현됐어요. A가 0.5초짜리 락을 잡고 0.8초 동안 작업했어요. 0.5초에 락이 만료되고 0.6초에 B가 잡았는데, A가 0.8초에 `DEL`하자 B의 락이 지워졌고 0.9초에 C까지 들어왔어요. 토큰+Lua로 바꾸자 A의 해제는 `0`(안 지움)을 돌려줬고 C는 실패했어요.

**왜 Lua로 한 번에?** `GET`으로 비교하고 `DEL`을 따로 보내면, 그 사이에 락이 만료되고 다른 클라이언트가 잡을 수 있어요. Lua 스크립트는 실행 중 다른 명령이 끼어들지 않아서 "비교+삭제"가 한 덩어리로 일어나요.

| 잘못된 방법 | 무엇이 깨지나 |
|---|---|
| `SETNX`만 (TTL 없음) | 락 쥔 서버가 죽으면 영원히 잠김 |
| `SETNX` + `EXPIRE` 따로 | 두 명령 사이에 죽으면 위와 같음 |
| 해제를 그냥 `DEL` | 만료 후 남이 잡은 락을 지움 |
| `GET` 비교 후 `DEL` 따로 | 비교와 삭제 사이에 끼어들 틈 |

### 3. TTL보다 작업이 길면: 워치독과 펜싱 토큰

TTL은 "자동 해제 시각"이면서 "그 안에 작업을 끝내야 하는 시간"이에요. 상호 배제는 **잡은 뒤 TTL 동안만** 보장돼요.

<Aside type="caution" title="토큰+Lua도 겹침은 못 막아요">
토큰 해제는 **남의 락을 지우지 않을 뿐**이에요. 위 실험에서도 0.6~0.8초 사이에는 락이 만료된 줄 모르는 A와 새로 잡은 B가 **동시에 작업**했어요. 작업이 TTL을 넘기는 순간 겹침 자체는 남아요.
</Aside>

TTL을 아주 길게 잡으면 될까요? 락 쥔 서버가 죽으면 그 시간 동안 아무도 못 써요. 그래서 보통 **짧게 잡고 연장**해요.

**워치독(락 자동 연장)**
Java 클라이언트 Redisson의 `RLock`은 락을 쥔 인스턴스가 살아 있는 동안 **워치독**(watchdog, 만료 전에 TTL을 계속 늘려 주는 감시자)이 만료를 연장해요. 클라이언트가 죽으면 연장이 멈추니 결국 만료돼요.

- `lockWatchdogTimeout` 기본값은 **30초**예요.
- 연장 주기는 이 값의 1/3(기본 10초마다 30초로 갱신)로 흔히 알려져 있어요.
- **leaseTime을 주면 워치독이 꺼져요.** `tryLock(100, 10, SECONDS)`는 최대 100초 기다리고, 잡으면 10초 뒤 연장 없이 자동 해제돼요.
- 락을 잡은 스레드만 `unlock`할 수 있고, 아니면 `IllegalMonitorStateException`이 나요.

```java
RLock lock = redisson.getLock("lock:coupon:" + couponId);
// 최대 3초 대기, leaseTime 생략 → 워치독이 연장
if (!lock.tryLock(3, TimeUnit.SECONDS)) {
    throw new IllegalStateException("잠시 후 다시 시도");
}
try {
    couponService.issue(userId, couponId); // 트랜잭션은 이 안에서 시작·커밋
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

워치독도 만능은 아니에요. 프로세스가 살아 있어도 **GC 멈춤**(GC pause, 가비지 컬렉터가 일하는 동안 앱 전체가 멈추는 것)이나 네트워크 단절 중에는 연장이 안 될 수 있어요. 공식 문서도 "락 잡은 프로세스가 살아 있으면 락도 유지된다"고 가정하지 말라고 해요.

**펜싱 토큰**
**펜싱 토큰**(fencing token)은 락을 잡을 때마다 받는 **계속 커지는 번호**예요. 저장소는 지금까지 본 가장 큰 번호보다 작은 번호의 쓰기를 거절해요. 두 번째 그림처럼 33번이 늦게 깨어나 써도 이미 34번을 봤으니 막혀요.

redis.io 공식 문서도 "펜싱 토큰을 구현하라, 오래 걸리는 작업일수록 중요하고 모든 분산 락에 해당한다"고 경고해요. 실무에서는 별도 번호 대신 **DB 조건부 UPDATE**(`WHERE status = 'READY'`, `WHERE version = ?`)나 **유니크 제약**이 같은 역할을 하는 경우가 많아요.

| 문제 | 워치독 | 펜싱 토큰(또는 DB 조건) |
|---|---|---|
| 작업이 TTL을 넘김 | 연장해서 만료를 막음 | 만료 뒤 늦은 쓰기를 거절 |
| GC 멈춤·네트워크 단절 | 연장 못 해서 뚫릴 수 있음 | 저장소가 막으니 안전 |
| 비용 | 라이브러리만 쓰면 됨 | 저장소가 번호·조건을 검사해야 함 |

### 4. 복제와 Redlock

**복제본을 붙이면 안전할까?** Redis 복제는 **비동기**(마스터가 복제본 반영을 기다리지 않고 응답)예요. A가 마스터에서 락을 잡고 → 복제되기 전 마스터가 죽고 → 복제본이 승격되면 → B가 같은 락을 또 잡아요. 공식 문서도 "장애 때 가끔 둘이 잡아도 괜찮을 때만" 복제 기반으로 쓰라고 해요. ([복제와 클러스터](../replication-cluster/))

**Redlock**은 공식 문서가 제안한 다중 노드 알고리즘이에요.

1. 현재 시각을 기록해요.
2. 서로 **독립된**(복제 관계 없는) Redis 마스터 N개(예: 5개)에 같은 키·같은 토큰으로 `SET NX PX`를 보내요. 노드별 타임아웃은 TTL보다 훨씬 짧게 해요(TTL 10초면 5~50ms).
3. **과반(5개 중 3개 이상)** 성공하고 걸린 시간이 TTL보다 짧으면 획득이에요.
4. 실제 유효 시간은 TTL − 걸린 시간이에요.
5. 실패하면 **모든 노드**에서 해제하고, 무작위로 잠깐 기다렸다 재시도해요.

공식 문서가 밝힌 전제와 한계도 있어요.

- 노드들의 시계가 거의 같은 속도로 흐른다는 가정에 기대요.
- Redis 만료는 **단조 시계**(monotonic clock, 뒤로 가지 않는 시계)를 쓰지 않아서, 시스템 시간이 튀면 둘이 동시에 잡을 수 있어요.
- 노드가 재시작돼 락 키를 잃으면 과반이 또 생길 수 있어요. 그래서 죽은 노드를 TTL보다 조금 더 오래 빼 두는 **지연 재시작**을 권해요.

Redisson도 `RedissonRedLock`을 **deprecated**(앞으로 쓰지 말라고 표시) 처리했고, 대신 `RLock`이나 펜싱 토큰이 필요하면 `RFencedLock`을 권해요.

### 5. Redlock 논쟁 (의견)

<Aside type="note" title="여기부터는 개인 블로그의 주장이에요">
아래는 업계에서 유명한 2016년 논쟁을 요약한 거예요. 공식 사실이 아니라 **의견**으로 읽어 주세요.
</Aside>

**Martin Kleppmann의 주장**
- 락의 목적을 **효율**(중복 작업을 줄이는 것, 가끔 실패해도 됨)과 **정확성**(데이터가 깨지면 안 됨)으로 나눠야 한다.
- 효율 목적이면 단일 Redis + `SET NX` + 토큰 해제로 충분하다.
- 정확성 목적이면 GC 멈춤 등으로 언제든 겹칠 수 있으니, 합의 기반 시스템(ZooKeeper 등)이나 트랜잭션이 확실한 DB를 쓰고 **펜싱 토큰**을 강제해야 한다. Redlock의 랜덤 값은 커지는 번호가 아니라 펜싱 토큰이 될 수 없다.

**antirez(Redis 창시자)의 반론**
- 저장소가 펜싱 토큰을 검사할 만큼 강하다면 랜덤 토큰으로 check-and-set을 해도 된다.
- 시계 문제는 수동 시간 변경 금지와 NTP 설정으로 피할 수 있다. 단조 시계로 바꿔야 한다는 점은 동의한다.
- 락 획득 뒤의 지연 문제는 자동 만료를 쓰는 모든 락에 공통이니, 작업 전에 남은 시간을 확인해야 한다.

결과적으로 공식 문서도 이 논쟁을 링크하고 펜싱 토큰·시계 경고를 반영했어요. 면접에서는 이렇게 정리하면 충분해요. **"Redis 락은 TTL 기반 리스(lease, 기한부 대여)라서, 정확성이 필수인 곳에는 펜싱 토큰이나 DB 제약을 함께 둔다."**

### 6. DB 락 vs Redis 락, 무엇을 고를까

데이터가 DB에 있으면 먼저 DB로 풀 수 있는지 봐요. 원자적 조건부 UPDATE, `FOR UPDATE`, version 같은 방법은 [InnoDB 락](../../db/locks/)에 있어요.

| 기준 | DB 락 (조건부 UPDATE·FOR UPDATE·version) | Redis 분산 락 |
|---|---|---|
| 보호 대상 | DB 행 하나의 값 | 여러 자원·외부 API 호출을 묶은 "작업 전체" |
| 정확성 | 트랜잭션이 보장 | TTL 만료·페일오버 때 깨질 수 있음 |
| 추가 인프라 | 없음 | Redis 필요, Redis 장애가 곧 락 장애 |
| DB 부하 | 대기 동안 커넥션·행 락 점유 | 대기를 DB 앞에서 처리 |
| 잘 맞는 곳 | 재고·포인트 단순 증감, 상태 전이 | 배치 중복 실행 방지, 외부 결제 호출 직렬화, DB 앞단 트래픽 거르기 |

가장 흔한 실무 답은 **둘을 겹쳐 쓰는 것**이에요. Redis 락으로 대부분의 중복을 앞에서 거르고, 혹시 뚫려도 DB의 유니크 제약·조건부 UPDATE가 최종으로 막아요.

### 7. 락과 @Transactional 순서

<Aside type="caution" title="주의할 점으로 흔히 언급되는 함정">
`@Transactional` 메서드 **안에서** 락을 잡고 풀면, 메서드가 끝나기 전에 락이 먼저 풀리고 커밋은 그 뒤에 일어나요. 그 틈에 다음 요청이 락을 잡고 **커밋 전 값**을 읽을 수 있어요. 그래서 락은 트랜잭션 **바깥**에서 잡아 "락 획득 → 트랜잭션 시작 → 커밋 → 락 해제" 순서를 만들어요. 이건 공식 문서 문장이 아니라 Spring 트랜잭션 프록시 동작에서 나오는 일반적인 결론이에요. ([@Transactional](../../spring/transactional/))
</Aside>

## 면접 질문

<details>
<summary>Q. Redis로 분산 락을 어떻게 구현하나요?</summary>

**답변(30초)** `SET key 토큰 NX PX 시간` 한 명령으로 잡아요. NX로 없을 때만 만들고, PX로 만료를 같이 걸어서 서버가 죽어도 락이 남지 않게 해요. 값에는 요청마다 유일한 토큰을 넣고, 해제는 Lua 스크립트로 "값이 내 토큰일 때만 DEL"을 원자적으로 해요. Redis 8.4+에서는 `DELEX key IFEQ 토큰`으로도 돼요.

**꼬리질문**
- Q. SETNX 후 EXPIRE를 따로 보내면 왜 위험해요? → 두 명령 사이에 서버가 죽으면 만료 없는 락이 영원히 남아요.
- Q. 락을 못 잡으면요? → nil을 받으니 잠시 뒤 재시도하거나 실패를 응답해요. Redisson은 pub/sub으로 해제를 알려 줘서 계속 물어보는 비용을 줄여요.
</details>

<details>
<summary>Q. 해제할 때 왜 그냥 DEL하면 안 되나요?</summary>

**답변(30초)** 남의 락을 지울 수 있어서예요. 내 작업이 TTL보다 길어지면 락이 자동 만료되고 다른 서버가 새로 잡아요. 그때 내가 DEL하면 그 서버의 락이 사라지고 세 번째 서버까지 들어와요. 그래서 토큰을 비교한 뒤 지우는데, GET과 DEL을 따로 보내면 그 사이에 끼어들 틈이 있으니 Lua로 한 번에 해요.

**꼬리질문**
- Q. 토큰+Lua면 완벽한가요? → 아니에요. 남의 락을 안 지울 뿐, 만료 뒤 두 서버가 동시에 작업하는 겹침은 남아요. 그래서 펜싱 토큰이나 DB 조건이 필요해요.
</details>

<details>
<summary>Q. 작업이 락 TTL보다 길어지면 어떻게 하나요?</summary>

**답변(30초)** 두 가지를 같이 써요. 하나는 워치독처럼 만료 전에 TTL을 계속 연장하는 방법이에요. Redisson은 leaseTime 없이 잡으면 기본 30초 TTL을 자동 연장해요. 다른 하나는 펜싱 토큰이에요. GC 멈춤처럼 연장이 안 되는 경우가 있어서, 저장소가 늦게 온 작은 번호의 쓰기를 거절하게 만들어요.

**꼬리질문**
- Q. tryLock(100, 10, SECONDS)의 의미는요? → 최대 100초 기다리고, 잡으면 10초 뒤 자동 해제예요. leaseTime을 줬으니 워치독은 안 돌아요.
- Q. 그냥 TTL을 아주 길게 잡으면요? → 서버가 죽으면 그 시간 동안 아무도 못 써서 가용성이 떨어져요.
</details>

<details>
<summary>Q. 펜싱 토큰이 뭔가요?</summary>

**답변(30초)** 락을 잡을 때마다 받는 계속 커지는 번호예요. 저장소는 지금까지 본 가장 큰 번호를 기억하고, 그보다 작은 번호의 쓰기를 거절해요. 그러면 락이 만료된 줄 모르고 늦게 깨어난 클라이언트의 쓰기가 막혀요. redis.io 공식 문서도 오래 걸리는 작업일수록 펜싱 토큰을 구현하라고 권해요.

**꼬리질문**
- Q. 실무에서는 어떻게 구현해요? → 별도 번호 대신 DB의 version 조건 UPDATE나 `WHERE status='READY'` 같은 상태 조건이 같은 역할을 하는 경우가 많아요.
</details>

<details>
<summary>Q. Redlock이 뭐고, 어떤 비판이 있나요?</summary>

**답변(30초)** 독립된 Redis 마스터 여러 대(예: 5대)에 같은 락을 걸어 과반이 성공하고 걸린 시간이 TTL보다 짧으면 획득으로 보는 알고리즘이에요. 단일 Redis나 비동기 복제의 장애 문제를 줄이려는 거예요. 다만 시계가 비슷하게 흐른다는 가정에 기대고, GC 멈춤 뒤 겹침은 여전히 못 막는다는 비판이 유명해요. 그래서 저는 정확성이 필요하면 펜싱 토큰이나 DB 제약을 같이 두겠다고 답해요.

**꼬리질문**
- Q. 복제본을 붙인 단일 락은요? → 복제가 비동기라 마스터가 복제 전에 죽고 승격되면 두 클라이언트가 락을 잡을 수 있어요.
- Q. Redisson에서 RedLock을 쓰나요? → `RedissonRedLock`은 deprecated고, 문서는 `RLock`이나 `RFencedLock`을 권해요.
</details>

<details>
<summary>Q. DB 락과 Redis 분산 락은 언제 무엇을 쓰나요?</summary>

**답변(30초)** 데이터가 DB 한 행에 있으면 먼저 원자적 조건부 UPDATE 같은 DB 방법을 써요. 추가 인프라 없이 트랜잭션이 정확성을 보장하니까요. Redis 락은 외부 API 호출까지 묶은 작업 전체를 한 번에 하나만 돌려야 할 때, 배치 중복 실행을 막을 때, DB 앞에서 트래픽을 거르고 싶을 때 써요. 그리고 Redis 락을 쓰더라도 최종 방어선은 DB 제약으로 둬요.

**꼬리질문**
- Q. synchronized로는 안 되나요? → JVM 하나 안에서만 통해서 서버가 2대 이상이면 못 막아요.
</details>

## 서술형 연습

<details>
<summary>상황: 선착순 쿠폰 1000장 이벤트에서 서버 3대가 요청을 받습니다. 발급 메서드에 synchronized를 붙였는데도 1000장보다 많이 발급됐고, 한 사람이 같은 쿠폰을 두 장 받은 경우도 있습니다.</summary>

**상황 파악**
수량 초과와 1인 중복, 두 가지가 같이 터졌어요. 돈과 바로 연결되는 정합성 문제라 우선순위가 높아요.

**원인 후보**
1. `synchronized`는 서버(JVM)마다 따로 걸려서 서버 3대가 동시에 발급해요.
2. "남은 수량 읽기 → 확인 → 발급 저장" 사이에 틈이 있어 갱신 분실이 생겨요.
3. 사용자 더블클릭이나 재시도로 같은 사람 요청이 거의 동시에 여러 번 와요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. DB 원자적 UPDATE `SET remain = remain - 1 WHERE id = ? AND remain >= 1` + (쿠폰, 사용자) 유니크 제약 | 추가 인프라 없음, DB가 정확성 보장 | 인기 쿠폰 한 행에 요청이 몰려 DB 부하 |
| B. Redis 분산 락(`SET NX PX` + 토큰 해제)으로 발급 구간 직렬화 | DB 앞에서 대기를 처리 | 한 명씩 처리라 처리량 감소, Redis 장애·TTL 만료 시 뚫릴 수 있음 |
| C. 사용자별 락 키(`lock:coupon:{id}:{userId}`) | 같은 사람 중복만 막아 동시성 유지 | 전체 수량 제한은 따로 필요 |

**내가 고를 방법**
A를 기본으로 해요. 수량은 조건부 UPDATE의 바뀐 행 수로, 1인 중복은 유니크 제약으로 DB가 확실히 막아요. 트래픽이 DB가 감당하기 어려울 만큼 크면 앞단에 사용자별 Redis 락(C)을 둬서 중복 요청을 미리 걸러요. 이때도 락은 `NX`와 `PX`를 한 명령으로, 해제는 토큰 확인으로 해요. 락이 뚫려도 DB 제약이 남아 있으니 정확성은 유지돼요.

**채점 포인트**: synchronized는 JVM 단위, 갱신 분실, 원자적 획득(NX+PX 한 명령), 토큰 확인 해제, TTL, 최종 방어선은 DB 조건부 UPDATE·유니크 제약, 락의 처리량 비용.
</details>

<details>
<summary>상황: 포인트 차감 API에 Redis 분산 락을 걸었습니다. 그런데 같은 사용자 요청이 연달아 오면 가끔 잔액이 한 번만 차감됩니다. 락은 @Transactional 메서드 안에서 잡고 finally에서 풉니다.</summary>

**상황 파악**
락이 있는데도 갱신 분실이 생겼어요. 락이 지키는 구간과 트랜잭션 구간이 어긋났을 가능성이 커요. 이건 주의할 점으로 흔히 언급되는 함정이에요.

**원인 후보**
1. 메서드 안의 `finally`에서 락을 풀면, 트랜잭션 커밋은 메서드가 끝난 **뒤** 프록시에서 일어나요. 락 해제 → 커밋 사이 틈에 다음 요청이 락을 잡고 **커밋 전 잔액**을 읽어요.
2. 작업이 TTL보다 길어 락이 먼저 만료됐을 수도 있어요.
3. 해제를 그냥 `DEL`로 해서 남의 락을 지웠을 수도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 락을 트랜잭션 바깥(파사드 클래스)에서 잡고, 안쪽 서비스가 트랜잭션을 커밋한 뒤 해제 | "락 → 시작 → 커밋 → 해제" 순서 보장 | 클래스가 하나 늘어남 |
| B. 락 대신 DB 원자적 UPDATE `SET balance = balance - ? WHERE id = ? AND balance >= ?` | 락 없이 DB가 정확성 보장 | 복잡한 검증을 SQL 하나로 표현하기 어려움 |
| C. 트랜잭션 커밋 이후 콜백에서 락 해제 | 기존 구조 유지 | 코드가 흩어지고 실수하기 쉬움 |

**내가 고를 방법**
A로 순서를 바로잡고, 차감 자체는 B처럼 조건부 UPDATE로 바꿔 최종 방어선을 둬요. 해제는 토큰 확인으로 하고, TTL이 작업 시간보다 넉넉한지(또는 워치독이 켜져 있는지)도 확인해요.

**채점 포인트**: 락 해제가 커밋보다 먼저 일어나는 문제, Spring 프록시가 메서드 밖에서 커밋, 락은 트랜잭션 바깥, 획득→시작→커밋→해제 순서, DB 조건부 UPDATE로 최종 방어, TTL·토큰 해제 점검.
</details>

<details>
<summary>상황: 매일 새벽 정산 배치가 서버 3대에 똑같이 배포돼 있어서, 같은 시각에 세 번 실행되며 정산이 중복으로 처리됐습니다.</summary>

**상황 파악**
스케줄러가 서버마다 따로 돌아서 같은 일을 세 번 했어요. 막아야 할 건 "같은 날짜 정산이 두 번 반영되는 것"이에요. 중복 실행 자체는 효율 문제고, 중복 반영은 정확성 문제라 둘을 나눠서 봐요.

**원인 후보**
1. 서버마다 독립된 스케줄러라 서로의 실행을 몰라요.
2. 정산 결과 저장에 "이미 처리했는지" 확인이 없어서, 두 번 실행되면 두 번 반영돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 배치 시작 시 Redis 락 `SET lock:settle:{날짜} 토큰 NX PX ...`, 못 잡은 서버는 그냥 종료 | 간단, 대부분의 중복 실행을 막음 | TTL이 배치보다 짧으면 만료 후 다른 서버가 시작, Redis 장애·페일오버 때 뚫릴 수 있음 |
| B. 정산 테이블에 (정산 날짜, 가맹점) 유니크 제약 또는 상태 조건 UPDATE로 **멱등**(여러 번 실행해도 결과가 한 번과 같음)하게 | 몇 번 돌아도 결과가 정확 | 중복 실행 자체의 자원 낭비는 남음 |
| C. 배치 전용 서버 1대에서만 실행 | 구조가 단순 | 그 서버가 죽으면 배치가 안 돎(단일 장애점) |

**내가 고를 방법**
A와 B를 같이 써요. A로 효율(중복 실행 방지)을 챙기고, B로 정확성을 보장해요. 락이 뚫려도 B가 막아 주니까요. A의 TTL은 배치 최대 실행 시간보다 넉넉하게 잡거나 워치독으로 연장하고, 해제는 토큰 확인으로 해요.

**채점 포인트**: 서버별 스케줄러 중복, 효율 vs 정확성 구분, SET NX PX + 토큰 해제, TTL과 배치 시간 관계(워치독), 멱등성·유니크 제약이 최종 방어선, 단일 장애점 트레이드오프.
</details>

## 필기 포인트

- 획득은 `SET key value NX PX ms` **한 명령**. NX = 없을 때만, PX = 밀리초 만료.
- 이미 있으면 NX SET은 **nil**, 성공은 `OK`.
- `SETNX` 직후 TTL은 **-1**(만료 없음). `SETNX`+`EXPIRE` 분리는 위험.
- 해제: Lua로 "GET == 토큰이면 DEL". Redis **8.4+**는 `DELEX key IFEQ token`.
- Redis 복제는 **비동기** → 페일오버 때 락 중복 가능.
- Redlock: 독립 마스터 N개 중 **과반** 성공 + 걸린 시간 < TTL. 유효 시간 = TTL − 걸린 시간.
- Redis 만료는 단조 시계를 쓰지 않음(공식 문서 경고).
- Redisson `lockWatchdogTimeout` 기본 **30초**, leaseTime을 주면 워치독 꺼짐. `RedissonRedLock`은 deprecated.
