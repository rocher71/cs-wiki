:::tip[한 줄 요약]
Redis는 **세션·처리율 제한·랭킹·멱등 키·캐시**에 많이 써요. 여러 명령을 묶을 땐 목적부터 정해요. **빠르게만** 보내려면 파이프라인, **끼어듦만** 막으려면 MULTI/EXEC, **읽은 값으로 판단해서 쓰려면** Lua예요. 그리고 Redis 트랜잭션에는 **롤백이 없어요.**
:::

:::note[처음이라면 여기까지]
① Redis는 캐시 말고도 로그인 세션, 요청 횟수 제한, 랭킹, 중복 요청 막기(멱등 키)에 많이 써요.

② 여러 명령을 묶는 도구는 목적별로 달라요. 빨리 보내기는 파이프라인, 끼어들기 막기는 MULTI/EXEC, 읽고 판단해서 쓰기는 Lua예요.

③ Redis 트랜잭션은 중간에 한 명령이 실패해도 앞의 것을 되돌리지(**롤백**) 않아요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

<Aside type="note" title="이 페이지의 기준">
설명은 redis.io 최신 공식 문서(2026-11 조회)를 바탕으로 했어요. 직접 돌린 실험은 **Redis 8.x**(Docker 공식 이미지, 노트북 1회 실행)라서 숫자는 "이 정도 차이가 난다"는 경향으로만 봐 주세요.
</Aside>

## 쉽게 이해하기

택배 기사가 물건 100개를 배달한다고 해 봐요. 하나 싣고 가서 내려놓고, 돌아와서 또 하나 싣는다면 하루가 다 가요. 트럭에 100개를 **한 번에 싣고 가면** 왕복은 한 번이에요. 이게 **파이프라인**이에요.

그런데 "한 번에 실었다"고 해서 **중간에 남의 짐이 섞이지 않는다**는 보장은 없어요. 남의 짐이 못 끼어들게 칸막이를 치는 게 **MULTI/EXEC**예요. 다만 칸막이 안의 짐 하나가 깨져도 나머지는 그대로 배달돼요. "하나라도 깨지면 전부 되돌리기"는 해 주지 않아요.

"창고에 재고가 남아 있으면 그때만 꺼내 줘"처럼 **확인하고 판단해서** 처리해야 할 때는, 기사에게 메모(작은 프로그램)를 건네서 창고 안에서 한 번에 처리하게 해요. 이게 **Lua 스크립트**예요.

단, 실제로는 Lua가 도는 동안 Redis는 **다른 모든 손님을 세워 둬요.** 메모가 길면 모두가 기다려요.

## 제대로 알기

### 1. 실무 패턴 한눈에 보기

| 패턴 | 쓰는 자료구조·명령 | 핵심 포인트 | 자세히 |
|---|---|---|---|
| 세션 저장 | Hash 또는 문자열 + TTL | 서버가 여러 대여도 로그인 상태를 공유 | [쿠키·세션·JWT](../../web/cookie-session-jwt/) |
| 처리율 제한 | `INCR` + `EXPIRE`, ZSET | 증가와 만료를 **원자적으로** 묶기 | 아래 3절 |
| 랭킹 | ZSET(`ZINCRBY`, `ZRANGE ... REV`, `ZREVRANK`) | 점수 갱신과 상위 N 조회가 바로 됨 | [자료구조](../data-structures/) |
| 멱등 키 | `SET key value NX EX 초` | 같은 요청이 두 번 와도 한 번만 처리 | 아래 4절 |
| 캐시 | 문자열·Hash + TTL | DB 앞에 자주 읽는 값을 둠 | [캐시 패턴](../cache-patterns/) |

**세션**부터 짧게 볼게요. 서버 한 대의 메모리에 세션을 두면, 서버를 늘렸을 때 다른 서버로 간 요청은 "로그인 안 된 사람"이 돼요. 세션을 Redis에 두면 모든 서버가 같은 곳을 봐요. Spring에서는 **Spring Session Data Redis**가 `HttpSession` 데이터를 Redis에 저장해 줘요. `@EnableRedisHttpSession`이나 Spring Boot 자동 설정으로 켜고, 키 앞에는 기본으로 `spring:session`이 붙어요.

### 2. 여러 명령을 묶는 네 가지 도구

Redis는 명령 **하나**는 원자적이에요(끼어듦 없이 한 번에 끝남, [Redis 기본](../redis-basics/) 참고). 문제는 명령 **여러 개**를 묶을 때예요. 도구마다 해 주는 일이 달라요.

| 도구 | 원자성(끼어듦 막기) | 롤백 | 중간 결과로 분기 | 성능 | 언제 쓰나 |
|---|---|---|---|---|---|
| 파이프라인 | 없음. 다른 클라이언트 명령이 끼어들 수 있음 | 없음 | 불가 | 왕복을 묶음당 1번으로 줄여 가장 빠름 | 대량 적재처럼 서로 독립인 명령 |
| MULTI/EXEC | 있음. 실행 중 끼어듦 없음 | **없음** | 불가(응답이 EXEC 때 한꺼번에 옴) | 보통 파이프라인으로 같이 보냄 | 함께 실행돼야 하는 고정 명령 묶음 |
| WATCH + MULTI/EXEC | 있음 + 감시 키가 바뀌면 전체 취소 | 없음(취소는 됨) | 가능(WATCH 후 읽고 판단) | 충돌이 잦으면 재시도가 몰림 | 충돌이 드문 "읽고 고치기" |
| Lua 스크립트 | 있음. 도는 동안 서버 전체가 다른 일을 안 함 | 없음 | 가능 | 왕복 1번. 단 길면 서버 전체를 막음 | 읽고 계산하고 쓰기를 한 번에 |

#### 파이프라이닝

**RTT**(round-trip time, 요청이 갔다가 응답이 돌아오는 데 걸리는 시간)는 명령 하나마다 들어요. 공식 문서 예시로는 RTT가 250ms면, 서버가 초당 10만 건을 처리할 수 있어도 클라이언트는 초당 4건밖에 못 보내요.

**파이프라이닝**(pipelining)은 응답을 기다리지 않고 명령을 연달아 보낸 뒤 응답을 한꺼번에 읽는 방식이에요. 이득은 두 가지예요.

- 왕복을 묶음당 한 번만 해요.
- 명령마다 드는 **시스템 콜**(프로그램이 운영체제에 "소켓 읽어 줘/써 줘" 부탁하는 일)이 줄어요. 한 번 읽고 쓸 때 여러 명령을 처리하니까요. 문서는 그래서 처리량이 파이프라인 길이에 따라 늘다가 약 10배에서 멈춘다고 해요.

실험(Redis 8.x)에서 직접 재 봤어요.

| 방식 | 결과 |
|---|---|
| SET 1만 개, 하나씩 왕복 | 약 1662ms |
| SET 1만 개, 한 번에 보내고 응답 읽기 | 약 7ms |
| `redis-benchmark` SET, 파이프라인 없음 | 초당 약 30만 건 |
| `redis-benchmark` SET, 100개씩 파이프라인 | 초당 약 430만 건(약 14배) |

1662ms vs 7ms는 200배가 넘지만, Docker 가상 머신을 거쳐 왕복이 느렸던 탓에 과장된 숫자예요. 벤치마크의 약 14배가 문서의 "약 10배"와 같은 자릿수예요.

주의할 점이 있어요.

- 서버는 응답을 메모리에 쌓아 둬요. 그래서 아주 많으면 **1만 개 정도씩 끊어서** 보내고 응답을 읽은 뒤 다음 묶음을 보내라고 문서가 권해요.
- 파이프라인은 **원자적이지 않아요.** 보낸 순서대로 실행되지만 그 사이에 다른 클라이언트 명령이 끼어들 수 있어요.
- 앞 명령 결과를 보고 다음 명령을 정해야 하면 못 써요. 그땐 Lua예요.

#### MULTI / EXEC: 끼어듦은 막지만 롤백은 없다

`MULTI` 다음 명령은 바로 실행되지 않고 **큐**(대기열)에 쌓여서 `QUEUED`를 돌려줘요. `EXEC`를 보내면 한꺼번에 실행되고 응답이 배열로 와요. `DISCARD`는 큐를 비우고 끝내요.

보장은 두 가지예요.

1. 큐에 있던 명령은 순서대로 **연달아** 실행되고, 도중에 다른 클라이언트가 못 끼어들어요.
2. `EXEC` 전에 연결이 끊기면 아무것도 실행되지 않아요.

그런데 에러는 두 종류고, 결과가 달라요.

| 에러 종류 | 예 | 결과 |
|---|---|---|
| 큐에 넣을 때 에러 | 명령 이름 오타, 인자 개수 틀림 | `EXEC`가 `EXECABORT`로 **전체를 버림**(2.6.5부터) |
| 실행 중 에러 | 문자열 키에 리스트 명령 | **그 명령만 실패, 나머지는 다 실행됨** |

실험(Redis 8.x)으로 확인했어요.

```text
SET a 1
MULTI
SET b 2      -> QUEUED
LPUSH a x    -> QUEUED   # a는 문자열이라 실행하면 에러
INCR b       -> QUEUED
EXEC
# 1) OK  2) WRONGTYPE 에러  3) 3
GET b        -> "3"      # 앞뒤 명령은 반영됨. 되돌리기 없음
```

문법 에러를 넣은 `MULTI; SET c 1; NOSUCHCMD; EXEC`는 `EXECABORT`가 나고 `c`는 생기지 않았어요.

공식 문서는 롤백을 안 넣은 이유로 **단순성과 성능**을 들어요. 그래서 "Redis 트랜잭션은 DB 트랜잭션(ACID, 롤백)과 같다"고 말하면 틀려요.

#### 심화: WATCH: 바뀌었으면 취소하는 낙관적 락

**낙관적 락**(optimistic lock, "충돌은 드물 거야"라고 가정하고 일단 진행한 뒤, 끝에 누가 건드렸는지 확인하는 방식)이에요. `WATCH`한 키가 `EXEC` 전에 바뀌면 트랜잭션 전체가 취소되고 `EXEC`는 **nil**을 돌려줘요. 에러가 아니라 nil이라서, 앱이 nil을 확인하고 처음부터 다시 시도해야 해요.

실험 흐름이에요.

1. A: `WATCH balance`, `GET balance` → 100
2. B: `SET balance 50` (끼어듦)
3. A: `MULTI`, `SET balance 90`, `EXEC` → nil(취소)
4. 최종 값은 50. A는 1번부터 다시 해요.

알아 둘 점이에요.

- 다른 클라이언트의 쓰기뿐 아니라 Redis의 **만료·퇴출**로 키가 사라져도 취소돼요(만료로 취소되는 건 6.0.9부터).
- `EXEC`가 호출되면 성공이든 취소든 WATCH가 모두 풀려요.
- Redis 8.4부터는 `SET ... IFEQ`(값이 같을 때만 설정) 같은 옵션이 생겨서, 단순한 "확인 후 바꾸기"는 WATCH 없이 명령 하나로도 돼요.

#### Lua 스크립트: 읽고 계산하고 쓰기를 한 번에

`EVAL`로 보내는 Lua 스크립트는 **원자적으로** 실행돼요. 다른 클라이언트는 결과를 "아직 전혀 안 일어남" 아니면 "전부 일어남"으로만 봐요. 공식 문서도 트랜잭션으로 할 수 있는 일은 스크립트로도 되고, 보통 스크립트가 더 단순하고 빠르다고 적어요.

```lua
-- 잔액이 충분할 때만 차감 (KEYS[1]=잔액 키, ARGV[1]=금액)
local bal = tonumber(redis.call('GET', KEYS[1]) or '0')
local amt = tonumber(ARGV[1])
if bal < amt then
  return -1                       -- 잔액 부족: 아무것도 안 씀
end
return redis.call('DECRBY', KEYS[1], amt)
```

대가와 규칙이에요.

- 도는 동안 **다른 모든 클라이언트가 아무 명령도 못 해요.** 스크립트는 짧게 써요.
- 기본 5초(`busy-reply-threshold`, 옛 이름 `lua-time-limit`)를 넘겨도 **자동으로 멈추지 않아요.** 다른 클라이언트에 `BUSY` 에러를 돌려줄 뿐이에요.
- 그때 `SCRIPT KILL`은 **아직 아무것도 안 쓴** 스크립트에만 통해요. 이미 썼다면 `SHUTDOWN NOSAVE`(저장 없이 종료)밖에 없어요.
- 스크립트가 쓰는 키 이름은 반드시 `KEYS`로, 나머지 값은 `ARGV`로 넘겨요. 클러스터가 키의 위치를 알아야 하거든요.
- 한 번 보낸 스크립트는 SHA1 값으로 서버에 캐시돼서 `EVALSHA`로 다시 부를 수 있어요. 7.0부터는 이름 붙여 저장하는 **Functions**(`FUNCTION LOAD`, `FCALL`)도 있어요.

### 3. 처리율 제한(rate limiting)

**처리율 제한**은 "한 사용자는 1초에 10번까지"처럼 요청 수를 막는 장치예요. 공격이나 실수로 서버가 넘어지지 않게 해요.

#### 고정 윈도우 카운터

가장 쉬운 방법은 시간을 칸(윈도우)으로 자르고 칸마다 숫자를 세는 거예요. INCR 공식 문서의 첫 번째 예시(키 `IP:초 단위 시각`, 초당 10회)와 같은 방식이에요.

- 키를 `사용자:시각칸`으로 만들고, `MULTI` 안에서 `INCR`과 `EXPIRE`를 함께 실행해요.
- 결과가 한도를 넘으면 거절해요.

`INCR`과 `EXPIRE`를 **따로** 보내면 위험해요. `INCR`만 되고 그 사이 클라이언트가 죽으면 **만료 없는 키**가 남아서, 그 사용자는 영원히 막혀요. 문서도 이 경쟁 조건을 짚고, 둘을 Lua 하나로 묶으라고 해요.

#### 경계에서 2배가 통과하는 문제

고정 윈도우는 칸이 바뀌는 순간 숫자가 0이 돼요. 그래서 **경계 직전에 한도만큼, 직후에 또 한도만큼** 보내면 짧은 시간에 2배가 통과해요.

실험(Redis 8.x, 한도 5회/2초)에서 재현했어요. 경계 0.3초 전에 5개, 경계 0.05초 뒤에 5개가 모두 허용되고 11번째만 거절됐어요. **약 0.35초 동안 10개, 한도의 2배**였어요.

#### 심화: 다른 방법들 (개요만)

- **슬라이딩 윈도우 로그**: 사용자별 ZSET에 요청 시각을 넣고, "지금부터 N초 전"까지의 개수만 세는 방식으로 알려져 있어요. 경계 문제가 없는 대신 요청마다 기록이 남아 메모리를 더 써요.
- **토큰 버킷**: 일정 속도로 채워지는 토큰을 요청마다 하나씩 꺼내는 방식으로 알려져 있어요. 순간 몰림을 버킷 크기만큼 허용해요.

두 방법 모두 여러 명령이 필요해서 보통 Lua로 묶어요. 알고리즘 비교는 대규모 시스템 설계 섹션의 처리율 제한 장에서 자세히 다룰 예정이에요.

### 4. 멱등 키: 같은 요청은 한 번만

**멱등성**(idempotency, 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같음)은 결제처럼 두 번 실행되면 안 되는 API에 필요해요. 네트워크가 끊겨 클라이언트가 재시도하거나 사용자가 버튼을 두 번 누르면 같은 요청이 또 와요. → [HTTP 기본](../../web/http-basics/)

Redis로는 이렇게 해요.

1. 클라이언트가 요청마다 고유한 `Idempotency-Key`를 보내요.
2. 서버가 `SET idem:키 processing NX EX 86400`으로 선점해요. `NX`는 "없을 때만", `EX`는 만료 초예요. 이 한 명령이 원자적이에요.
3. `OK`면 처음 온 요청이니 처리하고 결과를 같은 키에 저장해요.
4. `nil`이면 이미 처리 중이거나 끝난 요청이에요. 저장된 결과를 돌려주거나 409로 응답해요.

`SET NX EX`로 락을 만드는 패턴도 있는데, 공식 문서는 단순 락 대신 Redlock을 권해요. → [분산 락](../distributed-lock/)

## 면접 질문

<details>
<summary>Q. Redis 트랜잭션은 롤백되나요?</summary>

**답변(30초)** 안 돼요. `MULTI`/`EXEC`는 명령들이 끼어듦 없이 연달아 실행되는 것만 보장해요. 큐에 넣을 때 문법 에러가 나면 `EXECABORT`로 전체가 취소되지만, 실행 중에 난 에러는 그 명령만 실패하고 나머지는 그대로 반영돼요. 공식 문서는 롤백을 안 넣은 이유로 단순성과 성능을 들어요. 그래서 DB 트랜잭션과 같다고 보면 안 돼요.

**꼬리질문**
- Q. 그럼 "전부 아니면 전무"가 필요하면요? → 조건을 먼저 확인하고 쓰는 Lua 스크립트로 바꿔요. 실패할 조건이면 아무것도 안 쓰고 끝내요.
- Q. MULTI 안에서 GET 결과를 보고 분기할 수 있나요? → 없어요. 응답이 EXEC 때 한꺼번에 와요. WATCH로 먼저 읽거나 Lua를 써요.
</details>

<details>
<summary>Q. 파이프라인, MULTI/EXEC, Lua 스크립트는 어떻게 다른가요?</summary>

**답변(30초)** 목적이 달라요. 파이프라인은 왕복 횟수를 줄이는 **성능 도구**라 원자적이지 않아요. MULTI/EXEC는 끼어듦을 막지만 중간 결과로 분기할 수 없고 롤백도 없어요. Lua는 읽고 계산하고 쓰기를 서버에서 한 번에 원자적으로 해요. 대신 도는 동안 서버 전체가 다른 일을 못 하니 짧게 써야 해요.

**꼬리질문**
- Q. WATCH는요? → 낙관적 락이에요. 감시한 키가 EXEC 전에 바뀌면 EXEC가 nil을 돌려주고, 앱이 재시도해요. 충돌이 드물 때 좋아요.
- Q. Lua가 5초 넘게 돌면요? → 자동으로 안 멈춰요. 다른 클라이언트가 BUSY를 받고, 아직 안 썼으면 SCRIPT KILL, 썼으면 SHUTDOWN NOSAVE밖에 없어요.
</details>

<details>
<summary>Q. 파이프라이닝은 왜 빠른가요? 주의할 점은요?</summary>

**답변(30초)** 명령마다 응답을 기다리지 않고 묶어 보내서, 왕복 시간을 묶음당 한 번만 내기 때문이에요. 서버도 한 번 읽고 쓸 때 여러 명령을 처리해서 시스템 콜이 줄어요. 실험에서 SET 1만 개가 하나씩은 약 1.7초, 파이프라인은 약 7ms였어요. 다만 원자적이지 않고, 너무 크게 보내면 서버가 응답을 쌓느라 메모리를 써서 1만 개 정도씩 끊어 보내요.

**꼬리질문**
- Q. 앞 명령 결과가 다음 명령에 필요하면요? → 파이프라인으로는 안 돼요. Lua로 서버에서 처리해요.
</details>

<details>
<summary>Q. Redis로 처리율 제한을 어떻게 만드나요?</summary>

**답변(30초)** 가장 간단한 건 고정 윈도우예요. `사용자:시각칸` 키에 `INCR`하고 `EXPIRE`를 같이 걸어서, 한도를 넘으면 거절해요. 이때 INCR과 EXPIRE는 MULTI나 Lua로 꼭 묶어요. 따로 보내다 중간에 죽으면 만료 없는 키가 남아 영원히 막혀요. 고정 윈도우는 경계 직전·직후로 한도의 2배가 통과할 수 있어서, 정확해야 하면 ZSET 기반 슬라이딩 윈도우나 토큰 버킷을 검토해요.

**꼬리질문**
- Q. 2배 문제를 직접 본 적 있나요? → 한도 5회/2초로 실험했더니 경계 앞뒤 약 0.35초 동안 10개가 통과했어요.
</details>

<details>
<summary>Q. 결제 버튼 중복 클릭으로 이중 결제가 나는 걸 어떻게 막나요?</summary>

**답변(30초)** 멱등 키를 써요. 클라이언트가 요청마다 고유 키를 보내고, 서버는 `SET idem:키 processing NX EX 초`로 선점해요. 처음 요청만 OK를 받아 처리하고, 두 번째부터는 nil이 와서 저장된 결과를 돌려줘요. NX와 EX가 한 명령이라 "확인하고 설정하기" 사이에 끼어들 틈이 없어요.

**꼬리질문**
- Q. Redis가 죽으면요? → DB의 유니크 제약 같은 최종 방어선을 같이 둬요.
- Q. 처리하다 실패하면요? → 키를 지워서 클라이언트가 다시 시도할 수 있게 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 외부 공개 API에 사용자별 처리율 제한(분당 100회)을 걸어야 합니다. API 서버는 여러 대이고, 정각마다 몰리는 트래픽도 있습니다. 어떻게 설계하시겠어요?</summary>

**상황 파악**
서버가 여러 대라 각 서버 메모리에서 세면 사용자가 서버 수만큼 더 보낼 수 있어요. 그래서 모든 서버가 같은 카운터를 보는 **공유 저장소**가 필요하고, 요청마다 확인해야 하니 빨라야 해요. Redis가 맞아요. 또 "정각마다 몰린다"는 건 윈도우 경계 문제를 고려하라는 뜻이에요.

**원인 후보(설계 시 깨질 수 있는 곳)**
1. 카운터 증가와 만료 설정을 따로 보내면, 사이에 장애가 나서 만료 없는 키가 남고 사용자가 영구 차단돼요.
2. 고정 윈도우는 경계 직전·직후에 한도의 2배가 통과해요(실험에서 약 0.35초 동안 2배 통과).
3. 여러 서버가 "읽고 → 비교하고 → 쓰기"를 따로 하면 경쟁 조건으로 한도를 넘겨요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 고정 윈도우: `INCR` + `EXPIRE`를 MULTI 또는 Lua로 묶음 | 키 하나, 명령 두 개라 가장 단순하고 메모리가 적음 | 경계에서 최대 2배 통과 |
| B. 슬라이딩 윈도우 로그: ZSET에 요청 시각 저장, 오래된 기록 삭제 후 개수 확인, Lua로 묶음 | 경계 문제가 없어 정확 | 요청마다 기록이 남아 사용자 수 × 한도만큼 메모리 사용 |
| C. 토큰 버킷: Hash에 남은 토큰과 마지막 충전 시각, Lua로 계산 | 순간 몰림을 버킷 크기만큼 허용해 유연 | 구현이 복잡하고 파라미터 조정이 필요 |

**내가 고를 방법**
먼저 A로 시작해요. 구현이 쉽고, 분당 100회 기준으로 2배가 잠깐 통과해도 백엔드가 버틴다면 충분해요. 단 INCR과 EXPIRE는 반드시 Lua(또는 MULTI)로 묶어요. 정각 몰림 때문에 백엔드가 실제로 흔들린다면 B로 바꿔요. 메모리는 사용자 수 × 100건 정도라 미리 계산해 보고, 키마다 TTL을 걸어 안 쓰는 키가 정리되게 해요. Redis 장애 때 전부 막을지(안전 우선) 전부 통과시킬지(가용성 우선)도 정해 둬요.

**채점 포인트**: 공유 저장소 필요성(서버 여러 대), INCR+EXPIRE 원자적 묶기와 TTL 누수, 고정 윈도우 경계 2배, 슬라이딩 윈도우의 메모리 비용, Lua로 원자성, TTL로 키 정리, Redis 장애 시 정책.
</details>

<details>
<summary>상황: 매일 새벽 배치가 DB에서 읽은 상품 10만 건을 Redis에 SET으로 넣는데 수십 초가 걸립니다. Redis CPU는 한가합니다.</summary>

**상황 파악**
Redis CPU가 한가한데 느리다면, Redis가 일을 오래 하는 게 아니라 **기다리는 시간**이 길다는 뜻이에요. 명령 하나마다 응답을 기다리면 걸리는 시간은 "명령 수 × 왕복 시간"이에요. 예를 들어 왕복이 0.3ms라고 치면 10만 건 × 0.3ms = 30초예요(실측이 아닌 계산 예시).

**원인 후보**
1. 코드가 루프 안에서 SET을 하나씩 보내고 응답을 기다려요(왕복 10만 번).
2. 요청마다 연결을 새로 맺고 끊어서 연결 비용까지 더해져요.
3. 배치 서버와 Redis가 다른 네트워크 구간에 있어 왕복 시간 자체가 커요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 파이프라인으로 1만 개씩 끊어 보내기 | 왕복이 10번 정도로 줄어 대부분의 시간이 사라짐. 실험에서 1만 개가 약 1.7초에서 약 7ms로 줄어듦 | 원자적이지 않아 중간에 실패하면 일부만 들어감. 너무 크게 묶으면 서버가 응답을 쌓느라 메모리 사용 |
| B. `MSET`으로 여러 키를 한 명령에 | 명령 하나라 원자적이고 단순 | 키마다 TTL을 따로 못 줌. 클러스터에서는 키들이 같은 슬롯이어야 함 |
| C. `redis-cli --pipe`로 파일을 통째로 밀어 넣기 | 앱 코드 없이 대량 적재에 특화 | 배치 코드와 분리돼 운영이 따로 필요 |

**내가 고를 방법**
A를 골라요. 코드 변경이 작고 효과가 가장 커요. 배치 크기는 문서 권장대로 1만 개 정도로 하고, 묶음마다 응답을 읽어 실패한 키를 로그로 남겨 재시도해요. 원자성이 필요 없는 적재라 파이프라인의 약점이 문제가 안 돼요. 커넥션 풀도 함께 확인해요. 적용 후 전체 소요 시간과 Redis 메모리를 다시 재서 배치 크기를 조정해요.

**채점 포인트**: 원인이 RTT × 명령 수임을 짚기, 파이프라인 원리, 배치 크기 끊기(서버 응답 버퍼 메모리), 파이프라인은 원자적이지 않음, 실패 처리, MSET·`--pipe` 대안, 적용 후 측정.
</details>

<details>
<summary>상황: 포인트 잔액 차감을 "GET으로 잔액 확인 → 충분하면 MULTI 안에서 DECRBY"로 구현했는데, 동시 요청이 몰리자 잔액이 음수가 됐습니다. "트랜잭션을 썼는데 왜?"라는 질문을 받았습니다.</summary>

**상황 파악**
MULTI/EXEC는 **큐에 넣은 명령들이 끼어듦 없이 실행되는 것**만 보장해요. 잔액을 확인한 `GET`은 MULTI **바깥**에 있었고, 확인과 차감 사이에 다른 요청이 끼어들 수 있었어요. 또 Redis 트랜잭션은 롤백이 없어서, "음수가 되면 되돌린다" 같은 동작도 해 주지 않아요.

**원인 후보**
1. 요청 A와 B가 동시에 잔액 100을 읽고, 둘 다 "충분하다"고 판단해 각각 80씩 차감해요. 결과 -60.
2. MULTI 안에 GET을 넣었더라도, 응답이 EXEC 때 한꺼번에 와서 그 값으로 분기할 수 없어요.
3. "트랜잭션이면 롤백된다"는 DB식 기대가 설계에 깔려 있었어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Lua 스크립트로 "잔액 확인 후 차감"을 한 번에 | 확인과 차감 사이에 끼어들 틈이 없음. 왕복 1번. 재시도 불필요 | 스크립트를 관리해야 함. 길게 쓰면 서버 전체를 막음 |
| B. `WATCH balance` → GET → 판단 → MULTI/DECRBY/EXEC, nil이면 재시도 | 앱 코드에서 로직을 유지 | 동시 요청이 몰리면 대부분 nil이 나서 재시도가 폭주. 재시도 횟수 제한 필요 |
| C. `DECRBY` 먼저 하고 결과가 음수면 `INCRBY`로 되돌리기 | 가장 간단 | 순간적으로 음수가 다른 요청에 보임. 되돌리기 전에 죽으면 그대로 남음 |

**내가 고를 방법**
A를 골라요. 이 상황은 "동시 요청이 몰리는" 경우라 충돌이 잦고, WATCH는 충돌이 잦을수록 재시도가 늘어나 불리해요. Lua 스크립트는 몇 줄이라 짧게 끝나서 서버를 막을 걱정도 적어요. 키는 `KEYS`, 금액은 `ARGV`로 넘기고, 잔액 부족이면 아무것도 쓰지 않고 실패 코드를 돌려줘요. 충돌이 드문 다른 곳이라면 B도 괜찮아요. 돈이 걸린 일이니 최종 원장은 DB에 두고 Redis 값과 정기적으로 맞춰 보는 장치도 둬요.

**채점 포인트**: MULTI/EXEC는 격리만, 롤백 없음, MULTI 안에서 중간 결과로 분기 불가, 확인과 차감 사이 경쟁 조건, Lua로 원자적 확인-차감, WATCH는 낙관적 락이며 충돌 잦으면 재시도 폭주, KEYS/ARGV 규칙, Lua는 짧게.
</details>

## 필기 포인트

- 파이프라인: 왕복(RTT) 감소 + 시스템 콜 감소. **원자성 없음**. 권장 묶음 약 1만 개.
- `MULTI` 후 명령은 `QUEUED`, `EXEC`에서 실행, `DISCARD`로 취소.
- 큐잉 에러 → `EXECABORT`로 전체 취소(2.6.5+). 실행 중 에러 → **그 명령만 실패, 나머지 실행.** 롤백 없음.
- `WATCH` 키가 바뀌면 `EXEC`가 **nil**(에러 아님). 만료로도 취소(6.0.9+). EXEC 후 WATCH 해제.
- Lua: 원자적, 실행 중 서버 전체 대기. `busy-reply-threshold` 기본 5초, 넘어도 자동 종료 안 됨 → `BUSY`. 쓰기 전이면 `SCRIPT KILL`, 쓴 뒤면 `SHUTDOWN NOSAVE`.
- 키는 `KEYS`, 값은 `ARGV`. Functions(`FCALL`)는 7.0+.
- `SET key value NX EX 초`: 없을 때만 + 만료 설정, 원자적. 성공 OK, 실패 nil.
- 고정 윈도우는 경계에서 최대 2배 통과.
