:::tip[한 줄 요약]
캐시가 있어도 DB가 터지는 대표 상황은 네 가지예요. **인기 키 하나가 만료되는 순간 요청이 한꺼번에 DB로 가는 스탬피드**, **DB에도 없는 키를 계속 묻는 관통**, **많은 키가 동시에 사라지는 눈사태**, **키 하나에 요청이 몰리는 핫키**예요. 막는 방법은 각각 "한 요청만 다시 계산(락·조기 갱신)", "없음도 기억(null 캐싱·블룸 필터)", "만료 시각 흩기(TTL 지터)·캐시 이중화", "부하 나누기(로컬 캐시·키 복제)"예요.
:::

<Aside type="note" title="이 페이지의 기준">
"캐시 스탬피드"는 논문과 영어권 문서에서 쓰는 이름이에요. **"관통"·"눈사태"는 업계에서 흔히 부르는 이름**이고 redis.io 공식 문서에 있는 용어는 아니에요. 면접에서 이 이름으로 물어볼 수 있으니 알아 두세요. 실험은 Docker 공식 `redis:8` 이미지(Redis 8.x)로 노트북에서 돌린 거라 숫자는 경향으로만 봐 주세요.
</Aside>

## 쉽게 이해하기

인기 맛집 입구에 **"오늘의 대기 시간" 안내판**(캐시)이 있다고 해 봐요. 손님은 안내판만 보고 가니까 주방(DB)은 조용해요.

- **스탬피드**: 안내판이 정각에 지워졌어요. 그 순간 서 있던 손님 100명이 전부 주방 문을 열고 "대기 몇 분이에요?" 하고 물어요. 한 명만 물어보고 안내판을 다시 써 두면 될 일이었는데요.
- **관통**: 누가 장난으로 "없는 메뉴 있어요?"를 계속 물어요. 안내판엔 당연히 없으니 매번 주방까지 가요.
- **눈사태**: 안내판 수백 장이 **똑같이 자정에** 지워지거나, 안내판 벽 자체가 무너졌어요. 모든 질문이 한꺼번에 주방으로 가요.
- **핫키**: 안내판은 멀쩡한데 "오늘의 특선" 안내판 **한 장 앞에만** 사람이 몰려서 그 앞 통로가 막혀요.

단, 실제로는 "안내판을 다시 쓰는 일"이 DB 쿼리 한 번이 아니라 수 초 걸리는 무거운 계산일 때가 많아요. 계산이 길수록 그사이 더 많은 요청이 몰려서 피해가 커져요.

## 제대로 알기

### 1. 네 가지 한눈에 보기

먼저 이름을 정확히 구분하는 게 반이에요. 기준은 "**어떤 키가, 몇 개나, 왜** 캐시를 못 쓰게 됐나"예요.

| 이름 | 무슨 일 | 증상 | 대표 대응 |
|---|---|---|---|
| 스탬피드 | **인기 키 하나**가 만료된 순간 요청들이 같은 값을 동시에 다시 계산 | 특정 시각에 DB 같은 쿼리 폭증, 응답 지연이 연쇄로 커짐 | 락(뮤텍스), 확률적 조기 갱신, 백그라운드 갱신, 옛 값 주기 |
| 관통 | **DB에도 없는 키**를 반복 조회 | 캐시 히트율 급락, 없는 ID 조회가 전부 DB로 | null 캐싱, 블룸 필터, 입력 검증, 요청 제한 |
| 눈사태 | **많은 키가 동시에** 만료되거나 캐시 서버 자체가 다운 | 전체 DB 트래픽 스파이크, 여러 API가 함께 느려짐 | TTL 지터, 캐시 고가용성, 로컬 캐시 2단, 서킷 브레이커 |
| 핫키 | 만료와 상관없이 **키 하나에 트래픽 집중** | Cluster에서 노드 하나만 CPU 100% | 로컬 캐시, 키 복제, 레플리카 읽기 분산 |

핫키와 만료가 겹치면 그게 곧 스탬피드예요. 이 경우를 따로 "캐시 격파(breakdown)"라고 부르는 글도 있어요.

### 2. 캐시 스탬피드: 인기 키 하나가 만료되는 순간

**왜 생기나.** 캐시를 쓰는 흔한 코드는 "캐시에 있나? 없으면 DB에서 계산해서 넣는다"예요([캐시 패턴](../cache-patterns/)의 Cache-Aside). 이 코드는 혼자 돌 때는 문제없어요. 그런데 만료 순간에 요청 여러 개가 **동시에** "없네"를 보면, 전부 계산에 들어가요. 이걸 **캐시 스탬피드**(cache stampede, 소 떼가 한꺼번에 몰려드는 것에 빗댄 이름)라고 해요. dog-piling, cache miss storm이라고도 불러요.

몇 개나 몰릴까요? 대략 **요청 빈도 × 재계산 시간**이에요. 초당 10번 읽히는 키를 다시 계산하는 데 3초 걸리면 약 30개 요청이 같은 계산을 해요.

더 나쁜 건 **악순환**이에요. 계산이 겹쳐 DB가 느려지면 → 계산이 더 오래 걸리고 → 그동안 더 많은 요청이 미스에 합류해요. 그래서 **연쇄 장애**(cascading failure)로 번지기 쉬워요.

막는 방법은 크게 넷이에요.

| 방법 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| 락(뮤텍스) | 미스가 나면 락을 잡은 **한 요청만** 계산, 나머지는 기다렸다 캐시 재확인 | DB 조회를 1번으로 줄임 | 나머지가 기다려야 함(지연). 락 TTL 조절 필요 |
| 확률적 조기 갱신 | 만료 **전에** 요청마다 확률로 "미리 갱신할까?"를 정함 | 락 없음, 아무도 안 기다림 | "정확히 1번"은 보장 못 함 |
| 백그라운드 갱신 | 별도 작업이 주기적으로 미리 채움 | 스탬피드 원천 차단 | 별도 프로세스를 운영·감시해야 함. 안 읽히는 키까지 갱신할 수 있음 |
| 옛 값 주기(stale) | 만료가 지나도 옛 값을 주면서 뒤에서 한 요청만 갱신 | 사용자 대기 없음 | 잠깐 오래된 데이터가 보임 |

#### 락(뮤텍스)

**뮤텍스**(mutex, "한 번에 한 명만" 들어가게 하는 자물쇠)를 Redis 키 하나로 만들어요.

```text
# 캐시 미스가 나면 락부터 시도
SET lock:rank 토큰 NX PX 3000
# NX: 키가 없을 때만 설정 → 먼저 온 1명만 OK, 나머지는 nil
# PX: 3000ms 뒤 자동 삭제 → 락 잡은 서버가 죽어도 영원히 잠기지 않음

# OK를 받은 요청: DB 조회 → 캐시 저장 → 락 해제
# nil을 받은 요청: 잠깐(예: 20ms) 쉬고 캐시를 다시 확인
```

몇 가지 주의점이 있어요.

- 락을 풀 때 그냥 `DEL`하면 안 돼요. 내 락이 이미 만료되고 남이 새로 잡았을 수 있거든요. **내 토큰과 같을 때만** 지우는 Lua 스크립트로 풀어요. → [분산 락](../distributed-lock/)
- 락 TTL은 **재계산 시간보다 길게** 잡아야 해요. 짧으면 계산 중에 락이 풀려 두 번째 요청이 또 계산해요.
- 락을 못 잡은 요청은 돌려줄 값이 없어요. 선택지는 "기다렸다 재확인", "옛 값 반환", "값 없음 처리" 중 하나예요.
- 락 잡은 요청이 실패하면 락이 만료될 때까지 아무도 값을 못 받아요.
- redis.io는 단일 Redis의 `SET NX` 락을 정합성이 중요한 락으로는 권하지 않아요(Redlock 언급). 다만 여기서 락의 목적은 "중복 계산 줄이기"라, 락이 가끔 깨져도 DB 조회가 몇 번 더 나갈 뿐이에요.

Spring의 `@Cacheable(sync = true)`도 같은 키 미스에 한 스레드만 계산하게 해 줘요. 단, 이건 **서버(JVM) 한 대 안에서만** 막아요. 서버가 10대면 최대 10번 조회될 수 있어요.

#### 확률적 조기 갱신(XFetch)

**확률적 조기 만료**(probabilistic early expiration)는 "만료되면 계산"이 아니라 "**만료가 다가올수록** 점점 높은 확률로 미리 계산"하는 방법이에요. 요청마다 판단 시점이 흩어지니 한 순간에 몰리지 않아요. 락이 필요 없어요.

2015년 VLDB 논문이 이걸 **XFetch**라는 이름으로 정리했고, 지수분포로 확률을 고르는 방식이 이론적으로 최적이라고 증명했어요. 아이디어를 풀어 쓰면 이래요.

```text
캐시에 함께 저장: 값, Δ(지난번 계산에 걸린 시간), expiry(만료 시각)

읽을 때:
  if 값이 없음 or  현재시각 - Δ × β × ln(rand()) ≥ expiry:
      다시 계산하고 저장   # rand()는 0~1 → ln은 음수 → 현재시각을 "미래로 당겨 보기"
  else:
      캐시 값 사용
# β 기본 1. 키우면 더 일찍 갱신(대신 조기 갱신 횟수 증가)
```

- 계산이 오래 걸리는 키(Δ가 큰 키)일수록 더 일찍 갱신을 시작해요.
- 요청 빈도에 맞춰 튜닝할 필요가 거의 없어요. 논문 실험에서 β=1로도 평균 스탬피드 크기가 2 미만이었어요.
- 대신 "정확히 1번"은 아니에요. 아무도 기다리지 않는 대가예요.

#### 옛 값 주기(stale-while-revalidate)

HTTP 캐시에는 **stale-while-revalidate**(RFC 5861)라는 규칙이 있어요. `max-age=600, stale-while-revalidate=30`이면 600초 동안은 신선하고, 그 뒤 30초 동안은 **오래된 응답을 바로 주면서 뒤에서 새로 확인**해요. 같은 RFC의 **stale-if-error**는 원본 서버가 500·502·503·504 에러일 때 옛 응답을 대신 쓰게 해요.

이 아이디어를 Redis 캐시에 옮겨 쓰는 흔한 방법이 있어요. 값 안에 **논리 만료 시각**을 적고, Redis TTL(물리 만료)은 그보다 길게 걸어요. 논리 만료가 지나도 키는 살아 있으니 옛 값을 주고, 한 요청만 락을 잡아 갱신해요. (RFC는 HTTP 규칙이고 Redis 기능은 아니에요.)

#### 실험: 대응 없음 vs 뮤텍스

Redis 8.x에서 파이썬 스레드 100개가 **동시에** 만료된 키를 읽게 했어요. DB 조회는 200ms 걸리는 것으로 흉내 냈고, 각각 3번씩 돌렸어요.

| 방식 | DB 조회 횟수 | 전체 걸린 시간 |
|---|---|---|
| 대응 없음 | **100번** (3회 모두) | 약 0.21~0.23초 |
| 뮤텍스(`SET NX PX` + 실패 시 20ms 뒤 캐시 재확인) | **1번** (3회 모두) | 약 0.21~0.23초 |

전체 시간이 비슷한 이유는 기다린 99개가 락 잡은 1개의 결과를 그대로 받아 갔기 때문이에요. **사용자 입장의 속도는 거의 같은데 DB가 받는 부하는 100분의 1**이 된 거예요. 실제 DB는 동시 쿼리가 100개 몰리면 느려지니, 실제 서비스에서 "대응 없음"은 이 실험보다 훨씬 오래 걸릴 수 있어요.

### 3. 캐시 관통: 원래 없는 키를 계속 묻는다

**왜 생기나.** 존재하지 않는 상품 ID(예: 봇이 만든 랜덤 ID)로 조회하면 캐시엔 당연히 없어요. Cache-Aside 코드는 DB에 가서 "없음"을 받고, **아무것도 캐시에 넣지 않아요.** 그래서 다음 요청도, 그다음도 전부 DB까지 가요. 캐시가 있으나 마나예요.

| 대응 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| null 캐싱 | "없음"도 **짧은 TTL**(수십 초~몇 분)로 캐시 | 구현이 가장 쉬움 | 랜덤 ID 공격엔 키가 끝없이 늘어 효과 약함. TTL이 길면 새로 생긴 데이터가 한동안 "없음"으로 보임 |
| 블룸 필터 | 앞단에서 "확실히 없음"이면 바로 거절 | 아주 적은 메모리로 랜덤 ID도 막음 | 데이터 추가 때 필터에도 넣어야 함. 삭제 불가 |
| 입력 검증·요청 제한 | ID 형식·범위 체크, IP별 **rate limit**(처리율 제한) | 공격 자체를 줄임 | 형식이 맞는 가짜 ID는 못 거름 |

#### 블룸 필터

**블룸 필터**(Bloom filter)는 "이 값이 들어 있나?"를 아주 적은 메모리로 답하는 **확률 자료구조**(정확도를 조금 양보하고 메모리를 크게 아끼는 자료구조)예요.

- **"없다"고 하면 100% 없어요**(거짓 음성 없음).
- **"있다"고 하면 가끔 틀려요**(거짓 양성, 없는데 있다고 함).

그래서 관통 방지에 딱 맞아요. "없다"면 DB에 안 가고 바로 거절하고, "있을 수도"면 평소처럼 캐시 → DB로 가요. 가끔 오탐으로 DB까지 가는 요청이 생겨도 대부분은 막혀요.

```text
BF.RESERVE products 0.01 1000000   # 오탐률 1%, 예상 100만 개
BF.ADD products 7                  # 상품 등록할 때 필터에도 추가
BF.EXISTS products 7               # → 1 (있을 수도 있음 → 캐시·DB 조회)
BF.EXISTS products 99999           # → 0 (확실히 없음 → 바로 404)
```

알아 둘 사실이에요.

- **Redis 8부터 본체에 포함**돼서 모듈 없이 써요. 7.x 이하는 RedisBloom 모듈이나 Redis Stack을 따로 깔아야 했어요. 실험(Redis 8.x)에서도 위 명령이 설치 없이 바로 동작했어요.
- 크기: 오탐률 1%면 아이템당 약 9.6비트(해시 함수 7개), 0.1%면 약 14.4비트(10개)예요. Set에 IP를 넣으면 아이템당 약 320비트라 훨씬 커요.
- 예상 개수를 넘기면 실패하지 않고 필터를 하나 더 쌓아 자동으로 늘어나요. 대신 쌓일수록 조회가 느려져요.
- **원소 삭제가 안 돼요.** 삭제가 필요하면 **Cuckoo 필터**(삭제 가능하고 조회가 더 빠른 비슷한 자료구조)를 써요.
- 상품을 추가할 때 필터에 넣는 걸 빠뜨리면 진짜 있는 상품이 "없음"으로 막혀요. 필터 오류가 아니라 동기화 누락이에요.

### 4. 캐시 눈사태: 많은 키가 한꺼번에 무너진다

**왜 생기나.** 원인은 두 가지예요.

1. **동시 대량 만료**: 자정 배치가 상품 캐시 수만 개를 한 번에 TTL 24시간으로 넣으면, 다음 날 자정 정각에 전부 같이 만료돼요.
2. **캐시 서버 장애**: Redis가 죽거나, 영속성을 끈 채 재시작해서 캐시가 텅 비어요.

둘 다 DB로 트래픽이 한꺼번에 쏟아져요. 스탬피드가 "키 하나"라면 눈사태는 "키 전부"예요.

| 대응 | 막는 원인 | 설명 |
|---|---|---|
| **TTL 지터**(jitter, 일부러 섞는 작은 무작위 값) | 동시 만료 | TTL에 랜덤을 더해 만료 시각을 흩어요. 예: 3600초 + 0~300초 랜덤 |
| 미리 갱신 | 동시 만료 | 만료를 기다리지 않고 배치가 미리 새 값으로 덮어써요 |
| 캐시 고가용성 | 서버 장애 | 복제 + Sentinel/Cluster로 노드 하나가 죽어도 계속 서비스해요. → [복제와 클러스터](../replication-cluster/) |
| 영속성 켜기 | 재시작 | RDB/AOF가 있으면 재시작 후 데이터가 남아 빈 캐시로 시작하지 않아요. → [영속성](../persistence/) |
| 다중 레벨 캐시 | 서버 장애 | 앱 서버 메모리 캐시(Caffeine 등) + Redis. Redis가 흔들려도 로컬 캐시가 일부 받아 줘요 |
| **서킷 브레이커**(circuit breaker, 실패가 많으면 호출을 잠시 끊는 장치) | DB 보호 | 실패율이 기준(Resilience4j 기본 50%)을 넘으면 OPEN이 되어 호출을 바로 거절해요. 기다린 뒤(기본 60초) HALF_OPEN에서 시험 호출로 회복을 확인하고 CLOSED로 돌아가요 |
| 요청 제한·폴백 | DB 보호 | DB로 가는 동시 요청 수를 제한하고, 실패하면 기본값이나 옛 값을 줘요 |
| **캐시 워밍**(warming, 미리 데워 두기) | 재시작·배포 | 재시작이나 배포 직후 인기 키를 미리 채워 둬요 |

TTL 지터는 "동시 만료"만 풀어 줘요. 캐시 서버가 통째로 죽는 경우는 고가용성·로컬 캐시·서킷 브레이커로 따로 막아야 해요.

### 5. 핫키: 키 하나에 트래픽이 몰린다

**왜 생기나.** 연예인 게시물이나 한정판 상품처럼 **키 하나**에 요청이 몰리는 경우예요. Redis Cluster에서 키 하나는 슬롯 하나, 즉 **노드 하나**에만 있어요. 그래서 노드를 아무리 늘려도 그 노드 하나만 과부하가 걸려요. 만료와는 상관없이 생기는 문제예요.

**찾기**: `redis-cli --hotkeys`로 자주 쓰이는 키를 볼 수 있어요. 단, `maxmemory-policy`가 LFU 계열일 때만 동작해요. → [만료와 퇴출](../expire-eviction/)

| 대응 | 어떻게 | 단점 |
|---|---|---|
| 로컬 캐시 | 앱 서버 메모리에 짧게 보관. 네트워크를 안 타서 훨씬 빠르고 Redis로 가는 요청이 줄어요 | 서버마다 값이 잠깐 다를 수 있음 |
| 키 복제 | 같은 값을 `hot:1` ~ `hot:N`에 나눠 넣고 읽을 때 랜덤 선택 → 여러 노드로 분산 | 쓸 때 N개를 다 갱신해야 함 |
| 레플리카 읽기 | 읽기를 복제본으로 분산 | 복제가 비동기라 방금 쓴 값이 늦게 보일 수 있음 |

로컬 캐시의 약점은 "Redis 값이 바뀌었는데 내 메모리 값은 옛날 것"이 되는 거예요. **Redis 6부터** 이걸 돕는 **클라이언트 측 캐싱**(client-side caching) 기능이 있어요. `CLIENT TRACKING ON`을 켠 연결이 읽은 키가 바뀌면 서버가 **INVALIDATE**(이 키 버려) 메시지를 보내 줘요.

- 기본 모드: 서버가 누가 뭘 읽었는지 기억해요(서버 메모리 사용).
- BCAST 모드: 접두사를 구독해요. 서버 메모리는 안 쓰지만 메시지가 많아요.

공식 문서의 주의점도 있어요. 무효화 메시지를 받는 연결이 끊기면 로컬 캐시를 비워야 하고, 모든 키에 최대 TTL을 두는 게 좋아요. 전역 카운터처럼 계속 바뀌는 키는 로컬 캐시에 맞지 않아요.

## 면접 질문

<details>
<summary>Q. 캐시 스탬피드(thundering herd)가 뭔가요? 어떻게 막나요?</summary>

**답변(30초)** 자주 읽히는 캐시 키가 만료되는 순간, 동시에 들어온 요청들이 전부 캐시 미스를 보고 같은 값을 DB에서 다시 계산하는 현상이에요. 몰리는 양은 대략 요청 빈도 곱하기 재계산 시간이고, DB가 느려지면 더 많은 요청이 합류하는 악순환이 생겨요. 대표 대응은 `SET NX PX`로 락을 잡은 한 요청만 계산하게 하는 뮤텍스예요. 실험에서도 동시 요청 100개의 DB 조회가 100번에서 1번으로 줄었어요. 기다림이 싫으면 확률적 조기 갱신이나 옛 값을 주며 뒤에서 갱신하는 방법을 써요.

**꼬리질문**
- Q. 뮤텍스 방식의 단점은요? → 락을 못 잡은 요청이 기다려야 해서 지연이 생겨요. 락 TTL을 재계산 시간보다 길게 맞춰야 하고, 락 잡은 요청이 실패하면 락 만료까지 값이 없어요.
- Q. 락 잡은 서버가 죽으면요? → `PX`로 만료를 걸어 두었으니 그 시간이 지나면 락이 자동으로 풀리고 다른 요청이 다시 잡아요.
- Q. `@Cacheable(sync = true)`면 충분하지 않나요? → 서버 한 대 안에서만 막아요. 서버가 여러 대면 서버마다 한 번씩 조회해요.
</details>

<details>
<summary>Q. 확률적 조기 갱신(XFetch)은 뭐고, 락과 비교하면 어떤가요?</summary>

**답변(30초)** 만료될 때까지 기다리지 않고, 만료가 가까워질수록 높은 확률로 요청 하나가 미리 다시 계산하는 방법이에요. 요청마다 판단 시점이 흩어져서 만료 순간에 몰리지 않아요. 락이 없어 아무도 기다리지 않는 게 장점이에요. 대신 "정확히 1번 계산"은 보장 못 하고, 논문 실험 기준 평균 2번 미만 수준이에요. 계산이 오래 걸리는 키일수록 더 일찍 갱신하는 것도 특징이에요.

**꼬리질문**
- Q. 무엇을 같이 저장해야 하나요? → 값과 함께 지난번 계산 시간(Δ)과 만료 시각을 저장해요.
- Q. β를 키우면요? → 더 일찍 갱신해서 스탬피드는 더 확실히 막지만, 미리 계산하는 횟수가 늘어요.
</details>

<details>
<summary>Q. 캐시 관통이 뭔가요? null 캐싱과 블룸 필터는 각각 언제 쓰나요?</summary>

**답변(30초)** DB에도 없는 키를 반복해서 조회해서 매번 캐시를 지나 DB까지 가는 상황이에요. 업계에서 흔히 관통(penetration)이라고 불러요. 없는 키가 몇 개로 반복된다면 "없음"을 짧은 TTL로 캐시하는 null 캐싱이 가장 쉬워요. 봇이 랜덤 ID를 쏟아내면 키가 끝없이 늘어 null 캐싱이 약해지니, 앞단에 블룸 필터를 둬서 "확실히 없음"이면 바로 거절해요. 여기에 ID 형식 검증과 요청 제한을 더해요.

**꼬리질문**
- Q. null 캐싱 TTL을 길게 잡으면요? → 나중에 실제로 생긴 데이터가 한동안 "없음"으로 보여요. 그래서 짧게 잡아요.
- Q. 블룸 필터 쓰려면 모듈을 깔아야 하나요? → Redis 8부터는 본체에 들어 있어요. 7.x 이하는 RedisBloom 모듈이나 Redis Stack이 필요해요.
</details>

<details>
<summary>Q. 블룸 필터의 거짓 양성·거짓 음성은 어떻게 되나요?</summary>

**답변(30초)** 블룸 필터는 거짓 음성이 없어요. "없다"고 하면 정말 없어요. 대신 거짓 양성이 있어서 "있다"는 가끔 틀려요. 그래서 "없음"이면 바로 거절하고, "있을 수도"면 실제 조회를 해요. 오탐률은 설정할 수 있고, 1%면 아이템당 약 9.6비트로 Set보다 훨씬 작아요.

**꼬리질문**
- Q. 원소를 지울 수 있나요? → 안 돼요. 삭제가 필요하면 Cuckoo 필터를 써요.
- Q. 예상 개수를 넘으면요? → 실패하지 않고 필터를 더 쌓아 늘어나지만, 쌓일수록 조회가 느려져요.
</details>

<details>
<summary>Q. 캐시 눈사태가 뭔가요? 어떻게 대비하나요?</summary>

**답변(30초)** 많은 키가 한꺼번에 사라져서 DB로 트래픽이 쏟아지는 상황이에요. 원인은 같은 TTL로 한 번에 넣은 키들이 같은 시각에 만료되는 경우와, 캐시 서버 자체가 죽는 경우 두 가지예요. 동시 만료는 TTL에 랜덤 값을 더하는 지터로 만료 시각을 흩어서 막아요. 서버 장애는 복제와 Sentinel·Cluster로 이중화하고, 로컬 캐시를 한 단 더 두고, 서킷 브레이커로 DB를 보호해요.

**꼬리질문**
- Q. Redis가 재시작되면 캐시가 비지 않나요? → 영속성(RDB/AOF)을 켜 두면 데이터가 남아요. 그래도 재시작·배포 직후엔 인기 키를 미리 채우는 캐시 워밍을 해요.
- Q. 서킷 브레이커는 어떻게 동작하나요? → 실패율이 기준을 넘으면 OPEN이 되어 호출을 바로 거절하고, 일정 시간 뒤 HALF_OPEN에서 시험 호출로 회복을 확인해 CLOSED로 돌아가요.
</details>

<details>
<summary>Q. 핫키 문제는 뭐고 어떻게 해결하나요?</summary>

**답변(30초)** 키 하나에 요청이 몰리는 문제예요. Redis Cluster에서 키 하나는 노드 하나에만 있어서, 노드를 늘려도 그 노드만 과부하가 걸려요. 가장 효과적인 건 앱 서버 메모리에 짧게 두는 로컬 캐시예요. 그다음으로 같은 값을 `hot:1`부터 `hot:N`까지 복제해 읽을 때 랜덤으로 골라 여러 노드로 나누는 방법이 있어요. 찾을 땐 LFU 정책에서 `redis-cli --hotkeys`를 써요.

**꼬리질문**
- Q. 로컬 캐시면 데이터 정합성은요? → Redis 6의 클라이언트 측 캐싱(`CLIENT TRACKING`)을 켜면 키가 바뀔 때 서버가 무효화 메시지를 보내 줘요. 연결이 끊기면 로컬 캐시를 비우고, 모든 키에 최대 TTL을 둬요.
- Q. 키 복제의 단점은요? → 값을 바꿀 때 N개를 다 갱신해야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 오전 10시 이벤트 오픈 순간 DB CPU가 100%가 되고 응답 시간이 10배로 늘었습니다. 메인 배너의 상품 랭킹은 Redis에 TTL 5분으로 캐시돼 있습니다.</summary>

**상황 파악**
캐시가 있는데도 DB가 터졌다면 "캐시를 못 쓴 요청이 순간적으로 많았다"는 뜻이에요. 이벤트 오픈이라 랭킹 키 하나에 요청이 몰려 있었고(핫키), 그 키가 마침 만료되면 동시 미스가 전부 같은 랭킹 쿼리로 DB에 가요. DB 슬로 쿼리 로그에서 **같은 랭킹 쿼리가 동시에 수십~수백 개** 돌았는지, 그 시각에 랭킹 키가 만료됐는지부터 확인해요.

**원인 후보**
1. **캐시 스탬피드**: 인기 키 만료 순간 요청들이 동시에 재계산. 랭킹 쿼리가 무거워 재계산 시간이 길수록 몰리는 요청도 많아요.
2. 이벤트 직전 캐시가 비어 있었음(배포·재시작 뒤 워밍 안 함).
3. 랭킹 키가 든 Redis 노드 자체가 핫키로 과부하.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 뮤텍스(`SET lock:rank 토큰 NX PX`) | DB 조회를 1번으로 줄임(실험: 100번 → 1번). 구현이 단순 | 나머지 요청이 기다림. 락 TTL을 재계산 시간보다 길게 맞춰야 함 |
| B. 옛 값 반환 + 한 요청만 갱신(논리 만료 > 물리 TTL) | 사용자 대기 없음 | 잠깐 이전 랭킹이 보임 |
| C. 백그라운드 갱신(스케줄러가 1분마다 덮어쓰기) | 만료 자체가 없어 스탬피드 원천 차단 | 갱신 작업을 따로 운영·감시해야 함 |
| D. 확률적 조기 갱신(XFetch) | 락 없음, 대기 없음 | 정확히 1번 보장은 아님, 값과 함께 계산 시간을 저장해야 함 |

**내가 고를 방법**
랭킹은 몇 초 늦어도 괜찮은 데이터라 **B + A**를 골라요. 옛 값을 주면서 갱신은 락 잡은 한 요청만 해서 사용자도 안 기다리고 DB도 한 번만 맞아요. 이벤트처럼 시각이 정해진 경우엔 **오픈 전에 캐시 워밍**을 하고, 이벤트 기간엔 C로 아예 만료가 안 나게 해요. 키 하나에 몰리는 게 심하면 앱 서버 로컬 캐시를 짧게 더해요. 적용 후 DB 동시 쿼리 수와 p99 응답 시간이 평소 수준인지 확인해요.

**채점 포인트**: 만료 순간 동시 미스, 요청 빈도 × 재계산 시간, 한 요청만 재계산(SET NX PX), 락 TTL과 PX 자동 해제, 대기 vs 옛 값 트레이드오프, 확률적 조기 갱신, 캐시 워밍, 핫키면 로컬 캐시, 적용 후 측정.
</details>

<details>
<summary>상황: 봇이 존재하지 않는 상품 ID로 초당 수천 건씩 조회해서 캐시 히트율이 급락하고 DB 부하가 올라갔습니다.</summary>

**상황 파악**
캐시 히트율이 떨어졌는데 조회되는 키가 **DB에도 없는 ID**라면 업계에서 흔히 부르는 **캐시 관통**이에요. 없는 키는 캐시에 아무것도 남지 않아서 매번 DB까지 가요. 로그에서 404 비율, 요청 ID 분포(랜덤인지, 몇 개가 반복되는지), 요청 IP를 먼저 봐요.

**원인 후보**
1. 랜덤 ID 공격: 매 요청이 새 키라 어떤 캐싱도 히트가 안 나요.
2. 몇 개의 없는 ID 반복(삭제된 상품 링크 등): "없음"을 캐시하지 않아 반복적으로 DB에 가요.
3. ID 형식 검증이 없어 말도 안 되는 값(음수, 너무 큰 수)도 DB까지 가요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. null 캐싱(짧은 TTL, 예: 1분) | 구현이 가장 쉬움. 반복되는 없는 ID에 바로 효과 | 랜덤 ID면 쓰레기 키만 쌓여 효과 약함. TTL이 길면 새 상품이 늦게 보임 |
| B. 블룸 필터(Redis 8 내장 `BF.EXISTS`) | 적은 메모리로 랜덤 ID도 "확실히 없음"이면 바로 거절 | 상품 추가 시 필터에도 넣어야 함(빠지면 진짜 상품이 막힘). 삭제 불가 → 삭제 많으면 Cuckoo 필터 |
| C. 입력 검증 + IP별 요청 제한 | 공격량 자체를 줄임 | 형식이 맞는 가짜 ID는 못 거름 |

**내가 고를 방법**
당장은 **C**로 형식이 틀린 요청과 과도한 IP를 끊고, 랜덤 ID 공격이니 **B**를 앞단에 둬요. 상품 등록 로직에 `BF.ADD`를 넣고, 초기에는 전체 상품 ID로 필터를 채워요. "있을 수도"라는 오탐으로 가끔 DB까지 가는 건 그다음 단계인 **A**(null 캐싱, 짧은 TTL)로 받아요. 블룸 필터가 비거나 누락되면 진짜 상품이 막히니, 필터 적재가 끝났는지 확인하고 켜요.

**채점 포인트**: 없는 키는 캐시에 안 남음, null 캐싱과 짧은 TTL 이유, 랜덤 키엔 null 캐싱 약함, 블룸 필터 거짓 음성 없음·거짓 양성 있음, 데이터 추가 시 필터 동기화, 삭제 불가(Cuckoo), Redis 8 내장, 입력 검증·rate limit.
</details>

<details>
<summary>상황: 매일 자정에 배치가 상품 캐시 수만 개를 TTL 24시간으로 한꺼번에 넣습니다. 그 뒤로 매일 자정 정각마다 DB 트래픽이 튀고 여러 API가 함께 느려집니다.</summary>

**상황 파악**
**정해진 시각에, 여러 API가 함께** 느려진다면 키 하나가 아니라 많은 키가 동시에 캐시를 못 쓰게 된 거예요. 같은 시각에 같은 TTL로 넣었으니 다음 날 같은 시각에 같이 만료돼요. 업계에서 흔히 **캐시 눈사태**라고 불러요. 자정 전후 Redis의 만료 키 수와 DB 쿼리 수 그래프를 겹쳐 보면 확인돼요.

**원인 후보**
1. 동일 TTL로 동시 적재 → 동시 만료.
2. 그 순간 인기 키들은 스탬피드까지 겹쳐 같은 쿼리가 여러 번 나감.
3. 배치 적재 자체가 자정에 DB를 크게 읽음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. TTL 지터(24시간 + 0~30분 랜덤) | 한 줄 수정으로 만료를 흩음 | 키마다 갱신 시각이 달라 데이터 최신성이 키마다 조금씩 다름 |
| B. 배치가 만료 전에 미리 덮어쓰기 | 만료로 인한 미스 자체가 없음 | 배치가 실패하면 결국 동시 만료로 돌아감. 배치 감시 필요 |
| C. 인기 키에 뮤텍스/옛 값 반환 추가 | 겹친 스탬피드까지 막음 | 코드 복잡도 증가 |

**내가 고를 방법**
**A**를 바로 적용해요. 변경이 작고 원인(같은 만료 시각)을 직접 없애요. 상품 데이터가 자정에 바뀌는 게 아니라면 배치도 한 시각에 몰지 말고 나눠 돌려요. 인기 상품 몇 개는 **C**를 더해 남은 동시 미스도 한 번 조회로 줄여요. 이건 동시 만료만 푸는 것이니, Redis 장애로 캐시가 통째로 비는 경우에 대비한 이중화(Sentinel/Cluster)와 서킷 브레이커도 함께 점검해요.

**채점 포인트**: 동일 TTL → 동시 만료, 키 하나(스탬피드)와 키 전부(눈사태) 구분, TTL 지터, 배치 분산·미리 갱신, 인기 키 스탬피드 겹침, 서버 장애는 고가용성·서킷 브레이커·로컬 캐시로 별도 대비, 만료 키 수와 DB 쿼리 그래프로 검증.
</details>

<details>
<summary>상황: 한정판 상품 하나에 트래픽이 몰려 Redis Cluster 노드 6개 중 한 노드만 CPU 100%이고, 그 노드를 쓰는 요청이 전부 느려졌습니다.</summary>

**상황 파악**
노드 하나만 바쁘다면 데이터가 고르게 나뉘지 않았거나 **특정 키에 요청이 몰린** 거예요. Cluster에서 키 하나는 슬롯 하나, 노드 하나에만 있으니 노드를 늘려도 안 풀려요. `redis-cli --hotkeys`(LFU 정책일 때)로 어떤 키가 뜨거운지 확인해요.

**원인 후보**
1. 핫키: 한정판 상품 키 하나에 읽기 집중.
2. 그 키가 큰 값(빅키)이라 한 번 읽을 때마다 네트워크·CPU를 많이 씀.
3. 같은 슬롯에 다른 인기 키도 몰려 있음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 앱 서버 로컬 캐시(수 초 TTL) | Redis로 가는 요청 자체가 크게 줄고 가장 빠름 | 서버마다 값이 잠깐 다를 수 있음 → `CLIENT TRACKING`으로 무효화하거나 TTL을 짧게 |
| B. 키 복제(`hot:1` ~ `hot:N`, 읽을 때 랜덤) | 여러 노드로 읽기 분산 | 값이 바뀔 때 N개 다 갱신해야 함 |
| C. 레플리카에서 읽기 | 설정만으로 읽기 분산 | 복제가 비동기라 방금 바뀐 재고 같은 값이 늦게 보임 |

**내가 고를 방법**
상품 상세 정보처럼 잘 안 바뀌는 데이터라면 **A**가 가장 효과가 커요. TTL을 몇 초로 짧게 두고, 정합성이 더 필요하면 Redis 6+의 클라이언트 측 캐싱으로 무효화 메시지를 받아요. 그래도 Redis로 가는 양이 많으면 **B**로 노드를 나눠요. 재고처럼 계속 바뀌는 숫자는 로컬 캐시에 맞지 않으니 따로 처리해요. 그리고 이 키가 만료되는 순간 스탬피드가 나지 않도록 뮤텍스나 미리 갱신을 같이 걸어요.

**채점 포인트**: 키 하나 = 슬롯 하나 = 노드 하나, `--hotkeys`(LFU)로 탐지, 로컬 캐시와 정합성(Tracking·짧은 TTL), 키 복제의 쓰기 비용, 레플리카 비동기 복제, 계속 바뀌는 값은 로컬 캐시 부적합, 핫키 + 만료 = 스탬피드.
</details>

## 필기 포인트

- 스탬피드 = **키 하나**(인기 키) 만료, 관통 = **원래 없는 키**, 눈사태 = **많은 키 동시**(또는 캐시 서버 전체), 핫키 = 만료 무관 **키 하나에 집중**.
- "관통·눈사태·격파"는 업계 통칭이고 Redis 공식 용어가 아님. 영어로 stampede / penetration / avalanche / breakdown.
- 블룸 필터: **거짓 음성 없음, 거짓 양성 있음**. 삭제 불가(→ Cuckoo). Redis 8부터 본체 포함.
- `SET key 값 NX PX ms`: NX = 없을 때만, 이미 있으면 nil. PX = 밀리초 만료.
- `@Cacheable(sync = true)`는 JVM 하나 안에서만 보호.
- TTL 지터는 동시 만료만 해결. 서버 장애는 고가용성·서킷 브레이커·로컬 캐시.
- `redis-cli --hotkeys`는 LFU 계열 `maxmemory-policy`에서만 동작.
