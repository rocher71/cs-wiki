:::tip[한 줄 요약]
**Pub/Sub**는 메시지를 저장하지 않고 **지금 구독 중인 사람에게 한 번만** 보내요(at-most-once). 구독자가 없거나 끊겨 있으면 그 메시지는 사라져요. **Streams**는 메시지를 키에 **저장**하고, 컨슈머 그룹이 **누가 받았고 처리를 끝냈는지(ACK)** 기록해서 죽은 컨슈머 몫도 다시 가져올 수 있어요(at-least-once).
:::

:::note[처음이라면 여기까지]
① **Pub/Sub**는 라디오 방송처럼 지금 듣고 있는 구독자에게만 보내고 저장하지 않아요. 듣는 사람이 없으면 그 메시지는 사라져요.

② **Streams**는 메시지를 저장해 두고, 누가 받았고 처리를 끝냈는지(**ACK**, 처리 완료 확인) 기록해요. 그래서 처리하다 죽은 몫도 다시 가져올 수 있어요.

③ 놓치면 곤란한 메시지는 Streams 쪽이에요. 다만 Streams도 유실이 완전히 0은 아니에요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

**Pub/Sub는 라디오 방송**이에요. 방송국(발행자)은 누가 듣는지 모른 채 주파수(채널)에 말을 내보내요. 그 순간 라디오를 켜 둔 사람(구독자)만 들어요. 라디오를 꺼 둔 사이에 나온 뉴스는 다시 들을 방법이 없어요. 녹음을 안 하니까요.

**Streams는 아파트 택배 보관함**이에요. 택배 기사(생산자)가 물건을 보관함에 넣으면, 받는 사람이 집에 없어도 물건은 남아 있어요. 관리실(컨슈머 그룹)은 "몇 번 칸 물건을 누가 가져갔는지, 수령 확인 도장(ACK)을 찍었는지" 장부에 적어요. 누가 물건을 가져가 놓고 도장을 안 찍은 채 연락이 끊기면, 관리실이 일정 시간 뒤 그 물건을 다른 사람에게 넘겨 처리하게 할 수 있어요.

단, 실제로는 보관함이 무한히 크지 않아요. Streams도 메모리에 저장되기 때문에 오래된 메시지를 잘라 내야 하고, 잘라 내는 순간 아직 도장을 안 찍은 메시지까지 사라질 수 있어요. 아래 실험에서 직접 확인해요.

## 제대로 알기

### 1. Pub/Sub: 보내고 잊는 방송

**Pub/Sub**(Publish/Subscribe, 발행/구독)는 발행자가 받을 사람을 모른 채 **채널**(channel, 메시지를 흘려보내는 이름표)에 메시지를 보내고, 구독자는 관심 있는 채널만 구독하는 방식이에요. 발행자와 구독자는 서로의 존재를 몰라도 돼요. 이걸 **디커플링**(decoupling, 서로 직접 묶이지 않음)이라고 해요.

```bash
# 터미널 1: 구독자
SUBSCRIBE news
# 터미널 2: 발행자 — 반환값은 "메시지를 받은 클라이언트 수"
PUBLISH news "hello"
```

꼭 알아야 할 성질이에요.

- **전달 보장은 at-most-once**(최대 한 번, 많아야 한 번 전달하고 다시 보내지 않음)예요. 구독자가 처리하다 실패하거나 네트워크가 끊기면 그 메시지는 영영 사라져요. 공식 문서도 더 강한 보장이 필요하면 Streams를 쓰라고 안내해요.
- **어디에도 저장하지 않아요.** 구독자가 없을 때 발행하면 아무도 못 받고, 나중에 구독해도 지난 메시지는 오지 않아요. AOF·RDB 같은 영속성과도 상관없어요.
- `PUBLISH`의 반환값은 **보낸 클라이언트 수**일 뿐, 처리에 성공한 수가 아니에요. Cluster에서는 **발행한 노드에 붙은 구독자만** 세요.
- 한 구독자는 발행된 순서대로 메시지를 받아요.
- **DB 번호를 무시해요.** db 10에서 발행해도 db 1 구독자가 받아요. 환경을 나누려면 `prod:`, `test:` 같은 접두사를 채널 이름에 붙여요.

#### 구독 전용 연결

예전 통신 규약인 RESP2에서는 구독 중인 연결이 `SUBSCRIBE`/`UNSUBSCRIBE` 계열, `PING`, `QUIT`, `RESET`만 쓸 수 있어요. RESP3(`HELLO 3`)에서는 구독 중에도 다른 명령을 쓸 수 있어요. 그래서 클라이언트 라이브러리는 보통 **구독용 연결을 따로** 둬요.

#### 패턴 구독

`PSUBSCRIBE news.*`처럼 **글롭 패턴**(glob, `*` 같은 와일드카드로 이름을 고르는 방식)으로 여러 채널을 한 번에 구독할 수 있어요. 이때 받는 메시지 종류는 `pmessage`예요(패턴, 실제 채널, 내용이 같이 와요). 공식 문서에 따르면 채널 `news.art`와 그 채널에 맞는 패턴 `news.*`을 **둘 다 구독하면 같은 메시지를 두 번**(`message` 한 번, `pmessage` 한 번) 받아요.

#### 심화: Cluster와 Sharded Pub/Sub

일반 Pub/Sub는 Cluster에서 아무 노드에 발행해도 되지만, 그 메시지가 **클러스터의 모든 노드로 퍼져요.** 노드가 많아질수록 노드끼리 주고받는 트래픽이 커져요.

**Sharded Pub/Sub**(**Redis 7.0+**, `SSUBSCRIBE`/`SPUBLISH`)는 채널 이름을 키처럼 **해시 슬롯**(키가 배정되는 칸)에 배정해서, 그 슬롯을 맡은 샤드(마스터와 레플리카) 안에서만 메시지를 퍼뜨려요. 그래서 샤드를 늘리면 처리량도 같이 늘어요. → [복제와 클러스터](../replication-cluster/)

### 2. Streams: 저장하는 로그

**Stream**은 **추가 전용 로그**(append-only log, 뒤에 붙이기만 하는 기록장)예요. 메시지(**엔트리**, entry)가 키에 저장되고, 사용자가 지우거나 잘라 내지 않으면 계속 남아요.

```bash
# 엔트리 추가 — * 를 주면 서버가 ID를 만들어 줌
XADD orders * orderId 1
# 전체 조회 (- 는 최소 ID, + 는 최대 ID)
XRANGE orders - +
# 새 메시지가 올 때까지 최대 5초 대기 ($ = 지금 마지막 ID 이후)
XREAD BLOCK 5000 STREAMS orders $
```

- **엔트리 ID**는 `밀리초타임스탬프-순번` 형식이에요(예: `1764200000000-0`). 서버 시계가 뒤로 가도 직전 ID를 기준으로 삼아 **ID는 항상 커져요.**
- `XADD`는 O(1)이에요. `XRANGE`는 가져오는 개수만큼 O(N)이에요.
- `XREAD`는 읽는 클라이언트가 여러 명이면 **모두가 같은 메시지를 받아요**(팬아웃, fan-out). 작업을 나눠 갖고 싶으면 컨슈머 그룹을 써요.
- 다른 자료구조와 달리 엔트리가 0개가 돼도 **키가 지워지지 않아요.** 컨슈머 그룹 정보를 지키기 위해서예요.

#### 심화: 헷갈리는 특수 ID 정리

| 기호 | 쓰는 곳 | 뜻 |
|---|---|---|
| `*` | `XADD` | ID를 서버가 자동 생성 |
| `-` / `+` | `XRANGE` | 가능한 최소 / 최대 ID |
| `$` | `XREAD`, `XGROUP CREATE` | 지금 스트림의 마지막 ID (이후 새 것만) |
| `>` | `XREADGROUP` | 그룹에서 아직 아무에게도 안 준 새 메시지 |
| `0` | `XREADGROUP` | 새 메시지가 아니라 **내 PEL 이력**(받고 ACK 안 한 것) |

### 3. 컨슈머 그룹, PEL, ACK

**컨슈머 그룹**(consumer group)은 여러 **컨슈머**(consumer, 메시지를 꺼내 처리하는 프로그램)가 한 스트림을 **나눠서** 처리하게 해 줘요. 그룹 안에서는 **한 메시지를 한 컨슈머에게만** 줘요.

```bash
# 그룹 g1 생성 (0 = 처음부터, $ = 지금 이후부터)
XGROUP CREATE orders g1 0
# c1이 새 메시지 2개 받기
XREADGROUP GROUP g1 c1 COUNT 2 STREAMS orders >
# 처리 끝났다고 알리기
XACK orders g1 <엔트리ID>
```

- 컨슈머는 이름으로 구분하고, 처음 이름이 나올 때 자동으로 만들어져요.
- 그룹은 "아직 아무에게도 안 준 첫 위치"(last-delivered-id)를 기억해요.
- **한 스트림에 그룹을 여러 개** 붙이면 **각 그룹이 모든 엔트리를 받아요.** 그래서 "알림 서비스용 그룹", "정산 서비스용 그룹"을 따로 두면 같은 이벤트를 각자 처리할 수 있어요.
- Redis는 컨슈머가 "준비됐다"고 읽어 갈 때 메시지를 줘요. 빠른 컨슈머가 더 많이 가져가요.
- `XREADGROUP`은 이름은 읽기지만 그룹 상태를 바꾸는 **쓰기 명령**이라 마스터에서만 호출할 수 있어요.

**PEL**(Pending Entries List, 대기 목록)은 **컨슈머에게 줬지만 아직 ACK 안 된 메시지 목록**이에요. **ACK**(acknowledge, `XACK`)는 "제대로 처리했어요"라는 확인이고, 그 메시지를 그룹의 PEL에서 빼요. 중요한 점은 **ACK해도 스트림의 엔트리는 그대로 남는다**는 거예요. 메모리는 아래 트리밍으로 따로 관리해요.

`XPENDING orders g1`은 대기 개수와 컨슈머별 개수를, `XPENDING orders g1 - + 10`은 메시지마다 **주인 컨슈머, idle 시간**(마지막으로 전달된 뒤 지난 ms), **전달 횟수**를 보여 줘요. 읽기 전용이라 운영 중에 봐도 안전해요. `XINFO GROUPS orders`에는 pending, lag(아직 안 읽은 양) 같은 모니터링 값이 나와요.

### 4. 컨슈머가 죽으면: XCLAIM과 XAUTOCLAIM

컨슈머가 메시지를 받고 ACK 전에 죽으면, 그 메시지는 **누군가 가져가지(claim) 않는 한 영원히 그 컨슈머 몫으로 PEL에 남아요.** Redis가 알아서 다른 컨슈머에게 넘겨주지 않아요.

- `XCLAIM key group consumer min-idle-time id...`: idle이 기준보다 긴 메시지만 내 소유로 가져와요. 가져오면 idle이 0이 되고 전달 횟수가 1 늘어요. 그래서 두 컨슈머가 동시에 가져가려 해도 하나만 성공해요.
- `XAUTOCLAIM key group consumer min-idle-time start [COUNT n]`(**Redis 6.2+**): `XPENDING`으로 찾고 `XCLAIM`으로 가져오는 일을 한 번에, **커서**(다음에 이어 볼 위치) 방식으로 조금씩 해요(기본 100개). 응답은 3개예요.
  1. 다음 커서 (`0-0`이면 PEL을 끝까지 다 봤다는 뜻)
  2. 가져온 메시지들
  3. 이미 스트림에서 사라진 ID 목록 (**7.0+**, 이 PEL 항목은 정리됨)
- 재시작한 컨슈머는 `XREADGROUP ... STREAMS orders 0`으로 **자기가 받고 처리 못 한 메시지**부터 다시 처리할 수 있어요.

#### 포이즌 메시지와 dead letter

어떤 메시지는 내용이 잘못돼서 몇 번을 다시 처리해도 실패해요(**포이즌 메시지**, poison message). 가져갈 때마다 전달 횟수가 늘어나니, **횟수가 임계값을 넘으면 별도 스트림으로 옮기고 알림**을 보내요. 이게 Streams에서 쓰는 **dead letter**(처리 불가 메시지 격리) 방식이에요. Redis에 자동 DLQ 기능은 없어서 직접 구현해요.

#### 결국 at-least-once, 그래서 멱등하게

컨슈머가 처리는 끝냈는데 ACK 직전에 죽으면, 다른 컨슈머가 그 메시지를 가져가 **한 번 더 처리**해요. 그래서 컨슈머 그룹은 **at-least-once**(최소 한 번, 중복될 수는 있지만 빠지진 않게)예요. exactly-once(정확히 한 번)는 아니에요. 컨슈머는 **멱등**(idempotent, 같은 일을 두 번 해도 결과가 같음)하게 짜야 해요. 예를 들어 주문 ID로 "이미 처리했는지"를 먼저 확인해요.

<Aside type="tip" title="최신 기능 (언급만)">
**8.8+** `XNACK`: 컨슈머가 자기 pending 메시지를 ACK 없이 그룹에 돌려놓아 바로 재전달되게 해요(정상 종료 시 등). **8.6+** `XADD ... IDMP`: 생산자 쪽 중복 추가를 막아요. **8.2+** 트리밍 옵션 `ACKED`는 아래에서 볼게요.
</Aside>

### 5. 트리밍: 보관함 비우기와 그 함정

스트림은 메모리에 계속 쌓이니 잘라 내야 해요.

- `XADD orders MAXLEN ~ 10000 * ...`: 최근 약 1만 개만 남겨요. `~`는 **근사 트리밍**(내부 덩어리 단위로 잘라서 정확히 N개보다 조금 더 남을 수 있지만 효율적)이고, 공식 문서는 이 방식을 권해요.
- `MINID`(**6.2+**): 이 ID보다 작은(오래된) 엔트리를 지워요. 시간 기준으로 보존할 때 좋아요.
- `XTRIM`으로 따로 잘라도 돼요.

**함정**: 트리밍의 기본 동작(KEEPREF)은 **ACK 여부를 보지 않고** 잘라요. 느린 그룹이 아직 처리하지 않은 메시지도 사라질 수 있어요. **Redis 8.2+**에서는 `ACKED` 옵션(모든 그룹이 ACK한 것만 자름)을 쓸 수 있지만, 기본값은 여전히 KEEPREF예요.

### 심화: 6. 내구성: Streams도 유실이 0은 아니에요

스트림과 **컨슈머 그룹 상태(PEL 포함)**는 AOF·RDB에 저장되고 레플리카로 복제돼요. 다만 복제가 **비동기**(마스터가 레플리카 반영을 기다리지 않음)라, 장애 조치 뒤 최근 `XADD`나 ACK 기록이 빠질 수 있어요. 중요하면 AOF + 강한 fsync 설정, 필요하면 `WAIT`을 써요. 그래도 Sentinel/Cluster 장애 조치는 최선을 다할 뿐이라 유실 가능성이 완전히 0은 아니에요. → [영속성](../persistence/)

### 7. Pub/Sub vs Streams vs Kafka

**Kafka**는 이벤트를 디스크에 저장하는 분산 이벤트 스트리밍 플랫폼이에요. 여기서는 개요만 비교하고, 자세한 내용은 [메시지 큐와 Kafka](../../distributed/message-queue-kafka/)에서 다뤄요.

| | Pub/Sub | Streams | Kafka (개요) |
|---|---|---|---|
| 저장 | 안 함 | 메모리(키), AOF·RDB로 영속화 | 디스크 로그, 보존 기간 설정 |
| 전달 보장 | at-most-once | at-least-once (컨슈머 그룹) | 기본 at-least-once, 트랜잭션을 쓰면 Kafka 토픽 사이 처리에서 exactly-once 가능 |
| 지난 메시지 다시 읽기 | 불가 | 가능 (트리밍 전까지) | 가능 (소비해도 안 지움) |
| 나눠 처리 | 없음 (모두에게 방송) | 컨슈머 그룹 | 컨슈머 그룹 + 파티션 |
| 확장 단위 | Sharded Pub/Sub(7.0+) | 키 하나는 한 노드, 나누려면 키 여러 개 | 토픽을 여러 브로커의 파티션으로 |
| 순서 | 발행 순서 | 스트림 안 ID 순 (컨슈머 여럿이면 처리 순서는 섞일 수 있음) | 파티션 안에서만 |
| 잘 맞는 곳 | 실시간 알림, 서버 간 브로드캐스트 | 이미 Redis를 쓰는 곳의 작업 큐, 짧은 보존 | 대용량, 장기 보존, 재처리, 여러 팀 공유 |

공식 문서는 **Redis 컨슈머 그룹이 이름만 같을 뿐 Kafka 컨슈머 그룹과 구현이 다르다**고 밝혀요. Kafka는 파티션을 컨슈머에게 배정하지만, Redis는 한 키에서 준비된 컨슈머에게 메시지를 줘요. 스트림 하나는 여러 서버로 자동으로 나뉘지 않아서, Kafka 파티션처럼 쓰려면 **키를 N개** 만들어 Cluster로 흩어야 해요.

### 심화: 8. 실험 결과 (Redis 8.x)

**A. Pub/Sub 유실**

| 단계 | 결과 |
|---|---|
| 구독자 없이 `PUBLISH news hello-nobody` | 반환 `0` (아무도 못 받음) |
| 구독자 1명 연결 후 발행 | `PUBSUB NUMSUB news` = 1, 반환 `1`, 구독자가 받음 |
| 구독자 종료 후 `PUBLISH news lost-msg` | 반환 `0` |
| 다시 구독 후 `after-resub` 발행 | `after-resub`만 받고 `lost-msg`는 끝내 안 옴 |

채널과 패턴을 동시에 구독했을 때의 이중 수신은 실험 방식(명령을 파이프로 흘려보냄) 때문에 패턴 구독이 늦게 등록돼 재현하지 못했어요. 위 설명은 공식 문서 근거예요.

**B. Streams 컨슈머 그룹**

| 단계 | 결과 |
|---|---|
| 4건 `XADD` 후 c1, c2가 각각 `COUNT 2`로 읽기 | c1이 1·2번, c2가 3·4번. c1이 다시 `>`로 읽으면 빈 응답 |
| 1번 `XACK` 후 `XPENDING` | 3건 (c1: 1건, c2: 2건) |
| 1.5초 뒤 `XAUTOCLAIM orders g1 c1 1000 0-0` | 커서 `0-0`, 2·3·4번 모두 c1로 이동(c1 자신의 2번도 idle이 1초를 넘어 포함), 전달 횟수 2, idle은 수십 ms로 리셋 |
| 그룹 g2 추가 | g2는 4건 모두 따로 받음 |
| `XADD orders MAXLEN 2 * ...` | `XLEN` 2인데 g1의 PEL은 여전히 3건 (없는 엔트리를 가리킴) |
| 이어서 `XAUTOCLAIM` | 세 번째 응답으로 사라진 ID 2개를 돌려주고 PEL에서 정리 → **ACK 전에 잘린 메시지는 내용이 사라짐** |

## 면접 질문

<details>
<summary>Q. Redis Pub/Sub의 전달 보장은 무엇이고, 구독자가 없거나 끊기면 어떻게 되나요?</summary>

**답변(30초)** at-most-once예요. Pub/Sub는 메시지를 저장하지 않고 그 순간 구독 중인 클라이언트에게 한 번만 보내요. 구독자가 없으면 아무도 못 받고, 끊겨 있던 사이의 메시지는 다시 구독해도 오지 않아요. 실험에서도 구독자가 없을 때 `PUBLISH` 반환값이 0이었고, 재구독 후 그 메시지는 오지 않았어요. 놓치면 안 되는 메시지는 Streams를 써요.

**꼬리질문**
- Q. `PUBLISH` 반환값이 1이면 처리가 성공한 건가요? → 아니에요. 메시지를 보낸 클라이언트 수일 뿐이고, 구독자가 처리에 실패해도 다시 보내지 않아요. Cluster에서는 발행한 노드의 구독자만 세요.
- Q. Pub/Sub 메시지도 AOF에 남나요? → 아니에요. 저장 자체를 안 해서 영속성과 무관해요.
</details>

<details>
<summary>Q. Pub/Sub와 Streams는 어떻게 다르고, 언제 무엇을 쓰나요?</summary>

**답변(30초)** 가장 큰 차이는 저장 여부예요. Pub/Sub는 저장 없이 지금 듣는 모두에게 방송하는 at-most-once라, 놓쳐도 괜찮은 실시간 알림이나 서버 간 브로드캐스트에 써요. Streams는 메시지를 키에 저장하고, 컨슈머 그룹이 누가 받았고 ACK했는지 기록해서 at-least-once를 줘요. 그래서 주문 이벤트 처리처럼 빠지면 안 되는 작업 큐에 써요.

**꼬리질문**
- Q. Streams에서 여러 서비스가 같은 이벤트를 다 받게 하려면요? → 서비스마다 컨슈머 그룹을 따로 만들어요. 그룹끼리는 모든 엔트리를 각자 받고, 그룹 안에서만 나눠 처리해요.
- Q. 그냥 `XREAD`와 `XREADGROUP`의 차이는요? → `XREAD`는 읽는 모두가 같은 메시지를 받고 ACK 기록이 없어요. `XREADGROUP`은 그룹 안에서 한 메시지를 한 컨슈머에게만 주고 PEL로 추적해요.
</details>

<details>
<summary>Q. 컨슈머 그룹에서 PEL과 ACK는 무엇인가요?</summary>

**답변(30초)** PEL은 컨슈머에게 전달했지만 아직 ACK를 받지 못한 메시지 목록이에요. 메시지마다 주인 컨슈머, 마지막 전달 후 지난 시간, 전달 횟수를 기록해요. 컨슈머가 처리를 끝내고 `XACK`을 보내면 그 메시지가 PEL에서 빠져요. 단, ACK는 PEL에서만 빼는 거라 스트림의 엔트리 자체는 남고, 메모리는 MAXLEN이나 MINID로 따로 관리해요.

**꼬리질문**
- Q. 재시작한 컨슈머는 무엇부터 처리하나요? → `XREADGROUP ... STREAMS key 0`으로 자기 PEL의 미처리 메시지를 먼저 처리하고, 그다음 `>`로 새 메시지를 받아요.
- Q. PEL을 어떻게 모니터링하나요? → `XPENDING`으로 개수와 idle 시간을, `XINFO GROUPS`로 pending과 lag을 봐요.
</details>

<details>
<summary>Q. 컨슈머가 처리 중에 죽으면 메시지는 어떻게 되고, 어떻게 복구하나요?</summary>

**답변(30초)** 그 메시지는 죽은 컨슈머 몫으로 PEL에 계속 남아요. Redis가 자동으로 다른 컨슈머에게 넘기지 않아요. 살아 있는 컨슈머가 `XAUTOCLAIM`으로 idle 시간이 기준을 넘은 메시지를 가져와 처리하고 ACK해요. 가져갈 때마다 전달 횟수가 늘어서, 횟수가 임계값을 넘는 메시지는 dead letter 스트림으로 옮겨요.

**꼬리질문**
- Q. 그러면 같은 메시지가 두 번 처리될 수 있나요? → 네. 처리 후 ACK 직전에 죽으면 다시 처리돼요. at-least-once라서 주문 ID 같은 멱등키로 중복을 막아요.
- Q. `XCLAIM`을 두 컨슈머가 동시에 하면요? → 가져가는 순간 idle이 0으로 리셋되니, idle 조건을 만족하는 쪽은 하나뿐이라 하나만 성공해요.
</details>

<details>
<summary>Q. Streams가 끝없이 커지면 어떻게 하나요?</summary>

**답변(30초)** `XADD`에 `MAXLEN ~ N`을 붙이거나 `XTRIM`, `MINID`로 오래된 엔트리를 잘라요. `~`는 근사 트리밍이라 효율적이고 공식 문서도 권해요. 주의할 점은 기본 트리밍이 ACK 여부를 안 봐서, 느린 그룹이 아직 처리 못 한 메시지도 잘린다는 거예요. 실험에서도 MAXLEN 2로 자르자 PEL에 있던 메시지 내용이 사라졌어요. 8.2부터는 모두가 ACK한 것만 자르는 `ACKED` 옵션이 있어요.

**꼬리질문**
- Q. XACK하면 메모리가 줄지 않나요? → 아니에요. ACK는 PEL에서만 빼고 엔트리는 남아요.
</details>

<details>
<summary>Q. Cluster에서 Pub/Sub를 쓰면 어떤 문제가 있나요?</summary>

**답변(30초)** 일반 Pub/Sub는 한 노드에 발행한 메시지를 클러스터의 모든 노드로 퍼뜨려요. 그래서 노드를 늘려도 처리량이 늘지 않고 오히려 노드 간 트래픽만 커져요. Redis 7.0의 Sharded Pub/Sub는 채널을 해시 슬롯에 배정해서 그 슬롯을 가진 샤드 안에서만 메시지를 퍼뜨려요. 그래서 샤드를 늘리면 수평으로 확장돼요.

**꼬리질문**
- Q. 명령이 어떻게 달라요? → `SSUBSCRIBE`, `SPUBLISH`, `SUNSUBSCRIBE`를 써요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문이 완료되면 주문 서버가 Redis Pub/Sub로 이벤트를 보내고, 알림 서버가 받아 푸시를 보냅니다. 그런데 "알림이 가끔 안 온다"는 문의가 들어옵니다. 특히 알림 서버 배포 시간대에 몰려 있습니다.</summary>

**상황 파악**
"가끔", "배포 시간대"라는 단서가 중요해요. 알림 서버가 재시작하는 몇 초 동안 Redis 채널을 구독하는 클라이언트가 없었을 가능성이 커요. Pub/Sub는 저장하지 않고 at-most-once라서, 그 사이 발행된 이벤트는 그냥 사라져요. 주문 서버 로그에서 그 시각 `PUBLISH` 반환값이 0이었는지 확인하면 바로 증명돼요.

**원인 후보**
1. 배포·재시작 중 구독자가 0명이라 메시지가 증발했어요.
2. 알림 서버가 메시지를 받았지만 처리 중 예외가 났어요. Pub/Sub는 재전달이 없어요.
3. 구독 연결이 네트워크 문제로 잠깐 끊겼다가 다시 붙었어요. 끊긴 사이 메시지는 오지 않아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. **Redis Streams + 컨슈머 그룹**으로 전환. 처리 후 `XACK`, 재시작 시 자기 PEL부터 처리 | 구독자가 없어도 메시지가 남음. 재시작 후 이어서 처리. 이미 Redis를 쓰므로 인프라 추가 없음 | at-least-once라 중복 알림 가능 → 주문 ID로 멱등 체크 필요. 트리밍 정책과 PEL 회수 코드 필요 |
| B. Pub/Sub 유지 + 주문을 DB에 "알림 미발송"으로 저장, 주기적 배치가 누락분 재발송 | 기존 구조를 거의 안 바꿈 | 누락 알림이 배치 주기만큼 늦음. DB 조회 부하. 결국 큐를 DB로 흉내 내는 셈 |
| C. Kafka 도입 | 디스크 보존, 재처리, 대용량에 강함 | 이 문제 하나로 새 시스템을 운영하기엔 비용이 큼 |

**내가 고를 방법**
A를 골라요. 원인이 "저장 없는 방송"이라는 구조 자체라서, 메시지를 저장하고 ACK로 추적하는 Streams가 정확한 해결이에요. 이미 Redis를 운영 중이라 추가 비용도 작아요. 중복 알림은 주문 ID를 키로 "발송함" 표시를 남겨 막고, `MAXLEN ~`로 메모리를 관리해요. 전환 후에는 배포 시간대에도 `XINFO GROUPS`의 lag가 0으로 돌아오는지 확인해요.

**채점 포인트**: Pub/Sub는 저장 없음·at-most-once, 구독자 0명이면 PUBLISH 반환 0, PUBLISH 반환값은 처리 성공이 아님, Streams 컨슈머 그룹·XACK, 재시작 시 PEL 재처리, at-least-once와 멱등키, 트리밍, 적용 후 검증.
</details>

<details>
<summary>상황: Streams 컨슈머 그룹으로 작업을 처리하고 있는데, 일부 주문이 몇 시간째 처리되지 않습니다. XPENDING을 보니 이미 없어진 파드 이름의 컨슈머에 수천 건이 쌓여 있습니다.</summary>

**상황 파악**
컨슈머가 메시지를 받은 뒤 ACK 전에 죽으면 그 메시지는 PEL에 그 컨슈머 몫으로 남고, **누가 claim하지 않으면 영원히** 그 상태예요. 쿠버네티스 파드가 재생성될 때 컨슈머 이름이 파드 이름이라 새 이름으로 바뀌었고, 새 컨슈머는 `>`로 새 메시지만 읽으니 옛 이름 몫은 아무도 안 가져가고 있어요. `XPENDING orders g1 - + 10 <옛컨슈머>`로 idle 시간과 전달 횟수를 확인해요.

**원인 후보**
1. 컨슈머 이름이 재시작마다 바뀌어 자기 PEL을 `0`으로 다시 읽는 복구가 안 돼요.
2. PEL을 회수하는 `XAUTOCLAIM` 루틴이 없어요.
3. 일부는 포이즌 메시지라 회수해도 계속 실패할 수 있어요(전달 횟수가 비정상적으로 큼).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 모든 컨슈머가 주기적으로 `XAUTOCLAIM`(min-idle 예: 처리 시간의 몇 배) 실행 | 이름이 바뀌든 죽든 누락분을 자동 회수. 6.2+ 기본 기능 | min-idle을 너무 짧게 잡으면 처리 중인 메시지를 뺏어 와 중복 처리 증가. 멱등 처리 필수 |
| B. 컨슈머 이름 고정(예: StatefulSet 순번) + 시작 시 `XREADGROUP ... 0`으로 자기 PEL 먼저 처리 | 재시작 후 자기 몫을 바로 이어서 처리 | 그 컨슈머가 영영 안 돌아오면(축소 등) 여전히 남음 → A가 같이 필요 |
| C. 전달 횟수가 임계값을 넘으면 dead letter 스트림으로 옮기고 ACK, 알림 | 포이즌 메시지가 계속 회수·실패를 반복하며 자원을 먹는 걸 막음 | 사람이 dead letter를 확인하는 운영 절차 필요 |

**내가 고를 방법**
A + C를 기본으로 깔고 B를 더해요. 지금 쌓인 수천 건은 A로 바로 회수해요. 앞으로도 컨슈머는 언제든 죽을 수 있으니 회수 루틴은 꼭 있어야 하고, 회수만 하면 포이즌 메시지가 무한 반복되니 C로 끊어요. B는 재시작 직후 복구를 빠르게 해 줘요. 안 쓰는 옛 컨슈머는 pending을 다 회수한 뒤 `XGROUP DELCONSUMER`로 지워요. 이후 `XPENDING` 개수와 가장 오래된 idle 시간을 지표로 걸어 알림을 받아요.

**채점 포인트**: PEL은 claim 전까지 그 컨슈머에 묶임, Redis가 자동 재배정하지 않음, XAUTOCLAIM(min-idle, 커서, 6.2+), 전달 횟수와 dead letter, at-least-once·멱등, 컨슈머 이름 관리, DELCONSUMER 전 회수, XPENDING 모니터링, (참고) 8.8+ XNACK.
</details>

<details>
<summary>상황: 새 서비스에 메시지 큐가 필요합니다. 팀은 이미 Redis를 캐시로 운영 중이고, 누군가는 Redis Streams를, 누군가는 Kafka를 제안합니다. 어떻게 결정하겠습니까?</summary>

**상황 파악**
두 기술 모두 "메시지를 저장하고 컨슈머 그룹으로 나눠 처리"할 수 있어요. 결정은 **요구사항**으로 해야 해요. 하루 메시지 양, 얼마나 오래 보관해야 하는지, 지난 이벤트를 다시 처리(리플레이)할 일이 있는지, 몇 팀이 같은 이벤트를 쓰는지, 유실을 얼마나 견딜 수 있는지를 먼저 물어요.

**원인 후보(판단 기준)**
1. **보존량과 기간**: Streams는 메모리에 담겨서 보존량이 메모리 크기에 묶여요. Kafka는 디스크에 보존 기간을 정해 오래 둘 수 있어요.
2. **재처리**: Kafka는 소비해도 지우지 않아 다시 읽기 쉬워요. Streams도 트리밍 전까지는 다시 읽을 수 있지만 길게 보관하기 어려워요.
3. **확장**: Streams 키 하나는 한 노드에 있어서, 나누려면 키를 여러 개 만들어 Cluster로 흩어야 해요. Kafka는 토픽을 파티션으로 나눠 여러 브로커에 둬요.
4. **내구성**: Redis는 비동기 복제라 장애 조치 때 최근 메시지가 빠질 수 있어요.
5. **운영 비용**: Redis는 이미 있어요. Kafka는 새 클러스터를 운영해야 해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Redis Streams | 이미 운영 중이라 바로 시작. 가볍고 지연이 낮음. XACK·XAUTOCLAIM으로 at-least-once | 메모리에 묶인 보존량, 트리밍 시 미처리 메시지 유실 위험, 비동기 복제, 파티션 개념이 없어 키를 직접 나눠야 함 |
| B. Kafka | 디스크 장기 보존, 리플레이, 파티션·복제로 대용량과 여러 팀 공유에 강함 | 새 시스템 학습·운영 비용, 소규모엔 과함 |

**내가 고를 방법**
메시지 양이 적당하고, 보존이 짧고(처리하면 끝), 한두 서비스만 쓰는 작업 큐라면 A를 골라요. 이미 있는 Redis로 빨리 시작할 수 있어요. 대신 AOF 설정, `MAXLEN ~`와 lag 모니터링, 멱등 컨슈머를 같이 챙겨요. 반대로 여러 팀이 같은 이벤트를 구독하는 이벤트 버스이거나, 며칠 이상 보관하고 다시 처리해야 하거나, 유입량이 메모리로 감당하기 어려우면 B를 골라요. 처음엔 A로 시작해도, 이벤트를 다루는 코드를 인터페이스 뒤에 두면 나중에 B로 옮기기 쉬워요.

**채점 포인트**: 요구사항(양·보존·리플레이·소비자 수·유실 허용)부터 질문, 메모리 vs 디스크 보존, 비동기 복제 유실 가능성, Redis 컨슈머 그룹과 Kafka 파티션 구조 차이, 운영 비용, 둘 다 at-least-once라 멱등 필요, 선택 이유를 요구사항과 연결.
</details>

## 필기 포인트

- Pub/Sub: **저장 없음, at-most-once**. `PUBLISH` 반환 = 받은 클라이언트 수(Cluster에선 그 노드만).
- 채널과 맞는 패턴을 둘 다 구독하면 같은 메시지를 **두 번** 받음(`message` + `pmessage`).
- Pub/Sub는 DB 번호 무시. Sharded Pub/Sub(`SPUBLISH`)는 **7.0+**.
- Stream ID = `밀리초-순번`, 항상 증가. `XADD` O(1).
- 특수 ID: `*`(자동 생성), `-`/`+`(최소/최대), `$`(지금 마지막), `>`(그룹 새 메시지), `0`(내 PEL).
- 그룹 안: 한 메시지 → 한 컨슈머. 그룹 사이: 모든 그룹이 전부 받음.
- `XACK`은 PEL에서만 제거, 엔트리는 남음. 컨슈머 그룹 = **at-least-once**.
- `XAUTOCLAIM` **6.2+**, 사라진 ID 정리 **7.0+**. `MINID` **6.2+**. `ACKED` 트리밍 **8.2+**. `XNACK` **8.8+**.
- `XREADGROUP`은 쓰기 명령(마스터에서만).
