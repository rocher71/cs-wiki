**복제**는 마스터의 사본(레플리카)을 만들어 읽기를 나누고, **Sentinel**은 마스터가 죽으면 레플리카를 자동으로 마스터로 올려 주고, **Cluster**는 키를 **16384개 해시 슬롯**으로 나눠 여러 마스터에 분산 저장해요. 셋 다 **비동기 복제**라서, 클라이언트가 OK를 받은 쓰기도 장애 조치 때 잃을 수 있어요.
:::

:::note[처음이라면 여기까지]
① **복제**는 마스터(원본)의 사본(레플리카)을 만들어 읽기를 나눠 받아요.

② **Sentinel**은 마스터가 죽으면 사본 하나를 자동으로 새 마스터로 올려요. **Cluster**는 데이터를 여러 마스터에 나눠 담아요.

③ 사본으로 복사하는 걸 기다리지 않는 방식(**비동기**)이라, OK를 받은 쓰기도 장애 때 잃을 수 있어요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

**복제**는 본점 장부를 지점들이 계속 베껴 쓰는 것과 같아요. 주문(쓰기)은 본점만 받고, 지점은 "장부 보여 주세요"(읽기)만 받아요. 본점은 지점이 다 베꼈는지 기다리지 않고 다음 손님을 받아요. 그래서 빠르지만, 지점 장부는 늘 **조금 늦어요.**

**Sentinel**은 본점을 지켜보는 감시원 여러 명이에요. 본점 불이 꺼지면 감시원끼리 "정말 문 닫았나?" 투표하고, 과반이 동의하면 지점 하나를 새 본점으로 정해요. 손님은 감시원에게 "지금 본점이 어디예요?"라고 물어서 찾아가요.

**Cluster**는 장부가 너무 두꺼워져서 **가나다 순으로 나눠** 여러 본점이 나눠 맡는 거예요. 손님 이름으로 담당 본점이 정해지고, 각 본점은 자기 지점(레플리카)을 따로 둬요.

단, 실제로는 감시원이 지점을 본점으로 올리는 순간, 원래 본점이 받았지만 아직 지점에 베껴지지 않은 주문은 사라질 수 있어요. 이게 이 페이지에서 가장 중요한 함정이에요.

## 제대로 알기

### 1. 복제: 마스터의 사본 만들기

**복제**(replication, 같은 데이터를 다른 서버에도 두는 것)는 Redis에서 **마스터-레플리카**(master-replica) 구조예요. 쓰기를 받는 원본이 **마스터**, 그 사본이 **레플리카**예요. 레플리카는 마스터와 똑같아지려고 계속 따라가고, 연결이 끊기면 알아서 다시 붙어요.

왜 쓸까요?

- **읽기 분산**: 오래 걸리는 읽기를 레플리카로 돌려 마스터 부담을 줄여요.
- **데이터 안전·고가용성**: 마스터가 죽어도 사본이 남아 있어요.

레플리카는 2.6부터 기본이 **읽기 전용**이에요. 실험에서 레플리카에 `SET x 1`을 보내자 `READONLY You can't write against a read only replica.` 에러가 났어요. 쓰기 가능 설정도 있지만 데이터가 어긋나서 권하지 않아요.

#### 동작 방식 3가지

| 상황 | 하는 일 |
|---|---|
| 연결이 멀쩡할 때 | 마스터가 데이터를 바꾸는 명령(쓰기, 만료·퇴출로 지운 것 포함)을 계속 흘려보내요 |
| 잠깐 끊겼다 다시 붙을 때 | 놓친 부분만 받는 **부분 재동기화**를 시도해요 |
| 그게 안 될 때 | 데이터 전체를 다시 받는 **전체 재동기화**를 해요 |

이걸 가능하게 하는 게 **복제 ID**(데이터 이력을 나타내는 랜덤 문자열)와 **오프셋**(복제로 보낸 바이트 수만큼 늘어나는 번호)이에요. 둘을 합치면 "어느 이력의 몇 번째 바이트까지"라는 데이터 버전이 돼요.

- 레플리카는 다시 붙을 때 `PSYNC 복제ID 오프셋`으로 "저 여기까지 받았어요"라고 알려요.
- 마스터는 최근 쓰기를 메모리의 **백로그**(backlog, 최근 복제 스트림을 담아 두는 고정 크기 버퍼)에 들고 있어요. 그 오프셋부터 백로그에 남아 있으면 빠진 부분만 보내요.
- 백로그에서 이미 밀려났거나 모르는 복제 ID면 전체 재동기화로 가요. 백로그 기본 크기는 1MB예요(실험에서 `repl_backlog_size:1048576` 확인).

**전체 재동기화**는 이렇게 진행돼요.

1. 마스터가 백그라운드에서 **RDB**(데이터 전체 스냅숏 파일)를 만들어요. 그동안 들어온 쓰기는 버퍼에 쌓아요.
2. RDB를 레플리카에 보내요. 레플리카는 옛 데이터를 비우고 새로 로드해요.
3. 버퍼에 쌓인 쓰기를 보내고, 이후로는 쓰기 스트림을 계속 흘려보내요.

여러 레플리카가 동시에 요청하면 스냅숏은 한 번만 만들어요. **디스크리스 복제**(diskless, 스냅숏을 디스크에 쓰지 않고 바로 네트워크로 보내는 방식)는 다른 레플리카를 조금 기다렸다가(`repl-diskless-sync-delay`, 실험 기본값 5초) 한꺼번에 보내요. 동기화 중에도 마스터는 요청을 계속 받아요. 스냅숏 파일 자체는 [영속성](../persistence/)에서 자세히 다뤄요.

#### 심화: 실험으로 본 복제

| 해 본 것 | 결과 |
|---|---|
| 레플리카 띄운 직후 마스터에 `SET user:1 kim`, 1초 뒤 레플리카 `GET user:1` | **빈 값**. 초기 동기화가 약 5초 뒤에 끝났어요(디스크리스 대기 5초) |
| 동기화 끝난 뒤 레플리카 `GET user:1` | `kim` |
| 첫 접속 로그 | 마스터 `Full resync requested by replica`, 레플리카 `Partial resynchronization not possible (no cached master)` (이력이 없으니 전체 동기화) |
| 마스터에서 `CLIENT KILL TYPE replica`로 연결 끊기 | 재접속 시 레플리카가 `Trying a partial resynchronization`, 마스터 `Partial resynchronization request ... accepted` → **부분 재동기화 성공** |
| 마스터에서 `WAIT 2 1000` | `2` (레플리카 2개가 받았다고 확인) |

#### 비동기 복제: 가장 중요한 성질

Redis 복제는 기본이 **비동기**(asynchronous, 마스터가 레플리카 반영을 기다리지 않고 바로 응답)예요. 마스터는 클라이언트에 OK를 먼저 돌려주고, 레플리카는 받은 양을 1초에 한 번쯤 따로 알려요.

그래서 이런 일이 생겨요.

1. 클라이언트가 마스터에 쓰고 OK를 받아요.
2. 그 쓰기가 레플리카로 가기 전에 마스터가 죽어요.
3. 레플리카가 새 마스터가 되면, 그 쓰기는 **처음부터 없던 일**이 돼요.

줄이는 도구는 두 가지예요. 둘 다 **보장이 아니라 확률·시간을 줄이는 장치**예요.

| 도구 | 하는 일 | 한계 |
|---|---|---|
| `WAIT 개수 타임아웃` | 방금 쓴 것을 레플리카 N개가 받았다고 확인할 때까지 기다려요 | Redis를 강한 일관성 시스템으로 바꾸지 않아요. 확인된 쓰기도 장애 조치 때 잃을 수 있어요(확률은 크게 줄어요). 응답이 느려져요 |
| `min-replicas-to-write N` + `min-replicas-max-lag M` | 지연 M초 이하 레플리카가 N개 이상일 때만 쓰기를 받고, 아니면 에러를 내요 | 잃는 창을 "몇 초"로 묶는 최선 노력이에요. 레플리카가 부족하면 쓰기 자체가 막혀요 |

#### 복제에서 알아 둘 것들

- **레플리카는 스스로 키를 만료시키지 않아요.** 마스터가 만료·퇴출할 때 `DEL`을 만들어 보내요. 다만 읽을 때 이미 만료 시간이 지난 키는 "없음"으로 답해요.
- **레플리카는 기본적으로 `maxmemory`를 무시해요.** 퇴출은 마스터가 하니까, 레플리카 메모리는 따로 지켜봐야 해요. → [만료와 퇴출](../expire-eviction/)
- **영속성 끈 마스터 + 자동 재시작은 위험해요.** 마스터가 빈 상태로 다시 살아나면 레플리카가 그걸 따라가서 **레플리카 데이터까지 지워져요.** 영속성을 켜거나 자동 재시작을 꺼요.
- 레플리카 아래에 레플리카를 다는 계단식 구성도 돼요.

이 페이지는 Redis 복제만 다뤄요. 일반 DB 복제(동기/비동기, 리더 선출 등)는 분산 섹션에서 따로 다룰 예정이에요.

### 2. Sentinel: 마스터가 죽으면 자동으로 바꿔 주기

복제만 쓰면 마스터가 죽었을 때 사람이 레플리카에 `REPLICAOF NO ONE`을 보내 직접 마스터로 올려야 해요. **Sentinel**(감시병)은 이 일을 자동으로 해 주는, 클러스터를 안 쓰는 Redis의 고가용성 장치예요.

Sentinel이 하는 일은 4가지예요.

| 기능 | 뜻 |
|---|---|
| 모니터링 | 마스터·레플리카가 살아 있는지 계속 확인 |
| 알림 | 문제가 생기면 관리자나 다른 프로그램에 알림 |
| 자동 장애 조치 | 레플리카 하나를 마스터로 올리고, 나머지 레플리카를 새 마스터에 다시 붙이고, 앱에 새 주소를 알림 |
| 설정 제공 | 클라이언트가 "지금 마스터 어디야?"라고 물으면 주소를 알려 줌 |

클라이언트는 `SENTINEL GET-MASTER-ADDR-BY-NAME 이름`으로 마스터 주소를 받아요. 장애 조치 뒤에는 승격된 레플리카 주소가 나와요. Sentinel 기본 포트는 26379예요.

#### 장애 조치 순서

1. Sentinel들이 마스터와 레플리카에 주기적으로 PING을 보내요.
2. Sentinel 하나가 `down-after-milliseconds` 동안 응답을 못 받으면 **SDOWN**(주관적 다운, "내가 보기엔 죽었음")이에요.
3. **quorum**(정족수) 수만큼의 Sentinel이 동의하면 **ODOWN**(객관적 다운, "여럿이 보기에 죽었음")이에요.
4. Sentinel **과반수**의 투표로 장애 조치를 맡을 리더를 뽑아요.
5. 리더가 승격할 레플리카를 골라 마스터로 올려요.
6. 나머지 레플리카를 새 마스터에 붙이고, 옛 마스터는 돌아오면 레플리카가 돼요.
7. 클라이언트는 Sentinel에 다시 물어 새 마스터로 접속해요.

승격할 레플리카는 이 순서로 골라요. 마스터와 끊긴 지 너무 오래된 레플리카는 빼요 → `replica-priority`가 낮은 것 → **복제 오프셋이 큰 것**(데이터를 더 많이 받은 것) → run ID가 사전순으로 작은 것. priority가 0이면 절대 승격되지 않아요.

#### 심화: quorum과 과반수는 달라요

면접에 자주 나오는 함정이에요.

- **quorum**은 "마스터가 죽었다"고 **판단**하는 데만 쓰여요.
- 실제 **장애 조치 실행**은 전체 Sentinel의 **과반수**가 리더 선출에 참여해야 시작돼요.
- 예: Sentinel 5개, quorum 2 → 2개가 동의하면 죽었다고 판단해요. 하지만 장애 조치는 3개 이상과 연락이 돼야 해요.

그래서 Sentinel은 **최소 3개, 서로 다른 장비**에 둬요. 2개면 한 장비가 죽었을 때 남은 1개로는 과반수(2)가 안 돼서 장애 조치를 못 해요. 네트워크가 갈라졌을 때 소수 쪽 Sentinel도 장애 조치를 하지 않아요.

#### Sentinel이 막지 못하는 쓰기 유실

**네트워크 분할**(network partition, 네트워크가 끊겨 서버들이 두 무리로 갈라지는 것) 상황을 생각해 봐요.

1. 옛 마스터와 일부 클라이언트가 한쪽에, Sentinel 과반과 레플리카가 다른 쪽에 갇혀요.
2. 과반 쪽은 레플리카를 새 마스터로 올려요.
3. 그동안 옛 마스터 쪽 클라이언트는 옛 마스터에 계속 써요.
4. 분할이 풀리면 옛 마스터는 레플리카로 강등되고, 그사이 받은 쓰기는 **영구히 사라져요.**

공식 문서는 `min-replicas-to-write 1`, `min-replicas-max-lag 10` 같은 설정으로 이 창을 줄이라고 권해요. 레플리카와 끊긴 옛 마스터가 일정 시간 뒤 쓰기를 거부하게 되거든요.

### 3. Cluster: 데이터를 여러 마스터에 나눠 담기

Sentinel 구성에서도 쓰기를 받는 마스터는 하나예요. 레플리카를 늘려도 **읽기만** 나눠지고, 메모리와 쓰기 처리량은 마스터 한 대가 한계예요. **Cluster**는 데이터를 여러 마스터에 **자동 샤딩**(sharding, 데이터를 나눠 여러 서버에 담기)해서 이 한계를 넘어요. 일부 노드가 죽어도 계속 돌아가요.

#### 해시 슬롯

키 공간은 **16384개 해시 슬롯**(hash slot, 키가 배정되는 번호 칸)으로 나뉘어요. 키의 슬롯은 이렇게 정해져요.

```text
HASH_SLOT = CRC16(key) mod 16384
```

**CRC16**은 문자열을 16비트 숫자로 바꾸는 계산이에요. 각 마스터가 슬롯 구간을 나눠 맡아요(예: A는 0~5460, B는 5461~10922, C는 10923~16383).

실험(클러스터 모드 단일 노드, `CLUSTER KEYSLOT`)에서 나온 슬롯이에요.

| 키 | 슬롯 |
|---|---|
| `user:1` | 10778 |
| `user:2` | 6777 |
| `user:1:cart` | 6211 |
| `{user:1}:cart` | 10778 |
| `{user:1}:orders` | 10778 |
| `{}x` / `{}y` | 10595 / 14658 |

`user:1`과 `user:1:cart`는 이름이 비슷해도 슬롯이 완전히 달라요. 해시 결과는 이름의 앞부분이 같다고 비슷해지지 않아요.

<Aside type="caution" title="왜 하필 16384개?">
공식 명세에 있는 사실은 "CRC16 결과 16비트 중 14비트만 쓴다(2^14 = 16384)"까지예요. "노드끼리 주고받는 하트비트 메시지에 슬롯 비트맵을 싣는데, 16384개면 2KB, 65536개면 8KB라서 작게 잡았다"는 설명은 Redis 제작자가 GitHub 이슈에 남긴 답으로 알려진 **일반 지식**이에요. 면접에서는 "공식 문서 근거는 아니지만 이렇게 알려져 있다"고 구분해 말하는 게 안전해요.
</Aside>

공식 튜토리얼은 Redis Cluster가 **일관된 해싱**(consistent hashing, 노드를 원 위에 배치해 키를 나누는 방식)을 쓰지 않는다고 분명히 말해요. 고정된 16384개 슬롯을 노드에 나눠 주고, 노드를 추가·제거하면 슬롯 일부만 옮겨요. 이걸 **리샤딩**이라 하고, 서비스 중에도 할 수 있어요.

#### 해시 태그와 멀티키 제약

`MSET`, `MGET`, `SUNION`, 트랜잭션, Lua 스크립트처럼 **키 여러 개를 한 번에 다루는 명령**은 그 키들이 **모두 같은 슬롯**일 때만 돼요. 다르면 이 에러가 나요.

```text
> MSET user:1 a user:2 b
(error) CROSSSLOT Keys in request don't hash to the same slot
```

실험에서도 그대로 나왔어요. 이걸 해결하는 게 **해시 태그**(hash tag)예요.

- 키에 `{`가 있고, 그 뒤 첫 `}`까지 사이에 한 글자 이상 있으면 **그 안쪽만** 해시해요.
- `{user:1}:cart`와 `{user:1}:orders`는 둘 다 `user:1`만 해시해서 같은 슬롯(10778)이에요.
- `{}x`처럼 중괄호 안이 비어 있으면 키 전체를 해시해요. 그래서 `{}x`와 `{}y`는 슬롯이 달라요.

대가도 있어요. 같은 태그를 너무 많은 키에 붙이면 그 키들이 **한 슬롯, 한 노드**에 몰려요. 그러면 그 노드만 메모리와 트래픽이 터지는 **핫 슬롯**이 생겨요(이건 일반 지식이고, 공식 문서는 태그 규칙만 설명해요).

이 밖의 제약도 있어요.

- Cluster는 **DB 0만** 써요. `SELECT 1`이 안 돼요.
- 리샤딩 중에는 멀티키 명령이 잠깐 `-TRYAGAIN`으로 거부될 수 있어요. 단일 키 명령은 항상 돼요.
- 그래서 단일 Redis에서 잘 돌던 `KEYS`·멀티키 Lua 스크립트가 클러스터로 바꾸면 깨지기 쉬워요.

#### 심화: 클라이언트는 어느 노드로 보낼까: MOVED와 ASK

Cluster에는 요청을 대신 나눠 주는 **프록시**(중간 전달 서버)가 없어요. 클라이언트가 슬롯→노드 지도를 들고 있다가 직접 찾아가요. 지도가 틀리면 노드가 리다이렉트로 알려 줘요(공식 명세 기준).

| 응답 | 언제 | 클라이언트가 할 일 |
|---|---|---|
| `-MOVED 3999 노드주소` | 그 슬롯을 **원래** 다른 노드가 맡고 있을 때 (영구 이동) | 그 노드로 다시 보내고 **지도를 갱신**해요 |
| `-ASK 3999 노드주소` | 그 슬롯을 다른 노드로 **옮기는 중**일 때 (일회성) | 그 요청 하나만 `ASKING`을 먼저 보내고 대상 노드로 보내요. **지도는 갱신하지 않아요** |

슬롯 이전이 끝나면 그다음부터는 MOVED가 와요. 이렇게 지도를 캐시하고 리다이렉트를 따라가는 클라이언트를 **스마트 클라이언트**라고 불러요.

#### 구성과 장애 조치

- 최소 **마스터 3개**가 있어야 정상 클러스터이고, 운영 권장은 **6노드(마스터 3 + 레플리카 3)**예요. `redis-cli --cluster create ... --cluster-replicas 1`로 만들어요.
- 노드끼리는 데이터 포트 + 10000(예: 16379)인 **클러스터 버스** 포트로 서로 상태를 주고받아요(**gossip**, 소문 퍼뜨리듯 서로 상태를 전하는 방식). 두 포트 모두 열어야 해요. NAT 환경은 지원하지 않고, Docker는 host 네트워크 모드가 필요해요.
- 노드가 `NODE_TIMEOUT` 넘게 응답이 없으면 **PFAIL**(의심), 마스터 과반수가 그렇게 보고하면 **FAIL**이에요.
- FAIL된 마스터의 레플리카가 선거를 열고 **마스터 과반수의 표**를 받으면 승격돼요. 이때 새 `configEpoch`(설정 버전 번호, 높은 쪽이 이김)를 받아요.
- 마스터와 그 레플리카가 **같이** 죽으면 그 슬롯을 맡을 노드가 없어요. 기본값 `cluster-require-full-coverage yes`면 클러스터 전체가 쓰기를 멈춰요. 마스터 과반이 죽는 큰 장애에서도 멈춰요.
- 레플리카에서 읽으려면 그 연결에 `READONLY` 명령을 보내야 해요. 기본으로는 레플리카도 MOVED로 마스터에 보내요.

Cluster도 **강한 일관성을 보장하지 않아요.** 비동기 복제라 마스터가 OK를 보낸 뒤 레플리카에 전하기 전에 죽으면 잃어요. 네트워크 분할 때 소수 쪽에 남은 마스터에 쓴 내용도 잃을 수 있어요. 다만 소수 쪽 마스터는 `NODE_TIMEOUT`이 지나면 쓰기를 거부해서, 잃는 시간에 상한이 있어요.

### 4. 세 구성 한눈에 비교

| 구분 | 복제만 | Sentinel | Cluster |
|---|---|---|---|
| 목적 | 사본, 읽기 분산 | 복제 + 자동 장애 조치 | 샤딩(메모리·쓰기 확장) + 장애 조치 |
| 쓰기 받는 노드 | 마스터 1개 | 마스터 1개 | 마스터 여러 개(슬롯 나눠 맡음) |
| 데이터 분산 | 없음(전부 복사) | 없음(전부 복사) | 16384 슬롯으로 나눔 |
| 장애 조치 | 사람이 `REPLICAOF NO ONE` | Sentinel 과반수 투표로 자동 | 마스터 과반수 투표로 자동 |
| 마스터 찾는 법 | 주소 고정 | Sentinel에 물어봄 | 슬롯 지도 + MOVED/ASK |
| 멀티키 명령 | 제약 없음 | 제약 없음 | 같은 슬롯만(해시 태그) |
| DB 번호 | 0~15 | 0~15 | 0만 |
| 최소 구성 | 마스터 1 + 레플리카 1 | Sentinel 3 + 마스터 1 + 레플리카 1 이상 | 마스터 3 (권장 6노드) |
| 쓰기 유실 | 가능(비동기) | 가능(비동기, 분할) | 가능(비동기, 분할) |

**셋 다 비동기 복제라, 클라이언트가 OK를 받은 쓰기도 장애 때 잃을 수 있어요.** `WAIT`와 `min-replicas-*`는 그 가능성을 줄일 뿐 없애지 못해요. 잃으면 안 되는 원본 데이터(돈, 주문)는 트랜잭션을 지원하는 DB에 두고, Redis는 캐시나 보조 저장소로 쓰는 게 기본이에요. → [캐시 패턴](../cache-patterns/)

## 면접 질문

<details>
<summary>Q. Redis 복제는 동기인가요, 비동기인가요? 데이터가 유실될 수 있나요?</summary>

**답변(30초)** 기본은 비동기라서 유실될 수 있어요. 마스터는 레플리카가 받았는지 기다리지 않고 클라이언트에 OK를 먼저 줘요. 그래서 OK를 준 직후, 레플리카에 전하기 전에 마스터가 죽고 레플리카가 승격되면 그 쓰기는 사라져요. `WAIT`로 레플리카 확인을 기다리거나 `min-replicas-to-write`로 레플리카가 부족할 때 쓰기를 막아 창을 줄일 수 있지만, 공식 문서도 이게 강한 일관성 보장은 아니라고 해요.

**꼬리질문**
- Q. WAIT 2를 받았으면 안전한가요? → 확률은 크게 줄지만 장애 조치 때 확인된 쓰기도 잃을 수 있어요. 대신 응답 지연이 늘어요.
- Q. 그럼 돈 같은 데이터는요? → 원본은 트랜잭션 DB에 두고 Redis는 캐시로 써요.
</details>

<details>
<summary>Q. Sentinel과 Cluster는 어떻게 다르고, 언제 무엇을 쓰나요?</summary>

**답변(30초)** Sentinel은 마스터 하나 + 레플리카 구성에 자동 장애 조치를 붙인 거고, 데이터를 나누지 않아요. Cluster는 키를 16384개 슬롯으로 나눠 여러 마스터에 분산하고, 장애 조치도 스스로 해요. 데이터가 한 대 메모리에 들어가고 쓰기도 한 대로 충분하면 Sentinel이 단순해서 좋아요. 메모리나 쓰기 처리량이 한 대를 넘으면 Cluster로 가는데, 멀티키 명령이 같은 슬롯에서만 되고 DB 0만 쓰는 제약을 감수해야 해요.

**꼬리질문**
- Q. 레플리카를 늘리면 쓰기도 늘어나지 않나요? → 아니에요. 쓰기는 여전히 마스터 한 대가 받아요. 쓰기 확장은 샤딩, 즉 Cluster가 필요해요.
</details>

<details>
<summary>Q. Redis Cluster는 키를 어떻게 분산하나요? 왜 16384개인가요?</summary>

**답변(30초)** 키에 CRC16을 계산하고 16384로 나눈 나머지가 슬롯 번호예요. 각 마스터가 슬롯 구간을 나눠 맡고, 노드를 늘리면 슬롯 일부만 옮겨요. 일관된 해싱이 아니라 고정 슬롯 방식이에요. 16384는 CRC16 결과 중 14비트만 쓰는 값이고, 노드끼리 주고받는 메시지의 슬롯 비트맵을 2KB로 작게 유지하려고 이 크기를 골랐다고 알려져 있어요. 다만 그 이유는 공식 문서가 아니라 제작자가 남긴 답변이에요.

**꼬리질문**
- Q. 여러 키를 한 번에 다루려면요? → 해시 태그로 `{}` 안의 같은 값만 해시하게 해서 같은 슬롯에 모아요.
</details>

<details>
<summary>Q. 클러스터에서 마스터가 죽으면 어떻게 되나요? 마스터와 레플리카가 같이 죽으면요?</summary>

**답변(30초)** 노드들이 클러스터 버스로 서로 상태를 확인하다가, `NODE_TIMEOUT` 동안 응답이 없으면 의심(PFAIL)하고 마스터 과반수가 동의하면 FAIL로 확정해요. 그러면 그 마스터의 레플리카가 마스터 과반수 표를 받아 승격되고 슬롯을 이어받아요. 마스터와 레플리카가 같이 죽으면 그 슬롯을 맡을 노드가 없어서, 기본 설정에선 클러스터 전체가 쓰기를 멈춰요.

**꼬리질문**
- Q. 쓰기 유실은 없나요? → 있어요. 비동기 복제라 마스터가 OK를 준 뒤 레플리카에 전하기 전에 죽으면 그 쓰기는 사라져요. `WAIT`로 줄일 수 있지만 강한 일관성은 아니에요.
</details>

<details>
<summary>Q. Sentinel의 장애 조치 과정과, quorum과 과반수의 차이를 설명해 주세요.</summary>

**답변(30초)** Sentinel 하나가 정해진 시간 동안 마스터 응답을 못 받으면 SDOWN, quorum만큼 동의하면 ODOWN이 돼요. 그다음 전체 Sentinel 과반수의 투표로 리더를 뽑고, 리더가 오프셋이 큰 레플리카를 골라 마스터로 올려요. 즉 quorum은 "죽었다"는 판단에만 쓰이고, 실제 실행은 과반수가 있어야 해요. 그래서 Sentinel은 최소 3개를 서로 다른 장비에 둬요.

**꼬리질문**
- Q. Sentinel 2개면 안 되나요? → 한 장비가 죽으면 남은 1개로는 과반수(2)가 안 돼 장애 조치를 못 해요.
- Q. 앱은 새 마스터를 어떻게 알아요? → Sentinel에 `SENTINEL GET-MASTER-ADDR-BY-NAME`으로 물어요. 그래서 마스터 주소를 하드코딩하지 않고 Sentinel 지원 클라이언트를 써요.
</details>

<details>
<summary>Q. 전체 재동기화와 부분 재동기화는 어떻게 다르고, 언제 전체 재동기화가 일어나나요?</summary>

**답변(30초)** 부분 재동기화는 끊긴 동안 놓친 쓰기만 받는 것이고, 전체 재동기화는 마스터가 스냅숏을 새로 떠서 데이터 전체를 다시 보내는 거예요. 레플리카가 `PSYNC`로 복제 ID와 오프셋을 보내면, 마스터는 그 지점이 백로그에 남아 있을 때만 부분 재동기화를 해요. 처음 붙을 때, 백로그(기본 1MB)에서 이미 밀려났을 때, 복제 ID가 다를 때 전체 재동기화가 일어나요.

**꼬리질문**
- Q. 재접속할 때마다 전체 동기화가 일어나면요? → 끊긴 동안 쓰기량이 백로그보다 커서 그래요. `repl-backlog-size`를 늘려요. 전체 동기화는 마스터에 fork와 네트워크 부하를 줘요.
- Q. 장애 조치 후에도 부분 재동기화가 되나요? → 4.0부터 승격된 레플리카가 옛 복제 ID를 두 번째 ID로 기억해서, 다른 레플리카가 전체 동기화 없이 붙을 수 있어요.
</details>

<details>
<summary>Q. MOVED와 ASK 리다이렉트는 어떻게 다른가요?</summary>

**답변(30초)** 둘 다 "이 슬롯은 다른 노드로 가세요"라는 응답이에요. MOVED는 슬롯 주인이 정말 다른 노드라는 영구 안내라서, 클라이언트는 다시 보내고 슬롯 지도를 갱신해요. ASK는 슬롯을 옮기는 도중의 일회성 안내라서, 그 요청 하나만 `ASKING`을 붙여 새 노드로 보내고 지도는 그대로 둬요. 이전이 끝나면 MOVED가 와요.

**꼬리질문**
- Q. 왜 ASK 때는 지도를 안 바꿔요? → 이전 중이라 슬롯의 키 일부는 아직 원래 노드에 있어요. 지도를 바꾸면 남은 키 요청이 엉뚱한 곳으로 가요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제가 끝나면 사용자 포인트 차감 기록을 Redis(Sentinel 구성)에 쓰고 OK를 받습니다. 어느 날 마스터 장애로 Sentinel이 장애 조치를 했는데, 장애 직전 몇 초간의 차감 기록이 새 마스터에 없었습니다. 팀에서 "WAIT를 붙이면 해결되지 않냐"는 의견이 나왔습니다.</summary>

**상황 파악**
OK를 받았는데 장애 조치 뒤 사라졌다면, 그 쓰기가 **레플리카에 전해지기 전에** 마스터가 죽었을 가능성이 커요. Redis 복제는 기본이 비동기라 마스터가 레플리카를 기다리지 않고 OK를 줘요. 사라진 구간이 장애 직전 몇 초에 몰려 있다는 점도 이 설명과 맞아요. 돈과 관련된 데이터라 "얼마나 줄이냐"보다 "잃어도 되는 구조냐"가 핵심이에요.

**원인 후보**
1. 비동기 복제: 마스터가 OK를 준 뒤 레플리카 전파 전에 죽고, 그 레플리카가 승격됐어요.
2. 네트워크 분할: 옛 마스터가 Sentinel 과반과 끊긴 채 쓰기를 계속 받다가, 복구 때 레플리카로 강등되며 그 쓰기를 버렸어요.
3. 승격된 레플리카가 원래 많이 뒤처져 있었어요(오프셋이 작은 레플리카만 살아 있던 경우).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 쓰기 뒤 `WAIT 1 타임아웃`으로 레플리카 확인 | 코드 수정이 작고 유실 확률이 크게 줄어요 | 요청마다 지연이 늘어요. 공식 문서상 확인된 쓰기도 장애 조치 때 잃을 수 있어요. 타임아웃이 나면 앱이 어떻게 할지 정해야 해요 |
| B. `min-replicas-to-write 1`, `min-replicas-max-lag 10` | 레플리카와 끊긴 마스터가 쓰기를 거부해서, 분할 때 잃는 창이 몇 초로 줄어요 | 레플리카가 부족하면 쓰기가 에러 나서 가용성이 떨어져요. 여전히 보장은 아니에요 |
| C. 포인트 원본은 트랜잭션 DB에 쓰고, Redis는 캐시로만 | 커밋된 기록은 DB가 지켜요. Redis가 날아가도 DB에서 다시 채우면 돼요 | DB 쓰기가 늘어 느려지고, 캐시와 DB 사이 일관성을 따로 관리해야 해요 |

**내가 고를 방법**
C를 고를래요. 질문의 답은 "WAIT로 줄일 수는 있지만 해결은 아니다"예요. WAIT와 min-replicas는 유실 창을 좁힐 뿐 Redis를 강한 일관성 저장소로 만들지 못해요. 돈은 한 건도 잃으면 안 되니까 원본은 DB 트랜잭션에 두고, Redis는 빠른 조회용 캐시로 써요. Redis를 계속 쓰는 나머지 데이터에는 B를 켜서 분할 때의 유실 창을 줄여요. 사라진 구간은 DB나 결제 로그와 대조해 복구해요.

**채점 포인트**: 비동기 복제가 원인, OK ≠ 레플리카 반영, WAIT는 보장 아님(확인된 쓰기도 유실 가능) + 지연 증가, min-replicas-to-write/max-lag와 가용성 감소, 네트워크 분할 시 옛 마스터 쓰기 유실, 돈 원본은 트랜잭션 DB, 유실 구간 복구 방법.
</details>

<details>
<summary>상황: 읽기 부하를 줄이려고 조회를 Redis 레플리카로 돌렸습니다. 그 뒤 "프로필을 수정하고 저장했는데 화면에 예전 값이 보인다"는 문의가 가끔 들어옵니다. 새로고침하면 바뀐 값이 보입니다.</summary>

**상황 파악**
쓰기는 마스터로, 바로 뒤의 읽기는 레플리카로 갔을 가능성이 커요. 복제가 비동기라 레플리카는 마스터보다 조금 늦어요. "가끔", "새로고침하면 정상"이라는 증상이 짧은 **복제 지연**(replication lag)과 딱 맞아요. 사용자가 자기가 쓴 값을 바로 보는 **read-your-writes**(자기 쓰기 읽기) 일관성이 깨진 거예요. 실험에서도 레플리카 연결 직후 마스터에 쓴 값이 1초 뒤 레플리카에선 빈 값이었다가 몇 초 뒤에야 보였어요.

**원인 후보**
1. 평소의 짧은 비동기 복제 지연이에요.
2. 레플리카가 전체 재동기화 중이라 옛 데이터로 응답하고 있어요(`replica-serve-stale-data` 설정에 따라).
3. 레플리카 쪽 부하나 네트워크 문제로 지연이 커졌어요. `INFO replication`의 `master_link_status`와 오프셋 차이로 확인해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 쓰고 바로 읽는 경로(내 프로필 조회 등)만 마스터에서 읽기 | 그 경로는 항상 최신 값이에요. 나머지 읽기는 계속 레플리카로 분산돼요 | 경로를 나누는 코드가 필요하고, 마스터 읽기 부하가 조금 늘어요 |
| B. 쓴 직후 몇 초 동안 그 사용자의 읽기를 마스터로 고정 | 화면이 여러 개여도 일관되게 최신 값을 봐요 | 사용자별 "최근에 썼음" 상태를 들고 있어야 해서 구현이 복잡해요. 지연이 그 몇 초보다 길면 또 보여요 |
| C. 쓰기 뒤 `WAIT`로 레플리카 반영 확인 후 응답 | 레플리카에서 읽어도 대부분 최신이에요 | 모든 쓰기가 느려지고, 레플리카가 여러 대면 확인 안 된 레플리카로 읽기가 갈 수 있어요 |

**내가 고를 방법**
A를 고를래요. 문제는 "자기가 방금 쓴 값" 화면에서만 생기니까, 그 경로만 마스터로 보내면 효과가 크고 구현이 단순해요. 다른 사람 프로필이나 목록처럼 몇 초 늦어도 되는 읽기는 레플리카에 그대로 둬서 분산 효과를 지켜요. 그리고 레플리카 지연(오프셋 차이)을 모니터링해서, 평소보다 크게 벌어지면 알림이 오게 해요.

**채점 포인트**: 비동기 복제로 인한 복제 지연, read-your-writes, 쓰기는 마스터/읽기는 레플리카 분리의 대가, 전체 재동기화 중 옛 데이터 응답, `INFO replication`·오프셋으로 확인, 경로별 라우팅과 WAIT의 비용, 지연 모니터링.
</details>

<details>
<summary>상황: 메모리 한계로 단일 Redis를 Redis Cluster로 옮겼습니다. 그 뒤 장바구니 화면에서 `MGET cart:123 coupon:123 point:123`을 부르는 코드가 `CROSSSLOT Keys in request don't hash to the same slot` 에러를 냅니다.</summary>

**상황 파악**
Cluster에서는 여러 키를 한 번에 다루는 명령이 **모든 키가 같은 슬롯**일 때만 돼요. 세 키는 이름이 달라서 CRC16 결과가 다르고, 서로 다른 슬롯(아마 다른 노드)에 흩어져 있어요. 단일 Redis에서는 문제없던 코드가 클러스터 전환으로 깨진 전형적인 경우예요. 같은 이유로 `MSET`, 트랜잭션, 멀티키 Lua 스크립트, `KEYS`도 함께 점검해야 해요.

**원인 후보**
1. 키 이름에 해시 태그가 없어 같은 사용자 데이터가 여러 슬롯으로 흩어졌어요.
2. 클러스터를 지원하는 클라이언트를 쓰지 않아서 멀티키 명령을 노드별로 나눠 주지 못해요.
3. (참고) 리샤딩 중이라면 같은 슬롯 키여도 `TRYAGAIN`이 잠깐 날 수 있지만, 이번 에러는 CROSSSLOT이라 키 설계 문제예요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 해시 태그로 키 이름 변경: `{user:123}:cart`, `{user:123}:coupon`, `{user:123}:point` | 한 사용자 데이터가 같은 슬롯에 모여 `MGET`, 트랜잭션, Lua가 그대로 돼요 | 키 이름을 바꾸는 데이터 이관이 필요해요. 태그 단위를 크게 잡으면(예: 모든 키에 같은 태그) 한 노드에 몰리는 핫 슬롯이 생겨요 |
| B. `MGET`을 단일 키 `GET` 여러 개로 나누고 파이프라이닝 | 키 이름을 안 바꿔도 되고, 데이터가 고르게 퍼진 상태를 유지해요 | 여러 노드에 요청이 가서 왕복이 늘어요. 여러 키를 원자적으로 바꾸는 트랜잭션·Lua는 이 방법으로 못 풀어요 |
| C. 클러스터 지원 클라이언트가 슬롯별로 쪼개서 보내게 하기 | 앱 코드 변경이 적어요 | 결국 노드별 여러 요청이라 원자성은 없어요. 클라이언트 라이브러리 동작에 의존해요 |

**내가 고를 방법**
A를 고를래요. 장바구니·쿠폰·포인트는 같은 사용자 단위로 함께 읽고, 결제 때 함께 바꿀 일도 많아서 같은 슬롯에 있어야 원자적 처리가 가능해요. 태그는 **사용자 ID처럼 값이 아주 많은 단위**로 잡아요. 그래야 수많은 사용자가 16384개 슬롯에 고르게 퍼져 핫 슬롯이 안 생겨요. 함께 원자적으로 다룰 필요가 없는 조회는 B로 나눠 둬요. 전환 전에 `CLUSTER KEYSLOT`으로 새 키들이 같은 슬롯인지 확인해요.

**채점 포인트**: 멀티키 명령은 같은 슬롯만, CRC16 mod 16384, 해시 태그 규칙(`{}` 안만 해시, 빈 태그는 전체 해시), 태그 단위와 핫 슬롯 트레이드오프, 트랜잭션·Lua도 같은 제약, 키 이관 비용, 대안(단일 키 분할 + 파이프라이닝)과 원자성 상실, `CLUSTER KEYSLOT`으로 검증.
</details>

## 필기 포인트

- Redis 기본 복제 = **비동기**. `WAIT`·`min-replicas-to-write`도 **보장 아님**(유실 창 축소).
- 레플리카 기본 **읽기 전용**(2.6+). 쓰면 `READONLY` 에러.
- 부분 재동기화 조건: 같은 복제 ID + 백로그에 그 오프셋이 남아 있음. 백로그 기본 1MB.
- Sentinel: **quorum = 장애 판단**, **과반수 = 장애 조치 실행**. 최소 3개, 서로 다른 장비. 기본 포트 26379.
- 승격 레플리카 선택: priority 낮은 순 → 오프셋 큰 순 → run ID 작은 순. priority 0은 승격 안 됨.
- Cluster: **16384 슬롯**, `CRC16(key) mod 16384`, 일관된 해싱 아님. DB 0만. 최소 마스터 3, 권장 6노드.
- 클러스터 버스 포트 = 데이터 포트 + 10000.
- **MOVED**(영구, 지도 갱신) vs **ASK**(이전 중 일회성, `ASKING`, 지도 그대로).
- 해시 태그: 첫 `{`와 그 뒤 첫 `}` 사이가 비어 있지 않으면 그 안쪽만 해시.
