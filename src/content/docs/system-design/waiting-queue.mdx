:::tip[한 줄 요약]
대기열은 몰려든 사용자를 **번호표로 줄 세우고, 뒷단이 버틸 만큼만 들여보내는** 장치예요. 대기열은 들어오는 속도만 줄여 줄 뿐이라, 입장한 사람끼리 마지막 재고를 다투는 문제는 **재고 차감을 원자적으로** 만들어 따로 풀어야 해요.
:::

:::note[처음이라면 여기까지]
① 티켓 오픈처럼 한순간에 사람이 몰리면 서버를 늘리는 것만으로는 못 버텨요. 그래서 줄을 세우고 조금씩 들여보내요.

② 줄은 Redis의 Sorted Set(점수 순으로 자동 정렬되는 목록)으로 만들어요. 새로고침해도 번호가 안 바뀌게 `ZADD NX`를 써요.

③ 줄을 통과했다고 끝이 아니에요. 안에서 "재고 확인 → 차감"을 한 번에 처리하지 않으면 100장짜리 쿠폰이 103장 나가요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

유명 맛집 앞을 떠올려 보세요. 문 열자마자 수백 명이 몰려들면 가게는 다 받을 수 없어요. 그래서 입구에서 **번호표**를 나눠 줘요. 번호표를 뽑은 사람은 밖에서 기다리고, 자리가 나는 만큼 "37번부터 42번까지 들어오세요" 하고 부르죠.

가게 안에는 테이블 수만큼만 사람이 있어요. 주방이 감당할 수 있는 속도로만 손님을 들이니 음식이 밀리지 않아요. 잠깐 화장실에 다녀왔다고 번호표를 다시 뽑게 하지도 않아요. 받은 번호는 그대로예요.

그런데 가게 안에도 문제가 남아요. "오늘 한정 메뉴 10그릇"이 있는데 안에 있는 손님 30명이 동시에 주문하면, 주방이 잘 세지 않으면 12그릇을 팔겠다고 해 버려요. **줄 세우기**와 **한정 수량 세기**는 서로 다른 문제예요.

온라인 티켓팅도 같아요. 번호표는 대기열 서버가, 테이블 수는 "동시에 안에 있을 수 있는 인원"이, 한정 메뉴는 좌석·쿠폰 재고예요.

단, 실제로는 번호표 종이 대신 **서명된 입장 토큰**(위조할 수 없는 디지털 입장권)을 줘요. 종이는 베낄 수 있지만 서명은 서버의 비밀키 없이는 못 만들어요.

## 제대로 알기

### 왜 대기열이 필요한가

"서버를 늘리면 되지 않나요?"가 첫 질문이에요. 세 가지 이유로 부족해요.

- **늘리는 데 시간이 걸려요.** 자동으로 서버를 늘리는 **오토스케일링**(부하를 보고 서버 대수를 자동 조절하는 기능)은 새 서버가 뜨기까지 수 분이 걸려요. 티켓 오픈은 몇 초 만에 몰려요.
- **DB는 쉽게 못 늘려요.** 앱 서버는 무상태라 복사하면 되지만, 재고를 들고 있는 DB는 한 행(좌석 하나)을 여러 대로 나눌 수 없어요.
- **이 몰림은 정상 사용자예요.** 공격이 아니라서 사용자별 처리율 제한으로 막을 대상도 아니에요.

그래서 **가상 대기실**(virtual waiting room)을 둬요. 평소에는 그냥 통과시키고, 트래픽이 서비스가 감당할 한계에 가까워질 때만 줄을 세워 원래 서버(origin)를 보호해요.

### 공통 뼈대로 설계해 보기: "콘서트 티켓 오픈, 1분에 50만 명"

[시스템 설계 면접 푸는 법](../design-approach/)의 순서대로 풀어요.

**1. 요구사항**

| 구분 | 내용 |
|---|---|
| 기능 | 대기 순번 발급, "내 앞에 몇 명" 표시, 차례가 되면 입장, 좌석 선택·결제 |
| 비기능 | 먼저 온 사람이 먼저 들어감(공정성), 새로고침해도 순번 유지, 뒷단(예매·결제·DB) 보호, 초과 판매 0 |
| 범위 밖(가정) | 결제 자체의 정합성은 [결제 시스템 설계](../payment-system/)로 넘겨요 |

**2. 규모 추정** (모두 가정값이에요)

- 대기열 진입: 50만 명 ÷ 60초 ≈ 초당 8,300명. 실제로는 정각 몇 초에 대부분 몰려서 순간 값은 훨씬 커요.
- 뒷단 처리량: 예매 서버가 **초당 2,000명**의 신규 입장까지 버틴다고 가정해요.
- 대기 시간: 50만 ÷ 2,000 = 250초, 맨 뒤 사람은 약 4분 기다려요.
- 순번 조회: 50만 명이 20초마다 한 번씩 물으면 초당 25,000건, 5초마다면 초당 10만 건이에요. 조회 간격이 곧 대기열 서버 부하예요.

**3. API**

| API | 하는 일 |
|---|---|
| `POST /queue/{eventId}/join` | 번호표 발급(이미 있으면 기존 번호 유지) |
| `GET /queue/{eventId}/status` | 내 순번, 예상 대기 시간. 입장 차례면 입장 토큰을 함께 돌려줌 |
| `POST /events/{eventId}/reserve` | 좌석 예매. 입장 토큰이 없거나 위조면 대기열로 돌려보냄 |

**4. 데이터 모델**

- 대기열: Redis Sorted Set `queue:{eventId}`, 멤버 = 사용자 ID, 점수(score) = 도착 시각(밀리초).
- 재고: Redis 키 `stock:{eventId}` 또는 DB `product.stock` 컬럼.
- 최종 주문: DB에 기록해요(진실의 원천).

**5. 상위 설계**

```text
사용자 → CDN(정적 대기 페이지) → 대기열 서버 ─ Redis(Sorted Set)
                                     │
                       스케줄러: 1초마다 N명 꺼냄 → 입장 토큰 발급
                                     ↓
                 예매 서버(토큰 검증) → 재고 차감 → DB(주문)
```

**6. 심화**는 아래 소제목들, **7. 병목**은 "심화: Redis가 죽으면"과 서술형 연습에서 다뤄요.

### 번호표: Redis Sorted Set

**Sorted Set**은 멤버가 중복 없이 들어가고 **점수 오름차순으로 자동 정렬**되는 Redis 자료구조예요. 점수가 같으면 멤버 이름의 사전순으로 정렬돼요. 점수에 도착 시각을 넣으면 그대로 "먼저 온 순서"가 돼요. → [Redis 자료구조](../../redis/data-structures/)

| 명령 | 대기열에서 하는 일 | 주의 |
|---|---|---|
| `ZADD queue NX 점수 user:42` | 번호표 발급 | `NX`는 "없을 때만 추가". 이미 있으면 점수를 안 바꾸고 0을 돌려줘요 |
| `ZRANK queue user:42` | 내 순번 | **0부터** 시작해요. 화면엔 +1 해서 보여 줘요. 없으면 nil |
| `ZPOPMIN queue 100` | 앞에서 100명 꺼내 입장 | 꺼내면서 지워요. 남은 수보다 많이 달라고 해도 에러가 아니에요 |
| `ZCARD queue` | 전체 대기 인원 | |

```text
ZADD queue NX 1700000000000 user:42   # 처음 → 1(추가됨), 다시 → 0(순번 유지)
ZRANK queue user:42                   # 0부터 시작하는 순위
ZPOPMIN queue 100                     # 앞에서 100명 입장
```

`ZADD`와 `ZRANK`는 한 번에 O(log N)이라, 대기자가 수십만 명이어도 빨라요. O(log N)은 "사람이 100배 늘어도 걸리는 시간은 조금만 는다"는 뜻이에요.

**한 번 재 본 예시**를 보면 동작이 분명해요.

- 1만 명을 도착 순서대로 `ZADD NX`로 넣으니 에러 없이 대기 인원 10,000이 됐어요.
- 이미 있는 user:5000에게 점수 99999로 다시 `ZADD NX`를 보내니 0이 돌아왔고, 점수는 원래 5000 그대로였어요. **새로고침해도 뒤로 안 밀려요.**
- `ZRANK`: user:1은 0, user:5000은 4999, user:10000은 9999였어요.
- `ZPOPMIN queue 100` 후 user:1, user:2, … 순서로 100명이 나왔고, 대기 인원은 9,900, user:5000의 순위는 4999에서 4899로 앞당겨졌어요.

<Aside type="caution" title="NX를 빼면 새로고침할 때마다 맨 뒤로 가요">
`NX` 없이 `ZADD`를 하면 이미 있는 멤버의 점수를 새 도착 시각으로 덮어써요. 사용자가 F5를 누를 때마다 맨 뒤로 밀리는 거예요.
</Aside>

### 입장 속도는 뒷단 처리량에 맞춰요

대기열의 핵심 손잡이는 두 개예요. Cloudflare Waiting Room도 이 두 값으로 설정해요.

| 손잡이 | 뜻 | 정하는 기준 |
|---|---|---|
| 동시 활성 인원 | 한 번에 안에 있을 수 있는 최대 인원 | 예매·결제 서버와 DB가 동시에 감당할 수 있는 사용자 수 |
| 입장 속도 | 1분(또는 1초)에 새로 들여보내는 인원 | 뒷단이 새 사용자를 받아들이는 속도 |

스케줄러가 1초마다 `ZPOPMIN queue N`을 하는 게 곧 입장 속도예요. N은 **대기열 서버가 아니라 가장 약한 뒷단**(보통 DB나 결제)을 기준으로 정해요. 대기열 서버가 아무리 빨라도 들어간 사람이 DB를 쓰러뜨리면 소용없어요.

### 입장 토큰: 대기열을 통과했다는 증명

예매 서버는 "이 사람이 진짜 줄을 섰는지" 알아야 해요. 안 그러면 대기열을 건너뛰고 예매 API를 바로 부르면 그만이에요.

그래서 꺼낸 사용자에게 **서명된 입장 토큰**을 줘요. 서명은 서버만 아는 비밀키로 만든 도장이라, 내용을 한 글자라도 고치면 검증에서 걸려요. 흔히 **JWT**(JSON Web Token, 서명이 붙은 작은 JSON 문서)를 써요. → [쿠키·세션·JWT](../../web/cookie-session-jwt/)

토큰에는 이런 걸 넣어요.

- 사용자 ID: 남의 토큰을 가져다 쓰지 못하게 묶어요.
- 이벤트 ID: 다른 공연에 쓰지 못하게 해요.
- 만료 시각: 입장 후 일정 시간이 지나면 다시 줄 서게 해요.

예매 서버는 요청마다 서명과 만료를 검사하고, 없거나 위조면 대기열로 돌려보내요.

### 재고 차감은 따로 원자적으로

대기열은 **들어오는 속도만** 줄여요. 초당 2,000명을 들여보냈는데 남은 좌석이 1개라면, 그 2,000명이 동시에 마지막 좌석을 눌러요. 여기서 **"남았나 확인 → 하나 빼기"** 사이에 다른 요청이 끼어들면 초과 판매가 나요.

```text
요청 A: 재고 조회 → 1개 남음
요청 B: 재고 조회 → 1개 남음     ← A가 빼기 전에 끼어듦
요청 A: 차감 → 0
요청 B: 차감 → -1  (초과 판매)
```

Redis 명령 **하나**는 다른 명령과 섞이지 않고 한 번에 실행돼요(원자적). 하지만 `GET`으로 확인하고 `DECR`로 빼는 **두 명령** 사이에는 다른 클라이언트 명령이 끼어들 수 있어요. 해결책은 "확인과 차감을 한 덩어리로 만들기"예요.

#### 방법 비교

| 방법 | 어떻게 | 초과 판매 | 단점 |
|---|---|---|---|
| `GET` 후 `DECR` | 확인하고 빼기 | **생김** | 두 명령 사이에 끼어듦 |
| `DECR`만 | 빼고 나온 값이 0 이상이면 성공 | 막힘 | 실패한 요청도 깎아서 값이 계속 음수로 내려감 |
| `DECR` + `INCR` 되돌리기 | 결과가 음수면 다시 1 더함 | 막힘 | 되돌리기 전 잠깐 음수가 보임, 되돌리기 실패 시 재고가 틀어짐 |
| Lua 스크립트 | "0보다 크면 빼기"를 한 덩어리로 | 막힘 | 스크립트 실행 중엔 Redis 전체가 멈추니 짧게 |
| DB 조건부 `UPDATE` | `WHERE stock > 0` 조건으로 빼기 | 막힘 | 인기 상품 한 행에 요청이 몰리면 DB가 버거움 |
| 비관적 락 `SELECT ... FOR UPDATE` | 읽는 순간 행을 잠그고 트랜잭션 끝까지 유지 | 막힘 | 잠금 대기 줄이 길어져 커넥션이 고갈될 수 있음 → [DB 락](../../db/locks/) |
| 분산 락 | 락을 잡고 확인·차감 후 해제 | 막힘 | 차감 하나에 락 잡기·풀기 왕복이 더해져 느림 → [분산 락](../../redis/distributed-lock/) |

재고 100에 요청 1,000개를 동시에 보내 **한 번 재 본 예시**예요.

| 방식 | 성공 | 끝난 뒤 재고 값 |
|---|---|---|
| `DECR`만 | 정확히 100건 | **-900** |
| `DECR` + `INCR` 되돌리기 | 100건 | 0 |
| Lua | 100건 | 0 (음수 없음) |

`DECR`만 쓰면 판매 수는 맞지만, 재고 숫자를 화면에 보여 주거나 취소분을 되돌려 넣을 때 엉망이 돼요. -900에 1을 더해도 여전히 음수라 다음 사람이 못 사요.

Lua로 묶으면 이래요.

```lua
-- KEYS[1] = 재고 키. 확인과 차감이 한 덩어리로 실행돼요
local s = tonumber(redis.call('GET', KEYS[1]))
if s and s > 0 then
  return redis.call('DECR', KEYS[1])  -- 차감 후 남은 수
else
  return -1                            -- 매진
end
```

DB로 한다면 이렇게 써요.

```sql
UPDATE product SET stock = stock - 1
WHERE id = ? AND stock > 0;
-- 바뀐 행 수(affected rows)가 1이면 성공, 0이면 매진
```

MySQL InnoDB에서 기본 키로 한 행을 찾는 `UPDATE`는 그 행에만 쓰기 잠금을 걸어요. 동시에 온 요청은 줄 서서 하나씩 처리되고, 재고가 0이 되면 조건에 안 맞아 바뀐 행이 0개가 돼요. → [트랜잭션과 ACID](../../db/transaction-acid/)

### 심화: 순번 알림, 폴링 vs SSE

"내 앞에 N명"을 어떻게 화면에 갱신할까요?

| | 폴링 | SSE |
|---|---|---|
| 방식 | 브라우저가 몇 초마다 물어봄 | 서버가 연결을 열어 두고 바뀔 때 밀어 줌 |
| 장점 | 단순, 연결을 들고 있지 않음, 간격을 서버가 조절 가능 | 바로바로 갱신, 끊기면 브라우저가 자동 재연결 |
| 단점 | 간격만큼 늦게 보임, 요청 수가 많음 | 대기자 수십만 명 = 열린 연결 수십만 개 |

**SSE**(Server-Sent Events)는 서버 → 브라우저 **한 방향** 스트림이에요. `Content-Type: text/event-stream`으로 보내고, `retry:` 필드로 재연결 간격을 정해요. HTTP/1.1에서는 브라우저가 도메인당 6개까지만 연결을 열 수 있어 탭 여러 개에서 막힐 수 있어요. → [WebSocket과 실시간 통신](../../web/websocket-realtime/)

순번은 초 단위로만 바뀌니 대기열엔 **폴링이 더 싸고 단순한** 경우가 많아요. Cloudflare 대기 화면도 20초마다 자동 새로고침하며 예상 대기 시간을 갱신해요. 폴링 간격을 서버 응답에 담아 주면, 혼잡할 때 간격을 늘려 대기열 서버를 보호할 수 있어요.

### 심화: 사례 — Cloudflare Waiting Room

Cloudflare 공식 문서 기준으로 정리해요.

- **설정값**: 동시 활성 인원(`total active users`)과 분당 신규 입장(`new users per minute`). 입장한 사용자는 `session duration`(분) 동안 활성으로 집계되고, 그 안에 나갔다 와도 다시 줄 서지 않아요.
- **입장 순서**: 기본은 **FIFO**(먼저 온 순서). 빈자리가 나면 무작위로 뽑는 **Random**, 줄 없이 통과시키며 트래픽만 재는 Passthrough, 아무도 안 들이고 정적 페이지를 보여 주는 Reject도 있어요. FIFO 외 방식은 일부 요금제 고객만 쓸 수 있어요.
- **쿠키**: `__cfwaitingroom` 쿠키에 대기 순서, 안에 머문 시간, 재입장 허용 여부를 담고, 사용자가 고치지 못하게 **암호화**해요. 대기 중엔 5분 만료(탭이 열려 있으면 20초마다 갱신), 입장 후엔 `session duration`만큼 유지돼요. 큐가 켜진 동안 쿠키를 끈 브라우저는 그 경로에 들어갈 수 없어요.
- 전 세계 트래픽 상태는 Durable Objects(Cloudflare의 상태 저장 실행 단위)로 몇 초마다 맞춰요.

쿠키를 지우거나 탭을 여러 개 열면 어떻게 되는지는 공식 문서에 나와 있지 않아요.

Random 방식은 "일찍 와서 F5 연타하는 매크로"의 이점을 줄여 줘요. 대신 "먼저 온 사람이 먼저"라는 공정성은 포기해요.

### 심화: 사례 — AWS Virtual Waiting Room(단종)

<Aside type="caution" title="단종된 솔루션이에요">
AWS의 오픈소스 Virtual Waiting Room 솔루션은 단종됐고 GitHub 레포는 2025-11-04에 보관(archive) 처리됐어요. AWS는 Marketplace 제품이나 CloudFront Functions 기반 패턴을 권해요. 여기선 **설계 아이디어 사례로만** 봐요.
</Aside>

이 솔루션은 Sorted Set 대신 **카운터 두 개**로 줄을 세워요.

- `queue position`: 요청마다 1씩 오르는 내 번호표.
- `serving counter`: "여기까지 들어와도 돼요"인 가장 큰 번호.
- 내 번호가 serving counter 이하이면 입장. 카운터는 Redis(AWS의 관리형 Redis인 ElastiCache, 가용 영역 2곳)에 둬요.
- serving counter를 언제 얼마나 올릴지는 주기적으로 도는 함수가 정해요(입장 속도).
- 순번에 만료를 걸 수 있고, 만료로 빈 자리만큼 카운터를 자동으로 더 올리는 옵션도 있어요(결제 이탈자 자리 채우기).
- 차례가 오면 개인키로 서명한 **JWT 입장 토큰**을 주고, 보호할 API 앞에서 공개키로 검증해요. 토큰 사용 여부 같은 세션 상태는 DynamoDB에 둬요.

### 심화: 새로고침·매크로 대책

대기 화면에서 순번이 안 줄면 사람들은 F5를 연타해요. 매크로는 더 심하죠.

- **순번 고정**: `ZADD NX`로 새로고침해도 번호 유지.
- **정적 대기 페이지**: 대기 화면 자체는 CDN에서 내려 주고, 대기열 서버는 순번 조회만 받아요.
- **조회 간격을 서버가 정함**: 폴링 간격을 응답에 담아 혼잡할수록 늘려요.
- **사용자·IP별 처리율 제한**: 한 사람이 1초에 수십 번 묻는 건 막아요. → [처리율 제한기 설계](../rate-limiter/)
- **1인 1토큰**: 토큰을 사용자 ID에 묶고, 한 번 쓴 토큰은 사용 처리해서 공유·재사용을 막아요.
- **CAPTCHA, Random 입장**: 사람인지 확인하거나 도착 순서의 이점을 줄여요.

### 심화: Redis가 죽으면

대기열이 Redis 메모리에만 있으면, Redis가 죽는 순간 수십만 명의 번호표가 사라질 수 있어요.

- **복제와 자동 전환**: 복제본을 두고 주 노드가 죽으면 복제본이 이어받게 해요(AWS 사례도 가용 영역 2곳). 단, 복제는 비동기라 전환 직전 몇 건은 빠질 수 있어요. → [Redis 복제와 클러스터](../../redis/replication-cluster/)
- **영속성**: AOF·RDB로 디스크에 남기면 재시작 후 복구할 수 있지만, 마지막 저장 이후 것은 잃을 수 있어요. → [Redis 영속성](../../redis/persistence/)
- **장애 시 정책**: 대기열이 없으면 "전원 대기(입장 중단)"로 뒷단을 지킬지, "전원 통과"로 서비스를 열지 미리 정해 둬요. 티켓팅처럼 뒷단이 약하면 보통 입장 중단 쪽이 안전해요.
- **재고는 DB가 최종 진실**: Redis에서 재고를 먼저 깎더라도 최종 주문은 DB에 기록하고, 둘이 맞는지 나중에 맞춰 보는 **대사**(정합성 확인)를 해요.

### 심화: 헷갈리기 쉬운 것들

- `MULTI`/`EXEC` 트랜잭션 안에서는 앞 명령의 결과를 보고 분기하기 어려워요. 그래서 "있으면 빼기" 같은 조건부 차감은 Lua가 간단해요(WATCH로 낙관적 재시도를 하는 방법도 있어요).
- 파이프라인은 여러 명령을 한 번에 보내 왕복만 줄일 뿐, 그 사이에 다른 클라이언트 명령이 끼어들 수 있어요. 원자성은 없어요.
- Lua 스크립트 캐시는 재시작·전환 때 사라질 수 있어서, `EVALSHA`가 NOSCRIPT 오류를 내면 다시 올리는 처리가 필요해요.
- Sorted Set 점수는 64비트 실수라 정수는 2^53까지만 정확해요. 밀리초 시각(약 1.7×10^12)은 안전해요.
- 순번을 쿠키 평문이나 숨은 입력값에 맡기면 사용자가 고칠 수 있어요. 서버에 두거나 서명·암호화해요.

## 면접 질문

<details>
<summary>Q. 대기열은 왜 필요한가요? 서버를 늘리면 안 되나요?</summary>

**답변(30초)**
순간 몰림은 서버 증설로 못 따라가기 때문이에요. 오토스케일링은 새 서버가 뜨는 데 수 분이 걸리는데 티켓 오픈은 몇 초 만에 몰려요. 또 재고를 가진 DB는 앱 서버처럼 쉽게 늘릴 수 없어요. 그래서 사용자를 줄 세우고 뒷단이 버틸 만큼만 들여보내 원래 서버를 보호해요.

**꼬리질문**
- Q. 처리율 제한으로는 안 되나요? → 처리율 제한은 한 사용자의 과한 요청을 막는 거예요. 정상 사용자 50만 명이 한 번씩 누르는 건 막을 대상이 아니라 줄 세울 대상이에요.
- Q. 평소에도 줄을 세우나요? → 아니요. 한계에 가까워질 때만 줄을 세우고 평소엔 바로 통과시켜요.
</details>

<details>
<summary>Q. Redis로 대기 순번을 어떻게 관리하나요? 왜 Sorted Set인가요?</summary>

**답변(30초)**
Sorted Set에 사용자 ID를 멤버로, 도착 시각을 점수로 넣어요. 점수 순으로 자동 정렬되니 그 자체가 줄이 돼요. `ZADD NX`로 번호표를 주고, `ZRANK`로 내 순번을 O(log N)에 조회하고, 스케줄러가 `ZPOPMIN`으로 앞에서 N명씩 꺼내 입장시켜요. 멤버가 중복되지 않아 한 사람이 줄을 두 번 설 수도 없어요.

**꼬리질문**
- Q. List로 하면요? → 넣고 꺼내긴 쉽지만 "내가 몇 번째인지"를 찾으려면 앞에서부터 세야 하고, 같은 사람이 중복으로 들어가는 걸 막기 어려워요.
- Q. ZRANK 값을 그대로 보여 줘도 되나요? → 0부터 시작해서 +1 해서 보여 줘야 해요.
</details>

<details>
<summary>Q. 대기 중에 새로고침하면 순번이 뒤로 밀리나요?</summary>

**답변(30초)**
`ZADD`에 `NX` 옵션을 쓰면 밀리지 않아요. NX는 없는 멤버만 추가하고, 이미 있으면 점수를 바꾸지 않아요. 한 번 재 보니 이미 있는 사용자에게 다시 ZADD NX를 보내면 0이 돌아오고 점수는 그대로였어요. NX를 빼면 새로고침할 때마다 도착 시각이 갱신돼 맨 뒤로 가요.

**꼬리질문**
- Q. 순번을 쿠키에 넣으면요? → 평문이면 사용자가 고칠 수 있어요. Cloudflare는 대기열 쿠키를 암호화해요.
- Q. 새로고침 연타 자체가 부하가 되면? → 대기 페이지는 CDN에서 주고, 조회 간격을 서버가 정하고, 사용자별 처리율 제한을 걸어요.
</details>

<details>
<summary>Q. 입장 속도는 어떻게 정하나요?</summary>

**답변(30초)**
가장 약한 뒷단의 처리량을 기준으로 정해요. 보통 DB나 결제 서버예요. 스케줄러가 1초마다 `ZPOPMIN`으로 꺼내는 인원이 입장 속도이고, 동시에 안에 있을 수 있는 인원 상한도 함께 둬요. Cloudflare도 동시 활성 인원과 분당 신규 입장 두 값으로 설정해요.

**꼬리질문**
- Q. 입장한 사람이 결제 안 하고 떠나면? → 입장 세션에 만료를 걸고, 만료로 빈 자리만큼 다음 사람을 더 들여보내요.
- Q. 처리량은 어떻게 아나요? → 부하 테스트로 재고, 운영 중엔 응답 시간·에러율을 보며 조절해요.
</details>

<details>
<summary>Q. 예매 서버는 사용자가 대기열을 통과했는지 어떻게 아나요?</summary>

**답변(30초)**
차례가 된 사용자에게 서버가 서명한 입장 토큰을 줘요. 토큰엔 사용자 ID, 이벤트 ID, 만료 시각을 넣어요. 예매 서버는 요청마다 서명과 만료를 검사하고, 없거나 위조면 대기열로 돌려보내요. 서명은 비밀키가 있어야 만들 수 있어서 사용자가 지어낼 수 없어요.

**꼬리질문**
- Q. 토큰을 다른 사람에게 넘기면? → 사용자 ID에 묶어 로그인 사용자와 비교하고, 한 번 쓴 토큰은 사용 처리해요. AWS 사례는 사용 여부를 DynamoDB에 뒀어요.
- Q. 서명과 암호화의 차이는? → 서명은 위조를 막고 내용은 보일 수 있어요. 암호화는 내용을 숨겨요.
</details>

<details>
<summary>Q. 선착순 쿠폰 100장에 1,000명이 동시에 요청하면 초과 발급을 어떻게 막나요?</summary>

**답변(30초)**
"남았나 확인"과 "하나 빼기"를 한 덩어리로 만들어요. Redis라면 Lua 스크립트로 "0보다 크면 DECR"을 원자적으로 실행하고, DB라면 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`으로 바뀐 행 수를 보고 판정해요. 확인과 차감을 따로 하면 그 사이에 다른 요청이 끼어들어 초과 발급이 나요.

**꼬리질문**
- Q. DECR만 쓰면요? → 결과가 0 이상일 때만 성공 처리하면 초과 발급은 막아요. 하지만 한 번 재 보니 실패한 900건도 깎아서 재고 값이 -900까지 내려갔어요.
- Q. 대기열이 있으면 이 문제가 없지 않나요? → 대기열은 들어오는 속도만 줄여요. 입장한 사람끼리는 여전히 경쟁해요.
</details>

<details>
<summary>Q. Redis Lua, DB 조건부 UPDATE, 비관적 락, 분산 락 중 무엇을 고르나요?</summary>

**답변(30초)**
요청이 아주 많은 단일 재고 차감이면 Redis Lua가 가장 빠르고 단순해요. 대신 Redis가 최종 진실이 아니니 주문은 DB에 남기고 대사해요. 트래픽이 적당하면 DB 조건부 UPDATE 한 줄이 가장 안전해요. 비관적 락은 인기 상품 한 행에 대기가 몰려 커넥션이 고갈될 수 있고, 분산 락은 차감 하나에 락 왕복이 더해져 느려요. 여러 자원을 함께 바꿔야 할 때 락을 고려해요.

**꼬리질문**
- Q. 핫 로우 문제는? → 인기 상품 한 행에 잠금 대기가 몰리는 거예요. Redis 앞단에서 먼저 깎고 DB 주문은 메시지 큐로 뒤에서 만들거나, 재고를 여러 행으로 쪼개요.
- Q. Lua의 단점은? → 실행 중엔 Redis 전체가 멈춰서 짧게 써야 하고, 스크립트 캐시가 재시작 때 사라질 수 있어요.
</details>

<details>
<summary>Q. 대기 순번을 실시간으로 보여 주려면 폴링과 SSE 중 무엇이 나은가요?</summary>

**답변(30초)**
대기열은 폴링이 더 나은 경우가 많아요. 순번은 초 단위로만 바뀌는데, SSE는 대기자 수만큼 연결을 계속 열어 둬야 해서 수십만 개 연결 유지 비용이 커요. 폴링은 간격을 서버가 정해 혼잡할 때 늘릴 수 있어요. Cloudflare 대기 화면도 20초마다 새로고침해요. 즉시성이 중요하고 대기자가 적으면 SSE를 써요.

**꼬리질문**
- Q. WebSocket은요? → 양방향이 필요 없어서 과해요. 순번 알림은 서버→클라이언트 한 방향이라 SSE로 충분해요.
- Q. SSE 연결 제한은? → HTTP/1.1에선 브라우저가 도메인당 6개까지라 탭이 많으면 막혀요. HTTP/2에선 협상값(기본 100 스트림)이에요.
</details>

<details>
<summary>Q. 대기열 Redis가 죽으면 어떻게 하나요?</summary>

**답변(30초)**
먼저 복제본과 자동 전환으로 대기열이 통째로 사라지지 않게 해요. 그래도 비동기 복제라 전환 직전 몇 건은 잃을 수 있어요. 그리고 장애 때 "입장 중단"으로 뒷단을 지킬지 "전원 통과"로 열지 정책을 미리 정해 둬요. 티켓팅은 뒷단이 약하니 보통 입장 중단이 안전해요. 재고를 Redis에서 깎았다면 최종 주문은 DB에 두고 대사해요.

**꼬리질문**
- Q. AOF를 켜면 안전한가요? → 디스크에 남지만 마지막 동기화 이후 것은 잃을 수 있고, 매 쓰기마다 동기화하면 느려져요.
- Q. 사용자 입장에선? → 번호표를 잃은 사용자에게 원래 순번을 돌려줄 근거(서명된 쿠키·토큰의 도착 시각)를 남겨 두면 복구에 도움이 돼요.
</details>

## 서술형 연습

<details>
<summary>상황: 선착순 쿠폰 100장 이벤트를 열었는데 103장이 발급됐어요. 코드는 "발급 수를 세서 100 미만이면 발급 기록을 INSERT"하는 방식이었어요. 원인과 해결책은?</summary>

**상황 파악**
초과는 3장으로 작아요. 대부분은 정상 동작했고, 마지막 몇 장 근처에서 동시에 온 요청 몇 개가 함께 통과했을 가능성이 커요.

**원인 후보**
1. **확인-행동 경합**: 요청 A, B, C, D가 동시에 "발급 수 = 99"를 읽고 모두 "100 미만이네" 하고 INSERT했어요. 세기와 넣기 사이에 다른 요청이 끼어든 거예요.
2. 트랜잭션은 걸었지만 격리 수준상 다른 트랜잭션의 INSERT를 막지 못했어요. MySQL InnoDB의 일반 SELECT는 SERIALIZABLE이 아니면 잠금을 안 걸어요. → [격리 수준](../../db/isolation-levels/)
3. 같은 사용자가 여러 번 받았을 수도 있어요(1인 1매 제약 없음).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 남은 수량 컬럼을 두고 `UPDATE ... SET remain = remain - 1 WHERE id = ? AND remain > 0`, 바뀐 행이 1일 때만 발급 | DB 한 곳에서 정확, 코드 변경 작음 | 요청이 아주 많으면 한 행에 잠금 대기가 몰림 |
| B. Redis Lua로 "남았으면 차감"을 원자적으로 처리 후 DB에 발급 기록 | 매우 빠름, DB 부하 적음 | Redis와 DB 두 곳을 맞춰야 함, Redis 장애 대비 필요 |
| C. `SELECT ... FOR UPDATE`로 카운트 행을 잠그고 확인·발급 | 기존 흐름 유지 | 잠금 대기가 길어져 커넥션 고갈 위험 |
| D. (사용자 ID, 이벤트 ID) 유니크 제약 | 1인 1매를 DB가 보장 | 총량 초과는 못 막음, A·B와 함께 써야 함 |

**내가 고를 방법**
트래픽이 감당할 만하면 A + D로 가요. 한 줄 조건부 UPDATE로 총량을, 유니크 제약으로 1인 1매를 DB가 직접 보장해서 가장 단순하고 틀리기 어려워요. 수십만 명이 몰리는 이벤트라면 B로 앞단에서 먼저 걸러 DB에 닿는 요청을 100건 근처로 줄이고, DB에도 D를 걸어 이중으로 지켜요. 이미 나간 3장은 발급 시각 순으로 뒤 3장을 확인해 회수할지, 비용으로 감수할지 정해요.

**채점 포인트**: 확인-행동 경합(check-then-act), 원자적 차감(조건부 UPDATE·affected rows 또는 Lua), 일반 SELECT는 잠금 없음, 1인 1매 유니크 제약, 비관적 락의 핫 로우 문제, Redis 사용 시 DB와의 정합성.
</details>

<details>
<summary>상황: 대기 화면에서 새로고침하면 맨 뒤로 간다는 민원이 쏟아지고, 동시에 대기열 서버 CPU가 치솟았어요. 원인과 해결책은?</summary>

**상황 파악**
두 증상이 서로를 키우고 있어요. 순번이 밀리니 사람들이 불안해서 새로고침하고, 새로고침할수록 더 밀리고, 요청이 늘어 서버가 느려지니 또 새로고침해요.

**원인 후보**
1. `ZADD`를 `NX` 없이 써서, 새로고침할 때마다 점수(도착 시각)가 새 값으로 덮어써짐.
2. 새로고침하면 새 세션 ID가 발급돼, 대기열에서 다른 사람으로 취급됨(멤버 키가 사용자 ID가 아님).
3. 대기 페이지 전체를 대기열 서버가 렌더링하고 있어, 새로고침마다 페이지와 순번 조회가 함께 들어옴.
4. 폴링 간격이 너무 짧거나 클라이언트마다 제각각.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `ZADD NX` + 멤버를 로그인 사용자 ID로 | 새로고침해도 순번 유지, 근본 원인 해결 | 로그인 전 대기는 서명된 쿠키 등 다른 식별자 필요 |
| B. 대기 페이지를 CDN 정적 파일로, 순번만 API로 | 대기열 서버 부하 크게 줄어듦 | 배포 구조 변경 |
| C. 폴링 간격을 서버 응답에 담아 혼잡 시 늘림 | 부하를 서버가 조절 | 순번 갱신이 늦게 보임 |
| D. 사용자·IP별 처리율 제한 | 매크로·연타 차단 | 같은 IP 뒤 여러 사용자가 억울하게 막힐 수 있음 |
| E. SSE로 전환 | 새로고침 동기 감소 | 대기자 수만큼 연결 유지 비용 |

**내가 고를 방법**
먼저 A로 순번이 밀리지 않게 고쳐요. 이게 새로고침의 동기를 없애는 근본 해결이에요. 화면에도 "새로고침해도 순번은 유지돼요"라고 알려요. 그다음 B와 C로 남은 조회 부하를 줄이고, D로 매크로를 막아요([처리율 제한기 설계](../rate-limiter/)). E는 대기자가 수십만 명이면 연결 비용이 커서 폴링 간격 조절을 먼저 해요.

**채점 포인트**: ZADD NX(기존 멤버 점수 유지), 멤버 키를 안정적인 사용자 식별자로, 새로고침과 부하의 악순환, CDN 정적 대기 페이지, 서버가 정하는 폴링 간격, 처리율 제한, SSE 연결 비용.
</details>

<details>
<summary>상황: 대기열은 정상 동작했는데, 입장시킨 사용자들이 결제 페이지로 한꺼번에 넘어가면서 DB가 다운됐어요. 원인과 해결책은?</summary>

**상황 파악**
대기열이 지킨 건 "입구"였고, 안쪽 단계마다 부하가 다르다는 걸 놓쳤어요. 좌석 선택은 버텼는데 결제는 DB 쓰기와 외부 결제사 호출이 겹쳐 훨씬 무거워요.

**원인 후보**
1. 입장 속도를 대기열 서버나 좌석 조회 처리량 기준으로 정함. 가장 약한 결제·DB가 기준이 아니었음.
2. 동시 활성 인원 상한이 없어서, 앞서 들어간 사람이 안 나갔는데도 계속 새 사람을 들여보냄.
3. 결제 단계에서 재고 행을 `FOR UPDATE`로 잡고 외부 결제사 응답을 기다려, 잠금 대기가 쌓여 커넥션 풀이 고갈됨.
4. 결제 실패 시 클라이언트가 즉시 재시도해 부하가 배로 늘어남.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 입장 속도를 결제·DB 처리량 기준으로 낮추고 동시 활성 인원 상한 추가 | 가장 단순, 뒷단 전체 보호 | 대기 시간이 길어짐 |
| B. 결제 단계에 별도 제한(결제 전용 대기열·동시 처리 수 제한) | 앞 단계는 빠르게, 무거운 단계만 조절 | 대기열이 두 겹이라 사용자 경험·구현 복잡 |
| C. 좌석은 짧은 TTL로 임시 점유(Redis), 결제 완료 때만 DB에 확정 | DB 잠금 시간 짧아짐 | 점유 만료·반납 처리 필요 |
| D. 외부 결제사 호출을 DB 트랜잭션 밖으로 빼기 | 잠금이 외부 응답을 안 기다림 | 결제 결과와 주문 상태를 맞추는 처리 필요 |
| E. 재시도에 백오프+지터(간격을 점점 늘리고 무작위로 흩기), 결제 서버에 부하 차단 | 재시도 폭주 차단 | 일부 사용자는 실패 메시지를 봄 |

**내가 고를 방법**
당장은 A로 입장 속도를 결제가 버티는 수준으로 낮추고 동시 활성 인원 상한을 걸어 DB를 살려요. 그다음 C와 D로 결제 단계가 DB 잠금을 오래 잡지 않게 바꿔요. 결제 단계의 처리량이 여전히 앞 단계보다 훨씬 낮으면 B로 결제에만 별도 제한을 둬요. E는 어느 경우든 같이 해요. 결제 정합성은 [결제 시스템 설계](../payment-system/)의 멱등성과 상태 관리를 따라요.

**채점 포인트**: 입장 속도는 가장 약한 뒷단 기준, 입장 속도와 동시 활성 인원 구분, 단계별 부하 차이와 결제 단계 별도 제한, 트랜잭션 안의 외부 호출·잠금 대기·커넥션 풀 고갈, 좌석 임시 점유 TTL, 재시도 백오프.
</details>
