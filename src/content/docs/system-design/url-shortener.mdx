:::tip[한 줄 요약]
URL 단축기는 긴 주소에 **짧은 코드**를 붙여 저장해 두고, 그 코드로 들어오면 원래 주소로 보내 주는(리다이렉트) 서비스예요. 설계의 핵심은 **코드를 어떻게 만들지**(해시 자르기 / ID를 base62로 / 미리 만든 키 풀)와 **301과 302 중 무엇으로 보낼지**(서버 부하 vs 클릭 통계) 두 가지 선택이에요.
:::

:::note[처음이라면 여기까지]
① 긴 주소를 저장하고 "사물함 번호" 같은 짧은 코드를 돌려줘요. 누가 그 번호로 오면 원래 주소로 보내요.

② 코드는 숫자 0-9, 소문자, 대문자 총 62가지 글자로 만들어요(**base62**). 7자리면 약 3.5조 개를 만들 수 있어요.

③ 읽기(클릭)가 만들기보다 훨씬 많아서 캐시가 잘 먹혀요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

택배 보관함을 떠올려 보세요. 물건(긴 주소)을 맡기면 **"A-1234"** 같은 짧은 사물함 번호를 받아요. 친구에게는 긴 주소 대신 이 번호만 알려 주면 돼요. 친구가 번호를 들고 오면 보관함 관리자가 그 칸을 열어 원래 물건(원래 주소)을 건네줘요.

설계에서 고민할 건 두 가지예요. 첫째, **번호를 어떻게 매길까?** 1번, 2번 순서대로 주면 절대 겹치지 않지만, 누군가 1235번, 1236번을 차례로 열어 볼 수 있어요. 둘째, **친구가 두 번째 올 때도 관리자를 거치게 할까?** "앞으로는 그냥 직접 가세요"라고 하면 관리자는 편하지만, 몇 번 왔는지 셀 수 없어요.

단, 실제로는 보관함과 달리 물건을 "꺼내 가는" 게 아니에요. 원래 주소는 계속 저장돼 있고, 브라우저에게 "그 주소로 가세요"라고 알려 주기만 해요.

## 제대로 알기

### 1. 요구사항

면접에서 먼저 물어 범위를 좁혀요. 이 페이지는 아래처럼 정했다고 가정해요.

**기능 요구사항**

- **단축**: 긴 URL을 받아 짧은 URL을 돌려줘요.
- **리다이렉트**: 짧은 URL로 들어오면 원래 URL로 보내요.
- **만료**: 정해진 날짜가 지나면 링크가 더 이상 안 열려요.
- **커스텀 별칭**: 사용자가 `/my-event`처럼 코드를 직접 정할 수 있어요.
- **통계**: 링크별 클릭 수를 셀 수 있어요.

**비기능 요구사항**

- 리다이렉트는 빨라야 해요(사용자가 기다리는 경로).
- 서비스가 멈추면 이미 퍼진 링크가 전부 깨지니 가용성이 중요해요.
- 코드는 짧아야 하고, 남이 쉽게 추측하면 안 돼요.

### 2. 규모 추정

아래 숫자는 **가정**이에요. 면접에서도 "이렇게 가정할게요"라고 먼저 말해요.

| 항목 | 계산 | 결과 |
|---|---|---|
| 하루 생성(쓰기) | 가정 | 1억 건 |
| 읽기:쓰기 | 가정(공유된 링크는 여러 번 클릭됨) | 100:1 |
| 평균 쓰기 QPS | 1억 ÷ 86,400 | **약 1,160** |
| 평균 읽기 QPS | 1,160 × 100 | **약 11.6만** |
| 피크 | 평균 × 2~3(가정) | 읽기 약 23만~35만 |
| 저장 | 1억 × 500B(레코드 1개 가정) | 하루 50GB, 10년 약 180TB |
| 10년간 코드 수 | 1억 × 365 × 10 | **3,650억 개** |

**숫자가 말해 주는 것**

- 읽기가 쓰기의 100배라서 **캐시가 핵심**이에요. 인기 링크에 클릭이 몰리니 적중률도 높아요.
- 10년간 3,650억 개가 필요하니, 코드 길이는 아래 표로 정해요.

### 3. base62와 코드 길이

**base62**는 숫자 10개 + 소문자 26개 + 대문자 26개 = 62글자로 수를 적는 방법이에요. 10진수가 0~9 열 글자로 수를 적듯, 62글자로 적는 62진법이에요. 이 62글자는 URL에 특수 처리(퍼센트 인코딩) 없이 그대로 넣을 수 있어요.

| 길이 | 만들 수 있는 코드 수 | 대략 | 10년치(3,650억) 충분? |
|---|---|---|---|
| 5자 | 62^5 = 916,132,832 | 약 9.2억 | 부족 |
| 6자 | 62^6 = 56,800,235,584 | 약 568억 | 부족 |
| 7자 | 62^7 = 3,521,614,606,208 | 약 3.5조 | **충분** |
| 8자 | 62^8 | 약 218조 | 넉넉 |

그래서 이 가정에선 **7자**를 골라요.

<Aside type="note" title="왜 base64가 아니라 base62예요?">
base64는 `+`와 `/`를 써서 URL에 그대로 넣으면 의미가 꼬여요(URL용 변형인 base64url은 `-`, `_`를 써요). base62는 처음부터 이 두 글자를 빼서 문제를 피한 거예요.
</Aside>

### 4. API

| 요청 | 입력 | 출력 |
|---|---|---|
| `POST /api/links` | 원본 URL, (선택) 별칭, (선택) 만료일 | 짧은 URL (예: `https://s.example/aZ3kP9x`) |
| `GET /{code}` | 코드 | 301 또는 302 + `Location: 원본 URL` |
| `GET /api/links/{code}/stats` | 코드 | 클릭 수 등 |

리다이렉트 응답의 `Location` 헤더에 원래 URL을 넣으면, 브라우저가 그 주소로 이동해요.

### 5. 데이터 모델

| 컬럼 | 설명 |
|---|---|
| `code` | 짧은 코드, **기본키(UNIQUE)** |
| `long_url` | 원래 URL |
| `created_at` | 만든 시각 |
| `expires_at` | 만료 시각(없으면 영구) |
| `owner_id` | 만든 사람(선택) |

조회는 거의 항상 "코드로 원본 찾기"라서 키-값 구조와 잘 맞아요. 클릭 통계는 이 테이블에 바로 +1 하지 않고 따로 모아요(아래 설계 참고).

### 6. 상위 설계

```text
[생성] 클라이언트 → 앱 서버 → ID 생성기 → base62 인코딩 → DB 저장
[이동] 브라우저 → 앱 서버 → Redis(캐시) → 없으면 DB → 302 응답
                       └→ 클릭 이벤트 → 큐(Kafka 등) → 통계 저장소
```

**생성 흐름**

1. 원본 URL(+별칭, 만료일)을 받아요.
2. URL 형식을 검사하고, 악성 URL 차단 목록을 확인해요.
3. 별칭이 있으면 이미 쓰였는지 확인, 없으면 ID 생성기에서 정수를 받아요.
4. 정수를 base62로 바꿔 코드를 만들어요.
5. DB에 저장하고 짧은 URL을 돌려줘요.

**리다이렉트 흐름**

1. Redis에서 코드를 찾아요. 있으면 바로 원본 URL.
2. 없으면 DB에서 찾고, Redis에 TTL(유효 기간)을 걸어 넣어 둬요. 이렇게 "없을 때만 DB에서 가져와 캐시에 채우는" 방식을 **cache-aside**라고 해요. → [캐시 패턴](../../redis/cache-patterns/)
3. 만료 시각이 지났으면 404나 410을 돌려줘요.
4. 클릭 이벤트는 큐에 던지고 기다리지 않아요. 통계 때문에 이동이 느려지면 안 되니까요.
5. 302 + `Location`으로 응답해요.

읽기가 압도적이라 캐시·CDN으로 앞단에서 흡수하는 이야기는 [캐시·CDN으로 규모 키우기](../cache-cdn-scale/)에 이어져요.

### 7. 핵심 선택 ①: 코드를 어떻게 만들까

| | A. 해시 자르기 + 충돌 처리 | B. ID → base62 | C. 미리 만든 키 풀 |
|---|---|---|---|
| 방법 | 원본 URL을 MD5·SHA-256으로 **해시**(아무 길이 입력을 고정 길이 값으로 바꾸는 함수)한 뒤 일부만 씀 | DB 자동 증가 번호나 분산 ID 생성기로 받은 정수를 base62로 바꿈 | 쓰이지 않은 코드를 미리 잔뜩 만들어 두고 하나씩 꺼내 줌 |
| 충돌 | **있음**. 잘라서 짧아지는 순간 다른 URL이 같은 코드가 될 수 있어요 → DB 확인 후 재시도 | **없음**. 정수가 고유하면 코드도 고유해요 | 없음(풀 관리가 맞다면) |
| 같은 URL을 또 줄이면 | 항상 같은 코드(자동으로 합쳐짐) | 매번 새 코드(합치려면 원본 URL로 먼저 조회) | 매번 새 코드 |
| 예측 가능성 | 낮음 | **순차 번호면 높음** → 보안 고려 필요 | 무작위로 만들면 낮음 |
| 단점 | 데이터가 많아질수록 충돌·재시도가 늘어요 | ID 생성기가 필요하고, 다음 코드를 추측당할 수 있어요 | 풀을 채우고 나눠 주는 별도 관리가 필요해요 |

**해시 충돌은 생각보다 빨리 나요.** "7자면 3.5조 개니까 충돌 걱정 없다"는 틀린 말이에요. 반 학생 23명만 모여도 생일이 같은 쌍이 있을 확률이 50%를 넘는 것처럼(**생일 문제**), 7자 base62 공간에서도 **약 221만 개**만 넣으면 충돌이 한 번 이상 날 확률이 50%예요. 1억 개를 넣으면 예상 충돌이 약 1,420건이에요.

직접 돌려 본 **실험 예시**도 있어요. URL 10만 개를 MD5로 해시해서 **16진수 앞 7자**를 코드로 썼더니, 세 번 시도에서 각각 **12건, 21건, 17건** 충돌이 났어요. 16진수는 글자가 16가지뿐이라 7자여도 공간이 약 2.7억 개밖에 안 되거든요. 같은 7자라도 base62(3.5조)와 공간 크기가 전혀 달라요.

**순차 ID는 추측당해요.** ID → base62 방식에서 번호를 1, 2, 3 순서로 주면, 내 코드에서 한 글자만 바꿔 다음·이전 코드를 넣어 볼 수 있어요. 남의 비공개 문서 링크가 열릴 수도 있고, 코드 증가 속도로 서비스 규모까지 드러나요. 그래서 ID를 그대로 쓰지 않고 한 번 섞거나(아래 심화), 무작위 코드를 쓰거나, 민감한 링크는 코드를 더 길게 하거나 인증을 붙여요.

여러 서버에서 겹치지 않는 정수를 만드는 방법은 [분산 시간과 ID](../../distributed/distributed-time-ids/)에 있어요.

### 8. 핵심 선택 ②: 301 vs 302

둘 다 "다른 주소로 가세요"라는 **리다이렉트** 응답 코드예요. 차이는 브라우저가 이 답을 **기억하느냐**예요.

| | 301 Moved Permanently | 302 Found |
|---|---|---|
| 뜻 | "영구히 이사 갔어요" | "지금은 잠깐 저기 있어요" |
| 브라우저 캐시 | 캐시 헤더가 없어도 브라우저가 알아서 저장해도 돼요 | 캐시 헤더가 있을 때만 저장해요 |
| 두 번째 클릭 | 단축 서버를 **안 거치고** 바로 원본으로 갈 수 있어요 | **매번** 단축 서버를 거쳐요 |
| 서버 부하 | 줄어요 | 그대로 와요 |
| 클릭 통계 | **덜 잡혀요** | 정확해요 |
| 목적지 변경·만료 | 이미 기억한 브라우저는 옛 목적지로 가요 | 바로 반영돼요 |

통계·만료·목적지 변경이 요구사항에 있으니 이 설계에선 **302**를 골라요. 서버 부하는 캐시로 줄여요.

<Aside type="caution" title="301을 써도 통제할 수는 있어요">
301에 `Cache-Control: max-age=...`나 `no-store` 같은 캐시 헤더를 명시하면, 브라우저가 기억하는 기간을 직접 정할 수 있어요(명시한 헤더가 브라우저의 추측보다 우선). 헤더가 없으면 주요 브라우저는 꽤 오래 기억하는데, 정확한 기간은 표준이 정하지 않아요.
</Aside>

### 9. 커스텀 별칭과 만료

**커스텀 별칭**은 자동 코드와 같은 자리(코드 컬럼)를 써요. 그래서

- UNIQUE 제약으로 이미 쓰였는지 확인해요.
- `api`, `admin` 같은 예약어는 막아요.
- 길이와 글자 종류를 제한해요.
- 자동 코드와 겹치지 않게 규칙을 나눠요(예: 하이픈은 별칭에만 허용).

**만료**는 레코드에 `expires_at`을 저장하고, 조회할 때 지났으면 404나 **410 Gone**(의도적으로 영구 제거됨)을 돌려줘요. 실제 삭제는 나중에 배치로 몰아서 해요. Redis 캐시 TTL도 만료 시각에 맞춰 걸어야, 캐시에 남은 옛 값이 만료 뒤에 열리는 일이 없어요. → [만료와 메모리 정책](../../redis/expire-eviction/)

만료된 코드는 보통 **다시 쓰지 않아요**. 재사용하면 옛 링크를 가진 사람이 엉뚱한 사이트로 가게 되니까요.

### 심화: base62 인코딩 코드

정수를 62로 계속 나누고, 나머지를 글자로 바꾸면 돼요.

```python
CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode(n):
    if n == 0:
        return CHARS[0]
    s = []
    while n > 0:
        n, r = divmod(n, 62)   # 몫과 나머지
        s.append(CHARS[r])
    return "".join(reversed(s))

def decode(code):
    n = 0
    for ch in code:
        n = n * 62 + CHARS.index(ch)
    return n

# 61 → "Z", 62 → "10", 10억 → "15FTGg"(6자)
assert decode(encode(10**9)) == 10**9
```

### 심화: 해시를 자를 때의 함정

같은 실험에서 하나 더 발견한 게 있어요. MD5 값을 큰 정수로 보고 base62 문자열로 바꾼 뒤 **맨 앞 몇 글자**를 자르면, 큰 수의 맨 앞자리는 고르게 나오지 않아서 충돌이 훨씬 많아졌어요(5자 기준 예상치의 약 8배). 자를 땐 **뒤쪽 자리**(`해시값 mod 62^k`)를 쓰거나 해시 바이트를 직접 쓰는 게 맞아요.

충돌 처리 루프는 이래요.

```text
URL → 해시 → 7자 추출 → DB에 이미 있나?
  ├ 없음 → 저장
  ├ 있음, 같은 URL → 기존 코드 돌려줌
  └ 있음, 다른 URL → URL에 소금(salt)이나 카운터를 붙여 다시 해시
```

데이터가 늘수록 "있음, 다른 URL" 경우가 늘어 생성이 느려져요. 그래서 대규모에선 ID 기반이 유리해요.

### 심화: 순차 ID 섞기와 Snowflake 길이

- **ID 섞기**: 비밀키로 정수를 다른 정수로 1:1 바꾸는 변환(순열, 블록 암호)을 거친 뒤 base62로 바꿔요. 여전히 겹치지 않지만, 바깥에선 순서를 알 수 없어요.
- **Snowflake 길이**: 시간 기반 64비트 ID(Snowflake 등)는 값이 커서 base62로 바꾸면 **10~11자**가 돼요. "짧게"가 목표라면 서버마다 번호 묶음(예: 1~100만)을 미리 받아 쓰는 **범위 할당**이 더 짧아요.
- 예측 가능한 식별자로 남의 데이터에 접근되는 문제는 OWASP가 접근 제어 취약점(**IDOR**, 객체를 직접 가리키는 번호를 바꿔 남의 것에 접근)으로 분류해요.

### 심화: 블룸 필터로 없는 코드 막기

**블룸 필터**(Bloom filter)는 "아마 있음" 또는 "확실히 없음"만 답하는, 메모리를 아주 적게 쓰는 자료구조예요. "있음"은 틀릴 수 있지만(거짓 양성), "없음"은 항상 맞아요. 기본형은 넣은 값을 지울 수 없어요.

URL 단축기에서는 두 군데 써요.

- 봇이 무작위 코드로 대량 요청을 보내면, 캐시에도 없고 DB까지 내려가요(**캐시 관통**). 블룸 필터가 "확실히 없음"이라 하면 DB에 가지 않고 바로 404를 줘요. → [캐시 문제](../../redis/cache-problems/)
- 무작위·해시 코드를 만들 때 "이미 쓰였나"를 먼저 걸러요. "아마 있음"이면 DB로 다시 확인해요.

Redis에선 `BF.RESERVE`(오차율·용량 지정), `BF.ADD`, `BF.EXISTS`(1이면 아마 있음, 0이면 확실히 없음)로 써요. 이것만으로 부족하면 "없음" 결과도 짧게 캐시하고, IP별 요청 수를 제한해요([레이트 리미터](../rate-limiter/)).

### 심화: 307과 308

307은 302와, 308은 301과 뜻이 같아요. 차이는 **요청 방식(메서드)을 바꾸면 안 된다**는 점이에요. 301·302는 옛날부터 브라우저가 POST 요청을 GET으로 바꿔 다시 보내는 게 허용돼 왔어요. 링크 클릭은 원래 GET이라 단축 URL에선 사실상 차이가 없고, POST를 다른 주소로 넘길 때 차이가 나요.

## 면접 질문

<details>
<summary>Q. base62가 뭐고 왜 쓰나요? 7자면 몇 개 만들 수 있나요?</summary>

**답변(30초)**
base62는 숫자 10개, 소문자 26개, 대문자 26개 총 62글자로 수를 적는 62진법이에요. 이 글자들은 URL에 그대로 넣을 수 있어서 짧은 코드에 써요. base64는 `+`, `/`가 들어가 URL에서 문제가 돼요. 7자면 62의 7제곱, 약 3.5조 개를 만들 수 있어요. 하루 1억 개씩 10년이면 3,650억 개라 7자면 충분하고, 6자(약 568억)는 부족해요.

**꼬리질문**
- Q. 정수를 base62로 어떻게 바꾸나요? → 62로 계속 나눈 나머지를 글자로 바꿔 거꾸로 이어 붙여요.
- Q. 코드 길이를 늘리면 뭐가 좋아요? → 공간이 62배씩 커져서 충돌과 추측이 어려워져요. 대신 URL이 길어져요.
</details>

<details>
<summary>Q. 301과 302 중 무엇을 쓰겠어요?</summary>

**답변(30초)**
클릭 통계나 만료가 필요하면 302를 써요. 301은 "영구 이동"이라 브라우저가 캐시 헤더 없이도 기억할 수 있어서, 두 번째 클릭부터 단축 서버를 안 거치고 바로 원본으로 가요. 그러면 서버 부하는 줄지만 클릭 수가 덜 잡히고, 목적지를 바꾸거나 만료해도 이미 기억한 브라우저엔 반영이 안 돼요. 302는 매번 서버를 거쳐서 정확하고, 늘어난 부하는 캐시로 흡수해요.

**꼬리질문**
- Q. 301을 쓰면서 통제할 방법은요? → `Cache-Control: max-age`나 `no-store`를 명시해 기억 기간을 직접 정해요.
- Q. 307은 302와 뭐가 달라요? → 뜻은 같지만 307은 POST를 GET으로 바꾸면 안 돼요. 링크 클릭(GET)에선 차이가 거의 없어요.
</details>

<details>
<summary>Q. 규모를 추정해 보세요. 하루 1억 개 생성, 읽기:쓰기 100:1이라면요?</summary>

**답변(30초)**
쓰기는 1억 ÷ 86,400으로 평균 약 1,160 QPS, 읽기는 그 100배인 약 11.6만 QPS예요. 피크는 2~3배로 가정해요. 레코드 하나를 500B로 가정하면 하루 50GB, 10년에 약 180TB예요. 읽기가 압도적이니 코드→원본 URL을 Redis에 캐시하는 게 핵심이고, 10년간 3,650억 개가 필요하니 코드는 7자로 정해요.

**꼬리질문**
- Q. 캐시 크기는 어떻게 잡아요? → 인기 링크에 클릭이 몰리니 "하루 읽기 중 상위 20%" 같은 식으로 추정해요.
</details>

<details>
<summary>Q. 짧은 코드를 어떻게 만들 건가요? 해시 방식과 ID 방식을 비교해 보세요.</summary>

**답변(30초)**
저는 ID를 받아 base62로 바꾸는 방식을 고를래요. 해시 방식은 같은 URL이 늘 같은 코드가 되는 장점이 있지만, 짧게 자르는 순간 충돌이 생겨 DB 확인과 재시도가 필요해요. ID 방식은 정수가 고유하니 충돌이 구조적으로 없어요. 다만 순차 번호면 다음 코드를 추측당하니, ID를 비밀키로 섞어서 인코딩하거나 민감한 링크는 더 길게 만들어요.

**꼬리질문**
- Q. 미리 만든 키 풀은요? → 무작위 코드를 미리 만들어 두고 꺼내 주는 방식이라 충돌과 추측이 없지만, 풀을 채우고 나눠 주는 관리가 따로 필요해요.
- Q. 여러 서버에서 ID가 안 겹치게 하려면요? → 서버마다 번호 묶음을 미리 받아 쓰거나 Snowflake 같은 분산 ID를 써요. Snowflake는 10~11자로 길어져요.
</details>

<details>
<summary>Q. 해시를 7자로 자르면 충돌이 얼마나 나나요?</summary>

**답변(30초)**
생각보다 빨리 나요. 생일 문제 때문에 7자 base62(약 3.5조 공간)라도 약 221만 개만 넣으면 충돌이 한 번 이상 날 확률이 50%예요. 1억 개면 예상 충돌이 약 1,420건이에요. 16진수로 7자를 자르면 공간이 약 2.7억밖에 안 돼서 더 심해요. 실험 예시로 10만 개를 넣었을 때 12~21건이 났어요. 그래서 저장 전 UNIQUE 확인과 소금을 붙인 재해시가 꼭 필요해요.

**꼬리질문**
- Q. 데이터가 많아지면 어떻게 돼요? → 재시도가 늘어 생성이 느려져요. 길이를 늘리거나 ID 방식으로 바꿔요.
</details>

<details>
<summary>Q. 존재하지 않는 코드로 대량 요청이 오면 어떻게 막나요?</summary>

**답변(30초)**
그런 요청은 캐시에 없어서 매번 DB까지 내려가요. 블룸 필터를 앞에 두면 "확실히 없음"인 코드는 DB에 가지 않고 바로 404를 줄 수 있어요. 블룸 필터는 "있음"은 틀릴 수 있지만 "없음"은 항상 맞아요. 추가로 "없음" 결과를 짧게 캐시하고, IP별 요청 수를 제한해요.

**꼬리질문**
- Q. 블룸 필터에서 링크를 지우면요? → 기본형은 삭제가 안 돼요. 만료된 링크는 "아마 있음"으로 나오고 DB에서 만료를 확인해 걸러요.
</details>

## 서술형 연습

<details>
<summary>상황: 마케팅팀이 "캠페인 단축 링크 클릭 수가 실제 방문자보다 적게 잡혀요"라고 해요. 어떻게 원인을 찾고 고칠까요?</summary>

**상황 파악**
원본 사이트 방문 수보다 단축 서버 집계가 적다는 건, 클릭 일부가 **단축 서버를 거치지 않았거나**, 거쳤는데 **기록이 빠졌다**는 뜻이에요. 같은 사람이 여러 번 클릭할수록 차이가 커지는지 먼저 봐요.

**원인 후보**
1. 리다이렉트를 **301**로 주고 있어서, 두 번째 클릭부터 브라우저가 기억해 둔 답으로 바로 원본에 가요. 서버는 그 클릭을 못 봐요.
2. 클릭 이벤트를 큐로 보내는 중에 유실되거나, 집계 작업이 밀려 있어요.
3. 봇 필터가 사람 클릭까지 걸러 내고 있어요.

응답 헤더를 확인해 301이고, 같은 브라우저 재클릭이 서버 로그에 안 찍히면 1번이 원인이에요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 302(또는 307)로 바꾸기 | 매번 서버를 거쳐 정확히 셀 수 있어요 | 서버 트래픽이 늘어요 → 캐시로 흡수해야 해요 |
| B. 301 유지 + `Cache-Control: no-store` 또는 짧은 `max-age` 명시 | 301 의미는 유지하면서 기억 기간을 통제해요 | 헤더를 빠뜨리면 다시 문제, 효과는 302와 비슷해요 |
| C. 원본 페이지 쪽 분석 도구로 보완 | 단축 서버를 안 바꿔도 돼요 | 남의 사이트면 쓸 수 없고, 단축 링크별 구분이 어려워요 |

**내가 고를 방법**
통계가 요구사항이니 **A(302)**로 바꾸고, 늘어나는 읽기는 Redis 캐시로 흡수해요. 단, 이미 301을 기억한 브라우저는 서버가 고칠 방법이 없어요. 사용자가 캐시를 지우기 전까지는 계속 바로 원본으로 가요. 그래서 마케팅팀에 "변경 이후 새로 퍼진 클릭부터 정확해진다"고 알리고, 중요한 캠페인이면 새 코드를 발급해요. 2·3번 원인도 큐 지연·유실 지표로 같이 점검해요.

**채점 포인트**: 301은 캐시 헤더 없이도 브라우저가 기억할 수 있음, 두 번째 클릭이 서버를 안 거침, 302 전환과 부하 증가 트레이드오프, 캐시 헤더로 통제하는 대안, 이미 캐시된 브라우저는 못 고침, 비동기 집계 유실 점검.
</details>

<details>
<summary>상황: 보안팀 제보 — 경쟁사가 단축 코드를 한 글자씩 바꿔 가며 긁어서, 고객의 비공개 문서 링크를 모으고 있대요. 어떻게 대응할까요?</summary>

**상황 파악**
코드가 **순차 ID를 그대로 base62로 바꾼 값**이라서, 내 코드 하나만 알면 앞뒤 코드를 쉽게 추측할 수 있는 상태예요. 비공개 링크가 "코드를 아는 사람만 열 수 있다"에 기대고 있었다면, 코드가 사실상 공개된 셈이에요. 생성 속도로 우리 서비스 규모까지 드러나요.

**원인 후보**
1. 코드가 예측 가능해요(순차 ID). OWASP가 접근 제어 취약점(IDOR)으로 분류하는 유형이에요.
2. 코드 조회에 요청 수 제한이 없어서 대량으로 긁어 갈 수 있어요.
3. 민감한 링크에도 인증 없이 코드만으로 접근돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. ID를 비밀키로 섞은 뒤 인코딩 | 겹치지 않는 성질은 그대로, 바깥에선 순서를 알 수 없어요 | 키 관리가 필요해요, 기존 코드는 그대로 남아요 |
| B. 무작위 코드 + 충돌 재시도 | 추측이 어려워요 | 데이터가 많아지면 충돌 확인 비용이 늘어요 |
| C. 민감 링크는 더 긴 코드 + 접근 인증 | 코드가 새도 열 수 없어요 | 사용이 불편해지고 링크가 길어져요 |
| D. 조회 rate limit, 없는 코드 연속 요청 차단 | 긁어 가는 속도를 늦춰요 | 근본 해결은 아니에요, IP를 바꾸면 우회돼요 |

**내가 고를 방법**
당장은 **D**로 긁기를 늦추고, 새 코드는 **A**로 만들어요. 충돌 없는 ID 방식의 장점을 지키면서 순서만 숨길 수 있어서요. 비공개 문서처럼 민감한 링크는 **C**로 인증을 붙여, 코드가 알려져도 열리지 않게 해요. 이미 노출된 기존 링크는 고객에게 알리고, 재발급하거나 만료시켜요.

**채점 포인트**: 순차 ID의 예측 가능성, 열거(enumeration) 공격, ID 섞기·무작위 코드, 코드만으로 보안에 기대지 않기(인증), rate limit, 기존 노출 링크 처리, 규모 노출.
</details>

<details>
<summary>상황: 같은 긴 URL을 여러 번 줄이면 같은 코드를 줘야 할까요, 다른 코드를 줘야 할까요?</summary>

**상황 파악**
정답이 정해진 문제가 아니라 **요구사항에 따라 갈리는** 문제예요. 먼저 "통계를 누구 기준으로 보나요?", "만료나 별칭을 사람마다 다르게 줄 수 있나요?"를 물어요.

**원인 후보(판단 기준)**
1. 저장 공간: 같은 URL이 많이 중복되면 합치는 게 아껴요.
2. 통계: A팀과 B팀이 같은 URL로 각자 캠페인을 돌리면, 코드가 같을 때 클릭이 섞여요.
3. 만료·소유자: 한 사람이 링크를 만료시키면, 같은 코드를 공유하는 다른 사람 링크도 죽어요.
4. 개인정보: 같은 코드를 돌려주면 "누가 이미 이 URL을 줄였다"는 사실이 드러날 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 항상 같은 코드(해시 방식 또는 원본 URL로 먼저 조회) | 저장이 줄고 중복이 없어요 | 통계·만료·소유자가 섞여요, 원본 URL 인덱스가 필요해요 |
| B. 항상 다른 코드(ID 방식 기본 동작) | 사용자·캠페인별로 따로 관리돼요 | 같은 URL이 여러 번 저장돼요 |
| C. 같은 사용자가 같은 URL을 줄일 때만 같은 코드 | 한 사람 안에선 중복을 막고, 사람끼리는 분리돼요 | (사용자, 원본 URL) 조회용 인덱스가 필요해요 |

**내가 고를 방법**
이 설계엔 통계·만료·커스텀 별칭 요구사항이 있으니 **사람끼리는 코드를 나눠야** 해요. 그래서 **C**를 골라요. 레코드가 500B라 중복 저장 비용은 크지 않아서, 통계와 만료가 섞이는 문제보다 덜 아파요. 통계가 없는 단순 서비스라면 A도 괜찮다고 덧붙여요.

**채점 포인트**: 요구사항 먼저 확인, 통계·만료·소유자 분리, 저장 비용과 비교, 해시 방식은 자연히 같은 코드·ID 방식은 다른 코드, 원본 URL 인덱스, 정보 노출 고려.
</details>

## 필기 포인트

- base62 = 0-9, a-z, A-Z 62글자. 62^6 ≈ 568억, 62^7 ≈ 3.5조.
- 301 Moved Permanently(영구, 캐시 헤더 없이도 캐시 가능) / 302 Found(임시, 명시 헤더 있을 때만 캐시).
- 307 = 302 + 메서드 변경 금지, 308 = 301 + 메서드 변경 금지.
- 410 Gone = 의도적으로 영구 제거됨.
- 블룸 필터: 거짓 양성 있음, 거짓 음성 없음, 기본형은 삭제 불가.
- 생일 문제: 공간 M에서 충돌 확률 50% 지점은 대략 √(2·ln2·M).
