:::tip[한 줄 요약]
뉴스피드는 **글을 쓸 때 팔로워 피드에 미리 넣어 두는 push(팬아웃 온 라이트)**와 **피드를 열 때 팔로우한 사람들 글을 모아 오는 pull(팬아웃 온 리드)** 중 무엇을 고르냐의 문제예요. 실제로는 대부분 push로 하고, 팔로워가 아주 많은 계정만 pull로 섞는 **하이브리드**를 써요.
:::

:::note[처음이라면 여기까지]
① 피드를 만드는 방법은 두 가지예요. 글 쓸 때 미리 나눠 주거나(push), 볼 때 모아 오거나(pull).

② 읽기가 쓰기보다 훨씬 많아서 보통 push가 유리해요. 그런데 팔로워 1,000만 명인 연예인이 글 하나 쓰면 1,000만 번을 써야 해서, 그런 계정만 pull로 돌려요(하이브리드).

③ 피드 캐시에는 글 본문이 아니라 **글 ID만**, 사용자당 **최근 몇백 개만** 넣어요.

④ 스크롤 페이지는 "몇 번째부터"(오프셋)가 아니라 "마지막으로 본 글 다음부터"(커서)로 받아야 같은 글이 두 번 안 나와요.

⑤ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

신문을 독자에게 전하는 방법은 두 가지예요.

하나는 **새벽 배달**이에요. 신문이 나오면 배달원이 구독자 집집마다 미리 넣어 둬요. 독자는 아침에 문 앞에서 집어 들기만 하면 되니 아주 빨라요. 대신 구독자가 1,000만 명이면 1,000만 집을 다 돌아야 하고, 이사 가서 아무도 안 읽는 집에도 계속 넣게 돼요.

다른 하나는 **가판대**예요. 신문사는 가판대에 한 부씩만 놓아요. 독자가 가판대에 가서 자기가 보는 신문 열 종류를 직접 골라 와야 해요. 신문사는 편하지만, 독자는 매번 여러 곳을 돌아야 해서 느려요.

뉴스피드도 똑같아요. 새벽 배달이 **push**, 가판대가 **pull**이에요. 보통 사람 글은 새벽 배달로, 구독자가 엄청 많은 유명 신문만 가판대에 두면 둘의 장점을 섞을 수 있어요. 이게 **하이브리드**예요.

단, 실제 피드 캐시에는 신문 전체(글 본문)가 아니라 "몇 번 기사"라는 **번호표(글 ID)**만 넣어요. 본문은 읽을 때 번호로 찾아와요.

## 제대로 알기

이 페이지는 [시스템 설계 면접 푸는 법](../design-approach/)의 뼈대(요구사항 → 규모 추정 → API → 데이터 모델 → 상위 설계 → 심화 → 병목)를 따라가요. 예제는 "SNS 홈 피드"예요.

### 1. 요구사항

**기능**(무엇을 하나)

- 글을 쓴다(텍스트, 이미지 첨부 가능).
- 홈 피드를 연다. 내가 팔로우한 사람들의 글이 **최신순**으로 보인다.
- 아래로 스크롤하면 더 오래된 글이 이어서 나온다(무한 스크롤).

**비기능**(얼마나 많이·빨리)

- 피드 열기는 빨라야 해요(사람이 기다린다고 느끼지 않을 정도).
- 새 글이 팔로워 피드에 뜨기까지는 **몇 초 늦어도 괜찮아요**. 은행 잔고처럼 즉시 정확할 필요는 없어요. 이 "조금 늦어도 된다"가 설계를 크게 쉽게 해 줘요.
- 읽기가 쓰기보다 훨씬 많아요.

범위 밖으로 두는 것: 좋아요·댓글, 추천(랭킹) 피드. 랭킹은 마지막에 개요만 볼게요.

### 2. 실제 규모 감 잡기: 트위터 2012년 사례

트위터가 2012년 11월 발표에서 공개한 수치를 『데이터 중심 애플리케이션 설계』가 정리해 두었어요.

| 동작 | 초당 처리량(2012년 11월 기준) |
|---|---|
| 트윗 쓰기 | 평균 약 4.6k, 피크 12k 이상 |
| 홈 타임라인 읽기 | 약 300k |

같은 발표를 요약한 다른 글은 쓰기 평균을 약 5k/초로 적는 등 출처마다 숫자가 조금 달라요. 그래서 "언제, 어느 출처 기준"인지 붙여 말하는 게 안전해요.

숫자가 말해 주는 건 두 가지예요.

- 초당 쓰기 1만 건 정도는 그 자체로는 어려운 숫자가 아니에요. 진짜 문제는 글 하나를 **팔로워 수만큼 퍼뜨려야 한다**는 거예요. 이걸 **팬아웃**(fan-out, 요청 하나를 처리하려고 다른 곳에 보내야 하는 요청 수)이라고 해요.
- 읽기가 쓰기보다 수십 배 많아요. 그러면 "쓸 때 일을 더 하고 읽을 때 덜 하는" 쪽이 이득이에요.

### 3. 규모 추정: 우리 SNS

**가정**(면접에서 먼저 말할 것): 하루 사용자(DAU) 1,000만 명, 1인당 하루 글 2개, 피드 열기 하루 10번, **평균 팔로워 100명**, 피크 계수 3.

| 항목 | 계산 | 결과 |
|---|---|---|
| 글 쓰기 QPS | 2×10^7 ÷ 86,400 | 약 231 |
| 피드 읽기 QPS | 10^8 ÷ 86,400 | 약 1,157 (피크 약 3,500) |
| push일 때 피드 캐시 쓰기 | 231 × 100명 | 초당 약 23,000건 |
| 피드 캐시 크기 | 10^7명 × 800개 × 20바이트 | 약 160GB (복제 3벌이면 약 480GB) |

항목 하나를 20바이트로 잡은 건 트위터 사례처럼 **글 ID 8바이트 + 작성자 ID 8바이트 + 플래그 4바이트**만 넣는다고 가정했기 때문이에요. Redis 자료구조 자체의 오버헤드는 뺐어요(예시 계산).

**숫자가 말해 주는 것**

- 글 쓰기 231건이 push를 하면 피드 쓰기 2만 건이 돼요. 쓰기가 100배로 불어나요. 이게 팬아웃 비용이에요.
- 피드 캐시는 ID만 넣으면 수백 GB라 메모리에 들어가요. 본문까지 넣으면 몇 배로 커지고, 글을 고칠 때 수백만 복사본을 다 고쳐야 해요.

### 4. API

```text
POST /posts                         # 글 쓰기 → { postId }
GET  /feed?limit=20                 # 첫 페이지
GET  /feed?limit=20&cursor=abc123   # 다음 페이지(마지막으로 본 위치)
GET  /feed/new?since=xyz789         # 맨 위 이후 새 글 ("새 게시물 3개" 배너)
```

`cursor`는 "마지막으로 본 글이 어디였나"를 담은 값이에요. 7절에서 자세히 봐요.

### 5. 데이터 모델

| 저장소 | 무엇을 | 어디에 |
|---|---|---|
| 글 | 글 ID, 작성자, 본문, 작성 시각 | DB(원본) + 글 캐시 |
| 팔로우 관계 | (팔로워, 팔로잉) 쌍 | DB, 자주 읽으면 캐시 |
| 피드 캐시 | 사용자별 **글 ID 목록**, 최근 N개 | Redis |
| 이미지 | 파일 | 객체 저장소 + CDN |

글 ID는 여러 서버에서 겹치지 않고 **시간순으로 커지는** 값(Snowflake 같은 ID)이면 정렬과 커서가 쉬워져요. → [분산 시간과 ID](../../distributed/distributed-time-ids/)

### 6. 핵심 선택: push vs pull vs 하이브리드

**pull**(팬아웃 온 리드, fan-out on read): 글은 글 테이블에 한 번만 넣어요. 피드를 열 때 "내가 팔로우하는 사람들의 최근 글"을 찾아 시간순으로 합쳐요. DB라면 글·사용자·팔로우 테이블을 조인하는 쿼리 하나예요.

**push**(팬아웃 온 라이트, fan-out on write): 사용자마다 "우편함" 같은 피드 캐시를 둬요. 글이 올라오면 작성자의 팔로워를 전부 찾아 각자의 우편함에 글 ID를 넣어요. 피드를 열 때는 내 우편함만 읽으면 돼요.

트위터도 처음엔 pull로 시작했는데, 읽기 부하를 못 버텨 push로 옮겼어요.

| | push (쓸 때 퍼뜨리기) | pull (읽을 때 모으기) | 하이브리드 |
|---|---|---|---|
| 쓰기 비용 | 팔로워 수만큼 (비쌈) | 글 1번 저장 (쌈) | 일반인만 팔로워 수만큼 |
| 읽기 비용 | 내 캐시 1번 (쌈) | 팔로잉 수만큼 모아 합치기 (비쌈) | 내 캐시 + 팔로우한 셀럽 몇 명 |
| 새 글 반영 | 팬아웃이 끝나야 보임(지연 가능) | 바로 보임 | 셀럽 글은 바로, 일반 글은 팬아웃 후 |
| 약점 | 셀럽 글 1개 = 쓰기 수백만 건, 안 읽는 사람 피드도 채움 | 피드 열 때마다 무거운 조회 | 두 경로를 다 만들고 합쳐야 해서 복잡 |
| 어울리는 곳 | 읽기가 많고 팔로워 수가 고른 서비스 | 사용자가 적거나 쓰기가 많은 서비스 | 팔로워 수 차이가 극단적인 SNS |

**셀럽 문제**

트위터 사례에서 트윗 하나는 평균 약 75명에게 전달됐어요. 그래서 초당 4.6k 트윗이 피드 캐시 쓰기 초당 약 345k건이 됐어요. 평균만 보면 괜찮아 보여요. 그런데 팔로워가 3천만 명이 넘는 계정은 트윗 **하나**가 쓰기 3천만 건이에요. 트위터의 목표는 "5초 안에 팔로워에게 전달"이었는데, 이런 계정 때문에 지키기 어려웠어요.

그래서 이 시스템의 부하를 정하는 건 평균 팔로워 수가 아니라 **팔로워 수 분포**, 특히 꼬리 쪽 소수예요. 트위터가 찾은 답은 하이브리드였어요. 대부분의 글은 계속 push하고, 팔로워가 아주 많은 소수는 팬아웃에서 빼서, 피드를 열 때 따로 가져와 합쳐요.

<Aside type="note" title="예시 계산: 셀럽 0.025%가 쓰기의 1/3">
사용자 100만 명, 팔로워 수가 한쪽으로 크게 치우친 분포(평균 40명, 중앙값 5명)를 가정하고 모델로 계산해 봤어요. 실제 서비스 측정이 아니라 가정에 따른 값이에요.

- 팔로워 1만 명 초과를 셀럽으로 치면 246명, 전체의 **0.025%**뿐이에요.
- 그런데 이 246명 몫이 push 팬아웃 쓰기 전체의 **약 1/3**이에요(4,000만 → 2,700만).
- 대신 읽기는 "내 피드 + 내가 팔로우한 셀럽 목록"만 추가돼서, 순수 pull(약 4억)보다 훨씬 적은 약 1.4억이에요.

숫자보다 결론이 중요해요. **평균은 40이어도, 아주 적은 꼬리가 비용을 지배해요.**
</Aside>

### 7. 피드 캐시: 무엇을, 얼마나

- **ID만 넣어요.** 트위터는 항목마다 트윗 ID, 작성자 ID, 4바이트 플래그(리트윗·답글 여부 등)만 넣었어요. 본문은 읽을 때 ID로 글 캐시에서 채워요. 이걸 **하이드레이션**(hydration, ID에 실제 내용을 채워 넣기)이라고 해요.
- **사용자당 최근 N개만 넣어요.** 트위터는 사용자당 최대 800개였어요. 피드 캐시는 영구 저장소가 아니라 캐시예요. 원본은 글 DB에 있으니 날아가면 다시 만들면 돼요.
- **활성 사용자만 넣어요.** 트위터는 최근 30일 안에 로그인한 사용자의 피드만 메모리에 뒀어요. 캐시가 없는 사용자가 오면 팔로잉 목록으로 피드를 다시 만들어 채워요(이때는 pull처럼 동작).

Redis에서는 두 가지 자료구조를 흔히 써요. 자료구조 기초는 [Redis 자료구조](../../redis/data-structures/)에 있어요.

| | 리스트 | Sorted Set |
|---|---|---|
| 넣기 | `LPUSH feed:{uid} postId` | `ZADD feed:{uid} score postId` |
| N개 상한 | `LTRIM feed:{uid} 0 799` | `ZREMRANGEBYRANK feed:{uid} 0 -801` |
| 정렬 기준 | 넣은 순서 | score(시간 등) |
| 장점 | 단순, 빠름 | 늦게 온 글·셀럽 글 병합이 쉬움, 중복 자동 제거, 개별 삭제(`ZREM`) 쉬움 |
| 약점 | "넣은 순서 = 시간순"이어야 함, 중간 삭제가 불편 | 메모리를 조금 더 씀 |

리스트는 `LPUSH`로 앞에 넣고 바로 `LTRIM`으로 뒤를 잘라요. 보통 맨 뒤 1개만 지워지니 거의 상수 시간이에요.

### 8. 페이지네이션: 오프셋 vs 커서

**오프셋**(offset)은 "앞에서 몇 개 건너뛰고 20개"예요. **커서**(cursor, 여기서는 "마지막으로 본 위치를 담은 값")는 "마지막으로 본 글보다 오래된 것 20개"예요. DB 세션의 커서 객체와는 다른 말이에요.

```sql
-- 오프셋: 앞의 40개를 읽고 버린 뒤 20개
SELECT * FROM feed WHERE user_id = ? ORDER BY created_at DESC, id DESC LIMIT 40, 20;

-- 커서: 마지막으로 본 (시각, id) 바로 다음부터 20개
SELECT * FROM feed WHERE user_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC LIMIT 20;
```

오프셋이 피드에 안 맞는 이유는 두 가지예요.

**① 느려요.** 오프셋은 앞의 행을 실제로 읽고 버려요. 이 위키의 MySQL 실측(100만 행)에서 깊은 오프셋은 약 86~99ms에 90만 행을 읽었고, 커서는 약 0.6ms에 20행만 읽었어요. 자세한 실측은 [커넥션 풀과 쿼리 튜닝 6절](../../db/connection-pool-query/)에 있어요.

**② 새 글이 끼어들면 중복·누락이 생겨요.** 피드는 맨 위에 계속 새 글이 들어와요.

- 1페이지로 글 10, 9, 8을 봤어요(숫자가 클수록 최신, 페이지 크기 3).
- 그사이 새 글 11, 12가 맨 위에 들어왔어요.
- 오프셋 2페이지("3개 건너뛰고 3개")는 이제 9, 8, 7이에요. **9와 8이 또 나와요.**
- 반대로 위쪽 글이 삭제되면 한 칸씩 당겨져서 **못 보고 지나가는 글**이 생겨요.
- 커서 2페이지(`id < 8`)는 7, 6, 5예요. 위에 무엇이 들어와도 흔들리지 않아요. 새 글 11, 12는 "새 게시물 2개" 배너로 따로 받아요(`id > 10`).

<OffsetCursorInsert />

정렬 키는 **유일**해야 해요. `created_at`만 쓰면 같은 시각에 쓴 글이 페이지 경계에서 빠지거나 겹칠 수 있어요. 그래서 `(created_at, id)`처럼 유일한 값을 덧붙이고, 그 순서대로 정렬하는 복합 인덱스 `(user_id, created_at, id)`를 둬요. → [복합 인덱스](../../db/composite-index/)

커서의 단점은 "37페이지로 바로 가기"가 안 된다는 거예요. 피드처럼 무한 스크롤이나 "더보기" 화면엔 문제가 안 돼요. 커서 값은 보통 `(created_at, id)`를 인코딩한 알아보기 힘든 문자열(불투명 토큰)로 클라이언트에 줘요.

### 9. 상위 설계

```text
[쓰기]
클라이언트 → 글 API → 글 DB 저장(글 ID 발급)
                  └→ 메시지 큐에 "글 생성" 이벤트
                        └→ 팬아웃 워커: 팔로워 목록을 페이지 단위로 읽어
                           각 피드 캐시에 ID 추가 + 상한 자르기 (묶어서 한 번에)
                           ※ 셀럽이면 팬아웃 생략

[읽기]
클라이언트 → 피드 API → 피드 캐시에서 ID 20개
                     + 내가 팔로우한 셀럽들의 최근 글 ID (하이브리드)
                     → 합쳐서 정렬 → 글·사용자 캐시로 본문 채움 → 응답
```

팬아웃을 글 API 안에서 바로 하지 않고 **메시지 큐**로 넘기는 이유는, 글쓴이가 팔로워 수만큼 기다리지 않게 하고 몰림을 큐가 흡수하게 하려는 거예요. → [메시지 큐와 Kafka](../../distributed/message-queue-kafka/)

### 10. 병목과 트레이드오프

| 병목 | 대응 | 대가 |
|---|---|---|
| 셀럽 글 팬아웃 폭주 | 셀럽은 팬아웃 제외, 읽을 때 병합 | 읽기 경로가 복잡해지고 조금 느려짐 |
| 피드 캐시 메모리 | ID만, 최근 N개, 활성 사용자만 | 오래된 글·휴면 사용자는 느린 경로(재구성) |
| 팬아웃 큐 적체 | 워커 수평 확장, 활성 사용자 먼저 팬아웃 | 일부 팔로워는 늦게 받음 |
| 삭제·차단 반영 | 하이드레이션 때 삭제·차단 걸러냄, 캐시는 비동기로 정리 | 잠깐 캐시에 ID가 남아 있음 |

### 심화: 트위터 발표의 더 자세한 수치 (2차 출처)

아래는 트위터 2012년 발표를 요약한 High Scalability 글에 나온 내용이에요. 공식 문서가 아닌 요약 글이라 참고용으로만 봐요.

- 홈 타임라인은 Redis 클러스터에 두고, 각 타임라인을 다른 머신 3대에 복제했어요.
- 팔로워 100만 명 팬아웃이 중간값(p50) 3.5초, 느린 쪽(p99)은 최대 5분까지 걸렸어요. 큰 팬아웃은 5초 목표를 가끔 못 지켰다는 뜻이에요.
- 팔로워가 아주 많은 계정은 팬아웃을 그만두고 읽을 때 합치는 쪽으로 옮기는 중이며, 이걸로 계산 자원을 수십 % 아낀다고 했어요.
- 리트윗은 원본 글을 가리키는 포인터로 저장했어요.

### 심화: Redis Sorted Set으로 커서 페이징

Sorted Set도 오프셋처럼 쓰면 똑같이 느려져요. `ZRANGE`의 `LIMIT offset count`는 offset이 크면 그만큼 훑어야 해서, Redis 공식 문서도 O(N)까지 늘어날 수 있다고 경고해요. 그래서 **score 기준 커서**를 써요.

```text
# 마지막으로 본 score(1700000000123) 미만의 최신 20개
ZRANGE feed:{uid} (1700000000123 -inf BYSCORE REV LIMIT 0 20
```

- `(`를 붙이면 그 값은 빼는 열린 구간이에요.
- `REV`와 `BYSCORE`를 같이 쓰면 큰 값부터 작은 값 순으로 적어요.
- `BYSCORE`·`REV`·`LIMIT` 옵션은 Redis 6.2.0부터예요. 그 전에는 `ZREVRANGEBYSCORE` 같은 별도 명령을 썼어요.
- score가 같으면 member(글 ID) 사전순으로 정렬돼요.

<Aside type="caution" title="score에 64비트 ID를 통째로 넣으면 (일반지식)">
Redis score는 배정밀도 부동소수점(double)이라 정수는 약 2^53까지만 정확해요. 64비트 Snowflake ID 전체를 score로 넣으면 끝자리가 뭉개져 순서가 틀어질 수 있어요. 보통은 score에 밀리초 시각을 넣고 member에 글 ID를 넣어요. 같은 밀리초 글이 경계에 걸리는 경우는 그 score를 포함해 가져온 뒤 이미 본 ID를 빼는 식으로 처리해요. 이 부분은 이번에 공식 문서로 다시 확인하지 못한 일반지식이에요.
</Aside>

### 심화: 셀럽 기준은 어떻게 정하나

정답 숫자는 없어요. 기준을 **낮추면**(셀럽이 많아지면) 팬아웃 쓰기는 줄지만, 사람들이 피드를 열 때 합칠 셀럽이 많아져 읽기가 늘어요. 기준을 **올리면** 반대예요. 위 예시 계산에서 기준을 1만 명에서 10만 명으로 올리면 셀럽은 29명으로 줄고, 쓰기는 약 3,240만으로 늘고, 읽기는 약 8,600만으로 줄었어요. 실제로는 팔로워 분포와 팬아웃 지연 지표를 보며 정해요.

### 심화: 랭킹 피드로 바뀌면 (개요)

최신순이 아니라 "추천순" 피드(X의 For You 등)는 보통 단계형으로 만들어요. X가 공개한 저장소(the-algorithm) README 기준으로 보면 이래요.

1. **후보 모으기**: 팔로우한 사람 글(in-network)과 팔로우 안 한 사람 글(out-of-network)을 모아요. README에 따르면 후보의 약 절반이 팔로우한 사람 쪽에서 와요.
2. **랭킹**: 가벼운 모델로 먼저 거르고, 무거운 신경망 모델로 최종 점수를 매겨요.
3. **필터·섞기**: 차단·뮤트, 품질·법적 필터를 거치고 광고·추천 계정을 섞어요.

설계 관점에선 피드 캐시에 "최종 순서"보다 **후보 ID 목록**을 두고, 읽을 때 점수를 매기는 경우가 많아요. 이때 커서는 시간이 아니라 "이번 세션에서 이미 보여 준 글/페이지 토큰"이 돼요(일반지식). 면접에선 이 정도 개요면 충분해요.

### 심화: 자주 하는 오해

- **"push가 항상 낫다"** → 읽기가 많고 팔로워 수가 고를 때만이에요. 셀럽과 휴면 사용자에선 낭비가 커요.
- **"pull은 구식이다"** → 셀럽 글 병합, 휴면 사용자 피드 재구성, 캐시가 날아갔을 때 복구에 여전히 써요.
- **"Redis `LIMIT`이면 오프셋도 괜찮다"** → Redis도 큰 offset은 느려요. score 기준 커서를 써요.
- **"트위터는 초당 30만 읽기"** → 2012년 발표 기준이에요. 연도 없이 말하지 않아요.

<details>
<summary>Q. 뉴스피드를 어떻게 만들겠어요? push와 pull의 차이는 뭔가요?</summary>

**답변(30초)**
피드를 만드는 방법은 두 가지예요. push는 글을 쓸 때 팔로워 전원의 피드 캐시에 글 ID를 미리 넣어 두는 방식이라 읽기가 빠르고 쓰기가 비싸요. pull은 피드를 열 때 팔로우한 사람들의 최근 글을 모아 합치는 방식이라 쓰기는 싸고 읽기가 비싸요. SNS는 읽기가 쓰기보다 훨씬 많아서 기본은 push로 하고, 팔로워가 아주 많은 계정만 pull로 섞는 하이브리드를 고를게요.

**꼬리질문**
- Q. 트위터는 어떻게 했나요? → 처음엔 pull이었는데 읽기 부하 때문에 push로 옮겼고, 이후 셀럽만 빼는 하이브리드로 갔어요.
- Q. pull이 나은 경우는요? → 사용자가 적거나 쓰기가 읽기보다 많을 때, 그리고 셀럽 글이나 휴면 사용자 피드처럼 미리 만들어 둘 가치가 없을 때예요.
</details>

<summary>Q. 피드 캐시에는 무엇을, 얼마나 저장하나요?</summary>

**답변(30초)**
글 본문이 아니라 글 ID와 작성자 ID 정도만, 사용자당 최근 몇백 개만 저장해요. 트위터는 사용자당 800개였어요. 본문을 넣으면 메모리가 몇 배로 들고, 글을 고치거나 지울 때 수백만 복사본을 고쳐야 해요. 본문은 읽을 때 ID로 글 캐시에서 채워요. 그리고 최근 활성 사용자만 캐시에 두고, 나머지는 필요할 때 다시 만들어요.

**꼬리질문**
- Q. Redis 자료구조는요? → 리스트라면 `LPUSH` 뒤 `LTRIM`으로 상한을 지키고, 순서 병합·중복 제거·개별 삭제가 필요하면 Sorted Set을 써요.
- Q. 800개보다 오래된 글은요? → 캐시가 아니라 DB에서 pull로 읽어요. 그렇게 깊이 스크롤하는 사람은 드물어요.
</details>

<details>
<summary>Q. 피드 페이지네이션은 오프셋으로 하나요, 커서로 하나요?</summary>

**답변(30초)**
커서로 해요. 이유는 두 가지예요. 오프셋은 앞의 행을 읽고 버려서 깊은 페이지일수록 느려요. 그리고 피드는 맨 위에 새 글이 계속 들어오는데, 오프셋은 위치가 밀려서 같은 글이 두 번 나오거나 빠져요. 커서는 "마지막으로 본 (시각, id)보다 오래된 것"을 가져오니 깊이와 무관하게 빠르고, 새 글이 들어와도 흔들리지 않아요.

**꼬리질문**
- Q. 커서 단점은요? → 특정 페이지로 바로 점프할 수 없어요. 무한 스크롤엔 문제가 없어요.
- Q. 커서에 created_at만 넣으면요? → 같은 시각 글이 경계에서 겹치거나 빠져요. id를 붙여 유일하게 만들어요.
</details>

<details>
<summary>Q. push 방식에서 팔로워가 아주 많은 계정은 어떻게 처리하나요?</summary>

**답변(30초)**
팔로워 1,000만 명 계정이 글 하나를 쓰면 피드 쓰기가 1,000만 건이라 팬아웃 큐가 밀리고 반영이 늦어져요. 그래서 팔로워 수가 기준을 넘는 계정은 팬아웃에서 빼요. 대신 사용자가 피드를 열 때 내 피드 캐시와 내가 팔로우한 셀럽들의 최근 글을 합쳐 정렬해요. 셀럽은 아주 소수라 읽기 쪽 추가 비용은 작고, 쓰기 폭주는 사라져요.

**꼬리질문**
- Q. 셀럽이 소수인데 그렇게 중요해요? → 예시 계산에서 상위 0.025%가 팬아웃 쓰기의 약 1/3을 차지했어요. 평균이 아니라 꼬리가 비용을 정해요.
- Q. 기준은 어떻게 정해요? → 낮추면 쓰기가 줄고 읽기가 늘어요. 팔로워 분포와 팬아웃 지연 지표를 보며 정해요.
</details>

<details>
<summary>Q. 무한 스크롤 중에 새 글이 올라오면 어떻게 처리하나요?</summary>

**답변(30초)**
아래 방향(더 오래된 글)과 위 방향(새 글)을 따로 다뤄요. 스크롤은 "마지막으로 본 글보다 오래된 것" 커서로 받아서, 위에 새 글이 들어와도 중복이 생기지 않아요. 새 글은 "맨 위 글보다 새로운 것"을 따로 물어서 "새 게시물 3개" 배너로 보여 주고, 사용자가 누르면 위에 붙여요. 오프셋으로 받으면 새 글 수만큼 밀려서 방금 본 글이 또 나와요.

**꼬리질문**
- Q. 글이 삭제되면요? → 오프셋은 한 칸 당겨져서 글 하나를 건너뛰어요. 커서는 기준이 값이라 영향이 없어요.
</details>

<details>
<summary>Q. 피드 캐시(Redis)가 통째로 날아가면 어떻게 되나요?</summary>

**답변(30초)**
피드 캐시는 원본이 아니라 캐시라서 데이터가 사라지진 않아요. 원본은 글 DB와 팔로우 관계에 있어요. 캐시가 없는 사용자가 오면 팔로잉 목록으로 최근 글을 모아 피드를 다시 만들고 캐시에 채워요. 즉 그 순간만 pull로 동작해요. 다만 모두가 동시에 재구성하면 DB가 몰리니 복제를 두고, 재구성은 활성 사용자부터 천천히 해요.

**꼬리질문**
- Q. 휴면 사용자 피드는 왜 안 채워요? → 안 읽을 피드를 채우는 건 메모리와 쓰기 낭비예요. 돌아오면 그때 만들어요.
- Q. 동시 재구성 몰림은요? → [캐시 문제](../../redis/cache-problems/)의 스탬피드 대응(락, 요청 합치기)과 같은 방법을 써요.
</details>

<details>
<summary>Q. 랭킹(추천) 피드로 바꾸면 설계가 어떻게 달라지나요?</summary>

**답변(30초)**
최신순은 시간으로 정렬하면 끝이지만, 랭킹 피드는 후보 모으기, 점수 매기기, 필터·섞기 단계가 생겨요. 피드 캐시에는 최종 순서보다 후보 ID를 두고 읽을 때 점수를 매기는 경우가 많아요. 그래서 커서도 시간 대신 "이미 보여 준 글"이나 페이지 토큰이 돼요. X가 공개한 저장소도 이런 단계형 구조를 설명해요.

**꼬리질문**
- Q. 후보는 어디서 오나요? → 팔로우한 사람 글과 팔로우하지 않은 사람 글 두 곳이에요. README 기준 약 절반이 팔로우한 쪽이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 팔로워 1,000만 명인 연예인이 글을 올리면, 일부 팔로워 피드에는 수 분이 지나서야 보인다는 불만이 들어와요. 원인과 해결책을 서술하세요.</summary>

**상황 파악**
글 자체는 저장됐는데 "팔로워 피드에 뜨기까지"가 늦어요. 피드 반영은 팬아웃 경로라서, 이 계정의 글이 팬아웃 큐에서 어떻게 처리되는지 봐야 해요. 다른 일반 사용자 글도 같이 늦어지는지도 확인해요.

**원인 후보**
1. 글 하나가 피드 쓰기 1,000만 건이 돼서 팬아웃 큐가 적체됨. 워커가 초당 10만 건을 쓴다고 가정해도 약 100초가 걸려요(예시 계산).
2. 같은 큐를 쓰는 일반 사용자 팬아웃까지 그 뒤에 밀림.
3. 팔로워 중 상당수가 휴면 사용자인데도 똑같이 팬아웃하고 있음.
4. 워커가 팔로워마다 한 건씩 따로 써서 왕복이 많음(묶어 쓰기를 안 함).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 하이브리드: 팔로워 기준 이상은 팬아웃 제외, 읽을 때 병합 | 쓰기 폭주가 근본적으로 사라지고, 셀럽 글은 즉시 보여요 | 피드 읽기 경로에 병합 로직이 생기고 조금 느려져요 |
| B. 워커 증설 + 묶어 쓰기(파이프라인) | 구조 변경 없이 처리량이 늘어요 | 팔로워가 더 늘면 다시 밀려요, 비용이 계속 커져요 |
| C. 셀럽 전용 큐를 분리하고 활성 사용자부터 팬아웃 | 일반 사용자 글이 셀럽 때문에 밀리지 않고, 실제 볼 사람이 먼저 받아요 | 휴면 팔로워는 더 늦게 받아요, 큐 운영이 늘어요 |

**내가 고를 방법**
A를 기본으로 해요. 팔로워 수 분포를 보면 아주 적은 계정이 쓰기의 큰 몫을 차지하니, 그 꼬리만 잘라도 효과가 커요. 셀럽 수는 적어서 읽을 때 합치는 비용이 작아요. 전환 전까지는 C로 셀럽 팬아웃을 별도 큐로 떼어 일반 사용자 지연부터 막고, B의 묶어 쓰기는 어느 방식이든 같이 적용해요. 셀럽 기준은 팬아웃 지연(p99)과 피드 읽기 지연을 함께 보며 조정해요.

**채점 포인트**: 팬아웃 비용 = 팔로워 수, 평균이 아닌 분포 꼬리, 하이브리드(셀럽 pull 병합), 큐 분리·우선순위, 활성 사용자 우선, 묶어 쓰기, 쓰기↔읽기 트레이드오프, 지연 지표(p99)로 기준 조정.
</details>

<details>
<summary>상황: 앱에서 피드를 아래로 스크롤하다 보면 방금 본 글이 또 나온다는 버그 리포트가 들어와요. 원인과 해결책을 서술하세요.</summary>

**상황 파악**
언제 재현되는지부터 봐요. 사용 중 새 글이 많이 올라오는 시간대나, 팔로잉이 많은 사용자에게 자주 나온다면 페이지 경계 문제일 가능성이 커요. 서버가 다음 페이지를 어떤 기준으로 주는지 확인해요.

**원인 후보**
1. 오프셋 페이징: 1페이지를 본 뒤 맨 위에 새 글 N개가 들어오면, 2페이지가 N칸 밀려 1페이지 끝 N개가 다시 나와요. 삭제가 있으면 반대로 글이 빠져요.
2. 커서를 쓰지만 `created_at`만 기준이라, 같은 시각 글이 경계에서 겹침.
3. 하이브리드에서 셀럽 글을 합칠 때, 같은 글이 피드 캐시와 셀럽 목록 양쪽에서 와 중복됨.
4. 클라이언트 재시도로 같은 페이지를 두 번 붙임.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 커서 페이징 `(created_at, id)` + 복합 인덱스 | 새 글·삭제와 무관하게 안정적이고, 깊어도 빨라요 | 특정 페이지로 점프 불가, API와 앱을 같이 바꿔야 해요 |
| B. 오프셋 유지 + 클라이언트에서 이미 본 ID 걸러내기 | 서버 변경이 작아요 | 중복은 숨겨도 누락은 못 막고, 깊은 페이지 느림도 그대로예요 |
| C. 첫 요청 시점 스냅샷을 고정해 그 안에서만 페이지 | 세션 동안 목록이 완전히 고정돼요 | 스냅샷 저장 비용이 들고, 새 글을 보려면 새로고침해야 해요 |

**내가 고를 방법**
A로 바꿔요. 피드는 무한 스크롤이라 페이지 점프가 필요 없고, 중복·누락·느림을 한 번에 해결해요. 새 글은 "맨 위 글보다 새로운 것"을 따로 물어 배너로 보여 줘요. 하이브리드 병합 단계에서는 글 ID로 중복을 제거해요. 앱 업데이트가 퍼지는 동안은 B를 임시로 같이 둬요.

**채점 포인트**: 오프셋이 위치 기준이라 삽입·삭제에 밀림, 중복과 누락 둘 다, 커서(키셋) 페이징, 정렬 키 유일성(id 덧붙이기), 복합 인덱스, 새 글은 위 방향 별도 요청, 병합 시 ID 중복 제거, 페이지 점프 불가 트레이드오프.
</details>

<details>
<summary>상황: 가입자는 1억 명인데 대부분이 휴면이에요. 그런데도 모든 사용자 피드를 push로 채우다 보니 Redis 메모리가 부족해졌어요. 어떻게 해결할까요?</summary>

**상황 파악**
메모리를 누가 쓰는지부터 나눠요. 사용자 수 × 사용자당 항목 수 × 항목 크기로 따져요. 예를 들어 1억 명 × 800개 × 20바이트면 ID만 넣어도 약 1.6TB인데, 하루 사용자가 1,000만 명이면 그중 90%는 아무도 안 보는 피드예요(예시 계산, Redis 오버헤드 제외).

**원인 후보**
1. 휴면 사용자 피드까지 팬아웃으로 계속 채움.
2. 사용자당 상한(N)이 없거나 너무 큼.
3. 항목에 글 본문까지 넣어 항목이 큼.
4. 만료(TTL)가 없어 한 번 만든 피드가 영원히 남음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 활성 사용자(예: 최근 30일 로그인)만 캐시, 돌아오면 pull로 재구성 | 메모리를 실제 읽는 사람 몫만 써요, 팬아웃 쓰기도 줄어요 | 돌아온 사용자의 첫 피드가 느려요, 재구성 몰림 대비 필요 |
| B. 사용자당 최근 N개 상한(`LTRIM`, `ZREMRANGEBYRANK`) | 사용자당 메모리가 고정돼요 | 오래된 글은 DB에서 읽어야 해요 |
| C. 항목은 ID만, 본문은 하이드레이션 | 항목이 작아지고 수정·삭제가 쉬워요 | 읽을 때 글 캐시 조회가 한 번 더 생겨요 |
| D. Redis 노드 증설 | 코드 변경 없이 바로 돼요 | 휴면 사용자가 늘수록 비용이 계속 커져요 |

**내가 고를 방법**
A + B + C를 같이 적용해요. 핵심은 A예요. 안 읽을 피드를 미리 만드는 게 낭비의 원인이니, 팬아웃 대상에서 휴면 사용자를 빼고 캐시에도 TTL을 걸어요. 휴면 사용자가 돌아오면 팔로잉 목록으로 피드를 다시 만들어 채워요. B와 C로 활성 사용자 몫도 작게 유지해요. D는 원인을 안 고치니 급할 때만 임시로 써요. 휴면 사용자가 한꺼번에 돌아오는 이벤트(대규모 푸시 알림 등) 전에는 재구성 몰림을 대비해 둬요.

**채점 포인트**: 메모리 = 사용자 × N × 항목 크기로 계산, 활성 사용자만 캐시, 미스 시 pull 재구성, 사용자당 상한 N, ID만 저장 + 하이드레이션, TTL, 증설은 임시방편, 재구성 몰림 대비.
</details>

## 필기 포인트

- 팬아웃 온 라이트(push) = 쓸 때 팔로워 피드에 미리 넣기 → 읽기 쌈, 쓰기 비쌈.
- 팬아웃 온 리드(pull) = 읽을 때 모아 합치기 → 쓰기 쌈, 읽기 비쌈.
- 하이브리드 = 일반 사용자는 push, 팔로워가 아주 많은 계정은 pull 병합.
- 트위터(2012년 11월 발표 기준): 쓰기 평균 약 4.6k/초·피크 12k/초 이상, 타임라인 읽기 약 300k/초.
- 오프셋 페이징은 깊을수록 느리고 삽입·삭제 시 중복·누락. 커서(키셋) 페이징은 정렬 키가 유일해야 함.
- Redis 리스트 상한: `LPUSH` + `LTRIM 0 N-1`. Sorted Set 범위: `ZRANGE ... BYSCORE REV LIMIT`(6.2.0+).
