:::tip[한 줄 요약]
결제 시스템의 핵심은 **돈이 두 번 빠지지도, 빠졌는데 기록이 없지도 않게** 만드는 거예요. 서버가 저장해 둔 금액으로 검증한 뒤 PG 승인 API를 **멱등 키**와 함께 부르고, 결제 상태를 **상태 머신**으로 관리해요. 응답이 안 오면 실패로 단정하지 않고 **조회 API·웹훅·대사**로 진짜 결과를 확인해 확정해요.
:::

:::note[처음이라면 여기까지]
① 카드 결제는 한 번에 끝나지 않아요. "승인(허락받기) → 매입(실제 청구) → 정산(가게에 입금)"으로 시점이 나뉘어요.

② 사용자가 카드 인증을 마쳐도 돈은 아직 안 빠져요. 우리 **서버**가 PG(결제대행사)에 "승인해 주세요"를 불러야 빠져요. 이때 금액은 꼭 서버에 저장해 둔 값과 비교해요.

③ 승인 요청에 응답이 안 오면 "실패"가 아니라 "모름"이에요. 돈이 빠졌을 수도 있으니 먼저 PG에 물어보고(조회) 정해요.

④ 같은 요청을 다시 보내도 한 번만 결제되게 하는 장치가 **멱등 키**예요. 면접에선 질문 1~3번부터 연습하세요. "심화:"는 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

식당에서 카드로 계산하는 장면을 떠올려 봐요.

계산대에서 카드를 꽂으면 단말기가 카드사에 "이 카드로 3만 원 써도 돼요?"라고 물어요. 카드사는 한도를 확인하고 3만 원을 **잡아 둬요**. 이게 **승인**이에요. 아직 가게 통장에 돈이 들어온 건 아니에요.

밤에 가게 문을 닫으면 그날 승인된 건들을 모아 카드사에 "이 금액들 청구할게요"라고 보내요. 이게 **매입**이에요. 이때 거래가 확정돼요.

며칠 뒤 카드사·PG가 수수료를 뗀 돈을 가게 통장에 넣어 줘요. 이게 **정산**이에요.

온라인 결제에선 계산대 대신 **우리 서버**가 카드사 쪽(PG)에 승인을 요청해요. 그런데 요청을 보낸 직후 와이파이가 끊기면, 승인이 났는지 안 났는지 알 수 없어요. 식당이라면 영수증을 다시 뽑아 보듯, 서버도 "그 주문 결제됐어요?"라고 **다시 물어보는 절차**가 꼭 필요해요. 이 페이지는 대부분 그 "모르는 순간"을 다뤄요.

단, 실제로는 승인 순간에 카드 한도가 차감되고, 매입·정산 시점과 방식은 PG·카드사·계약마다 달라요. 비유는 "단계가 나뉜다"는 감만 잡는 용도예요.

## 제대로 알기

### 요구사항 정리

시스템 설계 면접에서는 먼저 무엇을 만들지 정해요. → [시스템 설계 면접 푸는 법](../design-approach/)

| 구분 | 내용 |
|---|---|
| 기능 | 결제 요청·승인, 취소·부분취소, 결제 상태 조회, PG 웹훅 수신 |
| 비기능(가장 중요) | **정확성**: 이중 결제 금지, 돈이 빠졌는데 기록 없음 금지 |
| 비기능 | 추적 가능성: 누가 언제 얼마를 바꿨는지 남아야 함 |
| 비기능 | 가용성: PG가 느려도 우리 서비스 전체가 멈추지 않아야 함 |

결제는 다른 설계 문제와 우선순위가 달라요. 피드나 채팅은 조금 늦거나 한두 개 틀려도 되지만, 결제는 **느려도 되니 틀리면 안 돼요**.

**규모 추정**은 간단히 해요. 하루 100만 건이라고 가정하면 100만 ÷ 86,400초 ≈ 초당 12건이에요. 행사 때 평소의 10배가 몰린다고 해도 초당 100여 건이에요. 결제는 대개 처리량보다 **정확성과 외부 PG 응답 지연**이 더 큰 문제예요.

### 용어: 승인·매입·정산·취소

| 용어 | 뜻 | 언제 |
|---|---|---|
| **승인** | 카드가 유효한지, 한도가 되는지 확인하고 결제를 허락받음 | 결제 순간 |
| **매입** | PG가 카드사에 승인된 거래 대금을 청구해 거래를 확정 | 토스페이먼츠 기준: 매일 23:59:59에 승인 마감, 자정부터 전날 승인 건 매입 |
| **정산** | PG가 수수료(와 그 부가세)를 뺀 금액을 가맹점 계좌로 지급 | 주기·지급일은 계약마다 다름(일반지식) |
| **승인취소** | 매입 **전** 취소. 간단히 끝남 | 매입 전 |
| **매입취소** | 매입 **후** 취소. 카드사 반영까지 며칠 걸림(약 D+3) | 매입 후 |
| **부분취소** | 결제 금액 중 일부만 취소 | 승인 후 |

승인과 매입을 나누는 건 한국만의 개념이 아니에요. Stripe도 승인(authorize)과 매입(capture)을 분리할 수 있어요.

### 결제 흐름: 요청 → 인증 → 승인

토스페이먼츠 공개 개발자 문서 기준으로 정리하면 결제는 3단계예요.

1. **결제 요청**: 브라우저가 PG의 SDK로 결제창을 띄워요. 이때 `orderId`(우리가 만든 주문번호), 금액, `successUrl`·`failUrl`(끝나면 돌아올 주소)을 넘겨요.
2. **구매자 인증**: 사용자가 카드 정보를 넣거나 앱으로 인증해요. 카드사가 본인인지 확인해요. 성공하면 `successUrl`로 `paymentKey`, `orderId`, `amount`가 돌아와요.
3. **결제 승인**: 우리 **서버**가 승인 API(`POST /v1/payments/confirm`)를 `paymentKey`·`orderId`·`amount`와 함께 불러요. **이때 실제로 돈이 빠져요.**

여기서 꼭 기억할 두 가지가 있어요.

- **인증 성공 ≠ 결제 완료.** 서버가 승인 API를 부르지 않으면 돈은 안 빠지고, 일정 시간이 지나면 결제가 만료(`EXPIRED`)돼요. 만료 시간은 같은 문서 안에서도 10분·30분으로 다르게 적혀 있어서, 실제로 쓸 땐 최신 문서를 확인해야 해요.
- **`paymentKey`는 받은 그대로 저장해요.** 승인·취소·조회에 모두 필요해요.

### 금액 위변조 검증

결제창에 넘기는 금액은 브라우저에서 정해져요. 브라우저는 사용자 손에 있으니 **얼마든지 바꿀 수 있어요**. 예를 들어 쿠폰 적용 금액을 조작해 3만 원짜리를 300원으로 보낼 수도 있어요.

그래서 순서가 이래요.

1. 결제창을 띄우기 **전에** 서버가 주문을 만들고 `orderId`와 **서버가 계산한 금액**을 DB에 저장해요.
2. 인증 후 돌아온 `amount`를 저장된 금액과 비교해요.
3. 다르면 승인 API를 부르지 않고 중단해요.

원칙은 하나예요. **클라이언트가 보낸 금액은 믿지 않는다.**

### 결제 상태 머신

**상태 머신**(state machine)은 "가능한 상태 목록 + 어느 상태에서 어느 상태로 갈 수 있는지 규칙"이에요. 결제는 상태가 꼬이면 돈이 꼬이니까, 허용된 이동만 받아들이게 만들어요.

먼저 **PG가 정한 공식 상태값**(토스페이먼츠 Payment 객체의 `status`)이에요.

| 상태 | 뜻 |
|---|---|
| `READY` | 결제 생성 직후, 인증 전 |
| `IN_PROGRESS` | 인증 완료, 승인 API를 부르면 완료 |
| `DONE` | 승인 완료 |
| `WAITING_FOR_DEPOSIT` | 가상계좌 발급 후 입금 대기 |
| `CANCELED` / `PARTIAL_CANCELED` | 전액 취소 / 부분취소 |
| `ABORTED` | 승인 실패 |
| `EXPIRED` | 유효시간이 지나 취소됨 |

Stripe도 `processing` 같은 "처리 중" 상태를 둬요. 두 PG 모두 **결과가 바로 확정되지 않는 구간**이 있다는 뜻이에요.

다음은 **우리 서비스가 주문 테이블에 두는 내부 상태**예요(일반 설계, 예시). 이름이 같아도 뜻은 조금 달라요. 여기서 `IN_PROGRESS`는 "PG에 승인 요청을 보냄"이고, PG의 `IN_PROGRESS`는 "인증 끝, 승인 대기"예요.

```text
READY ──승인 요청 보냄──▶ IN_PROGRESS ──▶ DONE ──▶ CANCELED / PARTIAL_CANCELED
                              │
                              ├──▶ FAILED
                              └──▶ UNKNOWN ──조회·웹훅·대사──▶ DONE 또는 FAILED
```

<Aside type="caution" title="UNKNOWN은 PG 공식 상태값이 아니에요">
토스페이먼츠·Stripe의 공식 상태 목록에 `UNKNOWN`은 없어요. "PG에 요청은 보냈는데 결과를 못 받음"을 표현하려고 **우리가 내부에 두는 상태**예요(일반 설계). 면접에서 "PG가 UNKNOWN을 준다"고 말하면 틀려요.
</Aside>

상태를 바꿀 땐 **조건부 UPDATE**로 동시성을 막아요.

```sql
-- 지금 IN_PROGRESS나 UNKNOWN일 때만 DONE으로 바꾼다
UPDATE payment
SET status = 'DONE', approved_at = NOW()
WHERE order_id = 'order-101' AND status IN ('IN_PROGRESS', 'UNKNOWN');
-- 바뀐 행이 0개면: 이미 누가 처리했거나 허용되지 않은 전이 → 무시하거나 확인
```

이렇게 하면 웹훅과 조회 결과가 동시에 들어와도 한쪽만 반영돼요. `CANCELED → DONE`처럼 말이 안 되는 전이도 자연스럽게 막혀요.

### 중복 결제 방지: 멱등 키

사용자가 버튼을 두 번 누르거나, 앱이 응답을 못 받아 재요청하면 승인이 두 번 나갈 수 있어요. 이걸 막는 게 **멱등 키**(Idempotency-Key, 같은 요청에 붙이는 고유 번호)예요. 원리와 서버 구현은 → [Outbox 패턴과 멱등성](../../distributed/outbox-idempotency/)에 자세히 있어요. 여기선 PG별 차이만 정리해요(작성 시점 기준).

| 항목 | 토스페이먼츠 | Stripe(API v1) |
|---|---|---|
| 적용 | 모든 POST API, `Idempotency-Key` 헤더 | POST 요청(GET·DELETE엔 보내지 말 것) |
| 같은 키 재요청 | 작업 다시 안 하고 첫 응답 그대로 | 저장된 첫 응답 그대로(500 에러도 그대로) |
| 처리 중 재요청 | 409 `IDEMPOTENT_REQUEST_PROCESSING` | 동시 실행 충돌이면 결과 저장 안 함 |
| 유효기간 | 첫 요청일로부터 15일 | 최소 24시간 뒤 삭제될 수 있음 |
| 키 길이 | 최대 300자 | 최대 255자 |

공통 규칙도 있어요.

- 키는 **UUID처럼 충분히 랜덤한 값**으로 만들어요.
- 에러가 났다고 **키를 바꿔서 재시도하지 않아요**. 키를 바꾸면 새 결제로 처리될 수 있어요. 토스페이먼츠 문서도 원인부터 확인하라고 해요.
- 유효기간은 PG마다 다르니 **문서로 확인**해요.

멱등 키와 별개로, `orderId`가 같은 결제를 PG가 또 승인하려 하면 `ALREADY_PROCESSED_PAYMENT`로 거절해요. 우리 DB에도 주문번호 **유니크 제약**을 걸어 이중으로 막아요.

### 타임아웃 났을 때: 실패가 아니라 "모름"

승인 API를 불렀는데 5초 동안 응답이 없어요. 가능한 경우는 세 가지예요.

1. 요청이 PG까지 못 갔다 → 돈 안 빠짐
2. PG가 처리 중이다 → 곧 빠질 수 있음
3. PG는 승인했는데 응답만 못 받았다 → **돈은 이미 빠짐**

우리 서버는 셋을 구별할 수 없어요. 그래서 실패로 처리하면 3번일 때 "돈은 빠졌는데 주문은 실패"가 되고, 사용자가 다시 결제하면 **이중 결제**가 돼요.

처리 순서는 이래요(공식 문서의 조회 API·멱등 키·웹훅 안내를 조합한 **일반 설계**예요. "타임아웃 시 이렇게 하라"는 전용 가이드는 문서에서 찾지 못했어요).

1. 내부 상태를 `UNKNOWN`으로 바꾸고, 사용자에겐 "결제 확인 중" 화면을 보여줘요(다시 누르지 않게).
2. 조회 API로 PG 쪽 상태를 물어요. `GET /v1/payments/orders/` 뒤에 주문번호를 붙이면 `paymentKey` 없이 **우리 주문번호로** 확인할 수 있어요.
3. `DONE`이면 우리도 `DONE`. 아직 승인 전(`IN_PROGRESS`)이면 **같은 멱등 키**로 재시도하고, `ABORTED`·`EXPIRED`처럼 실패로 끝났으면 실패 처리해요. 여전히 모르면 간격을 두고 다시 조회해요.
4. 그 사이 웹훅이 오면 똑같이 반영해요. 먼저 온 쪽이 확정하고, 나중 것은 조건부 UPDATE에서 걸러져요.
5. 일정 시간이 지나도 `UNKNOWN`이면 대사 배치가 잡고, 운영자에게 알려요.

재시도 간격·지터·서킷브레이커 같은 일반 도구는 → [장애 대응 패턴](../../architecture/resilience/)을 보세요. 단, 결제에선 **"PG가 느리면 성공으로 간주" 같은 폴백은 금지**예요. 돈은 보수적으로 다뤄요.

### 웹훅 수신: 두 번 와도 한 번만

**웹훅**(webhook)은 PG가 "결제 상태 바뀌었어요"를 우리 서버로 **먼저 알려주는** HTTP 요청이에요. 가상계좌 입금처럼 나중에 일어나는 일은 웹훅으로 알게 돼요.

웹훅에는 두 가지 성질이 있어요.

- **중복될 수 있어요.** 토스페이먼츠는 10초 안에 200을 못 받으면 최대 7회 재전송해요(간격 1·4·16·64·256·1024·4096분). Stripe도 같은 이벤트가 두 번 이상 올 수 있다고 안내해요.
- **순서가 보장되지 않아요**(Stripe 문서 명시).

그래서 받는 쪽은 이렇게 해요.

1. **서명 검증**: 진짜 PG가 보낸 건지 확인해요(토스페이먼츠는 서명 헤더와 전송 시각 헤더를 줘요).
2. **빨리 200 응답**: 무거운 처리는 큐에 넣고 바로 응답해요. 처리하다 10초를 넘기면 PG는 실패로 보고 또 보내요.
3. **본문을 그대로 믿지 않기**: 결제 조회 API로 금액·상태를 다시 확인해요(토스페이먼츠 권장).
4. **멱등 처리**: 처리한 이벤트 ID나 결제 키를 기록하고, 상태 전이는 조건부 UPDATE로 해요. 이미 `DONE`인데 또 `DONE`이 오면 무시해요. → [멱등 소비자](../../distributed/outbox-idempotency/)

### 금액 표현: double 금지

`double`로 0.1 + 0.2를 계산하면 `0.30000000000000004`가 나와요(Java 17에서 한 번 실행해 본 결과). 컴퓨터는 숫자를 2진수로 저장하는데, 0.1은 2진수로 딱 떨어지지 않아서 근삿값이 들어가요. 금액에서 이런 오차는 허용이 안 돼요.

| 방법 | 언제 | 주의 |
|---|---|---|
| **최소 단위 정수**(`long`, DB `BIGINT`) | 원화처럼 소수점 없는 통화, 대부분의 결제 금액 | 외화는 센트 단위로(10달러 → `1000`) |
| **`BigDecimal`** (DB `DECIMAL`) | 수수료율·이자·외화 환산처럼 소수 계산이 필요할 때 | 아래 함정 3개 |
| `float`/`double` | 쓰지 않음 | 0.1을 정확히 못 나타냄 |

Stripe API는 모든 금액을 **통화의 최소 단위 정수**로 받아요. 10달러면 `1000`(센트), 소수점이 없는 통화면 금액 그대로예요.

`BigDecimal`(자바의 정확한 10진수 숫자 클래스)에는 면접 단골 함정이 있어요.

```java
new BigDecimal(0.1);       // 0.1000000000000000055511151231257827021181583404541015625
new BigDecimal("0.1");     // 0.1  ← 문자열로 만들거나
BigDecimal.valueOf(0.1);   // 0.1  ← valueOf를 써요

new BigDecimal("2.0").equals(new BigDecimal("2.00"));    // false (자릿수까지 비교)
new BigDecimal("2.0").compareTo(new BigDecimal("2.00")); // 0 (값만 비교) → 금액 비교는 이것

BigDecimal a = new BigDecimal("1000");
a.add(new BigDecimal("500"));        // a는 그대로 1000! (불변 객체)
a = a.add(new BigDecimal("500"));    // 결과를 다시 받아야 1500
```

1. `new BigDecimal(0.1)`은 이미 오차가 있는 double을 그대로 옮겨요. 문자열이나 `valueOf`를 써요.
2. `equals`는 값과 **스케일**(소수점 아래 자릿수)까지 비교해서 `2.0`과 `2.00`이 다르다고 해요. 금액 비교는 `compareTo`예요.
3. 나눗셈이 1/3처럼 끝나지 않으면 반올림 방식을 안 줬을 때 `ArithmeticException`이 나요. `divide(x, 2, RoundingMode.HALF_UP)`처럼 자릿수와 방식을 정해요.

### 심화: 원장과 복식부기

여기부터는 일반지식이에요(특정 회사 구조가 아니에요).

**원장**(ledger)은 돈의 이동을 적는 장부예요. 결제 시스템에서는 잔액 칸 하나를 덮어쓰는 대신 **거래 기록을 추가만 하는(append-only)** 방식으로 만들어요.

- 잔액은 기록을 더한 값으로 계산하거나 검증해요.
- 잘못 적었으면 지우지 않고 **반대 기록**(역분개)을 하나 더 추가해 바로잡아요. 취소도 "삭제"가 아니라 "반대 방향 기록 추가"예요.

**복식부기**(double-entry)는 모든 거래를 **차변(debit)과 대변(credit) 두 쪽에 같은 금액으로** 적는 회계 방식이에요. 예를 들어 사용자가 3만 원을 결제하면 "고객 쪽 −30,000"과 "가맹점 미지급금 쪽 +30,000"처럼 두 줄이 한 쌍으로 들어가요.

| 장점 | 이유 |
|---|---|
| 버그 탐지 | 한 거래의 차변 합 ≠ 대변 합이면 바로 이상 |
| 감사 추적 | 지운 기록이 없으니 언제 무슨 일이 있었는지 다 남음 |
| 되돌리기 안전 | 덮어쓰기가 없으니 동시 수정 충돌이 줄어듦 |

이 생각은 Saga의 "보상은 되돌리기가 아니라 반대 동작"과 같은 맥락이에요. → [분산 트랜잭션](../../distributed/distributed-transactions/)

### 심화: 대사(Reconciliation)

**대사**는 우리 DB 기록과 외부(PG·카드사·은행) 기록을 대조해 안 맞는 걸 찾아 고치는 작업이에요(일반지식). 토스페이먼츠 문서도 사용자 이탈이나 웹훅 누락으로 데이터가 어긋날 수 있으니 정합성을 검증하라고 안내해요.

대사는 보통 두 층으로 둬요(일반 설계).

| 층 | 무엇을 | 언제 |
|---|---|---|
| 실시간에 가까운 대사 | `IN_PROGRESS`·`UNKNOWN`에 오래 머문 건을 조회 API로 확인 | 몇 분 간격 배치 |
| 일 단위 대사 | PG 거래·정산 내역과 우리 원장의 금액·건수·상태 비교 | 하루 한 번 |

타임아웃 처리, 웹훅, 대사는 **세 겹 안전망**이에요. 하나가 놓쳐도 다음이 잡아요.

### 심화: 서비스가 나뉘어 있으면 Saga

주문·결제·포인트가 서로 다른 서비스(다른 DB)라면 "결제 성공 + 포인트 차감 + 주문 확정"을 한 DB 트랜잭션으로 묶을 수 없어요. 이럴 땐 **Saga**(각 단계를 따로 커밋하고, 뒤 단계가 실패하면 앞 단계를 반대 동작으로 되돌리는 방식)를 써요. 예를 들어 포인트 차감이 실패하면 결제 취소 API를 불러 보상해요. 결제 완료 이벤트를 다른 서비스로 보낼 땐 Outbox로 유실을 막아요. → [분산 트랜잭션](../../distributed/distributed-transactions/), [Outbox 패턴과 멱등성](../../distributed/outbox-idempotency/)

### 심화: 첫 설계 → 병목 → 개선

| 단계 | 설계 | 문제 |
|---|---|---|
| 첫 설계 | 서버가 PG 승인 API 호출 → 성공이면 주문 저장, 예외면 실패 | 타임아웃을 실패로 봄, 재요청 시 이중 결제 |
| 개선 1 | 주문 먼저 저장 + 금액 검증 + 멱등 키 | 결과 모름 상태 표현이 없음 |
| 개선 2 | 내부 상태 머신(UNKNOWN 포함) + 조회 API 재확인 | 웹훅 중복·누락 |
| 개선 3 | 웹훅 서명 검증·멱등 처리 + 대사 배치 | PG 지연이 우리 스레드를 잡아먹음 |
| 개선 4 | 타임아웃·서킷브레이커·벌크헤드(폴백은 "성공 처리" 금지) | 서비스 분리 시 정합성 |
| 개선 5 | Saga + Outbox, 원장 append-only | 운영 복잡도 증가(트레이드오프) |

### 면접에서 이렇게 말하기

"결제는 정확성이 최우선이라, 클라이언트 금액을 믿지 않고 서버에 저장한 금액으로 검증한 뒤 PG 승인 API를 멱등 키와 함께 호출하겠습니다. 결제 상태는 상태 머신으로 관리하고 조건부 UPDATE로 허용된 전이만 받습니다. 승인 응답이 타임아웃 나면 실패로 단정하지 않고 내부적으로 UNKNOWN으로 두고 조회 API로 확인하며, 웹훅은 멱등하게 처리하고, 마지막 안전망으로 대사 배치를 둡니다."

## 면접 질문

<details>
<summary>Q. 온라인 카드 결제가 어떤 흐름으로 이루어지는지 설명해 주세요.</summary>

**답변(30초)**
결제 요청, 구매자 인증, 결제 승인 3단계예요. 브라우저가 PG 결제창을 띄우고, 사용자가 카드 인증을 하면 paymentKey·orderId·amount가 돌아와요. 그다음 우리 서버가 저장해 둔 금액과 비교한 뒤 승인 API를 불러야 실제로 돈이 빠져요. 인증만으로는 결제가 끝나지 않는다는 게 핵심이에요.

**꼬리질문**
- Q. 승인 API를 클라이언트에서 부르면 안 되나요? → 안 돼요. 브라우저 값은 조작될 수 있어서, 서버가 저장해 둔 금액과 비교한 뒤 서버에서 승인 API를 불러야 해요.
- Q. 인증 후 승인을 안 부르면요? → 일정 시간 뒤 결제가 만료(EXPIRED)돼요. 시간은 문서마다 다르게 적혀 있어 최신 문서를 확인해요.
</details>

<details>
<summary>Q. 금액을 double로 다루면 안 되는 이유는 뭔가요?</summary>

**답변(30초)**
double은 2진 부동소수점이라 0.1 같은 수를 정확히 못 나타내요. 실제로 0.1 + 0.2가 0.30000000000000004가 나와요. 그래서 원화처럼 소수점 없는 금액은 최소 단위 정수(long, BIGINT)로, 수수료율이나 외화처럼 소수가 필요하면 BigDecimal로 다뤄요. Stripe도 금액을 최소 단위 정수로 받아요.

**꼬리질문**
- Q. BigDecimal을 만들 때 주의할 점은? → `new BigDecimal(0.1)`은 이미 오차가 있는 값을 옮겨요. 문자열 생성자나 `valueOf`를 써요.
- Q. BigDecimal 비교는? → `equals`는 스케일까지 비교해 2.0과 2.00이 다르다고 해요. 금액 비교는 `compareTo`를 써요.
- Q. 1을 3으로 나누면? → 반올림 방식을 안 주면 ArithmeticException이 나요. 자릿수와 RoundingMode를 지정해요.
</details>

<details>
<summary>Q. 중복 결제를 어떻게 막나요?</summary>

**답변(30초)**
여러 겹으로 막아요. 첫째, PG 승인 API에 멱등 키를 붙여서 같은 요청이 다시 가도 첫 응답만 돌려받게 해요. 둘째, 주문번호에 유니크 제약을 걸고, 결제 상태 변경은 `WHERE status = 이전상태` 조건부 UPDATE로 해서 한 번만 바뀌게 해요. 셋째, 클라이언트는 결제 중 버튼을 잠가요. PG도 같은 주문의 재승인은 거절해요.

**꼬리질문**
- Q. 멱등 키는 얼마나 유효해요? → PG마다 달라요. 토스페이먼츠는 첫 요청일로부터 15일, Stripe는 최소 24시간 뒤 삭제될 수 있어요(작성 시점 기준).
- Q. 에러가 나면 새 키로 다시 보내도 되나요? → 안 돼요. 새 키는 새 요청으로 처리돼 이중 결제가 될 수 있어요. 원인부터 확인해요.
</details>

<details>
<summary>Q. 승인, 매입, 정산은 어떻게 다른가요?</summary>

**답변(30초)**
승인은 카드가 유효하고 한도가 되는지 확인해 결제를 허락받는 거예요. 매입은 PG가 승인된 거래 대금을 카드사에 청구해 거래를 확정하는 거고, 정산은 PG가 수수료를 뺀 돈을 가맹점에 지급하는 거예요. 시점이 다 달라서, 매입 전 취소는 승인취소로 간단히 끝나지만 매입 후 취소는 카드사 반영까지 며칠 걸려요.

**꼬리질문**
- Q. 승인과 매입을 나누는 게 한국만의 방식인가요? → 아니에요. Stripe도 authorize와 capture를 분리할 수 있어요.
</details>

<details>
<summary>Q. 결제 상태는 어떻게 관리하나요?</summary>

**답변(30초)**
상태 머신으로 관리해요. PG 공식 상태(READY, IN_PROGRESS, DONE, CANCELED, ABORTED, EXPIRED 등)를 참고하되, 우리 주문 테이블엔 "결과를 모름"을 뜻하는 UNKNOWN 같은 내부 상태를 따로 둬요. 상태 변경은 허용된 전이만 조건부 UPDATE로 받아서, 웹훅과 조회 결과가 동시에 와도 한 번만 반영되고 CANCELED에서 DONE 같은 잘못된 이동은 거부돼요.

**꼬리질문**
- Q. UNKNOWN은 PG가 주는 상태인가요? → 아니에요. 토스페이먼츠·Stripe 공식 상태값에 없어요. 우리가 설계로 두는 내부 상태예요.
- Q. 부분취소를 두 번 동시에 요청하면? → 남은 금액을 조건부 UPDATE나 락으로 지켜요. PG도 취소 가능 금액을 넘으면 `NOT_CANCELABLE_AMOUNT`로 거절해요.
</details>

<details>
<summary>Q. 웹훅이 중복되거나 순서가 바뀌어 오면 어떻게 하나요?</summary>

**답변(30초)**
웹훅은 최소 한 번 전달이고 순서도 보장되지 않는다고 보고 멱등하게 받아요. 서명을 검증하고, 빨리 200을 돌려준 뒤 처리는 큐에서 해요. 본문을 그대로 믿지 않고 조회 API로 현재 상태를 다시 확인해, 조건부 UPDATE로 반영해요. 이미 처리한 이벤트나 이미 DONE인 결제면 무시해요.

**꼬리질문**
- Q. 왜 빨리 200을 줘야 하나요? → 토스페이먼츠는 10초 안에 200을 못 받으면 재전송해요. 처리 시간이 길면 중복이 늘어요.
- Q. 순서가 바뀌면 상태가 거꾸로 가지 않나요? → 웹훅 본문 대신 조회 API의 현재 상태를 기준으로 하고, 허용된 전이만 받으니 거꾸로 가지 않아요.
</details>

<details>
<summary>Q. PG 승인 API가 타임아웃 나면 어떻게 처리하나요?</summary>

**답변(30초)**
실패로 단정하지 않아요. PG가 이미 승인했는데 응답만 못 받았을 수 있어서, 실패 처리하고 사용자가 다시 결제하면 이중 결제가 돼요. 내부 상태를 UNKNOWN으로 두고 사용자에겐 "확인 중"을 보여준 뒤, 주문번호로 조회 API를 불러 결과를 확인해요. 승인됐으면 확정하고, 안 됐으면 같은 멱등 키로 재시도하거나 실패 처리해요. 오래 모르는 건은 대사 배치와 알림으로 잡아요.

**꼬리질문**
- Q. 조회도 타임아웃 나면? → 간격을 늘려 가며 다시 조회하고, 그 사이 웹훅이 오면 그걸로 확정해요. 일정 시간을 넘으면 운영자에게 알려요.
- Q. PG 장애가 길어지면? → 타임아웃과 서킷브레이커로 우리 스레드를 보호해요. 단 "성공으로 간주" 같은 폴백은 쓰지 않아요.
</details>

<details>
<summary>Q. 우리 DB와 PG 기록이 안 맞으면 어떻게 알아내고 고치나요?</summary>

**답변(30초)**
대사로 찾아요. 몇 분 간격으로 IN_PROGRESS나 UNKNOWN에 오래 머문 건을 조회 API로 확인하고, 하루 한 번 PG 거래·정산 내역과 우리 원장의 금액·건수·상태를 비교해요. 불일치는 원장에 반대 기록을 추가하는 식으로 고치고, 자동으로 못 고치는 건 운영자가 확인해요.

**꼬리질문**
- Q. 왜 원장 기록을 수정하지 않고 추가하나요? → 지우거나 덮어쓰면 무슨 일이 있었는지 추적할 수 없어요. 반대 기록을 남기면 감사 추적이 되고, 차변·대변 합으로 오류도 바로 보여요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제 승인 API를 호출했는데 5초 동안 응답이 없어 타임아웃이 났어요. 사용자 카드사에서 결제 문자가 갔는지, 돈이 빠졌는지 우리는 몰라요. 어떻게 처리해야 할까요?</summary>

**상황 파악**
타임아웃은 "실패"가 아니라 "결과 모름"이에요. 요청이 PG에 못 갔을 수도, 처리 중일 수도, 이미 승인됐는데 응답만 잃었을 수도 있어요. 가장 위험한 실수는 실패로 처리해 사용자가 다시 결제하게 만드는 거예요(이중 결제). 반대로 성공으로 처리하면 돈 안 받고 상품을 내줄 수 있어요.

**원인 후보**
1. 우리 서버 → PG 구간 네트워크 문제(요청 미도달)
2. PG나 카드사 처리 지연(처리 중)
3. PG는 승인했지만 응답 패킷 유실(돈은 빠짐)
4. 우리 타임아웃이 PG 평소 응답 시간보다 너무 짧음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 내부 UNKNOWN 상태 + 조회 API로 확인 후 확정 | 진짜 결과로 확정, 이중 결제·누락 둘 다 방지 | 상태·조회 로직 추가, 사용자가 잠깐 "확인 중"을 봄 |
| B. 같은 멱등 키로 승인 재요청 | 이미 처리됐으면 첫 응답을 그대로 받음 | 처리 중이면 409가 와서 결국 기다려야 함, 키 유효기간 내에서만 |
| C. 웹훅으로 결과를 기다림 | 우리가 폴링 안 해도 됨 | 늦게 오거나 누락될 수 있음 |
| D. 일정 시간 뒤 자동 취소 API 호출 | 돈이 빠졌어도 돌려줌 | 사용자는 결제 실패 경험, 매입 후면 환불이 며칠 걸림 |

**내가 고를 방법**
A를 기본으로 해요. 상태를 UNKNOWN으로 바꾸고 사용자에겐 "결제 확인 중"을 보여 재결제를 막아요. 주문번호로 조회 API를 불러 DONE이면 확정, 승인 안 됐으면 B처럼 같은 멱등 키로 재시도하거나 실패 처리해요. C는 함께 받아서 먼저 온 결과로 확정하고, 둘 다 조건부 UPDATE라 중복 반영은 없어요. 일정 시간 넘게 UNKNOWN이면 대사 배치와 운영자 알림으로 넘기고, 정책상 주문을 진행할 수 없으면 D로 취소해요. 이건 공식 가이드가 아니라 조회 API·멱등 키·웹훅을 조합한 일반 설계라고 밝혀요.

**채점 포인트**: 타임아웃 ≠ 실패, 이중 결제 위험, 내부 UNKNOWN 상태(PG 공식 상태 아님), 조회 API(주문번호로 조회), 같은 멱등 키로 재시도(새 키 금지), 웹훅 병행, 조건부 UPDATE, 대사 배치·알림, 사용자 "확인 중" 화면, 결제엔 낙관적 폴백 금지.
</details>

<details>
<summary>상황: 사용자가 결제 버튼을 빠르게 두 번 눌렀어요. 같은 주문에 승인 요청이 두 번 나갈 뻔했어요. 어떻게 막나요?</summary>

**상황 파악**
같은 의도의 요청이 두 번 들어왔어요. 아무 장치가 없으면 서버가 둘 다 새 결제로 처리해 카드가 두 번 결제될 수 있어요. 버튼 연타뿐 아니라 네트워크 재시도, 앱 자동 재요청도 같은 문제를 만들어요.

**원인 후보**
1. 클라이언트가 처리 중에 버튼을 막지 않음
2. 서버가 "같은 결제 시도"를 구분할 식별자가 없음
3. 두 요청이 동시에 와서 "아직 결제 없음"을 둘 다 확인하고 진행(경쟁 상태)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 클라이언트 버튼 잠금 | 즉시 적용, 대부분 막음 | 네트워크 재시도·다른 기기는 못 막음, 보안 장치 아님 |
| B. PG 호출에 멱등 키 | 재전송해도 PG가 첫 응답만 돌려줌 | 키 저장·유효기간 관리 필요 |
| C. orderId 유니크 + 상태 조건부 UPDATE(`READY → IN_PROGRESS`) | DB가 동시 요청 중 하나만 통과시킴 | 한 주문에 여러 결제가 필요한 구조면 설계 변경 필요 |
| D. 분산 락(Redis 등)으로 주문별 직렬화 | 여러 서버에서도 한 번에 하나만 처리 | 락 만료·장애 처리 복잡, DB 제약으로 충분하면 과함 |

**내가 고를 방법**
A + B + C를 함께 써요. A로 대부분을 거르고, C에서 두 번째 요청은 `READY → IN_PROGRESS` 전이가 0행으로 끝나 "이미 처리 중"으로 응답해요. 그래도 재시도로 PG 호출이 다시 나가면 B가 막아요. PG 쪽도 같은 orderId 재승인은 `ALREADY_PROCESSED_PAYMENT`로 거절해요. D는 DB 제약으로 충분하면 쓰지 않아요.

**채점 포인트**: 클라이언트 방어는 보조, 서버 멱등 키, orderId 유니크, 조건부 UPDATE로 경쟁 상태 방지, SELECT 후 INSERT의 동시성 함정, 같은 키 재사용(새 키 금지), PG의 중복 승인 거절.
</details>

<details>
<summary>상황: 웹훅 처리 중 서버 배포가 겹쳐 PG에 200을 못 돌려줬어요. PG가 같은 결제 완료 웹훅을 다시 보냈고, 포인트가 두 번 적립됐어요. 원인과 해결은?</summary>

**상황 파악**
웹훅은 최소 한 번 전달이에요. 응답을 못 받은 PG는 재전송하는 게 정상 동작이에요. 문제는 **받는 쪽이 멱등하지 않아서** 같은 이벤트를 두 번 처리한 거예요.

**원인 후보**
1. 처리한 이벤트·결제를 기록하지 않음
2. 포인트 적립과 "처리 완료" 기록이 다른 트랜잭션이라 사이에서 끊김
3. 무거운 처리를 응답 전에 해서 10초를 넘기거나 배포 중 끊김
4. 웹훅 본문만 보고 처리해 상태 확인이 없음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 이벤트 ID(또는 paymentKey + 상태)를 유니크 키로 처리 기록, 적립과 같은 트랜잭션 | DB가 중복을 확실히 막음 | 기록 테이블 관리·정리 필요 |
| B. 결제 상태 조건부 UPDATE(`IN_PROGRESS → DONE`)가 성공했을 때만 적립 | 상태 머신과 자연스럽게 결합 | 적립이 다른 서비스면 이벤트 전달에 또 멱등 필요 |
| C. 받자마자 200 + 큐에 넣고 비동기 처리 | 재전송 자체가 줄어듦 | 큐 유실 대비 필요, 중복은 여전히 가능 |
| D. 서명 검증 + 조회 API 재확인 | 위조·오래된 본문 방지 | 조회 호출 비용 |

**내가 고를 방법**
A나 B로 "한 번만 반영"을 DB가 보장하게 하고, C로 재전송 빈도를 줄이며, D로 진위와 현재 상태를 확인해요. 포인트가 다른 서비스라면 결제 완료 이벤트를 Outbox로 보내고 포인트 서비스도 멱등 소비자로 만들어요. 이미 두 번 적립된 건은 원장에 반대 기록을 추가해 바로잡아요.

**채점 포인트**: 웹훅 at-least-once·순서 비보장, 이벤트 ID 기록 + 유니크 제약, 같은 트랜잭션, 빠른 200·비동기 처리, 서명 검증, 조회 API 재확인, Outbox·멱등 소비자 연계, 역분개로 정정.
</details>

<details>
<summary>상황: PG 승인은 DONE으로 성공했는데, 그 직후 우리 DB에 주문 상태를 저장하다 실패했어요(DB 장애). 고객 돈은 빠졌는데 주문은 "결제 전"이에요. 어떻게 하나요?</summary>

**상황 파악**
외부(PG)와 내부(우리 DB)는 한 트랜잭션으로 묶이지 않아요. 그래서 "PG는 성공, 우리는 실패"인 틈이 생겨요. 방치하면 고객은 돈을 냈는데 상품을 못 받아요.

**원인 후보**
1. 승인 직후 DB 쓰기 실패(장애, 락 타임아웃 등)
2. 승인 응답 처리 중 서버가 죽음
3. 서비스가 나뉜 구조라면 주문 서비스 쪽 저장 실패

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 주문을 승인 **전에** 먼저 저장(IN_PROGRESS)하고, 승인 후엔 상태만 바꿈. 실패 시 재시도 | 최소한 "결제 시도한 주문"은 남아 추적 가능 | 상태 UPDATE도 실패할 수 있음 |
| B. 조회·웹훅·대사로 나중에 DONE 반영(앞으로 나아가기) | 고객은 결국 상품을 받음, 매출 유지 | 반영까지 지연, 재고 등 다른 조건이 바뀌었을 수 있음 |
| C. 결제 취소 API로 보상(Saga) | 돈과 주문이 다시 일치 | 고객은 실패 경험, 매입 후면 환불이 며칠 걸림 |
| D. 결제 완료 이벤트를 Outbox로 기록해 다른 서비스에 확실히 전달 | 서비스 분리 시 유실 방지 | 구현·운영 부담, 소비자 멱등 필요 |

**내가 고를 방법**
A를 전제로 해요. 주문이 IN_PROGRESS로 남아 있으니 B의 조회 배치가 PG에서 DONE을 확인하고 주문을 DONE으로 바꿔 진행해요(고객이 원한 건 주문 완료라서 앞으로 나아가는 쪽이 우선). 재고 소진 등으로 주문을 진행할 수 없을 때만 C로 결제를 취소해요. 주문·결제·포인트가 다른 서비스라면 D로 이벤트를 보내고 Saga로 보상 흐름을 정해요. 어떤 경우든 일 대사에서 "PG DONE인데 우리 주문 미완료"를 다시 확인해요.

**채점 포인트**: 외부 API와 DB는 한 트랜잭션 불가, 주문 선저장(IN_PROGRESS), 조회 API·웹훅·대사로 상태 확정, 앞으로 나아가기 vs 보상(취소) 판단 기준, Saga·Outbox, 매입 전후 취소 차이, 고객 안내.
</details>
