:::tip[한 줄 요약]
읽기가 많은 서비스는 요청이 DB까지 내려가기 전에 **브라우저 → CDN → 앱 로컬 캐시 → Redis → DB 버퍼 풀** 순서로 여러 층에서 먼저 답하게 해서 확장해요. 위층일수록 빠르고 싸지만 **지우기 어려워서**, 층마다 무엇을 얼마나 오래 둘지(TTL)와 어떻게 바꿀지(퍼지·파일명 버전)를 정하는 게 설계의 핵심이에요.
:::

:::note[처음이라면 여기까지]
① 캐시는 "자주 찾는 걸 가까운 곳에 미리 두기"예요. 집 냉장고(브라우저), 동네 편의점(CDN), 본사 창고(서버) 순서로 멀어져요.

② **CDN**(Content Delivery Network, 전 세계에 흩어진 캐시 서버 묶음)은 사용자 가까이에서 이미지·CSS·JS 같은 파일을 대신 내줘서, 본 서버(오리진)에 오는 요청을 크게 줄여요.

③ 모두에게 똑같은 것(상품 이미지)은 오래 캐시하고, 사람마다 다른 것(장바구니)은 CDN에 캐시하지 않아요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

라면이 먹고 싶을 때를 떠올려 보세요. 먼저 **집 냉장고**를 열어요. 있으면 바로 끝이에요. 없으면 **동네 편의점**에 가요. 편의점에도 없으면 편의점이 **본사 창고**에 주문하고, 창고는 마지막으로 **공장**에서 받아 와요.

웹 요청도 똑같아요. 집 냉장고가 **브라우저 캐시**, 동네 편의점이 **CDN 엣지**(사용자 가까운 캐시 서버), 본사 창고가 **오리진**(우리 회사 서버), 공장이 **DB**예요. 대부분의 손님이 냉장고나 편의점에서 해결하면, 창고와 공장은 한가해져요. 이게 "캐시로 읽기를 확장한다"는 말이에요.

대신 문제가 하나 있어요. 공장에서 라면 가격을 바꿔도, 이미 냉장고와 편의점에 있는 라면엔 옛 가격표가 붙어 있어요. 그래서 "각 층에 얼마나 오래 둘지"와 "바뀌면 어떻게 알릴지"를 함께 설계해야 해요.

단, 실제로는 편의점(CDN)이 전 세계 수백 곳에 있고, 편의점과 창고 사이에 **지역 물류센터**(리전 캐시·오리진 실드) 같은 중간 층이 더 있어요. 그리고 집 냉장고(브라우저)는 회사가 직접 비울 수 없다는 점이 비유보다 훨씬 중요해요.

## 제대로 알기

### 1. 캐시 계층 전체 그림

요청 하나가 DB까지 가는 길에는 캐시를 둘 수 있는 곳이 여러 군데 있어요. 위에서 아래 순서예요.

| 계층 | 어디 있나 | 누가 같이 쓰나 | 막아 주는 것 | 약점 |
|---|---|---|---|---|
| 브라우저 캐시 | 사용자 기기 | 그 사용자 혼자(**사설 캐시**) | 네트워크 요청 자체 | 서버가 지울 수 없음 |
| CDN 엣지 | 사용자 가까운 데이터센터 | 모든 사용자(**공유 캐시**) | 먼 거리 왕복, 오리진 트래픽 | 사용자별 응답은 못 둠 |
| 리버스 프록시 캐시(nginx) | 우리 데이터센터 입구 | 모든 사용자 | 앱 서버 호출 | 앱 로직이 필요한 응답은 못 둠 |
| 앱 로컬 캐시(Caffeine) | 앱 서버 프로세스 메모리 | 그 서버 한 대 | Redis·DB 왕복 | 서버마다 값이 다를 수 있음 |
| 분산 캐시(Redis) | 별도 캐시 서버 | 모든 앱 서버 | DB 쿼리 | 네트워크 1번은 탐 |
| DB 버퍼 풀 | DB 서버 메모리 | DB 안 | 디스크 읽기 | 쿼리 실행 비용은 그대로 |

**사설 캐시**(private cache)는 한 사용자만 쓰는 캐시(보통 브라우저)이고, **공유 캐시**(shared cache)는 여러 사용자가 같은 저장본을 재사용하는 캐시(CDN, 리버스 프록시)예요.

규칙 하나만 기억하세요. **아래로 갈수록 느리지만 최신에 가깝고, 위로 갈수록 빠르지만 무효화하기 어려워요.** 브라우저에 한번 들어간 파일은 서버가 "지워"라고 명령할 방법이 없어요.

<Aside type="note">
Cache-Control·ETag·304 같은 HTTP 캐시 헤더는 [HTTP 기초 — 심화: 6. 캐시](../../web/http-basics/)에 정리돼 있어요. 여기선 한 줄만: `max-age`는 "몇 초 동안 다시 묻지 말고 써도 돼", `s-maxage`는 "공유 캐시(CDN)에만 적용되는 max-age", `private`는 "브라우저만 저장하고 CDN은 저장하지 마"예요.
</Aside>

### 2. CDN은 어떻게 동작하나

**CDN**은 전 세계 여러 곳에 캐시 서버를 두고, 사용자를 가장 가까운 곳으로 보내 대신 응답하게 하는 서비스예요. AWS CloudFront, Cloudflare가 대표적이에요.

용어부터 정리할게요.

- **엣지**(edge, 또는 **POP** Point of Presence): 사용자 가까이 있는 CDN 캐시 서버. 동네 편의점.
- **오리진**(origin): 원본을 가진 우리 서버(S3, 웹 서버 등). 본사 창고.
- **캐시 키**(cache key): "같은 물건인가"를 판단하는 이름표. 키가 같으면 같은 저장본을 꺼내 줘요.
- **TTL**(Time To Live): 저장본을 얼마나 오래 써도 되는지.
- **퍼지**(purge, 무효화): CDN에 있는 저장본을 강제로 지우기.

CloudFront 문서 기준으로 요청은 이렇게 흘러가요.

1. 사용자가 요청하면 DNS가 지연이 가장 짧은 POP으로 보내요.
2. POP에 저장본이 있으면 바로 응답해요(**적중**, hit).
3. 없으면(**미스**, miss) 설정된 오리진에 요청해요. 오리진에서 첫 바이트가 오자마자 사용자에게 흘려보내면서 동시에 캐시에도 저장해요.

오리진이 캐시 헤더(Cache-Control, Expires)를 안 주면 CloudFront는 기본 24시간 캐시해요. Cloudflare는 상태 코드별 기본값이 있어요(200은 120분 등).

### 3. 캐시 키: 적중률을 결정하는 이름표

HTTP 캐시 키는 최소 "메서드 + URL"이에요. 응답에 `Vary` 헤더가 있으면 거기 적힌 요청 헤더도 키에 들어가요. Cloudflare 기본 키는 쿼리스트링까지 포함한 전체 URL이에요.

그래서 이런 일이 생겨요.

- `?a=1&b=2`와 `?b=2&a=1`은 **다른 키**예요. 순서·대소문자가 다르면 같은 파일을 따로따로 저장해요.
- 광고 추적용 쿼리(`?utm_source=...`)가 붙으면 링크마다 다른 키가 돼요.
- 쿠키를 키에 넣으면 사본이 곱으로 늘어요. 쿠키 2개에 값이 3가지씩이면 객체 하나에 사본이 최대 9개예요.
- User-Agent(브라우저 종류 문자열)는 값이 너무 다양해서 키에 넣으면 적중률이 바닥나요. 대신 "모바일/데스크톱" 같은 기기 유형 헤더를 써요.

CloudFront가 권하는 적중률 올리는 법을 묶으면 이래요.

| 방법 | 효과 |
|---|---|
| `max-age`를 실용적인 최대값으로 | 오래 적중 |
| 오리진 응답을 실제로 바꾸는 쿼리만 키에 포함, 순서·대소문자 통일 | 키 폭발 방지 |
| 필요한 쿠키만 오리진에 전달 | 사본 수 감소 |
| 정적 경로와 동적 경로의 캐시 설정 분리 | 정적은 오래, 동적은 안 함 |
| Origin Shield 켜기 | 오리진으로 가는 미스 감소(5절) |

### 4. 정적 vs 동적 콘텐츠

**정적 콘텐츠**는 누가 요청하든 같은 응답이에요. 이미지·CSS·JS·폰트가 그래요. 공유 캐시에 오래 둘 수 있어요.

**동적 콘텐츠**는 사람이나 시점마다 다른 응답이에요. 로그인한 사용자의 마이페이지, 장바구니, 결제 같은 쓰기 요청이 그래요. CDN은 이걸 캐시하지 않고 오리진으로 그냥 전달(프록시)해요.

| 종류 | 예 | CDN 처리 | 헤더 예 |
|---|---|---|---|
| 정적 | 상품 이미지, `app.3f2a.js` | 오래 캐시 | `max-age` 길게 |
| 모두에게 같지만 자주 바뀜 | 상품 상세 본문, 인기 상품 목록 | 짧게 캐시 | 짧은 `s-maxage` + `stale-while-revalidate` |
| 사용자별 | 장바구니, 내 주문 | 캐시 안 함 | `private` 또는 `no-store` |
| 쓰기 | 주문 생성(POST) | 캐시 안 함, 오리진으로 | - |

몇 가지 기본 동작을 알아 두면 좋아요.

- Cloudflare는 HTML과 JSON을 **기본으로 캐시하지 않아요.** MIME 타입이 아니라 **파일 확장자**로 판단해요(이미지·CSS·JS·폰트 등만 기본 대상).
- 응답에 `Set-Cookie`가 있거나 `Cache-Control`이 `private`·`no-store`·`no-cache`·`max-age=0`이면 Cloudflare는 캐시하지 않아요. nginx도 기본으로 `Set-Cookie` 응답은 캐시하지 않아요.
- 동적 요청도 CDN을 거치는 것만으로 이점이 있어요. CloudFront는 오리진과 연결을 계속 열어 두고 재사용해요.

`stale-while-revalidate`는 "만료돼도 잠깐은 옛 값을 주면서 뒤에서 새로 받아 와"라는 뜻이에요. 자세한 동작은 [캐시 장애 패턴](../../redis/cache-problems/)에 있어요.

### 5. 오리진 실드와 요청 합치기

CDN 엣지가 수백 곳이면, 새 파일 하나가 올라왔을 때 엣지마다 한 번씩 오리진에 물으러 와요. 이걸 줄이는 장치가 두 가지예요.

**요청 합치기**(request collapsing): 캐시에 없는 객체에 **같은 캐시 키** 요청이 동시에 몰리면, CloudFront는 첫 요청 하나만 오리진에 보내고 나머지는 기다리게 했다가 같은 응답을 나눠 줘요. 단, 헤더·쿠키·쿼리로 키를 잘게 쪼개 놨으면 서로 다른 요청이라 합쳐지지 않아요. nginx에선 `proxy_cache_lock`이 같은 일을 해요(기본은 꺼져 있음).

**중간 캐시 층**: 엣지와 오리진 사이에 캐시를 한 층 더 둬서, 오리진으로 나가는 요청을 한 곳으로 모아요.

| 이름 | 회사 | 하는 일 |
|---|---|---|
| 리전 엣지 캐시 | CloudFront | POP보다 큰 캐시. 같은 지역 POP들이 공유. 기본으로 있음 |
| **Origin Shield** | CloudFront | 리전 캐시들과 오리진 사이 한 층 더. 모든 미스가 실드 한 곳을 거쳐 나감. 추가 요금 |
| **Tiered Cache** | Cloudflare | 하위 티어(사용자 근처) 미스 → 상위 티어에 묻고, 상위 티어만 오리진에 요청 |

이름에 "실드"가 들어가지만 보안 장치가 아니라 **캐시 계층**이에요. 동적 콘텐츠나 거의 안 쓰이는 파일에는 효과가 작아요.

### 6. 로컬 캐시 vs 분산 캐시 (요약)

앱 서버 안의 **로컬 캐시**(예: Caffeine, 자바 라이브러리)는 네트워크를 안 타서 가장 빠르지만, 서버마다 사본이 따로 있어 **서버끼리 값이 다를 수 있어요.** **분산 캐시**(Redis)는 모든 서버가 같은 값을 보지만 네트워크를 한 번 타요. 둘을 겹쳐 "로컬 → Redis → DB" 2단계로 쓰기도 해요.

비교표, 갱신 순서, Pub/Sub으로 로컬 캐시 지우기는 [캐시 전략 — 8. 로컬 캐시 vs Redis](../../redis/cache-patterns/)를 보세요.

### 7. 적중률 계산: 90%와 99%는 10배 차이

**적중률**(hit ratio) = 적중 수 ÷ 전체 요청 수예요. 다음 층으로 넘어가는 요청은 `들어온 요청 × (1 − 적중률)`이에요.

아래는 **직접 만든 숫자**로 한 계산이에요(실제 서비스 수치 아님).

| 단계 | 들어온 요청 | 적중률 | 다음 층으로 |
|---|---|---|---|
| CDN | 초당 10,000 | 90% | 1,000 |
| 앱(Redis) | 초당 1,000 | 95% | 50 |
| DB | 초당 50 | - | - |

CDN 적중률이 90%에서 99%로 오르면 오리진 도착은 1,000에서 100으로 **10분의 1**이 돼요. 9%p 차이처럼 보이지만, **미스율**은 10%에서 1%로 10배 차이예요. 적중률은 "몇 %p 올랐나"보다 "미스가 몇 배 줄었나"로 보세요.

평균 응답 시간도 같아요. `적중률 × 적중 지연 + (1 − 적중률) × 미스 지연`이에요. 적중 1ms, 미스 50ms라고 치면(역시 만든 숫자) 적중률 90%일 때 5.9ms, 99%일 때 1.49ms예요.

### 8. 핫키: 한 곳에 몰릴 때

**핫키**(hot key)는 특정 데이터 하나에 요청이 몰리는 상황이에요. 층마다 막는 방법이 달라요.

| 층 | 대책 |
|---|---|
| CDN | 요청 합치기, 오리진 실드·티어드 캐시. 캐시 키를 쪼개지 않기 |
| 리버스 프록시(nginx) | `proxy_cache_lock`(동시 미스 1개만 통과), `proxy_cache_use_stale updating` + `proxy_cache_background_update`(갱신 중엔 옛 응답) |
| 앱·Redis | 로컬 캐시로 흡수, 키 복제, 레플리카 읽기 → [캐시 장애 패턴 — 5. 핫키](../../redis/cache-problems/) |

### 9. 설계 질문으로 풀어 보기: 이미지 많은 쇼핑몰 상품 페이지

[설계 면접 푸는 법](../design-approach/)의 순서대로 따라가 볼게요. 숫자는 모두 **연습용으로 만든 가정**이에요.

**① 요구사항**
- 기능: 상품 상세 조회(이름·설명·가격·이미지 10장), 재고 표시, 장바구니 담기.
- 비기능: 읽기가 쓰기보다 압도적으로 많음, 페이지가 빨리 떠야 함, 가격은 바뀌면 너무 오래 옛 값이 보이면 안 됨.

**② 규모 추정**(가정)
- 상품 상세 조회 하루 1억 회 → 1억 ÷ 10^5초 ≈ 초당 1,000, 피크는 몇 배.
- 페이지 하나에 이미지 10장 → 이미지 요청은 초당 1만 이상. 이미지 한 장 200KB면 초당 약 2GB를 내보내야 함.
- 결론: **이미지 트래픽이 압도적**이고, 이건 오리진이 직접 감당할 일이 아니에요.

**③ 첫 설계(단순)**
브라우저 → 로드 밸런서 → 앱 서버 → DB. 이미지도 앱 서버가 직접 줘요.

**④ 병목**
- 이미지 대역폭이 앱 서버와 네트워크를 다 잡아먹음.
- 상품 정보 조회마다 DB 쿼리 → 피크 때 DB CPU가 먼저 한계.
- 해외 사용자는 거리 때문에 느림.

**⑤ 개선**
- 이미지·CSS·JS는 오브젝트 스토리지(S3 등)에 두고 **CDN으로 서빙**. 파일명에 버전(해시)을 넣고 `max-age`를 길게.
- 상품 상세 본문(모두에게 같은 부분)은 CDN에 **짧은** `s-maxage` + `stale-while-revalidate`.
- **재고·장바구니처럼 실시간이거나 사용자별인 부분은 별도 API로 분리**해서 CDN에 캐시하지 않음.
- 앱 서버는 Redis로 상품 정보를 Cache-Aside, 아주 인기 있는 상품은 로컬 캐시로 한 번 더.
- 엣지가 많아 오리진 미스가 겹치면 오리진 실드 켜기.

**⑥ 트레이드오프**
- TTL을 길게 → 적중률은 오르지만 가격 변경이 늦게 보임. 짧게 → 최신이지만 오리진 부하.
- 층을 많이 쌓으면 빠르지만, 값이 바뀌었을 때 지워야 할 곳도 늘어요.
- 퍼지는 CDN만 지우고 브라우저는 못 지워요.

**⑦ 면접에서 이렇게 말하기**
"상품 페이지는 이미지 트래픽이 대부분이라 정적 파일을 CDN으로 빼고 파일명 버전으로 길게 캐시하겠습니다. 상품 정보는 모두에게 같으니 CDN에 짧게, 앱에선 Redis로 캐시하고, 재고와 장바구니는 실시간·개인화라 API를 분리해 캐시하지 않겠습니다. 가격 변경은 TTL을 짧게 잡고 변경 시 퍼지로 보완하겠습니다."

### 심화: 리버스 프록시 캐시(nginx) 세부

- 기본 캐시 키는 `$scheme$proxy_host$request_uri`예요. 기본으로 GET·HEAD만 캐시해요.
- `proxy_cache_valid 5m`처럼 시간만 쓰면 200·301·302 응답만 캐시해요. 오리진 응답의 `Cache-Control`·`Expires`가 이 설정보다 우선해요.
- `inactive`(기본 10분) 동안 안 쓰인 데이터는 신선도와 상관없이 지워지고, `max_size`를 넘으면 오래 안 쓴 것부터 지워요.
- `proxy_cache_lock_timeout`의 기본값은 5초예요.

### 심화: Caffeine과 InnoDB 버퍼 풀은 무엇을 남기나

- **Caffeine**은 **W-TinyLFU** 정책을 써요. 새 항목은 작은 LRU 창에 먼저 넣고, "예전에 얼마나 자주 쓰였나"를 작은 빈도 표(Count-Min Sketch)로 추정해서 본 영역에 들일지 정해요. 최근성과 빈도를 같이 봐서 단순 LRU보다 적중률이 크게 낫다고 보고돼 있어요.
- **InnoDB 버퍼 풀**(MySQL)은 테이블·인덱스 데이터를 페이지 단위로 메모리에 들고 있어요. 전용 DB 서버면 물리 메모리의 80% 정도까지 주는 경우가 많아요. 새로 읽은 페이지는 리스트 중간(old 영역 머리)에 넣고, 다시 쓰이면 앞으로 올려요. 그래야 테이블 전체를 한 번 훑는 쿼리가 자주 쓰는 페이지를 밀어내는 걸 줄일 수 있어요. 적중률은 `SHOW ENGINE INNODB STATUS`의 `Buffer pool hit rate`로 봐요.
- "버퍼 풀이 있으니 DB 앞 캐시가 필요 없다"는 틀려요(일반적인 추론이에요). 버퍼 풀은 디스크 읽기만 줄일 뿐, 쿼리 파싱·조인·정렬 비용과 커넥션 수 한계는 그대로예요.

### 심화: 캐시에서 나온 응답인지 확인하는 법

- `Age` 응답 헤더: 오리진에서 응답이 만들어진 뒤 흐른 시간(초). 값이 크면 캐시에서 나온 것이에요.
- Cloudflare `cf-cache-status`: HIT(캐시에서 응답), MISS(없어서 오리진), EXPIRED(만료돼 새로 받음), STALE(만료됐지만 오리진에 못 닿아 옛것), BYPASS(오리진 응답이 캐시 불가 — `Set-Cookie`, `private` 등), REVALIDATED(오리진에 물어보니 안 바뀜), UPDATING(옛것 주며 뒤에서 갱신), DYNAMIC(애초에 캐시 대상 아님).
- CloudFront는 로그의 `x-edge-result-type`(Hit/Miss), 실드 적중은 `OriginShieldHit`로 봐요.

### 심화: 퍼지 vs 파일명 버전

| | 퍼지(무효화) | 파일명 버전(`app.3f2a.js`) |
|---|---|---|
| 지워지는 곳 | CDN만 | 지울 필요 없음. 새 이름이라 새 파일 |
| 브라우저·회사 프록시의 옛 사본 | 만료까지 남음 | 상관없음(HTML이 새 이름을 가리킴) |
| 비용 | CloudFront는 월 1,000경로까지 무료, 초과 과금(`/images/*` 같은 와일드카드는 1경로) | 없음 |
| 롤백 | 다시 퍼지 | 옛 이름을 가리키면 끝 |

CloudFront는 자주 바뀌는 파일엔 **버전 붙인 파일명**을 주로 쓰라고 권해요. Cloudflare는 퍼지 API가 200을 돌려줘도 "접수됨"일 뿐이니 `cf-cache-status`가 HIT가 아닌지 직접 확인하라고 안내해요. 요금제별로 퍼지 횟수 제한도 있어요.

### 심화: 자주 하는 오해

- "CDN은 정적 파일만 다룬다" → 기본은 정적 위주지만, 설정하면 짧은 TTL로 공개 HTML·API도 캐시할 수 있고, 동적 요청도 CDN을 통과해요.
- "퍼지하면 모두가 즉시 새 파일을 본다" → CDN만 지워져요. 브라우저 사본은 만료까지 남아요.
- "캐시 층은 많을수록 좋다" → 층마다 TTL이 겹치면 옛 값이 보이는 시간이 길어질 **가능성**이 있어요(최악엔 층별 TTL을 더한 만큼까지 — 공식 문서가 아니라 일반적인 추론이에요).
- "정적 파일인데 적중률이 0%" → 응답에 세션 쿠키(`Set-Cookie`)가 붙어서 BYPASS 되는 경우가 흔해요.

## 면접 질문

<details>
<summary>Q. CDN이 뭐고 왜 쓰나요?</summary>

**답변(30초)**
CDN은 전 세계에 흩어진 캐시 서버 묶음이에요. 사용자를 가장 가까운 엣지 서버로 보내서, 엣지에 저장본이 있으면 거기서 바로 응답해요. 그래서 거리 때문에 생기는 지연이 줄고, 오리진 서버로 오는 요청과 대역폭이 크게 줄어요. 엣지에 없을 때만 오리진에 가져와 저장해 두고 다음 사용자에겐 엣지에서 줘요.

**꼬리질문**
- Q. 엣지에 없으면 매번 오리진으로 가나요? → CloudFront는 POP과 오리진 사이에 리전 엣지 캐시가 있어서 거기서 한 번 더 찾아요. Origin Shield를 켜면 한 층 더 생겨요.
- Q. 사용자를 가까운 엣지로 어떻게 보내요? → CloudFront 기준으로 DNS가 지연이 가장 짧은 POP 주소를 알려 줘요.
</details>

<details>
<summary>Q. 캐시는 어디어디에 둘 수 있나요?</summary>

**답변(30초)**
요청 경로를 따라 브라우저, CDN, 리버스 프록시, 앱 서버 로컬 캐시, Redis 같은 분산 캐시, DB 버퍼 풀에 둘 수 있어요. 위로 갈수록 사용자에게 가까워 빠르지만 무효화가 어려워요. 특히 브라우저 캐시는 서버가 지울 수 없어요. 아래로 갈수록 느리지만 최신에 가까워요. 그래서 바뀌지 않는 건 위층에 오래, 자주 바뀌는 건 아래층에 짧게 둬요.

**꼬리질문**
- Q. 브라우저 캐시와 CDN 캐시의 차이는? → 브라우저는 한 사용자 전용인 사설 캐시, CDN은 여러 사용자가 같이 쓰는 공유 캐시예요. `Cache-Control: private`면 브라우저만 저장해요.
</details>

<details>
<summary>Q. 정적 콘텐츠와 동적 콘텐츠를 CDN에서 어떻게 다르게 다루나요?</summary>

**답변(30초)**
정적 콘텐츠는 누구에게나 같은 응답이라 CDN에 오래 캐시해요. 이미지·CSS·JS가 그래요. 동적 콘텐츠, 즉 사용자별 페이지나 쓰기 요청은 캐시하지 않고 오리진으로 전달만 해요. 그 사이에 상품 상세처럼 모두에게 같지만 자주 바뀌는 응답은 짧은 s-maxage로 CDN에 잠깐만 둬요. 사용자별 응답엔 `private`를 붙여 CDN이 저장하지 않게 해요.

**꼬리질문**
- Q. 동적 요청은 CDN을 거칠 이유가 없나요? → 거쳐도 이점이 있어요. CloudFront는 오리진과 연결을 계속 열어 두고 재사용해요.
- Q. Cloudflare에서 JSON API가 캐시 안 되는데요? → Cloudflare는 HTML·JSON을 기본으로 캐시하지 않고 파일 확장자로 판단해요. 따로 캐시 규칙을 줘야 해요.
</details>

<details>
<summary>Q. CDN 캐시 키는 무엇으로 정해지고, 적중률을 높이려면 어떻게 하나요?</summary>

**답변(30초)**
기본 캐시 키는 URL이고, 쿼리스트링도 포함되며 `Vary`에 적힌 헤더가 더해져요. 그래서 쿼리 순서나 대소문자가 다르거나 추적용 파라미터가 붙으면 같은 파일이 다른 키로 따로 저장돼 적중률이 떨어져요. 오리진 응답을 실제로 바꾸는 쿼리만 키에 넣고 순서를 통일하고, 쿠키·헤더는 꼭 필요한 것만 키에 넣어요. 그리고 max-age를 가능한 길게 잡아요.

**꼬리질문**
- Q. User-Agent로 모바일/PC를 나누고 싶어요. → User-Agent는 값 종류가 너무 많아 키가 폭발해요. 기기 유형 헤더처럼 값이 몇 개뿐인 걸로 나눠요.
- Q. 적중률이 낮은 원인을 어떻게 찾아요? → `cf-cache-status`나 CloudFront 로그의 결과 타입을 보고, BYPASS가 많으면 `Set-Cookie`·`private` 응답부터 의심해요.
</details>

<details>
<summary>Q. 로컬 캐시와 분산 캐시의 차이는 무엇이고, 같이 쓰면 어떤 문제가 있나요?</summary>

**답변(30초)**
로컬 캐시는 앱 서버 메모리 안에 있어 가장 빠르지만 서버마다 따로라서 서버끼리 값이 달라질 수 있어요. Redis 같은 분산 캐시는 모든 서버가 같은 값을 보지만 네트워크를 한 번 타요. 둘을 겹쳐 로컬 → Redis → DB로 쓰면 빠르지만, 값이 바뀔 때 모든 서버의 로컬 캐시를 지워야 해요. 그래서 로컬 TTL을 짧게 하거나 Pub/Sub으로 무효화 신호를 보내요.

**꼬리질문**
- Q. 가격처럼 정확해야 하는 값도 로컬 캐시에 두나요? → 정합성이 중요하면 로컬 캐시에서 빼거나 TTL을 아주 짧게 잡는 게 안전해요.
</details>

<details>
<summary>Q. 캐시 적중률 90%와 99%는 9%p 차이인데, 왜 큰 차이라고 하나요?</summary>

**답변(30초)**
다음 층으로 넘어가는 건 미스인데, 미스율이 10%에서 1%로 10배 줄기 때문이에요. 예를 들어 초당 1만 요청이면 오리진에 오는 요청이 1,000에서 100이 돼요. 평균 응답 시간도 미스 지연이 크게 좌우해서, 적중 1ms·미스 50ms라고 치면 5.9ms에서 1.49ms로 줄어요. 그래서 적중률은 퍼센트포인트보다 미스가 몇 배 줄었는지로 봐요.

**꼬리질문**
- Q. 계층이 여러 개면요? → 곱해져요. CDN 90%, Redis 95%면 DB엔 1만 × 0.1 × 0.05 = 50만 도착해요.
</details>

<details>
<summary>Q. 인기 상품 하나에 요청이 몰려 오리진이 죽을 것 같다면 어떻게 하나요?</summary>

**답변(30초)**
층별로 막아요. CDN에서는 같은 키 동시 미스를 하나로 합치는 요청 합치기와, 엣지 미스를 한 곳으로 모으는 오리진 실드나 티어드 캐시를 써요. 리버스 프록시에선 nginx의 proxy_cache_lock으로 한 요청만 통과시키고, 갱신 중엔 옛 응답을 줘요. 앱 층에선 로컬 캐시로 흡수하거나 Redis 키를 복제해요. 이때 캐시 키를 쿠키·헤더로 쪼개 놓으면 합치기가 안 되니 키를 단순하게 유지해요.

**꼬리질문**
- Q. 오리진 실드는 보안 기능인가요? → 아니요. 엣지들과 오리진 사이에 한 층 더 둔 캐시예요. 오리진 요청을 한 곳에서 내보내 중복을 줄여요.
- Q. 실드가 효과 없는 경우는? → 동적 콘텐츠, 캐시성이 낮거나 거의 안 쓰이는 파일이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 관리자가 상품 가격을 39,000원에서 29,000원으로 바꿨어요. 그런데 몇 분이 지나도 일부 사용자에게는 여전히 39,000원이 보이고, 새로고침할 때마다 가격이 바뀌기도 한다는 문의가 들어왔어요. 원인과 해결 방법은?</summary>

**상황 파악**
DB에는 새 가격이 있는데 일부 사용자에게만 옛 가격이 보여요. "새로고침마다 바뀐다"는 건 요청이 어느 서버·어느 캐시에 닿느냐에 따라 답이 다르다는 뜻이에요. 즉 **여러 캐시 층 중 어딘가에 옛 값이 남아 있는 상황**이에요. 아래는 일반적인 원인 추론이에요.

**원인 후보**
1. 앱 서버마다 있는 로컬 캐시(Caffeine) 중 일부만 갱신됨. 로드 밸런서가 다른 서버로 보내면 가격이 바뀌어 보임.
2. Redis 캐시를 가격 변경 때 지우지 않아 TTL이 끝날 때까지 옛 값.
3. 상품 상세 응답을 CDN에 캐시했고 퍼지를 안 함. 엣지마다 저장 시점이 달라 지역별로 다름.
4. 브라우저 캐시에 상품 상세 응답이 `max-age`로 남아 있음.
5. 층마다 TTL이 따로 돌아서, 최악엔 층별 TTL이 겹친 만큼 옛 값이 보일 수 있음(추론).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 가격 변경 시 Redis 삭제 + Pub/Sub으로 로컬 캐시 무효화 방송 | 서버 간 불일치 빠르게 해소 | 메시지 유실 시 일부 서버는 TTL까지 남음 |
| B. 가격은 로컬 캐시에서 빼고 Redis·DB에서만 읽기 | 서버 간 불일치 원천 차단 | Redis 왕복만큼 느림 |
| C. 상품 상세 CDN TTL을 짧게 + 가격 변경 시 해당 URL 퍼지 | CDN 옛 값 노출 시간 단축 | 퍼지 API 제한·비용, 짧은 TTL은 오리진 부하 증가 |
| D. 가격·재고를 본문에서 떼어 캐시 안 하는 별도 API로 | 가격은 항상 최신 | 요청 1개 추가, 오리진 부하 |
| E. 상품 상세 HTML/JSON은 브라우저에 `no-cache`(매번 검증) | 브라우저 옛 사본 문제 해결 | 매번 조건부 요청 |

**내가 고를 방법**
먼저 `Age`·`cf-cache-status` 헤더와 서버별 응답을 확인해 **어느 층이 옛 값을 들고 있는지** 찾아요. 그다음 가격은 돈과 직결되니 D로 본문과 분리하고, 가격 API는 B처럼 로컬 캐시 없이 Redis(변경 시 삭제)만 거치게 해요. 상품 설명·이미지는 그대로 CDN에 짧은 TTL로 둬서 적중률은 지켜요. 가격 분리가 당장 어렵다면 A와 C를 같이 적용해 노출 시간을 줄여요. 그리고 결제 시점엔 캐시가 아니라 **DB 가격으로 다시 계산**해서, 화면 가격이 늦게 바뀌어도 돈이 틀리지 않게 해요.

**채점 포인트**: 다층 캐시 진단(브라우저·CDN·로컬·Redis), 서버별 로컬 캐시 불일치, 변경 시 무효화(Redis 삭제·Pub/Sub·CDN 퍼지), TTL 트레이드오프, 정적/동적 분리(가격 별도 API), 결제 시점 재검증, 헤더로 원인 층 확인.
</details>

<details>
<summary>상황: 프론트엔드를 배포했는데, 일부 사용자 화면이 깨졌어요. 확인해 보니 새 HTML은 받았는데 CSS는 옛 버전(`style.css`)을 쓰고 있어요. CDN 퍼지도 했는데 아직 깨진다는 사람이 있어요. 왜 그렇고, 어떻게 고치나요?</summary>

**상황 파악**
HTML과 CSS의 버전이 어긋났어요. 같은 이름 `style.css`를 덮어써 배포했기 때문에, 어딘가 캐시에 남은 옛 CSS가 새 HTML과 섞였어요. CDN은 퍼지했으니, 남은 곳은 **서버가 지울 수 없는 캐시**예요.

**원인 후보**
1. 브라우저 캐시: `style.css`를 `max-age`로 받아 둔 브라우저는 만료까지 서버에 다시 묻지 않음.
2. 회사·통신사 프록시 같은 중간 공유 캐시: CDN 퍼지가 닿지 않음.
3. 퍼지 자체가 아직 반영 전: Cloudflare 문서도 API 200은 접수일 뿐이라고 안내함.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 파일명에 내용 해시 넣기(`style.3f2a.css`) + 긴 `max-age`, HTML은 짧은 TTL 또는 `no-cache` | 새 HTML이 새 이름을 가리켜 옛 캐시와 절대 안 섞임. 퍼지 불필요, 롤백 쉬움 | 빌드 도구 설정 필요, 옛 파일도 한동안 남겨 둬야 함 |
| B. 같은 이름 유지 + 배포마다 CDN 퍼지 | 빌드 변경 없음 | 브라우저·중간 프록시 사본은 못 지움, 퍼지 비용·제한 |
| C. CSS에 `max-age`를 아주 짧게 | 금방 새 파일 | 적중률 하락, 매번 오리진 검증 |
| D. 쿼리로 버전(`style.css?v=2`) | 간단 | CDN이 쿼리를 키에서 무시하도록 설정돼 있으면 효과 없음 |

**내가 고를 방법**
A를 골라요. 이 방식을 **캐시 버스팅**(cache busting, 이름을 바꿔 캐시를 우회)이라고 불러요. 내용이 바뀌면 이름이 바뀌니 정적 파일은 아주 오래 캐시해도 안전하고, 진짜 바뀌어야 하는 HTML만 짧게 캐시하면 돼요. CloudFront도 자주 바뀌는 파일엔 버전 붙인 파일명을 권해요. 배포 순서는 새 CSS·JS를 먼저 올리고 HTML을 나중에 바꾸며, 옛 파일은 옛 HTML을 들고 있는 사용자를 위해 한동안 남겨 둬요(배포 순서·옛 파일 보존은 공식 문서가 아니라 일반적인 운영 방법이에요). 퍼지는 HTML처럼 이름을 못 바꾸는 파일에만 보조로 써요.

**채점 포인트**: 브라우저 캐시는 서버가 못 지움, 퍼지는 CDN만 지움, 파일명 해시(캐시 버스팅), 정적은 긴 max-age·HTML은 짧게/no-cache, 배포 순서(에셋 먼저), 옛 파일 보존, 쿼리 버전의 함정.
</details>

<details>
<summary>상황: 대형 할인 이벤트 시작 순간, 새로 올린 이벤트 배너 이미지와 이벤트 페이지에 전 세계 요청이 몰렸어요. CDN이 있는데도 오리진 서버 요청이 치솟아 오리진이 다운됐어요. 왜 CDN이 못 막았고, 어떻게 해야 하나요?</summary>

**상황 파악**
새로 올린 파일이라 모든 엣지에 아직 저장본이 없어요. 이벤트 시작과 동시에 **모든 엣지가 동시에 캐시 미스**를 내고, 각 엣지가 저마다 오리진에 물으러 와서 오리진이 버티지 못했어요. 일종의 캐시 스탬피드가 CDN 층에서 일어난 거예요.

**원인 후보**
1. 엣지(POP)가 많을수록 같은 파일을 오리진에 각자 요청함. 중간 층(실드·상위 티어)이 없음.
2. 캐시 키가 쿠키·헤더·추적용 쿼리로 쪼개져 있어 요청 합치기가 안 되고, 같은 파일이 여러 키로 미스남.
3. 이벤트 페이지 응답에 `Set-Cookie`나 `private`가 붙어 아예 BYPASS(캐시 불가) 처리.
4. TTL이 짧아 피크 중에도 계속 만료·재요청.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Origin Shield(CloudFront) / Tiered Cache(Cloudflare) 켜기 | 모든 엣지 미스가 한 곳을 거쳐 오리진엔 최소 1개만 | 추가 요금(CloudFront), 한 홉 늘어남 |
| B. 캐시 키 정리(필요한 쿼리만, 쿠키·User-Agent 제외) | 요청 합치기가 동작, 적중률 상승 | 실수로 응답이 다른 요청까지 합치면 잘못된 응답 |
| C. 오리진 앞 nginx `proxy_cache_lock` + `proxy_cache_use_stale updating` | CDN 뒤에서 한 번 더 동시 미스를 1개로 | 기다리는 요청의 지연 증가 |
| D. 이벤트 전 미리 요청해 캐시 데우기(워밍) | 시작 순간 미스 자체를 줄임 | 엣지가 많으면 모두 데우기 어려움 |
| E. `stale-while-revalidate`, `max-age` 늘리기 | 만료 순간에도 옛 응답으로 버팀 | 변경이 늦게 반영 |

**내가 고를 방법**
A와 B를 먼저 해요. 실드가 있으면 엣지 수백 곳의 미스가 한 지점으로 모이고, 같은 키 요청은 합쳐져 오리진엔 거의 하나만 가요. 그런데 키가 쪼개져 있으면 합치기가 안 되니 B로 키를 정리하고, 이벤트 페이지 응답에서 `Set-Cookie`를 빼 BYPASS를 없애요. 사용자별 부분(로그인 상태, 쿠폰)은 별도 API로 분리해요. 오리진 쪽 마지막 방어로 C를 둬요. 이벤트처럼 시작 시각을 아는 경우엔 D로 주요 파일을 미리 데우면 더 안전해요(워밍은 일반적인 운영 방법이고, 효과는 CDN 구조에 따라 달라요).

**채점 포인트**: 동시 미스(CDN 층 스탬피드) 진단, 오리진 실드/티어드 캐시, 요청 합치기와 캐시 키의 관계, Set-Cookie·private로 인한 BYPASS, proxy_cache_lock, stale 응답, 정적/동적 분리.
</details>

## 필기 포인트

- **사설 캐시**(브라우저, 한 사용자) vs **공유 캐시**(CDN·리버스 프록시, 여러 사용자).
- HTTP 캐시 키 = 최소 메서드 + URL, `Vary` 헤더의 요청 헤더가 추가. `Vary: *`면 재사용 불가.
- `s-maxage`는 공유 캐시 전용, `private`는 공유 캐시 저장 금지.
- `Age` = 오리진에서 만들어진 뒤 흐른 초.
- CloudFront 기본 TTL 24시간(오리진이 캐시 헤더를 안 줄 때). GET·HEAD는 항상 캐시.
- Cloudflare는 HTML·JSON 기본 미캐시, **확장자**로 판단. `Set-Cookie` 있으면 캐시 안 함.
- 요청 합치기는 **같은 캐시 키**끼리만.
- 오리진 실드 = 캐시 계층(보안 아님).
- 퍼지는 CDN만 지움 → 자주 바뀌는 파일은 **파일명 버전**.
