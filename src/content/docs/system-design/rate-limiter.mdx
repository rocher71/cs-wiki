:::tip[한 줄 요약]
**처리율 제한기**(rate limiter, 정해진 시간 동안 받을 요청 수를 제한하는 장치)는 한 사용자가 너무 많이 보내는 요청을 막아 서버와 비용과 다른 사용자를 지켜요. 알고리즘은 순간 몰림을 어느 정도 허용하는 **토큰 버킷**이 가장 흔하고, 서버가 여러 대면 카운터를 **Redis**에 두고 **Lua 스크립트**로 원자적으로 계산해요. 막을 때는 **429 Too Many Requests**와 `Retry-After`로 언제 다시 오라고 알려 줘요.
:::

:::note[처음이라면 여기까지]
① 처리율 제한은 "1분에 100번까지만" 같은 규칙이에요. 한 사람이 서버를 독차지하거나 실수로 폭주시키는 걸 막아요.

② 알고리즘은 다섯 가지가 있지만, 먼저 **토큰 버킷**(토큰이 일정 속도로 채워지고 요청마다 하나씩 쓰는 방식) 하나만 확실히 이해하세요.

③ 서버가 여러 대면 각자 세면 안 되고, Redis 한 곳에 모아서 세요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

놀이공원 입구를 떠올려 보세요. 안이 너무 붐비면 사고가 나니까 입구에서 "1분에 몇 명만 입장"이라고 정해요. 줄 선 사람이 많아도 정해진 인원만 들여보내고, 나머지는 "잠시 후 다시 오세요"라는 안내를 받아요.

입구 직원은 입장권 통을 하나 갖고 있다고 해 볼게요. 통에는 일정 시간마다 입장권이 한 장씩 채워지고, 통이 가득 차면 더는 안 들어가요. 손님은 입장권을 한 장 받아야 들어갈 수 있어요. 한동안 손님이 없었다면 통에 입장권이 꽉 차 있어서, 단체 손님이 한꺼번에 와도 통에 있는 만큼은 바로 들어가요. 이게 **토큰 버킷**이에요.

서버도 똑같아요. 요청 하나가 손님 한 명이고, 처리율 제한기가 입구 직원이에요. 직원이 막아 주니까 안쪽 서버와 데이터베이스는 감당할 수 있는 만큼만 일해요.

단, 실제로는 "놀이공원 전체 인원"보다 **사용자 한 명당** 몇 번으로 제한하는 경우가 많아요. 한 사람이 너무 많이 보내도 다른 사람은 정상적으로 쓸 수 있게 하려는 거예요. 전체 인원을 지키는 장치는 따로 있어요(아래 "부하 차단"에서 다뤄요).

## 제대로 알기

### 왜 필요한가

처리율 제한이 없으면 생기는 일을 세 가지로 묶을 수 있어요.

| 문제 | 예 | 제한기가 하는 일 |
|---|---|---|
| 남용 | 로그인 무차별 대입, 크롤러가 쉬지 않고 긁어 감, 공격성 대량 요청 | 한 키(사용자·IP·API 키)가 보낼 수 있는 양을 묶음 |
| 비용 | 외부 유료 API(문자 발송, 지도 등)를 대신 부르는 엔드포인트가 폭주 | 돈이 나가는 호출을 상한선 아래로 유지 |
| 장애 전파 | 한 고객의 버그 난 스크립트가 무한 반복 → DB가 느려짐 → 다른 고객까지 실패 | 문제를 일으킨 한 사용자만 429를 받고 나머지는 정상 |

Stripe는 사용자별 처리율 제한을 "가장 먼저 도입할 장치"로 꼽아요. 한 사용자의 폭주가 다른 사용자를 망치지 않게 하는 **공정성**이 핵심이에요.

### 막을 때는 이렇게 답해요: 429와 Retry-After

- **429 Too Many Requests**: "정해진 시간 안에 요청을 너무 많이 보냈다"는 뜻의 HTTP 상태 코드예요. RFC 9110이 아니라 **RFC 6585**에 정의돼 있어요.
- 응답 본문에 상황 설명을 넣는 게 권장돼요.
- **`Retry-After`** 헤더(몇 초 뒤, 또는 어느 시각 이후 다시 오라는 안내)는 넣어도 되는 선택 사항이에요. 값은 초 단위 숫자(`120` = 2분 뒤)나 HTTP 날짜 형식이에요.
- 429 응답은 캐시가 저장하면 안 돼요.

RFC 6585는 "누구를 기준으로, 무엇을 셀지"는 정하지 않아요. 사용자 ID로 셀지, IP로 셀지, 엔드포인트별로 셀지는 설계자가 정해요.

클라이언트는 429를 받으면 바로 다시 보내지 말고 `Retry-After`만큼 기다려야 해요. 다 같이 즉시 재시도하면 더 막혀요. 재시도 간격을 늘리는 방법은 [장애 대응 패턴](../../architecture/resilience/)에 있어요.

### 알고리즘 5종 비교

먼저 표로 전체를 보고, 아래에서 하나씩 볼게요.

| 알고리즘 | 한 줄 동작 | 정확도 | 메모리(키 하나당) | 순간 몰림(burst) |
|---|---|---|---|---|
| 토큰 버킷 | 토큰이 일정 속도로 차고, 요청마다 1개 씀 | 평균 속도를 잘 지킴 | 숫자 2개(남은 토큰, 마지막 시각) | 버킷 용량만큼 허용 |
| 누출 버킷 | 요청을 통에 넣고 일정 속도로 흘려보냄 | 출력 속도가 일정 | 큐 길이만큼 | 대기시키거나 버림 |
| 고정 윈도 카운터 | 1분 같은 고정 칸마다 개수를 셈 | 칸 경계에서 최대 2배 통과 | 숫자 1개 | 경계에서 의도치 않게 2배 |
| 슬라이딩 윈도 로그 | 요청 시각을 모두 기록해 최근 1분 개수를 셈 | 정확 | 요청 수만큼 | 없음(정확히 N개) |
| 슬라이딩 윈도 카운터 | 직전 칸과 현재 칸 개수를 비율로 섞음 | 근사치지만 오차 작음 | 숫자 2개 | 거의 없음 |

### 토큰 버킷 자세히

**토큰 버킷**(token bucket)은 두 숫자로 정해져요.

- **채우는 속도**: 초당 몇 개씩 토큰이 생기는가. 이게 **평균 처리율**이 돼요.
- **버킷 용량**: 토큰이 최대 몇 개까지 쌓이는가. 이게 **한 번에 몰려도 받아 주는 양**이 돼요.

요청이 오면 이렇게 판단해요.

1. 마지막으로 본 시각부터 지금까지 흐른 시간만큼 토큰을 채워요(용량을 넘지는 않게).
2. 토큰이 1개 이상이면 1개 빼고 통과.
3. 없으면 거절(429).

실제로는 타이머로 토큰을 넣지 않아요. 요청이 올 때 "지난번 이후 몇 초 지났나"를 계산해서 한꺼번에 채워요. 그래서 키 하나에 숫자 두 개(남은 토큰, 마지막 시각)만 저장하면 돼요.

Stripe의 요청 속도 제한기가 토큰 버킷이고, Spring Cloud Gateway의 `RedisRateLimiter`도 같은 방식이에요. 거기선 이름이 이렇게 붙어 있어요.

| Spring Cloud Gateway 설정 | 뜻 |
|---|---|
| `replenishRate` | 초당 채우는 토큰 수(평균 속도) |
| `burstCapacity` | 버킷 용량(한 번에 받아 줄 최대치). 0이면 전부 차단 |
| `requestedTokens` | 요청 하나가 쓰는 토큰 수(기본 1) |

두 값을 같게 두면 고른 속도만 허용하고, `burstCapacity`를 크게 두면 순간 몰림을 더 받아 줘요. 게이트웨이에서 설정하는 방법은 [API 게이트웨이](../../architecture/api-gateway-discovery/)에 있어요.

### 누출 버킷은 뭐가 다른가

**누출 버킷**(leaky bucket)은 바닥에 구멍 난 양동이예요. 요청은 양동이(큐)에 쌓이고, 구멍으로 일정한 속도로만 빠져나가 처리돼요. 양동이가 넘치면 버려요.

- 토큰 버킷: 쌓아 둔 토큰만큼 몰림을 **바로 통과**시켜요.
- 누출 버킷: 몰림을 **줄 세워서 고르게 펴요**(대기 또는 거절).

nginx의 `limit_req`가 이 방식이라고 공식 문서에 적혀 있어요. 다만 자료마다 "누출 버킷"이라는 이름을 조금씩 다르게 쓰니, 면접에서는 "요청을 큐에 담아 일정 속도로 흘려보낸다"처럼 동작으로 설명하는 게 안전해요.

### 고정 윈도의 경계 문제 (2N)

**고정 윈도 카운터**(fixed window counter)는 시간을 1분, 10초 같은 고정 칸으로 자르고 칸마다 개수를 세요. Redis `INCR`(숫자 1 올리기)과 `EXPIRE`(만료 시간 걸기) 두 명령이면 만들 수 있을 만큼 단순해요.

약점은 **칸 경계**예요. 칸 끝 직전에 N건, 다음 칸 시작 직후에 N건을 보내면 둘 다 "자기 칸에선 N건"이라 모두 통과해요. 아주 짧은 시간에 2N건이 지나가요.

<Aside type="note" title="실험 예시: 10초당 5건 제한">
Redis로 직접 재 본 예시예요. 한도는 "10초 칸마다 5건", 칸 끝 1초 전에 6건을 보내고 바로 다음 칸 시작에 6건을 또 보냈어요.

- 고정 윈도: 첫 칸에서 5건 통과·1건 거절, 다음 칸에서 카운터가 새로 시작돼 또 5건 통과. **약 1초 사이에 10건**이 지나갔어요. 한도의 2배예요.
- 토큰 버킷(용량 5, 초당 0.5개)으로 같은 패턴을 보냈더니: 처음 5건 통과, 그 뒤 1초 동안은 토큰이 1개도 안 차서 전부 거절. **1초 사이 5건**만 통과했어요.

토큰 버킷도 처음 가득 찬 상태에선 용량(5)만큼은 한꺼번에 받아 줘요. 다만 "칸이 바뀌었으니 다시 가득"이 없어서 2배가 생기지 않아요.
</Aside>

### 슬라이딩 윈도: 로그와 카운터

경계 문제를 없애려면 "고정 칸" 대신 "지금부터 거꾸로 1분"을 봐야 해요. 이걸 **슬라이딩 윈도**(sliding window, 미끄러지는 창)라고 해요.

**슬라이딩 윈도 로그**(sliding window log)는 요청 시각을 전부 저장해요(Redis에선 [Sorted Set](../../redis/data-structures/)이 잘 맞아요). 새 요청이 오면 1분보다 오래된 기록을 지우고 남은 개수를 세요. 정확하지만 요청 수만큼 메모리를 써요. 거절된 요청까지 기록하면 계속 두드리는 클라이언트는 영영 못 들어올 수 있어서, 무엇을 기록할지 정해야 해요.

**슬라이딩 윈도 카운터**(sliding window counter)는 숫자 두 개로 근사해요. 직전 칸 개수에 "지금 창과 겹치는 비율"을 곱하고 현재 칸 개수를 더해요.

Cloudflare 블로그(2017)의 예시로 계산해 볼게요.

- 한도: 분당 50건
- 직전 1분: 42건, 현재 1분: 18건, 현재 칸이 시작된 지 15초
- 최근 60초 창은 직전 칸의 마지막 45초와 겹쳐요 → 42 × (45/60) + 18 = **49.5**
- 50보다 작으니 이번 요청은 통과, 바로 한 건 더 오면 초과예요.

"직전 칸 안에서 요청이 고르게 왔다"고 가정한 근사치예요. 그래도 Cloudflare가 실제 트래픽 4억 건(출처 27만 곳)으로 검증했을 때 잘못 허용·차단된 요청은 **0.003%**였고, 실제 속도와 근사 속도의 평균 차이는 6%였다고 해요(Cloudflare 블로그, 2017-06).

### 어디에 두나

| 위치 | 장점 | 단점 |
|---|---|---|
| 클라이언트(앱·브라우저) | 서버까지 안 와서 가장 가벼움 | 사용자가 고칠 수 있어 믿을 수 없음. 보호 장치로는 못 씀 |
| [API 게이트웨이](../../architecture/api-gateway-discovery/)·리버스 프록시(nginx, Envoy) | 모든 서비스 앞에서 한 번에 처리, 백엔드는 막힌 요청을 아예 못 봄 | 요청 내용(주문 금액 등)을 보고 하는 세밀한 제한은 어려움 |
| 앱 미들웨어(서비스 코드 안) | 로그인 사용자·요청 내용까지 보고 판단 | 서비스마다 중복 구현, 이미 서버 자원을 쓴 뒤 막음 |

보통은 **게이트웨이에서 사용자별 기본 제한**을 걸고, 로그인 실패 횟수처럼 업무 의미가 있는 제한만 앱에서 해요. Envoy는 인스턴스마다 거르는 **로컬 제한**과 외부 서비스로 모아 세는 **글로벌 제한**을 둘 다 제공하고, 로컬로 큰 몰림을 먼저 거른 뒤 글로벌로 세밀하게 거르는 2단 조합을 소개해요.

### 서버가 여러 대면: Redis + Lua

게이트웨이나 앱 서버가 여러 대인데 카운터를 각 서버 메모리에 두면, 로드 밸런서가 요청을 나눠 주는 만큼 **한도가 서버 수만큼 늘어나요**. 서버 4대에 "분당 100회"면 사실상 400회까지 통과할 수 있어요.

그래서 카운터를 Redis 같은 공유 저장소 한 곳에 둬요. Stripe, Spring Cloud Gateway, Envoy 글로벌 제한 참조 구현이 모두 Redis를 써요.

공유만으로는 부족해요. "읽기 → 계산 → 쓰기"를 서버에서 따로 하면, 두 서버가 동시에 "토큰 1개 남음"을 읽고 둘 다 통과시켜요. 이런 걸 **경쟁 조건**(race condition, 동시에 실행돼 결과가 꼬이는 상황)이라고 해요.

해결은 계산을 Redis 안에서 **Lua 스크립트**로 한 번에 하는 거예요. Redis는 스크립트가 도는 동안 다른 명령을 실행하지 않아서, 스크립트의 효과는 "전부 일어났거나, 아직 하나도 안 일어났거나" 둘 중 하나예요. 이걸 **원자적**(atomic, 쪼개지지 않음)이라고 해요.

```lua
-- 토큰 버킷 한 번 판단 (KEYS[1]=사용자 키, ARGV[1]=용량, ARGV[2]=초당 채움)
local cap, rate = tonumber(ARGV[1]), tonumber(ARGV[2])
local t = redis.call('TIME')                 -- Redis 서버 시계 사용
local now = t[1] + t[2] / 1e6
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap          -- 처음이면 가득 찬 상태
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) * rate)  -- 흐른 시간만큼 채움
local ok = 0
if tokens >= 1 then tokens = tokens - 1; ok = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) * 2)  -- 안 쓰는 키 정리
return {ok, tostring(tokens)}
```

고정 윈도를 `INCR` 뒤 `EXPIRE`로 따로 보내는 것도 위험해요. 그 사이 연결이 끊기면 만료 없는 키가 남아 그 사용자가 영원히 막힐 수 있어요. 이 부분은 [Redis 실전 활용](../../redis/redis-practice/)에서 자세히 다뤄요.

### 공통 뼈대로 설계해 보기: "사용자당 분당 100회"

[시스템 설계 면접 푸는 법](../design-approach/)의 순서대로 풀어 볼게요.

**1. 요구사항**
- 기능: 로그인 사용자 ID별로 API 호출을 분당 100회로 제한. 초과 시 429 + `Retry-After`.
- 비기능: 제한기 때문에 응답이 눈에 띄게 느려지면 안 됨. 서버가 여러 대여도 한도가 정확해야 함. 제한기가 고장 나도 API 전체가 멈추면 안 됨.

**2. 규모 추정** (숫자는 연습용 가정이에요)
- 동시에 활동하는 사용자 100만 명, 키 하나에 숫자 두 개 + 키 이름이면 대략 100바이트 안팎 → 100만 × 100B ≈ 100MB. Redis 메모리 한 대에 충분히 들어가는 크기예요.
- API 전체가 초당 1만 요청이면, 요청마다 Lua 호출 1번 → Redis에도 초당 1만 번. 실제로 버티는지는 부하 테스트로 확인하고, 모자라면 Redis 클러스터로 키를 나눠요.

**3. 첫 설계**
1. 요청이 게이트웨이에 도착
2. 사용자 ID로 키 생성(예: `rl:user:42`)
3. Redis에 Lua 스크립트 한 번 호출 → 허용/거절 결정
4. 허용이면 백엔드로 전달, 거절이면 429 + `Retry-After`

**4. 알고리즘 선택**
토큰 버킷, 채우는 속도는 100/60 ≈ 초당 1.67개. 용량은 정책 결정이에요. 100으로 두면 1분 동안 쉬던 사용자가 1초 만에 100건을 보낼 수 있고, 20으로 두면 몰림은 20건까지만 받아 줘요. 백엔드가 순간 몰림에 약하면 용량을 줄이고, 정상 사용자가 화면 하나 열 때 여러 API를 동시에 부른다면 그만큼은 받아 줘야 해요.

**5. 병목과 개선**
- Redis가 한 곳에 몰림 → 클러스터로 나누기. 사용자별 키라 잘 나뉘어요.
- Redis가 죽으면 → 아래 fail open/closed 정책.
- 네트워크 왕복이 매 요청 추가됨 → 게이트웨이와 Redis를 가까이 두고, 큰 몰림은 각 게이트웨이의 로컬 제한으로 먼저 거르는 2단 구성.

**6. 트레이드오프 정리**
정확도(Redis 공유) ↔ 가용성(Redis 의존), 몰림 허용(큰 용량) ↔ 백엔드 보호(작은 용량)를 어디에 맞출지 말할 수 있으면 돼요.

### 심화: Redis가 죽으면 fail open vs fail closed

제한기가 Redis에 의존하니, Redis가 응답하지 않을 때 어떻게 할지 정해 둬야 해요.

- **fail open**(장애 시 통과): 제한 없이 요청을 들여보내요. API는 계속 동작하지만 그동안 제한이 없어요.
- **fail closed**(장애 시 차단): 전부 막아요. 안전하지만 Redis 하나 때문에 서비스 전체가 멈춰요.

Stripe는 제한기 버그나 Redis 장애가 API를 멈추지 않도록 **예외를 잡아서 통과시키라**(fail open)고 권해요. 반대로 로그인 시도처럼 막지 않으면 보안 사고가 나는 경로는 fail closed나 "Redis 대신 서버별 로컬 제한으로 대체"를 고민할 만해요.

Envoy 글로벌 제한 필터에도 같은 선택지가 있어요. `failure_mode_deny`가 false면 제한 서비스 오류 때 통과시키고, true면 500으로 막아요.

### 심화: 처리율 제한과 부하 차단은 달라요

Stripe는 네 종류를 구분해요.

| 종류 | 무엇을 막나 | 목적 |
|---|---|---|
| 요청 속도 제한기 | 사용자당 초당 N건 | 사용자별 공정성(가장 기본) |
| 동시 요청 제한기 | 한 사용자의 진행 중인 요청 수 | CPU를 많이 쓰는 엔드포인트 보호 |
| 전체 사용량 부하 차단기 | 중요 요청용 용량을 남겨 두고 나머지를 503 | 시스템 전체 보호 |
| 워커 사용률 부하 차단기 | 사고 시 우선순위 낮은 요청부터 버림 | 최후 방어선 |

앞의 둘은 "사용자별 제한", 뒤의 둘은 **부하 차단**(load shedding, 서버가 버틸 수 있게 일부 요청을 일부러 버림)이에요. 이벤트 오픈처럼 모든 사용자가 정상적으로 몰리는 상황은 사용자별 제한만으로는 못 막아요. 그럴 땐 [대기열](../waiting-queue/) 같은 장치가 필요해요.

Stripe는 운영 팁도 남겼어요. 명확한 오류 메시지, 제한기를 끌 수 있는 스위치([기능 플래그](../../architecture/feature-flag/)), 발동 횟수 모니터링, 그리고 처음엔 막지 않고 관찰만 하는 dark launch로 한도를 맞춰 보라는 거예요.

### 심화: nginx limit_req의 함정

nginx `limit_req`는 설정 몇 줄로 쓸 수 있어서 많이 써요. 헷갈리는 점이 몇 개 있어요.

```nginx
# IP별 평균 초당 1건, 넘치면 5건까지 줄 세움
limit_req_zone $binary_remote_addr zone=one:10m rate=1r/s;
location /api/ {
    limit_req zone=one burst=5;
    limit_req_status 429;   # 안 쓰면 기본 503
}
```

- **거절 기본 상태 코드는 503**이에요. 429로 주려면 `limit_req_status 429`를 써야 해요.
- `burst=5`는 5건을 바로 통과시키는 게 아니라 **줄 세워서 늦게 처리**해요. 바로 처리하려면 `nodelay`를 붙여요.
- `limit_req_dry_run on`을 켜면 실제로 막지 않고 세기만 해서, 한도를 시험해 볼 수 있어요.
- 상태가 nginx 인스턴스 하나의 공유 메모리에 있어요. nginx가 여러 대면 각자 따로 세요.

### 심화: 남은 한도를 알려 주는 헤더

현장에서 자주 보이는 `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`은 업체들이 관례로 쓰는 헤더라 표준이 아니에요.

IETF에서 표준 헤더를 만드는 중인데 아직 **초안**(Internet-Draft)이고 RFC가 아니에요. 2026-11 기준 최신판(-12)은 두 헤더를 정의해요.

- `RateLimit-Policy: "fixedwindow";q=100;w=60` → 정책: 60초에 100번
- `RateLimit: "fixedwindow";a=99;w=50` → 현재: 50초 동안 99번 남음

예전 판에는 `RateLimit-Limit/Remaining/Reset`처럼 헤더를 나눠 쓰던 형식이 있었어요. 초안이라 형식이 바뀔 수 있으니, 쓸 때는 몇 번째 판을 따랐는지 적어 두는 게 좋아요.

### 심화: Lua 스크립트 주의점

- 스크립트가 쓰는 키 이름은 반드시 `KEYS` 인자로 넘겨요. 그래야 Redis 클러스터에서 키가 어느 노드에 있는지 알고 제대로 동작해요.
- 스크립트 캐시는 휘발성이라 재시작이나 페일오버 뒤 `EVALSHA`가 `NOSCRIPT` 오류를 낼 수 있어요. 클라이언트는 이때 스크립트를 다시 올려요.
- 스크립트가 도는 동안 Redis 전체가 멈추니 짧게 써요.
- 시각은 스크립트 안에서 Redis `TIME`으로 얻으면 앱 서버들의 시계가 조금씩 달라도 Redis 한 곳의 시계로 계산돼요. 최근 Redis(7.0부터)는 스크립트 안에서 `TIME`을 쓰는 데 제약이 없어요.
- `MULTI/EXEC` 트랜잭션은 앞 명령 결과를 보고 분기할 수 없어서, "읽고 판단하고 쓰는" 토큰 버킷에는 Lua가 맞아요.

### 심화: 단정하면 안 되는 기본값들

문서에서 확인하지 못한 기본값은 면접에서도 "확인해 봐야 한다"고 말하는 게 안전해요.

- Spring Cloud Gateway: `replenishRate`·`burstCapacity`의 기본값은 문서에 없어요(직접 설정하는 값으로 보면 돼요). 기본 키는 로그인 사용자 이름이고, 키가 비면 기본으로 거절해요. 이때 어떤 상태 코드를 주는지, Redis 장애 시 어떻게 하는지는 해당 문서에 적혀 있지 않아요.
- Envoy: `failure_mode_deny`의 기본값이 false(통과)로 보이지만, 해당 페이지에 명시돼 있진 않아요.

## 면접 질문

<details>
<summary>Q. 처리율 제한은 왜 필요한가요?</summary>

**답변(30초)**
한 사용자가 너무 많은 요청을 보내서 서버와 다른 사용자를 망치지 않게 하려고요. 공격이나 크롤링 같은 남용을 막고, 버그 난 클라이언트의 무한 반복이 DB까지 번지는 장애 전파를 막아요. 외부 유료 API를 부르는 기능이라면 비용 폭주도 막아요. 핵심은 사용자별 공정성이에요.

**꼬리질문**
- Q. 클라이언트에서 막으면 안 되나요? → 사용자가 앱을 고치거나 직접 요청을 보낼 수 있어서 믿을 수 없어요. 서버 쪽에 있어야 해요.
- Q. 무엇을 기준으로 세나요? → 로그인 사용자 ID, API 키, IP 등. 로그인 전 경로는 IP, 로그인 후는 사용자 ID가 흔해요.
</details>

<details>
<summary>Q. 제한에 걸린 요청에는 어떻게 응답하나요?</summary>

**답변(30초)**
429 Too Many Requests로 답해요. 언제 다시 오면 되는지 `Retry-After` 헤더에 초나 시각으로 넣어 줄 수 있고, 본문에 이유를 설명하는 게 좋아요. 429는 RFC 6585에 정의된 코드예요. 남은 한도를 알려 주는 헤더는 아직 IETF 초안 단계라, 현장에선 `X-RateLimit-*` 같은 업체 관례 헤더도 많이 써요.

**꼬리질문**
- Q. 503과 차이는? → 503은 서버가 일시적으로 처리 못 하는 상태, 429는 "당신이 너무 많이 보냈다"예요. nginx `limit_req`는 기본이 503이라 `limit_req_status 429`로 바꿔야 해요.
- Q. 클라이언트는 429를 받으면? → `Retry-After`만큼 기다리고, 없으면 지수 백오프(기다리는 시간을 1·2·4초처럼 늘림)에 지터(무작위로 조금씩 어긋나게 함)를 섞어 재시도해요.
</details>

<details>
<summary>Q. 토큰 버킷 알고리즘을 설명해 주세요.</summary>

**답변(30초)**
버킷에 토큰이 일정 속도로 채워지고, 요청마다 토큰 하나를 써서 통과해요. 토큰이 없으면 거절해요. 채우는 속도가 평균 처리율이 되고, 버킷 용량만큼은 순간 몰림을 받아 줘요. 키 하나에 남은 토큰과 마지막 시각만 저장하면 돼서 가볍고, Stripe와 Spring Cloud Gateway가 이 방식을 써요.

**꼬리질문**
- Q. 토큰을 타이머로 채우나요? → 아니요. 요청이 올 때 지난번 이후 흐른 시간만큼 한꺼번에 계산해 채워요.
- Q. 요청마다 비용이 다르면? → 요청 하나가 쓰는 토큰 수를 다르게 해요(Spring Cloud Gateway의 `requestedTokens`).
</details>

<details>
<summary>Q. 토큰 버킷과 누출 버킷은 어떻게 다른가요?</summary>

**답변(30초)**
토큰 버킷은 쌓아 둔 토큰만큼 몰린 요청을 바로 통과시켜요. 누출 버킷은 요청을 큐에 넣고 일정한 속도로만 내보내서, 몰림을 줄 세워 고르게 펴요. 그래서 토큰 버킷은 사용자 경험에 유연하고, 누출 버킷은 뒤쪽 서버에 고른 부하를 줘요. nginx `limit_req`가 누출 버킷 방식이에요.

**꼬리질문**
- Q. nginx `burst`는 몰림을 바로 통과시키나요? → 기본은 대기시켜요. 바로 처리하려면 `nodelay`를 붙여요.
</details>

<details>
<summary>Q. 고정 윈도 카운터의 문제는 무엇이고, 어떻게 보완하나요?</summary>

**답변(30초)**
칸 경계에서 한도의 2배가 통과할 수 있어요. 칸 끝 직전에 N건, 다음 칸 시작 직후에 N건을 보내면 둘 다 자기 칸 기준으론 N건이라 짧은 시간에 2N건이 지나가요. 보완은 "지금부터 거꾸로 1분"을 보는 슬라이딩 윈도예요. 요청 시각을 다 저장하는 로그 방식은 정확하지만 메모리가 많이 들고, 직전 칸과 현재 칸 카운터를 비율로 섞는 카운터 방식은 근사지만 가벼워요.

**꼬리질문**
- Q. 슬라이딩 윈도 카운터는 얼마나 정확한가요? → 직전 칸에 요청이 고르게 왔다고 가정한 근사예요. Cloudflare가 4억 건으로 검증했을 때 잘못 판단한 요청이 0.003%였다고 공개했어요.
- Q. 토큰 버킷도 몰림을 허용하는데 뭐가 달라요? → 토큰 버킷은 용량만큼만 허용하고, 칸이 바뀐다고 다시 가득 차지 않아서 경계 2배가 없어요.
</details>

<details>
<summary>Q. 처리율 제한기는 어디에 두나요?</summary>

**답변(30초)**
보통 API 게이트웨이나 nginx·Envoy 같은 리버스 프록시에 둬요. 모든 서비스 앞에서 한 번에 처리하고, 막힌 요청이 백엔드 자원을 쓰지 않아서예요. 로그인 실패 횟수처럼 업무 의미가 있는 제한은 앱 안에서 해요. 클라이언트에만 두는 건 우회할 수 있어서 보호 장치가 못 돼요.

**꼬리질문**
- Q. 게이트웨이가 여러 대면? → 카운터를 Redis에 모아요. 큰 몰림은 각 인스턴스의 로컬 제한으로 먼저 거르는 2단 구성도 있어요(Envoy).
</details>

<details>
<summary>Q. 서버 여러 대에서 한도를 정확히 지키려면 어떻게 하나요?</summary>

**답변(30초)**
카운터를 각 서버 메모리가 아니라 Redis 같은 공유 저장소에 둬요. 그리고 읽고 계산하고 쓰는 과정을 Lua 스크립트 하나로 Redis 안에서 실행해요. Redis는 스크립트를 원자적으로 실행해서, 두 서버가 동시에 "1개 남음"을 읽고 둘 다 통과시키는 경쟁 조건이 생기지 않아요.

**꼬리질문**
- Q. MULTI/EXEC로 묶으면 안 되나요? → MULTI 안에서는 앞 명령 결과를 보고 분기할 수 없어서, 판단이 필요한 토큰 버킷엔 Lua가 맞아요.
- Q. 시각은 어디 걸 쓰나요? → 스크립트 안에서 Redis `TIME`을 쓰면 앱 서버 간 시계 차이가 섞이지 않아요.
- Q. 클러스터에선? → 키 이름을 `KEYS` 인자로 넘겨야 올바른 노드로 가요.
</details>

<details>
<summary>Q. 제한기가 쓰는 Redis가 죽으면 어떻게 하나요?</summary>

**답변(30초)**
fail open과 fail closed 중 정해 둬야 해요. 일반 API는 제한기 때문에 서비스 전체가 멈추면 안 되니 오류를 잡고 통과시키는 fail open이 흔하고, Stripe도 그렇게 권해요. 로그인 시도처럼 막지 않으면 보안 문제가 되는 경로는 fail closed나 서버별 로컬 제한으로 대체하는 걸 고려해요. 그리고 Redis 오류율과 통과된 요청 수를 모니터링해요.

**꼬리질문**
- Q. fail open이면 그동안 공격을 못 막지 않나요? → 맞아요. 그래서 각 인스턴스에 느슨한 로컬 제한을 두 번째 방어선으로 같이 둬요.
- Q. 처음 도입할 땐 뭘 조심하나요? → 바로 막지 말고 관찰만 하는 dark launch(nginx `limit_req_dry_run`)로 정상 사용자 패턴을 보고 한도를 정해요. 끄는 스위치도 둬요.
</details>

## 서술형 연습

<details>
<summary>상황: 이벤트 오픈 정각(10:00:00)에 정상 사용자들도 429를 대량으로 받았어요. 한도는 사용자당 분당 100회인데, 사용자 한 명이 보낸 요청은 1분에 30건 정도였어요. 원인과 해결 방법은?</summary>

**상황 파악**
1분 평균으로는 한도의 3분의 1밖에 안 썼는데 막혔어요. 평균이 아니라 **짧은 순간에 몰린 양**이 문제였을 가능성이 커요. 정각에 앱이 화면을 열면서 여러 API를 동시에 부르고, 사용자가 새로고침을 연타했을 수 있어요.

**원인 후보**
1. 토큰 버킷 용량(`burstCapacity`)이 너무 작음. 예: 평균은 분당 100(초당 약 1.67)인데 용량을 2~3으로 둬서, 1초에 10건 몰리면 바로 거절.
2. 사용자 ID가 아니라 IP로 세고 있어서, 같은 회사·통신사 NAT(여러 기기가 공인 IP 하나를 함께 쓰는 구조) 뒤 여러 사용자가 한 키로 묶임.
3. 앱이 429를 받자마자 재시도해서 거절이 거절을 부름.
4. 사실 사용자별 한도가 아니라 백엔드 전체 용량이 부족했는데, 제한기 설정만 의심하고 있음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 버킷 용량을 실제 화면 진입 패턴에 맞게 키움(예: 20~30) | 정상 사용자의 순간 몰림 수용, 평균 한도는 그대로 | 백엔드가 받는 순간 부하도 커짐 |
| B. 키를 IP → 로그인 사용자 ID로 변경 | 여러 사람이 한 키에 묶이는 문제 해소 | 로그인 전 경로는 여전히 IP 필요 |
| C. 앱이 `Retry-After`를 지키고 백오프+지터로 재시도 | 재시도 폭주 차단 | 앱 업데이트가 퍼질 때까지 시간 걸림 |
| D. 이벤트 엔드포인트엔 사용자별 제한 대신 대기열·부하 차단 | 전체 용량 보호, 공정한 순번 | 구현 비용, 사용자 대기 |

**내가 고를 방법**
먼저 로그에서 거절된 요청의 키와 초 단위 분포를 봐서 원인 1·2를 가려요. 용량 문제면 A로 화면 하나가 부르는 API 수 이상으로 용량을 키우고, IP 문제면 B로 키를 바꿔요. 동시에 C로 재시도 폭주를 막아요. 이벤트처럼 모두가 정상적으로 몰리는 상황은 사용자별 제한의 일이 아니므로 D([대기열](../waiting-queue/))로 전체 용량을 지켜요. 다음부턴 새 한도를 dark launch로 먼저 관찰해요.

**채점 포인트**: 평균 속도와 순간 몰림(버킷 용량) 구분, 화면 진입 시 동시 API 호출, 키 선택(IP vs 사용자 ID, NAT), 클라이언트 재시도와 Retry-After, 사용자별 제한 vs 전체 부하 차단 구분, 관찰 모드로 한도 조정.
</details>

<details>
<summary>상황: 처리율 제한기가 쓰는 Redis가 장애로 몇 분간 응답하지 않았는데, 그동안 모든 API가 500 오류를 냈어요. 제한기는 부가 기능인데 왜 전체가 막혔고, 어떻게 바꿔야 할까요?</summary>

**상황 파악**
제한기가 Redis 호출 실패를 예외로 던지고, 그게 요청 전체 실패로 이어졌어요. 결과적으로 Redis가 **API 전체의 단일 장애점**이 됐어요. 정책 없이 기본 동작이 **fail closed**였던 거예요.

**원인 후보**
1. 제한기 코드가 Redis 예외를 잡지 않음.
2. Redis 호출에 타임아웃이 길거나 없어서 요청 스레드가 줄줄이 묶임.
3. 프록시(예: Envoy)의 제한 서비스 실패 정책이 "차단"으로 설정됨.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. fail open: 오류·타임아웃 시 통과 | API 가용성 유지(Stripe 권고) | 장애 동안 제한 없음, 남용 가능 |
| B. fail closed 유지 | 제한이 절대 풀리지 않음 | Redis 하나 때문에 전체 중단 |
| C. A + 인스턴스별 로컬 제한을 예비로 | 가용성 유지하면서 최소한의 보호 | 로컬 한도는 서버 수만큼 느슨, 구현 추가 |
| D. 경로별로 다르게(일반 API는 open, 로그인·문자 발송은 closed) | 위험도에 맞춤 | 정책 관리 복잡 |

**내가 고를 방법**
C를 기본으로 하고 D를 더해요. Redis 호출에 짧은 타임아웃을 걸고 실패하면 통과시키되, 각 인스턴스의 메모리 토큰 버킷으로 느슨한 상한은 지켜요. 로그인 시도나 비용이 드는 문자 발송처럼 뚫리면 피해가 큰 경로만 fail closed로 둬요. 제한기를 끌 수 있는 스위치와 "Redis 실패로 통과된 요청 수" 지표를 만들어 알림을 걸고, Redis는 복제와 자동 페일오버로 장애 시간을 줄여요.

**채점 포인트**: 단일 장애점 인식, fail open/closed 용어와 선택 근거, 짧은 타임아웃, 로컬 제한 예비, 경로별 정책, 모니터링·킬 스위치, Redis 고가용성.
</details>

<details>
<summary>상황: 앱 서버 4대가 각자 메모리에 카운터를 두고 "사용자당 분당 100회"를 지키고 있어요. 그런데 한 사용자가 분당 350건 넘게 성공한 기록이 나왔어요. 원인과 해결 방법은?</summary>

**상황 파악**
로드 밸런서가 요청을 서버 4대에 고르게 나눠 주면, 각 서버는 그 사용자 요청을 분당 약 90건씩만 봐요. 서버마다 "100 이하"라 다 통과시켜서, 합치면 최대 400건까지 성공할 수 있어요. **카운터가 공유되지 않아 한도가 서버 수만큼 풀린** 거예요.

**원인 후보**
1. 카운터가 서버별 메모리에 있음(핵심 원인).
2. 고정 윈도를 써서 경계마다 최대 2배가 더해짐.
3. 오토스케일링으로 서버가 늘면 한도가 더 풀림.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Redis에 카운터를 모으고 Lua로 원자적 계산 | 서버 수와 무관하게 정확 | 요청마다 네트워크 왕복, Redis 의존(장애 정책 필요) |
| B. 서버별 한도를 100 ÷ 서버 수로 나눔 | 구현 간단, 외부 의존 없음 | 서버 수가 바뀌면 틀어짐, 분배가 고르지 않으면 정상 사용자가 막힘 |
| C. 같은 사용자를 항상 같은 서버로(스티키 라우팅) | 로컬 카운터로도 정확 | 서버 장애·추가 시 재배치, 부하 쏠림 |
| D. 게이트웨이 한 곳(또는 Redis 공유 게이트웨이)에서 제한 | 앱은 신경 안 써도 됨 | 게이트웨이도 여러 대면 결국 A가 필요 |

**내가 고를 방법**
A를 고르고 D처럼 게이트웨이로 옮겨요. 사용자별 키로 Redis에 토큰 버킷을 두고, 읽기·계산·쓰기를 Lua 스크립트 하나로 실행해 경쟁 조건을 없애요. 시각은 스크립트 안에서 Redis `TIME`을 써서 서버 간 시계 차이를 피해요. Redis 장애에 대비해 fail open + 로컬 예비 제한을 같이 두고, 이때 로컬 한도는 B처럼 나눠 둔 값을 써요. 고정 윈도였다면 이번에 토큰 버킷이나 슬라이딩 윈도 카운터로 바꿔 경계 2배도 없애요.

**채점 포인트**: 로컬 카운터 × 서버 수 진단, 공유 저장소(Redis), 경쟁 조건과 Lua 원자성(MULTI로는 분기 불가), 시계 차이, 고정 윈도 경계 문제, Redis 장애 대비, 오토스케일링 영향.
</details>

## 필기 포인트

- 429 Too Many Requests는 **RFC 6585**에 정의. `Retry-After`는 선택(MAY), 429 응답은 캐시 금지.
- 토큰 버킷 = 순간 몰림을 용량만큼 허용, 누출 버킷 = 출력을 일정 속도로 평탄화.
- 고정 윈도 카운터는 경계에서 최대 **2N** 통과.
- nginx `limit_req` 거절 기본 코드는 **503**.
- `RateLimit`/`RateLimit-Policy` 헤더는 IETF **초안**(RFC 아님), `X-RateLimit-*`은 업체 관례.
