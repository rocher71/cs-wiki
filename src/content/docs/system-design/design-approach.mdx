:::tip[한 줄 요약]
시스템 설계 면접은 정답을 맞히는 시험이 아니에요. **요구사항을 묻고 → 규모를 숫자로 추정하고 → 단순한 설계에서 시작해 → 병목과 트레이드오프를 스스로 짚는** 과정을 보여 주는 자리예요.
:::

:::note[이 섹션 안내]
이 섹션의 모든 페이지(URL 단축기, 뉴스 피드, 채팅, 결제…)는 이 페이지에서 소개하는 **같은 뼈대**로 풀어요.

요구사항 → 규모 추정 → API → 데이터 모델 → 상위 설계 → 심화 → 병목·트레이드오프

이 순서는 "정답 순서"가 아니라 이 위키가 권하는 진행 순서예요. 면접관이 다른 곳부터 묻는다면 그쪽을 따라가면 돼요. 캐시·샤딩·복제 같은 부품은 이미 다른 섹션에 있으니, 여기선 "부품을 어떻게 조립해 말하나"에 집중해요.
:::

:::note[처음이라면 여기까지]
① 문제를 듣자마자 그림부터 그리면 안 돼요. "사용자가 몇 명인가요?", "어떤 기능이 꼭 필요한가요?"부터 물어요.

② 규모는 계산으로 잡아요. 하루는 약 10만(10^5) 초라서, "하루 요청 수 ÷ 10만"이 초당 요청 수예요.

③ 메모리는 아주 빠르고(나노초), 디스크·다른 대륙 왕복은 아주 느려요(밀리초). 이 "몇 배 차이"만 기억하면 돼요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

건축가에게 "집 하나 지어 주세요"라고 하면, 좋은 건축가는 바로 도면을 그리지 않아요. 먼저 **"몇 명이 살아요? 아이가 있나요? 예산은요?"**를 물어요. 혼자 사는 원룸과 열 명이 사는 대가족 집은 설계가 완전히 다르니까요.

그다음 숫자를 따져요. 네 식구면 방 3개, 화장실 2개. 하루에 물을 얼마나 쓸지, 주차는 몇 대인지도요. 이 숫자가 있어야 "보일러는 이 정도면 충분해요"라고 근거를 댈 수 있어요.

도면도 처음엔 방 배치만 큼직하게 그리고, 손님이 "부엌은 어떻게 돼요?"라고 물으면 그 부분만 자세히 그려요. 마지막엔 "창을 크게 내면 밝지만 겨울에 추워요" 같은 장단점을 같이 말해요.

시스템 설계 면접도 똑같아요. **누가 얼마나 쓰는지 묻고 → 숫자로 규모를 잡고 → 큰 그림 → 한 부분 깊게 → 장단점**이에요.

단, 실제 면접은 집 짓기보다 훨씬 짧아요(회사마다 다르지만 보통 한 시간이 안 돼요). 그래서 질문을 끝없이 하는 게 아니라, 몇 가지만 물어 범위를 정하고 나머지는 "이렇게 가정할게요"라고 말하고 넘어가요.

## 제대로 알기

### 왜 순서가 필요한가

시스템 설계 질문은 일부러 애매하게 나와요. "트위터를 설계해 보세요"에는 정답이 없어요. 면접관은 **애매한 문제를 스스로 좁혀 가는 방법**을 보고 싶어 해요.

순서가 없으면 흔히 이렇게 돼요.

- 규모를 모르니 필요 없는 Kafka·샤딩을 잔뜩 넣거나(과설계), 반대로 DB 한 대로 다 된다고 해요(과소설계).
- 한 부분에 빠져서 시간이 끝날 때까지 전체 그림을 못 보여 줘요.

뼈대를 정해 두면 긴장해도 "지금 몇 단계지?"를 알 수 있어요.

### 단계별로 할 일과 면접관에게 할 말

| 단계 | 할 일 | 말 예시 |
|---|---|---|
| 1. 요구사항 | **기능**(무엇을 하나)과 **비기능**(얼마나 많이·빨리·안 죽고) 정리 | "핵심 기능은 글쓰기와 피드 보기로 좁혀도 될까요? 사용자는 하루 몇 명 정도 생각하세요?" |
| 2. 규모 추정 | 하루 사용자 → 초당 요청 → 피크 → 저장량 | "하루 1,000만 명이 2개씩 쓰면 초당 약 200건이에요. 피크는 평균의 2~3배로 가정할게요." |
| 3. API | 핵심 요청 2~3개의 입력·출력 | "`POST /posts`로 글을 쓰고, `GET /feed?cursor=...`로 피드를 받을게요." |
| 4. 데이터 모델 | 무엇을 저장하고 어디에 둘지 | "글 본문은 DB, 이미지는 용량이 커서 객체 저장소에 둘게요." |
| 5. 상위 설계 | 큰 상자와 화살표 | "일단 단순하게 그리고, 숫자가 요구하는 곳만 키워 갈게요." |
| 6. 심화 | 면접관이 고른 한 부분 깊게 | "어느 부분을 더 자세히 볼까요? 피드 생성 쪽이 제일 까다로워 보여요." |
| 7. 병목·트레이드오프 | 약한 곳과 포기한 것 | "DB가 단일 장애점이라 복제를 두고, 대신 복제 지연으로 잠깐 옛 데이터가 보일 수 있어요." |

용어 몇 개만 풀어 둘게요.

- **DAU**(Daily Active Users): 하루에 한 번 이상 쓰는 사용자 수.
- **QPS**(Queries Per Second): 초당 요청 수.
- **API**: 클라이언트가 서버에 "이거 해 줘"라고 부르는 약속된 창구.
- **로드밸런서**: 들어온 요청을 여러 서버에 나눠 주는 교통정리 담당. → [로드밸런서와 프록시](../../web/load-balancer-proxy/)
- **객체 저장소**: 이미지·영상 같은 큰 파일을 통째로 보관하는 저장소.
- **CDN**: 사용자 가까운 곳에 파일 복사본을 두는 배달망. → [캐시·CDN으로 규모 키우기](../cache-cdn-scale/)

### 상위 설계는 단순하게 시작해요

대부분의 서비스는 처음에 이런 모양에서 출발해요.

```text
클라이언트 → 로드밸런서 → 앱 서버 여러 대(무상태) → 캐시 → DB
                                      └→ 객체 저장소 + CDN (이미지·영상)
```

처음부터 복잡하게 그리지 않는 이유는, **복잡함에는 숫자로 된 이유가 있어야** 하기 때문이에요. 쓰기가 초당 수백 건이면 DB 한 대(+읽기 복제)로도 버틸 수 있어요. 그런데 샤딩부터 넣으면 "왜 필요하죠?"에 답할 수 없어요.

### 확장 기본: 수직 vs 수평, 그리고 무상태

| | 수직 확장(scale up) | 수평 확장(scale out) |
|---|---|---|
| 방법 | 더 큰 서버로 바꿈(CPU·메모리 증설) | 같은 서버를 여러 대로 늘림 |
| 장점 | 코드 변경 없이 간단 | 이론상 계속 늘릴 수 있음, 한 대가 죽어도 버팀 |
| 단점 | 한계가 있고, 그 한 대가 죽으면 끝(**단일 장애점**) | 서버가 **무상태**여야 함 |

**무상태**(stateless)는 "데이터를 안 저장한다"가 아니에요. 로그인 세션 같은 **상태를 서버 메모리가 아니라 밖(DB·Redis·객체 저장소)에 둔다**는 뜻이에요. 그래야 로드밸런서가 어느 서버로 요청을 보내도 같은 결과가 나와요. 자세한 내용은 [12-Factor App](../../architecture/twelve-factor/)의 "VI. Processes"에 있어요.

### 이미 있는 부품들

설계에서 자주 꺼내 쓰는 부품은 이미 다른 섹션에 정리돼 있어요. 면접 중 "여기에 캐시를 둘게요"라고 했다면, 아래 페이지 내용으로 꼬리질문에 답하면 돼요.

| 부품 | 언제 꺼내나 | 페이지 |
|---|---|---|
| 캐시 | 읽기가 쓰기보다 훨씬 많을 때 | [캐시 패턴](../../redis/cache-patterns/), [캐시 문제](../../redis/cache-problems/) |
| 샤딩(파티셔닝) | 한 DB에 데이터나 쓰기가 다 안 들어갈 때 | [파티셔닝](../../distributed/partitioning/) |
| 복제 | 읽기를 나누거나 장애에 대비할 때 | [복제](../../distributed/replication/) |
| 고유 ID 생성 | 여러 서버에서 겹치지 않는 ID가 필요할 때 | [분산 시간과 ID](../../distributed/distributed-time-ids/) |
| 메시지 큐 | 느린 작업을 뒤로 미루거나 서비스끼리 느슨하게 연결할 때 | [메시지 큐와 Kafka](../../distributed/message-queue-kafka/) |

### 규모 추정: 계산 요령

규모 추정은 **봉투 뒷면 계산**(back-of-the-envelope, 종이 귀퉁이에 대충 하는 어림셈)이에요. 구글의 Jeff Dean이 "시스템을 실제로 만들지 않고 성능을 추정하는 능력"을 중요한 기술로 꼽으면서 널리 알려졌어요. 목표는 정확한 값이 아니라 **자릿수**(10배, 100배 단위)를 맞히는 거예요.

외워 둘 것은 세 가지예요.

**1) 하루 ≈ 10^5초.** 정확히는 86,400초인데, 100,000으로 반올림하면 암산이 쉬워요(오차 약 16%, 추정에선 괜찮아요). 대신 "반올림했어요"라고 말해요.

- 평균 QPS = 하루 요청 수 ÷ 86,400 (≈ ÷ 10^5)

**2) 공식 세 개.**

- 피크 QPS = 평균 QPS × 피크 계수 (보통 2~3배로 **가정**)
- 저장량 = 하루 쓰기 건수 × 건당 크기 × 보관 일수 × 복제 수
- 대역폭 = QPS × 요청(또는 응답) 크기

**3) 단위 표.** 컴퓨터는 2의 거듭제곱을 쓰지만, 2^10 = 1,024 ≈ 1,000이라 추정에선 10진으로 통일해요.

| 2의 거듭제곱 | 대략 | 단위 | 감 잡기 |
|---|---|---|---|
| 2^10 | 10^3 (천) | KB | 짧은 글 한 개 |
| 2^20 | 10^6 (백만) | MB | 사진 한 장 |
| 2^30 | 10^9 (십억) | GB | 영화 한 편 |
| 2^40 | 10^12 (조) | TB | 큰 서버 디스크 한 개 |
| 2^50 | 10^15 | PB | 대형 서비스의 미디어 전체 |

"감 잡기" 열은 크기를 느끼기 위한 대략적인 예시예요.

<Aside type="caution" title="피크 계수는 가정이에요">
"피크 = 평균 × 2~3"은 공식이 있는 상수가 아니라 서비스마다 다른 **가정값**이에요. 티켓팅처럼 오픈 시각에 몰리는 서비스는 수십 배일 수도 있어요. 면접에선 "피크는 평균의 3배로 가정할게요"처럼 **가정이라고 밝히고** 말해요.
</Aside>

### 예제 1: 하루 1,000만 명이 쓰는 SNS

**가정**(면접에서 먼저 말할 것): 1인당 하루 글 2개, 글 1KB(텍스트), 10%는 1MB 이미지 포함, 읽기:쓰기 = 10:1, 피크 계수 2~3(가정), 5년 보관.

| 항목 | 계산 | 결과 |
|---|---|---|
| 하루 쓰기 | 10^7명 × 2 | 2×10^7건 |
| 평균 쓰기 QPS | 2×10^7 ÷ 86,400 | **약 231** (암산 200) |
| 피크 쓰기 QPS | 231 × 2~3 | **약 463~694** |
| 평균 읽기 QPS | 231 × 10 | **약 2,315** |
| 텍스트 저장 | 2×10^7 × 1KB = 20GB/일 → × 365 × 5 | **36.5TB** |
| 이미지 저장 | 2×10^6 × 1MB = 2TB/일 → × 365 × 5 | **3.65PB** |
| 이미지 업로드 대역폭(평균) | 2TB ÷ 86,400초 | **약 23MB/s** |

**숫자가 말해 주는 것**

- 쓰기는 피크에도 초당 수백 건이라, DB 한 대(+읽기 복제)로 시작해도 돼요. 처음부터 샤딩할 근거는 아직 없어요.
- 저장량은 이미지가 텍스트의 100배라 **미디어가 지배**해요. 텍스트는 DB, 이미지는 객체 저장소 + CDN으로 나눠요.

### 예제 2: 하루 500만 명이 쓰는 채팅

**가정**: 1인당 하루 메시지 40개, 메시지 100B, 피크 계수 3(가정), 5년 보관, 복제 3벌.

| 항목 | 계산 | 결과 |
|---|---|---|
| 하루 메시지 | 5×10^6 × 40 | 2×10^8건 |
| 평균 QPS | 2×10^8 ÷ 86,400 | **약 2,315** (암산 2,000) |
| 피크 QPS | 2,315 × 3 | **약 6,944** (≈ 7,000) |
| 저장(1벌) | 2×10^8 × 100B = 20GB/일 → × 365 × 5 | **36.5TB** |
| 저장(3벌 복제) | 36.5TB × 3 | **109.5TB** |
| 유입 대역폭(평균) | 20GB ÷ 86,400초 | **약 231KB/s** |

**숫자가 말해 주는 것**

- 대역폭은 아주 작아요. 병목은 대역폭이 아니라 **초당 쓰기 수(피크 약 7,000)와 동시 연결 수**예요. → [채팅 시스템](../chat-system/)에서 이어서 다뤄요.

### 지연 숫자: 자릿수 감각

설계 판단("캐시에 둘까, DB에서 읽을까", "다른 대륙 사용자는 왜 느릴까")에는 각 동작이 대략 얼마나 걸리는지 감이 필요해요. Jeff Dean의 강연 표가 유명한데, **판본마다 값이 조금씩 달라요**. 아래는 두 출처를 나란히 둔 **근사치**예요.

| 동작 | Jeff Dean 강연 자료 | Peter Norvig 글 |
|---|---|---|
| L1 캐시 참조 | 0.5ns | — |
| 메인 메모리 참조 | 100ns | — |
| 뮤텍스 잠금/해제 | 100ns | 25ns |
| 메모리에서 1MB 순차 읽기 | 0.25ms | — |
| 같은 데이터센터 안 왕복 | 0.5ms | — |
| 디스크 탐색(seek) | 10ms | 8ms |
| 디스크에서 1MB 순차 읽기 | 30ms | 20ms |
| 대륙 간 왕복 | 150ms (캘리포니아↔네덜란드) | 150ms (미국↔유럽) |

"—"는 이 페이지에서 비교하지 않은 칸이에요. 두 표 모두 2000년대 하드웨어 기준이라 오늘날 실제 값과 다를 수 있어요.

**외울 건 값이 아니라 순서예요.** 판본이 달라도 이 순서는 그대로예요.

메모리(100ns) ≪ 같은 데이터센터 왕복(0.5ms) ≪ 디스크 seek(약 10ms) ≪ 대륙 간 왕복(150ms)

메모리 참조와 대륙 간 왕복은 약 **10^6배**(백만 배) 차이예요. 1ns를 1초로 늘려 보면 감이 와요.

| 동작 | 실제 | 1ns = 1초로 늘리면 |
|---|---|---|
| 메모리 참조 | 100ns | 100초(약 1.7분) |
| 같은 데이터센터 왕복 | 0.5ms | 약 5.8일 |
| 디스크 seek | 10ms | 약 116일 |
| 대륙 간 왕복 | 150ms | 약 4.8년 |

그래서 "자주 읽는 건 메모리(캐시)에", "디스크 왕복은 줄이고", "다른 대륙 사용자에겐 가까운 곳에 복사본(CDN·리전)을"이라는 설계 원칙이 나와요.

### 흔한 실수

| 실수 | 왜 문제인가 | 이렇게 |
|---|---|---|
| 문제 듣자마자 상자부터 그리기 | 규모를 모르니 과설계·과소설계를 판단할 근거가 없어요 | 처음 몇 분은 질문과 가정 정리에 써요 |
| 요구사항을 안 묻기 | 면접관이 원한 기능과 다른 걸 설계하게 돼요 | 기능·비기능을 묻고, 범위를 "이렇게 좁힐게요"라고 확인받아요 |
| 한 가지 정답 고집 | 설계엔 정답이 없고, 면접관은 대안을 비교하는 능력을 봐요 | "A와 B가 있는데, 지금 숫자로는 A가 맞아요. 쓰기가 10배 늘면 B로 바꿔요" |
| 처음부터 샤딩·Kafka 넣기 | 숫자로 필요성을 못 보여 줘요 | 추정 결과가 단일 DB 한계를 넘을 때 꺼내요 |
| 지연 숫자를 정확히 외우려 하기 | 판본마다 다르고, 중요한 건 몇 배 차이인지예요 | 자릿수와 순서만 기억해요 |
| KB와 KiB 섞어 쓰기 | 계산이 꼬여요 | 추정에선 10진(1KB = 1,000B)으로 통일해요 |

### 심화: 계산으로 설계안 비교하기

추정은 규모를 재는 것뿐 아니라 **두 설계안 중 무엇이 나은지 고르는 데**도 써요. Jeff Dean이 든 예가 있어요. 이미지 검색 결과 페이지에 썸네일 30장(각 256KB)을 디스크에서 읽는다고 해 봐요.

- **순차로 읽기**: 30 × 10ms(seek) + 30 × 256KB ÷ 30MB/s ≈ **560ms**
- **병렬로 읽기**: 10ms + 256KB ÷ 30MB/s ≈ **18ms** (디스크마다 응답 시간이 들쭉날쭉한 걸 고려하면 30~60ms)

만들어 보기 전에 "병렬이 한 자릿수 이상 빠르다"는 걸 알 수 있죠. 면접에서도 "이 방식이면 왕복이 N번이라 대략 몇 ms예요"처럼 숫자로 비교하면 설득력이 커져요.

### 심화: 대륙 간 지연은 하드웨어로 안 줄어요

대륙 간 왕복 150ms의 대부분은 **빛이 광섬유를 지나는 시간**이에요. 물리 법칙이 하한이라 서버를 좋게 바꿔도 거의 줄지 않아요. 그래서 해외 사용자 지연은 두 가지로 풀어요.

- **왕복 횟수를 줄이기**: 요청 하나에 왕복이 3번이면 150ms × 3 = 450ms예요. 묶어 보내면 줄어요.
- **사용자 가까이 두기**: 정적 파일은 CDN, 데이터까지 필요하면 다른 지역(리전)에 서버를 추가해요. 대신 리전 간 데이터 동기화라는 새 문제가 생겨요.

참고로 같은 리전 안의 데이터센터 묶음(AWS의 **가용 영역**, AZ)끼리는 서로 최대 약 100km 떨어져 있고, 한 자릿수 밀리초 지연으로 연결돼 있어서 동기 복제가 가능하다고 AWS 문서는 설명해요.

### 심화: 지연 표에 대한 흔한 오해

- **"SSD도 Jeff Dean 표에 있다"** → 원래 표엔 SSD 행이 없어요. 흔히 보이는 "SSD 랜덤 읽기 약 16µs" 같은 값은 Colin Scott의 인터랙티브 표에서 온 건데, 이건 **실측이 아니라** 2000년대 초 기준값에 하드웨어 발전 추세를 곱해 늘린 **외삽값**이에요(슬라이더도 2020년까지).
- **"최신 실측 표가 있다"** → 최신 하드웨어로 다시 재서 갱신한 권위 있는 공개 표는 확인하지 못했어요. 그래서 이 위키는 값보다 순서를 강조해요.

- Q. 기능 요구사항은 몇 개까지 다루나요? → 시간이 짧으니 핵심 2~3개로 좁히고, 나머지는 "범위 밖으로 둘게요"라고 말해요.

<details>
<summary>Q. 하루 사용자 1,000만 명인 서비스의 QPS를 추정해 보세요.</summary>

**답변(30초)**
1인당 하루 2번 글을 쓴다고 가정하면 하루 2,000만 건이에요. 하루는 약 86,400초, 대략 10^5초라서 평균 쓰기 QPS는 약 200, 정확히는 231이에요. 피크는 평균의 2~3배로 가정해 약 460~700이고, 읽기가 쓰기의 10배라면 평균 읽기는 약 2,300 QPS예요. 이 정도면 DB 한 대와 읽기 복제, 캐시로 시작할 수 있어요.

**꼬리질문**
- Q. 왜 86,400 대신 10^5로 나눠요? → 암산이 쉽고 오차가 16% 정도라 자릿수 추정엔 충분해요. 반올림했다고 밝혀요.
- Q. 피크 계수 2~3은 어디서 나왔어요? → 공식 상수가 아니라 가정이에요. 실제 서비스라면 과거 트래픽 지표로 정해요.
</details>

<details>
<summary>Q. 수직 확장과 수평 확장의 차이는 무엇이고, 수평 확장에 무상태 서버가 왜 필요한가요?</summary>

**답변(30초)**
수직 확장은 서버 한 대를 더 좋은 사양으로 바꾸는 것이고, 간단하지만 한계가 있고 그 서버가 단일 장애점이에요. 수평 확장은 서버 대수를 늘리는 것이라 계속 늘릴 수 있고 한 대가 죽어도 버텨요. 다만 로드밸런서가 아무 서버에나 요청을 보내도 되려면, 세션 같은 상태를 서버 메모리가 아니라 Redis나 DB 같은 바깥에 둬야 해요. 그게 무상태예요.

**꼬리질문**
- Q. 세션을 서버 메모리에 두고 서버를 늘리면 어떻게 되나요? → 다른 서버로 요청이 가면 세션이 없어 로그인이 풀려요. Redis 세션이나 토큰 방식으로 바꿔요.
- Q. 무상태면 데이터를 안 저장하는 건가요? → 아니요. 상태를 프로세스 밖으로 빼는 거예요.
</details>

<details>
<summary>Q. 메모리, 디스크, 네트워크 접근 지연은 대략 얼마나 차이 나나요?</summary>

**답변(30초)**
메모리 참조가 약 100ns, 같은 데이터센터 왕복이 약 0.5ms, 디스크 탐색이 약 10ms, 대륙 간 왕복이 약 150ms예요. 메모리와 대륙 간 왕복은 약 백만 배 차이예요. 값은 판본마다 조금씩 달라서 저는 정확한 값보다 자릿수와 순서를 기억해요. 그래서 자주 읽는 건 캐시에, 먼 사용자에겐 CDN을 두는 설계가 나와요.

**꼬리질문**
- Q. SSD는요? → 원래 표엔 없어요. 흔히 보이는 SSD 값은 추세로 늘린 외삽값이라 참고만 해요.
</details>

<details>
<summary>Q. 5년 치 저장량을 추정하고, 저장소를 어떻게 고를지 말해 보세요.</summary>

**답변(30초)**
하루 2,000만 건 글에 1KB씩이면 하루 20GB, 5년이면 36.5TB예요. 10%가 1MB 이미지라면 하루 2TB, 5년이면 3.65PB로 텍스트의 100배예요. 저장량은 미디어가 지배하니, 텍스트는 DB에, 이미지는 객체 저장소에 두고 CDN으로 배포해요. 복제를 3벌 둔다면 저장량에 3을 곱해야 해요.

**꼬리질문**
- Q. 이미지 업로드 대역폭은요? → 하루 2TB ÷ 86,400초로 평균 약 23MB/s예요. 피크는 계수를 곱해요.
</details>

<details>
<summary>Q. 해외(다른 대륙) 사용자의 응답이 느려요. 서버를 더 좋게 바꾸면 해결되나요?</summary>

**답변(30초)**
잘 안 돼요. 대륙 간 왕복 약 150ms의 대부분은 빛이 광섬유를 지나는 시간이라 하드웨어로 줄지 않아요. 대신 요청당 왕복 횟수를 줄이고, 정적 파일은 CDN으로 사용자 근처에서 주고, 필요하면 해외 리전을 추가해요. 리전을 늘리면 데이터 동기화와 비용이 새로 생기는 트레이드오프가 있어요.

**꼬리질문**
- Q. 왕복이 3번이면요? → 150ms × 3 = 약 450ms예요. API를 묶거나 연결을 재사용해 왕복을 줄여요.
</details>

<details>
<summary>Q. 피크 계수는 어떻게 정했나요? 추정이 틀리면 어떡하나요?</summary>

**답변(30초)**
피크 계수 2~3은 공식이 아니라 가정이라고 먼저 밝혀요. 실제로는 과거 트래픽 지표나 이벤트 특성으로 정해요. 추정이 틀릴 수 있으니 설계에 여유를 둬요. 앱 서버는 무상태로 만들어 자동으로 늘릴 수 있게 하고, 갑자기 몰리면 대기열로 받아 DB를 보호해요. 추정의 목적은 정확한 값이 아니라 자릿수를 맞혀 방향을 정하는 거예요.

**꼬리질문**
- Q. 티켓팅처럼 오픈 시각에 몰리면요? → 피크가 평균의 수십 배일 수 있어요. 대기열로 입장 속도를 조절해요. → [대기열 시스템](../waiting-queue/)
</details>

## 서술형 연습

<details>
<summary>상황: 평소 하루 사용자 100만 명인 서비스에 대형 마케팅 이벤트가 잡혀 트래픽이 10배가 될 거래요. 무엇을 확인하고 어떻게 대비할까요?</summary>

**상황 파악**
"10배"가 평균인지 피크인지부터 확인해요. 이벤트는 특정 시각에 몰리니 피크는 평소 피크의 10배를 훌쩍 넘을 수 있어요. 그다음 현재 구조에서 **어디가 먼저 터질지**를 숫자로 따져요.

**원인 후보(먼저 터질 곳)**
1. 앱 서버: 세션을 메모리에 두는 등 상태가 있으면 대수를 늘려도 효과가 없어요.
2. DB 쓰기: 주문·참여 같은 쓰기가 몰리면 단일 Primary가 한계예요.
3. DB 읽기: 같은 이벤트 페이지를 모두가 보니 같은 데이터 읽기가 폭증해요.
4. 외부 연동(결제·알림): 우리 쪽을 늘려도 상대 쪽 처리량이 그대로예요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 앱 서버 무상태화 + 수평 확장(오토스케일) | 서버만 늘리면 처리량이 늘어요 | DB가 병목이면 소용없어요, 미리 늘려 둬야 해요(뜨는 데 시간이 걸림) |
| B. 이벤트 페이지 캐시 + CDN | 읽기 대부분을 DB 앞에서 흡수해요 | 잠깐 옛 데이터가 보일 수 있어요, 만료 순간 몰림 주의 |
| C. 대기열로 입장 속도 조절 | DB가 감당할 만큼만 들여보내 전체가 안 죽어요 | 사용자는 기다려야 해요, 대기열 자체도 만들어야 해요 |
| D. 쓰기는 메시지 큐로 받고 뒤에서 처리 | 순간 몰림을 평평하게 펴요 | 결과가 바로 안 나와요(비동기), 중복·순서 처리 필요 |
| E. DB 수직 확장(일시적) | 코드 변경 없이 바로 적용 | 한계가 있고 비용이 커요 |

**내가 고를 방법**
먼저 현재 지표로 평소 피크 QPS를 구하고 10배를 곱해 각 부품의 한계와 비교해요. 앱 서버는 A로 미리 늘려 두고, 읽기는 B로 흡수해요. 쓰기가 DB 한계를 넘는다면 C로 들어오는 양 자체를 조절해요. 이벤트처럼 짧게 몰리는 트래픽엔 샤딩 같은 큰 구조 변경보다 C가 싸고 빨라요. 이벤트 전 부하 테스트로 숫자를 검증해요.

**채점 포인트**: 평균 vs 피크 구분, 병목 지점을 숫자로 찾기, 무상태와 수평 확장, 캐시·CDN으로 읽기 흡수, 대기열·메시지 큐로 쓰기 몰림 완화, 외부 연동 한계, 부하 테스트, 트레이드오프 비교.
</details>

<details>
<summary>상황: 신규 서비스 오픈 전에 "DB 한 대로 버틸 수 있나요?"라는 질문을 받았어요. 하루 사용자 1,000만 명, 1인당 하루 글 2개, 10%는 이미지 첨부로 예상해요. 어떻게 판단할까요?</summary>

**상황 파악**
"버틴다"는 쓰기 처리량, 읽기 처리량, 저장량 세 가지로 나눠 봐야 해요. 각각 숫자로 추정해요.

**원인 후보(추정 결과)**
1. 쓰기: 하루 2,000만 건 → 평균 약 231 QPS, 피크(2~3배 가정) 약 460~700 QPS.
2. 읽기: 쓰기의 10배 가정 → 평균 약 2,315 QPS.
3. 저장: 텍스트 5년 36.5TB, 이미지 5년 3.65PB.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Primary 1대 + 읽기 복제 + 캐시, 이미지는 객체 저장소 + CDN | 단순해요, 쓰기 수백 QPS엔 충분해 보여요 | 쓰기가 크게 늘면 Primary가 한계, 복제 지연으로 옛 데이터가 잠깐 보일 수 있어요 |
| B. 처음부터 샤딩 | 쓰기·저장 확장 여유가 커요 | 운영 복잡, 샤드 간 조회가 어려움, 지금 숫자로는 근거가 약해요 |
| C. 모든 걸 DB 한 대에(이미지 포함) | 가장 단순해요 | 페타바이트급 이미지를 DB에 넣는 건 비용·백업 모두 비현실적이에요 |

**내가 고를 방법**
A로 시작해요. 쓰기 피크가 수백 QPS라 Primary 한 대로 시작할 근거가 있고, 읽기는 복제와 캐시로 나눠요. 저장량은 이미지가 텍스트의 100배라서 미디어는 반드시 객체 저장소로 분리해요. 텍스트도 5년이면 수십 TB라, 쓰기 QPS나 저장량이 한 대 한계에 가까워지는 시점을 지표로 지켜보다가 샤딩(B)으로 옮길 계획을 미리 세워 둬요. 단, "DB 한 대가 몇 QPS까지 버티는지"는 장비와 쿼리에 따라 달라서 부하 테스트로 확인해야 한다고 덧붙여요.

**채점 포인트**: 쓰기·읽기·저장 분리, 86,400(≈10^5) 나눗셈, 피크는 가정이라고 밝힘, 미디어와 텍스트 분리(객체 저장소+CDN), 읽기 복제·캐시, 샤딩은 숫자가 요구할 때, 부하 테스트로 검증.
</details>

<details>
<summary>상황: 면접에서 "추정한 숫자가 실제와 크게 다르면 설계가 다 틀린 거 아닌가요?"라는 질문을 받았어요. 어떻게 답할까요?</summary>

**상황 파악**
면접관은 추정의 목적을 이해하는지, 불확실성에 대비하는 설계를 하는지를 보려는 거예요.

**원인 후보(숫자가 틀리는 이유)**
1. DAU·사용 패턴 가정이 실제와 다름(신규 서비스는 특히).
2. 피크 계수가 가정이라 이벤트·시간대 몰림을 못 반영함.
3. 건당 크기(이미지 비율 등)가 바뀜.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 여유를 크게 잡아 미리 넉넉히 구축 | 갑작스런 증가에 안전 | 안 쓰는 자원에 비용이 나가요 |
| B. 늘리기 쉬운 구조로(무상태 앱 + 오토스케일, 객체 저장소) | 실제 트래픽에 맞춰 늘리고 줄여요 | DB처럼 상태가 있는 곳은 쉽게 안 늘어나요 |
| C. 지표 모니터링 + 한계 도달 전 경보 | 가정이 틀린 걸 일찍 알아채요 | 경보 기준을 정하고 관리해야 해요 |
| D. 대기열·레이트 리미터로 과부하 시 들어오는 양 제한 | 예상을 넘어도 전체 장애는 막아요 | 일부 사용자는 기다리거나 거절당해요 |

**내가 고를 방법**
"추정의 목적은 정확한 값이 아니라 자릿수를 맞혀 방향을 정하는 것"이라고 먼저 답해요. 231과 300은 같은 설계로 감당되지만, 231과 23,000은 설계가 달라져요. 그래서 자릿수가 바뀌는 지점을 미리 말해 두고(예: 쓰기가 몇천 QPS를 넘으면 샤딩 검토), B로 늘리기 쉬운 부분을 만들고, C로 가정이 틀렸는지 일찍 알아채고, D로 예상을 넘어도 서비스 전체가 죽지 않게 해요. A는 비용이 커서 핵심 구간에만 써요.

**채점 포인트**: 추정의 목적(자릿수), 가정을 명시했는지, 설계가 바뀌는 임계점 제시, 수평 확장 가능한 구조, 모니터링·경보, 과부하 보호(대기열·[레이트 리미터](../rate-limiter/)), 비용 트레이드오프.
</details>

## 필기 포인트

- 하루 = 86,400초 ≈ 10^5초. 평균 QPS = 하루 요청 수 ÷ 86,400.
- 저장량 = 하루 쓰기 건수 × 건당 크기 × 보관 일수 × 복제 수. 대역폭 = QPS × 요청 크기.
- 2^10 ≈ 10^3(K), 2^20 ≈ 10^6(M), 2^30 ≈ 10^9(G), 2^40 ≈ 10^12(T), 2^50 ≈ 10^15(P).
- 지연 순서: 메모리(약 100ns) ≪ 같은 DC 왕복(약 0.5ms) ≪ 디스크 seek(약 10ms) ≪ 대륙 간 왕복(약 150ms).
- 수직 확장 = 더 큰 서버(한계·단일 장애점), 수평 확장 = 서버 대수 증가(무상태 필요).
