:::tip[한 줄 요약]
검색 자동완성은 사용자가 친 **접두사**(앞부분 글자)로 시작하는 인기 검색어 상위 5개를 **0.1초 안에** 보여 주는 기능이에요. **트라이의 노드마다 상위 5개를 미리 붙여 두고**, 빈도는 검색 로그를 **주기적으로 집계해 트라이를 통째로 다시 만들어** 바꿔 끼우는 게 기본 설계예요.
:::

:::note[처음이라면 여기까지]
① 자동완성은 글자를 칠 때마다 뜨니까 아주 빨라야 해요. 목표는 0.1초예요.

② 그래서 "가"로 시작하는 인기 검색어 5개를 **미리 계산해 붙여 둬요**. 물어보면 찾지 않고 꺼내기만 해요.

③ 인기 순위는 실시간으로 고치지 않고, 몇 시간마다 검색 기록을 모아 새로 만들어요. 그 대신 방금 터진 이슈가 늦게 떠요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

두꺼운 국어사전 옆면에는 "가, 나, 다…" 색인 탭이 붙어 있어요. "강"으로 시작하는 단어를 찾을 때 첫 쪽부터 넘기지 않고, "가" 탭을 잡아 바로 그 쪽을 펼쳐요.

자동완성도 같아요. 사용자가 "강"을 치면 "강"으로 시작하는 쪽을 바로 펼쳐요. 여기에 한 가지를 더해요. 그 쪽 맨 위에 **"이 쪽에서 사람들이 제일 많이 찾은 단어 5개"를 포스트잇으로 붙여 둬요.** 그러면 쪽 전체를 훑을 필요 없이 포스트잇만 읽으면 끝이에요.

포스트잇은 매번 새로 쓰기 귀찮으니, 몇 시간마다 "요즘 많이 찾은 단어" 기록을 모아 사전을 한 권 새로 찍어서 바꿔 놓아요.

단, 실제 사전은 쪽이 글자 순서대로 한 줄로 늘어서 있지만, 자동완성에 쓰는 **트라이**는 글자마다 갈라지는 나무 모양이에요. 그리고 한국어는 "강"을 치는 도중에 "가"나 "ㄱ" 상태가 있어서, 사전 탭보다 더 잘게(자음·모음 단위로) 나눠야 해요.

## 제대로 알기

이 페이지는 [시스템 설계 면접 푸는 법](../design-approach/)의 공통 뼈대(요구사항 → 규모 → API → 데이터 모델 → 상위 설계 → 심화 → 병목)를 따라가요.

### 1. 요구사항

면접에서 먼저 물어볼 것들이에요.

| 질문 | 이 페이지의 가정 |
|---|---|
| 몇 개를 보여 주나요? | 상위 **5개** |
| 순위 기준은요? | 검색 **빈도**(많이 검색된 순) |
| 접두사만 맞추나요, 중간 단어도요? | **접두사만**("강남"은 "강"으로 찾고 "남"으로는 안 찾음) |
| 얼마나 빨라야 하나요? | 사용자가 느끼는 전체 왕복 **0.1초 이내** |
| 새 검색어는 얼마나 빨리 반영되나요? | 기본은 몇 시간 단위, 급상승은 따로 보강 |
| 언어는요? | 영어 + **한국어**(초성 검색 포함) |
| 부적절한 검색어는요? | 걸러야 함, 급한 건 즉시 |

### 2. 왜 0.1초인가

사용성 연구자 Jakob Nielsen이 정리한 응답 시간 기준이 자주 인용돼요. 원출처는 Miller(1968), Card 외(1991)의 연구이고, Nielsen의 책 『Usability Engineering』(1993) 5장에 정리돼 있어요.

| 시간 | 사용자가 느끼는 것 |
|---|---|
| 0.1초 | 즉시 반응한다. 따로 "로딩 중" 표시가 필요 없다 |
| 1초 | 기다린 건 느끼지만 생각의 흐름은 안 끊긴다 |
| 10초 | 집중을 유지할 수 있는 한계 |

자동완성은 글자를 칠 때마다 뜨니까 **0.1초**를 목표로 잡아요. 주의할 점은 이 0.1초가 **사용자 입장의 전체 왕복**이라는 거예요. 네트워크 왕복 시간을 빼면 서버가 쓸 수 있는 시간은 훨씬 짧아요.

### 3. 규모 추정

자동완성 요청은 **검색 요청보다 훨씬 많아요.** 검색은 엔터를 칠 때 한 번이지만, 자동완성은 글자마다 부를 수 있거든요. 그래서 요청 수를 줄이는 장치(디바운스, 캐시)가 설계의 큰 부분이에요.

반대로 **데이터는 읽기 전용에 가까워요.** 조회는 엄청 많고, 순위가 바뀌는 건 몇 시간에 한 번이에요. 이 "읽기 압도적, 쓰기 드묾" 성격이 아래 설계를 정해요.

### 4. API

```text
GET /autocomplete?q=강남&limit=5
→ 200 ["강남역 맛집", "강남역", "강남구청", "강남 날씨", "강남 카페"]
```

입력이 같으면 결과도 같으니(몇 시간 동안은) **GET + 짧은 캐시**가 잘 어울려요.

### 5. 자료구조: 트라이

**트라이**(trie, 접두사 트리. 문자열을 한 글자씩 나눠 나무 가지로 저장하는 구조)는 루트에서 출발해 글자 하나마다 한 칸씩 내려가요. "car"와 "cat"은 "c → a"까지 같은 길을 쓰고 마지막에 갈라져요.

- 길이 p인 접두사의 노드를 찾는 데 **O(p)**예요. 전체 단어 수와 상관없이 친 글자 수만큼만 내려가요.
- 문제는 그다음이에요. 그 노드 **아래의 모든 단어**를 모아 빈도순으로 정렬해야 상위 5개가 나와요. "a"처럼 한 글자 접두사면 아래에 단어가 엄청 많아서 느려요.

### 6. 핵심: 노드마다 top5를 미리 붙인다

해결은 사전의 포스트잇이에요. **각 노드에 "이 접두사로 시작하는 단어 중 빈도 상위 5개"를 미리 저장**해 두면, 조회는 노드 찾기 O(p) + 5개 꺼내기로 끝나요.

한 번 재 본 실험 예시예요(파이썬, 영어 단어 1만 개, 노트북 1회 측정이라 절대값보다 비율만 보세요).

| 접두사 | 캐시 없음(하위 전체 탐색) | 노드별 top5 캐시 |
|---|---|---|
| a | 382µs | 0.12µs |
| ab | 48.9µs | 0.11µs |
| abc | 8.0µs | 0.13µs |

접두사가 짧을수록 아래가 넓어서 캐시 효과가 극적이에요. 대신 **트라이를 만드는 시간은 약 3배** 걸렸어요.

공짜는 아니에요.

- **메모리**: 노드마다 5개 목록이 붙어요.
- **갱신 비용**: 어떤 단어의 빈도가 바뀌면 그 단어로 가는 경로 위 **모든 노드의 목록**을 고쳐야 해요.

그래서 "검색될 때마다 고치기"보다 "모아서 통째로 다시 만들기"와 궁합이 좋아요.

### 7. 상위 설계: 조회와 갱신을 분리

**조회 경로(빠르게)**

1. 사용자가 입력 → 클라이언트가 **디바운스** 후 요청 1번(아래 8번 참고)
2. 브라우저·CDN 캐시에 있으면 바로 반환
3. 자동완성 서버가 입력을 정리(소문자로, 공백 정리, 한글은 자모 분해)
4. 메모리에 올린 트라이에서 접두사 노드까지 내려가 top5를 그대로 꺼냄
5. 부적절어 필터를 한 번 거쳐 응답

**갱신 경로(따로, 천천히)**

1. 검색이 실행될 때마다 로그를 남김
2. 몇 시간(또는 하루)마다 **배치**로 검색어별 빈도 집계
3. 금칙어 제거
4. 새 트라이를 만들고 노드마다 top5 채움
5. 스냅샷으로 저장 → 서버들이 새 버전으로 **통째로 교체**

조회 서버는 읽기 전용 구조만 봐요. 쓰기와 읽기가 엉키지 않으니 단순하고 빨라요.

### 8. 요청 줄이기: 디바운스와 캐시

**디바운스**(debounce, 입력이 멈춘 뒤 잠깐 기다렸다가 한 번만 실행하기)를 쓰면 "강남역맛집"을 빠르게 칠 때 글자마다 요청하지 않고, 손이 멈춘 뒤 한 번만 요청해요. 기다리는 시간은 보통 수십~수백 ms로 잡아요.

함께 챙길 것:

- **이전 요청 취소**: "강" 응답이 "강남" 응답보다 늦게 오면 화면이 옛날 결과로 덮여요. 브라우저의 `AbortController`로 이전 요청을 끊거나, 응답 순서를 확인해요.
- **캐시**: 같은 접두사는 몇 시간 동안 결과가 같으니 브라우저·CDN에 짧게 캐시해요. 자세한 건 [캐시·CDN으로 규모 키우기](../cache-cdn-scale/)를 보세요.

| | 디바운스 | 스로틀(throttle) |
|---|---|---|
| 동작 | 멈춘 뒤 한 번 | 일정 간격마다 최대 한 번 |
| 자동완성 | 주로 이것 | 계속 치는 동안에도 중간 결과를 보여 주고 싶을 때 |

### 9. 배치 vs 실시간

| | 주기적 배치 재생성 | 실시간 반영 |
|---|---|---|
| 방식 | 로그를 모아 몇 시간마다 트라이를 새로 만듦 | 검색될 때마다 빈도와 경로의 top5를 고침 |
| 장점 | 단순, 조회가 빠르고 안정적 | 새 이슈가 바로 뜸 |
| 단점 | 반영이 늦음(방금 터진 이슈가 몇 시간 뒤) | 경로 전체 갱신 비용, 동시성 처리 복잡 |

실무에선 둘을 섞는 게 일반적이에요. 기본은 배치로 만들고, **Kafka 같은 스트림**으로 최근 몇 분의 급상승 검색어만 따로 집계해 응답에 섞어요. 최근 검색일수록 점수를 더 주는 **시간 감쇠**를 쓰기도 해요.

### 10. 한국어: 초성과 음절 중간 상태

한국어는 영어와 두 가지가 달라요.

**① 음절 중간 상태**

"강"을 치는 동안 화면에는 "ㄱ" → "가" → "강"이 차례로 떠요. 그런데 음절 단위로 비교하면 **"가"로 시작하는 범위에 "강남"이 안 들어가요.** "가"와 "강"은 서로 다른 한 글자거든요.

그래서 트라이의 키를 음절이 아니라 **자모**(자음·모음 낱자) 단위로 쪼개요. "강" = ㄱ + ㅏ + ㅇ. 이러면 "가"(ㄱ+ㅏ)는 "강"(ㄱ+ㅏ+ㅇ)의 접두사가 돼요. 유니코드의 **NFD 정규화**(한 글자를 구성 요소로 분해하는 표준 방식)가 이 분해를 해 줘요.

**② 초성 검색**

"ㄱㄴ"만 쳐도 "강남"이 나오게 하려면, 검색어마다 **초성만 뽑은 문자열을 따로 색인**해 둬요("강남" → "ㄱㄴ"). 초성은 공식으로 계산할 수 있어요(아래 심화 참고).

초성 색인은 겹침이 많아요. "ㄱㄴ"은 강남, 경남, 기능… 모두 해당해서, 결과 순위는 역시 빈도로 정해요.

### 11. 부적절 검색어 거르기

- **1차: 배치 단계에서 제거.** 금칙어 목록에 있는 건 트라이를 만들 때 아예 빼요.
- **2차: 조회 직전 필터.** 응답 나가기 전에 차단 목록을 한 번 더 확인해요. 트라이를 다시 만들지 않아도 **즉시** 막을 수 있어요. 법적 요청(명예훼손 등)처럼 급한 건 이쪽으로 막고, 다음 배치에서 영구 제거해요.

### 심화: 한글 음절 분해 공식

유니코드 표준(Unicode Standard 3.12절 "Conjoining Jamo Behavior")은 완성형 한글 11,172자를 공식으로 배치해 뒀어요. "가"(U+AC00)부터 초성 19 × 중성 21 × 종성 28 순서로 늘어서요.

- 종성 28개에는 "받침 없음"이 포함돼요(실제 받침은 27개).
- 초성 하나당 글자 수는 중성 21 × 종성 28 = **588**이에요.

```python
CHO = "ㄱㄲㄴㄷㄸㄹㅁㅂㅃㅅㅆㅇㅈㅉㅊㅋㅌㅍㅎ"  # 초성 19개

def chosung(word):
    out = []
    for c in word:
        s = ord(c) - 0xAC00          # "가"로부터 몇 번째 글자인가
        if 0 <= s < 11172:           # 완성형 한글이면
            out.append(CHO[s // 588]) # 588자마다 초성이 바뀜
        else:
            out.append(c)
    return "".join(out)

# 중성 = (s % 588) // 28, 종성 = s % 28 (0이면 받침 없음)
assert chosung("강남") == "ㄱㄴ"
```

"강"은 0번 초성(ㄱ), "남"은 2번 초성(ㄴ)이 나와요. NFD로 "강"을 분해하면 U+1100 U+1161 U+11BC(조합형 자모 세 개)가 돼요. 단, 키보드로 친 낱자 "ㄱ"은 호환 자모(U+3131)라서 NFD 결과의 초성 ㄱ(U+1100)과 코드가 달라요. 입력도 같은 형태로 바꿔 준 뒤 비교해야 해요.

### 심화: Redis로 만든다면

Redis의 **Sorted Set**(점수로 정렬되는 집합)으로도 만들 수 있어요. 자료구조 자체는 [Redis 자료구조](../../redis/data-structures/)를 보세요.

**사전순 접두사 조회: `ZRANGEBYLEX`**

```text
ZADD ac 0 apple 0 apply 0 banana     # 점수는 모두 0으로 같게
ZRANGEBYLEX ac "[app" "[app\xff" LIMIT 0 5
```

- `[`는 "이 값 포함", `\xff`는 거의 모든 바이트보다 큰 값이라 "app으로 시작하는 모든 문자열"을 범위로 잡아요(Redis 문서의 문법에 기반한 일반 기법).
- **모든 멤버의 점수가 같아야** 결과가 정의돼요. 점수가 다르면 동작이 정해져 있지 않아요.
- 복잡도는 O(log N + M)이고, LIMIT으로 M을 고정하면 사실상 O(log N)이에요.
- Redis 6.2.0부터 **deprecated**(사용 중단 예정)예요. 새로 쓸 땐 `ZRANGE ac "[app" "[app\xff" BYLEX LIMIT 0 5`를 써요.

**함정 ①: 인기순이 아니라 사전순.** 꺼내는 순서가 가나다순이라 "인기 top5"가 아니에요. 인기순이 필요하면 접두사마다 키를 따로 두고 점수=빈도로 넣은 뒤 `ZREVRANGE 키 0 4`로 꺼내는 식으로 따로 풀어야 해요.

**함정 ②: 바이트 비교.** Redis는 문자열을 바이트 단위(memcmp)로 비교해요. 문서에도 ASCII가 아닌 문자는 사람이 기대하는 순서와 다를 수 있다고 적혀 있어요. 완성형 한글은 UTF-8에서 3바이트이고 코드 순서대로 바이트도 커져서("가" EAB080 &lt; "각" EAB081) 순서는 유니코드 순서와 같아요. 하지만 앞의 10번처럼 "가" 범위에 "강"이 안 들어가니, 음절 중간 입력을 받으려면 **자모 분해한 키**를 써야 해요. Redis 문서도 정규화한 키를 앞에 붙이는 패턴(`ZADD autocomplete 0 foo:Foo`)을 자동완성 예로 들어요.

### 심화: Elasticsearch completion suggester

Elasticsearch의 **completion suggester**는 입력하는 즉시 접두사로 제안을 주는 전용 기능이에요. 필드를 `completion` 타입으로 매핑해서 써요.

- 공식 문서 설명: 빠른 조회가 가능한 자료구조를 쓰지만 **만들기 비싸고 메모리에 저장**돼요. 7.17 문서엔 completion 인덱스가 전부 **힙**(JVM이 쓰는 메모리 영역)에 상주한다고 적혀 있어요.
- 그 자료구조가 **FST**(finite state transducer)이고 세그먼트마다 인덱싱 때 만들어진다는 설명은 Elastic 공식 블로그(2013) 출처예요. 현재 레퍼런스 문서에는 FST라는 단어가 없어요.
- 제안마다 양의 정수 `weight`로 순위를 매기고, `fuzzy`로 오타를 허용하고, `regex`도 돼요. category/geo **context**로 필터·가중치를 줄 수 있어요(필드당 최대 10개).
- 삭제된 문서는 제안에 나오지 않아요.

접두사 전용이라 "남"으로 "강남"을 찾는 중간 매칭에는 맞지 않아요. 중간 매칭은 `search_as_you_type` 필드나 edge n-gram 쪽이 흔히 언급되지만, 이 위키에선 공식 문서로 아직 확인하지 않았어요.

### 심화: 트라이가 한 서버에 안 들어가면

- 접두사 **첫 글자 기준으로 샤딩**(데이터를 여러 서버로 나누기)하면 단순하지만, 글자마다 단어 수가 크게 달라서(영어 "s"로 시작하는 단어는 많고 "x"는 적음) 서버 부하가 고르지 않아요.
- 그래서 실제 빈도 분포를 보고 구간을 나누거나, 해시로 나눠요.

## 면접 질문

<details>
<summary>Q. 자동완성에는 어떤 자료구조를 쓰나요? 시간복잡도는요?</summary>

**답변(30초)**
트라이를 쓰고, 노드마다 상위 k개를 미리 붙여 둬요. 트라이는 문자열을 한 글자씩 가지로 저장해서, 길이 p인 접두사의 노드를 O(p)에 찾아요. 하지만 그 아래 단어를 전부 모아 정렬하면 한 글자 접두사에서 아주 느려요. 그래서 노드마다 "이 접두사로 시작하는 인기 top5"를 저장해 두면 조회가 O(p) + 5개 꺼내기로 끝나요.

**꼬리질문**
- Q. 노드별 캐시의 단점은요? → 노드마다 목록이 붙어 메모리가 늘고, 빈도가 바뀌면 경로 위 모든 노드를 고쳐야 해요.
- Q. 그럼 갱신은 어떻게 하죠? → 실시간으로 고치지 않고 주기적으로 통째로 다시 만들어 교체해요.
</details>

<details>
<summary>Q. 응답 속도 목표는 얼마로 잡고, 근거는 뭔가요?</summary>

**답변(30초)**
사용자가 느끼는 전체 왕복 0.1초로 잡아요. Nielsen이 정리한 응답 시간 기준(원출처 Miller 1968, Card 외 1991)에서 0.1초는 "즉시 반응한다"고 느끼는 한계예요. 자동완성은 글자마다 뜨니까 이걸 넘으면 결과가 타이핑을 못 따라와요. 네트워크 왕복을 빼면 서버 예산은 더 작아서, 조회는 메모리 트라이에서 바로 꺼내는 구조로 가요.

**꼬리질문**
- Q. 1초, 10초는 뭔가요? → 1초는 생각 흐름이 안 끊기는 한계, 10초는 집중을 유지하는 한계예요.
</details>

<details>
<summary>Q. 키를 누를 때마다 서버를 부르면 어떤 문제가 생기고, 어떻게 해결하나요?</summary>

**답변(30초)**
요청 수가 검색보다 몇 배 많아져 서버가 버거워지고, 늦게 온 옛 응답이 최신 결과를 덮는 문제도 생겨요. 클라이언트에서 디바운스로 입력이 멈춘 뒤 한 번만 부르고, 새 요청을 보낼 때 이전 요청은 AbortController로 취소해요. 같은 접두사는 몇 시간 동안 결과가 같으니 브라우저·CDN에 짧게 캐시해 서버까지 오는 요청 자체를 줄여요.

**꼬리질문**
- Q. 디바운스와 스로틀 차이는요? → 디바운스는 멈춘 뒤 한 번, 스로틀은 일정 간격마다 최대 한 번이에요.
- Q. 최소 글자 수 제한은 어때요? → 한 글자 요청을 막으면 요청이 줄지만, 한국어는 한 글자 후보도 쓸모 있어서 짧은 접두사는 캐시로 푸는 쪽이 나아요.
</details>

<details>
<summary>Q. 검색 빈도는 어떻게 갱신하나요? 배치와 실시간을 비교해 보세요.</summary>

**답변(30초)**
기본은 배치예요. 검색 로그를 모아 몇 시간마다 빈도를 집계하고, 새 트라이를 만들어 서버에 통째로 교체해요. 조회 서버는 읽기만 하니 단순하고 빨라요. 단점은 방금 터진 이슈가 몇 시간 뒤에야 뜬다는 거예요. 그래서 스트림으로 최근 몇 분의 급상승어만 따로 집계해 응답에 섞는 식으로 보강해요.

**꼬리질문**
- Q. 왜 처음부터 실시간으로 안 하나요? → 빈도가 바뀔 때마다 경로 위 모든 노드의 top5를 고쳐야 하고, 조회 중인 구조를 동시에 고치는 게 복잡해서예요.
</details>

<details>
<summary>Q. Redis로 자동완성을 만든다면요? 주의할 점은요?</summary>

**답변(30초)**
Sorted Set에 점수를 모두 0으로 넣고 ZRANGEBYLEX로 접두사 범위를 꺼낼 수 있어요. 다만 세 가지를 조심해요. 점수가 모두 같아야 동작이 정의되고, 결과는 인기순이 아니라 사전순이에요. 그리고 6.2부터 deprecated라 ZRANGE BYLEX를 써요. 인기순이 필요하면 접두사별 키에 점수=빈도로 넣고 ZREVRANGE로 상위를 꺼내요.

**꼬리질문**
- Q. 한글은 문제없나요? → 바이트 비교라 완성형 순서는 맞지만 "가" 범위에 "강"이 안 들어가서, 자모 분해한 키가 필요해요.
</details>

<details>
<summary>Q. 한국어 초성 검색과 타이핑 중간 상태는 어떻게 처리하나요?</summary>

**답변(30초)**
두 가지 색인을 둬요. 타이핑 중간 상태는 음절을 자모로 분해한 키로 트라이를 만들어 해결해요. "강"을 ㄱ+ㅏ+ㅇ으로 쪼개면 "가"가 "강"의 접두사가 돼요. 초성 검색은 검색어마다 초성만 뽑은 문자열을 따로 색인해요. 초성은 유니코드 공식으로 (코드 − 0xAC00) ÷ 588의 몫이라 계산이 간단해요.

**꼬리질문**
- Q. 588은 어디서 나와요? → 중성 21 × 종성 28(받침 없음 포함)이에요.
- Q. 초성은 겹치지 않나요? → "ㄱㄴ"은 강남·경남·기능 등 많이 겹쳐요. 순위는 빈도로 정해요.
</details>

<details>
<summary>Q. Elasticsearch completion suggester는 일반 검색과 뭐가 다르고 주의할 점은요?</summary>

**답변(30초)**
일반 검색과 다른 접두사 전용 자료구조를 써서 아주 빨라요. 대신 만들기 비싸고 메모리에 올라가요. 7.17 문서에선 전부 힙에 상주한다고 해서, 데이터가 크면 힙 사용량을 봐야 해요. weight로 순위를 주고 fuzzy로 오타도 허용해요. 접두사 전용이라 중간 단어 매칭에는 맞지 않아요.

**꼬리질문**
- Q. 내부 자료구조는요? → Elastic 공식 블로그(2013)에 따르면 FST이고 세그먼트마다 인덱싱 때 만들어져요.
</details>

<details>
<summary>Q. 부적절한 검색어가 자동완성에 뜨면 어떻게 막나요?</summary>

**답변(30초)**
두 단계로 막아요. 평소엔 배치에서 트라이를 만들 때 금칙어를 빼요. 하지만 배치는 몇 시간 주기라 급한 건 못 막으니, 조회 직전에 차단 목록을 확인하는 필터를 둬요. 이 목록은 바로 바꿀 수 있어서 법적 요청 같은 급한 건 즉시 막고, 다음 배치에서 영구 제거해요.

**꼬리질문**
- Q. 필터 때문에 5개가 안 채워지면요? → 노드에 5개보다 조금 더 저장해 두고 걸러진 만큼 다음 순위로 채워요.
</details>

<details>
<summary>Q. 트라이가 서버 한 대 메모리에 안 들어가면 어떻게 하나요?</summary>

**답변(30초)**
여러 서버로 나눠요. 가장 단순한 건 첫 글자 기준 분할인데, 글자마다 단어 수가 달라 특정 서버에 몰려요. 그래서 실제 빈도 분포를 보고 구간을 나누거나 해시로 나눠요. 조회는 접두사를 보고 담당 서버로 보내요.

**꼬리질문**
- Q. 복제는요? → 읽기 전용이라 같은 스냅샷을 여러 대에 올려 읽기를 나누기 쉬워요.
</details>

## 서술형 연습

<details>
<summary>상황: 앱 출시 후 자동완성 API 요청이 검색 API보다 몇 배 많아져 서버가 버거워요.</summary>

**상황 파악**
자동완성은 타이핑마다 호출될 수 있어서 검색(엔터 한 번)보다 요청이 많은 게 정상이에요. 먼저 "사용자당 한 번 검색할 때 자동완성이 몇 번 불리는지", "같은 접두사 요청 비율이 얼마인지"를 봐요.

**원인 후보**
- 클라이언트가 키 입력마다 요청한다(디바운스 없음).
- 이전 요청을 취소하지 않아 쓸모없는 응답까지 서버가 다 처리한다.
- 같은 접두사("ㄱ", "a")가 반복되는데 캐시가 없다.

**해결책과 트레이드오프**
1. **클라이언트 디바운스 + 이전 요청 취소**: 요청 수가 크게 줄어요. 대신 기다리는 시간만큼 결과가 늦게 떠요. 너무 길면 0.1초 체감 목표를 깨요.
2. **브라우저·CDN 캐시**: 결과가 몇 시간 동안 같으니 짧은 TTL로 캐시하면 서버까지 오는 요청이 줄어요. 대신 급상승어나 차단어 반영이 TTL만큼 늦어요.
3. **짧은 접두사는 정적 결과로**: 한두 글자 접두사는 경우의 수가 적어서 미리 만들어 CDN에 올려 둘 수 있어요. 빌드·배포 단계가 하나 늘어요.
4. **최소 글자 수 제한**: 가장 쉽지만, 한국어는 한 글자 후보도 쓸모 있어서 사용성이 떨어져요.

**내가 고를 방법**
디바운스 + 요청 취소를 먼저 넣고, 짧은 TTL 캐시를 더해요. 둘 다 서버 코드를 거의 안 바꾸고 효과가 크거든요. 그래도 많으면 짧은 접두사 정적화로 가요. 최소 글자 수 제한은 한국어 사용성 때문에 마지막 수단으로 둬요.

**채점 포인트**: 디바운스, 이전 요청 취소(순서 역전 문제), 캐시 TTL과 반영 지연의 트레이드오프, 0.1초 목표, 읽기 전용이라 캐시가 잘 맞는다는 근거
</details>

<details>
<summary>상황: 큰 이슈가 터졌는데 자동완성에 몇 시간째 관련 검색어가 안 떠요.</summary>

**상황 파악**
검색은 이미 폭증하고 있는데 자동완성만 반영이 안 된 상황이에요. 자동완성이 배치로 트라이를 다시 만드는 구조라면, 다음 배치 전까지는 안 뜨는 게 설계대로의 동작이에요.

**원인 후보**
- 배치 주기가 길다(몇 시간~하루).
- 배치가 실패했거나 밀려서 새 트라이가 배포되지 않았다.
- 새 검색어가 금칙어 필터에 잘못 걸렸다.

**해결책과 트레이드오프**
1. **배치 주기 단축**: 가장 단순해요. 대신 빌드 비용(노드별 top5 계산 때문에 빌드가 무거움)이 주기만큼 늘고, 그래도 분 단위까지는 어려워요.
2. **급상승 스트림 집계 병합**: 검색 로그를 Kafka 같은 스트림으로 흘려 최근 몇 분의 급상승어만 따로 세고, 응답 때 배치 결과와 섞어요. 거의 실시간으로 뜨지만 시스템이 하나 더 생기고, 장난성 급상승을 걸러야 해요.
3. **시간 감쇠 가중치**: 최근 검색일수록 점수를 크게 줘서 오래된 인기어가 자리를 비켜 주게 해요. 순위가 더 출렁여요.

**내가 고를 방법**
먼저 배치 실패 여부와 필터 오탐부터 확인해요. 정상 동작이었다면 기본 트라이는 배치로 두고, 급상승어만 스트림으로 보강해요. 조회 경로는 여전히 읽기 전용이라 빠르고, 이슈는 분 단위로 반영돼요. 급상승 쪽엔 부적절어 필터를 반드시 같이 걸어요.

**채점 포인트**: 배치 주기 한계 인식, 배치 실패 모니터링, 스트림 급상승 집계와 병합, 시간 감쇠, 급상승 경로에도 필터 적용
</details>

<details>
<summary>상황: "ㄱㄴ"을 입력하면 아무것도 안 뜬다는 문의가 들어왔어요.</summary>

**상황 파악**
사용자는 "강남"을 기대하고 초성만 쳤어요. 트라이가 완성형 음절("강", "남") 기준이라면 "ㄱ"이라는 글자로 시작하는 검색어가 없으니 결과가 0개인 게 당연해요. 같은 이유로 "가"를 쳤을 때 "강남"이 안 뜨는지도 같이 확인해요.

**원인 후보**
- 색인이 음절 단위라 초성 입력을 처리하지 못한다.
- 음절 중간 상태("가")도 "강"과 다른 글자로 비교된다.

**해결책과 트레이드오프**
1. **초성 색인을 따로 구축**: 검색어마다 초성 문자열("강남" → "ㄱㄴ")을 계산해 별도 트라이에 넣고, 입력이 초성으로만 돼 있으면 그쪽을 조회해요. 공식이 간단해 배치에 넣기 쉬워요. 대신 저장 공간이 늘고 "ㄱㄴ" = 강남·경남·기능처럼 겹침이 많아 순위 품질이 중요해요.
2. **자모 분해 키**: 음절을 자모로 쪼개 트라이를 만들면 "가"가 "강"의 접두사가 돼서 중간 입력 문제가 풀려요. 하지만 이것만으로 "ㄱㄴ"(강남의 자모는 ㄱㅏㅇㄴㅏㅁ)은 안 맞아요.
3. **클라이언트에서 초성 매칭**: 서버를 안 바꾸지만 후보 전체를 클라이언트가 가져야 해서 대규모엔 안 맞아요.

**내가 고를 방법**
1번과 2번을 같이 해요. 초성 문의는 1번으로, 같은 뿌리의 "가 → 강" 문제는 2번으로 풀어요. 두 색인 모두 배치 단계에서 만들어 조회 경로는 그대로 빠르게 유지해요. 초성 결과는 빈도순으로 정렬해 겹침 문제를 줄여요.

**채점 포인트**: 음절 단위 비교의 한계, 초성 별도 색인, 자모 분해(NFD), 유니코드 공식(588 = 21 × 28), 겹침과 빈도 정렬, 배치에서 생성
</details>

## 필기 포인트

- 트라이에서 접두사 노드 찾기는 **O(p)**(p = 접두사 길이). 전체 단어 수와 무관.
- 한글 완성형: U+AC00부터 **11,172자** = 초성 19 × 중성 21 × 종성 28. 588 = 21 × 28. 초성 인덱스 = (코드 − 0xAC00) ÷ 588의 몫.
- 종성 28에는 받침 없음 포함(실제 받침 27개).
- 디바운스 = 멈춘 뒤 한 번, 스로틀 = 일정 간격마다 최대 한 번.
