:::tip[한 줄 요약]
알림 시스템은 **요청을 받는 API**와 **실제로 보내는 채널별 워커**를 큐로 떼어 놓는 구조예요. 푸시는 우리 서버가 폰에 직접 못 보내고 **FCM**(안드로이드)·**APNs**(아이폰)에 대신 보내 달라고 요청해요. 앱을 지운 기기의 토큰은 지우고, 일시 오류만 재시도하고, **알림 ID로 중복을 막고**, 보내기 직전에 **수신 설정·빈도 제한·광고 야간 규정**을 확인해요.
:::

:::note[처음이라면 여기까지]
① 알림 요청은 바로 보내지 않고 **큐**(일감을 줄 세워 두는 대기열)에 넣고 "접수했어요"라고 먼저 답해요. 보내는 건 뒤에서 워커가 해요.

② 푸시·문자·이메일은 **큐를 따로** 둬요. 문자 업체가 고장 나도 푸시는 계속 나가게요.

③ 푸시는 "우리 서버 → FCM/APNs → 폰" 순서로 가요. 폰마다 **디바이스 토큰**(그 폰 앱의 주소)이 있고, 앱을 지우면 이 주소가 무효가 돼요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

우체국을 떠올려 보세요. 손님은 **접수 창구**에 편지를 맡기고 영수증을 받으면 바로 돌아가요. 창구 직원이 직접 배달하러 나가면 뒤에 선 손님들이 한없이 기다려야 하니까요.

접수된 편지는 종류별 바구니에 나뉘어 담겨요. 등기 바구니, 일반 우편 바구니, 소포 바구니. 바구니마다 **전담 배달원**이 있어서, 소포 트럭이 고장 나도 등기 편지는 제때 나가요.

배달원은 주소가 틀린 편지를 계속 들고 다니지 않아요. "이사 감, 수취인 없음"이 확인되면 주소록에서 그 주소를 지워요. 또 같은 편지를 두 번 배달하지 않도록 송장 번호로 확인하고, 받는 사람이 "광고 전단은 넣지 마세요"라고 해 뒀다면 전단은 빼요.

알림 시스템도 같아요. 접수 창구가 **알림 API**, 바구니가 **채널별 큐**, 배달원이 **채널별 워커**, 송장 번호가 **알림 ID**예요.

단, 실제로는 우리 배달원이 집 앞까지 가지 않아요. 푸시는 FCM·APNs, 문자는 문자 중계 업체, 이메일은 발송 대행 업체라는 **다른 회사 배달망**에 넘겨요. 그래서 "넘겼다(발송)"와 "도착했다(도달)"는 따로 확인해야 해요.

## 제대로 알기

### 왜 큐를 두고, 왜 채널마다 나누나

알림 요청을 받은 자리에서 바로 FCM이나 문자 업체를 부르면 문제가 생겨요.

- 외부 서비스가 느리면 주문 API까지 느려져요. 사용자는 알림 때문에 주문 버튼이 안 눌리는 걸 겪어요.
- 외부 서비스가 잠깐 죽으면 그 알림은 그냥 사라져요.
- 마케팅 100만 건을 한꺼번에 보내면 서버가 감당을 못 해요.

그래서 API는 **큐에 넣고 바로 응답**하고, 뒤에서 워커가 천천히 꺼내 보내요. 큐 자체의 동작은 [메시지 큐와 Kafka](../../distributed/message-queue-kafka/)에 정리돼 있어요.

큐를 **채널별로**(push / sms / email) 나누는 이유는 이래요.

- **장애 격리**: 문자 업체가 30분 다운돼도 sms 큐만 쌓이고 푸시·이메일은 그대로 나가요. 큐가 하나면 앞에 밀린 문자 때문에 뒤의 푸시까지 막혀요.
- **채널마다 다른 속도·재시도·비용**: FCM은 분당 한도가 있고, 문자는 건당 돈이 들고, 이메일은 업체 평판을 관리해야 해요. 워커 수와 재시도 정책을 채널마다 따로 맞출 수 있어요.

### 채널 비교

| | 앱 푸시 | 문자(SMS) | 이메일 |
|---|---|---|---|
| 거쳐 가는 곳 | FCM(안드로이드)·APNs(아이폰) | 문자 중계 업체 API → 통신사망 | 발송 대행(SES, SendGrid 등) → SMTP |
| 받는 주소 | 디바이스 토큰(바뀔 수 있음) | 전화번호 | 이메일 주소 |
| 비용 | 쌈 | 건당 비용, 비쌈 | 쌈 |
| 잘 쓰는 곳 | 주문·배송·채팅·마케팅 | 인증번호, 푸시 실패 시 대체 채널 | 영수증, 뉴스레터, 긴 안내 |
| 무효 주소 신호 | FCM `UNREGISTERED`(404), APNs `Unregistered`(410) | 업체별로 다름 | 하드 바운스(없는 주소) |
| 주의 | 앱 삭제·재설치로 토큰이 바뀜 | 길이 제한 | 바운스·스팸 신고가 쌓이면 정상 메일도 스팸함으로 감 |

- **SMTP**: 메일 서버끼리 메일을 주고받는 표준 약속이에요.
- **바운스**: 메일이 반송되는 것. 없는 주소처럼 영구 실패면 **하드 바운스**(목록에서 뺌), 메일함 가득 참처럼 일시 실패면 **소프트 바운스**(재시도)예요.

### 푸시가 폰까지 가는 길

1. 앱이 실행되면 OS를 통해 FCM 또는 APNs에서 **디바이스 토큰**을 받아요.
2. 앱이 그 토큰을 **우리 서버에 등록**해요. 서버는 "사용자 42번 = 토큰 A, B"처럼 저장해요. 한 사람이 폰·태블릿 여러 대를 쓰면 토큰도 여러 개예요.
3. 알림을 보낼 때 우리 서버가 **FCM/APNs에 "토큰 A로 이 내용 보내 줘"**라고 요청해요.
4. FCM/APNs가 기기에 전달해요. 기기가 꺼져 있으면 잠깐 보관했다가 켜지면 보내요.

```text
앱 ──(토큰 등록)──▶ 우리 서버 ──(토큰 + 내용)──▶ FCM / APNs ──▶ 폰
```

우리 서버가 폰에 직접 보내지 못하는 이유는, 폰이 수많은 앱 서버와 각각 연결을 유지하면 배터리가 버티지 못하기 때문이에요. 그래서 OS 회사가 운영하는 연결 하나로 모아요.

### 토큰은 바뀌고, 무효가 돼요

토큰은 영구 주소가 아니에요. APNs는 백업에서 복원할 때, 새 기기에 앱을 설치할 때, OS를 재설치할 때 새 토큰을 줘요. 애플은 토큰을 앱에 저장해 두지 말고 실행할 때마다 시스템에 요청하라고 안내해요.

앱을 지운 기기로 계속 보내면 FCM/APNs가 "이 주소는 없어요"라고 답해요.

| 서비스 | 응답 | 뜻 | 할 일 |
|---|---|---|---|
| FCM | `UNREGISTERED` (HTTP 404) | 앱 인스턴스 등록이 해제됨(앱 삭제 등) | 토큰 삭제, 다시 안 보냄 |
| FCM | `INVALID_ARGUMENT` (400) | 요청이 잘못됨. 페이로드가 정상인데도 나면 토큰이 잘못된 것 | 토큰 문제면 삭제 |
| APNs | `410 Unregistered` | 이 토큰이 더 이상 활성 상태가 아님 | 토큰 삭제, 다시 안 보냄 |
| APNs | `400 BadDeviceToken` | 토큰이 무효이거나 개발/운영 환경이 안 맞음 | 환경부터 확인, 무효면 삭제 |

APNs는 개발용(sandbox)과 운영용(production) 토큰이 달라요. 개발 빌드에서 받은 토큰을 운영 서버로 보내면 `BadDeviceToken`이 나요. 그래서 400이 무조건 "삭제"는 아니에요.

FCM 공식 권장은 이래요.

- 토큰을 저장할 때 **마지막으로 받은 시각**을 같이 저장하고, 앱이 토큰을 올릴 때마다 갱신해요.
- 매일 같은 주기 작업으로 기준 기간(공식 예시는 30일)을 넘긴 토큰을 지워요.

### 어떤 실패를 재시도하나

| 종류 | 예 | 처리 |
|---|---|---|
| 일시 오류 | FCM `QUOTA_EXCEEDED`(429), `UNAVAILABLE`(503), `INTERNAL`(500) / APNs 429·500·503 | **지수 백오프**(1초, 2초, 4초…처럼 점점 길게 기다리기) + **지터**(기다리는 시간을 조금씩 랜덤하게 흔들기)로 재시도 |
| 영구 오류 | FCM 400·403·404 / APNs 400·410·413 | 재시도 안 함. 토큰 삭제나 요청 수정 |
| 설정 오류 | FCM `THIRD_PARTY_AUTH_ERROR`(401, APNs 인증서·키 문제) | 재시도 안 함. 자격 증명을 고쳐야 함 |

영구 오류를 재시도하면 계속 실패하면서 한도만 깎아 먹어요. 재시도 횟수를 넘긴 메시지는 **DLQ**(Dead Letter Queue, 처리 못 한 메시지를 따로 모아 두는 큐)로 보내 나중에 사람이 확인해요. FCM `UNAVAILABLE`에 `Retry-After` 헤더가 오면 그 시간만큼 기다려요.

### 같은 알림이 두 번 가지 않게: 알림 ID

큐는 보통 **at-least-once**(최소 한 번은 전달, 대신 두 번 갈 수도 있음)예요. 워커가 FCM에 보내고 나서 "처리 끝" 표시(ack)를 하기 직전에 죽으면, 큐는 그 메시지를 다른 워커에게 다시 줘요. 그러면 사용자는 같은 푸시를 두 번 받아요.

막는 방법은 **멱등 키**(같은 요청이 여러 번 와도 결과가 한 번과 같게 만드는 고유 번호)예요.

1. 알림마다 고유 ID를 만들어요. 예: `이벤트ID + 사용자ID + 채널`.
2. 보내기 전에 "이 ID 이미 보냄?"을 확인해요. DB의 unique 제약이나 Redis `SET NX`(없을 때만 저장) + 만료 시간을 써요.
3. 이미 있으면 건너뛰고, 없으면 기록하고 보내요.

다만 외부 서비스까지 **정확히 한 번**은 보장할 수 없어요. "기록은 했는데 FCM 호출 전에 죽음" 같은 틈이 남아요. 멱등 키로 "거의 한 번"에 가깝게 만드는 거예요.

주문 서비스가 "주문 완료" 이벤트를 낼 때 DB 저장과 이벤트 발행이 어긋나는 문제(저장은 됐는데 이벤트가 안 나감)는 **Outbox 패턴**으로 막아요. → [Outbox와 멱등성](../../distributed/outbox-idempotency/)

### 사용자 설정과 빈도 제한

사용자별로 이런 걸 저장해요.

- 채널별(푸시/문자/이메일) 수신 여부
- 카테고리별(거래/보안/마케팅) 수신 여부
- 광고 수신 동의, **야간 광고 수신 동의**, 동의한 일시

워커는 **보내기 직전에** 한 번 더 확인해요. 큐에서 기다리는 동안 사용자가 수신을 끌 수 있으니까요.

**빈도 제한**은 "한 사용자에게 마케팅 알림은 하루 N건까지" 같은 규칙이에요. 구현은 [처리율 제한기](../rate-limiter/)의 카운터 방식을 그대로 쓰면 돼요. 거꾸로 외부 한도에 맞춰 **우리가 보내는 속도**도 조절해야 해요(아래 심화에서 숫자로 다뤄요).

### 템플릿과 전송 추적

**템플릿**: 문구를 코드에 박지 않고 `템플릿 ID + 변수`로 관리해요. 예: `ORDER_DONE` 템플릿에 `{name}`, `{orderNo}`를 채워요. 이렇게 하면 문구 수정에 배포가 필요 없고, 다국어를 넣기 쉽고, 채널별 길이 제한에 맞춰 버전을 나눌 수 있어요. 광고 문자의 "(광고)" 표시도 템플릿에서 강제할 수 있어요.

**전송 추적**: 알림마다 상태를 기록해요.

```text
요청됨 → 큐 대기 → 발송(외부 서비스가 접수) → 도달 → 열람
                     └→ 실패(사유)
```

가장 많이 헷갈리는 부분은 **"FCM이 200을 줬다 = 사용자가 받았다"가 아니라는 것**이에요. 200은 FCM이 **접수**했다는 뜻이고, 기기에 **도달**했는지는 따로 측정해요. 도달은 FCM 리포트(BigQuery로 메시지별 이벤트를 내보낼 수 있음)나 이메일 대행사 웹훅으로, 열람은 앱이 알림을 열었을 때 서버로 이벤트를 보내 모아요.

### 공통 뼈대로 설계해 보기: "주문·배송·마케팅 알림을 푸시·SMS·이메일로"

[시스템 설계 면접 푸는 법](../design-approach/)의 순서대로 풀어 볼게요.

**1. 요구사항**
- 기능: 주문 완료·배송 출발 같은 **거래 알림**과 쿠폰·이벤트 같은 **마케팅 알림**을 푸시·문자·이메일로 보냄. 사용자가 채널·카테고리별로 끌 수 있음. 발송 결과를 조회할 수 있음.
- 비기능: 거래 알림은 몇 초 안에 가야 함. 마케팅 대량 발송이 거래 알림을 늦추면 안 됨. 같은 알림이 두 번 가면 안 됨. 광고성 알림은 법 규정을 지켜야 함.

**2. 규모 추정** (숫자는 연습용 가정이에요)
- 하루 주문 100만 건, 주문당 거래 알림 3건(완료·출발·도착) → 하루 300만 건 ÷ 86,400 ≈ 평균 초당 35건. 피크 3배로 가정하면 초당 100건 안팎.
- 마케팅은 한 번에 500만 명. FCM 기본 한도(프로젝트당 분당 60만 메시지)로만 따지면 9분쯤 걸려요. 한도를 거래 알림과 나눠 써야 하니 실제로는 더 천천히 보내요.

**3. API**
- `POST /notifications` — 입력: `templateId`, `userIds`, `variables`, `category`(거래/마케팅), `idempotencyKey`. 출력: 접수 ID(202 Accepted, 접수만 하고 처리는 나중에).
- `GET /notifications/{id}` — 발송 상태 조회.

**4. 데이터 모델**
- 디바이스 토큰: 사용자ID, 토큰, 플랫폼(Android/iOS), 마지막 갱신 시각
- 사용자 설정: 사용자ID, 채널·카테고리별 수신 여부, 광고·야간 동의와 일시
- 템플릿: 템플릿ID, 채널, 언어, 문구
- 발송 기록: 알림ID(멱등 키, unique), 상태, 실패 사유, 시각

**5. 상위 설계**
```text
주문 서비스 ─(Outbox)─▶ 알림 API ─▶ 설정·빈도 확인 ─▶ 템플릿 ─▶ 중복 검사
                                                                │
          ┌──────────────────┬──────────────────┬───────────────┘
          ▼                  ▼                  ▼
      push 큐             sms 큐            email 큐
          ▼                  ▼                  ▼
      푸시 워커           문자 워커          메일 워커
          ▼                  ▼                  ▼
     FCM / APNs         문자 중계사        이메일 대행
          └─────────────── 발송 기록 ◀─────────┘
```

**6. 심화로 고를 곳**: 거래와 마케팅을 같은 큐에 두지 않기(우선순위 분리), 무효 토큰 정리, 재시도와 중복 방지, 야간 광고 규정.

**7. 병목·트레이드오프**
- 큐를 거치니 알림이 몇 초 늦어질 수 있어요 ↔ 대신 외부 장애가 주문 API로 번지지 않아요.
- 멱등 기록을 확인하는 비용이 매번 들어요 ↔ 대신 중복 발송을 막아요.
- 마케팅 발송 속도를 낮추면 끝나는 데 오래 걸려요 ↔ 대신 거래 알림 몫의 한도를 지켜요.

### 심화: 우선순위·만료·덮어쓰기 (공식 헤더 이름)

푸시에는 "얼마나 급한지", "언제까지 의미 있는지", "앞의 것을 덮어써도 되는지"를 정하는 옵션이 있어요.

| 목적 | FCM | APNs |
|---|---|---|
| 우선순위 | `priority`: `high` / `normal`. 생략하면 normal(Android 문서 기준, notification·data 메시지 모두) | `apns-priority`: 10(즉시, 생략 시 기본) / 5(기기 전력 상태 고려) / 1(전력 우선) |
| 만료 | `ttl`(REST v1은 `"3600s"` 같은 초 단위 문자열). 최대 4주, 생략 시 4주. 0이면 바로 못 보낼 때 버림 | `apns-expiration`: UNIX 시각(초). 그때까지 보관하며 재시도. 0이면 한 번만 시도 |
| 덮어쓰기 | `collapse_key`(Android). 아직 전달 안 된 같은 키의 옛 메시지를 새 것으로 대체. 기기당 서로 다른 키 4개까지 보관 | `apns-collapse-id`: 같은 값의 알림을 기기에서 하나로 합침. 최대 64바이트 |

- **high를 남용하지 마세요.** high는 잠든 기기를 깨워 배터리를 써요. FCM은 즉시성이 필요 없으면 normal을 권장하고, APNs의 5와 1은 묶여서 오거나 쓰로틀링되거나 경우에 따라 안 갈 수 있어요. 인증번호·거래 알림은 high/10, 마케팅은 normal/5처럼 나눠요.
- **인증번호는 짧은 만료**를 줘요. 10분 지난 인증번호가 뒤늦게 도착하면 혼란만 줘요.
- **덮어쓰기는 "최신 값만 의미 있을 때"**만 써요(예: 배송 위치, 경기 점수). 채팅처럼 하나하나 다 가야 하면 쓰지 않아요.

<Aside type="caution" title="꺼졌던 폰을 켜도 밀린 알림이 다 오지 않아요">
APNs는 기기가 오프라인이면 앱(번들 ID)당 **1건만** 보관하고, 보통 마지막 알림이 남아요(최대 30일, `apns-expiration`에 따라). FCM도 collapse key는 기기당 4개까지만 보관해요. 반드시 전해야 하는 내용이면 푸시만 믿지 말고 앱을 열었을 때 서버에서 "안 읽은 알림 목록"을 받아 오게 해요.
</Aside>

### 심화: 외부 한도와 보내는 속도 조절

FCM HTTP v1 기본 한도(공식 문서 기준):

- 프로젝트당 **분당 60만 메시지**(요청 수가 아니라 메시지 수). 넘으면 429 `RESOURCE_EXHAUSTED`이고 다음 분에 다시 차요. 전체·토픽 한도 초과는 최소 1분부터 백오프하라고 해요.
- Android 기기 하나에는 **분당 240건, 시간당 5,000건**.
- collapsible 메시지는 기기의 앱마다 20건까지 몰아서 보낼 수 있고, 이후 3분에 1건씩 다시 채워져요.

그래서 대량 발송은 이렇게 해요.

1. 대상자를 한 번에 다 조회하지 않고 **배치로 나눠** 큐에 넣어요.
2. 마케팅 워커는 한도의 일부만 쓰도록 속도를 묶고, 나머지는 거래 알림 몫으로 남겨요.
3. 429가 나면 바로 다시 보내지 말고 백오프해요. 다 같이 다시 보내면 또 429가 나요.

APNs 페이로드는 최대 4KB(VoIP는 5KB)라 템플릿을 만들 때 길이도 확인해요.

### 심화: 한국의 광고성 알림 야간 규정

<Aside type="note" title="법률 자문이 아니에요">
아래는 설계에 필요한 개념을 정리한 것이고, 실제 적용은 최신 법령 원문과 법무 검토로 확인하세요.
</Aside>

정보통신망법 제50조는 **영리 목적의 광고성 정보**를 다뤄요.

- 제1항: 광고를 보내려면 수신자의 **명시적인 사전 동의**가 필요해요. 예외로, 거래하면서 연락처를 직접 받은 곳이 같은 종류 상품을 광고하는 경우가 있고, 시행령 제61조 제1항에 따라 그 기간은 거래가 끝난 날부터 6개월이에요.
- 제2항: 수신을 거부하거나 동의를 철회한 사람에게는 보낼 수 없어요.
- 제3항: **오후 9시부터 다음 날 오전 8시까지** 광고를 보내려면 위 동의와 **별도로** 또 동의를 받아야 해요. 시행령 제61조 제2항이 정한 예외 매체는 **전자우편**이라, 앱 푸시와 문자는 야간 별도 동의가 필요하고 이메일은 예외예요. (제3항 문언은 국가법령정보센터 원문으로 확인했어요. 예외 매체가 전자우편이라는 시행령 내용은 법제처 해석례에서 확인했어요. 법령은 바뀔 수 있으니 적용 전에 **최신 원문 재확인 필요**.)
- 제4항: 광고에는 **전송자의 명칭·연락처**와 **수신거부·동의 철회를 쉽게 하는 방법**을 밝혀야 해요. "(광고)" 같은 구체적인 표시 방식은 시행령에 맡겨져 있는데, 그 세부 문언은 **확인하지 못했어요**.

이 규정은 **광고성 정보에만** 적용돼요. 주문·결제·배송·보안 알림 같은 정보성(거래) 알림은 대상이 아니에요. 그래서 설계에서는:

- 템플릿과 알림 요청에 **카테고리(광고/정보)**를 필수로 둬요.
- 워커는 보내기 직전에 "광고 + 야간 시간 + 야간 동의 없음"이면 보내지 않고 **아침으로 미뤄요**(예약 발송).
- 동의 여부와 **동의 일시**를 저장해 두면 나중에 근거를 보여 줄 수 있어요.

### 심화: 이메일 도달률 관리

- 발신 도메인을 **SPF·DKIM·DMARC**(이 도메인에서 보낸 메일이 진짜라는 걸 증명하는 설정)로 인증해요. 안 하면 스팸함으로 가기 쉬워요.
- 대행사가 웹훅으로 바운스·스팸 신고를 알려 주면, 하드 바운스 주소는 목록에서 빼요. 쌓이면 발신 평판이 떨어져 정상 영수증 메일까지 스팸함으로 가요.
- 대량 메일의 원클릭 수신거부 헤더(`List-Unsubscribe`, RFC 8058)가 2024년부터 Gmail·Yahoo 대량 발신자 요건에 들어갔다고 알려져 있어요. (업계 일반 정보이고 공식 문서로는 확인하지 못했어요.)

## 면접 질문

<details>
<summary>Q. 푸시 알림은 어떤 경로로 사용자 폰에 도달하나요?</summary>

**답변(30초)**
우리 서버가 폰에 직접 보내지 않고 FCM이나 APNs를 거쳐요. 앱이 실행되면 플랫폼에서 디바이스 토큰을 받아 우리 서버에 등록하고, 서버는 사용자별로 토큰을 저장해요. 알림을 보낼 때 서버가 FCM·APNs에 "이 토큰으로 이 내용을 보내 달라"고 요청하면, 플랫폼이 기기에 전달해요. 기기가 꺼져 있으면 플랫폼이 만료 시간 동안 보관했다가 보내요.

**꼬리질문**
- Q. 토큰은 한 번 받으면 계속 쓰나요? → 아니요. 재설치·백업 복원·새 기기에서 바뀌어요. 앱이 실행될 때마다 받아서 바뀌었으면 다시 올려요.
- Q. 한 사용자가 기기를 여러 대 쓰면요? → 토큰을 여러 개 저장하고 모두에게 보내요.
</details>

<details>
<summary>Q. 알림 요청을 바로 보내지 않고 큐에 넣는 이유는요? 채널별로 큐를 나누는 이유는요?</summary>

**답변(30초)**
외부 서비스가 느리거나 죽어도 요청한 쪽(주문 API)이 영향을 받지 않게 하려고 큐에 넣고 바로 응답해요. 큐에 남아 있으니 장애가 풀린 뒤 다시 보낼 수 있고, 대량 발송도 속도를 조절하며 흘려보낼 수 있어요. 채널별로 나누는 건 장애 격리 때문이에요. 문자 업체가 다운돼도 sms 큐만 쌓이고 푸시·이메일은 계속 나가요. 채널마다 한도·비용·재시도 정책이 달라서 워커를 따로 맞출 수도 있어요.

**꼬리질문**
- Q. 큐를 쓰면 단점은요? → 몇 초 지연이 생기고, 같은 메시지가 두 번 처리될 수 있어서 중복 방지가 필요해요.
- Q. 같은 푸시 채널 안에서도 나눌 게 있나요? → 거래 알림과 마케팅 알림을 다른 큐로 나눠 마케팅 대량 발송이 거래 알림을 막지 않게 해요.
</details>

<details>
<summary>Q. 디바이스 토큰은 어떻게 관리하고, 무효 토큰은 어떻게 알아내나요?</summary>

**답변(30초)**
토큰을 사용자ID·플랫폼·마지막 갱신 시각과 함께 저장하고, 앱이 토큰을 올릴 때마다 시각을 갱신해요. 무효 토큰은 발송 응답으로 알아요. FCM이 `UNREGISTERED`(404)를, APNs가 410 `Unregistered`를 주면 앱이 지워졌거나 토큰이 더 이상 활성이 아니라는 뜻이라 바로 지우고 다시 보내지 않아요. 여기에 더해 오래 갱신되지 않은 토큰(공식 예시는 30일)을 주기 작업으로 정리해요.

**꼬리질문**
- Q. APNs가 400 `BadDeviceToken`을 주면 바로 지우나요? → 개발/운영 환경이 안 맞아도 나기 때문에, 먼저 환경 설정을 확인해요.
- Q. 무효 토큰을 안 지우면요? → 계속 실패하며 한도와 처리 시간을 낭비하고, 발송 성공률 지표도 왜곡돼요.
</details>

<details>
<summary>Q. FCM 호출이 실패하면 어떻게 하나요? 모든 실패를 재시도하나요?</summary>

**답변(30초)**
아니요, 오류 종류로 나눠요. 429·500·503 같은 일시 오류는 지수 백오프와 지터로 재시도하고, `Retry-After`가 있으면 따라요. 400·404·410 같은 영구 오류는 재시도해도 똑같이 실패하니 토큰을 지우거나 요청을 고쳐요. 재시도 횟수를 넘긴 메시지는 DLQ로 보내 나중에 확인해요.

**꼬리질문**
- Q. 왜 지터를 넣나요? → 실패한 워커들이 같은 시각에 다시 보내면 또 몰려서 실패해요. 기다리는 시간을 흩어 놔요.
- Q. 401 `THIRD_PARTY_AUTH_ERROR`는요? → APNs 인증서나 키 문제라 재시도가 아니라 자격 증명을 고쳐야 해요.
</details>

<details>
<summary>Q. 같은 알림이 두 번 가는 걸 어떻게 막나요?</summary>

**답변(30초)**
큐는 보통 최소 한 번 전달이라, 워커가 보낸 뒤 처리 완료를 알리기 전에 죽으면 같은 메시지가 다시 와요. 그래서 알림마다 이벤트ID·사용자·채널로 만든 고유 ID를 두고, 보내기 전에 DB unique 제약이나 Redis `SET NX`로 "이미 보냄"을 확인해요. 이미 있으면 건너뛰어요. 다만 외부 서비스까지 정확히 한 번은 보장 못 하니 "거의 한 번"에 가깝게 만드는 거예요.

**꼬리질문**
- Q. FCM collapse key로 중복을 막으면 안 되나요? → 아직 전달 안 된 메시지만 대체하는 보조 수단이라, 서버 쪽 멱등 처리를 대신하지 못해요.
- Q. 주문 저장과 알림 이벤트 발행이 어긋나면요? → Outbox 패턴으로 같은 트랜잭션에 이벤트를 기록하고 따로 발행해요.
</details>

<details>
<summary>Q. 사용자가 알림을 받았는지, 열었는지 어떻게 아나요?</summary>

**답변(30초)**
발송·도달·열람을 따로 기록해요. FCM이 200을 주는 건 접수했다는 뜻이지 기기에 도달했다는 뜻이 아니에요. 도달은 FCM 전송 리포트나 BigQuery 내보내기, 이메일은 대행사 웹훅으로 받고, 열람은 앱이 알림을 열 때 서버로 이벤트를 보내 모아요. 그래서 "발송 성공률 99%"만 보고 안심하면 안 돼요.

**꼬리질문**
- Q. 캠페인별로 보고 싶으면요? → FCM `analyticsLabel`로 묶어서 볼 수 있어요.
</details>

<details>
<summary>Q. 마케팅 알림을 500만 명에게 보낼 때 무엇을 고려하나요?</summary>

**답변(30초)**
네 가지를 봐요. 첫째, 대상자를 배치로 나눠 큐에 넣고, FCM 프로젝트 한도(분당 60만 메시지)에 맞춰 속도를 묶어 거래 알림 몫을 남겨요. 둘째, 마케팅은 거래 알림과 다른 큐로 보내 거래 알림이 밀리지 않게 해요. 셋째, 사용자별 빈도 제한과 수신 설정을 보내기 직전에 확인해요. 넷째, 광고성이라 오후 9시~오전 8시에는 야간 동의자에게만 보내거나 아침으로 미뤄요.

**꼬리질문**
- Q. 우선순위는 high로 보내나요? → 마케팅은 normal(APNs 5)로 보내요. high는 기기를 깨워 배터리를 써서 꼭 필요할 때만 써요.
- Q. 이메일도 야간 동의가 필요한가요? → 시행령이 전자우편을 야간 규정 예외로 두고 있어요. 다만 원문 재확인이 필요해요.
</details>

<details>
<summary>Q. 인증번호 SMS가 늦게 오는 문제는 어떻게 다루나요?</summary>

**답변(30초)**
인증번호는 늦게 오면 의미가 없어서 우선순위와 만료로 다뤄요. 인증·거래·마케팅을 다른 큐로 나눠 인증 큐 워커는 항상 여유 있게 두고, 메시지에 짧은 만료를 줘서 일정 시간이 지난 인증번호는 보내지 않고 버려요. 문자 업체가 느리면 다른 업체로 넘기는 대체 경로도 둬요.

**꼬리질문**
- Q. 푸시로 인증번호를 보내면요? → 싸고 빠르지만 앱이 설치·로그인돼 있어야 해서, 보통 문자를 기본으로 두고 푸시는 보조로 써요.
</details>

## 서술형 연습

<details>
<summary>상황: 마케팅 푸시 500만 건 발송을 시작한 뒤로 "주문 완료" 알림이 10분 넘게 늦게 온다는 문의가 쏟아져요. 원인과 대책을 서술하세요.</summary>

**상황 파악**
주문 알림이 실패한 게 아니라 **늦게** 도착해요. 마케팅 발송 시작 시점과 겹치니, 두 알림이 같은 자원(큐·워커·외부 한도)을 나눠 쓰고 있을 가능성이 커요. 먼저 큐 대기 시간과 FCM 429 비율을 확인해요.

**원인 후보**
1. 거래 알림과 마케팅 알림이 **같은 push 큐**에 있어, 앞에 쌓인 500만 건 뒤에 주문 알림이 줄 서 있음.
2. 큐는 나뉘어 있어도 **워커를 같이 써서** 워커가 마케팅만 처리 중.
3. 마케팅이 FCM 프로젝트 한도(분당 60만 메시지)를 다 써서 주문 알림도 429를 받고 백오프 중.
4. 모든 알림을 high로 보내 기기 쪽 처리까지 몰림(부차적).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 큐를 카테고리별로 분리(거래 / 마케팅), 워커도 분리 | 마케팅이 아무리 쌓여도 거래 알림 줄은 짧아요 | 큐·워커 운영 대상이 늘어요 |
| B. 하나의 큐 안에서 우선순위 처리 | 구조 변경이 작아요 | 큐 제품에 따라 우선순위 지원이 약하고, 높은 쪽이 계속 들어오면 낮은 쪽이 굶을 수 있어요 |
| C. 마케팅 발송 속도 제한(한도의 일부만 사용) | 외부 한도를 거래 알림 몫으로 남겨요 | 마케팅이 끝나는 데 더 오래 걸려요 |
| D. 마케팅을 normal 우선순위·배치 분할로 발송 | 기기·플랫폼 부담이 줄어요 | 마케팅 도달이 조금 늦어요 |

**내가 고를 방법**
A와 C를 같이 써요. 큐와 워커를 거래/마케팅으로 나눠 **줄 자체를 분리**하고, 마케팅 워커는 FCM 한도의 일부만 쓰도록 속도를 묶어요. 큐만 나누면 외부 한도에서 다시 부딪히기 때문에 둘 다 필요해요. 마케팅은 원래 몇 분 늦어도 되는 알림이라 C의 단점을 받아들일 수 있어요. 마케팅은 D처럼 normal로 보내고, 거래 알림 큐 대기 시간에 경보를 걸어 재발을 일찍 알아채요.

**채점 포인트**: 지연과 실패 구분, 큐 대기 시간·429 지표 확인, 거래/마케팅 큐·워커 분리, 외부 한도(분당 60만) 나눠 쓰기, 발송 속도 조절·배치 분할, 우선순위(high/normal) 구분, 우선순위 큐의 굶주림 문제, 재발 경보.
</details>

<details>
<summary>상황: 일부 사용자가 "주문 완료" 푸시를 두 번씩 받았다고 해요. 원인과 대책을 서술하세요.</summary>

**상황 파악**
일부 사용자만 겪으니 상시 버그보다는 특정 상황(배포, 워커 재시작, 큐 재전달)에서 생긴 문제일 가능성이 커요. 발송 기록에서 같은 주문·같은 사용자에 대한 발송이 두 건인지, 두 건의 시각 차이와 처리한 워커가 무엇인지 확인해요.

**원인 후보**
1. 워커가 FCM에 보낸 뒤 ack 전에 죽어서 큐가 같은 메시지를 다시 전달함(at-least-once).
2. 주문 서비스가 이벤트를 두 번 발행함(재시도, Outbox 릴레이 중복 발행).
3. FCM 응답 타임아웃을 실패로 보고 재시도했는데, 사실 첫 요청이 접수돼 있었음.
4. 한 사용자의 같은 기기 토큰이 중복 저장돼 있음(토큰 등록 시 중복 체크 없음).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 알림 ID(이벤트ID+사용자+채널)로 발송 전 중복 검사(DB unique) | 원인 1·2·3을 한 번에 막아요, 기록이 남아요 | 매 발송마다 DB 쓰기 비용 |
| B. 같은 검사를 Redis `SET NX` + 만료로 | 빠르고 DB 부담이 적어요 | 만료 후 재전달은 못 막고, Redis 장애 시 정책이 필요해요 |
| C. 토큰 테이블에 (사용자, 토큰) unique 제약 | 원인 4를 막아요 | 기존 중복 데이터 정리가 필요해요 |
| D. `apns-collapse-id`·collapse key를 알림 ID로 설정 | 아직 전달 전인 중복은 기기에서 합쳐져요 | 이미 도착한 건 못 막는 보조 수단이에요 |

**내가 고를 방법**
A를 기본으로 해요. 주문 알림은 양이 많지 않아 DB unique 제약 비용이 감당되고, 왜 중복이 막혔는지 기록이 남아 추적하기 좋아요. 양이 많은 마케팅은 B로 바꿀 수 있어요. 토큰 중복은 C로 막고, D는 보조로 겹쳐 둬요. 다만 "기록 후 FCM 호출 전에 죽음" 같은 틈 때문에 정확히 한 번은 불가능하다고 밝히고, 그 경우 빠지는 쪽과 중복 쪽 중 무엇을 택할지(주문 알림은 한 번 빠지는 것보다 두 번이 낫다 등)를 정해 둬요. 이벤트 발행 중복은 [Outbox와 멱등성](../../distributed/outbox-idempotency/)처럼 소비자 쪽 멱등 처리로 흡수해요.

**채점 포인트**: at-least-once, ack 전 장애, 멱등 키(알림 ID) 구성, DB unique vs Redis SET NX, 타임아웃 후 재시도의 중복, 토큰 중복 저장, collapse는 보조 수단, 정확히 한 번 불가능, Outbox.
</details>

<details>
<summary>상황: 몇 달 전부터 FCM 오류(404 UNREGISTERED)가 급증했고, 발송 시간도 점점 길어져요. 확인해 보니 앱을 삭제한 사용자에게도 계속 보내고 있었어요. 어떻게 할까요?</summary>

**상황 파악**
404 `UNREGISTERED`는 앱 인스턴스 등록이 해제됐다는 뜻(앱 삭제 등)이에요. 이 응답을 받고도 토큰을 지우지 않아 **죽은 토큰이 계속 쌓이고**, 발송할 때마다 그만큼 헛요청을 하고 있어요. 전체 토큰 중 무효 비율과, iOS 쪽 410 응답도 같이 확인해요.

**원인 후보**
1. 발송 워커가 404·410 응답을 "실패"로만 기록하고 토큰 정리를 안 함.
2. 404를 일시 오류로 보고 재시도까지 해서 헛요청이 몇 배로 늘어남.
3. 오래된 토큰 정리 작업이 없음(마지막 갱신 시각을 저장하지 않음).
4. 앱이 토큰이 바뀌어도 서버에 다시 올리지 않아 옛 토큰만 남음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 응답 즉시 정리: FCM 404 `UNREGISTERED`, APNs 410이면 토큰 삭제 | 다음 발송부터 바로 헛요청이 사라져요 | 워커에 토큰 테이블 쓰기 책임이 생겨요 |
| B. 주기 정리: 마지막 갱신 시각이 기준 기간(공식 예시 30일)을 넘은 토큰 삭제 | 발송하지 않은 토큰도 정리돼요 | 기준이 짧으면 오래 안 쓴 정상 사용자를 놓칠 수 있어요 |
| C. 재시도 정책 수정: 영구 오류(400·404·410)는 재시도 안 함 | 헛요청 배수가 사라져요 | 오류 분류표를 관리해야 해요 |
| D. 앱이 실행마다 토큰을 받아 바뀌었으면 서버에 갱신 | 옛 토큰이 쌓이는 근원을 줄여요 | 앱 배포가 필요하고 옛 버전 사용자는 남아요 |

**내가 고를 방법**
A와 C를 바로 적용해요. 서버만 고치면 되고 효과가 즉시 나요. 이미 쌓인 토큰은 B로 한 번 정리하고 이후 매일 돌려요. 기준 기간은 공식 예시(30일)를 참고하되, 서비스의 재방문 주기를 보고 정해요. 장기적으로 D로 앱이 토큰을 갱신하게 해요. APNs 400 `BadDeviceToken`은 환경 불일치일 수 있어서 자동 삭제 대상에서 빼고 따로 확인해요. 이후 "무효 토큰 비율"을 지표로 두고 경보를 걸어요.

**채점 포인트**: UNREGISTERED(404)·410 Unregistered의 의미, 즉시 토큰 삭제, 영구 오류는 재시도 금지, 마지막 갱신 시각 저장과 주기 정리, 앱의 토큰 갱신, BadDeviceToken 환경 불일치 예외, 무효 토큰 비율 지표.
</details>

## 필기 포인트

- 푸시 경로: 앱이 토큰 등록 → 우리 서버 → FCM(안드로이드)/APNs(아이폰) → 기기. 서버가 기기에 직접 보내지 않아요.
- 무효 토큰: FCM `UNREGISTERED`(404), APNs `410 Unregistered` → 토큰 삭제. APNs `400 BadDeviceToken`은 환경 불일치일 수도 있어요.
- 재시도: 429·500·503만 지수 백오프. 400·404·410은 재시도 안 함.
- FCM 200 = 접수(accepted). 도달(delivered)은 별개예요.
- APNs 헤더: `apns-priority`(10/5/1), `apns-expiration`, `apns-collapse-id`(최대 64바이트), `apns-id`, `apns-push-type`. 페이로드 최대 4KB.
- FCM: TTL 최대·기본 4주, 프로젝트당 분당 60만 메시지, collapse key 기기당 4개.
- 정보통신망법 제50조: 광고성 정보만 대상, 오후 9시~오전 8시는 별도 동의(시행령상 전자우편 예외, 최신 원문 재확인 필요).
