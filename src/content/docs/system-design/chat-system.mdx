:::tip[한 줄 요약]
채팅 서버는 사용자와 **연결을 계속 잡고 있는 상태 있는 서버**예요. 그래서 서버가 여러 대면 **누가 어느 서버에 붙었는지 기록**하고, 서버끼리 메시지를 넘겨 줄 **공유 통로**(Redis Pub/Sub·Kafka 등)를 둬요. 메시지는 **DB에 먼저 저장**하고, **방별 순번**과 **클라이언트 임시 ID**로 순서·중복·누락을 관리해요.
:::

:::note[처음이라면 여기까지]
① 채팅은 서버가 먼저 "새 메시지 왔어요"를 보내야 해서, 보통 **WebSocket**(한 번 연결하면 양쪽이 계속 주고받는 통로)을 써요.

② 연결은 특정 서버 한 대에 묶여요. 그래서 서버가 여러 대면 "B는 2번 서버에 있다"는 **주소록**과 서버끼리 메시지를 넘기는 **통로**가 필요해요.

③ 연결은 언제든 끊겨요. 그래서 메시지는 DB에 먼저 저장하고, 다시 붙으면 "마지막으로 받은 번호 다음부터" 받아 와요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

옛날 전화국의 **교환원**을 떠올려 보세요. 전화를 걸면 교환원이 교환대에 선을 꽂아 두 사람을 이어 주고, 통화가 끝날 때까지 그 선을 **계속 꽂아 둬요**. 웹사이트처럼 "물어보면 답하고 끝"이 아니에요.

교환대가 하나면 쉬워요. 그런데 손님이 늘어 교환대를 세 개로 늘리면 문제가 생겨요. 1번 교환대에 연결된 철수가 3번 교환대에 연결된 영희와 이야기하려면, 1번 교환원이 **"영희는 3번 교환대에 있다"를 알아야** 하고, **교환대끼리 잇는 선**도 있어야 해요.

교환원이 퇴근할 때도 조심해야 해요. 꽂힌 선을 뽑기 전에 "다른 교환대로 다시 걸어 주세요"라고 알려 줘야 하고, 수만 명이 같은 순간에 다시 걸면 다른 교환대가 터지니 조금씩 나눠서 걸게 해야 해요.

채팅 시스템도 같아요. 교환대가 **채팅 서버**, 꽂힌 선이 **WebSocket 연결**, "누가 몇 번에 있나" 장부가 **세션 레지스트리**, 교환대끼리 잇는 선이 **Pub/Sub나 메시지 큐**예요.

단, 실제로는 통화 내용이 녹음되듯 메시지를 **DB에 저장**해요. 선이 끊겨도 나중에 저장된 걸 다시 받아 오면 되니까, 연결은 "빨리 전하는 길"이고 진짜 원본은 DB예요.

## 제대로 알기

### 실시간 전달 방식: 요약만

폴링·SSE·WebSocket의 차이, 핸드셰이크, Ping/Pong은 [WebSocket과 실시간 통신](../../web/websocket-realtime/)에 자세히 있어요. 여기선 표 하나로 정리해요.

| 방식 | 방향 | 한 줄 설명 | 채팅에 쓰면 |
|---|---|---|---|
| 숏 폴링 | 클라이언트가 물어봄 | 몇 초마다 "새 거 있어요?" | 지연 = 폴링 주기, 헛요청 많음 |
| 롱 폴링 | 클라이언트가 물어봄 | 서버가 새 데이터나 타임아웃까지 답을 미룸 | 매번 HTTP 헤더 비용, 재요청 사이 공백 |
| SSE | 서버 → 클라이언트 | 한 방향 스트림, 브라우저가 자동 재연결 | 보내는 쪽은 일반 HTTP 요청으로 따로 |
| WebSocket | 양방향 | 연결 하나로 양쪽이 계속 주고받음 | **채팅의 보통 선택** |

채팅은 양쪽이 수시로 주고받으니 보통 WebSocket을 써요. 알림처럼 한 방향이면 SSE로도 충분해요. 하나 기억할 점: **WebSocket에는 자동 재연결이 없어서** 앱이 직접 구현해야 해요.

### 연결 서버는 "상태 있는 서버"예요

일반 REST 서버는 **무상태**(stateless, 요청마다 필요한 정보가 다 들어 있어서 어느 서버가 받아도 같은 결과)라서 로드밸런서가 아무 서버로나 보내도 돼요.

WebSocket은 달라요. 연결을 맺으면 그 **연결 객체가 특정 서버의 메모리**에 있어요. B에게 메시지를 보내려면 반드시 B의 연결을 가진 그 서버를 거쳐야 해요. 이런 서버를 **상태 있는**(stateful) 서버라고 해요. 그래서 세 가지 고민이 생겨요.

1. 누가 어느 서버에 붙어 있나? → **세션 레지스트리**
2. 다른 서버에 붙은 사람에게 어떻게 넘기나? → **서버 간 전달 통로**
3. 서버를 끄면(배포) 붙어 있던 사람들은? → **재연결 유도**

그래서 실무에선 **연결만 잡는 서버**(WebSocket 게이트웨이)와 **저장·로직을 하는 서버**(무상태 API)를 나누는 구성이 흔해요[일반]. 연결 서버는 가볍게 두고 자주 재시작하지 않게요.

### 세션 레지스트리: 누가 어느 서버에 있나

**세션 레지스트리**는 "사용자 → 연결된 서버" 장부예요[일반]. 연결될 때 쓰고, 끊길 때 지워요. 보통 Redis처럼 빠른 공유 저장소에 둬요.

```text
session:userB  →  server-2    (연결 시 기록, 끊기면 삭제, TTL도 걸어 둠)
```

서버가 갑자기 죽으면 "끊길 때 지우기"를 못 해요. 그래서 이 키에도 TTL(만료 시간)을 걸고 하트비트로 연장해요. 아래 "온라인 상태"와 같은 원리예요.

방법은 두 가지예요[일반].

| 방법 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 레지스트리를 보고 콕 집어 보내기 | "B는 서버2" 확인 → 서버2에게만 전달 | 필요 없는 서버는 안 깨움 | 레지스트리 조회·관리 필요, 값이 낡으면 엉뚱한 서버로 감 |
| 방 채널로 뿌리기 | 모든 서버가 자기 연결이 있는 방 채널을 구독 → 발행하면 구독한 서버만 받음 | 레지스트리 없이도 동작, 단순 | 큰 방은 많은 서버가 같이 받음 |

### 서버 간 전달: Pub/Sub, Kafka, 브로커 릴레이

A(서버1)가 B(서버2)에게 보낼 때, 서버1은 B의 연결이 없어서 직접 못 보내요. 그래서 서버들이 함께 쓰는 통로에 올려요.

| 통로 | 특징 | 주의 |
|---|---|---|
| [Redis Pub/Sub](../../redis/pubsub-streams/) | 빠르고 단순. 발행하면 지금 구독 중인 서버에 바로 전달 | **at-most-once**(최대 한 번): 구독자가 잠깐 끊겨 있으면 그 메시지는 사라짐 |
| Redis Streams | 컨슈머 그룹, at-least-once(최소 한 번, 중복 가능) | 확인(ack)·재처리 관리 필요 |
| [Kafka](../../distributed/message-queue-kafka/) | 방 ID를 키로 쓰면 같은 방 메시지는 같은 파티션 → 방 안 순서 유지 | 운영 부담이 크고 실시간 알림용으로는 무거울 수 있음 |
| 외부 STOMP 브로커(RabbitMQ 등) | Spring의 broker relay로 연결 | 브로커 운영 필요 |

**핵심은 원본과 통로를 나누는 것**이에요. Redis Pub/Sub는 메시지가 사라질 수 있으니, 메시지 원본은 **DB에 먼저 저장**하고 Pub/Sub는 "지금 접속 중인 사람에게 빨리 알리는 용도"로만 써요. 놓친 메시지는 재연결할 때 DB에서 다시 받아 가요.

Spring STOMP를 쓴다면, 기본 **Simple Broker**는 구독 정보를 서버 메모리에 둬서 공식 문서가 **클러스터링(서버 여러 대)에 적합하지 않다**고 밝혀요. 서버 여러 대면 broker relay로 외부 브로커를 붙여요. 설정은 [WebSocket과 실시간 통신](../../web/websocket-realtime/)에 있어요.

### 메시지 ID와 순서

"보낸 시각으로 정렬하면 되지 않나?" 싶지만 두 가지 문제가 있어요.

- 서버마다 **시계가 조금씩 달라서** 나중에 보낸 메시지가 앞에 올 수 있어요.
- **같은 밀리초**에 두 메시지가 생길 수 있어요.

그래서 두 가지를 써요.

| 방법 | 무엇 | 좋은 점 |
|---|---|---|
| **Snowflake ID** | 시간 + 기계 번호 + 순번을 합친 64비트 숫자 | 서버끼리 의논 없이 고유 ID, 대략 시간순 정렬 |
| **방별 순번**[일반] | 채팅방마다 1, 2, 3…을 한 곳에서 매김 | 방 안 순서가 엄격, **빈 번호로 누락 감지** |

중요한 건 **전체 메시지의 순서는 필요 없고, 방 안 순서만 필요하다**는 점이에요. 모든 방을 한 줄로 세우는 건 비싸고 쓸모도 없어요. 방별 순번은 "3 다음에 5가 왔네? 4가 빠졌다 → 다시 요청" 같은 누락 감지에도 쓰여요. 자세한 원리는 [분산 환경의 시간과 ID](../../distributed/distributed-time-ids/)에 있어요.

### 전송 보장: 저장 → ack → 다시 받기

"WebSocket이니까 안전하게 가겠지"는 오해예요. 모바일 네트워크는 수시로 끊겨요. 유실·중복을 막는 흐름은 이래요[일반].

1. 앱이 보낼 때 **클라이언트 임시 ID**(`clientMsgId`, 앱이 만든 고유값)를 붙여요. 화면엔 "전송 중"으로 표시.
2. 서버는 DB에 저장하고 정식 ID(순번)를 매긴 뒤 **ack**(받았다는 확인)를 돌려줘요. 앱은 "전송 중"을 확정으로 바꿔요.
3. ack를 못 받으면 앱이 **같은 임시 ID로 다시 보내요**. 서버는 "이 임시 ID는 이미 저장했다"를 보고 새로 저장하지 않고 기존 ID로 ack만 다시 줘요. 이게 **멱등성**(같은 요청을 여러 번 해도 결과가 한 번과 같음)이에요. → [Outbox 패턴과 멱등성](../../distributed/outbox-idempotency/)
4. 받는 쪽은 방마다 **마지막으로 받은 순번**을 기억해 두고, 다시 연결되면 "그 다음부터" 요청해요. SSE가 재연결할 때 `Last-Event-ID`를 보내는 것과 같은 발상이에요.

### 읽음 표시와 안 읽은 수

메시지마다 "누가 읽었나" 목록을 저장하면, 100명 방에 메시지 1,000개면 쓰기가 10만 번이에요. 대신 **(방, 사용자)마다 마지막으로 읽은 메시지 순번 하나만** 저장해요[일반].

| 질문 | 계산 |
|---|---|
| B가 안 읽은 메시지 수 | 방의 최신 순번 − B의 마지막 읽은 순번 (예: 108 − 105 = 3) |
| 메시지 #104를 안 읽은 사람 수 | 마지막 읽은 순번이 104보다 작은 멤버 수 |

메시지 ID가 시간순이라 "이 번호 이하는 다 읽음"으로 해석할 수 있어서 가능한 방법이에요.

### 온라인 상태: 하트비트 + TTL

"WebSocket 연결이 있으면 온라인"이라고 하면 안 돼요. 폰이 와이파이에서 LTE로 바뀌면 연결이 **조용히 죽어도** 서버는 한동안 몰라요.

그래서 **하트비트**(앱이 "나 살아 있어요"를 주기적으로 보내는 신호)와 **TTL**(키가 저절로 사라지는 시간)을 같이 써요[일반].

```text
앱이 20초마다 하트비트  →  SET presence:u1 online EX 60   (60초 뒤 자동 삭제)
앱 강제 종료            →  하트비트 끊김
60초 뒤                 →  키 만료 → 조회하면 "오프라인"
```

장점은 앱이 비정상 종료돼 "나가요" 신호를 못 보내도 **저절로 오프라인 처리**된다는 거예요. TTL을 하트비트 주기의 몇 배로 두는 이유는, 지하철에서 잠깐 끊길 때마다 온라인/오프라인이 깜빡이지 않게 하려는 거예요.

친구가 많으면 "온라인 됐어요"를 모든 친구에게 보내는 비용도 커요. 그래서 **화면에 보이는 사람만 조회**하거나 상태 변화를 묶어서 보내요[일반].

### 그룹 채팅: 작은 방과 큰 방은 다르게

| 방 크기 | 방식 | 장점 | 단점 |
|---|---|---|---|
| 1:1, 소규모 | 메시지를 멤버 각자에게 밀어 줌(쓰기 시 팬아웃) | 받는 쪽은 자기 것만 읽으면 됨 | 인원 × 메시지만큼 쓰기 |
| 대규모(수천~수만 명) | 방에 **한 번만 저장**, 접속 중인 멤버가 있는 서버로만 실시간 전달, 나머지는 접속할 때 방에서 읽어 감(읽기 시 팬아웃) | 쓰기가 한 번 | 읽을 때 방 단위로 조회 |

**팬아웃**(fan-out)은 메시지 하나를 여러 명에게 퍼뜨리는 일이에요. 오프라인 멤버에게는 [알림 시스템](../notification-system/)으로 푸시를 보내요. 그래서 방 인원에 상한을 두거나, 큰 방만 다른 경로로 처리하는 혼합 방식이 흔해요[일반]. [뉴스 피드 설계](../news-feed/)의 푸시/풀 선택과 같은 고민이에요.

### 공통 뼈대로 설계해 보기: "1:1·그룹 채팅 앱"

[시스템 설계 면접 푸는 법](../design-approach/)의 순서대로 풀어 볼게요.

**1. 요구사항**
- 기능: 1:1 채팅, 그룹 채팅(최대 인원은 질문해서 정함), 텍스트 메시지, 읽음 표시·안 읽은 수, 온라인 상태, 오프라인 사용자 푸시, 여러 기기 로그인.
- 비기능: 메시지가 **사라지면 안 됨**, 방 안 순서가 맞아야 함, 보내면 1초 안에 상대 화면에 보임(목표로 가정), 서버를 늘릴 수 있어야 함.

**2. 규모 추정** (숫자는 연습용 가정이에요)
- [설계 면접 푸는 법의 예제 2](../design-approach/)와 같은 가정: 하루 500만 명, 1인당 40개 → 하루 2억 건, 평균 초당 약 2,300건, 피크(3배 가정) 약 7,000건, 5년 저장 약 36.5TB(1벌).
- 동시 접속을 20%로 가정하면 **동시 연결 100만 개**. 서버 한 대가 감당하는 연결 수는 메모리·설정에 따라 달라 부하 테스트로 정해요. 한 대에 5만 개로 가정하면 연결 서버 20대 이상.
- 결론: 병목은 대역폭이 아니라 **초당 쓰기 수와 동시 연결 수**예요.

**3. API**
- WebSocket 연결: `GET /ws` (로그인 토큰으로 인증)
- 보내기(WebSocket 메시지): `roomId`, `clientMsgId`, `content` → 응답 ack: `clientMsgId`, `seq`(방별 순번)
- 받기(서버가 내려보냄): `roomId`, `seq`, `senderId`, `content`
- 놓친 것 받기(HTTP): `GET /rooms/{roomId}/messages?afterSeq=103&limit=50`
- 이전 대화 스크롤: `GET /rooms/{roomId}/messages?beforeSeq=50&limit=50`
- 읽음: `POST /rooms/{roomId}/read` 본문 `seq`

**4. 데이터 모델**
- 메시지: (방ID, 순번)이 기본 키, 보낸 사람, 내용, 시각, 클라이언트 임시 ID(방ID와 함께 unique)
- 방 멤버: 방ID, 사용자ID, **마지막 읽은 순번**
- 세션 레지스트리(Redis): `session:userId` → 서버 ID, TTL
- 온라인 상태(Redis): `presence:userId`, TTL

**5. 상위 설계**
```text
 앱 ──WebSocket──▶ LB ──▶ 연결 서버 1..N ──▶ 채팅 API(무상태) ──▶ 메시지 DB
                            ▲    │                 │
                            │    │                 └──▶ 알림 시스템(오프라인 푸시)
                            │    ▼
                  Redis: 세션 레지스트리·온라인 상태
                            ▲
                            └── 서버 간 전달: Redis Pub/Sub / Kafka
```

**6. 심화로 고를 곳**: 서버 간 전달(레지스트리 + Pub/Sub), 메시지 순서(방별 순번), 유실·중복(임시 ID + 재동기화), 배포 시 재연결, 저장소 파티션.

**7. 병목·트레이드오프**
- DB 저장 후 전달하니 몇 ms 늦어져요 ↔ 대신 연결이 끊겨도 메시지가 안 사라져요.
- Pub/Sub는 빠르지만 유실될 수 있어요 ↔ DB 재동기화로 메꿔요. Kafka는 덜 잃지만 무겁고 지연이 늘 수 있어요.
- 방별 순번은 순서가 엄격하지만 한 방의 순번을 한 곳에서 매겨야 해서, 아주 붐비는 방은 그곳이 병목이 돼요.

### 심화: 배포할 때 연결은 어떻게 되나

Spring Boot의 **graceful shutdown**(종료할 때 진행 중 요청을 마저 끝내고 내려가기)은 Tomcat·Jetty·Reactor Netty에서 기본으로 켜져 있어요. 새 요청은 막고, 진행 중 요청은 유예 시간(`spring.lifecycle.timeout-per-shutdown-phase`, 문서 예시 `20s`) 안에 끝내게 해요.

<Aside type="caution">
Spring Boot 문서는 "persistent connection은 동작이 다를 수 있다"고만 하고, **WebSocket 같은 장기 연결을 어떻게 정리하는지는 언급하지 않아요.** WebSocket은 "끝나기를 기다리는 요청"이 아니라 끝나지 않는 연결이라, 재연결 유도는 직접 설계해야 해요.
</Aside>

흔히 쓰는 순서예요[일반].

1. 내릴 서버를 **로드밸런서에서 빼서** 새 연결을 막아요.
2. 기존 연결에 **Close 1001**(going away, "서버가 내려가요")을 보내요.
3. 클라이언트는 **무작위 지연(지터)** 뒤에 다른 서버로 재연결해요. 지터가 없으면 수만 명이 같은 순간에 몰려요. → [장애 격리: 타임아웃·재시도·서킷브레이커](../../architecture/resilience/)
4. 재연결 직후 방마다 "마지막 받은 순번 이후"를 받아 빈틈을 채워요.
5. 서버를 종료해요.

롤링 배포 자체는 [무중단 배포 전략](../../architecture/zero-downtime-deploy/)를 참고하세요.

### 심화: 로드밸런서·프록시 타임아웃

nginx는 기본으로 60초 동안 백엔드가 아무것도 안 보내면 연결을 끊고(`proxy_read_timeout`), AWS ALB의 idle timeout도 기본 60초예요. 조용한 채팅방이 1분마다 끊긴다면 이게 원인이에요. **하트비트 주기를 이 값보다 짧게** 둬요. nginx 설정 방법은 [WebSocket과 실시간 통신](../../web/websocket-realtime/)에 있어요.

### 심화: Spring에서 다른 서버에 붙은 사용자

Spring STOMP의 사용자 전용 목적지(`/user/queue/...`)는 사용자 세션별 주소로 바뀌는데, 공식 문서는 **사용자가 다른 서버에 붙어 있으면 해석이 안 될 수 있다**고 적고 `userDestinationBroadcast` 설정을 안내해요. 세션 레지스트리 문제를 프레임워크 차원에서 푸는 장치예요.

### 심화: Snowflake 비트 구성

Snowflake ID는 64비트를 **시간 41비트(밀리초) + 기계 ID 10비트 + 시퀀스 12비트**로 나눠요. 기계끼리 의논 없이 겹치지 않는 ID를 만들고 대략 시간순으로 정렬돼요. 단, "A를 보고 답장한 B가 반드시 뒤"같은 인과적 순서까지 보장하진 않아요. Discord는 모든 ID를 Snowflake로 쓰고, `created_at`을 정렬 키로 쓰지 않은 이유를 "두 메시지의 생성 시각이 같을 수 있어서"라고 밝혔어요(2017).

### 심화: 저장소 선택 — Discord 공개 블로그 사례

채팅에서 가장 많은 읽기는 **"이 방의 최근 메시지 N개"**와 위로 스크롤하며 그 이전을 이어 읽는 거예요. 그래서 **(방 ID, 메시지 ID 역순)** 범위 조회가 빨라야 해요. 처음엔 RDB에 `(room_id, message_id)` 인덱스로 시작해도 돼요[일반].

Discord는 이 과정을 공개 블로그에 두 번 썼어요. **연도가 다르니 수치를 섞지 마세요.**

**2017년 글 "How Discord Stores Billions of Messages"**
- 하루 메시지가 4천만 → 1억 → 글을 쓸 때 1억 2천만 이상으로 늘었어요.
- 처음엔 MongoDB 레플리카셋 하나 + (channel_id, created_at) 인덱스. 2015년 11월쯤 저장 메시지 1억 개에서 **데이터와 인덱스가 RAM에 안 들어가** 지연이 예측 불가해졌어요.
- Cassandra로 옮김. 기본 키는 처음 (channel_id, message_id) → 이후 **((channel_id, bucket), message_id)**. bucket은 약 10일치로, 파티션을 100MB 아래로 유지하려는 장치예요.
- 12노드, 복제 계수 3. 쓰기 1ms 미만, 읽기 5ms 미만.
- 겪은 문제: 수백만 개가 지워지고 1개 남은 채널을 읽는 데 20초 + 10초 GC 정지(삭제 흔적인 툼스톤 때문) → 툼스톤 보관 기간 10일 → 2일, 빈 버킷 건너뛰기.

**2023년 글 "How Discord Stores Trillions of Messages"**
- 2022년 초 Cassandra 177노드, 메시지 수조 개.
- 문제: **핫 파티션**(한 채널에 트래픽이 몰려 클러스터 전체가 느려짐), 컴팩션 밀림, GC 정지로 지연 급증, 온콜 부담.
- 2022년 5월 메시지 저장소를 **ScyllaDB**로 전환. API와 DB 사이에 Rust로 만든 data services 계층을 두고, 같은 행에 대한 동시 요청을 DB 질의 한 번으로 합치는 **request coalescing**과 채널 ID 기준 consistent hash 라우팅을 넣었어요.
- 결과 72노드. p99 과거 메시지 조회 40~125ms → 15ms, 메시지 삽입 5~70ms → 5ms 안정.

**두 글에서 끌어낼 교훈**[일반]: 채팅 저장소는 **방 단위 파티션 + 방 안 시간순 정렬 + 시간 버킷으로 파티션 크기 제한**이 핵심이고, 한 방에 몰리는 **핫 파티션**이 실제 장애 원인이 돼요. 파티션 개념은 [파티셔닝(샤딩)](../../distributed/partitioning/)에 있어요.

### 심화: Redis Pub/Sub를 클러스터에서

Redis 7.0부터 **Sharded Pub/Sub**(`SSUBSCRIBE`/`SPUBLISH`)가 있어요. 일반 Pub/Sub는 클러스터 전체 노드로 메시지를 퍼뜨리지만, Sharded는 채널을 해시 슬롯으로 한 샤드에 배정해 그 안에서만 퍼뜨려서 노드를 늘릴수록 확장돼요.

## 면접 질문

<details>
<summary>Q. 채팅에 왜 WebSocket을 쓰나요? 폴링·SSE와 차이는요?</summary>

**답변(30초)**
채팅은 양쪽이 수시로 주고받고, 서버가 먼저 "새 메시지"를 밀어줘야 해서 WebSocket을 써요. 폴링은 주기만큼 늦고 헛요청이 많고, 롱 폴링은 응답마다 HTTP 헤더 비용과 재요청 공백이 있어요. SSE는 서버→클라이언트 한 방향이라 보내기는 따로 HTTP로 해야 해요. WebSocket은 연결 하나로 양방향이 되지만, 자동 재연결이 없어서 앱이 직접 구현해야 해요.

**꼬리질문**
- Q. 알림만 받는 화면이면? → 한 방향이니 SSE로 충분해요. 자동 재연결과 `Last-Event-ID`도 기본 제공이에요.
- Q. WebSocket을 쓰면 서버 구조에서 뭐가 달라지죠? → 연결이 특정 서버에 묶여 서버가 상태를 갖게 돼요.
</details>

<details>
<summary>Q. 채팅 서버가 여러 대면, 다른 서버에 붙은 사용자에게 메시지를 어떻게 보내나요?</summary>

**답변(30초)**
서버끼리 공유하는 전달 통로를 둬요. 받은 서버가 메시지를 DB에 저장한 뒤 Redis Pub/Sub의 방 채널에 발행하면, 그 방 사용자의 연결을 가진 서버가 구독하고 있다가 받아서 내려보내요. 누가 어느 서버에 있는지는 Redis 같은 세션 레지스트리에 기록해 두고 콕 집어 보낼 수도 있어요. Pub/Sub는 유실될 수 있어서 원본은 DB에 두고 재연결 때 메꿔요.

**꼬리질문**
- Q. Spring STOMP Simple Broker로는 안 되나요? → 구독 정보가 서버 메모리에 있어서 공식 문서가 클러스터에 부적합하다고 해요. broker relay로 외부 브로커를 붙여요.
- Q. 세션 레지스트리 값이 낡으면? → 서버가 죽어 지우지 못한 경우를 위해 TTL을 걸고 하트비트로 연장해요.
</details>

<details>
<summary>Q. 메시지 순서는 어떻게 보장하나요? 보낸 시각으로 정렬하면 안 되나요?</summary>

**답변(30초)**
시각 정렬은 서버 시계 오차와 같은 밀리초 충돌 때문에 순서가 뒤바뀔 수 있어요. 그래서 방마다 한 곳에서 1, 2, 3… 순번을 매기거나 Snowflake ID를 써요. 핵심은 전체 순서가 아니라 방 안 순서만 맞추면 된다는 점이에요. 방별 순번은 빈 번호로 누락까지 감지할 수 있어요.

**꼬리질문**
- Q. Snowflake면 완벽한가요? → 대략 시간순일 뿐 인과적 순서까지 보장하진 않아요.
- Q. Kafka를 쓰면? → 방 ID를 키로 하면 같은 방은 같은 파티션이라 그 안에서 순서가 유지돼요.
</details>

<details>
<summary>Q. 읽음 표시와 안 읽은 메시지 수는 어떻게 저장하나요?</summary>

**답변(30초)**
메시지마다 읽은 사람 목록을 저장하면 인원 × 메시지만큼 쓰기가 늘어요. 대신 방·사용자마다 마지막으로 읽은 순번 하나만 저장해요. 안 읽은 수는 방의 최신 순번에서 내 마지막 읽은 순번을 빼면 되고, 특정 메시지를 안 읽은 사람 수는 마지막 읽은 순번이 그보다 작은 멤버 수예요.

**꼬리질문**
- Q. 왜 이게 가능하죠? → 순번이 시간순이라 "이 번호 이하는 다 읽음"으로 해석할 수 있어서요.
</details>

<details>
<summary>Q. 온라인 상태는 어떻게 아나요? 앱이 강제 종료되면요?</summary>

**답변(30초)**
앱이 주기적으로 하트비트를 보내고, 서버는 Redis에 TTL이 있는 키를 갱신해요. 예를 들어 20초마다 하트비트, TTL 60초예요. 앱이 강제 종료되면 하트비트가 끊기고 TTL이 지나 키가 저절로 사라져 오프라인이 돼요. 연결 유무만 보면 조용히 죽은 연결을 못 잡아서 이 방식을 써요.

**꼬리질문**
- Q. 지하철에서 상태가 깜빡여요. → TTL을 하트비트 주기의 몇 배로 늘리고, 상태 변경 알림을 늦춰서 묶어 보내요.
- Q. 친구가 수천 명이면? → 온라인 변경을 모두에게 밀지 않고, 화면에 보이는 사람만 조회해요.
</details>

<details>
<summary>Q. 메시지 유실과 중복은 어떻게 막나요?</summary>

**답변(30초)**
세 가지를 같이 써요. 첫째, 메시지를 DB에 먼저 저장하고 ack를 줘서 저장된 것만 "보냄"으로 확정해요. 둘째, 앱이 클라이언트 임시 ID를 붙여 보내고, 재전송이 오면 서버가 그 ID로 중복을 걸러요. 셋째, 받는 쪽은 마지막 받은 순번을 기억했다가 재연결 때 그 이후를 받아 빈틈을 채워요.

**꼬리질문**
- Q. 실시간으로도 오고 재동기화로도 오면? → 순번으로 이미 있는 건 버려요.
- Q. 임시 ID 중복 검사는 어디서? → DB에 (방ID, 임시 ID) unique 제약을 걸어요.
</details>

<details>
<summary>Q. 1만 명 단톡방에 메시지 하나가 오면 어떻게 퍼뜨리나요?</summary>

**답변(30초)**
1만 명에게 각각 복사하면 메시지 하나에 쓰기 1만 번이라, 큰 방은 방에 한 번만 저장해요. 실시간 전달은 지금 접속 중인 멤버의 연결이 있는 서버로만 보내고, 나머지는 접속할 때 방에서 읽어 가요. 오프라인 멤버는 푸시 알림으로 알려요. 작은 방은 각자에게 밀어주는 방식이 단순해서, 크기에 따라 섞어 써요.

**꼬리질문**
- Q. 이 방 하나 때문에 DB가 느려지면? → 핫 파티션 문제예요. 시간 버킷으로 파티션 크기를 제한하고, 동시 요청을 합치거나 최근 메시지를 캐시해요.
</details>

<details>
<summary>Q. 메시지 저장소는 무엇을 쓰고, 파티션 키는 어떻게 잡나요?</summary>

**답변(30초)**
가장 많은 조회가 "이 방의 최근 메시지"라서 방 ID로 묶고 메시지 ID로 정렬해요. 처음엔 RDB에 (방ID, 메시지ID) 인덱스로 시작해도 돼요. 커지면 Discord처럼 Cassandra·ScyllaDB 같은 와이드 컬럼 DB에 (방ID, 시간 버킷)을 파티션 키로 둬요. Discord 2017년 글에서 bucket은 약 10일치로, 파티션을 100MB 아래로 유지하려는 장치였어요.

**꼬리질문**
- Q. Discord는 왜 ScyllaDB로 갔나요? → 2023년 글 기준 핫 파티션, 컴팩션 밀림, GC 정지 지연 때문이에요. 177노드에서 72노드로 줄었어요.
- Q. 버킷 없이 방 ID만 쓰면? → 오래된 큰 방은 파티션이 끝없이 커져요.
</details>

<details>
<summary>Q. WebSocket 서버를 배포하면 붙어 있던 연결은 어떻게 되나요?</summary>

**답변(30초)**
연결은 서버와 같이 끊겨요. 그래서 내릴 서버를 로드밸런서에서 먼저 빼고, 기존 연결에 Close 1001을 보내 다른 서버로 재연결하게 해요. 클라이언트는 무작위 지연 후 재연결해서 몰림을 막고, 재연결 직후 마지막 받은 순번 이후를 받아 빈틈을 채워요. Spring Boot graceful shutdown 문서는 장기 연결 처리를 언급하지 않아서 이건 직접 설계해야 해요.

**꼬리질문**
- Q. 지터 없이 재연결하면? → 수만 명이 같은 순간 몰려 남은 서버와 인증·DB가 같이 터져요.
</details>

## 서술형 연습

<details>
<summary>상황: 채팅 서버를 1대에서 3대로 늘렸더니, 같은 방인데 다른 서버에 붙은 상대에게는 메시지가 안 간다는 제보가 들어와요. 원인과 대책을 서술하세요.</summary>

**상황 파악**
같은 서버에 붙은 사람끼리는 되고 **다른 서버에 붙은 사람에게만** 안 가요. 서버를 늘린 직후라, 각 서버가 **자기 메모리에 있는 연결만** 보고 메시지를 뿌리고 있을 가능성이 커요. 보낸 메시지가 DB에는 저장됐는지(새로고침하면 보이는지) 먼저 확인해요.

**원인 후보**
1. 서버가 받은 메시지를 자기에게 붙은 연결에만 보내고, 다른 서버로 넘기는 통로가 없음.
2. Spring STOMP **Simple Broker**를 그대로 씀. 구독 정보가 서버 메모리에 있어 공식 문서상 클러스터에 부적합.
3. `/user/queue/...` 같은 사용자 목적지가 다른 서버에 붙은 사용자를 못 찾음(`userDestinationBroadcast` 미설정).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Redis Pub/Sub로 방 채널 발행, 각 서버가 구독 | 빠르고 단순, 이미 Redis가 있으면 바로 적용 | at-most-once라 구독 서버가 잠깐 끊기면 유실 → DB 재동기화 필요 |
| B. 세션 레지스트리 + 대상 서버에만 전달 | 필요 없는 서버를 안 깨움 | 레지스트리 관리(TTL·정리) 필요, 낡은 값 위험 |
| C. 외부 STOMP 브로커(RabbitMQ 등) + broker relay | Spring 구조를 크게 안 바꿈, 브로커가 구독 관리 | 브로커 운영 부담 |
| D. Kafka(방 ID 키) | 덜 잃고 방 안 순서 유지 | 무겁고, 실시간 알림 용도로는 지연·운영 비용이 큼 |
| E. LB에서 같은 방 사람을 같은 서버로 몰기 | 통로가 필요 없어 보임 | 한 사람이 여러 방에 있어 불가능에 가깝고, 큰 방이 한 서버를 터뜨림 |

**내가 고를 방법**
A를 기본으로 해요. 메시지는 **DB에 먼저 저장**하고, Redis Pub/Sub 방 채널로 다른 서버에 알려요. Pub/Sub의 유실은 클라이언트가 재연결 때 "마지막 받은 순번 이후"를 받아 메꿔요. Spring STOMP를 이미 쓰고 있다면 C(broker relay)가 코드 변경이 가장 적어요. 방이 매우 많아져 모든 서버가 너무 많은 채널을 구독하게 되면 B를 섞어 필요한 서버에만 보내요. E는 근본 해결이 아니라서 고르지 않아요.

**채점 포인트**: 연결은 특정 서버 메모리에 있음(상태 있는 서버), 서버 간 전달 통로(Pub/Sub·브로커·Kafka), Simple Broker 클러스터 부적합, 세션 레지스트리, Pub/Sub at-most-once → 원본 DB 저장, 재연결 동기화, 트레이드오프 비교.
</details>

<details>
<summary>상황: 사용자가 지하철에서 네트워크가 끊겼다 붙으면 메시지가 두 번 보이거나, 중간 메시지 몇 개가 빠져 있다는 문의가 와요. 원인과 대책을 서술하세요.</summary>

**상황 파악**
두 증상이 같이 있어요. **중복**은 보내는 쪽 재전송 문제, **누락**은 받는 쪽이 끊긴 동안의 메시지를 못 받은 문제일 가능성이 커요. 중복 메시지가 DB에 실제로 두 줄 저장됐는지, 누락된 메시지가 DB에는 있는지 먼저 확인해요.

**원인 후보**
1. 앱이 보냈는데 ack가 오기 전에 끊김 → 앱이 다시 보냄 → 서버는 새 메시지로 또 저장(중복).
2. 끊긴 동안 온 메시지는 Pub/Sub로 실시간 전달만 시도됐고, 받을 연결이 없어 사라짐(누락). 재연결 후 빠진 걸 다시 받는 과정이 없음.
3. 재연결 후 "최근 50개"처럼 개수로만 받아서 그보다 많이 쌓이면 중간이 빠짐.
4. 실시간 전달과 재동기화가 같은 메시지를 두 번 내려보내는데 앱이 걸러내지 않음(중복).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 클라이언트 임시 ID + DB unique 제약 | 재전송이 와도 한 번만 저장(멱등) | 임시 ID 저장·인덱스 비용 |
| B. 방별 순번 + "마지막 받은 순번 이후" 재동기화 | 끊긴 동안의 메시지를 빠짐없이 받음, 빈 번호로 누락 감지 | 방마다 순번을 한 곳에서 매겨야 함 |
| C. 앱이 순번으로 중복 표시 제거 | 실시간·재동기화 겹침을 화면에서 정리 | 앱 로직 추가 |
| D. Redis Streams·Kafka로 전달 보장 강화 | 통로 자체의 유실이 줄어듦 | 운영 복잡, 중복 가능성(at-least-once)은 여전해서 A·C는 그대로 필요 |

**내가 고를 방법**
A + B + C를 같이 써요. 보낼 때는 **임시 ID로 멱등하게 저장**하고 ack를 받은 것만 확정해요. 받을 때는 방마다 **마지막 받은 순번**을 기억했다가 재연결 때 그 이후를 페이지 단위로 끝까지 받아요. 화면에는 순번 기준으로 한 번만 보여 줘요. 원본이 DB에 있으니 전달 통로는 Pub/Sub로 충분하고, D는 통로 자체를 믿어야 하는 요구가 생길 때 검토해요.

**채점 포인트**: 중복(보내는 쪽 재전송)과 누락(받는 쪽 공백) 구분, 저장 후 ack, 클라이언트 임시 ID와 멱등성, unique 제약, 방별 순번·마지막 받은 순번, 재동기화는 개수가 아니라 순번 기준, Pub/Sub at-most-once, at-least-once면 중복 처리 필요.
</details>

<details>
<summary>상황: 채팅 서버를 배포할 때마다 수만 명이 동시에 재접속하면서 남은 서버와 인증 서버가 폭주하고, 배포가 끝난 뒤에도 몇 분간 채팅이 느려요. 원인과 대책을 서술하세요.</summary>

**상황 파악**
배포 자체보다 **재접속이 한 순간에 몰리는 것**이 문제예요. 서버를 내리면 그 서버의 연결이 동시에 끊기고, 클라이언트가 모두 즉시 재연결하면서 연결 수립·인증·재동기화 조회가 한꺼번에 일어나요. 배포 시점의 연결 수 그래프, 인증 요청 수, 재동기화 API 호출량을 확인해요.

**원인 후보**
1. 클라이언트가 끊기자마자 **고정 간격**(또는 즉시)으로 재연결 → 모두 같은 순간에 몰림.
2. 서버를 LB에서 빼지 않고 바로 꺼서, 끊긴 연결이 한꺼번에 생김.
3. 롤링 배포 단위가 커서(예: 3대 중 2대 동시) 남은 서버가 감당 못 함.
4. 재연결 직후 모든 방의 놓친 메시지를 한꺼번에 조회해 DB가 몰림.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 클라이언트 재연결에 지수 백오프 + **지터** | 재접속이 시간에 고르게 퍼짐 | 일부 사용자는 재연결이 몇 초 늦어짐 |
| B. LB에서 먼저 제외 → Close 1001 → 일정 시간에 걸쳐 나눠 끊기 | 서버 쪽에서 몰림을 조절 | 배포 시간이 길어짐 |
| C. 한 번에 내리는 서버 수 줄이기, 여유 서버 미리 확보 | 남은 서버 부하 감소 | 배포가 느리고 비용 증가 |
| D. 재동기화를 지금 연 방만 먼저, 나머지는 천천히 | DB 몰림 감소 | 안 연 방의 안 읽은 수가 잠깐 늦게 맞음 |
| E. 연결 서버와 로직 서버 분리 | 로직 배포 때 연결 서버를 안 건드림 | 서버 종류가 늘어 운영 대상 증가 |

**내가 고를 방법**
A와 B를 기본으로 해요. 클라이언트는 끊기면 **무작위 지연(지터)을 섞은 백오프**로 재연결하고, 서버는 LB에서 먼저 빠진 뒤 Close 1001을 일정 시간에 걸쳐 나눠 보내요. 재연결 후에는 D처럼 지금 보는 방부터 동기화해요. 길게 보면 E로 연결 서버를 따로 떼서 로직 배포가 연결을 끊지 않게 해요. Spring Boot graceful shutdown은 진행 중 요청만 기다려 주고 장기 연결 처리는 문서에 없어서, 이 과정은 직접 만들어야 해요.

**채점 포인트**: 동시 재접속(thundering herd) 인식, 지수 백오프 + 지터, LB 제외 후 Close 1001, 나눠 끊기, 롤링 단위·여유 용량, 재동기화 몰림 완화, graceful shutdown이 장기 연결을 다루지 않음, 연결 서버 분리.
</details>
