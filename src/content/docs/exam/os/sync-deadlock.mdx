:::tip[한 줄 요약]
**동기화**는 공유 자원을 쓰는 코드(임계 구역)에 한 번에 하나만 들어가게 하는 일이고, **교착상태**는 프로세스들이 서로 상대가 쥔 자원을 기다리며 아무도 못 움직이는 상태예요. 교착은 **상호 배제·점유와 대기·비선점·순환 대기** 넷이 모두 성립할 때만 생기고, 은행원 알고리즘은 **Need ≤ Work인 프로세스를 하나씩 끝내 보며** 안전 순서가 있는지 확인해요.
:::

:::note[처음이라면 여기까지]
① 두 사람이 같은 은행 계좌에서 동시에 돈을 빼면 잔액이 꼬일 수 있어요. 그래서 "한 번에 한 명만" 들어가게 막는 게 동기화예요.

② 세마포어는 "빈 자리 개수"를 세는 숫자예요. 들어갈 때 P(하나 빼기), 나올 때 V(하나 더하기)만 기억하세요.

③ 교착 4조건은 상호 배제·점유와 대기·비선점·순환 대기예요. 보기에 "선점"이 나오면 틀린 거예요.

④ 아래 "단계별 계산"의 은행원 예제 1·2를 손으로 따라 하고, 연습 문제 1~5번을 풀어 보세요. "심화:"는 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

외나무다리가 하나 있어요. 양쪽에서 한 사람씩 동시에 올라서면 가운데서 마주쳐요. 둘 다 "네가 비켜"라며 버티면 아무도 건너지 못해요. 이게 **교착상태**(deadlock, 서로 상대를 기다리며 모두 멈춘 상태)예요.

해결 방법은 크게 네 가지예요. "다리는 동쪽 사람이 항상 먼저" 같은 규칙을 정해 애초에 마주치지 않게 하면 **예방**이에요. 올라서기 전에 반대편을 보고 위험하면 기다리면 **회피**예요. 일단 건너다가 마주치면 한 명을 되돌려 보내면 **탐지·회복**이에요. 마주칠 일이 거의 없다고 보고 아무 대책도 안 세우면 **무시**예요.

다리 위에 한 번에 한 명만 올라가게 하는 것 자체는 **동기화**(synchronization, 공유 자원 접근 순서를 맞추는 일)예요. 다리가 공유 자원이고, 다리를 건너는 구간이 임계 구역이에요.

단, 실제 교착은 꼭 두 명일 필요가 없어요. A는 B를, B는 C를, C는 A를 기다리는 식으로 여러 프로세스가 원을 그려도 생겨요.

## 제대로 알기

### 경쟁 상태와 임계 구역

- **경쟁 상태**(race condition): 여러 프로세스·스레드가 공유 데이터를 동시에 바꿀 때, 실행 순서에 따라 결과가 달라지는 상황이에요. 모두 읽기만 하면 문제가 없고, 쓰기가 섞일 때 생겨요.
- **임계 구역**(critical section): 공유 자원을 건드리는 **코드 부분**이에요. 공유 자원 자체(변수, 프린터 등)는 **임계 자원**이라고 따로 불러요.

임계 구역 문제를 제대로 풀었다고 말하려면 세 조건을 지켜야 해요.

| 조건 | 뜻 | 막는 문제 |
|---|---|---|
| **상호 배제**(mutual exclusion) | 한 번에 하나만 임계 구역 안에 있음 | 동시 접근으로 데이터가 꼬이는 것 |
| **진행**(progress) | 임계 구역이 비어 있고 들어가려는 프로세스가 있으면, 그중 하나는 유한 시간 안에 들어감. 임계 구역 밖 프로세스는 이 결정을 막지 못함 | 비어 있는데 아무도 못 들어가는 것 |
| **한정 대기**(bounded waiting) | 요청한 뒤 다른 프로세스가 먼저 들어가는 횟수에 상한이 있음 | 한 프로세스만 계속 밀리는 **기아** |

추가로 "프로세스 속도나 CPU 개수에 대해 아무 가정도 하지 않는다"는 전제가 붙어요. 교재에 따라 이 전제까지 넣어 조건 4개로 쓰기도 해요.

### 상호 배제 기법

| 기법 | 분류 | 핵심 | 시험 포인트 |
|---|---|---|---|
| **데커**(Dekker) 알고리즘 | 소프트웨어, 2개 프로세스 | `flag` 배열(들어가고 싶다) + `turn`(누구 차례) | 2개 프로세스 상호 배제를 소프트웨어만으로 처음 정확히 푼 방법 |
| **피터슨**(Peterson) 알고리즘 | 소프트웨어, 2개 프로세스 | 데커를 단순화. "나 들어갈래, 근데 차례는 너한테 양보" | 3조건을 모두 만족 |
| **램포트 빵집**(Bakery) | 소프트웨어, n개 프로세스 | 번호표를 뽑아 작은 번호부터 | n개용이라는 점 |
| 인터럽트 금지 | 하드웨어 | 임계 구역 동안 인터럽트를 끔 | **단일 CPU**에서만 통함 |
| test-and-set, compare-and-swap | 하드웨어 | 읽기와 쓰기를 쪼갤 수 없는 한 명령으로 | 원자적(중간에 끼어들 수 없음) 명령 |
| **세마포어**(semaphore) | OS 제공 | 정수 변수 + P/V 연산 | 다익스트라 고안. P = 들어갈 때, V = 나올 때 |
| **모니터**(monitor) | 언어 수준 | 공유 데이터 + 그걸 다루는 함수를 한 묶음으로 | 안에는 **한 번에 하나만**. 상호 배제가 자동 |

출처: 데커·피터슨·빵집·하드웨어 기법·모니터는 표준 OS 교재(Silberschatz) 내용이고, 세마포어 P/V는 『정처기-컴퓨터일반』 운영체제 편에도 나와요.

피터슨 알고리즘은 이렇게 생겼어요(프로세스 i 기준, 상대는 j).

```c
flag[i] = true;          // 나 들어가고 싶어
turn = j;                // 근데 차례는 너한테 양보할게
while (flag[j] && turn == j)
    ;                    // 상대도 원하고 상대 차례면 기다림
/* 임계 구역 */
flag[i] = false;         // 다 썼어
```

### 세마포어 P와 V

세마포어 S는 "쓸 수 있는 자원 개수"를 나타내는 정수예요. 초기화 말고는 P와 V로만 건드려요. 두 연산은 **원자적**(atomic, 중간에 다른 프로세스가 끼어들 수 없음)이에요.

| 연산 | 다른 이름 | 하는 일 | 언제 |
|---|---|---|---|
| **P(S)** | wait, 네덜란드어 Proberen(검사) | S가 0 이하면 기다리고, 아니면 S를 1 줄임 | 임계 구역 **들어가기 전** |
| **V(S)** | signal, Verhogen(증가) | S를 1 늘리고, 기다리는 프로세스가 있으면 깨움 | 임계 구역 **나온 뒤** |

- **이진 세마포어**: 값이 0과 1뿐. 뮤텍스(자물쇠 하나)처럼 써요.
- **계수 세마포어**(counting): 자원이 n개면 초기값 n. 예: DB 커넥션 풀 10개면 S = 10.
- P와 V 순서를 잘못 쓰면 상호 배제가 깨지거나 교착이 생겨요. 세마포어를 쓴다고 교착이 자동으로 사라지지 않아요.

### 모니터

모니터는 공유 데이터와 그 데이터를 다루는 함수를 한 상자에 넣고, 바깥에서는 그 함수로만 데이터에 접근하게 만든 구조예요. 상자 안에서는 **한 번에 하나의 프로세스만** 실행돼요.

특정 조건(버퍼가 빔 등)을 기다릴 때는 **조건 변수**(condition variable)의 `wait()`와 `signal()`을 써요. 세마포어와 헷갈리는 지점이 하나 있어요.

| | 세마포어 V | 모니터 조건 변수 signal |
|---|---|---|
| 기다리는 프로세스가 없을 때 | 값이 1 늘어나 **남아 있음** | **아무 효과 없음**(사라짐) |

Java의 `synchronized`와 `wait/notify`가 모니터를 구현한 것이에요. 실무 쪽 이야기는 [동기화와 자바 메모리 모델](../../../java/synchronization/)을 보세요.

### 생산자-소비자 문제

크기 n인 버퍼에 생산자는 넣고 소비자는 꺼내요. 세마포어 3개를 써요.

| 세마포어 | 초기값 | 뜻 |
|---|---|---|
| `mutex` | 1 | 버퍼에 한 번에 한 명만 |
| `empty` | n | 빈 칸 개수 |
| `full` | 0 | 찬 칸 개수 |

```text
생산자: P(empty) → P(mutex) → 넣기 → V(mutex) → V(full)
소비자: P(full)  → P(mutex) → 꺼내기 → V(mutex) → V(empty)
```

버퍼가 2칸이면 이렇게 움직여요. 처음 empty 2, full 0 → 한 번 생산 후 empty 1, full 1 → 두 번 생산 후 empty 0, full 2 → 세 번째 생산자는 P(empty)에서 멈춤 → 소비자가 하나 꺼내면 empty 1이 되고 멈췄던 생산자가 깨어나요.

함정은 P 순서예요. 생산자가 **P(mutex)를 P(empty)보다 먼저** 하면, 버퍼가 꽉 찼을 때 mutex를 쥔 채 잠들어요. 소비자는 mutex를 못 얻어 꺼낼 수 없으니 둘 다 멈춰요. 교착이에요.

다른 고전 문제로 **판독자-기록자**(읽는 사람은 여럿 동시에, 쓰는 사람은 혼자)와 **식사하는 철학자**(다섯 명이 동시에 왼쪽 포크를 집으면 교착)가 있어요.

### 교착상태 4조건

교착은 아래 넷이 **동시에** 성립할 때만 생겨요. 그래서 넷은 필요조건이고, 하나라도 깨면 교착이 생기지 않아요.

| 조건 | 뜻 | 외나무다리로 보면 |
|---|---|---|
| **상호 배제** | 자원을 한 번에 하나만 씀 | 다리 폭이 한 사람분 |
| **점유와 대기**(hold and wait) | 자원을 쥔 채 다른 자원을 기다림 | 반쯤 건넌 채로 버팀 |
| **비선점**(no preemption) | 남이 쥔 자원을 강제로 못 뺏음 | 상대를 밀어낼 수 없음 |
| **순환 대기**(circular wait) | P0→P1→…→P0 원형으로 기다림 | 서로가 서로를 기다림 |

순환 대기가 성립하면 점유와 대기도 이미 성립해요. 그래서 네 조건이 완전히 따로 노는 건 아니에요.

**기아**(starvation)와 헷갈리지 마세요. 기아는 다른 프로세스는 잘 돌아가는데 **특정 프로세스만** 계속 밀리는 거예요. 교착은 관련된 프로세스 **전부**가 멈춰요.

### 해결 방법 4가지

| 방법 | 아이디어 | 대표 |
|---|---|---|
| **예방**(prevention) | 4조건 중 하나를 처음부터 못 생기게 막음 | 하벤더(Havender)의 방법 |
| **회피**(avoidance) | 자원을 주기 전에 "줘도 안전한가" 검사, 위험하면 기다리게 함 | 다익스트라의 **은행원 알고리즘** |
| **탐지·회복**(detection·recovery) | 일단 허용하고, 주기적으로 찾아서 풀어 줌 | 자원 할당 그래프, 대기 그래프 |
| **무시**(타조 알고리즘) | 드물게 생기니 아무것도 안 함 | 대부분의 범용 OS |

### 예방: 조건별로 깨는 법

| 깨는 조건 | 방법 | 단점 |
|---|---|---|
| 상호 배제 | 자원을 여럿이 같이 쓰게 함 | 프린터처럼 원래 혼자 써야 하는 자원엔 불가 → 보통 이 조건은 못 깸 |
| 점유와 대기 | 필요한 자원을 **한 번에 전부** 받고 시작, 또는 아무것도 안 쥔 상태에서만 요청 | 안 쓰는 자원까지 미리 잡아 **이용률 저하**, 많이 필요한 프로세스는 **기아** |
| 비선점 | 요청이 거절되면 쥔 자원을 다 내놓고 다시 요청 / 우선순위 높은 쪽이 뺏음 | 상태 저장·복구가 쉬운 자원(CPU 레지스터, 메모리)에만 현실적 |
| 순환 대기 | 모든 자원에 번호를 매기고 **번호가 커지는 순서로만** 요청 | 번호 순서가 실제 사용 순서와 달라 낭비가 생길 수 있음 |

실무에서 가장 많이 쓰는 건 마지막 줄이에요. "락은 항상 계좌 번호가 작은 쪽부터 잡는다" 같은 규칙이 순환 대기 깨기예요. DB에서 생기는 교착은 [InnoDB 락](../../../db/locks/)을 보세요.

### 회피: 안전 상태

- **안전 상태**: 모든 프로세스가 최대 요구량까지 받아 끝낼 수 있는 순서(**안전 순서**, safe sequence)가 **하나 이상** 있는 상태예요.
- **불안전 상태**: 그런 순서가 없는 상태예요. **불안전이라고 지금 당장 교착인 건 아니에요.** 교착이 날 수 있는 위험한 상태일 뿐이에요.
- 관계: 교착 상태 ⊂ 불안전 상태. 안전 상태에서는 교착이 생기지 않아요.

은행원 알고리즘은 은행이 대출해 줄 때 "이 돈을 빌려줘도 모든 고객의 최대 한도를 언젠가 채워 줄 수 있나"를 따지는 것과 같아요. 그래서 이런 전제가 필요해요.

| 필요한 것 | 그래서 생기는 단점 |
|---|---|
| 각 프로세스의 **최대 요구량을 미리** 알아야 함 | 실제로는 미리 알기 어려움 |
| 프로세스 수·자원 수가 고정 | 실행 중 프로세스가 늘고 줄면 맞지 않음 |
| 요청마다 안전성 검사 | 검사 오버헤드, 안전하게만 주니 **자원 이용률이 낮음** |

### 탐지: 자원 할당 그래프

**자원 할당 그래프**(RAG, Resource Allocation Graph)는 프로세스를 원, 자원을 사각형(안의 점 = 자원 개수)으로 그려요. 프로세스→자원은 "요청", 자원→프로세스는 "할당" 화살표예요.

| 그래프 모양 | 결론 |
|---|---|
| 사이클(원형 고리) 없음 | 교착 **없음** |
| 사이클 있음 + 자원마다 1개 | 교착 **있음** |
| 사이클 있음 + 자원이 여러 개 | 교착일 **수도, 아닐 수도** 있음 → 은행원과 비슷한 탐지 알고리즘으로 확인 |

자원이 모두 1개씩이면 자원 정점을 빼고 프로세스끼리만 화살표를 이은 **대기 그래프**(wait-for graph)에서 사이클을 찾아요. 탐지를 자주 돌리면 빨리 찾지만 오버헤드가 커요. 그래서 일정 시간마다, 또는 CPU 이용률이 떨어질 때 돌리기도 해요.

### 회복

| 방법 | 내용 | 단점 |
|---|---|---|
| 교착 프로세스 **전부 종료** | 확실히 풀림 | 그동안 한 작업이 모두 날아감 |
| **하나씩 종료** | 하나 죽이고 다시 탐지, 풀릴 때까지 반복 | 탐지를 여러 번 돌려야 함 |
| **자원 선점** | 희생자를 골라 자원을 뺏고, 안전한 시점으로 **롤백** | 같은 프로세스만 계속 희생되면 기아 → 롤백 횟수를 비용에 넣음 |

희생자는 실행한 시간, 남은 시간, 쓴 자원 수, 더 필요한 자원 수, 대화형인지 일괄 처리인지 등을 보고 골라요.

### 심화: 피터슨 알고리즘이 지금은 그대로 안 통하는 이유

현대 CPU와 컴파일러는 성능을 위해 명령 순서를 바꿔 실행할 수 있어요. 그러면 `flag[i] = true`와 `turn = j`의 순서가 뒤집혀 상호 배제가 깨질 수 있어요. 그래서 실제로는 **메모리 배리어**(순서를 바꾸지 말라는 명령)가 필요해요. 시험에서는 피터슨을 "올바른 해법"으로 보면 돼요.

## 단계별 계산

### 공식 두 줄

```text
Need      = Max − Allocation       (앞으로 더 필요한 양)
Available = 전체 자원 − ΣAllocation (지금 남은 양)
```

안전성 검사 순서예요.

1. Work = Available로 시작해요.
2. 아직 안 끝난 프로세스 중 **Need ≤ Work**(모든 자원 종류에서)인 걸 하나 찾아요.
3. 그 프로세스가 끝났다고 보고, 쥐고 있던 자원을 돌려받아요. **Work += 그 프로세스의 Allocation**.
4. 2~3을 반복해요. 모두 끝나면 안전, 중간에 고를 게 없으면 불안전이에요.

Work에 더하는 건 Need가 아니라 **Allocation**이에요. 끝난 프로세스는 원래 쥐고 있던 것과 새로 받은 것을 모두 내놓는데, 새로 받은 Need만큼은 Work에서 빌려 갔던 거라 결과적으로 Allocation만큼 늘어나요.

### 예제 1: 자원 3종, 안전 순서 찾기

전체 자원 (A, B, C) = (9, 5, 6)

| 프로세스 | Allocation | Max | Need = Max − Allocation |
|---|---|---|---|
| P0 | 1 1 0 | 5 3 2 | 4 2 2 |
| P1 | 2 0 1 | 3 2 2 | 1 2 1 |
| P2 | 1 2 1 | 2 2 3 | 1 0 2 |
| P3 | 0 0 2 | 4 1 3 | 4 1 1 |

ΣAllocation = (4, 3, 4)이니 Available = (9, 5, 6) − (4, 3, 4) = **(5, 2, 2)**.

| 단계 | Work | 고른 프로세스 | Need ≤ Work? | 새 Work = Work + Allocation |
|---|---|---|---|---|
| 1 | (5, 2, 2) | P0 | (4, 2, 2) ≤ (5, 2, 2) 예 | (5, 2, 2) + (1, 1, 0) = (6, 3, 2) |
| 2 | (6, 3, 2) | P1 | (1, 2, 1) ≤ (6, 3, 2) 예 | + (2, 0, 1) = (8, 3, 3) |
| 3 | (8, 3, 3) | P2 | (1, 0, 2) ≤ (8, 3, 3) 예 | + (1, 2, 1) = (9, 5, 4) |
| 4 | (9, 5, 4) | P3 | (4, 1, 1) ≤ (9, 5, 4) 예 | + (0, 0, 2) = **(9, 5, 6)** |

모두 끝났으니 **안전 상태**, 안전 순서는 P0 → P1 → P2 → P3이에요.

- **검산 포인트**: 마지막 Work가 전체 자원 (9, 5, 6)과 같아야 해요. 다르면 어딘가 틀린 거예요.
- 안전 순서는 하나가 아니에요. 이 예제는 Available이 넉넉해서 P2나 P3부터 시작해도 끝까지 가요. 보기에 "안전 순서는 유일하다"가 나오면 틀린 거예요.
- 여기서 P1이 (1, 0, 0)을 더 요청하면? Request ≤ Need(1, 2, 1), Request ≤ Available(5, 2, 2)를 확인하고 임시로 줘요. Available (4, 2, 2), P1 Need (0, 2, 1)로 다시 검사하면 P0 → P1 → P2 → P3이 그대로 통해서 **승인**이에요.

### 예제 2: 자원 1종, 요청을 들어주면 불안전

전체 자원 10개.

| 프로세스 | Allocation | Max | Need |
|---|---|---|---|
| P0 | 3 | 8 | 5 |
| P1 | 2 | 4 | 2 |
| P2 | 3 | 6 | 3 |

Available = 10 − 8 = **2**.

1. Work = 2. P1(Need 2) 가능 → Work = 2 + 2 = 4
2. P2(Need 3) 가능 → Work = 4 + 3 = 7
3. P0(Need 5) 가능 → Work = 7 + 3 = 10

지금은 P1 → P2 → P0으로 **안전**해요.

이제 **P0이 1개를 더 요청**했다고 해요. 임시로 주면:

| 프로세스 | Allocation | Need |
|---|---|---|
| P0 | 4 | 4 |
| P1 | 2 | 2 |
| P2 | 3 | 3 |

Available = 1. Need가 1 이하인 프로세스가 하나도 없어요(4, 2, 3). 첫 단계부터 막히니 **불안전**이에요.

그래서 은행원 알고리즘은 이 요청을 **거절하고 P0을 기다리게** 해요. 지금 당장 교착이 난 건 아니에요. 하지만 이대로 가면 날 수 있으니 미리 피하는 거예요. 이게 "회피"라는 이름의 뜻이에요.

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 교착 발생 조건에 "선점"이 있다 | 조건은 **비선점**(no preemption) |
| 4조건 중 하나만 성립해도 교착이 생긴다 | 넷이 **모두** 성립해야 함(필요조건). 하나라도 깨면 교착 없음 |
| 불안전 상태는 곧 교착 상태다 | 교착 ⊂ 불안전. 불안전은 **교착 가능성**만 있음 |
| 은행원 알고리즘은 교착 예방(또는 탐지) 기법이다 | **회피** 기법 |
| 은행원 알고리즘은 자원 이용률을 높인다 | 안전할 때만 주니 이용률은 **낮아짐**. 최대 요구량을 **미리** 알아야 함 |
| 안전 순서는 하나뿐이다 | 여러 개일 수 있음 |
| 자원 할당 그래프에 사이클이 있으면 항상 교착이다 | 자원마다 1개일 때만 확정. 여러 개면 아닐 수도 있음 |
| 순환 대기 예방 = 필요한 자원을 한 번에 모두 할당 | 그건 **점유와 대기** 예방. 순환 대기는 **자원 번호 순서대로** 요청 |
| 상호 배제 조건을 없애는 것이 가장 현실적인 예방이다 | 프린터 같은 비공유 자원이 있어 보통 **불가** |
| 진행 조건은 기아를 막는다 | 기아를 막는 건 **한정 대기**. 진행은 "비어 있는데 아무도 못 들어감"을 막음 |
| P는 임계 구역을 나올 때, V는 들어갈 때 | **P = 들어가기 전**(감소, wait), **V = 나온 뒤**(증가, signal) |
| 모니터 안에서는 여러 프로세스가 동시에 실행될 수 있다 | 한 번에 **하나만** |
| 조건 변수 signal도 세마포어 V처럼 값이 누적된다 | 기다리는 프로세스가 없으면 **아무 효과 없음** |
| 인터럽트 금지는 다중 프로세서에서도 상호 배제를 보장한다 | **단일 CPU**에서만 |
| 기아와 교착은 같은 말이다 | 기아는 **일부**만 밀림, 교착은 관련 프로세스 **전부** 멈춤 |
| 이미 교착에 빠진 뒤 은행원 알고리즘으로 해결한다 | 이미 빠졌으면 **탐지·회복**. 은행원은 빠지기 전에 쓰는 회피 |

## 연습 문제

<details>
<summary>1. 교착상태 발생의 필요조건이 아닌 것은?</summary>

① 상호 배제 ② 점유와 대기 ③ 선점 ④ 순환 대기

**정답: ③**

네 조건은 상호 배제·점유와 대기·**비선점**·순환 대기예요. "선점"은 오히려 교착을 깨는 쪽이에요.
</details>

<details>
<summary>2. 임계 구역 문제의 해결 조건 중, 요청한 프로세스가 무한정 밀리지 않도록 다른 프로세스가 먼저 들어가는 횟수에 상한을 두는 조건은?</summary>

① 상호 배제 ② 진행 ③ 한정 대기 ④ 순환 대기

**정답: ③**

한정 대기는 기아를 막는 조건이에요. 진행은 임계 구역이 비어 있는데 아무도 못 들어가는 상황을 막아요. 순환 대기는 교착 조건이라 여기와 상관없어요.
</details>

<details>
<summary>3. 세마포어와 모니터에 대한 설명으로 옳은 것은?</summary>

① P 연산은 임계 구역을 나올 때 수행하며 세마포어 값을 1 증가시킨다.

② 모니터 내부에서는 여러 프로세스가 동시에 실행될 수 있다.

③ 모니터의 조건 변수에 signal을 보냈을 때 기다리는 프로세스가 없으면 아무 효과가 없다.

④ 세마포어를 사용하면 교착상태가 절대 발생하지 않는다.

**정답: ③**

① P는 들어가기 전에 하고 값을 줄여요. V가 나올 때 늘려요. ② 모니터 안은 한 번에 하나만이에요. ④ P/V 순서를 잘못 쓰면 교착이 생길 수 있어요(생산자-소비자의 P 순서 함정).
</details>

<details>
<summary>4. 교착상태 예방 방법과 깨뜨리는 조건을 바르게 짝지은 것은?</summary>

① 모든 자원에 번호를 매기고 번호가 커지는 순서로만 요청 - 순환 대기

② 필요한 자원을 한 번에 모두 할당받고 시작 - 비선점

③ 요청이 거절되면 가진 자원을 모두 반납 - 점유와 대기

④ 자원을 여러 프로세스가 공유하게 함 - 순환 대기

**정답: ①**

② 한 번에 다 받는 건 **점유와 대기** 부정이에요. ③ 가진 걸 내놓게 하는 건 **비선점** 부정이에요. ④ 공유하게 하는 건 **상호 배제** 부정이에요.
</details>

<details>
<summary>5. 자원 1종이 모두 11개이고 현재 상태가 다음과 같다. 안전 순서가 아닌 것은? (P0 할당 4·최대 7, P1 할당 1·최대 5, P2 할당 3·최대 4)</summary>

① P2 → P0 → P1 ② P0 → P2 → P1 ③ P0 → P1 → P2 ④ P1 → P0 → P2

**정답: ④**

Available = 11 − (4 + 1 + 3) = 3. Need는 P0 = 3, P1 = 4, P2 = 1이에요.

- ④ P1부터: Need 4 > Work 3이라 첫 단계에서 막혀요.
- ① Work 3 → P2(1) 끝 → 6 → P0(3) 끝 → 10 → P1(4) 끝 → 11.
- ② 3 → P0(3) 끝 → 7 → P2(1) 끝 → 10 → P1 끝 → 11.
- ③ 3 → P0 끝 → 7 → P1(4) 끝 → 8 → P2 끝 → 11.

안전 순서가 세 개나 있어요. 안전 순서는 하나가 아니라는 걸 기억하세요.
</details>

<details>
<summary>6. 자원 A·B·C가 모두 (6, 4, 4)개이고 상태가 다음과 같다. P0이 (1, 0, 1)을 요청할 때 은행원 알고리즘의 판단은? (Allocation / Max — P0: 1 1 0 / 4 2 2, P1: 2 0 1 / 3 1 2, P2: 1 1 1 / 3 1 3, P3: 0 1 1 / 1 3 1)</summary>

① 요청 후에도 안전하므로 승인한다.

② 요청 후 불안전 상태가 되므로 P0을 기다리게 한다.

③ 요청량이 Need를 넘으므로 오류로 처리한다.

④ 요청을 들어주면 즉시 교착상태가 되므로 P0을 종료한다.

**정답: ②**

먼저 현재 상태를 구해요.

- Need: P0 (3, 1, 2), P1 (1, 1, 1), P2 (2, 0, 2), P3 (1, 2, 0)
- ΣAllocation = (4, 3, 3), Available = (2, 1, 1)
- 지금은 P1 → P0 → P2 → P3이 통해서 안전해요.

요청 (1, 0, 1)은 Need (3, 1, 2)와 Available (2, 1, 1)을 넘지 않으니 일단 임시로 줘요(③ 아님).

- Available = (1, 1, 0), P0 Need = (2, 1, 1)
- Work (1, 1, 0)과 비교: P0 (2, 1, 1) 안 됨, P1 (1, 1, 1)은 C가 1 > 0이라 안 됨, P2 (2, 0, 2) 안 됨, P3 (1, 2, 0)은 B가 2 > 1이라 안 됨

아무도 못 고르니 **불안전**이에요. 그래서 요청을 되돌리고 P0을 기다리게 해요. 불안전은 교착이 날 수 있다는 뜻이지 지금 교착이라는 뜻이 아니라서 ④는 틀려요.
</details>

<details>
<summary>7. 크기 n인 버퍼의 생산자-소비자 문제에서 세마포어 mutex = 1, empty = n, full = 0을 쓴다. 생산자 코드의 앞부분을 P(mutex) → P(empty) 순서로 바꿨을 때(나머지는 넣기 → V(mutex) → V(full)) 생길 수 있는 문제는?</summary>

① 버퍼가 비었을 때 소비자가 빈 칸을 꺼낸다.

② 버퍼가 꽉 찼을 때 생산자가 mutex를 쥔 채 잠들어 교착이 생긴다.

③ 두 생산자가 동시에 버퍼에 쓴다.

④ 아무 문제 없다.

**정답: ②**

원래 순서는 P(empty) → P(mutex)예요. 순서를 바꾸면 버퍼가 꽉 찼을 때(empty = 0) 생산자가 mutex를 먼저 잡은 뒤 P(empty)에서 잠들어요. 소비자는 꺼내려고 P(mutex)를 해야 하는데 생산자가 쥐고 있어서 못 들어가요. 생산자는 소비자가 빈 칸을 만들어 주길, 소비자는 생산자가 mutex를 놓아 주길 기다리니 교착이에요. ③은 mutex가 여전히 있어서 생기지 않아요.
</details>

**꼬리질문**
- Q. 은행원 알고리즘은 왜 실무에서 잘 안 쓰나요? → 프로세스마다 최대 자원 요구량을 미리 알아야 하고, 프로세스 수가 고정이라고 가정하며, 요청마다 안전성 검사를 해야 해서 오버헤드가 커요. 실제 시스템에선 이 전제가 잘 맞지 않아요.
- Q. 기아와 교착의 차이는? → 기아는 다른 프로세스는 진행되는데 특정 프로세스만 계속 밀리는 것이고, 교착은 관련된 프로세스 전부가 서로를 기다리며 멈춘 거예요.
</details>

<details>
<summary>Q. 뮤텍스와 세마포어, 모니터는 어떻게 다른가요?</summary>

**답변(30초)** 세마포어는 쓸 수 있는 자원 개수를 세는 정수이고, P로 줄이고 V로 늘려요. 값이 0과 1뿐인 이진 세마포어가 뮤텍스처럼 한 번에 하나만 들여보내고, 계수 세마포어는 커넥션 풀처럼 n개까지 동시에 허용해요. 모니터는 공유 데이터와 그걸 다루는 함수를 묶어서, 안에서는 한 번에 하나만 실행되게 언어가 보장해 주는 구조예요. 세마포어는 P/V 순서를 개발자가 직접 맞춰야 해서 실수하기 쉽고, 모니터는 상호 배제를 자동으로 해 줘요. Java의 synchronized가 모니터예요.

**꼬리질문**
- Q. 뮤텍스와 이진 세마포어는 완전히 같나요? → 보통 뮤텍스는 잠근 스레드만 풀 수 있다는 소유 개념이 있고, 세마포어는 다른 스레드가 V를 해도 돼요.
</details>
