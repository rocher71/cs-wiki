:::tip[한 줄 요약]
메모리는 **페이징**(같은 크기로 쪼개기, 내부 단편화)이나 **세그먼테이션**(의미 단위로 쪼개기, 외부 단편화)으로 나눠 써요. 빈 자리가 없으면 **페이지 교체 알고리즘**으로 내보낼 페이지를 고르는데, 이론상 최선은 OPT, 현실에서 흉내 내는 건 LRU, 가장 단순한 건 FIFO예요.
:::

:::note[처음이라면 여기까지]
① 메모리는 책상, 디스크는 책장이에요. 책상엔 몇 권만 펼칠 수 있어서, 새 책이 필요하면 한 권을 책장에 돌려놔야 해요. 이걸 **페이지 교체**라고 해요.

② **페이징 = 내부 단편화, 세그먼테이션 = 외부 단편화**. 이 짝을 거꾸로 낸 보기가 제일 자주 나와요.

③ 계산 문제는 네 가지예요. 배치 전략(최초·최적·최악 적합), 주소 변환(페이지 번호·오프셋), TLB 유효 접근 시간, 페이지 부재 횟수. 아래 예제를 손으로 한 번씩 따라 하세요.

④ **벨레이디 이상**(프레임을 늘렸는데 부재가 늘어남)은 FIFO에서만 생긴다고 외우세요. "심화:"는 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

공부할 때 책상(메모리)은 좁고 책장(디스크)은 넓어요. 책상에는 책을 세 권만 펼칠 수 있다고 해 봐요. 네 번째 책이 필요해지면 펼쳐 둔 책 하나를 책장에 돌려놔야 해요.

어떤 책을 치울지가 문제예요. "제일 먼저 꺼낸 책"을 치우면 FIFO, "제일 오래 안 본 책"을 치우면 LRU, "앞으로 제일 늦게 볼 책"을 치우면 OPT예요. OPT가 가장 좋지만, 앞으로 뭘 볼지 미리 알 수는 없죠.

책상에 책을 놓는 방식도 두 가지예요. 책을 같은 크기 낱장 묶음(페이지)으로 잘라 빈 칸 아무 데나 꽂으면 **페이징**, 단원(장) 단위로 통째로 놓으면 **세그먼테이션**이에요.

단, 실제로는 책 한 권을 다 꺼내는 게 아니라 필요한 **페이지**(보통 4KB 조각)만 메모리에 올려요. 그래서 큰 프로그램도 일부만 올린 채로 실행할 수 있어요. 이걸 **가상 메모리**라고 해요.

## 제대로 알기

### 연속 할당과 배치 전략

**연속 할당**은 프로그램 하나를 메모리의 한 덩어리 연속 공간에 올리는 방식이에요. 프로그램이 들어왔다 나가기를 반복하면 중간중간 빈 공간(**hole**, 구멍)이 생겨요. 새 요청이 오면 어느 hole에 넣을지 정하는 게 **배치 전략**이에요.

| 전략 | 고르는 hole | 특징 |
|---|---|---|
| 최초 적합 (first fit) | 앞에서부터 보다가 **처음** 만난 충분히 큰 것 | 찾기가 가장 빨라요 |
| 최적 적합 (best fit) | 들어가는 것 중 **가장 작은** 것(남는 공간 최소) | 크기순 정렬이 없으면 전부 훑어야 해요. 아주 작은 조각이 많이 남아요 |
| 최악 적합 (worst fit) | **가장 큰** 것 | 전부 훑어야 해요. 남는 조각이 커서 다시 쓰기는 쉬워요 |

표준 교재(Silberschatz 『Operating System Concepts』)는 시뮬레이션상 최초·최적 적합이 최악 적합보다 시간·공간 효율이 대체로 낫고, 그중 최초 적합이 보통 더 빠르다고 정리해요.

#### 단계별 계산: 배치 전략

빈 공간이 앞에서부터 **150K, 400K, 250K, 90K, 520K** 순서로 있고, 230K짜리 요청이 왔어요.

1. 230K 이상인 hole만 추려요 → 400K, 250K, 520K. (150K, 90K는 못 써요.)
2. **최초 적합**: 앞에서부터 처음 맞는 것 → **400K** (남는 공간 170K)
3. **최적 적합**: 후보 중 가장 작은 것 → **250K** (남는 공간 20K)
4. **최악 적합**: 후보 중 가장 큰 것 → **520K** (남는 공간 290K)

150K와 90K를 합치면 240K라서 230K보다 크지만, 떨어져 있어서 이 요청에는 못 써요. 이게 바로 외부 단편화예요.

### 내부 단편화 vs 외부 단편화

**단편화**(fragmentation)는 메모리가 남는데도 못 쓰는 낭비예요.

| 구분 | 뜻 | 어디서 생기나 | 해결 |
|---|---|---|---|
| 내부 단편화 | 할당받은 칸 **안**에서 남는 공간 | 고정 분할, 페이징(마지막 페이지) | 페이지 크기 줄이기 |
| 외부 단편화 | 빈 공간 합은 충분한데 **떨어져 있어서** 못 씀 | 가변 분할, 세그먼테이션 | 통합, 압축, 페이징 |

- **통합**(coalescing): 바로 붙어 있는 빈 공간끼리 하나로 합쳐요.
- **압축**(compaction): 사용 중인 영역을 한쪽으로 몰아서 빈 공간을 한 덩어리로 만들어요. 시간이 많이 들고, 실행 중에 프로그램 위치를 옮길 수 있어야 해요.
- 근본 해결은 연속으로 놓지 않는 것, 즉 페이징이에요.

### 페이징과 주소 변환

**페이징**(paging)은 프로그램을 같은 크기의 **페이지**로, 실제 메모리를 같은 크기의 **프레임**으로 나눠요. **페이지 테이블**(page table, 페이지 번호 → 프레임 번호 대응표)만 있으면 빈 프레임 아무 데나 넣을 수 있어서 외부 단편화가 없어요. 다만 마지막 페이지가 꽉 차지 않으면 내부 단편화가 생겨요.

프로그램이 쓰는 주소(**논리 주소**)는 "몇 번째 페이지의(p) 몇 번째 칸(d, **오프셋**)"으로 읽어요.

- p = 논리 주소 ÷ 페이지 크기 (몫)
- d = 논리 주소 mod 페이지 크기 (나머지)
- **물리 주소 = 프레임 번호 × 페이지 크기 + d**

<PagingAddressStepper />

#### 단계별 계산: 페이징 주소 변환

페이지 크기 1KB(1024바이트), 논리 주소 3500, 페이지 테이블은 아래와 같아요.

| 페이지 번호 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| 프레임 번호 | 5 | 2 | 7 | 1 |

1. p = 3500 ÷ 1024 = **3** (1024 × 3 = 3072)
2. d = 3500 − 3072 = **428**
3. 페이지 테이블에서 페이지 3 → 프레임 **1**
4. 물리 주소 = 1 × 1024 + 428 = **1452**

비트로 나오는 문제도 있어요. 32비트 주소, 페이지 4KB(2^12)라면 하위 **12비트가 오프셋**, 상위 **20비트가 페이지 번호**예요(페이지 테이블 항목은 최대 2^20개). 16진수 한 자리가 4비트라서 0x12345는 하위 세 자리 0x345(=837)가 오프셋, 나머지 0x12(=18)가 페이지 번호예요.

페이지 테이블의 각 항목에는 **타당 비트**(valid bit, 이 페이지를 써도 되는지)가 있고, 쓰면 안 되는 페이지에 접근하면 운영체제로 넘어가요(트랩).

### 세그먼테이션

**세그먼테이션**(segmentation)은 프로그램을 메인 코드, 함수, 스택, 데이터처럼 **의미 단위**로 나눠요. 크기가 제각각이라 외부 단편화가 생겨요.

논리 주소는 (세그먼트 번호 s, 오프셋 d)이고, 세그먼트 테이블에 **기준**(base, 시작 위치)과 **한계**(limit, 길이)가 있어요. `d < limit`이면 물리 주소 = base + d, 아니면 주소 오류(트랩)예요.

#### 단계별 계산: 세그먼트 주소 변환

세그먼트 1의 base = 3000, limit = 600이에요.

1. (1, 250): 250은 600보다 작아요 → 물리 주소 = 3000 + 250 = **3250**
2. (1, 700): 700은 600 이상이에요 → **트랩**(주소 오류). 3700이라고 답하면 틀려요.

| 비교 | 페이징 | 세그먼테이션 |
|---|---|---|
| 나누는 단위 | 같은 크기(물리적) | 의미 단위, 크기 가변(논리적) |
| 단편화 | 내부 | 외부 |
| 테이블 내용 | 프레임 번호 | base, limit |

둘을 합친 **페이지화된 세그먼테이션**(세그먼트를 다시 페이지로 나눔)도 있어요.

### TLB와 유효 접근 시간

페이지 테이블은 메모리에 있어요. 그러면 데이터 하나를 읽으려고 메모리에 **두 번**(테이블 한 번, 데이터 한 번) 가야 해요. 그래서 최근에 쓴 "페이지 → 프레임" 짝을 CPU 옆 작고 빠른 저장소에 둬요. 이게 **TLB**(Translation Lookaside Buffer, 주소 변환 캐시, 연관 레지스터라고도 불러요)예요. 모든 항목을 한꺼번에 비교해서 빠르지만 비싸서 작아요.

**적중률**(hit ratio) h는 TLB에서 바로 찾는 비율이에요.

- TLB 적중: TLB 시간 + 메모리 1번
- TLB 실패: TLB 시간 + 메모리 2번(테이블 + 데이터)
- **유효 접근 시간(EAT) = h × (TLB + 메모리) + (1 − h) × (TLB + 2 × 메모리)**

#### 단계별 계산: TLB 유효 접근 시간

TLB 20ns, 메모리 100ns, 적중률 0.8이에요.

1. 적중 시: 20 + 100 = 120ns
2. 실패 시: 20 + 100 × 2 = 220ns
3. EAT = 0.8 × 120 + 0.2 × 220 = 96 + 44 = **140ns**

적중률이 0.9면 130ns, 0.98이면 122ns예요. 지문이 "TLB 검색 시간은 무시"라고 하거나 "적중 시 몇 ns, 실패 시 몇 ns"를 통째로 주면 그 조건대로 넣어야 해요. 공식을 외워서 기계적으로 넣지 마세요.

### 가상 메모리와 페이지 부재

**가상 메모리**는 프로그램 일부만 메모리에 올려도 실행되게 해서, 실제 메모리보다 큰 프로그램도 돌리게 해 줘요. 필요한 페이지를 그때그때 올리는 걸 **요구 페이징**(demand paging)이라고 해요.

찾는 페이지가 메모리에 없으면 **페이지 부재**(page fault)예요. 처리 순서는 이래요.

1. 타당 비트가 꺼진 페이지를 참조 → 운영체제로 트랩
2. 빈 프레임을 찾고, 없으면 교체 알고리즘으로 내보낼 페이지(희생 페이지)를 골라요. 수정된 페이지면 디스크에 먼저 써요.
3. 필요한 페이지를 디스크에서 읽어 프레임에 올려요.
4. 페이지 테이블을 고치고, 멈췄던 명령을 다시 실행해요.

가상 메모리는 CPU 이용률과 처리율을 높이지만, 응답 시간·반환 시간이 좋아진다고 보장하지는 않아요.

### 페이지 교체 알고리즘

| 알고리즘 | 내보내는 페이지 | 특징 |
|---|---|---|
| FIFO | 가장 **먼저 들어온** 것 | 큐 하나로 구현, 가장 단순. **벨레이디 이상** 발생 |
| OPT (최적, MIN) | 앞으로 **가장 오래 안 쓸** 것 | 부재 최소. 미래를 알아야 해서 **구현 불가**, 비교 기준용 |
| LRU | 가장 **오래전에 쓴** 것 | 과거로 미래를 추측(시간 지역성). 카운터나 스택으로 구현, 하드웨어 지원이 많이 필요 |
| LFU | 사용 **횟수가 가장 적은** 것 | 초반에 많이 쓰고 버린 페이지가 오래 남는 문제 |
| 2차 기회(시계, clock) | FIFO 순서로 보되 참조 비트 1이면 0으로 지우고 한 번 봐줌 | LRU 근사. 원형 큐 + 포인터 |
| NUR | 참조 비트·변경 비트로 등급을 매겨 낮은 등급부터 | 순서 (0,0) → (0,1) → (1,0) → (1,1) |

#### 단계별 계산: 같은 참조열, 프레임 3개로 5개 비교

참조열 **4, 2, 1, 4, 1, 5, 1, 2, 3, 2, 1, 3** (12번), 프레임 3개, 처음 비어 있어요. F = 부재, · = 적중이에요. 처음 세 번 채우는 것도 부재로 세요(지문에 "초기 적재 제외"가 있으면 빼요).

처음 세 번(4, 2, 1)은 모든 알고리즘이 똑같이 부재 3번이고 프레임은 [4, 2, 1]이에요. 다음 4, 1은 적중이에요. 차이는 **5가 들어올 때**부터 나요.

**FIFO (부재 7)** — 들어온 순서 4 → 2 → 1을 기억해요.

| 참조 | 4 | 2 | 1 | 4 | 1 | 5 | 1 | 2 | 3 | 2 | 1 | 3 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 결과 | F | F | F | · | · | F | · | · | F | F | F | · |
| 내보냄 | | | | | | 4 | | | 2 | 1 | 5 | |

5가 오면 가장 먼저 온 4를, 3이 오면 그다음 2를 내보내요. 그래서 바로 다음 2에서 또 부재가 나요.

**LRU (부재 6)** — 마지막으로 쓴 시점을 봐요.

| 참조 | 4 | 2 | 1 | 4 | 1 | 5 | 1 | 2 | 3 | 2 | 1 | 3 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 결과 | F | F | F | · | · | F | · | F | F | · | · | · |
| 내보냄 | | | | | | 2 | | 4 | 5 | | | |

5가 올 때 프레임 [4, 2, 1] 중 마지막 사용이 가장 오래된 건 2예요(4와 1은 방금 다시 썼으니까요).

**OPT (부재 5)** — 앞으로를 봐요. 5가 올 때 남은 참조(1, 2, 3, 2, 1, 3)에 4가 다시 안 나오니 4를, 3이 올 때 5가 다시 안 나오니 5를 내보내요. 부재는 처음 3번 + 5 + 3 = **5번**이에요.

**시계 (부재 7)** — 5와 3이 들어올 때는 세 프레임의 참조 비트가 모두 1이라, 포인터가 한 바퀴 돌며 다 0으로 지운 뒤 FIFO와 같은 페이지(4, 2)를 내보내요. 그 뒤 2와 1이 들어올 때는 포인터가 가리킨 페이지(1, 5)의 비트가 이미 0이라 바로 내보내는데, 마침 그게 FIFO의 희생 페이지와 같아서 결과가 FIFO와 똑같아요.

**LFU (부재 8)** — 횟수가 같으면 먼저 들어온 것을 내보내고, 쫓겨난 페이지의 횟수는 0으로 되돌리는 관례로 셌어요. 4가 초반에 두 번 쓰여서 끝까지 버티고, 2·3·5가 서로 밀어내며 부재가 늘어요.

| 알고리즘 | OPT | LRU | FIFO | 시계 | LFU |
|---|---|---|---|---|---|
| 부재 횟수 | **5** | 6 | 7 | 7 | 8 |

OPT가 가장 적은 건 항상 그래요. LFU가 꼴찌인 건 이 참조열 특성일 뿐 일반 법칙은 아니에요.

### 심화: 벨레이디 이상

**벨레이디 이상**(Belady's anomaly)은 프레임을 늘렸는데 페이지 부재가 오히려 늘어나는 현상이에요. FIFO(와 FIFO처럼 동작하는 시계)에서 생겨요.

참조열 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5로 세어 보면 이래요.

| 알고리즘 | 프레임 3 | 프레임 4 |
|---|---|---|
| FIFO | 9 | **10** (늘어남) |
| LRU | 10 | 8 |
| OPT | 7 | 6 |

프레임 4개 FIFO는 5가 들어오면서 1을 내보내고, 이어서 1, 2, 3, 4가 올 때마다 바로 직전에 내보낸 페이지를 다시 찾느라 연속으로 부재가 나요. LRU와 OPT는 "프레임 n개일 때 메모리에 있는 페이지가 n+1개일 때도 항상 있는" **스택 알고리즘**이라 이 현상이 없어요.

### 스래싱, 워킹셋, 지역성

**스래싱**(thrashing)은 프로세스가 실제 일보다 페이지 교체에 더 많은 시간을 쓰는 상태예요. 책상이 너무 좁아서 책 꺼내고 넣다가 하루가 끝나는 거예요.

생기는 과정은 악순환이에요.

1. 동시에 돌리는 프로세스(**다중 프로그래밍 정도**)가 너무 많아 프로세스마다 프레임이 부족해요.
2. 페이지 부재가 폭증하고, 다들 디스크를 기다리느라 CPU가 놀아요.
3. 운영체제는 CPU가 한가해 보여서 프로세스를 더 넣어요 → 더 나빠져요.

그래서 다중 프로그래밍 정도를 올리면 CPU 이용률이 오르다가 어느 지점에서 **급락**해요.

| 해결 방법 | 내용 |
|---|---|
| 워킹셋 모델 | 최근 Δ번 참조에 나온 페이지 집합(워킹셋)을 메모리에 붙잡아 둬요. 워킹셋 합이 전체 프레임보다 크면 프로세스 하나를 멈춰요 |
| PFF (페이지 부재 빈도) | 부재율 상한을 넘으면 프레임을 더 주고, 하한보다 낮으면 회수해요. 부재가 날 때만 조정해서 부담이 적어요 |
| 다중 프로그래밍 정도 낮추기 | 프로세스 일부를 중지하거나 디스크로 내보내요 |

**워킹셋 예**: 참조 1, 2, 1, 3, 4, 4, 3, 4이고 Δ = 4예요. 4번째 참조 시점의 최근 4개는 1, 2, 1, 3이라 워킹셋은 `{1, 2, 3}`(크기 3)이에요. 8번째 시점의 최근 4개는 4, 4, 3, 4라 `{3, 4}`(크기 2)예요. Δ가 너무 작으면 지금 필요한 페이지를 다 못 담고, 너무 크면 예전 페이지까지 담아요.

**지역성**(locality)은 프로그램이 메모리를 골고루가 아니라 몰려서 쓰는 성질이에요. 캐시, TLB, LRU, 워킹셋이 전부 이 성질에 기대요.

| 종류 | 뜻 | 예 |
|---|---|---|
| 시간 지역성 | 방금 쓴 것을 곧 또 써요 | 반복문, 합계·카운터 변수, 스택, 자주 부르는 함수 |
| 공간 지역성 | 쓴 곳 근처를 곧 써요 | 배열 순서대로 돌기, 코드 순차 실행 |

### 심화: 페이지 크기, LRU 구현, 요구 페이징 접근 시간

- **페이지가 작으면**: 내부 단편화 줄어듦, 페이지 테이블 커짐, 디스크 입출력 횟수 늘어남, 필요한 부분만 올려서 지역성 반영이 좋아요. 크면 반대예요. Intel은 4KB·2MB/4MB·1GB, ARM은 4KB·16KB·64KB처럼 여러 크기를 지원해요.
- **LRU 구현**: 카운터 방식은 페이지마다 마지막 사용 시각을 적어 두고 가장 작은 걸 내보내요. 스택 방식은 참조할 때마다 그 페이지를 맨 위로 올리고 맨 아래를 내보내요. 둘 다 매 참조마다 일이 생겨서 실제로는 참조 비트·시계 알고리즘으로 근사해요.
- **LFU 보완**: 횟수를 주기적으로 오른쪽 시프트(절반으로)해서 옛날 횟수의 영향을 줄여요. 반대로 횟수가 가장 많은 걸 내보내는 MFU도 있지만 잘 안 써요.
- **NUR 순서 이유**: 수정된 페이지는 내보낼 때 디스크에 다시 써야 해서 비싸요. 그래서 "참조 안 했지만 수정함"(0,1)이 "참조했지만 수정 안 함"(1,0)보다 먼저 교체돼요. 참조 비트는 주기적으로 0으로 지워요.
- **공유 페이지**: 여러 프로세스가 같은 코드(편집기 등)를 같은 프레임으로 공유할 수 있어요. 페이징의 장점이에요.
- **요구 페이징 EAT** = (1 − p) × 메모리 시간 + p × 부재 처리 시간 (p = 부재율). 메모리 200ns, 부재 처리 8ms(= 8,000,000ns), p = 0.001이면 0.999 × 200 + 0.001 × 8,000,000 = **8199.8ns**로 약 40배 느려져요. 부재는 1000번에 한 번이어도 치명적이에요.

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 페이징은 외부 단편화, 세그먼테이션은 내부 단편화 | 거꾸로예요. 페이징 = **내부**, 세그먼테이션 = **외부** |
| 가상 메모리를 쓰면 단편화가 없다 | 페이징에도 내부 단편화는 있어요 |
| 페이지 크기가 커지면 외부 단편화가 커진다 | 커지는 건 **내부** 단편화 |
| LRU는 사용 횟수가 가장 적은 페이지를 교체 | 그건 **LFU**. LRU는 마지막 사용이 가장 오래된 것(시간 기준) |
| OPT는 실제 시스템에서 가장 많이 쓰는 알고리즘 | 미래를 알아야 해서 **구현 불가**. 비교 기준이에요 |
| LRU에서 벨레이디 이상이 생긴다 | **FIFO**(와 시계)에서 생겨요. LRU·OPT는 스택 알고리즘이라 안 생겨요 |
| 최적 적합은 항상 단편화가 가장 적다 | 아주 작은 조각을 많이 남겨요. "최적"은 남는 공간이 가장 작은 hole이라는 뜻일 뿐 |
| 최악 적합은 가장 작은 hole에 넣는다 | **가장 큰** hole이에요 |
| 압축은 인접한 빈 공간만 합친다 | 그건 **통합**. 압축은 사용 중인 영역을 옮겨서 빈 공간을 한 덩어리로 |
| NUR은 (참조1, 변경0)을 (참조0, 변경1)보다 먼저 교체 | (0,0) → **(0,1)** → (1,0) → (1,1) 순 |
| 스래싱은 다중 프로그래밍 정도를 높여 해결 | **낮춰야** 해요. 스래싱 때 CPU 이용률은 떨어져요 |
| 가상 메모리는 응답 시간을 줄인다 | CPU 이용률·처리율은 높이지만 응답·반환 시간은 보장 안 해요 |
| TLB 실패 시 메모리 접근은 1번 | **2번**(페이지 테이블 + 데이터) |
| 세그먼트 오프셋이 limit 이상이면 base + d | **트랩**(주소 오류) |

<summary>2. 빈 공간이 앞에서부터 200K, 50K, 120K, 300K, 90K 순서로 있다. 100K 요청을 최적 적합(best fit)으로 배치하면 어느 공간에 들어가고, 얼마가 남는가?</summary>

<details>
<summary>3. 페이지 크기가 2KB(2048바이트)이고 페이지 테이블이 0→3, 1→6, 2→4일 때, 논리 주소 5000의 물리 주소는?</summary>

① 904

② 5000

③ 9096

④ 13192

**정답: ③**

p = 5000 ÷ 2048 = 2 (2048 × 2 = 4096), d = 5000 − 4096 = 904예요. 페이지 2는 프레임 4라서 물리 주소 = 4 × 2048 + 904 = 9096이에요. ①은 오프셋만 쓴 값, ④는 프레임 6(페이지 1)을 잘못 고른 값(6 × 2048 + 904)이에요.
</details>

<details>
<summary>4. 세그먼트 2의 base가 1800, limit이 400이다. 논리 주소 (2, 350)과 (2, 420)에 대한 설명으로 옳은 것은?</summary>

① (2, 350) → 2150, (2, 420) → 2220

② (2, 350) → 2150, (2, 420) → 트랩(주소 오류)

③ (2, 350) → 트랩, (2, 420) → 2220

④ 둘 다 트랩

**정답: ②**

350은 limit 400보다 작아서 1800 + 350 = 2150이에요. 420은 limit 400 이상이라 세그먼트 범위를 벗어나므로 트랩이에요. ①처럼 그냥 base에 더하면 틀려요.
</details>

<details>
<summary>5. TLB 검색 10ns, 메모리 접근 100ns, TLB 적중률 90%일 때 유효 접근 시간은?</summary>

① 110ns

② 111ns

③ 120ns

④ 210ns

**정답: ③**

적중 시 10 + 100 = 110ns, 실패 시 10 + 100 × 2 = 210ns예요. 0.9 × 110 + 0.1 × 210 = 99 + 21 = 120ns예요. 실패 때도 메모리를 한 번만 간다고 착각하면 ①이 나와요.
</details>

<details>
<summary>6. 프레임 3개(처음엔 비어 있음)에서 참조열 1, 3, 0, 3, 5, 6, 3, 1, 5, 0을 LRU로 처리할 때 페이지 부재 횟수는? (처음 적재도 부재로 센다)</summary>

① 6

② 7

③ 8

④ 9

**정답: ③**

1F 3F 0F → [1, 3, 0], 3 적중. 5F: 가장 오래전에 쓴 1을 내보냄 → [5, 3, 0]. 6F: 0을 내보냄 → [5, 3, 6]. 3 적중. 1F: 5를 내보냄 → [1, 3, 6]. 5F: 6을 내보냄 → [1, 3, 5]. 0F: 3을 내보냄 → [1, 0, 5]. 부재는 1, 3, 0, 5, 6, 1, 5, 0으로 8번이에요. 같은 참조열에서 OPT는 7번(②), FIFO는 9번(④)이에요.
</details>

<details>
<summary>7. 페이지 교체 알고리즘에 대한 설명으로 옳은 것은?</summary>

① LRU는 프레임 수를 늘렸을 때 페이지 부재가 늘어나는 벨레이디 이상이 생길 수 있다.

② OPT는 부재율이 가장 낮아 실제 운영체제에서 주로 쓰인다.

③ NUR에서는 참조 비트 0·변경 비트 1인 페이지가 참조 비트 1·변경 비트 0인 페이지보다 먼저 교체된다.

④ LFU는 가장 오래전에 사용한 페이지를 교체한다.

**정답: ③**

NUR 순서는 (0,0) → (0,1) → (1,0) → (1,1)이에요. ① 벨레이디 이상은 FIFO 쪽 문제고 LRU는 스택 알고리즘이라 안 생겨요. ② OPT는 미래를 알아야 해서 구현할 수 없어요. ④는 LRU 설명이에요. LFU는 사용 횟수가 가장 적은 걸 교체해요.
</details>

<details>
<summary>8. 스래싱에 대한 설명으로 옳지 않은 것은?</summary>

① 페이지 부재 처리에 실제 실행보다 더 많은 시간을 쓰는 현상이다.

② 다중 프로그래밍 정도를 높이면 CPU 이용률이 계속 올라가 스래싱이 해소된다.

③ 워킹셋 모델은 최근 참조된 페이지 집합을 메모리에 유지해 스래싱을 막는다.

④ 페이지 부재 빈도(PFF) 방식은 부재율이 상한을 넘으면 프레임을 더 준다.

**정답: ②**

다중 프로그래밍 정도를 계속 높이면 프로세스마다 프레임이 모자라서 부재가 폭증하고 CPU 이용률이 급락해요. 스래싱을 풀려면 오히려 낮춰야 해요.
</details>

## 면접 질문

<details>
<summary>Q. 페이징과 세그먼테이션의 차이는 무엇인가요?</summary>

**답변(30초)** 둘 다 프로그램을 쪼개서 메모리에 올리는 방법인데, 쪼개는 기준이 달라요. 페이징은 같은 크기 페이지로 나눠서 빈 프레임 아무 데나 넣을 수 있어 외부 단편화가 없고, 대신 마지막 페이지에서 내부 단편화가 생겨요. 세그먼테이션은 코드·데이터·스택처럼 의미 단위로 나눠서 보호·공유가 자연스럽지만, 크기가 제각각이라 외부 단편화가 생겨요. 그래서 둘을 합친 페이지화된 세그먼테이션도 써요.

**꼬리질문**
- Q. 페이징이면 메모리 접근이 두 번인데 느리지 않나요? → 최근 주소 변환 결과를 TLB에 캐시해서, 적중하면 메모리 접근 한 번으로 끝나요. 지역성 덕분에 적중률이 높아요.
</details>

<details>
<summary>Q. 스래싱이 무엇이고 어떻게 막나요?</summary>

**답변(30초)** 스래싱은 메모리가 모자라서 프로세스가 일보다 페이지 교체에 더 많은 시간을 쓰는 상태예요. 프로세스가 너무 많으면 각자 프레임이 부족해져 부재가 폭증하고, CPU가 놀아 보이니 운영체제가 프로세스를 더 넣어서 악순환이 돼요. 워킹셋만큼 프레임을 보장하거나, 부재 빈도를 보고 프레임을 조정하거나, 동시에 도는 프로세스 수를 줄여서 막아요. 서버라면 스왑이 계속 일어날 때 프로세스 수나 힙 크기를 줄이거나 메모리를 늘리는 게 같은 대응이에요.

**꼬리질문**
- Q. LRU는 실제로 어떻게 구현하나요? → 매 참조마다 시각을 기록하면 비싸서, 참조 비트와 시계(2차 기회) 알고리즘으로 근사해요.
</details>
