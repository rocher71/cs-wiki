:::tip[한 줄 요약]
**프로세스**는 메모리에 올라와 실행 중인 프로그램이고, OS는 프로세스마다 하나씩 둔 **PCB**에 상태·PC·레지스터 등을 적어 관리해요. **스레드**는 프로세스 안의 실행 흐름이라 코드·데이터·힙은 함께 쓰고, **스택·레지스터·PC만 따로** 가져요.
:::

:::note[처음이라면 여기까지]
① 프로그램은 디스크에 있는 레시피, 프로세스는 그 레시피로 지금 요리하고 있는 상태예요.

② 상태 전이 이름 네 개를 외우세요. 준비→실행 **디스패치**, 실행→준비 **타이머 런아웃**, 실행→대기 **블록**, 대기→준비 **웨이크업**. 대기에서 실행으로 바로 가는 길은 없어요.

③ 스레드끼리 **따로 갖는 건 스택·레지스터·PC** 세 가지, 나머지(코드·데이터·힙·파일)는 공유해요.

④ 아래 "객관식 함정" 표를 보고 연습 문제 1~4번을 풀어 보세요. "심화:"는 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

부엌에 요리책이 꽂혀 있어요. 책에 적힌 레시피는 그냥 글자일 뿐 아무 일도 하지 않아요. 이게 **프로그램**이에요. 요리사가 레시피를 펴고 재료를 꺼내 지금 3번째 단계를 하고 있다면, 그 "진행 중인 요리"가 **프로세스**예요.

요리사(CPU)는 한 명인데 요리는 여러 개예요. 그래서 하나를 하다가 오븐을 기다리는 동안 다른 요리로 넘어가요. 넘어가기 전에 "파스타: 4단계, 면 삶는 중, 소금 넣었음"처럼 메모를 남겨야 돌아와서 이어 할 수 있어요. 이 메모장이 **PCB**예요.

한 요리를 보조 요리사 여러 명이 나눠 맡을 수도 있어요. 재료와 냉장고(데이터·힙)는 같이 쓰지만, 각자 "내가 지금 몇 단계인지"와 자기 도마(스택)는 따로 가져요. 이 보조 요리사가 **스레드**예요.

단, 실제로는 요리사가 "오븐 기다리는 중"이면 OS가 알아서 다른 프로세스에 CPU를 줘요. 프로세스가 스스로 넘어가는 게 아니라 OS의 스케줄러가 결정해요.

## 제대로 알기

### 프로그램과 프로세스

| 구분 | 프로그램 | 프로세스 |
|---|---|---|
| 어디에 | 디스크 | 메모리 |
| 성격 | 정적인 코드 파일 | 실행 중인 상태(동적) |
| OS 관리 정보 | 없음 | PCB가 하나씩 붙음 |

프로세스 메모리는 네 영역으로 나뉘어요.

| 영역 | 담는 것 | 특징 |
|---|---|---|
| 코드(텍스트) | 실행할 기계어 명령 | 읽기 전용 |
| 데이터 | 전역 변수, 정적(static) 변수 | 프로그램 시작 때 크기 고정 |
| 힙 | 실행 중 동적으로 만든 객체(`new`, `malloc`) | 위(높은 주소)로 자람 |
| 스택 | 지역 변수, 함수 복귀 주소 | 아래(낮은 주소)로 자람 |

### 상태와 전이 이름

프로세스는 기본 5가지 상태를 오가요.

- **생성**(new): 막 만들어지는 중
- **준비**(ready): CPU만 받으면 바로 실행할 수 있어 준비 큐에서 기다림
- **실행**(running): CPU를 받아 명령을 실행 중
- **대기**(waiting, 책에 따라 "블록·보류"): 입출력 같은 사건이 끝나기를 기다림
- **종료**(terminated): 실행이 끝남

필기에서 가장 많이 묻는 건 화살표 이름이에요.

| 전이 | 이름 | 언제 |
|---|---|---|
| 준비 → 실행 | **디스패치**(dispatch) | 디스패처가 준비 큐 맨 앞 프로세스에 CPU를 줌 |
| 실행 → 준비 | **타이머 런아웃**(timer runout, 타임아웃) | 받은 시간을 다 써서 타이머 인터럽트가 걸림, 또는 선점당함 |
| 실행 → 대기 | **블록**(block) | 입출력을 요청하는 등 스스로 기다려야 함 |
| 대기 → 준비 | **웨이크업**(wakeup) | 기다리던 입출력·사건이 끝남 |

없는 화살표도 중요해요.

- **대기 → 실행은 없어요.** 입출력이 끝나도 바로 CPU를 받는 게 아니라 준비 큐에 다시 줄 서요.
- **준비 → 대기도 없어요.** 입출력을 요청하려면 먼저 실행 중이어야 하니까요.

### PCB (프로세스 제어 블록)

**PCB**(Process Control Block, 프로세스 관리 정보를 모은 표)는 OS가 프로세스마다 하나씩 만드는 자료구조예요. 프로세스가 생길 때 만들고 끝날 때 지워요. 사용자 프로그램이 아니라 **OS(커널) 메모리**에 있어요.

| 항목 | 내용 |
|---|---|
| 프로세스 식별자(PID) | 프로세스 번호 |
| 프로세스 상태 | 생성·준비·실행·대기·종료 중 어느 것 |
| 프로그램 카운터(PC) | 다음에 실행할 명령어 주소 |
| CPU 레지스터 | 누산기, 스택 포인터, 범용 레지스터 등 하던 계산의 중간값 |
| CPU 스케줄링 정보 | 우선순위, 스케줄링 큐 포인터 |
| 메모리 관리 정보 | 기준·한계 레지스터, 페이지 테이블·세그먼트 테이블 |
| 계정 정보 | 사용한 CPU 시간, 시간 제한, 계정 번호 |
| 입출력 상태 정보 | 할당된 입출력 장치, 열린 파일 목록 |

교재에 따라 부모·자식 프로세스 포인터를 넣기도 해요. 책에 따라 PCB를 TCB(Task Control Block)라고도 불러요.

객관식에서 "PCB에 없는 것"으로는 **프로그램 소스 코드**, 컴파일러 정보, 다른 프로세스의 PCB 내용 같은 보기가 자주 나와요.

### 문맥 교환

**문맥 교환**(context switch)은 CPU를 다른 프로세스에 넘길 때 일어나는 일이에요.

1. 지금 실행 중인 프로세스의 레지스터·PC 등을 그 프로세스의 PCB에 저장해요.
2. 다음에 실행할 프로세스의 PCB에서 그 값들을 꺼내 CPU에 복원해요.
3. 새 프로세스가 멈췄던 지점부터 이어서 실행해요.

바꾸는 동안 CPU는 쓸모 있는 일을 못 해요. 그래서 문맥 교환 시간은 **순수 오버헤드**(일에 보탬이 안 되는 추가 비용)예요. 비용은 메모리 속도, 레지스터 개수, 전용 명령어가 있는지에 따라 달라요.

언제 일어날까요? 준비→실행, 실행→준비, 실행→대기로 바뀔 때예요. 계기는 타이머·입출력 인터럽트나 시스템 호출이에요. 자세한 흐름 그림은 [스레드 기초](../../../java/thread-basics/)에 있어요.

### 스레드: 공유하는 것과 따로 갖는 것

**스레드**(thread)는 프로세스가 가진 "자원"과 "실행 흐름" 중에서 실행 흐름만 떼어 낸 단위예요. **경량 프로세스**(LWP)라고도 불러요. 프로세스는 스레드를 하나 이상 가져요.

| 공유한다 (프로세스 단위) | 스레드마다 따로 |
|---|---|
| 코드(텍스트) 영역 | **스택** |
| 데이터 영역(전역 변수) | **레지스터 집합** |
| 힙 | **프로그램 카운터(PC)** |
| 열린 파일 등 OS 자원 | 스레드 ID |

| 장점 | 단점 |
|---|---|
| 생성·종료·문맥 교환이 프로세스보다 가벼움 | 한 스레드가 메모리를 망가뜨리거나 죽으면 프로세스 전체가 영향받음 |
| 자원을 따로 복사하지 않고 공유 | 공유 데이터를 동시에 고치면 꼬여서 동기화가 필요 |
| 하나가 기다려도 다른 스레드가 일해 응답성이 좋음 | 같은 주소 공간이라 다른 스레드 스택도 건드릴 수 있음(보호 없음) |
| 멀티코어에서 병렬 실행 | |

같은 프로세스 안 스레드끼리 바꿀 때는 주소 공간(페이지 테이블 등)을 그대로 두면 돼서 프로세스끼리 바꿀 때보다 싸요.

스레드별 정보는 **TCB**(Thread Control Block)에 담아요. 레지스터·PC·스택 포인터, 상태, 우선순위, 소속 PCB 포인터가 들어가요. PCB가 자기 스레드들의 TCB 목록을 가진다고 보면 돼요.

### 심화: 사용자 수준 스레드와 커널 수준 스레드

스레드를 누가 관리하느냐에 따라 두 종류로 나눠요(표준 OS 교재 기준).

| 구분 | 사용자 수준 스레드 | 커널 수준 스레드 |
|---|---|---|
| 관리 주체 | 사용자 공간의 스레드 라이브러리 | OS 커널 |
| 커널이 아는가 | 모름(프로세스 하나로 봄) | 앎, 스레드 단위로 스케줄 |
| 생성·전환 속도 | **빠름**(커널에 안 들어감) | 상대적으로 느림(커널 모드 전환) |
| 한 스레드가 블로킹 호출하면 | **프로세스 전체가 멈춤** | 다른 스레드는 계속 실행 |
| 멀티코어 병렬 | 불가 | 가능 |
| 이식성 | 좋음 | OS에 의존 |

둘을 잇는 방식(매핑 모델)도 있어요.

| 모델 | 뜻 | 특징 |
|---|---|---|
| 다대일(N:1) | 사용자 스레드 여러 개 → 커널 스레드 1개 | 하나가 블록되면 전체 정지, 병렬 불가 |
| 일대일(1:1) | 사용자 스레드 1개 → 커널 스레드 1개 | 병렬 가능, 커널 스레드가 많아지는 부담. Linux·Windows 방식 |
| 다대다(M:N) | 여러 개 → 그보다 적거나 같은 수의 커널 스레드 | 둘의 절충 |

자바의 일반 스레드는 OS 스레드와 1:1이고, Java 21 가상 스레드는 많은 가상 스레드를 적은 OS 스레드에 올리는 M:N 방식이에요. → [가상 스레드](../../../java/virtual-threads/)

### 심화: 스케줄러 세 종류와 유예 상태

| 스케줄러 | 하는 일 | 다른 이름 |
|---|---|---|
| 장기 스케줄러 | 어떤 작업을 메모리에 올려 준비 큐에 넣을지 결정 → **다중 프로그래밍 정도**(메모리에 동시에 올라온 프로세스 수)를 정함 | 작업 스케줄러 |
| 단기 스케줄러 | 준비 큐에서 누구에게 CPU를 줄지 결정(디스패치) | CPU 스케줄러 |
| 중기 스케줄러 | 메모리가 부족할 때 프로세스를 디스크로 내보내거나(스왑 아웃) 다시 들임(스왑 인) | 스와퍼 |

중기 스케줄러가 디스크로 내보낸 프로세스는 **유예(중단) 준비**·**유예 대기** 상태가 돼요. 이 상태의 프로세스는 메인 메모리가 아니라 **디스크**에 있어요. 단기 스케줄러가 누구를 고르는지는 [CPU 스케줄링](../cpu-scheduling/)에서 다뤄요.

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 실행 → 대기는 타이머 런아웃 | 실행 → 대기는 **블록**. 타이머 런아웃은 실행 → **준비** |
| 입출력을 요청하면 준비 상태가 된다 | 입출력 요청은 **대기** 상태로(블록) |
| 대기 → 준비 전이를 디스패치라 한다 | 대기 → 준비는 **웨이크업**. 디스패치는 준비 → 실행뿐 |
| 입출력이 끝나면 바로 실행 상태가 된다 | 대기 → 실행 직행은 **없음**. 준비로 갔다가 디스패치 |
| PCB는 사용자 프로그램 영역에 있고 프로그램 소스를 담는다 | PCB는 **커널 메모리**에 있고, 소스 코드는 담지 않음 |
| 스레드끼리 스택을 공유한다 | 스택·레지스터·PC는 **스레드마다 따로** |
| 스레드마다 힙을 따로 가진다 | 힙·데이터·코드·열린 파일은 **공유** |
| 사용자 수준 스레드는 하나가 블록돼도 나머지가 실행된다 | 그건 **커널 수준**. 사용자 수준은 프로세스 전체가 블록 |
| 커널 수준 스레드가 생성·전환이 더 빠르다 | 커널 모드 전환이 필요해 **사용자 수준이 더 빠름** |
| 문맥 교환이 잦을수록 시스템 성능이 좋아진다 | 문맥 교환은 **오버헤드**라 줄여야 함 |
| 장기 스케줄러는 스왑 인/아웃을 맡는다 | 스왑은 **중기**. 장기는 메모리에 올릴 작업 선택 |

## 연습 문제

<details>
<summary>1. 실행 중인 프로세스가 할당받은 시간을 모두 사용했을 때 일어나는 상태 전이는?</summary>

① 실행 → 대기(블록) ② 실행 → 준비(타이머 런아웃) ③ 대기 → 준비(웨이크업) ④ 준비 → 실행(디스패치)

**정답: ②**

시간을 다 쓴 건 기다릴 사건이 있는 게 아니라 차례가 끝난 거라 준비 큐로 돌아가요. ①은 입출력을 요청했을 때예요.
</details>

<details>
<summary>2. 프로세스 상태 전이로 존재하지 않는 것은?</summary>

① 준비 → 실행 ② 실행 → 대기 ③ 대기 → 실행 ④ 대기 → 준비

**정답: ③**

입출력이 끝난 프로세스는 바로 CPU를 받지 않고 준비 큐에 줄 서요(웨이크업). 그다음 디스패치돼야 실행돼요.
</details>

<details>
<summary>3. PCB에 저장되는 정보가 아닌 것은?</summary>

① 프로그램 카운터 ② 프로세스 상태 ③ 프로그램의 소스 코드 ④ 열린 파일 목록

**정답: ③**

PCB는 프로세스를 관리하는 정보(번호, 상태, PC, 레지스터, 스케줄링·메모리·계정·입출력 정보)를 담아요. 소스 코드는 PCB에 들어가지 않아요.
</details>

<details>
<summary>4. 같은 프로세스에 속한 스레드들이 서로 공유하지 않는 것은?</summary>

① 힙 영역 ② 전역 변수가 있는 데이터 영역 ③ 스택 ④ 열린 파일

**정답: ③**

스택(지역 변수·함수 호출 기록), 레지스터, PC는 스레드마다 따로 있어요. 그래야 각 스레드가 자기 실행 위치를 따로 기억할 수 있어요.
</details>

<details>
<summary>5. 문맥 교환에 대한 설명으로 옳지 않은 것은?</summary>

① 현재 프로세스의 레지스터 값을 PCB에 저장하고 다음 프로세스의 값을 복원한다.

② 문맥 교환 중에도 CPU는 사용자 프로세스의 명령을 계속 실행하므로 손해가 없다.

③ 같은 프로세스 안 스레드 간 교환은 주소 공간을 바꾸지 않아 프로세스 간 교환보다 가볍다.

④ 타이머 인터럽트나 입출력 인터럽트가 계기가 될 수 있다.

**정답: ②**

문맥 교환하는 동안 CPU는 쓸모 있는 일을 못 해요. 그래서 순수 오버헤드이고, 너무 자주 일어나면 성능이 떨어져요.
</details>

<details>
<summary>6. 사용자 수준 스레드와 커널 수준 스레드에 대한 설명으로 옳은 것은?</summary>

① 사용자 수준 스레드는 커널이 직접 스케줄링한다.

② 사용자 수준 스레드는 한 스레드가 블로킹 시스템 호출을 하면 같은 프로세스의 스레드가 모두 멈출 수 있다.

③ 커널 수준 스레드는 커널 모드 전환이 없어 사용자 수준 스레드보다 생성이 빠르다.

④ 다대일 모델은 여러 스레드를 여러 CPU 코어에서 동시에 실행할 수 있다.

**정답: ②**

커널은 사용자 수준 스레드를 몰라서 프로세스 하나로 봐요. 그래서 하나가 블록되면 프로세스 전체가 블록돼요. ①은 커널 수준 설명, ③은 반대(사용자 수준이 더 빠름), ④ 다대일은 커널 스레드가 하나라 병렬 실행이 안 돼요.
</details>

## 면접 질문

<details>
<summary>Q. 프로세스와 스레드의 차이는 무엇이고, 스레드끼리 무엇을 공유하나요?</summary>

**답변(30초)** 프로세스는 OS에게 메모리 같은 자원을 따로 받아 실행되는 프로그램이고, 스레드는 그 프로세스 안의 실행 흐름이에요. 같은 프로세스의 스레드는 코드·데이터·힙·열린 파일을 공유하고, 스택·레지스터·PC만 따로 가져요. 그래서 스레드는 만들고 바꾸는 비용이 작고 데이터 공유가 쉽지만, 공유 데이터를 동시에 고치면 동기화 문제가 생기고 한 스레드의 오류가 프로세스 전체에 퍼질 수 있어요.

**꼬리질문**
- Q. 왜 스택은 따로 가져야 하나요? → 스레드마다 호출 중인 함수와 지역 변수가 달라서, 같이 쓰면 서로의 실행 위치를 덮어써요.
- Q. 멀티 프로세스는 언제 쓰나요? → 하나가 죽어도 다른 쪽이 살아야 할 때(격리). 자세한 비교는 [스레드 기초](../../../java/thread-basics/)를 보세요.
</details>

<details>
<summary>Q. 문맥 교환이란 무엇이고, 왜 비용인가요?</summary>

**답변(30초)** CPU를 다른 프로세스에 넘길 때 지금 프로세스의 레지스터·PC를 PCB에 저장하고, 다음 프로세스의 PCB에서 값을 복원하는 과정이에요. 이 시간 동안 CPU는 실제 일을 못 하니 순수 오버헤드예요. 스레드끼리는 주소 공간을 그대로 쓰니 프로세스끼리보다 싸요. 그래서 RR 스케줄링의 시간 할당량을 너무 작게 잡으면 문맥 교환이 늘어 오히려 느려져요.

**꼬리질문**
- Q. 프로세스 간 문맥 교환이 더 비싼 이유는? → 페이지 테이블 같은 메모리 정보도 바꿔야 하고, 캐시·TLB에 있던 내용이 새 프로세스에는 쓸모가 없어져요.
</details>
