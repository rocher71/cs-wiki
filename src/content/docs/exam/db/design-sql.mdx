:::tip[한 줄 요약]
**E-R 다이어그램은 개념적 설계, 정규화·릴레이션 스키마는 논리적 설계, 인덱스·저장 구조는 물리적 설계**의 일이에요. SQL은 정의(DDL: CREATE·ALTER·DROP)·조작(DML: SELECT·INSERT·UPDATE·DELETE)·제어(DCL: GRANT·REVOKE)로 나눠요.
:::

:::note[처음이라면 여기까지]
① DB 설계는 집 짓기처럼 "뭐가 필요한지 듣기 → 스케치(E-R) → 설계도(테이블) → 시공 계획(인덱스) → 짓기(SQL 실행)" 순서예요.

② SQL 명령은 세 묶음이에요. 표를 **만드는** 명령(DDL), 표 안의 데이터를 **다루는** 명령(DML), **권한을 주고 뺏는** 명령(DCL).

③ **뷰**는 실제 데이터를 저장하지 않는 "가상의 표"예요. 뷰를 지워도 원래 표는 그대로예요.

④ 시험 답은 수험서 기준이에요. 실제 DB 제품과 다른 부분은 "필기 정답 기준 vs 실무" 상자에 따로 적었어요. 연습 문제 1~5번부터 풀어 보세요.
:::

## 쉽게 이해하기

카페를 새로 연다고 해 볼게요. 먼저 사장님께 "어떤 메뉴, 어떤 손님 정보가 필요한지" 들어요(요구 사항 분석). 그다음 "손님이 메뉴를 주문한다"를 동그라미·네모로 그려 봐요(개념적 설계). 이 그림을 엑셀 시트 구조로 옮기고 중복 칸을 정리해요(논리적 설계). 시트가 커지면 어떤 칸에 색인을 붙일지 정해요(물리적 설계). 마지막으로 실제로 시트를 만들어요(구현).

SQL은 이 시트를 다루는 말이에요. 시트를 만들고 지우는 말(DDL), 줄을 추가·수정·조회하는 말(DML), 알바생에게 "이 시트는 보기만 해"라고 권한을 주는 말(DCL)로 나뉘어요.

단, 실제 설계는 한 방향으로만 가지 않아요. 뒤 단계에서 문제가 보이면 앞 단계로 돌아가 고쳐요.

## 제대로 알기

### 설계 단계와 산출물

| 단계 | 하는 일 | 산출물 | DBMS 의존 |
|---|---|---|---|
| 1. 요구 사항 분석 | 사용자 면담·설문·문서로 DB 용도 파악 | 요구 사항 명세서 | |
| 2. **개념적 설계** | 현실을 개체·관계로 추상화 | **E-R 다이어그램**(개념적 스키마) | **독립**(어떤 DBMS든 상관없음) |
| 3. **논리적 설계** | E-R을 릴레이션으로 변환, 속성 타입·NULL·제약 결정, **정규화** | 릴레이션 스키마(논리적 스키마), 테이블 명세서 | 목표 **데이터 모델**(관계형 등)에 맞춤 |
| 4. **물리적 설계** | 하드웨어·OS 특성을 고려한 저장 구조·접근 경로 | 인덱스, 레코드 배치(물리적 스키마) | 특정 DBMS·하드웨어에 종속 |
| 5. 구현 | SQL(DDL)로 실제 DB 생성 | CREATE 문 실행 결과 | |

- "목표 DBMS에 맞는 스키마 설계 + 트랜잭션 인터페이스 설계"라고 나오면 **논리적 설계**예요.
- 표준 교재 보충: 개념적 설계 단계에서 어떤 처리(트랜잭션)가 필요한지도 함께 모델링하고, 물리적 설계에서는 응답 시간·저장 공간 효율·트랜잭션 처리량을 따져요.

### E-R 다이어그램 기호 (피터 첸 표기)

| 기호 | 뜻 | 예 |
|---|---|---|
| 사각형 | **개체**(entity) | 학생, 과목 |
| 마름모 | **관계**(relationship) | 수강한다 |
| 타원 | **속성**(attribute) | 이름 |
| 밑줄 친 속성 | 키 속성 | <u>학번</u> |
| 이중 타원 | **다중값 속성**(값이 여러 개) | 전화번호(집·휴대폰) |
| 점선 타원 | **유도 속성**(다른 값으로 계산) | 생년월일로 구하는 나이 |
| 타원에 작은 타원이 달림 | 복합 속성(더 쪼갤 수 있음) | 주소 = 시 + 구 + 동 |
| 이중 사각형 | **약한 개체**(혼자 식별 못 함) | 부양가족 |
| 이중 마름모 | 약한 개체와 주인 개체를 잇는 식별 관계 | 직원–부양가족 |
| 이중선 | 필수(전체) 참여 | 모든 부양가족은 직원이 있어야 함 |
| 선 위 1, n, m | 매핑 카디널리티 | 1:1, 1:n, n:m |

관계는 참여하는 개체 수에 따라 이항·삼항·N항, 자기 자신과 맺으면 순환 관계라고 해요.

### E-R → 릴레이션 변환 규칙 (논리적 설계)

| E-R 요소 | 변환 방법 |
|---|---|
| 개체 | 릴레이션 하나로 |
| n:m 관계 | **별도 릴레이션**으로. 양쪽 기본키를 외래키로 받아 둘의 조합을 기본키로 |
| 1:n 관계 | **n쪽**에 1쪽 기본키를 외래키로 추가 |
| 1:1 관계 | 한쪽에 외래키(필수 참여하는 쪽이 받음, 둘 다 필수면 합칠 수도 있음) |
| 약한 개체 | 주인 개체의 기본키를 외래키로 받아 자기 기본키에 포함 |
| 다중값 속성 | 별도 릴레이션으로 분리 |

### 이상 현상

중복이 많은 표에서 생기는 문제예요. 예를 들어 (학번, 이름, 과목코드, 과목명)을 한 표에 넣었다고 해 볼게요.

| 이상 | 뜻 | 예 |
|---|---|---|
| **삽입 이상** | 원하지 않는 값까지 같이 넣어야 함 | 아직 수강생이 없는 새 과목을 등록할 수 없음 |
| **갱신 이상** | 중복된 값 중 일부만 바뀌어 모순 | 과목명을 한 줄만 고쳐서 같은 과목코드에 이름이 두 개 |
| **삭제 이상** | 지우고 싶지 않은 정보까지 사라짐 | 그 과목을 듣던 유일한 학생을 지우니 과목 정보도 사라짐 |

원인은 불필요한 **중복**이고, 해결은 표를 나누는 **정규화**예요.

### 정규화 단계 요약

자세한 설명과 예제는 [정규화](../../../db/normalization/) 페이지에 있어요. 필기용으로는 이 표만 외우면 돼요.

| 단계 | 조건 | 없애는 것 |
|---|---|---|
| 1NF | 모든 속성 값이 **원자값** | 반복 그룹·다중값 |
| 2NF | 1NF + **완전 함수 종속** | **부분** 함수 종속(복합 기본키의 일부만으로 결정됨) |
| 3NF | 2NF + 이행 종속 없음 | **이행** 함수 종속(X→Y, Y→Z라서 X→Z) |
| BCNF | 모든 **결정자가 후보키** | 후보키가 아닌 결정자 |
| 4NF | BCNF + 다치 종속 없음 | **다치** 종속(MVD) |
| 5NF | 4NF + 조인 종속 없음 | **조인** 종속(JD) |

- 암기: "**원부이결다조**"(원자값·부분·이행·결정자·다치·조인).
- 정규화는 **논리적 설계** 단계의 일이고, 나눈 표를 자연 조인하면 원래대로 돌아와야 해요(**무손실 분해**). 실무에선 보통 3NF나 BCNF까지 해요.

### SQL 분류

| 분류 | 뜻 | 명령 |
|---|---|---|
| **DDL**(Data Definition Language, 정의어) | 테이블·뷰·인덱스 같은 **구조**를 정의 | CREATE, ALTER, DROP, TRUNCATE, RENAME |
| **DML**(Data Manipulation Language, 조작어) | 표 안의 **데이터**를 다룸 | SELECT, INSERT, UPDATE, DELETE |
| **DCL**(Data Control Language, 제어어) | **권한**·보안 제어 | GRANT, REVOKE (DENY는 SQL Server 전용) |
| **TCL**(Transaction Control Language) | 트랜잭션 확정·취소 | COMMIT, ROLLBACK, SAVEPOINT |

- SELECT를 DQL(질의어)로 따로 빼는 책도 있어요. 보기에 DQL이 없으면 DML이에요.
- **보기에 TCL이 없으면 COMMIT·ROLLBACK은 DCL**로 답하세요. 많은 수험서가 3분류(DDL·DML·DCL)를 쓰고 COMMIT·ROLLBACK을 DCL에 넣어요.

| 명령 | 분류 | 지우는 것 | WHERE | 롤백 |
|---|---|---|---|---|
| DELETE | DML | 행(조건 가능) | 가능 | 가능 |
| TRUNCATE | DDL | 행 전부(표 구조는 남음) | 불가 | 불가(수험서 기준. MySQL·Oracle은 자동 커밋) |
| DROP | DDL | 표 자체(구조까지) | 불가 | 불가 |

DROP과 REVOKE 등에 붙는 옵션 두 가지도 자주 나와요.

- **CASCADE**: 이걸 참조하는 것까지 함께 삭제·회수.
- **RESTRICT**: 참조하는 게 있으면 거부.

DDL을 실행하면 진행 중이던 트랜잭션이 자동 커밋되는 DBMS가 많아요. 자세한 건 [트랜잭션과 ACID](../../../db/transaction-acid/)를 보세요.

### 뷰

**뷰**(view)는 기본 테이블에서 SELECT로 만들어 낸 **가상 테이블**이에요. 데이터는 따로 저장하지 않고 정의(SELECT 문)만 저장해요.

```sql
-- 상담원용: 고객 표에서 이름·등급만 보이는 뷰
CREATE VIEW 고객요약 (이름, 등급)
AS SELECT 이름, 등급 FROM 고객 WHERE 탈퇴 = 'N'
WITH CHECK OPTION;   -- 뷰 조건(탈퇴='N')을 벗어나는 INSERT/UPDATE 거부
```

| 구분 | 내용 |
|---|---|
| 장점 | 복잡한 질의를 단순하게, **보안**(보여 줄 행·열만 공개, 뷰에만 권한 부여), **논리적 데이터 독립성**, 관리 편의 |
| 조회 | 모든 뷰에서 가능 |
| 변경(INSERT·UPDATE·DELETE) | 실제로는 기본 테이블에 반영되고, **제한적**으로만 가능 |
| 변경 불가 뷰 | 기본 테이블의 **기본키 열이 빠진** 뷰, **집계 함수**·**DISTINCT**·**GROUP BY**가 있는 뷰, 여러 테이블을 **조인**한 뷰(대부분) |
| 뷰 위의 뷰 | 만들 수 있어요 |
| DROP VIEW | 뷰만 사라지고 **기본 테이블은 그대로** |
| 기본 테이블 삭제 | 그 테이블로 만든 뷰는 쓸 수 없게 됨 |
| 정의 안의 ORDER BY | 수험서 기준 불가 |
| 단점(수험서) | **독립적인 인덱스를 가질 수 없음**, 변경 제약, **ALTER로 정의를 바꿀 수 없어 DROP 후 다시 CREATE** |

### GRANT / REVOKE

```sql
-- 권한 주기: TO
GRANT SELECT, UPDATE ON 고객 TO 김대리 WITH GRANT OPTION;
-- 권한 뺏기: FROM
REVOKE UPDATE ON 고객 FROM 김대리 CASCADE;
```

| 키워드 | 뜻 |
|---|---|
| GRANT … **TO** | 권한을 준다 |
| REVOKE … **FROM** | 권한을 뺏는다 |
| WITH GRANT OPTION | 받은 사람이 그 권한을 **다른 사람에게 다시 줄 수** 있게 |
| REVOKE … CASCADE | 그 사람이 다시 나눠 준 권한까지 **연쇄 회수** |
| REVOKE … RESTRICT | 다시 나눠 준 권한이 있으면 회수 거부 |
| 권한 종류 | SELECT, INSERT, UPDATE, DELETE, REFERENCES, ALL PRIVILEGES |

예: 관리자 → 김대리(WITH GRANT OPTION) → 김대리가 박사원에게 다시 부여. 이때 `REVOKE ... FROM 김대리 CASCADE`를 하면 박사원 권한도 같이 사라져요.

표준 교재 보충: 권한을 여러 개 묶은 **역할**(ROLE)을 만들어 한꺼번에 줄 수 있어요. Oracle은 시스템 권한·역할을 줄 때 WITH ADMIN OPTION을 써요.

:::caution[필기 정답 기준 vs 실무]
시험에서는 **수험서 기준**으로 답하세요. 실제 DBMS 문서와 다른 부분이 있어요.

| 항목 | 필기 정답 기준 | 실무(DBMS 문서) |
|---|---|---|
| GRANT·REVOKE 분류 | **DCL** | Oracle SQL Language Reference는 GRANT·REVOKE를 **DDL**로 분류 |
| COMMIT·ROLLBACK 분류 | TCL이 보기에 없으면 **DCL** | Oracle은 Transaction Control로 따로 분류 |
| 뷰 정의 변경 | **ALTER 불가** → DROP 후 재생성 | MySQL은 `ALTER VIEW` 지원, Oracle·MySQL 모두 `CREATE OR REPLACE VIEW`로 바꿈 |

면접에서 "뷰를 어떻게 수정하나요?"라고 물으면 실무 답(`CREATE OR REPLACE`)을, 필기 보기에서 "뷰는 ALTER로 정의를 변경할 수 있다"가 나오면 **틀린 보기**로 고르세요.
:::

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| E-R 다이어그램은 논리적 설계의 산출물 | **개념적** 설계 산출물 |
| 정규화는 물리적 설계 단계에서 한다 | **논리적** 설계 |
| 인덱스·저장 구조는 논리적 설계에서 정한다 | **물리적** 설계 |
| 개념적 설계는 특정 DBMS에 맞춰 진행 | 개념적 설계는 DBMS **독립** |
| 마름모는 속성, 타원은 관계 | 마름모 = **관계**, 타원 = **속성** |
| 이중 타원은 유도 속성 | 이중 타원 = **다중값**, 점선 타원 = 유도 |
| 2NF는 이행 종속 제거, 3NF는 부분 종속 제거 | 2NF = **부분**, 3NF = **이행** |
| DELETE는 DDL | DELETE = **DML**. TRUNCATE·DROP이 DDL |
| GRANT는 DML | GRANT·REVOKE = **DCL**(필기 기준) |
| 뷰를 삭제하면 기본 테이블도 삭제된다 | 기본 테이블은 **그대로** |
| 모든 뷰는 INSERT·UPDATE가 가능하다 | 집계·DISTINCT·GROUP BY·기본키 누락 뷰는 **변경 불가** |
| 뷰는 별도의 저장 공간에 데이터를 복사한다 | 데이터는 저장 안 함(**가상** 테이블) |
| 뷰는 ALTER VIEW로 정의를 바꾼다 | 필기 기준 **ALTER 불가**(DROP 후 재생성) |
| REVOKE 권한 ON 표 TO 사용자 | REVOKE는 **FROM**, GRANT가 TO |
| WITH GRANT OPTION은 권한 회수 옵션 | 받은 권한을 **다시 줄 수 있게** 하는 옵션. 연쇄 회수는 CASCADE |
| WHERE는 그룹 조건, HAVING은 행 조건 | WHERE = 행, HAVING = **그룹** 조건([SQL 기초와 JOIN](../../../db/sql-basics-join/)) |

① 요구 사항 분석 ② 개념적 설계 ③ 논리적 설계 ④ 물리적 설계

**정답: ②**

현실 세계를 개체·관계로 추상화해 E-R 다이어그램을 그리는 건 개념적 설계예요. 이 그림을 릴레이션으로 바꾸는 게 논리적 설계예요.
</details>

<details>
<summary>2. E-R 모델을 릴레이션 스키마로 변환하고 정규화를 수행하는 설계 단계는?</summary>

① 요구 사항 분석 ② 개념적 설계 ③ 논리적 설계 ④ 물리적 설계

**정답: ③**

목표 데이터 모델(관계형)에 맞춰 스키마를 만들고 정규화하는 건 논리적 설계예요. 인덱스나 레코드 배치를 정하는 물리적 설계와 헷갈리지 마세요.
</details>

<details>
<summary>3. 피터 첸의 E-R 다이어그램 기호와 의미를 바르게 짝지은 것은?</summary>

① 마름모 - 속성 ② 이중 타원 - 다중값 속성 ③ 점선 타원 - 키 속성 ④ 이중 사각형 - 관계

**정답: ②**

마름모는 관계, 점선 타원은 유도 속성(키 속성은 밑줄), 이중 사각형은 약한 개체예요.
</details>

<details>
<summary>4. (학번, 이름, 과목코드, 과목명) 표에서 어떤 과목을 듣던 유일한 학생의 행을 지웠더니 그 과목의 과목명 정보까지 사라졌다. 이 현상은?</summary>

① 삽입 이상 ② 갱신 이상 ③ 삭제 이상 ④ 함수 종속

**정답: ③**

지우고 싶지 않은 정보까지 같이 사라지는 건 삭제 이상이에요. 과목 정보를 따로 표로 나누면(정규화) 해결돼요.
</details>

<details>
<summary>5. 기본키가 (학번, 과목코드)인 수강 표에서 "과목코드 → 과목명" 종속이 있다. 이를 없애 도달하는 정규형은?</summary>

① 1NF ② 2NF ③ 3NF ④ BCNF

**정답: ②**

과목명이 기본키 전체가 아니라 일부(과목코드)만으로 결정되니 부분 함수 종속이에요. 부분 함수 종속을 없애면 2NF예요. 이행 종속(X→Y→Z) 제거가 3NF예요.
</details>

<details>
<summary>6. 다음 중 DDL에 속하지 않는 명령은?</summary>

① CREATE ② ALTER ③ TRUNCATE ④ DELETE

**정답: ④**

DELETE는 행을 지우는 DML이라 WHERE를 쓸 수 있고 롤백도 돼요. TRUNCATE는 행을 전부 지우지만 구조를 다루는 DDL로 분류해요.
</details>

<details>
<summary>7. 뷰(view)에 대한 설명으로 옳지 않은 것은?</summary>

① 뷰 위에 또 다른 뷰를 정의할 수 있다.

② 뷰를 삭제하면 그 뷰의 기본 테이블도 함께 삭제된다.

③ GROUP BY를 포함한 뷰는 INSERT·UPDATE가 제한된다.

④ 사용자에게 필요한 열만 보여 주어 보안에 도움이 된다.

**정답: ②**

DROP VIEW는 뷰 정의만 지우고 기본 테이블은 그대로 둬요. 반대로 기본 테이블을 지우면 그 뷰는 쓸 수 없게 돼요.
</details>

<details>
<summary>8. 관리자가 A에게 `GRANT SELECT ON 고객 TO A WITH GRANT OPTION`으로 권한을 주었고, A가 B에게 같은 권한을 주었다. 이후 관리자가 `REVOKE SELECT ON 고객 FROM A CASCADE`를 실행하면?</summary>

① A의 권한만 회수되고 B는 유지된다.

② A와 B의 권한이 모두 회수된다.

③ B가 권한을 갖고 있으므로 회수가 거부된다.

④ A의 권한은 유지되고 B의 권한만 회수된다.

**정답: ②**

CASCADE는 A가 다시 나눠 준 권한까지 연쇄로 회수해요. ③처럼 거부되는 건 RESTRICT를 썼을 때예요.
</details>

## 면접 질문

<details>
<summary>Q. 뷰를 쓰는 이유와 한계를 말해 주세요.</summary>

**답변(30초)** 뷰는 SELECT 결과를 이름 붙여 둔 가상 테이블이에요. 복잡한 조인을 숨겨 질의를 단순하게 하고, 필요한 열·행만 보여 주면서 뷰에만 권한을 줘서 보안에도 써요. 기본 테이블 구조가 바뀌어도 뷰 정의만 맞추면 되니 논리적 독립성도 생겨요. 다만 데이터를 저장하지 않아 매번 원래 쿼리가 실행되고, 집계나 조인이 들어간 뷰는 INSERT·UPDATE가 제한돼요.

**꼬리질문**
- Q. 뷰 정의는 어떻게 바꾸나요? → 실무에서는 `CREATE OR REPLACE VIEW`로 바꾸고 MySQL은 `ALTER VIEW`도 돼요. 필기 시험에서는 "ALTER 불가, DROP 후 재생성"이 정답 기준이에요.
</details>
