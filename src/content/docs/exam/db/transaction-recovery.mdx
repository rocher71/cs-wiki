:::tip[한 줄 요약]
장애가 나면 **커밋된 트랜잭션은 REDO, 커밋 안 된 트랜잭션은 UNDO**해요. **즉시 갱신은 REDO+UNDO, 지연 갱신은 REDO만, 그림자 페이징은 둘 다 필요 없어요.** 병행 제어의 **2PL은 직렬 가능성은 보장하지만 교착 상태는 막지 못해요.**
:::

:::note[처음이라면 여기까지]
① **트랜잭션**은 "계좌 이체"처럼 다 되거나 아예 안 돼야 하는 작업 묶음이에요.

② 서버가 갑자기 꺼지면 DB는 로그(작업 일지)를 보고, 끝까지 확정(커밋)된 작업은 **다시 하고(REDO)**, 확정 안 된 작업은 **없던 일로(UNDO)** 해요.

③ 여러 트랜잭션이 동시에 같은 데이터를 건드리면 값이 꼬여요. 그래서 **락**(lock, 사용 중 표시)을 걸어요. 락을 "모두 얻은 다음에만 풀기 시작"하는 규칙이 **2단계 로킹(2PL)**이에요.

④ "단계별 계산"의 체크포인트 예제를 따라 하고 연습 문제 1~5번부터 풀어 보세요. "심화:"는 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

은행 창구 직원이 하루 동안 처리한 일을 **업무 일지**에 적는다고 해 볼게요. "김씨 계좌 100 → 90으로 바꿈(이체 시작)", "이체 완료 도장" 같은 식으로요.

정전이 나서 컴퓨터가 꺼졌어요. 다시 켜면 일지를 봐요. "완료 도장"이 찍힌 이체는 장부에 반영이 안 됐을 수도 있으니 **다시 적고**(REDO), 도장이 없는 이체는 중간에 끊긴 거라 **원래 값으로 되돌려요**(UNDO).

일지를 처음부터 다 보면 오래 걸리니까, 중간중간 "여기까지는 장부에 확실히 반영함"이라고 **책갈피**를 꽂아요. 이게 **체크포인트**예요. 정전 뒤에는 책갈피 이후만 보면 돼요.

창구가 여러 개라 두 직원이 같은 계좌를 동시에 고치면 한쪽 작업이 덮여 사라져요. 그래서 "이 계좌 내가 쓰는 중" 팻말(락)을 걸어요.

단, 실제 DB는 일지(로그)를 장부(데이터 파일)보다 **먼저** 디스크에 써요(WAL). 그래야 정전 때 일지가 남아 있어요.

## 제대로 알기

### 트랜잭션과 ACID

**트랜잭션**(transaction)은 DB에서 한 번에 처리돼야 하는 논리적 작업 단위이고, 회복과 병행 제어의 단위예요. ACID 각각의 뜻과 실무 예는 [트랜잭션과 ACID](../../../db/transaction-acid/)에 있어요. 필기에서는 "어떤 성질을 어떤 기능이 지키나"가 나와요.

| 성질 | 지키는 DBMS 기능 |
|---|---|
| 원자성(Atomicity) | **회복** |
| 일관성(Consistency) | 병행 제어(+ 무결성 제약) |
| 격리성(Isolation) | **병행 제어** |
| 지속성(Durability) | **회복** |

- **commit**: 성공을 선언하고 결과를 확정해요.
- **rollback**: 실패를 선언하고 트랜잭션 전 상태로 되돌려요.

### 트랜잭션 상태 5가지

| 상태 | 뜻 |
|---|---|
| **활동**(active) | 실행 중 |
| **부분 완료**(partially committed) | 마지막 연산까지 실행했지만 **아직 commit 전** |
| **완료**(committed) | commit 실행, 결과가 확정됨 |
| **실패**(failed) | 장애로 더 진행할 수 없음 |
| **철회**(aborted) | rollback 실행, 시작 전 상태로 복구됨 |

```text
         마지막 연산            commit
 활동 ─────────────▶ 부분 완료 ─────────▶ 완료
  │                     │
  │ 장애                │ 장애
  ▼                     ▼
 실패 ◀─────────────────┘
  │ rollback
  ▼
 철회 ──▶ 재시작 또는 폐기
```

- 부분 완료에서도 실패로 갈 수 있어요(예: 디스크에 확정하다 장애).
- 실패와 철회는 다른 상태예요. 실패한 뒤 rollback을 해야 철회가 돼요.
- 표준 교재 보충: 끝나는 상태는 완료·철회 두 가지예요. 철회 뒤에는 하드웨어·소프트웨어 문제였다면 **재시작**, 트랜잭션 자체의 논리 오류였다면 **폐기**(kill)해요.

### 장애와 저장 장치

| 장애 | 원인 예 |
|---|---|
| 트랜잭션 장애 | 논리 오류, 잘못된 입력, 자원 초과, 데이터 없음 |
| 시스템 장애 | 하드웨어 결함으로 메인 메모리 내용 손실, 교착 상태 |
| 미디어 장애 | 디스크 헤드 손상 등 디스크 자체가 망가짐 |

| 저장 장치 | 예 | 장애 시 |
|---|---|---|
| 휘발성 | 메인 메모리 | 전원이 꺼지면 사라짐 |
| 비휘발성 | 디스크, 테이프 | 전원이 꺼져도 남음 |
| 안정 저장 장치 | 여러 사본을 둔 저장소(개념) | 어떤 장애에도 손실 없음 |

`input(X)`·`output(X)`는 디스크 ↔ 메모리 버퍼 사이, `read(X)`·`write(X)`는 버퍼 ↔ 프로그램 변수 사이의 이동이에요.

### 회복의 재료: 덤프와 로그

회복은 데이터를 **중복**해 두는 데서 시작해요.

- **덤프**(dump): DB 전체를 주기적으로 통째로 복사해 둔 것.
- **로그**(log): 변경마다 "바꾸기 전 값, 바꾼 후 값"을 기록한 일지.

```text
<T1, start>              T1 시작
<T1, X, 100, 90>         T1이 X를 100 → 90으로 바꿈 (old, new)
<T1, commit>             T1 커밋
```

| 연산 | 뜻 | 대상 |
|---|---|---|
| **REDO**(재실행) | 로그의 **새 값**으로 다시 반영 | **커밋된** 트랜잭션 |
| **UNDO**(취소) | 로그의 **이전 값**으로 되돌림 | **커밋 안 된** 트랜잭션 |

### 회복 기법 비교

| 기법 | 언제 DB에 반영 | 로그에 필요한 값 | 장애 시 커밋된 것 | 장애 시 미커밋 | 필요한 연산 |
|---|---|---|---|---|---|
| **즉시 갱신**(immediate update) | 실행 중 **바로** (로그 먼저) | old + new | REDO | **UNDO** | **REDO + UNDO** |
| **지연 갱신**(deferred update) | 부분 완료 후 **한꺼번에** | new만 | REDO | 아무것도 안 함(로그만 버림) | **REDO만**(NO-UNDO) |
| **그림자 페이징** | 새 페이지에 쓰고 커밋 때 교체 | 로그 불필요 | 이미 반영됨 | 그림자 테이블로 복귀 | **둘 다 불필요** |
| **미디어 회복** | | | 덤프로 복원 후 로그로 REDO | | 덤프 + REDO |

지연 갱신에 UNDO가 필요 없는 이유는 커밋 전에는 DB를 건드리지 않았기 때문이에요. 되돌릴 게 없어요.

### 검사 시점(체크포인트)

**체크포인트**(checkpoint)는 주기적으로 메모리의 로그와 변경 내용을 디스크에 내려 쓰고, 그 시점에 실행 중인 트랜잭션 목록 L과 함께 `<checkpoint L>`을 로그에 남기는 거예요. 장애가 나면 **가장 최근 체크포인트 이후만** 보면 돼서 회복 시간이 줄어요.

판정 규칙(즉시 갱신 기준):

| 트랜잭션 상황 | 처리 |
|---|---|
| 체크포인트 **전에** 커밋 | 아무것도 안 함(이미 디스크에 반영) |
| 체크포인트 뒤 ~ 장애 전에 커밋(체크포인트 전에 시작했어도) | **REDO** |
| 장애 때까지 커밋 없음 | **UNDO** |

### 그림자 페이징 (표준 교재 보충)

국내 수험서 본문에는 없지만 표준 교재에서 회복 기법으로 다뤄요.

1. 트랜잭션이 시작하면 **현재 페이지 테이블**을 복사해 **그림자 페이지 테이블**로 디스크에 보관해요.
2. 변경은 원래 페이지를 덮어쓰지 않고 **새 페이지**에 쓰고, 현재 페이지 테이블만 새 페이지를 가리키게 고쳐요.
3. **커밋**: 현재 페이지 테이블을 디스크에 기록하고 그림자를 버려요(포인터 교체).
4. **장애**: 현재 페이지 테이블을 버리고 그림자로 돌아가면 끝 → **UNDO·REDO 모두 불필요**.

단점은 페이지가 흩어지는 **데이터 단편화**, 안 쓰게 된 옛 페이지를 치우는 **가비지 수집**이 필요하다는 점이에요. 여러 트랜잭션이 동시에 도는 환경에서는 결국 로그·체크포인트와 함께 써야 해요.

### 병행 수행의 문제

**병행 수행**은 여러 트랜잭션의 연산을 번갈아(인터리빙) 실행하는 거예요. 제어하지 않으면 이런 문제가 생겨요.

| 문제 | 뜻 | 예 |
|---|---|---|
| **갱신 분실**(lost update) | 한 트랜잭션의 변경을 다른 트랜잭션이 덮어씀 | 둘 다 재고 10을 읽고 각각 1, 2를 빼서 9와 8을 씀 → 최종 8(정답 7) |
| **모순성**(inconsistency) | 일관성 없는 중간 상태를 읽어 모순된 결과 | 이체 중 X는 바뀌기 전, Y는 바뀐 후 값을 읽어 합계가 틀림 |
| **연쇄 복귀**(cascading rollback) | 철회된 트랜잭션이 바꾼 값을 읽은 트랜잭션도 줄줄이 철회 | 이미 커밋했다면 되돌릴 수도 없음 |
| 커밋되지 않은 의존성(표준 교재 용어) | 커밋 안 된 값을 읽음(= dirty read) | [격리 수준](../../../db/isolation-levels/) 참고 |

| 스케줄 | 뜻 | 정확성 |
|---|---|---|
| 직렬 스케줄 | 한 트랜잭션씩 차례로 | 항상 정확, 하지만 병행이 아님 |
| 비직렬 스케줄 | 번갈아 실행 | 보장 안 됨 |
| **직렬 가능 스케줄** | 번갈아 실행하지만 어떤 직렬 스케줄과 결과가 같음 | 정확. **병행 제어의 목표** |

### 로킹과 로킹 단위

| 락 | 허용 | 다른 트랜잭션과 함께 |
|---|---|---|
| **공용 락**(S, shared) | 읽기만 | 다른 S 락과는 동시 가능 |
| **전용 락**(X, exclusive) | 읽기 + 쓰기 | S·X 모두 불가 |

호환되는 짝은 **S–S 하나뿐**이에요.

**로킹 단위**(granularity)는 락을 거는 크기예요. DB 전체·릴레이션(테이블)·투플(행)·속성(열)까지 가능해요.

| 로킹 단위 | 병행성 | 락 개수 | 제어 | 오버헤드 |
|---|---|---|---|---|
| **크게**(DB·테이블) | **낮음** | 적음 | 쉬움 | **작음** |
| **작게**(행·열) | **높음** | 많음 | 복잡 | **큼** |

S/X 락이 실제 MySQL에서 어떻게 보이는지, 데드락 사례는 [락](../../../db/locks/)을 보세요.

### 2단계 로킹 (2PL)

락만 건다고 직렬 가능성이 보장되진 않아요. 너무 일찍 풀면 다른 트랜잭션이 중간 상태를 볼 수 있어요. 그래서 **2단계 로킹**(two-phase locking)은 두 단계로 나눠요.

| 단계 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| **확장 단계**(growing) | lock | unlock |
| **축소 단계**(shrinking) | unlock | lock |

- 첫 unlock 전에 필요한 lock을 **전부** 얻어야 해요.
- 2PL은 **직렬 가능성을 보장**해요.
- 2PL은 **교착 상태를 막지 못해요**. 락을 오래 쥘수록 서로 기다리는 상황이 오히려 늘 수 있어요.

### 타임스탬프 순서와 낙관적 기법

| 기법 | 방식 | 교착 상태 | 잘 맞는 환경 |
|---|---|---|---|
| **2PL**(로킹) | 쓰기 전에 락을 얻음. 충돌하면 **기다림** | **생길 수 있음** | 충돌이 잦을 때 |
| **타임스탬프 순서**(표준 교재 보충) | 시작 순서대로 타임스탬프를 주고, 그 순서로 실행된 것처럼 강제. 먼저 시작한(타임스탬프가 작은) 트랜잭션이 나중 트랜잭션이 이미 읽거나 쓴 데이터를 뒤늦게 건드리면 그 트랜잭션을 **철회 후 재시작** | **없음**(락을 안 씀) | |
| **낙관적 기법**(검증, 표준 교재 보충) | 일단 지역 사본에서 실행 → 커밋 직전에 검증 → 실패하면 철회·재시작 | 없음 | **충돌이 드물고 읽기가 많을 때** |
| **다중 버전**(MVCC) | 데이터 버전을 여러 개 두고 타임스탬프로 맞는 버전을 읽음 | | 읽기가 많을 때(읽기가 기다리지 않음) |

- 낙관적 기법의 단계 순서: **판독**(read) → **검증**(validation) → **기록**(write).
- 타임스탬프 순서는 데이터마다 마지막으로 읽은 시각(read_TS)·쓴 시각(write_TS)을 기록해 두고 비교해요.

### 교착 상태와 기아

- **교착 상태**: 두 트랜잭션이 서로 상대가 가진 락이 풀리기를 기다려 둘 다 못 움직임 → 예방하거나, 탐지 후 하나를 철회해 회복해요. 운영체제 쪽 교착 4조건은 [동기화·교착상태](../../os/sync-deadlock/)를 보세요.
- **기아**: 특정 트랜잭션만 계속 락을 못 얻고 기다림 → 먼저 요청한 순서대로 주는 공평한 대기로 막아요.

### 심화: 2PL 변형과 로크 전환 (표준 교재 보충)

| 변형 | 규칙 | 효과 |
|---|---|---|
| **엄격**(strict) 2PL | X 락을 커밋·철회 때까지 쥠 | **연쇄 복귀 방지** |
| **강**(rigorous) 2PL | 모든 락을 커밋 때까지 쥠 | 커밋 순서 = 직렬 순서 |
| **보수적**(conservative) 2PL | 시작 전에 필요한 락을 한꺼번에 얻음 | **교착 상태 없음** |

- 로크 **상승**(upgrade): S → X. 그 데이터에 S 락을 가진 게 자기 하나일 때만 가능해요.
- 로크 **하강**(downgrade): X → S.
- 실무 DB(InnoDB)의 크래시 복구는 redo·undo 로그를 둘 다 쓰고 로그를 먼저 쓰는 WAL 방식이라, 필기의 **즉시 갱신**에 가까워요.

## 단계별 계산

### 예제: 체크포인트 이후 REDO·UNDO 판정

즉시 갱신을 쓰는 시스템이에요. 시각 10에 체크포인트, 시각 20에 시스템 장애가 났어요.

| 트랜잭션 | 시작 | 커밋 |
|---|---|---|
| T1 | 1 | 5 |
| T2 | 3 | 15 |
| T3 | 4 | 없음 |
| T4 | 12 | 18 |
| T5 | 14 | 없음 |

```text
시각  0    5    10(체크포인트)   15   20(장애)
T1    |-----C     :                    :
T2       |--------:----------C         :
T3        |-------:--------------------:  (커밋 없음)
T4                :     |--------C     :
T5                :       |------------:  (커밋 없음)
```

1. **체크포인트 전에 커밋**한 트랜잭션을 찾아요 → T1(5). 체크포인트 때 이미 디스크에 반영됐으니 **할 일 없음**.
2. **체크포인트 뒤 ~ 장애 전에 커밋**한 트랜잭션 → T2(15), T4(18). T2는 체크포인트 전에 시작했지만 커밋이 뒤라서 포함돼요 → **REDO**.
3. **장애 때까지 커밋 없는** 트랜잭션 → T3, T5 → **UNDO**.

| 트랜잭션 | 즉시 갱신 | 지연 갱신 |
|---|---|---|
| T1 | 할 일 없음 | 할 일 없음 |
| T2 | **REDO** | **REDO** |
| T3 | **UNDO** | 무시(DB에 안 썼으니 되돌릴 것 없음) |
| T4 | **REDO** | **REDO** |
| T5 | **UNDO** | 무시 |

로그로만 판정하면 이렇게 해요. 체크포인트 이후 로그(와 체크포인트의 실행 중 목록 L)를 훑어서 `commit`이 보이면 REDO 목록, `start`만 있으면 UNDO 목록에 넣어요.

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 지연 갱신은 UNDO가 필요하다 | 지연 갱신 = **REDO만**(NO-UNDO) |
| 즉시 갱신은 REDO만 필요하다 | 즉시 갱신 = **REDO + UNDO** |
| 그림자 페이징은 UNDO가 필요하다 | 그림자 페이징 = **UNDO·REDO 모두 불필요**, 로그도 불필요(단일 트랜잭션 기준) |
| 커밋된 트랜잭션은 UNDO, 미커밋은 REDO | 거꾸로. 커밋 = **REDO**, 미커밋 = **UNDO** |
| 체크포인트 전에 커밋한 트랜잭션도 REDO | 체크포인트 전 커밋은 **제외** |
| 부분 완료는 commit이 끝난 상태다 | 부분 완료 = 마지막 연산 직후, **commit 전** |
| 실패 상태와 철회 상태는 같다 | 실패 후 **rollback**을 해야 철회 |
| 원자성은 병행 제어가 보장한다 | 원자성·지속성 = **회복**, 격리성 = **병행 제어** |
| 2PL은 교착 상태를 방지한다 | 2PL은 직렬 가능성 보장 O, **교착 방지 X** |
| 2PL은 연쇄 복귀를 막는다 | 기본 2PL은 못 막음. **엄격 2PL**이어야 막음 |
| 2PL 확장 단계에서 unlock할 수 있다 | 확장 = lock만, 축소 = unlock만 |
| 타임스탬프 순서 기법에서 교착 상태가 발생한다 | 락을 안 써서 **교착 없음** |
| 로킹 단위가 클수록 병행성이 높다 | 클수록 병행성 **낮음**, 오버헤드 **작음** |
| 로킹 단위가 작을수록 오버헤드가 작다 | 작을수록 오버헤드 **큼**, 병행성 높음 |
| 공용 락과 전용 락은 동시에 걸 수 있다 | 호환은 **S–S만** |
| 낙관적 기법은 검증 → 판독 → 기록 | **판독 → 검증 → 기록** |
| 갱신 분실 = 철회가 다른 트랜잭션에 전파 | 그건 **연쇄 복귀**. 갱신 분실 = 덮어쓰기 |

## 연습 문제

<details>
<summary>1. 트랜잭션이 마지막 연산까지 실행했지만 아직 commit 연산을 실행하기 전의 상태는?</summary>

① 활동 ② 부분 완료 ③ 완료 ④ 철회

**정답: ②**

마지막 연산 직후, commit 전은 부분 완료예요. commit까지 실행해야 완료예요. 부분 완료에서도 장애가 나면 실패로 갈 수 있어요.
</details>

<details>
<summary>2. 트랜잭션의 원자성과 지속성을 보장하기 위한 DBMS의 기능은?</summary>

① 병행 제어 ② 회복 ③ 무결성 제약 ④ 보안

**정답: ②**

다 되거나 아예 안 되게(원자성), 커밋한 건 장애 뒤에도 남게(지속성) 하는 건 회복 기능이에요. 격리성은 병행 제어가 지켜요.
</details>

<details>
<summary>3. 지연 갱신(deferred update) 회복 기법에 대한 설명으로 옳은 것은?</summary>

① 장애가 나면 REDO와 UNDO를 모두 해야 한다.

② 트랜잭션 실행 중에 변경 내용을 DB에 바로 반영한다.

③ 커밋 전 장애가 나면 로그만 버리면 되므로 UNDO가 필요 없다.

④ 로그에 변경 전 값과 변경 후 값을 모두 기록해야 한다.

**정답: ③**

지연 갱신은 부분 완료 뒤에야 DB에 반영하니, 커밋 전에는 되돌릴 게 없어요. ①·②·④는 즉시 갱신의 설명이에요.
</details>

<details>
<summary>4. 로그를 쓰지 않고 현재 페이지 테이블과 그림자 페이지 테이블을 두어, 장애 시 그림자 테이블로 되돌리는 회복 기법에서 필요한 연산은?</summary>

① REDO만 ② UNDO만 ③ REDO와 UNDO ④ 둘 다 필요 없음

**정답: ④**

그림자 페이징은 커밋 전 변경이 새 페이지에만 있으니 그림자 테이블로 돌아가면 끝이에요. 커밋된 건 이미 현재 테이블로 교체됐고요. 그래서 UNDO·REDO 모두 필요 없어요.
</details>

<details>
<summary>5. 2단계 로킹(2PL) 규약에 대한 설명으로 옳은 것은?</summary>

① 교착 상태가 절대 발생하지 않는다.

② 직렬 가능성을 보장한다.

③ 확장 단계에서는 lock과 unlock을 모두 할 수 있다.

④ 축소 단계에서 새로운 lock을 얻을 수 있다.

**정답: ②**

2PL은 직렬 가능성을 보장하지만 교착 상태는 막지 못해요. 확장 단계는 lock만, 축소 단계는 unlock만 할 수 있어요.
</details>

<details>
<summary>6. 로킹 단위에 대한 설명으로 옳은 것은?</summary>

① 로킹 단위가 크면 병행성이 높아진다.

② 로킹 단위가 작으면 락 관리 오버헤드가 줄어든다.

③ 로킹 단위가 크면 락 개수가 적어 제어가 쉽다.

④ 로킹 단위는 데이터베이스 전체로만 정할 수 있다.

**정답: ③**

크게 잡으면 락 개수가 적어 제어가 쉽고 오버헤드도 작지만, 한 번에 많이 잠가서 병행성이 낮아져요. 작게 잡으면 그 반대예요. 단위는 DB 전체부터 속성까지 고를 수 있어요.
</details>

<details>
<summary>7. 두 트랜잭션이 재고 X = 10을 함께 읽은 뒤, T1은 X − 3 = 7을, T2는 X − 5 = 5를 차례로 기록했다. 최종 X는 5이다. 이 문제는?</summary>

① 갱신 분실 ② 연쇄 복귀 ③ 모순성 ④ 교착 상태

**정답: ①**

정답은 10 − 3 − 5 = 2여야 하는데 T2가 T1의 변경을 덮어써서 5가 됐어요. 이게 갱신 분실이에요. X에 전용 락을 걸어 T2가 T1이 끝난 값을 읽게 하면 막을 수 있어요.
</details>

<details>
<summary>8. 즉시 갱신 시스템에서 시각 10에 체크포인트, 시각 20에 장애가 났다. T1(시작 2·커밋 12), T2(시작 5·커밋 9), T3(시작 11·커밋 없음), T4(시작 13·커밋 17), T5(시작 8·커밋 없음)일 때 REDO 대상은?</summary>

① T2 ② T1, T4 ③ T1, T2, T4 ④ T3, T5

**정답: ②**

- T2: 체크포인트(10) 전인 9에 커밋 → 할 일 없음.
- T1: 체크포인트 전에 시작했지만 12에 커밋 → **REDO**.
- T4: 17에 커밋 → **REDO**.
- T3, T5: 커밋 없음 → UNDO.

③은 체크포인트 전 커밋까지 넣은 실수, ④는 UNDO 대상이에요.
</details>

## 면접 질문

<details>
<summary>Q. 2단계 로킹(2PL)이 무엇이고, 왜 교착 상태가 생길 수 있나요?</summary>

**답변(30초)** 2PL은 트랜잭션이 락을 얻기만 하는 확장 단계와 풀기만 하는 축소 단계로 나눠, 한 번이라도 락을 풀면 더는 새 락을 얻지 못하게 하는 규약이에요. 이렇게 하면 동시에 실행해도 어떤 순서로 하나씩 실행한 것과 결과가 같아져서 직렬 가능성이 보장돼요. 하지만 락을 쥔 채 다른 락을 기다리기 때문에, T1은 A를 잡고 B를, T2는 B를 잡고 A를 기다리면 교착 상태가 생겨요. 그래서 DB는 교착을 탐지해 한쪽을 롤백해요.

**꼬리질문**
- Q. 낙관적 동시성 제어와 차이는? → 2PL은 미리 락을 거는 비관적 방식이고, 낙관적 방식은 락 없이 실행한 뒤 커밋 직전에 충돌을 검사해 실패하면 재시도해요. 충돌이 드물고 읽기가 많을 때 낙관적 방식이 유리해요. 실무 구현(버전 컬럼)은 [락](../../../db/locks/) 페이지에 있어요.
</details>
