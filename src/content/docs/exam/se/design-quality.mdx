:::tip[한 줄 요약]
좋은 설계는 **결합도는 약할수록(낮을수록), 응집도는 강할수록(높을수록)** 좋아요. 결합도는 강→약 **내용 > 공통 > 외부 > 제어 > 스탬프 > 자료**, 응집도는 강→약 **기능 > 순차 > 교환 > 절차 > 시간 > 논리 > 우연**이에요.
:::

:::note[처음이라면 여기까지]
① **결합도**는 모듈과 모듈이 서로 얼마나 엮여 있는지, **응집도**는 한 모듈 안의 내용이 한 가지 목적으로 얼마나 잘 뭉쳐 있는지예요.

② 결합도는 **자료** 결합(값만 주고받음)이 가장 좋고 **내용** 결합(남의 속을 직접 건드림)이 가장 나빠요. 응집도는 **기능** 응집이 가장 좋고 **우연** 응집이 가장 나빠요.

③ 순서 문제는 보기가 "강→약"인지 "약→강"인지부터 확인하세요. 방향을 거꾸로 읽어서 틀리는 경우가 가장 많아요.

④ 아래 순서 표 두 개와 연습 문제 1~4번을 먼저 보세요. UML·패턴·ISO는 표만 외워도 돼요.
:::

## 쉽게 이해하기

회사 부서로 생각해 볼게요. **결합도**는 부서끼리 얼마나 얽혀 있는지예요. 영업팀이 회계팀 장부를 직접 열어 숫자를 고치면(내용 결합) 회계팀이 장부 양식만 바꿔도 영업팀이 망가져요. 반대로 "이번 달 매출 숫자 하나만 주세요"처럼 필요한 값만 주고받으면(자료 결합) 서로 영향을 덜 받아요.

**응집도**는 한 부서 안의 일이 얼마나 한 목적에 맞는지예요. 급여팀이 급여 계산만 하면(기능 응집) 일이 분명해요. 그런데 "남는 일 다 모아 둔 부서"에 택배 수령, 회식 예약, 서버 점검이 섞여 있으면(우연 응집) 누구도 그 부서가 뭘 하는지 설명하지 못해요.

그래서 목표는 하나예요. 부서끼리는 **느슨하게**, 부서 안은 **똘똘 뭉치게**. 이러면 한 곳을 고쳐도 다른 곳이 덜 깨져요.

단, 실제 코드에서는 결합도를 0으로 만들 수 없어요. 모듈이 협력하려면 어느 정도 연결은 필요하고, 목표는 "필요한 만큼만" 연결하는 거예요.

## 제대로 알기

### 결합도 6단계 (강 = 나쁨 → 약 = 좋음)

| 순서 | 결합도 | 무엇을 주고받나 | 짧은 예 |
|---|---|---|---|
| 1 (가장 나쁨) | **내용**(content) | 다른 모듈의 **내부** 코드·데이터를 직접 참조·변경 | A가 B 안의 변수를 직접 고치거나 B 함수 중간으로 goto 점프 |
| 2 | **공통**(common) | **전역 변수**를 여러 모듈이 같이 씀 | `static Map config`를 여러 클래스가 고침. 하나 바꾸면 전부 영향 |
| 3 | **외부**(external) | 외부에서 정한 데이터 형식·통신 규약·장치 인터페이스를 공유 | 두 모듈이 같은 외부 파일 포맷이나 장비 프로토콜에 묶임 |
| 4 | **제어**(control) | 상대의 처리 흐름을 정하는 **제어 플래그** | `process(order, type)`에서 type 값으로 상대 안의 분기를 고름 |
| 5 | **스탬프**(stamp) | 구조체·레코드·배열 같은 **자료 구조 통째로** | 주문 객체 전체를 넘기는데 받는 쪽은 id만 씀 |
| 6 (가장 좋음) | **자료**(data) | 필요한 **값만** 매개변수로 | `calcTax(price)`처럼 숫자 하나만 넘김 |

외우는 요령: 좋은 쪽부터(약→강) 앞 글자를 따서 **"데스제외공내"**(데이터·스탬프·제어·외부·공통·내용)로 외우고, 문제가 강→약이면 거꾸로 읽어요.

### 응집도 7단계 (강 = 좋음 → 약 = 나쁨)

| 순서 | 응집도 | 묶인 이유 | 짧은 예 |
|---|---|---|---|
| 1 (가장 좋음) | **기능**(functional) | 딱 **하나의 기능** | 제곱근 계산 함수 |
| 2 | **순차**(sequential) | 앞 요소의 **출력이 다음 요소의 입력** | 파일 읽기 → 형식 변환 → 저장 |
| 3 | **교환**(communicational) | **같은 입력·출력 데이터**를 쓰는 서로 다른 기능. 순서는 상관없음 | 같은 주문 레코드로 합계 계산 + 송장 출력 |
| 4 | **절차**(procedural) | 정해진 **순서**대로 실행되지만 데이터 전달은 없음 | "권한 확인 → 로그 남기기 → 화면 갱신"을 순서만 맞춰 묶음 |
| 5 | **시간**(temporal) | 같은 **시점**에 실행돼서 | 프로그램 시작 시 하는 초기화를 모두 모은 모듈 |
| 6 | **논리**(logical) | 비슷한 **종류**라서. 플래그로 하나 골라 실행 | 모든 입출력 처리를 한 모듈에 넣고 코드 값으로 골라 실행 |
| 7 (가장 나쁨) | **우연**(coincidental) | 관련 없음, 우연히 같이 있음 | 날짜·암호화·문자열 함수가 뒤섞인 `CommonUtil` |

외우는 요령: 나쁜 쪽부터(약→강) **"우논시절교순기"**(우연·논리·시간·절차·교환·순차·기능). 교환 응집은 **통신적·정보적** 응집이라고도 불러요(번역 차이일 뿐 같은 것).

### 헷갈리는 짝 구분하기

| 짝 | 구분 방법 |
|---|---|
| 제어 vs 스탬프 결합 | **플래그**(흐름 지시)를 넘기면 제어, **자료 구조 통째**면 스탬프 |
| 순차 vs 절차 응집 | 앞 결과가 다음 입력으로 **전달되면** 순차, **순서만** 있으면 절차 |
| 시간 vs 논리 응집 | **시점**이 같아서 묶었으면 시간, **종류**가 같아서 묶었으면 논리 |
| 공통 vs 외부 결합 | 내부 **전역 변수** 공유면 공통, **외부**에서 정한 형식·장치 공유면 외부 |

결합도를 5단계로 쓰는 교재도 있어요. 그때는 보통 외부 결합이 빠진 거예요. 정처기 계열 수험서는 6단계로 나와요.

### 설계 원리

| 원리 | 뜻 |
|---|---|
| **분할과 정복** | 큰 문제를 작은 문제로 나눠 풀기 |
| **추상화** | 핵심만 남기고 세부를 숨기기. 과정 추상화(함수), 데이터 추상화(클래스·추상 자료형), 제어 추상화(고급 언어 문장이 기계어 세부를 숨김) |
| **단계적 분해** | 위에서부터 조금씩 구체화(하향식) |
| **모듈화** | 시스템을 독립적인 부품(모듈)으로 나누기. 너무 잘게 나누면 연결 비용이 늘어요 |
| **정보 은닉** | 바뀌기 쉬운 결정을 모듈 안에 숨기고 정해진 인터페이스로만 접근하게 하기 |

- 설계가 상세해질수록 추상화 수준은 **낮아져요**(점점 구체적).
- **정보 은닉**(Parnas 1972)을 하면 숨긴 부분을 바꿔도 다른 모듈이 영향을 덜 받아요. 객체지향의 **캡슐화**가 이걸 구현하는 방법이에요. [추상 클래스와 인터페이스](../../../oop/abstract-interface/)도 같이 보면 좋아요.
- 클래스 수준 설계 원칙(SRP·OCP·LSP·ISP·DIP)은 [SOLID](../../../oop/solid/)에 정리돼 있어요.

### 팬인과 팬아웃

- **팬인**(fan-in): 그 모듈을 **부르는** 상위 모듈 수예요. "나를 부르는 수".
- **팬아웃**(fan-out): 그 모듈이 **부르는** 하위 모듈 수예요. "내가 부르는 수".
- 공통 모듈은 팬인이 높을수록 재사용이 잘 된다는 뜻이고, 팬아웃이 너무 크면 그 모듈이 복잡하다는 신호예요.

예제: 호출 구조가 Main → A, B, C / A → D, E / B → E / C → E, F 일 때

| 모듈 | 팬인(나를 부르는 수) | 팬아웃(내가 부르는 수) |
|---|---|---|
| Main | 0 | 3 (A, B, C) |
| A | 1 (Main) | 2 (D, E) |
| B | 1 (Main) | 1 (E) |
| C | 1 (Main) | 2 (E, F) |
| D | 1 (A) | 0 |
| E | **3** (A, B, C) | 0 |
| F | 1 (C) | 0 |

E는 세 모듈이 같이 쓰는 공통 모듈이라 팬인이 가장 커요. 팬아웃이 가장 큰 건 Main(3)이에요.

### UML 다이어그램 분류

**UML**(Unified Modeling Language)은 Rumbaugh(OMT)·Booch·Jacobson(OOSE)의 방법을 합친 모델링 언어로, OMG가 표준으로 관리해요.

| 분류 | 다이어그램 | 보여 주는 것 |
|---|---|---|
| **구조**(정적) | 클래스, 객체, 컴포넌트, 배치, 패키지, 복합 구조 (프로파일) | 무엇으로 이루어졌나 |
| **행위**(동적) | 유스케이스, 활동, 상태 머신 | 무엇을 어떻게 하나 |
| 행위 중 **상호작용** | 시퀀스, 커뮤니케이션(UML 1의 협업), 타이밍, 상호작용 개요 | 객체끼리 메시지를 어떻게 주고받나 |

요령: 이름에 **시간·순서·상태·행동**이 느껴지면 행위(시퀀스·상태·활동·유스케이스), **부품·배치·묶음**이 느껴지면 구조(클래스·컴포넌트·배치·패키지)예요.

### UML 관계 기호

| 관계 | 기호 | 뜻 |
|---|---|---|
| 연관 | 실선(방향 있으면 화살표) | 서로 알고 지냄 |
| **집합**(aggregation) | 실선 + **빈 마름모**(전체 쪽) | 부분이 따로 살 수 있음(팀과 선수) |
| **합성**(composition) | 실선 + **채운 마름모**(전체 쪽) | 전체가 사라지면 부분도 사라짐(집과 방) |
| 일반화(상속) | 실선 + 빈 삼각 화살표(부모 쪽) | is-a 관계 |
| 실체화 | 점선 + 빈 삼각 화살표 | 인터페이스 구현 |
| 의존 | 점선 + 열린 화살표 | 잠깐 사용(매개변수 등) |

유스케이스 관계: **포함**(include)은 항상 같이 수행하는 필수 기능이고 화살표가 기본 → 포함 방향이에요. **확장**(extend)은 조건에 따라 하는 선택 기능이고 화살표가 확장 → 기본 방향이에요. 두 화살표 방향이 반대라는 게 함정이에요.

### GoF 디자인 패턴 분류(23개)

| 분류 | 개수 | 패턴 | 자세히 |
|---|---|---|---|
| **생성** | 5 | 싱글턴, 팩토리 메서드, 추상 팩토리, 빌더, 프로토타입 | [생성 패턴](../../../oop/patterns-creational/) |
| **구조** | 7 | 어댑터, 브리지, 컴포지트, 데코레이터, 퍼사드, 플라이웨이트, 프록시 | [구조 패턴](../../../oop/patterns-structural/) |
| **행위** | 11 | 책임 연쇄, 커맨드, 인터프리터, 반복자, 중재자, 메멘토, 옵서버, 상태, 전략, 템플릿 메서드, 방문자 | [행위 패턴](../../../oop/patterns-behavioral/) |

- 생성 = 객체를 **만드는** 방법, 구조 = 클래스·객체를 **조립하는** 방법, 행위 = 객체끼리 **책임을 나누고 소통하는** 방법이에요.
- 구조 7개는 앞 글자를 따서 "어브컴데퍼플프"(이 위키의 자체 암기법)로 외워 두면 편해요. 나머지는 이름에 생성 느낌(만들기·복제·하나만)이 없으면 행위로 보면 대부분 맞아요.

### ISO 품질 특성: 9126에서 25010으로

| ISO/IEC 9126 (6특성) | ISO/IEC 25010:2011 (8특성) | ISO/IEC 25010:2023 (9특성) |
|---|---|---|
| 기능성 | 기능 적합성 | 기능 적합성 |
| 효율성 | 성능 효율성 | 성능 효율성 |
| - | **호환성**(새로 생김) | 호환성 |
| 사용성 | 사용성 | **상호작용 능력**(사용성 이름 바뀜) |
| 신뢰성 | 신뢰성 | 신뢰성 |
| - | **보안성**(독립 특성으로) | 보안성 |
| 유지보수성 | 유지보수성 | 유지보수성 |
| 이식성 | 이식성 | 유연성(이식성을 넓힌 것) |
| - | - | 안전성(새로 생김) |

- 9126 6특성 외우기: 기능성·신뢰성·사용성·효율성·유지보수성·이식성. 9126에서 보안은 독립 특성이 아니라 기능성 아래 세부 특성이었어요.
- 25010(2011)이 9126을 대체하면서 **호환성과 보안성**이 독립 특성으로 추가됐어요. 시험은 대부분 2011판 8특성 기준이에요.
- 2023판 표: 9특성 구성과 "상호작용 능력" 명칭은 ISO 25000 포털에서 확인했고, 유연성·안전성 등 나머지 명칭은 **표준 지식**으로 보충했어요(원문은 유료라 미열람).

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 좋은 설계는 결합도와 응집도가 모두 높다 | 결합도는 **낮게**, 응집도는 **높게** |
| 결합도(강→약): 자료 > 스탬프 > 제어 > … | 그건 약→강. 강→약은 **내용 > 공통 > 외부 > 제어 > 스탬프 > 자료** |
| 가장 바람직한 결합도는 스탬프 결합이다 | **자료** 결합 |
| 가장 바람직한 응집도는 순차적 응집이다 | **기능적** 응집(순차는 두 번째) |
| 제어 플래그를 넘기는 것은 스탬프 결합이다 | **제어** 결합 |
| 초기화 작업을 모은 모듈은 논리적 응집이다 | 같은 시점이라 **시간적** 응집 |
| 교환적 응집과 통신적 응집은 다른 단계다 | 같은 단계(교환 = 통신 = 정보적) |
| 팬인은 그 모듈이 호출하는 하위 모듈 수다 | 그건 팬아웃. 팬인은 **나를 호출하는** 수 |
| 어댑터·브리지·컴포지트는 행위 패턴이다 | **구조** 패턴 |
| 옵서버·전략은 구조 패턴이다 | **행위** 패턴 |
| 싱글턴·빌더는 구조 패턴이다 | **생성** 패턴 |
| 시퀀스·상태 다이어그램은 구조 다이어그램이다 | **행위** 다이어그램 |
| 컴포넌트·배치 다이어그램은 행위 다이어그램이다 | **구조** 다이어그램 |
| 합성은 빈 마름모, 집합은 채운 마름모 | 집합 = **빈** 마름모, 합성 = **채운** 마름모 |
| ISO 9126 품질 특성에 보안성이 있다 | 9126에는 없음(기능성의 하위). 25010에서 독립 |
| 상세 설계로 갈수록 추상화 수준이 높아진다 | **낮아짐**(구체화) |

## 연습 문제

<details>
<summary>1. 결합도를 약한 것(바람직)부터 강한 것 순서로 바르게 나열한 것은?</summary>

① 자료 → 스탬프 → 제어 → 외부 → 공통 → 내용

② 자료 → 제어 → 스탬프 → 공통 → 외부 → 내용

③ 내용 → 공통 → 외부 → 제어 → 스탬프 → 자료

④ 스탬프 → 자료 → 제어 → 외부 → 공통 → 내용

**정답: ①**

"데스제외공내" 순서예요. ③은 강→약 순서라 방향이 반대예요. 문제의 "약한 것부터"를 먼저 확인하세요.
</details>

<details>
<summary>2. 응집도가 가장 높은(바람직한) 것부터 순서대로 나열할 때 세 번째에 오는 것은?</summary>

① 순차적 응집 ② 교환적 응집 ③ 절차적 응집 ④ 시간적 응집

**정답: ②**

강→약: 기능 > 순차 > **교환** > 절차 > 시간 > 논리 > 우연. 세 번째는 교환(통신적) 응집이에요.
</details>

<details>
<summary>3. 모듈 A가 모듈 B를 호출하면서 "1이면 저장, 2면 삭제"처럼 B 내부의 처리 흐름을 결정하는 값을 넘긴다. 이 결합도는?</summary>

① 자료 결합 ② 스탬프 결합 ③ 제어 결합 ④ 공통 결합

**정답: ③**

상대의 흐름을 정하는 플래그를 넘기니 제어 결합이에요. 호출한 쪽이 B의 내부 로직을 알아야 해서 정보 은닉에 어긋나요. 저장·삭제를 별도 메서드로 나누면 자료 결합으로 낮출 수 있어요.
</details>

<details>
<summary>4. 프로그램 시작 시 실행되는 변수 초기화, 로그 파일 열기, 설정 읽기를 한 모듈에 모았다. 이 모듈의 응집도는?</summary>

① 기능적 응집 ② 논리적 응집 ③ 시간적 응집 ④ 우연적 응집

**정답: ③**

세 작업의 공통점은 "같은 시점(시작할 때)에 실행된다"는 것뿐이라 시간적 응집이에요. 종류가 같아서 묶고 플래그로 골라 실행하면 논리적 응집이에요.
</details>

<details>
<summary>5. 호출 구조가 M → A, B / A → C, D / B → D / D → E 일 때, 모듈 D의 팬인과 모듈 A의 팬아웃은?</summary>

① D 팬인 1, A 팬아웃 2 ② D 팬인 2, A 팬아웃 1 ③ D 팬인 2, A 팬아웃 2 ④ D 팬인 1, A 팬아웃 1

**정답: ③**

D를 부르는 모듈은 A와 B라서 팬인 2예요. A가 부르는 모듈은 C와 D라서 팬아웃 2예요. D가 E를 부르는 건 D의 팬아웃(1)이지 팬인이 아니에요.
</details>

<details>
<summary>6. GoF 디자인 패턴 중 구조(structural) 패턴이 아닌 것은?</summary>

① 어댑터(Adapter) ② 데코레이터(Decorator) ③ 퍼사드(Facade) ④ 옵서버(Observer)

**정답: ④**

옵서버는 한 객체의 변화를 여러 객체에게 알리는 **행위** 패턴이에요. 어댑터·데코레이터·퍼사드는 객체를 조립하는 구조 패턴이에요.
</details>

<details>
<summary>7. UML 다이어그램 중 행위(동적) 다이어그램이 아닌 것은?</summary>

① 시퀀스 다이어그램 ② 상태 머신 다이어그램 ③ 배치 다이어그램 ④ 활동 다이어그램

**정답: ③**

배치 다이어그램은 소프트웨어가 어떤 하드웨어(노드)에 놓이는지 보여 주는 **구조** 다이어그램이에요.
</details>

<details>
<summary>8. ISO/IEC 9126과 비교해 ISO/IEC 25010(2011)에서 독립 품질 특성으로 새로 추가된 것만 묶은 것은?</summary>

① 호환성, 보안성 ② 이식성, 신뢰성 ③ 사용성, 효율성 ④ 유지보수성, 호환성

**정답: ①**

9126의 6특성(기능성·신뢰성·사용성·효율성·유지보수성·이식성)에 호환성과 보안성이 더해져 8특성이 됐어요. 효율성은 이름이 "성능 효율성"으로 바뀐 거라 새 특성이 아니에요.
</details>

## 면접 질문

<details>
<summary>Q. 결합도와 응집도가 무엇이고, 왜 "낮은 결합, 높은 응집"이 좋은가요?</summary>

**답변(30초)** 결합도는 모듈끼리 서로 얼마나 의존하는지, 응집도는 한 모듈 안의 요소가 한 목적으로 얼마나 뭉쳐 있는지예요. 결합도가 낮으면 한 모듈을 고쳐도 다른 모듈로 변경이 덜 번지고, 응집도가 높으면 모듈의 책임이 분명해서 이해·테스트·재사용이 쉬워요. 예를 들어 타입 플래그로 분기하는 메서드는 제어 결합이라, 전략 패턴이나 메서드 분리로 결합을 낮출 수 있어요.

**꼬리질문**
- Q. 정보 은닉과 캡슐화는 어떤 관계인가요? → 정보 은닉은 바뀌기 쉬운 결정을 숨기자는 설계 원칙이고, 캡슐화는 데이터와 메서드를 묶고 접근 제어자로 내부를 감춰 그 원칙을 구현하는 방법이에요.
- Q. 엔티티를 통째로 넘기는 건 왜 문제인가요? → 받는 쪽이 일부만 써도 엔티티 구조가 바뀌면 영향을 받는 스탬프 결합이에요. 필요한 값이나 DTO만 넘기면 좋아요.
</details>
