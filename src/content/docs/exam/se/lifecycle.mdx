:::tip[한 줄 요약]
소프트웨어 생명주기는 **계획 → 요구 분석 → 설계 → 구현 → 테스트 → 유지보수**의 흐름이고, 모델마다 이 흐름을 도는 방식이 달라요. 필기 키워드는 **폭포수 = 되돌아가기 어려움, 프로토타입 = 견본으로 요구 파악, 나선형 = 위험 분석, 애자일 = 변화 대응**이에요.
:::

:::note[처음이라면 여기까지]
① 폭포수는 설계도를 다 그린 뒤 집을 짓는 방식이고, 애자일은 방 하나씩 지어서 보여 주고 고치는 방식이에요.

② 나선형이 보기에 나오면 정답 키워드는 거의 항상 **위험 분석**이에요.

③ 계산 문제는 공식 세 개면 돼요. LOC·PERT는 **(낙관 + 4×중간 + 비관) ÷ 6**, CPM은 **가장 긴 경로가 임계 경로**예요.

④ "단계별 계산"의 LOC·PERT·CPM 예제를 손으로 따라 하고, 연습 문제 1~5번을 먼저 풀어 보세요. "심화:"는 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

집을 짓는다고 해 볼게요. **폭포수**는 설계도를 마지막 콘센트 위치까지 다 그린 다음 공사를 시작하는 방식이에요. 계획이 분명해서 관리하기 쉽지만, 다 지은 뒤 "거실이 좁아요"라는 말을 들으면 고치기가 아주 비싸요.

**프로토타입**은 모형 집을 먼저 만들어 보여 주고 "이런 느낌 맞아요?"를 확인하는 방식이에요. **나선형**은 한 층씩 올리면서 매번 "이 땅이 꺼질 위험은 없나?"를 먼저 따지는 방식이에요.

**애자일**은 방 하나를 다 지어 집주인에게 보여 주고, 의견을 들어 다음 방을 짓는 방식이에요. 중간에 요구가 바뀌어도 다음 방에서 반영하면 돼요.

단, 실제 소프트웨어는 집보다 고치기 쉬워서 "다 짓고 나서 고치기"의 비용이 집만큼 극단적이지는 않아요. 그래도 늦게 발견한 요구 변경일수록 비싸다는 점은 같아요.

## 제대로 알기

### 생명주기와 방법론은 다른 말

- **생명주기**(SDLC, Software Development Life Cycle): 계획 → 요구 분석 → 설계 → 구현 → 테스트 → 유지보수라는 **전체 흐름**이에요.
- **생명주기 모델**: 이 흐름을 한 번에 쭉 갈지, 여러 번 돌지 정한 틀이에요(폭포수, 나선형 등).
- **개발 방법론**: 각 단계를 실제로 어떻게 할지 정한 방법이에요(구조적, 객체지향, 애자일 등).

### 생명주기 모델 비교

| 모델 | 핵심 키워드 | 장점 | 단점 | 적합한 경우 |
|---|---|---|---|---|
| **폭포수**(waterfall) | 단계가 끝나야 다음 단계, 되돌아가기 어려움 | 단순, 단계별 산출물 명확, 관리 쉬움 | 요구 변경에 약함, 동작하는 결과를 늦게 봄 | 요구가 분명하고 잘 알려진 문제 |
| **프로토타입**(prototyping) | 견본(시범 시스템)을 먼저 만들어 요구 파악 | 요구를 정확히 끌어냄, 사용자 참여 | 사용자 기대가 과해짐, 견본을 그대로 제품으로 쓰려는 압박 | 요구가 불분명할 때 |
| **나선형**(spiral, Boehm 1988) | 반복하며 점진 개발, **위험 분석** | 위험을 일찍 줄임, 대규모에 유리 | 위험 분석 비용·전문성이 필요, 관리 복잡 | 대규모·고위험 시스템 |
| **V 모델** | 폭포수 변형, 개발 단계마다 테스트 단계를 짝지음 | 검증 계획이 분명, 신뢰성 | 변경 대응이 어려움 | 신뢰성이 중요한 분야 |
| **반복·점진**(UP 등) | 조각으로 나눠 조금씩 완성, 같은 범위를 여러 번 다듬음 | 일찍 일부 기능 제공 | 전체 구조 관리가 필요 | 중·대규모, 요구가 점점 드러날 때 |
| **애자일**(agile) | 짧은 주기 반복, 변화 대응, 고객 협력 | 요구 변경에 강함, 빠른 피드백 | 문서·계약 중심 조직엔 맞추기 어려움 | 요구가 자주 바뀌는 소규모 팀 |

- 프로토타입은 견본을 **버리는**(throw-away) 방식과 견본을 계속 키워 제품으로 만드는 **진화형** 두 가지가 있어요.
- **UP**(통합 프로세스, Unified Process)는 유스케이스 중심·아키텍처 중심·반복 점진이 특징이에요.
- V 모델의 단계 짝(요구 분석 ↔ 인수 테스트 등)은 [소프트웨어 테스트](../testing/)에서 자세히 다뤄요.

### 나선형 모델 한 바퀴(4단계)

나선을 한 바퀴 돌 때마다 아래 4단계를 거치고, 바퀴가 커질수록(반지름이 커질수록) 누적 비용이 늘어나요.

| 순서 | 단계 | 하는 일 |
|---|---|---|
| ① | **계획 수립** | 목표·대안·제약 정하기 |
| ② | **위험 분석** | 위험을 찾고 프로토타입 등으로 줄이기 |
| ③ | **개발(공학)과 검증** | 실제로 만들고 확인 |
| ④ | **고객 평가** | 결과를 보여 주고 다음 바퀴 계획에 반영 |

순서 문제에서 **위험 분석은 계획 다음, 개발 앞**이에요. 폭포수와 프로토타입의 장점을 합친 모델이라고 설명하기도 해요.

### 애자일 선언 4가치(2001)

| 더 중시(왼쪽) | 덜 중시(오른쪽) |
|---|---|
| 개인과 상호작용 | 프로세스와 도구 |
| 작동하는 소프트웨어 | 포괄적인 문서 |
| 고객과의 협력 | 계약 협상 |
| 변화에 대응 | 계획을 따르기 |

오른쪽도 가치가 있지만 왼쪽을 **더** 중시한다는 뜻이에요. 문서나 계획을 **버리라는 말이 아니에요**.

### XP(익스트림 프로그래밍)

Kent Beck이 만든 애자일 방법론이에요. 소규모 팀, 요구 변경이 잦은 상황에 맞아요.

- **5가치**: 의사소통, 단순성, 피드백, 용기, 존중. (존중은 2판에서 추가돼서 1판 기준 문제는 4가치로 나오기도 해요.)
- **대표 실천**:
  - 짝 프로그래밍(두 명이 한 컴퓨터로 같이 코딩)
  - **TDD**(테스트 주도 개발, 테스트를 먼저 쓰고 코드를 나중에)
  - 리팩터링(동작은 그대로 두고 코드 구조 개선)
  - 지속적 통합(코드를 자주 합치고 자동 테스트)
  - 작은 릴리스, 공동 코드 소유, 고객 상주, 계획 게임
  - 단순한 설계, 코딩 표준, 주 40시간(지속 가능한 속도), 메타포

지속적 통합이 실무에서 어떻게 돌아가는지는 [CI/CD와 GitOps](../../../architecture/ci-cd-gitops/)를 보세요.

| 구분 | 항목 | 내용 |
|---|---|---|
| 역할(책임) 3 | **Product Owner** | 제품 백로그의 우선순위를 정하고 제품 가치를 최대화 |
| | **Scrum Master** | 팀이 스크럼을 잘 하도록 돕고 장애물을 치움. 관리자·팀장이 아님 |
| | **Developers** | 실제로 만드는 사람들. 2020판부터 "개발 팀" 대신 이 이름 |

| | **Sprint Planning** | 이번 스프린트 목표와 할 일 정하기(1개월 스프린트 기준 최대 8시간) |
| | **Daily Scrum** | 매일 **15분** |
| | **Sprint Review** | 결과를 이해관계자에게 보여 주고 의견 받기(최대 4시간) |
| | **Sprint Retrospective** | 팀의 일하는 방식 돌아보기(최대 3시간) |
| 산출물 3 | **Product Backlog** | 제품에 필요한 일 목록. 약속은 Product Goal |
| | **Sprint Backlog** | 이번 스프린트에서 할 일. 약속은 Sprint Goal |
| | **Increment** | 완성된 결과물. 약속은 Definition of Done(완료의 정의) |

- 스프린트 흐름: Product Backlog → Sprint Planning → 매일 Daily Scrum → Increment → Sprint Review → Retrospective → 다음 스프린트.
- **번다운 차트**(남은 일의 양을 날짜별로 그린 그래프)는 많이 쓰지만 가이드의 공식 산출물은 아니에요.
- 국내 수험서는 스프린트를 "30일 정도"로 쓰기도 해요. 가이드 표현은 "1개월 이하"예요.

### 요구사항: 기능과 비기능

| 구분 | 뜻 | 예 |
|---|---|---|
| **기능 요구** | 시스템이 **무엇을** 하는가 | "회원은 비밀번호를 재설정할 수 있다", "주문하면 영수증을 메일로 보낸다" |
| **비기능 요구** | **얼마나 잘** 하는가, 무엇을 지켜야 하는가 | "응답 2초 이내", "가용성 99.9%", "Java로 개발", "개인정보는 암호화" |

- 비기능 요구에는 성능·가용성·보안·신뢰성·사용성 같은 품질과 언어·OS·미들웨어 지정 같은 **제약**이 들어가요.
- **요구 공학 단계**: 도출(추출) → 분석 → 명세 → 확인(검증). 변경·추적 같은 **관리**는 전 과정에 걸쳐요.

### 비용 산정 기법 분류

| 분류 | 기법 | 특징 |
|---|---|---|
| **하향식** | 전문가 판단, **델파이** | 경험 많은 사람의 판단. 델파이는 여러 전문가에게 익명으로 반복해서 의견을 모아 한 사람의 편향을 줄여요 |
| **상향식** | **LOC**, 개발 단계별 노력 | 작은 작업 단위로 추정해 더함 |
| **수학적** | **COCOMO**, **기능 점수**(FP), Putnam | 공식·모델로 계산 |

### COCOMO 유형 3가지

**COCOMO**(Boehm 1981)는 코드 규모(천 줄 단위, KDSI)를 넣어 노력과 기간을 계산하는 모델이에요.

```text
노력 E = a × (KDSI)^b   [PM, 사람-월]
기간 D = 2.5 × E^c       [월]
```

| 유형 | 프로젝트 성격 | 수험서 규모 기준 | a | b | c |
|---|---|---|---|---|---|
| **조직형**(organic) | 소규모, 익숙한 사무용 | 5만 라인 이하 | 2.4 | 1.05 | 0.38 |
| **반분리형**(semi-detached) | 중간 규모·중간 복잡도 | 30만 라인 이하 | 3.0 | 1.12 | 0.35 |
| **내장형**(embedded) | 하드웨어·제약이 강한 시스템 | 30만 라인 이상 | 3.6 | 1.20 | 0.32 |

- **PM**(Person-Month, 사람-월): 한 사람이 한 달 일한 양이에요. 5 PM이면 5명이 1개월, 또는 1명이 5개월이에요.
- 라인 수 기준은 국내 수험서 관례예요. 원래 모델은 규모보다 프로젝트 환경·제약으로 유형을 나눠요. 그래서 "규모와 복잡도로 판단한다"고 기억하면 안전해요.
- 같은 규모라도 **내장형이 노력이 가장 커요**.

### 기능 점수(FP)

- 코드 줄 수가 아니라 **사용자가 보는 기능의 수**로 규모를 재요. 그래서 **언어와 상관없어요**.
- 세는 대상은 데이터 기능 2개(내부 논리 파일 ILF, 외부 인터페이스 파일 EIF)와 트랜잭션 기능 3개(외부 입력 EI, 외부 출력 EO, 외부 조회 EQ)이고, 복잡도에 따라 가중치를 곱해요.
- 설계 이후 정밀하게 세는 **정규 기능 점수**와, 기획·발주 단계에서 평균 복잡도로 세는 **간이 기능 점수**가 있어요.

### 일정 관리: PERT·CPM·간트

| 기법 | 핵심 | 언제 |
|---|---|---|
| **PERT** | 작업 기간을 낙관·최빈·비관 세 값으로 추정해 기대 시간 계산 | 기간이 불확실할 때(확률적) |
| **CPM** | 작업 네트워크에서 **가장 긴 경로**(임계 경로)를 찾음 | 기간이 비교적 확실할 때 |
| **간트 차트** | 작업별 시작·끝을 가로 막대로 표시 | 진척 확인. 작업 사이 의존 관계는 잘 못 보여 줌 |

### 심화: COCOMO 모델 단계와 COCOMO II

- COCOMO는 **기본형 → 중간형(비용 승수 15개를 곱해 보정) → 상세형**으로 정밀해져요.
- **COCOMO II**는 응용 합성 → 초기 설계 → 구조 설계 이후의 3단계 모델이에요. 초기 설계 단계에서는 기능 점수를 써요. 그래서 "COCOMO는 기능 점수만 쓴다"도, "COCOMO는 기능 점수를 전혀 안 쓴다"도 틀린 말이에요.

## 단계별 계산

### 예제 1: LOC 기법

낙관 3,000줄, 중간(가장 가능성 높은) 5,000줄, 비관 10,000줄로 추정했어요. 1인당 월 생산성은 275줄, 1인당 월 임금은 500만 원, 투입 인원은 5명이에요.

1. 추정 LOC = (낙관 + 4×중간 + 비관) ÷ 6 = (3,000 + 20,000 + 10,000) ÷ 6 = **5,500줄**
2. 노력(PM) = LOC ÷ 월 생산성 = 5,500 ÷ 275 = **20 PM**
3. 비용 = 노력 × 월 임금 = 20 × 500만 = **1억 원**
4. 기간 = 노력 ÷ 인원 = 20 ÷ 5 = **4개월**

### 예제 2: COCOMO로 같은 규모 비교

규모가 32 KDSI(3만 2천 줄)일 때 유형만 바꿔 계산하면 이래요.

| 유형 | 노력 E = a × 32^b | 기간 D = 2.5 × E^c |
|---|---|---|
| 조직형 | 2.4 × 32^1.05 ≈ **91.3 PM** | ≈ 13.9개월 |
| 반분리형 | 3.0 × 32^1.12 ≈ **145.5 PM** | ≈ 14.3개월 |
| 내장형 | 3.6 × 32^1.20 ≈ **230.4 PM** | ≈ 14.3개월 |

지수 b가 클수록 규모가 커질 때 노력이 더 빨리 늘어나요. 시험에서는 거듭제곱 계산보다 "같은 규모면 내장형 노력이 가장 크다"를 더 자주 물어요.

### 예제 3: PERT 기대 시간

어떤 작업을 낙관 a = 2일, 최빈 m = 4일, 비관 b = 12일로 추정했어요.

```text
기대 시간 te = (a + 4m + b) / 6 = (2 + 16 + 12) / 6 = 5일
분산 σ² = ((b − a) / 6)² = (10 / 6)² ≈ 2.78
```

최빈값이 4일이지만 비관 쪽이 길어서 기대 시간은 5일로 늘어나요.

### 예제 4: CPM 임계 경로

| 작업 | 기간(일) | 선행 작업 |
|---|---|---|
| A | 3 | 없음 |
| B | 4 | A |
| C | 2 | A |
| D | 5 | B |
| E | 3 | C |
| F | 2 | D, E |

<CpmCriticalPath />

**방법 1: 경로별 합 비교**(작은 네트워크는 이게 가장 빨라요)

- A → B → D → F = 3 + 4 + 5 + 2 = **14일**
- A → C → E → F = 3 + 2 + 3 + 2 = 10일

가장 **긴** 경로가 임계 경로예요. 임계 경로는 **A → B → D → F**, 프로젝트 최소 완료 기간은 **14일**이에요.

**방법 2: ES·LS로 여유 계산**(여유를 묻는 문제에 필요해요)

1. 앞에서부터: ES(가장 빠른 시작) = 선행 작업 EF 중 **최댓값**, EF = ES + 기간.
2. 뒤에서부터: LF(가장 늦은 끝) = 후속 작업 LS 중 **최솟값**, LS = LF − 기간.
3. 여유 = LS − ES. 여유가 0인 작업을 이으면 임계 경로예요.

| 작업 | ES | EF | LS | LF | 여유 |
|---|---|---|---|---|---|
| A | 0 | 3 | 0 | 3 | **0** |
| B | 3 | 7 | 3 | 7 | **0** |
| C | 3 | 5 | 7 | 9 | 4 |
| D | 7 | 12 | 7 | 12 | **0** |
| E | 5 | 8 | 9 | 12 | 4 |
| F | 12 | 14 | 12 | 14 | **0** |

F의 ES는 D의 EF(12)와 E의 EF(8) 중 큰 값인 12예요. C와 E는 4일 늦어져도 전체 일정에 영향이 없어요. 반대로 임계 경로 작업이 하루 늦으면 프로젝트 전체가 하루 늦어져요.

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 임계 경로는 시작에서 끝까지 가장 짧은 경로다 | **가장 긴** 경로. 그 길이가 최소 완료 기간 |
| 나선형 모델의 핵심은 프로토타입 제작이다 | 핵심은 **위험 분석** |
| 나선형 4단계: 계획 → 개발 → 위험 분석 → 평가 | 계획 → **위험 분석** → 개발·검증 → 고객 평가 |
| 프로토타입 모델은 요구 파악이 어렵다 | 요구 파악은 오히려 **장점**. 단점은 기대 과잉·견본을 제품으로 쓰려는 압박 |
| V 모델은 반복형 모델이다 | V 모델은 **폭포수의 변형** |
| 애자일은 문서와 계획을 작성하지 않는다 | 문서·계획을 **덜 중시**할 뿐 버리지 않음 |
| XP의 가치에 문서화가 있다 | 5가치: 의사소통·단순성·피드백·용기·존중 |
| 스크럼 마스터는 팀을 관리·지시하는 팀장이다 | 스크럼이 잘 되도록 돕는 역할(지시하는 관리자가 아님) |
| 데일리 스크럼은 1시간 회의다 | **15분** |
| 기능 점수는 코드 라인 수로 계산한다 | 사용자 관점 **기능 수**, 언어와 무관 |
| 델파이는 수학적 비용 산정 기법이다 | 전문가 판단을 보완하는 **하향식** 기법 |
| "응답 시간 2초 이내"는 기능 요구다 | **비기능** 요구(성능). "Java로 개발"도 비기능(제약) |
| 간트 차트는 작업 간 의존 관계를 잘 보여 준다 | 의존 관계는 **PERT/CPM 네트워크** |

## 연습 문제

<details>
<summary>1. 위험 분석을 핵심으로 하며 여러 번 반복하면서 점진적으로 개발하는 생명주기 모델은?</summary>

① 폭포수 모델 ② 프로토타입 모델 ③ 나선형 모델 ④ V 모델

**정답: ③**

나선형은 한 바퀴마다 계획 → 위험 분석 → 개발·검증 → 고객 평가를 거쳐요. 폭포수와 V 모델은 반복형이 아니고, 프로토타입의 핵심은 견본으로 요구를 확인하는 거예요.

<details>
<summary>2. 애자일 선언의 가치로 옳지 않은 것은?</summary>

① 프로세스와 도구보다 개인과 상호작용

② 작동하는 소프트웨어보다 포괄적인 문서

③ 계약 협상보다 고객과의 협력

④ 계획을 따르기보다 변화에 대응

**정답: ②**

앞뒤가 바뀌었어요. 원래는 "포괄적인 문서보다 **작동하는 소프트웨어**"예요.
</details>

<details>
<summary>3. 스크럼(Scrum Guide 2020)에 대한 설명으로 옳은 것은?</summary>

① 데일리 스크럼은 하루 1시간씩 진행한다.

② 제품 백로그의 우선순위는 Product Owner가 정한다.

③ Scrum Master는 개발자에게 업무를 배정하는 팀장이다.

④ 스프린트 길이는 매번 상황에 맞게 늘였다 줄였다 한다.

**정답: ②**

① 15분이에요. ③ Scrum Master는 지시하는 관리자가 아니라 팀이 스크럼을 잘 하도록 돕는 역할이에요. ④ 스프린트는 1개월 이하의 **고정** 길이예요.
</details>

<details>
<summary>4. 다음 중 비기능 요구사항이 아닌 것은?</summary>

① 검색 결과는 1초 안에 표시되어야 한다.

② 서비스 가용성은 99.9% 이상이어야 한다.

③ 사용자는 장바구니에 담은 상품을 삭제할 수 있다.

④ 서버는 Linux 환경에서 동작해야 한다.

**정답: ③**

③은 시스템이 **무엇을** 하는지 말하니 기능 요구예요. ①은 성능, ②는 가용성, ④는 환경 제약이라 비기능 요구예요.
</details>

<details>
<summary>5. LOC 기법으로 낙관 2,000줄, 중간 4,000줄, 비관 9,000줄을 추정했다. 1인당 월 생산성이 300줄이고 3명이 투입될 때 개발 기간은?</summary>

① 3개월 ② 4개월 ③ 5개월 ④ 15개월

**정답: ③**

1. 추정 LOC = (2,000 + 4×4,000 + 9,000) ÷ 6 = 27,000 ÷ 6 = 4,500줄
2. 노력 = 4,500 ÷ 300 = 15 PM
3. 기간 = 15 ÷ 3 = 5개월

④ 15는 노력(PM)이에요. 기간과 헷갈리게 내는 보기예요.
</details>

<details>
<summary>6. COCOMO 모델에 대한 설명으로 옳은 것은?</summary>

① 사용자 관점의 기능 수로 규모를 측정하므로 언어와 무관하다.

② 내장형(embedded)은 하드웨어 제약이 강한 시스템에 해당하며, 같은 규모일 때 노력이 가장 크다.

③ 조직형(organic)은 30만 라인 이상의 대규모 시스템에 해당한다.

④ 델파이 기법처럼 전문가 판단에 의존하는 하향식 기법이다.

**정답: ②**

① 기능 점수(FP) 설명이에요. ③ 조직형은 소규모 사무용(수험서 기준 5만 라인 이하)이에요. ④ COCOMO는 공식을 쓰는 수학적 기법이에요.
</details>

<details>
<summary>7. PERT에서 어떤 작업의 낙관 시간 3일, 최빈 시간 6일, 비관 시간 15일일 때 기대 시간은?</summary>

① 6일 ② 7일 ③ 8일 ④ 8.5일

**정답: ②**

te = (3 + 4×6 + 15) ÷ 6 = (3 + 24 + 15) ÷ 6 = 42 ÷ 6 = 7일. ③ 8일은 세 값의 단순 평균((3+6+15)÷3)이라 틀려요.
</details>

<details>
<summary>8. 다음 작업 네트워크의 임계 경로 길이와 작업 C의 여유 시간은? (A 2일·선행 없음, B 3일·A, C 5일·A, D 4일·B, E 1일·C, F 3일·D와 E)</summary>

① 11일, 0일 ② 11일, 1일 ③ 12일, 0일 ④ 12일, 1일

**정답: ④**

- 경로 A→B→D→F = 2 + 3 + 4 + 3 = **12일**
- 경로 A→C→E→F = 2 + 5 + 1 + 3 = 11일

가장 긴 12일이 임계 경로예요. C는 ES = 2이고, F의 LS가 9라서 E의 LS = 9 − 1 = 8, C의 LF = 8, LS = 8 − 5 = 3이에요. 여유 = 3 − 2 = **1일**. 경로 길이 차이(12 − 11)로도 바로 보여요.
</details>

## 면접 질문

<details>
<summary>Q. 폭포수와 애자일의 차이, 각각 언제 쓰면 좋은지 말해 주세요.</summary>

**답변(30초)** 폭포수는 요구 분석부터 테스트까지 한 단계씩 끝내고 넘어가는 방식이고, 애자일은 짧은 주기로 작동하는 결과물을 만들어 피드백을 받으며 반복하는 방식이에요. 폭포수는 산출물이 분명해서 관리하기 쉽지만 요구가 바뀌면 되돌아가기 어려워요. 그래서 요구가 명확하고 규제·신뢰성이 중요한 시스템에 맞고, 요구가 불분명하거나 자주 바뀌는 신규 서비스에는 애자일이 맞아요.

**꼬리질문**
- Q. 애자일이면 문서를 안 쓰나요? → 아니에요. 애자일 선언은 문서보다 작동하는 소프트웨어를 **더** 중시한다는 뜻이고, 필요한 문서는 써요.
- Q. 스프린트 중간에 고객이 요구를 바꾸면요? → Product Owner가 제품 백로그에 넣고 다음 Sprint Planning에서 반영해요. 진행 중인 스프린트 목표는 지켜요.
</details>
