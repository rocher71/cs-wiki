:::tip[한 줄 요약]
**블랙박스**는 명세만 보고(동등 분할·경계값·원인-결과 그래프), **화이트박스**는 코드 구조를 보고(구문·결정·조건 커버리지, 기본 경로) 테스트해요. 순환 복잡도는 **V(G) = E − N + 2**, 하향식 통합은 **스텁**, 상향식 통합은 **드라이버**예요.
:::

:::note[처음이라면 여기까지]
① 블랙박스는 "자판기에 동전을 넣으면 음료가 나오나"만 보고, 화이트박스는 자판기를 열어 "모든 배선에 전기가 한 번씩 흐르나"를 봐요.

② 동등 분할·경계값은 블랙박스, 커버리지·기본 경로는 화이트박스예요. 이 분류 문제가 가장 자주 나와요.

③ 통합 테스트에서 **스텁**은 아직 없는 아래 모듈의 가짜, **드라이버**는 아직 없는 위 모듈의 가짜예요. 하향식은 스텁, 상향식은 드라이버예요.

④ 경계값 예제, 순환 복잡도 예제, 연습 문제 1~5번을 먼저 보세요. MC/DC는 "심화:"라서 나중에 봐도 돼요.
:::

## 쉽게 이해하기

자판기를 검사한다고 해 볼게요. **블랙박스 테스트**는 겉에서만 봐요. 1,000원을 넣으면 음료가 나오는지, 999원이면 거절하는지, 0원이면 어떻게 되는지 확인해요. 안의 구조는 몰라도 돼요.

**화이트박스 테스트**는 자판기를 열고 회로도를 보며 검사해요. "잔돈 반환 회로를 한 번이라도 지나가게 했나?", "품절 분기로 빠지는 길을 확인했나?"처럼 내부의 길을 빠짐없이 지나가는 게 목표예요.

자판기를 다 만든 뒤에 한 번에 검사하지 않고, 부품 하나(단위) → 부품끼리 연결(통합) → 완성품 전체(시스템) → 손님이 직접 써 보기(인수) 순서로 검사해요.

단, 실제로 모든 입력과 모든 길을 다 시험할 수는 없어요. 그래서 "어떤 입력 몇 개면 충분한가"를 정하는 기법들이 필요해요.

## 제대로 알기

### 블랙박스와 화이트박스

| 구분 | 블랙박스(명세 기반) | 화이트박스(구조 기반) |
|---|---|---|
| 보는 것 | 요구 명세(입력 → 기대 출력) | 코드의 문장·분기·경로 |
| 묻는 것 | 원하는 기능을 하는가 | 내부 길을 빠짐없이 지나갔는가 |
| 대표 기법 | 동등 분할, 경계값 분석, 원인-결과 그래프, 오류 예측, 비교 테스트, 결정 테이블, 상태 전이 | 구문·결정·조건 커버리지, 기본 경로(순환 복잡도), 루프 테스트 |
| 주로 쓰는 단계 | 시스템·인수 테스트 | 단위 테스트 |

두 가지를 섞은 **그레이박스** 테스트도 있어요.

### 블랙박스 기법

| 기법 | 핵심 |
|---|---|
| **동등 분할**(동치 분할) | 입력을 같은 결과를 내는 그룹(유효·무효)으로 나누고 그룹마다 대표값 하나 |
| **경계값 분석** | 오류는 경계에서 많이 나니 경계와 그 바로 안·밖 값을 시험. 동등 분할을 보완 |
| **원인-결과 그래프** | 입력 조건(원인)과 결과의 논리 관계를 그래프로 그리고 결정 테이블로 바꿔 조합 케이스를 뽑음 |
| **오류 예측** | 경험·직관으로 실수가 많을 곳을 추측. 다른 기법의 보충 |
| **비교**(back-to-back) | 같은 명세로 만든 여러 버전에 같은 입력을 넣어 결과 비교 |

### 예제 1: 동등 분할과 경계값

명세: "나이는 1~100만 유효하다."

1. **동등 분할**: 무효(0 이하) / 유효(1~100) / 무효(101 이상) 세 그룹 → 대표값 예 −5, 50, 150 (**3개**)
2. **2-값 경계**(경계와 바로 바깥): 0, 1, 100, 101 (**4개**)
3. **3-값 경계**(경계와 양옆): 0, 1, 2, 99, 100, 101 (**6개**)

동등 분할만 하면 50으로 "유효"를 확인하고 끝나요. 실제 버그는 `age < 100`처럼 등호 하나를 빠뜨려서 100에서 나는 경우가 많아서 경계값이 필요해요.

### 화이트박스 커버리지

**커버리지**(coverage, 테스트가 코드를 얼마나 지나갔는지의 비율)는 기준마다 엄격함이 달라요.

| 기준 | 만족 조건 |
|---|---|
| **구문**(문장) | 모든 문장을 최소 1번 실행 |
| **결정**(분기) | 각 결정문(if 전체)이 참·거짓을 각각 1번 이상 |
| **조건** | 결정문 안의 **개별 조건식**이 각각 참·거짓을 1번 이상(결정 전체 결과는 상관없음) |
| **조건/결정** | 조건 + 결정을 동시에 만족 |
| **MC/DC**(변형 조건/결정) | 조건/결정 + 각 조건이 **혼자 바뀌어 결과를 바꾸는** 짝을 보임 |
| **다중 조건** | 개별 조건의 **모든 조합** |

강도: 구문 &lt; 결정 &lt; 조건/결정 &lt; MC/DC &lt; 다중 조건. **조건 커버리지는 결정 커버리지를 포함하지 않아요.** 그래서 위 사슬에 끼지 못해요.

### 예제 2: 같은 코드, 기준별 필요한 테스트 수

```java
if (a > 0 && b > 0) {   // 조건 A: a > 0, 조건 B: b > 0
    x = 1;
}
y = 2;                   // else는 없음
```

T는 참, F는 거짓이에요. TF는 "조건 A 참, 조건 B 거짓"이에요.

| 기준 | 최소 케이스 수 | 예 | 왜 |
|---|---|---|---|
| 구문 | **1** | TT | TT면 `x = 1`과 `y = 2`를 모두 실행 |
| 결정 | **2** | TT, FT | 결정 전체가 참(TT) 한 번, 거짓(FT) 한 번 |
| 조건 | **2** | TF, FT | A와 B가 각각 T·F를 한 번씩. 그런데 결정은 **둘 다 거짓** → 결정 미충족 |
| 조건/결정 | **2** | TT, FF | 각 조건 T·F + 결정 참·거짓 |
| MC/DC | **3** | TT, TF, FT | TT↔FT가 A 혼자 바뀌어 결과가 바뀜, TT↔TF가 B 혼자 바뀌어 결과가 바뀜 |
| 다중 조건 | **4** | TT, TF, FT, FF | 2개 조건의 모든 조합 2² |

조건 커버리지 줄이 바로 시험 함정이에요. TF·FT는 조건마다 참·거짓이 다 나왔지만, `x = 1` 쪽 길은 한 번도 안 지나가요.

### 순환 복잡도(McCabe)

**순환 복잡도**(cyclomatic complexity)는 코드의 제어 흐름 그래프에 독립적인 경로가 몇 개인지 센 값이에요. **기본 경로 테스트**에 필요한 최소 테스트 케이스 수와 같아요.

공식 세 가지는 모두 같은 값을 줘요.

```text
① V(G) = E − N + 2        (E: 간선 수, N: 노드 수)
② V(G) = 판단 노드 수 + 1  (판단 노드: 나가는 화살표가 2개인 노드)
③ V(G) = 닫힌 영역 수 + 1  (그래프가 둘러싼 영역 + 바깥 영역 1개)
```

### 예제 3: 순환 복잡도 계산

do-while 반복 안에 if-else가 있는 코드의 흐름 그래프예요.

| 노드 | 역할 |
|---|---|
| 1 | 시작 |
| 2 | if 판단 |
| 3 | 참일 때 처리 |
| 4 | 거짓일 때 처리 |
| 5 | 합류 |
| 6 | 반복 조건 판단 |
| 7 | 종료 |

간선: 1→2, 2→3, 2→4, 3→5, 4→5, 5→6, 6→2(다시 반복), 6→7

1. 공식 ①: E = 8, N = 7 → V(G) = 8 − 7 + 2 = **3**
2. 공식 ②: 판단 노드는 2와 6 (2개) → 2 + 1 = **3**
3. 공식 ③: 닫힌 영역은 2-3-5-4로 둘러싼 칸 하나, 2→…→6→2 반복으로 둘러싼 칸 하나 (2개) → 2 + 1 = **3**

독립 경로 3개 예: 1-2-3-5-6-7 / 1-2-4-5-6-7 / 1-2-3-5-6-2-…-7(한 번 더 반복). 테스트 케이스도 최소 3개예요.

- 공식 ①을 **N − E + 2**로 바꿔 낸 보기는 틀려요.
- McCabe는 한 모듈의 V(G)가 **10**을 넘지 않게 하라고 권했어요. 넘으면 분기를 줄이도록 쪼개요.

### 테스트 단계와 V 모델

| 개발 단계(V의 왼쪽) | 짝이 되는 테스트(V의 오른쪽) | 무엇을 보나 |
|---|---|---|
| 요구 분석 | **인수 테스트** | 사용자 요구에 맞나. 출시·인수 여부 결정 |
| 시스템(기본) 설계 | **시스템 테스트** | 완성된 시스템의 기능 + 성능·부하·보안 같은 비기능 |
| 상세 설계 | **통합 테스트** | 모듈 사이 인터페이스 |
| 코딩(모듈 설계) | **단위 테스트** | 모듈 하나. 주로 화이트박스 |

- 실행 순서는 단위 → 통합 → 시스템 → 인수예요.
- 시스템 테스트는 **개발 조직**이 하는 마지막 테스트이고, 인수 테스트는 **사용자·고객**이 주도해요.

### 통합 방식: 스텁과 드라이버

- **스텁**(stub): 테스트 대상이 **부르는** 아래 모듈의 가짜예요. 정해진 값만 돌려줘요.
- **드라이버**(driver): 테스트 대상을 **불러 주는** 위 모듈의 가짜예요.

| 방식 | 순서 | 가짜 모듈 | 장점 | 단점 |
|---|---|---|---|---|
| **빅뱅** | 한꺼번에 합침 | 없음 | 단순, 소규모에 적합 | 결함 위치 찾기 어려움 |
| **하향식** | 최상위 → 아래로 | **스텁**(없는 하위 대신) | 주요 제어 흐름·인터페이스 결함을 일찍 발견 | 하위 계산은 늦게 검증 |
| **상향식** | 최하위(클러스터) → 위로 | **드라이버**(없는 상위 대신) | 하위 계산을 정밀하게 검증 | 전체 흐름은 늦게 확인 |
| **샌드위치**(혼합) | 위는 하향, 아래는 상향 동시 | 스텁 + 드라이버 | 양쪽 장점 | 비용이 큼 |

하향식은 두 가지 순서가 있어요. 트리가 A → B, C, D / B → E, F / C → G일 때:

- **넓이 우선**: A-B, A-C, A-D를 먼저 붙이고, 그다음 E, F, G
- **깊이 우선**: A-B-E-F, 그다음 A-C-G, 마지막 A-D
- 상향식은 (E, F → B), (G → C)를 먼저 묶어 시험하고, 그다음 B·C·D를 A에 붙여요.

### 인수 테스트: 알파와 베타

| 구분 | 알파 테스트 | 베타 테스트 |
|---|---|---|
| 장소 | **개발자** 사이트 | **사용자** 환경 |
| 누가 | 사용자가 하고 개발자가 지켜봄 | 일부 실사용자가 개발자 없이 |
| 환경 | 통제됨 | 통제 안 됨, 결과를 피드백 |

### 회귀 테스트

- **회귀 테스트**(regression test): 코드를 고치거나 기능을 더한 뒤 **원래 되던 기능**이 깨지지 않았는지 다시 시험해요. 고친 모듈과 관련 모듈이 대상이에요.
- **확정 테스트**(재테스트): 고친 결함 **그 자체**가 정말 고쳐졌는지 확인해요. 회귀 테스트와 다른 말이에요.
- 실무에서는 CI 파이프라인의 자동 테스트가 회귀 테스트 역할을 해요. [CI/CD와 GitOps](../../../architecture/ci-cd-gitops/)를 보세요.

### 검증(Verification)과 확인(Validation)

| 영어 | 묻는 것 | 관점 | 주로 하는 활동 |
|---|---|---|---|
| **Verification** | 제품을 **올바르게** 만들고 있나? (명세·설계대로인가) | 개발자 | 리뷰, 인스펙션, 단위~시스템 테스트 |
| **Validation** | **올바른 제품**을 만들었나? (사용자가 원하는 것인가) | 사용자 | 인수 테스트 |

:::caution[함정: 한국어 이름이 책마다 반대]
정처기 관례는 **검증 = Verification, 확인 = Validation**이에요. 그런데 일부 수험서는 시스템 테스트를 "확인(verification)", 인수 테스트를 "검증(validation)"처럼 한국어를 **거꾸로** 붙여요.

영어 뜻은 어느 책이나 같아요. 그러니 한국어 단어가 아니라 **영어 단어로 외우세요.** Verification은 "명세대로 만들었나", Validation은 "사용자가 원하는 걸 만들었나". 보기에 영어가 같이 있으면 영어를 기준으로 판단하면 돼요.
:::

### 심화: MC/DC를 확인하는 방법

- MC/DC는 조건이 n개면 최소 **n + 1개** 케이스가 필요해요. 2개면 3개, 3개면 4개예요. 다중 조건(2ⁿ)보다 훨씬 적어요.
- 확인 방법: 조건마다 "**그 조건만 다르고 나머지는 같은** 두 케이스인데 결과가 다른" 짝이 있어야 해요.
- 예제 2에서 TT·FF는 조건/결정은 만족하지만 MC/DC는 아니에요. TT와 FF는 두 조건이 동시에 바뀌어서 누구 때문에 결과가 바뀌었는지 알 수 없어요.
- 항공 소프트웨어 인증(DO-178C 최고 등급)이 MC/DC를 요구해요.
- 실제 코드에서 `&&`는 앞 조건이 거짓이면 뒤 조건을 평가하지 않아요(단락 평가). 그래서 결정 커버리지만으로는 뒤 조건의 오류를 놓칠 수 있어요.

### 심화: 테스트 7원리

1. 테스트는 결함이 **있음**을 보여 줄 뿐, **없음**을 증명하지 못해요.
2. 모든 경우를 다 시험하는 완벽한 테스트는 불가능해요.
3. 일찍 시작할수록 고치는 비용이 싸요.
4. **결함 집중**: 결함은 소수 모듈에 몰려 있어요(파레토 80/20).
5. **살충제 역설**: 같은 케이스만 반복하면 새 결함을 못 찾아요. 케이스를 주기적으로 바꿔요.
6. 테스트 방법은 정황(분야)에 따라 달라요.
7. **오류-부재의 궤변**: 결함이 없어도 사용자 요구에 안 맞으면 쓸모없어요.

## 객관식 함정

| 이렇게 나오면 틀린 보기 | 맞는 내용 |
|---|---|
| 하향식 통합 테스트에는 드라이버가 필요하다 | 하향식 = **스텁**, 상향식 = **드라이버** |
| 스텁은 테스트 대상 모듈을 호출하는 상위 모듈이다 | 그건 드라이버. 스텁은 대상이 **호출하는** 하위 가짜 |
| 경계값 분석은 화이트박스 기법이다 | 동등 분할·경계값·원인-결과 그래프는 **블랙박스** |
| 기본 경로 테스트는 블랙박스 기법이다 | 기본 경로·커버리지·루프 테스트는 **화이트박스** |
| 조건 커버리지를 만족하면 결정 커버리지도 만족한다 | 만족하지 **않을 수 있음**(예: TF, FT) |
| 구문 커버리지 100%면 모든 분기를 시험한 것이다 | 거짓 쪽 분기를 한 번도 안 볼 수 있음 |
| V(G) = N − E + 2 | **E − N + 2** |
| 알파 테스트는 개발자가 혼자 수행한다 | **사용자**가 개발자 사이트에서, 개발자가 지켜보며 |
| 베타 테스트는 개발자 사이트에서 진행한다 | **사용자 환경**에서, 개발자 없이 |
| 인수 테스트의 주목적은 결함 발견이다 | 목적은 **인수(출시) 여부 결정**, 주도는 사용자 |
| 회귀 테스트 = 고친 결함만 다시 확인하는 테스트 | 그건 확정(재) 테스트. 회귀는 **기존 기능**이 깨졌는지 |
| V 모델에서 상세 설계는 시스템 테스트와 짝이다 | 상세 설계 ↔ **통합**, 시스템 설계 ↔ 시스템 |
| Validation은 명세대로 만들었는지 본다 | 그건 Verification. Validation은 **사용자 요구**에 맞는지 |

## 연습 문제

<details>
<summary>1. 다음 중 블랙박스 테스트 기법이 아닌 것은?</summary>

① 동등 분할 ② 경계값 분석 ③ 원인-결과 그래프 ④ 기본 경로 테스트

**정답: ④**

기본 경로 테스트는 제어 흐름 그래프에서 독립 경로를 뽑는 **화이트박스** 기법이에요. 나머지 셋은 명세만 보고 케이스를 만들어요.
</details>

<details>
<summary>2. 하향식 통합 테스트에서 아직 개발되지 않은 하위 모듈 대신 쓰는 것은?</summary>

① 드라이버 ② 스텁 ③ 클러스터 ④ 테스트 하네스

**정답: ②**

하향식은 위에서부터 붙여 가므로 없는 **아래** 모듈을 스텁으로 대신해요. 드라이버는 상향식에서 없는 위 모듈을 대신하고, 클러스터는 상향식에서 하위 모듈을 묶은 단위예요.
</details>

<details>
<summary>3. 입력 점수가 0~100일 때 유효하다. 2-값 경계값 분석으로 고른 테스트 값으로 옳은 것은?</summary>

① 0, 50, 100 ② −1, 0, 100, 101 ③ 1, 99 ④ −10, 50, 110

**정답: ②**

경계(0, 100)와 그 바로 바깥(−1, 101)을 시험해요. ④는 동등 분할의 그룹별 대표값에 가까워요.
</details>

<details>
<summary>4. 인수 테스트에 대한 설명으로 옳은 것은?</summary>

① 알파 테스트는 사용자 환경에서 개발자 없이 진행한다.

② 베타 테스트는 개발자 사이트에서 개발자가 지켜보며 진행한다.

③ 알파 테스트는 개발자 사이트에서 사용자가 수행하고 개발자가 지켜본다.

④ 인수 테스트는 개발 조직이 주도하는 마지막 내부 테스트다.

**정답: ③**

①과 ②는 알파와 베타 설명이 서로 바뀌었어요. ④는 시스템 테스트 설명이에요. 인수 테스트는 사용자가 주도해요.
</details>

<details>
<summary>5. 제어 흐름 그래프의 간선이 10개, 노드가 8개일 때 순환 복잡도는?</summary>

① 2 ② 3 ③ 4 ④ 20

**정답: ③**

V(G) = E − N + 2 = 10 − 8 + 2 = 4. 기본 경로 테스트에 최소 4개 케이스가 필요해요. 공식을 N − E + 2로 잘못 쓰면 0이 나와요.
</details>

<details>
<summary>6. 결정문 `if (A && B)`에 대해 테스트 케이스 (A=참, B=거짓), (A=거짓, B=참) 두 개를 만들었다. 옳은 설명은?</summary>

① 결정 커버리지를 만족한다.

② 조건 커버리지는 만족하지만 결정 커버리지는 만족하지 않는다.

③ 다중 조건 커버리지를 만족한다.

④ 구문 커버리지와 결정 커버리지를 모두 만족한다.

**정답: ②**

A와 B가 각각 참·거짓을 한 번씩 가져서 조건 커버리지는 만족해요. 하지만 두 케이스 모두 결정 결과가 거짓이라 참 분기를 한 번도 안 지나가요. 그래서 결정도, 참 분기 안의 문장을 실행해야 하는 구문 커버리지도 만족하지 않아요. 다중 조건은 4가지 조합이 다 필요해요.
</details>

<details>
<summary>7. 결정문 안에 개별 조건이 3개 있을 때, 다중 조건 커버리지와 MC/DC에 필요한 최소 테스트 케이스 수는?</summary>

① 8개, 4개 ② 8개, 3개 ③ 6개, 4개 ④ 3개, 3개

**정답: ①**

다중 조건은 모든 조합이라 2³ = 8개예요. MC/DC는 조건 n개에 최소 n + 1개라 4개예요. (`A && B && C`에서 TTT, FTT, TFT, TTF면 각 조건이 혼자 바뀌어 결과를 바꾸는 짝이 모두 생겨요.)
</details>

<details>
<summary>8. "사용자가 실제로 원하는 제품을 만들었는가?"를 확인하는 활동과, 이에 가장 가까운 테스트 단계를 바르게 짝지은 것은?</summary>

① Verification — 단위 테스트 ② Verification — 인수 테스트 ③ Validation — 통합 테스트 ④ Validation — 인수 테스트

**정답: ④**

"올바른 제품을 만들었나"는 **Validation**이고, 사용자가 주도하는 인수 테스트가 대표적이에요. "명세대로 올바르게 만들고 있나"가 Verification이에요. 한국어 이름(검증·확인)은 책마다 반대로 붙기도 하니 영어로 판단하세요.
</details>

## 면접 질문

<details>
<summary>Q. 단위 테스트와 통합 테스트의 차이, 스텁과 목(mock)의 차이를 말해 주세요.</summary>

**답변(30초)** 단위 테스트는 클래스나 함수 하나를 다른 부분과 떼어서 시험하고, 통합 테스트는 여러 모듈이나 DB·외부 API를 실제로 연결해 인터페이스가 맞물리는지 시험해요. 단위 테스트에서 아직 없거나 느린 의존성은 가짜로 바꾸는데, 스텁은 정해진 값을 돌려주기만 하고, 목은 "이 메서드가 몇 번, 어떤 인자로 불렸나"까지 검증해요. 예를 들어 결제 API가 아직 없으면 스텁으로 응답을 고정하고 상위 서비스를 먼저 시험할 수 있어요.

**꼬리질문**
- Q. 커버리지 100%면 버그가 없나요? → 아니에요. 커버리지는 코드를 지나갔다는 뜻일 뿐이고, 테스트는 결함이 있음을 보일 수 있어도 없음을 증명하지 못해요. 명세에서 빠진 요구나 경계값 오류는 커버리지로 안 보여요.
- Q. 회귀 테스트는 왜 자동화하나요? → 수정할 때마다 기존 기능을 다 다시 봐야 하는데 손으로는 비용이 너무 커요. CI에 묶어 두면 커밋마다 자동으로 확인돼요.
</details>
