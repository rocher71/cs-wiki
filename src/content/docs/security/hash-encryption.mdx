:::tip[한 줄 요약]
**해시**는 되돌릴 수 없는 고정 길이 지문, **암호화**는 키로 잠갔다가 다시 여는 것, **전자서명**은 개인키 주인만 만들 수 있는 도장이에요. 비밀번호는 암호화하지 않고 **사용자마다 다른 솔트를 붙여 일부러 느린 해시**(Argon2id, bcrypt 등)로 저장해요.
:::

:::note[이 섹션 안내]
**보안·테스트** 섹션은 백엔드 개발자가 "안전하게, 그리고 믿을 수 있게" 코드를 내보내는 법을 다뤄요. 앞쪽은 보안(이 페이지 → [SQL 인젝션](../injection/) → [XSS·CSRF](../xss-csrf/) → [인증 보안](../auth-security/)), 뒤쪽은 테스트([테스트 기초](../testing-basics/) → [Spring 테스트](../spring-testing/) → [TDD와 코드 품질](../tdd-quality/))예요.

이미 다른 섹션에 있는 내용은 링크로 넘겨요. HTTPS 동작은 [HTTPS와 TLS](../../web/https-tls/), 로그인 상태 유지와 JWT는 [쿠키·세션·JWT](../../web/cookie-session-jwt/), 브라우저 출처 정책은 [CORS](../../web/cors/), 소셜 로그인은 [OAuth 2.0](../../web/oauth2/), 스프링에서의 인증·인가는 [Spring Security](../../spring/spring-security/)를 보세요.
:::

:::note[처음이라면 여기까지]
① 해시는 믹서기예요. 갈면 결과는 늘 같지만 되돌릴 수 없어요. 암호화는 열쇠가 있으면 다시 열 수 있어요.

② Base64는 암호화가 아니에요. 글자 모양만 바꾼 거라 누구나 바로 되돌려요.

③ 비밀번호는 "솔트(사용자마다 다른 랜덤값) + 일부러 느린 해시"로 저장해요. SHA-256 한 번은 너무 빨라서 안 돼요.

④ 대칭키는 열쇠 하나를 나눠 갖고, 비대칭키는 우체통처럼 누구나 넣고 주인만 열어요. 전자서명은 주인만 찍을 수 있는 도장이에요.

⑤ 면접에선 질문 1~4번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

**해시는 믹서기**예요. 딸기와 바나나를 넣고 갈면 늘 같은 색의 주스가 나와요. 그런데 주스를 보고 원래 과일을 되살릴 수는 없죠. 그래서 "원문은 몰라도, 같은 걸 넣었는지는 확인"하는 데 써요.

**대칭키 암호화는 같은 열쇠로 잠그고 여는 자물쇠**예요. 친구와 같은 열쇠를 하나씩 나눠 가지면 상자를 주고받을 수 있어요. 문제는 그 열쇠를 처음에 어떻게 안전하게 건네느냐예요.

**비대칭키 암호화는 우체통**이에요. 투입구(공개키)는 누구에게나 열려 있어서 아무나 편지를 넣을 수 있지만, 꺼내는 열쇠(개인키)는 주인만 가져요.

**전자서명은 도장**이에요. 내 도장(개인키)은 나만 찍을 수 있고, 도장 모양(공개키)은 누구나 대조해 볼 수 있어요. 그래서 "이 문서는 내가 만들었고, 그 뒤로 안 바뀌었다"를 증명해요.

단, 실제로는 다른 점이 있어요. 해시는 결과가 늘 같은 길이(예: SHA-256은 32바이트)이고, 아주 드물게 다른 입력이 같은 결과를 낼 수도 있어요. 전자서명도 문서 자체가 아니라 문서의 해시에 도장을 찍어요.

## 제대로 알기

### 인코딩·해시·암호화는 서로 달라요

셋 다 "글자가 알아볼 수 없게 바뀐다"는 겉모습은 비슷해서 자주 섞여요. 구분 기준은 **키가 있는가**, **되돌릴 수 있는가**예요.

| | 인코딩 | 해시 | 암호화 |
|---|---|---|---|
| 목적 | 다른 시스템이 읽기 쉬운 모양으로 바꾸기 | 같은지 확인(지문) | 남이 못 보게 숨기기 |
| 키 | 없음 | 없음 | 있음 |
| 되돌리기 | 누구나 가능 | 불가능(단방향) | 키가 있으면 가능 |
| 출력 길이 | 입력에 비례(Base64는 약 4/3배) | 늘 고정(SHA-256은 32바이트) | 입력에 비례 |
| 예 | Base64, URL 인코딩 | SHA-256, bcrypt | AES, RSA |

**Base64**(바이너리 데이터를 64개의 안전한 문자로 바꿔 적는 방식)는 인코딩이에요. 한 번 해 보면 바로 알 수 있어요.

```python
import base64
base64.b64encode(b"password123")        # b'cGFzc3dvcmQxMjM='
base64.b64decode(b"cGFzc3dvcmQxMjM=")   # b'password123' — 키 없이 바로 원복
```

그래서 JWT 페이로드처럼 Base64로 된 값은 **누구나 읽을 수 있어요**. 숨기고 싶은 정보를 넣으면 안 돼요. → [쿠키·세션·JWT](../../web/cookie-session-jwt/)

### 해시 함수: 되돌릴 수 없는 지문

**해시 함수**(hash function)는 아무 길이의 입력을 받아 고정 길이 값(**다이제스트**, digest)을 내는 단방향 함수예요. SHA-256은 256비트(32바이트)를 내요. SHA-256은 **SHA-2** 계열의 하나이고, 이 계열은 미국 표준 FIPS 180-4에 정의돼 있어요.

보안용 해시가 갖춰야 할 성질은 세 가지예요.

| 성질 | 뜻 |
|---|---|
| 역상 저항 | 해시값만 보고 원래 입력을 찾기 어렵다 |
| 제2역상 저항 | 주어진 입력과 같은 해시를 내는 **다른** 입력을 찾기 어렵다 |
| 충돌 저항 | 같은 해시를 내는 입력 두 개를 아무거나 찾기도 어렵다 |

출력 길이가 정해져 있으니 **충돌**(collision, 다른 입력이 같은 해시를 냄)은 이론상 반드시 있어요. "없다"가 아니라 "찾기 어렵다"가 정확해요. MD5와 SHA-1은 실제로 충돌을 만들어 낸 사례가 있어서 서명·무결성 용도로 쓰면 안 돼요.

같은 입력은 항상 같은 해시가 나와요. 이 성질 덕분에 파일이 안 바뀌었는지 확인할 수 있지만, 비밀번호 저장에선 약점이 돼요(아래에서 설명).

### 비밀번호는 왜 "암호화"가 아니라 "해시"로 저장하나

서버는 사용자의 비밀번호 원문을 알 필요가 없어요. 로그인할 때 입력한 값을 **같은 방식으로 해시해서 저장된 값과 같은지만** 보면 돼요.

암호화로 저장하면 복호화 키가 서버 어딘가에 있어야 해요. 그 키가 DB와 함께 털리면 모든 비밀번호가 한 번에 원문으로 돌아가요. 해시는 애초에 되돌릴 방법이 없으니 이 위험이 없어요. OWASP(웹 보안 권고를 내는 비영리 단체)도 비밀번호는 해시로 저장하라고 해요.

### 솔트: 같은 비밀번호도 다른 해시로

솔트 없이 `SHA-256(비밀번호)`만 저장하면 두 가지 문제가 생겨요.

- **같은 비밀번호는 같은 해시**가 돼요. 한 명만 뚫리면 같은 비밀번호를 쓴 사람이 전부 드러나요.
- 공격자가 흔한 비밀번호의 해시를 **미리 계산해 둔 표**(**레인보우 테이블**, rainbow table)로 바로 찾아봐요.

**솔트**(salt)는 비밀번호마다 새로 만드는 랜덤값이에요. `해시(비밀번호 + 솔트)`로 저장하면 같은 비밀번호라도 해시가 완전히 달라지고, 미리 만든 표는 쓸모가 없어져요.

실험 예시로 같은 비밀번호 `password123`을 솔트만 바꿔 해시해 봤어요(PBKDF2-SHA256, 60만 회).

| 솔트(앞부분) | 해시(앞부분) |
|---|---|
| `4809b3d0…` | `1731ec825b36dffb…` |
| `4f313e3f…` | `7aab2cf647a0cf4c…` |
| 솔트 없이 SHA-256 두 번 | `ef92b778bafe771e…` 두 번 다 같음 |

<Aside type="note" title="솔트는 비밀이 아니에요">
솔트는 해시 바로 옆에 그대로 저장해요. 로그인 때 같은 솔트로 다시 해시해야 하니까요. 비밀로 따로 숨기는 값은 **페퍼**(pepper)라고 해요(아래 심화 참고).
</Aside>

### 느린 해시: SHA-256 한 번은 왜 안 되나

SHA-256은 **너무 빨라서** 비밀번호 저장에 맞지 않아요. 원래 큰 파일의 지문을 빨리 뽑으려고 만든 함수라서요. DB가 털리면 공격자는 후보 비밀번호를 해시해 보며 맞춰 보는데, 해시가 빠를수록 1초에 더 많이 시도할 수 있어요.

그래서 비밀번호 전용 해시는 **비용 인자**(work factor, 반복 횟수나 메모리 양)를 두고 **일부러 느리게** 만들어요. 정상 사용자는 로그인 한 번에 수십~수백 ms라 차이를 못 느끼지만, 수억 개를 맞춰 보는 공격자에겐 그 배수가 그대로 쌓여요. 하드웨어가 빨라지면 비용 인자만 올리면 돼요.

실험 예시로 노트북 CPU 한 코어에서 재 봤어요(Python 표준 라이브러리).

| 방식 | 한 번 걸린 시간 | 1초에 시도할 수 있는 횟수 |
|---|---|---|
| SHA-256 1회 | 약 0.19 µs | 약 520만 회 |
| PBKDF2-SHA256 60만 회 | 약 43 ms | 약 23회 |

**약 22만 배** 느려요. 반복 횟수를 10배 늘리면 시간도 거의 10배가 돼요(1,000회 0.1 ms → 10,000회 0.7 ms → 100,000회 7.0 ms). 비용 인자가 곧 "공격자가 써야 할 시간의 배수"예요. 단, 실제 공격자는 GPU를 쓰니 SHA-256 추측 속도는 이보다 훨씬 빨라요. 이 숫자는 비율 감각용이에요.

### OWASP 권장 알고리즘

OWASP Password Storage Cheat Sheet의 현재 권장값이에요(2026-11 확인). 위에서부터 우선순위예요.

| 알고리즘 | 언제 | 최소 설정 |
|---|---|---|
| **Argon2id** | 기본 1순위 | 메모리 19 MiB, 반복 t=2, 병렬 p=1 (동급 대안: 46 MiB·t=1 / 12 MiB·t=3 / 9 MiB·t=4 / 7 MiB·t=5, 모두 p=1) |
| **scrypt** | Argon2id를 못 쓸 때 | N=2^17(128 MiB), r=8, p=1 |
| **bcrypt** | 레거시 시스템 | work factor 10 이상, **입력 72바이트 제한** |
| **PBKDF2** | FIPS-140 준수가 필요할 때 | HMAC-SHA256 600,000회, HMAC-SHA512 220,000회 |

- **Argon2id·scrypt는 메모리도 많이 써요**(memory-hard). GPU나 전용 칩은 계산은 빠르지만 메모리를 많이 붙이기 어려워서, 병렬로 대량 추측하기가 더 힘들어져요.
- **bcrypt는 72바이트까지만 봐요.** 그보다 긴 비밀번호는 구현에 따라 잘리거나 거부돼요. 긴 패스프레이즈를 허용하는 서비스라면 주의해야 해요.
- PBKDF2-HMAC-SHA1은 레거시 전용이고 새로 쓰면 안 돼요.
- 해시 한 번은 보통 **1초 미만**이 되게 하고, 최적값은 **실제 서버에서 재 보고** 정해요. 너무 높이면 로그인 요청만으로 CPU가 바닥나는 **DoS**(서비스 거부) 위험이 생겨요.

### Spring의 비밀번호 저장: DelegatingPasswordEncoder

Spring Security는 `PasswordEncoderFactories.createDelegatingPasswordEncoder()`로 만드는 **DelegatingPasswordEncoder**를 권해요. 저장 값 앞에 어떤 알고리즘인지 이름표를 붙여요.

```text
{bcrypt}$2a$10$<솔트 22자><해시 31자>
{pbkdf2}...
{noop}password      ← 평문(테스트용, 운영 금지)
```

- 새로 저장할 땐 bcrypt를 쓰고 `{bcrypt}` 접두사를 붙여요.
- 검증할 땐 접두사를 보고 맞는 인코더에 맡겨요. 그래서 **알고리즘을 바꿔도 옛 해시를 계속 검증**할 수 있어요. 마이그레이션의 핵심이에요.
- `BCryptPasswordEncoder`의 기본 strength(비용)는 **10**이에요. Spring 문서는 내 서버에서 검증 한 번이 약 1초 걸리도록 조정하라고 해요. OWASP는 "1초 미만"이라고 해서, 실무에선 수백 ms~1초 사이에서 실측으로 정하면 돼요.
- bcrypt 문자열 하나에 버전(`2a`), 비용(`10`), 솔트가 다 들어 있어서 **솔트 컬럼을 따로 만들 필요가 없어요**.

```java
PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
String saved = encoder.encode("password123");   // "{bcrypt}$2a$10$..."
encoder.matches("password123", saved);          // true — 저장된 솔트·비용으로 다시 해시해 비교
```

스프링에서 로그인 흐름 전체는 [Spring Security](../../spring/spring-security/)를 보세요.

### 대칭키와 비대칭키 암호화

**대칭키 암호화**는 잠글 때와 열 때 **같은 키**를 써요. 빨라서 실제 데이터를 암호화하는 데 써요. 대표는 **AES**(미국 표준 FIPS 197, 128비트 블록, 키 128/192/256비트)예요. 약점은 그 키를 상대에게 어떻게 안전하게 건네느냐(**키 분배** 문제)예요.

**비대칭키 암호화**(공개키 암호화)는 **공개키·개인키 한 쌍**을 써요. 공개키로 잠근 건 개인키로만 열려요. 반대로 개인키로 서명한 건 공개키로 검증해요. 대표는 RSA와 **ECC**(타원곡선 암호: ECDSA, ECDH, Ed25519 등)예요.

| | 대칭키 | 비대칭키 |
|---|---|---|
| 키 | 하나를 양쪽이 공유 | 공개키·개인키 한 쌍 |
| 속도 | 빠름 | 훨씬 느림 |
| 대표 | AES(-GCM), ChaCha20-Poly1305 | RSA, ECC(ECDSA, ECDH, Ed25519) |
| 약점 | 키를 안전하게 나눠 주기 어려움 | 느림, 공개키가 진짜 그 사람 것인지 확인 필요 |
| 주 용도 | 실제 데이터 암호화, DB 컬럼 암호화 | 키 교환, 전자서명 |
| n명이 서로 통신할 때 키 수 | n(n-1)/2개 | 2n개(각자 한 쌍) |

### 하이브리드: 둘을 섞어 쓴다

비대칭키는 느려서 큰 데이터를 직접 암호화하지 않아요. 실제로는 **비대칭키로 대칭키를 안전하게 합의**하고, **본문은 그 대칭키로** 암호화해요. 우체통으로 열쇠만 보내고, 짐은 그 열쇠로 잠근 상자로 보내는 셈이에요.

HTTPS가 바로 이 방식이에요. 핸드셰이크와 인증서 확인은 [HTTPS와 TLS](../../web/https-tls/)에 자세히 있어요.

공개키가 정말 그 서버 것인지는 암호화만으로 알 수 없어요. 그래서 믿을 만한 기관(**CA**)이 "이 공개키는 이 도메인 것"이라고 서명해 준 **인증서**를 써요. 이것도 위 TLS 페이지에 있어요.

### MAC과 전자서명: 누가 만들었나

**MAC**(Message Authentication Code, 메시지 인증 코드)은 **공유 비밀키**로 만든 짧은 태그예요. 메시지가 안 바뀌었고, 키를 가진 쪽이 만들었다는 걸 보여 줘요. 해시 함수로 만드는 MAC이 **HMAC**(RFC 2104)이에요.

**전자서명**(digital signature)은 **개인키**로 만들고 **공개키**로 누구나 검증해요. 순서는 이래요.

1. 보내는 쪽이 문서를 해시해 지문을 만들어요.
2. 그 지문을 개인키로 서명해요.
3. 받는 쪽은 문서를 다시 해시하고, 공개키로 서명을 검증해 두 지문이 맞는지 봐요.

문서 전체가 아니라 해시에 서명하는 이유는, 비대칭 연산이 느리고 입력 크기에 제한이 있어서 짧은 지문에 하는 게 낫기 때문이에요. 서명 표준은 FIPS 186-5(RSA, ECDSA, EdDSA)예요.

| | MAC(HMAC) | 전자서명 |
|---|---|---|
| 키 | 공유 비밀키 1개 | 개인키로 서명, 공개키로 검증 |
| 무결성(안 바뀜) | O | O |
| 인증(누가 만듦) | O(키를 가진 쪽) | O(개인키 주인) |
| **부인 방지** | X | O |
| 속도 | 빠름 | 느림 |
| 예 | JWT HS256, 웹훅 서명, API 요청 서명 | JWT RS256, 인증서, 코드 서명 |

**부인 방지**(non-repudiation)는 "내가 보낸 거 아니에요"라고 발뺌할 수 없게 하는 성질이에요. MAC은 받는 쪽도 같은 키를 가지고 있어서 같은 태그를 만들 수 있어요. 그래서 제3자에게 "저 사람이 만들었다"를 증명하지 못해요. 서명은 개인키 주인만 만들 수 있으니 증명돼요.

JWT의 HS256(HMAC)과 RS256(RSA 서명)이 정확히 이 차이예요. → [쿠키·세션·JWT](../../web/cookie-session-jwt/)

<Aside type="caution" title="암호화와 서명은 보장하는 게 달라요">
상대 공개키로 암호화하면 **그 사람만 읽을 수 있다**(기밀성)는 보장만 생겨요. **보낸 사람이 누구인지**는 보장하지 않아요. 누구나 그 공개키로 암호화할 수 있으니까요. 보낸 사람 확인은 서명이 맡아요.
</Aside>

### 심화: 솔트와 페퍼

**페퍼**(pepper)는 모든 비밀번호에 공통으로 섞는 **비밀** 값이에요. 솔트와 달리 DB에 두지 않고 시크릿 매니저나 **HSM**(키를 안전하게 보관·연산하는 전용 하드웨어) 같은 곳에 따로 둬요. DB만 털렸을 땐 페퍼가 없으니 크래킹을 시작조차 못 해요.

| | 솔트 | 페퍼 |
|---|---|---|
| 비밀인가 | 아니요 | 예 |
| 값 | 비밀번호마다 다름 | 보통 전체 공통 |
| 저장 위치 | 해시 옆(DB) | DB 밖(시크릿 매니저·HSM) |
| 목적 | 레인보우 테이블 무력화, 같은 비번 다른 해시 | DB만 털렸을 때 한 겹 더 방어 |

NIST SP 800-63B(Rev.4)도 같은 생각이에요. 비밀번호는 솔트(최소 32비트)를 붙여 해시해야 하고, 비용 인자는 성능을 해치지 않는 선에서 높게 잡고, 알고리즘과 비용 정보를 비밀번호마다 같이 저장하라고 해요. 또 검증 서버만 아는 비밀키로 HMAC 같은 키 있는 해시를 한 번 더 하고, 그 키는 해시와 따로 보관하라고 해요. NIST는 "pepper"라는 단어를 쓰진 않지만 같은 개념이에요. NIST는 Argon2 같은 알고리즘 이름을 직접 고르지 않고 다른 NIST 지침(SP 800-132)을 따르라고만 해요.

### 심화: bcrypt 문자열 읽기

`$2a$10$` 다음에 22자 솔트, 31자 해시가 붙어요. `10`은 2^10번 반복이라는 뜻이라, 비용을 1 올리면 시간이 약 2배가 돼요. 10 → 14로 올리면 16배 느려져요.

### 심화: 인증 암호화(AEAD)와 AES-GCM

암호화만 하면 내용은 숨겨져도 누가 중간에 바꿨는지는 모를 수 있어요. **AEAD**(인증 암호화)는 암호화와 위변조 확인 태그를 **한 번에** 해 줘요. **AES-GCM**이 대표예요. TLS 1.3은 AEAD 방식만 허용해요.

GCM에서는 같은 키로 **nonce**(IV, 매번 달라야 하는 일회용 값)를 **절대 재사용하면 안 돼요**. 재사용하면 안전성이 무너져요(NIST SP 800-38D).

일반 지식으로, AES를 **ECB 모드**로 쓰면 같은 평문 블록이 같은 암호문 블록이 돼서 패턴이 드러나요. 그래서 GCM 같은 AEAD 모드를 써요.

### 심화: HMAC은 왜 그냥 `H(키 + 메시지)`가 아닌가

HMAC은 키를 두 번 섞어 해시를 두 번 하는 구조예요(RFC 2104). 일반 지식으로, 단순히 `SHA-256(키 + 메시지)`를 하면 SHA-256 같은 해시에선 **길이 확장 공격**(원래 메시지 뒤에 내용을 덧붙이고 맞는 태그를 계산해 내는 공격)이 가능해서 HMAC 구조를 써요. 직접 만들지 말고 언어가 주는 HMAC을 쓰면 돼요.

### 심화: "서명 = 개인키로 암호화"는 단순화예요

교과서는 RSA 서명을 "개인키로 암호화"라고 설명하곤 해요. 실제 규격(RFC 8017의 RSASSA-PSS, ECDSA)은 별도의 서명 연산이고, ECDSA에는 아예 암호화 연산이 없어요. 면접에선 **"개인키로 서명하고 공개키로 검증한다"**고 말하는 게 안전해요.

## 면접 질문

<details>
<summary>Q1. 해시와 암호화의 차이는요?</summary>

**답변(30초)** 가장 큰 차이는 되돌릴 수 있느냐예요. 해시는 입력을 고정 길이 값으로 바꾸는 단방향 함수라 원문으로 되돌릴 수 없고, 같은 입력이면 늘 같은 값이 나와서 "같은지 확인"하는 데 써요. 암호화는 키로 잠그고 키가 있으면 다시 원문을 꺼낼 수 있어서 "숨겼다가 다시 읽어야 하는" 데이터에 써요. 그래서 비밀번호는 해시, 주민번호처럼 다시 읽어야 하는 개인정보는 암호화로 저장해요.

**꼬리질문**
- Q. 해시에 충돌은 없나요? → 출력 길이가 정해져 있어서 이론상 반드시 있어요. 좋은 해시는 찾기 어려울 뿐이고, MD5·SHA-1은 실제로 충돌을 만들어서 보안 용도로 안 써요.
- Q. 주민번호를 해시로 저장하면 안 되나요? → 다시 읽어 보여 주거나 외부로 보내야 한다면 암호화(AES-GCM)여야 해요. 검색만 필요하면 HMAC 값을 따로 저장해 찾는 방법도 있어요.
</details>

<details>
<summary>Q2. Base64는 암호화인가요?</summary>

**답변(30초)** 아니요, 인코딩이에요. 바이너리 데이터를 64개의 안전한 문자로 바꿔 적을 뿐 키가 없어서 누구나 바로 원래대로 돌릴 수 있어요. 크기는 약 4/3배로 늘어나요. 그래서 JWT 페이로드도 Base64url이라 누구나 읽을 수 있고, 비밀 정보를 넣으면 안 돼요.

**꼬리질문**
- Q. 인코딩·해시·암호화를 한 줄씩 구분하면? → 인코딩은 키 없이 모양만 바꿈, 해시는 되돌릴 수 없는 지문, 암호화는 키로 숨기고 키로 꺼냄.
</details>

<details>
<summary>Q3. 대칭키와 비대칭키 암호화의 차이와 쓰임은요?</summary>

**답변(30초)** 대칭키는 잠그고 여는 키가 같아서 빠르지만, 그 키를 상대에게 안전하게 건네기 어려워요. 비대칭키는 공개키·개인키 쌍이라 공개키는 마음껏 나눠 줘도 되지만 훨씬 느려요. 그래서 실제로는 비대칭키로 대칭키를 안전하게 합의하고, 데이터는 대칭키로 암호화하는 하이브리드 방식을 써요. HTTPS가 대표 예예요.

**꼬리질문**
- Q. 공개키가 진짜 그 서버 것인지 어떻게 아나요? → CA가 서명한 인증서로 확인해요.
- Q. 100명이 서로 통신하면 키가 몇 개 필요한가요? → 대칭키는 100×99/2 = 4,950개, 비대칭키는 각자 한 쌍이라 200개예요.
</details>

<details>
<summary>Q4. 비밀번호를 DB에 어떻게 저장하나요? 솔트는 왜 쓰나요?</summary>

**답변(30초)** 암호화가 아니라 해시로 저장해요. 서버는 원문을 알 필요 없이, 로그인 때 입력값을 같은 방식으로 해시해 비교하면 되니까요. 이때 비밀번호마다 랜덤 솔트를 붙여요. 솔트가 없으면 같은 비밀번호는 같은 해시가 되고, 미리 계산한 레인보우 테이블로 바로 찾아져요. 그리고 SHA-256 같은 빠른 해시가 아니라 Argon2id나 bcrypt처럼 일부러 느린 해시를 써요.

**꼬리질문**
- Q. 솔트는 어디에 저장하나요? 비밀인가요? → 비밀이 아니라 해시 옆에 같이 저장해요. bcrypt는 해시 문자열 안에 솔트가 들어 있어요.
- Q. 솔트와 페퍼 차이는? → 솔트는 비번마다 다르고 공개, 페퍼는 비밀이고 DB 밖(시크릿 매니저·HSM)에 둬요.
</details>

<details>
<summary>Q5. SHA-256으로 비밀번호를 해시하면 안 되나요? 왜 bcrypt나 Argon2id를 쓰죠?</summary>

**답변(30초)** SHA-256은 안전한 해시지만 너무 빨라서 비밀번호용으론 부적합해요. DB가 털리면 공격자는 후보를 해시해 보며 맞추는데, 빠를수록 1초에 더 많이 시도해요. 한 번 재 보니 PBKDF2 60만 회가 SHA-256 1회보다 약 22만 배 느렸어요. 비용 인자로 일부러 느리게 만들면 사용자는 체감이 없고 공격자만 그 배수만큼 느려져요. Argon2id·scrypt는 메모리도 많이 써서 GPU 병렬 공격까지 어렵게 해요.

**꼬리질문**
- Q. OWASP 권장 순서는요? → Argon2id(최소 19 MiB, t=2, p=1) → scrypt(N=2^17, r=8, p=1) → bcrypt(레거시, work factor 10 이상) → PBKDF2(FIPS 필요 시, SHA256 60만 회).
- Q. bcrypt 주의점은? → 입력을 72바이트까지만 봐서 그 이상은 잘리거나 거부돼요.
</details>

<details>
<summary>Q6. 전자서명은 어떻게 동작하고 무엇을 보장하나요?</summary>

**답변(30초)** 보내는 쪽이 문서를 해시하고 그 해시에 개인키로 서명해 문서와 함께 보내요. 받는 쪽은 문서를 다시 해시하고, 보낸 사람의 공개키로 서명을 검증해 두 해시가 맞는지 확인해요. 맞으면 문서가 안 바뀌었다는 무결성, 개인키 주인이 만들었다는 인증, 나중에 발뺌할 수 없는 부인 방지가 보장돼요.

**꼬리질문**
- Q. 왜 문서 전체가 아니라 해시에 서명하나요? → 비대칭 연산은 느리고 입력 크기 제한이 있어서 짧은 지문에 서명해요.
- Q. 서명은 개인키로 암호화하는 건가요? → 교과서식 단순화예요. 실제 규격은 별도 서명 연산이고 ECDSA는 암호화가 없어서 "개인키로 서명, 공개키로 검증"이라고 말해요.
</details>

<details>
<summary>Q7. MAC(HMAC)과 전자서명의 차이는요? 부인 방지가 뭐죠?</summary>

**답변(30초)** 둘 다 무결성과 "누가 만들었는지"를 확인하지만 키가 달라요. HMAC은 양쪽이 같은 비밀키를 가져서 빠르지만, 받는 쪽도 같은 태그를 만들 수 있으니 제3자에게 보낸 사람을 증명하지 못해요. 전자서명은 개인키 주인만 만들 수 있어서 부인 방지, 즉 "내가 안 보냈다"고 발뺌할 수 없게 해 줘요. JWT HS256과 RS256이 이 차이예요.

**꼬리질문**
- Q. 그럼 언제 HMAC을 쓰나요? → 두 당사자끼리만 통신하고 속도가 중요할 때요. 웹훅 서명, API 요청 서명이 대표예요. 검증하는 쪽이 여럿이거나 부인 방지가 필요하면 서명을 써요.
</details>

<details>
<summary>Q8. 비밀번호 해시 알고리즘을 바꾸려면 어떻게 하나요?</summary>

**답변(30초)** 원문이 없으니 한 번에 새 알고리즘으로 다시 해시할 수는 없어요. 그래서 저장값에 알고리즘 이름표를 붙이고, 사용자가 로그인해 원문이 들어오는 순간 옛 방식으로 검증한 뒤 새 방식으로 다시 저장해요. Spring은 DelegatingPasswordEncoder가 `{bcrypt}` 같은 접두사로 이걸 지원해요. 오래 안 들어오는 계정은 옛 해시를 그대로 새 느린 해시로 한 번 감싸 두는 방법을 같이 써요.

**꼬리질문**
- Q. bcrypt 비용을 너무 높이면? → 로그인 한 번이 비싸져서 트래픽이 몰리면 CPU가 바닥나요. 해시 하나 1초 미만, 서버에서 실측해 정하고 로그인 API에는 레이트 리밋을 걸어요.
</details>

<details>
<summary>Q9. AES-GCM은 뭐가 좋나요? nonce를 재사용하면요?</summary>

**답변(30초)** AES-GCM은 인증 암호화(AEAD)라서 내용을 숨기는 것과 위변조 확인 태그를 한 번에 해 줘요. 그래서 암호문을 누가 바꾸면 복호화 단계에서 바로 걸려요. TLS 1.3도 AEAD만 허용해요. 단, 같은 키로 nonce를 재사용하면 안전성이 무너지니 매번 새 nonce를 써야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 회원 비밀번호가 솔트 없이 SHA-256 한 번으로 저장돼 있어요. 서비스를 멈추지 않고 안전한 방식으로 옮기려면?</summary>

**상황 파악**
원문은 서버에 없어요. 그래서 "모든 행을 Argon2id로 다시 해시"하는 배치는 불가능해요. 지금 상태는 솔트가 없고 해시가 빨라서, DB가 털리면 흔한 비밀번호부터 금방 뚫리는 상태예요. 목표는 무중단 이관, 그리고 이관이 끝날 때까지의 위험도 줄이는 거예요.

**원인 후보(왜 위험한가)**
- 솔트 없음 → 같은 비밀번호는 같은 해시, 레인보우 테이블로 바로 조회돼요.
- 빠른 해시 → 실험 예시로 SHA-256 1회는 느린 해시보다 수십만 배 빨라요. 공격자 추측 속도가 그만큼 빨라요.

**해결책**

| 방법 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| A. 로그인 시 재해시 | 로그인 때 입력값으로 옛 SHA-256 검증 → 성공하면 Argon2id(또는 bcrypt)로 새로 저장 | 단순, 결과가 깔끔한 정식 해시 | 로그인 안 하는 휴면 계정은 계속 약한 해시로 남음 |
| B. 옛 해시 감싸기 | 저장된 SHA-256 값을 입력으로 느린 해시를 씌워 일괄 변환: `bcrypt(sha256(pw))` | 배치 한 번으로 **전체 계정이 즉시** 솔트+느린 해시 보호 | 검증 로직이 한 단계 복잡, 이후 로그인 때 정식 해시로 다시 바꿔야 깔끔 |

Spring이라면 DelegatingPasswordEncoder에 옛 형식용 id를 등록하고, 새 저장은 `{bcrypt}`로 해요. 접두사로 어떤 방식인지 구분하니 옛 해시와 새 해시가 한 테이블에 섞여 있어도 돼요.

**내가 고를 방법**
A와 B를 같이 써요. 먼저 B로 배치를 돌려 모든 계정을 바로 "솔트 + 느린 해시" 상태로 만들어요. 위험한 기간을 짧게 만드는 게 가장 중요하니까요. 그다음 로그인 때 원문이 들어오면 A처럼 정식 Argon2id로 다시 저장해요. 일정 기간 뒤에도 남은 휴면 계정은 비밀번호 재설정을 요구해요. 비용 인자는 운영 서버에서 해시 하나가 1초 미만이 되도록 실측해 정하고, 로그인 API에는 레이트 리밋을 걸어 DoS를 막아요.

**채점 포인트**: 원문 없음(일괄 재해시 불가), 솔트, 느린 해시(Argon2id/bcrypt), 로그인 시 재해시, 옛 해시 감싸기, 알고리즘 식별자(`{id}` 접두사), 휴면 계정 처리, 무중단, 비용 인자 실측.
</details>

<details>
<summary>상황: 회원 DB 덤프가 외부로 유출됐어요. 피해 범위를 어떻게 판단하고 어떻게 대응하나요?</summary>

**상황 파악**
먼저 "무엇이 어떤 형태로" 나갔는지가 피해 범위를 정해요. 같은 유출이라도 비밀번호가 어떻게 저장됐는지, 개인정보가 암호화됐는지, 키가 같이 나갔는지에 따라 결과가 크게 달라요.

**원인 후보(피해 범위 판단 기준)**

| 저장 상태 | 피해 |
|---|---|
| 비밀번호 평문 또는 복호화 가능한 암호화 + 키도 같이 유출 | 전원 즉시 노출 |
| 솔트 없는 빠른 해시(MD5, SHA-256 1회) | 흔한 비밀번호는 금방 뚫림, 같은 비번 쓰는 사람 동시 노출 |
| 솔트 + 느린 해시(bcrypt, Argon2id) | 크래킹 비용이 크지만 **약한 비밀번호는 여전히 뚫릴 수 있음** |
| 위 + 페퍼(DB 밖 보관) | 페퍼가 안 나갔다면 DB만으로 크래킹 시작 불가 |
| 개인정보 AES 암호화, 키는 KMS에 따로 | 키가 안 나갔다면 암호문만 유출 |

**해결책**
- A. **전원 강제 비밀번호 재설정 + 세션·토큰 무효화**: 가장 확실하지만 사용자 불편과 이탈이 커요.
- B. **위험도별 대응**: 느린 해시라면 즉시 전원 재설정 대신 변경 안내, 의심 로그인 탐지 강화, 추가 인증을 걸어요. 불편은 적지만 약한 비밀번호 계정이 뚫릴 시간이 남아요.

공통으로 할 일: 유출 경로 차단, 같은 비밀번호를 다른 사이트에서 쓴 사람에게 변경 안내(크리덴셜 스터핑 대비), DB 접근 키·API 키·서명 키 교체, 관련 기관 신고와 사용자 고지.

**내가 고를 방법**
비밀번호가 빠른 해시나 복호화 가능한 형태였다면 A예요. 사실상 원문이 나간 것과 같아서요. 솔트 + 느린 해시였다면 B로 시작하되, 리프레시 토큰과 세션은 바로 끊고 다음 로그인 때 비밀번호 변경을 요구해요. 사고 후엔 저장 방식을 Argon2id + 페퍼로 올리고, 개인정보 암호화 키는 DB와 분리해 KMS에 두도록 바꿔요.

**채점 포인트**: 저장 방식별 피해 차이, 솔트·느린 해시도 약한 비번은 뚫림, 키 분리 여부, 비밀번호 재설정, 세션·토큰 무효화, 키 교체, 크리덴셜 스터핑 안내, 사후 개선(Argon2id·페퍼·KMS).
</details>

<details>
<summary>상황: 외부 제휴사 시스템과 API를 주고받아요. 요청이 중간에 위변조되거나 남이 보낸 가짜 요청을 어떻게 막나요?</summary>

**상황 파악**
HTTPS만으로는 "전송 중 엿보기·변조"는 막지만, 우리 API를 호출한 게 정말 그 제휴사인지, 예전 요청을 누가 다시 보낸 건 아닌지는 따로 확인해야 해요. 막아야 할 건 세 가지예요. 내용 변조, 가짜 발신자, **재전송 공격**(replay attack, 가로챈 정상 요청을 그대로 다시 보내기).

**원인 후보**
- 요청 본문에 무결성 확인 값이 없음
- API 키만 헤더에 실어 보냄 → 키가 한 번 새면 누구나 위조
- 같은 요청을 다시 보내도 서버가 구분 못 함

**해결책**

| 방법 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| A. HMAC-SHA256 서명 | 공유 비밀키로 `HMAC(키, 타임스탬프 + 메서드 + 경로 + 본문)`을 계산해 헤더에 실음. 서버가 같은 계산 후 비교 | 빠르고 구현 쉬움, 키 자체는 전송 안 됨 | 양쪽이 같은 키라 부인 방지 없음, 키 공유·교체 관리 필요 |
| B. 비대칭 서명 | 제휴사가 개인키로 서명, 우리는 공개키로 검증 | 부인 방지, 검증하는 쪽이 여럿이어도 개인키는 한 곳에만 | 느리고 키 관리·구현이 더 복잡 |

어느 쪽이든 재전송을 막으려면 **타임스탬프**를 서명 대상에 넣고, 서버 시간과 일정 범위(예: 5분) 넘게 차이 나면 거부해요. 범위 안의 재전송까지 막으려면 **nonce**(요청마다 다른 일회용 값)를 함께 넣고 처리한 nonce를 그 시간 동안 저장해 중복을 거부해요. 서명 비교는 **상수 시간 비교**(앞 글자부터 다른 곳에서 바로 멈추지 않고 끝까지 비교해, 응답 시간으로 정답을 추측하지 못하게 하는 방식)로 해요.

**내가 고를 방법**
제휴사가 하나이고 양쪽 다 우리가 관리하는 서버라면 A를 고를 거예요. HMAC-SHA256 + 타임스탬프 + nonce, 상수 시간 비교, 키는 시크릿 매니저에 두고 정기 교체(교체 기간엔 옛 키·새 키 둘 다 허용)해요. 금액이 큰 결제 지시처럼 나중에 "누가 보냈나"를 다툴 수 있는 요청이거나 여러 곳이 검증해야 하면 B로 가요.

**채점 포인트**: HMAC(공유키) vs 서명(부인 방지), 서명 대상에 본문·경로·타임스탬프 포함, 재전송 공격, 타임스탬프 허용 범위, nonce 저장, 상수 시간 비교, 키 보관·교체, HTTPS는 기본.
</details>

## 필기 포인트

- 해시 = 단방향·고정 길이. SHA-256 출력 **256비트(32바이트)**. SHA-2 계열 표준 FIPS 180-4.
- 해시 성질: **역상 저항, 제2역상 저항, 충돌 저항**. 충돌은 "없음"이 아니라 "찾기 어려움". MD5·SHA-1은 충돌이 실제로 발견됨.
- **Base64는 인코딩**(키 없음, 누구나 복원, 약 4/3배). 암호화 아님.
- 솔트는 **공개**, 비밀번호마다 다름. 페퍼는 **비밀**, DB 밖에 보관.
- 대칭키: 같은 키, 빠름, 대표 **AES**(블록 128비트, 키 128/192/256). 키 수 **n(n-1)/2**.
- 비대칭키: 공개키·개인키, 느림, RSA·ECC. 키 수 **2n**. 공개키로 암호화 → 개인키로 복호화 / 개인키로 서명 → 공개키로 검증.
- **MAC은 부인 방지 X**, 전자서명은 무결성·인증·**부인 방지 O**.
- 전자서명은 문서의 **해시**에 서명.
- AES-GCM = AEAD(기밀성 + 무결성). GCM nonce 재사용 금지. ECB는 패턴 노출.
