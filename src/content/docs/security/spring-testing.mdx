:::tip[한 줄 요약]
`@SpringBootTest`는 앱 전체 컨텍스트를 띄우고, `@WebMvcTest`·`@DataJpaTest` 같은 **슬라이스 테스트**는 웹 층이나 JPA 층에 필요한 빈만 띄워 훨씬 가벼워요. 스프링은 한 번 띄운 컨텍스트를 **캐시**해 재사용하니, 설정을 제각각 바꾸면 매번 새로 떠서 느려져요. 테스트의 `@Transactional`은 끝나면 **자동 롤백**돼 편하지만 커밋 때만 드러나는 버그를 가릴 수 있고, DB는 H2 대신 **Testcontainers**로 운영과 같은 DB를 띄워 확인해요.
:::

:::note[처음이라면 여기까지]
① 스프링 테스트는 "앱 전체를 띄우는 테스트"와 "한 층만 띄우는 테스트(슬라이스)"로 나뉘어요. 한 층만 띄우는 쪽이 훨씬 빨라요.

② 스프링은 테스트용으로 띄운 앱을 저장해 두고 다음 테스트에서 다시 써요. 테스트마다 설정을 조금씩 다르게 하면 이 재사용이 깨져 느려져요.

③ 테스트에 `@Transactional`을 붙이면 끝날 때 DB 변경이 취소돼요. 편하지만 "실제로 저장될 때" 나는 오류를 못 볼 수 있어요.

④ 면접에선 질문 1~3번(@SpringBootTest vs @WebMvcTest, @DataJpaTest, @MockitoBean)부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

식당 위생 검사를 떠올려 보세요. 가게 전체를 열고 손님까지 받아 보는 검사는 확실하지만 준비가 오래 걸려요. 이게 **`@SpringBootTest`**예요. 앱의 모든 **빈**(bean, 스프링이 만들어 관리하는 객체)을 다 띄워요.

주방만 따로 점검하거나, 냉장고만 따로 점검하면 훨씬 빨라요. 이게 **슬라이스 테스트**예요. 컨트롤러가 요청을 잘 받는지만 보려면 웹 층만(`@WebMvcTest`), 쿼리가 잘 도는지만 보려면 JPA 층만(`@DataJpaTest`) 띄워요.

또 한 번 열어 둔 가게는 다음 검사관이 그대로 이어서 써요. 매번 문을 닫고 다시 열면 시간이 많이 드니까요. 이게 **컨텍스트 캐시**예요.

마지막으로, 연습용 주방은 장난감이 아니라 **실제 가게와 같은 기종의 화덕**이어야 해요. 장난감 화덕(H2)에선 잘 구워지던 피자가 진짜 화덕(MySQL)에선 탈 수 있거든요. 이게 **Testcontainers**를 쓰는 이유예요.

단, 실제로는 슬라이스도 메인 애플리케이션 클래스를 출발점으로 삼기 때문에 완전히 분리된 건 아니에요. 아래에서 그 함정도 다뤄요.

## 제대로 알기

### @SpringBootTest: 앱 전체를 띄워요

`@SpringBootTest`는 실제 실행할 때처럼 `SpringApplication`으로 **애플리케이션 컨텍스트 전체**(앱의 모든 빈이 들어 있는 상자)를 띄워요. 웹 환경은 `webEnvironment`로 골라요.

| 값 | 무엇을 띄우나 | 언제 |
|---|---|---|
| `MOCK`(기본) | 내장 서버 없이 모의 서블릿 환경 | MockMvc로 컨트롤러~DB까지 한 스레드에서 확인 |
| `RANDOM_PORT` | 진짜 내장 서버를 빈 포트로 | 실제 HTTP 요청으로 확인(`@LocalServerPort`로 포트 주입) |
| `DEFINED_PORT` | 진짜 서버를 설정 포트(기본 8080)로 | 포트가 정해져야 할 때 |
| `NONE` | 웹 환경 없음 | 배치·메시지 소비자 같은 비웹 앱 |

가장 확실하지만 가장 무거워요. 빈이 많을수록 뜨는 시간이 길어요.

### 슬라이스 테스트: 한 층만 띄워요

**슬라이스 테스트**(test slice)는 특정 층에 필요한 자동 설정만 켜고, 빈을 찾는 범위(컴포넌트 스캔)를 좁혀요.

| | `@WebMvcTest` | `@DataJpaTest` | `@JsonTest` |
|---|---|---|---|
| 확인할 것 | 요청 매핑, 검증, 응답 형식, 예외 처리 | 쿼리, 엔티티 매핑, 리포지토리 | 객체 ↔ JSON 변환 형태 |
| 뜨는 빈 | `@Controller`, `@ControllerAdvice`, `Converter`, `Filter`, `HandlerInterceptor`, `WebMvcConfigurer`, `HandlerMethodArgumentResolver`, JSON 컴포넌트 | `@Entity` 스캔, Spring Data JPA 리포지토리, DataSource | JSON 매퍼(Jackson, Gson, Jsonb) |
| 안 뜨는 빈 | `@Service`, `@Repository`, 일반 `@Component`, `@ConfigurationProperties` | 일반 `@Component`, `@ConfigurationProperties`, 웹 층 | 나머지 거의 전부 |
| 같이 주는 도구 | `MockMvc`(AssertJ가 있으면 `MockMvcTester`도) | `TestEntityManager`, `JdbcTemplate` | `JacksonTester` 등 |
| DB | 없음 | 클래스패스에 임베디드 DB가 있으면 그걸로 교체 | 없음 |
| 트랜잭션 | — | **기본으로 각 테스트 끝에 롤백** | — |

다른 슬라이스도 있어요. `@WebFluxTest`, `@JdbcTest`, `@DataJdbcTest`, `@DataRedisTest`, `@DataMongoTest`, `@RestClientTest` 등이에요.

`@WebMvcTest`에서 가장 많이 하는 실수는 "서비스가 자동으로 뜰 것"이라고 생각하는 거예요. 서비스는 안 뜨니까, 컨트롤러가 의존하는 서비스는 직접 대역으로 넣어야 해요. 안 넣으면 의존성 주입이 실패해요.

```java
@WebMvcTest(UserController.class)   // 컨트롤러 하나로 범위를 더 좁힘
class UserControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean UserService userService;   // 안 뜨는 서비스 자리에 대역

    @Test
    void 회원_조회() throws Exception {
        given(userService.find(1L)).willReturn(new UserDto(1L, "kim"));
        mvc.perform(get("/users/1"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.name").value("kim"));
    }
}
```

```java
@DataJpaTest
class UserRepositoryTest {
    @Autowired UserRepository repo;
    @Autowired TestEntityManager em;

    @Test
    void 이메일로_찾기() {
        em.persist(new User("a@b.com"));
        em.flush();   // INSERT를 실제로 DB에 보냄
        em.clear();   // 1차 캐시 비우기 → 아래 조회가 진짜 SELECT로 감
        assertThat(repo.findByEmail("a@b.com")).isPresent();
    }
}
```

### @MockitoBean: 컨텍스트 안의 빈을 대역으로 바꿔요

[테스트 더블](../testing-basics/)에서 본 Mockito의 `@Mock`은 스프링과 상관없는 그냥 Mockito 객체예요. 반면 **`@MockitoBean`**은 **스프링 컨텍스트 안에 있는 빈을 Mockito 대역으로 바꿔 끼워요**(없으면 새로 만들어요).

| | `@Mock` | `@MockitoBean` |
|---|---|---|
| 소속 | Mockito | Spring Framework(6.2부터) |
| 스프링 컨텍스트 | 필요 없음 | 컨텍스트의 빈을 교체 |
| 쓰는 곳 | 순수 단위 테스트(`MockitoExtension`) | `@WebMvcTest`, `@SpringBootTest` |
| 리셋 | `MockitoExtension`이 테스트마다 새로 만듦 | 컨텍스트와 함께 재사용, 기본으로 각 테스트 후 자동 리셋 |

<Aside type="caution" title="@MockBean은 이제 쓰지 마세요">
예전엔 Spring Boot의 `@MockBean`·`@SpyBean`을 썼어요. **Spring Boot 3.4에서 deprecated**(곧 없앨 예정이라는 표시)됐고, **Spring Boot 4.0에서 제거**됐어요. 대신 Spring Framework 6.2에서 들어온 `@MockitoBean`·`@MockitoSpyBean`을 써요. 둘의 동작이 완전히 같지는 않아서, 예를 들어 `@Configuration` 클래스 안에 두던 것은 테스트 클래스 필드로 옮겨야 할 수 있어요.
</Aside>

`@MockitoSpyBean`은 원래 빈을 버리지 않고 **감싸서** 진짜 메서드를 부르면서 호출을 기록해요. 일부 메서드만 답을 바꾸고 싶을 때 써요.

### 컨텍스트 캐시: 띄운 앱을 재사용해요

컨텍스트를 띄우는 데는 수 초가 걸려요. 그래서 스프링 TestContext는 한 번 띄운 컨텍스트를 **JVM 안의 static 캐시**에 넣어 두고, **설정이 같은 테스트끼리 재사용**해요.

"설정이 같다"를 판단하는 **캐시 키**에는 이런 것들이 들어가요.

- 설정 클래스·위치(`@ContextConfiguration`, `@SpringBootTest`의 설정)
- 활성 프로필(`@ActiveProfiles`)
- 테스트 프로퍼티(`@TestPropertySource`), `@DynamicPropertySource`
- **빈 오버라이드(`@MockitoBean` 등)의 조합**

그래서 테스트 클래스마다 `@MockitoBean` 조합이나 프로필이 조금씩 다르면, 키가 달라져 **클래스마다 컨텍스트를 새로 띄워요.** 테스트가 갑자기 느려지는 가장 흔한 원인이에요.

<Aside type="danger" title="@DirtiesContext는 비싼 버튼이에요">
`@DirtiesContext`는 지금 컨텍스트를 캐시에서 지워서, 다음 테스트가 **컨텍스트 전체를 다시 띄우게** 해요. 테스트가 빈 정의나 싱글턴 빈의 상태를 망가뜨렸을 때만 써요. DB 데이터 정리 용도로 습관처럼 붙이면 전체 테스트 시간이 크게 늘어요. 데이터 정리는 롤백이나 삭제(truncate)로 해요.
</Aside>

### 테스트의 @Transactional: 자동 롤백의 장점과 함정

테스트 메서드(또는 클래스)에 `@Transactional`을 붙이면, 스프링이 테스트 시작 때 트랜잭션을 열고 **끝나면 기본으로 롤백**해요. → 트랜잭션 자체는 [@Transactional 완전 정리](../../spring/transactional/)

**장점**: 테스트마다 넣은 데이터가 자동으로 사라져서 다음 테스트에 영향을 안 줘요. 정리 코드가 필요 없어요.

**함정 1: 커밋되지 않아서 못 잡는 버그.** JPA는 `save()`를 해도 SQL을 바로 보내지 않고 **영속성 컨텍스트**(JPA가 엔티티를 잠시 들고 있는 메모리 공간)에 모아 뒀다가 **flush**(모아 둔 SQL을 DB로 보내기) 때 보내요. 테스트가 롤백으로 끝나면 flush가 한 번도 안 일어날 수 있어요. 스프링 공식 문서도 "flush하지 않으면 테스트는 통과하는데 운영에서는 같은 코드가 예외를 던지는 **거짓 양성**(false positive, 실제론 문제인데 통과로 나옴)이 생긴다"고 경고해요.

| | 테스트(@Transactional, 롤백) | 운영(커밋) |
|---|---|---|
| 중복 이메일 `save()` | 메모리에만 있다 롤백 → **통과** | 커밋 때 INSERT → 유니크 제약 위반 |
| 대처 | `em.flush()`로 SQL을 강제로 보내 확인 | — |

**함정 2: 롤백이 안 되는 경우.** 트랜잭션은 **현재 스레드**에 묶여요. 그래서 다른 스레드나 다른 트랜잭션에서 일어난 일은 테스트 롤백에서 빠져요.

- `@SpringBootTest(webEnvironment = RANDOM_PORT)` 또는 `DEFINED_PORT`: 테스트가 보낸 HTTP 요청은 **서버 쪽 다른 스레드**에서 처리돼요. 서버에서 시작한 트랜잭션은 거기서 커밋되고, 테스트 끝 롤백으로 **되돌아가지 않아요.** 데이터가 DB에 남아요.
- 테스트 안에서 새 스레드로 실행되는 코드(예: `assertTimeoutPreemptively`): 테스트 트랜잭션 밖이라 **실제로 커밋돼요.**
- `REQUIRES_NEW`로 새 트랜잭션을 여는 코드: 별도 트랜잭션이라 롤백에서 빠져요.

반면 `MOCK` 환경의 MockMvc는 테스트와 **같은 스레드**에서 컨트롤러를 부르니 같은 트랜잭션에 묶여 롤백돼요.

필요하면 `@Commit`(또는 `@Rollback(false)`)으로 커밋하게 바꿀 수 있어요.

### Testcontainers: H2 대신 진짜 DB로

**Testcontainers**는 테스트할 때 **Docker**(프로그램을 격리된 상자에 담아 띄우는 도구)로 MySQL·Redis·Kafka 같은 진짜 서비스를 잠깐 띄워 주는 라이브러리예요.

왜 H2(자바로 만든 가벼운 인메모리 DB)로는 부족할까요? H2 공식 문서는 MySQL 호환 모드(`MODE=MySQL`)도 **DB 간 차이 중 작은 일부만** 흉내 낸다고 스스로 밝혀요.

| 차이 | H2(MySQL 모드) | 운영 MySQL |
|---|---|---|
| `INSERT IGNORE`, `REPLACE INTO` | 부분 지원 | 지원 |
| 문자열 비교 | 기본 대소문자 구분 | 기본 콜레이션은 구분 안 함 |
| MySQL 전용 문법·함수, 네이티브 쿼리 | 없거나 다르게 동작할 수 있음 | 그대로 동작 |
| 락·격리 수준 동작 | MySQL(InnoDB)과 같다는 보장 없음 | 실제 동작 |

그래서 "H2에선 통과, 운영에선 실패"가 생겨요. Testcontainers로 **운영과 같은 종류·같은 버전의 DB**를 띄우면 이 차이가 사라져요. 대신 Docker가 필요하고 컨테이너가 뜨는 데 몇 초 걸려요. 스프링 Boot 문서가 `@DataJpaTest`에 속도 때문에 인메모리 DB를 권하는 것도 이 트레이드오프 때문이에요(속도 vs 운영과 같음).

**`@ServiceConnection`**(Spring Boot 3.1부터, `spring-boot-testcontainers`)을 붙이면 컨테이너의 접속 주소·계정을 Boot가 알아서 읽어 DataSource에 연결해요. `spring.datasource.url`을 손으로 안 써도 돼요.

```java
@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfig {
    @Bean
    @ServiceConnection   // 접속 정보를 자동으로 연결
    MySQLContainer mysql() {
        return new MySQLContainer("mysql:8.0.36");  // 운영과 같은 버전으로
    }
}

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE) // 임베디드 DB로 바꾸지 않음
@Import(TestcontainersConfig.class)
class OrderRepositoryMySqlTest { /* ... */ }
```

`@DataJpaTest`는 기본으로 임베디드 DB로 바꿔 끼우려고 하니, 진짜 DB를 쓰려면 `replace = NONE`이 필요해요.

### 테스트 격리: 테스트끼리 서로 몰라야 해요

좋은 테스트는 **어떤 순서로 돌려도, 혼자 돌려도** 결과가 같아요. 깨지는 흔한 이유와 대처예요.

| 원인 | 증상 | 대처 |
|---|---|---|
| `RANDOM_PORT` 테스트가 남긴 데이터 | 다음 테스트가 가끔 실패(플래키) | `@AfterEach`에서 삭제·truncate, 테스트마다 고유한 데이터(이메일 등) |
| 공유 컨텍스트의 싱글턴 빈 상태 변경 | 순서에 따라 결과가 바뀜 | 상태를 되돌리거나, 정말 필요할 때만 `@DirtiesContext` |
| `@MockitoBean` 설정이 다음 테스트로 새어 나감 | 엉뚱한 답이 돌아옴 | 기본 리셋(각 테스트 후)을 끄지 않기 |
| 새 스레드·`REQUIRES_NEW`로 커밋된 데이터 | 롤백했는데 데이터가 남음 | 직접 정리 |

### 심화: 컨텍스트 캐시 세부

- 캐시 크기는 기본 **32개**이고, 넘으면 가장 오래 안 쓴 것부터(LRU) 닫아요. `spring.test.context.cache.maxSize` JVM 시스템 프로퍼티로 바꿀 수 있어요.
- 캐시가 몇 번 맞았는지는 `org.springframework.test.context.cache` 로거를 DEBUG로 켜면 보여요.
- 캐시는 **JVM 안**에만 있어요. 빌드 도구가 테스트 클래스마다 JVM을 새로 띄우도록(fork) 설정돼 있으면 캐시가 매번 사라져 크게 느려져요.
- `@MockitoBean` 필드의 타입·이름이 다르면 다른 컨텍스트가 필요해져요. 공식 문서는 필드 이름을 일관되게 하면 추가 컨텍스트를 피할 수 있다고 해요. 여기서 나온 실무 패턴이 **공통 베이스 테스트 클래스에 `@MockitoBean` 조합을 모아 두는 것**이에요(문서의 직접 권장이 아니라 이 원리에서 나온 방법이에요).

### 심화: @MockitoBean 세부

- 기본 전략은 "있으면 교체, 없으면 생성"이에요. `enforceOverride = true`면 교체할 빈이 꼭 있어야 해요.
- 교체된 대역은 **AOP 프록시로 감싸지지 않아요.** 원래 빈에 붙던 `@Transactional` 같은 프록시 기능이 대역엔 없어요.
- `@MockitoSpyBean`은 감쌀 빈이 정확히 하나여야 해요. 원래 빈이 `@Transactional` 등으로 프록시되는 빈이면, 프록시가 spy를 감싸요.
- 필드뿐 아니라 생성자 파라미터, 클래스 위(`types` 속성, 6.2.2+)에도 선언할 수 있어요.

### 심화: 슬라이스가 깨지는 흔한 이유

슬라이스도 `@SpringBootApplication` 클래스를 설정의 출발점으로 써요. 그래서 메인 클래스에 `@EnableMongoAuditing` 같은 특정 영역용 설정을 붙여 두면, 상관없는 `@WebMvcTest`까지 그걸 켜려다 실패해요. 이런 설정은 **별도 `@Configuration` 클래스로 분리**해요.

### 심화: Spring Boot 4.0에서 바뀐 것

- `@MockBean`·`@SpyBean` 제거(위 참고).
- 기술별 테스트 스타터가 생겼어요(예: `spring-boot-starter-webmvc-test`, `spring-boot-starter-data-jpa-test`). 모두 `spring-boot-starter-test`를 같이 가져와요.
- `@SpringBootTest`만으로는 MockMvc를 더 이상 주지 않아요. `@AutoConfigureMockMvc`를 붙여야 해요.
- JSON 컴포넌트용 `@JsonComponent`는 `@JacksonComponent`로 바뀌고 deprecated됐어요.

### 심화: 테스트 트랜잭션 세부와 Testcontainers 생명주기

- `@BeforeTransaction`/`@AfterTransaction`은 트랜잭션 **밖**에서 실행돼요.
- `TestTransaction.flagForCommit()`, `end()`, `start()`로 테스트 도중에 커밋하고 새 트랜잭션을 시작할 수 있어요.
- 테스트가 관리하는 트랜잭션에서 전파 속성은 `NOT_SUPPORTED`·`NEVER`만 쓸 수 있고, `rollbackFor`/`noRollbackFor`는 지원하지 않아요. `@DataJpaTest`에서 트랜잭션을 끄려면 `@Transactional(propagation = Propagation.NOT_SUPPORTED)`를 붙여요.
- `@PostPersist` 같은 JPA 생명주기 콜백도 flush/clear 없이는 호출되지 않을 수 있어요.
- Testcontainers를 붙이는 방법은 셋이에요. (a) 위 예시처럼 컨테이너를 `@Bean`으로 등록(스프링이 생명주기를 관리, 컨텍스트 캐시와 가장 안전), (b) JUnit 확장 `@Testcontainers` + `@Container` 필드, (c) `@DynamicPropertySource`로 주소를 직접 등록.
- (b)에서 static `@Container`는 **테스트 클래스가 끝나면 멈추는데**, 스프링 컨텍스트는 캐시돼 다음 클래스에서 재사용될 수 있어요. 그러면 멈춘 컨테이너를 가리키는 빈이 실패해요. 공식 문서는 (a) 방식이나 `@ImportTestcontainers`를 권해요.
- Testcontainers 2.x의 MySQL 모듈 좌표는 `org.testcontainers:testcontainers-mysql`이에요. JDBC URL을 `jdbc:tc:mysql:8.0.36:///dbname`처럼 쓰는 방법도 있어요.

## 면접 질문

<details>
<summary>Q. @SpringBootTest와 @WebMvcTest의 차이는 무엇인가요?</summary>

**답변(30초)**
`@SpringBootTest`는 앱 전체 컨텍스트를 띄워 모든 빈이 다 올라오고, `@WebMvcTest`는 컨트롤러·필터·인터셉터·JSON 변환 같은 MVC 층 빈만 띄워요. 그래서 `@WebMvcTest`는 훨씬 빠르지만 서비스와 리포지토리가 안 떠서, 컨트롤러가 쓰는 서비스는 `@MockitoBean`으로 넣어 줘야 해요. 요청 매핑·검증·응답 형식만 볼 땐 `@WebMvcTest`, 층을 넘는 흐름을 볼 땐 `@SpringBootTest`를 써요.

**꼬리질문**
- Q. `@WebMvcTest`에서 서비스를 안 넣으면요? → 서비스 빈이 없어서 컨트롤러 의존성 주입이 실패해요.
- Q. `@SpringBootTest`의 기본 웹 환경은? → `MOCK`이에요. 진짜 서버 없이 모의 서블릿 환경이에요.
</details>

<details>
<summary>Q. @DataJpaTest는 무엇을 띄우고, 트랜잭션은 어떻게 되나요?</summary>

**답변(30초)**
엔티티와 Spring Data JPA 리포지토리, DataSource 같은 JPA 층만 띄우고, 서비스나 웹 층은 안 띄워요. 클래스패스에 임베디드 DB가 있으면 그걸로 바꿔 끼우고, SQL 로그도 기본으로 켜요. 각 테스트는 기본으로 트랜잭션 안에서 돌고 끝나면 롤백돼요. 진짜 DB를 쓰려면 `@AutoConfigureTestDatabase(replace = NONE)`를 붙여요.

**꼬리질문**
- Q. `@DataJpaTest`는 항상 H2를 쓰나요? → 아니요. 임베디드 DB가 클래스패스에 있을 때만 그걸로 교체해요.
- Q. 롤백을 끄려면? → `@Transactional(propagation = NOT_SUPPORTED)`나 `@Commit`을 써요.
</details>

<details>
<summary>Q. @MockitoBean은 무엇이고, Mockito의 @Mock과 무엇이 다른가요?</summary>

**답변(30초)**
`@Mock`은 스프링과 무관한 순수 Mockito 객체이고, `@MockitoBean`은 스프링 컨텍스트 안의 빈을 Mockito 대역으로 교체해요. 그래서 `@Mock`은 스프링 없이 도는 단위 테스트에, `@MockitoBean`은 `@WebMvcTest`처럼 컨텍스트를 띄우는 테스트에 써요. 예전엔 Boot의 `@MockBean`을 썼지만 Boot 3.4에서 deprecated, 4.0에서 제거돼서 지금은 Spring Framework 6.2의 `@MockitoBean`을 써요.

**꼬리질문**
- Q. `@MockitoBean`을 남발하면 왜 느려지나요? → 빈 오버라이드 조합이 컨텍스트 캐시 키에 들어가서, 조합이 다른 클래스마다 컨텍스트를 새로 띄워요.
- Q. `@MockitoBean`으로 바꾼 빈에도 `@Transactional`이 적용되나요? → 아니요. 대역은 AOP 프록시로 감싸지지 않아요.
</details>

<details>
<summary>Q. 테스트에 @Transactional을 붙이면 어떻게 되고, 단점은 무엇인가요?</summary>

**답변(30초)**
테스트가 끝나면 기본으로 롤백돼서 데이터 정리가 자동으로 돼요. 하지만 커밋을 안 하니 flush가 안 일어나 유니크 제약 위반 같은 버그가 테스트에선 안 보일 수 있다고 공식 문서가 경고해요. 또 테스트 내내 영속성 컨텍스트가 살아 있어서 지연 로딩이 운영과 다르게 성공할 수 있어요. 그리고 `RANDOM_PORT` 서버 쪽 트랜잭션이나 `REQUIRES_NEW`, 새 스레드 작업은 롤백되지 않아요. 그래서 `flush()`·`clear()`로 확인하고, 핵심 흐름은 트랜잭션 없이 돌린 뒤 직접 정리해요.

**꼬리질문**
- Q. 테스트 도중에 커밋하려면? → `@Commit`이나 `TestTransaction.flagForCommit()`과 `end()`를 써요.
</details>

<details>
<summary>Q. 스프링 테스트가 느린 이유와 개선 방법은 무엇인가요?</summary>

**답변(30초)**
대부분 컨텍스트를 너무 자주 새로 띄워서예요. 스프링은 설정이 같은 테스트끼리 컨텍스트를 캐시해 재사용하는데, 클래스마다 `@MockitoBean` 조합이나 프로필, 테스트 프로퍼티가 다르면 캐시 키가 달라져 매번 새로 떠요. `@DirtiesContext`도 다음 테스트에서 전체를 다시 띄우게 해요. 그래서 설정을 공통 베이스 클래스로 통일하고, `@DirtiesContext`를 빼고, 한 층만 보는 테스트는 슬라이스로 내려요.

**꼬리질문**
- Q. 캐시가 잘 맞는지 어떻게 확인하나요? → `org.springframework.test.context.cache` 로거를 DEBUG로 켜면 통계가 나와요.
- Q. 빌드 도구 설정 때문에 느려질 수도 있나요? → 테스트마다 JVM을 fork하면 캐시가 JVM과 함께 사라져서 느려져요.
</details>

<details>
<summary>Q. 통합 테스트에서 H2 대신 Testcontainers를 쓰는 이유는 무엇인가요?</summary>

**답변(30초)**
운영과 같은 DB로 테스트하려고요. H2는 MySQL 호환 모드에서도 차이의 작은 일부만 흉내 낸다고 공식 문서가 밝혀요. 그래서 MySQL 전용 문법이나 네이티브 쿼리, 대소문자 비교 같은 콜레이션 차이, 락 동작이 H2에선 다르게 나올 수 있어요. Testcontainers는 Docker로 운영과 같은 버전의 MySQL을 띄우고, Boot 3.1부터는 `@ServiceConnection`으로 접속 정보도 자동 연결돼요. 대신 Docker가 필요하고 기동에 몇 초 걸려요.

**꼬리질문**
- Q. 기동 시간이 부담되면? → 컨테이너를 `@Bean`으로 두고 컨텍스트 캐시와 함께 여러 테스트 클래스가 공유하게 해요.
</details>

<details>
<summary>Q. RANDOM_PORT 테스트에서 @Transactional을 붙였는데 데이터가 남는 이유는?</summary>

**답변(30초)**
트랜잭션은 스레드에 묶이는데, `RANDOM_PORT`에선 테스트 스레드와 요청을 처리하는 서버 스레드가 달라요. 테스트 쪽 트랜잭션은 롤백되지만, 서버 쪽에서 시작한 트랜잭션은 거기서 커밋돼 DB에 남아요. 그래서 다음 테스트가 남은 데이터 때문에 가끔 실패하는 플래키 테스트가 생겨요. `@AfterEach`에서 직접 지우거나, 테스트마다 고유한 데이터를 써요.

**꼬리질문**
- Q. MOCK 환경의 MockMvc는 왜 롤백되나요? → 같은 스레드에서 컨트롤러를 호출해서 테스트 트랜잭션에 함께 묶이기 때문이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 테스트 스위트 전체를 돌리는 데 20분이 걸려서 개발자들이 로컬에서 테스트를 안 돌리고 PR을 올려요. 로그를 보니 스프링 컨텍스트가 수십 번 새로 뜨고 있어요. 원인과 개선 방법은?</summary>

**상황 파악**
컨텍스트가 수십 번 뜬다는 건 **컨텍스트 캐시가 재사용되지 못하고 있다**는 뜻이에요. 컨텍스트 한 번에 수 초씩 걸리니, 수십 번이면 그것만으로 몇 분이 사라져요. 게다가 `@SpringBootTest`로 다 띄울 필요가 없는 테스트도 많을 가능성이 커요.

**원인 후보**
1. 테스트 클래스마다 `@MockitoBean` 조합이 달라 캐시 키가 매번 다름.
2. `@ActiveProfiles`, `@TestPropertySource`가 클래스마다 제각각.
3. 데이터 정리용으로 `@DirtiesContext`를 습관처럼 붙임 → 매번 전체 재로딩.
4. 빌드 도구가 테스트마다 JVM을 fork해서 캐시가 사라짐.
5. 컨트롤러·리포지토리만 보면 되는 테스트도 전부 `@SpringBootTest`.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 공통 베이스 테스트 클래스에 `@MockitoBean` 조합·프로필·프로퍼티를 모아 통일 | 캐시가 맞아 컨텍스트 수가 확 줄어듦 | 안 쓰는 대역도 같이 뜸, 베이스 클래스가 비대해질 수 있음 |
| B. `@DirtiesContext` 제거, 데이터는 롤백·truncate로 정리 | 재로딩 비용 제거 | 상태를 망가뜨리는 테스트를 찾아 고쳐야 함 |
| C. 한 층만 보는 테스트를 `@WebMvcTest`/`@DataJpaTest`로 내리고, 순수 로직은 스프링 없이 Mockito 단위 테스트로 | 컨텍스트 자체가 작아지거나 없어짐 | 슬라이스도 조합마다 캐시되니 여기도 통일 필요, 층을 넘는 버그는 못 봄 |
| D. fork 설정 확인(JVM 재사용) | 설정 한 줄로 캐시가 살아남 | 테스트끼리 JVM 상태를 공유하니 격리를 더 신경 써야 함 |

**내가 고를 방법**
먼저 `org.springframework.test.context.cache` 로거를 DEBUG로 켜서 컨텍스트가 몇 개 뜨는지, 어느 클래스에서 캐시가 빗나가는지 확인해요. 그다음 D(fork)를 점검하고, B로 `@DirtiesContext`를 걷어내요. 남은 `@SpringBootTest`는 A로 설정을 통일해 컨텍스트를 몇 개로 줄여요. 동시에 C로 피라미드를 바로잡아서, 컨트롤러 테스트는 `@WebMvcTest`, 쿼리 테스트는 `@DataJpaTest`, 비즈니스 규칙은 순수 단위 테스트로 옮겨요. 전체 흐름 `@SpringBootTest`는 핵심 몇 개만 남겨요. 목표는 커밋 때 돌리는 묶음을 10분 안에 끝내는 거예요.

**채점 포인트**: 컨텍스트 캐시와 캐시 키(@MockitoBean 조합·프로필·프로퍼티), @DirtiesContext 비용, 로그로 원인 측정, fork 시 캐시 소멸, 베이스 클래스 통일, 슬라이스·순수 단위 테스트로 내리기(피라미드), 트레이드오프(불필요한 대역, 층 넘는 버그).
</details>

<details>
<summary>상황: H2로 돌리는 리포지토리 테스트는 전부 통과했는데, 운영 MySQL에 배포하자 일부 쿼리가 문법 오류로 실패하고, 대소문자만 다른 이메일 중복 검사가 다르게 동작했어요. 원인과 해결 방법은?</summary>

**상황 파악**
테스트 DB(H2)와 운영 DB(MySQL)가 달라서 생긴 문제예요. H2의 MySQL 호환 모드는 차이의 작은 일부만 흉내 내요. 테스트가 "H2에서 잘 된다"를 확인했을 뿐, "MySQL에서 잘 된다"는 확인하지 못했어요.

**원인 후보**
1. MySQL 전용 문법·함수·네이티브 쿼리(예: `ON DUPLICATE KEY UPDATE`, JSON 함수, `FOR UPDATE SKIP LOCKED`)를 H2가 지원하지 않거나 다르게 처리.
2. 문자열 비교: H2는 기본 대소문자 구분, MySQL 기본 콜레이션은 구분 안 함 → 중복 검사 결과가 달라짐.
3. 락·격리 수준 동작이 다르다는 걸 테스트가 못 봄.
4. 스키마를 운영 마이그레이션(Flyway 등)이 아니라 JPA 자동 생성으로 만들어 인덱스·제약이 운영과 다름.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Testcontainers로 운영과 같은 버전의 MySQL을 띄우고 `@ServiceConnection` 연결, `@DataJpaTest`엔 `replace = NONE` | 운영과 같은 문법·콜레이션·락 동작 | Docker 필요, 컨테이너 기동 수 초 |
| B. H2 호환 모드 옵션을 더 맞추기 | 빠름, 설정만 바꿈 | 작은 일부만 흉내 내서 근본 해결 아님 |
| C. 공용 개발 DB에 붙여 테스트 | 실제 MySQL | 테스트끼리 데이터 충돌, 격리 안 됨, CI에서 불안정 |
| D. MySQL 전용 쿼리를 안 쓰도록 제한 | DB 무관 | 성능·기능을 포기, 콜레이션 차이는 여전 |

**내가 고를 방법**
A를 골라요. 리포지토리·쿼리 테스트는 운영과 같은 버전의 MySQL 컨테이너로 돌려요. 컨테이너는 `@TestConfiguration`의 `@Bean` + `@ServiceConnection`으로 등록해 스프링이 생명주기를 관리하게 하고, 컨텍스트 캐시와 함께 여러 테스트 클래스가 공유하게 해서 기동 비용을 한 번으로 줄여요. 스키마도 운영과 같은 마이그레이션 스크립트로 만들어요. 기동 시간이 부담인 순수 로직 테스트는 DB 없이 단위 테스트로 남겨요(피라미드 유지). 이번 두 버그는 먼저 재현 테스트로 만들어 둬요.

**채점 포인트**: H2 호환 모드 한계(공식 문서가 일부만 구현이라고 밝힘), 방언 SQL·콜레이션·락 차이, Testcontainers + @ServiceConnection(Boot 3.1+), replace = NONE, 컨테이너 공유로 기동 비용 절감, 트레이드오프(Docker·속도 vs 운영 일치), 재현 테스트.
</details>

<details>
<summary>상황: 주문 조회 기능의 통합 테스트(@SpringBootTest + @Transactional)는 통과하는데, 운영에서는 주문 상세 API에서 LazyInitializationException이 나요. 왜 테스트에서는 안 잡혔을까요?</summary>

**상황 파악**
`LazyInitializationException`은 **지연 로딩**(연관 엔티티를 처음 쓸 때 DB에서 가져오는 방식)할 엔티티를, 영속성 컨텍스트가 이미 닫힌 뒤에 건드릴 때 나요. 운영에선 서비스의 트랜잭션이 끝난 뒤(예: 컨트롤러나 JSON 변환 중) 연관 엔티티에 접근해서 터진 것으로 보여요. → [JPA 영속성 컨텍스트](../../spring/jpa-persistence-context/)

**원인 후보(아래는 공식 문서 문장이 아니라 테스트 트랜잭션 원리에서 추론한 것이에요)**
1. 테스트 메서드 전체가 하나의 트랜잭션이라, 서비스 메서드가 끝난 뒤에도 영속성 컨텍스트가 테스트 끝까지 살아 있어요. 그래서 테스트에선 지연 로딩이 성공해요.
2. 테스트에서 저장한 엔티티를 같은 영속성 컨텍스트의 1차 캐시에서 그대로 꺼내 와서, DB 조회도 지연 로딩도 실제로 일어나지 않았을 수 있어요.
3. 운영은 OSIV(뷰까지 영속성 컨텍스트를 열어 두는 설정)를 끈 상태라 서비스 트랜잭션이 끝나면 컨텍스트가 닫혀요.

**해결책과 트레이드오프**

테스트 쪽(버그를 잡게 만들기):

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 저장 후 `flush()` + `clear()` 하고 다시 조회 | 1차 캐시 착시 제거, 실제 SELECT 확인 | 여전히 테스트 트랜잭션 안이라 지연 로딩 문제는 가려질 수 있음 |
| B. 핵심 흐름 테스트는 `@Transactional` 없이 실행(서비스 경계 밖에서 결과 검증), 끝나고 직접 정리 | 운영과 같은 트랜잭션 경계라 예외가 재현됨 | 데이터 정리 코드 필요 |
| C. MockMvc나 HTTP로 API 응답(JSON 변환까지)을 끝까지 확인 | 컨트롤러·직렬화 단계의 접근까지 확인 | 느려짐 |

코드 쪽(버그 고치기):

| 방법 | 장점 | 단점 |
|---|---|---|
| D. 필요한 연관을 서비스 안에서 페치 조인 등으로 미리 가져오고 DTO로 변환해 반환 | 트랜잭션 안에서 다 끝남, N+1도 같이 관리 | 조회 용도별 쿼리가 늘어남 |
| E. OSIV 켜기 | 코드 수정 최소 | DB 커넥션을 응답 끝까지 잡아 둬 트래픽이 많으면 부담 |

**내가 고를 방법**
먼저 B로 테스트에서 `@Transactional`을 빼고 같은 API를 호출해 예외를 **재현**해요. 그다음 D로 서비스 안에서 필요한 연관을 함께 조회해 DTO로 바꿔 돌려줘요. 리포지토리 테스트에는 A의 `flush()`·`clear()` 습관을 들여서 1차 캐시 착시를 막아요. E는 커넥션 점유 부담 때문에 고르지 않아요. 앞으로는 "테스트 트랜잭션이 운영의 트랜잭션 경계를 가린다"는 점을 팀 테스트 가이드에 적어 둬요.

**채점 포인트**: 지연 로딩과 영속성 컨텍스트 생명주기, 테스트 트랜잭션이 경계를 넓혀 버그를 가림(추론임을 밝힘), 1차 캐시 착시와 flush/clear, @Transactional 없는 재현 테스트, 서비스 안 페치 조인 + DTO, OSIV 트레이드오프.
</details>
