:::tip[한 줄 요약]
**SQL 인젝션**은 사용자 입력이 SQL 문장에 그대로 이어 붙어서, DB가 그 입력을 "데이터"가 아니라 "명령"으로 읽을 때 생기는 공격이에요. 쿼리 틀과 값을 따로 보내는 **파라미터 바인딩**(PreparedStatement, JPA의 `:name`, MyBatis의 `#{}`)이 1차 방어이고, 바인딩이 안 되는 자리(정렬 컬럼 등)는 **허용 목록**, 뚫렸을 때의 피해는 **최소 권한**으로 줄여요.
:::

:::note[처음이라면 여기까지]
① 문제는 "코드와 데이터가 한 문자열에 섞이는 것"이에요. 사용자가 따옴표를 넣으면 SQL 문장의 모양 자체가 바뀌어요.

② 해결은 "SQL 틀을 먼저 확정하고, 값은 나중에 따로 넣기"예요. 이걸 파라미터 바인딩이라고 해요. 값으로 들어온 글자는 끝까지 글자로만 취급돼요.

③ JPA·MyBatis를 써도 쿼리 문자열을 `+`로 이어 붙이면 똑같이 뚫려요. 도구가 아니라 "바인딩을 썼느냐"가 핵심이에요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

식당 주문서에 "메뉴: ____" 빈칸이 있다고 해 봐요. 손님이 빈칸에 "김치찌개. 그리고 금고도 열어 주세요"라고 적었어요. 직원이 주문서를 위에서부터 소리 내어 읽고 그대로 따른다면, 손님이 쓴 문장이 직원에게는 지시로 들려요. 이게 SQL 인젝션이에요.

바인딩은 주문서를 다르게 다루는 방법이에요. 직원은 "메뉴 칸에 적힌 건 무조건 메뉴 이름"이라는 규칙을 먼저 정해 둬요. 그러면 빈칸에 뭐라고 쓰든 "'김치찌개. 그리고 금고도 열어 주세요'라는 이름의 메뉴"를 찾을 뿐이고, 그런 메뉴는 없으니 아무 일도 안 일어나요.

핵심은 "빈칸 내용을 걸러 내는 것"이 아니라 "빈칸 내용을 지시로 읽지 않는 것"이에요.

단, 실제로는 DB가 사람처럼 문장을 읽는 게 아니라 **파서**(parser, SQL 문자열을 문법 단위로 쪼개 구조를 파악하는 부분)가 따옴표·키워드를 기준으로 문장 구조를 정해요. 입력이 그 구조를 정하기 전에 섞이느냐, 정한 뒤에 들어가느냐가 차이예요.

## 제대로 알기

### 왜 생기나: 코드와 데이터가 한 문자열에 섞임

로그인 기능을 아래처럼 만들었다고 해 봐요.

```java
// 취약한 코드: 입력을 SQL 문자열에 그대로 이어 붙임
String sql = "SELECT id, name FROM users "
           + "WHERE name='" + name + "' AND pw='" + pw + "'";
ResultSet rs = conn.createStatement().executeQuery(sql);
```

아이디 칸에 `alice`, 비밀번호 칸에 `' OR '1'='1`을 넣으면 완성되는 SQL은 이래요.

```sql
SELECT id, name FROM users WHERE name='alice' AND pw='' OR '1'='1'
```

사용자가 넣은 첫 번째 `'`가 비밀번호 문자열을 **닫아 버렸고**, 그 뒤의 `OR '1'='1'`은 이제 값이 아니라 SQL 조건이 됐어요. SQL에서는 **AND가 OR보다 먼저 묶이기 때문에** 이 조건은 `(name='alice' AND pw='') OR '1'='1'`로 읽혀요. 뒤쪽 `'1'='1'`이 항상 참이니 WHERE 전체가 항상 참이 되고, 테이블의 모든 행이 나와요. 로그인 코드가 "결과가 1행 이상이면 성공"이라면 비밀번호 없이 들어가지는 거예요.

### 어떻게 막나: 파라미터 바인딩

**파라미터 바인딩**(parameter binding)은 SQL 틀에 값 자리(`?`)만 비워 두고, 값은 따로 넘기는 방식이에요. Java에서는 JDBC의 **PreparedStatement**(미리 준비된 SQL 문을 담는 객체)를 써요.

```java
// 안전한 코드: 틀과 값을 분리
String sql = "SELECT id, name FROM users WHERE name=? AND pw=?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, name);  // 1번 ? 자리에 값
ps.setString(2, pw);    // 2번 ? 자리에 값
ResultSet rs = ps.executeQuery();
```

DB는 `WHERE name=? AND pw=?`라는 구조를 먼저 확정해요. 그다음 들어온 `' OR '1'='1`은 따옴표가 몇 개 있든 "비밀번호 문자열 하나"로만 비교돼요. 그런 비밀번호를 가진 사용자는 없으니 0행이에요.

Java 공식 문서에 따르면 PreparedStatement의 SQL은 미리 컴파일돼 객체에 저장되고, `setString`·`setInt`처럼 값의 타입에 맞는 setter로 `?` 자리를 채워요. 같은 쿼리를 여러 번 효율적으로 실행할 수 있다는 장점도 있어요.

<Aside type="caution" title="PreparedStatement를 썼는데도 뚫리는 경우">
`conn.prepareStatement("... WHERE pw='" + pw + "'")`처럼 **SQL 문자열을 `+`로 만든 뒤** 넘기면 아무 소용이 없어요. 클래스 이름이 아니라 `?` 자리에 값을 넣었는지가 핵심이에요.
</Aside>

### 실험 예시: 실제로 돌려 보면

임시 MySQL에 `users` 테이블(alice, bob, carol 3행)을 만들고 한 번 재 본 결과예요.

| 실험 | 입력 | 결과 | 의미 |
|---|---|---|---|
| ① 문자열 연결 | 비밀번호 칸에 `' OR '1'='1` | **3행(전체)** | WHERE가 항상 참이 됨 |
| ② 바인딩 | 같은 입력 | **0행** | 입력 전체가 문자열 하나로 비교됨 |
| ③ 바인딩 | 정상 아이디·비밀번호 | 1행 | 정상 동작은 그대로 |
| ④ SELECT 권한만 가진 계정 | `DROP TABLE users` 실행 | 권한 거부 에러 | 뚫려도 피해 범위가 줄어듦 |
| ⑤ `ORDER BY ?`에 `name` 바인딩 + DESC | 정렬 컬럼을 값으로 넘김 | 에러 없이 alice, bob, carol(정렬 안 됨) | 구조 부분은 바인딩이 안 됨 |
| ⑤ 비교: `ORDER BY name DESC` 직접 작성 | - | carol, bob, alice | 원래 기대한 결과 |

<Aside type="note" title="'안 먹혔다'가 안전하다는 뜻은 아니에요">
처음엔 아이디 칸에 `' OR '1'='1`을 넣었는데 0행이 나왔어요. 뒤에 `AND pw='nope'`가 붙으면서 `name='' OR ('1'='1' AND pw='nope')`로 묶였기 때문이에요. AND가 먼저 묶이는 우선순위 때문에 우연히 막힌 것뿐이고, 다른 칸에 넣거나 SQL 주석(`-- `)으로 뒷부분을 잘라 내면 얼마든지 결과가 바뀌어요. 문자열 연결 코드는 "이 입력으로 안 뚫렸다"로 안전을 판단할 수 없어요.
</Aside>

### 방어 순서 (OWASP 권고)

**OWASP**(웹 보안 지침을 만드는 비영리 단체)의 SQL Injection Prevention Cheat Sheet는 1차 방어 세 가지를 아래 순서로 두고, 최소 권한을 추가 방어로 따로 둬요.

| 순서 | 방법 | 언제 | 한계 |
|---|---|---|---|
| 1 | 파라미터 바인딩(PreparedStatement, JPA·Spring Data 파라미터, MyBatis `#{}`) | 값이 들어가는 모든 자리 | 테이블명·컬럼명·정렬 방향엔 못 씀 |
| 2 | 허용 목록 매핑 | 바인딩이 안 되는 구조 자리 | 목록을 코드로 관리해야 함 |
| 3 | 수동 이스케이프(최후 수단) | 정말 다른 방법이 없을 때 | DB 종류·설정마다 규칙이 달라 실수하기 쉬움, OWASP가 강력히 비권장 |
| 추가 | 최소 권한 | 항상 | 막는 게 아니라 피해를 줄임 |

예전 판 Cheat Sheet는 "안전하게 만든 Stored Procedure"를 2번째 방어로 넣었는데, 지금 판은 이를 주의 사항으로 옮겼어요(아래 심화 참고).

**허용 목록**(allow-list)은 "받아도 되는 값을 코드에 미리 적어 두고, 그 밖은 전부 거부"하는 방식이에요. **최소 권한**은 애플리케이션 DB 계정에 꼭 필요한 권한(예: SELECT·INSERT·UPDATE)만 주고, 관리자 권한이나 테이블 삭제 권한은 주지 않는 거예요. 앱마다 계정을 나누고, **뷰**(View, 테이블 일부만 보여 주는 가상 테이블)로 보이는 범위를 줄이는 것도 같은 생각이에요.

### 바인딩이 안 되는 자리: 허용 목록

`?`에는 **값**만 들어가요. 테이블명, 컬럼명, `ORDER BY`의 정렬 컬럼, `ASC`/`DESC` 같은 SQL 구조는 바인딩할 수 없어요. 실험 ⑤처럼 억지로 바인딩하면 에러는 안 나지만 `'name'`이라는 **상수 문자열**로 정렬하게 돼서 정렬이 안 돼요. 조용히 틀리는 버그라 더 위험해요.

그래서 사용자가 보낸 값을 SQL에 직접 붙이지 않고, 코드가 가진 안전한 문자열로 바꿔서 붙여요.

```java
// 사용자 입력 → 코드가 정해 둔 컬럼명으로만 매핑
private static final Map<String, String> SORT_COLUMNS =
    Map.of("name", "name", "created", "created_at");

String column = SORT_COLUMNS.getOrDefault(sortParam, "id"); // 없으면 기본값
String dir = "desc".equalsIgnoreCase(dirParam) ? "DESC" : "ASC";
String sql = "SELECT id, name FROM users ORDER BY " + column + " " + dir;
```

마지막 줄에도 `+`가 있지만, 이어 붙이는 건 사용자 입력이 아니라 **코드에 적힌 문자열**뿐이라 안전해요.

### 입력 검증과 출력 인코딩은 다른 일

| 구분 | 언제 | 질문 | 대표 용도 |
|---|---|---|---|
| **입력 검증**(input validation) | 들어올 때 | "업무 규칙에 맞는 값인가?" | 형식·길이·범위 확인, 허용 목록 |
| **출력 인코딩**(output encoding) | 내보낼 때 | "이 위치(HTML 등)에서 코드로 읽히지 않는가?" | XSS 방어 |
| **파라미터 바인딩** | SQL 실행할 때 | "값이 SQL 구조를 바꿀 수 없는가?" | SQL 인젝션 방어 |

OWASP Input Validation Cheat Sheet는 입력 검증을 두 가지로 나눠요.

- **문법적 검증**: 형식·타입이 맞나(예: 우편번호가 숫자 5자리인가)
- **의미적 검증**: 업무상 말이 되나(예: 종료일이 시작일보다 뒤인가)

검증은 허용 목록으로 하고, "나쁜 문자열을 다 찾아 막는" **거부 목록**(deny-list)은 피하라고 해요. 그리고 검증은 반드시 서버에서 해요. 브라우저(클라이언트) 검증은 사용자가 쉽게 우회할 수 있어서 편의 기능일 뿐이에요.

중요한 건, **입력 검증은 SQL 인젝션 방어를 대신하지 못한다**는 점이에요. 작은따옴표를 막으면 `O'Brien` 같은 정상 이름만 거부되고, 쿼리를 문자열 연결로 만드는 근본 문제는 그대로 남아요. SQL 인젝션은 바인딩, XSS는 출력 인코딩이 답이고, 검증은 그 위에 얹는 보조예요. XSS는 [XSS와 CSRF](../xss-csrf/)에서 다뤄요.

### 심화: JPA·Spring Data에서의 함정

JPA를 쓰면 SQL 대신 **JPQL**(엔티티 기준으로 쓰는 JPA의 쿼리 언어, Hibernate에선 HQL)을 써요. JPQL도 문자열이라, 이어 붙이면 **JPQL 인젝션**이 돼요. Hibernate 공식 가이드도 사용자 입력은 반드시 파라미터로 넘기고, 쿼리 조각을 사용자 입력과 이어 붙이는 건 "극도로 위험하다"고 적어 둬요.

```java
// 취약: JPQL 문자열 연결
em.createQuery("select u from User u where u.name = '" + name + "'");

// 안전: 이름 파라미터 바인딩
em.createQuery("select u from User u where u.name = :name", User.class)
  .setParameter("name", name);
```

Spring Data JPA의 `@Query`에서는 위치 바인딩 `?1` 또는 이름 바인딩 `:name` + `@Param("name")`을 써요. 둘 다 바인딩이라 안전해요. `nativeQuery = true`로 쓰는 SQL도 바인딩만 쓰면 안전하고, 문자열을 이어 붙이면 똑같이 취약해요.

정렬은 `Sort`나 `PageRequest`로 넘기면 Spring Data가 정렬 속성이 **엔티티 속성과 맞는지 확인**하고, 아니면 예외를 던져요. 함수 호출이 든 정렬은 기본으로 거부하고, 꼭 필요하면 `JpaSort.unsafe(...)`로 명시해야 해요. 이름부터 "안전하지 않음"이니 사용자 입력을 넣지 않는 게 맞아요(문서에 그렇게 적힌 건 아니고 이름에서 나오는 판단이에요).

검색어 LIKE도 주의할 점이 있어요. 파생 쿼리(`findByNameContaining` 같은 메서드 이름 쿼리)는 `%`, `_` 와일드카드를 글자로 이스케이프해 줘요. `@Query`에서 직접 LIKE를 쓰면 이 처리를 따로 해야 해요. 이건 인젝션이라기보다 "검색어에 `%`를 넣으면 전부 걸리는" 문제예요.

<Aside type="note" title="확인 범위">
JPA 표준 명세(Jakarta Persistence) 본문의 파라미터 관련 문구는 직접 확인하지 못했고, 여기서는 Hibernate·Spring Data 공식 문서를 근거로 했어요.
</Aside>

### 심화: MyBatis의 `#{}`와 `${}`

MyBatis는 XML에 SQL을 직접 써요. 여기서 두 표기가 완전히 달라요.

| 표기 | 동작 | 안전? |
|---|---|---|
| `#{name}` | PreparedStatement의 `?` 자리로 바뀌고 값은 바인딩 | 안전 |
| `${column}` | 값을 손대지 않고 SQL 문자열에 그대로 끼워 넣음 | 사용자 입력이면 위험 |

MyBatis 문서도 `ORDER BY ${columnName}`을 예로 들며, 사용자 입력을 이렇게 그대로 받는 건 SQL 인젝션이 가능하니 막거나 직접 검사하라고 경고해요. 정렬처럼 `${}`가 꼭 필요한 자리는 Java 코드에서 허용 목록으로 바꾼 값만 넘겨요.

### 심화: Stored Procedure는 안전한가

**Stored Procedure**(DB 안에 저장해 두고 이름으로 호출하는 SQL 묶음)를 호출할 때 인자를 바인딩하면 호출 자체는 안전해요. 하지만 프로시저 **안에서** 인자를 문자열로 이어 붙여 동적 SQL을 만들면 그대로 인젝션이 가능해요. 안에서도 정적 SQL이나 바인딩을 써야 해요. "프로시저니까 안전"이 아니라 "어디서든 문자열 연결이 없어야 안전"이에요.

## 면접 질문

<details>
<summary>Q. SQL 인젝션이 뭔가요?</summary>

**답변(30초)** 사용자 입력이 SQL 문자열에 그대로 이어 붙어서, DB가 그 입력을 데이터가 아니라 SQL 명령으로 해석하는 공격이에요. 예를 들어 비밀번호 칸에 `' OR '1'='1`을 넣으면 따옴표가 문자열을 닫고 뒤의 OR 조건이 붙어서 WHERE가 항상 참이 돼요. 그러면 비밀번호 없이 로그인되거나 전체 데이터가 조회돼요. 원인은 코드와 데이터가 한 문자열에 섞이는 거예요.

**꼬리질문**
- Q. 왜 `OR '1'='1'`이면 전체가 나오나요? → AND가 OR보다 먼저 묶여 `(name=... AND pw='') OR 참`이 되니까 항상 참이에요.
- Q. 피해는 조회뿐인가요? → DB 계정 권한에 따라 수정·삭제까지 가능해요. 그래서 최소 권한이 필요해요.
</details>

<details>
<summary>Q. SQL 인젝션은 어떻게 막나요? PreparedStatement는 왜 안전한가요?</summary>

**답변(30초)** 1차 방어는 파라미터 바인딩이에요. PreparedStatement는 `?`가 있는 SQL 틀을 먼저 DB에 보내 구조를 확정하고, 값은 따로 넘겨요. 구조가 이미 정해졌으니 값에 따옴표나 OR가 들어 있어도 문자열 하나로만 비교되고, SQL 문법으로 다시 해석되지 않아요. 바인딩이 안 되는 자리는 허용 목록으로, 뚫렸을 때를 대비해 최소 권한 계정을 써요.

**꼬리질문**
- Q. PreparedStatement를 쓰면 무조건 안전한가요? → 아니요. SQL 문자열을 `+`로 만든 뒤 넘기면 똑같이 취약해요. `?` 바인딩을 했는지가 핵심이에요.
- Q. 이스케이프로 막으면 안 되나요? → OWASP는 최후 수단으로만 봐요. DB 종류·설정마다 규칙이 달라 빠뜨리기 쉬워요.
</details>

<details>
<summary>Q. JPA나 MyBatis를 쓰면 SQL 인젝션에서 안전한가요?</summary>

**답변(30초)** 바인딩을 쓸 때만 안전해요. JPA도 JPQL을 문자열로 이어 붙이면 JPQL 인젝션이 생기고, `:name` + `setParameter`나 Spring Data의 `?1`, `@Param`을 써야 해요. MyBatis는 `#{}`는 바인딩이라 안전하지만 `${}`는 값을 SQL에 그대로 끼워 넣어서 사용자 입력이면 위험해요. 도구가 아니라 쿼리를 어떻게 썼는지가 안전을 정해요.

**꼬리질문**
- Q. 그럼 `${}`는 언제 쓰나요? → 정렬 컬럼처럼 바인딩이 안 되는 구조 자리에만, 그것도 허용 목록으로 걸러 낸 값만 넣어요.
- Q. 네이티브 쿼리는요? → 바인딩을 쓰면 안전, 문자열 연결이면 똑같이 취약해요.
</details>

<details>
<summary>Q. 정렬 컬럼이나 테이블명을 사용자가 고르게 하려면 어떻게 하나요?</summary>

**답변(30초)** 이런 SQL 구조 부분은 `?`로 바인딩할 수 없어서 허용 목록으로 처리해요. 사용자가 보낸 값을 키로 코드에 미리 정해 둔 컬럼명을 찾고, 없으면 기본값을 쓰거나 거부해요. SQL에는 사용자 입력이 아니라 코드가 가진 문자열만 붙어요. `ORDER BY ?`로 바인딩하면 에러 없이 상수로 정렬돼 정렬이 안 되는 조용한 버그가 생겨요.

**꼬리질문**
- Q. Spring Data JPA에선요? → `Sort`/`PageRequest`를 쓰면 엔티티 속성과 맞는지 검사해 줘요. 그래도 API 쪽에서 허용 목록을 두면 에러 메시지·의도가 분명해져요.
- Q. ASC/DESC는요? → 두 값 중 하나로만 매핑하고 나머지는 기본값으로 처리해요.
</details>

<details>
<summary>Q. 입력 검증과 출력 인코딩은 어떻게 다른가요? 입력 검증만으로 인젝션을 막을 수 있나요?</summary>

**답변(30초)** 입력 검증은 들어올 때 값이 업무 규칙에 맞는지 보는 거고, 출력 인코딩은 내보낼 때 HTML 같은 출력 위치에서 코드로 읽히지 않게 바꾸는 거예요. 입력 검증만으로는 못 막아요. 작은따옴표를 막으면 O'Brien 같은 정상 이름이 거부되고, 거부 목록은 우회도 돼요. SQL 인젝션은 바인딩, XSS는 출력 인코딩이 답이고, 검증은 허용 목록 방식으로 서버에서 하는 보조 방어예요.

**꼬리질문**
- Q. 클라이언트에서 검증하면 되지 않나요? → 요청을 직접 만들어 보내면 우회돼요. 서버 검증이 필수고 클라이언트 검증은 UX용이에요.
- Q. 문법적 검증과 의미적 검증은? → 형식·타입이 맞나와, 업무상 말이 되나(종료일이 시작일보다 뒤인가)예요.
</details>

<details>
<summary>Q. Stored Procedure를 쓰면 안전한가요?</summary>

**답변(30초)** 호출할 때 인자를 바인딩하면 호출 자체는 안전해요. 하지만 프로시저 안에서 인자를 이어 붙여 동적 SQL을 만들면 그대로 인젝션이 돼요. 그래서 프로시저 내부도 정적 SQL이나 바인딩으로 써야 해요. 어떤 계층이든 문자열 연결이 남아 있으면 취약해요.

**꼬리질문**
- Q. 호출하는 쪽은 어떻게 써야 하나요? → 호출할 때도 인자를 바인딩해서 넘겨요. 호출 문장을 문자열로 이어 붙이면 거기서 또 뚫려요.
</details>

<details>
<summary>Q. 인젝션이 뚫렸다고 가정하면, 피해를 줄이려면 어떻게 하나요?</summary>

**답변(30초)** 최소 권한이 핵심이에요. 애플리케이션 DB 계정엔 SELECT·INSERT·UPDATE처럼 필요한 권한만 주고, DDL(테이블 생성·삭제)이나 관리자 권한은 주지 않아요. SELECT만 가진 계정으로 DROP TABLE을 실행하면 권한 거부 에러가 나요. 앱마다 계정을 나누고, 마이그레이션용 계정은 따로 두고, 뷰로 노출 범위를 줄여요.

**꼬리질문**
- Q. WAF(웹 방화벽)로 막으면 되지 않나요? → 보조 수단일 뿐이에요. 원인은 코드의 문자열 연결이라, 바인딩으로 고치는 걸 대신하지 못해요.
</details>

<details>
<summary>Q. OWASP Top 10에서 인젝션은 몇 위인가요?</summary>

**답변(30초)** 2021판 기준 A03, 3위예요. 2017판에선 1위였고, 2021판부터 XSS도 Injection 항목에 합쳐졌어요. 2025판에서는 A05, 5위예요. 순위가 내려갔어도 여전히 상위 위험이라, 연도를 붙여서 말하는 게 정확해요.

**꼬리질문**
- Q. 2025판 1위는? → 접근 제어 실패(Broken Access Control)예요.
- Q. 2021판에서 바뀐 점은? → XSS가 Injection 항목에 합쳐졌어요.
</details>

## 서술형 연습

<details>
<summary>상황: 관리자 회원 목록 API가 정렬 기준(sort)과 방향(dir)을 쿼리스트링으로 받아요. 지금은 MyBatis 매퍼에서 두 값을 문자열 치환 표기(달러 기호)로 ORDER BY 뒤에 그대로 붙이고 있어요. 보안 점검에서 지적을 받았어요. 어떻게 고칠까요?</summary>

**상황 파악**
`${}`는 값을 SQL에 그대로 끼워 넣어요. 쿼리스트링은 누구나 바꿀 수 있으니, `sort` 자리에 SQL 조각을 넣으면 쿼리 구조가 바뀌어요. 관리자 화면이라도 URL만 알면 요청을 직접 만들 수 있어서 안전하지 않아요.

**원인 후보**
1. 정렬 컬럼은 `#{}`로 바인딩이 안 돼서 `${}`를 썼음(구조 자리는 바인딩 불가).
2. 입력값 검사가 없거나, 특수문자 거부 목록 정도만 있음.
3. 앱 DB 계정 권한이 넓으면 피해가 더 커짐.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 허용 목록 매핑(`name`→`name`, `created`→`created_at`, 없으면 기본값) 후 `${}`에 매핑 결과만 전달 | 사용자 입력이 SQL에 절대 안 들어감, 구조 단순 | 정렬 컬럼이 늘 때마다 목록 수정 |
| B. `<choose>`로 XML 안에서 컬럼별 분기 | SQL만 보고 가능한 정렬이 보임 | 컬럼이 많으면 XML이 길어짐 |
| C. `#{sort}`로 바꾸기 | 코드 수정 최소 | 에러 없이 상수로 정렬돼 정렬 기능이 조용히 고장 남 |
| D. 특수문자 거부 목록 필터 | 빠르게 적용 | 우회 가능, 근본 해결 아님 |

**내가 고를 방법**
A를 골라요. Java 쪽에 `Map`으로 허용 목록을 두고, 방향은 `ASC`/`DESC` 둘 중 하나로만 매핑해요. 목록에 없는 값은 기본 정렬로 처리하거나 400으로 거부해요. C는 보안은 막지만 기능이 깨지고, D는 우회돼서 고르지 않아요. 추가로 앱 DB 계정이 SELECT 등 필요한 권한만 갖는지 확인하고, 같은 패턴(`${`)이 다른 매퍼에도 있는지 검색해요. Spring Data JPA로 옮길 계획이 있다면 `Sort.by`가 엔티티 속성 검사를 해 주지만, API 단의 허용 목록은 그대로 두는 게 의도가 분명해요.

**채점 포인트**: `${}`는 문자열 치환·`#{}`는 바인딩, 정렬 컬럼은 바인딩 불가, `ORDER BY ?`의 조용한 버그, 허용 목록 매핑과 기본값, 방향도 2값 매핑, 거부 목록 필터의 한계, 최소 권한, 다른 매퍼 전수 검색.
</details>

<details>
<summary>상황: 10년 된 레거시 서비스를 맡았어요. 쿼리가 JDBC 직접 호출, MyBatis, JPA에 섞여 있어요. 인젝션 취약 쿼리를 찾아서 고치는 계획을 세워 보세요.</summary>

**상황 파악**
코드가 크고 방식이 섞여 있어서 한 번에 다 고치기 어려워요. "어디가 취약한지 찾기 → 위험한 것부터 고치기 → 다시 안 생기게 막기" 순서로 나눠야 해요.

**원인 후보(찾아야 할 패턴)**
1. JDBC: `createStatement()` + 문자열 연결, 또는 `prepareStatement(... + 변수 + ...)`.
2. MyBatis: XML의 `${`.
3. JPA: `createQuery`·`createNativeQuery`·`@Query`에 `+`로 이어 붙인 문자열.
4. Stored Procedure 내부의 동적 SQL 연결.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. grep으로 패턴 검색(`${`, `createStatement`, `+ "'"`, `"' +`) 후 사람이 검토 | 바로 시작 가능, 도구 불필요 | 놓치는 패턴 있음, 오탐 많음 |
| B. 정적 분석 도구를 CI에 붙이기 | 반복 검사, 새 코드도 잡음 | 도입·튜닝 비용, 오탐 관리 필요 |
| C. 전부 한 번에 재작성 | 깔끔함 | 회귀 위험 큼, 오래 걸림 |
| D. 위험도 순 점진 수정 + 테스트 | 위험 큰 곳부터 빨리 닫음 | 끝날 때까지 기간이 김 |

**내가 고를 방법**
A로 목록을 만들고, 외부 입력이 닿는 쿼리(로그인, 검색, 목록 정렬, 관리자 기능)를 위험도 1순위로 표시해요. 고칠 때는 값 자리는 바인딩(`?`, `:name`, `#{}`)으로, 정렬·테이블명 같은 구조 자리는 허용 목록으로 바꿔요. 각 수정에 `' OR '1'='1` 같은 입력으로 "결과가 늘지 않는다"는 테스트와 정상 입력 테스트를 같이 붙여 회귀를 막아요(D). 동시에 앱 DB 계정 권한을 점검해 DDL·관리자 권한을 빼고, 마이그레이션 계정을 분리해요. 마지막으로 B를 CI에 붙이고 코드 리뷰 체크리스트에 "문자열 연결 쿼리 금지"를 넣어 새로 생기지 않게 해요. C는 회귀 위험이 커서 고르지 않아요.

**채점 포인트**: 계층별 검색 패턴(JDBC·MyBatis `${}`·JPQL·네이티브·프로시저), 외부 입력 기준 우선순위, 값은 바인딩·구조는 허용 목록, 수정마다 회귀 테스트, 최소 권한·계정 분리, 재발 방지(CI 정적 분석·리뷰 규칙), 이스케이프는 최후 수단.
</details>

<details>
<summary>상황: 코드 리뷰에서 팀원이 "우리는 JPA(ORM)를 쓰니까 SQL 인젝션은 신경 안 써도 돼요"라고 해요. 어떻게 답할까요?</summary>

**상황 파악**
반은 맞고 반은 틀린 말이에요. JPA의 기본 기능(`findById`, 파생 쿼리, 파라미터 바인딩)은 값을 바인딩해서 안전해요. 하지만 JPA 안에도 문자열로 쿼리를 만드는 길이 있고, 그 길에서는 똑같이 인젝션이 생겨요.

**원인 후보(JPA에서도 뚫리는 곳)**
1. JPQL/HQL 문자열 연결: `"... where u.name = '" + name + "'"`.
2. 네이티브 쿼리 문자열 연결.
3. 정렬을 문자열로 만들어 쿼리 끝에 붙이거나, `JpaSort.unsafe`에 사용자 입력을 넣음.
4. 같은 프로젝트의 MyBatis·JDBC 코드는 JPA와 무관하게 따로 점검해야 함.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 리뷰 규칙: 쿼리 문자열 연결 금지, `:name`/`?1`/`@Param`만 허용 | 원인 자체를 막음 | 사람이 놓칠 수 있음 |
| B. 정렬은 `Sort`/`Pageable` + API 허용 목록 | 속성 검사를 프레임워크가 해 줌 | 복잡한 정렬은 별도 처리 필요 |
| C. 정적 분석으로 `createQuery(... +` 패턴 탐지 | 자동·반복 | 도입 비용, 오탐 |
| D. "ORM이니 안전" 유지 | 비용 없음 | 연결식 쿼리가 하나만 있어도 뚫림 |

**내가 고를 방법**
팀원에게 "ORM이 안전한 게 아니라 바인딩이 안전한 것"이라고 정리해 말해요. 근거로 Hibernate 공식 문서도 쿼리 조각을 사용자 입력과 이어 붙이는 걸 극도로 위험하다고 적어 뒀다는 점과, JPQL 연결 예시를 같이 보여 줘요. 그다음 A와 B를 팀 규칙으로 정하고, C로 기존 코드를 한 번 훑어요. 앱 DB 계정 최소 권한은 ORM 여부와 상관없이 유지해요. D는 고르지 않아요.

**채점 포인트**: ORM 기본 기능은 바인딩이라 안전, JPQL/HQL·네이티브 문자열 연결은 취약, 정렬 문자열·`JpaSort.unsafe` 주의, 같은 프로젝트의 MyBatis `${}`·JDBC도 점검, 공식 문서 근거 제시, 팀 규칙·자동 검사, 최소 권한.
</details>
