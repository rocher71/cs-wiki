:::tip[한 줄 요약]
**TDD**(테스트 주도 개발)는 실패하는 테스트를 하나 먼저 쓰고(**레드**), 그 테스트만 통과하게 가장 단순하게 구현한 뒤(**그린**), 테스트를 초록으로 유지한 채 코드를 정리하는(**리팩터**) 짧은 반복이에요. 좋은 테스트는 빠르고, 서로 독립이고, 언제 돌려도 같은 결과를 내요. 커버리지 숫자는 "실행됐다"만 알려 줄 뿐 "결함을 잡는다"는 보장이 아니에요.
:::

:::note[처음이라면 여기까지]
① TDD는 "시험 문제를 먼저 만들고 공부하기"예요. 테스트 하나 쓰기 → 통과시키기 → 정리하기를 계속 반복해요.

② 좋은 테스트는 빠르고, 다른 테스트와 상관없이 혼자 돌아가고, 몇 번을 돌려도 결과가 같아야 해요.

③ "가끔만 실패하는 테스트"는 대부분 시간·실행 순서·공유 데이터·기다리기(sleep) 문제예요. 재시도로 덮지 말고 원인을 고쳐요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

보통은 공부를 다 하고 나서 시험을 봐요. TDD는 순서를 뒤집어요. **시험 문제를 먼저 한 문제 만들고**, 그 문제를 풀 수 있을 만큼만 공부해요. 풀리면 노트를 깔끔하게 정리하고, 다음 문제를 만들어요.

이렇게 하면 두 가지가 좋아져요. 첫째, "어디까지 하면 끝인가"가 문제로 분명해져요. 둘째, 정리하다가 실수로 뭔가 망가뜨려도 이미 만든 문제들이 바로 알려 줘요.

대신 문제를 잘 만드는 능력이 필요하고, 처음엔 느리게 느껴져요. 문제 자체가 엉터리면(답을 안 확인하는 테스트) 아무리 많이 풀어도 실력이 안 늘어요.

단, 실제 TDD에서 "문제"는 코드로 자동 실행되는 테스트이고, 한 번에 아주 작은 동작 하나만 다뤄요. 몇 분 단위로 레드 → 그린 → 리팩터를 돌아요.

## 제대로 알기

### 레드 → 그린 → 리팩터

TDD를 널리 알린 켄트 벡(Kent Beck)은 2023년 글 "Canon TDD"에서 순서를 이렇게 정리해요.

1. **테스트 목록 쓰기**: 이번 변경으로 생길 동작 사례를 적어요. "기존 동작은 그대로여야 한다"는 사례도 넣어요. 구현을 어떻게 할지는 여기서 정하지 않아요.
2. **테스트 하나 쓰기(레드)**: 목록에서 하나만 골라 실제로 실행되는 테스트로 만들고, **실패하는 걸 확인**해요.
3. **통과시키기(그린)**: 그 테스트(와 앞서 통과한 테스트들)가 통과할 만큼만 코드를 고쳐요. 하다가 떠오른 새 사례는 목록에 적어 둬요.
4. **리팩터(선택)**: 테스트가 초록인 상태를 지키며 이름·중복·구조를 정리해요. 구현 설계는 이때 결정해요.
5. 목록이 빌 때까지 2번으로 돌아가요.

벡의 요약은 "먼저 돌아가게, 그다음 바르게(Make it run, then make it right)"예요. 그린 단계에선 지저분해도 되고, 정리는 리팩터 단계에서 따로 해요.

<Aside type="caution" title="가장 흔한 실패는 리팩터를 빼먹는 것">
마틴 파울러(Martin Fowler)는 TDD에서 가장 흔한 실패가 레드-그린-리팩터의 세 번째, 리팩터를 건너뛰는 거라고 해요. 테스트는 통과하는데 코드는 점점 지저분해져요.
</Aside>

벡이 꼽은 흔한 실수도 기억해 두면 좋아요.

- 커버리지를 올리려고 **assert(결과 확인) 없는 테스트**를 씀
- 목록을 전부 테스트로 먼저 만든 뒤 한꺼번에 통과시키려 함
- 테스트를 통과시키려고 assert를 지움
- **코드를 실행해서 나온 값을 그대로 기대값에 복사**함(버그도 같이 정답이 됨)
- 통과시키는 중에 리팩터를 섞음, 필요 이상으로 미리 추상화함

### TDD의 장점과 비판: "Is TDD Dead?"

| 장점 | 단점·비판 |
|---|---|
| 테스트가 빠짐없이 함께 생김 | 처음엔 느리게 느껴지고 익숙해지는 데 시간이 걸림 |
| "어디까지 만들면 끝"이 분명함 | 탐색적 작업(뭘 만들지 아직 모를 때)엔 맞지 않을 수 있음 |
| 리팩터를 겁내지 않게 됨 | 목(mock)을 남용하면 테스트 때문에 설계가 복잡해짐 |
| 테스트하기 쉬운 설계로 자연스럽게 유도 | 테스트 자체도 유지보수 대상 |

2014년 루비 온 레일스를 만든 DHH가 "TDD는 죽었다"는 글을 쓰면서, DHH·파울러·벡 세 사람이 다섯 번에 걸쳐 공개 화상 대담을 했어요. 요지는 이래요.

- **DHH**: 목 위주 TDD는 테스트를 격리하려고 불필요한 간접 계층을 늘려 **설계를 망가뜨린다**(test-induced design damage). 정말 지키고 싶은 건 "스스로 테스트하는 코드"다.
- **파울러**: TDD는 스스로 테스트하는 코드에 이르는 **한 가지 방법**일 뿐이다. TDD가 목 남용을 요구하지도 않는다.
- **벡**: TDD는 확신과 피드백을 얻는 방법이다. 자기는 목을 거의 안 쓴다. 새로 잡아 주는 게 없는 테스트는 지우자.

세 사람 모두 **자동 테스트가 있는 코드는 중요하다**는 데 동의했고, 테스트 수나 커버리지 수치는 품질을 잘 보여 주지 못한다고 봤어요. TDD를 어디까지 쓸지는 팀이 실험하며 정하라는 게 결론이에요.

### 좋은 테스트의 조건: F.I.R.S.T

로버트 C. 마틴의 『클린 코드』 9장에 나오는 기준이에요(일반적으로 알려진 내용으로 정리).

| 글자 | 뜻 | 어기면 생기는 일 |
|---|---|---|
| **F**ast | 빠르다 | 느리면 자주 안 돌리게 되고, 버그를 늦게 발견해요 |
| **I**ndependent | 서로 독립이다(순서 상관없음) | 앞 테스트가 남긴 데이터 때문에 뒤 테스트가 실패해요 |
| **R**epeatable | 어느 환경에서나 같은 결과 | 내 PC에선 되는데 CI에선 실패해요 |
| **S**elf-Validating | 통과/실패를 스스로 판정 | 로그를 사람이 눈으로 확인해야 해요 |
| **T**imely | 제때(실제 코드 직전에) 쓴다 | 나중에 쓰려면 테스트하기 어려운 구조가 이미 굳어 있어요 |

R은 Reliable이 아니라 **Repeatable**, S는 **Self-Validating**이에요. 필기에서 자주 바꿔 내요.

### 테스트 이름과 "테스트 하나에 개념 하나"

테스트 이름만 읽어도 **어떤 조건에서 무엇을 하면 어떤 결과인지** 알 수 있게 써요. given-when-then(주어진 상황 - 할 일 - 기대 결과) 구조가 흔한 관례예요.

```java
@Test
@DisplayName("만료된 쿠폰이면 결제에 실패한다")  // JUnit 5는 한글 이름 표시 가능
void 만료된_쿠폰이면_결제에_실패한다() {
    // given: 어제 만료된 쿠폰
    // when: 결제 시도
    // then: 예외 발생
}
```

같은 장의 권고로, **테스트 하나에는 개념 하나**만 담아요. "할인도 되고, 포인트도 쌓이고, 알림도 간다"를 한 테스트에 넣으면, 실패했을 때 무엇이 깨졌는지 이름만으로 알 수 없어요. 테스트 코드도 실제 코드만큼 읽기 쉽게 유지해요.

### 커버리지 숫자의 함정

**커버리지**(coverage)는 테스트를 돌렸을 때 코드가 얼마나 실행됐는지의 비율이에요. 문제는 **실행만 됐지 결과를 확인했는지는 모른다**는 거예요.

```java
@Test
void 할인_계산() {
    calculator.discount(20000); // assert가 없어도 이 줄은 '커버'됨
}
```

이 테스트는 커버리지를 올리지만, `discount`가 엉뚱한 값을 돌려줘도 통과해요. 벡이 흔한 실수로 꼽은 바로 그 패턴이에요. 경계값(정확히 1만 원 같은)을 빠뜨려도 커버리지는 100%일 수 있어요. 구문·결정·조건 커버리지의 차이는 [소프트웨어 테스트](../../exam/se/testing/)를 보세요.

### 테스트하기 쉬운 설계: 바깥 것을 주입받기

테스트가 어려운 코드는 대개 **안에서 몰래 바깥 세상을 불러요**. DB, 외부 API, 그리고 의외로 자주 **현재 시각**이요.

```java
// 테스트하기 어려움: 오늘 날짜에 따라 결과가 바뀜
boolean isExpired() {
    return LocalDateTime.now().isAfter(expiresAt);
}
```

```java
// 테스트하기 쉬움: 시계를 생성자로 받음
class Coupon {
    private final Clock clock;
    private final LocalDateTime expiresAt;
    Coupon(Clock clock, LocalDateTime expiresAt) { this.clock = clock; this.expiresAt = expiresAt; }

    boolean isExpired() {
        return LocalDateTime.now(clock).isAfter(expiresAt);
    }
}

// 테스트: 시각을 고정
Clock fixed = Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC);
Coupon coupon = new Coupon(fixed, LocalDateTime.of(2025, 12, 31, 23, 59));
assertTrue(coupon.isExpired()); // 언제 돌려도 같은 결과
```

`java.time.Clock`(Java 8부터) 공식 문서도 "현재 시각이 필요한 메서드엔 Clock을 넘기는 게 모범 사례"라고 해요. 테스트에선 `Clock.fixed`(항상 같은 시각)나 `Clock.offset`(미래·과거로 이동)을 넣고, 운영에선 `Clock.systemUTC()` 같은 실제 시계를 넣어요. 난수도 같은 원리로 주입받아요.

이렇게 **필요한 걸 바깥에서 받는 것**이 DI(의존성 주입)예요. 스프링에서 생성자 주입을 쓰는 이유이기도 해요([IoC와 DI](../../spring/ioc-di/)). 계산 로직은 입력 → 출력만 있는 순수 함수로 떼어 내면 목 없이도 테스트할 수 있어요. 단, DHH의 비판처럼 테스트만을 위해 인터페이스와 계층을 끝없이 늘리는 것도 피해야 해요.

### 플래키 테스트: 가끔만 실패하는 테스트

**플래키 테스트**(flaky test)는 코드를 안 바꿨는데 돌릴 때마다 통과·실패가 바뀌는 테스트예요. "다시 돌리면 되겠지"가 반복되면 팀이 빨간불을 무시하게 되고, 진짜 버그도 놓쳐요.

파울러의 글("Eradicating Non-Determinism in Tests")과 Google 테스팅 블로그의 공개 글에서 꼽는 원인과 처방이에요.

| 원인 | 예 | 처방 |
|---|---|---|
| **시간** | 자정·월말에만 실패하는 만료 테스트 | 시계를 주입해 고정(`Clock.fixed`) |
| **실행 순서 의존** | 테스트 A가 회원을 저장하고 안 지움 → B의 "회원 0명"이 A 다음일 때만 실패 | 테스트마다 시작 상태를 새로 만들기 |
| **공유 상태** | 같은 DB·static 변수·파일을 여러 테스트가 같이 씀 | 테스트별 데이터 분리, 트랜잭션 롤백, 정리 코드 |
| **비동기 대기** | `Thread.sleep(1000)` 후 결과 확인 → 느린 CI에선 부족 | 고정 sleep 금지. 원하는 상태가 될 때까지 짧게 폴링 + 넉넉한 전체 타임아웃 |
| **외부 서비스** | 테스트가 실제 외부 API를 부름 | 테스트 더블로 대체, 계약 테스트로 실제와 맞는지 따로 확인 |
| **자원 누수** | DB 커넥션을 안 닫아 뒤 테스트가 커넥션 부족으로 실패 | 풀로 관리. 테스트에선 풀 크기를 1로 해서 누수가 바로 드러나게 |

Google 블로그는 원인이 테스트 코드만이 아니라 **실행 프레임워크, 대상 시스템과 의존 서비스, OS·하드웨어·네트워크**에서도 올 수 있다고 정리해요. 그리고 처방으로 "임의 지연(sleep)을 넣지 말고, 특정 상태를 기다리는 동기화를 쓰라"고 해요.

플래키 테스트를 별도 묶음으로 빼 두는 **격리**(quarantine)는 임시 조치예요. 개수와 기간을 제한하고, 근본 원인은 따로 고쳐야 해요. E2E 테스트가 특히 플래키하기 쉬운 이유는 [단위·통합 테스트](../testing-basics/)에 있어요.

### 심화: 뮤테이션 테스트(PIT)

**뮤테이션 테스트**(mutation testing)는 "테스트가 정말 버그를 잡는지"를 확인하는 방법이에요. 도구가 코드에 일부러 작은 결함(**변이**, mutant)을 심고 테스트를 돌려요. 예를 들어 `if (age >= 19)`를 `if (age > 19)`로 바꿔요. 테스트가 실패하면 변이를 **잡은 것(killed)**, 그래도 통과하면 **살아남은 것(survived)**이에요. 19세 경계 테스트가 없으면 라인 커버리지는 100%여도 이 변이가 살아남아서 빈틈이 드러나요. Java에서는 **PIT**(PITest)가 대표 도구이고, 라인 커버리지보다 강한 척도로 쓰여요. 대신 변이마다 테스트를 다시 돌려서 실행 시간이 오래 걸려요.

<summary>Q. TDD가 뭔가요? 레드-그린-리팩터를 설명해 주세요.</summary>

**답변(30초)**
TDD는 테스트를 먼저 쓰고 그 테스트를 통과시키는 방식으로 개발하는 방법이에요. 먼저 실패하는 테스트를 하나 써서 빨간불을 확인하고, 그 테스트만 통과할 만큼 가장 단순하게 구현해 초록불을 만들어요. 그다음 테스트를 초록으로 유지한 채 중복과 이름을 정리하는 리팩터를 해요. 이걸 몇 분 단위로 반복해서, 기능과 테스트가 항상 함께 자라요.

**꼬리질문**
- Q. 왜 꼭 실패를 먼저 확인하나요? → 테스트가 실제로 그 동작을 검사하는지 확인하려고요. 처음부터 통과하는 테스트는 아무것도 안 잡는 테스트일 수 있어요.
- Q. 가장 흔한 실수는? → 리팩터 단계를 건너뛰는 거예요(파울러).
</details>

<details>
<summary>Q. 좋은 단위 테스트의 조건은 무엇인가요?</summary>

**답변(30초)**
F.I.R.S.T로 정리할 수 있어요. 빠르고(Fast), 서로 독립적이고(Independent), 어느 환경에서나 같은 결과를 내고(Repeatable), 통과·실패를 스스로 판정하고(Self-Validating), 제때 쓰는(Timely) 테스트예요. 여기에 테스트 하나엔 개념 하나만 담고, 이름만 보고도 조건과 기대 결과를 알 수 있게 써요.

**꼬리질문**
- Q. Independent가 깨지면 어떤 일이 생기나요? → 실행 순서에 따라 결과가 바뀌는 플래키 테스트가 돼요.
</details>

<details>
<summary>Q. 커버리지가 높으면 좋은 테스트인가요?</summary>

**답변(30초)**
아니에요. 커버리지는 코드가 실행됐는지만 보여 주고, 결과를 제대로 확인했는지는 알려 주지 않아요. assert 없는 테스트로도 커버리지는 올라가고, 경계값을 빠뜨려도 100%가 나올 수 있어요. 그래서 커버리지는 "테스트가 전혀 없는 곳"을 찾는 용도로 쓰고, 테스트 품질은 뮤테이션 테스트나 핵심 로직의 경계값 테스트로 봐요.

**꼬리질문**
- Q. 뮤테이션 테스트가 뭔가요? → 코드에 일부러 작은 결함을 심고 테스트가 잡아내는지 보는 방법이에요. Java는 PIT가 대표 도구예요.
</details>

<details>
<summary>Q. 현재 시간이나 랜덤에 의존하는 코드는 어떻게 테스트하나요?</summary>

**답변(30초)**
그 값을 메서드 안에서 직접 부르지 않고 바깥에서 주입받게 바꿔요. Java라면 `LocalDateTime.now()` 대신 생성자로 `Clock`을 받아 `now(clock)`을 쓰고, 테스트에선 `Clock.fixed`로 시각을 고정해요. 그러면 언제 돌려도 결과가 같아요. 랜덤도 시드나 생성기를 주입하면 같은 방식으로 테스트할 수 있어요.

**꼬리질문**
- Q. 이게 DI와 무슨 관계인가요? → 필요한 의존(시계)을 바깥에서 넣어 주는 게 DI라서, 테스트용·운영용 구현을 바꿔 끼울 수 있어요.
</details>

<details>
<summary>Q. 플래키 테스트를 만나면 어떻게 하나요?</summary>

**답변(30초)**
재시도로 덮지 않고 원인을 찾아요. 흔한 원인은 시간 의존, 실행 순서 의존, 공유 상태, 고정 sleep으로 비동기를 기다리는 것, 외부 서비스 호출이에요. 단독 실행·순서 섞기·반복 실행으로 재현한 뒤, 시계 주입, 테스트별 데이터 초기화, 상태를 기다리는 폴링으로 고쳐요. 당장 못 고치면 격리해 두되 기한을 정해요.

**꼬리질문**
- Q. `Thread.sleep`이 왜 나쁜가요? → 짧으면 느린 환경에서 실패하고, 길면 전체 테스트가 느려져요. 원하는 상태가 될 때까지 기다리는 방식이 나아요.
</details>

<details>
<summary>Q. TDD의 단점이나 비판은 무엇인가요?</summary>

**답변(30초)**
대표적인 건 2014년 "Is TDD Dead?" 논쟁이에요. DHH는 목 위주 TDD가 테스트 격리를 위해 불필요한 계층을 늘려 설계를 망친다고 비판했어요. 파울러와 벡은 TDD가 목 남용을 요구하지 않으며, 자동 테스트를 갖춘 코드에 이르는 한 방법이라고 답했어요. 세 사람 모두 자동 테스트 자체는 중요하다고 봤고, 어디까지 적용할지는 맥락에 따라 다르다는 게 결론이에요.

**꼬리질문**
- Q. 그럼 본인은 TDD를 어떻게 쓰겠어요? → 규칙이 분명한 도메인 로직(할인·정산)엔 TDD, 화면이나 탐색적 작업엔 구현 후 테스트처럼 섞어 쓰겠다고 답하면 돼요.
</details>

## 서술형 연습

<details>
<summary>상황: CI에서 특정 테스트가 열 번에 한 번꼴로 실패하고, 다시 돌리면 통과해요. 팀에서 "실패하면 자동 재시도 3회"를 설정하자는 의견이 나왔어요. 어떻게 하시겠어요?</summary>

**상황 파악**
코드 변경 없이 결과가 바뀌는 **플래키 테스트**예요. 재시도로 초록불은 얻겠지만, 팀이 실패를 무시하는 습관이 생기고 진짜 버그(예: 실제 동시성 문제)도 같이 묻힐 수 있어요.

**원인 후보**
1. **실행 순서 의존·공유 상태**: 앞 테스트가 DB에 남긴 데이터, static 변수. CI는 병렬·다른 순서로 돌리기도 해요.
2. **비동기 대기**: `Thread.sleep`으로 기다리는데 CI 머신이 느림.
3. **시간 의존**: `now()` 직접 호출, 자정·월말·시간대 차이.
4. **외부 의존**: 실제 외부 API나 공유 테스트 서버 호출.
5. **자원 누수**: 커넥션을 안 닫아 뒤 테스트가 실패.

**재현 방법**: 그 테스트만 단독으로 수십 번 반복 실행, 테스트 순서를 섞어 실행, CI와 같은 병렬 설정·시간대로 실행. 단독에선 늘 통과하고 섞을 때만 실패하면 순서·공유 상태가 유력해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 자동 재시도 | 즉시 초록불, 배포가 안 막힘 | 원인을 숨김, 진짜 간헐 버그도 묻힘, 실행 시간 증가 |
| B. 격리(별도 묶음으로 빼기) + 기한 | 다른 작업은 계속 진행, 문제를 목록으로 관리 | 그동안 그 기능은 테스트 보호가 없음 |
| C. 근본 수정(초기화·롤백, 시계 주입, 폴링 대기, 테스트 더블) | 다시 안 생김, 테스트를 믿을 수 있게 됨 | 원인 찾는 데 시간이 듦 |

**내가 고를 방법**
재시도를 기본 해결책으로 쓰는 건 반대해요. 당장 배포가 막히면 **B로 격리하고 담당자·기한을 정한 뒤 C로 근본 수정**해요. 재시도를 꼭 써야 한다면 "재시도로 통과한 테스트"를 따로 기록해서 플래키 목록을 보이게 만들어요. 고친 뒤엔 같은 유형이 다시 안 생기게 "고정 sleep 금지, 테스트마다 데이터 정리" 같은 규칙을 팀에 공유해요.

**채점 포인트**: 플래키 정의, 재시도는 증상 완화, 원인 후보(순서·공유 상태·시간·비동기 대기·외부 의존·자원 누수), 재현 방법(단독·반복·순서 섞기), sleep 대신 상태 대기, 시계 주입, 격리는 임시·기한, 재발 방지 규칙.
</details>

<details>
<summary>상황: 우리 서비스의 테스트 커버리지는 90%인데, 운영에서 버그가 계속 나와요. 무엇이 문제이고 어떻게 개선할까요?</summary>

**상황 파악**
커버리지는 "실행됐다"만 보여 줘요. 90%인데 버그가 많다는 건 **테스트가 코드를 지나가기만 하고 결과를 제대로 검사하지 않거나, 버그가 나는 곳을 안 보고 있다**는 신호예요.

**원인 후보**
1. assert가 없거나 약한 테스트("예외만 안 나면 통과").
2. 실행 결과를 복사해 기대값으로 붙여서 버그가 정답으로 굳음.
3. 경계값·예외 경로 누락(정확히 1만 원, 0원, 음수, 만료 직전).
4. 목을 과하게 써서 실제 연동(DB 쿼리, 외부 API 응답 형식)은 검증 안 됨.
5. 운영 버그가 주로 설정·동시성·데이터 문제라 단위 테스트가 다루지 않는 영역.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 뮤테이션 테스트(PIT) 도입 | 결함을 못 잡는 테스트를 수치로 찾아냄 | 실행 시간이 길어 핵심 모듈이나 야간 실행으로 제한 |
| B. 운영 버그마다 재현 테스트 먼저 추가 | 실제 버그가 나는 곳부터 채워짐, 재발 방지 | 사후 대응 위주 |
| C. 핵심 로직에 경계값·예외 테스트 보강 | 돈·권한처럼 중요한 곳을 집중 보호 | 어디가 핵심인지 판단 필요 |
| D. 통합 테스트 보강(실제 DB 등) | 목이 가린 연동 문제를 잡음 | 느리고 관리 비용 큼 |

**내가 고를 방법**
먼저 최근 운영 버그를 분류해서 "단위 로직 오류인지, 연동·설정 문제인지" 봐요. 로직 오류가 많으면 **B와 C**로 버그 재현 테스트와 경계값을 채우고, 핵심 모듈에 **A**를 돌려 살아남은 변이를 줄여요. 연동 문제가 많으면 **D**를 늘려요. 커버리지 목표 숫자를 더 올리는 건 assert 없는 테스트를 늘리기 쉬워서 고르지 않고, 지표는 "변경된 코드의 커버리지"와 뮤테이션 점수 정도로 바꿔요.

**채점 포인트**: 커버리지 = 실행 여부일 뿐, assert 없는 테스트·기대값 복사, 경계값 누락, 목 과다, 뮤테이션 테스트(killed/survived), 버그 재현 테스트 먼저, 단위/통합 균형, 숫자 목표의 부작용.
</details>

<details>
<summary>상황: 테스트가 하나도 없는 5년 된 정산 모듈을 고쳐야 해요. 코드가 길고 DB·외부 API·현재 시각을 곳곳에서 직접 불러요. 테스트를 어디서부터 붙이시겠어요?</summary>

**상황 파악**
테스트가 없으니 고치다가 기존 동작이 깨져도 알 수 없어요. 그렇다고 한 번에 전부 테스트하거나 다 뜯어고치는 건 위험해요. 목표는 **"지금 동작을 먼저 고정하고, 고칠 부분부터 조금씩"**이에요.

**원인 후보(테스트가 어려운 이유)**
1. DB·외부 API·`now()`를 메서드 안에서 직접 호출(주입 불가).
2. 한 메서드가 너무 많은 일을 함(계산·저장·알림이 섞임).
3. 지금 동작이 "맞는지" 아는 사람이 없음(명세 부재).

**순서(일반적으로 알려진 레거시 코드 접근법으로 정리)**

1. **바꿀 지점을 정해요.** 전체가 아니라 이번에 고칠 기능 주변만.
2. **특성 테스트**(characterization test)를 써요. "올바른 동작"이 아니라 **지금 실제로 하는 동작**을 기록하는 테스트예요. 몇 가지 입력으로 돌려 나온 결과를 기대값으로 고정해요. 그래야 고치다가 무엇이 바뀌었는지 알 수 있어요. (평소엔 "결과 복사"가 실수지만, 여기선 현재 동작을 보존하려는 의도적 선택이에요. 이상해 보이는 결과는 따로 표시해 확인해요.)
3. **이음새를 만들어요.** `now()`는 `Clock` 주입으로, 외부 API·DB 호출은 생성자로 받는 객체 뒤로 옮기는 작은 리팩터만 해요. 동작은 바꾸지 않아요.
4. **계산 로직을 순수 함수로 떼어 내요.** 입력 → 출력만 있으면 단위 테스트가 쉬워요.
5. **이제 고쳐요.** 새 동작·버그 수정은 TDD로(실패하는 테스트 먼저).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 바깥에서 통합·E2E 특성 테스트부터 | 코드를 안 건드리고 바로 시작, 전체 동작 보호 | 느리고 플래키하기 쉬움, 실패 원인 찾기 어려움 |
| B. 이음새를 만들어 단위 테스트 | 빠르고 정밀 | 테스트 없이 하는 첫 리팩터에 위험이 있음(작게 해야 함) |
| C. 전면 재작성 | 깨끗한 구조 | 숨은 규칙을 놓치기 쉽고 오래 걸림 |

**내가 고를 방법**
**A로 큰 흐름을 먼저 고정**하고(몇 개만), 그 보호 아래에서 **B로 바꿀 부분만 이음새를 만들어** 단위 테스트를 늘려요. 정산은 돈이 걸려서 C처럼 한 번에 갈아엎는 건 피해요. 새 버그가 나면 재현 테스트부터 추가해서 테스트가 실제 문제 지점을 따라 자라게 해요.

**채점 포인트**: 전부 말고 바꿀 곳부터, 특성 테스트로 현재 동작 고정, 이음새(Clock·의존 주입) 만들기, 동작 보존 리팩터는 작게, 순수 함수 분리, 수정은 TDD, 전면 재작성 위험, 통합 테스트 소수 + 단위 테스트 증가.
</details>

## 필기 포인트

- TDD 순서: **레드(실패 테스트) → 그린(최소 구현) → 리팩터(정리)**. 리팩터 생략이 가장 흔한 실패(파울러).
- F.I.R.S.T = Fast, Independent, **Repeatable**, **Self-Validating**, Timely.
- 커버리지는 실행 여부만 측정. 결함 검출력은 **뮤테이션 테스트**(변이를 잡으면 killed, 못 잡으면 survived).
- 플래키 원인: 시간, 순서 의존, 공유 상태, 비동기 대기(sleep), 외부 서비스, 자원 누수.
