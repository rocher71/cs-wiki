:::tip[한 줄 요약]
**401**은 "누구인지 확인이 안 됨"(인증 실패), **403**은 "누군지는 알지만 그 일을 할 권한이 없음"(인가 실패)이에요. 보안 사고는 대부분 **로그인 여부만 보고 "이 데이터가 이 사람 것인가"를 확인하지 않는 실수**(IDOR)에서 나와요. 로그인 오류 메시지는 계정 존재를 숨기게 쓰고, 비밀번호는 길이와 유출 목록으로 검사하고, 키가 새면 지우기보다 **폐기·교체가 먼저**예요.
:::

:::note[처음이라면 여기까지]
① 401은 "출입증이 없거나 가짜", 403은 "출입증은 진짜인데 그 층엔 못 들어감"이에요. 이름이 Unauthorized(인가 안 됨)라서 헷갈리지만 401은 **인증** 문제예요.

② "로그인했는지"와 "이 주문이 네 것인지"는 따로 확인해야 해요. 두 번째를 빼먹으면 주소창의 숫자만 바꿔서 남의 주문을 볼 수 있어요.

③ 로그인 실패 메시지는 "아이디 또는 비밀번호가 올바르지 않습니다" 하나로 통일해요. "없는 아이디입니다"라고 알려 주면 가입 여부가 새요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

회사 건물에 들어간다고 생각해 보세요. 1층 게이트에서 출입증을 찍어요. 출입증이 없거나 위조된 거라면 게이트가 안 열려요. 경비원은 "당신이 누군지 모르겠어요, 출입증부터 보여 주세요"라고 해요. 이게 **401**이에요.

출입증은 진짜라서 게이트는 통과했어요. 그런데 10층 임원실 문 앞에서 카드를 찍으니 빨간불이 들어와요. "당신이 누군지는 아는데, 이 층에 들어올 권한은 없어요." 이게 **403**이에요. 다시 출입증을 찍어도 결과는 같아요.

가끔은 경비원이 "그런 방은 없는데요"라고 답하기도 해요. 방이 있다는 사실 자체를 외부인에게 알리고 싶지 않을 때요. 이게 **404로 존재를 숨기는** 방식이에요.

가장 흔한 사고는 이런 거예요. 게이트에서 출입증만 확인하고, 안에서는 아무 사무실 문이나 다 열려요. 직원이면 누구나 남의 서랍을 열 수 있는 거죠. 웹에서 이 실수를 **IDOR**라고 불러요.

단, 실제 웹에서 "출입증"은 세션 쿠키나 토큰이고, "층 권한"은 역할(관리자/일반)뿐 아니라 "이 주문의 주인이 맞나" 같은 **데이터 하나하나의 소유권**까지 포함해요.

## 제대로 알기

### 인증과 인가는 다른 질문이에요

- **인증**(authentication, "너 누구야?"): 아이디·비밀번호, 토큰 등으로 요청한 사람이 누구인지 확인하는 일이에요.
- **인가**(authorization, "너 이거 해도 돼?"): 확인된 사람이 이 기능·이 데이터에 접근해도 되는지 판단하는 일이에요.

순서는 항상 인증 → 인가예요. 누군지 모르면 권한을 따질 수도 없으니까요. 인증에 실패하면 401, 인증은 됐는데 인가에 실패하면 403이에요.

### 401 vs 403 vs 404 (HTTP 명세 기준)

HTTP 명세(**RFC 9110**, HTTP 동작을 정한 공식 문서)는 세 코드를 이렇게 정의해요.

| 코드 | 이름 | 뜻 | 명세가 정한 것 | 클라이언트는 |
|---|---|---|---|---|
| 401 | Unauthorized | 유효한 인증 정보가 없음(없거나, 보냈는데 거절됨) | 응답에 `WWW-Authenticate` 헤더를 **반드시(MUST)** 포함 | 새 인증 정보로 다시 시도해도 됨 |
| 403 | Forbidden | 요청은 이해했지만 수행을 거부. 인증 정보가 있었다면 권한이 부족함 | 인증과 무관한 이유로도 쓸 수 있음 | 같은 인증 정보로 자동 재시도하면 안 됨(SHOULD NOT) |
| 404 | Not Found | 자원을 못 찾았거나, **있다는 사실을 공개할 생각이 없음** | 존재를 숨기고 싶으면 403 대신 404를 써도 됨(MAY) | — |

기억법은 이거예요. **401 = "다시 로그인하면 될 수도 있음"**, **403 = "같은 계정으로 다시 로그인해도 안 됨"**.

<Aside type="caution" title="이름이 함정이에요">
401의 이름 "Unauthorized"는 글자 그대로 "인가 안 됨"이지만, 실제 뜻은 "인증 안 됨"이에요. 권한 부족은 403이에요. 퀴즈와 면접에서 가장 많이 틀리는 지점이에요.
</Aside>

**`WWW-Authenticate`**(어떤 방식으로 인증하라는 안내 헤더)는 명세상 필수인데, JSON API에서는 자주 빠뜨려요. 토큰 방식이면 보통 `WWW-Authenticate: Bearer` 형태로 보내요(일반 관례).

이 구분이 실무에서 왜 중요할까요? 프론트엔드는 보통 **401을 받으면 토큰을 새로 받고 다시 시도**해요. 그런데 권한 부족까지 401로 보내면, 권한 없는 사용자가 토큰 갱신 → 다시 401 → 다시 갱신을 무한 반복하게 돼요. 403은 "재시도해도 소용없다"는 신호라서 갱신을 시도하지 않아요.

Spring Security에서 누가 401/403을 만드는지(EntryPoint, AccessDeniedHandler)는 [Spring Security](../../spring/spring-security/) 페이지에 있어요.

### IDOR: 로그인 확인만 하고 주인 확인을 빼먹는 실수

**IDOR**(Insecure Direct Object Reference, 안전하지 않은 직접 객체 참조)는 요청에 들어 있는 ID만 믿고 데이터를 내주는 실수예요.

1. 사용자 A가 자기 주문 `GET /api/orders/1001`을 봐요.
2. 주소의 숫자를 1002로 바꿔요.
3. 서버는 "로그인했나?"만 보고 "이 주문이 A 것인가?"는 안 봐요.
4. B의 주문(주소·전화번호)이 A에게 보여요.

OWASP(웹 보안 비영리 단체) Top 10 2021에서 이런 **접근 통제 실패**(Broken Access Control)가 1위(A01)예요. 2017년 5위에서 올라왔고, 조사한 앱에서 발생 건수가 가장 많았어요.

**고치는 법**은 "데이터 한 건마다 주인을 확인"하는 거예요.

```java
@GetMapping("/api/orders/{id}")
public OrderResponse get(@PathVariable Long id, @AuthenticationPrincipal LoginUser user) {
    // 나쁜 예: orderRepository.findById(id) — 아무 주문이나 나옴
    // 좋은 예: 조회 조건에 소유자를 같이 넣는다
    Order order = orderRepository.findByIdAndUserId(id, user.getId())
            .orElseThrow(OrderNotFoundException::new); // 남의 주문이면 404
    return OrderResponse.from(order);
}
```

OWASP가 권하는 예방책은 이래요.

- **기본 거부**(deny by default): 공개 자원이 아니면 일단 막고, 허용할 것만 연다.
- **레코드 소유권 강제**: 아무 사용자나 아무 레코드를 읽고 고치지 못하게.
- 접근 통제 코드를 **한 곳에 모아** 재사용(컨트롤러마다 따로 짜면 하나는 꼭 빠져요).
- 접근 통제 실패를 **로그로 남기고 알림**(ID를 하나씩 올려 보는 요청이 쌓이면 공격 신호).
- 접근 통제도 **단위·통합 테스트**에 포함("B가 A 주문 조회 시 404" 테스트).

<Aside type="caution" title="ID를 UUID로 바꾸면 해결될까요?">
추측하기 어려워질 뿐이에요. 링크 공유나 로그로 ID가 새면 그대로 뚫려요. 본질은 소유자 확인이에요.
</Aside>

### 로그인 화면에서 새는 정보

로그인 실패 메시지를 친절하게 쓰면 공격자에게 힌트가 돼요. OWASP 인증 치트시트(보안 권고 모음)는 응답만 보고 **계정이 있는지·잠겼는지·비활성인지 구별할 수 없게** 하라고 해요. 이렇게 가입 여부를 알아내는 공격을 **계정 열거**(account enumeration)라고 해요.

| 화면 | 나쁜 메시지 | 좋은 메시지 |
|---|---|---|
| 로그인 실패 | "존재하지 않는 아이디입니다" / "비활성화된 계정입니다" | "아이디 또는 비밀번호가 올바르지 않습니다" |
| 비밀번호 찾기 | "가입되지 않은 이메일입니다" | "가입된 이메일이면 재설정 메일을 보냈습니다" |
| 회원가입 | "이미 사용 중인 아이디입니다" | "입력한 주소로 활성화 링크를 보냈습니다" |

**응답 시간**도 같게 해야 해요. 없는 아이디일 때 비밀번호 해시 계산을 건너뛰면 응답이 빨라져서, 시간 차이로 가입 여부가 드러나요. HTTP 상태 코드도 경우마다 달라지지 않게 하는 게 좋아요.

### 무차별 대입 막기

로그인을 노리는 자동 공격은 세 종류로 나눠요.

| 공격 | 방식 | 잘 막는 것 |
|---|---|---|
| **무차별 대입**(brute force) | 한 계정에 비밀번호를 수없이 시도 | 계정별 실패 횟수 제한 |
| **크리덴셜 스터핑**(credential stuffing) | 다른 사이트에서 유출된 아이디·비번 쌍을 그대로 시도 | 유출 비번 대조, MFA, 이상 탐지 |
| **패스워드 스프레잉**(password spraying) | 흔한 비번 하나로 수많은 계정을 1~2번씩 시도 | 흔한 비번 금지, IP·전체 단위 제한, MFA |

방어는 여러 겹으로 쌓아요.

- **계정별로 실패 횟수를 세요.** OWASP는 IP가 아니라 계정 기준을 권해요. 공격자는 IP를 수천 개씩 바꾸니까요.
- IP별 요청 제한도 함께 둬요. 알고리즘은 [처리율 제한기](../../system-design/rate-limiter/)를 참고하세요. 계정별 제한은 "계정당 1~2번"인 스프레잉에 약하고, IP별 제한은 분산 IP에 약해서 둘을 겹쳐 쓰는 걸로 볼 수 있어요.
- 몇 번 실패한 뒤에만 CAPTCHA를 보여 주거나 응답을 늦춰요.
- **MFA**(다중 인증, 비밀번호 + 휴대폰 인증 같은 두 번째 수단)가 가장 강한 방어예요. 비밀번호가 새도 두 번째 수단이 없으면 못 들어와요.
- 실패·잠금은 전부 로그로 남겨요.

<Aside type="caution" title="잠금을 세게 할수록 안전할까요?">
공격자가 남의 계정에 일부러 틀린 비번을 넣어 잠가 버릴 수 있어요(서비스 거부). 그래서 잠긴 상태에서도 비밀번호 재설정으로 풀 수 있게 해 둬요.
</Aside>

비밀번호 변경, 이메일·결제 정보 변경처럼 민감한 작업은 로그인 중이어도 **현재 비밀번호를 다시 확인**(재인증)해요.

### 비밀번호 정책: 옛 관행이 틀렸어요

"특수문자 꼭 섞기, 90일마다 바꾸기"는 오래된 관행이에요. 미국 표준기술연구소의 인증 지침 **NIST SP 800-63B Rev.4**는 오히려 이걸 금지해요. 복잡한 규칙을 강제하면 사람들이 `Password1!`, `Password2!`처럼 예측 가능하게 바꾸기 때문이에요.

| 항목 | NIST 800-63B Rev.4 | 옛 관행 |
|---|---|---|
| 최소 길이 | 비밀번호만 쓰면 **15자 이상**(SHALL), MFA의 일부면 8자 이상 | 8자 |
| 최대 길이 | 최소 64자까지는 허용(SHOULD) | 16자 등으로 제한 |
| 문자 조합 규칙 | 강제 **금지**(SHALL NOT) | 대문자·숫자·특수문자 필수 |
| 주기적 변경 | 강제 **금지**(SHALL NOT). 단 유출 증거가 있으면 변경 강제(SHALL) | 90일마다 변경 |
| 유출·흔한 비번 | 목록과 **대조해 거부**(SHALL), 이유도 알려 줌 | 확인 안 함 |
| 비번 힌트·보안 질문 | 금지(SHALL NOT) | "첫 애완동물 이름은?" |
| 붙여넣기·비번 관리자 | 관리자·자동완성 허용(SHALL), 붙여넣기 허용(SHOULD) | 붙여넣기 막음 |
| 실패 횟수 제한 | 필수(SHALL), 연속 실패 100회가 상한 | — |

SHALL은 "반드시", SHOULD는 "권장", SHALL NOT은 "하면 안 됨"이에요. 저장할 때는 솔트를 붙인 느린 비밀번호 해시를 써요. 자세한 건 [해시·암호화](../hash-encryption/)에 있어요.

### 심화: 세션 고정 공격과 Spring의 기본 방어

**세션 고정**(session fixation)은 공격자가 **미리 알고 있는 세션 ID**를 피해자가 쓰게 만드는 공격이에요.

1. 공격자가 사이트에 접속해 세션 ID `abc`를 받아요.
2. 피해자가 `abc`를 쓰도록 꾸며요(링크 등).
3. 피해자가 `abc`인 채로 로그인해요.
4. 방어가 없으면 서버는 `abc`를 "로그인된 세션"으로 바꿔요. 공격자도 `abc`를 갖고 있으니 피해자로 로그인된 상태가 돼요.

방어는 간단해요. **로그인하는 순간 세션 ID를 새로 바꾸면** 공격자의 `abc`는 그냥 비로그인 세션으로 남아요.

Spring Security는 이걸 **기본으로** 해 줘요. `sessionFixation` 설정값은 이래요.

| 값 | 동작 |
|---|---|
| `changeSessionId` | 세션은 그대로 두고 ID만 바꿈. **Servlet 3.1 이상 컨테이너의 기본값** |
| `migrateSession` | 새 세션을 만들고 기존 속성을 전부 복사. Servlet 3.0 이하의 기본값 |
| `newSession` | 깨끗한 새 세션(Spring Security 관련 속성만 복사) |
| `none` | 보호 끔(쓰지 말 것) |

요즘 환경의 기본은 `migrateSession`이 아니라 `changeSessionId`예요. 그리고 **세션 ID를 URL에 넣으면 안 돼요.** URL은 서버 로그나 다른 사이트로 가는 Referer 헤더에 그대로 남아요.

### 심화: JWT는 어떻게 폐기하나

JWT는 서버가 상태를 안 들고 있어서 "로그아웃시켜도 토큰은 만료 전까지 유효"한 문제가 있어요. OWASP는 **JWT 수명을 짧게**, 오래 유지해야 하면 OAuth 표준(Refresh 토큰)을 따르라고 해요. Refresh 토큰 회전, 재사용 탐지, 차단 목록은 [쿠키·세션·JWT](../../web/cookie-session-jwt/)에 정리돼 있어요.

### 심화: 비밀(키·비밀번호) 관리

DB 비밀번호, AWS 키, API 토큰 같은 **비밀**(secret)을 다루는 원칙이에요(OWASP 비밀 관리 치트시트).

- **코드·설정 파일에 직접 쓰지 않아요.** 커밋 전에 pre-commit 훅이나 탐지 도구(예: detect-secrets)로 잡아요.
- **한 곳에 모아** 관리해요(AWS Secrets Manager, Vault, 쿠버네티스 [Secret](../../infra/k8s-config/) 등). 엔지니어가 모든 비밀을 읽을 수 없게 최소 권한, 누가 읽었는지 감사 로그.
- **정기적으로 자동 교체**(순환, rotation)해요. 가능하면 짧게 쓰고 버리는 임시 자격 증명을 써요.
- 환경 변수는 코드에 박는 것보단 낫지만, 같은 환경의 다른 프로세스가 볼 수 있고 로그·덤프에 찍힐 수 있어요. Docker의 `ENV`/`ARG`에 비밀을 넣으면 이미지 레이어에 남아요.
- 로그에 비밀번호·토큰을 그대로 찍지 않아요. 마스킹은 [로그로 디버깅하기](../../practice/debugging-with-logs/)를 보세요.

키가 새면 순서가 중요해요. **① 즉시 폐기(revoke) → ② 새 키로 교체(rotate) → ③ 노출된 곳(코드·로그)에서 삭제**. 앱을 재시작해도 훔쳐 간 키는 여전히 유효해요. Git 히스토리를 고쳐 쓸 수는 있지만, 그 전에 이미 누가 복제했을 수 있어요.

### 심화: OWASP Top 10에서의 위치

| 순위(2021) | 이름 | 이 페이지 내용 |
|---|---|---|
| A01 | Broken Access Control(접근 통제 실패) | IDOR, 권한 상승, 관리자 URL 직접 접근, JWT 변조 |
| A07 | Identification and Authentication Failures(식별·인증 실패) | 무차별 대입 허용, 약한 비번, MFA 없음, 세션 ID URL 노출, 로그인 후 세션 ID 재사용, 로그아웃 시 무효화 안 함 |

A07은 2017년판에서 "Broken Authentication"으로 2위였다가 7위로 내려왔어요. 2025년판에서도 접근 통제 실패는 A01 그대로이고, A07은 "Authentication Failures"로 이름만 짧아졌어요.

## 면접 질문

<details>
<summary>Q. 401과 403의 차이는 무엇인가요?</summary>

**답변(30초)**
401은 인증 실패, 403은 인가 실패예요. 401은 토큰이 없거나 만료·위조돼서 서버가 요청한 사람이 누구인지 확인하지 못한 경우이고, 다시 로그인하면 해결될 수 있어요. 403은 누군지는 확인됐지만 그 자원에 접근할 권한이 없는 경우라 같은 계정으로 다시 로그인해도 같아요. 이름이 Unauthorized라 헷갈리지만 401이 인증 쪽이에요.

**꼬리질문**
- Q. 401 응답에 꼭 넣어야 하는 헤더는? → `WWW-Authenticate`예요. RFC 9110이 MUST로 정해요.
- Q. 프론트에서 401과 403을 다르게 처리해야 하는 이유는? → 401이면 토큰 갱신 후 재시도, 403이면 재시도 없이 "권한 없음" 안내. 섞으면 무한 갱신 루프가 생겨요.
</details>

<details>
<summary>Q. IDOR가 뭐고 어떻게 막나요?</summary>

**답변(30초)**
IDOR는 요청에 담긴 ID만 믿고 데이터를 내주는 취약점이에요. 로그인은 확인했지만 "이 주문이 이 사용자 것인가"를 안 봐서, 주소의 주문 번호만 바꾸면 남의 주문이 보여요. 막으려면 데이터 한 건마다 소유자를 확인해야 해요. 조회 조건에 사용자 ID를 함께 넣고, 이 검사를 공통 코드로 모으고, "다른 사람 ID로 조회" 테스트를 둬요.

**꼬리질문**
- Q. ID를 UUID로 바꾸면 되지 않나요? → 추측만 어려워질 뿐, 새면 뚫려요. 소유자 확인이 본질이에요.
- Q. OWASP Top 10에서 몇 위인가요? → 2021년판 A01 Broken Access Control, 1위예요.
</details>

<details>
<summary>Q. 로그인 실패 메시지를 왜 "아이디 또는 비밀번호가 올바르지 않습니다"로 쓰나요?</summary>

**답변(30초)**
계정 열거를 막기 위해서예요. "없는 아이디입니다"라고 구분해 주면 공격자가 가입된 아이디 목록을 만들 수 있고, 그 목록으로 비밀번호 공격을 집중해요. 그래서 로그인뿐 아니라 비밀번호 찾기, 회원가입 응답도 가입 여부가 드러나지 않게 써요. 메시지뿐 아니라 응답 시간과 상태 코드도 같게 맞춰야 해요.

**꼬리질문**
- Q. 응답 시간은 왜 차이가 나나요? → 없는 아이디면 비밀번호 해시 계산을 건너뛰어 응답이 빨라지기 때문이에요.
</details>

<details>
<summary>Q. 좋은 비밀번호 정책은 뭔가요? 주기적 변경을 강제해야 하나요?</summary>

**답변(30초)**
NIST 800-63B Rev.4 기준으로는 길이를 충분히 요구하고 유출된 비번 목록과 대조하는 게 핵심이에요. 비밀번호만 쓰면 15자 이상, MFA와 함께면 8자 이상이고, 최소 64자까지 허용해요. 문자 조합 규칙과 주기적 변경 강제는 오히려 금지예요. 사람들이 예측 가능한 패턴으로 바꾸기 때문이고, 변경은 유출 증거가 있을 때만 강제해요.

**꼬리질문**
- Q. 붙여넣기를 막는 건 어떤가요? → 비번 관리자를 못 쓰게 해서 약한 비번을 유도해요. NIST는 허용을 권해요.
</details>

<details>
<summary>Q. 무차별 대입이나 크리덴셜 스터핑은 어떻게 막나요?</summary>

**답변(30초)**
한 가지로는 안 되고 여러 겹으로 막아요. 실패 횟수는 IP가 아니라 계정별로 세고, IP별 요청 제한도 함께 둬요. 몇 번 실패하면 CAPTCHA나 지연을 넣고, 유출 비번 대조와 MFA를 붙여요. 크리덴셜 스터핑은 수천 개 IP에서 오니까 IP 차단만으로는 못 막고, MFA가 가장 강한 방어예요.

**꼬리질문**
- Q. 계정 잠금의 부작용은? → 공격자가 남의 계정을 일부러 잠글 수 있어요. 비밀번호 재설정으로 풀 수 있게 해요.
- Q. 패스워드 스프레잉은 계정별 제한으로 막히나요? → 계정당 1~2번만 시도해서 잘 안 막혀요. 흔한 비번 금지와 전체 단위 이상 탐지가 필요해요.
</details>

<details>
<summary>Q. 세션 고정 공격이 뭐고, Spring Security는 어떻게 막나요?</summary>

**답변(30초)**
공격자가 미리 알고 있는 세션 ID를 피해자에게 쓰게 하고, 피해자가 로그인하면 같은 ID로 로그인된 세션을 가로채는 공격이에요. 로그인 순간 세션 ID를 새로 바꾸면 막혀요. Spring Security는 기본으로 이걸 해 주고, Servlet 3.1 이상에선 `changeSessionId`로 세션은 유지한 채 ID만 바꿔요.

**꼬리질문**
- Q. 세션 ID를 URL에 넣으면 안 되는 이유는? → 서버 로그와 Referer 헤더로 새서 남이 그대로 쓸 수 있어요.
</details>

<details>
<summary>Q. 남의 자원에 접근하면 403과 404 중 무엇을 줘야 하나요?</summary>

**답변(30초)**
둘 다 명세상 가능하고, 존재를 숨길지가 기준이에요. RFC 9110은 자원의 존재를 숨기고 싶으면 403 대신 404를 써도 된다고 해요. 남의 주문처럼 "그 번호의 주문이 있다"는 것조차 정보가 되면 404가 나아요. 관리자 메뉴처럼 존재가 알려져도 괜찮고 사용자에게 이유를 알려 주는 게 중요하면 403이 더 명확해요.

**꼬리질문**
- Q. 404로 숨기면 단점은? → 정상 사용자도 "권한 문제"인지 "없는 것"인지 모르니 디버깅과 고객 문의 대응이 어려워요. 서버 로그엔 실제 이유를 남겨요.
</details>

<details>
<summary>Q. API 키가 GitHub에 올라갔어요. 어떻게 하나요?</summary>

**답변(30초)**
가장 먼저 키를 폐기하고 새 키로 교체해요. 커밋을 지우는 건 그 다음이에요. 공개 레포는 올라간 순간 복제됐을 수 있어서 히스토리 삭제만으론 부족하고, 앱 재시작도 키를 무효로 만들지 않아요. 그다음 그 키로 무슨 일이 있었는지 감사 로그를 확인하고, 재발 방지로 pre-commit 검사와 비밀 관리 도구를 도입해요.

**꼬리질문**
- Q. 환경 변수에 넣으면 안전한가요? → 코드보다는 낫지만 다른 프로세스·로그·덤프로 샐 수 있어요. 비밀 관리 도구로 주입하는 게 더 나아요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 상세 API(GET /api/orders/주문번호)에서 고객이 "주소창 숫자를 바꿨더니 다른 사람 주문의 이름·주소·전화번호가 보인다"고 신고했어요. 어떻게 대응하고 재발을 막을까요?</summary>

**상황 파악**
인증(로그인 확인)은 되는데 **객체 단위 인가(이 주문의 주인 확인)가 빠진 IDOR**예요. 개인정보가 노출됐으니 버그이면서 보안 사고예요. 이미 다른 사람이 악용했을 수도 있어요.

**원인 후보**
1. `findById(id)`로만 조회하고 `order.userId`와 로그인 사용자를 비교하지 않음.
2. 목록 API엔 사용자 조건이 있지만 상세·수정·취소 API엔 빠짐(엔드포인트마다 따로 짠 검사).
3. 관리자용 API를 일반 사용자도 호출할 수 있음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 조회 쿼리에 소유자 조건(`findByIdAndUserId`) | 가장 확실, 남의 데이터가 아예 안 읽힘 | 모든 쿼리를 손봐야 하고, 하나라도 빠지면 그대로 뚫림 |
| B. 공통 인가 계층(`@PreAuthorize`로 소유자 검사, 또는 서비스 공통 메서드) | 검사를 한 곳에 모아 누락이 줄어듦 | 처음 구조를 잡는 비용, 규칙이 복잡하면 읽기 어려움 |
| C. 주문 번호를 UUID로 변경 | 추측이 어려워짐 | 근본 해결 아님, 링크·로그로 새면 그대로 |
| D. 이상 탐지(한 사용자가 남의 ID로 404/403을 연속으로 받으면 알림) | 악용 시도를 빨리 발견 | 막아 주진 못함 |

**내가 고를 방법**
먼저 **즉시 A로 핫픽스**해요. 남의 주문이면 404를 줘서 그 번호의 존재도 숨겨요. 동시에 접근 로그로 다른 사람 주문을 조회한 기록이 있는지 확인하고, 있으면 개인정보 유출 절차(보고·통지)를 밟아요. 그다음 **B로 검사를 공통화**하고, 상세·수정·취소 API 전부에 "B 사용자가 A 주문 접근 시 404" 통합 테스트를 넣어요. D는 안전망으로 추가해요. C는 근본 해결이 아니라서 보조로만 생각해요.

**채점 포인트**: IDOR/객체 단위 인가 누락 진단, 인증과 인가 구분, 소유자 조건 조회, 404로 존재 숨김(RFC 9110 MAY), 상세 외 다른 API도 점검, 공통화, 접근 통제 테스트, 실패 로깅, 유출 여부 확인과 보고, UUID는 근본 해결 아님.
</details>

<details>
<summary>상황: 보안 점검에서 "로그인 실패 시 '존재하지 않는 아이디입니다'와 '비밀번호가 틀렸습니다'가 따로 나와서 가입 여부가 드러난다"는 지적을 받았어요. 무엇을 어떻게 고칠까요?</summary>

**상황 파악**
**계정 열거** 취약점이에요. 공격자가 아이디 목록을 넣어 보며 가입자를 골라낸 뒤, 그 계정에만 비밀번호 공격(크리덴셜 스터핑 등)을 집중할 수 있어요. 금융 서비스라면 "이 사람이 우리 고객"이라는 사실 자체도 민감 정보예요.

**원인 후보**
1. 로그인 실패 메시지를 경우별로 나눔.
2. 비밀번호 찾기·회원가입 화면도 "가입되지 않은 이메일", "이미 쓰는 아이디"로 같은 정보를 흘림.
3. 메시지를 통일해도 없는 아이디는 해시 계산을 건너뛰어 응답이 빠름(시간 차).
4. 경우별로 HTTP 상태 코드가 다름.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 모든 실패를 한 메시지·한 상태 코드로 통일 | 구현이 쉽고 효과가 큼 | 사용자가 "아이디를 틀렸는지" 몰라 불편, 문의 증가 |
| B. 응답 시간 통일(없는 아이디도 더미 해시 계산) | 시간 차 공격까지 막음 | 매 요청 해시 비용 |
| C. 비번 찾기·가입도 "가입돼 있으면 메일을 보냈습니다" 형태로 | 우회 경로까지 막음 | 가입 화면 흐름이 이메일 인증 중심으로 바뀜 |
| D. 로그인 시도 제한·이상 탐지 추가 | 대량 열거 자체를 늦춤 | 메시지 문제를 직접 고치진 못함 |

**내가 고를 방법**
A + B + C를 같이 해요. 로그인 화면만 고치면 비밀번호 찾기나 가입 화면이 같은 정보를 계속 흘려서 의미가 줄어들어요. 사용자 불편은 "아이디 찾기" 기능을 이메일·본인인증 기반으로 따로 제공해서 줄여요. D는 열거 시도 자체를 늦추려고 함께 둬요. 실제 실패 이유(없는 아이디인지)는 화면이 아니라 서버 로그에만 남겨요.

**채점 포인트**: 계정 열거 개념, 로그인·비번 찾기·가입 세 화면 모두, 메시지·상태 코드·응답 시간 통일, 사용성 트레이드오프와 보완책, 시도 제한·로깅 병행.
</details>

<details>
<summary>상황: 신입 개발자가 AWS 액세스 키가 들어 있는 설정 파일을 public GitHub 레포에 푸시했고, 20분 뒤 알아챘어요. 무엇부터 해야 할까요?</summary>

**상황 파악**
공개 레포에 올라간 키는 **이미 누군가 가져갔다고 가정**해야 해요. 커밋을 지워도 이미 복제됐을 수 있어서 "지우면 끝"이 아니에요.

**원인 후보(재발 방지용)**
1. 키를 설정 파일에 직접 적음(하드코딩).
2. `.gitignore`·pre-commit 검사가 없음.
3. 키 권한이 넓고 오래 쓰는 정적 키라 피해 범위가 큼.

**해결책과 트레이드오프**

| 순서 | 할 일 | 이유 |
|---|---|---|
| 1 | **키 즉시 폐기(비활성화)** | 가장 빨리 피해를 멈춤. 재시작은 무효화가 아님 |
| 2 | 새 키 발급 → 비밀 관리 도구로 서비스에 배포 | 폐기로 멈춘 서비스를 복구 |
| 3 | 클라우드 감사 로그로 20분간 그 키로 한 일 확인, 생성된 자원 정리 | 몰래 서버를 띄웠거나 데이터를 가져갔을 수 있음 |
| 4 | Git 히스토리에서 제거 | 추가 노출 줄이기. 단 히스토리 재작성은 커밋 링크가 깨지는 등 부작용이 있음 |
| 5 | pre-commit 비밀 탐지, 레포 스캔, Secrets Manager·짧은 수명 자격 증명 도입 | 재발 방지 |

두 가지 접근을 비교하면, **히스토리 삭제부터** 하면 화면에서는 빨리 사라지지만 이미 가져간 키는 계속 유효해요. **폐기부터** 하면 잠깐 서비스가 멈출 수 있지만 피해가 확실히 멈춰요.

**내가 고를 방법**
폐기 → 교체 → 사용 내역 확인 → 히스토리 정리 → 재발 방지 순서로 가요. 서비스 중단이 걱정되면 새 키를 먼저 발급해 배포 준비를 해 두고 폐기를 곧바로 이어서 해요. 그래도 순서의 핵심은 "옛 키가 살아 있는 시간을 최소로"예요. 재발 방지에서는 신입 개인을 탓하기보다, 키를 코드에 쓸 수 없게 만드는 구조(비밀 관리 도구, 커밋 전 검사)를 갖춰요.

**채점 포인트**: 공개 즉시 유출로 간주, 폐기·순환이 삭제보다 먼저, 재시작은 무효화 아님, 감사 로그로 피해 범위 확인, 히스토리 재작성의 한계와 부작용, 하드코딩 금지·pre-commit 탐지·중앙 비밀 관리·최소 권한·자동 순환.
</details>

## 필기 포인트

- 401 = 인증 실패(이름은 Unauthorized), `WWW-Authenticate` 헤더 **MUST**. 403 = 인가 실패, 같은 자격 증명으로 재시도 **SHOULD NOT**.
- 존재를 숨기려면 403 대신 **404 MAY**.
- OWASP Top 10:2021 **A01 = Broken Access Control**(2017년 5위 → 1위), **A07 = Identification and Authentication Failures**(2017년 2위 Broken Authentication).
- NIST 800-63B Rev.4: 단일 요소 비번 **최소 15자**, MFA 일부면 8자, 최대 64자 이상 허용, **조합 규칙·주기 변경 강제 금지**, 유출 목록 대조 필수.
- Spring Security 세션 고정 기본값: Servlet 3.1+ **`changeSessionId`**(3.0 이하는 `migrateSession`).
