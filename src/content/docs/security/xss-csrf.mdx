:::tip[한 줄 요약]
**XSS**는 공격자가 넣은 스크립트가 **우리 사이트 안에서** 사용자 권한으로 실행되는 공격이고, **CSRF**는 **다른 사이트가** 로그인된 사용자의 브라우저를 시켜 요청만 보내게 하는 공격이에요. XSS는 **출력할 때 컨텍스트에 맞게 인코딩**해서 막고, CSRF는 **CSRF 토큰 + SameSite 쿠키**로 막아요. XSS가 뚫리면 CSRF 방어도 같이 무너져요.
:::

:::note[처음이라면 여기까지]
① XSS는 "게시판에 남이 쓴 글이 내 화면에서 프로그램처럼 실행되는 것"이에요. 막는 법은 남이 쓴 글을 화면에 넣을 때 **글자로만** 보이게 바꾸는 거예요.

② CSRF는 "내가 로그인해 둔 상태를 남이 빌려 쓰는 것"이에요. 브라우저가 쿠키를 알아서 붙여 주는 성질을 이용해요. 막는 법은 "우리 화면에서 보낸 요청이 맞는지" 확인하는 **토큰**이에요.

③ Thymeleaf `th:text`, React의 `{}` 출력은 기본으로 글자 처리를 해 줘요. 위험한 건 `th:utext`, `dangerouslySetInnerHTML`, `innerHTML`처럼 "HTML로 그대로 넣기"예요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

**XSS 비유.** 회사 게시판에 누가 쪽지를 붙였는데, 그 쪽지를 읽는 순간 읽은 사람 이름으로 "내 사원증을 저 사람에게 넘겨라"라는 명령이 실행된다고 해 봐요. 쪽지를 쓴 사람은 공격자인데, 명령은 **읽은 사람의 권한**으로 실행돼요. 게시판 관리자가 쪽지를 붙이기 전에 "명령문은 그냥 글자로만 보이게" 바꿔 두면 아무 일도 안 생겨요.

**CSRF 비유.** 내가 은행 창구에서 본인 확인을 마치고 잠깐 자리를 비운 사이, 누가 내 대신 "송금" 버튼을 눌러요. 은행은 "본인 확인이 된 사람의 요청"으로 보고 처리해요. 공격자는 내 통장 잔고를 볼 수는 없지만, 버튼을 누르게 하는 것만으로 충분해요. 은행이 "창구에서 직접 받은 번호표"를 함께 내야만 처리해 주면 막을 수 있어요. 이 번호표가 **CSRF 토큰**이에요.

단, 실제로는 사람이 아니라 **브라우저**가 이 일을 해요. XSS는 브라우저가 남의 글을 코드로 해석해서, CSRF는 브라우저가 쿠키를 자동으로 붙여서 생겨요.

## 제대로 알기

### XSS와 CSRF 한눈에

| | XSS | CSRF |
|---|---|---|
| 이름 | Cross-Site Scripting | Cross-Site Request Forgery(요청 위조) |
| 어디서 실행? | **우리 사이트 안**에서 공격자 코드 실행 | **다른 사이트**에서 요청만 보냄 |
| 공격자가 할 수 있는 것 | 화면 읽기, 쿠키(HttpOnly 아닌 것) 읽기, API 호출 등 거의 전부 | 상태를 바꾸는 요청 보내기(응답은 못 읽음) |
| 이용하는 성질 | 브라우저가 HTML 속 코드를 실행함 | 브라우저가 쿠키를 자동으로 붙임 |
| 주된 방어 | 출력 인코딩, 안전한 API, CSP | CSRF 토큰, SameSite, Origin·Fetch Metadata 검사 |

XSS로 실행된 코드는 우리 사이트의 **출처**(origin, "프로토콜+도메인+포트" 묶음, 브라우저가 "같은 사이트 코드인가"를 가르는 기준)로 돌아가요. 그래서 우리 페이지에 있는 CSRF 토큰도 읽어서 같이 보낼 수 있어요. **XSS가 있으면 CSRF 방어도 소용없어요.**

### XSS 3종류

| 종류 | 공격 문자열이 오는 길 | 서버 응답에 공격 문자열이 있나 | 예 |
|---|---|---|---|
| 저장형(Stored) | DB에 저장됐다가 다른 사람이 볼 때 화면에 나옴 | 있음 | 게시판 댓글, 프로필 소개 |
| 반사형(Reflected) | 요청 URL·파라미터가 응답에 그대로 되돌아옴 | 있음 | 검색 결과 "○○ 검색 결과" |
| DOM 기반 | 브라우저 JS가 URL 등을 읽어 화면에 직접 넣음 | **없을 수도 있음** | `location.hash`를 `innerHTML`에 넣기 |

저장형과 반사형은 "공격 문자열이 피해자에게 **어떤 길로** 오나"로 나눈 거예요. 저장형은 한 번 심으면 그 글을 보는 모든 사람이 당해서 피해가 커요. 반사형은 공격자가 조작한 링크를 피해자가 눌러야 해요.

DOM 기반은 "**어디서** 잘못 처리했나"가 다른 경우예요. 서버는 잘못이 없고 프론트 JS가 위험하게 처리해요. 이때 데이터가 들어오는 곳을 **소스**(source, 예: `location.hash`), 데이터가 HTML·코드로 해석되는 곳을 **싱크**(sink, 예: `innerHTML`, `document.write()`, `eval()`, 문자열을 넘긴 `setTimeout`)라고 불러요.

### 1차 방어: 출력할 때 인코딩

XSS 방어의 핵심은 "**입력할 때 거르기**"가 아니라 "**출력할 때 그 자리에 맞게 바꾸기**"예요. 같은 글이라도 HTML 본문, 태그 속성, JS 코드, URL 중 어디에 들어가느냐에 따라 위험한 글자가 달라서, 입력 시점엔 어떻게 바꿔야 할지 알 수 없기 때문이에요.

**HTML 엔티티**(entity)는 `<`를 `&lt;`처럼 "글자로만 보이는 표기"로 바꾸는 거예요. 브라우저는 `&lt;`를 태그 시작으로 보지 않고 화면에 `<` 글자만 그려요.

| 들어가는 자리(컨텍스트) | OWASP 권장 |
|---|---|
| HTML 본문 | `&`, `<`, `>`, `"`, `'`를 HTML 엔티티로 |
| HTML 속성값 | 값을 반드시 따옴표로 감싸고 속성 인코딩. 단 `onclick` 같은 **이벤트 핸들러 속성은 인코딩해도 안전하지 않음** → `addEventListener()` 사용 |
| JavaScript 코드 | 신뢰할 수 없는 데이터를 코드로 넣지 않기. 직접 따옴표 이스케이프 금지, 검증된 인코더 사용 |
| CSS | CSS 소스에 넣지 않기. `style.setProperty()` + 허용 목록 값 |
| URL | URL 전체가 아니라 **파라미터 값만** `encodeURIComponent`로. `href`·`src`에 넣으면 URL 인코딩 뒤 속성 인코딩도. `javascript:` 스킴은 따로 검증 |

### 템플릿 엔진의 자동 이스케이프

대부분의 템플릿·프레임워크는 **기본으로 글자 처리**를 해 줘요. 위험한 건 "HTML 그대로 넣기" **탈출구**(escape hatch)를 쓸 때예요.

| 도구 | 안전(이스케이프함) | 위험(그대로 넣음) |
|---|---|---|
| Thymeleaf 3.1 | `th:text`, 인라인 `[[...]]` | `th:utext`, 인라인 `[(...)]` |
| React | JSX 안의 `{값}` 출력 | `dangerouslySetInnerHTML` |
| Angular·Lit 등 | 기본 바인딩 | `bypassSecurityTrustAs*`, `unsafeHTML` |

Thymeleaf에서 값이 `<b>굵게</b>`라면 `th:text`는 `&lt;b&gt;굵게&lt;/b&gt;`로 바꿔 넣어 화면에 태그가 글자로 보이고, `th:utext`는 진짜 굵은 글씨가 돼요. `utext`의 u는 unescaped(이스케이프 안 함)예요.

```html
<!-- 안전: 사용자 입력은 글자로만 -->
<p th:text="${comment.body}"></p>
<!-- 위험: 사용자 입력이면 XSS -->
<p th:utext="${comment.body}"></p>
```

React의 `dangerouslySetInnerHTML`은 이름에 "위험하다(dangerously)"를 일부러 넣었어요. 쓰려면 `{{ __html: 값 }}`처럼 한 번 더 감싸야 해서 실수로 쓰기 어렵게 했어요. React 공식 문서도 신뢰되고 정제된 데이터에만 쓰라고 해요.

<Aside type="caution" title="React를 쓰면 XSS가 없다?">
아니에요. `dangerouslySetInnerHTML` 말고도 `href`에 사용자가 준 URL을 넣으면 `javascript:` 링크가 될 수 있어요. OWASP 치트시트는 React 19가 `href`·`src`의 `javascript:` URL을 막는다고 설명하지만, 이번에 React 공식 문서에서 직접 확인하진 못했어요. 어느 쪽이든 앱에서 URL 스킴(`https:`만 허용 등)을 검증해야 해요.
</Aside>

### innerHTML vs textContent

프론트 JS에서 글을 화면에 넣을 때 가장 흔한 실수예요.

- `innerHTML`: 넣은 문자열을 **HTML로 해석**해요. 태그가 진짜 태그가 돼요.
- `textContent`: 넣은 문자열을 **글자로만** 넣어요. 코드를 실행하지 않아요.

```js
const input = '<img src=x onerror="alert(1)"><b>bold</b>';
box1.innerHTML = input;    // img 태그가 만들어지고 onerror 실행됨
box2.textContent = input;  // 화면에 위 문자열이 글자 그대로 보임
```

실험 예시로 브라우저(Chromium)에서 한 번 넣어 보면 이래요.

| 넣은 방법 | 넣은 문자열 | 결과 |
|---|---|---|
| `innerHTML` | `img onerror` + `b` 태그 | `b`는 굵은 글씨, `onerror` **실행됨** |
| `textContent` | 같은 문자열 | 글자 그대로 표시, 실행 안 됨 |
| `innerHTML` | `script` 태그 | **실행 안 됨** |

마지막 줄이 중요해요. HTML 표준상 `innerHTML`로 넣은 `script`는 실행되지 않아요. 그래서 "`script` 태그만 걸러내면 된다"는 틀린 생각이에요. 실제 공격은 `onerror` 같은 이벤트 핸들러나 `javascript:` URL로 들어와요.

안전한 API는 `textContent`, `createTextNode`, `insertAdjacentText`, `value`, `className`, 이름이 고정된 `setAttribute` 등이에요. JSON 문자열은 `eval` 대신 `JSON.parse`로 읽어요.

### 사용자가 HTML을 써야 한다면: 정제

게시판 에디터처럼 굵게·링크를 허용해야 하면 전부 글자 처리할 수는 없어요. 이때는 **HTML 정제**(sanitize, 허용한 태그·속성만 남기고 나머지는 지우기) 라이브러리를 써요. 브라우저 쪽에선 **DOMPurify**가 대표적이에요. 정제한 뒤에 결과를 다시 문자열로 가공하면 정제가 깨질 수 있으니 그대로 넣어요.

### HttpOnly 쿠키: 훔치기만 막아요

**HttpOnly** 쿠키는 JS의 `document.cookie`로 읽을 수 없어요. 그래서 XSS 코드가 세션 쿠키 **값을 훔쳐 가는 것**은 막아요. 하지만 그 페이지에서 `fetch()`로 요청을 보내면 쿠키는 여전히 실려 가요. 즉 XSS 코드가 **그 자리에서 사용자 대신 요청 보내기**는 못 막아요. 쿠키 속성 전체 표는 [쿠키·세션·JWT](../../web/cookie-session-jwt/)에 있어요.

### CSRF는 왜 생기나

브라우저는 `bank.com`으로 가는 요청에 `bank.com` 쿠키를 **자동으로** 붙여요. 요청을 누가 시작했는지(우리 화면인지, 다른 사이트의 숨은 폼인지)는 따지지 않아요. 공격자는 이 점을 이용해 자기 사이트에 숨은 폼을 두고, 방문자의 브라우저가 `bank.com/transfer`로 POST하게 만들어요. 공격자는 응답을 못 읽지만, 송금이 처리되기만 하면 목적을 이뤄요.

전제가 하나 있어요. **GET은 상태를 바꾸면 안 돼요.** GET으로 송금·삭제를 하게 만들면 링크나 이미지 태그만으로 요청을 보낼 수 있고, 아래 SameSite=Lax 같은 방어도 비켜 가요.

### CSRF 방어 1: 토큰

**동기화 토큰 패턴**(Synchronizer Token Pattern)이 기본이에요.

1. 서버가 예측할 수 없는 토큰을 만들어 세션에 저장해요.
2. 폼을 그릴 때 숨은 필드(Spring에선 `_csrf`)나 헤더 값으로 같이 내려줘요.
3. 상태를 바꾸는 요청이 오면 요청 속 토큰과 세션의 토큰을 비교해요. 다르거나 없으면 거절해요.

공격자 사이트는 **동일 출처 정책**(SOP, 다른 출처의 응답은 JS가 읽을 수 없다는 브라우저 규칙) 때문에 우리 페이지를 읽을 수 없어서 토큰 값을 알 수 없어요.

주의할 점: 토큰을 **쿠키에만** 넣고 쿠키로 비교하면 의미가 없어요. 쿠키는 공격 요청에도 자동으로 붙으니까요. 비교 대상은 요청 **본문이나 헤더**에 직접 넣은 값이어야 해요.

### CSRF 방어 2: SameSite 쿠키

**SameSite**는 "다른 사이트에서 시작된 요청에도 이 쿠키를 붙일까"를 정하는 쿠키 속성이에요.

| 값 | 다른 사이트에서 온 요청에 쿠키를 붙이나 | 특징 |
|---|---|---|
| `Strict` | 안 붙임 | 가장 안전. 외부 링크로 들어오면 로그인이 풀린 것처럼 보일 수 있음 |
| `Lax` | 링크 클릭 같은 **최상위 이동 + 안전한 메서드(GET 등)**일 때만 붙임. POST·PUT·DELETE엔 안 붙임 | 일반적인 절충 |
| `None` | 항상 붙임 | 반드시 `Secure`(HTTPS 전용)와 함께 |

SameSite는 **보조 방어**로 쓰고, 토큰을 대신하지는 않아요(OWASP와 Spring 문서 모두 같은 입장). 이유는 아래 심화에 있어요.

### CORS는 CSRF 방어가 아니에요

**CORS**는 "다른 출처의 JS가 우리 응답을 **읽어도** 되나"를 정하는 규칙이에요. CSRF는 응답을 읽을 필요가 없어서, CORS를 우리 도메인만 허용해도 폼 POST는 그대로 날아가요. 자세한 건 [CORS](../../web/cors/)에 있어요.

### 심화: CSP(Content Security Policy)

**CSP**는 서버가 `Content-Security-Policy` 응답 헤더로 "이 페이지에서 실행해도 되는 스크립트는 이것뿐"이라고 브라우저에 알려 주는 장치예요. `script-src`(또는 `default-src`)를 정하면 이렇게 돼요.

- 인라인 `script` 블록, `onclick` 같은 인라인 핸들러, `javascript:` URL이 **nonce나 hash 없이는 차단**돼요.
- `eval`, `new Function`은 `'unsafe-eval'`이 없으면 차단돼요.

많이 권하는 **Strict CSP** 예시예요.

```http
Content-Security-Policy: script-src 'nonce-R4nd0m'; object-src 'none'; base-uri 'none'
```

```html
<script nonce="R4nd0m">/* 허용된 우리 스크립트 */</script>
```

**nonce**(한 번 쓰는 값)는 **응답마다 새로, 예측할 수 없게** 만들어야 해요. 고정값이면 공격자가 그 값을 붙여 스크립트를 넣을 수 있으니까요. 그래서 서버가 페이지를 매번 그리는 구조가 필요하고, 정적 페이지는 스크립트 내용의 hash로 허용해요. `'unsafe-inline'`을 넣으면 CSP의 목적이 대부분 사라져요.

도입은 `Content-Security-Policy-Report-Only` 헤더로 시작해요. 차단은 안 하고 위반만 보고받아서, 어떤 스크립트가 걸리는지 먼저 파악할 수 있어요. 덤으로 `frame-ancestors 'none'`은 다른 사이트가 우리 페이지를 iframe에 넣는 **클릭재킹**을 막아요(`X-Frame-Options`를 대체).

CSP는 **심층 방어**(defense in depth, 앞 방어가 뚫렸을 때를 대비한 겹겹 방어)예요. 출력 인코딩을 안 해도 되는 면허가 아니에요.

### 심화: CSRF 토큰 방식 비교

| 방식 | 어떻게 | 언제 | 주의 |
|---|---|---|---|
| 동기화 토큰 | 서버 세션에 토큰 저장, 요청 값과 비교 | 세션 있는(상태 있는) 앱 | 세션 저장소 필요 |
| 서명형 더블 서브밋 쿠키 | 쿠키와 요청 헤더·파라미터에 같은 토큰. 토큰을 HMAC으로 세션 값에 묶어 서명 | 서버 세션이 없는 앱 | 서명 없는 단순형(naive)은 서브도메인 등에서 쿠키를 심으면 깨져서 비권장 |
| Fetch Metadata | 브라우저가 붙이는 `Sec-Fetch-Site` 헤더가 cross-site이고 메서드가 안전하지 않으면 거절 | 최신 OWASP가 주요 신호로 서술 | 헤더 없는 구형 브라우저 대비 Origin 검사 폴백 필수 |
| Origin/Referer 검사 | 요청의 `Origin`을 우리 출처와 **정확히** 비교 | 보조 | 접두사 비교 금지. 헤더 없음·`Origin: null`은 같은 출처 증거가 아님 |
| 커스텀 헤더 요구 | API가 `X-CSRF-Token` 같은 헤더를 요구 | API | 다른 출처가 커스텀 헤더를 붙이면 preflight가 생기고 CORS가 막음. CORS를 넓게 열면 약해짐 |

**로그인 CSRF**도 있어요. 피해자를 공격자 계정으로 로그인시켜서, 피해자가 입력한 정보(검색 기록, 카드 정보 등)를 공격자 계정에 쌓이게 하는 공격이에요. 그래서 로그인 폼에도 토큰을 쓰고, 로그인 후엔 세션을 새로 발급해요(세션 고정 방지). 로그아웃도 보호 대상이에요.

### 심화: SameSite 기본값과 한계

SameSite를 **아예 안 쓰면** 브라우저마다 달라요. MDN은 "일부 브라우저가 Lax를 기본으로 쓴다"고 하고, OWASP는 Chromium 계열은 Lax가 기본이고 Firefox·Safari는 아니라고 설명해요.

게다가 기본값으로 적용된 Lax는 명시한 Lax보다 느슨해요. **만들어진 지 2분 안 된 쿠키**는 다른 사이트에서 온 최상위 POST에도 실릴 수 있어요(로그인 직후를 깨뜨리지 않으려는 예외).

쿠키 규칙의 개정판 **RFC 6265bis**는 아직 **초안**(draft-ietf-httpbis-rfc6265bis-22, 2025-12 개정)이에요. 정식 RFC로 발행되지 않았어요. 이 초안은 속성이 없을 때를 "Default" 모드(Lax와 같음)로 두고, 브라우저가 고를 수 있는 "Lax-allowing-unsafe" 모드를 설명해요. 이건 따로 쓰는 값이 아니라, 속성 없는 쿠키 중 최근 생긴 것(2분 이하 제안)에 한해 메서드와 상관없이 cross-site 최상위 요청에 붙이는 모드예요.

SameSite만 믿으면 안 되는 이유를 모으면 이래요.

- 브라우저마다 기본값이 다르고, 구형 브라우저는 지원하지 않아요.
- 2분 예외가 있어요.
- Lax는 상태를 바꾸는 GET을 못 막아요.
- Strict는 외부 링크로 들어오면 로그인이 안 된 것처럼 보여 사용자가 헷갈려요.
- "같은 사이트"는 등록 도메인 기준이라, 형제 서브도메인(예: 같은 회사의 다른 서브도메인)이 뚫리면 같은 사이트로 취급된다고 알려져 있어요(초안 원문 대조는 이번에 하지 못함).

### 심화: Spring Security의 CSRF와 끄는 기준

Spring Security 레퍼런스 7.2.0 기준이에요(6.x도 같은 동작으로 보이지만 6.x 문서와 따로 대조하진 않았어요).

- 서블릿 앱에선 CSRF 보호가 **기본으로 켜져** 있고 POST 같은 안전하지 않은 메서드에 적용돼요. 토큰이 없으면 403이에요.
- 기본 저장소는 세션(`HttpSessionCsrfTokenRepository`), 기본 처리기는 매 요청 토큰을 섞어(마스킹) 보내는 `XorCsrfTokenRequestAttributeHandler`예요.
- Thymeleaf 같은 뷰는 POST 폼에 `_csrf` 숨은 필드를 자동으로 넣어 줘요.

끌지 판단하는 기준은 하나예요. **브라우저가 자격 정보(쿠키·Basic 인증)를 자동으로 붙이는가?**

| 인증 방식 | 브라우저 자동 첨부 | CSRF |
|---|---|---|
| 세션 쿠키 로그인 | 예 | 켜 둬야 함 |
| JWT를 쿠키에 저장 | 예 | **켜 둬야 함** |
| JWT를 `Authorization: Bearer` 헤더로, JS가 직접 붙임 | 아니요 | 끄는 경우가 많음 |
| 브라우저가 아닌 서버 간 호출만 받음 | 해당 없음 | 꺼도 됨 |

"REST·JSON이라 안전하다"는 오해예요. `enctype="text/plain"` 폼으로 JSON처럼 생긴 본문을 보낼 수 있고, Basic 인증도 자동 첨부돼요. 끄는 코드는 `http.csrf(csrf -> csrf.disable())`, 일부 경로만 빼려면 `ignoringRequestMatchers`예요. SPA 설정(`csrf.spa()`)과 403 디버깅은 [Spring Security](../../spring/spring-security/)에 있어요.

## 면접 질문

<details>
<summary>Q. XSS와 CSRF의 차이는 무엇인가요?</summary>

**답변(30초)**
XSS는 공격자 스크립트가 우리 사이트 안에서 사용자 권한으로 실행되는 공격이고, CSRF는 다른 사이트가 로그인된 사용자의 브라우저를 시켜 요청만 보내게 하는 공격이에요. XSS는 브라우저가 남의 글을 코드로 해석해서, CSRF는 브라우저가 쿠키를 자동으로 붙여서 생겨요. CSRF는 응답을 못 읽지만 XSS는 화면과 데이터를 다 볼 수 있어요. 그래서 XSS가 있으면 페이지의 CSRF 토큰도 읽어 보낼 수 있어서 CSRF 방어가 무너져요.

**꼬리질문**
- Q. 둘 중 뭐가 더 위험해요? → 보통 XSS예요. 같은 출처에서 실행되니 CSRF로 할 수 있는 건 다 할 수 있어요.
- Q. CSRF에서 공격자가 응답을 못 읽는데 왜 위험해요? → 송금·비밀번호 변경처럼 요청이 처리되기만 하면 피해가 생기니까요.
</details>

<details>
<summary>Q. XSS의 종류를 설명해 보세요.</summary>

**답변(30초)**
저장형, 반사형, DOM 기반이 있어요. 저장형은 공격 문자열이 DB에 저장됐다가 다른 사용자가 볼 때 실행돼서 피해 범위가 커요. 반사형은 URL 파라미터가 응답에 그대로 되돌아와 실행되고, 조작된 링크를 눌러야 해요. DOM 기반은 서버가 아니라 프론트 JS가 `location.hash` 같은 값을 `innerHTML`에 넣어서 생기고, 서버 응답엔 공격 문자열이 없을 수도 있어요.

**꼬리질문**
- Q. DOM XSS는 서버에서 못 잡나요? → 서버 응답에 페이로드가 없을 수 있어서 서버 필터로는 못 잡아요. 프론트에서 안전한 싱크(`textContent`)를 써야 해요.
- Q. 소스와 싱크가 뭐예요? → 소스는 데이터가 들어오는 곳(`location.hash`), 싱크는 그게 코드나 HTML로 해석되는 곳(`innerHTML`, `eval`)이에요.
</details>

<details>
<summary>Q. XSS는 어떻게 막나요?</summary>

**답변(30초)**
1차 방어는 출력할 때 컨텍스트에 맞게 인코딩하는 거예요. HTML 본문이면 `<` 같은 글자를 엔티티로 바꾸고, 속성·JS·URL은 각각 규칙이 달라요. 실무에선 Thymeleaf `th:text`나 React 기본 출력처럼 자동 이스케이프를 쓰고, `th:utext`, `dangerouslySetInnerHTML`, `innerHTML` 같은 탈출구를 피해요. HTML을 허용해야 하면 DOMPurify 같은 정제 라이브러리를 써요. 여기에 CSP와 HttpOnly 쿠키를 심층 방어로 더해요.

**꼬리질문**
- Q. 입력받을 때 다 이스케이프해서 저장하면 안 되나요? → 출력 위치(HTML·속성·JS·URL)마다 인코딩이 달라서, 출력할 때 그 자리에 맞게 해야 해요.
- Q. `script` 태그만 막으면 되지 않나요? → 아니요. `img onerror` 같은 이벤트 핸들러나 `javascript:` URL로도 실행돼요. `innerHTML`로 넣은 `script`는 오히려 실행되지 않아요.
</details>

<details>
<summary>Q. CSRF는 어떻게 막나요?</summary>

**답변(30초)**
기본은 CSRF 토큰이에요. 서버가 예측할 수 없는 토큰을 세션에 저장하고 폼이나 헤더로 내려준 뒤, 상태를 바꾸는 요청에서 그 값을 비교해요. 다른 사이트는 동일 출처 정책 때문에 우리 페이지를 읽을 수 없어 토큰을 모르니까 막혀요. 여기에 SameSite=Lax 쿠키, Fetch Metadata(`Sec-Fetch-Site`)나 Origin 헤더 검사를 보조로 겹쳐요. 그리고 GET으로는 상태를 바꾸지 않게 설계해요.

**꼬리질문**
- Q. 토큰을 쿠키에 넣어 두고 쿠키로 비교하면요? → 쿠키는 공격 요청에도 자동으로 붙어서 의미가 없어요. 요청 본문이나 헤더 값과 비교해야 해요.
- Q. CORS를 우리 도메인만 허용하면 CSRF도 막히나요? → 아니요. CORS는 응답 읽기를 막을 뿐이고 폼 POST는 그대로 전송돼요.
</details>

<details>
<summary>Q. th:text와 th:utext의 차이는? React의 dangerouslySetInnerHTML은 왜 이런 이름일까요?</summary>

**답변(30초)**
`th:text`는 값을 HTML 이스케이프해서 태그가 글자로 보이고, `th:utext`는 이스케이프하지 않아서 HTML로 해석돼요. 사용자 입력을 `th:utext`로 출력하면 XSS가 돼요. React도 기본 출력은 이스케이프하고, HTML을 그대로 넣는 탈출구에 일부러 "dangerously"를 붙여 위험을 드러냈어요. 둘 다 신뢰되고 정제된 데이터에만 써야 해요.

**꼬리질문**
- Q. Thymeleaf 인라인 표현식은요? → `[[...]]`는 `th:text`처럼 이스케이프, `[(...)]`는 `th:utext`처럼 그대로예요.
</details>

<details>
<summary>Q. HttpOnly 쿠키를 쓰면 XSS로부터 안전한가요?</summary>

**답변(30초)**
아니요, 쿠키 값을 훔치는 것만 막아요. HttpOnly는 JS가 `document.cookie`로 쿠키를 읽지 못하게 하지만, 그 페이지에서 `fetch`로 요청을 보내면 쿠키는 여전히 붙어요. 그래서 XSS 코드가 사용자 대신 API를 호출하는 건 못 막아요. 피해를 줄이는 장치일 뿐이고, XSS 자체는 출력 인코딩으로 없애야 해요.

**꼬리질문**
- Q. 그래도 왜 켜요? → 세션 값을 밖으로 빼 가면 공격자가 자기 브라우저에서 계속 쓸 수 있어요. HttpOnly면 피해가 그 페이지가 열려 있는 동안으로 줄어요.
</details>

<details>
<summary>Q. SameSite=Lax가 기본이라면 CSRF 토큰은 필요 없지 않나요?</summary>

**답변(30초)**
아직 필요해요. 기본값이 Lax인지는 브라우저마다 다르고 구형 브라우저는 지원하지 않아요. 기본값으로 적용된 Lax는 만들어진 지 2분 안 된 쿠키를 cross-site POST에도 보낼 수 있고, 상태를 바꾸는 GET은 Lax로 못 막아요. 같은 사이트로 취급되는 서브도메인이 뚫리면 SameSite가 통하지 않는 것으로도 알려져 있어요. 그래서 SameSite는 명시해서 보조 방어로 두고 토큰은 유지해요.

**꼬리질문**
- Q. 그럼 Strict로 하면요? → 더 안전하지만 외부 링크로 들어온 사용자가 로그인이 풀린 것처럼 보여요. 세션 쿠키는 Lax, 민감한 작업은 토큰으로 막는 식으로 절충해요.
- Q. SameSite 기본값은 표준인가요? → RFC 6265bis는 아직 초안이에요. 정식 RFC가 아니에요.
</details>

<details>
<summary>Q. 스프링 시큐리티에서 REST API는 왜 CSRF를 끄나요? 언제 끄면 안 되나요?</summary>

**답변(30초)**
CSRF는 브라우저가 자격 정보를 자동으로 붙여야 성립해요. JWT를 `Authorization: Bearer` 헤더로 JS가 직접 붙이면 다른 사이트의 요청엔 토큰이 없으니 CSRF 조건이 안 돼서 끄는 경우가 많아요. 하지만 세션 쿠키나 JWT를 쿠키에 담는 방식이면 다시 자동 첨부되니 켜 둬야 해요. "REST라서, JSON이라서 안전하다"는 오해고, 기준은 자동 첨부 여부예요.

**꼬리질문**
- Q. Spring Security는 기본으로 켜져 있나요? → 네, 서블릿 앱에서 기본 활성이고 POST 등에 토큰이 없으면 403이에요(레퍼런스 7.2.0 기준).
- Q. JSON API면 폼으로 위조가 안 되지 않나요? → `enctype="text/plain"` 폼으로 JSON처럼 생긴 본문을 보낼 수 있어요.
</details>

<details>
<summary>Q. CSP는 무엇이고, nonce는 왜 매번 바뀌어야 하나요?</summary>

**답변(30초)**
CSP는 응답 헤더로 "이 페이지에서 실행해도 되는 스크립트"를 브라우저에 알려 주는 장치예요. `script-src`에 nonce를 지정하면 같은 nonce가 붙은 스크립트만 실행되고, 인라인 핸들러나 `javascript:` URL은 막혀요. nonce가 고정이면 공격자가 그 값을 알아내 자기 스크립트에 붙일 수 있으니 응답마다 예측 불가능하게 새로 만들어요. CSP는 심층 방어라서 출력 인코딩을 대신하지 않아요.

**꼬리질문**
- Q. 레거시라 인라인 스크립트가 많으면요? → `Content-Security-Policy-Report-Only`로 위반만 먼저 수집하고, nonce를 붙인 뒤 강제로 바꿔요.
- Q. `'unsafe-inline'`을 넣으면? → 인라인 스크립트가 다 허용돼서 CSP의 목적이 대부분 사라져요.
</details>

<details>
<summary>Q. 동기화 토큰과 더블 서브밋 쿠키의 차이는? 단순한 더블 서브밋이 왜 위험한가요?</summary>

**답변(30초)**
동기화 토큰은 서버 세션에 토큰을 저장하고 요청 값과 비교해서, 세션이 있는 앱에 맞아요. 더블 서브밋은 서버에 저장하지 않고 쿠키와 요청 헤더에 같은 토큰을 보내 둘을 비교해서, 상태 없는 앱에 써요. 그런데 단순형은 공격자가 서브도메인 등으로 쿠키를 심을 수 있으면 쿠키와 헤더를 같은 값으로 맞출 수 있어 깨져요. 그래서 OWASP는 토큰을 HMAC으로 세션 값에 묶는 서명형을 권해요.

**꼬리질문**
- Q. Fetch Metadata는요? → 브라우저가 붙이는 `Sec-Fetch-Site`로 cross-site 요청을 거르는 방식이에요. 헤더가 없는 구형 브라우저를 위해 Origin 검사 폴백이 필요해요.
</details>

## 서술형 연습

<details>
<summary>상황: 게시판 글을 열면 알림창이 뜨고 이상한 곳으로 요청이 나간다는 제보가 들어왔어요. 어떻게 대응할까요?</summary>

**상황 파악**
특정 글을 열 때마다 스크립트가 실행된다면, 누군가 글이나 댓글에 넣은 코드가 다른 사용자 화면에서 실행되는 **저장형 XSS**일 가능성이 커요. 이미 다른 사용자의 브라우저에서 실행됐을 수 있으니 확산 차단과 원인 수정을 함께 해야 해요.

**원인 후보**
1. 서버 템플릿에서 본문을 `th:utext`(또는 JSP의 이스케이프 없는 출력)로 출력.
2. 프론트에서 API로 받은 본문을 `innerHTML`이나 `dangerouslySetInnerHTML`로 넣음(DOM 쪽 처리 문제).
3. 에디터 기능 때문에 HTML을 허용하는데 정제가 없거나 허용 목록이 너무 넓음.
4. 링크 `href`에 사용자 URL을 그대로 넣어 `javascript:` 링크가 됨.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 출력을 자동 이스케이프로 교체(`th:text`, `textContent`, React 기본 출력) | 근본 해결, 단순 | 굵게·링크 같은 서식이 사라짐 |
| B. HTML 허용 유지 + DOMPurify 같은 정제(허용 태그만) | 서식 유지 | 허용 범위 관리, 라이브러리 업데이트 필요, 정제 후 재가공 금지 |
| C. 마크다운 등 제한된 문법으로 전환 | 위험한 HTML 자체를 안 받음 | 기존 글 변환, 사용자 습관 변경 |
| D. CSP(nonce) 도입 | 인코딩이 뚫려도 인라인 핸들러 실행 차단 | 레거시 인라인 스크립트 정리 필요, 이것만으론 부족 |

**대응 순서와 내가 고를 방법**
먼저 문제 글을 숨기고, DB에서 `onerror`, `javascript:` 같은 패턴이 든 글을 찾아 영향 범위를 파악해요. 세션 쿠키가 HttpOnly가 아니었다면 세션을 무효화해요. 수정은 **A를 기본**으로 해요. 서식이 꼭 필요한 화면만 **B**로 정제해요. 그 위에 **D**를 Report-Only로 먼저 걸어 위반을 모은 뒤 강제해요. 입력 시점 필터만 추가하는 건 출력 위치마다 규칙이 달라 고르지 않아요. 같은 출처에서 코드가 실행되면 CSRF 토큰도 소용없으니, CSRF 토큰이 있다고 안심하지 않아요.

**채점 포인트**: 저장형 XSS 진단, 출력 시점·컨텍스트별 인코딩, `th:utext`·`innerHTML`·`dangerouslySetInnerHTML` 탈출구, HTML 허용 시 정제(DOMPurify), `script`만 거르는 필터의 한계(`onerror`), CSP는 심층 방어·Report-Only, HttpOnly는 탈취 완화, 영향 범위 파악·세션 무효화, XSS가 CSRF 방어를 무력화.
</details>

<details>
<summary>상황: SPA에서 로그인 후 받은 JWT를 localStorage에 둘지 HttpOnly 쿠키에 둘지 팀에서 의견이 갈려요. 어떻게 판단할까요?</summary>

**상황 파악**
저장 위치에 따라 막히는 공격과 열리는 공격이 바뀌어요. localStorage는 JS가 읽을 수 있어 **XSS에 토큰이 털릴** 수 있고, 쿠키는 브라우저가 자동으로 붙여 **CSRF 대상**이 돼요. 어느 쪽도 공짜가 아니에요.

**원인(위험) 후보**
1. localStorage: XSS 코드가 토큰을 읽어 외부로 보내면 공격자가 자기 환경에서 계속 쓸 수 있음.
2. HttpOnly 쿠키: 토큰 값은 못 훔치지만, 자동 첨부라서 다른 사이트의 폼 POST에 실림(CSRF). XSS가 있으면 그 페이지에서 요청을 대신 보내는 건 여전히 가능.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. localStorage + `Authorization: Bearer` 헤더 | 자동 첨부가 없어 CSRF 조건 불성립, 구현 단순, 다른 도메인 API 호출 쉬움 | XSS 한 번에 토큰 유출. 만료가 길면 피해가 큼 |
| B. HttpOnly + Secure + SameSite 쿠키 + CSRF 토큰 | 토큰 값 탈취를 막음 | CSRF 방어(토큰·SameSite·Origin 검사)를 반드시 같이 해야 함, 도메인 구성 제약 |
| C. 짧은 액세스 토큰은 메모리, 리프레시 토큰은 HttpOnly 쿠키 | 유출돼도 짧게만 유효, 쿠키 쪽은 재발급 경로 하나만 보호하면 됨 | 구조가 복잡, 새로고침 시 재발급 흐름 필요 |

**내가 고를 방법과 이유**
같은 도메인에서 서비스하는 웹이라면 **B**를 골라요. 토큰 값이 JS 밖에 있어 XSS 피해가 "페이지가 열린 동안"으로 줄고, CSRF는 Spring Security CSRF 토큰(SPA면 쿠키 저장소 + 헤더 전송 설정)과 SameSite=Lax로 막을 수 있어요. 다만 이때 "JWT니까 CSRF 끄자"는 하면 안 돼요. 어느 방식이든 XSS가 있으면 결국 사용자 권한으로 요청이 나가니, **출력 인코딩과 CSP가 먼저**라는 점을 팀에 함께 말해요. 다른 도메인 API를 부르거나 토큰 수명을 짧게 가져가고 싶다면 **C**도 좋은 선택이에요. 비교표와 C 조합은 [쿠키·세션·JWT](../../web/cookie-session-jwt/)에 더 있어요.

**채점 포인트**: localStorage = XSS로 탈취, 쿠키 = 자동 첨부 → CSRF, HttpOnly는 탈취만 막고 요청 대행은 못 막음, 쿠키 선택 시 CSRF 토큰·SameSite 필수, 헤더 방식이면 CSRF 조건 불성립, 짧은 만료, XSS 방어가 우선.
</details>

<details>
<summary>상황: 신규 REST API 서버에서 "REST니까 CSRF는 꺼도 된다"며 csrf.disable() 설정을 넣자는 코드 리뷰가 올라왔어요. 승인할까요?</summary>

**상황 파악**
"REST라서"는 기준이 아니에요. CSRF는 **브라우저가 자격 정보를 자동으로 붙이는가**로 판단해요. 먼저 이 API의 인증 방식과 호출자를 확인해야 해요.

**원인(판단) 후보**
1. 인증이 세션 쿠키 → 자동 첨부, CSRF 대상.
2. JWT를 쿠키에 담음 → 자동 첨부, CSRF 대상.
3. JWT를 `Authorization: Bearer` 헤더로 JS가 직접 붙임 → 다른 사이트 요청엔 토큰이 없어 CSRF 조건 불성립.
4. 브라우저가 아닌 서버 간 호출만 받음 → CSRF 해당 없음.
5. Basic 인증 → 브라우저가 자동 첨부, CSRF 대상.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 전체 끄기 `csrf.disable()` | 설정 단순 | 쿠키 인증이 섞이면 바로 취약. 나중에 쿠키 로그인이 추가돼도 모름 |
| B. 켜 두고 브라우저 쪽은 토큰 헤더 전송(SPA 설정) | 쿠키 인증에서도 안전 | 프론트가 토큰을 읽어 헤더로 보내는 작업 필요 |
| C. 서버 간 호출 경로만 `ignoringRequestMatchers`로 제외 | 필요한 곳만 끔 | 경로 관리 필요, 실수로 넓게 제외하면 위험 |

**내가 고를 방법과 이유**
인증이 **Bearer 헤더 방식뿐**이고 쿠키·Basic 인증이 전혀 없다면 A를 승인하되, 그 이유(자동 첨부 없음)를 주석과 PR에 남기고 쿠키 인증을 추가하면 다시 켜야 한다고 적어요. 세션·쿠키 JWT가 하나라도 있다면 **B**를 요구하고, 외부 서버만 부르는 웹훅 같은 경로는 **C**로 빼요. "JSON만 받으니 안전하다"는 근거는 받아들이지 않아요. `text/plain` 폼으로 JSON처럼 생긴 본문을 보낼 수 있어서예요. CORS 설정도 CSRF 방어가 아니라는 점을 함께 짚어요.

**채점 포인트**: 판단 기준 = 자동 첨부 여부, 세션 쿠키·쿠키 JWT·Basic은 대상, Bearer 헤더면 불성립, "REST/JSON이라 안전" 반박(`text/plain` 폼), 일부 경로만 제외(`ignoringRequestMatchers`), CORS는 CSRF 방어 아님, Spring Security 기본 활성(7.2.0 기준).
</details>
