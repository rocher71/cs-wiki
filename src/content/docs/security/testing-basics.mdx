:::tip[한 줄 요약]
**단위 테스트**는 클래스 하나 같은 작은 단위를 빠르게, **통합 테스트**는 DB·외부 API 같은 경계를 실제로 붙여서 확인해요. **테스트 피라미드**는 빠르고 싼 단위 테스트를 가장 많이, 느리고 비싼 E2E 테스트를 가장 적게 두라는 경험칙이에요. 진짜 협력 객체 대신 쓰는 대역의 총칭은 **테스트 더블**이고, 그중 **Stub은 정해 둔 답을 주고 결과 상태를 확인**할 때, **Mock은 "이 호출을 했는가"를 검증**할 때 써요.
:::

:::note[처음이라면 여기까지]
① 테스트는 크게 셋이에요. 부품 하나만 보는 단위, 부품끼리(또는 DB와) 붙여 보는 통합, 사용자처럼 처음부터 끝까지 눌러 보는 E2E예요.

② 단위 테스트는 빠르고 싸서 많이, E2E는 느리고 자주 깨져서 조금만 둬요. 이 모양이 피라미드예요.

③ 진짜 DB나 결제 서버 대신 세우는 가짜를 "테스트 더블"이라고 불러요. 영화의 스턴트 대역과 같아요.

④ 면접에선 질문 1~3번(단위 vs 통합, 피라미드, Mock vs Stub)부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

자동차 공장을 떠올려 보세요. 브레이크, 엔진, 핸들 같은 부품은 조립 전에 하나씩 검사대에 올려 확인해요. 빠르고, 어디가 고장인지 바로 알 수 있어요. 이게 **단위 테스트**예요.

부품을 다 조립한 뒤에는 차를 실제로 몰아 보는 주행 시험을 해요. 부품은 각각 멀쩡해도 "엔진과 변속기 연결부가 헐겁다" 같은 문제는 조립해 봐야 보여요. 이게 **통합 테스트**와 **E2E 테스트**예요. 다만 주행 시험은 시간이 오래 걸리고, 어디가 문제인지 찾기도 어려워요.

영화 촬영에서 위험한 장면엔 배우 대신 **스턴트 대역**이 서요. 관객 눈엔 배우처럼 보이면 충분해요. 테스트에서도 진짜 결제 서버나 메일 서버를 부르면 돈이 나가거나 메일이 실제로 가니까, 그 자리에 대역을 세워요. 이게 **테스트 더블**(test double)이에요.

단, 실제로는 "단위"의 크기가 정해져 있지 않아요. 클래스 하나일 수도, 함수 하나일 수도, 서로 붙어 다니는 클래스 몇 개일 수도 있어요. 팀이 정하기 나름이에요.

## 제대로 알기

### 테스트의 세 층

| | 단위(unit) | 통합(integration) | E2E(end-to-end) |
|---|---|---|---|
| 무엇을 | 클래스·함수 하나의 동작 | 경계 하나(DB, 파일, 외부 API, JSON 변환)를 실제로 붙여서 | 사용자 흐름 전체(화면 → 서버 → DB) |
| 협력자 | 진짜 또는 테스트 더블 | 해당 경계는 진짜(또는 진짜에 가까운 가짜) | 전부 진짜 |
| 속도 | 아주 빠름(ms) | 중간(초) | 느림 |
| 실패하면 | 어디가 문제인지 바로 보임 | 경계 문제를 잡음 | 어디가 문제인지 찾기 어려움, 랜덤 실패도 잦음 |
| 개수 | 가장 많이 | 중간 | 핵심 흐름 몇 개만 |

**SUT**(System Under Test, 지금 테스트하는 대상)를 중심으로 생각하면 쉬워요. 단위 테스트는 SUT 하나에 집중하고, 통합 테스트는 SUT와 그 너머 경계가 제대로 맞물리는지 봐요.

여기서 말하는 통합 테스트는 "경계 하나만" 붙여 보는 **좁은 통합 테스트**예요. 객체를 JSON으로 바꾸거나(직렬화) DB 행을 객체로 바꾸는 곳처럼 **데이터 모양이 바뀌는 지점**에서 특히 쓸모가 커요.

<Aside type="note" title="필기의 단위·통합 테스트와는 관점이 달라요">
정보처리기사·전공 필기에서 배우는 단위 → 통합 → 시스템 → 인수 테스트(V 모델), 블랙박스·화이트박스, 커버리지 계산은 [소프트웨어 테스트(필기)](../../exam/se/testing/) 페이지에 있어요. 이 페이지는 개발자가 실제로 코드를 짜는 관점이에요.
</Aside>

### 테스트 피라미드

**테스트 피라미드**는 Mike Cohn이 *Succeeding with Agile*에서 그린 3층 그림이에요. 아래부터 단위 → 서비스 → UI 순이에요. 층 이름이 오해를 부를 수 있어서, 팀 안에서 일관되게만 쓰면 바꿔 불러도 괜찮다고 해요(Ham Vocke, martinfowler.com).

핵심 규칙은 두 가지예요.

1. 크기(단위·통합·E2E)가 다른 테스트를 **섞어서** 써요.
2. **위로 갈수록 개수를 줄여요.**

그리고 같은 경우를 아래 층에서 이미 확인했으면 위에서 또 확인하지 않아요. 테스트는 할 수 있는 한 **피라미드 아래로 내려요.**

거꾸로 E2E가 대부분이고 단위 테스트가 적은 모양을 **아이스크림 콘** 안티패턴이라고 불러요. 실행이 오래 걸리고, 유지보수가 힘들어요. E2E는 가치가 있지만 느리고, **플래키**(flaky, 코드가 안 바뀌었는데 됐다 안 됐다 하는 테스트)해지기 쉽고, 고치는 비용이 커서 핵심 사용자 흐름 몇 개로 제한하라고 권해요.

단위 테스트는 코드를 바꿀 때마다 돌릴 만큼 빨라야 해요. Kent Beck의 경험칙은 "커밋할 때 돌리는 테스트 묶음은 10분 안에 끝나야 한다"예요.

### 테스트 더블 5종

**테스트 더블**은 진짜 협력 객체 대신 쓰는 대역의 **총칭**이에요. Gerard Meszaros가 *xUnit Test Patterns*에서 다섯 가지로 나눴어요. 흔히 "Mock"을 가짜 객체 전체를 부르는 말로 쓰는데, 정확히는 Mock은 그중 하나예요.

| 종류 | 한 줄 뜻 | 비유 | 예 |
|---|---|---|---|
| **Dummy** | 자리만 채우고 실제로 안 쓰임 | 엑스트라(서 있기만 함) | 메서드 파라미터에 넘기는 안 쓰는 Logger |
| **Stub** | 호출하면 미리 정해 둔 답만 돌려줌 | 대사 한 줄만 외운 대역 | "재고 조회하면 항상 10개" |
| **Spy** | 답도 주고, 어떻게 불렸는지 **기록**도 함 | 촬영 내용을 메모하는 대역 | 보낸 메일 개수를 세는 메일러 |
| **Mock** | 받아야 할 호출을 **미리 기대**해 두고 그대로 왔는지 검증 | 동선이 정해진 스턴트 | "결제 API가 정확히 1번, 30000원으로 불려야 함" |
| **Fake** | 진짜처럼 동작하지만 운영엔 못 쓸 지름길 구현 | 촬영용 소품 자동차(진짜 굴러감) | HashMap에 저장하는 회원 저장소, 인메모리 DB |

짧은 코드로 보면 이래요. (`OrderService`가 재고 조회, 메일 발송, 회원 저장소를 쓴다고 가정)

```java
// Dummy: 넘기기만 하고 테스트에선 안 쓰임
Logger dummyLogger = null;

// Stub: 정해 둔 답만 돌려줌
class StubStock implements StockClient {
    public int count(long itemId) { return 10; }
}

// Spy: 답 + 호출 기록
class SpyMailer implements Mailer {
    int sent = 0;
    public void send(String to) { sent++; }
}

// Fake: HashMap으로 진짜처럼 동작하는 저장소
class FakeMemberRepo implements MemberRepo {
    private final Map<Long, Member> store = new HashMap<>();
    public void save(Member m) { store.put(m.id(), m); }
    public Optional<Member> findById(long id) { return Optional.ofNullable(store.get(id)); }
}
```

```java
// Mock: Mockito로 "이렇게 불려야 한다"를 검증
PaymentClient payment = mock(PaymentClient.class);
OrderService service = new OrderService(payment);  // 대역을 주입
service.order(1L, 30000);
verify(payment).pay(1L, 30000);   // 정확히 1번, 이 인자로 불렸는가
```

<Aside type="caution" title="필기의 '스텁'과 같은 뿌리, 다른 맥락">
필기에서 스텁은 하향식 통합 때 **아직 없는 하위 모듈** 대신 세우는 것이고, 상향식의 **드라이버**와 짝으로 나와요. 여기의 Stub도 "정해 둔 답을 주는 대역"이라는 뿌리는 같지만, 실무에선 이미 있는 외부 시스템을 대신하는 경우가 대부분이에요.
</Aside>

### 상태 검증 vs 행위 검증

같은 테스트 "주문하면 메일을 한 통 보낸다"를 두 방식으로 쓸 수 있어요.

| | 상태 검증(state verification) | 행위 검증(behavior verification) |
|---|---|---|
| 무엇을 확인 | 실행 **후의 결과 상태** | SUT가 협력자에게 **올바른 호출을 했는지** |
| 질문 | "결과가 맞나?" | "이 메서드를 이 인자로 불렀나?" |
| 짝꿍 더블 | Stub, Spy, Fake | Mock |
| 예 | `assertThat(spyMailer.sent).isEqualTo(1)` | `verify(mailer).send("a@b.com")` |

Mock만 행위 검증을 고집하고, 나머지 더블은 보통 상태 검증과 함께 써요.

### Given-When-Then 구조

테스트를 세 칸으로 나누면 읽기 쉬워요. **Given**(준비) → **When**(실행) → **Then**(검증)이에요. 같은 뜻으로 Arrange-Act-Assert라고도 해요.

```java
@Test
void 잔액이_충분하면_출금된다() {
    // Given: 1번 회원은 잔액 5000원
    Account account = new Account(1L, 5000);
    given(accountRepo.findById(1L)).willReturn(Optional.of(account));

    // When: 1000원 출금
    service.withdraw(1L, 1000);

    // Then: 잔액 4000원
    assertThat(account.balance()).isEqualTo(4000);
}
```

### JUnit · AssertJ · Mockito 한눈에

자바 백엔드 테스트는 보통 이 세 개를 같이 써요. 셋 다 `spring-boot-starter-test`에 들어 있어요.

- **JUnit**: 테스트를 실행하는 틀이에요. 현재 공식 문서는 **JUnit 6** 세대예요(6.0.0이 2025-09에 나왔어요). 테스트를 쓰는 기본 애노테이션은 JUnit 5와 같아서 "JUnit 5 문법"으로 배워도 그대로 통해요. JUnit 6은 Java 17 이상이 필요해요.
- **AssertJ**: `assertThat(...)`으로 시작해 점(.)으로 이어 쓰는 단언 라이브러리예요. 영어 문장처럼 읽혀요.
- **Mockito**: 테스트 더블을 쉽게 만드는 라이브러리예요. `when/thenReturn`으로 답을 정하고, `verify`로 호출을 확인해요.

자주 쓰는 JUnit 애노테이션이에요.

```java
@Test            // 테스트 메서드
@DisplayName("잔액 부족이면 예외")   // 보고서에 보일 이름
@BeforeEach      // 각 테스트 전에 실행
@AfterEach       // 각 테스트 후에 실행
@BeforeAll       // 클래스당 한 번 (기본 설정에선 static이어야 함)
@ParameterizedTest  // 여러 입력값으로 같은 테스트 반복
@Nested          // 테스트를 묶는 중첩 클래스
@Disabled        // 잠시 끄기
@ExtendWith(MockitoExtension.class)  // 확장 등록
```

AssertJ 예시예요.

```java
assertThat(name).startsWith("김").contains("토스");
assertThat(list).containsExactly("a", "b");           // 순서까지 같아야 함
assertThat(list).containsExactlyInAnyOrder("b", "a"); // 순서 무관
assertThatThrownBy(() -> service.withdraw(1L, 99999))
    .isInstanceOf(IllegalStateException.class);
```

Mockito 예시예요.

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock PaymentClient payment;
    @InjectMocks OrderService service;

    @Test
    void 주문하면_결제를_요청한다() {
        when(payment.pay(anyLong(), anyInt())).thenReturn(PayResult.ok()); // 답 정하기
        service.order(1L, 30000);

        ArgumentCaptor<Integer> amount = ArgumentCaptor.forClass(Integer.class);
        verify(payment).pay(eq(1L), amount.capture());   // 1번 불렸는지 + 인자 잡기
        assertThat(amount.getValue()).isEqualTo(30000);
    }
}
```

- `when(...).thenReturn(...)`: 이 호출엔 이 답. 답을 정하지 않은 메서드는 기본값(객체는 null, 숫자는 0, boolean은 false, 컬렉션은 빈 컬렉션)을 돌려줘요.
- `verify(mock).method(...)`: 기본은 "정확히 1번". `never()`, `times(2)`, `atLeast(1)`도 있어요.
- **ArgumentCaptor**: 넘어간 인자를 붙잡아 꼼꼼히 확인할 때 써요. Mockito 문서는 **verify와 함께 쓰고, 답 정하기(스텁)에는 쓰지 말라**고 권해요.
- `BDDMockito.given(...).willReturn(...)`은 `when`과 같은 기능을 Given-When-Then 말투로 바꾼 별칭이에요.

### 과한 모킹의 함정: 구현에 묶인 테스트

모든 협력자를 Mock으로 바꾸고 `verify`로 호출 하나하나를 검사하면, 테스트가 **"무엇을 하는가"가 아니라 "어떻게 하는가"를 고정**해 버려요.

- 내부 구현만 바꿨는데(조회 두 번 → 한 번) 결과는 같아도 `verify(repo, times(2))`가 깨져요. **리팩터링**(동작은 그대로 두고 코드 구조만 고치는 것)을 테스트가 방해해요.
- 테스트와 상관없는 호출과 인자까지 적어 두니 사소한 변경에도 깨져요.
- 기대를 잘못 세우면, 진짜 협력자와는 안 맞는데도 테스트는 초록불이에요. 진짜 객체끼리 부딪혀 보는 "작은 통합" 효과가 사라져요.

그래서 단위 테스트는 **public 메서드로 밖에서 관찰할 수 있는 동작**을 확인해야 해요. private 메서드를 직접 테스트하고 싶어진다면, 그 클래스가 너무 많은 일을 한다는 신호일 수 있어요.

실무에서 쓰는 기준은 이래요.

- 결과로 확인할 수 있으면 **상태 검증**을 먼저 써요.
- `verify`는 결과가 밖으로 나가 되돌릴 수 없는 **외부 경계**(결제 요청, 메일 발송, 메시지 발행)에 아껴 써요.
- `List` 같은 값 객체는 목으로 만들지 말고 진짜를 써요(Mockito 문서 예시).

### 심화: Sociable vs Solitary, Classicist vs Mockist

| | Solitary 단위 테스트 | Sociable 단위 테스트 |
|---|---|---|
| 협력자 | 테스트 더블로 바꿈 | 진짜를 그대로 씀 |
| 장점 | 다른 클래스의 버그가 이 테스트를 깨뜨리지 않음, 실패 위치가 정확 | 구현이 바뀌어도 덜 깨짐, 협력자끼리 맞물림도 같이 확인 |
| 단점 | 구현에 묶이기 쉬움 | 한 버그에 여러 테스트가 같이 깨질 수 있음 |
| 선호하는 쪽 | **Mockist** | **Classicist**(Fowler가 이쪽) |

용어는 Jay Fields가 만들었어요. 중요한 점은 **sociable도 단위 테스트**라는 거예요. "단위 테스트면 협력자를 전부 모킹해야 한다"는 오해예요. Classicist도 원격 서비스처럼 다루기 어려운 협력자에는 더블을 써요.

### 심화: Mockito의 mock·spy와 Meszaros 용어

아래는 두 출처(Fowler 글, Mockito 문서)를 비교한 **해석**이에요. 공식 정의는 아니에요.

- Mockito의 `mock()` 객체는 `when/thenReturn`만 쓰고 결과값을 단언하면 사실상 **Stub + 상태 검증**이고, `verify`를 쓰면 **Mock + 행위 검증**이에요. "Mockito를 쓰면 다 mock 테스트"는 아니에요.
- Mockito의 `spy()`는 **진짜 객체를 감싸 진짜 메서드를 호출**하는 부분 목이라, Meszaros의 Spy(기록하는 Stub)와 완전히 같지는 않아요.
- 엄밀히는 Meszaros의 Mock은 실행 **전에** 기대를 세워 두는 객체인데, Mockito는 실행 **후에** `verify`로 확인해요. 그래서 Mockito의 mock을 "기록해 두었다가 나중에 묻는" Spy에 더 가깝다고 보는 시각도 있어요. 면접에선 "verify로 호출을 검증하면 행위 검증"이라고만 말해도 충분해요.

### 심화: 자주 밟는 함정

```java
// spy에 when을 쓰면 진짜 get(0)이 먼저 실행돼 예외가 날 수 있어요
List<String> spy = spy(new ArrayList<>());
// when(spy.get(0)).thenReturn("foo");   // IndexOutOfBoundsException
doReturn("foo").when(spy).get(0);        // 이렇게 써요
```

- **엄격 스텁**: `MockitoExtension`은 정해 두고 한 번도 안 쓴 스텁을 찾아 `UnnecessaryStubbingException`으로 알려 줘요. 정말 필요하면 `lenient()`로 풀어요.
- **final 클래스**: Mockito 5부터 기본 설정으로 final 클래스·메서드도 목으로 만들 수 있어요.
- **`@BeforeAll`은 static**: 테스트 클래스 생명주기가 기본값일 때 `@BeforeAll` 메서드를 static으로 안 만들면 오류예요. JUnit Jupiter는 기본적으로 테스트 메서드마다 테스트 클래스 인스턴스를 새로 만들어서(per-method 생명주기), 필드 상태가 테스트끼리 섞이지 않아요.
- **JUnit 4 테스트**: JUnit 4 테스트를 돌려 주는 Vintage 엔진은 JUnit 6에서 deprecated예요. 옮기는 동안 임시로만 써요.

단위 테스트는 클래스 하나 같은 작은 단위의 동작을 빠르게 확인하는 테스트이고, 통합 테스트는 DB·외부 API처럼 경계를 실제로 붙여서 맞물림을 확인하는 테스트예요. 단위 테스트는 빠르고 실패 위치가 정확하지만, SQL 문법이나 JSON 변환 같은 경계 문제는 못 잡아요. 그래서 단위 테스트를 많이 두고, 데이터 모양이 바뀌는 경계마다 좁은 통합 테스트를 둬요.

- Q. 단위 테스트면 협력자를 다 모킹해야 하나요? → 아니요. 진짜 협력자를 쓰는 sociable 단위 테스트도 단위 테스트예요.

<summary>Q. 테스트 피라미드가 무엇이고, 왜 단위 테스트가 가장 많아야 하나요?</summary>

**꼬리질문**

- Q. E2E는 아예 없어도 되나요? → 아니요. 진짜 사용자 흐름을 확인하는 유일한 층이라 핵심 흐름은 남겨요.
</details>

<details>
<summary>Q. Mock과 Stub의 차이는 무엇인가요?</summary>

**답변(30초)**
둘 다 테스트 더블이지만 검증 방식이 달라요. Stub은 호출에 미리 정해 둔 답을 돌려주고, 테스트는 실행 후 결과 상태를 확인해요(상태 검증). Mock은 받아야 할 호출을 미리 기대해 두고, SUT가 그 호출을 했는지 확인해요(행위 검증). 예를 들어 "재고 10개"라는 답만 주면 Stub, "결제 API가 30000원으로 한 번 불렸나"를 확인하면 Mock이에요.

**꼬리질문**
- Q. Mockito로 만든 객체는 다 Mock인가요? → 꼭 그렇진 않아요. `when/thenReturn`만 쓰고 결과를 단언하면 사실상 Stub처럼 쓰는 거예요(용어 해석 차이는 있어요).
- Q. Mock과 Stub을 통틀어 뭐라고 하나요? → 테스트 더블이에요.
</details>

<details>
<summary>Q. 테스트 더블의 종류를 설명해 주세요.</summary>

**답변(30초)**
Meszaros 분류로 다섯 가지예요. Dummy는 자리만 채우고 안 쓰이는 객체, Stub은 정해 둔 답만 주는 객체, Spy는 답을 주면서 호출을 기록하는 객체, Mock은 받아야 할 호출을 기대해 두고 검증하는 객체, Fake는 HashMap 저장소처럼 진짜로 동작하지만 운영엔 못 쓰는 가벼운 구현이에요. 앞의 넷은 정해진 반응만 하고, Fake만 실제 로직이 있어요.

**꼬리질문**
- Q. 인메모리 DB는 어디에 속하나요? → Fake예요. 진짜로 저장·조회가 되지만 운영용은 아니에요.
</details>

<details>
<summary>Q. Given-When-Then으로 테스트를 어떻게 구성하나요?</summary>

**답변(30초)**
테스트를 준비, 실행, 검증 세 칸으로 나눠요. Given에서 테스트 데이터와 협력자의 답을 정하고, When에서 테스트할 메서드를 딱 한 번 호출하고, Then에서 결과를 단언해요. 세 칸이 보이면 무엇을 테스트하는지 한눈에 읽혀요. Mockito의 `given().willReturn()`은 이 말투에 맞춘 별칭이에요.

**꼬리질문**
- Q. Arrange-Act-Assert와는 뭐가 다른가요? → 같은 세 단계(준비 → 실행 → 검증)를 부르는 다른 이름이에요.
</details>

<details>
<summary>Q. Mockito의 verify와 ArgumentCaptor는 언제 쓰나요?</summary>

**답변(30초)**
verify는 SUT가 협력자 메서드를 몇 번, 어떤 인자로 불렀는지 확인할 때 써요. 결제 요청이나 메일 발송처럼 결과가 밖으로 나가서 상태로 확인하기 어려운 경계에 써요. ArgumentCaptor는 넘어간 인자가 복잡한 객체일 때 붙잡아서 필드를 하나씩 단언할 때 써요. Mockito 문서는 ArgumentCaptor를 스텁이 아니라 verify와 함께 쓰라고 권해요.

**꼬리질문**
- Q. 호출되지 않아야 하는 걸 확인하려면? → `verify(mock, never()).method(...)`예요.
- Q. 스텁에 ArgumentCaptor를 쓰면 왜 안 좋나요? → 읽기 어렵고, 실패했을 때 어디가 잘못됐는지 찾기 어려워져요.
</details>

<details>
<summary>Q. 모킹을 너무 많이 하면 어떤 문제가 생기나요?</summary>

**답변(30초)**
테스트가 결과가 아니라 구현 방식에 묶여요. 협력자 호출 순서나 횟수를 다 verify하면, 동작은 같은데 내부만 바꿔도 테스트가 깨져서 리팩터링을 막아요. 또 기대를 잘못 세우면 진짜 객체와 안 맞는데도 통과해서 버그를 가려요. 그래서 결과는 상태 검증으로 확인하고, verify는 외부 경계에만 쓰고, DB 같은 경계는 Fake나 통합 테스트로 확인해요.

**꼬리질문**
- Q. private 메서드는 어떻게 테스트하나요? → 직접 하지 않고 public 메서드로 관찰되는 동작을 확인해요. 꼭 필요하다면 클래스를 쪼갤 신호예요.
</details>

<details>
<summary>Q. Classicist와 Mockist 중 어느 쪽을 선호하나요?</summary>

**답변(30초)**
기본은 classicist 쪽으로 진짜 협력자를 쓰는 sociable 테스트를 선호하고, 외부 API나 메일처럼 다루기 어려운 협력자만 더블로 바꿔요. 구현이 바뀌어도 덜 깨지고 협력자끼리 맞물림도 같이 확인되기 때문이에요. 대신 한 버그에 여러 테스트가 같이 깨질 수 있어서, 실패 메시지를 명확하게 쓰고 테스트를 작게 유지해요.

**꼬리질문**
- Q. Fowler는 어느 쪽인가요? → classicist라고 밝혀요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 서비스가 외부 결제 API(PG사)를 호출해 결제한 뒤 주문 상태를 '결제 완료'로 바꿔요. 이 서비스의 단위 테스트를 어떻게 작성할지 설명하세요.</summary>

**상황 파악**
테스트할 것은 "결제가 성공하면 주문이 결제 완료가 되고, 실패하면 결제 실패가 된다"는 주문 서비스의 규칙이에요. 외부 결제 API를 테스트마다 진짜로 부르면 돈이 나가거나 테스트 계정 한도에 걸리고, 네트워크 때문에 느리고 랜덤 실패해요. 그래서 결제 API 자리에 테스트 더블을 세워야 해요.

**원인 후보(테스트가 어려운 이유)**
1. 결제 API 호출이 부작용(실제 결제)을 만든다.
2. 성공·실패·타임아웃 같은 응답을 마음대로 만들기 어렵다.
3. 주문 서비스가 결제 클라이언트를 직접 `new`로 만들면 대역을 끼울 자리가 없다.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 결제 클라이언트를 생성자 주입받고, Mockito Stub으로 성공/실패/예외 응답을 정해 주문 상태를 단언 | 빠름, 실패·타임아웃 같은 드문 경우도 쉽게 만듦 | 진짜 PG 응답 형식과 어긋나도 모름 |
| B. 결제 API에 `verify`로 "금액·주문번호로 정확히 1번 호출"을 확인 | 잘못된 금액 전송 같은 치명적 실수를 잡음 | 남발하면 구현에 묶임 |
| C. 직접 만든 Fake 결제 클라이언트(메모리에 승인 내역 저장) | 여러 테스트에서 재사용, 읽기 쉬움 | Fake 자체를 유지보수해야 함 |
| D. 경계는 따로: HTTP 응답을 흉내 내는 서버나 계약 테스트로 실제 요청·응답 형식을 확인 | 직렬화·필드 이름 같은 경계 버그를 잡음 | 단위 테스트보다 느리고 준비가 필요 |

**내가 고를 방법**
단위 테스트는 A를 기본으로 써요. Given에서 결제 Stub이 성공·실패·예외를 돌려주게 하고, Then에서 **주문 상태**를 상태 검증해요. 결제는 돈이 나가는 외부 경계라 B의 `verify`를 **한 테스트에서만** 써서 "금액과 주문번호가 정확히 한 번 전달된다"를 ArgumentCaptor로 확인해요. 결제 실패 테스트에서는 호출 횟수까지 따지지 않고 주문 상태가 '결제 실패'인지만 봐요. 진짜 PG 형식과의 어긋남은 단위 테스트로는 못 잡으니 D처럼 좁은 통합 테스트(또는 계약 테스트)를 따로 하나 둬요.

**채점 포인트**: 외부 API는 테스트 더블로 대체하는 이유(부작용·속도·제어), 생성자 주입으로 대역 끼울 자리 만들기, 성공/실패/타임아웃 경우 나눔, 상태 검증 우선 + 외부 경계만 verify, ArgumentCaptor로 금액 확인, Given-When-Then, 단위 테스트가 못 잡는 형식 문제는 통합·계약 테스트로.
</details>

<details>
<summary>상황: 서비스 코드를 리팩터링할 때마다 동작은 그대로인데 테스트가 수십 개씩 깨져서, 팀원들이 "테스트가 짐이 된다"며 테스트를 지우거나 고치기만 해요. 원인과 해결 방법은?</summary>

**상황 파악**
동작이 같은데 테스트가 깨진다는 건, 테스트가 **결과가 아니라 구현 방식**을 확인하고 있다는 뜻이에요. 리팩터링을 지켜 줘야 할 테스트가 오히려 리팩터링을 막고 있어요.

**원인 후보**
1. 모든 협력자를 Mock으로 바꾸고 `verify(repo, times(2)).findById(...)`처럼 호출 횟수·순서를 일일이 확인한다(행위 검증 과다).
2. 테스트와 상관없는 호출과 인자까지 스텁·검증한다.
3. private 메서드나 내부 필드를 리플렉션으로 직접 테스트한다.
4. 값 객체(`List`, DTO)까지 목으로 만든다.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 결과로 확인 가능한 테스트는 상태 검증으로 바꾸고, verify는 결제·메일·메시지 같은 외부 경계에만 남기기 | 리팩터링에 강해짐 | 기존 테스트를 하나씩 다시 써야 함 |
| B. 저장소 Mock을 HashMap Fake로 바꿔 sociable하게 테스트 | 조회 횟수가 바뀌어도 안 깨짐, 재사용 쉬움 | Fake를 유지보수해야 하고 진짜 DB 동작과는 다를 수 있음 |
| C. 저장소는 단위 테스트에서 빼고 진짜 DB로 좁은 통합 테스트 | SQL·매핑까지 확인 | 느려지고 준비가 필요 |
| D. 깨지는 테스트를 지우기 | 당장 편함 | 안전망이 사라져 다음 리팩터링이 더 무서워짐 |

**내가 고를 방법**
A를 중심으로 B·C를 섞어요. 먼저 "이 테스트가 확인하려는 동작이 뭔지" 한 줄로 적고, 그 동작을 public 메서드의 결과(반환값, 저장된 상태)로 확인하게 고쳐요. 저장소처럼 자주 바뀌는 내부 협력자는 Fake로 바꾸고, 쿼리 자체는 C의 통합 테스트로 따로 지켜요. `verify`는 되돌릴 수 없는 외부 호출에만 남겨요. 엄격 스텁(`MockitoExtension`)을 켜 두면 안 쓰는 스텁이 쌓이는 것도 막을 수 있어요. D는 문제를 미룰 뿐이라 고르지 않아요.

**채점 포인트**: 구현에 묶인 테스트 진단, 행위 검증 과다·불필요한 스텁, 상태 검증 전환, verify는 외부 경계만, Fake/sociable 테스트, public 동작 테스트(private 직접 테스트 금지), 저장소는 통합 테스트로 보완, 테스트 삭제는 해결이 아님.
</details>

<details>
<summary>상황: 단위 테스트가 수백 개 있고 커버리지도 80%가 넘는데, 배포 후 "주문 조회 API가 500 에러"와 "JSON 응답에 필드 이름이 바뀜" 버그가 연달아 났어요. 원인과 해결 방법은?</summary>

**상황 파악**
단위 테스트는 많지만, 실제 버그는 **경계**에서 났어요. SQL·DB 매핑, JSON 직렬화처럼 데이터 모양이 바뀌는 곳은 Mock으로 대신하면 한 번도 진짜로 실행되지 않아요. 커버리지는 "코드 줄이 실행됐다"는 뜻이지, 경계가 맞물린다는 보장이 아니에요.

**원인 후보**
1. 저장소를 전부 Mock으로 바꿔서, 잘못된 쿼리나 매핑이 테스트에서 한 번도 실행되지 않았다.
2. 컨트롤러 테스트가 없어서 JSON 필드 이름 변경(필드명 리팩터링)이 응답 형식에 미치는 영향을 못 봤다.
3. Mock의 기대가 실제 협력자와 달라서(예: null을 안 돌려준다고 가정) 테스트만 통과했다.
4. 피라미드 가운데 층(통합)이 비어 있다.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. DB 경계마다 진짜 DB로 저장소 통합 테스트 추가 | 쿼리 문법·매핑 오류를 잡음 | 느려지고 DB 준비 필요 |
| B. JSON 직렬화 테스트(응답 형식을 문자열로 고정 비교) | 필드 이름·형식 변경을 즉시 잡음 | 의도한 변경 때도 같이 고쳐야 함 |
| C. 주문 흐름 전체 E2E 테스트 몇 개 추가 | 진짜 사용자 흐름 확인 | 느리고 플래키, 많이 두면 아이스크림 콘 |
| D. 커버리지 목표를 90%로 올리기 | 숫자는 좋아 보임 | 경계 문제는 여전히 못 잡음 |

**내가 고를 방법**
A와 B로 피라미드 가운데 층을 채워요. 데이터 모양이 바뀌는 경계(DB 매핑, JSON 변환)마다 좁은 통합 테스트를 하나씩 두는 게 가장 효과가 커요. 이번 두 버그는 각각 A와 B로 바로 재현 테스트부터 만들어요. C는 "주문하고 조회하기" 같은 핵심 흐름 한두 개만 추가해요. D는 원인과 상관없어서 고르지 않아요. 스프링에서 이 테스트들을 빠르게 짜는 방법은 [스프링 테스트 실전](../spring-testing/)에 있어요.

**채점 포인트**: 경계(DB·JSON) 버그는 단위 테스트로 못 잡음, Mock 기대가 실제와 어긋날 위험, 커버리지 ≠ 품질, 좁은 통합 테스트로 피라미드 중간층 채우기, 버그 재현 테스트 먼저, E2E는 핵심 흐름만.
</details>
