:::tip[한 줄 요약]
**세션**은 로그인 정보를 서버에 저장하고 클라이언트에는 추측 못 할 ID만 쿠키로 주는 방식이고, **JWT**는 사용자 정보를 서명해서 클라이언트가 직접 들고 다니게 하는 방식이에요. 세션은 즉시 로그아웃이 쉽고, JWT는 서버가 저장소를 안 찾아봐도 돼서 확장이 쉽지만 만료 전 무효화가 어려워요.
:::

## 쉽게 이해하기

놀이공원 입장을 떠올려 볼게요.

1. **세션**은 **물품 보관소 번호표**예요. 내 정보(누구인지, 어떤 이용권인지)는 놀이공원 보관소(서버)에 있고, 나는 번호표(세션 ID)만 들고 다녀요. 직원은 번호표를 받을 때마다 보관소 장부를 찾아봐요.
2. **JWT**는 **도장 찍힌 손목 띠**예요. 띠에 "자유이용권, 오늘 18시까지"라고 적혀 있고, 위조 못 하게 놀이공원 도장(서명)이 찍혀 있어요. 직원은 장부를 볼 필요 없이 도장만 확인하면 돼요.
3. **쿠키**는 번호표나 손목 띠를 넣고 다니는 **주머니**예요. 브라우저가 이 주머니를 같은 사이트에 갈 때마다 자동으로 꺼내 보여 줘요.
4. 번호표는 잃어버려도 보관소에서 "이 번호 무효"라고 장부에서 지우면 끝이에요. 손목 띠는 이미 도장이 찍혀 있어서 18시까지는 누가 차고 있든 통과돼요.

단, 실제 JWT 손목 띠는 **투명**해요. 적힌 내용을 누구나 읽을 수 있고, 도장은 "고쳐 쓰지 않았다"는 것만 보장해요. 그래서 비밀 정보는 적으면 안 돼요.

## 제대로 알기

### 1. 왜 필요한가: HTTP는 기억을 못 해요

HTTP는 **무상태**(stateless, 서버가 앞 요청을 기억하지 않음)예요. 로그인 요청이 성공해도 다음 요청에서 서버는 "아까 그 사람"인지 몰라요. 그래서 **매 요청마다 "나 누구예요"라는 증거를 같이 보내야** 해요. 그 증거를 어디에 두느냐가 세션과 JWT의 차이예요.

<Aside type="caution" title="자주 하는 실수: 쿠키 vs JWT">
"쿠키와 JWT 중 뭐가 나아요?"는 비교 대상이 틀린 질문이에요. 쿠키는 **실어 나르는 수단**이고, 세션과 JWT는 **로그인 상태를 어디에 두느냐**의 방식이에요. JWT도 쿠키에 담아 보낼 수 있어요.
</Aside>

### 2. 쿠키: 브라우저가 자동으로 붙이는 메모

**쿠키**(cookie, 서버가 브라우저에 맡겨 두는 작은 이름=값 쌍)는 이렇게 오가요.

```http
HTTP/1.1 200 OK
Set-Cookie: SESSIONID=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

GET /mypage HTTP/1.1
Cookie: SESSIONID=abc123
```

서버가 응답의 `Set-Cookie` 헤더로 내려주면, 브라우저가 이후 그 사이트로 가는 요청의 `Cookie` 헤더에 알아서 실어 보내요.

속성별로 무엇을 정하는지 정리하면 이래요.

| 속성 | 하는 일 | 헷갈리는 점 |
|---|---|---|
| `Expires` / `Max-Age` | 만료 시각 / 몇 초 동안 유지 | 둘 다 없으면 **세션 쿠키**라서 브라우저 세션이 끝나면 사라짐. 둘 다 있으면 Max-Age 우선 |
| `Domain` | 어느 호스트로 보낼지 | **생략이 가장 좁음**(설정한 호스트에만). `Domain=example.com`을 쓰면 하위 도메인까지 넓어짐 |
| `Path` | 어느 경로 요청에 붙일지 | 보안 경계가 아님. 같은 출처의 다른 경로 스크립트는 읽을 수 있음 |
| `Secure` | HTTPS 요청에만 보냄 | 평문 HTTP로 새는 걸 막음 |
| `HttpOnly` | 자바스크립트(`document.cookie`)가 못 읽게 숨김 | XSS로 **값을 훔쳐 가는 것**만 막음. XSS 자체나, 그 페이지에서 쿠키가 붙은 요청을 보내는 건 못 막음 |
| `SameSite` | 다른 사이트에서 시작된 요청에 보낼지 | 아래 표 참고 |

**XSS**(Cross-Site Scripting, 공격자 스크립트가 내 사이트 페이지에서 실행되는 공격)와 **CSRF**(Cross-Site Request Forgery, 다른 사이트가 내 브라우저를 시켜 몰래 요청을 보내는 공격)는 이 페이지에서 계속 나와요.

**SameSite**는 CSRF를 막는 속성이에요.

| 값 | 다른 사이트에서 시작된 요청에 쿠키를 |
|---|---|
| `Strict` | 아예 안 보냄 |
| `Lax` | 링크를 눌러 이동하는 최상위 GET 이동에만 보냄. 다른 사이트의 POST, iframe, fetch에는 안 보냄 |
| `None` | 항상 보냄. 대신 `Secure`가 반드시 같이 있어야 함 |

<Aside type="note" title="SameSite를 안 쓰면?">
생략했을 때 기본값은 **브라우저마다 달라요**. Chrome 계열 등 일부 브라우저는 생략하면 Lax처럼 다루지만, 모든 브라우저가 그렇다고 기대하면 안 돼요. 그래서 정답은 "기본값에 기대지 말고 명시한다"예요.
</Aside>

**쿠키 접두사**도 알아 두면 좋아요. 이름이 `__Host-`로 시작하면 브라우저가 Secure 필수, Domain 금지, Path=/ 필수를 강제해요(가장 엄격해서 하위 도메인이 쿠키를 덮어쓰는 공격을 막아요). `__Secure-`는 Secure만 강제해요.

### 3. 세션 방식

**세션**(session, 서버가 로그인한 사용자 정보를 저장해 두는 것)의 흐름이에요.

1. 로그인 성공 → 서버가 **추측할 수 없는 무작위 세션 ID**를 만들어요(OWASP는 최소 64비트 엔트로피, 아무 의미 없는 값을 권장해요).
2. 사용자 정보는 서버 쪽 저장소(메모리, DB, Redis)에 `세션ID → 사용자정보`로 저장해요.
3. 클라이언트에는 세션 ID만 쿠키로 줘요.
4. 요청이 오면 서버가 ID로 저장소를 찾아서 누구인지 확인해요.
5. 로그아웃하면 서버 저장소에서 지워요. 바로 무효가 돼요.

지켜야 할 것 세 가지예요.

- **세션 고정 공격**(session fixation, 공격자가 미리 아는 세션 ID를 피해자에게 심어 두고, 피해자가 그 ID로 로그인하면 같은 ID로 들어오는 공격)을 막으려면 **로그인할 때 세션 ID를 새로 발급**해요. 스프링 시큐리티는 기본으로 로그인 시 세션 ID를 바꿔요.
- 만료는 **유휴 타임아웃**(한동안 안 쓰면 끝)과 **절대 타임아웃**(써도 일정 시간 지나면 끝)을 둘 다 둬요.
- 로그아웃은 **서버에서 세션을 무효화**해야 해요. 브라우저 쿠키만 지우면 ID를 복사해 둔 사람은 계속 쓸 수 있어요.

### 4. JWT 방식

**JWT**(JSON Web Token, 서명된 JSON 정보를 한 줄 문자열로 만든 토큰, RFC 7519)는 점(.)으로 이은 세 덩어리예요.

```text
헤더.페이로드.서명
= Base64url(헤더) . Base64url(페이로드) . Base64url(서명)
```

- **헤더**: 어떤 알고리즘으로 서명했는지(`alg`)와 종류(`typ`).
- **페이로드**: 담고 싶은 정보, 즉 **클레임**(claim, 토큰에 적힌 항목 하나하나).
- **서명**: 헤더와 페이로드를 비밀키로 계산한 값. 한 글자라도 바뀌면 값이 달라져요.

자주 쓰는 등록 클레임이에요. 모두 선택 사항이고 어떤 걸 쓸지는 서비스가 정해요. 시각은 1970년 1월 1일부터 센 초예요.

| 클레임 | 뜻 |
|---|---|
| `iss` | 발급자(누가 만들었나) |
| `sub` | 주체(보통 사용자 ID) |
| `aud` | 대상(이 토큰을 받아야 할 서비스) |
| `exp` | 만료 시각. 이후엔 거부 |
| `nbf` | 이 시각 전에는 거부 |
| `iat` | 발급 시각 |
| `jti` | 토큰 고유 ID. 재사용 방지, 차단 목록에 씀 |

#### 직접 만들어 보기

표준 라이브러리만으로 HS256 JWT를 만들고 위조해 본 예시예요(교육용이에요. 실제로는 검증된 라이브러리를 써요).

```python
import hmac, hashlib, base64, json
b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=").decode()
KEY = b"demo-secret"     # 서버만 아는 비밀키(예시용)
def sign(h, p):          # 서명 = HMAC-SHA256(키, "헤더.페이로드")
    return b64(hmac.new(KEY, f"{h}.{p}".encode(), hashlib.sha256).digest())
h = b64(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
p = b64(json.dumps({"sub": "user42", "role": "user", "exp": 1900000000}).encode())
token = f"{h}.{p}.{sign(h, p)}"

def verify(t):           # 받은 서명과 다시 계산한 서명을 비교
    h, p, s = t.split(".")
    return hmac.compare_digest(s, sign(h, p))   # 타이밍 공격 방지용 비교

# 공격자: role을 admin으로 바꾸고 원래 서명을 그대로 붙임
fake_p = b64(json.dumps({"sub": "user42", "role": "admin", "exp": 1900000000}).encode())
forged = f"{h}.{fake_p}.{token.split('.')[2]}"
```

한 번 실행해 본 결과예요.

```text
eyJhbGciOiAiSFMyNTYiLCAidHlwIjogIkpXVCJ9.eyJzdWIiOiAidXNlcjQyIiwg...
decoded payload: b'{"sub": "user42", "role": "user", "exp": 1900000000}'
original valid: True | forged valid: False
```

여기서 두 가지를 확인할 수 있어요.

1. **키 없이도 페이로드가 그대로 읽혀요.** Base64url은 **인코딩**(글자를 다른 글자로 바꿔 적기)일 뿐 **암호화**(키 없이는 못 읽게 하기)가 아니에요. 그래서 페이로드에 비밀번호나 개인정보를 넣으면 안 돼요. 내용을 숨겨야 하면 JWE(RFC 7516)라는 별도 형식을 써요.
2. **내용을 바꾸면 서명이 안 맞아요.** 비밀키가 없으면 맞는 서명을 새로 만들 수 없어서 위조가 막혀요.

#### 서명 알고리즘

| | HS256 | RS256 / ES256 |
|---|---|---|
| 방식 | **대칭키**(발급·검증이 같은 비밀키) | **비대칭키**(개인키로 서명, 공개키로 검증) |
| 검증하는 쪽 | 비밀키를 가져야 함 → 검증하는 서비스도 위조할 수 있음 | 공개키만 있으면 됨 → 위조 불가 |
| 잘 맞는 곳 | 발급과 검증을 한 서버가 다 할 때 | 여러 서비스가 각자 검증하는 MSA |

<Aside type="danger" title="alg를 믿으면 안 돼요">
토큰 헤더의 `alg`는 **공격자가 마음대로 쓸 수 있는 값**이에요. 서버가 이걸 보고 알고리즘을 고르면 `alg: none`(서명 없음)으로 위조하거나, RS256 공개키를 HS256 비밀키처럼 쓰게 만드는 **알고리즘 혼동 공격**이 가능해져요. RFC 8725는 서버가 **허용할 알고리즘을 미리 고정**하고 나머지는 거부하라고 해요. `iss`, `aud`도 검증하고, HMAC 키는 충분히 길고 무작위여야 해요.
</Aside>

### 5. 세션 vs JWT 한눈에

| | 세션 | JWT |
|---|---|---|
| 상태를 어디에 | 서버 저장소 | 토큰 안(클라이언트가 들고 다님) |
| 클라이언트가 가진 것 | 의미 없는 ID | 서명된 사용자 정보 |
| 요청마다 서버가 하는 일 | 저장소 조회 | 서명·만료 검증(조회 없음) |
| 서버 여러 대 | 세션 저장소 공유가 필요 | 같은 키(또는 공개키)만 있으면 어디서든 검증 |
| 즉시 로그아웃·강제 차단 | 쉬움(저장소에서 삭제) | 어려움(exp까지 유효) |
| 요청 크기 | 작음(ID 하나) | 큼(정보+서명) |
| 탈취되면 | 서버에서 세션 삭제 | 만료까지 기다리거나 차단 목록 필요 |
| 잘 맞는 곳 | 단일 서비스 웹, 즉시 차단이 중요한 서비스 | 여러 서비스 간 인증 전달, 모바일 앱 API |

JWT의 약점을 메우려고 **차단 목록**(denylist, `jti`로 무효 토큰을 기록)을 두면 결국 서버에 상태가 생겨요. 반대로 세션 방식도 앱 서버 자체는 상태 없이 두고 상태를 Redis에 몰아 두면 확장이 쉬워요. "JWT가 무조건 낫다"는 틀린 말이에요.

### 6. Access Token과 Refresh Token

JWT는 만료 전에 무효화하기 어려워서, 수명을 둘로 나눠요.

- **Access Token**: API 요청에 쓰는 토큰. **짧게**(분 단위). 탈취돼도 금방 만료돼요.
- **Refresh Token**: Access가 만료됐을 때 새 Access를 받는 데만 쓰는 토큰. **길게**. 인가 서버(토큰을 발급하는 서버)에만 보내고, 일반 API 서버에는 보내지 않아요.

```http
GET /api/orders HTTP/1.1
Authorization: Bearer eyJhbGciOi...
```

Access가 만료되면 401을 받고, 클라이언트가 Refresh Token으로 토큰 발급 엔드포인트에 새 토큰을 요청해요.

**회전**(rotation)은 Refresh Token을 쓸 때마다 **새 Refresh Token을 주고 옛 것은 무효로** 만드는 거예요. 이미 쓴 옛 토큰이 다시 들어오면 누군가 훔쳐 쓴 거예요. 서버는 진짜 사용자와 공격자 중 누가 누군지 모르니 **그 계열 Refresh Token을 전부 폐기**하고 다시 로그인하게 해요(재사용 탐지). RFC 9700(OAuth 2.0 보안 모범 사례)은 브라우저 앱처럼 비밀을 못 지키는 클라이언트의 Refresh Token에 회전이나 **송신자 제약**(토큰을 특정 클라이언트 키에 묶어서 훔쳐도 못 쓰게 하는 것, 예: DPoP·mTLS) 중 하나를 반드시 쓰라고 해요.

### 7. 토큰을 어디에 저장하나

| 저장 위치 | XSS(스크립트 탈취) | CSRF(몰래 요청) |
|---|---|---|
| localStorage / sessionStorage | **약함**. JS로 읽혀서 XSS 한 번이면 통째로 털림 | 강함. 브라우저가 자동으로 안 붙임 |
| HttpOnly 쿠키 | 강함. JS가 값을 못 읽음 | **대비 필요**. 자동으로 붙으니 SameSite, CSRF 토큰을 같이 써야 함 |
| 메모리(JS 변수) | 새로고침하면 사라짐. XSS 중엔 접근 가능 | 강함 |

흔히 권하는 조합은 이래요.

- **Refresh Token**: `HttpOnly; Secure; SameSite=Strict`(또는 Lax) 쿠키에 담고, `Path`를 갱신 경로로 좁혀요.
- **Access Token**: 메모리(JS 변수)에 두고, 새로고침하면 Refresh로 다시 받아요.

어느 쪽이든 **XSS가 있으면 완전히 안전하지는 않아요**. HttpOnly는 값을 훔쳐 가는 것만 막고, 그 페이지에서 요청을 대신 보내는 건 못 막아요. 결국 XSS 자체를 막는 게 먼저예요.

### 8. 스프링에서는

스프링 시큐리티는 기본이 세션 방식이에요(로그인 정보를 `HttpSession`에 저장). 세션 방식일 때 CSRF 보호가 기본으로 켜져 있어요. JWT를 쓰려면 리소스 서버 설정(`oauth2ResourceServer`의 `jwt()`)으로 Bearer 토큰 검증을 켜요. 서버 여러 대에서 세션을 공유할 때는 Spring Session으로 세션을 Redis에 저장하는 방식을 많이 써요.

## 면접 질문

<details>
<summary>Q. 쿠키와 세션의 차이가 뭔가요?</summary>

**답변(30초)** 쿠키는 브라우저에 저장되는 데이터이고, 세션은 서버에 저장되는 사용자 상태예요. HTTP는 무상태라서 서버가 사용자를 기억하려면 증거가 필요한데, 세션 방식은 서버에 사용자 정보를 저장해 두고 그걸 가리키는 무작위 세션 ID만 쿠키로 브라우저에 줘요. 그래서 둘은 경쟁 관계가 아니라, 세션 ID를 쿠키로 실어 나르는 협력 관계예요. 쿠키에 정보를 직접 넣으면 사용자가 볼 수 있고 바꿀 수 있어서, 민감한 정보는 서버 세션에 둬요.

**꼬리질문**
- Q. 쿠키를 탈취당하면요? → 세션 ID만으로 로그인이 되니 위험해요. HttpOnly로 JS 접근을 막고, Secure로 HTTPS에서만 보내고, 서버에서 세션을 무효화할 수 있게 해요.
- Q. 세션 쿠키와 영속 쿠키 차이는? → `Expires`나 `Max-Age`가 없으면 브라우저 세션이 끝날 때 사라지는 세션 쿠키, 있으면 그때까지 남는 영속 쿠키예요.
</details>

<details>
<summary>Q. 세션 방식과 JWT 방식의 차이와 장단점은요? 언제 무엇을 쓰나요?</summary>

**답변(30초)** 차이는 로그인 상태를 어디에 두느냐예요. 세션은 서버 저장소에 두고 클라이언트엔 ID만 주기 때문에, 로그아웃이나 강제 차단을 저장소에서 지우는 것만으로 바로 할 수 있어요. 대신 요청마다 저장소를 조회하고, 서버가 여러 대면 저장소를 공유해야 해요. JWT는 서명된 정보를 클라이언트가 들고 다녀서 서버가 조회 없이 검증만 하면 되니 확장과 서비스 간 전달이 쉬워요. 대신 만료 전에 무효화하기 어렵고 토큰이 커요. 단일 웹 서비스면 세션 + Redis, 여러 서비스가 각자 인증해야 하면 짧은 JWT + Refresh Token을 고르겠어요.

**꼬리질문**
- Q. JWT로 로그아웃은 어떻게 하나요? → 클라이언트에서 지워도 토큰은 exp까지 유효해요. Access를 짧게 두고 Refresh Token을 서버에서 폐기하거나, `jti` 차단 목록을 둬요. 차단 목록을 두면 서버 상태가 생기는 트레이드오프가 있어요.
- Q. JWT면 서버가 완전히 stateless인가요? → 검증만 보면 그렇지만, Refresh 회전이나 차단 목록을 쓰면 서버에 저장하는 상태가 생겨요.
</details>

<details>
<summary>Q. JWT 구조를 설명해 주세요. 페이로드에 민감정보를 넣어도 되나요?</summary>

**답변(30초)** JWT는 헤더, 페이로드, 서명 세 부분을 Base64url로 인코딩해서 점으로 이은 문자열이에요. 헤더에는 서명 알고리즘, 페이로드에는 사용자 ID나 만료 시각 같은 클레임, 서명에는 앞 두 부분을 비밀키로 계산한 값이 들어가요. 민감정보는 넣으면 안 돼요. Base64url은 암호화가 아니라 인코딩이라 누구나 디코딩해서 읽을 수 있고, 서명은 위조를 막을 뿐 내용을 숨기지 않아요.

**꼬리질문**
- Q. 그럼 위조는 왜 안 되나요? → 페이로드를 바꾸면 서명이 달라져야 하는데, 서명을 다시 만들려면 서버 비밀키가 필요해서요.
- Q. 내용을 숨기고 싶으면요? → JWE라는 암호화 형식을 쓰거나, 애초에 토큰엔 식별자만 넣어요.
</details>

<details>
<summary>Q. Refresh Token은 왜 필요하고, 탈취되면 어떻게 하나요?</summary>

**답변(30초)** JWT는 만료 전에 끊기 어려워서 Access Token을 몇 분 단위로 짧게 두고, 만료되면 수명이 긴 Refresh Token으로 새로 받게 해요. 탈취 피해를 짧게 줄이면서 사용자는 계속 로그인 상태를 유지하는 거예요. Refresh Token 탈취에는 회전을 써요. 쓸 때마다 새 토큰으로 바꾸고 옛 것을 무효로 해서, 옛 토큰이 다시 오면 탈취로 보고 그 계열 전체를 폐기해 재로그인시켜요.

**꼬리질문**
- Q. Refresh Token은 어디에 보내요? → 토큰을 발급하는 인가 서버에만 보내요. 일반 API 서버에는 Access Token만 보내요.
- Q. 회전 말고 다른 방법은? → 송신자 제약(DPoP, mTLS)으로 토큰을 특정 클라이언트 키에 묶어서 훔쳐도 못 쓰게 해요.
</details>

<details>
<summary>Q. 토큰을 localStorage와 쿠키 중 어디에 저장해야 하나요?</summary>

**답변(30초)** 둘 다 장단점이 있어서 위협에 따라 골라요. localStorage는 JS로 읽혀서 XSS 한 번에 토큰이 털리지만, 자동 전송이 안 돼 CSRF에는 강해요. HttpOnly 쿠키는 JS가 못 읽어서 XSS 탈취에 강하지만, 브라우저가 자동으로 붙이니 SameSite나 CSRF 토큰으로 CSRF를 막아야 해요. 저는 Refresh Token은 HttpOnly·Secure·SameSite 쿠키에, Access Token은 메모리에 두는 조합을 고르겠어요.

**꼬리질문**
- Q. HttpOnly면 XSS가 막히나요? → 쿠키 값을 훔쳐 가는 것만 막아요. XSS 코드가 그 페이지에서 요청을 보내면 쿠키는 자동으로 붙어요.
- Q. SameSite를 안 쓰면 기본이 Lax 아닌가요? → Chrome 계열 등 일부 브라우저만 그렇게 다뤄요. 브라우저마다 다르니 명시해야 해요.
</details>

<details>
<summary>Q. HttpOnly, Secure, SameSite는 각각 무엇을 막나요?</summary>

**답변(30초)** Secure는 쿠키를 HTTPS 요청에만 보내서 평문 통신으로 새는 걸 막아요. HttpOnly는 자바스크립트가 쿠키를 못 읽게 해서 XSS로 쿠키 값을 훔쳐 가는 걸 막아요. SameSite는 다른 사이트에서 시작된 요청에 쿠키를 안 보내게 해서 CSRF를 막아요. Strict는 아예 안 보내고, Lax는 링크로 이동하는 GET만 보내고, None은 항상 보내되 Secure가 필수예요.

**꼬리질문**
- Q. Domain 속성을 지정하면 범위가 좁아지나요? → 반대예요. 생략하면 설정한 호스트에만 가고, 지정하면 하위 도메인까지 넓어져요.
- Q. `__Host-` 접두사는요? → Secure 필수, Domain 금지, Path=/ 필수를 브라우저가 강제해서 하위 도메인이 쿠키를 덮어쓰는 걸 막아요.
</details>

<details>
<summary>Q. 세션 고정 공격이 뭐고 어떻게 막나요?</summary>

**답변(30초)** 공격자가 자기가 아는 세션 ID를 피해자 브라우저에 심어 두고, 피해자가 그 ID로 로그인하면 같은 ID로 피해자 계정에 들어오는 공격이에요. 로그인처럼 권한이 바뀌는 순간에 세션 ID를 새로 발급하면 막을 수 있어요. 공격자가 아는 옛 ID는 로그인 후 쓸모가 없어지거든요. 스프링 시큐리티는 기본으로 로그인 시 세션 ID를 바꿔요.

**꼬리질문**
- Q. 세션 ID는 어떻게 만들어야 하나요? → 추측할 수 없는 무작위 값이어야 하고, 사용자 정보 같은 의미를 담지 않아야 해요.
</details>

<details>
<summary>Q. HS256과 RS256의 차이, alg none 공격은요?</summary>

**답변(30초)** HS256은 발급과 검증에 같은 비밀키를 쓰는 대칭 방식이고, RS256은 개인키로 서명하고 공개키로 검증하는 비대칭 방식이에요. 여러 서비스가 토큰을 검증해야 하면 RS256이 유리해요. 공개키만 나눠 주면 되고, 검증하는 쪽이 토큰을 위조할 수 없어요. alg none 공격은 헤더의 알고리즘을 none으로 바꿔 서명 없는 토큰을 통과시키는 공격이라, 서버가 허용 알고리즘을 고정하고 헤더의 alg를 믿지 않으면 막을 수 있어요.

**꼬리질문**
- Q. 알고리즘 혼동 공격은? → RS256 공개키를 HS256 비밀키처럼 쓰게 만들어서, 누구나 아는 공개키로 서명을 만드는 공격이에요. 역시 알고리즘 고정으로 막아요.
</details>

## 서술형 연습

<details>
<summary>상황: 트래픽이 늘어 서버를 1대에서 2대로 늘렸더니, 사용자들이 로그인한 직후에도 간헐적으로 로그아웃됩니다.</summary>

**상황 파악**
서버가 1대일 땐 문제가 없었고 늘린 뒤에 생겼어요. "간헐적"이라는 건 요청이 어느 서버로 가느냐에 따라 결과가 갈린다는 뜻이에요. 세션 방식에서 세션이 각 서버 **메모리**에 저장돼 있으면, 서버 A에서 로그인한 사용자의 다음 요청이 서버 B로 갔을 때 B는 그 세션 ID를 몰라서 로그인 안 된 사용자로 봐요.

**원인 후보**
1. 세션을 앱 서버 메모리(기본 설정)에 저장하고 있어요.
2. 로드밸런서가 요청을 서버에 번갈아 나눠 보내요.
3. (드물게) 두 서버의 설정이 달라 세션 쿠키 이름이나 Domain이 어긋나요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 스티키 세션: 로드밸런서가 같은 사용자를 항상 같은 서버로 보냄 | 코드 수정 없이 로드밸런서 설정만 바꾸면 됨 | 서버 하나가 죽으면 그 서버 사용자 세션이 전부 사라짐. 부하가 고르게 안 나뉠 수 있고, 배포로 서버를 내릴 때마다 로그아웃 발생 |
| B. 세션 복제: 서버끼리 세션을 서로 복사 | 어느 서버로 가도 세션이 있음 | 서버가 늘수록 복사 비용과 메모리가 커지고, 복제 지연 중엔 여전히 못 찾을 수 있음 |
| C. 외부 세션 저장소: 모든 서버가 Redis 하나를 같이 씀(Spring Session) | 앱 서버가 상태를 안 가져서 마음껏 늘리고 줄일 수 있음. 실무에서 가장 흔함 | 요청마다 Redis 조회가 생기고, **Redis가 죽으면 전원 로그아웃**. Redis 자체를 복제·자동 장애 전환 구성으로 지켜야 함 |
| D. JWT로 전환 | 서버가 조회 없이 서명만 검증 | 로그인 구조를 크게 바꿔야 하고, 즉시 로그아웃이 어려워지는 새 문제가 생김 |

**내가 고를 방법**
C를 고르겠어요. 스티키 세션은 당장은 빠르지만 서버 장애·배포 때마다 같은 증상이 다시 나요. Redis 세션 저장소는 앱 서버를 상태 없이 만들어서 이후 서버를 더 늘려도 문제가 없어요. 스프링이면 Spring Session으로 저장 위치만 바꾸면 돼서 코드 변경도 작아요. 대신 Redis가 단일 장애 지점이 되지 않게 복제와 자동 장애 전환을 함께 구성해요. JWT 전환은 이 문제 하나 때문에 하기엔 비용과 부작용이 커요.

**채점 포인트**: 세션이 서버 메모리에 있음, 로드밸런서 분산과의 관계, 스티키 세션의 장애·배포 약점, 외부 저장소(Redis) 공유, Redis 장애 시 전원 로그아웃과 고가용성 구성, 앱 서버 무상태화, JWT 전환은 과한 선택일 수 있음.
</details>

<details>
<summary>상황: JWT 인증을 쓰는 서비스에서 한 사용자의 토큰이 유출된 정황이 있습니다. 해당 계정을 모든 기기에서 즉시 로그아웃시켜야 합니다.</summary>

**상황 파악**
JWT는 서버가 저장소 없이 서명만 검증하기 때문에, 이미 발급한 Access Token은 `exp`까지 어느 서버에서든 통과해요. 클라이언트에서 토큰을 지우는 건 공격자가 가진 사본에는 영향이 없어요. 그래서 "만료 전 무효화" 수단을 서버에 따로 만들어야 하고, 이건 어느 정도 서버 상태를 다시 들이는 일이에요.

**원인 후보**(왜 지금 즉시 차단이 안 되나)
1. Access Token 수명이 길어요(몇 시간~며칠).
2. Refresh Token을 서버에 저장하지 않아서 폐기할 대상이 없어요.
3. 서버가 토큰 검증 때 서명과 만료만 보고 다른 상태는 안 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Access를 짧게(분 단위) + 해당 사용자의 Refresh Token 전부 폐기 | 요청마다 조회가 없음. JWT 장점 유지 | Access 수명만큼은 공격자가 계속 쓸 수 있음(완전 즉시는 아님). Refresh 저장소가 필요 |
| B. `jti` 차단 목록: 유출된 토큰 ID를 Redis에 넣고 매 요청 확인 | 그 토큰을 즉시 차단 | 매 요청 조회가 생겨 세션과 비슷해짐. 차단 항목은 원래 exp까지만 보관하면 됨 |
| C. 사용자별 토큰 버전: 사용자 정보에 버전 번호를 두고 토큰에도 넣어, 강제 로그아웃 시 버전을 올림 | 한 번에 그 사용자의 모든 기기 토큰을 무효화 | 역시 요청마다 버전 조회(캐시 가능)가 필요 |

**내가 고를 방법**
평소 구조는 A로 두고, 비상 차단용으로 C를 더하겠어요. Access는 짧게, Refresh는 서버에 저장하고 회전시켜서 평소엔 조회 없이 검증해요. 계정 정지·비밀번호 변경·유출 같은 사건이 나면 그 사용자의 Refresh Token을 모두 폐기하고 토큰 버전을 올려서, 남은 Access까지 바로 막아요. 버전은 Redis에 캐시해서 조회 비용을 줄여요. B는 토큰 하나 단위라 "모든 기기"를 한 번에 끊기엔 C가 더 맞아요. 이렇게 하면 결국 상태가 생기는데, 즉시 차단이 요구사항이면 그건 피할 수 없는 대가라고 설명하겠어요.

**채점 포인트**: JWT는 exp까지 유효, 클라이언트 삭제로는 부족, 짧은 Access + Refresh 폐기, jti 차단 목록, 사용자별 토큰 버전, 상태 도입 트레이드오프(stateless 장점 감소), 차단 항목 보관 기간은 exp까지, 서명 알고리즘 고정·키 교체도 점검.
</details>

<details>
<summary>상황: 다른 나라 IP에서 한 사용자의 Refresh Token으로 토큰 갱신 요청이 들어왔습니다. Refresh Token을 어떻게 설계하면 이런 탈취에 대응할 수 있을까요?</summary>

**상황 파악**
Refresh Token은 수명이 길어서, 훔치면 Access Token을 계속 새로 받아 오랫동안 계정을 쓸 수 있어요. 지금 구조에서 같은 Refresh Token을 여러 번 쓸 수 있다면, 진짜 사용자와 공격자가 둘 다 정상처럼 갱신하고 있어도 서버는 알 수 없어요. 서버가 "이 토큰이 이미 쓰였다"를 알아챌 수 있게 만들어야 해요.

**원인 후보**
1. Refresh Token을 재사용할 수 있어요(회전 없음).
2. 토큰을 XSS에 약한 곳(localStorage)에 저장하고 있어요.
3. 토큰이 특정 기기·클라이언트에 묶여 있지 않아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 회전 + 재사용 탐지: 갱신할 때마다 새 Refresh를 주고 옛 것은 무효. 무효된 옛 토큰이 다시 오면 그 계열 전부 폐기 | 훔친 토큰을 한 번이라도 쓰면 탈취가 드러나고 피해가 끊김 | 서버가 토큰 계열과 사용 여부를 저장해야 함. 네트워크 재시도로 같은 토큰이 두 번 오면 정상 사용자도 로그아웃될 수 있음 |
| B. 송신자 제약(DPoP, mTLS): 토큰을 클라이언트 키에 묶음 | 토큰만 훔쳐서는 못 씀 | 클라이언트와 서버 구현이 복잡하고, 지원 환경을 확인해야 함 |
| C. 이상 징후 탐지(IP 국가 변경 등) 후 재인증 요구 | 기존 구조에 덧붙이기 쉬움 | 오탐(해외여행, VPN)이 있고 보조 수단일 뿐 |

**내가 고를 방법**
A를 기본으로 하겠어요. RFC 9700도 브라우저처럼 비밀을 못 지키는 클라이언트의 Refresh Token에는 회전이나 송신자 제약을 요구해요. 재사용이 감지되면 누가 공격자인지 모르기 때문에 그 계열 전체를 폐기하고 재로그인시켜요. 저장 위치도 Refresh Token을 HttpOnly·Secure·SameSite 쿠키로 옮기고 Path를 갱신 경로로 좁혀서 탈취 자체를 어렵게 해요. C는 경고·추가 인증용 보조로 붙이고, 보안 요구가 높은 서비스면 B를 검토해요.

**채점 포인트**: Refresh Token은 수명이 길어 탈취 피해가 큼, 회전(새 토큰 발급 + 옛 토큰 무효), 재사용 탐지 시 계열 전체 폐기, 서버측 저장 필요, 송신자 제약(DPoP·mTLS), RFC 9700 요구, HttpOnly 쿠키 저장과 Path 제한, Refresh는 인가 서버에만 전송, 이상 징후 탐지는 보조.
</details>
