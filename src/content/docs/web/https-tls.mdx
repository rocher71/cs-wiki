:::tip[한 줄 요약]
HTTPS는 **HTTP를 TLS로 감싼 것**이에요. TLS 핸드셰이크에서 **인증서와 서명으로 서버가 진짜인지 확인**하고, **키 교환으로 둘만 아는 대칭키**를 만든 뒤, 실제 데이터는 그 **대칭키로 암호화**해요. TLS 1.3은 이 과정을 왕복 1번(1-RTT)에 끝내요.
:::

## 쉽게 이해하기

처음 만난 가게와 **비밀 편지**를 주고받고 싶다고 해 봐요. 풀어야 할 문제는 세 가지예요.

1. **이 가게가 진짜 그 가게 맞아?** 가게는 구청이 도장 찍어 준 **사업자 등록증(인증서)** 을 보여 줘요. 등록증은 복사할 수 있으니, 가게는 "지금 이 대화"에 **자기만 가진 도장(개인키)** 을 찍어서 진짜 주인임을 보여요.
2. **같은 자물쇠 열쇠를 어떻게 나눠 갖지?** 열쇠를 택배로 보내면 중간에 훔쳐볼 수 있어요. 그래서 둘이 모두가 아는 같은 바탕색에 **자기만 아는 물감 한 방울씩**을 섞어 보내고, 받은 쪽이 거기에 자기 물감을 또 섞어요. 그러면 양쪽 손에 **같은 색**이 생기지만, 중간에서 본 사람은 그 색을 만들 수 없어요. 이게 **키 교환**이에요.
3. **그다음부터는?** 같은 열쇠로 잠그고 여는 **자물쇠 상자(대칭키)** 에 편지를 넣어 주고받아요. 이 방식이 가장 빨라요.

단, 실제로는 "물감"이 수학 계산(Diffie-Hellman)이고, "도장"은 전자서명이에요. 그리고 TLS 1.3에서는 열쇠 자체가 네트워크로 **한 번도 오가지 않아요**. 양쪽이 각자 계산해서 같은 값을 얻을 뿐이에요.

## 제대로 알기

### HTTPS가 보장하는 세 가지

HTTP는 내용을 **평문**(누구나 읽을 수 있는 글자 그대로)으로 보내요. 중간의 와이파이, 공유기, 통신사 어디서든 엿보거나 바꿀 수 있어요. HTTPS는 HTTP를 **TLS**(Transport Layer Security, 전송 구간 암호화 규약) 위에서 보내서 이 문제를 막아요. 기본 포트는 443이에요.

| 보장 | 뜻 | 담당 |
|---|---|---|
| **기밀성** | 남이 못 읽음 | 대칭키 암호화 |
| **무결성** | 중간에 바뀌면 알아챔 | 대칭키 암호화의 인증 태그, Finished |
| **인증** | 상대가 진짜임 | 인증서 + 전자서명 |

### 대칭키, 비대칭키, 인증서의 역할 구분

이 페이지에서 가장 중요한 표예요. "어떤 암호가 어디에 쓰이나"만 정확히 잡으면 핸드셰이크가 저절로 이해돼요.

| 도구 | 한 줄 뜻 | TLS에서 하는 일 |
|---|---|---|
| **대칭키**(symmetric key, 잠그는 열쇠와 여는 열쇠가 같음) | 빠름 | 핸드셰이크 뒤 **실제 데이터 전부**를 암호화. TLS 1.3은 AES-GCM, ChaCha20-Poly1305 같은 **AEAD**(암호화와 변조 검사를 한 번에) 방식만 씀 |
| **키 교환**(ECDHE, 비대칭 수학으로 같은 비밀 만들기) | 열쇠를 안 보내고 공유 | 양쪽이 임시 값을 주고받아 **같은 공유 비밀**을 각자 계산. 여기서 대칭키가 나옴 |
| **전자서명**(개인키로 찍고 공개키로 확인) | "누구인지" 증명 | 서버가 개인키로 CertificateVerify에 서명. CA가 인증서에 서명 |
| **인증서**(certificate, 공개키 + 주인 이름 + CA 도장) | 공개키의 신분증 | "이 공개키는 www.example.com 것"이라고 CA가 보증 |
| **해시**(hash, 긴 데이터를 짧은 지문으로) | 요약·확인 | 핸드셰이크 대화 전체 요약, 키 만들기, Finished 계산 |

왜 둘 다 쓸까요? 비대칭 방식은 처음 만난 상대와도 안전하게 시작할 수 있지만 느려요. 대칭키는 빠르지만, 같은 키를 먼저 나눠 가져야 해요. 그래서 **시작은 비대칭, 본 데이터는 대칭**으로 장점만 섞어요.

<Aside type="note">
암호 알고리즘 내부(AES 구조, RSA·타원곡선 수학)는 보안 섹션에서 자세히 다룰 예정이에요. 여기서는 역할만 알면 충분해요.
</Aside>

### TLS 1.3 핸드셰이크 (1-RTT)

TCP 연결(→ [TCP와 UDP](../tcp-udp/))이 맺어진 뒤에 시작해요. "(암호화)"가 붙은 메시지는 암호화돼서 가요.

| 순서 | 방향 | 메시지 | 하는 일 |
|---|---|---|---|
| 1 | 클라 → 서버 | `ClientHello` | 지원 버전·암호 목록, **key_share**(내 임시 공개값), **SNI**(접속할 도메인 이름) |
| 2 | 서버 → 클라 | `ServerHello` | 고른 암호, key_share(서버 임시 공개값). 이제 양쪽이 같은 비밀을 계산 |
| 3 | 서버 → 클라 | `EncryptedExtensions` (암호화) | 추가 설정(예: HTTP/2 쓸지 정하는 ALPN) |
| 4 | 서버 → 클라 | `Certificate` (암호화) | 서버 인증서 + 중간 CA 인증서 |
| 5 | 서버 → 클라 | `CertificateVerify` (암호화) | 지금까지 대화 요약에 **개인키로 서명** |
| 6 | 서버 → 클라 | `Finished` (암호화) | 핸드셰이크 전체가 맞는지 확인하는 값 |
| 7 | 클라 → 서버 | `Finished` (암호화) + HTTP 요청 | 검증 끝나면 바로 요청을 같이 보냄 |

2~6은 서버가 **한 번에 몰아서** 보내요. 그래서 클라이언트 입장에서 한 번 왕복(1-RTT)하면 HTTP 요청을 보낼 수 있어요.

핵심 메시지 두 개는 따로 기억해 둬요.

- **CertificateVerify**: 인증서는 공개 정보라 누구나 복사할 수 있어요. 그래서 "인증서 속 공개키의 짝인 **개인키를 내가 진짜 갖고 있다**"는 증거로, 지금까지 주고받은 메시지 전체의 요약에 서명해요. TLS 1.3에서 서버 인증서의 키는 **암호화가 아니라 이 서명**에 쓰여요.
- **Finished**: 핸드셰이크 전체와 만들어진 키가 양쪽에서 똑같은지 확인하는 값이에요. 중간에 누가 메시지를 바꿨으면 여기서 어긋나서 연결을 끊어요.

클라이언트가 보낸 key_share 방식을 서버가 지원하지 않으면, 서버가 `HelloRetryRequest`로 "다른 걸로 다시 보내 줘"라고 해요. 이때는 왕복이 하나 더 들어요.

### 직접 해보기: curl로 순서 보기

터미널에서 `curl -v https://www.google.com`을 실행하면 핸드셰이크 메시지가 찍혀요. 한 번 실행해 본 예시에서 필요한 줄만 골랐어요(환경과 시점에 따라 다르게 나올 수 있어요).

```text
TLS handshake, Client hello (1):
TLS handshake, Server hello (2):
TLS handshake, Unknown (8):        ← 8번 = EncryptedExtensions
TLS handshake, Certificate (11):
TLS handshake, CERT verify (15):
TLS handshake, Finished (20):
TLS handshake, Finished (20):      ← 클라이언트의 Finished
SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256
ALPN: server accepted h2
SSL certificate verify ok.
```

위 표의 순서가 그대로 보여요. 괄호 속 숫자는 규격에 정해진 메시지 번호예요. 마지막 줄들은 "TLS 1.3, 대칭 암호는 ChaCha20-Poly1305, HTTP/2 사용, 인증서 검증 통과"라는 뜻이에요.

### 인증서와 CA, 체인 검증

**CA**(Certificate Authority, 인증서 발급 기관)는 "이 공개키는 이 도메인 주인 것"이라고 도장(서명)을 찍어 주는 곳이에요. 인증서 안에는 이런 게 들어 있어요.

- 주인 이름과 도메인(**SAN**, Subject Alternative Name 확장에 도메인 목록)
- 주인의 공개키
- 발급자(어느 CA가 찍었는지), 유효기간, 일련번호
- 위 내용 전체에 대한 CA의 서명

그런데 브라우저가 세상 모든 CA를 알 수는 없어요. 그래서 **체인**(chain, 인증서 사슬)을 써요.

```text
루트 CA (브라우저·OS에 미리 들어 있음)
  └ 서명 → 중간 CA
              └ 서명 → www.example.com (리프 인증서)
```

서버는 보통 **리프 + 중간 CA 인증서**를 보내고, 루트는 클라이언트가 이미 가진 걸 써요. 검증은 **아래에서 위로** 올라가요. 각 인증서마다 이걸 확인해요.

1. 위 인증서의 공개키로 서명이 맞는가
2. 지금이 유효기간 안인가
3. 폐기되지 않았는가(CRL이나 OCSP 같은 폐기 정보)
4. 발급자 이름이 위 인증서의 주인 이름과 같은가

그리고 브라우저는 SAN의 도메인이 내가 접속한 도메인과 맞는지도 확인해요. 다른 인증서에 서명할 수 있는 CA 인증서는 "CA다"라는 표시(Basic Constraints의 `cA=true`)가 있어야 해요.

`openssl s_client`로 구글에 한 번 접속해 본 예시에서도 depth 0(리프 `www.google.com`) → depth 1(중간 CA) → depth 2(루트 계열) 세 칸이 보였어요.

### TLS 1.2와 1.3의 차이

| 항목 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| 데이터 보내기 전 왕복 | 2-RTT | 1-RTT (재접속은 0-RTT 가능) |
| 키 교환 | 정적 RSA 키 교환도 허용 | 정적 RSA·정적 DH **제거**, (EC)DHE 중심 |
| 전방 비밀성 | 방식에 따라 없음 | 공개키 기반 교환은 모두 제공 |
| 인증서 전송 | 평문 | **암호화** (ServerHello 이후 전부 암호화) |
| 대칭 암호 | 옛 방식 다수 | AEAD만 |
| 암호 스위트 이름 | `ECDHE-RSA-AES128-GCM-SHA256` (키교환-인증-암호-해시) | `TLS_AES_128_GCM_SHA256` (암호+해시만) |

### 전방 비밀성(Forward Secrecy)

**전방 비밀성**은 "나중에 서버 개인키가 털려도, 과거에 녹화해 둔 대화는 못 푼다"는 성질이에요.

- TLS 1.2의 **RSA 키 교환**은 클라이언트가 만든 비밀값을 서버 공개키로 잠가서 보냈어요. 누가 대화를 몽땅 녹화해 두었다가 나중에 서버 개인키를 훔치면, 과거 대화를 전부 풀 수 있어요.
- **(EC)DHE**는 연결마다 임시 키를 만들고 끝나면 버려요. 서버 개인키는 서명에만 쓰니, 털려도 과거 대화의 키는 다시 만들 수 없어요.

그래서 TLS 1.3은 정적 RSA 키 교환을 아예 없앴어요.

### 0-RTT: 빠르지만 위험한 재접속

전에 접속한 적이 있으면 서버가 준 **세션 티켓**(다음에 쓸 미리 나눈 키, PSK)으로 **첫 메시지에 바로 데이터**를 실어 보낼 수 있어요. 이걸 **0-RTT**(early data)라고 해요. 대신 두 가지가 약해요.

1. **재전송(replay) 공격**: 공격자가 그 첫 메시지를 복사해서 서버에 또 보낼 수 있어요. 서버가 이걸 완벽히 막는다는 보장이 없어요.
2. **전방 비밀성 없음**: 0-RTT 데이터는 미리 나눈 키로만 잠가요.

그래서 실무에서는 0-RTT에 **조회처럼 여러 번 해도 결과가 같은 요청**(멱등 요청)만 허용하고, 결제·주문 같은 요청은 막아요. 규격 문서도 "보통 멱등으로 여겨지는 요청조차" 악용될 수 있다고 경고해요.

### 중간자 공격(MITM)과 HTTPS

**중간자 공격**(Man-In-The-Middle)은 공격자가 사용자와 서버 사이에 끼어들어 양쪽인 척하는 거예요. HTTPS에서 이게 어려운 이유는 이래요.

- 공격자는 그 도메인용으로 **믿을 수 있는 CA가 서명한 인증서**를 내야 해요.
- 진짜 인증서를 복사해 와도, 그 **개인키가 없으니 CertificateVerify 서명**을 못 만들어요.
- 협상 내용을 몰래 바꾸면 **Finished**에서 걸려요.

그래도 뚫리는 경우가 있어요.

- 사용자가 **인증서 경고를 무시**하고 들어갈 때
- 공격자(또는 회사 보안 장비, 악성코드)가 **가짜 루트 CA를 기기에 설치**했을 때
- 처음부터 **http로 접속**해서 https로 넘어가기 전에 가로챌 때(SSL 스트리핑)

### HSTS: "우리 사이트는 https로만 와"

**HSTS**(HTTP Strict Transport Security)는 서버가 HTTPS 응답에 이 헤더를 넣는 거예요.

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

- `max-age`: 이 규칙을 기억할 기간(초). 필수예요.
- `includeSubDomains`: 하위 도메인까지 적용.

이 헤더를 받은 브라우저는 그 기간 동안 사용자가 `http://`를 쳐도 **네트워크에 내보내기 전에** `https://`로 바꿔요. HSTS를 기억한 사이트에서 인증서 오류가 나면 브라우저는 연결을 끊어야 하고, 사용자에게 "무시하고 진행" 버튼도 주지 말라고 권고해요.

한계는 **첫 방문**이에요. 헤더를 받기 전 첫 http 요청은 여전히 가로챌 수 있어요. 이를 막으려고 브라우저에 미리 넣어 두는 **HSTS preload 목록**이 있어요. 헤더 끝의 `preload` 단어는 정식 규격 문법이 아니라, 그 목록에 등록하겠다는 관례적 표시예요. 실제로 github.com에 요청해 보면 `max-age=31536000; includeSubdomains; preload`를 돌려줘요.

<Aside type="caution" title="자주 헷갈리는 점">
- **HTTPS가 데이터를 비대칭키로 암호화한다?** 아니에요. 비대칭은 키 교환과 서명에만 쓰고, 실제 데이터는 대칭키로 암호화해요.
- **TLS 1.3도 세션키를 서버 공개키로 잠가 보낸다?** 그건 1.2의 RSA 키 교환이고, 1.3에서는 없어졌어요. 키는 양쪽이 각자 계산해요.
- **인증서만 있으면 진짜 서버다?** 인증서는 누구나 복사할 수 있어요. 개인키로 만든 서명(CertificateVerify)까지 맞아야 해요.
- **TLS 1.3이면 접속 도메인도 숨겨진다?** SNI는 ClientHello에 평문으로 실려요. 인증서는 1.3부터 암호화돼요.
- **TLS 1.3은 1-RTT니까 HTTPS 접속이 왕복 1번?** 앞에 TCP 연결 1-RTT가 따로 있어요. TCP + TLS 1.3 = 2-RTT 뒤에 요청이 나가요. HTTP/3(QUIC)는 둘을 합쳐 1-RTT예요. → [HTTP 버전](../http-versions/)
- **SSL과 TLS는 같은 것?** 흔히 섞어 부르지만 SSL은 TLS의 옛 이름이자 예전 프로토콜이에요. 지금 쓰는 건 TLS 1.2와 1.3이에요.
</Aside>

## 면접 질문

<details>
<summary>Q. HTTPS는 HTTP와 무엇이 다르고, 무엇을 보장하나요?</summary>

**답변(30초)** HTTPS는 HTTP를 TLS 위에서 보내는 것이고, 기밀성·무결성·인증 세 가지를 보장해요. 핸드셰이크에서 서버가 인증서와 서명으로 자기가 진짜임을 증명하고, 키 교환으로 둘만 아는 대칭키를 만들어요. 이후 데이터는 그 대칭키로 암호화하면서 변조 검사도 같이 해요. 기본 포트는 443이에요.

**꼬리질문**
- Q. HTTPS면 어떤 정보도 안 보이나요? → 경로·헤더·본문은 암호화되지만 목적지 IP와 SNI의 도메인 이름은 보여요.
- Q. 무결성은 어떻게 지켜요? → AEAD 암호가 데이터마다 변조 검사값을 붙이고, 핸드셰이크 자체는 Finished로 확인해요.
</details>

<details>
<summary>Q. TLS 핸드셰이크 과정을 설명해 주세요. (TLS 1.3 기준)</summary>

**답변(30초)** TLS 1.3은 왕복 1번에 끝나요. 클라이언트가 ClientHello에 지원 암호와 키 교환용 임시 공개값, 접속 도메인(SNI)을 보내요. 서버는 ServerHello로 자기 임시 공개값을 보내고, 이때부터 양쪽이 같은 비밀을 계산해 나머지를 암호화해요. 서버는 이어서 인증서, 개인키 서명인 CertificateVerify, Finished를 보내요. 클라이언트는 인증서 체인과 서명을 검증하고 Finished와 함께 HTTP 요청을 바로 보내요.

**꼬리질문**
- Q. CertificateVerify와 Finished는 각각 무엇을 증명하나요? → CertificateVerify는 인증서 속 공개키의 짝인 개인키를 서버가 갖고 있다는 증거예요. Finished는 핸드셰이크 전체와 만들어진 키가 양쪽에서 같다는 확인이에요.
- Q. SNI는 왜 필요해요? → IP 하나에 여러 사이트가 있을 때 서버가 어느 인증서를 줄지 골라야 하니까요.
- Q. 서버가 클라이언트의 키 교환 방식을 지원하지 않으면요? → HelloRetryRequest로 다시 보내라고 하고, 왕복이 하나 늘어요.
</details>

<details>
<summary>Q. 대칭키와 비대칭키를 왜 같이 쓰나요?</summary>

**답변(30초)** 각자의 약점을 서로 메우려고요. 대칭키는 빠르지만 같은 키를 먼저 안전하게 나눠 가져야 하는 문제가 있어요. 비대칭 방식은 처음 만난 상대와도 키를 합의하고 서명으로 신원을 증명할 수 있지만 느려요. 그래서 핸드셰이크에서는 키 교환과 서명에 비대칭을 쓰고, 실제 데이터는 그 결과로 얻은 대칭키로 암호화해요.

**꼬리질문**
- Q. 인증서의 공개키로 데이터를 암호화하나요? → TLS 1.3에서는 아니에요. 인증서 공개키는 서버 서명을 확인하는 데 써요.
</details>

<details>
<summary>Q. 인증서와 CA의 역할, 브라우저는 인증서를 어떻게 검증하나요?</summary>

**답변(30초)** 인증서는 "이 공개키는 이 도메인 것"이라는 내용에 CA가 서명한 신분증이에요. 서버는 자기 인증서와 중간 CA 인증서를 보내고, 브라우저는 미리 가진 루트 CA까지 아래에서 위로 서명을 확인해요. 각 단계에서 유효기간, 폐기 여부, 발급자 이름을 보고, 마지막으로 인증서의 도메인(SAN)이 접속한 도메인과 맞는지 확인해요. 하나라도 틀리면 경고를 띄워요.

**꼬리질문**
- Q. 서버가 중간 인증서를 빼먹으면요? → 루트까지 사슬이 안 이어져서 일부 클라이언트에서 "신뢰할 수 없음" 오류가 나요.
- Q. 개인키가 유출되면요? → 그 인증서를 폐기하고 새 키로 재발급해야 해요.
</details>

<details>
<summary>Q. 전방 비밀성이 뭐고, TLS 1.3은 왜 RSA 키 교환을 없앴나요?</summary>

**답변(30초)** 전방 비밀성은 나중에 서버 개인키가 털려도 과거 대화는 풀 수 없다는 성질이에요. RSA 키 교환은 세션 비밀을 서버 공개키로 잠가 보내서, 녹화한 트래픽을 나중에 개인키로 다 풀 수 있었어요. ECDHE는 연결마다 임시 키를 만들고 버리니까 개인키가 털려도 과거 키를 다시 못 만들어요. 그래서 TLS 1.3은 정적 RSA 키 교환을 없애고 (EC)DHE 중심으로 바꿨어요.

**꼬리질문**
- Q. TLS 1.2와 1.3의 다른 차이는요? → 1-RTT로 줄었고, 인증서까지 암호화하고, 대칭 암호는 AEAD만 남겼어요.
</details>

<details>
<summary>Q. 0-RTT의 장점과 위험은 무엇인가요?</summary>

**답변(30초)** 재접속할 때 미리 받은 세션 티켓으로 첫 메시지에 데이터를 실어 왕복 없이 요청할 수 있는 게 장점이에요. 하지만 공격자가 그 메시지를 복사해 다시 보내는 재전송 공격을 완전히 막을 수 없고, 전방 비밀성도 없어요. 그래서 조회 같은 멱등 요청만 0-RTT로 받고, 결제처럼 상태를 바꾸는 요청은 막아야 해요.
</details>

<details>
<summary>Q. HSTS가 무엇이고 왜 필요한가요? 한계는요?</summary>

**답변(30초)** HSTS는 서버가 "정해진 기간 동안 https로만 와"라고 알리는 헤더예요. http로 들어온 걸 301로 https에 보내기만 하면, 첫 http 요청이 평문으로 나가서 SSL 스트리핑을 당할 수 있어요. HSTS를 받은 브라우저는 http 요청을 아예 안 내보내고 내부에서 https로 바꿔요. 다만 헤더를 받기 전 첫 방문은 여전히 위험해서 브라우저 내장 preload 목록으로 보완해요.

**꼬리질문**
- Q. 중간자 공격을 HTTPS가 어떻게 막나요? → 공격자는 믿을 수 있는 CA의 인증서도, 그 개인키 서명도 만들 수 없어요. 경고를 무시하거나 가짜 루트 CA가 설치된 경우엔 뚫려요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제 API 앞단 CDN에서 TLS 1.3 0-RTT를 켠 뒤, 같은 결제가 두 번 처리된 건이 생겼습니다.</summary>

**상황 파악**
0-RTT를 켠 시점부터 중복이 생겼다면 **0-RTT의 재전송 위험**이 가장 유력해요. 0-RTT 데이터는 공격자나 네트워크 장비가 복사해 다시 보내도 서버가 구분한다는 보장이 없어요.

**원인 후보**
1. 0-RTT로 온 결제 요청이 재전송되어 두 번 도착했어요.
2. 0-RTT와 무관하게 클라이언트의 자동 재시도가 중복을 만들었어요(타임아웃 후 재요청).
3. 서버에 같은 요청을 한 번만 처리하는 장치(중복 방지)가 없어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 결제 같은 비멱등 요청은 0-RTT를 받지 않기(조회만 허용) | 원인을 바로 끊음, 설정 변경만으로 가능 | 해당 요청은 재접속 때 왕복이 하나 늘어요 |
| B. 0-RTT를 아예 끄기 | 가장 단순하고 안전 | 조회 요청까지 재접속 속도 이점이 사라짐 |
| C. 멱등키(요청마다 고유 ID)로 서버에서 중복 처리 막기 | 0-RTT·재시도·네트워크 중복 모두 방어 | 키 저장소와 보관 기간 관리가 필요 |

**내가 고를 방법**
A와 C를 같이 써요. A로 결제 경로의 0-RTT 위험을 바로 없애고, 원인 후보 2처럼 0-RTT와 상관없는 중복도 있을 수 있으니 C로 결제 처리 자체를 한 번만 되게 만들어요. 운영이 부담스러우면 우선 B로 끄고 나서 A로 좁혀요.

**채점 포인트**: 0-RTT 재전송(replay) 위험, 멱등 요청만 허용, 결제는 비멱등, 멱등키로 중복 방지, 0-RTT 끌 때의 속도 트레이드오프.
</details>

<details>
<summary>상황: 사내망에서만 외부 API를 호출하면 "인증서를 신뢰할 수 없음" 오류가 납니다.</summary>

**상황 파악**
같은 코드가 외부에서는 되고 사내망에서만 안 된다면, 서버보다 **중간 경로**를 의심해요. 회사가 TLS 트래픽을 검사하는 프록시를 쓰면, 프록시가 **자체 루트 CA로 인증서를 다시 서명**해서 내 앱에 줘요. 사실상 허가된 중간자예요.

**원인 후보**
1. 사내 보안 프록시가 인증서를 재서명했고, 그 사내 루트 CA가 앱(JVM 등)의 신뢰 목록에 없어요.
2. 상대 서버가 중간 CA 인증서를 빼먹고 보냈어요(외부에선 캐시로 우연히 통과).
3. 인증서가 만료됐거나 서버 시각이 틀렸어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 사내 루트 CA를 앱의 신뢰 저장소(truststore)에 추가 | 검증은 그대로 유지하면서 문제 해결 | 환경마다 배포 관리가 필요하고, 사내 CA를 믿는 범위가 넓어짐 |
| B. 해당 API 도메인만 프록시 검사 예외 등록 | 앱 수정이 없음 | 보안팀 협의가 필요하고 검사 공백이 생김 |
| C. 인증서 검증 끄기 | 당장 동작 | **절대 금지**. 누구든 중간자가 될 수 있어요 |

**내가 고를 방법**
먼저 `openssl s_client`로 실제로 받은 인증서의 발급자가 사내 CA인지 확인해요. 사내 CA가 맞으면 A를 써요. 검증을 유지하는 게 핵심이에요. 발급자가 정상인데 체인이 짧으면 원인 2이니 상대에게 중간 인증서를 보내 달라고 해요.

**채점 포인트**: 체인 검증과 신뢰 앵커, 사내 TLS 검사 프록시의 재서명, truststore에 CA 추가, 검증 비활성화 금지, openssl로 발급자·depth 확인.
</details>

<details>
<summary>상황: 로그인 페이지가 http로 들어오면 301로 https에 보내고 있습니다. 보안팀이 "이걸로는 부족하다"고 합니다.</summary>

**상황 파악**
301 리다이렉트는 **첫 http 요청이 평문으로 나간 뒤**에 동작해요. 공용 와이파이 같은 곳에서 공격자가 그 첫 요청을 가로채 https로 안 넘어가게 막을 수 있어요(SSL 스트리핑).

**원인 후보**
1. HSTS 헤더가 없어 브라우저가 매번 http부터 시도해요.
2. HSTS가 있어도 첫 방문 사용자는 보호받지 못해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. HSTS 헤더 추가(`max-age` + `includeSubDomains`) | 한 번 방문한 사용자는 http 요청 자체가 사라짐 | 하위 도메인 중 https가 안 되는 곳이 있으면 접속 장애 |
| B. HSTS preload 목록 등록 | 첫 방문부터 보호 | 목록에서 빼기 어렵고 오래 걸려서 되돌리기 힘듦 |

**내가 고를 방법**
A부터 해요. 처음엔 `max-age`를 짧게 시작해 하위 도메인 장애가 없는지 보고, 문제없으면 길게 늘려요. 모든 하위 도메인이 https로 안정되면 B로 preload 등록까지 가요. 301 리다이렉트는 HSTS를 처음 받기 전 사용자를 위해 그대로 둬요.

**채점 포인트**: 첫 요청 평문 문제(SSL 스트리핑), HSTS 동작(브라우저 내부 변환), max-age 점진 확대, includeSubDomains 장애 위험, preload로 첫 방문 보호와 되돌리기 어려움.
</details>

## 필기 포인트

- HTTPS = HTTP + TLS, 기본 포트 443.
- 대칭키 = 데이터 암호화(빠름). 비대칭 = 키 교환 + 전자서명. 해시 = 요약·무결성 확인.
- TLS 1.3 = 1-RTT, TLS 1.2 = 2-RTT, 재접속 0-RTT(재전송 위험).
- TLS 1.3 순서: ClientHello → ServerHello → EncryptedExtensions → Certificate → CertificateVerify → Finished → (클라) Finished.
- TLS 1.3: 정적 RSA 키 교환 제거, 인증서 암호화, AEAD만, 전방 비밀성.
- 인증서 체인: 리프 → 중간 CA → 루트 CA(신뢰 앵커). 검사: 서명, 유효기간, 폐기(CRL/OCSP), 발급자, 도메인(SAN).
- SNI = 접속 도메인 이름, ClientHello에 평문. ALPN = HTTP 버전 협상.
- HSTS: `Strict-Transport-Security`, `max-age` 필수, `includeSubDomains`. 첫 방문 취약 → preload 목록.
