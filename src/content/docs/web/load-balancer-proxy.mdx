:::tip[한 줄 요약]
**로드밸런서**는 클라이언트에게 주소 하나만 보여 주고, 들어온 요청을 뒤에 있는 여러 서버 중 **건강한 서버에만** 나눠 보내는 장치예요. **L4**는 IP와 포트만 보고 연결 단위로 나눠서 빠르고, **L7**은 HTTP 내용(경로, 헤더, 쿠키)을 읽어서 더 똑똑하게 나누지만 그만큼 일이 많아요.
:::

## 쉽게 이해하기

로드밸런서는 **큰 식당 입구의 안내 직원**과 비슷해요.

1. 손님은 식당 대표 번호(주소 하나)만 알아요. 안쪽에 홀 직원이 몇 명인지는 몰라요.
2. 안내 직원이 손님을 홀 직원들에게 **차례대로**, 또는 **지금 제일 한가한 직원에게** 배정해요(분산 알고리즘).
3. 안내 직원은 틈틈이 홀 직원들에게 "괜찮아요?" 하고 물어봐요. 대답이 없는 직원에게는 손님을 보내지 않아요(**헬스 체크**).
4. 손님이 몰리면 홀 직원을 더 뽑으면 돼요. 손님은 대표 번호가 그대로라 아무것도 바꿀 필요가 없어요(수평 확장).
5. 안내 직원은 두 종류가 있어요. 손님 **번호표만 보고** 바로 보내는 직원(L4)과, **주문서를 펼쳐 읽고** "디저트 주문은 2층" 하고 보내는 직원(L7)이에요.

단, 실제로는 안내 직원이 서버 대신 손님을 맞기 때문에 서버 입장에서는 "모든 손님이 안내 직원에게서 왔다"고 보여요. 그래서 진짜 손님이 누군지 따로 적어 넘겨야 해요(X-Forwarded-For). 이 부분은 아래에서 자세히 봐요.

## 제대로 알기

### 1. 로드밸런서가 왜 필요할까

서버 한 대로 버티다가 사용자가 늘면 서버를 여러 대로 늘려야 해요. 그런데 클라이언트가 서버 주소를 하나하나 알아야 한다면, 서버를 추가하거나 뺄 때마다 클라이언트도 바뀌어야 해요.

**로드밸런서**(Load Balancer, 요청을 여러 서버에 나눠 주는 장치)는 그 앞에 서서 **단일 접점**이 돼요. 하는 일은 크게 세 가지예요.

- **분산**: 요청을 여러 대상(서버, 컨테이너, IP)에 나눠 보내요.
- **상태 감시**: 대상이 비정상이면 빼고, 다시 정상이 되면 되돌려요.
- **TLS 오프로딩**: HTTPS 암호를 푸는 일(TLS 종료)을 로드밸런서가 대신 해서, 서버는 본 업무에 집중해요. AWS에서는 HTTPS 리스너에 인증서를 붙이면 로드밸런서가 연결을 끝내고 요청을 복호화해요.

### 2. 포워드 프록시 vs 리버스 프록시

**프록시**(proxy, 대리인)는 둘 사이에서 요청을 대신 전달하는 서버예요. 누구 편에 서 있느냐로 나뉘어요.

| 구분 | 포워드 프록시 | 리버스 프록시 |
|---|---|---|
| 위치 | 클라이언트 쪽 | 서버 쪽 앞 |
| 누구를 대신하나 | 클라이언트를 대신해 밖으로 나감 | 서버를 대신해 요청을 받음 |
| 누가 모르나 | 서버가 진짜 클라이언트를 모름 | 클라이언트가 진짜 서버를 모름 |
| 주 용도 | 사내 접근 통제, 캐시 | 로드밸런싱, TLS 종료, 캐시, 압축, 내부 서버 숨기기 |
| 예 | 회사 프록시 | nginx, AWS ALB |

L7 로드밸런서는 **리버스 프록시의 한 용도**예요. nginx 하나로 리버스 프록시와 로드밸런서를 같이 해요.

참고로 **CDN**(Content Delivery Network)은 전 세계에 흩어진 캐시 서버에 정적 파일을 복사해 두고 사용자와 가까운 곳에서 응답하는, 지리적으로 흩어진 리버스 프록시 캐시라고 보면 돼요.

### 3. L4 vs L7

숫자는 [네트워크 계층](../network-layers/)의 층 번호예요. 4계층은 TCP/UDP, 7계층은 HTTP 같은 애플리케이션이에요.

| 항목 | L4 로드밸런서 | L7 로드밸런서 |
|---|---|---|
| 보는 정보 | IP와 **포트**(TCP/UDP) | HTTP 내용: 경로, Host 헤더, 다른 헤더, 메서드, 쿼리, 쿠키 |
| 나누는 단위 | **연결** 하나 | **요청** 하나 |
| 라우팅 예 | 이 포트로 온 연결은 이 서버 그룹 | `/api/*`는 API 서버, `/static/*`는 정적 서버, 도메인별 분기 |
| 헤더 추가 | 못 함(HTTP를 안 읽음) | X-Forwarded-For 등 추가 가능 |
| 쿠키 스티키 세션 | 불가 | 가능 |
| 속도 | 해석이 없어 빠름 | HTTP 해석 비용이 듦 |
| 프로토콜 | TCP, UDP 등 아무거나 | HTTP/HTTPS 중심 |
| AWS 예 | NLB | ALB |

AWS 문서 기준으로 조금 더 보면 이래요.

- **NLB**(Network Load Balancer)는 TCP 연결을 **흐름 해시**로 배정해요. 재료는 프로토콜, 출발지 IP·포트, 목적지 IP·포트, TCP 시퀀스 번호예요. 연결 하나는 끝날 때까지 한 서버로만 가요. 같은 클라이언트라도 새 연결은 출발지 포트가 달라서 다른 서버로 갈 수 있어요.
- NLB는 가용 영역(데이터센터 묶음)마다 **고정 IP**를 가져요. 고객사 방화벽에 IP를 등록해야 할 때 유리해요. ALB는 DNS 이름으로 접근하고 IP가 바뀔 수 있어요.
- **ALB**(Application Load Balancer)는 요청이 오면 규칙을 우선순위대로 보고 대상 그룹을 고른 다음, 그 안에서 알고리즘으로 서버를 골라요. 리다이렉트, 고정 응답, 사용자 인증도 할 수 있어요.
- ALB는 여러 클라이언트의 요청을 **백엔드 연결 하나로 모아** 보낼 수 있어요(커넥션 멀티플렉싱). 서버 쪽 연결은 기본 HTTP/1.1 keep-alive예요.

<Aside type="caution" title="자주 하는 오해">
"L4는 IP만 본다"는 틀려요. **포트**까지 봐요. L4가 못 보는 건 HTTP 안쪽(경로, 헤더, 쿠키)이에요.
</Aside>

### 4. 분산 알고리즘

| 알고리즘 | 어떻게 고르나 | 장점 | 단점·주의 |
|---|---|---|---|
| 라운드 로빈 | 순서대로 돌아가며 | 단순, 상태가 필요 없음 | 요청마다 처리 시간이 다르면 불균형 |
| 가중치 라운드 로빈 | 가중치 비율대로 | 성능이 다른 서버를 섞을 수 있음 | 가중치를 사람이 정해야 함 |
| 최소 연결(least_conn) | 활성 연결이 가장 적은 서버 | 긴 요청이 섞여도 덜 몰림 | 연결 수를 추적해야 함 |
| 최소 처리 중 요청(ALB) | 처리 중 요청이 가장 적은 대상 | 위와 같은 장점 | 위와 같음 |
| IP 해시(ip_hash) | 클라이언트 IP로 해시 | 같은 클라이언트는 같은 서버 | 같은 IP 뒤 많은 사용자가 한 서버에 몰림 |
| 일관된 해싱(hash ... consistent) | 임의 키를 해시 링에 배치 | 서버 추가·제거 때 재배정되는 키가 적음 | 키를 잘 골라야 함 |
| 가중치 랜덤(ALB) | 가중치를 반영해 무작위 | 단순 | - |

nginx 기준 세부 사실이에요.

- 아무것도 안 쓰면 **가중치 라운드 로빈**이고 `weight` 기본값은 1이에요. weight가 5, 1, 1이면 요청 7개 중 5개가 첫 서버로 가요.
- `least_conn`은 동률이면 가중치 라운드 로빈으로 정해요.
- `ip_hash`는 IPv4 주소의 **앞 세 덩어리**(옥텟)만 키로 써요. 그래서 같은 대역의 사용자는 같은 서버로 가요. 서버를 잠시 빼려면 지우지 말고 `down`을 표시해야 다른 사용자 배정이 흔들리지 않아요.
- `backup` 서버는 주 서버가 모두 안 될 때만 요청을 받아요. 해시 계열 알고리즘과는 같이 못 써요.

```nginx
upstream api {
    least_conn;                 # 최소 연결
    server app1:8080 weight=2;  # 2배 더 받음
    server app2:8080;
    server app3:8080 backup;    # 평소엔 안 받음
}
server {
    location / {
        proxy_pass http://api;
        proxy_set_header Host $host;  # 원래 Host 유지(기본은 upstream 이름으로 바뀜)
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

AWS ALB에는 **slow start**도 있어요. 새로 등록된 서버에 정해진 시간(30~900초) 동안 트래픽을 조금씩 늘려 보내요. 기본은 꺼져 있어요. 막 뜬 서버는 JVM 워밍업이 덜 됐고 캐시도 비어 있어서, 한꺼번에 몰리면 느려지기 때문이에요.

### 5. 헬스 체크: 능동과 수동

**헬스 체크**(health check)는 로드밸런서가 서버가 살아 있는지 확인하는 방법이에요. 두 가지가 있어요.

| 구분 | 수동(passive) | 능동(active) |
|---|---|---|
| 방식 | 실제 요청이 실패하는 걸 보고 판단 | LB가 주기적으로 검사 요청을 보냄 |
| 장점 | 추가 트래픽 없음 | 사용자 요청이 실패하기 전에 알아챔 |
| 단점 | 사용자 요청이 실패해야 알아챔 | 검사 요청 부하, 엔드포인트 설계 필요 |
| 예 | nginx 오픈소스의 `max_fails`/`fail_timeout` | AWS ALB, nginx 상용판(NGINX Plus)의 `health_check` |

- **nginx 오픈소스**: `fail_timeout`(기본 10초) 안에 실패가 `max_fails`(기본 1)번 나면 그 서버를 `fail_timeout` 동안 쉬게 해요. 무엇을 실패로 칠지는 `proxy_next_upstream`(기본 `error timeout`)이 정해요. 주기적으로 찔러 보는 능동 헬스 체크는 nginx 문서에 **상용 구독 기능**으로 적혀 있어요.
- **AWS ALB 기본값**(instance/ip 대상): `GET /`, 30초 간격, 5초 타임아웃, **연속 2번 실패하면 비정상**, **연속 5번 성공하면 정상**, 성공 코드 200.
- ALB는 대상이 **전부** 비정상이면 오히려 **전부에게 보내요**(fail open). 다 막아 버리는 것보다 낫다는 판단이에요.

<Aside type="tip" title="헬스 체크에서 무엇까지 확인할까">
공식 문서에 나온 규칙은 아니고, 실무에서 일반적으로 알려진 이야기예요. 헬스 체크가 DB 같은 외부 의존성까지 확인하면, DB가 잠깐 느려질 때 서버 전부가 동시에 빠질 수 있어요. 그래서 "프로세스가 살아 있나"와 "트래픽을 받을 준비가 됐나"를 나눠 생각하는 경우가 많아요. Spring Boot Actuator의 liveness/readiness 구분이 이 생각과 연결돼요.
</Aside>

### 6. 스티키 세션

**스티키 세션**(sticky session, 같은 사용자를 같은 서버에 붙여 두기)은 서버 메모리에 로그인 세션을 둘 때 쓰는 방법이에요.

- AWS ALB: `stickiness.enabled`(기본 꺼짐). LB가 만든 쿠키(`lb_cookie`) 또는 앱 쿠키(`app_cookie`)를 써요. 쿠키 기본 유효 1일, 최대 7일이에요.
- nginx: `sticky` 지시어(`cookie`, `route`, `learn`)가 있어요. 예전에는 상용 전용이라는 설명이 많은데, 현재 nginx 문서 기준으로는 `sticky` 지시어가 1.29.6부터 오픈소스에 들어왔고 `learn`의 `sync` 옵션만 아직 상용이에요. 버전에 따라 다르니 쓰는 버전 문서를 확인하세요.

일반적으로 알려진 단점은 이래요. 특정 서버에 사용자가 몰릴 수 있고, 그 서버가 죽으면 세션이 사라지고, 배포나 서버 축소 때 붙어 있던 사용자를 옮기기 어려워요. `ip_hash`로 붙이면 회사망·NAT 뒤 사용자들이 같은 IP로 보여서 한 서버에 뭉쳐요. 모바일은 IP가 자주 바뀌어 고정도 깨져요.

대안은 서버를 **무상태**로 만드는 거예요. 세션을 Redis 같은 외부 저장소(Spring Session)에 두거나 토큰(JWT)을 써요. 자세한 비교는 [쿠키·세션·JWT](../cookie-session-jwt/)에서 봐요.

### 7. 진짜 클라이언트 IP: X-Forwarded-For

리버스 프록시를 거치면 서버가 보는 TCP 상대 주소는 **프록시의 IP**예요. 원래 클라이언트 IP는 헤더로 따로 넘겨야 해요.

```http
X-Forwarded-For: 203.0.113.7, 198.51.100.17
```

- **X-Forwarded-For**(XFF)는 표준은 아니지만 사실상 표준이에요. 프록시마다 **자기에게 접속한 주소를 오른쪽에 덧붙여요**. 가장 왼쪽이 원래 클라이언트, 오른쪽으로 갈수록 최근 프록시예요(모두 정직하다는 가정).
- nginx의 `$proxy_add_x_forwarded_for`는 "들어온 XFF 값 + 콤마 + 지금 접속한 주소"예요. AWS ALB는 X-Forwarded-For, X-Forwarded-Proto(원래 http/https), X-Forwarded-Port를 자동으로 붙여요.
- 표준 헤더는 RFC 7239의 `Forwarded`예요(`for=`, `by=`, `host=`, `proto=`). 실제로는 XFF가 훨씬 많이 쓰여요. RFC 7239는 이 헤더가 내부망 구조를 드러낼 수 있으니 기본은 끄고, 필요하면 `for=_hidden` 같은 가린 이름을 쓰라고 권해요.

<Aside type="danger" title="위조 주의">
클라이언트도 XFF 헤더를 **마음대로 넣어서** 보낼 수 있어요. 그래서 가장 왼쪽 값을 레이트 리밋이나 IP 차단에 쓰면 공격자가 쉽게 우회해요. 보안 용도로는 **오른쪽부터** 읽으면서 내가 믿는 프록시 주소를 건너뛰고, 처음 만나는 믿지 않는 주소를 클라이언트로 봐야 해요. 프록시가 1개뿐이면 가장 오른쪽 값이에요.
</Aside>

이 규칙을 직접 짤 필요는 없어요.

- **nginx**: `ngx_http_realip_module`의 `set_real_ip_from`(믿는 주소), `real_ip_header X-Forwarded-For`, `real_ip_recursive on`을 쓰면 위 방식대로 진짜 IP를 골라요.
- **Spring Boot**: 버전마다 설정 이름이 달라요.

| 버전 | 설정 | 값 |
|---|---|---|
| Boot 3.x까지 | `server.forward-headers-strategy` | `native` / `framework` / `none` |
| Boot 4.2 문서 기준 | `server.request.header.forwarded.strategy` | `web-server`(권장) / `framework` / `none` |

지원하는 클라우드 플랫폼에서는 기본이 `web-server`, 아니면 기본이 `none`이에요. Tomcat은 `server.tomcat.remoteip.internal-proxies`(정규식)로 믿을 프록시를 정해요. 이걸 비워서 모든 주소를 믿게 하는 건 운영에서 하면 안 돼요.

### 8. 배포할 때: 커넥션 드레이닝

서버를 그냥 끄면 그 서버가 처리하던 요청이 끊겨요. **커넥션 드레이닝**(connection draining, 처리 중인 요청을 마저 끝내게 기다리기)이 이걸 막아요.

- AWS: 서버를 대상에서 **등록 해제**하면 LB는 바로 새 요청을 안 보내고, 서버는 처리 중인 요청이 끝날 때까지 `draining` 상태가 돼요. 기다리는 시간은 `deregistration_delay.timeout_seconds`로 정하고 기본 300초예요(0~3600).
- 반대로 새 서버는 등록 후 첫 헬스 체크를 통과하면 바로 트래픽을 받아요.
- 쿠버네티스: 파드를 끌 때 기본 유예 시간은 30초예요. 먼저 SIGTERM(정상 종료 요청)을 보내고, 유예가 끝나면 SIGKILL(강제 종료)을 보내요. 종료 직전에 실행되는 preStop 훅이 있어요.

무중단 배포 방식(롤링, 블루그린, 카나리)은 아키텍처·배포 섹션에서 따로 다룰 예정이에요.

## 면접 질문

<details>
<summary>Q. L4 로드밸런서와 L7 로드밸런서의 차이는요? 언제 무엇을 쓰나요?</summary>

**답변(30초)** 보는 정보가 달라요. L4는 IP와 포트만 보고 TCP 연결 단위로 나눠서 빠르고, TCP·UDP 아무거나 받을 수 있어요. L7은 HTTP를 해석해서 경로나 Host 헤더로 서버 그룹을 나누고, X-Forwarded-For를 붙이거나 쿠키로 세션을 고정할 수 있지만 해석 비용이 들어요. 일반 웹 API는 경로 라우팅이 필요하니 L7을, 게임이나 채팅처럼 긴 TCP 연결과 높은 처리량, 고정 IP가 필요하면 L4를 써요.

**꼬리질문**
- Q. L4는 같은 사용자를 항상 같은 서버로 보내나요? → 아니요. 연결 단위라서 새 연결은 출발지 포트가 달라져 다른 서버로 갈 수 있어요.
- Q. L4에서 HTTPS를 쓰면 인증서는 어디에 두나요? → 암호를 풀지 않고 그대로 통과시키면 서버가 인증서를 가져요. 이때 LB는 HTTP 내용을 못 봐요.
</details>

<details>
<summary>Q. 로드밸런싱 알고리즘에는 뭐가 있고, 라운드 로빈의 약점은요?</summary>

**답변(30초)** 라운드 로빈, 가중치 라운드 로빈, 최소 연결, IP 해시, 일관된 해싱이 대표적이에요. 라운드 로빈은 순서대로 돌리니 단순하지만, 요청마다 처리 시간이 다르면 긴 요청이 쌓인 서버에도 계속 보내서 불균형이 생겨요. 그래서 처리 시간이 들쭉날쭉하면 활성 연결이 가장 적은 서버로 보내는 최소 연결 방식을 써요.

**꼬리질문**
- Q. IP 해시의 문제는요? → 회사망이나 NAT 뒤 많은 사용자가 같은 IP로 보여 한 서버에 몰려요. nginx는 IPv4 앞 세 옥텟만 써서 더 뭉쳐요.
- Q. 일관된 해싱은 왜 써요? → 서버를 추가하거나 뺄 때 다시 배정되는 키가 적어서 캐시 서버처럼 "같은 키는 같은 서버"가 중요한 곳에 좋아요.
</details>

<details>
<summary>Q. 헬스 체크는 어떻게 동작하나요? 능동과 수동의 차이는요?</summary>

**답변(30초)** 로드밸런서가 서버 상태를 확인해서 비정상이면 트래픽을 끊고, 회복하면 다시 넣는 기능이에요. 능동 방식은 LB가 주기적으로 검사 요청을 보내요. AWS ALB는 기본으로 30초마다 보내고 연속 2번 실패하면 빼요. 수동 방식은 실제 요청이 실패하는 걸 보고 판단해서 추가 부하가 없지만, 사용자 요청이 실패해야 알아채요. nginx 오픈소스는 수동 방식이고 능동 헬스 체크는 상용판 기능이에요.

**꼬리질문**
- Q. 서버가 전부 비정상이면요? → ALB는 전부에게 보내요(fail open). 다 막는 것보다 일부라도 처리되는 게 낫다는 판단이에요.
- Q. 헬스 체크에서 DB까지 확인하면요? → DB가 잠깐 느려지면 모든 서버가 동시에 빠져 전면 장애가 날 수 있어서 조심해야 해요.
</details>

<details>
<summary>Q. 스티키 세션이 뭐고, 단점과 대안은요?</summary>

**답변(30초)** 같은 사용자를 계속 같은 서버로 보내는 방식이에요. 세션을 서버 메모리에 둘 때 로그인이 풀리지 않게 하려고 써요. 하지만 특정 서버에 사용자가 몰릴 수 있고, 그 서버가 죽거나 배포로 내려가면 세션이 사라져요. 그래서 보통은 서버를 무상태로 만들고 세션을 Redis 같은 외부 저장소에 두거나 토큰을 써서, 어느 서버가 받아도 같게 처리하게 해요.

**꼬리질문**
- Q. L4로도 스티키 세션이 되나요? → 쿠키 기반은 HTTP를 읽어야 해서 L7에서만 돼요. L4는 IP 해시 같은 방식만 가능해요.
</details>

<details>
<summary>Q. 포워드 프록시와 리버스 프록시의 차이는요?</summary>

**답변(30초)** 누구를 대신하느냐가 달라요. 포워드 프록시는 클라이언트 쪽에서 클라이언트를 대신해 밖으로 나가서, 서버가 진짜 클라이언트를 몰라요. 사내 접근 통제나 캐시에 써요. 리버스 프록시는 서버 앞에서 서버를 대신해 요청을 받아서, 클라이언트가 진짜 서버를 몰라요. 로드밸런싱, TLS 종료, 캐시, 내부 서버 숨기기에 쓰고 nginx가 대표적이에요.

**꼬리질문**
- Q. 로드밸런서와 리버스 프록시는 다른 건가요? → L7 로드밸런서는 리버스 프록시가 하는 일 중 하나예요. nginx 하나로 둘 다 해요.
</details>

<details>
<summary>Q. 로드밸런서 뒤에서 클라이언트의 진짜 IP는 어떻게 알아요?</summary>

**답변(30초)** 서버가 보는 접속 주소는 LB의 IP라서, LB가 붙여 주는 X-Forwarded-For 헤더로 알아요. 프록시마다 자기에게 접속한 주소를 오른쪽에 덧붙이니 왼쪽이 원래 클라이언트예요. 하지만 클라이언트가 이 헤더를 위조할 수 있어서, 보안 용도라면 오른쪽부터 믿는 프록시를 건너뛰고 처음 나오는 주소를 써야 해요. nginx는 realip 모듈, Spring Boot는 forwarded 헤더 전략 설정으로 처리해요.

**꼬리질문**
- Q. 표준 헤더는 없나요? → RFC 7239의 `Forwarded` 헤더가 표준이지만 실제로는 X-Forwarded-For가 더 많이 쓰여요.
- Q. X-Forwarded-Proto는 왜 필요해요? → LB에서 TLS를 풀면 서버는 http로 받아요. 이 헤더가 원래 요청이 http였는지 https였는지 알려 줘요.
</details>

<details>
<summary>Q. TLS 종료를 로드밸런서에서 하는 이유는요? 내부가 평문이면 위험하지 않나요?</summary>

**답변(30초)** 암호화·복호화 부담과 인증서 관리를 LB 한 곳에 모으려는 거예요. 서버는 본 업무에 집중하고, 인증서 교체도 LB에서만 하면 돼요. 또 L7 라우팅을 하려면 어차피 HTTP 내용을 읽어야 해서 LB에서 풀어야 해요. 내부 평문이 걱정되면 LB에서 서버까지 다시 TLS로 암호화하거나, L4에서 풀지 않고 그대로 통과시키는 방법이 있어요.

**꼬리질문**
- Q. 다시 암호화하면 단점은요? → 서버도 인증서와 암호 처리 부담을 다시 지게 돼요. 규제·보안 요건과 성능을 저울질해요.
</details>

<details>
<summary>Q. 로드밸런서 자체가 단일 장애점(SPOF) 아닌가요?</summary>

**답변(30초)** 한 대만 두면 그래요. 클라우드 로드밸런서는 가용 영역마다 노드를 두고 DNS로 여러 IP를 돌려줘서 한 곳이 죽어도 나머지가 받아요. 직접 운영하는 환경에서는 보통 LB를 두 대 이상으로 이중화해서 한 대가 죽으면 다른 대가 이어받게 하는 방식이 일반적으로 알려져 있어요.
</details>

## 서술형 연습

<details>
<summary>상황: 서버 3대 중 한 대만 응답이 매우 느려졌는데, 로드밸런서는 그 서버로 계속 요청을 보내고 있습니다.</summary>

**상황 파악**
서버가 완전히 죽지 않고 "느린" 상태예요. 로드밸런서가 이 서버를 정상으로 보고 있어서, 라운드 로빈이라면 요청 3개 중 1개는 계속 느린 서버로 가요. 사용자 일부가 계속 느린 응답이나 타임아웃을 겪어요.

**원인 후보**
1. 헬스 체크가 없거나 수동 방식뿐이라, 요청이 "실패"하지 않고 느리기만 하면 알아채지 못해요.
2. 헬스 체크가 있지만 타임아웃이 너무 길거나, `/` 같은 가벼운 경로만 확인해서 느린 상태가 잡히지 않아요.
3. 알고리즘이 라운드 로빈이라 처리 중인 요청이 쌓인 서버에도 순서대로 보내요.
4. 서버 자체 문제(GC 멈춤, 스레드 풀 고갈, 특정 무거운 요청)도 따로 봐야 해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 능동 헬스 체크를 두고 타임아웃·임계값을 조정(예: ALB 기본은 5초 타임아웃, 연속 2번 실패 시 제외) | 느려서 응답을 못 하는 서버를 자동으로 빼요 | 너무 민감하면 잠깐 느린 서버도 자꾸 빠졌다 들어갔다 해요. 너무 둔하면 늦게 빠져요. nginx 오픈소스는 능동 헬스 체크가 상용 기능이라 별도 방법이 필요해요 |
| B. 알고리즘을 최소 연결(least_conn)이나 최소 처리 중 요청으로 변경 | 처리 중 요청이 쌓인 서버로는 덜 보내서 느린 서버가 자연스럽게 덜 받아요 | 서버를 빼 주지는 않아요. 또 아주 빠르게 에러를 내는 서버는 연결이 적어 보여 오히려 더 받을 수 있어요 |
| C. 수동 헬스 체크(`max_fails`/`fail_timeout`)에 프록시 타임아웃을 짧게 걸기 | 추가 검사 트래픽 없이 nginx 오픈소스로 가능 | 사용자 요청이 실제로 타임아웃 나야 빠져요 |

**내가 고를 방법**
A와 B를 같이 쓰겠어요. 능동 헬스 체크로 "응답을 못 하는" 서버는 빼고, 최소 연결로 "조금 느린" 서버에는 덜 보내요. 그와 별개로 느린 서버의 원인(GC, 스레드 풀, 특정 API)을 찾아요. 헬스 체크 엔드포인트가 DB까지 확인하게 만들면 DB 문제 때 서버가 다 같이 빠질 수 있으니, 무엇을 확인할지도 신중하게 정해요.

**채점 포인트**: 느림과 죽음의 구분, 능동/수동 헬스 체크 차이, 타임아웃·비정상 임계값 조정, 너무 민감한 설정의 부작용, 라운드 로빈 → 최소 연결, nginx 오픈소스 vs 상용 차이, 근본 원인 조사.
</details>

<details>
<summary>상황: 서버 로그와 IP 기반 레이트 리밋에 모든 요청이 로드밸런서 IP 하나로 찍힙니다. 그래서 한 사용자가 많이 보내면 모든 사용자가 같이 막힙니다.</summary>

**상황 파악**
서버가 TCP 접속 주소(`remote address`)를 클라이언트 IP로 쓰고 있어요. LB 뒤에서는 이 값이 LB의 IP라서 모든 사용자가 한 사람처럼 보여요.

**원인 후보**
1. LB는 X-Forwarded-For를 붙여 주는데 앱이 그 헤더를 안 읽어요(예: Spring Boot에서 forwarded 헤더 전략이 `none`).
2. 중간 nginx가 XFF를 넘기지 않거나 덮어써요.
3. 고쳤다고 XFF의 **가장 왼쪽 값**을 그냥 쓰면, 공격자가 헤더를 위조해 레이트 리밋을 우회해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 웹 서버·프록시 단에서 처리: nginx realip 모듈(`set_real_ip_from` + `real_ip_recursive on`), 또는 Spring Boot forwarded 전략(Boot 3.x `server.forward-headers-strategy`, Boot 4.2 `server.request.header.forwarded.strategy=web-server`) + Tomcat `internal-proxies`에 믿는 프록시만 등록 | 검증된 구현이 오른쪽부터 믿는 프록시를 건너뛰어 진짜 IP를 골라요. 앱 코드는 그냥 접속 주소를 쓰면 돼요 | 믿는 프록시 목록을 인프라 변경 때마다 맞춰 줘야 해요. 목록을 비워서 다 믿으면 위조가 그대로 통해요 |
| B. 앱 코드에서 XFF를 직접 파싱: 프록시가 N개로 고정이면 오른쪽에서 N번째 값을 사용 | 설정 없이 원하는 규칙을 바로 짤 수 있어요 | 프록시 구성이 바뀌면 조용히 틀려져요. 왼쪽 값을 쓰는 실수가 흔해요 |
| C. 서버를 인터넷에 직접 노출하지 않고 LB에서만 접근 가능하게 막기 | A·B의 전제를 지켜 줘요. 서버로 바로 와서 XFF를 위조하는 길이 막혀요 | 이것만으로는 IP를 못 구해요. A·B와 함께 써야 해요 |

**내가 고를 방법**
A와 C를 같이 쓰겠어요. 진짜 IP 고르기는 웹 서버나 프레임워크의 검증된 기능에 맡기고, 서버는 LB를 통해서만 들어오게 막아요. 로그 표시처럼 보안 영향이 없는 곳에서만 왼쪽 값을 참고하고, 레이트 리밋·IP 차단에는 믿는 프록시가 붙인 주소만 써요. Spring Boot는 버전에 따라 설정 이름이 다르니 쓰는 버전 문서를 확인해요.

**채점 포인트**: remote address = LB IP, X-Forwarded-For의 덧붙이는 순서, 클라이언트 위조 가능, 오른쪽부터 신뢰 프록시 건너뛰기, nginx realip / Spring Boot forwarded 설정, 신뢰 프록시 목록을 비우지 않기, 서버 직접 노출 차단, RFC 7239 Forwarded 언급.
</details>

<details>
<summary>상황: 배포할 때마다 일부 사용자가 502 Bad Gateway를 봅니다.</summary>

**상황 파악**
502는 로드밸런서(게이트웨이)가 뒤 서버에게서 제대로 된 응답을 못 받았다는 뜻이에요. 배포 때만 나니까, 서버가 내려가거나 올라오는 순간에 LB가 그 서버로 요청을 보낸 거예요.

**원인 후보**
1. 구 버전 서버를 LB에서 빼기 전에 바로 꺼서, 처리 중이던 요청과 이미 배정된 요청이 끊겨요(드레이닝 없음).
2. 앱이 SIGTERM을 받으면 처리 중인 요청을 마치지 않고 바로 죽어요(정상 종료 미처리).
3. 새 서버가 아직 준비가 안 됐는데 트래픽을 받아요. 헬스 체크가 너무 가벼워서 앱이 다 뜨기 전에 통과해요.
4. 쿠버네티스라면 엔드포인트 제거와 SIGTERM이 동시에 진행돼서, 종료 중인 파드로 잠깐 요청이 더 갈 수 있다고 일반적으로 알려져 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 커넥션 드레이닝: 등록 해제 → `draining`에서 처리 중 요청 마무리 → 그 다음 종료(AWS 기본 대기 300초) | 처리 중 요청이 끊기지 않아요 | 대기 시간이 길면 배포가 느려지고, 짧으면 긴 요청이 끊겨요. 서비스의 가장 긴 요청 시간에 맞춰 정해요 |
| B. 앱의 정상 종료 + 쿠버네티스 preStop: SIGTERM을 받으면 새 요청을 멈추고 처리 중 요청을 마친 뒤 종료, preStop에 짧은 대기를 둬서 엔드포인트 제거가 먼저 퍼지게 함 | LB 바깥 구간(파드 종료 순서)까지 막아요 | 유예 시간(기본 30초) 안에 끝나야 해요. 넘으면 SIGKILL로 강제 종료돼요. preStop 대기만큼 배포가 느려져요 |
| C. 준비된 다음에만 투입: 헬스 체크를 "실제로 요청을 받을 수 있나" 기준으로, 필요하면 slow start로 트래픽을 천천히 늘림 | 올라오는 쪽의 502·느림을 줄여요 | 헬스 체크 설계가 필요하고, 투입이 늦어져요 |

**내가 고를 방법**
A, B, C를 함께 쓰겠어요. 502는 내려가는 쪽과 올라오는 쪽 양쪽에서 생기기 때문에 하나만으로는 부족해요. 순서는 "새 서버 준비 확인 → 투입 → 구 서버 등록 해제 → 드레이닝 → 정상 종료"로 잡고, 드레이닝 시간과 쿠버네티스 유예 시간은 가장 긴 요청보다 길게 맞춰요. 롤링·블루그린 같은 배포 방식 자체는 아키텍처·배포 섹션에서 이어서 다뤄요.

**채점 포인트**: 502의 의미, 내려가는 쪽(드레이닝, 정상 종료, SIGTERM→SIGKILL 유예)과 올라오는 쪽(헬스 체크, slow start) 둘 다, 등록 해제 → 종료 순서, 대기 시간 트레이드오프, 엔드포인트 제거와 종료의 경쟁.
</details>
