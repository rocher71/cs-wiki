:::tip[한 줄 요약]
HTTP는 클라이언트가 **요청**을 보내면 서버가 **응답**하는 규약이고, 서버는 앞 요청을 기억하지 않아요(**무상태**). 메서드는 **안전**(서버를 안 바꿈)과 **멱등**(여러 번 보내도 결과가 한 번과 같음)으로 나뉘고, 상태 코드는 첫 자리(2xx 성공, 4xx 클라이언트 잘못, 5xx 서버 잘못)로 뜻이 갈려요.
:::

:::note[처음이라면 여기까지]
① HTTP는 클라이언트가 요청하면 서버가 응답하는 약속이에요. 서버는 앞 요청을 기억하지 않아요(무상태).

② 멱등은 "같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다"는 뜻이에요. GET·PUT·DELETE는 멱등이고 POST는 아니에요. 결제 POST를 두 번 보내면 두 번 처리될 수 있어요.

③ 상태 코드는 첫 자리로 뜻이 갈려요(2xx 성공, 4xx 클라이언트 잘못, 5xx 서버 잘못). 401은 "누구인지 모르겠어요(로그인 필요)", 403은 "누구인지는 알지만 권한이 없어요"예요.

④ 면접에선 질문 1·3·4번 먼저 연습하세요.
:::

## 쉽게 이해하기

HTTP는 **식당 주문서**와 비슷해요.

1. 손님(브라우저)이 주문서에 "**무엇을 할지**(메서드) + **어떤 메뉴**(경로) + **요청 사항**(헤더)"을 적어 내요.
2. 주방(서버)은 결과와 함께 **번호표**(상태 코드)를 붙여 돌려줘요. "200 나왔어요", "404 그런 메뉴 없어요", "500 주방에 불났어요" 같은 식이에요.
3. 이 식당 직원은 **손님 얼굴을 기억하지 않아요**(무상태). 그래서 단골이라는 걸 알리려면 매번 **회원 카드**(쿠키·토큰)를 같이 내야 해요.
4. 메뉴판을 매번 새로 받으면 낭비라서, 손님이 **사진을 찍어 두고**(캐시) 한동안은 그걸 봐요. 오래되면 "메뉴판 바뀌었어요?"라고 물어보고, 안 바뀌었다는 답(304)을 들으면 사진을 계속 써요.

단, 실제 서버는 얼굴을 기억 못 하는 게 약점이 아니라 장점이에요. 아무 직원(서버)이 받아도 같은 처리를 할 수 있어서 서버를 여러 대로 늘리기 쉬워요.

## 제대로 알기

### 1. 메시지 생김새

요청과 응답 모두 **시작줄 + 헤더 + 빈 줄 + 본문** 모양이에요.

```http
POST /orders HTTP/1.1
Host: shop.example
Content-Type: application/json
Content-Length: 27

{"productId": 1, "qty": 2}
```

```http
HTTP/1.1 201 Created
Location: /orders/42
Content-Length: 0
```

- **헤더**(header, 메시지에 붙는 부가 정보)는 `이름: 값` 한 줄씩이에요.
- `Host`는 HTTP/1.1 요청에 **반드시** 있어야 해요. IP 하나에 여러 도메인이 올라가 있을 때(가상 호스팅) 어느 사이트인지 구분하는 근거예요. 없으면 400이에요.
- `200 OK`의 "OK" 같은 **사유 문구**는 사람을 위한 글자일 뿐이라, 바꾸거나 빼도 동작에는 영향이 없어요. 프로그램은 숫자만 봐요.

### 2. 무상태(stateless)

**무상태**(stateless, 서버가 이전 요청을 기억하지 않음)란 요청 하나만 따로 떼어 봐도 뜻이 통해야 한다는 거예요. 같은 연결로 두 요청이 와도 서버는 "같은 사람이겠지"라고 가정하면 안 돼요.

- **왜 이렇게 만들었나**: 서버가 기억할 게 없으니 **로드밸런서**(요청을 여러 서버에 나눠 주는 장치)가 아무 서버에나 요청을 보내도 돼요. 프록시가 연결을 여러 사용자 요청에 재사용할 수도 있어요.
- **로그인은 어떻게 하나**: 프로토콜이 기억하지 않을 뿐이에요. 쿠키나 토큰을 **매 요청에 실어 보내서** 상태를 흉내 내요. → [쿠키·세션·JWT](../cookie-session-jwt/)

### 3. 메서드와 안전·멱등

먼저 두 단어부터요.

- **안전**(safe, 읽기 전용): 클라이언트가 서버 상태를 바꿔 달라고 요청하지 않는 메서드예요. 서버가 접근 로그를 남기는 정도의 부수효과는 있어도 돼요. 그건 클라이언트가 요청한 게 아니니까요.
- **멱등**(idempotent, 여러 번 해도 한 번 한 것과 같음): 같은 요청을 여러 번 보내도 서버에 **의도된 효과**가 한 번 보낸 것과 같은 메서드예요. **응답까지 같다는 뜻은 아니에요.** DELETE를 두 번 하면 두 번째는 404가 올 수 있지만 "그 리소스가 없다"는 결과는 같아요.

| 메서드 | 하는 일 | 안전 | 멱등 |
|---|---|---|---|
| GET | 조회 | O | O |
| HEAD | GET에서 본문 빼고 헤더만 | O | O |
| OPTIONS | 지원하는 기능 묻기 | O | O |
| TRACE | 받은 요청 되돌려 보기(진단용) | O | O |
| PUT | 통째로 교체(없으면 생성) | X | O |
| DELETE | 삭제 | X | O |
| POST | 서버가 알아서 처리(생성·폼 제출 등) | X | X |
| PATCH | 일부만 바꾸는 변경 지시 | X | X |
| CONNECT | 터널 열기(프록시용) | X | X |

**왜 이걸 나누나**

- **안전**은 자동화를 위해서예요. 검색 크롤러나 링크 미리보기는 GET 링크를 마구 따라가요. GET으로 삭제가 되게 만들면(`/post?do=delete`) 크롤러가 데이터를 지울 수 있어요. 이건 서버를 그렇게 만든 쪽 책임이에요.
- **멱등**은 재시도를 위해서예요. 응답을 받기 전에 연결이 끊기면, 요청이 처리됐는지 모르는 상태가 돼요. 멱등이면 그냥 다시 보내도 돼요. 멱등이 아닌 요청은 클라이언트가 **자동으로** 재시도하지 않는 게 원칙이고, 프록시는 절대 하면 안 돼요.

**자주 비교하는 쌍**

- **PUT vs POST**: "PUT은 수정, POST는 생성"은 반만 맞아요. PUT도 리소스가 없으면 만들어요(201). 진짜 차이는 **URI를 누가 정하나**예요. PUT은 클라이언트가 `/users/42`처럼 위치를 정해서 그 자리를 통째로 채우고, POST는 `/orders`에 보내면 서버가 `/orders/42`를 정해서 `Location` 헤더로 알려 줘요.
- **PUT vs PATCH**: PUT은 **전체 교체**라 멱등이에요. PATCH는 "이 필드를 이렇게 바꿔라" 같은 **변경 지시**를 보내고, 규격(RFC 5789)상 멱등이 아니에요. "재고 1 줄여라" 같은 지시는 두 번 보내면 두 번 줄죠. 멱등하게 설계할 수는 있어요.
- **GET 본문**: GET에 본문을 넣으면 정해진 의미가 없고, 일부 서버는 보안상 거부하고 연결을 끊어요. 조회 조건은 쿼리 문자열로 보내요.
- 서버가 메서드 자체를 모르면 **501**, 알지만 그 리소스에서 허용하지 않으면 **405**예요. 범용 서버가 반드시 지원해야 하는 건 GET과 HEAD 둘이에요.

### 4. 상태 코드

첫 자리만 봐도 누구 탓인지 알 수 있어요.

| 클래스 | 뜻 | 한마디 |
|---|---|---|
| 1xx | 정보 | 아직 처리 중이에요 |
| 2xx | 성공 | 됐어요 |
| 3xx | 리다이렉션 | 다른 데 보세요 |
| 4xx | 클라이언트 오류 | 요청이 잘못됐어요 |
| 5xx | 서버 오류 | 서버가 잘못했어요 |

**자주 쓰는 코드**

| 코드 | 이름 | 언제 |
|---|---|---|
| 200 | OK | 성공 |
| 201 | Created | 새로 만들었음. `Location`에 새 주소 |
| 204 | No Content | 성공했는데 돌려줄 본문 없음 |
| 301 | Moved Permanently | 영구 이동 |
| 302 | Found | 임시 이동 |
| 303 | See Other | POST 처리 후 결과 페이지는 GET으로 보라고 안내 |
| 304 | Not Modified | 갖고 있는 사본 그대로 쓰세요 |
| 307 | Temporary Redirect | 임시 이동, 메서드 유지 |
| 308 | Permanent Redirect | 영구 이동, 메서드 유지 |
| 400 | Bad Request | 문법·형식이 틀림 |
| 401 | Unauthorized | 인증 안 됨(누군지 모름) |
| 403 | Forbidden | 누군지 알지만 권한 없음 |
| 404 | Not Found | 없음(또는 있다고 밝히기 싫음) |
| 405 | Method Not Allowed | 이 리소스엔 그 메서드 안 됨. `Allow` 필수 |
| 409 | Conflict | 현재 상태와 충돌(버전 충돌 등) |
| 412 | Precondition Failed | `If-Match` 같은 조건이 틀림 |
| 415 | Unsupported Media Type | 본문 형식(Content-Type)을 지원 안 함 |
| 422 | Unprocessable Content | 형식·문법은 맞는데 내용이 말이 안 됨 |
| 429 | Too Many Requests | 너무 자주 보냄(요청 수 제한) |
| 500 | Internal Server Error | 서버 내부 예외 |
| 502 | Bad Gateway | 중간 서버가 뒤 서버에게 **잘못된 응답**을 받음(실무에선 뒤 서버 연결 실패도 흔히 502) |
| 503 | Service Unavailable | 과부하·점검으로 잠시 못 받음 |
| 504 | Gateway Timeout | 중간 서버가 뒤 서버 응답을 **제때 못 받음** |

**리다이렉트 4종은 2x2로 외워요**

|  | 메서드가 바뀔 수 있음 | 메서드 유지 |
|---|---|---|
| 영구 | 301 | 308 |
| 임시 | 302 | 307 |

301·302는 역사적인 이유로 브라우저가 POST를 GET으로 바꿔 다시 보내도 돼요. 그게 싫으면 308·307을 써요.

**헷갈리는 쌍**

- **401 vs 403**: 401은 이름과 달리 "**인증**(authentication, 누구인지 확인) 안 됨"이에요. 401을 보낼 땐 어떻게 인증하면 되는지 `WWW-Authenticate` 헤더로 반드시 알려야 해요. 403은 "**인가**(authorization, 무엇을 해도 되는지 허락) 실패"예요. 같은 자격 증명으로 다시 보내도 소용없어요. 리소스가 있다는 것 자체를 숨기고 싶으면 403 대신 404를 보내도 돼요.
- **400 vs 415 vs 422**: JSON 문법이 깨졌으면 400, 서버가 JSON을 아예 안 받는데 XML을 보냈으면 415, 문법은 맞는데 "수량이 -3" 같은 내용 문제면 422예요. 422는 원래 WebDAV용 코드였는데 RFC 9110부터 HTTP 공통 코드가 됐어요.
- **502 vs 504**: 둘 다 **게이트웨이**(앞에서 요청을 받아 뒤 서버로 넘기는 중간 서버, 예: Nginx, 로드밸런서) 입장의 오류예요. 502는 뒤 서버가 이상한 응답을 준 것(실무에선 뒤 서버에 연결이 안 되거나 끊겨도 502를 많이 내요), 504는 기다렸는데 답이 안 온 것이에요.
- **429**는 RFC 9110이 아니라 RFC 6585에 있어요. `Retry-After`로 얼마 뒤에 다시 오라고 알려 줄 수 있어요.

### 5. 자주 보는 헤더

| 헤더 | 방향 | 역할 |
|---|---|---|
| Host | 요청 | 어느 도메인인지. HTTP/1.1 필수 |
| Content-Type | 양쪽 | 본문 형식(`application/json` 등) |
| Content-Length | 양쪽 | 본문 길이(바이트) |
| Accept | 요청 | 받고 싶은 형식 |
| Authorization | 요청 | 자격 증명(토큰 등) |
| WWW-Authenticate | 응답 | 401일 때 인증 방법 안내 |
| Location | 응답 | 201·3xx에서 새 주소 |
| Allow | 응답 | 405일 때 허용 메서드 목록 |
| Retry-After | 응답 | 503·429에서 기다릴 시간 |
| Cache-Control | 양쪽 | 캐시 규칙 |
| ETag / Last-Modified | 응답 | 버전 표시(검증자) |
| If-None-Match / If-Modified-Since | 요청 | "바뀌었으면 주세요" |
| Vary | 응답 | 어떤 요청 헤더에 따라 응답이 달라지는지 캐시에 알림 |

### 심화: 6. 캐시: 신선도와 검증

캐시는 두 단계로 생각하면 쉬워요.

1. **신선한가?** 응답의 나이가 `max-age`(초)보다 작으면 **신선**해요. 서버에 묻지 않고 바로 써요.
2. **낡았으면 확인** 받기. 버리지 않고 "이 버전 아직 맞아요?"라고 묻는 걸 **검증**(validation)이라고 해요. 이때 쓰는 게 **ETag**(엔티티 태그, 리소스 버전에 붙인 이름표)예요.

검증 흐름은 이래요. 브라우저가 `If-None-Match: "v1"`을 붙여 보내요. 서버의 현재 ETag도 `"v1"`이면 **304**를 본문 없이 보내요. 브라우저는 갖고 있던 사본을 다시 신선한 걸로 갱신해서 써요. 바뀌었으면 200과 새 본문, 새 ETag가 와요.

- ETag와 Last-Modified(마지막 수정 시각)가 둘 다 있으면 ETag 쪽(`If-None-Match`)이 이겨요. 시각보다 정확하기 때문이에요.
- `W/"..."`처럼 생긴 건 **약한 ETag**예요. 의미가 같으면 바이트가 조금 달라도 같은 버전으로 봐요. 앞에 `W/`가 없는 **강한 ETag**는 본문이 1바이트라도 바뀌면 값이 바뀌어요.
- `If-None-Match`는 **약한 비교**를 해요. `W/`가 붙었는지는 무시하고 따옴표 안 값만 같으면 일치로 봐서 304를 줘요.
- 신선도 기준이 여러 개면 순서는 `s-maxage`(공유 캐시만) → `max-age` → `Expires` → (없으면 서버가 추정)이에요.

**Cache-Control 지시어**

| 지시어 | 진짜 뜻 |
|---|---|
| max-age=N | N초 동안은 신선 |
| no-cache | 저장은 해도 됨. 쓰기 **전에 매번 검증** |
| no-store | 아예 **저장 금지** |
| private | 브라우저에만 저장. CDN·프록시 같은 **공유 캐시**는 저장 금지 |
| public | 원래 저장이 안 될 응답(인증 붙은 요청 등)도 공유 캐시가 저장 가능 |
| s-maxage=N | 공유 캐시에만 적용되는 max-age |
| must-revalidate | 낡은 뒤엔 검증 없이 쓰지 마. 서버가 안 닿으면 옛 응답 대신 오류 |

<Aside type="caution" title="자주 틀리는 캐시 상식">
- **no-cache는 "캐시하지 마"가 아니에요.** 저장하고 매번 확인하는 거예요. 저장 금지는 no-store예요.
- **private는 보안 기능이 아니에요.** 저장 위치만 제한할 뿐 암호화가 아니에요. RFC도 no-store조차 개인정보 보호 수단으로 충분하지 않다고 경고해요(규칙을 무시하는 캐시가 있을 수 있어서요).
- **304는 리다이렉트가 아니에요.** 3xx지만 다른 곳으로 보내는 게 아니라 "갖고 있는 거 쓰세요"예요.
</Aside>

<Aside type="tip" title="직접 해 보기">
`curl -sI https://www.rfc-editor.org/rfc/rfc9110.txt`로 헤더를 보면 `cache-control`과 `etag`가 보여요. 그 etag 값을 복사해서 `curl -sI -H 'If-None-Match: 복사한값' 같은주소`로 다시 보내면 304가 와요. ETag 값은 바뀔 수 있으니 꼭 첫 응답에서 복사해요.
</Aside>

### 심화: 7. 지속 연결(Keep-Alive)

요청마다 TCP 연결을 새로 맺으면 매번 핸드셰이크 왕복이 들어요. 그래서 **지속 연결**(persistent connection, 연결 하나로 요청·응답을 여러 번)을 써요.

- **HTTP/1.1은 기본이 지속 연결**이에요. 따로 켤 필요가 없고, 끊고 싶은 쪽이 `Connection: close`를 보내요.
- **HTTP/1.0은 기본이 끊기**라서, `Connection: keep-alive`를 보냈을 때만 유지해요. "Keep-Alive 헤더를 보내야 유지된다"는 건 1.0 시절 이야기예요.
- 한 연결에 메시지를 이어 보내려면 각 메시지가 어디서 끝나는지 알아야 해요. 그래서 `Content-Length`나 chunked 방식으로 길이를 알려 줘요.
- 응답을 안 기다리고 요청을 연달아 보내는 **파이프라이닝**도 있지만, 서버는 받은 순서대로 응답해야 해요. 앞 응답이 느리면 뒤가 다 막혀요(**HOL 블로킹**, 줄 맨 앞이 막혀 전체가 멈춤). 이 문제를 HTTP/2가 풀어요. → [HTTP 버전](../http-versions/)

## 면접 질문

<details>
<summary>Q. GET과 POST의 차이가 뭔가요?</summary>

**답변(30초)** 가장 큰 차이는 안전성과 멱등성이에요. GET은 조회용이라 서버 상태를 바꾸지 않는 안전한 메서드이고, 여러 번 보내도 결과가 같은 멱등 메서드예요. POST는 서버가 본문을 자기 방식대로 처리하는 메서드라 둘 다 아니에요. 그래서 GET은 캐시되고 자동 재시도해도 되지만, POST는 보통 캐시되지 않고 함부로 재시도하면 중복 처리될 수 있어요. 데이터도 GET은 쿼리 문자열, POST는 본문에 실어요.

**꼬리질문**
- Q. GET에 본문을 넣으면요? → 정해진 의미가 없고, 일부 서버는 보안상 거부하고 연결을 끊어요. 넣지 않는 게 원칙이에요.
- Q. GET으로 삭제 API를 만들면 왜 위험해요? → 크롤러나 링크 미리보기가 GET 링크를 자동으로 따라가서 데이터를 지울 수 있어요.
</details>

<details>
<summary>Q. HTTP가 무상태라는 건 무슨 뜻이고, 장점은요?</summary>

**답변(30초)** 서버가 이전 요청을 기억하지 않아서 요청 하나만 봐도 처리할 수 있어야 한다는 뜻이에요. 장점은 확장성이에요. 어느 서버가 요청을 받아도 같은 결과를 낼 수 있으니 로드밸런서가 아무 서버에나 나눠 줘도 되고, 서버를 늘리기 쉬워요. 로그인 같은 상태는 쿠키나 토큰을 매 요청에 실어 보내서 해결해요.

**꼬리질문**
- Q. 세션을 쓰면 무상태가 깨지지 않나요? → 프로토콜은 여전히 무상태고, 서버 애플리케이션이 상태를 가진 거예요. 서버가 여러 대면 세션을 Redis 같은 공용 저장소에 둬야 해요. → [쿠키·세션·JWT](../cookie-session-jwt/)
</details>

<details>
<summary>Q. 멱등성이 뭐고, 왜 중요한가요?</summary>

**답변(30초)** 같은 요청을 여러 번 보내도 서버에 남는 효과가 한 번 보낸 것과 같은 성질이에요. GET, HEAD, PUT, DELETE 등이 멱등이고 POST와 PATCH는 아니에요. 중요한 이유는 재시도 때문이에요. 응답 전에 연결이 끊기면 처리됐는지 알 수 없는데, 멱등이면 그냥 다시 보내도 안전해요. 그래서 클라이언트와 프록시는 멱등 요청만 자동 재시도해요.

**꼬리질문**
- Q. DELETE를 두 번 하면 두 번째는 404인데 멱등인가요? → 네. 멱등은 응답이 아니라 서버 상태에 대한 효과가 같다는 뜻이에요. 두 번 다 "그 리소스는 없다"로 끝나요.
- Q. 안전하면 멱등이고, 멱등이면 안전한가요? → 앞은 맞고 뒤는 틀려요. PUT, DELETE는 멱등이지만 서버를 바꾸니 안전하지 않아요.
- Q. PUT과 PATCH 차이는요? → PUT은 리소스를 통째로 교체해서 멱등이고, PATCH는 부분 변경 지시라 규격상 멱등이 아니에요.
</details>

<details>
<summary>Q. 401과 403의 차이는요?</summary>

**답변(30초)** 401은 인증 실패, 403은 인가 실패예요. 401은 이름이 Unauthorized지만 실제 뜻은 "누구인지 모르겠다"라서, 토큰이 없거나 만료됐을 때 보내요. 이때 어떻게 인증할지 `WWW-Authenticate` 헤더로 알려 줘야 해요. 403은 누구인지는 알지만 그 일을 할 권한이 없을 때 보내요. 다시 로그인해도 안 되니 클라이언트가 같은 자격 증명으로 재시도하면 안 돼요.

**꼬리질문**
- Q. 남의 주문 내역을 조회하면 403인가요? → 403도 맞지만, 주문이 있다는 사실 자체를 숨기려고 404를 보내는 것도 허용돼요.
- Q. 프론트엔드는 둘을 어떻게 다르게 처리해요? → 401이면 토큰 갱신이나 로그인 화면으로 보내고, 403이면 "권한이 없어요" 안내를 보여요.
</details>

<details>
<summary>Q. 301, 302, 307, 308은 어떻게 달라요?</summary>

**답변(30초)** 영구냐 임시냐, 메서드를 유지하냐로 나뉘어요. 301과 308은 영구 이동, 302와 307은 임시 이동이에요. 301과 302는 브라우저가 POST를 GET으로 바꿔 다시 보내도 되고, 307과 308은 메서드를 바꾸면 안 돼요. 그래서 POST 요청을 그대로 다른 주소로 넘기려면 307이나 308을 써요.

**꼬리질문**
- Q. 캐시 관점에서 차이는요? → 301과 308은 별도 캐시 지시가 없어도 캐시될 수 있는 코드고, 302와 307은 아니에요. 그래서 301을 잘못 걸면 되돌리기 어려워요.
- Q. 303은 언제 써요? → 폼 POST를 처리한 뒤 결과 페이지를 GET으로 보라고 안내할 때요. 새로고침으로 POST가 다시 나가는 걸 막아요.
</details>

<details>
<summary>Q. 502, 503, 504는 어떻게 구분해요?</summary>

**답변(30초)** 502와 504는 중간 서버(게이트웨이) 입장의 오류이고, 503은 서버가 스스로 못 받는다고 하는 거예요. 502는 뒤 서버가 잘못된 응답을 줬거나 연결이 끊겼을 때, 504는 뒤 서버가 제한 시간 안에 응답하지 않았을 때예요. 503은 과부하나 점검으로 지금은 못 받지만 곧 풀릴 상황이고, `Retry-After`로 언제 다시 오라고 알려 줄 수 있어요.

**꼬리질문**
- Q. 504가 갑자기 늘면 뭘 봐요? → 뒤 서버가 느려진 거라 DB 느린 쿼리, 외부 API 지연, 게이트웨이와 서버의 타임아웃 설정을 봐요.
</details>

<details>
<summary>Q. Keep-Alive(지속 연결)가 뭔가요?</summary>

**답변(30초)** TCP 연결 하나로 여러 요청과 응답을 주고받는 거예요. 요청마다 연결을 새로 맺으면 핸드셰이크 왕복이 계속 들어서 느려요. HTTP/1.0은 기본이 요청마다 끊기라 keep-alive를 따로 요청해야 했고, HTTP/1.1부터는 기본이 유지예요. 끊고 싶을 때 `Connection: close`를 보내요.

**꼬리질문**
- Q. 지속 연결이면 HTTP/1.1은 충분히 빠른가요? → 한 연결에서 응답을 순서대로 줘야 해서 앞이 느리면 뒤가 막혀요(HOL 블로킹). HTTP/2가 한 연결에 여러 요청을 섞어 보내서 풀어요. → [HTTP 버전](../http-versions/)
</details>

<details>
<summary>Q. Cache-Control의 no-cache와 no-store는 어떻게 달라요?</summary>

**답변(30초)** no-cache는 저장은 해도 되지만 쓰기 전에 매번 서버에 검증을 받으라는 뜻이고, no-store는 아예 저장하지 말라는 뜻이에요. no-cache는 ETag로 확인해서 안 바뀌었으면 304로 본문 없이 끝나니 전송량이 줄어요. no-store는 매번 전체를 받아요. 그래서 자주 바뀌지만 재사용 가치가 있는 HTML엔 no-cache, 민감한 응답엔 no-store를 써요.

**꼬리질문**
- Q. ETag는 어떻게 동작해요? → 서버가 응답에 버전 이름표를 붙이고, 브라우저가 다음에 `If-None-Match`로 그 값을 보내요. 같으면 304, 다르면 200과 새 본문이에요.
- Q. max-age와 Expires가 같이 있으면요? → max-age가 우선이에요.
- Q. private과 public은요? → private은 브라우저에만 저장하고 CDN 같은 공유 캐시는 저장 금지예요. 로그인 사용자 화면에 써요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제 버튼을 누른 뒤 응답 전에 네트워크가 끊겼고, 앱이 자동으로 다시 보내서 이중 결제가 났습니다. 어떻게 막겠습니까?</summary>

**상황 파악**
결제 요청은 POST예요. POST는 멱등이 아니라서 같은 요청이 두 번 도착하면 두 번 처리돼요. 첫 요청은 서버에서 성공했는데 응답만 못 받은 상황이고, 클라이언트는 그걸 구분할 수 없어서 재시도했어요.

**원인 후보**
1. 앱(또는 HTTP 라이브러리, 중간 프록시 설정)이 비멱등 요청을 자동 재시도해요.
2. 서버가 "같은 결제 요청"을 알아볼 방법이 없어요.
3. 사용자가 버튼을 두 번 눌러도 같은 문제가 생겨요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 멱등 키: 클라이언트가 결제 시도마다 고유 키를 만들어 `Idempotency-Key` 헤더로 보내고, 서버는 키별 결과를 저장해서 같은 키가 오면 저장된 결과를 돌려줌 | POST를 유지하면서 재시도를 안전하게 만듦. 결제 API에서 흔히 쓰는 방식 | 키 저장소(DB 유니크 제약이나 Redis)와 만료 기간 관리가 필요. 첫 요청이 아직 처리 중일 때 같은 키가 오면 어떻게 할지, 같은 키에 다른 본문이 오면 거부할지 정책도 정해야 함 |
| B. 결제 ID를 클라이언트가 정해서 `PUT /payments/{id}`로 설계 | PUT 자체가 멱등이라 규약만으로 재시도가 안전 | 클라이언트가 충돌 없는 ID를 만들어야 하고, "결제 생성"을 PUT으로 표현하는 게 API 설계상 어색할 수 있음 |
| C. 자동 재시도를 끄고 상태 조회 API로 확인 | 구현이 단순 | 끊길 때마다 사용자가 기다리거나 다시 시도해야 해서 경험이 나쁘고, 버튼 연타는 못 막음 |

**내가 고를 방법**
A를 고르겠어요. 결제는 돈이 걸려 있어서 재시도는 필요하고, 중복은 절대 안 되기 때문이에요. 서버는 키에 유니크 제약을 걸어 동시에 두 요청이 와도 하나만 처리되게 하고, 키는 재시도가 일어날 만한 기간만 보관해요(예: 24시간처럼 서비스가 정해요). 버튼 연타는 화면에서 버튼을 잠시 막는 걸로 보조해요.

참고로 `Idempotency-Key`는 IETF에서 표준화를 논의 중인 헤더예요. 아직 확정된 표준이라고 말하기보다는 "널리 쓰이는 관례"라고 설명하는 게 안전해요.

**채점 포인트**: POST 비멱등, 응답 유실 시 처리 여부를 모름, 멱등 키 + 서버 저장, 유니크 제약으로 동시 요청 방어, 키 만료 기간, 같은 키 다른 본문 정책, PUT 대안, 버튼 중복 클릭 보조.
</details>

<details>
<summary>상황: 관리자 API에서 토큰이 없을 때, 토큰은 있지만 일반 사용자일 때 각각 어떤 상태 코드를 줘야 할지 팀에서 의견이 갈립니다.</summary>

**상황 파악**
두 경우는 실패 단계가 달라요. 토큰이 없거나 만료된 건 "누구인지 모름"(인증 실패)이고, 일반 사용자 토큰은 "누구인지 알지만 관리자 권한이 없음"(인가 실패)이에요. 코드를 섞어 쓰면 클라이언트가 다음 행동을 잘못 골라요. 예를 들어 403인데 로그인 화면으로 보내면 다시 로그인해도 계속 실패해요.

**원인 후보**
1. 401의 이름(Unauthorized)이 "권한 없음"처럼 읽혀서 헷갈려요.
2. 스프링 시큐리티 같은 프레임워크의 기본 응답을 그대로 쓰고 기준을 정한 적이 없어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 규격대로: 토큰 없음·무효 → 401 + `WWW-Authenticate`, 권한 부족 → 403 | 클라이언트가 "로그인/토큰 갱신"과 "권한 없음 안내"를 명확히 나눌 수 있음 | 관리자 API가 있다는 사실이 403으로 드러남 |
| B. 권한 부족도 404로 응답 | 관리자 기능의 존재 자체를 숨김(규격상 허용) | 정상 사용자도 "없음"으로 보여 디버깅이 어렵고, 클라이언트 처리 기준이 흐려짐 |

**내가 고를 방법**
기본은 A로 하겠어요. 클라이언트 동작이 코드만 보고 정해져서 실수가 줄어요. 다만 다른 사용자의 개별 리소스(예: 남의 주문)처럼 존재 여부가 정보가 되는 경우에만 B처럼 404를 써요. 이 기준을 API 문서에 적어 두고, 프레임워크의 인증 실패·인가 실패 처리기를 각각 설정해서 코드가 섞이지 않게 해요.

**채점 포인트**: 401=인증, 403=인가, 401에 WWW-Authenticate 필수, 403은 같은 자격 증명으로 재시도 무의미, 404로 존재 숨기기 허용, 클라이언트 처리 분기(토큰 갱신 vs 권한 안내).
</details>

<details>
<summary>상황: 새 버전을 배포했는데 일부 사용자 화면이 계속 옛날 모습입니다.</summary>

**상황 파악**
서버에는 새 파일이 있는데 사용자 쪽에선 옛 파일을 쓰고 있어요. 서버에 묻지도 않고 저장본을 쓰고 있다는 뜻이라, HTTP 캐시가 원인일 가능성이 커요.

**원인 후보**
1. `app.js`, `style.css` 같은 파일에 긴 `max-age`가 걸려 있어서, 만료 전까지 브라우저가 서버에 확인하지 않아요.
2. HTML 자체도 캐시돼서 새 파일을 가리키는 HTML을 못 받아요.
3. CDN(공유 캐시)에 옛 파일이 남아 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 정적 파일 이름에 내용 해시를 넣고(`app.3f2a.js`) 긴 `max-age` + `immutable`(신선한 동안은 새로고침해도 다시 묻지 말라는 표시), HTML은 `no-cache` | 내용이 바뀌면 이름이 바뀌어 무조건 새 파일을 받음. 안 바뀐 파일은 캐시를 끝까지 활용 | 빌드 도구 설정이 필요. HTML은 매번 검증 요청이 나감(대부분 304라 가볍긴 함) |
| B. 모든 파일의 `max-age`를 짧게 줄이기 | 설정이 간단 | 재방문마다 요청이 늘어 느려지고 서버·CDN 부하 증가. 짧아도 그 시간만큼은 여전히 옛 화면 |

**내가 고를 방법**
A를 고르겠어요. "안 바뀌는 건 오래, 바뀌는 건 즉시"를 둘 다 얻어요. HTML은 `no-cache`라 매번 ETag로 확인하고, 그 HTML이 새 해시 파일 이름을 가리키니 배포 즉시 반영돼요. 이미 퍼진 옛 파일 문제는 CDN 캐시 무효화(purge)로 한 번 정리해요.

**채점 포인트**: max-age 동안 서버에 묻지 않음, no-cache는 저장+매번 검증(캐시 금지 아님), ETag/304, 파일명 해시(캐시 버스팅), HTML과 정적 파일 정책 분리, CDN 무효화.
</details>

## 필기 포인트

- 안전 메서드 4개: **GET, HEAD, OPTIONS, TRACE**. 멱등은 여기에 **PUT, DELETE** 추가. **POST, PATCH, CONNECT**는 둘 다 아님.
- 모든 안전 메서드는 멱등이지만, 모든 멱등 메서드가 안전하진 않음(PUT, DELETE).
- 범용 서버 필수 메서드: GET, HEAD. 메서드를 모르면 501, 알지만 불허면 405.
- 필수 헤더 짝: 405 → `Allow`, 401 → `WWW-Authenticate`, 201·3xx → `Location`. HTTP/1.1 요청 → `Host`(없으면 400).
- 302는 POST→GET 변경 허용, 307은 금지. 301 ↔ 308도 같은 관계.
- 304는 GET/HEAD 조건부 요청에서만. 다른 메서드에서 `If-None-Match` 조건이 틀리면 412.
- `If-None-Match`가 있으면 `If-Modified-Since`는 무시.
- 신선도 우선순위: s-maxage(공유 캐시) > max-age > Expires.
- PATCH는 RFC 5789, 429는 RFC 6585에 정의(RFC 9110 아님).
- HTTP/1.1은 기본 지속 연결, HTTP/1.0은 기본 비지속.
