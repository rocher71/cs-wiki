:::tip[한 줄 요약]
**동일 출처 정책**은 브라우저가 다른 출처(scheme·host·port 중 하나라도 다른 곳)의 응답을 JS가 읽지 못하게 막는 규칙이고, **CORS**는 서버가 `Access-Control-Allow-Origin` 같은 응답 헤더로 "이 출처는 읽어도 된다"고 허락해 그 예외를 만드는 방법이에요. 검사는 브라우저가 하고, 해결은 서버 응답 헤더에서 해요.
:::

:::note[처음이라면 여기까지]
① 출처(origin)는 주소 앞부분인 프로토콜(https 등)·도메인·포트 묶음이에요. 셋 중 하나라도 다르면 다른 출처예요.

② 브라우저는 다른 출처에서 온 응답을 JS가 읽지 못하게 막아요. 이게 동일 출처 정책이에요.

③ CORS 에러는 서버가 응답 헤더로 "이 출처는 읽어도 돼요"라고 허락해야 풀려요. 프론트가 아니라 서버에서 고쳐요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

아파트 **경비실**을 떠올려 보세요.

1. 101동 주민(프론트 페이지의 JS)이 102동(다른 출처의 API)에 택배를 **보내는 것**은 자유예요. 경비실도 막지 않아요.
2. 그런데 102동에서 온 **답장을 뜯어 보는 것**은 경비실(브라우저)이 막아요. 102동이 "101동 사람은 읽어도 돼요"라는 **허가 도장**(CORS 응답 헤더)을 찍어 보냈을 때만 건네줘요.
3. 이사짐처럼 큰 짐(PUT, JSON 본문, 인증 헤더가 붙은 요청)은 경비실이 먼저 102동에 **전화로 물어봐요**(preflight). "이런 짐 보내도 되나요?" 허락이 안 나면 짐 자체를 안 보내요.
4. 경비실은 아파트(브라우저) 안에만 있어요. 바깥 택배 기사(curl, Postman, 다른 서버)는 경비실을 거치지 않으니 아무 검사도 안 받아요.

단, 실제로는 "보내는 건 자유"라는 점이 중요해요. 단순한 요청은 서버에 그대로 도착해서 **처리까지 끝나요.** 브라우저는 결과를 JS에 안 넘길 뿐이에요. 그래서 CORS는 "남이 우리 서버에 요청을 보내는 것"을 막는 보안 장치가 아니에요.

## 제대로 알기

### 1. 출처(origin)란

**출처**(origin, 웹 주소의 "어디서 왔나"를 나타내는 묶음)는 **scheme + host + port** 세 가지예요. 셋이 모두 같아야 같은 출처예요. 경로(`/dir/page.html`)는 상관없어요.

`http://store.company.com/dir/page.html` 기준:

| 비교 대상 | 같은 출처? | 이유 |
|---|---|---|
| `http://store.company.com/other/x.html` | O | 경로만 다름 |
| `https://store.company.com/` | X | scheme 다름 |
| `http://store.company.com:81/` | X | 포트 다름(http 기본은 80) |
| `http://news.company.com/` | X | host 다름 |

- 포트를 안 쓰면 scheme의 기본 포트(http 80, https 443)로 봐요.
- `localhost:3000`과 `localhost:8080`은 포트가 달라 **다른 출처**예요. `localhost`와 `127.0.0.1`도 host 글자가 달라 다른 출처예요.

### 2. 동일 출처 정책(SOP)이 막는 것과 안 막는 것

**동일 출처 정책**(Same-Origin Policy, SOP)은 브라우저가 다른 출처와의 상호작용을 제한하는 규칙이에요. 다만 전부 막지는 않아요.

| 종류 | 예 | 다른 출처일 때 |
|---|---|---|
| 쓰기 | 링크 이동, 리다이렉트, 폼 제출 | 대체로 허용 |
| 임베드 | `<script src>`, `<img>`, `<link rel=stylesheet>`, `<iframe>` | 대체로 허용 |
| 읽기 | JS로 다른 출처 응답 내용 읽기(fetch, XHR) | 기본 차단 |

- 왜 필요할까요? 이 규칙이 없으면 내가 들어간 아무 사이트의 JS가, 로그인해 둔 은행 사이트에 요청을 보내고 **그 응답(내 계좌 정보)을 읽어 갈 수** 있어요.
- 쿠키는 SOP와 규칙이 달라요. 도메인 단위로 붙고 포트·scheme으로 나뉘지 않아요.
- `Origin` 요청 헤더는 요청을 일으킨 출처를 알려 줘요. 개인정보에 민감한 상황에서는 브라우저가 `null`을 보내기도 해요.

### 3. CORS는 SOP의 예외를 여는 방법

**CORS**(Cross-Origin Resource Sharing, 교차 출처 자원 공유)는 서버가 응답 헤더로 "이 출처는 내 응답을 읽어도 된다"고 브라우저에 알리는 규약이에요. WHATWG Fetch Standard가 정해요.

- 다른 출처 요청이 실패하면 JS는 "실패했다"(TypeError)는 것만 알고 **이유는 몰라요.** 이유는 브라우저 개발자 도구 콘솔에만 나와요. 보안상 일부러 숨긴 거예요.
- 그래서 "CORS 에러"가 보이면 프론트 코드보다 **서버 응답 헤더**를 먼저 봐야 해요.

### 4. 단순 요청 vs preflight

브라우저는 요청 모양을 보고 바로 보낼지, 먼저 물어볼지 정해요. 아래를 **모두** 만족하면 **단순 요청**(simple request, 허락 확인 없이 바로 보내는 요청)이에요.

| 조건 | 허용 값 |
|---|---|
| 메서드 | GET, HEAD, POST |
| 직접 넣은 헤더 | `Accept`, `Accept-Language`, `Content-Language`, `Content-Type`, `Range`(단일 범위)만 |
| Content-Type | `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`만 |

- 그래서 **`application/json` POST는 preflight가 붙어요.** 흔한 오해예요.
- `Authorization` 헤더는 목록에 없어요. **JWT를 헤더로 보내는 API 호출은 전부 preflight**가 붙어요.
- 허용 헤더라도 값이 128바이트를 넘는 등 너무 길면 단순 요청에서 빠져요.

조건을 하나라도 벗어나면 브라우저가 실제 요청 전에 **preflight**(사전 확인, `OPTIONS` 메서드로 먼저 묻는 요청)를 보내요.

```http
OPTIONS /orders/1 HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization
```

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 600
```

- preflight가 실패하면 **실제 요청은 아예 안 나가요.**
- preflight에는 **쿠키 같은 자격 증명이 절대 실리지 않아요.** 이게 뒤에 나올 "OPTIONS 401" 문제의 원인이에요.
- `Access-Control-Max-Age`는 preflight 결과를 캐시할 시간(초)이에요. 없으면 기본 5초예요. 크게 줘도 브라우저 상한이 있어요(Firefox 24시간, Chromium 2시간).

### 5. 주요 응답 헤더

| 헤더 | 뜻 | 주의 |
|---|---|---|
| `Access-Control-Allow-Origin` | 읽기를 허락할 출처 하나 또는 `*` | 여러 개 보내면 오류. 값이 요청 출처와 다르면 오류 |
| `Access-Control-Allow-Methods` | preflight에서 허락할 메서드 | |
| `Access-Control-Allow-Headers` | preflight에서 허락할 요청 헤더 | `Authorization`은 `*`에 안 들어가서 직접 적어야 함 |
| `Access-Control-Max-Age` | preflight 캐시 시간(초) | 브라우저 상한 있음 |
| `Access-Control-Allow-Credentials` | 쿠키 포함 요청의 응답을 읽어도 됨 | `true`일 때 다른 헤더에 `*` 금지 |
| `Access-Control-Expose-Headers` | JS가 읽을 수 있는 응답 헤더 추가 | 기본으로는 Content-Type 등 몇 개만 보임 |
| `Vary: Origin` | 출처마다 응답이 다르다고 캐시에 알림 | 허용 목록에서 골라 동적으로 돌려줄 때 필수 |

- `Vary: Origin`이 없으면 CDN 같은 캐시가 A 출처용 응답(`Allow-Origin: A`)을 B 출처 요청에도 재사용해서, B에서 가끔 CORS 에러가 나요.
- 응답의 커스텀 헤더나 `Location`을 JS에서 못 읽는다면 `Expose-Headers`에 넣어야 해요.

### 심화: 6. 쿠키를 같이 보내는 요청

- fetch의 `credentials` 기본값은 `same-origin`이라 **다른 출처로는 쿠키가 안 실려요.** 실으려면 `credentials: "include"`(XHR은 `withCredentials = true`)를 써요.
- 이때 서버는 preflight 응답과 실제 응답 **모두** 아래를 지켜야 해요.
  - `Access-Control-Allow-Credentials: true`
  - `Access-Control-Allow-Origin`에 **정확한 출처**. `*` 불가.
  - `Allow-Headers`, `Allow-Methods`, `Expose-Headers`도 `*` 대신 명시.
- `*`로 두면 브라우저가 응답을 버리고, 응답의 `Set-Cookie`도 저장하지 않아요.
- CORS로 허락해도 브라우저의 서드파티 쿠키 차단과 `SameSite` 규칙은 그대로 적용돼요.

### 7. CORS가 막지 않는 것

로컬에서 API 서버를 띄우고, 허용하지 않은 출처를 `Origin` 헤더에 넣어 curl로 GET을 보내 확인해 봤어요(주소는 예시로 바꿨어요).

```text
$ curl -i https://api.example.com/api -H "Origin: http://evil.example"
HTTP/1.0 200 OK
Content-Type: application/json

{"ok":true}
(서버 로그: GET 요청 처리함)
```

- 서버는 요청을 **받아서 처리하고** 200을 돌려줬어요. 응답에 `Allow-Origin`만 없었어요.
- 브라우저였다면 이 응답을 JS에 안 넘겼을 거예요. curl은 CORS 검사를 안 하니 본문이 그대로 보였어요.
- "Postman에선 되는데 브라우저에선 안 돼요"가 이래서 생겨요. **CORS는 브라우저만 하는 검사**예요. 서버 간 호출에도 없어요.
- 그래서 CORS는 **CSRF 방어가 아니에요.** 폼 제출 같은 다른 출처 "쓰기"는 원래 허용이고, 그건 CSRF 토큰과 SameSite 쿠키로 막아요.

### 8. 개발용 프록시로 피하는 원리

프론트 개발 서버의 프록시 기능(Vite, CRA, webpack dev server 등에 있어요)은 브라우저가 **같은 출처**(개발 서버)로 요청하게 만들고, 개발 서버가 뒤에서 API로 넘겨줘요. 개발 서버 → API 구간은 서버 간 호출이라 CORS가 없어요. 운영에서 Nginx 같은 리버스 프록시로 같은 도메인 아래 `/api`를 두는 것도 같은 원리예요. 도구별 설정 방법은 각 도구 문서를 확인하세요.

### 심화: 9. 스프링에서 설정하기

| 방법 | 범위 | 기본값 |
|---|---|---|
| `@CrossOrigin` | 컨트롤러·메서드 | 모든 출처, 모든 헤더, 매핑된 메서드, 쿠키 허용 꺼짐, maxAge 30분 |
| `WebMvcConfigurer.addCorsMappings` | 전역 | 모든 출처, 모든 헤더, GET/HEAD/POST |
| `CorsFilter` | 필터 단계 | `CorsConfigurationSource`로 지정 |

```java
// 스프링 시큐리티를 쓸 때: CORS를 시큐리티 필터 안에서 먼저 처리
@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.cors(withDefaults()); // 아래 CorsConfigurationSource 빈을 사용
    // ... 인증·인가 설정
    return http.build();
}

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("https://app.example.com")); // 쿠키 쓰면 * 금지
    c.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    c.setAllowedHeaders(List.of("Content-Type", "Authorization"));
    c.setAllowCredentials(true);
    c.setMaxAge(600L);
    UrlBasedCorsConfigurationSource s = new UrlBasedCorsConfigurationSource();
    s.registerCorsConfiguration("/**", c);
    return s;
}
```

- `allowCredentials(true)`와 `allowedOrigins("*")`는 같이 못 써요. 출처를 명시하거나 `allowedOriginPatterns`로 패턴을 써요.
- 스프링 MVC는 `HandlerMapping` 단계에서 CORS를 처리해요. 맞는 설정이 없으면 CORS 헤더가 안 붙고, 브라우저가 거부해요.
- 시큐리티를 쓰면서 `WebMvcConfigurer`만 설정하고 `http.cors()`를 빼면, preflight가 MVC까지 가기 전에 시큐리티 인증 필터에서 막힐 수 있어요. preflight엔 쿠키(세션 ID)도 토큰도 없으니까요. → [스프링 시큐리티](../../spring/spring-security/)

<Aside type="caution" title="서버 에러가 CORS 에러로 보일 때">
500 에러 응답이나 인증 필터가 만든 401 응답처럼 정상 경로가 아닌 곳에서 나간 응답에 CORS 헤더가 안 붙으면, 브라우저는 진짜 원인 대신 CORS 에러만 보여 줘요. 원인은 서버 로그와 개발자 도구 네트워크 탭의 상태 코드로 확인하세요.
</Aside>

## 면접 질문

<details>
<summary>Q. 동일 출처 정책이 뭐고, 출처는 어떻게 판단하나요?</summary>

**답변(30초)** 브라우저가 다른 출처의 응답을 스크립트가 읽지 못하게 막는 규칙이에요. 출처는 scheme, host, port 세 값이고 셋이 모두 같아야 같은 출처예요. 그래서 포트만 달라도 다른 출처예요. 링크 이동이나 폼 제출, 이미지·스크립트 임베드는 대체로 허용되고, JS로 응답을 읽는 것이 기본으로 막혀요. 로그인된 다른 사이트의 정보를 아무 페이지나 읽어 가지 못하게 하려는 거예요.

**꼬리질문**
- Q. `localhost:3000`과 `localhost:8080`은요? → 포트가 달라 다른 출처예요. `localhost`와 `127.0.0.1`도 host 글자가 달라 다른 출처예요.
- Q. 쿠키도 같은 규칙인가요? → 아니요. 쿠키는 도메인 기준이라 포트·scheme으로 나뉘지 않아요.
</details>

<details>
<summary>Q. CORS가 뭐고, 왜 필요한가요?</summary>

**답변(30초)** 동일 출처 정책의 예외를 서버가 허락하는 규약이에요. 서버가 `Access-Control-Allow-Origin` 같은 응답 헤더로 "이 출처는 읽어도 된다"고 알려 주면 브라우저가 그 응답을 JS에 넘겨줘요. 프론트와 API 도메인이 다른 요즘 구조에선 이게 없으면 API 응답을 못 읽어요. 검사는 브라우저가 하지만, 해결은 서버 응답 헤더에서 해요.

**꼬리질문**
- Q. Postman에선 되는데 브라우저에서만 에러가 나요. → CORS는 브라우저만 하는 검사라서예요. Postman, curl, 서버 간 호출은 검사를 안 해요.
- Q. JS에서 에러 원인을 알 수 있나요? → 알 수 없어요. 보안상 JS는 실패 사실만 받고, 원인은 콘솔에만 나와요.
</details>

<details>
<summary>Q. 단순 요청과 preflight는 언제 갈리나요? JSON POST는요?</summary>

**답변(30초)** 메서드가 GET·HEAD·POST이고, 직접 넣은 헤더가 허용 목록뿐이고, Content-Type이 폼·multipart·text/plain 중 하나면 단순 요청이라 바로 보내요. 하나라도 벗어나면 브라우저가 먼저 OPTIONS로 허락을 물어요. 그래서 `application/json` POST나 `Authorization` 헤더를 단 요청은 preflight가 붙어요. preflight가 실패하면 실제 요청은 아예 안 나가요.

**꼬리질문**
- Q. preflight에는 어떤 헤더가 오가요? → 요청엔 `Origin`, `Access-Control-Request-Method`, `Access-Control-Request-Headers`, 응답엔 `Allow-Origin`, `Allow-Methods`, `Allow-Headers`, `Max-Age`예요.
- Q. preflight가 매번 나가서 느려요. → `Access-Control-Max-Age`로 결과를 캐시해요. 다만 브라우저 상한(Chromium 2시간, Firefox 24시간)이 있어요.
</details>

<details>
<summary>Q. 쿠키를 포함한 CORS 요청은 어떻게 설정하나요? 왜 *를 못 쓰나요?</summary>

**답변(30초)** 프론트는 `credentials: "include"`를 줘야 다른 출처로 쿠키가 실려요. 서버는 preflight와 실제 응답 모두에 `Access-Control-Allow-Credentials: true`와 정확한 출처를 담은 `Allow-Origin`을 보내야 해요. 쿠키 포함 요청에서 `*`는 허용되지 않는데, "아무 사이트나 내 로그인 상태로 응답을 읽어도 된다"는 뜻이 되기 때문이에요. `*`이면 브라우저가 응답을 버리고 `Set-Cookie`도 저장하지 않아요.

**꼬리질문**
- Q. 허용할 출처가 여러 개면요? → 허용 목록에서 요청의 `Origin`과 맞는 걸 골라 돌려주고, `Vary: Origin`을 꼭 붙여요.
- Q. `Vary: Origin`은 왜요? → 없으면 CDN 캐시가 다른 출처용 응답을 재사용해서 가끔 CORS 에러가 나요.
</details>

<details>
<summary>Q. CORS 에러가 났으면 서버는 요청을 받은 건가요?</summary>

**답변(30초)** 단순 요청이면 받았고 처리도 끝났어요. CORS 검사는 응답이 브라우저에 돌아온 뒤 JS에 넘길지 정하는 단계라서요. preflight가 필요한 요청이고 preflight가 실패했다면 실제 요청은 안 나갔어요. 그래서 CORS는 요청 자체를 막는 보안 장치가 아니고, CSRF 방어도 따로 해야 해요.

**꼬리질문**
- Q. 서버 500 에러인데 콘솔엔 CORS 에러만 보여요. → 에러 응답에 CORS 헤더가 안 붙어서예요. 서버 로그와 네트워크 탭의 상태 코드를 봐야 해요.
</details>

<details>
<summary>Q. 스프링에서 CORS는 어떻게 설정하고, 시큐리티를 쓸 땐 뭘 주의하나요?</summary>

**답변(30초)** 컨트롤러 단위는 `@CrossOrigin`, 전역은 `WebMvcConfigurer.addCorsMappings`로 설정해요. 스프링 시큐리티를 쓰면 `http.cors()`를 켜고 `CorsConfigurationSource` 빈을 둬서 시큐리티가 CORS를 먼저 처리하게 해야 해요. preflight에는 쿠키나 토큰이 없어서, CORS보다 인증 필터가 먼저 돌면 OPTIONS가 401로 막히기 때문이에요. 쿠키를 쓰면 `allowCredentials(true)`와 명시적 출처를 같이 써요.

**꼬리질문**
- Q. 응답 헤더를 프론트 JS에서 못 읽어요. → 기본으로 보이는 응답 헤더는 몇 개뿐이라, `Expose-Headers`에 추가해야 해요.
- Q. `Authorization`을 허용 헤더 `*`로 열면 되나요? → 안 돼요. `Authorization`은 `*`에 포함되지 않아서 이름을 직접 적어야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 프론트(app.example.com)에서 로그인 후 API(api.example.com)를 부르니 콘솔에 "Access-Control-Allow-Origin이 '*'이면 credential을 지원하지 않는다"는 에러가 납니다.</summary>

**상황 파악**
프론트와 API는 host가 달라 다른 출처예요. 로그인 상태를 유지하려고 쿠키를 실어 보내는 요청(`credentials: "include"`)인데, 서버가 `Allow-Origin: *`로 답하고 있어요. 쿠키 포함 요청에서 `*`는 허용되지 않아서 브라우저가 응답을 버렸어요.

**원인 후보**
1. 서버 CORS 설정이 "모든 출처 허용"(`*`)으로 되어 있어요.
2. `Access-Control-Allow-Credentials: true`가 없거나, preflight 응답에만 있고 실제 응답에는 없어요(또는 그 반대).
3. `Allow-Headers`나 `Allow-Methods`도 `*`로 되어 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 허용 출처를 명시(`https://app.example.com`) + `Allow-Credentials: true` + `Vary: Origin`, 프론트는 `credentials: "include"` | 지금 구조 그대로 해결. 허용 범위가 분명해져 보안도 나아짐 | 출처가 늘 때마다 목록 관리가 필요. 동적으로 돌려주면 `Vary: Origin`을 잊으면 캐시 문제가 생김. 서드파티 쿠키 차단·SameSite 정책에 따라 쿠키가 여전히 안 실릴 수 있음 |
| B. 리버스 프록시로 같은 도메인 아래 `/api`를 둠 | 브라우저 입장에서 같은 출처라 CORS 자체가 없어짐. 쿠키 문제도 단순해짐 | 프록시 인프라 설정·운영이 생김. 프론트와 API 배포가 묶일 수 있음 |

**내가 고를 방법**
당장은 A로 고치겠어요. 설정 몇 줄로 바로 해결되고, `*`를 걷어 내는 것 자체가 보안상 맞는 방향이에요. 스프링이면 `allowedOrigins`에 출처를 적고 `allowCredentials(true)`를 켜요. 쿠키가 서드파티 정책에 계속 막힌다면 B로 같은 도메인 구조를 검토해요.

**채점 포인트**: 다른 출처 판단(host 다름), 쿠키 포함 시 `*` 금지, `Allow-Credentials: true`를 preflight·실제 응답 모두에, 프론트 `credentials: "include"`, 출처 명시와 `Vary: Origin`, 리버스 프록시 대안과 트레이드오프, SameSite·서드파티 쿠키 정책.
</details>

<details>
<summary>상황: GET 조회는 되는데 JWT를 Authorization 헤더에 넣은 PUT만 실패합니다. 서버 로그를 보니 OPTIONS 요청이 401로 거절되고 있습니다.</summary>

**상황 파악**
`Authorization` 헤더와 PUT은 단순 요청 조건을 벗어나서 브라우저가 먼저 OPTIONS(preflight)를 보내요. preflight에는 자격 증명이 실리지 않아서 토큰이 없어요. 스프링 시큐리티 인증 필터가 이 OPTIONS를 "토큰 없는 요청"으로 보고 401을 줬고, preflight가 실패했으니 실제 PUT은 아예 안 나갔어요. GET은 단순 요청이라 preflight 없이 통과했어요.

**원인 후보**
1. CORS를 `WebMvcConfigurer`에만 설정해서, 시큐리티 필터가 MVC보다 먼저 OPTIONS를 막아요.
2. `http.cors()`는 켰지만 허용 헤더에 `Authorization`이 없어요(`*`에는 포함되지 않아요).
3. 401 응답에 CORS 헤더가 없어서 프론트엔 원인이 CORS 에러로만 보여요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 시큐리티에 `http.cors(withDefaults())` + `CorsConfigurationSource` 빈, 허용 헤더에 `Authorization` 명시 | 시큐리티 안에서 CORS가 먼저 처리돼 preflight가 인증 전에 응답됨. 스프링 시큐리티 문서가 "preflight엔 쿠키(JSESSIONID)가 없으니 CORS를 시큐리티보다 먼저 처리하라"며 권하는 방식 | CORS 설정 위치가 시큐리티 쪽으로 모여 MVC 설정과 중복되지 않게 정리해야 함 |
| B. 시큐리티에서 OPTIONS 요청만 인증 없이 통과(permitAll) | 설정 한 줄로 증상이 사라짐. 통과한 OPTIONS는 MVC의 CORS 설정이 응답함 | 공식 문서가 안내하는 방식이 아닌 우회. 모든 경로의 OPTIONS가 인증 없이 열리고, MVC 쪽 CORS 설정이 빠져 있으면 여전히 실패함 |

여기에 preflight 횟수를 줄이려면 `Access-Control-Max-Age`를 둬요. 다만 브라우저 상한이 있어 완전히 없앨 수는 없어요.

**내가 고를 방법**
A를 고르겠어요. 원인이 "CORS 처리가 인증보다 늦다"는 순서 문제라서, 순서를 바로잡는 게 근본 해결이에요. 허용 헤더에 `Authorization`, `Content-Type`을 적고, Max-Age로 preflight 부담을 줄여요.

**채점 포인트**: Authorization·PUT·JSON이면 preflight, preflight엔 자격 증명 없음, 인증 필터가 OPTIONS를 401로 거부, preflight 실패 시 실제 요청 안 나감, `http.cors()` + `CorsConfigurationSource`, `Authorization` 명시(와일드카드 불포함), Max-Age와 브라우저 상한.
</details>

<details>
<summary>상황: 동료가 "CORS를 우리 프론트 도메인만 허용했으니 CSRF는 걱정 안 해도 된다"고 합니다. 어떻게 답하겠습니까?</summary>

**상황 파악**
CORS와 CSRF는 막는 대상이 달라요. CORS는 다른 출처 JS가 **응답을 읽는 것**을 제한해요. **CSRF**(사이트 간 요청 위조, 사용자가 로그인된 상태를 악용해 다른 사이트가 몰래 요청을 보내게 하는 공격)는 **요청을 보내게 만드는 것** 자체가 공격이라, 응답을 못 읽어도 성공해요.

**원인 후보(왜 CORS만으론 안 되나)**
1. 폼 제출 같은 다른 출처 "쓰기"는 동일 출처 정책에서도 원래 허용이에요.
2. 단순 요청(폼 POST 등)은 preflight 없이 서버에 도착해 처리돼요. 허용 안 된 출처로 보낸 GET도 서버가 처리하고 200을 돌려주는 걸 직접 확인했어요. 브라우저는 응답만 안 넘겨요.
3. 쿠키는 SameSite 정책이 허락하면 그 요청에 같이 실려요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. CSRF 토큰: 서버가 준 토큰을 상태 변경 요청에 같이 보내게 하고 검증 | 다른 출처 페이지는 토큰을 읽을 수 없어 위조 요청이 실패. 표준적인 방어 | 토큰 발급·검증 구현이 필요하고, SPA라면 토큰 전달 방식을 정해야 함 |
| B. SameSite 쿠키(Lax/Strict) | 다른 사이트에서 시작된 요청에 쿠키가 덜 실려 공격 표면이 줄어듦. 설정이 간단 | 브라우저 지원과 예외 경우에 기대는 부분이 있어 단독 방어로는 불안 |
| C. 상태 변경 API는 JSON + 커스텀 헤더만 받기 | 이런 요청은 preflight가 붙어서, 허용 안 된 출처는 실제 요청을 못 보냄 | 서버가 폼 형식 요청을 확실히 거부해야 효과가 있고, CORS 설정이 넓으면 무의미 |

**내가 고를 방법**
CORS는 그대로 두고 A와 B를 같이 쓰겠어요. 토큰이 주 방어이고, SameSite는 한 겹 더 두는 안전망이에요. 동료에게는 "CORS는 읽기를 막을 뿐이고 요청은 이미 서버에 도착해 처리된다"는 점을 근거로 설명해요.

**채점 포인트**: CORS는 응답 읽기 제한, 단순 요청은 서버에 도착해 처리됨, 폼 제출은 SOP에서도 허용, 쿠키는 SameSite에 따라 실림, CSRF 토큰, SameSite 쿠키, preflight 유도(JSON·커스텀 헤더)는 보조 수단.
</details>
