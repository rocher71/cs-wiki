:::tip[한 줄 요약]
브라우저는 먼저 **도메인 이름을 IP 주소로 바꾸고(DNS)**, 그 서버와 **TCP 연결**을 맺고, https라면 **TLS로 암호화 약속**을 한 뒤, **HTTP 요청**을 보내요. 서버가 HTML을 담아 응답하면 브라우저가 그걸 해석해서 **화면에 그려요(렌더링)**. 두 번째 방문은 캐시와 연결 재사용 덕분에 이 중 여러 단계를 건너뛰어서 빨라요.
:::

<Aside type="note" title="이 페이지는 지도예요">
웹 섹션의 첫 페이지예요. 각 단계는 짧게만 설명하고, 자세한 내용은 단계마다 붙은 링크로 넘어가요. 처음 읽을 땐 "이런 순서로 일어나는구나"만 잡으면 충분해요.
</Aside>

## 쉽게 이해하기

인터넷 쇼핑몰에 **택배로 카탈로그를 요청하는 일**이라고 생각해 봐요.

1. "○○쇼핑"이라는 **가게 이름**만 알아요. 택배를 보내려면 **실제 주소**가 필요하니 주소록(전화번호부)에서 찾아요. 이게 **DNS**예요.
2. 택배 기사와 가게가 "보낼게요" / "받을 준비 됐어요" / "알겠어요" 하고 **서로 확인**해요. 이게 **TCP 연결**이에요.
3. 남이 내용물을 훔쳐보지 못하게 **둘만 아는 자물쇠**를 정해요. 가게가 진짜 그 가게인지 **신분증(인증서)** 도 확인해요. 이게 **TLS**예요.
4. "카탈로그 첫 페이지 보내 주세요"라고 **주문서**를 보내요. 이게 **HTTP 요청**이에요.
5. 가게 안에서는 접수 창구, 담당 직원, 창고가 일을 나눠 처리하고 **상자**에 담아 보내요. 이게 **서버 처리와 HTTP 응답**이에요.
6. 받은 상자 안에는 완성된 그림이 아니라 **조립 설명서(HTML)와 부품(CSS, JS, 이미지)** 이 들어 있어요. 브라우저가 설명서대로 조립해서 화면을 만들어요. 이게 **렌더링**이에요.

단, 실제로는 주소록을 한 번 보면 한동안 기억해 두고(캐시), 한 번 맺은 연결도 계속 다시 써요. 그래서 같은 사이트를 다시 열면 1~3번을 대부분 건너뛰어요.

## 제대로 알기

### 1. 주소창 입력 해석

입력한 글자가 URL 모양이 아니면 브라우저는 **검색어**로 보고 기본 검색엔진에 넘겨요. 이건 표준 규칙이 아니라 브라우저마다 정한 동작이에요.

URL 모양이면 조각으로 나눠요.

| 조각 | 예시 | 뜻 |
|---|---|---|
| **scheme**(스킴, 통신 방식) | `https` | 어떤 규칙으로 통신할지 |
| **host**(호스트, 서버 이름) | `example.com` | 어느 서버에 갈지 |
| **port**(포트, 서버 안의 문 번호) | 생략 시 https=443, http=80 | 서버의 어느 프로그램에 갈지 |
| **path**(경로) | `/products/1` | 서버 안의 어떤 자원인지 |
| **query**(쿼리) | `?page=2` | 추가 조건 |
| **fragment**(프래그먼트) | `#review` | 페이지 안의 위치. **서버로 보내지 않아요** |

한글 도메인처럼 영어가 아닌 이름은 **퓨니코드**(punycode, 영문자만으로 바꾼 표기)로, 경로의 한글은 **퍼센트 인코딩**(`%EC%95%88`처럼 바꾼 표기)으로 바꿔서 보내요.

### 2. 보내기 전에 확인: HSTS와 캐시

- **HSTS**(HTTP Strict Transport Security, "이 사이트는 https로만 와" 약속): 서버가 `Strict-Transport-Security` 헤더를 한 번 보내 두면, 브라우저는 정해진 기간(`max-age`) 동안 `http://`로 접속해도 **네트워크에 나가기 전에** `https://`로 바꿔요. 첫 방문부터 강제하려면 브라우저에 내장된 **HSTS preload 목록**에 등록해요.
- **HTTP 캐시**: 같은 URL의 응답을 저장해 뒀고 아직 신선하면(`Cache-Control: max-age` 이내) **네트워크 요청 없이** 끝나요. 신선하지 않으면 "바뀌었나요?"라고 서버에 물어보고(`If-None-Match`), 서버가 `304 Not Modified`라고 하면 저장본을 그대로 써요.

### 3. DNS: 이름을 IP로 → [DNS](../dns/)

컴퓨터는 이름이 아니라 **IP 주소**(인터넷 위의 숫자 주소)로 상대를 찾아요. 그래서 이름을 IP로 바꾸는 **DNS**(Domain Name System, 인터넷 주소록)에 물어봐요.

브라우저 캐시 → OS 캐시(hosts 파일 포함) → **리졸버**(resolver, 대신 찾아 주는 DNS 서버. 통신사나 8.8.8.8 등) 순으로 물어요. 리졸버에도 없으면 리졸버가 **루트 → `.com` → 그 도메인의 권한 서버**(그 도메인의 정답을 가진 DNS 서버) 순으로 찾아가서 IP를 받아 와요. 답에는 **TTL**(Time To Live, 이 답을 기억해도 되는 시간)이 붙어 있어서 그동안은 캐시로 바로 답해요.

### 4. TCP 연결 → [TCP와 UDP](../tcp-udp/)

얻은 IP의 443번 포트로 **TCP 3-way handshake**(세 번 주고받는 연결 인사)를 해요. `SYN`(연결할래요?) → `SYN-ACK`(좋아요, 저도요) → `ACK`(확인). 여기에 **1 RTT**(Round Trip Time, 한 번 갔다 오는 시간)가 들어요.

한 번 맺은 연결은 같은 서버로 가는 다음 요청에 **다시 써요**(HTTP/1.1 keep-alive, HTTP/2는 연결 하나에 요청 여러 개). HTTP/3는 TCP 대신 **UDP 위의 QUIC**(퀵, TCP 역할과 암호화를 합친 새 전송 방식)을 써서 연결과 암호화를 1 RTT에 같이 끝내요. → [HTTP 버전](../http-versions/)

### 5. TLS 핸드셰이크 (https일 때) → [HTTPS와 TLS](../https-tls/)

TLS 1.3은 1 RTT로 끝나요(TLS 1.2는 2 RTT).

1. 브라우저 → 서버: **ClientHello**. 쓸 수 있는 암호 방식, 키 재료, 접속하려는 도메인 이름(**SNI**), 원하는 HTTP 버전(**ALPN**)을 보내요.
2. 서버 → 브라우저: **ServerHello + 인증서 + Finished**.
3. 브라우저 → 서버: **Finished**.

브라우저는 인증서가 믿을 수 있는 **CA**(Certificate Authority, 인증서 발급 기관)로 이어지는지, 기간이 지나지 않았는지, 인증서의 이름이 접속한 도메인과 맞는지 확인해요. 틀리면 경고 화면을 띄워요. 이 과정에서 양쪽이 같은 **대칭키**(같은 열쇠로 잠그고 여는 방식)를 얻고, 이후 데이터는 그 키로 암호화해요. HTTP/2를 쓸지도 여기서(ALPN) 정해져요.

### 6. HTTP 요청 → [HTTP 기초](../http-basics/)

요청은 **메서드**(`GET` 같은 동작) + **경로** + **헤더**(부가 정보) + (본문)으로 이뤄져요.

```http
GET /products/1 HTTP/1.1
Host: example.com
Accept: text/html
Cookie: session=abc123
```

`Host` 헤더는 HTTP/1.1에서 필수예요(HTTP/2에서는 `:authority`라는 이름으로 보내요). 그 도메인의 **쿠키**가 있으면 조건(Secure, SameSite 등)에 맞을 때 브라우저가 자동으로 붙여요. → [쿠키·세션·JWT](../cookie-session-jwt/)

### 7. 서버 측: 실제로는 여러 단계 → [로드밸런서와 프록시](../load-balancer-proxy/)

- DNS가 준 IP는 서버 한 대가 아니라 **CDN**(가까운 곳에 복사본을 두는 배달망)이나 **로드밸런서**(LB, 요청을 여러 서버에 나눠 주는 장치)인 경우가 많아요.
- TLS 암호 해제를 LB/CDN에서 끝내고(**TLS termination**), 안쪽은 평문 HTTP로 넘기는 구성이 흔해요.
- **웹서버**(Nginx 등)는 이미지 같은 정적 파일은 직접 주고, 동적 요청은 **WAS**(Tomcat처럼 코드를 실행하는 서버)로 넘겨요.
- 스프링이라면 톰캣 스레드가 요청을 받아 DispatcherServlet → Controller → Service → Repository(DB) 순으로 처리해요. → [스프링 MVC 요청 흐름](../../spring/mvc-flow/)

### 8. HTTP 응답

응답은 **상태코드** + 헤더 + 본문(HTML)이에요.

| 상태코드 | 뜻 |
|---|---|
| 200 | 성공 |
| 301 / 302 | 다른 주소로 가세요(`Location` 헤더). http→https 이동이 대표 예 |
| 304 | 안 바뀌었으니 저장본 쓰세요 |
| 404 | 없어요 |
| 500 | 서버 오류 |

본문은 보통 `gzip`이나 `br`로 **압축**돼서 오고, 브라우저가 풀어요.

### 9. 렌더링: HTML을 화면으로

1. HTML을 **다 받기 전부터** 받는 대로 해석해서 **DOM**(Document Object Model, 문서를 나무 모양으로 정리한 것)을 만들어요.
2. CSS를 해석해서 **CSSOM**(스타일을 나무 모양으로 정리한 것)을 만들어요. CSSOM이 없으면 화면을 그리지 않아요(**render-blocking**).
3. 평범한 `<script>`를 만나면 HTML 해석을 **멈추고** 스크립트를 받아 실행해요. `defer`는 해석이 끝난 뒤 순서대로, `async`는 받자마자 실행해요.
4. 이미지·CSS·JS 같은 하위 파일은 **각각 다시 요청**해요(6단계 HTTP 요청부터, 보통 연결 재사용).
5. DOM + CSSOM → **렌더 트리**(화면에 보이는 것만, `display:none` 제외) → **레이아웃**(위치·크기 계산, reflow) → **페인트**(색 칠하기) → **합성**(레이어를 GPU가 합치기).

JS로 크기나 위치를 바꾸면 레이아웃부터 다시 해서 무거워요. `transform`, `opacity` 변경은 합성만 다시 해서 가벼워요.

### 한 번 재 본 예시 값

`curl`로 구글 첫 화면을 한 번 재 본 값이에요. 환경마다 크게 다르니 **비율**만 봐 주세요.

| 구간 | 첫 접속 | 두 번째 접속 |
|---|---|---|
| DNS | 약 10ms | 약 3ms |
| TCP 연결 | 약 42ms | 약 50ms |
| TLS | 약 53ms | 약 53ms |
| 서버 처리 + 첫 바이트 | 약 113ms | 약 107ms |

- 두 번째 DNS가 줄어든 건 **DNS 캐시** 덕분이에요.
- TCP와 TLS가 비슷한 건 **둘 다 1 RTT**라서예요.
- `curl`은 요청마다 새로 연결해서 TCP·TLS가 그대로지만, 브라우저는 연결을 다시 써서 두 번째엔 이 구간도 거의 사라져요.

<Aside type="caution" title="자주 헷갈리는 점">
- **DNS는 매번 루트부터 묻지 않아요.** 대부분 캐시에서 끝나요. 루트까지 찾아가는 건 리졸버의 일이고, 브라우저는 리졸버에 한 번 물어요.
- **https여도 다 숨겨지지는 않아요.** 경로·쿼리·헤더는 암호화되지만, 목적지 IP와 (보통) SNI의 도메인 이름은 보여요.
- **301로 https 보내기만으로는 부족해요.** 첫 http 요청은 암호화 없이 나가요. HSTS가 그 왕복 자체를 없애요.
- **`#` 뒤(fragment)는 서버로 안 가요.** 그래서 서버 로그에 없어요.
- **IP 하나가 서버 한 대는 아니에요.** 대개 CDN이나 LB 주소예요.
</Aside>

## 면접 질문

<details>
<summary>Q. 브라우저에 google.com을 입력하면 무슨 일이 일어나나요?</summary>

**답변(30초)** 먼저 DNS로 도메인을 IP 주소로 바꿔요. 브라우저·OS 캐시를 보고, 없으면 리졸버가 루트부터 찾아 줘요. 그 IP의 443 포트로 TCP 3-way handshake를 하고, TLS 핸드셰이크로 인증서를 검증하고 대칭키를 맞춰요. 그다음 GET 요청을 보내면 로드밸런서, 웹서버, WAS를 거쳐 HTML 응답이 와요. 브라우저는 HTML로 DOM, CSS로 CSSOM을 만들고 렌더 트리 → 레이아웃 → 페인트 순으로 화면을 그려요.

**꼬리질문**
- Q. DNS 조회를 자세히 설명해 주세요. → 브라우저 → OS → 리졸버 순으로 묻고, 리졸버가 루트 → TLD(`.com` 같은 최상위 도메인) → 권한 서버를 차례로 물어 IP를 받아요. 답은 TTL 동안 캐시돼요. → [DNS](../dns/)
- Q. TCP는 왜 3번 주고받아요? → 양쪽이 각자 시작 번호(시퀀스 번호)를 보내고 상대가 "받았어요"라고 확인해 줘야 해요. 원래는 4번이지만 서버의 확인과 서버의 시작 번호를 한 메시지(SYN-ACK)에 묶어서 3번이 돼요. 이렇게 상대에게 되물어 확인하는 덕분에 네트워크에 떠돌던 옛 연결 요청을 새 요청으로 착각하지 않아요. → [TCP와 UDP](../tcp-udp/)
- Q. TLS에서 비대칭키와 대칭키를 왜 둘 다 써요? → 비대칭 방식(인증서 서명, 키 교환)은 처음 만난 상대를 확인하고 같은 키를 안전하게 나눠 갖는 데 써요. 그 뒤 실제 데이터는 그 키로 대칭 암호화해요. 대칭 암호가 훨씬 빨라서 많은 데이터를 처리하기에 맞기 때문이에요. → [HTTPS와 TLS](../https-tls/)
</details>

<details>
<summary>Q. 같은 사이트에 두 번째 들어가면 왜 더 빨라요?</summary>

**답변(30초)** 앞 단계들을 건너뛰기 때문이에요. DNS 결과가 TTL 동안 캐시돼서 IP를 다시 찾지 않아요. 이미 맺은 TCP·TLS 연결을 재사용하면 핸드셰이크 왕복이 없어요. 이미지나 CSS처럼 HTTP 캐시에 신선하게 남은 파일은 네트워크 요청 자체를 안 하고, 오래된 건 304 응답으로 본문 없이 확인만 해요.

**꼬리질문**
- Q. 304는 정확히 언제 와요? → 캐시가 만료돼 `If-None-Match` 같은 헤더로 "바뀌었나요?"를 물었는데 안 바뀌었을 때요.
- Q. HTTP/3는 첫 접속도 빠른가요? → QUIC이 연결과 TLS를 합쳐 1 RTT로 끝내서 TCP+TLS보다 왕복이 적어요. → [HTTP 버전](../http-versions/)
</details>

<details>
<summary>Q. HSTS가 뭐예요? 301 리다이렉트로 https 보내면 되지 않나요?</summary>

**답변(30초)** HSTS는 서버가 "앞으로 이 기간 동안은 https로만 와"라고 브라우저에 알려 두는 헤더예요. 301만 쓰면 첫 http 요청이 암호화 없이 나가서 중간에서 가로챌 틈이 있어요. HSTS를 받은 브라우저는 http 요청을 아예 내보내지 않고 내부에서 https로 바꿔요. 첫 방문까지 막으려면 브라우저 내장 preload 목록에 등록해요.

**꼬리질문**
- Q. `includeSubDomains`를 켜면 주의할 점은요? → https가 안 되는 하위 도메인이 있으면 그 사이트에 접속할 수 없게 돼요.
</details>

<details>
<summary>Q. 렌더링 과정과 reflow, repaint의 차이를 설명해 주세요.</summary>

**답변(30초)** HTML로 DOM, CSS로 CSSOM을 만들고, 둘을 합쳐 보이는 요소만 담은 렌더 트리를 만들어요. 그다음 레이아웃에서 위치·크기를 계산하고, 페인트에서 색을 칠하고, 합성에서 레이어를 합쳐요. reflow는 위치·크기가 바뀌어 레이아웃부터 다시 하는 것이고, repaint는 색처럼 모양만 바뀌어 페인트만 다시 하는 거예요. reflow가 더 무거워요.

**꼬리질문**
- Q. 애니메이션은 어떻게 가볍게 만들어요? → `transform`, `opacity`를 쓰면 합성 단계만 다시 해요.
- Q. `<script>`를 head에 두면 왜 느려져요? → 일반 script는 HTML 해석을 멈추게 해요. `defer`나 `async`로 피해요.
</details>

## 서술형 연습

<details>
<summary>상황: 사용자들이 "사이트가 느리다"고 합니다. 어느 단계가 느린지 어떻게 나눠서 확인하고 개선하겠습니까?</summary>

**상황 파악**
"느리다"는 DNS, 연결, 서버 처리, 다운로드, 렌더링 중 어디든 원인일 수 있어요. 감으로 고치지 않고 **구간별 시간**부터 나눠 봐요. `curl -w`나 브라우저 개발자 도구 Network 탭의 Timing이 DNS / 연결 / TLS / 첫 바이트(TTFB) / 다운로드를 따로 보여 줘요.

**원인 후보**
1. **TTFB가 길다**: 서버 안(WAS 로직, DB 쿼리)이 느려요.
2. **TCP·TLS가 길다**: 사용자와 서버가 멀어서 RTT가 커요.
3. **DNS가 길다**: 리졸버가 느리거나 TTL이 너무 짧아 캐시가 자주 비어요.
4. **다운로드가 길다**: 본문이 커요(압축 안 함, 큰 이미지).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. CDN 도입 | 사용자와 가까운 서버(엣지)에서 연결·정적 파일 처리, RTT 감소 | 비용, 바뀐 파일의 캐시 무효화가 까다로움 |
| B. 서버 쪽 개선(쿼리·인덱스, 캐시) | TTFB가 원인이면 효과가 가장 큼 | 원인 분석에 시간이 들고, 캐시는 데이터 정합성 관리 필요 |
| C. 압축 + HTTP 캐시 헤더 | 다운로드량과 재방문 요청 감소 | `max-age`가 길면 배포한 새 파일이 늦게 반영됨(파일명에 버전을 붙여 해결) |

**내가 고를 방법**
측정 결과로 고르는 게 원칙이에요. TTFB가 대부분이면 B부터 해요. 사용자가 해외에 많아 TCP·TLS 구간이 길면 A를 붙여요. C는 비용이 적어서 어느 경우든 같이 적용해요. 적용 후 같은 방식으로 다시 재서 해당 구간이 줄었는지 확인해요.

**채점 포인트**: 구간별 측정(DNS/TCP/TLS/TTFB/다운로드), TTFB=서버 문제, RTT=거리 문제→CDN, 압축·캐시, 캐시 무효화 트레이드오프, 적용 후 재측정.
</details>

<details>
<summary>상황: 서버를 새 IP로 옮겼는데, 일부 사용자는 몇 시간째 옛 서버로 접속합니다.</summary>

**상황 파악**
DNS 레코드는 바꿨는데 일부만 옛 IP로 가요. 사용자마다 다르다는 건 **어딘가에 캐시된 옛 답**이 남아 있다는 뜻이에요.

**원인 후보**
1. 기존 레코드의 **TTL이 길어서** 리졸버·OS·브라우저가 옛 IP를 아직 기억해요.
2. 일부 리졸버가 TTL을 제대로 지키지 않아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 이전 며칠 전에 TTL을 짧게 낮춰 두기 | 바꾼 뒤 빨리 퍼짐 | 그동안 DNS 질의가 늘어 조회가 조금 느려지고 DNS 부하 증가 |
| B. 옛 서버를 일정 기간 유지(또는 새 서버로 전달) | 늦게 바뀐 사용자도 서비스 정상 | 두 서버 운영 비용, 데이터 동기화 필요 |

**내가 고를 방법**
A와 B를 같이 써요. 이전 전에 TTL을 낮춰 두고, 이전 후에도 옛 TTL만큼 이상은 옛 서버를 살려 두거나 새 서버로 넘겨요. 다 옮겨지면 TTL을 원래대로 올려요.

**채점 포인트**: DNS 캐시와 TTL, 사전 TTL 단축, 옛 서버 유지 기간, 이후 TTL 복구.
</details>

<details>
<summary>상황: 로드밸런서 뒤에 있는 서버 로그에 사용자 IP가 전부 LB의 IP로 찍힙니다.</summary>

**상황 파악**
서버 입장에서 연결을 맺은 상대는 사용자가 아니라 LB예요. 그래서 연결 기준 IP는 LB 주소가 돼요.

**원인 후보**
1. LB가 원래 사용자 IP를 헤더로 넘기지 않아요.
2. 넘기고 있는데 서버(앱)가 그 헤더를 읽지 않아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. LB가 `X-Forwarded-For` 헤더를 붙이고 앱이 읽기 | 널리 쓰여 대부분의 LB·프레임워크가 지원 | 사용자가 헤더를 위조할 수 있어, 믿을 수 있는 LB가 붙인 값만 써야 함 |
| B. 표준 `Forwarded` 헤더(RFC 7239) | 표준 형식 | 지원하는 도구가 상대적으로 적음 |

**내가 고를 방법**
A를 써요. 대신 앱은 "우리 LB가 붙인 값"만 믿도록 신뢰할 프록시를 설정해서 위조를 막아요.

**채점 포인트**: 연결 상대는 LB, X-Forwarded-For/Forwarded, 헤더 위조 위험, 신뢰 프록시 설정.
</details>

## 필기 포인트

- URL 구성: scheme, host, port(https 443 / http 80), path, query(`?`), fragment(`#`, 서버로 안 감).
- DNS: 브라우저 → OS → 리졸버(재귀 질의) / 리졸버 → 루트 → TLD → 권한 서버(반복 질의). A=IPv4, AAAA=IPv6. TTL 동안 캐시.
- TCP 3-way handshake: SYN → SYN-ACK → ACK, 1 RTT.
- TLS 1.3 = 1 RTT, TLS 1.2 = 2 RTT. SNI=접속 도메인 이름, ALPN=HTTP 버전 협상.
- HTTP/3 = UDP 위 QUIC, `Alt-Svc` 헤더로 지원을 알림.
- CSS는 render-blocking, 일반 `<script>`는 parser-blocking. `defer`=파싱 후 순서대로, `async`=받는 대로.
- 렌더링 순서: DOM·CSSOM → 렌더 트리 → 레이아웃(reflow) → 페인트 → 합성.
