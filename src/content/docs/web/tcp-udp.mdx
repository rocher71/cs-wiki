:::tip[한 줄 요약]
**TCP**는 3-way handshake로 연결을 맺고, 시퀀스 번호·ACK·재전송·흐름 제어·혼잡 제어로 데이터를 **빠짐없이, 순서대로** 전달해요. **UDP**는 연결도 재전송도 없이 데이터그램을 바로 보내서 **가볍고 지연이 작아요**. 그래서 정확성이 중요하면 TCP, 실시간성이 중요하면 UDP를 골라요.
:::

## 쉽게 이해하기

TCP는 **등기 택배**예요. 보내기 전에 "받을 수 있어요?" 하고 전화로 확인하고(연결 수립), 상자마다 번호를 붙여요. 받는 사람은 "3번까지 받았어요"라고 영수증(ACK)을 보내고, 영수증이 안 오면 보낸 사람이 다시 부쳐요. 받는 쪽 창고가 차면 "천천히 보내 주세요"라고 알려 주고, 길이 막히면 보내는 쪽이 알아서 양을 줄여요.

UDP는 **전단지 돌리기**예요. 주소만 적어서 던지고 끝이에요. 잘 갔는지 확인하지 않고, 순서도 신경 쓰지 않아요. 대신 확인 전화도 영수증도 없으니 훨씬 빨라요.

영상 통화처럼 "1초 전 화면을 다시 받아 봐야 소용없는" 일에는 전단지 방식이 오히려 나아요. 계좌 이체처럼 하나라도 빠지면 큰일인 일에는 등기 택배가 필요해요.

단, 실제로는 TCP의 "상자"는 메시지 단위가 아니라 **바이트 단위**로 번호를 매겨요. 그리고 UDP도 체크섬으로 깨진 데이터는 알아챌 수 있어요. 고치지 않을 뿐이에요.

## 제대로 알기

### 1. 둘 다 "전송 계층" 프로토콜이에요

IP는 "이 주소까지 패킷을 보내 볼게" 수준이에요. 도중에 사라지거나 순서가 뒤바뀌어도 책임지지 않아요. 그 위에서 **어느 프로그램에게(포트)**, **얼마나 믿을 만하게** 전달할지를 정하는 층이 **전송 계층**이고, 대표가 TCP와 UDP예요. 계층 구조는 [네트워크 계층](../network-layers/)에서 봐요.

| 구분 | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 (handshake로 연결을 맺음) | 비연결 (바로 보냄) |
| 신뢰성 | 유실 감지·재전송, 순서 보장 | 보장 안 함 (유실·중복·순서 뒤바뀜 가능) |
| 데이터 단위 | **바이트 스트림** (경계 없는 바이트 흐름) | **데이터그램** (보낸 메시지 단위 그대로) |
| 흐름·혼잡 제어 | 있음 | 없음 |
| 헤더 크기 | 최소 20바이트 | 8바이트 |
| 속도·지연 | 상대적으로 무거움 | 가볍고 지연이 작음 |
| 대표 용도 | HTTP/1.1·HTTP/2, DB 연결, 이메일, 파일 전송 | DNS, 음성·영상 통화, 게임, 실시간 스트리밍, QUIC(HTTP/3) |

### 2. TCP는 신뢰성을 어떻게 만드나요

TCP는 세 가지 도구를 조합해요.

1. **시퀀스 번호**(sequence number, 보낸 바이트에 붙이는 일련번호)로 무엇이 빠졌는지 알아채요.
2. **체크섬**(checksum, 데이터가 깨졌는지 확인하는 검산 값)으로 오류를 알아채요.
3. **재전송**으로 빠지거나 깨진 걸 고쳐요.

받는 쪽은 **ACK**(acknowledgment, 확인 응답)를 돌려줘요. 여기서 헷갈리기 쉬운 점이 있어요. **ACK 번호는 "받은 개수"가 아니라 "다음에 받고 싶은 번호"**예요. 100~199번 바이트를 잘 받았으면 ACK 200을 보내요.

번호는 메시지마다가 아니라 **바이트마다** 매겨요. 예외로 SYN과 FIN은 데이터가 없어도 번호를 1 차지해요. 데이터 없는 순수 ACK는 번호를 차지하지 않아요. ACK에 또 ACK를 하는 끝없는 상황을 막으려는 거예요.

ACK가 일정 시간 안에 안 오면 다시 보내는데, 이 기다리는 시간을 **RTO**(Retransmission Timeout, 재전송 타이머)라고 해요. 초기값은 1초이고, 타이머가 만료될 때마다 RTO를 **2배**로 늘려요(**지수 백오프**). 망이 막혔는데 똑같이 자주 다시 보내면 더 막히니까요.

<Aside type="note" title="TCP 헤더 한눈에">
출발·목적 포트, 시퀀스 번호, ACK 번호, 헤더 길이, 플래그, 윈도우, 체크섬 등이 들어 있어요. 옵션이 없으면 **20바이트**예요. 플래그는 현재 규격 기준 **8개**(CWR, ECE, URG, ACK, PSH, RST, SYN, FIN)이고, 앞의 CWR·ECE 2개는 혼잡 알림용이에요. 옛 교재는 뒤의 6개만 외우게 하기도 해요.
</Aside>

### 3. 연결 맺기: 3-way handshake

TCP는 데이터를 보내기 전에 세 번 주고받아 연결을 맺어요.

| 순서 | 방향 | 세그먼트 | 보낸 뒤 상태 |
|---|---|---|---|
| 0 | - | 서버는 미리 열어 두고 기다림 | 서버 LISTEN |
| 1 | 클라이언트 → 서버 | SYN (seq=100) | 클라이언트 SYN-SENT |
| 2 | 서버 → 클라이언트 | SYN+ACK (seq=300, ack=101) | 서버 SYN-RECEIVED |
| 3 | 클라이언트 → 서버 | ACK (ack=301) | 양쪽 ESTABLISHED |

**SYN**(synchronize)은 "내 시작 번호는 이거야"라는 신호예요. 숫자 100, 300은 예시일 뿐이에요. 실제 **초기 시퀀스 번호**(ISN, Initial Sequence Number)는 0부터 시작하지 않고, 남이 맞히기 어렵게 시간과 비밀 값을 섞어 골라요. 번호를 쉽게 맞히면 공격자가 가짜 세그먼트를 끼워 넣을 수 있거든요.

**왜 2번이 아니라 3번인가요?** 양쪽이 **서로의 시작 번호를 확인**받아야 해요.

- 1번 SYN에 대한 확인은 2번이 해 줘요.
- 2번에 들어 있는 서버의 SYN에 대한 확인은 3번이 해 줘요.

2번에서 끝내면 서버는 자기 시작 번호가 클라이언트에게 잘 갔는지 몰라요. 또 네트워크에 떠돌던 **오래된 SYN**이 늦게 도착했을 때, 3번째 단계가 있어야 클라이언트가 "그건 내가 지금 보낸 게 아니야"라고 RST로 거절할 수 있어요.

참고로 handshake 세그먼트에 데이터를 실어도 규격 위반은 아니에요. 다만 받는 쪽은 ESTABLISHED가 될 때까지 그 데이터를 앱에 넘기지 않아요. 양쪽이 동시에 SYN을 보내는 **동시 open**도 규격에 있어요.

### 4. 연결 끊기: 4-way handshake

TCP 연결은 **양방향 도로 두 개**예요. 끊을 때도 방향마다 따로 닫아요. `close`는 "**나는** 더 보낼 게 없어"라는 뜻이지, 상대가 보내는 것까지 막는 게 아니에요.

| 순서 | 방향 | 세그먼트 | 상태 |
|---|---|---|---|
| 1 | 클라이언트 → 서버 | FIN | 클라이언트 FIN-WAIT-1 |
| 2 | 서버 → 클라이언트 | ACK | 서버 CLOSE-WAIT, 클라이언트 FIN-WAIT-2 |
| (중간) | 서버 → 클라이언트 | 남은 데이터 | 서버는 아직 보낼 수 있음 |
| 3 | 서버 → 클라이언트 | FIN (서버 앱이 close한 뒤) | 서버 LAST-ACK |
| 4 | 클라이언트 → 서버 | ACK | 클라이언트 TIME-WAIT, 서버 CLOSED |
| 끝 | - | 2MSL 기다림 | 클라이언트 CLOSED |

**왜 4번인가요?** FIN을 받은 서버는 일단 ACK만 바로 보내요. 서버 쪽에는 아직 보낼 데이터가 남아 있을 수 있거든요. 서버 **앱이 close를 호출해야** 서버의 FIN이 나가요. 그래서 2번(ACK)과 3번(FIN)이 따로 가서 4번이 돼요. 한쪽만 닫힌 이 중간 상태를 **half-close**라고 해요.

남은 데이터가 없으면 2번과 3번을 **FIN+ACK 하나로 합쳐** 보낼 수도 있어요. 양쪽이 동시에 close하면 FIN-WAIT-1 → CLOSING → TIME-WAIT를 거쳐 **양쪽 모두** TIME-WAIT가 돼요.

정상 종료 말고 **RST**(reset)로 끊는 방법도 있어요. 인사 없이 전화를 끊는 것처럼, 연결 상태를 즉시 버려요.

### 5. TIME-WAIT는 왜 있나요

먼저 끊은 쪽(능동 종료)은 마지막 ACK를 보낸 뒤 바로 사라지지 않고 **2MSL** 동안 TIME-WAIT 상태로 기다려야 해요. **MSL**(Maximum Segment Lifetime)은 세그먼트 하나가 네트워크에서 떠돌 수 있는 최대 시간이에요.

기다리는 이유는 두 가지예요.

1. **마지막 ACK가 유실될 수 있어서.** 서버가 ACK를 못 받으면 FIN을 다시 보내요. 클라이언트가 이미 사라졌으면 이 FIN에 RST로 답하게 돼서 서버는 정상 종료를 못 해요. 남아 있으면 ACK를 다시 보내 줄 수 있어요.
2. **늦게 도착한 옛 세그먼트가 새 연결에 섞이지 않게.** 같은 주소·포트 조합으로 바로 새 연결을 열면, 이전 연결에서 길을 헤매던 세그먼트가 새 연결 데이터인 척 들어올 수 있어요. 2MSL 기다리면 그런 세그먼트는 다 사라져요.

**값은 OS마다 달라요.**

| 기준 | 값 |
|---|---|
| 규격(RFC) | MSL 2분 → 2MSL 4분 (공학적 선택이라 바뀔 수 있다고 명시) |
| Linux | TIME_WAIT 길이 60초 고정 (커널 상수) |
| macOS | MSL 15초 → 2MSL 약 30초 (한 번 재 본 예시) |

<Aside type="caution" title="TIME-WAIT는 서버에 생기는 게 아니에요">
TIME-WAIT는 **먼저 close를 호출한 쪽**에 생겨요. 직접 내 컴퓨터 안에서 서버·클라이언트를 띄우고 클라이언트가 먼저 닫아 보니, 클라이언트 쪽에 `FIN_WAIT_2` → `TIME_WAIT`, 서버 쪽에 `CLOSE_WAIT`가 남았어요. 서버가 먼저 끊으면 TIME-WAIT는 서버에 쌓여요.
</Aside>

### 6. TCP 상태 한눈에

TCP 상태는 11개예요. 그중 CLOSED는 "연결 정보가 아예 없음"을 뜻하는 가상 상태예요.

| 상태 | 뜻 |
|---|---|
| LISTEN | 서버가 연결 요청을 기다림 |
| SYN-SENT | SYN을 보내고 응답을 기다림 |
| SYN-RECEIVED | SYN을 받고 SYN+ACK를 보낸 뒤 ACK를 기다림 |
| ESTABLISHED | 연결됨, 데이터 주고받는 중 |
| FIN-WAIT-1 | 내가 FIN을 보냄 |
| FIN-WAIT-2 | 내 FIN이 확인됨, 상대 FIN을 기다림 |
| CLOSE-WAIT | 상대 FIN을 받음, **내 앱이 close하길 기다림** |
| CLOSING | 양쪽이 동시에 FIN을 보냄 |
| LAST-ACK | 내 FIN의 마지막 ACK를 기다림 |
| TIME-WAIT | 2MSL 동안 대기 |
| CLOSED | 연결 없음 |

실무에서 자주 보는 건 **TIME_WAIT**와 **CLOSE_WAIT**예요. `netstat`이나 `ss`로 상태별 개수를 세어 진단해요. 둘은 원인이 전혀 달라요.

| 많이 쌓인 상태 | 뜻 | 보통 원인 |
|---|---|---|
| TIME_WAIT | 내가 먼저 끊은 연결이 많음 | 요청마다 연결을 새로 열고 닫음 (연결 재사용 안 함) |
| CLOSE_WAIT | 상대는 끊었는데 내 앱이 close를 안 함 | **코드의 close 누락** (커넥션·응답 스트림 누수) |

### 7. 흐름 제어 vs 혼잡 제어

둘 다 "보내는 양을 줄인다"는 점이 같아서 헷갈려요. **누구를 보호하느냐**로 구분해요.

| 구분 | 흐름 제어 | 혼잡 제어 |
|---|---|---|
| 보호 대상 | **받는 쪽**(수신 버퍼) | **네트워크**(중간 라우터들) |
| 사용하는 값 | **rwnd**(receive window) | **cwnd**(congestion window) |
| 값을 정하는 쪽 | 수신자가 헤더의 Window 필드로 알려 줌 | 송신자가 스스로 추정 |
| 비유 | "창고가 꽉 찼어요, 천천히요" | "길이 막히는 것 같으니 줄여야지" |

송신자가 ACK를 받기 전에 한 번에 보낼 수 있는 양은 **min(cwnd, rwnd)**, 둘 중 작은 값이에요.

**흐름 제어**에서 받는 쪽이 윈도우를 0으로 알리면 송신자는 멈춰요. 그리고 가끔 작은 탐색 세그먼트(**zero-window probe**)를 보내 윈도우가 다시 열렸는지 확인해요. 이렇게 윈도우만큼씩 밀어 가며 보내는 방식을 **슬라이딩 윈도우**라고 불러요.

### 8. 혼잡 제어 4단계

TCP 구현은 slow start, congestion avoidance, RTO 지수 백오프를 **반드시** 갖춰야 해요. 기준점은 **ssthresh**(slow start threshold, 속도를 바꾸는 문턱값)예요.

| 단계 | 언제 | cwnd 변화 |
|---|---|---|
| **Slow start** | cwnd가 ssthresh보다 작을 때 | ACK마다 1 세그먼트 증가 → RTT마다 약 **2배** (지수) |
| **Congestion avoidance** | cwnd가 ssthresh보다 클 때 | RTT마다 약 **1 세그먼트** 증가 (선형) |
| **Fast retransmit** | 중복 ACK 3개 | 타이머를 기다리지 않고 빠진 세그먼트를 바로 재전송 |
| **Fast recovery** | fast retransmit 직후 | ssthresh를 절반으로, cwnd도 **절반 근처**에서 다시 선형 증가 (slow start로 안 돌아감) |
| **Timeout** | 재전송 타이머 만료 | ssthresh를 절반으로, cwnd를 **1**로 → slow start부터 다시 |

**RTT**(Round Trip Time)는 보내고 응답이 돌아오기까지 걸리는 왕복 시간이에요.

- **Slow start는 느리지 않아요.** 시작값이 작을 뿐, 증가는 지수라 빨라요. 시작 크기(초기 윈도우)는 옛 규격에서 2~4 세그먼트였고, 지금 Linux는 10 세그먼트로 시작해요.
- **중복 ACK 3개**는 같은 ACK가 총 3번이 아니라, 원래 ACK 뒤에 **똑같은 ACK가 3번 더** 온 거예요. 받는 쪽은 순서가 어긋난 세그먼트를 받으면 "아직 N번을 기다려요"라는 ACK를 바로 다시 보내거든요.
- 표의 "절반"은 정확히는 **아직 확인받지 못하고 날아가는 중인 양**(FlightSize)의 절반이고, 최소 2 세그먼트예요. 보통 cwnd와 비슷해서 "cwnd의 절반"으로 외워도 돼요.
- **왜 중복 ACK는 절반, timeout은 1까지 줄이나요?** 중복 ACK가 계속 온다는 건 뒤따르는 패킷은 **여전히 도착하고 있다**는 뜻이에요. 하나만 빠진 가벼운 혼잡이에요. timeout은 아무 응답도 없는 심각한 상황이라 처음부터 조심스럽게 다시 시작해요.

이렇게 "평소엔 선형으로 늘리고, 손실이 나면 절반으로 줄이는" 방식을 **AIMD**(Additive Increase, Multiplicative Decrease)라고 해요.

<Aside type="tip" title="연결을 재사용해야 하는 또 하나의 이유">
새 연결은 매번 handshake 1왕복을 쓰고, cwnd도 작은 값에서 slow start를 다시 해요. 짧은 연결을 반복하면 매번 이 손해를 봐요. 오래 쉬었던 연결도 cwnd를 다시 줄이고 시작해요.
</Aside>

### 9. keep-alive는 두 가지예요

이름이 같아서 자주 섞어 써요.

| 구분 | TCP keep-alive | HTTP keep-alive (persistent connection) |
|---|---|---|
| 하는 일 | 오래 조용한 연결에 작은 탐색 패킷을 보내 상대가 살아 있는지 확인 | 요청 하나 끝나도 연결을 닫지 않고 다음 요청에 **재사용** |
| 기본값 | 선택 기능, 기본 꺼짐, 켜도 기본 간격은 2시간 이상 | HTTP 클라이언트·서버 설정으로 연결을 유지 |
| TIME_WAIT와 관계 | 거의 없음 | 연결을 덜 닫으니 TIME_WAIT가 줄어듦 |

"keep-alive로 TIME_WAIT를 줄인다"고 할 때는 HTTP 쪽 이야기예요. TCP에는 원래 상대가 살아 있는지 확인하는 기능이 기본으로 들어 있지 않아요. 그래서 TCP keep-alive라는 선택 기능이 따로 있는 거예요.

### 10. UDP

UDP는 최소한의 기능만 가진 전송 방식이에요. 규격 스스로 "순서 있는 신뢰성 전송이 필요하면 TCP를 쓰라"고 적어 둘 정도예요.

UDP 헤더는 필드 4개, 각 2바이트씩 **8바이트**가 전부예요.

| 필드 | 뜻 |
|---|---|
| 출발 포트 | 답장 받을 포트. 안 쓰면 0 (선택) |
| 목적 포트 | 받을 프로그램 |
| 길이 | 헤더 포함 전체 길이 (최소 8) |
| 체크섬 | 오류 확인. IPv4에서는 0을 넣어 생략 가능 |

연결 수립, 재전송, 순서 보장, 흐름·혼잡 제어가 **모두 없어요**. 그래서 오버헤드와 지연이 작아요.

**UDP를 쓰는 곳**

- **DNS**: 질문 하나, 답 하나로 끝나는 짧은 대화라 handshake가 아까워요. ([DNS](../dns/))
- **음성·영상 통화, 실시간 스트리밍, 온라인 게임**: 늦게 온 데이터는 쓸모가 없어요. 다시 받느라 기다리는 것보다 버리고 다음 걸 쓰는 게 나아요.
- **QUIC / HTTP/3**: 아래에서 봐요.

신뢰성이 필요하면 **앱이 UDP 위에서 직접 만들면** 돼요. 그 대표 예가 QUIC이에요.

### 11. QUIC: UDP 위에 다시 만든 TCP

TCP는 바이트를 반드시 순서대로 앱에 넘겨요. 그래서 앞의 패킷 하나가 빠지면 뒤에 도착한 데이터도 그게 올 때까지 줄 서서 기다려요. 이걸 **HOL blocking**(head-of-line blocking, 맨 앞이 막혀 뒤가 다 막히는 현상)이라고 해요.

**QUIC**은 UDP 위에서 연결, 재전송, 혼잡 제어를 직접 구현한 프로토콜이에요. TLS 1.3 암호화 handshake를 합쳐 연결을 빨리 맺고, 연결 하나 안에 **스트림 여러 개**를 두어 한 스트림의 손실이 다른 스트림을 막지 않게 했어요. **HTTP/3**가 QUIC 위에서 동작해요. 자세한 건 [HTTP 버전](../http-versions/)에서 봐요.

### 12. SYN flood

**SYN flood**는 SYN만 대량으로 보내고 마지막 ACK는 보내지 않는 공격이에요. 서버에는 SYN-RECEIVED 상태의 반쯤 열린 연결이 쌓여 자원이 바닥나요. 대표 완화책은 **SYN cookies**(반쯤 열린 연결 정보를 서버에 저장하지 않고 시퀀스 번호에 담아 두는 기법)이고, 대기열(backlog) 조정, 앞단 방화벽·로드밸런서에서 걸러 내는 방법도 써요.

<details>
<summary>Q. TCP와 UDP의 차이를 설명해 주세요.</summary>

**답변(30초)** TCP는 연결 지향이고 신뢰성을 보장하는 전송 프로토콜이에요. 3-way handshake로 연결을 맺고, 시퀀스 번호·ACK·재전송으로 유실 없이 순서대로 전달하며, 흐름 제어와 혼잡 제어도 해요. UDP는 연결 없이 데이터그램을 바로 보내고 재전송·순서 보장이 없어서, 헤더가 8바이트로 작고 지연이 짧아요. 그래서 정확성이 중요한 웹·DB 통신엔 TCP, DNS나 실시간 음성·게임엔 UDP를 써요.

**꼬리질문**
- Q. TCP가 "바이트 스트림"이라는 건 무슨 뜻인가요? → 보낸 메시지 경계를 지켜 주지 않고 바이트 흐름으로만 전달한다는 뜻이에요. 그래서 메시지를 어디서 끊을지는 그 위의 앱 프로토콜이 정해요. UDP는 보낸 데이터그램 단위가 그대로 가요.
- Q. UDP는 오류 검사도 안 하나요? → 체크섬은 있어요. IPv4에서만 생략할 수 있어요. 깨진 걸 알아채도 재전송은 안 할 뿐이에요.
</details>

<details>
<summary>Q. 3-way handshake 과정과, 왜 3번인지 설명해 주세요.</summary>

**답변(30초)** 클라이언트가 SYN으로 자기 시작 번호를 보내고, 서버가 SYN+ACK로 그걸 확인하면서 자기 시작 번호를 보내고, 클라이언트가 ACK로 서버 번호를 확인하면 연결이 맺어져요. 3번인 이유는 양쪽이 서로의 시작 시퀀스 번호를 확인받아야 하기 때문이에요. 2번이면 서버는 자기 번호가 전달됐는지 모르고, 네트워크에 떠돌던 오래된 SYN으로 잘못된 연결이 열리는 걸 걸러 낼 수 없어요.

**꼬리질문**
- Q. 시작 번호를 0부터 쓰면 안 되나요? → 안 돼요. 이전 연결의 세그먼트와 섞일 수 있고, 번호를 맞히기 쉬우면 공격자가 가짜 세그먼트를 끼워 넣을 수 있어서 예측하기 어렵게 골라요.
- Q. SYN+ACK의 ack가 왜 x+1인가요? → SYN이 데이터가 없어도 번호를 1 차지하고, ACK 번호는 "다음에 받을 번호"이기 때문이에요.
</details>

<details>
<summary>Q. 연결 종료는 왜 4-way인가요?</summary>

**답변(30초)** TCP는 방향마다 따로 닫기 때문이에요. 클라이언트가 FIN을 보내면 서버는 ACK부터 바로 보내지만, 서버 쪽엔 아직 보낼 데이터가 남아 있을 수 있어요. 서버 앱이 다 보내고 close해야 서버의 FIN이 나가요. 그래서 ACK와 FIN이 따로 가서 4번이 되고, 그 사이 한쪽만 닫힌 상태를 half-close라고 해요.

**꼬리질문**
- Q. ACK와 FIN을 합칠 수 있나요? → 네. 남은 데이터가 없으면 FIN+ACK 하나로 보내서 사실상 3번에 끝나기도 해요.
- Q. CLOSE_WAIT가 계속 쌓이면 뭘 의심하나요? → 상대는 끊었는데 우리 앱이 close를 안 부른 거라 코드의 커넥션 누수를 의심해요. 커널 설정이 아니라 코드를 고쳐야 해요.
</details>

<details>
<summary>Q. TIME_WAIT는 왜 필요하고, 왜 2MSL인가요?</summary>

**답변(30초)** TIME_WAIT는 먼저 연결을 끊은 쪽이 마지막 ACK를 보낸 뒤 2MSL 동안 기다리는 상태예요. 이유는 두 가지예요. 마지막 ACK가 유실돼 상대가 FIN을 다시 보내면 다시 ACK해 주려고, 그리고 이전 연결의 늦은 세그먼트가 같은 주소·포트로 새로 연 연결에 섞이지 않게 하려고요. MSL은 세그먼트가 네트워크에 살아 있을 수 있는 최대 시간이라, 한 번 오고 가는 시간인 2MSL을 기다리면 옛 세그먼트가 모두 사라져요.

**꼬리질문**
- Q. 실제로 몇 초인가요? → 규격상 MSL이 2분이라 4분이지만, Linux는 TIME_WAIT를 60초로 고정해 두었어요. OS마다 달라요.
- Q. TIME_WAIT는 서버에 생기나요? → 먼저 close한 쪽에 생겨요. 서버가 먼저 끊으면 서버에, 클라이언트가 먼저 끊으면 클라이언트에 생겨요.
</details>

<details>
<summary>Q. 흐름 제어와 혼잡 제어의 차이는요?</summary>

**답변(30초)** 흐름 제어는 받는 쪽을, 혼잡 제어는 네트워크를 보호해요. 흐름 제어는 수신자가 헤더의 윈도우 값으로 "버퍼에 이만큼 남았다"(rwnd)를 알려 주고 송신자가 그 안에서만 보내는 방식이에요. 혼잡 제어는 송신자가 네트워크 상태를 추정해 혼잡 윈도우(cwnd)로 스스로 양을 줄이는 방식이에요. 실제로 한 번에 보낼 수 있는 양은 둘 중 작은 값이에요.

**꼬리질문**
- Q. 수신 윈도우가 0이 되면요? → 송신자는 멈추고, 가끔 zero-window probe를 보내 윈도우가 다시 열렸는지 확인해요.
- Q. 혼잡 제어는 라우터가 하나요? → 혼잡은 라우터에서 생기지만, TCP 혼잡 제어 알고리즘은 송신 호스트가 cwnd를 조절하면서 돌아가요.
</details>

<details>
<summary>Q. TCP 혼잡 제어 방식을 설명해 주세요.</summary>

**답변(30초)** 처음엔 slow start로 cwnd를 작게 시작해 RTT마다 약 2배씩 늘려요. ssthresh에 닿으면 congestion avoidance로 바꿔 RTT마다 1 세그먼트씩 천천히 늘려요. 중복 ACK 3개를 받으면 바로 재전송(fast retransmit)하고, ssthresh와 cwnd를 절반 근처로 줄여 선형 증가를 이어 가요(fast recovery). 재전송 타이머가 만료되면 심각한 혼잡으로 보고 cwnd를 1로 줄여 slow start부터 다시 해요.

**꼬리질문**
- Q. 왜 중복 ACK와 timeout을 다르게 다루나요? → 중복 ACK는 뒤 패킷이 여전히 도착한다는 뜻이라 가벼운 손실로 보고, timeout은 아무 응답이 없는 상황이라 더 크게 줄여요.
- Q. AIMD가 뭔가요? → 평소엔 더하기로 천천히 늘리고(Additive Increase), 손실이 나면 곱하기로 크게 줄이는(Multiplicative Decrease) 방식이에요.
</details>

<details>
<summary>Q. UDP는 언제 쓰고, HTTP/3는 왜 UDP 위에서 동작하나요?</summary>

**답변(30초)** UDP는 늦게 온 데이터가 쓸모없거나 대화가 아주 짧을 때 써요. 실시간 음성·영상, 게임, DNS가 대표예요. HTTP/3는 UDP 위에서 동작하는 QUIC을 써요. TCP는 패킷 하나가 빠지면 뒤 데이터까지 다 기다리는 HOL blocking이 있는데, QUIC은 스트림을 여러 개 두어 한 스트림의 손실이 다른 스트림을 막지 않게 했어요. 또 TLS 1.3 handshake를 합쳐서 연결도 빨리 맺어요.

**꼬리질문**
- Q. 그럼 QUIC은 신뢰성이 없나요? → 있어요. UDP 위에서 재전송과 혼잡 제어를 직접 구현했어요. UDP는 "운반 수단"으로만 써요.
</details>

<details>
<summary>Q. SYN flood 공격은 무엇이고 어떻게 막나요?</summary>

**답변(30초)** SYN만 대량으로 보내고 마지막 ACK를 안 보내서, 서버에 SYN-RECEIVED 상태의 반쯤 열린 연결을 쌓아 자원을 고갈시키는 공격이에요. 대표 방어는 SYN cookies로, 연결 정보를 서버에 저장하지 않고 시퀀스 번호에 담아 두었다가 ACK가 올 때 확인해요. 그 밖에 대기열 크기 조정, 앞단 방화벽이나 로드밸런서에서 걸러 내는 방법을 함께 써요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 서버가 결제사 외부 API를 요청마다 새 HTTP 연결로 호출합니다. 트래픽이 몰리는 시간에 간헐적으로 "Cannot assign requested address" 연결 실패가 나고, 서버에서 TIME_WAIT 소켓이 수만 개 보입니다.</summary>

**상황 파악**
결제사 쪽 장애가 아니라 **우리 서버가 새 연결을 열 포트를 못 구하는** 상황이에요. 결제 실패는 돈과 직결되니 급해요. TIME_WAIT가 우리 쪽에 쌓였다는 건 **우리가 먼저 연결을 끊고 있다**는 뜻이에요.

**원인 후보**
1. 요청마다 연결을 새로 열고 먼저 닫아서, 닫을 때마다 TIME_WAIT가 하나씩 생겨요.
2. 같은 목적지(같은 IP·포트)로 가는 연결은 **내 쪽 임시 포트**만 바꿔서 구분해요. **임시 포트**(ephemeral port, 바깥으로 연결할 때 OS가 잠깐 빌려 주는 포트)는 IANA 기준 49152~65535, 약 1.6만 개예요. Linux 기본 범위는 32768~60999(약 2.8만 개)로 조금 더 넓지만 결론은 같아요.
3. TIME_WAIT는 Linux에서 60초 동안 포트를 붙잡아요. IANA 범위로 계산하면 대략 16,384개 ÷ 60초 ≈ **초당 273개** 정도가 같은 목적지로 여는 새 연결의 한계예요. 피크에 이걸 넘으면 포트가 바닥나요.

확인은 `ss`나 `netstat`으로 상태별·목적지별 개수를 세어 봐요. TIME_WAIT 대부분이 결제사 주소로 향하는지 보면 돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. HTTP 커넥션 풀 + keep-alive로 연결 재사용 (HTTP 클라이언트의 풀 설정) | 근본 해결. TIME_WAIT가 거의 안 생기고 handshake·slow start 비용도 사라져 응답도 빨라짐 | 풀 크기·유휴 타임아웃 설정 필요. 상대나 중간 장비가 유휴 연결을 끊는 경우를 대비해야 함 |
| B. 임시 포트 범위 넓히기 | 설정만으로 즉시 한계를 올림 | 한계를 미룰 뿐 원인은 그대로. 다른 서비스 포트와 겹치지 않게 주의 |
| C. TIME_WAIT 소켓 재사용 커널 옵션 (Linux `tcp_tw_reuse`) | 코드 변경 없이 완화 | 보조 수단일 뿐. 비슷한 목적의 `tcp_tw_recycle`은 NAT 환경에서 연결 실패를 일으켜 커널에서 제거됐을 만큼 이런 옵션은 조심해야 함 |
| D. 상대가 먼저 끊게 하기 | 우리 쪽 TIME_WAIT가 없어짐 | 외부 API라 우리가 정할 수 없음 |

**내가 고를 방법**
A를 먼저 해요. TIME_WAIT는 TCP가 정상적으로 동작한 결과라 없애는 게 아니라 **덜 만들어야** 해요. 연결을 재사용하면 포트 문제와 지연이 함께 줄어요. 풀의 유휴 타임아웃은 결제사나 중간 로드밸런서의 유휴 타임아웃보다 짧게 잡아서 끊긴 연결을 꺼내 쓰지 않게 해요. 당장 장애를 막아야 하면 B를 임시로 같이 적용하고, C는 원리를 이해한 상태에서만 보조로 검토해요.

**채점 포인트**: TIME_WAIT는 먼저 닫은 쪽에 생김, 2MSL(Linux 60초), 임시 포트 고갈 계산, 커넥션 풀·HTTP keep-alive로 재사용, 포트 범위 확대는 임시방편, 커널 옵션의 위험(`tcp_tw_recycle` 제거), TIME_WAIT 자체를 없애려 하지 않기.
</details>

<details>
<summary>상황: API 서버를 며칠 운영하면 "Too many open files" 에러가 나고, netstat을 보면 CLOSE_WAIT 상태 소켓이 계속 늘어나 줄지 않습니다.</summary>

**상황 파악**
**CLOSE_WAIT**는 상대가 FIN을 보내서 연결을 끊었는데 **우리 앱이 아직 close를 안 부른** 상태예요. 소켓 하나가 파일 디스크립터 하나를 쥐고 있어서, 계속 쌓이면 새 연결도 파일도 못 열어요. 시간이 지날수록 늘어난다는 건 어딘가에서 계속 새고 있다는 뜻이에요.

**원인 후보**
1. 예외가 나는 경로에서 커넥션이나 스트림을 닫지 않아요(try-with-resources·finally 누락).
2. HTTP 클라이언트로 응답을 받고 body를 다 읽거나 닫지 않아서 연결이 반납되지 않아요.
3. 커넥션 풀 바깥에서 직접 만든 연결을 버려 두고 있어요.

CLOSE_WAIT는 TCP 타이머로 저절로 사라지는 상태가 아니에요. 우리 앱이 close를 불러야 FIN이 나가요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 코드에서 close 누락 찾아 고치기 (try-with-resources, 응답 body 소비·close) | 근본 해결 | 원인 코드를 찾는 시간이 걸림. CLOSE_WAIT의 상대 주소로 어느 호출인지 좁혀야 함 |
| B. 파일 디스크립터 한도 올리기 | 즉시 버티는 시간이 늘어남 | 누수는 그대로라 결국 다시 터짐 |
| C. 주기적 재시작 | 바로 증상이 사라짐 | 원인을 가리고 운영 부담만 늘어남 |

**내가 고를 방법**
A를 해요. CLOSE_WAIT의 상대 주소와 포트로 어떤 외부 호출(DB, Redis, 외부 API)에서 새는지 먼저 좁혀요. 그 호출 코드의 예외 경로에서 자원이 닫히는지 보고 try-with-resources로 바꿔요. 고칠 때까지 B로 시간을 벌 수는 있지만 해결책으로 보지 않아요.

**채점 포인트**: CLOSE_WAIT = 상대가 먼저 끊음 + 내 앱이 close 안 함, 커널 설정이 아닌 코드 문제, 파일 디스크립터 고갈, try-with-resources·응답 body close, 상대 주소로 원인 좁히기, 한도 상향·재시작은 임시방편.
</details>

<details>
<summary>상황: 실시간 주식 시세를 앱에 푸시하는 기능을 만듭니다. 같은 서비스에는 주문·체결 기능도 있습니다. 각각 TCP와 UDP 중 무엇을 쓸지 정해 주세요.</summary>

**상황 파악**
두 기능의 요구가 반대예요. 시세는 **최신 값**이 중요하고 1초 전 값은 다시 받아도 쓸모가 없어요. 주문·체결은 **하나라도 빠지거나 순서가 바뀌면 안 돼요**.

**원인 후보 (TCP/UDP의 성질)**
1. TCP는 패킷 하나가 빠지면 재전송될 때까지 뒤 데이터도 앱에 넘기지 않아요(HOL blocking). 시세가 순간적으로 멈췄다가 몰려서 와요.
2. UDP는 빠진 걸 버리고 다음 값을 바로 쓸 수 있지만, 유실·순서 문제를 앱이 직접 다뤄야 해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 시세도 TCP(예: WebSocket) | 구현·운영이 쉬움 | 손실 시 지연이 몰려 오래된 값을 늦게 보여 줄 수 있음 |
| B. 시세는 UDP 기반(또는 QUIC) | 늦은 값은 버리고 최신 값만 빠르게 | 유실 감지, 순서 번호 같은 로직을 직접 만들어야 함 |
| C. 주문·체결은 TCP | 유실·순서 꼬임을 TCP가 막아 줌 | 지연이 조금 더 큼 (정확성이 우선이라 감수) |

**내가 고를 방법**
주문·체결은 무조건 C, TCP로 해요. 정확성이 속도보다 훨씬 중요해요. 시세는 일반 모바일 앱이라면 먼저 A로 시작해요. 만들고 운영하기 쉽기 때문이에요. 손실이 잦은 환경에서 지연이 실제 문제가 되면 B를 검토하고, 이때 메시지에 순번을 붙여 오래된 값을 버리도록 해요.

**채점 포인트**: 신뢰성 vs 지연 트레이드오프, HOL blocking, "최신 값만 중요"한 데이터는 UDP가 유리, 금융 거래는 TCP, UDP 쓸 때 앱이 유실·순서 처리, QUIC 언급.
</details>

## 필기 포인트

- TCP 헤더 최소 **20바이트**, UDP 헤더 **8바이트**(필드 4개: 출발 포트, 목적 포트, 길이, 체크섬).
- TCP 플래그: 현재 규격 **8개**(CWR, ECE, URG, ACK, PSH, RST, SYN, FIN). 6개로 묻는 문제도 있음.
- **ACK 번호 = 다음에 받기를 기대하는 시퀀스 번호.** 교재에서 "수신한 바이트 수"처럼 적혀 있어도 뜻은 이것.
- 시퀀스 번호는 **바이트 단위**. SYN·FIN은 1을 차지.
- 3-way: SYN → SYN+ACK → ACK. 4-way: FIN → ACK → FIN → ACK.
- TIME_WAIT는 **능동 종료 쪽**, **2MSL** 대기.
- 흐름 제어 = 수신자 보호, 슬라이딩 윈도우, rwnd. 윈도우 0이면 송신 중지 + probe(persist timer).
- 혼잡 제어 = 네트워크 보호, cwnd. 교재는 "흐름 제어는 종단 간, 혼잡 제어는 중간 라우터에서 발생"이라고 표현함. 시험은 이 표현대로, 면접은 "송신자가 cwnd로 조절"로 답하기.
- Slow start는 **지수 증가**, congestion avoidance는 **선형 증가**.
- 3중복 ACK → fast retransmit + fast recovery(**절반**). Timeout → cwnd **1**.
- 타임아웃 재전송 시 타이머 값 **2배**(지수 백오프).
- UDP: 비연결, 신뢰성 없음, 체크섬 있음(IPv4는 생략 가능). "UDP는 단방향"이라는 교재 표현은 "확인 없이 일방적으로 보낸다"는 뜻이지, 응답을 못 받는다는 뜻이 아님(DNS도 질의·응답을 주고받음).
