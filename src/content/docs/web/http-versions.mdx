:::tip[한 줄 요약]
HTTP/1.1은 한 연결에서 응답이 **요청 순서대로만** 와서 앞이 느리면 뒤가 막혀요(HOL 블로킹). HTTP/2는 **한 TCP 연결에 여러 요청을 프레임으로 섞어 보내서(멀티플렉싱)** 이 문제를 풀었지만, 패킷 하나가 사라지면 TCP가 전부 기다리게 만들어요. HTTP/3는 **UDP 위의 QUIC**으로 스트림마다 따로 순서를 맞춰서 그 막힘까지 없애고, 연결과 암호화를 한 번에 맺어요.
:::

## 쉽게 이해하기

택배 상자 여러 개를 한 집으로 보내는 상황이라고 생각해 봐요.

- **HTTP/1.1**은 **1차선 도로**예요. 트럭이 줄 서서 가고, 앞 트럭이 짐을 늦게 실으면 뒤 트럭은 다 기다려요. 그래서 도로를 여러 개(연결 여러 개) 깔아서 버텼어요.
- **HTTP/2**는 도로 하나에 **상자를 잘게 나눠 섞어 싣는 컨베이어 벨트**예요. 큰 상자가 늦어도 작은 상자 조각은 먼저 도착해요. 그런데 벨트 자체(TCP)가 "조각은 반드시 보낸 순서대로 내려놓는다"는 규칙을 가져요. 조각 하나가 떨어지면 그 조각을 다시 받을 때까지 **벨트 전체가 멈춰요**.
- **HTTP/3**는 **상자마다 따로 도는 작은 벨트 여러 개**예요(QUIC 스트림). 한 벨트에서 조각이 떨어져도 그 벨트만 기다리고 나머지는 계속 내려놔요.

단, 실제로 HTTP/3도 도로(UDP)는 하나고 혼잡 제어(차가 많을 때 속도 줄이기)는 연결 전체에 같이 걸려요. 독립적인 건 "순서 맞추기"예요.

## 제대로 알기

### 먼저: 바뀐 건 "뜻"이 아니라 "포장"

세 버전 모두 `GET`, `200`, `Content-Type` 같은 **의미는 같은 문서(RFC 9110)를 공유**해요. 버전이 올라가며 바뀐 건 그 메시지를 **어떻게 잘라서 실어 나르느냐**예요. 그래서 스프링 컨트롤러 코드는 버전이 바뀌어도 그대로예요. → [HTTP 기초](../http-basics/)

### HTTP/1.1: 텍스트, 한 연결에 한 줄

- 메시지는 **사람이 읽을 수 있는 텍스트**예요. 줄바꿈과 공백으로 구분해요. 읽기는 쉽지만 해석(파싱)이 복잡하고, 변형된 형식을 너무 너그럽게 받아 줘서 문제가 되기도 해요.
- **지속 연결**(persistent connection, 한 번 맺은 TCP 연결을 여러 요청에 재사용)이 기본이에요. 다만 요청은 한 연결에서 **차례로** 오가요.
- **파이프라이닝**(pipelining, 응답을 기다리지 않고 요청을 연달아 보내기)도 허용돼요. 하지만 서버는 **받은 순서대로 응답해야 해요**. 그래서 앞 요청이 느리면 뒤 응답들이 줄줄이 막혀요.
- 이렇게 맨 앞이 막혀 뒤가 다 서는 현상을 **HOL 블로킹**(Head-of-Line blocking, 줄 맨 앞 막힘)이라고 해요.
- 피하려고 브라우저는 **연결을 여러 개** 열어요(몇 개를 여는지는 브라우저가 정해요). 하지만 연결마다 서버 자원이 들고, TCP 연결끼리는 혼잡 제어를 공유하지 않아서 네트워크 효율이 나빠요.
- 헤더는 **압축하지 않아요**. 페이지 하나에 요청이 수십~수백 개인데 쿠키 같은 같은 헤더를 매번 통째로 보내서 낭비가 컸어요.

그 시절에는 흔히 **도메인 샤딩**(이미지를 `img1.`, `img2.` 같은 여러 도메인에 나눠 연결 수를 늘리기)이나 **이미지 스프라이트**(작은 이미지를 한 장에 합쳐 요청 수 줄이기) 같은 우회책을 썼다고 알려져 있어요.

### HTTP/2: 바이너리 프레임과 멀티플렉싱

- 여전히 **TCP 위**에서 동작해요. 의미는 그대로, 전송 방식만 바꿨어요.
- 메시지를 **프레임**(frame, 정해진 형식의 0과 1 덩어리)으로 잘라요. 모든 프레임은 9바이트짜리 고정 머리(길이, 종류, 플래그, 스트림 번호)를 달아요. 헤더는 `HEADERS` 프레임, 본문은 `DATA` 프레임에 실어요.
- **스트림**(stream, 한 연결 안의 독립된 대화 통로)이 요청·응답 한 쌍을 맡아요. 클라이언트가 연 스트림은 홀수 번호(1, 3, 5…), 서버가 연 건 짝수, 0번은 연결 관리용이에요.
- 여러 스트림의 프레임을 **섞어서** 보내요. 이게 **멀티플렉싱**(multiplexing, 한 길에 여러 흐름 섞어 보내기)이에요. 한 스트림이 느려도 다른 스트림은 진행돼요. **애플리케이션 계층의 HOL은 해결**됐어요.
- 헤더는 **HPACK**(HTTP/2 전용 헤더 압축)으로 줄여요. 자주 쓰는 헤더 61개를 미리 번호로 정해 둔 **정적 테이블**, 연결 중에 쌓아 가는 **동적 테이블**, 그리고 허프만 코딩을 써요. 한 번 보낸 헤더는 다음엔 번호만 보내면 돼요.
  - 일반 압축(DEFLATE)을 쓰지 않은 이유: 이전 실험 프로토콜(SPDY)이 그렇게 했다가 **CRIME 공격**(압축된 크기 변화로 쿠키 같은 비밀값을 알아내는 공격)에 당했기 때문이에요.
- 같은 서버(host:port)에는 **연결을 하나만** 열라고 권해요. 그래서 도메인 샤딩은 오히려 손해예요. 연결이 쪼개지면 멀티플렉싱도, 연결별로 쌓이는 HPACK 동적 테이블도 덜 효과적이에요.
- https에서는 TLS 핸드셰이크 중 **ALPN**(TLS가 "어떤 프로토콜 쓸래?"를 같이 정하는 확장)으로 `h2`를 고르며 시작해요. → [HTTPS와 TLS](../https-tls/)

**남은 문제: TCP 수준 HOL.** HTTP/2 표준 스스로 "TCP의 HOL 블로킹은 해결하지 않는다"고 적어 뒀어요. TCP는 바이트를 **보낸 순서대로만** 앱에 넘겨요. 스트림 1의 패킷 하나가 사라지면 그 뒤에 이미 도착한 스트림 3·5 데이터도 재전송을 기다리며 서 있어요. TCP는 그 안에 스트림이 여러 개라는 걸 모르기 때문이에요. → [TCP와 UDP](../tcp-udp/)

### HTTP/3: QUIC 위의 HTTP

- **QUIC**(퀵, UDP 위에서 TCP 역할과 TLS 암호화를 합친 전송 프로토콜) 위에 HTTP를 얹은 게 HTTP/3예요. 프레임 구조는 HTTP/2와 비슷하고, 스트림 관리는 QUIC에 맡겨요.
- QUIC 패킷은 **UDP**(연결 절차 없이 보내기만 하는 전송 방식)에 실려요. 기존 네트워크 장비를 그대로 지나가기 쉽게 하려는 선택이에요. 대신 **재전송·순서 맞추기·혼잡 제어는 QUIC이 직접** 해요. "UDP라서 믿을 수 없다"는 오해예요.
- **스트림마다 따로 순서를 맞춰요.** 받는 쪽은 각 스트림 안에서만 순서를 기다려요. 그래서 스트림 1의 패킷이 사라져도 스트림 3·5는 바로 앱으로 가요. **전송 계층 HOL까지 해결**한 거예요.
- **TLS 1.3이 QUIC 안에 들어 있어요.** 연결 맺기와 암호 협상을 한 핸드셰이크로 합쳐서 기본 **1 RTT**(한 번 왕복)에 끝나요. TCP(1 RTT) + TLS 1.3(1 RTT)를 따로 하던 것보다 왕복이 줄어요.
- **0-RTT**: 전에 연결한 적이 있으면 첫 패킷부터 요청을 실어 보낼 수 있어요. 대신 공격자가 그 패킷을 복사해 **다시 보내는(replay, 재전송 공격)** 위험이 있어요. HTTP/3 표준도 0-RTT를 쓸 때 재전송 대책을 반드시 적용하라고 해요. 실무에선 보통 **GET처럼 여러 번 실행돼도 결과가 같은(멱등) 요청만** 허용해요.
- **연결 ID**(Connection ID): QUIC 연결은 IP·포트가 아니라 연결 ID로 구분해요. 그래서 폰이 와이파이에서 LTE로 바뀌어 IP가 달라져도 같은 연결을 이어 쓸 수 있어요(**연결 마이그레이션**). 반면 TCP는 보통 (출발 IP, 출발 포트, 도착 IP, 도착 포트) 네 값으로 연결을 구분해서, 주소가 바뀌면 새로 연결해야 해요.
- 헤더 압축은 **QPACK**이에요. HPACK은 "모든 프레임이 순서대로 온다"고 가정하는데, QUIC은 스트림 간 순서를 보장하지 않아요. 그대로 쓰면 헤더 해석에서 HOL이 다시 생겨요. QPACK은 동적 테이블 갱신을 **별도 전용 스트림**(인코더/디코더 스트림)으로 주고받게 바꿨어요.

### 브라우저는 HTTP/3를 어떻게 알고 쓰나요

처음부터 UDP로 시도하지 않아요. 보통 이렇게 가요.

1. 처음엔 TCP로 접속해서 HTTP/2(또는 1.1)로 받아요.
2. 서버가 응답 헤더에 `Alt-Svc: h3=":443"`(같은 443 포트에서 HTTP/3도 돼요)라고 알려 줘요.
3. 다음 요청부터 QUIC으로 갈아타요.
4. UDP가 방화벽에 막혀 QUIC이 안 되면 TCP 기반 HTTP로 **돌아가야 해요**(폴백).

한 번 재 본 예시예요. 구글은 HTTP/2로 응답하면서 `alt-svc: h3=":443"` 헤더로 HTTP/3를 광고했어요. 반면 github.com은 이 헤더가 없었어요.

```bash
# 응답에 쓰인 HTTP 버전만 출력 (결과: 2, 1.1, 3 같은 숫자 형태)
curl -s -o /dev/null -w '%{http_version}\n' https://www.google.com
# HTTP/3 광고 헤더 확인
curl -sI --http2 https://www.google.com | grep -i '^alt-svc'
```

`curl --http3`는 curl이 HTTP/3 지원으로 빌드됐을 때만 돼요(`curl --version`의 Features에 `HTTP3`가 있어야 해요).

### 서버 푸시: 표준엔 있지만 사실상 안 써요

**서버 푸시**(server push)는 "곧 CSS도 달라고 하겠지?" 하고 서버가 먼저 보내 주는 HTTP/2 기능이에요. 그런데 HTTP/2 표준 스스로 "제대로 쓰기 어렵다"고 적었어요. 브라우저 캐시에 이미 있는 파일까지 또 보내기 쉽고, 예측이 틀리면 오히려 느려져요.

Chrome은 **Chrome 106(2022)**부터 기본으로 껐어요. 쓰는 사이트가 적었고, 이득이 불분명했고, HTTP/3 구현 다수가 푸시를 지원하지 않았기 때문이에요. 대안은 **103 Early Hints**(서버가 "이 파일 필요할 거야"라는 **힌트만** 먼저 주고, 받을지는 브라우저가 캐시를 보고 정함)와 `preload`예요. HTTP/3에서도 푸시는 표준에 있지만, 클라이언트가 허용 신호를 보내기 전엔 서버가 보낼 수 없어요.

### 한눈에 비교

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | UDP 위 QUIC |
| 메시지 형식 | 텍스트 | 바이너리 프레임 | 바이너리 프레임 |
| 한 연결에 동시 요청 | 안 됨(순서대로) | 됨(멀티플렉싱) | 됨(QUIC 스트림) |
| 앱 계층 HOL | 있음 | 해결 | 해결 |
| TCP(전송) HOL | 있음 | **남음** | 해결 |
| 헤더 압축 | 없음 | HPACK | QPACK |
| 암호화 | 선택(TLS 따로) | 표준상 선택, https면 ALPN `h2` | QUIC에 TLS 1.3 내장(필수) |
| 연결 맺기 왕복 | TCP 1 + TLS 1.3 1 | TCP 1 + TLS 1.3 1 | 1 (재방문 0-RTT 가능) |
| 네트워크 바뀌면 | 재연결 | 재연결 | 연결 ID로 이어 감 |
| 버전 알아내기 | 기본 | TLS ALPN | `Alt-Svc` 헤더 |

<Aside type="caution" title="자주 헷갈리는 점">
- **"HTTP/2가 HOL을 다 해결했다"는 틀려요.** 앱 계층 HOL만 해결했고, TCP 수준 HOL은 남아요. 그래서 패킷 손실이 잦은 망에서는 연결 하나에 모든 요청을 몰아넣은 HTTP/2가 불리할 수 있다는 분석도 있어요.
- **파이프라이닝과 멀티플렉싱은 달라요.** 파이프라이닝은 응답 순서가 고정이고, 멀티플렉싱은 프레임을 섞어 순서와 상관없이 끝나요.
- **HTTP/3도 신뢰성이 있어요.** UDP는 운반 수단이고 재전송·순서는 QUIC이 해요.
- **서버 푸시는 표준에서 지워지지 않았어요.** 브라우저가 꺼서 사실상 안 쓰는 거예요.
- **HTTP/2라고 메서드·상태코드가 바뀌지 않아요.** 바뀐 건 형식이에요(텍스트 → 프레임, 헤더 이름 소문자, `:method` 같은 의사 헤더).
- **HTTP/2는 표준상 https가 필수는 아니에요.** 다만 브라우저들은 TLS 위의 `h2`만 쓰는 걸로 알려져 있어요.
- **0-RTT는 공짜가 아니에요.** 재전송 공격 위험 때문에 멱등 요청에만 써요.
</Aside>

<summary>Q. HTTP/1.1과 HTTP/2의 차이를 설명해 주세요.</summary>

**답변(30초)** 가장 큰 차이는 멀티플렉싱이에요. HTTP/1.1은 텍스트 메시지를 한 연결에서 순서대로 주고받아서, 앞 응답이 느리면 뒤가 막히는 HOL 블로킹이 있었어요. HTTP/2는 메시지를 바이너리 프레임으로 잘라 스트림 번호를 붙이고, 한 TCP 연결에서 여러 요청을 섞어 보내요. 그리고 HPACK으로 반복되는 헤더를 압축해요. 메서드나 상태코드 같은 의미는 그대로예요.

**꼬리질문**
- Q. 1.1의 파이프라이닝이랑 뭐가 달라요? → 파이프라이닝은 요청만 연달아 보낼 뿐 응답은 요청 순서대로 와야 해요. 멀티플렉싱은 프레임을 섞어서 먼저 끝난 응답부터 받아요.
- Q. HPACK은 어떻게 줄여요? → 자주 쓰는 헤더는 정적 테이블 번호로, 이 연결에서 이미 보낸 헤더는 동적 테이블 번호로 보내요. 값은 허프만 코딩으로 줄여요.
- Q. 왜 그냥 gzip으로 압축 안 해요? → 이전 SPDY가 DEFLATE로 헤더를 압축했다가 압축 크기로 비밀값을 알아내는 CRIME 공격에 당해서, 그 위험을 줄인 전용 방식을 만들었어요.
</details>

<details>
<summary>Q. HOL 블로킹이 뭐예요? HTTP/2는 이걸 해결했나요?</summary>

**답변(30초)** 줄 맨 앞이 막혀서 뒤가 전부 기다리는 현상이에요. HTTP/1.1은 응답을 요청 순서대로 줘야 해서 앞 요청이 느리면 뒤가 막혀요. HTTP/2는 멀티플렉싱으로 이 애플리케이션 계층 HOL은 풀었어요. 하지만 TCP가 바이트를 순서대로만 넘기기 때문에 패킷 하나가 사라지면 연결 안의 모든 스트림이 멈춰요. 이 TCP 수준 HOL은 HTTP/3가 QUIC으로 해결했어요.

**꼬리질문**
- Q. QUIC은 어떻게 해결해요? → 스트림마다 따로 순서를 맞춰요. 손실된 스트림만 재전송을 기다리고 다른 스트림 데이터는 바로 앱에 넘겨요.
- Q. 그럼 HTTP/2가 1.1보다 느릴 때도 있어요? → 손실이 많은 망에선 연결 하나에 다 몰려 있어서 한 번의 손실이 모든 요청을 멈추게 해요. 그래서 불리할 수 있다는 분석이 있어요.
</details>

<details>
<summary>Q. HTTP/3는 왜 TCP 대신 UDP를 쓰나요?</summary>

**답변(30초)** TCP의 순서 보장 때문에 생기는 HOL을 없애고, 연결 수립을 빠르게 하려고요. TCP는 운영체제와 네트워크 장비에 깊이 박혀 있어서 고치기 어렵다고 알려져 있어요. 그래서 UDP를 운반 수단으로만 쓰고, 그 위에 QUIC이 재전송·혼잡 제어와 스트림별 순서 보장을 직접 해요. TLS 1.3도 QUIC에 넣어서 연결과 암호화를 1 RTT에 같이 끝내요.

**꼬리질문**
- Q. UDP면 패킷이 사라져도 모르는 거 아니에요? → QUIC이 직접 손실을 감지하고 재전송해요. UDP는 그냥 봉투 역할이에요.
- Q. 회사 방화벽이 UDP를 막으면요? → QUIC 연결이 실패하면 클라이언트는 TCP 기반 HTTP/2나 1.1로 돌아가요.
- Q. 브라우저는 서버가 HTTP/3를 지원하는지 어떻게 알아요? → 서버가 `Alt-Svc` 헤더로 `h3`를 광고하면 다음 요청부터 QUIC으로 시도해요. HTTP/2는 TLS의 ALPN으로 `h2`를 정해요.
</details>

<details>
<summary>Q. QUIC의 연결 마이그레이션과 0-RTT를 설명해 주세요.</summary>

**답변(30초)** QUIC 연결은 IP·포트 대신 연결 ID로 구분해요. 그래서 폰이 와이파이에서 LTE로 바뀌어 IP가 달라져도 같은 연결을 이어 써요. TCP라면 주소가 바뀌어 다시 연결해야 해요. 0-RTT는 전에 연결한 적이 있으면 첫 패킷에 요청을 같이 실어 보내는 기능이에요. 빠르지만 그 패킷을 복사해 다시 보내는 재전송 공격에 약해서, 보통 멱등한 GET 요청에만 써요.

**꼬리질문**
- Q. 결제 요청을 0-RTT로 보내면 왜 위험해요? → 공격자가 같은 패킷을 다시 보내면 결제가 두 번 될 수 있어요. 0-RTT는 멱등 요청만 받고, 결제는 멱등키 같은 중복 방지를 둬요.
- Q. 연결 ID는 하나만 써요? → 아니요. 주소가 바뀔 때 관찰자가 같은 연결임을 알아채지 못하게 여러 ID를 바꿔 쓰고, ID에 추적할 만한 정보를 넣지 않아야 해요.
</details>

<details>
<summary>Q. HTTP/2 서버 푸시는 왜 안 쓰나요? 대안은요?</summary>

**답변(30초)** 서버가 클라이언트에게 필요한 파일을 정확히 예측하기 어렵기 때문이에요. 브라우저 캐시에 이미 있는 파일도 또 보내기 쉽고, 예측이 틀리면 오히려 느려져요. 그래서 Chrome은 106 버전부터 기본으로 껐어요. 표준에서 지워진 건 아니고 사실상 안 쓰는 거예요. 대안은 103 Early Hints와 preload로, 서버는 힌트만 주고 받을지는 브라우저가 캐시를 보고 정해요.

**꼬리질문**
- Q. 103 Early Hints는 뭐예요? → 서버가 본 응답을 만드는 동안 먼저 보내는 임시 응답이에요. "이 CSS 필요할 거야"를 알려 주면 브라우저가 미리 받기 시작해요.
</details>

## 서술형 연습

<details>
<summary>상황: 모바일 앱 사용자들이 지하철에서 이미지 로딩이 자주 멈추거나 느리다고 합니다. 서버는 HTTP/2를 쓰고 있습니다.</summary>

**상황 파악**
지하철은 신호가 약해 **패킷 손실이 잦고**, 와이파이와 LTE 사이를 자주 **오가는** 환경이에요. 서버가 느린 게 아니라 망 상태가 원인일 가능성이 높아요. 먼저 같은 요청이 사무실 와이파이에선 빠른지, 지하철 구간에서만 느린지 나눠 봐요.

**원인 후보**
1. **TCP 수준 HOL**: HTTP/2는 이미지 여러 장을 TCP 연결 하나에 싣는데, 패킷 하나만 잃어도 모든 이미지가 같이 멈춰요.
2. **네트워크 전환 시 재연결**: IP가 바뀌면 TCP 연결이 끊겨서 TCP + TLS 핸드셰이크를 다시 해야 해요.
3. 이미지 자체가 커요(압축·리사이즈 안 함).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. HTTP/3(QUIC) 켜기(CDN이나 LB에서) | 스트림별 손실 처리로 한 이미지 손실이 다른 이미지를 안 막음, 연결 ID로 망 전환에도 연결 유지, 핸드셰이크 왕복 감소 | UDP를 막는 망에선 효과 없음(폴백 필요), LB·방화벽이 UDP를 지원해야 함, 패킷이 암호화돼 있어 디버깅·관측이 어려움 |
| B. 이미지 최적화(크기 축소, 효율 좋은 포맷, 해상도별 제공) | 프로토콜과 무관하게 전송량 자체가 줄어 손실 영향도 줄어듦 | 이미지 처리 파이프라인과 저장 비용이 늘어남 |
| C. 앱 쪽 재시도·타임아웃 조정 | 서버 변경 없이 바로 적용 | 근본 원인은 그대로, 재시도가 많으면 트래픽 증가 |

**내가 고를 방법**
A와 B를 같이 해요. 원인이 "손실 많은 망 + 망 전환"이라 HTTP/3가 정확히 겨냥하는 상황이에요. CDN이 지원하면 설정으로 켤 수 있어 비용도 적어요. 다만 UDP가 막히면 HTTP/2로 **폴백이 제대로 되는지** 꼭 확인하고, QUIC 도입 후 로딩 시간과 실패율을 다시 재요. B는 어떤 프로토콜이든 효과가 있어서 같이 적용해요.

**채점 포인트**: 손실 많은 망 = TCP 수준 HOL, HTTP/2는 앱 계층 HOL만 해결, QUIC 스트림별 순서 보장, 연결 ID·마이그레이션, UDP 차단 시 TCP 폴백, LB·방화벽 UDP 지원, 도입 후 재측정.
</details>

<details>
<summary>상황: HTTP/1.1 시절 정적 파일을 static1~4 도메인으로 나눠 뒀습니다. HTTP/2로 바꿨는데 속도가 거의 안 좋아졌어요.</summary>

**상황 파악**
HTTP/2의 이점은 **한 연결에 요청을 모아** 멀티플렉싱하고, 그 연결에서 헤더 압축 테이블을 재사용하는 데서 나와요. 도메인이 4개로 나뉘어 있으면 연결도 최소 4개로 쪼개져요.

**원인 후보**
1. **도메인 샤딩이 그대로 남음**: 연결마다 TCP + TLS 핸드셰이크를 따로 하고, 요청이 흩어져 멀티플렉싱 효과가 줄어요.
2. **HPACK 동적 테이블이 연결별**이라 같은 헤더를 연결마다 다시 처음부터 쌓아요.
3. 이미지 스프라이트·파일 합치기도 남아 있어서, 일부만 바뀌어도 큰 파일 전체의 캐시가 깨져요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 샤딩 제거, 정적 파일을 한 도메인으로 합치기 | 연결 하나로 멀티플렉싱·헤더 압축 이점을 다 누림 | 모든 HTML·앱의 URL을 바꿔야 함, 옛 URL 리다이렉트·캐시 정리 필요, 아직 HTTP/1.1로 오는 클라이언트는 연결 수가 줄어 느려질 수 있음 |
| B. 도메인은 두되 **연결 재사용(coalescing)** 되게 하기: 같은 IP + 4개 도메인을 다 덮는 인증서 | URL을 안 바꾸고 HTTP/2 연결을 하나로 합칠 수 있음 | 인증서·DNS 설정 관리가 필요하고, 재사용 여부는 브라우저 판단이라 확실하지 않음 |

**내가 고를 방법**
장기적으로는 A예요. 구조가 단순해지고 결과가 확실해요. 당장 URL을 바꾸기 어려우면 B로 먼저 효과를 보고, 다음 배포 때 A로 옮겨요. 스프라이트나 합친 파일도 HTTP/2에선 이득이 적으니 점차 개별 파일로 나눠 캐시 효율을 높여요.

**채점 포인트**: HTTP/2는 host:port당 연결 1개 권장, 샤딩이 연결을 쪼갬, HPACK 동적 테이블은 연결별, connection coalescing(인증서·IP), HTTP/1.1 클라이언트 영향, 스프라이트 캐시 단점.
</details>

<details>
<summary>상황: 응답 속도를 높이려고 결제 API에 HTTP/3의 0-RTT를 켜자는 제안이 나왔습니다.</summary>

**상황 파악**
0-RTT는 재방문 클라이언트가 핸드셰이크를 끝내기 전에 첫 패킷에 요청을 실어 보내는 기능이에요. 왕복 하나를 아끼지만, 그 데이터는 **재전송 공격**에 약해요. 결제는 두 번 실행되면 안 되는 대표적인 요청이에요.

**원인 후보(위험 요소)**
1. 공격자가 0-RTT 패킷을 복사해 다시 보내면 **같은 결제가 두 번** 처리될 수 있어요.
2. QUIC 자체 처리는 안전해도, 그 위에 실린 **애플리케이션 요청은 재생될 수 있어요**.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 0-RTT를 GET 같은 안전·멱등 요청에만 허용 | 조회 화면은 빨라지고 결제는 안전 | 결제 자체는 빨라지지 않음, 요청 종류별 설정 관리 필요 |
| B. 결제 API에 **멱등키**(요청마다 고유 ID, 같은 ID는 한 번만 처리) | 0-RTT든 네트워크 재시도든 중복 결제를 막음 | 서버가 키를 저장·조회해야 해서 구현·저장 비용 |
| C. 0-RTT 전체 끄기 | 가장 단순하고 안전 | 재방문 속도 이점을 포기 |

**내가 고를 방법**
A와 B를 같이 써요. 0-RTT는 조회성 요청에만 켜서 속도 이점은 챙기고, 결제는 0-RTT로 받지 않아요. 그리고 결제 API에는 원래부터 멱등키를 둬요. 0-RTT가 아니어도 모바일 재시도로 중복 요청은 생길 수 있기 때문이에요. 왕복 하나 아끼는 것보다 중복 결제 한 번의 비용이 훨씬 커요.

**채점 포인트**: 0-RTT = 재전송(replay) 위험, 멱등 요청만 허용, HTTP/3 표준이 0-RTT 재전송 대책 요구, 멱등키, 속도 이점 vs 안전성.
</details>

## 필기 포인트

- 세 버전 모두 의미는 RFC 9110 공유. HTTP/1.1 = RFC 9112, HTTP/2 = RFC 9113, HTTP/3 = RFC 9114, QUIC = RFC 9000.
- HTTP/1.1: 텍스트, 지속 연결 기본, 파이프라이닝은 응답 순서 고정 → HOL.
- HTTP/2: 바이너리 프레임(고정 9바이트 헤더), 스트림 ID 클라이언트 홀수/서버 짝수/0 = 연결 제어, 멀티플렉싱, HPACK(정적 테이블 61개, 인덱스 1부터), ALPN `h2`, TCP HOL은 남음.
- HTTP/3: UDP 위 QUIC, TLS 1.3 내장, 기본 1-RTT(재방문 0-RTT), 연결 ID로 마이그레이션, QPACK(정적 테이블 99개, 인덱스 0부터, 인코더/디코더 스트림), `Alt-Svc`로 `h3` 광고, ALPN 토큰 `h3`.
- 서버 푸시: HTTP/2·3 표준에 남아 있음. Chrome 106부터 기본 비활성. 대안 103 Early Hints, preload.
- h2c(평문 Upgrade 방식)는 RFC 9113에서 deprecated.
