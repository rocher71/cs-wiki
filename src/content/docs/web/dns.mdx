:::tip[한 줄 요약]
DNS는 **도메인 이름을 IP 주소로 바꿔 주는 분산된 주소록**이에요. 내 컴퓨터는 리졸버에게 "끝까지 찾아와 줘"라고 한 번 묻고(재귀 질의), 리졸버가 **루트 → TLD → 권한 서버**를 차례로 물어(반복 질의) 답을 받아 와요. 답에는 **TTL**이 붙어 있어서 그 시간 동안 브라우저·OS·리졸버가 캐시해요.
:::

:::note[처음이라면 여기까지]
① DNS는 google.com 같은 이름을 컴퓨터가 쓰는 숫자 주소(IP)로 바꿔 주는 주소록이에요.

② 내 컴퓨터는 리졸버(대신 찾아 주는 서버)에게 한 번만 물어요. 리졸버가 루트 → TLD(.com 같은 끝자리) → 권한 서버 순서로 물어서 답을 가져와요.

③ 답에는 유효기간(TTL)이 붙어 있어서, 그동안은 다시 묻지 않고 저장해 둔 답을 써요.

④ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

**전화번호부**를 떠올려 봐요. 사람은 "김철수"라는 이름을 기억하지만 전화를 걸려면 번호가 필요해요. 인터넷도 같아요. 우리는 `example.com`을 치지만 컴퓨터는 `203.0.113.10` 같은 **IP 주소**(인터넷 위의 숫자 주소)로만 상대를 찾아요.

그런데 전 세계 이름을 한 권에 다 담을 수는 없어요. 그래서 전화번호부를 **층층이 나눠** 둬요. 맨 위 안내 데스크(루트)는 "`.com`은 저 창구로 가세요"만 알려 주고, `.com` 창구는 "`example.com`은 이 회사 담당자에게 물어보세요"만 알려 줘요. 마지막 담당자(권한 서버)만 실제 번호를 알아요.

이 창구들을 직접 돌아다니는 건 귀찮으니 **비서(리졸버)** 에게 맡겨요. 비서는 찾아낸 번호를 **메모지에 적어 두고** 한동안 다시 묻지 않아요. 메모지에는 "이 번호는 5분까지만 믿어"처럼 **유효 시간(TTL)** 이 같이 적혀 있어요.

단, 실제로는 비서가 매번 맨 위 안내 데스크부터 가지 않아요. `.com` 창구 위치 같은 중간 정보도 메모해 두기 때문에 대부분은 바로 마지막 담당자에게 가거나, 아예 메모지에서 끝나요.

## 제대로 알기

### 왜 필요할까: 이름과 주소를 나누기

사람이 숫자 IP를 외우기는 어렵고, 서버를 옮기면 IP가 바뀌어요. 이름과 주소 사이에 **DNS**(Domain Name System, 이름 → 주소 변환 시스템)를 두면 사용자는 같은 이름을 계속 쓰고, 운영자는 뒤에서 IP만 바꾸면 돼요.

DNS는 세 부분으로 이뤄져요.

| 구성 | 뜻 |
|---|---|
| **이름 공간과 레코드** | 이름들의 나무 구조, 그리고 이름마다 붙은 정보(레코드) |
| **네임서버** | 나무의 한 구역에 대한 정보를 가진 서버 |
| **리졸버** | 질문을 받아 네임서버들에게 대신 물어 주는 프로그램 |

DNS는 TCP/IP 4계층 기준으로 **응용 계층** 프로토콜이에요. → [네트워크 계층](../network-layers/)

### 이름은 나무 모양: 루트, TLD, 권한 서버

`www.example.com.`은 **오른쪽이 위**예요. 맨 끝의 보이지 않는 점(`.`)이 **루트**, 그 아래 `com`, 그 아래 `example`, 그 아래 `www`예요.

- **TLD**(Top-Level Domain, 최상위 도메인): `com`, `net`, `kr`처럼 루트 바로 아래 이름.
- **영역**(zone, 한 관리 주체가 맡는 구역): 나무를 구역별로 잘라 각자 관리해요. 이렇게 하위 구역 관리를 넘기는 걸 **위임**(delegation)이라고 해요.
- 상위 영역은 하위 영역의 답을 갖고 있지 않아요. 대신 "저 서버에 물어봐"라는 **NS 레코드**만 줘요. 그 서버 이름이 하위 영역 안에 있으면 IP도 같이 주는데, 이를 **글루**(glue) 레코드라고 해요. 이름만 주면 그 이름을 또 찾아야 해서 끝없이 돌기 때문이에요.
- **apex**(에이펙스, 영역의 꼭대기 이름): `www.example.com`이 아닌 `example.com` 자체를 말해요.
- 라벨(점 사이 한 칸)은 최대 63바이트, 전체 이름은 최대 255바이트예요.

서버 역할도 이름이 정해져 있어요.

| 역할 | 하는 일 | 예 |
|---|---|---|
| **스텁 리졸버** | OS 안의 단순한 리졸버. 질문을 재귀 리졸버에 넘기기만 해요 | 내 노트북, 폰 |
| **재귀 리졸버** | 대신 끝까지 찾아다니고 결과를 캐시해요 | 통신사 DNS, 8.8.8.8, 사내 DNS |
| **권한 네임서버** | 그 영역의 원본 데이터를 가진 서버. 응답에 **AA**(권한 있는 답) 표시를 붙여요 | 도메인을 산 곳이나 DNS 업체의 서버 |

**루트 서버는 13대가 아니에요.** a부터 m까지 13개의 **이름**이 있고, 각 이름 뒤에서 **애니캐스트**(같은 IP를 여러 곳에서 동시에 운영해 가까운 곳이 답하는 방식)로 전 세계 수많은 서버가 돌아가요.

### 재귀 질의 vs 반복 질의

둘 다 "누가 끝까지 찾아다니느냐"의 차이예요.

| | 재귀(recursive) 질의 | 반복(iterative) 질의 |
|---|---|---|
| 요청 뜻 | "답을 끝까지 찾아와 줘" | "아는 만큼만 알려 줘" |
| 받는 답 | 최종 답(또는 에러)만 | 답, 또는 "더 가까운 서버는 여기" |
| 다음 서버에 가는 쪽 | 질문받은 서버 | 질문한 쪽 |
| 실제 쓰이는 구간 | 스텁 리졸버 → 재귀 리졸버 | 재귀 리졸버 → 루트·TLD·권한 서버 |
| 헤더 표시 | 요청에 **RD**(재귀 원함), 응답에 **RA**(재귀 가능) | 루트·TLD 서버 응답엔 RA가 없어요 |

루트·TLD 서버는 재귀를 해 주지 않아요. 직접 물어보면 답 칸은 비어 있고, "`.com`은 이 서버들에 물어봐"라는 위임 정보만 와요.

<Aside type="caution" title="여기서 많이 틀려요">
"루트 → TLD → 권한을 차례로 도는 것 = 재귀 질의"가 아니에요. 그렇게 차례로 도는 과정은 리졸버 입장에서 **반복** 질의예요. 재귀는 "대신 끝까지 찾아와 달라"는 **요청 방식**이에요. 시험 교재는 recursive / non-recursive / iterative 세 가지로 쓰기도 하는데, 표준 문서에서는 non-recursive와 iterative가 같은 쪽이에요.
</Aside>

### 레코드 종류

레코드 하나는 **이름, 타입, 클래스, TTL, 값**으로 이뤄져요.

| 타입 | 뜻 | 예 |
|---|---|---|
| **A** | 이름 → IPv4 주소 | `example.com → 203.0.113.10` |
| **AAAA** | 이름 → IPv6 주소 | `example.com → 2001:db8::10` |
| **CNAME** | 이 이름은 다른 이름의 **별칭** | `www.github.com → github.com` |
| **MX** | 이 도메인으로 오는 메일을 받는 서버. **숫자가 작을수록 우선** | `10 mail1`, `20 mail2` |
| **NS** | 이 영역의 권한 네임서버가 누구인지. 위임에 써요 | `example.com → ns1.dns-provider.net` |
| **TXT** | 아무 문자열. SPF(메일 발신 허용 서버 목록), 도메인 소유 확인 토큰 등에 써요 | `"v=spf1 -all"` |
| **SOA** | 영역의 기본 정보. 영역마다 하나, apex에 둬요 | 주 네임서버, 관리자 메일, 버전 번호 등 |
| **PTR** | 거꾸로 IP → 이름(역방향 조회) | `in-addr.arpa` 아래에 둬요 |

**SOA**(Start of Authority) 필드는 이렇게 생겼어요.

- MNAME: 주 네임서버 / RNAME: 관리자 메일(`@` 대신 `.`)
- SERIAL: 영역 버전 번호. 바꿀 때마다 올려요
- REFRESH, RETRY, EXPIRE: 보조 서버가 주 서버를 얼마나 자주 확인할지
- MINIMUM: 지금은 **"없음" 답을 캐시하는 시간**으로 써요(아래 부정 캐시)

### 심화: CNAME 규칙과 apex 문제

리졸버는 CNAME을 만나면 그 대상 이름으로 다시 찾아요. 그런데 규칙이 하나 있어요. **CNAME이 있는 이름에는 다른 레코드를 같이 둘 수 없어요**(DNSSEC용 레코드만 예외).

apex(`example.com`)에는 SOA와 NS가 **반드시** 있어야 해요. 그래서 apex에는 CNAME을 둘 수 없어요. 클라우드 로드밸런서처럼 IP 대신 호스트 이름을 주는 서비스를 apex에 연결하려면 이렇게 해요.

| 방법 | 설명 | 주의 |
|---|---|---|
| 업체 기능(ALIAS, CNAME flattening) | DNS 서버가 안에서 대상 이름을 따라가 A/AAAA로 바꿔 응답해요. AWS Route 53의 Alias, Cloudflare의 CNAME flattening이 예예요 | 표준이 아니라 업체 기능이에요 |
| apex는 A 레코드, `www`만 CNAME | apex는 고정 IP로, 나머지는 별칭으로 | 대상 IP가 바뀌면 직접 고쳐야 해요 |

MX와 NS의 값도 CNAME이면 안 되고, 실제 A/AAAA가 있는 이름이어야 해요.

### TTL과 캐시

모든 레코드에는 **TTL**(Time To Live, 이 답을 캐시해도 되는 시간, 초 단위)이 붙어 있어요.

- **TTL 0**은 "캐시하지 말고 이번에만 써"라는 뜻이에요. 영원히가 아니에요.
- 캐시는 **남은 시간을 깎아 가며** 답해요. 권한 서버는 항상 원래 TTL(예: 300)을 주지만, 리졸버 캐시에서 받은 답은 더 작은 값(예: 283)이 나와요.
- **부정 캐시**(negative caching): "그런 이름 없음"(NXDOMAIN)이나 "그 타입 레코드 없음"도 캐시돼요. 시간은 SOA 레코드의 TTL과 SOA MINIMUM 중 **작은 값**이에요.

캐시는 여러 층에 있어요. 가까운 순서로 봐요.

1. **브라우저 캐시**: Chrome은 `chrome://net-internals/#dns`에서 보고 비울 수 있어요.
2. **OS 캐시 + hosts 파일**: macOS는 mDNSResponder, Windows는 DNS Client 서비스가 맡아요.
3. **재귀 리졸버 캐시**: `.com`의 NS 같은 중간 정보도 따로 캐시해요. 그래서 루트까지 가는 일은 드물어요.
4. 다 없으면 루트 → TLD → 권한 서버를 돌아요.

**앱도 따로 캐시해요.** Java는 `InetAddress`가 결과를 캐시하고, `networkaddress.cache.ttl` 보안 속성으로 조절해요. 시큐리티 매니저가 없으면 기본 30초, 실패 답은 `networkaddress.cache.negative.ttl` 기본 10초예요. 이건 DNS 레코드의 TTL과 **따로** 움직여요.

또 일부 리졸버나 클라이언트는 TTL을 정확히 지키지 않아요(최솟값·최댓값으로 잘라 쓰거나 더 오래 붙잡아요). 그래서 TTL은 "정확히 이 시간 뒤 바뀐다"가 아니라 **"옛 답이 최대 TTL만큼, 일부에선 그보다 오래 남을 수 있다"** 로 보고 계획해요.

<Aside type="note" title="'DNS 전파'라는 말">
레코드를 바꾸면 "전파되는 데 시간이 걸린다"고들 말해요. 실제로는 새 값이 퍼져 나가는 게 아니라, 곳곳에 남은 **옛 캐시가 TTL이 끝나 사라지기를 기다리는** 거예요.
</Aside>

### TTL과 배포·장애 전환

서버 IP를 바꾸는 순서예요.

1. **미리 TTL을 낮춰요**(예: 3600 → 60).
2. **옛 TTL만큼 기다려요.** 이미 퍼진 캐시는 옛 TTL(3600초)로 살아 있어서, 낮춘 값이 퍼질 때까지 1시간이 걸려요.
3. 레코드를 **새 IP로 바꿔요.** 이제 약 60초면 대부분 새 IP로 가요.
4. **옛 서버를 한동안 살려 둬요.** TTL을 안 지키는 캐시나 앱 캐시 때문이에요.
5. 안정되면 **TTL을 다시 올려요.**

TTL은 짧게도 길게도 장단점이 있어요.

| | 짧은 TTL(예: 60초) | 긴 TTL(예: 1일) |
|---|---|---|
| 바꾼 값 반영 | 빨라요 | 느려요 |
| DNS 질의 수 | 많아요. 조회 지연과 권한 서버 부하가 늘어요 | 적어요 |
| DNS 서버가 죽었을 때 | 캐시가 빨리 비어 영향이 바로 커져요 | 캐시로 한동안 버텨요 |

한 번 재 본 예로 `example.com`의 A 레코드는 300초, NS는 21600초(6시간), `github.com`의 A 레코드는 60초였어요. 자주 바뀔 수 있는 건 짧게, 거의 안 바뀌는 건 길게 잡는 경향이 보여요.

**DNS로 부하 나누기**도 가능해요.

- **라운드 로빈 DNS**: 한 이름에 A 레코드를 여러 개 둬요. 하지만 클라이언트가 캐시하니 분산이 고르지 않고, DNS 자체는 **서버가 살아 있는지 확인(헬스체크)하지 않아요.** 관리형 DNS는 헬스체크 후 죽은 서버 레코드를 빼 주는 기능을 따로 팔아요.
- **GeoDNS**: 묻는 쪽 위치에 따라 가까운 리전·CDN의 IP를 줘요. 표준이 아니라 DNS 업체 기능이에요.

→ 진짜 부하 분산은 [로드밸런서와 프록시](../load-balancer-proxy/)에서 다뤄요.

### 심화: UDP 53과 TCP 53

| 언제 | 무엇을 써요 |
|---|---|
| 평소 질의·응답 | **UDP 53**. 질문과 답이 작고, 연결을 맺지 않아 빨라요 |
| 응답이 커서 잘렸을 때 | 원래 UDP 메시지는 512바이트까지예요. 넘치면 응답에 **TC**(잘림) 표시가 켜지고, 클라이언트가 **TCP 53**으로 다시 물어요 |
| 영역 전송(AXFR, 주 서버 → 보조 서버 복사) | **TCP 53** |

**EDNS(0)** 는 "나는 UDP로 4096바이트까지 받을 수 있어"처럼 크기를 알려 512바이트보다 큰 답도 UDP로 받게 해 줘요. 요즘 규격은 모든 DNS 구현이 TCP도 지원해야 한다고 정해요. → [TCP와 UDP](../tcp-udp/)

DNS는 원래 암호화가 없어서 중간에서 보거나 바꿀 수 있어요. 그래서 **DoH**(DNS over HTTPS, HTTPS에 실어 보내기, 보통 443 포트)와 **DoT**(DNS over TLS, 853 포트)가 나왔어요. → [HTTPS와 TLS](../https-tls/)

### 직접 해 보기: dig

터미널에서 `dig`로 확인할 수 있어요(macOS·Linux 기본 제공).

```bash
# A 레코드 조회. ANSWER 칸에 IP와 TTL이 나와요
dig example.com A
# 공개 리졸버에 직접 묻기
dig @8.8.8.8 example.com
# 메일 서버. 앞 숫자가 작을수록 우선
dig +short gmail.com MX
# TCP 53으로 묻기
dig +tcp example.com

# 루트 → TLD → 권한 서버를 손으로 따라가기
# (+norec = 재귀 말고 아는 만큼만 답해 줘)
dig @a.root-servers.net com NS +norec
dig @a.gtld-servers.net example.com NS +norec
# 위 결과에 나온 권한 서버 이름을 넣어요. flags에 aa가 보여요
dig @(권한 서버 이름) example.com A +norec
```

`dig +trace example.com`을 쓰면 이 과정을 한 번에 보여 주지만, 네트워크 환경에 따라 안 될 때가 있어요. 그럴 땐 위처럼 한 단계씩 따라가면 돼요. 같은 질문을 몇 초 뒤 다시 하면 TTL이 줄어든 걸 볼 수도 있어요(공개 리졸버는 캐시 서버가 여러 대라 원래 값이 다시 나오기도 해요).

<Aside type="caution" title="자주 헷갈리는 점">
- **"DNS는 UDP만 써요"** → 기본은 UDP 53이지만, 잘린 큰 응답과 영역 전송은 TCP 53을 써요.
- **"매번 루트부터 물어요"** → 대부분 캐시에서 끝나요.
- **"루트 서버는 13대"** → 13개 이름이고, 실제 서버는 애니캐스트로 훨씬 많아요.
- **"TTL 낮추고 바로 IP 바꾸면 돼요"** → 낮추기 전 옛 TTL만큼 기다려야 효과가 있어요.
- **"apex에도 CNAME 걸면 돼요"** → 표준상 안 돼요. ALIAS·flattening은 업체 기능이에요.
- **"TTL 0 = 영원히 캐시"** → 반대예요. 캐시하지 말라는 뜻이에요.
- **"DNS 라운드 로빈 = 로드밸런서"** → 헬스체크가 없고 캐시 때문에 고르게 안 나뉘어요.
- **"앱은 DNS TTL을 따라요"** → JVM 같은 런타임이 따로 캐시해요.
</Aside>

## 면접 질문

<details>
<summary>Q. 브라우저에 도메인을 입력하면 IP를 어떻게 찾나요?</summary>

**답변(30초)** 가까운 캐시부터 보고, 없으면 리졸버가 대신 찾아와요. 브라우저 캐시 → OS 캐시와 hosts 파일을 보고, 없으면 OS가 재귀 리졸버에게 재귀 질의를 보내요. 리졸버는 루트 서버에서 `.com` 담당 서버를, `.com` 서버에서 그 도메인의 권한 서버를 안내받고, 권한 서버에서 실제 IP를 받아요. 받은 답은 TTL 동안 리졸버·OS·브라우저에 캐시돼서 다음엔 바로 끝나요.

**꼬리질문**
- Q. 매번 루트까지 가나요? → 아니요. 리졸버가 `.com` NS 같은 중간 결과도 캐시해서 루트까지 가는 일은 드물어요.
- Q. 루트 서버는 몇 대예요? → 13개의 이름이 있고, 각 이름 뒤에 애니캐스트로 운영되는 서버가 전 세계에 많이 있어요.
</details>

<details>
<summary>Q. 재귀 질의와 반복 질의의 차이는 뭔가요?</summary>

**답변(30초)** 누가 끝까지 찾아다니느냐의 차이예요. 재귀 질의는 "최종 답을 찾아와 달라"는 요청이라 질문받은 서버가 대신 돌아다니고 최종 답만 돌려줘요. 반복 질의는 서버가 아는 만큼만 답하고 "다음은 저 서버에 물어봐"라고 알려 주면 질문한 쪽이 직접 다음 서버로 가요. 보통 내 PC → 리졸버는 재귀, 리졸버 → 루트·TLD·권한 서버는 반복이에요.

**꼬리질문**
- Q. 루트 서버는 왜 재귀를 안 해 줘요? → 전 세계 요청을 다 대신 찾아 주면 부하가 너무 커요. 루트는 위임 정보만 주고 실제 찾기는 리졸버가 맡아요.
- Q. 헤더에서는 어떻게 구분해요? → 요청의 RD 비트가 "재귀 원함", 응답의 RA 비트가 "재귀 가능"이에요.
</details>

<details>
<summary>Q. A, AAAA, CNAME, MX, NS 레코드를 설명해 주세요.</summary>

**답변(30초)** A는 이름을 IPv4 주소로, AAAA는 IPv6 주소로 바꿔요. CNAME은 이 이름이 다른 이름의 별칭이라는 뜻이라 리졸버가 그 이름으로 다시 찾아요. MX는 메일을 받는 서버이고 숫자가 작을수록 우선이에요. NS는 이 영역의 권한 네임서버가 누구인지 알려 주고, 상위 영역이 하위 영역을 위임할 때 써요.

**꼬리질문**
- Q. 루트 도메인(apex)에 CNAME을 못 쓰는 이유는? → CNAME이 있는 이름에는 다른 레코드를 둘 수 없는데, apex에는 SOA와 NS가 꼭 있어야 해서 충돌해요. 그래서 업체의 ALIAS나 CNAME flattening을 써요.
- Q. TXT는 어디에 써요? → SPF처럼 메일 발신 허용 서버를 적거나, 도메인 소유 확인 토큰을 넣을 때 써요.
</details>

<details>
<summary>Q. TTL이 뭔가요? 짧게 잡을 때와 길게 잡을 때 장단점은요?</summary>

**답변(30초)** TTL은 DNS 답을 캐시해도 되는 시간이에요. 짧으면 레코드를 바꿨을 때 빨리 반영되지만, 질의가 늘어서 조회가 느려지고 DNS 서버 부하가 커지며 DNS가 죽으면 영향이 바로 와요. 길면 질의가 줄고 DNS 장애에도 캐시로 버티지만 바꾼 값이 늦게 반영돼요. 그래서 평소엔 적당히 길게 두고, IP를 바꾸기 전에 미리 짧게 낮춰요.

**꼬리질문**
- Q. 부정 캐시가 뭐예요? → "그런 이름 없음"이라는 답도 캐시하는 거예요. 시간은 SOA의 TTL과 MINIMUM 중 작은 값이에요.
- Q. TTL을 낮추면 바로 효과가 있나요? → 아니요. 이미 퍼진 캐시는 옛 TTL로 살아 있어서 옛 TTL만큼 기다려야 해요.
</details>

<details>
<summary>Q. DNS는 UDP를 쓰나요, TCP를 쓰나요?</summary>

**답변(30초)** 둘 다 53번 포트를 쓰고, 기본은 UDP예요. 질문과 답이 작아서 연결을 맺는 TCP보다 UDP가 빠르기 때문이에요. 다만 응답이 너무 커서 잘리면 TC 비트가 켜지고 클라이언트가 TCP로 다시 물어요. 주 서버에서 보조 서버로 영역 전체를 복사하는 영역 전송도 TCP를 써요.

**꼬리질문**
- Q. 512바이트를 넘는 답은 무조건 TCP인가요? → EDNS(0)로 받을 수 있는 크기를 알리면 더 큰 답도 UDP로 받을 수 있어요.
- Q. 방화벽에서 TCP 53을 막으면? → 평소엔 되다가 큰 응답만 간헐적으로 실패해요. TCP 53도 열어야 해요.
- Q. DoH는 왜 써요? → DNS는 원래 평문이라 중간에서 보거나 바꿀 수 있어요. HTTPS에 실어 보내면 도청과 변조를 막아요.
</details>

<details>
<summary>Q. DNS로 로드밸런싱을 할 수 있나요?</summary>

**답변(30초)** 한 이름에 A 레코드를 여러 개 두는 라운드 로빈 DNS로 어느 정도는 돼요. 하지만 클라이언트와 리졸버가 답을 캐시해서 분산이 고르지 않아요. 또 DNS는 서버가 살아 있는지 확인하지 않아서 죽은 서버로도 보내요. 그래서 관리형 DNS의 헬스체크 기능을 쓰거나, 정교한 분산은 로드밸런서에 맡겨요.

**꼬리질문**
- Q. GeoDNS는 뭐예요? → 묻는 쪽 위치에 따라 가까운 리전이나 CDN의 IP를 주는 방식이에요. 표준이 아니라 DNS 업체 기능이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 다음 주 화요일 새벽에 서비스 서버를 새 데이터센터(새 IP)로 옮깁니다. DNS 쪽 계획을 세워 주세요.</summary>

**상황 파악**
사용자는 도메인 이름으로 들어오니 A 레코드만 새 IP로 바꾸면 돼요. 문제는 **캐시**예요. 현재 TTL이 3600초라면, 바꾼 뒤에도 최대 1시간(TTL을 안 지키는 곳은 더 오래) 옛 IP로 가는 사용자가 생겨요.

**원인 후보(옛 IP가 남는 곳)**
1. 재귀 리졸버(통신사, 공개 DNS) 캐시
2. OS·브라우저 캐시
3. 앱 런타임 캐시(우리 서비스를 호출하는 다른 서버가 Java라면 JVM의 `InetAddress` 캐시)
4. TTL을 제대로 지키지 않는 일부 리졸버

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. TTL 미리 낮추기(3600 → 60), 옛 TTL만큼 기다린 뒤 IP 변경 | 바꾼 뒤 1분 안팎이면 대부분 새 IP로 와요 | 낮춘 동안 DNS 질의가 늘어 조회 지연과 DNS 부하가 늘어요 |
| B. 옛 서버를 일정 기간 유지하거나 새 서버로 요청 전달 | 늦게 바뀐 사용자도 정상 이용 | 두 곳 운영 비용, 쓰기 데이터가 양쪽에 생기지 않게 관리 필요 |
| C. DNS 앞단을 로드밸런서·애니캐스트 IP로 고정하고 그 뒤 서버만 교체 | DNS 캐시와 무관하게 즉시 전환 | 구조 변경과 비용이 들고, 이번 이전 일정엔 과할 수 있어요 |

**내가 고를 방법**
A와 B를 같이 써요. 이전 최소 하루 전에 TTL을 60으로 낮추고, 옛 TTL(1시간) 이상 지난 뒤 IP를 바꿔요. 바꾼 뒤에도 옛 서버를 하루 정도 살려 두고 새 서버로 요청을 넘겨, 늦게 오는 사용자도 끊기지 않게 해요. 우리 서비스를 부르는 내부 서버에는 JVM DNS 캐시 설정을 확인하라고 공유해요. 전환이 안정되면 TTL을 원래대로 올려 DNS 부하를 되돌려요. 이전이 자주 반복된다면 다음엔 C처럼 DNS가 가리키는 주소 자체를 고정하는 구조를 검토해요.

**채점 포인트**: TTL 사전 인하, **옛 TTL만큼 대기**, IP 변경, 옛 서버 유지, TTL 원복, 짧은 TTL의 부하 트레이드오프, JVM 등 앱 캐시, TTL 미준수 리졸버.
</details>

<details>
<summary>상황: 리전 하나가 통째로 장애가 났습니다. DNS로 다른 리전에 트래픽을 돌렸는데 몇 분이 지나도 일부 사용자는 계속 에러를 봅니다.</summary>

**상황 파악**
DNS 레코드는 바꿨지만 사용자 쪽 캐시에 **죽은 리전의 IP**가 남아 있어요. DNS 기반 전환은 캐시 때문에 즉시 끝나지 않아요.

**원인 후보**
1. 레코드 TTL이 길게(예: 수십 분 이상) 잡혀 있었어요.
2. 일부 리졸버·클라이언트가 TTL을 늘려 쓰거나 오래 붙잡아요.
3. 앱 런타임(JVM 등)이 DNS 결과를 따로 캐시해요.
4. 사람이 장애를 알아채고 레코드를 바꾸기까지 시간이 걸렸어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 짧은 TTL(30~60초) + 헬스체크 기반 관리형 DNS 자동 전환 | 사람 개입 없이 죽은 리전 레코드를 빼 줘요. 구성이 비교적 단순 | 평소에도 DNS 질의가 많아요. 캐시를 안 지키는 곳은 여전히 늦어요 |
| B. 로드밸런서·애니캐스트 단에서 전환(DNS는 고정 주소) | DNS 캐시와 상관없이 바로 전환 | 비용이 들고, 그 앞단 자체가 하나뿐이면 단일 장애점이 돼요 |

**내가 고를 방법**
지금 당장은 A로 바꿔요. 헬스체크를 붙여 자동으로 레코드가 빠지게 하고 TTL을 짧게 둬요. 그래도 몇 분의 꼬리는 남으니, 장애 시간 목표가 아주 짧은 서비스라면 B를 함께 검토해요. 앱 쪽 DNS 캐시 시간도 짧게 맞춰 둬요.

**채점 포인트**: DNS 전환은 캐시 때문에 즉시가 아님, TTL과 전환 속도·부하 트레이드오프, 헬스체크(DNS 자체엔 없음), LB/애니캐스트 대안과 단일 장애점, 앱 런타임 캐시.
</details>

<details>
<summary>상황: 방금 새 서브도메인 레코드를 만들었는데, 팀원 PC에서는 계속 "주소를 찾을 수 없음"이 뜹니다.</summary>

**상황 파악**
레코드는 권한 서버에 있는데 일부 사람에게만 안 보여요. 레코드를 만들기 **전에** 누군가 그 이름을 조회했다면, "없음"이라는 답이 캐시됐을 수 있어요.

**원인 후보**
1. **부정 캐시**: 생성 전 조회 결과(NXDOMAIN)가 리졸버에 SOA MINIMUM(또는 SOA TTL 중 작은 값)만큼 남아 있어요.
2. OS·브라우저에도 실패 결과가 남아 있어요.
3. 레코드 이름 오타나 다른 영역에 만든 실수.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 권한 서버에 직접 물어(`dig @권한서버 이름 +norec`) 레코드를 확인하고, 부정 캐시 시간만큼 기다리기 | 원인을 정확히 구분해요. 아무것도 안 건드려요 | 기다리는 시간이 생겨요 |
| B. 로컬 캐시 비우기, 다른 리졸버로 확인 | 내 PC 문제는 바로 풀려요 | 통신사 리졸버 캐시는 내가 못 비워요 |
| C. SOA MINIMUM을 낮추기 | 다음부터 "없음" 캐시가 짧아져요 | 없는 이름 질의가 권한 서버로 더 많이 와요 |

**내가 고를 방법**
먼저 A로 권한 서버에 레코드가 맞게 있는지 확인해요. 맞다면 B로 내 쪽 캐시를 비우고, 나머지는 부정 캐시가 끝나길 기다려요. 앞으로는 레코드를 먼저 만들고 나서 조회하는 순서를 지켜요. 이런 일이 자주 생기면 C를 검토해요.

**채점 포인트**: 부정 캐시(NXDOMAIN도 캐시), SOA MINIMUM, 권한 서버 직접 확인(`+norec`, AA), 로컬 캐시 비우기, 리졸버 캐시는 못 비움.
</details>

## 필기 포인트

- DNS 포트 **53**. 기본 UDP, 큰 응답·영역 전송은 TCP. 교재는 DNS를 "UDP를 쓰는 응용"으로 분류하니, 보기에 "TCP만" 또는 "UDP만"이 나오면 함정일 수 있어요.
- 포트 표: FTP 20/21, Telnet 23, SMTP 25, **DNS 53**, TFTP 69, HTTP 80, POP3 110, IMAP 143, SNMP 161.
- 정방향: 이름 → IP(A/AAAA). **역방향(Inverse) DNS**: IP → 이름(PTR).
- 질의 방식: 교재는 recursive / non-recursive / iterative로 적어요. non-recursive와 iterative는 같은 쪽("아는 만큼만 답함")이에요.
- 이름 → IP는 **DNS**, IP → MAC 주소는 **ARP**. 섞어 내는 보기가 나와요.
- MX는 숫자가 **작을수록** 우선. TTL 0은 캐시하지 말라는 뜻.
