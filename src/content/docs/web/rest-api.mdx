:::tip[한 줄 요약]
REST는 프로토콜이 아니라 Roy Fielding이 정한 **6개 제약**(그중 code-on-demand만 선택)을 지키는 **아키텍처 스타일**이에요. 실무 REST API는 "자원은 **명사 URI**, 행동은 **HTTP 메서드**, 결과는 **상태 코드**"로 표현하고, 에러 형식·페이징·버전 규칙을 API 전체에서 똑같이 맞추는 게 핵심이에요.
:::

## 쉽게 이해하기

REST API는 **도서관 서가 규칙**과 비슷해요.

1. 책마다 **청구기호**(URI)가 붙어 있어요. "3층 소설 A-12"처럼 위치만 보면 무슨 책인지 알 수 있어요. 청구기호에 "빌리기"나 "반납하기" 같은 동작은 안 적혀 있어요.
2. 동작은 **창구에서 정해진 말**(HTTP 메서드)로 해요. "보여 주세요"(GET), "새로 등록해 주세요"(POST), "통째로 바꿔 주세요"(PUT), "일부만 고쳐 주세요"(PATCH), "없애 주세요"(DELETE).
3. 사서는 결과를 **정해진 번호표**(상태 코드)로 돌려줘요. "201 등록됐어요", "404 그런 책 없어요", "409 이미 대출 중이에요".
4. 사서는 손님을 **기억하지 않아요**(무상태). 그래서 손님이 매번 대출증을 내밀어요.
5. 어느 지점 도서관을 가도 규칙이 **똑같아서**(균일한 인터페이스) 처음 간 곳에서도 헤매지 않아요.

단, 실제 REST의 엄밀한 정의는 "응답 안에 다음에 할 수 있는 행동 링크까지 담겨 있어야 한다"(HATEOAS)는 데까지 가요. 실무 API 대부분은 거기까지 가지 않아서, 엄밀히는 "HTTP API"라고 부르는 게 맞다는 의견도 있어요.

## 제대로 알기

메서드 각각의 뜻, 안전·멱등, 상태 코드 하나하나의 정의는 [HTTP 기본](../http-basics/)에 있어요. 이 페이지는 "그걸 API를 설계할 때 **어떻게 고르나**"를 다뤄요.

### 1. REST는 제약 묶음이에요

REST(Representational State Transfer)는 Roy Fielding이 2000년 박사논문 5장에서 정의했어요. "이 제약들을 지키면 웹처럼 크게 늘리기 쉽고, 클라이언트와 서버가 따로 발전할 수 있다"는 설계 원칙 모음이에요. JSON도 HTTP도 필수가 아니에요.

<RestConstraints />

| 제약 | 뜻 | 얻는 것 | 대가 |
|---|---|---|---|
| Client-server | 화면(클라이언트)과 데이터 저장(서버)의 관심사를 나눠요 | 화면을 여러 기기로 옮기기 쉬움, 양쪽이 따로 발전, 서버 단순화 | 논문은 이점 위주로 설명 |
| Stateless | 요청 하나에 그 요청을 이해할 정보가 다 들어 있어요. 서버는 요청 사이에 대화 상태를 들고 있지 않아요 | 요청 하나만 보고 이해 가능, 장애 복구 쉬움, 서버 늘리기 쉬움 | 매 요청 같은 정보를 반복해서 보내 네트워크 효율이 떨어짐 |
| Cache | 응답이 캐시 가능한지 표시해야 해요 | 왕복 자체를 줄여 지연·부하 감소 | 낡은 데이터를 볼 수 있음 |
| Uniform interface | 모든 컴포넌트가 같은 방식으로 대화해요 | 구현과 서비스를 분리, REST의 가장 큰 특징 | 앱 맞춤형이 아니라 효율이 떨어질 수 있음 |
| Layered system | 각 컴포넌트는 바로 옆 계층만 알아요 | 로드밸런서·공유 캐시·방화벽을 중간에 끼울 수 있음 | 계층이 늘면 지연 증가 |
| Code-on-demand (선택) | 클라이언트가 서버에서 코드(스크립트)를 받아 실행해요 | 클라이언트 단순화 | 가시성 저하라서 **선택** 제약 |

**균일한 인터페이스**(uniform interface)는 "메서드를 통일하자"는 말이 아니라 하위 제약 4개를 뜻해요.

- **리소스 식별**: 이름 붙일 수 있는 모든 정보(문서, 이미지, 주문, 사람)가 **리소스**예요. URI로 하나하나 가리켜요.
- **표현으로 조작**: 주고받는 건 리소스 그 자체가 아니라 그 **표현**(representation, JSON·HTML 같은 한 형태)이에요. 같은 리소스를 `Accept` 헤더에 따라 다른 형식으로 줄 수 있어요.
- **자기 서술적 메시지**: 메시지만 보고 어떻게 처리할지 알 수 있어야 해요(메서드, `Content-Type` 등).
- **HATEOAS**(Hypermedia As The Engine Of Application State, 응답 속 링크로 다음 행동을 고르는 것): 클라이언트가 URI 구조를 외우는 대신 응답에 담긴 링크를 따라가요.

<Aside type="caution" title="무상태 ≠ 데이터가 없다">
Stateless는 서버가 **요청 사이의 대화 상태**(세션)를 기억하지 않는다는 뜻이에요. 주문, 회원 같은 **리소스 상태**는 당연히 DB에 있어요.
</Aside>

### 2. 리처드슨 성숙도 모델

Leonard Richardson이 제안하고 Martin Fowler가 정리한 4단계 모델이에요. "우리 API가 REST에 얼마나 가까운가"를 설명할 때 써요.

| 단계 | 모습 | 예 |
|---|---|---|
| Level 0 | HTTP를 그냥 통로로 씀. 엔드포인트 하나에 전부 POST | `POST /api` 본문에 `"action":"getOrder"` |
| Level 1 | 대상마다 URI(리소스)가 생김 | `POST /orders/1` |
| Level 2 | 메서드와 상태 코드를 의미대로 씀 | `GET /orders/1` → 200, 생성 → 201, 충돌 → 409 |
| Level 3 | 응답에 다음 행동 링크(하이퍼미디어)를 넣음 | 응답 `_links`에 `cancel`, `pay` 링크 |

- 실무 API 대부분은 **Level 2**예요.
- Fowler는 이 모델이 REST의 공식 정의가 아니라 **이해를 돕는 도구**이고 점수 매기기용이 아니라고 해요.
- Fielding은 2008년 글에서 "하이퍼텍스트로 다음 상태를 고르지 않으면 REST가 아니다"라고 했어요. REST를 안 따르는 건 괜찮지만, 그렇다면 REST라고 부르지는 말라는 취지예요.

### 3. URI 설계: 나쁜 예 → 좋은 예

기본 원칙은 네 가지예요.

- 리소스 이름은 **줄이지 않은 복수형 명사**: `/users`, `/orders`.
- 동작은 URI가 아니라 **HTTP 메서드**로 표현해요.
- 하위 리소스는 부모 아래에 둬요: `/users/{userId}/orders`. 다만 너무 깊게 중첩하지 않는 게 관례예요.
- 단어 구분은 kebab-case(`order-items`)를 많이 권장해요. 경로는 대소문자를 구분하니 한 가지로 통일해요.

| 하고 싶은 일 | 나쁜 URI | 좋은 URI | 이유 |
|---|---|---|---|
| 회원 목록 조회 | `GET /getUsers` | `GET /users` | 동사는 메서드가 이미 말해 줌 |
| 회원 한 명 조회 | `GET /user?id=1` | `GET /users/1` | 단수·쿼리 대신 컬렉션 + ID |
| 회원 생성 | `POST /createUser` | `POST /users` | 생성은 컬렉션에 POST |
| 회원 삭제 | `GET /users/1/delete` | `DELETE /users/1` | GET으로 바꾸면 크롤러가 지울 수 있음 |
| 회원의 주문 목록 | `GET /orders/user/1` | `GET /users/1/orders` | 소유 관계를 경로 계층으로 |
| 결제 완료 주문 검색 | `GET /orders/paid/sort-by-date` | `GET /orders?status=PAID&sort=-createdAt` | 필터·정렬은 쿼리 파라미터 |
| 주문 취소 | `POST /cancelOrder?id=42` | `POST /orders/42/cancel` | CRUD로 안 되는 동작은 행위 리소스 |
| 단어 구분 | `/orderItems`, `/Order_Items` 혼용 | `/order-items`로 통일 | 대소문자가 다르면 다른 경로(404) |

**동사는 절대 금지인가요?** 아니에요. 취소·승인·환불처럼 CRUD로 표현하기 어려운 동작은 **행위 리소스**(custom method)를 따로 둬요. Google API 가이드(AIP-136)는 `POST .../books/1:archive`처럼 콜론 + 동사를, Microsoft Azure 가이드는 `POST /<collection>/<id>:<action>`을 써요. 국내에서 흔한 `POST /orders/42/cancel`은 같은 생각의 슬래시 버전이에요. 두 가이드 모두 "표준 메서드로 깔끔하게 안 될 때만" 쓰라고 해요.

### 4. 메서드와 상태 코드 고르기

| 하고 싶은 일 | 메서드 | 성공 응답 |
|---|---|---|
| 조회 | GET | 200 |
| 생성(서버가 ID 결정) | POST | **201 + `Location` 헤더**(새 리소스 주소) |
| 전체 교체, 또는 클라이언트가 ID를 정해서 생성 | PUT | 교체 200/204, 생성 201 |
| 일부 수정 | PATCH | 200/204 |
| 삭제 | DELETE | 200/204 |

실패는 "누가, 왜 잘못했나"로 골라요.

| 상황 | 코드 |
|---|---|
| JSON 문법이 깨짐, 필수 값 누락 | 400 |
| 형식은 맞는데 값이 규칙에 안 맞음(검증 실패) | 422 (400으로 통일하는 팀도 많아요) |
| 로그인 안 함, 토큰 만료 | 401 |
| 로그인은 했지만 권한 없음 | 403 |
| 없음 | 404 |
| 지금 상태와 충돌(중복, 이미 처리됨) | 409 |
| `If-Match` 조건 실패(누가 먼저 고침) | 412 |
| 요청이 너무 많음 | 429 |

<Aside type="danger" title="200 + success:false 금지">
에러인데 200을 주고 본문에 `"success": false`를 넣으면 상태 코드(Level 2)의 의미를 버리는 거예요. 캐시, 모니터링, 재시도 로직이 모두 "성공"으로 오해해요.
</Aside>

**동시에 고치기 충돌 막기**: GET 응답에 `ETag`(리소스 버전 표시)를 주고, 수정 요청에 `If-Match: "그 ETag"`를 붙이게 해요. 그사이 누가 먼저 고쳐서 버전이 바뀌었으면 서버가 412로 거절해요. 결제처럼 재시도가 위험한 POST는 [HTTP 기본의 이중 결제 서술형](../http-basics/#서술형-연습)을 보세요.

### 5. 에러 응답 형식: RFC 9457

API마다 에러 모양이 다르면 프론트가 화면마다 다르게 파싱해야 해요. **RFC 9457**(Problem Details for HTTP APIs, 2023)은 에러 본문의 표준 모양이에요. 예전 **RFC 7807을 대체**했어요. 미디어 타입은 `application/problem+json`이에요.

```json
{
  "type": "https://api.example.com/problems/order-already-shipped",
  "title": "이미 배송된 주문은 취소할 수 없어요",
  "status": 409,
  "detail": "주문 42는 배송이 시작되어 취소할 수 없습니다.",
  "instance": "/orders/42/cancel"
}
```

| 필드 | 뜻 |
|---|---|
| `type` | 문제 **종류**를 가리키는 URI. 클라이언트는 이걸로 분기해요. 없으면 기본값 `about:blank` |
| `title` | 종류에 대한 짧은 요약. 발생할 때마다 바뀌지 않아요 |
| `status` | HTTP 상태 코드(숫자). 실제 응답 코드와 같아야 해요 |
| `detail` | **이번** 발생에 대한 사람용 설명. 클라이언트가 파싱하면 안 돼요 |
| `instance` | 이번 발생을 가리키는 URI |

- 종류별로 필드를 **추가**할 수 있어요(확장 멤버). 예: 검증 실패 때 `errors` 배열에 필드별 오류. 클라이언트는 모르는 필드를 무시해야 해요.
- **스택 트레이스 같은 내부 정보는 넣지 말아요.** 디버깅 도구가 아니에요.
- 꼭 RFC 9457이 아니어도 돼요. Azure 가이드는 `{"error": {"code", "message", ...}}` 모양을 써요. 공통 원칙은 **기계가 읽는 코드 + 사람이 읽는 메시지 + API 전체에서 같은 모양**이에요.

### 6. 필터·정렬·페이징

필터·정렬·페이징은 모두 **쿼리 파라미터**로 받아요: `GET /orders?status=PAID&sort=-createdAt&size=20`.

| | 오프셋 페이징 | 커서(키셋) 페이징 |
|---|---|---|
| 요청 예 | `?page=3&size=20` | `?cursor=eyJpZCI6...&size=20` |
| 응답 예 | `items`, `page`, `totalPages` | `items`, `nextCursor`(마지막이면 없음) |
| 동작 | 앞의 N개를 건너뜀 | 마지막으로 본 키 **다음부터** 읽음 |
| 장점 | 구현 쉬움, 원하는 페이지로 점프 | 페이지가 깊어도 속도 일정, 중간에 글이 추가돼도 중복·누락 적음 |
| 단점 | 뒤로 갈수록 느림, 조회 사이 추가·삭제 시 중복·누락 | 페이지 점프 불가, 정렬 키가 유일해야 함 |
| 어울리는 곳 | 관리자 게시판(페이지 번호) | 무한 스크롤 피드 |

오프셋이 왜 뒤로 갈수록 느린지(DB가 앞 행을 읽고 버리는 이유)는 [커넥션 풀과 쿼리](../../db/connection-pool-query/)에서 다뤄요.

- Google AIP-158은 응답에 `next_page_token`을 주고, 토큰은 **불투명**(opaque, 클라이언트가 속을 해석할 수 없음)하게 만들라고 해요. 빈 토큰이 "끝"이라는 유일한 신호예요. 페이징은 나중에 추가하면 하위 호환이 깨지니 **처음부터** 넣으라고 해요.
- Azure 가이드는 목록 응답에 `nextLink`(다음 페이지 전체 URL)를 주고 마지막 페이지엔 생략해요. 전체 개수(total count) 반환은 피하라고 해요.
- 응답 본문 대신 `Link` 헤더(RFC 8288)로 `rel="next"` 링크를 줄 수도 있어요.

### 7. 버전 관리

| 방식 | 예 | 장점 | 단점 |
|---|---|---|---|
| URI | `/v1/orders` | 눈에 보이고 라우팅·테스트 쉬움 | "리소스 주소는 버전과 무관해야 한다"는 비판 |
| 헤더 | GitHub: `X-GitHub-Api-Version: 2022-11-28` | URI가 깔끔 | 브라우저 주소창으로 테스트하기 어려움 |
| 쿼리 | Azure: `?api-version=2024-01-01` | URI 경로는 유지 | 빠뜨리면 400 등 규칙 필요 |

- 필드 **추가**처럼 기존 클라이언트를 안 깨는 변경은 버전을 안 올려요. 필드 삭제·이름 변경·의미 변경만 새 버전이에요.
- 그래서 클라이언트는 **모르는 필드는 무시**하도록 만들어요. RFC 9457의 "모르는 확장 필드 무시"와 같은 생각이에요.
- GitHub은 새 버전이 나와도 이전 버전을 24개월 지원하고, 폐기 예정이면 `Deprecation`·`Sunset` 헤더로 알리고, 폐기된 버전 요청엔 410을 줘요.

### 8. REST vs gRPC vs GraphQL

| | REST | gRPC | GraphQL |
|---|---|---|---|
| 모양 | 리소스 URI + HTTP 메서드, 보통 JSON | Protocol Buffers 스키마 + HTTP/2 위 함수 호출 | 엔드포인트 하나에 필요한 필드를 쿼리로 지정 |
| 강점 | 범용, GET을 HTTP 캐시가 그대로 활용 | 바이너리라 작고 빠름, 스트리밍 | 과다·과소 조회 해결, 화면이 다양한 프론트에 유리 |
| 약점 | 화면마다 여러 번 호출하거나 필요 없는 필드까지 받기 쉬움 | 브라우저에서 바로 쓰기 어려움(gRPC-Web 필요) | 보통 POST 하나라 HTTP 캐시 활용 어려움, 무거운 쿼리 제한 필요 |
| 주로 | 공개 API, 일반 웹·앱 | 내부 서비스 간(MSA) 통신 | 화면이 많은 프론트 백엔드 |

## 면접 질문

<details>
<summary>Q. REST가 뭔가요? 제약 조건을 말해 보세요.</summary>

**답변(30초)** REST는 Roy Fielding이 논문에서 정의한 아키텍처 스타일이고, 프로토콜이 아니라 제약 묶음이에요. 제약은 클라이언트-서버, 무상태, 캐시, 균일한 인터페이스, 계층형 시스템, 그리고 선택 사항인 code-on-demand까지 6개예요. 이걸 지키면 서버를 늘리기 쉽고 클라이언트와 서버가 따로 발전할 수 있어요. 실무에서는 리소스를 URI로, 행동을 HTTP 메서드로, 결과를 상태 코드로 표현하는 방식으로 적용해요.

**꼬리질문**
- Q. 균일한 인터페이스가 정확히 뭔가요? → 리소스 식별, 표현을 통한 조작, 자기 서술적 메시지, HATEOAS라는 하위 제약 4개예요. 메서드 통일만 뜻하는 게 아니에요.
- Q. 무상태면 서버에 데이터가 없다는 건가요? → 아니요. 요청 사이의 대화 상태를 서버가 안 들고 있다는 뜻이고, 리소스 상태는 DB에 있어요.
- Q. 무상태의 단점은요? → 요청마다 필요한 정보(토큰 등)를 반복해서 보내니 네트워크 효율이 떨어져요.
</details>

<details>
<summary>Q. 지금 쓰는 API가 진짜 RESTful한가요?</summary>

**답변(30초)** 엄밀히는 아닌 경우가 대부분이에요. 리처드슨 성숙도 모델로 보면 실무 API는 보통 Level 2, 즉 리소스 URI와 메서드·상태 코드를 의미대로 쓰는 단계예요. Fielding은 응답 속 링크로 다음 행동을 고르는 HATEOAS까지 있어야 REST라고 봐요. 그래서 저는 "REST 원칙을 따르는 HTTP API"라고 표현하고, 팀 안에서 URI·에러·페이징 규칙을 일관되게 지키는 걸 더 중요하게 봐요.

**꼬리질문**
- Q. Level 3를 안 하는 이유는요? → 클라이언트가 보통 화면에 맞춰 URI를 미리 알고 만들어져서 링크를 따라가는 이점이 작고, 응답이 커지고 구현 비용이 들어요.
- Q. 리처드슨 모델로 API 점수를 매기면 되나요? → Fowler도 이해를 돕는 도구일 뿐 평가 기준이 아니라고 했어요.
</details>

<details>
<summary>Q. 좋은 URI 설계 원칙은요? URI에 동사를 넣으면 안 되나요?</summary>

**답변(30초)** 리소스는 줄이지 않은 복수형 명사로 쓰고, 동작은 HTTP 메서드로 표현해요. `POST /createUser` 대신 `POST /users`, `GET /getUser?id=1` 대신 `GET /users/1`처럼요. 소유 관계는 `/users/1/orders`처럼 계층으로, 필터·정렬·페이징은 쿼리 파라미터로 둬요. 다만 취소·승인처럼 CRUD로 표현이 어색한 동작은 `POST /orders/42/cancel` 같은 행위 리소스를 둬도 되고, Google·Microsoft 가이드도 이걸 허용해요.

**꼬리질문**
- Q. 계층은 얼마나 깊게 해도 되나요? → 깊어지면 URI가 길고 부모 ID를 다 알아야 해서, 보통 한두 단계로 끊고 나머지는 `/orders/42`처럼 바로 접근하게 해요.
- Q. 대소문자나 단어 구분은요? → 경로는 대소문자를 구분하니 하나로 통일해요. kebab-case가 많이 권장돼요.
</details>

<details>
<summary>Q. 에러 응답은 어떻게 설계하나요?</summary>

**답변(30초)** 먼저 상태 코드를 의미대로 줘요. 에러인데 200을 주면 모니터링과 재시도가 오판해요. 본문은 API 전체에서 같은 모양으로 맞추고, 표준으로는 RFC 9457 Problem Details가 있어요. `type`으로 문제 종류를, `status`로 코드를, `detail`로 사람이 읽을 설명을 줘요. 클라이언트는 `type`이나 에러 코드로 분기하고, 스택 트레이스 같은 내부 정보는 절대 넣지 않아요.

**꼬리질문**
- Q. RFC 7807과 차이는요? → RFC 9457이 7807을 대체한 최신판이에요. 기본 필드 구조는 같은 계열이에요.
- Q. 검증 오류가 여러 개면요? → 확장 필드(예: `errors` 배열)에 필드별로 담아요. 클라이언트는 모르는 확장 필드를 무시하면 돼요.
</details>

<details>
<summary>Q. 오프셋 페이징과 커서 페이징을 비교해 주세요.</summary>

**답변(30초)** 오프셋은 `page`, `size`로 앞을 건너뛰는 방식이라 구현이 쉽고 원하는 페이지로 점프할 수 있어요. 대신 뒤 페이지일수록 DB가 앞 행을 읽고 버려서 느리고, 조회 사이에 글이 추가되면 중복이나 누락이 생겨요. 커서는 마지막으로 본 키 다음부터 읽어서 깊이와 상관없이 빠르고 무한 스크롤에 맞아요. 대신 페이지 점프가 안 되고 정렬 키가 유일해야 해요.

**꼬리질문**
- Q. 정렬 키가 유일하지 않으면요? → `createdAt`이 같은 행이 있으면 경계에서 빠지거나 겹치니, `id`를 덧붙여 `(createdAt, id)`로 정렬해요.
- Q. 커서는 그냥 마지막 id를 주면 되나요? → 동작은 하지만, 내부 구조를 숨기고 나중에 바꿀 수 있게 불투명한 토큰으로 주라는 가이드(Google AIP-158)가 있어요.
</details>

<details>
<summary>Q. API 버전은 어떻게 관리하나요?</summary>

**답변(30초)** 먼저 버전을 안 올려도 되게 설계해요. 필드 추가처럼 기존 클라이언트를 안 깨는 변경은 그대로 내보내고, 클라이언트는 모르는 필드를 무시하게 해요. 깨지는 변경만 새 버전을 만들어요. 방식은 `/v1` 같은 URI, GitHub처럼 헤더, Azure처럼 쿼리 파라미터가 있어요. URI 방식은 보기 쉽고 라우팅이 간단해서 많이 쓰고, 헤더 방식은 주소가 깔끔한 대신 테스트가 조금 번거로워요.

**꼬리질문**
- Q. 구버전은 언제 없애요? → 폐기 일정을 공지하고 `Deprecation`·`Sunset` 헤더로 알린 뒤 사용량을 보고 종료해요. GitHub은 이전 버전을 24개월 지원해요.
</details>

<details>
<summary>Q. REST, gRPC, GraphQL은 언제 쓰나요?</summary>

**답변(30초)** REST는 범용이고 HTTP 캐시를 그대로 쓸 수 있어서 공개 API나 일반 웹·앱에 맞아요. gRPC는 Protocol Buffers로 바이너리를 주고받아 작고 빠르고 스트리밍이 돼서 내부 서비스 간 통신에 많이 써요. GraphQL은 클라이언트가 필요한 필드만 골라 받아서 화면이 다양한 프론트에 유리하지만, 보통 POST 하나라 HTTP 캐시를 쓰기 어렵고 무거운 쿼리를 막는 장치가 필요해요.

**꼬리질문**
- Q. 그럼 MSA 내부도 gRPC, 외부도 gRPC로 하면 되나요? → 외부 클라이언트가 브라우저라면 gRPC를 바로 쓰기 어려워 gRPC-Web 같은 중계가 필요해요. 그래서 외부는 REST, 내부는 gRPC로 나누는 구성이 흔해요.
</details>

## 서술형 연습

<details>
<summary>상황: 쇼핑몰 주문 취소 API를 설계해야 합니다. 팀에서 DELETE /orders/42, PATCH /orders/42 (status: CANCELED), POST /orders/42/cancel 세 안이 나왔습니다. 어떻게 하겠습니까?</summary>

**상황 파악**
주문 취소는 "주문을 지우는 것"이 아니라 "주문의 상태를 취소로 바꾸고, 환불·재고 복구 같은 후속 처리를 하는 것"이에요. 취소된 주문도 내역 조회와 정산을 위해 남아 있어야 해요. 또 이미 배송된 주문처럼 취소할 수 없는 경우도 있어요.

**원인 후보(각 안의 문제)**
1. `DELETE /orders/42`: 리소스가 사라진다는 의미라, 취소 후에도 `GET /orders/42`가 되는 상황과 맞지 않아요.
2. `PATCH /orders/42`에 `status: CANCELED`: 단순 상태 변경처럼 보여서, 환불·재고 복구가 따라온다는 게 드러나지 않아요. 아무 상태로나 바꿀 수 있는 PATCH라면 `status: DELIVERED` 같은 엉뚱한 변경을 막는 검증도 필요해요.
3. `POST /orders/42/cancel`: URI에 동사가 들어가지만, CRUD로 표현이 어색한 동작을 위한 행위 리소스는 Google·Microsoft 가이드도 허용하는 패턴이에요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `POST /orders/42/cancel` (행위 리소스) | 의도가 분명함. 취소 사유를 본문에 받기 좋고, 권한·검증·후속 처리를 한곳에 모음 | 동작이 늘 때마다 행위 리소스가 늘어 URI가 동사로 어지러워질 수 있음 |
| B. `PATCH /orders/42` 상태 변경 | 순수 리소스 모델에 가까움, 엔드포인트가 안 늘어남 | 상태 전이 규칙과 부수 효과가 PATCH 안에 숨어서 클라이언트·리뷰어가 알기 어려움 |
| C. 취소를 별도 리소스로 생성: `POST /orders/42/cancellations` | 명사로 유지, 취소 이력(부분 취소 여러 번)을 리소스로 조회 가능 | 단순 전체 취소에는 과한 설계 |

**내가 고를 방법**
A를 고르겠어요. 취소에는 환불과 재고 복구라는 의미 있는 부수 로직이 붙어서, 별도 행위로 드러내는 게 읽는 사람에게 정확해요. 응답은 이렇게 정해요.
- 성공: 200 + 바뀐 주문 표현
- 없는 주문: 404, 남의 주문: 403(존재를 숨기고 싶으면 404)
- 이미 배송됐거나 이미 취소됨: **409** + `application/problem+json`, `type`은 `.../order-already-shipped`처럼 종류를 구분해서 프론트가 안내 문구를 고를 수 있게 해요.
- 두 번 눌러도 환불이 두 번 나가지 않게, 이미 취소된 주문에 대한 재요청은 상태를 다시 바꾸지 않아요.

부분 취소가 자주 생기는 서비스라면 C로 확장해요.

**채점 포인트**: DELETE는 기록 삭제라 의미 불일치, 부수 로직(환불·재고) 때문에 행위 리소스, 행위 리소스는 공식 가이드에서도 허용, 이미 배송 시 409, 일관된 에러 형식(problem+json), 403/404 구분, 중복 요청 시 환불 중복 방지, 대안과 트레이드오프.
</details>

<details>
<summary>상황: 앱 피드가 무한 스크롤인데, 아래로 많이 내릴수록 응답이 느려지고, 새 글이 올라오면 이미 본 글이 다시 보인다는 제보가 들어왔습니다. API를 어떻게 바꾸겠습니까?</summary>

**상황 파악**
지금은 `GET /posts?page=N&size=20` 같은 오프셋 페이징일 가능성이 커요. 증상 두 개가 모두 오프셋의 전형적인 한계와 맞아요.

**원인 후보**
1. **느려짐**: 오프셋은 "앞에서 N개 건너뛰기"라 DB가 건너뛸 행을 다 읽고 버려요. 페이지가 깊을수록 읽는 양이 늘어요.
2. **중복**: 사용자가 1페이지를 본 사이 맨 앞에 새 글 3개가 올라오면, 2페이지는 3칸씩 밀려서 1페이지 끝 글 3개가 다시 보여요. 삭제가 생기면 반대로 누락돼요.
3. 매 요청마다 전체 개수(`COUNT`)를 세고 있다면 그것도 느려지는 원인이에요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 커서 페이징: `GET /posts?cursor=...&size=20` → `items`, `nextCursor` | 마지막으로 본 키 다음부터 인덱스로 바로 읽어서 깊이와 상관없이 빠름. 앞에 새 글이 끼어도 밀리지 않음 | 특정 페이지로 점프 불가. 정렬 키가 유일해야 해서 `(createdAt, id)` 같은 복합 정렬과 인덱스 필요 |
| B. 오프셋 유지 + 첫 요청 시점 고정(예: `before=첫 조회 시각` 조건 추가) | 기존 클라이언트 변경이 작음, 중복 문제는 줄어듦 | 느려지는 문제는 그대로 |

**내가 고를 방법**
무한 스크롤은 페이지 점프가 필요 없으니 A를 고르겠어요.
- 정렬은 `createdAt DESC, id DESC`로 하고, 두 컬럼 복합 인덱스를 둬요.
- 커서는 마지막 글의 `(createdAt, id)`를 담되, 클라이언트가 해석하거나 조작하지 않게 **불투명한 토큰**으로 줘요. 그래야 나중에 정렬 방식을 바꿔도 API가 안 깨져요.
- `size + 1`개를 조회해서 하나가 더 있으면 `nextCursor`를 주고, 없으면 생략해서 "끝"을 알려요.
- 전체 개수는 무한 스크롤에 필요 없으니 응답에서 빼요.
- 기존 앱 호환을 위해 오프셋 파라미터는 한동안 유지하고 새 앱부터 커서를 쓰게 해요.

**채점 포인트**: 오프셋이 앞 행을 읽고 버림, 새 글 추가로 인한 밀림(중복·누락), 커서(키셋) 페이징, 정렬 키 유일성(id 덧붙이기)과 복합 인덱스, 불투명 토큰, 끝 신호(nextCursor 생략, size+1), total count 생략, 페이지 점프 불가라는 트레이드오프, 구버전 호환.
</details>

<details>
<summary>상황: 서비스마다 에러 응답 모양이 제각각이라(어떤 곳은 200 + success:false, 어떤 곳은 message만, 어떤 곳은 스택 트레이스까지) 프론트가 화면마다 다르게 처리하고 있습니다. 어떻게 통일하겠습니까?</summary>

**상황 파악**
문제는 세 가지예요. 상태 코드가 의미를 잃었고(200인데 실패), 본문 모양이 달라 공통 처리가 안 되고, 내부 정보가 밖으로 새고 있어요.

**원인 후보**
1. 팀마다 공통 규칙 없이 컨트롤러에서 직접 에러 본문을 만들어요.
2. 예외를 한곳에서 잡아 변환하는 공통 처리기가 없어서, 처리 안 된 예외의 기본 에러 페이지나 스택 트레이스가 그대로 나가요.
3. 프론트가 문구(`message`) 문자열을 비교해서 분기하고 있어 문구만 바꿔도 깨져요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 표준 RFC 9457 Problem Details 채택 (`type`, `title`, `status`, `detail`, `instance` + 확장 필드) | 공개 표준이라 설명·문서화가 쉽고, 외부 파트너도 이해함. `application/problem+json`으로 구분 가능 | 기존 클라이언트가 옛 모양을 기대하면 전환 기간이 필요. `type` URI 목록을 관리해야 함 |
| B. 사내 공통 포맷(예: `{"error": {"code", "message", "details"}}`) | 기존 모양과 가깝게 만들어 전환이 쉬움. Azure 가이드도 이런 형태를 씀 | 사내 규칙이라 새 팀원·외부에 따로 설명해야 함 |

**내가 고를 방법**
새로 정한다면 A를 고르겠어요. 핵심은 표준 여부보다 **모든 API가 같은 모양**이라는 점이고, 표준을 따르면 그 규칙을 따로 설득할 필요가 줄어요.
- **상태 코드부터 정상화**: 200 + success:false를 없애고 400/401/403/404/409/422/500을 의미대로 줘요.
- **공통 처리기 한 곳**: 예외를 한곳에서 잡아 Problem Details로 바꿔요(스프링이라면 컨트롤러 밖 공통 예외 처리 계층). 컨트롤러가 직접 에러 본문을 만들지 않게 해요.
- **분기는 `type`(또는 에러 코드)으로**: 프론트는 문구가 아니라 `type`으로 분기하고, `detail`은 화면 표시용으로만 써요.
- **검증 오류는 확장 필드**: `errors: [{ field, reason }]`처럼 필드별로 담아요.
- **내부 정보 차단**: 스택 트레이스와 SQL은 응답에 넣지 않고 서버 로그에만 남겨요. 응답엔 로그를 찾을 수 있는 추적 ID 정도만 줘요.
- **전환**: 기존 클라이언트를 위해 한동안 옛 필드를 같이 내려 주거나 새 버전에서만 바꾸고, 문서에 에러 `type` 목록을 계약으로 올려요.

**채점 포인트**: 상태 코드 의미 회복(200 + success:false 제거), 하나의 공통 형식(RFC 9457 또는 사내 포맷), 기계용 코드(`type`)와 사람용 메시지(`detail`) 분리, 공통 예외 처리 계층, 확장 필드로 검증 오류, 스택 트레이스 등 내부 정보 미노출, 구클라이언트 전환 계획과 문서화.
</details>
