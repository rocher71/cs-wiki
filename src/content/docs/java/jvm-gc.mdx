JVM은 `.class` 바이트코드를 클래스로더로 불러와 실행 엔진(인터프리터 + JIT)으로 돌리는 가상 머신이에요. 객체는 모든 스레드가 함께 쓰는 힙에 만들어지고, GC가 GC Root에서 닿지 않는 객체를 찾아 자동으로 치워요.
:::

## 쉽게 이해하기

JVM은 **어느 나라에서나 같은 메뉴를 내는 프랜차이즈 주방**과 비슷해요. 본사(개발자)는 레시피(바이트코드)를 한 번만 쓰고, 각 지점(Windows, Linux, Mac)의 주방(JVM)이 그 레시피를 자기 환경에 맞게 조리해요.

주방에는 모든 요리사가 같이 쓰는 **큰 창고(힙)**가 있고, 요리사마다 자기 **작업대(스택)**가 따로 있어요. 재료(객체)는 창고에 두고, 작업대에는 "창고 몇 번 칸에 있는 양파" 같은 메모(참조)만 올려 둬요.

창고 정리 담당(GC)은 주기적으로 돌면서 **어느 작업대의 메모에서도 가리키지 않는 재료**를 버려요. 대부분의 재료는 금방 쓰이고 버려지니까, 새로 들어온 재료 칸(Young)만 자주 훑고, 오래 쓰는 재료 칸(Old)은 가끔만 정리해요.

단, 실제로는 정리하는 동안 요리사들이 잠깐 손을 멈춰야 하는 순간(Stop-The-World)이 있어요. 이 멈춤이 길어지면 손님(사용자)이 응답을 오래 기다리게 돼요.

## 제대로 알기

### 1. .java가 실행되기까지

1. `javac`가 `.java`를 **바이트코드**(bytecode, OS와 상관없는 JVM용 명령어)로 바꿔 `.class` 파일을 만들어요.
2. `java` 명령으로 JVM이 뜨면 **클래스로더**(ClassLoader, `.class`를 찾아 메모리에 올리는 부품)가 클래스를 불러와요.
3. 불러온 클래스는 **로딩 → 링킹(검증·준비·해석) → 초기화** 순서를 거쳐요.
   - 준비: static 필드를 만들고 기본값(0, null)으로 채워요.
   - 해석: 이름으로만 적혀 있던 참조(심볼릭 참조)를 실제 위치로 바꿔요.
   - 초기화: `static int count = 5;`처럼 소스에 적은 값이 이때 들어가요(`<clinit>` 실행).
4. **실행 엔진**이 바이트코드를 돌려요. 처음엔 인터프리터로 한 줄씩 실행하다가, 자주 실행되는 부분(핫스팟)만 **JIT 컴파일러**(Just-In-Time, 실행 중에 기계어로 번역)가 네이티브 코드로 바꿔요.

**HotSpot**(오라클·OpenJDK의 기본 JVM 구현)은 **계층형 컴파일**(tiered compilation)을 써요. Java 7에서 도입됐고 JDK 8부터 기본으로 켜져 있어요. 빠르게 컴파일하는 C1이 먼저 쓰이면서 실행 정보를 모으고, 그 정보를 바탕으로 C2가 더 강하게 최적화해요.

<Aside type="note" title="클래스로더 부모 위임">
클래스를 찾을 때 ① 이미 로드했는지 보고 ② 부모 로더에게 먼저 맡기고 ③ 부모가 못 찾으면 그제야 자기가 찾아요. Java 9+ 기본 로더는 **시스템(앱) → 플랫폼 → 부트스트랩** 순서의 부모 관계예요. 앱이 `java.lang.String` 같은 코어 클래스를 바꿔치기하거나 같은 클래스를 두 번 올리는 일을 막는 효과가 있다고 흔히 설명해요.
</Aside>

### 2. 런타임 데이터 영역

JVM이 프로그램을 돌리면서 쓰는 메모리 구역이에요. 면접에서는 **"스레드끼리 공유하나, 따로 쓰나"**로 나눠 말하면 깔끔해요.

| 영역 | 공유 여부 | 무엇이 들어가나 | 터지면 |
|---|---|---|---|
| 힙(Heap) | 모든 스레드 공유 | 모든 객체와 배열. GC가 관리 | `OutOfMemoryError` |
| 메서드 영역 | 모든 스레드 공유 | 클래스 정보, 런타임 상수 풀(클래스가 쓰는 상수·참조 목록), 메서드 코드 | `OutOfMemoryError` |
| JVM 스택 | 스레드마다 | 메서드 호출마다 쌓이는 프레임(지역변수, 계산용 스택) | `StackOverflowError` |
| PC 레지스터 | 스레드마다 | 지금 실행 중인 명령의 주소 | - |
| 네이티브 메서드 스택 | 스레드마다 | C 같은 네이티브 메서드용 스택 | - |

- **프레임**(frame)은 메서드를 부를 때 생기고 끝나면 사라져요. 다른 스레드는 내 프레임을 볼 수 없어요.
- `User u = new User();`에서 **객체는 힙**, 그 객체를 가리키는 **변수 `u`는 스택 프레임**에 있어요.
- 재귀가 너무 깊으면 스택이 넘쳐 `StackOverflowError`가 나요. 스택 크기는 `-Xss`(예: `-Xss1m`)로 정해요.

### 3. PermGen → Metaspace, 그리고 static은 어디에?

**메서드 영역**은 JVM 스펙에 적힌 논리적인 개념이고, HotSpot이 그걸 실제로 어디에 두는지는 버전마다 달라요.

| 버전 | 클래스 메타데이터 | 인턴 문자열(문자열 상수 풀) | static 변수 |
|---|---|---|---|
| JDK 6 이전 | PermGen | PermGen | PermGen |
| JDK 7 | PermGen | **힙으로 이동** | PermGen |
| JDK 8+ | **Metaspace(네이티브 메모리)** | 힙 | **힙으로 이동** |

<Aside type="caution" title="자주 틀리는 포인트">
"static 변수와 문자열 상수 풀은 Metaspace에 있다"는 **틀린 말**이에요. JDK 8에서 PermGen을 없앨 때(JEP 122) Metaspace로 간 건 **클래스 메타데이터**뿐이고, static 변수와 인턴 문자열은 **힙**에 있어요.
</Aside>

Metaspace는 기본 상한이 없어요(`-XX:MaxMetaspaceSize`로 제한 가능). "PermGen OOM이 사라졌다"기보다 **네이티브 메모리를 끝없이 먹을 수 있게 됐다**고 보는 게 맞고, 메모리가 빠듯한 컨테이너에선 오히려 조심해야 해요.

### 4. GC는 무엇을 쓰레기로 보나: 도달 가능성

GC는 **GC Root**(힙 바깥에서 객체를 가리키는 출발점)에서 참조를 따라가 닿는 객체만 살려 둬요. 닿지 않으면 쓰레기예요.

GC Root의 대표 예시는 이래요.
- 실행 중인 메서드의 지역변수
- 살아 있는 스레드
- 시스템 클래스의 static 필드
- JNI(자바가 C 같은 네이티브 코드와 주고받는 통로) 참조, `synchronized`로 잡혀 있는 객체

그래서 자바의 **메모리 누수**는 "안 쓰는데 Root에서 여전히 닿는 객체"예요. static 컬렉션에 계속 넣기만 하는 캐시가 대표적이에요.

### 5. 세대별 GC: Eden, Survivor, Old

GC는 **약한 세대 가설**(Weak Generational Hypothesis, "대부분의 객체는 금방 죽는다")을 이용해 힙을 나눠요.

- **Young** = Eden + Survivor 2개(S0, S1). 새 객체는 대부분 Eden에 생겨요.
- **Minor GC**: Young이 차면 Young만 청소해요. 비용이 "살아 있는 객체 수"에 비례해서, 대부분 죽어 있으면 아주 빨라요.
- Eden과 쓰던 Survivor에서 살아남은 객체를 **비어 있는 Survivor로 복사**하고, 원래 칸은 통째로 비워요. 다음엔 두 Survivor 역할이 바뀌어요.
- 이렇게 살아남을 때마다 나이(age)가 오르고, 임계값(`-XX:MaxTenuringThreshold`, 최댓값 15)에 닿거나 공간이 모자라면 **Old로 승격**(promotion)돼요.
- **Old까지 차면** 전체 힙을 보는 큰 수집이 일어나고, Minor GC보다 훨씬 오래 멈춰요.

**Survivor가 2개인 이유**: 한쪽을 항상 비워 두고 복사 대상으로 쓰면, 복사만으로 살아남은 객체가 빈틈없이 모여요. 메모리 조각(단편화)을 따로 정리할 필요가 없어요.

### 6. Stop-The-World(STW)

**STW**는 GC 작업 동안 앱 스레드를 전부 멈추는 일시정지예요. 이 시간엔 요청 처리도 멈추니까 응답 지연으로 바로 보여요.

- Minor GC도 STW예요. 짧을 뿐이에요.
- G1·ZGC가 "동시(concurrent)"라고 하는 건 일부 단계를 앱과 같이 돌린다는 뜻이지, 멈춤이 0이라는 뜻은 아니에요.
- `System.gc()`를 부르면 Full GC가 날 수 있어요.

GC 로그는 `-Xlog:gc`(별칭 `-verbose:gc`)로 켜고, 자세히는 `-Xlog:gc*`로 봐요. 로그 한 줄은 이렇게 읽어요.

```text
GC(36) Pause Young (G1 Evacuation Pause) 239M->57M(307M) 5.048ms
# Young GC: 사용량 239MB → 57MB (전체 힙 307MB), 5ms 멈춤
GC(38) Pause Full (System.gc()) 69M->31M(104M) 164.581ms
# Full GC: 같은 앱에서 수십 배 더 오래 멈춤
```

### 7. GC 종류와 기본값

| 수집기 | 옵션 | 특징 | 언제 |
|---|---|---|---|
| Serial | `-XX:+UseSerialGC` | 스레드 1개로 수집 | CPU 1개, 데이터 ~100MB 이하 |
| Parallel | `-XX:+UseParallelGC` | 여러 스레드로 수집, 처리량 우선 | 1초 넘는 멈춤도 괜찮은 배치 |
| G1 | `-XX:+UseG1GC` | 힙을 Region으로 나눠 쓰레기 많은 곳부터 회수 | 응답 시간이 중요한 일반 서버 |
| ZGC | `-XX:+UseZGC` | 비싼 작업을 앱과 동시에, 멈춤 1ms 이하 | 응답 시간이 최우선 |

**기본 GC**: JDK 8까지는 Parallel, **JDK 9부터 G1**이에요(JEP 248). CMS는 JDK 14에서 제거됐어요.

<Aside type="note" title="정확한 조건 (버전 뉘앙스)">
JDK 9~26에서 G1이 기본이 되는 건 **서버급 머신(CPU 2개 이상 그리고 메모리 1792MB 이상)**일 때뿐이고, 그보다 작으면 Serial을 골라요. CPU 1개짜리 작은 컨테이너에서 Serial이 잡히는 이유가 이거예요. JDK 27(JEP 523)부터는 환경과 상관없이 항상 G1이에요. 기본 힙 크기는 초기 = 물리 메모리 1/64, 최대 = 1/4이에요.
</Aside>

### 8. G1 한눈에

- 힙을 같은 크기의 **Region**(1~32MB, 2의 거듭제곱) 여러 칸으로 나누고, 칸마다 Eden/Survivor/Old 역할을 붙여요. 세대가 물리적으로 붙어 있지 않아요.
- 이름(Garbage-First)대로 **쓰레기가 많은 칸부터** 비워요. 살아 있는 객체를 다른 칸으로 옮기며(evacuation) 정리해요.
- 멈춤 목표 `-XX:MaxGCPauseMillis` 기본 **200ms**. 보장이 아니라 목표예요.
- Old 점유율이 **IHOP**(동시 마킹을 시작하는 힙 점유율 기준, 기본 45%)에 닿으면 앱과 동시에 마킹하고, 이후 **Mixed GC**로 Young과 Old 일부를 같이 비워요.
- Region 절반 이상 크기의 객체는 **Humongous**로 따로 연속 칸에 들어가요. 남는 공간은 낭비돼요.
- 옮길 공간이 없으면 최후 수단으로 **Full GC**(STW)로 떨어지고, 이때 아주 느려요.

**ZGC 흐름**: JDK 15 정식 → JDK 21 세대형 ZGC 추가 → JDK 23 세대형이 기본 → JDK 24 비세대형 제거. 멈춤은 힙 크기와 상관없이 짧지만, 처리량이 조금 줄고 힙 여유(`-Xmx`)를 넉넉히 줘야 해요.

### 9. OOM 메시지와 진단 도구

| 메시지 | 뜻 |
|---|---|
| `Java heap space` | 힙에 객체를 더 못 만듦. 힙이 작거나 누수 |
| `GC overhead limit exceeded` | GC가 시간의 약 98%를 쓰는데 2% 미만만 회수 |
| `Metaspace` | 클래스 메타데이터 공간 소진. 클래스로더 누수 의심 |

- `-XX:+HeapDumpOnOutOfMemoryError`: OOM 순간 **힙 덤프**(힙에 있던 객체 전체를 떠 놓은 파일, `.hprof`)를 자동 저장해요.
- `jcmd <pid> GC.heap_dump filename=...`: 실행 중에 힙 덤프를 떠요. `GC.class_histogram`은 클래스별 객체 수를 보여줘요.
- `jstat -gcutil <pid> 1000`: 1초마다 Eden/Old 사용률과 Young·Full GC 횟수·시간을 찍어요.
- 힙 덤프는 Eclipse MAT 같은 도구로 열어 "누가 이 객체를 붙잡고 있나(GC Root 경로)"를 따라가요.

<details>
<summary>Q. 자바 코드가 실행되기까지의 과정을 설명해 주세요.</summary>

**답변(30초)** `javac`가 소스를 OS와 무관한 바이트코드(`.class`)로 컴파일하고, JVM이 이를 실행해요. 클래스로더가 부모 위임 방식으로 클래스를 찾아 로딩하고, 링킹(검증·준비·해석)과 초기화를 거쳐요. 그다음 실행 엔진이 인터프리터로 실행하다가, 자주 쓰이는 코드는 JIT 컴파일러가 네이티브 코드로 바꿔 빠르게 돌려요.

**꼬리질문**
- Q. 자바는 인터프리터 언어인가요? → 둘 다예요. 처음엔 인터프리트하고, 핫스팟은 JIT로 컴파일해요. HotSpot은 JDK 8부터 C1→C2 계층형 컴파일이 기본이에요.
- Q. 부모 위임 모델을 왜 쓰나요? → 코어 클래스를 앱이 바꿔치기하지 못하게 하고, 같은 클래스를 중복 로딩하지 않으려고요.
- Q. static 필드 값은 언제 들어가나요? → 준비 단계에서 기본값(0, null), 초기화 단계에서 소스에 적은 값이 들어가요.
</details>

<details>
<summary>Q. JVM 메모리 구조를 설명하고, 스레드 공유 영역과 개별 영역을 구분해 주세요.</summary>

**답변(30초)** 모든 스레드가 공유하는 영역은 힙과 메서드 영역이에요. 힙에는 객체와 배열이, 메서드 영역에는 클래스 정보와 런타임 상수 풀이 있어요. 스레드마다 따로 있는 영역은 JVM 스택, PC 레지스터, 네이티브 메서드 스택이에요. 스택에는 메서드 호출마다 지역변수를 담은 프레임이 쌓이고, 깊어지면 `StackOverflowError`가 나요.

**꼬리질문**
- Q. `User u = new User()`에서 각각 어디에 있나요? → 객체는 힙, 참조 변수 `u`는 그 메서드의 스택 프레임에 있어요.
- Q. 힙이 공유라서 생기는 문제는? → 여러 스레드가 같은 객체를 동시에 바꿀 수 있어서 동기화가 필요해요. 스택의 지역변수는 스레드마다 따로라 안전해요.
</details>

<details>
<summary>Q. PermGen과 Metaspace의 차이는? static 변수는 어디에 있나요?</summary>

**답변(30초)** JDK 8에서 PermGen이 없어지고, 클래스 메타데이터는 힙이 아닌 네이티브 메모리의 Metaspace로 옮겨졌어요. 고정 크기였던 PermGen과 달리 Metaspace는 기본 상한이 없어서 크기 부족 문제는 줄었어요. 주의할 점은 static 변수와 문자열 상수 풀은 Metaspace가 아니라 힙에 있다는 거예요. 문자열은 JDK 7, static은 JDK 8에 힙으로 옮겨졌어요.

**꼬리질문**
- Q. Metaspace는 상한이 없으니 안전한가요? → 아니요. 클래스로더 누수가 있으면 네이티브 메모리를 계속 먹어요. 컨테이너에선 `-XX:MaxMetaspaceSize`를 거는 걸 고려해요.
- Q. 메서드 영역과 Metaspace는 같은 건가요? → 메서드 영역은 JVM 스펙의 논리 개념이고, Metaspace는 HotSpot이 JDK 8부터 쓰는 구현이에요.
</details>

<details>
<summary>Q. GC는 어떤 객체를 쓰레기로 판단하나요?</summary>

**답변(30초)** 도달 가능성으로 판단해요. 스택의 지역변수, static 필드, 살아 있는 스레드 같은 GC Root에서 참조를 따라가 닿는 객체는 살아 있고, 닿지 않는 객체는 쓰레기로 보고 회수해요. 그래서 서로만 참조하는 순환 객체도 Root에서 끊기면 회수돼요.

**꼬리질문**
- Q. 자바에도 메모리 누수가 있나요? → 있어요. 안 쓰는데 Root에서 여전히 닿는 객체가 누수예요. static 컬렉션 캐시에 넣기만 하는 경우, 리스너를 해제하지 않는 경우, ThreadLocal을 비우지 않는 경우가 예예요.
- Q. `System.gc()`를 써도 되나요? → Full GC를 일으켜 오래 멈출 수 있어서 보통 쓰지 않아요.
</details>

<details>
<summary>Q. Young과 Old를 나누는 이유와 Minor GC 과정을 설명해 주세요.</summary>

**답변(30초)** 대부분의 객체는 금방 죽는다는 약한 세대 가설 때문이에요. 새 객체는 Eden에 만들고, Eden이 차면 Young만 청소하는 Minor GC를 해요. 살아남은 객체만 빈 Survivor로 복사하니 비용이 생존 객체 수에 비례해 빨라요. 여러 번 살아남은 객체는 Old로 승격되고, Old는 가끔만 큰 GC로 청소해요.

**꼬리질문**
- Q. Survivor는 왜 2개인가요? → 하나를 항상 비워 두고 복사 대상으로 써서, 복사만으로 단편화 없이 정리하려고요.
- Q. 몇 번 살아남으면 Old로 가나요? → `MaxTenuringThreshold`로 정하고 최댓값은 15예요. JVM이 상황에 따라 실제 임계값을 조정하고, Survivor가 모자라면 더 일찍 가요.
</details>

<details>
<summary>Q. Stop-The-World란 무엇이고 왜 문제가 되나요?</summary>

**답변(30초)** GC가 작업하는 동안 앱 스레드를 모두 멈추는 일시정지예요. 멈춘 동안 요청을 처리하지 못하니까 응답 지연, 특히 p99(가장 느린 1% 요청의 응답 시간) 같은 꼬리 지연으로 드러나요. Minor GC도 STW지만 짧고, Old까지 보는 Full GC는 훨씬 길어요. 그래서 G1이나 ZGC처럼 일부 작업을 앱과 동시에 돌려 멈춤을 줄이는 수집기를 써요.

**꼬리질문**
- Q. ZGC는 STW가 아예 없나요? → 아니요. 멈춤이 1ms 이하로 아주 짧을 뿐 있어요.
- Q. 힙을 키우면 멈춤이 줄어드나요? → GC 빈도는 줄 수 있지만, Full GC가 한 번 나면 볼 게 많아져 더 길어질 수 있어요.
</details>

<details>
<summary>Q. 자바의 기본 GC는 무엇이고, G1은 Parallel과 무엇이 다른가요?</summary>

**답변(30초)** JDK 9부터 기본 GC는 G1이고, 그 전엔 Parallel이었어요. Parallel은 처리량을 최우선으로 해서 긴 멈춤을 감수해요. G1은 힙을 같은 크기의 Region으로 나누고, 쓰레기가 많은 Region부터 골라 회수하면서 멈춤 시간 목표(기본 200ms)를 맞추려고 해요. 그래서 응답 시간이 중요한 일반 서버에 맞아요.

**꼬리질문**
- Q. 200ms는 보장되나요? → 아니요, 목표예요. 공간이 모자라면 Full GC로 떨어져 훨씬 길어질 수 있어요.
- Q. ZGC는 언제 쓰나요? → 응답 시간이 최우선일 때요. 멈춤은 힙 크기와 무관하게 짧지만 처리량이 조금 줄고 힙 여유가 필요해요.
- Q. 작은 컨테이너에서도 G1인가요? → JDK 9~26은 CPU 2개 미만이나 메모리 1792MB 미만이면 Serial을 골라요. 그래서 옵션으로 명시하는 게 안전해요.
</details>

## 서술형 연습

<details>
<summary>상황: API 응답이 몇 분마다 수백 ms에서 수 초씩 튑니다. 평소 응답은 빠릅니다.</summary>

**상황 파악**
평소엔 빠른데 **주기적으로** 튄다는 점이 핵심이에요. 특정 요청이 아니라 모든 요청이 같은 시각에 함께 느려진다면, 앱 전체가 잠깐 멈추는 원인을 먼저 의심해요. 대표 후보가 GC의 Stop-The-World예요.

**원인 후보**
1. Old가 차서 생기는 **Full GC**나 긴 STW
2. G1에서 Old 점유율이 높아 Mixed GC로 못 따라잡고 Full GC로 떨어지는 경우
3. 큰 배열이나 큰 JSON 문자열을 자주 만들어 **Humongous 할당**이 많은 경우
4. (GC가 아니라면) 외부 API, DB 커넥션 대기 같은 다른 병목

**확인 방법**
- `-Xlog:gc*`로 GC 로그를 남기고, `Pause Full`이나 긴 pause 시각을 지연이 난 시각과 맞춰 봐요.
- `jstat -gcutil <pid> 1000`으로 Old 사용률(O)과 Full GC 횟수(FGC)가 늘어나는지 봐요.
- 시각이 겹치지 않으면 GC가 아니라 다른 병목을 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 할당 줄이기(큰 객체, 불필요한 복사 제거) | 근본 원인을 줄임, 모든 GC에 효과 | 코드 수정과 프로파일링 시간이 듦 |
| B. 힙 크기, IHOP, `MaxGCPauseMillis` 조정 | 코드 수정 없이 빠르게 적용 | 원인이 할당 패턴이면 효과가 제한적, 힙을 키우면 Full GC 한 번이 더 길어질 수 있음 |
| C. ZGC로 전환(JDK 21+) | 멈춤이 힙 크기와 무관하게 1ms 이하 | 처리량 일부 손해, 힙 여유를 넉넉히 줘야 함 |

**내가 고를 방법**
먼저 로그로 GC가 원인인지 **증거를 확보**해요. GC가 맞다면 B로 당장의 피해를 줄이면서, A로 Humongous나 대량 할당을 만드는 코드를 찾아 고쳐요. 그래도 지연 요구를 못 맞추고 메모리 여유가 있다면 C를 검토해요. 바로 C로 가면 할당 문제는 그대로 남고 처리량만 잃을 수 있어서예요.

**채점 포인트**: Stop-The-World, Full GC, GC 로그(`-Xlog:gc*`)와 지연 시각 대조, `jstat`, Old 점유율, Humongous 객체, 해결책 2개 이상의 트레이드오프, GC가 아닐 가능성 언급.
</details>

<details>
<summary>상황: 배포하고 몇 시간 뒤 서버가 `OutOfMemoryError: Java heap space`로 죽었습니다.</summary>

**상황 파악**
배포 직후가 아니라 **몇 시간 뒤**에 죽었다는 건, 메모리가 서서히 쌓였다는 신호예요. 갑자기 큰 요청 하나가 들어온 것보다는 **누수**(안 쓰는데 GC Root에서 여전히 닿아서 못 치우는 객체)일 가능성이 커요. GC 직후의 Old 사용량이 계단처럼 계속 올라간다면 누수에 가까워요.

**원인 후보**
1. static Map 같은 캐시에 만료 없이 계속 쌓이는 경우
2. 리스너, 콜백을 등록만 하고 해제하지 않는 경우
3. ThreadLocal을 비우지 않아 스레드 풀에 값이 남는 경우
4. 누수는 아니고 이번 배포로 쓰는 메모리 자체가 늘었는데 힙이 작은 경우

**대응 순서**
1. **복구 먼저**: 롤백하거나 재시작해서 서비스를 살려요.
2. **증거 확보**: `-XX:+HeapDumpOnOutOfMemoryError`를 켜서 다음 OOM 때 힙 덤프가 남게 하고, 메모리가 오르는 중이라면 `jcmd <pid> GC.heap_dump`로 미리 떠 둬요.
3. **분석**: Eclipse MAT로 덤프를 열어 메모리를 가장 많이 잡고 있는 객체와, 그 객체까지 이어지는 GC Root 경로를 따라가요. 이번 배포의 변경점과 대조해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 원인 코드 수정(크기 제한과 만료가 있는 캐시, 리스너 해제 등) | 근본 해결 | 원인을 찾는 데 시간이 듦 |
| B. 힙 증설(`-Xmx` 상향) | 즉시 적용, 시간을 벎 | 누수라면 OOM이 늦게 올 뿐 다시 남. 힙이 커지면 Full GC도 길어질 수 있음 |

**내가 고를 방법**
롤백으로 복구한 뒤 덤프로 원인을 찾아 A로 고쳐요. 원인을 찾는 동안 롤백이 어렵다면 B로 시간을 벌 수 있지만, 임시방편이라는 걸 명확히 해요. 덤프에서 누수가 아니라 정상 사용량 증가로 보이면 그때 B가 근본 해결이 돼요.

**채점 포인트**: 복구 우선(롤백/재시작), 누수 정의(GC Root에서 도달 가능), 힙 덤프(`HeapDumpOnOutOfMemoryError`, `jcmd`), MAT로 GC Root 경로 추적, 캐시 크기 제한과 만료, 힙 증설은 임시방편이라는 점.
</details>
