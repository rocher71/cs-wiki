:::tip[한 줄 요약]
스레드 풀은 스레드를 미리 만들어 재사용해서 생성 비용을 아끼고, 스레드 수에 상한을 둬서 폭주해도 서버가 버티게 해요. ThreadPoolExecutor는 코어 수까지는 스레드를 만들고, 그다음엔 **큐에 쌓고**, 큐가 가득 차야 최대 수까지 스레드를 늘리고, 그래도 넘치면 거절해요.
:::

## 쉽게 이해하기

스레드 풀은 **콜센터**예요. 전화(작업)가 올 때마다 상담원을 새로 뽑아 교육시키면 비싸고, 전화가 폭주하면 사무실이 터져요. 그래서 상담원 몇 명을 고정으로 앉혀 두고 돌아가며 받게 해요.

상담원이 모두 통화 중이면 손님은 **대기열**에서 기다려요. 대기열까지 꽉 차면 그제야 아르바이트 상담원을 추가로 불러요. 아르바이트까지 다 차면 "지금은 연결이 어렵습니다" 하고 끊어요(거절). 한가해지면 아르바이트는 퇴근해요.

단, 실제 자바 스레드 풀에서는 대기열이 **무한**으로 설정된 경우가 많아요. 그러면 아르바이트는 영원히 오지 않고 대기열만 끝없이 길어져요. 이게 이 페이지에서 가장 중요한 함정이에요.

## 제대로 알기

### 1. 왜 스레드 풀을 쓰나요

요청마다 `new Thread()`를 하면 두 가지 문제가 생겨요.

- **생성 비용**: 스레드 객체는 메모리를 꽤 써요. 많이 만들고 버리면 메모리 관리 부담이 커져요. 풀은 **작업자 스레드**(worker thread, 작업을 꺼내 실행하는 스레드)를 재사용해서 이 비용을 줄여요.
- **상한이 없음**: 감당 못 할 만큼 요청이 오면 스레드가 계속 늘다가 시스템 용량을 넘는 순간 **모든 요청**에 응답을 못 해요. 스레드 수에 상한이 있으면 들어오는 속도만큼은 못 해도 버틸 수 있는 속도로는 계속 처리해요. 이걸 "우아하게 성능이 떨어진다"고 표현해요.

고정 크기 풀은 도중에 스레드가 죽어도 새 스레드로 자동 교체해요.

스레드를 직접 다루는 대신 작업만 넘기게 해 주는 객체를 **executor**(실행기)라고 불러요. 인터페이스는 3단계예요.

| 인터페이스 | 하는 일 |
|---|---|
| `Executor` | `execute(Runnable)` 하나뿐 |
| `ExecutorService` | `submit`(결과 받기), `invokeAll`, 종료(`shutdown`) 추가 |
| `ScheduledExecutorService` | 지연 실행, 주기 실행 추가 |

스레드 생성과 `Runnable`/`Callable` 차이는 [스레드 기초](../thread-basics/)에서 다뤄요.

### 2. ThreadPoolExecutor의 7가지 파라미터

`Executors`가 만들어 주는 풀은 전부 내부적으로 `ThreadPoolExecutor`예요. 생성자 인자는 7개예요.

| 파라미터 | 뜻 |
|---|---|
| `corePoolSize` | 놀고 있어도 유지하는 기본 스레드 수 |
| `maximumPoolSize` | 허용하는 최대 스레드 수 |
| `keepAliveTime`, `unit` | 코어를 넘는 스레드가 이 시간만큼 놀면 종료 |
| `workQueue` | 스레드가 모두 바쁠 때 작업이 기다리는 큐 |
| `threadFactory` | 스레드를 만드는 방법(이름, 데몬 여부 등) |
| `handler` | 꽉 찼을 때의 거절 정책 |

- 코어 스레드도 처음부터 만들어 두지 않고 **작업이 올 때** 만들어요. 미리 띄우려면 `prestartAllCoreThreads()`를 불러요.
- `allowCoreThreadTimeOut(true)`면 코어 스레드도 keepAliveTime 뒤 종료돼요.
- `max < core`처럼 값이 이상하면 `IllegalArgumentException`이 나요.

### 3. 작업이 들어올 때의 순서 (가장 중요)

`execute`로 작업이 들어오면 이 순서로 판단해요.

1. 실행 중 스레드가 **core 미만**이면, 다른 스레드가 놀고 있어도 **새 스레드를 만들어요.**
2. core 이상이면 새 스레드보다 **큐에 넣기를 먼저** 해요.
3. 큐가 **가득 차서** 못 넣으면, max를 넘지 않는 한 새 스레드를 만들어요.
4. max도 찼으면 **거절**해요.

<Aside type="caution" title="직관과 다른 점">
많은 사람이 "코어가 다 차면 최대까지 스레드를 늘리고, 그래도 넘치면 큐에 쌓는다"고 생각해요. 실제는 반대예요. **큐가 먼저, 스레드 추가는 큐가 가득 찬 다음**이에요. 그래서 큐가 무한이면 스레드는 영원히 core개이고, maximumPoolSize는 아무 효과가 없어요.
</Aside>

큐 종류에 따라 동작이 크게 달라져요.

| 큐 | 동작 | 위험 |
|---|---|---|
| `SynchronousQueue`(저장 안 함) | 받을 스레드가 없으면 바로 새 스레드 생성 | max가 무한이면 **스레드가 무한히** 늘 수 있음 |
| 용량 없는 `LinkedBlockingQueue`(무한 큐) | core개 스레드만 쓰고 나머지는 전부 큐에서 대기 | **큐가 무한히** 커져 메모리 고갈 |
| `ArrayBlockingQueue` 등(유한 큐) | 큐가 차면 max까지 늘리고, 그 뒤엔 거절 | 자원은 보호되지만 큐·풀 크기 튜닝이 어려움 |

참고로 톰캣의 요청 스레드 풀은 코어를 넘으면 큐보다 스레드를 먼저 늘리는, JDK와 다른 방식으로 알려져 있어요. "톰캣은 순서가 다르다" 정도만 기억해 두면 돼요.

### 4. Executors 팩토리의 함정

`Executors`의 편의 메서드는 쓰기 쉽지만, 실제로 만들어지는 설정을 보면 상한이 없는 곳이 있어요.

| 메서드 | 실제 설정 | 함정 |
|---|---|---|
| `newFixedThreadPool(n)` | core = max = n, **무한** `LinkedBlockingQueue` | 스레드는 n개로 정상인데 **큐가 끝없이 쌓여 OOM** |
| `newCachedThreadPool()` | core 0, max `Integer.MAX_VALUE`, `SynchronousQueue`, 60초 뒤 회수 | **스레드가 끝없이** 생길 수 있음 |
| `newSingleThreadExecutor()` | 스레드 1개 + 무한 큐, 순서대로 실행 | 무한 큐 |
| `newScheduledThreadPool(n)` | core n개 + 무한 큐 | max를 바꿔도 소용없음 |
| `newVirtualThreadPerTaskExecutor()` (Java 21) | 작업마다 새 가상 스레드 | 상한 없음([가상 스레드](../virtual-threads/) 참고) |

그래서 운영 코드에서는 `ThreadPoolExecutor`를 직접 만들어 **유한 큐 + 거절 정책**을 정하는 경우가 많아요.

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10, 20,                               // core 10, max 20
    60, TimeUnit.SECONDS,                 // 초과 스레드는 60초 놀면 종료
    new ArrayBlockingQueue<>(500),        // 유한 큐: 500개까지만 대기
    new ThreadPoolExecutor.CallerRunsPolicy() // 꽉 차면 제출한 스레드가 직접 실행
);
```

### 5. 거절 정책 4가지

거절은 ① shutdown된 풀에 제출했을 때, ② 최대 스레드와 큐가 **둘 다 유한**하고 모두 찼을 때 일어나요.

| 정책 | 동작 | 언제 |
|---|---|---|
| `AbortPolicy` (**기본값**) | `RejectedExecutionException` 던짐 | 빨리 실패시키고 호출자가 재시도·에러 응답 |
| `CallerRunsPolicy` | 제출한 스레드가 직접 실행 | 제출 속도를 자연스럽게 늦추는 **배압**(backpressure, 받는 쪽이 느리면 보내는 쪽도 늦추는 것) |
| `DiscardPolicy` | 조용히 버림 | 유실돼도 되는 작업(통계 등)만 |
| `DiscardOldestPolicy` | 큐 맨 앞(가장 오래된) 작업을 버리고 재시도 | 거의 권장되지 않음 |

`CallerRunsPolicy`는 편하지만, 제출한 스레드가 톰캣 요청 스레드라면 그 요청이 무거운 작업을 직접 돌리느라 응답이 느려질 수 있어요. 필요하면 `RejectedExecutionHandler`를 직접 구현해도 돼요.

### 6. Future와 CompletableFuture

`submit(Callable)`을 하면 **Future**(나중에 결과를 받을 수 있는 교환권)가 돌아와요.

- `get()`은 결과가 나올 때까지 **블록**(현재 스레드가 멈춰서 기다림)해요.
- 작업이 예외를 던지면 `get()`은 원인을 감싼 `ExecutionException`을 던져요. 기다리다 인터럽트되면 `InterruptedException`, 시간 제한 버전은 `TimeoutException`이에요.
- `cancel(true)`는 실행 중이면 인터럽트를 보내요. 이미 끝난 작업은 취소할 수 없어요.

Future만으로는 "끝나면 이어서 이걸 해라" 같은 조합을 할 수 없고, 결과를 쓰려면 결국 `get()`으로 기다려야 해요. 그래서 콜백을 이어 붙이는 **CompletableFuture**를 많이 써요(일반적인 설명).

```java
ExecutorService io = Executors.newFixedThreadPool(20); // 예시. 운영에선 유한 큐 권장
CompletableFuture<Order> order = CompletableFuture.supplyAsync(() -> orderApi.get(id), io);
CompletableFuture<Ship> ship  = CompletableFuture.supplyAsync(() -> shipApi.get(id), io);

order.thenCombine(ship, OrderView::new)       // 둘 다 끝나면 합치기
     .orTimeout(2, TimeUnit.SECONDS)          // Java 9+: 2초 넘으면 TimeoutException
     .exceptionally(e -> OrderView.empty());  // 예외면 기본값
```

| 메서드 | 하는 일 |
|---|---|
| `supplyAsync` / `runAsync` | 값을 주는 / 안 주는 작업을 비동기로 시작 |
| `thenApply` | 결과를 다른 값으로 변환(스트림의 `map`과 비슷) |
| `thenCompose` | 결과로 **또 다른 CompletableFuture**를 이어 붙이고 평평하게 펼침(`flatMap`과 비슷) |
| `thenCombine` | 두 작업이 **둘 다** 끝나면 두 결과로 함수 실행 |
| `exceptionally` / `handle` | 예외 시 대체 값 / 성공·실패 모두 처리 |
| `allOf` | 전부 끝나면 완료. 반환이 `CompletableFuture<Void>`라 **결과는 각 future에서 `join()`으로 꺼내야** 함 |

- `get()`은 체크 예외 `ExecutionException`, `join()`은 언체크 예외 `CompletionException`을 던져요.
- `thenApply`처럼 `Async`가 안 붙은 콜백은 앞 작업을 끝낸 스레드나 호출한 스레드에서 돌 수 있어요. 어느 쪽인지 보장되지 않아요.

<Aside type="caution" title="Executor를 안 넘기면 공용 풀이에요">
`supplyAsync(supplier)`처럼 Executor를 생략하면 `ForkJoinPool.commonPool()`에서 돌아요. 이 풀의 스레드 수는 보통 **CPU 코어 수 - 1**이고, 병렬 스트림 등과 **공유**해요. 여기서 블로킹 I/O(외부 API 호출 등)를 돌리면 몇 건만으로 풀이 막힐 수 있어요. I/O 작업은 전용 Executor를 두 번째 인자로 넘기는 게 일반적인 관례예요. 병렬 스트림 쪽 이야기는 [람다와 스트림](../lambda-stream/)에 있어요.
</Aside>

### 7. 풀 크기 정하기

아래 공식은 공식 문서가 아니라 *Java Concurrency in Practice* 8.2절에 나오는 **일반적인 출발점**이에요.

| 작업 종류 | 시작값 | 이유 |
|---|---|---|
| CPU 바운드(계산 위주) | 코어 수 + 1 | 스레드가 코어보다 많으면 전환 비용만 늘어요. +1은 잠깐 멈춘 스레드가 있어도 CPU를 놀리지 않으려는 것 |
| I/O 바운드(대기 위주) | 코어 수 × (1 + 대기 시간 / 계산 시간) | 기다리는 동안 다른 스레드가 CPU를 쓰게 하려는 것. 대기가 길수록 더 많이 |

- 코어 수는 `Runtime.getRuntime().availableProcessors()`로 얻어요.
- 공식은 시작점일 뿐이고 실제 값은 **부하 테스트**로 정해요.
- DB 커넥션 풀보다 작업 스레드가 훨씬 많으면, 스레드들이 커넥션을 기다리며 줄을 서니 함께 맞춰야 해요.

### 8. 우아한 종료

| 메서드 | 동작 |
|---|---|
| `shutdown()` | 새 작업은 거부, 이미 받은 작업은 실행. **기다리지 않고 바로 반환** |
| `shutdownNow()` | 실행 중 작업에 인터럽트를 보내고, 대기 중 작업은 실행하지 않고 **목록으로 반환** |
| `awaitTermination(t)` | 다 끝나거나 시간이 지날 때까지 기다림. 끝났으면 true |
| `close()` (Java 19+) | shutdown 후 다 끝날 때까지 **기다림**. try-with-resources 가능 |

`shutdownNow()`도 인터럽트를 보낼 뿐이라, 인터럽트를 무시하는 작업은 계속 돌아요. 그리고 Java 21에서 `ThreadPoolExecutor`는 GC될 때 알아서 닫히지 않으니 **직접 종료**해야 해요. javadoc이 권하는 2단계 패턴은 이래요.

```java
pool.shutdown();                                   // 1단계: 신규 거부
try {
    if (!pool.awaitTermination(60, TimeUnit.SECONDS)) {
        pool.shutdownNow();                        // 2단계: 인터럽트
        if (!pool.awaitTermination(60, TimeUnit.SECONDS))
            log.error("풀이 종료되지 않음");
    }
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();            // 인터럽트 상태 복구
}
```

### 9. Spring의 @Async와 기본 executor

Spring은 `ThreadPoolExecutor`를 감싼 `ThreadPoolTaskExecutor`를 주로 써요. `corePoolSize`, `maxPoolSize`, `queueCapacity`를 설정해요.

| 환경 | @Async 기본 executor | 기본값 |
|---|---|---|
| 순수 Spring Framework | `TaskExecutor` 빈 하나 또는 `taskExecutor` 이름의 빈. 없으면 `SimpleAsyncTaskExecutor`(호출마다 **새 스레드**, 재사용 안 함) | - |
| `ThreadPoolTaskExecutor`를 직접 만들 때 | - | core 1, max·큐 용량 `Integer.MAX_VALUE` |
| Spring Boot 자동 구성(가상 스레드 비활성) | `ThreadPoolTaskExecutor`(`applicationTaskExecutor`) | **core 8**, max·큐 용량 `Integer.MAX_VALUE` |

Boot 기본값도 큐가 사실상 무한이라 **실제로는 스레드 8개만** 쓰고, max는 의미가 없어요. Spring 문서도 무한 큐는 바람직한 경우가 드물고 `OutOfMemoryError`가 날 수 있다고 경고해요. `spring.task.execution.pool.queue-capacity`, `max-size` 등으로 바꿔요.

- `@Async`는 프록시를 거쳐야 동작해요. 같은 클래스 안에서 `this.method()`로 부르면 **동기로** 실행돼요. 다른 빈으로 분리해요.
- `void` 반환 메서드의 예외는 호출자에게 안 가고 로그로만 남아요. `AsyncUncaughtExceptionHandler`를 두거나 `CompletableFuture`를 반환해요.
- 꽉 차서 거절되면 Spring은 기본적으로 `TaskRejectedException`을 던져요.

**답변(30초)** 스레드 생성 비용을 줄이고 동시 실행 수에 상한을 두려고 써요. 스레드는 메모리를 꽤 쓰는 객체라 요청마다 만들고 버리면 부담이 커요. 그리고 상한 없이 만들면 요청이 폭주할 때 스레드가 시스템 용량을 넘어서 모든 요청이 실패해요. 풀은 스레드를 재사용하고 수를 제한해서, 몰려도 처리할 수 있는 만큼은 계속 처리하게 해 줘요.

**꼬리질문**
- Q. 풀의 스레드가 작업 중 예외로 죽으면요? → 고정 크기 풀은 새 스레드로 자동 교체해서 스레드 수를 유지해요.
- Q. 풀을 안 닫으면 GC가 정리해 주나요? → 아니요. Java 21의 ThreadPoolExecutor는 finalize에서 아무것도 안 해요. 직접 shutdown해야 해요.
</details>

<details>
<summary>Q. ThreadPoolExecutor에 작업이 들어오면 어떤 순서로 처리되나요?</summary>

**답변(30초)** 코어 → 큐 → 최대 → 거절 순서예요. 스레드가 corePoolSize 미만이면 노는 스레드가 있어도 새로 만들고, 코어가 다 차면 큐에 넣어요. 큐가 가득 차야 비로소 maximumPoolSize까지 스레드를 늘리고, 그것도 차면 거절 정책을 실행해요. 그래서 큐가 무한이면 스레드는 core개를 넘지 않고 max는 아무 의미가 없어요.

**꼬리질문**
- Q. 큐가 가득 차서 새로 생긴 스레드는 큐의 맨 앞 작업을 가져가나요? → 아니요. 방금 들어온 그 작업을 바로 실행해요.
- Q. 코어 초과 스레드는 언제 없어지나요? → keepAliveTime 동안 놀면 종료돼요. `allowCoreThreadTimeOut(true)`면 코어도 종료돼요.
- Q. 톰캣 스레드 풀도 같은 순서인가요? → 톰캣은 코어를 넘으면 큐보다 스레드를 먼저 늘리는 자체 방식으로 알려져 있어요.
</details>

<details>
<summary>Q. newFixedThreadPool과 newCachedThreadPool의 위험은 뭔가요?</summary>

**답변(30초)** 둘 다 상한이 없는 곳이 있어요. newFixedThreadPool은 스레드 수는 고정이지만 큐가 용량 없는 LinkedBlockingQueue라서, 처리보다 빨리 들어오면 큐가 끝없이 쌓여 OOM이 날 수 있어요. newCachedThreadPool은 큐 없이 SynchronousQueue로 바로 넘기고 max가 Integer.MAX_VALUE라 스레드가 끝없이 늘 수 있어요. 그래서 운영에선 ThreadPoolExecutor를 직접 만들어 유한 큐와 거절 정책을 정해요.

**꼬리질문**
- Q. newFixedThreadPool에서 OOM이 날 때 스레드 수 모니터링으로 알 수 있나요? → 스레드 수는 n개 그대로라 정상으로 보여요. 큐 길이(`getQueue().size()`)를 봐야 해요.
- Q. newCachedThreadPool은 언제 쓰나요? → 짧은 작업이 많고 동시 개수가 자연스럽게 제한되는 경우요. 쉬는 스레드는 60초 뒤 회수돼요.
</details>

<details>
<summary>Q. 거절 정책 4가지를 설명하고, 무엇을 고르겠어요?</summary>

**답변(30초)** 기본값인 AbortPolicy는 RejectedExecutionException을 던지고, CallerRunsPolicy는 제출한 스레드가 직접 실행해요. DiscardPolicy는 조용히 버리고, DiscardOldestPolicy는 큐에서 가장 오래된 작업을 버리고 다시 넣어요. 유실되면 안 되는 작업이면 AbortPolicy로 빨리 실패시켜 재시도하게 하거나, CallerRunsPolicy로 제출 속도를 늦추는 배압을 걸어요. 버리는 정책은 통계처럼 유실돼도 되는 작업에만 써요.

**꼬리질문**
- Q. CallerRunsPolicy의 단점은? → 제출한 스레드가 요청 스레드면 그 요청이 무거운 작업을 직접 돌려서 응답이 느려지고, 요청 스레드 풀까지 막힐 수 있어요.
- Q. 무한 큐에서도 거절이 일어나나요? → 큐가 안 차니까 포화로는 거절되지 않아요. shutdown 뒤 제출할 때만 거절돼요.
</details>

<details>
<summary>Q. Future와 CompletableFuture의 차이는?</summary>

**답변(30초)** Future는 결과를 받으려면 get()으로 블록해서 기다려야 하고, "끝나면 이걸 해라" 같은 조합 기능이 없어요. CompletableFuture는 thenApply, thenCompose, thenCombine으로 콜백을 이어 붙이고, exceptionally로 예외를 처리하고, allOf로 여러 작업을 묶을 수 있어요. 주의할 점은 Executor를 안 넘기면 공용 ForkJoinPool에서 돌기 때문에, 블로킹 I/O에는 전용 Executor를 넘겨야 한다는 거예요.

**꼬리질문**
- Q. thenApply와 thenCompose의 차이는? → 함수가 CompletableFuture를 반환할 때 thenApply는 결과가 중첩되고, thenCompose는 평평하게 이어 붙여요.
- Q. get()과 join()의 차이는? → get은 체크 예외인 ExecutionException, join은 언체크 예외인 CompletionException을 던져요. 원인 예외는 같아요.
- Q. allOf로 결과 리스트를 받을 수 있나요? → 반환이 `CompletableFuture<Void>`라 결과가 없어요. 각 future에서 join으로 꺼내요.
</details>

<details>
<summary>Q. 스레드 풀 크기는 어떻게 정하나요?</summary>

**답변(30초)** 작업 성격에 따라 출발점을 잡고 부하 테스트로 조정해요. 일반적으로 CPU 위주 작업은 코어 수 + 1 정도로 두는데, 그보다 많으면 전환 비용만 늘기 때문이에요. I/O 위주 작업은 기다리는 동안 다른 스레드가 CPU를 쓰게 해야 하니 코어 수 × (1 + 대기 시간/계산 시간)처럼 더 크게 잡아요. 그리고 DB 커넥션 풀 크기도 같이 봐야 해요.

**꼬리질문**
- Q. 이 공식은 어디서 나왔나요? → Java Concurrency in Practice에 나오는 경험식이에요. 정답이 아니라 시작점이에요.
- Q. 스레드를 아주 많이 늘리면 왜 안 되나요? → 메모리를 쓰고, 컨텍스트 스위칭이 늘고, DB 커넥션 같은 뒤쪽 자원에서 줄을 서게 돼요.
</details>

<details>
<summary>Q. shutdown과 shutdownNow의 차이, 우아한 종료는 어떻게 하나요?</summary>

**답변(30초)** shutdown은 새 작업만 거부하고 이미 받은 작업은 끝까지 실행하는데, 기다리지 않고 바로 반환해요. shutdownNow는 실행 중 작업에 인터럽트를 보내고 대기 작업을 목록으로 돌려줘요. 우아한 종료는 shutdown → awaitTermination으로 일정 시간 기다리고 → 안 끝나면 shutdownNow → 다시 awaitTermination 하는 2단계예요. Java 19부터는 close()가 이걸 기다려 줘서 try-with-resources로 쓸 수 있어요.

**꼬리질문**
- Q. shutdownNow면 즉시 다 멈추나요? → 인터럽트를 보낼 뿐이라 인터럽트를 무시하는 작업은 계속 돌아요.
- Q. Spring에서는요? → ThreadPoolTaskExecutor의 `setWaitForTasksToCompleteOnShutdown(true)`와 `setAwaitTerminationSeconds`, Boot는 `spring.task.execution.shutdown.await-termination`으로 설정해요.
</details>

<details>
<summary>Q. Spring @Async의 기본 executor는 뭐고, 주의할 점은?</summary>

**답변(30초)** Spring Boot에서는 ThreadPoolTaskExecutor가 자동 구성되는데 코어 8개에 큐 용량이 Integer.MAX_VALUE라, max를 아무리 크게 잡아도 실제로는 8개 스레드만 쓰고 큐만 쌓여요. 순수 Spring에서 executor 빈이 없으면 호출마다 새 스레드를 만드는 SimpleAsyncTaskExecutor를 써요. 그래서 용도별로 큐 용량과 거절 정책을 정한 executor를 직접 등록하는 게 좋아요.

**꼬리질문**
- Q. @Async를 붙였는데 동기로 돌아요. 왜죠? → 같은 클래스 안에서 this로 부르면 프록시를 안 거쳐서 그래요. 다른 빈으로 분리해요.
- Q. void @Async 메서드에서 예외가 나면? → 호출자에게 전달되지 않고 로그만 남아요. AsyncUncaughtExceptionHandler나 CompletableFuture 반환으로 처리해요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 완료 후 알림 발송을 @Async로 비동기 처리합니다. 이벤트 트래픽이 평소의 10배로 몰린 날, 스레드 수는 정상인데 힙이 계속 차오르다 OutOfMemoryError로 서버가 죽었습니다.</summary>

**상황 파악**
스레드 수가 정상인데 메모리만 늘었다는 건, 일을 처리하는 쪽이 아니라 **기다리는 쪽**이 쌓였다는 신호예요. 비동기 작업은 큐에 들어갔다가 스레드가 꺼내 가요.

**원인 후보**
1. **무한 큐**: Spring Boot 자동 구성 executor는 core 8, 큐 용량 `Integer.MAX_VALUE`예요. 8개가 바쁘면 나머지는 전부 큐에 쌓이고, 큐가 안 차니 max까지 늘지도 않고 거절도 안 돼요. 직접 `Executors.newFixedThreadPool`을 썼어도 무한 `LinkedBlockingQueue`라 같아요.
2. **처리 속도 저하**: 알림 서버가 느려져 작업 하나가 오래 걸리면 소비 속도가 더 떨어져 큐가 더 빨리 커져요.
3. 작업 객체가 주문 정보 등 큰 데이터를 들고 있으면 쌓이는 메모리가 더 커요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 유한 큐 + AbortPolicy | 메모리 상한이 생기고 빨리 실패 | 거절된 알림을 재시도·저장하는 처리를 따로 만들어야 함 |
| B. 유한 큐 + CallerRunsPolicy | 유실 없이 제출 속도가 저절로 느려짐(배압) | 요청 스레드가 알림을 직접 보내 주문 API 응답이 느려짐 |
| C. 메시지 큐(Kafka 등)나 DB에 저장 후 별도 소비 | 서버가 죽어도 작업이 남고, 배포 중 유실도 막음 | 인프라·운영 복잡도 증가 |

어느 쪽이든 외부 호출에 **타임아웃**을 걸고, 큐 길이를 모니터링해야 해요.

**내가 고를 방법**
당장은 A를 적용해요. 큐 용량과 max를 명시하고, 거절되면 실패 기록을 남겨 나중에 재발송하게 해요. 알림은 주문보다 덜 급하니 주문 응답을 늦추는 B보다 낫다고 봐요. 알림 유실이 사업적으로 중요하다면 C로 옮겨 서버 메모리가 아니라 영속 저장소에 작업을 쌓아요.

**채점 포인트**: 스레드 수는 정상인데 메모리 증가 = 큐 적체, 무한 큐(Boot 기본 큐 용량 `Integer.MAX_VALUE`, newFixedThreadPool의 `LinkedBlockingQueue`), 큐가 안 차면 max·거절이 동작 안 함, 유한 큐 + 거절 정책, 거절 정책 트레이드오프, 외부 호출 타임아웃, 큐 길이 모니터링, 중요 작업은 영속화.
</details>

<details>
<summary>상황: 상품 상세 API가 외부 재고 API를 CompletableFuture.supplyAsync로 호출합니다. 재고 API가 느려진 뒤로 상품 상세뿐 아니라 병렬 스트림을 쓰는 다른 기능까지 함께 느려졌습니다.</summary>

**상황 파악**
서로 관계없어 보이는 기능이 같이 느려졌다면 **같은 자원을 나눠 쓰고 있다**는 뜻이에요. 공통점은 스레드 풀이에요.

**원인 후보**
1. **공용 풀 고갈**: Executor를 안 넘긴 `supplyAsync`는 `ForkJoinPool.commonPool()`에서 돌아요. 스레드 수는 보통 코어 수 - 1이라 4코어면 3개뿐이에요. 재고 API를 기다리며 3개가 모두 묶이면 다른 작업은 줄을 서요.
2. **풀 공유**: 병렬 스트림도 같은 공용 풀을 써서 함께 느려져요.
3. **타임아웃 없음**: 느린 응답을 끝까지 기다려 스레드가 오래 묶여요.
4. 요청 스레드에서 바로 `join()`하면 톰캣 요청 스레드까지 함께 묶여요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 재고 API 전용 Executor를 `supplyAsync`의 두 번째 인자로 넘김 | 장애가 재고 호출에만 갇힘(격리) | 풀 크기·큐 용량을 따로 정하고 관리해야 함 |
| B. `orTimeout` / `completeOnTimeout`으로 시간 제한 | 스레드가 오래 묶이지 않음. 기본값으로 응답 가능 | 시간을 짧게 잡으면 정상 응답도 버림 |
| C. 공용 풀 병렬도를 시스템 프로퍼티로 키움 | 코드 변경 없음 | 근본 해결이 아니고 다른 사용처에도 영향 |

**내가 고를 방법**
A와 B를 함께 써요. 전용 Executor로 재고 호출을 격리하고, 그 풀은 유한 큐와 거절 정책을 둬서 재고 API가 아무리 느려도 상한을 넘지 않게 해요. 여기에 `completeOnTimeout`으로 "재고 확인 중" 같은 기본값을 돌려주면 상품 상세는 계속 응답해요. C는 증상만 늦출 뿐이라 고르지 않아요.

**채점 포인트**: Executor 생략 시 `ForkJoinPool.commonPool()`, 공용 풀 크기(보통 코어 수 - 1), 병렬 스트림과 공유, 블로킹 I/O를 공용 풀에서 돌리면 위험, 전용 Executor로 격리, 타임아웃(`orTimeout`/`completeOnTimeout`), 요청 스레드에서 `join()` 주의.
</details>
