:::tip[한 줄 요약]
`count++`는 읽기·더하기·쓰기 세 단계라서 두 스레드가 끼어들면 갱신 하나가 사라져요. synchronized는 한 번에 한 스레드만 들어가게 하고(상호배제) 바뀐 값이 보이게도 해 줘요(가시성). volatile은 가시성만, AtomicInteger는 CAS로 변수 하나를 락 없이 원자적으로 바꿔요. 이 셋은 모두 JVM 하나 안에서만 통해서, 서버가 여러 대면 DB 락이나 분산 락이 필요해요.
:::

:::note[처음이라면 여기까지]
① 여러 스레드가 같은 변수를 동시에 고치면 값이 사라질 수 있어요. `count++`도 읽기·더하기·쓰기 세 단계라서요.

② synchronized는 한 번에 한 스레드만 들어가게 막고, volatile은 바뀐 값이 보이게만, Atomic은 변수 하나를 락 없이 안전하게 바꿔요.

③ 이 셋은 서버 한 대 안에서만 통해요. 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

공유 칠판에 "남은 재고: 1"이 적혀 있어요. 직원 A와 B가 동시에 칠판을 보고 둘 다 "1이네, 하나 팔자"라고 생각해요. 둘 다 지우고 "0"이라고 써요. 물건은 두 개 팔렸는데 칠판은 한 번만 줄었어요. 이게 **경쟁 조건**이에요.

해결책은 칠판 앞에 **열쇠 하나**를 두는 거예요. 열쇠를 든 사람만 칠판을 보고 고칠 수 있고, 나머지는 줄을 서요. 이게 `synchronized`예요.

또 다른 문제도 있어요. A가 칠판을 고쳤는데, B는 아까 찍어 둔 **사진**을 계속 보고 있을 수 있어요. 이게 **가시성** 문제예요. `volatile`은 "사진 보지 말고 매번 칠판을 직접 봐"라는 규칙이에요.

단, 실제 자바는 "사진"이나 "캐시"로 규칙을 정하지 않아요. **happens-before**라는 "이 쓰기는 저 읽기에게 반드시 보인다"는 약속으로 정해요. 사진 비유는 이해를 돕는 그림일 뿐이에요.

## 제대로 알기

### 무엇이 공유되나

스레드끼리 함께 보는 건 **힙에 있는 값**이에요. 객체의 필드, static 필드, 배열 원소가 여기에 해당해요. 메서드 안의 지역변수와 파라미터는 스레드마다 따로라서 동기화가 필요 없어요.

같은 변수에 두 스레드가 접근하고 그중 하나라도 쓰기라면 문제가 생길 수 있어요.

### 경쟁 조건: count++는 한 줄이 아니에요

**경쟁 조건**(race condition, 실행 타이밍에 따라 결과가 달라지는 상황)의 대표 예가 `count++`예요. JVM에서는 이렇게 쪼개져요.

1. count 값을 읽어요.
2. 1을 더해요.
3. count에 다시 써요.

두 스레드가 1번을 동시에 하면 둘 다 0을 읽고, 둘 다 1을 써요. 증가 한 번이 사라졌어요. 이걸 **lost update**(갱신 손실)라고 해요. 타이밍에 따라 멀쩡할 때도 있어서 재현하기도, 찾기도 어려워요.

참고로 참조 변수와 대부분의 기본형은 **읽기 한 번, 쓰기 한 번**은 원자적이에요. 예외는 `long`, `double`이에요. volatile이 아니면 64비트를 32비트씩 두 번에 나눠 쓸 수 있어요. 하지만 원자적인 읽기·쓰기를 이어 붙인 `count++`는 원자적이지 않아요.

### 가시성과 재정렬

**가시성**(visibility) 문제는 한 스레드가 쓴 값을 다른 스레드가 못 보는 거예요.

```java
boolean done = false;  // volatile 아님

// 작업 스레드
while (!done) {
    Thread.sleep(1000);
}
// 다른 스레드가 done = true로 바꿔도 영원히 안 끝날 수 있음
```

컴파일러는 volatile이 아닌 필드를 한 번만 읽고 그 값을 계속 써도 돼요. `Thread.sleep`도 동기화 효과가 없어요.

**재정렬**(reordering)도 있어요. 한 스레드 혼자 결과가 같다면 컴파일러와 CPU는 서로 의존하지 않는 문장의 순서를 바꿀 수 있어요. JIT 컴파일러, 프로세서, 캐시 같은 메모리 계층 모두 원인이 될 수 있어요. 그래서 다른 스레드 입장에서는 "말도 안 되는 순서"가 보일 수 있어요.

### 심화: happens-before: "보인다"는 약속

**happens-before**(hb)는 "A의 쓰기 결과가 B에게 반드시 보인다"는 보장이에요. 이 관계가 없으면 다른 스레드의 쓰기가 보인다는 보장도 없어요.

꼭 알아야 할 규칙은 다섯 개예요.

| 규칙 | 뜻 |
|---|---|
| 프로그램 순서 | 같은 스레드 안에서는 앞 문장이 뒤 문장보다 hb |
| 모니터 락 | 락을 **푸는 것**은 나중에 같은 락을 **잡는 것**보다 hb |
| volatile | volatile 변수 **쓰기**는 나중에 그 변수 **읽기**보다 hb |
| 스레드 시작·종료 | `start()` 호출은 새 스레드의 모든 동작보다 hb, 스레드의 모든 동작은 다른 스레드의 `join()` 반환보다 hb |
| 이행성 | A hb B이고 B hb C면 A hb C |

이행성이 중요해요. 스레드 A가 `data = 42` 후 락을 풀고, 스레드 B가 같은 락을 잡은 뒤 `data`를 읽으면 42가 보장돼요. 락 안에서 한 일뿐 아니라 **락을 풀기 전에 한 모든 쓰기**가 넘어가요.

**데이터 경쟁**(data race)은 충돌하는 두 접근 사이에 hb가 없는 상태예요. 데이터 경쟁이 하나도 없는 프로그램은 "한 줄씩 순서대로 실행된 것처럼" 동작해요. 그러니 hb만 제대로 걸어 주면 재정렬은 신경 쓰지 않아도 돼요.

`java.util.concurrent` 도구도 hb를 줘요. 예를 들어 동시성 컬렉션에 넣기 전의 동작은 다른 스레드가 꺼낸 뒤에 보이고, `Future`의 계산 결과는 `get()` 뒤에 보여요.

### synchronized: 모니터 락

모든 객체에는 **모니터**(monitor, 고유 락)가 하나씩 있어요. 한 번에 한 스레드만 가질 수 있고, 나머지는 기다려요.

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() { count++; }  // this의 락
    public synchronized int get() { return count; }    // 읽기도 같은 락
}
```

- 인스턴스 메서드는 `this`의 락, `static synchronized`는 그 클래스의 `Class` 객체 락을 잡아요. **서로 다른 락**이라 서로 막지 않아요.
- 블록이 정상으로 끝나든 예외로 끝나든 자동으로 풀려요.
- **재진입**(reentrant)이 돼요. 이미 가진 락은 또 잡을 수 있어서, synchronized 메서드가 같은 락의 다른 synchronized 메서드를 불러도 스스로 막히지 않아요.
- `synchronized (lock) { ... }` 블록으로 필요한 부분만 잠글 수 있어요.
- 상호배제와 가시성을 **둘 다** 줘요. 그래서 위 예처럼 **읽는 `get()`도 같은 락**으로 묶어야 최신 값이 보여요.

<Aside type="note" title="wait와 notify">
조건이 될 때까지 기다리려면 `wait`, 깨우려면 `notify`/`notifyAll`을 써요. 아무 이유 없이 깨어나는 경우(가짜 깨어남)가 허용되므로 `wait`는 항상 `while`로 조건을 다시 확인하며 써요.
</Aside>

### volatile: 보이게만 해 줘요

volatile 변수에 쓰면, 그 뒤에 읽는 스레드는 쓴 값과 **쓰기 전에 한 일**까지 모두 봐요. volatile `long`, `double`의 읽기·쓰기는 원자적이에요.

하지만 **상호배제는 없어요.** 그래서 쓰임새가 정해져 있어요.

- 맞는 곳: 한 스레드가 쓰고 여러 스레드가 읽는 플래그(`volatile boolean running`)
- 안 맞는 곳: `count++` 같은 읽기-수정-쓰기. 세 단계 사이에 여전히 끼어들 수 있어요.

### Atomic과 CAS

**CAS**(Compare-And-Swap, "지금 값이 내가 예상한 값일 때만 바꾸는" 원자적 연산)는 락 없이 변수 하나를 안전하게 바꾸는 방법이에요. CPU의 원자적 비교-교환 명령으로 구현돼요.

```java
AtomicInteger count = new AtomicInteger();
count.incrementAndGet();  // 1 더한 새 값 반환 (getAndIncrement는 이전 값)

// CAS 재시도 루프의 원리
int cur, next;
do {
    cur = count.get();          // 1. 현재 값 읽기
    next = cur + 1;             // 2. 새 값 계산
} while (!count.compareAndSet(cur, next));  // 3. 그새 바뀌었으면 실패 → 다시
```

- `compareAndSet(expected, new)`: 현재 값이 expected면 new로 바꾸고 true, 아니면 아무것도 안 하고 false예요.
- Atomic의 `get`/`set`은 volatile 읽기/쓰기처럼 동작해서 가시성도 보장돼요.
- **원자성은 변수 하나 단위**예요. AtomicInteger 두 개를 각각 바꿔도 "두 값이 함께 맞아야 하는" 규칙은 못 지켜요. 그땐 락이 필요해요.
- `AtomicInteger`는 `equals`/`hashCode`를 재정의하지 않아서 `Integer` 대신 쓰거나 맵 키로 쓰면 안 돼요.

CAS의 약점도 두 가지 알아 두세요.

- **ABA 문제**: 값이 A → B → A로 바뀌면 CAS는 "안 바뀌었다"고 판단해요. 값에 버전을 붙이는 `AtomicStampedReference`로 피해요.
- **경합이 심하면 느려요**: 실패할 때마다 다시 돌기 때문에 CPU를 낭비해요. 그래서 CAS 같은 낙관적 방식은 충돌이 드물 때 유리해요.

`LongAdder`는 합계를 여러 칸에 나눠 세서 경합을 줄여요. 경합이 높을 때 `AtomicLong`보다 처리량이 훨씬 높지만 메모리를 더 쓰고, `sum()`은 정확한 순간 스냅샷이 아니에요. 조회수 같은 통계 집계에 맞아요.

### ReentrantLock

`ReentrantLock`은 synchronized와 **같은 의미**의 재진입 락에 기능을 더한 거예요.

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // 임계 구역
} finally {
    lock.unlock();  // 자동 해제가 없으니 반드시 finally에서
}
```

| | synchronized | ReentrantLock |
|---|---|---|
| 해제 | 블록 끝나면 자동 | `finally`에서 직접 `unlock()` |
| 기다리다 포기 | 불가 | `tryLock()`, `tryLock(시간)` |
| 대기 중 인터럽트 | 불가 | `lockInterruptibly()` |
| 공정성 | 없음 | `new ReentrantLock(true)`로 오래 기다린 순서 |
| 조건 대기 | 객체당 wait set 1개 | `newCondition()`으로 여러 개 |

- 기본은 **비공정**이에요. 공정 락은 기아가 없지만 처리량이 훨씬 낮을 수 있어요. 시간 없는 `tryLock()`은 공정 모드여도 순서를 무시하고 끼어들어요.
- 공식 문서는 "ReentrantLock이 더 빠르다"고 하지 않아요. **tryLock, 타임아웃, 인터럽트, 여러 Condition이 필요할 때** 골라요.

### 데드락, 기아, 라이브락

- **데드락**(deadlock, 교착 상태): 둘 이상의 스레드가 서로가 가진 락을 기다리며 영원히 멈춘 상태예요.
- **기아**(starvation): 한 스레드가 락을 오래 쥐고 있어서 다른 스레드가 계속 기회를 못 얻는 상태예요.
- **라이브락**(livelock): 멈추진 않았는데 서로 양보만 반복해서 진행이 안 돼요. 복도에서 서로 같은 쪽으로 계속 비켜 주는 두 사람 같아요.

데드락은 아래 **네 조건이 모두** 성립해야 생길 수 있어요.

| 조건 | 뜻 | 깨는 방법 |
|---|---|---|
| 상호배제 | 자원을 한 번에 하나만 씀 | 자원 성질상 보통 못 깸 |
| 점유와 대기 | 하나를 쥔 채 다른 걸 기다림 | 필요한 걸 한 번에 다 요청 |
| 비선점 | 남이 가진 걸 강제로 못 뺏음 | 못 얻으면 가진 걸 반납 |
| 순환 대기 | 서로 꼬리를 물고 기다림 | 자원에 번호를 매겨 순서대로만 요청 |

자바에서는 두 가지를 주로 써요.

1. **락 순서 고정**: 예를 들어 계좌 이체라면 계좌 ID가 작은 쪽부터 잠가요. 순환 대기가 깨져요.
2. **tryLock으로 물러나기**: 두 번째 락을 못 얻으면 첫 번째 락도 풀고 다시 시도해요. 가진 락을 스스로 내놓으니 비선점 조건이 깨져요(위 표의 "못 얻으면 반납").

자바는 데드락을 막지도 자동으로 풀지도 않아요. 찾는 건 도구로 해요. `jstack`이나 `jcmd <pid> Thread.print` 출력 끝에 "Found one Java-level deadlock"이 나오고, 코드에서는 `ThreadMXBean.findDeadlockedThreads()`로 synchronized와 ReentrantLock의 순환 대기를 찾을 수 있어요.

### 한 JVM 밖에서는 무력해요

synchronized, ReentrantLock, Atomic은 모두 **JVM 하나(프로세스 하나) 안**의 스레드만 조정해요. 서버가 두 대면 각 서버가 자기 락을 따로 가지니 서로를 전혀 막지 못해요. 여러 서버가 같은 DB 행을 고친다면 DB 수준 제어(원자적 UPDATE, 비관적 락, 낙관적 락)나 Redis 같은 분산 락이 필요해요. 이 부분은 JLS가 직접 정한 규칙이 아니라, 락이 "JVM 안의 객체"라는 정의에서 나오는 실무 상식이에요. DB 락과 Redis 분산 락은 DB·Redis 섹션에서 자세히 다뤄요.

<summary>Q. 경쟁 조건이 뭔가요? count++는 왜 스레드 안전하지 않나요?</summary>

**답변(30초)** 경쟁 조건은 여러 스레드가 공유 자원에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 상황이에요. `count++`는 한 줄이지만 읽기, 더하기, 쓰기 세 단계예요. 두 스레드가 같은 값 0을 읽고 둘 다 1을 쓰면 증가 하나가 사라지는 lost update가 생겨요. 그래서 synchronized로 세 단계를 묶거나 AtomicInteger의 `incrementAndGet()`을 써요.

**꼬리질문**
- Q. 지역변수도 위험한가요? → 아니요. 지역변수와 파라미터는 스레드마다 따로라서 공유되지 않아요. 문제는 힙의 필드, static 필드, 배열 원소예요.
- Q. int 대입 한 번은 원자적인가요? → 네. long, double을 뺀 기본형과 참조의 읽기·쓰기 한 번은 원자적이에요. long, double은 volatile로 선언하거나 락으로 보호해야 원자적이에요.
</details>

<details>
<summary>Q. synchronized, volatile, Atomic의 차이는?</summary>

**답변(30초)** synchronized는 상호배제와 가시성을 둘 다 줘요. 한 번에 한 스레드만 들어가고, 락을 풀기 전 쓰기가 다음에 락을 잡는 스레드에게 보여요. volatile은 가시성과 순서만 보장하고 상호배제가 없어서 `count++`를 못 지켜요. Atomic은 CAS로 변수 하나의 읽기-수정-쓰기를 락 없이 원자적으로 해요. 그래서 플래그는 volatile, 단일 카운터는 Atomic, 여러 변수를 함께 바꿔야 하면 synchronized예요.

**꼬리질문**
- Q. 읽기 메서드에도 synchronized가 필요한가요? → 네. 쓰기와 같은 락으로 묶지 않으면 hb가 없어서 오래된 값을 볼 수 있어요.
- Q. static synchronized와 인스턴스 synchronized는 서로 막나요? → 아니요. 앞은 Class 객체 락, 뒤는 this 락이라 서로 다른 락이에요.
</details>

<details>
<summary>Q. 데드락의 4가지 조건과 예방법은?</summary>

**답변(30초)** 데드락은 상호배제, 점유와 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때 생길 수 있어요. 그래서 하나만 깨면 예방돼요. 자바에서는 보통 락 획득 순서를 전역으로 고정해서 순환 대기를 깨고, `tryLock`에 타임아웃을 줘서 못 얻으면 가진 락을 풀어 비선점 조건을 깨요. 발생 여부는 jstack이나 ThreadMXBean으로 찾아요.

**꼬리질문**
- Q. 송금 A→B, B→A가 동시에 일어나면? → 각자 출금 계좌부터 잠그면 데드락이에요. 계좌 ID가 작은 쪽부터 잠그면 두 스레드가 같은 순서로 기다려서 안 생겨요.
- Q. 상호배제는 왜 못 깨나요? → 락 자체가 "한 번에 하나"라는 성질이라 깨면 동기화 의미가 없어져요.
- Q. 기아, 라이브락과는 뭐가 다른가요? → 기아는 남이 오래 쥐고 있어 기회를 못 얻는 것, 라이브락은 멈추진 않았지만 서로 반응만 하느라 진행이 안 되는 거예요.
</details>

<details>
<summary>Q. CAS가 뭔가요? 단점은요?</summary>

**답변(30초)** CAS는 "현재 값이 예상한 값과 같을 때만 새 값으로 바꾸는" 원자적 연산으로, CPU 명령으로 구현돼요. AtomicInteger는 현재 값을 읽고, 새 값을 계산하고, `compareAndSet`이 실패하면 다시 시도하는 루프로 락 없이 원자성을 지켜요. 단점은 경합이 심하면 재시도가 반복돼 CPU를 낭비한다는 점과, A→B→A로 바뀐 걸 못 알아채는 ABA 문제예요.

**꼬리질문**
- Q. ABA는 어떻게 피하나요? → `AtomicStampedReference`처럼 값에 버전 스탬프를 같이 붙여 비교해요.
- Q. 경합이 심한 카운터라면? → `LongAdder`를 써요. 여러 칸에 나눠 세서 처리량이 높아요. 대신 `sum()`이 정확한 순간 스냅샷은 아니에요.
- Q. DB에도 비슷한 게 있나요? → 낙관적 락이 같은 발상이에요. 버전이 그대로일 때만 업데이트하고 실패하면 재시도해요.
</details>

<details>
<summary>Q. synchronized와 ReentrantLock은 언제 무엇을 쓰나요?</summary>

**답변(30초)** 둘 다 같은 의미의 재진입 락이에요. 기본은 자동으로 풀리는 synchronized를 써요. 락을 기다리다 포기해야 하거나(`tryLock`, 타임아웃), 대기 중 인터럽트를 받아야 하거나, 공정성이나 여러 개의 Condition이 필요하면 ReentrantLock을 써요. ReentrantLock은 자동 해제가 없어서 반드시 `finally`에서 `unlock()` 해야 해요.

**꼬리질문**
- Q. 공정 락이 항상 좋은가요? → 기아는 없지만 처리량이 훨씬 낮을 수 있어요. 기본값은 비공정이에요.
- Q. ReentrantLock이 더 빠른가요? → 공식 문서는 성능 우위를 말하지 않아요. 기능 차이로 골라요.
</details>

<details>
<summary>Q. happens-before를 쉽게 설명해 주세요.</summary>

**답변(30초)** happens-before는 "A의 쓰기 결과가 B에게 반드시 보인다"는 자바 메모리 모델의 약속이에요. 이 관계가 없으면 다른 스레드의 쓰기가 보인다는 보장이 없어요. 대표 규칙은 같은 스레드의 프로그램 순서, 락 해제 → 같은 락 획득, volatile 쓰기 → 읽기, `start()`와 `join()`이에요. 이행성이 있어서 락을 풀기 전 모든 쓰기가 다음에 락을 잡는 스레드에게 넘어가요.

**꼬리질문**
- Q. 왜 이런 규칙이 필요하죠? → 컴파일러, CPU, 캐시가 성능을 위해 순서를 바꾸거나 값을 들고 있을 수 있어서예요. hb로 데이터 경쟁을 없애면 순서대로 실행된 것처럼 동작해요.
- Q. Thread.sleep을 넣으면 값이 보이나요? → 아니요. sleep과 yield는 동기화 효과가 없어요.
</details>

<details>
<summary>Q. 싱글톤 이중 검사 락(DCL)에 volatile이 왜 필요한가요?</summary>

**답변(30초)** 객체 생성은 메모리 할당, 필드 초기화, 참조 대입으로 나뉘는데 이 순서가 재정렬될 수 있어요. 그러면 다른 스레드가 첫 번째 null 검사를 락 없이 하다가, 참조는 대입됐지만 초기화가 덜 된 객체를 받아 쓸 수 있어요. instance를 volatile로 선언하면 volatile 쓰기 → 읽기 사이에 hb가 생겨서, 참조가 보이는 순간 초기화도 끝난 상태가 보장돼요.

**꼬리질문**
- Q. final 필드는요? → 생성자가 끝난 뒤 참조를 본 스레드는 final 필드의 올바른 값을 보장받아요. 단, 생성자 안에서 this가 밖으로 새면 안 돼요.
</details>

## 서술형 연습

<details>
<summary>상황: 선착순 이벤트 상품 재고 차감을 synchronized 메서드로 막아서 테스트를 통과했습니다. 그런데 운영에서 서버를 2대로 늘리자 재고가 다시 음수가 되고, 판매량이 재고보다 많아졌습니다.</summary>

**상황 파악**
재고 차감은 "조회 → 남았는지 검사 → 차감"이에요. 이 세 단계가 원자적이지 않으면 `count++`와 같은 lost update가 DB에서 일어나요. 한 대일 때 막혔던 건 synchronized가 그 JVM 안의 스레드를 줄 세웠기 때문이에요.

**원인 후보**
1. **synchronized의 범위가 JVM 하나**: 서버 1의 락과 서버 2의 락은 서로 다른 객체예요. 두 서버의 요청이 같은 재고 1을 동시에 읽고 둘 다 차감해요.
2. **(한 대여도 남은 틈)** `@Transactional`과 같이 쓰면 락이 풀린 뒤 커밋 전에 다른 스레드가 옛 값을 읽을 수 있어요(다음 문제 참고).
3. 조회 후 애플리케이션에서 계산해 덮어쓰는 `UPDATE ... SET stock = ?` 방식이라, 중간에 바뀐 값을 무시하고 덮어써요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 원자적 UPDATE: `UPDATE item SET stock = stock - 1 WHERE id = ? AND stock > 0` 후 영향받은 행 수 확인 | 가장 단순, 추가 인프라 없음, DB가 한 문장으로 검사와 차감을 같이 함 | 차감 외에 복잡한 검증(사용자별 구매 제한 등)을 같이 묶기 어려움 |
| B. 비관적 락: `SELECT ... FOR UPDATE`로 행을 잠그고 처리 | 복잡한 로직도 안전하게 묶음 | 인기 상품 한 행에 요청이 몰리면 대기가 길어짐, 잠그는 순서가 다르면 DB 데드락 |
| C. 낙관적 락: 버전 컬럼으로 `WHERE version = ?`일 때만 업데이트, 실패 시 재시도 | 충돌이 드물면 락 대기 없이 빠름(CAS와 같은 발상) | 선착순처럼 충돌이 많으면 재시도가 폭증 |
| D. Redis 분산 락 또는 Redis `DECR` 원자 연산 | DB 부하를 줄이고 여러 서버를 함께 조정 | 운영할 인프라가 늘고, 락 만료(TTL)·해제 실패·Redis와 DB 값 불일치를 처리해야 함 |

**내가 고를 방법**
A를 먼저 골라요. 재고 차감은 "0보다 크면 1 빼기"라서 SQL 한 문장으로 끝나고, 영향받은 행 수가 0이면 품절로 처리하면 돼요. 서버 대수와 상관없이 DB가 정확성을 지켜 줘요. 구매 제한처럼 여러 행을 함께 검증해야 하면 B를 쓰고, 이때는 행을 잠그는 순서를 고정해요. 트래픽이 커서 DB 한 행이 병목이 되면 그때 D로 앞단에서 걸러요. 충돌이 많은 선착순에는 C를 피해요.

**채점 포인트**: 조회-검사-차감이 원자적이지 않음(lost update), synchronized는 JVM 하나 범위라 스케일 아웃에서 무력, 원자적 UPDATE와 영향 행 수 확인, 비관적 락의 대기·데드락, 낙관적 락은 충돌 적을 때 유리(재시도), 분산 락의 TTL·운영 복잡도, 정확성 vs 처리량 vs 운영 복잡도 트레이드오프, 해결책 2개 이상 비교.
</details>

<details>
<summary>상황: 서버 1대에서 포인트 차감 메서드에 @Transactional과 synchronized를 함께 붙였는데도, 동시 요청 테스트에서 가끔 포인트가 덜 차감됩니다.</summary>

**상황 파악**
synchronized가 있으니 메서드 안은 한 번에 한 스레드만 들어가요. 그런데도 갱신이 사라진다면, 락이 지켜 주는 구간과 트랜잭션이 커밋되는 시점이 어긋났다는 뜻이에요.

**원인 후보**
1. **락 해제와 커밋 사이의 틈**: `@Transactional`은 스프링 프록시가 메서드를 감싸서, 메서드가 끝난 **뒤에** 커밋해요. synchronized는 메서드 본문이 끝나는 순간 풀려요. 그 사이에 다음 스레드가 들어와 아직 커밋 안 된 옛 포인트를 읽고 차감해요. (스프링 실무에서 널리 알려진 함정이에요.)
2. 서버를 늘리면 원인 1과 상관없이 synchronized 자체가 무력해져요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 락을 트랜잭션 바깥에서 잡기: synchronized를 트랜잭션 메서드를 호출하는 바깥 메서드에 둠. 단, 바깥 메서드는 **다른 빈**이어야 함(같은 클래스 안 호출은 프록시를 안 거쳐 트랜잭션이 아예 안 걸림) | 틈이 사라짐, 코드 변경 적음 | 여전히 JVM 하나 범위, 모든 사용자의 차감이 한 줄로 서서 느림 |
| B. 원자적 UPDATE: `UPDATE point SET balance = balance - ? WHERE user_id = ? AND balance >= ?` | 서버 여러 대에도 안전, synchronized 불필요 | 잔액 외 여러 조건을 함께 검사하기 어려움 |
| C. 비관적 락: `SELECT ... FOR UPDATE`로 사용자 행을 트랜잭션 안에서 잠금 | 락이 커밋 시점까지 유지돼 틈이 없음, 사용자별로 잠가서 서로 다른 사용자는 동시 처리 | 같은 사용자 동시 요청은 대기, 여러 행을 잠그면 순서 고정 필요 |

**내가 고를 방법**
synchronized를 빼고 B를 골라요. 락이 DB 트랜잭션과 같이 움직여야 틈이 없는데, 애플리케이션 락은 커밋 시점을 모르기 때문이에요. 차감 전 여러 조건을 확인해야 하면 C로 바꿔요. A는 원인을 이해했다는 걸 보여 주는 임시 처방일 뿐, 서버 증설을 생각하면 답이 아니에요.

**채점 포인트**: 프록시가 메서드 종료 후 커밋, synchronized 해제 시점과 커밋 시점의 어긋남, 커밋 전 옛 값 읽기(lost update), 락 범위는 트랜잭션보다 넓거나 같아야 함, JVM 하나 범위 한계, DB 수준 제어(원자적 UPDATE·비관적 락)로 이동, 해결책 2개 이상의 트레이드오프.
</details>

## 필기 포인트

- 교착 상태 4조건: **상호배제, 점유와 대기, 비선점, 순환 대기**. 넷 다 성립해야 발생할 수 있음(필요조건). 하나만 있다고 생기지 않음.
- 순환 대기는 점유와 대기를 포함해서, 네 조건이 서로 완전히 독립은 아님.
- 해결 방법 분류: **예방**(조건 하나 깨기), **회피**(은행원 알고리즘으로 위험한 할당 거부), **탐지 후 회복**(프로세스 중단, 자원 선점), **무시**.
- 예방: 한 번에 모두 요청(점유와 대기 방지, 자원 효율 낮고 기아 가능), 못 얻으면 반납(비선점 방지), 자원 번호 오름차순 요청(순환 대기 방지). 상호배제는 보통 못 깸.
- 자바 함정: volatile은 원자성 X, static synchronized와 인스턴스 synchronized는 다른 락, 시간 없는 `tryLock()`은 공정성 무시, `wait`/`await`는 while 루프.
