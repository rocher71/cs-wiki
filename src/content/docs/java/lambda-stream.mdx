:::tip[한 줄 요약]
람다는 추상 메서드가 하나뿐인 함수형 인터페이스를 짧게 구현하는 식이에요. 스트림의 중간 연산은 지연돼서 최종 연산을 호출해야 실행되고, 요소 하나가 filter부터 끝까지 통과한 다음에 다음 요소가 들어가요.
:::

:::note[처음이라면 여기까지]
① 람다는 메서드 하나짜리 인터페이스를 짧게 쓰는 문법이에요.

② 스트림은 filter·map 같은 중간 단계를 적어 두기만 하고, 마지막 단계(collect 등)를 부를 때 실제로 실행해요.

③ 면접에선 질문 1·2번 먼저 연습하세요.
:::

## 쉽게 이해하기

람다는 **심부름 쪽지**예요. "이 사람이 성인이면 체크해 줘"라고 적어서 건네면, 받은 쪽이 필요할 때 꺼내 읽고 실행해요. 쪽지를 쓰는 순간에 일이 일어나는 건 아니에요.

스트림은 **주문이 들어와야 돌아가는 공장 라인**이에요. `filter`, `map`을 이어 붙이는 건 라인에 기계를 설치하는 일일 뿐이에요. 마지막에 "완성품 하나 주세요"(`findFirst`)라는 주문이 들어와야 원료가 하나씩 라인을 타요. 첫 원료가 끝까지 가서 완성품이 나오면, 나머지 원료는 라인에 올리지도 않아요.

단, 실제로는 `sorted()`처럼 **전부 모아야 일할 수 있는 기계**도 있어요. 이 기계 앞에서는 원료가 다 쌓일 때까지 흐름이 멈춰요.

## 제대로 알기

### 1. 함수형 인터페이스

**함수형 인터페이스**(functional interface, 추상 메서드가 딱 하나인 인터페이스)는 "함수 하나짜리 약속"이에요. 람다와 메서드 참조는 이 인터페이스의 객체를 만드는 짧은 문법이에요.

- default·static 메서드는 구현이 있으니 개수에 안 쳐요. `equals`처럼 Object의 메서드를 다시 적은 것도 안 쳐요. 그래서 `Comparator`는 `compare`와 `equals`를 둘 다 선언하지만 함수형 인터페이스예요.
- `@FunctionalInterface`는 없어도 조건만 맞으면 람다를 쓸 수 있어요. 붙이면 조건을 어겼을 때 컴파일 에러를 내 줘요(실수 방지용).

| 인터페이스 | 모양 | 예 |
|---|---|---|
| `Function<T,R>` | T 받아서 R 반환 | `s -> s.length()` |
| `Consumer<T>` | T 받고 반환 없음 | `s -> System.out.println(s)` |
| `Predicate<T>` | T 받아서 boolean | `s -> s.isEmpty()` |
| `Supplier<T>` | 인자 없이 값 반환 | `() -> new ArrayList<>()` |

인자가 2개면 `BiFunction`처럼 `Bi`가 붙고, `IntPredicate`처럼 기본형 전용 버전도 있어요(int를 Integer 객체로 감싸는 **박싱** 비용을 피하려는 용도로 알려져 있어요).

### 2. 람다와 익명 클래스는 무엇이 다른가

| | 익명 클래스 | 람다 |
|---|---|---|
| `this` | 익명 클래스 객체 자신 | 람다를 감싼 바깥 클래스 객체 |
| 클래스 파일 | 따로 생김 | 따로 안 생김(`invokedynamic`으로 실행 중에 만든다고 알려져 있음) |
| 객체 정체성 | `new`라 매번 새 객체 | 새로 만들지 재사용할지 정해져 있지 않음 → `==`, `synchronized`에 쓰면 안 됨 |

**메서드 참조**(method reference, `::`로 메서드를 호출하지 않고 가리키기)는 람다를 더 줄인 형태예요. `Integer::parseInt`(정적), `System.out::println`(특정 객체), `String::length`(첫 인자가 호출 대상), `ArrayList::new`(생성자)가 있어요. `String::length`는 "String 하나 받아 int 반환"이라 `Function<String, Integer>` 자리에 들어갈 수 있어요.

### 3. 캡처와 effectively final

람다가 바깥의 **지역변수**를 쓰는 걸 **캡처**(capture)라고 해요. 이 변수는 `final`이거나 **effectively final**(final을 안 붙였지만 선언 후 한 번도 바뀌지 않는 변수)이어야 해요.

```java
int count = 0;
list.forEach(s -> count++);      // 컴파일 에러: 람다 안에서 대입

int base = 10;
Runnable r = () -> System.out.println(base);
base = 20;                       // 컴파일 에러: 람다 뒤에서 바꿔도 위반

List<String> out = new ArrayList<>();
list.forEach(s -> out.add(s));   // 컴파일은 됨 (변수 out은 그대로)
```

- **이유**: JLS(자바 언어 명세)는 계속 바뀌는 지역변수를 캡처하게 두면 **동시성 문제**가 생기기 쉬워서 막았다고 설명해요. 람다는 다른 스레드에서, 나중에 실행될 수 있으니까요. 흔히 "지역변수는 스택에 있어서 람다가 값을 복사해 가져간다"는 설명도 덧붙여요.
- 막는 건 **변수 재대입**뿐이에요. 위 `out.add`처럼 가리키는 객체 안을 바꾸는 건 컴파일러가 못 막아요. 하지만 스트림에서 이렇게 하면 아래 5번의 규칙 위반이에요.
- 필드(인스턴스·static 변수)는 이 제한 대상이 아니에요.
- 향상된 for문(`for (String s : arr)`)의 `s`는 반복마다 새 변수라 캡처돼요. 일반 for문의 `i`는 증가하니 안 돼요.

### 4. 스트림: 중간 연산, 최종 연산, 지연

스트림 파이프라인은 **소스**(컬렉션, 배열 등) + **중간 연산** 0개 이상 + **최종 연산** 1개예요.

| | 중간 연산 | 최종 연산 |
|---|---|---|
| 예 | `filter`, `map`, `sorted`, `distinct`, `limit` | `forEach`, `collect`, `toList`, `reduce`, `count`, `findFirst` |
| 반환 | 새 스트림 | 결과값(또는 void) |
| 실행 시점 | **지연**(lazy): 호출해도 아무 일 없음 | 호출하는 순간 소스 순회 시작 |

- 최종 연산이 없으면 중간 연산의 람다는 **한 번도 실행되지 않아요**.
- **수직 실행**: 요소 하나가 filter → map → 최종 연산까지 다 통과한 뒤 다음 요소가 들어가요. 공식 문서 표현으로는 여러 단계를 데이터 위 "한 번의 통과"로 합쳐요. 그래서 중간 목록을 만들지 않아요.
- **단락 연산**(short-circuiting, 다 안 보고 일찍 끝낼 수 있는 연산): `findFirst`, `anyMatch`, `limit` 등. 무한 스트림도 이게 있어야 끝날 수 있어요.
- **상태 있는 중간 연산**(`sorted`, `distinct`, `limit`, `skip`)은 앞서 본 요소를 기억해야 해요. 특히 `sorted`는 전부 받아야 결과를 낼 수 있어서 수직 흐름을 끊어요. `filter`, `map`은 **무상태**예요.
- 스트림은 **한 번만** 쓸 수 있어요. 최종 연산을 두 번 부르면 `IllegalStateException`이 날 수 있어요. 또 원본을 바꾸지 않아요(filter해도 원본 리스트는 그대로).

<Aside type="caution" title="peek 로그가 안 찍혀요">
`list.stream().peek(System.out::println).count()`는 아무것도 안 찍을 수 있어요. `count()`는 소스 크기를 바로 알면 파이프라인을 아예 돌리지 않을 수 있어서예요. `peek`은 디버깅용으로만 쓰세요.
</Aside>

`Stream.toList()`(Java 16+)는 **수정 불가** 리스트를 줘요. `add`하면 `UnsupportedOperationException`이에요. `Collectors.toList()`는 가변성을 보장하지 않아요(현재 구현이 ArrayList라 수정이 될 뿐이에요).

### 심화: 5. 스트림에 넘기는 람다의 규칙

- **비간섭**: 파이프라인이 도는 동안 소스 컬렉션을 수정하지 마세요. ArrayList라면 보통 `ConcurrentModificationException`이 나요.
- **무상태·부작용 없음**: 바깥 리스트에 `add`하거나 카운터를 올리지 마세요. 공식 문서가 직접 든 안티패턴이 `forEach(s -> results.add(s))`예요. 병렬에서 결과가 틀려요. 대신 `toList()`, `collect`, `count()` 같은 **리덕션**(reduction, 요소들을 하나의 결과로 모으는 연산)을 써요.

### 6. 병렬 스트림 주의

`parallelStream()`이나 `.parallel()`로 병렬 처리를 요청할 수 있어요. 파이프라인 중간에 넣어도 **마지막 설정이 전체에 적용**돼요(일부 구간만 병렬은 안 돼요).

| 주의점 | 이유 |
|---|---|
| 공유 가변 상태 금지 | 동기화 안 하면 데이터 경쟁, 동기화하면 경합으로 병렬 이득이 사라짐 |
| 순서 의존 연산은 비쌈 | `limit` 등은 순서를 지키려고 버퍼링. 순서가 필요 없으면 `unordered()` |
| `groupingBy` 병합 비용 | Map끼리 합치는 비용 때문에 오히려 느릴 수 있음 |
| `reduce` 함수 | 결합법칙을 만족하고 무상태여야 함 |
| 블로킹 I/O 금지 | 아래 공용 풀 문제 |

**공용 ForkJoinPool**(JVM 하나에 하나 있는 공용 작업 스레드 풀): 병렬 스트림은 기본적으로 이 풀에서 돈다고 널리 알려져 있어요(공식 스트림 문서에 명시된 내용은 아니에요). 기본 스레드 수는 보통 CPU 코어 수 - 1이에요. 그래서 병렬 스트림 안에서 DB·HTTP 호출처럼 기다리는 작업을 하면, 같은 JVM의 다른 병렬 스트림과 `CompletableFuture` 기본 실행까지 같이 막힐 수 있어요. 풀 크기는 `java.util.concurrent.ForkJoinPool.common.parallelism` 시스템 속성으로 바꿀 수 있어요.

병렬이 이득인 경우는 보통 요소가 많고, 요소당 계산이 무겁고, ArrayList·배열·`IntStream.range`처럼 쪼개기 쉬운 소스일 때라고 알려져 있어요. LinkedList나 `Stream.iterate`는 쪼개기 어려워요.

### 7. Optional 올바르게 쓰기

**Optional**은 값이 있거나 비어 있을 수 있는 상자예요(Java 8). 공식 문서가 밝힌 용도는 **"결과 없음"을 표현해야 하는 메서드의 반환 타입**이에요.

```java
// 사용자가 있어도 createDefaultUser()가 매번 실행됨
User u1 = repo.findById(id).orElse(createDefaultUser());

// 비어 있을 때만 실행됨
User u2 = repo.findById(id).orElseGet(() -> createDefaultUser());

// get() 대신 (Java 10+)
User u3 = repo.findById(id).orElseThrow();
```

- **orElse vs orElseGet**: `orElse`의 인자는 메서드에 넘기기 전에 **항상 먼저 계산**돼요(자바 인자 평가 규칙). `orElseGet`은 Supplier를 받아서 **비어 있을 때만** 호출해요. 기본값 만들기가 비싸면(DB 조회, INSERT, 객체 생성) `orElseGet`이에요.
- `get()`은 비어 있으면 `NoSuchElementException`이에요. 공식 문서도 `orElseThrow()`를 권해요.
- `Optional.of(null)`은 NPE예요. null일 수 있으면 `ofNullable`.
- **필드·파라미터·컬렉션 원소로는 쓰지 않는 게 관행**이에요. Optional은 `Serializable`이 아니라서 엔티티 필드 같은 곳에 맞지 않아요. Optional 변수 자체가 null이면 안 되고, `==`로 비교하지 말고 `isEmpty()`/`isPresent()`를 써요.
- `map`은 결과가 null이면 빈 Optional을 줘요. 매핑 함수가 이미 Optional을 돌려주면 `flatMap`으로 이중 포장을 피해요.

## 면접 질문

<details>
<summary>Q. 스트림의 지연 연산이 뭔가요? 중간 연산과 최종 연산은 어떻게 다른가요?</summary>

**답변(30초)** 중간 연산은 새 스트림을 돌려줄 뿐 바로 실행되지 않고, 최종 연산을 호출해야 소스 순회가 시작돼요. 이때 요소 하나가 filter, map을 끝까지 통과한 뒤 다음 요소가 들어가는 식으로 한 번에 처리돼서 중간 목록을 안 만들어요. 그래서 findFirst 같은 단락 연산이 있으면 필요한 만큼만 보고 멈추고, 무한 스트림도 다룰 수 있어요. 최종 연산이 없으면 아무것도 실행되지 않아요.

**꼬리질문**
- Q. 항상 요소 단위로 흐르나요? → `sorted`, `distinct` 같은 상태 있는 연산은 앞 단계 결과를 모아야 해서 흐름이 끊겨요. `sorted` 뒤에 `findFirst`를 둬도 정렬 전까지는 전부 처리돼요.
- Q. 스트림을 두 번 쓰면? → 한 번만 소비돼요. 두 번째 최종 연산에서 `IllegalStateException`이 날 수 있어서 새 스트림을 만들어야 해요.
- Q. `Stream.toList()`와 `Collectors.toList()` 차이는? → 앞은 수정 불가가 보장되고, 뒤는 가변성을 보장하지 않아요.
</details>

<details>
<summary>Q. Optional은 언제 쓰나요? orElse와 orElseGet 차이는요?</summary>

**답변(30초)** Optional은 "결과가 없을 수 있음"을 드러내는 메서드 반환 타입용이에요. 필드나 파라미터로는 쓰지 않는 게 관행이고, Serializable도 아니에요. orElse는 인자라서 값이 있든 없든 기본값이 먼저 계산되고, orElseGet은 비어 있을 때만 Supplier를 호출해요. 그래서 기본값을 만드는 데 DB 조회나 객체 생성 같은 비용이 들면 orElseGet을 써요.

**꼬리질문**
- Q. `get()`은 왜 피하나요? → 비어 있으면 `NoSuchElementException`이라 null 체크를 옮긴 것뿐이에요. `orElseThrow()`로 의도를 드러내요.
- Q. map과 flatMap 차이는? → 매핑 함수가 이미 Optional을 반환하면 map은 `Optional<Optional<T>>`가 되니 flatMap을 써요.
</details>

<details>
<summary>Q. 람다에서 바깥 지역변수를 바꿀 수 없는 이유는요? effectively final이 뭔가요?</summary>

**답변(30초)** 람다가 쓰는 바깥 지역변수는 final이거나 effectively final이어야 해요. effectively final은 final을 안 붙였어도 선언 후 한 번도 값이 안 바뀌는 변수예요. 자바 명세는 계속 바뀌는 지역변수를 캡처하면 동시성 문제가 생기기 쉬워서 막았다고 설명해요. 람다는 나중에, 다른 스레드에서 실행될 수 있기 때문이에요. 단, 막는 건 변수 재대입뿐이라 캡처한 리스트에 add하는 건 컴파일돼요.

**꼬리질문**
- Q. 그럼 람다 안에서 카운트를 세려면요? → `AtomicInteger`나 배열로 우회할 수는 있지만 스트림 무상태 규칙 위반이라 병렬에서 위험해요. `filter(...).count()` 같은 리덕션을 써요.
- Q. 필드도 같은 제한이 있나요? → 없어요. 규칙은 지역변수·파라미터에만 적용돼요.
- Q. 람다와 익명 클래스의 차이는? → 람다의 `this`는 바깥 클래스 객체이고, 별도 클래스 파일이 안 생기며, 객체 정체성이 보장되지 않아요.
</details>

<details>
<summary>Q. 병렬 스트림을 쓸 때 주의할 점은요?</summary>

**답변(30초)** 항상 빠르지 않다는 게 먼저예요. 쪼개고 합치는 비용, 순서 유지 비용, Map 병합 비용이 있어서 요소가 많고 계산이 무거울 때만 이득이에요. 공유 리스트에 add하는 것처럼 바깥 상태를 바꾸면 결과가 깨지니 collect 같은 리덕션을 써야 해요. 그리고 병렬 스트림은 보통 JVM 공용 ForkJoinPool에서 돌아서, 안에서 블로킹 I/O를 하면 다른 기능까지 느려질 수 있어요.

**꼬리질문**
- Q. 중간에 `.sequential()`을 넣으면 그 앞만 병렬인가요? → 아니요. 마지막 설정이 파이프라인 전체에 적용돼요.
- Q. `reduce`를 병렬로 쓰려면? → 함수가 결합법칙을 만족하고 무상태여야 하고, identity는 진짜 항등원이어야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 이체 내역 수천 건을 parallelStream으로 돌리며 건마다 외부 API(HTTP)를 호출했더니, 같은 서버의 전혀 다른 기능까지 느려졌습니다.</summary>

**상황 파악**
병렬 스트림은 보통 JVM에 하나 있는 공용 ForkJoinPool에서 돌아요(널리 알려진 동작이고, 스트림 공식 문서에 명시된 건 아니에요). 이 풀의 스레드는 보통 CPU 코어 수 - 1개뿐이에요. 그 스레드들이 HTTP 응답을 기다리며 멈춰 있으니, 같은 풀을 쓰는 다른 병렬 스트림과 `CompletableFuture` 기본 실행이 줄을 서게 돼요.

**원인 후보**
1. 공용 풀 스레드가 블로킹 I/O로 전부 묶임(가장 유력)
2. 외부 API 자체가 느려지거나 호출 제한에 걸림
3. 병렬로 동시에 쏘는 요청 수가 상대 서버 한도를 넘음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 병렬 스트림을 빼고, 크기를 정한 전용 Executor에 `CompletableFuture.supplyAsync(..., executor)`로 제출 | 공용 풀과 격리돼 다른 기능이 안 막힘. 동시 호출 수를 직접 조절 | 풀 크기·타임아웃·예외 처리 코드를 직접 관리 |
| B. 공용 풀 크기를 시스템 속성으로 키움 | 코드 변경 없음 | JVM 전체에 영향, I/O를 기다리는 근본 구조는 그대로 |
| C. 가상 스레드(Java 21)로 건마다 실행 | 기다리는 동안 OS 스레드를 점유하지 않아 많은 I/O에 유리 | Java 21 필요, 상대 서버 보호용 동시성 제한은 따로 필요 |

**내가 고를 방법**
A를 골라요. 병렬 스트림은 CPU 계산을 나누는 도구라 I/O 대기에 맞지 않고, 전용 풀로 떼어 내면 장애가 다른 기능으로 번지지 않아요. Java 21 환경이면 C도 검토해요. B는 원인을 그대로 둔 채 영향 범위만 넓히니 피해요. 바꾼 뒤 외부 API 타임아웃과 동시 호출 수를 함께 설정해요.

**채점 포인트**: 병렬 스트림의 공용 ForkJoinPool, 적은 스레드 수(코어 수 - 1), 블로킹 I/O로 풀 고갈, 같은 풀을 쓰는 다른 작업(CompletableFuture 기본) 영향, 전용 Executor로 격리, 병렬 스트림은 CPU 작업용, 타임아웃·동시성 제한.
</details>
