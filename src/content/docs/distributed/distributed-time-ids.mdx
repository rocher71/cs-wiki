:::tip[한 줄 요약]
서버마다 시계가 조금씩 어긋나기 때문에 **시각으로 "누가 먼저"를 정하면 틀릴 수 있어요.** 경과 시간은 **단조 시계**(`nanoTime()`)로 재고, 순서가 중요하면 시계 대신 **버전 번호·논리 시계**를 써요. 여러 서버가 따로 만드는 ID는 auto_increment 대신 **UUID v7**이나 **Snowflake**처럼 **조율 없이 고유하면서 시간순으로 정렬되는** 방식을 골라요.
:::

:::note[처음이라면 여기까지]
① 컴퓨터 시계는 서버마다 조금씩 빠르거나 느려요. 맞춰 줘도 몇 ms에서 수십 ms는 어긋나요.

② 그래서 "시각이 더 큰 쪽이 나중"이라고 믿으면, 진짜 나중에 한 일이 조용히 버려질 수 있어요.

③ 실행 시간을 잴 땐 `currentTimeMillis()` 말고 `nanoTime()`을 써요. 앞의 것은 시계가 맞춰질 때 뒤로 갈 수 있어요.

④ 서버 여러 대가 ID를 만들면 DB 하나가 1, 2, 3 매기던 방식이 안 통해요. 그래서 UUID v7이나 Snowflake를 써요.

⑤ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

학교 반마다 벽시계가 걸려 있는데, 1반 시계는 2분 빠르고 3반 시계는 1분 느려요. 1반 친구가 "10시 05분에 매점 갔어"라고 하고, 3반 친구가 "10시 04분에 매점 갔어"라고 하면 누가 먼저 갔을까요? 시계만 보고는 알 수 없어요. 실제로는 3반 친구가 나중에 갔을 수도 있어요.

서버도 똑같아요. 서버마다 시계가 있고, 인터넷으로 시간을 맞춰도 조금씩 어긋나요. 그래서 서버 시각만 보고 "이 쓰기가 나중이니 이걸 남기자"라고 하면, 진짜 나중에 한 쓰기를 버리는 사고가 나요.

번호표도 비슷한 문제예요. 은행 창구가 하나면 번호표 기계 하나로 1, 2, 3 순서대로 주면 돼요. 그런데 지점이 여러 개로 늘면 지점마다 1번부터 줘서 번호가 겹쳐요. 그래서 "지점 번호 + 시각 + 순번"을 섞은 번호표를 만들어요. 이게 Snowflake 같은 분산 ID의 생각이에요.

단, 실제로는 서버 시계가 몇 분씩 틀리진 않아요. 보통 몇 ms 수준이에요. 그런데 컴퓨터는 1ms 안에도 수많은 일을 해서, 그 몇 ms가 순서를 뒤집기에 충분해요.

## 제대로 알기

### 시계는 왜 서버마다 다른가

컴퓨터 시계는 보통 **수정 발진기**(quartz, 일정하게 떨리는 작은 결정)로 시간을 세요. 온도 같은 조건에 따라 조금씩 빠르거나 느려지는데, 이걸 **드리프트**(drift, 시계가 서서히 벗어나는 것)라고 해요.

그래서 **NTP**(Network Time Protocol, 네트워크로 정확한 시간 서버에서 시각을 받아 맞추는 규약)로 주기적으로 맞춰요. 하지만 NTP도 네트워크를 거치니까, 네트워크가 늦으면 오차가 생겨요.

얼마나 틀리는지 감을 잡아 볼게요.

- 구글은 서버 드리프트를 200ppm(100만분의 200)으로 가정해요. 30초마다 맞추면 최대 약 6ms, 하루에 한 번 맞추면 약 17초까지 벌어질 수 있어요.
- 공개 인터넷 NTP를 쓰면 잘해야 수십 ms, 네트워크가 혼잡하면 100ms 넘게 튀기 쉬워요.
- 시계 차이가 너무 크면 NTP가 시계를 **강제로 리셋**해요. 이때 시계가 **과거로 뒤로 뛸 수 있어요.**
- 그 밖에도 방화벽에 NTP가 막혀도 한동안 모르거나, **윤초**(1분이 61초가 되는 날)로 장애가 나거나, 가상 머신이 잠깐 멈췄다 깨서 시계가 앞으로 뛴 것처럼 보이는 일이 있어요.
- 사용자 폰 시계는 아예 믿으면 안 돼요. 게임 제한 시간을 피하려고 일부러 바꾸기도 해요.

<Aside type="caution" title="시계 고장은 티가 안 나요">
CPU나 네트워크가 고장 나면 금방 드러나요. 그런데 시계는 조금씩 어긋나도 "잘 도는 것처럼" 보여요. 그래서 시계에 기대는 시스템에선 큰 장애보다 **조용한 데이터 유실**로 나타나기 쉬워요. 노드 간 시계 차이를 모니터링하고, 너무 벗어난 노드는 빼는 게 좋아요.
</Aside>

### 시계는 두 종류: 일 기준 시계 vs 단조 시계

시계를 쓰는 목적은 두 가지예요. **"지금 몇 시?"**(게시 시각, 로그 시각)와 **"얼마나 걸렸지?"**(타임아웃, 응답 시간). 목적에 따라 써야 할 시계가 달라요.

| 구분 | 일 기준 시계 (wall-clock) | 단조 시계 (monotonic clock) |
|---|---|---|
| 알려 주는 것 | 달력상 지금 날짜·시각 | 어떤 임의 시점부터 흐른 시간 |
| Java | `System.currentTimeMillis()` | `System.nanoTime()` |
| 값 하나만 의미 있나 | 예 (1970-01-01 UTC부터 흐른 밀리초) | 아니요, **두 값의 차이만** 의미 있음 |
| 뒤로 갈 수 있나 | **예**, NTP가 강제로 맞추면 과거로 뛸 수 있음 | 아니요, 앞뒤로 뛰지 않음(NTP는 속도만 살짝 조절) |
| 다른 서버와 비교 | 이상적으로는 가능(NTP로 맞추니까) | **무의미** (원점이 서버·JVM마다 다름) |
| 쓰는 곳 | 저장할 시각, 화면에 보여 줄 시각 | 실행 시간 측정, 타임아웃 |

Java 문서 기준으로 정리하면 이래요.

- `currentTimeMillis()`는 단위가 밀리초지만, OS에 따라 실제로는 수십 ms 단위로 뭉툭할 수 있어요.
- `nanoTime()`은 **경과 시간 측정에만** 써야 하고, 벽시계 시각과 무관해요. 같은 JVM 안에서 구한 두 값의 차이만 의미 있어요. 원점이 임의라 값이 음수일 수도 있어요.

```java
// 실행 시간 측정: nanoTime으로 차이를 잰다
long start = System.nanoTime();
doWork();
long elapsedNs = System.nanoTime() - start;

// 타임아웃 확인: 빼고 나서 비교 (Java 문서 권장)
boolean timedOut = System.nanoTime() - start >= timeoutNs;
// start + timeoutNs와 비교하면 값이 넘쳐(overflow) 틀릴 수 있음
```

반대로 `nanoTime()` 값을 DB에 저장하거나 다른 서버와 비교하면 안 돼요. 그 값은 그 JVM 안에서만 뜻이 있어요.

### 시계로 순서를 정하면: LWW가 데이터를 잃는 이유

여러 곳에서 같은 데이터를 고칠 수 있는 구조(다중 리더 복제, Cassandra 같은 리더 없는 DB)에선 두 쓰기가 부딪칠 때 하나를 골라야 해요. 가장 흔한 방법이 **LWW**(Last Write Wins, 타임스탬프가 가장 큰 쓰기만 남기기)예요. → [복제](../replication/)

위 그림이 그 사고예요. 클라이언트 B는 A가 쓴 `x = 1`을 **보고 나서** 1을 더했으니, 분명히 나중에 한 일이에요. 그런데 B가 쓴 노드의 시계가 3ms 느려서 B의 타임스탬프가 더 작게 찍혔어요. LWW는 "큰 쪽이 최신"이라고 믿고 B의 쓰기를 버려요. 3ms 차이면 NTP 기준으로 아주 잘 맞춘 편인데도요.

LWW의 문제를 정리하면 세 가지예요.

1. **조용한 유실**: 시계가 느린 노드의 쓰기는, 시계가 빠른 노드가 먼저 쓴 값을 시계 차이만큼 시간이 지나기 전까지 덮어쓰지 못해요. 에러도 안 나요.
2. **"바로 이어서 쓴 것"과 "진짜 동시에 쓴 것"을 구분 못 해요.** 인과관계를 추적하려면 버전 벡터 같은 다른 장치가 필요해요.
3. **같은 타임스탬프**: 밀리초 단위면 두 노드가 같은 값을 낼 수 있어요. 무작위로 승자를 정해도 순서가 틀릴 수 있어요.

타임스탬프를 서버 대신 클라이언트가 붙여도 같은 문제예요. 순서를 시계로 정확히 정하려면 시계 오차가 네트워크 지연보다 훨씬 작아야 하는데, NTP로는 그게 사실상 안 돼요.

<Aside type="tip" title="그럼 순서는 뭘로 정하나요?">
실무에서 자주 쓰는 방법은 **시계 대신 숫자를 하나씩 올리는 것**이에요. DB 행에 버전 번호를 두고 "버전이 내가 읽은 값일 때만 수정"하게 하거나, 한 데이터는 한 곳(리더 하나, 같은 파티션)에서만 쓰게 해서 그곳의 순번으로 순서를 정해요. 이 "증가하는 카운터로 순서를 정한다"를 일반화한 게 아래 논리 시계예요.
</Aside>

### 분산 ID: 왜 auto_increment로는 부족한가

DB 한 대일 때는 `AUTO_INCREMENT`가 편해요. DB가 1, 2, 3 순서대로 번호를 매겨 주니까 겹칠 일도 없고 시간순이에요.

그런데 쓰기가 여러 곳으로 나뉘면 곤란해져요.

- **샤딩**(데이터를 여러 DB에 나눠 담기)을 하면 DB마다 1부터 매겨서 **전체에서 고유하지 않아요.** → [파티셔닝](../partitioning/)
- MySQL에는 `auto_increment_increment`(간격)·`auto_increment_offset`(시작점) 설정이 있어서, 서버 두 대면 한쪽은 홀수, 한쪽은 짝수를 매기게 할 수 있어요. 하지만 **서버 수를 미리 정해야** 하고, 서버의 모든 AUTO_INCREMENT 컬럼에 한꺼번에 적용되고, 서버 간 순서는 안 맞아요.
- ID를 알려면 INSERT를 먼저 해야 해요. 저장 전에 ID가 필요할 때(이벤트를 먼저 만들어야 할 때 등) 불편해요. (일반적인 실무 이야기예요)
- 번호가 밖에 보이면 "주문이 하루 몇 건인지" 짐작당할 수 있어요.

그래서 **각 서버가 다른 서버에 묻지 않고(조율 없이) 혼자 만들어도 겹치지 않는 ID**가 필요해요. 대표가 UUID와 Snowflake예요.

### UUID v4와 v7

**UUID**(Universally Unique IDentifier)는 128비트(16바이트)짜리 ID예요. 2024년에 나온 표준 RFC 9562가 이전 표준(RFC 4122)을 대체했어요. 여러 버전 중 지금 중요한 건 두 개예요.

- **v4**: 버전·변형 표시 6비트를 빼면 **122비트가 전부 난수**예요. 겹칠 걱정은 사실상 없지만, 값에 순서가 없어요.
- **v7**: **앞 48비트가 생성 시각(밀리초)**이고 나머지는 대부분 난수예요. 시간이 맨 앞에 있어서 **값 그대로 정렬하면 만든 순서**가 돼요. RFC 9562는 새 시스템이면 v1·v6 대신 v7을 쓰라고 권해요.

v7은 같은 밀리초 안에서는 뒤쪽이 난수라 순서가 섞여요. 같은 ms 안에서도 순서가 필요하면 난수 자리 일부에 카운터를 넣는 구현인지 확인해야 해요(RFC 9562 6.2절에 방법이 있어요).

### Snowflake

**Snowflake**는 트위터가 만든 64비트 ID 생성기예요. 64비트 정수(`BIGINT`) 하나에 들어가요.

| 위치 | 비트 수 | 내용 | 의미 |
|---|---|---|---|
| 맨 앞 | 1 | 부호 비트 0 | 음수가 안 되게 비워 둠(일반적 설명) |
| 시간 | 41 | 밀리초, 직접 정한 기준 시점부터 | 약 69년 쓸 수 있음 |
| 기계 ID | 10 | 생성 서버 번호 | 최대 1024대, 설정으로 배정 |
| 시퀀스 | 12 | 같은 ms 안 순번 | 서버 한 대가 1ms에 4096개까지 |

시간이 맨 앞이라 숫자 크기로 정렬하면 **대략** 시간순이에요. 원래 목표도 "서로 조율 없이, 대략 시간순(1초 안쪽 오차)"이었어요.

대신 관리할 게 생겨요.

- **기계 ID 배정**: 두 서버가 같은 기계 ID를 쓰면 ID가 겹칠 수 있어요. 서버를 늘리고 줄일 때 번호를 누가 나눠 줄지 정해야 해요.
- **시계 역행**: 시계가 뒤로 가면 이미 쓴 시각을 다시 써서 같은 ID가 나올 위험이 있어요. 그래서 구현들은 보통 "이전 시각보다 작으면 기다리거나 에러"로 처리해요. (README에 직접 있는 내용은 아니고 일반적으로 알려진 내용이에요)

설명에서 기계 ID 10비트를 "데이터센터 5 + 워커 5"로 나누는 경우가 많은데, 원래 README는 그냥 "기계 ID 10비트"라고만 적어요.

|---|---|---|---|---|---|

| Snowflake | 8바이트(BIGINT) | 대략 예 (서버 간 시계 차이만큼 섞임) | 기계 ID 중복·시계 역행 시 | 앱(서버별 생성기) | 기계 ID 배정, 시계 역행 처리 |

### UUID를 PK로 쓰면 왜 느려질 수 있나 (짧게)

MySQL InnoDB는 **PK 순서대로 데이터를 실제로 정렬해서 저장**해요(**클러스터드 인덱스**). 새 PK가 늘 커지는 값(auto_increment, v7)이면 맨 끝 페이지에 차곡차곡 붙어요. v4처럼 무작위면 아무 페이지 중간에 끼워 넣어야 해서 페이지가 쪼개지고, 반쯤 빈 페이지가 늘어요. MySQL 문서 기준으로 순서대로 넣으면 페이지가 약 15/16 차고, 무작위로 넣으면 1/2에서 15/16 사이로만 차요.

데이터가 메모리(버퍼 풀)에 다 들어갈 땐 별 차이가 없어요. 문제는 **데이터가 메모리보다 커질 때**예요. 무작위 위치에 넣으려면 이미 메모리에서 밀려난 페이지를 디스크에서 다시 읽어 와야 해서 INSERT가 크게 느려져요. 또 세컨더리 인덱스마다 PK가 들어가서, 16바이트 PK는 8바이트 BIGINT보다 인덱스 전체를 키워요.

자세한 내용과 MySQL `UUID()`가 v1이라는 함정은 [클러스터드·세컨더리·커버링 인덱스](../../db/clustered-covering/)에 있어요.

<Aside type="note" title="한 번 재 본 예시 (참고용)">
노트북 한 대에서 `(id PK, pad CHAR(100))` 테이블에 행을 한 번에 넣어 비교해 봤어요. 1회 측정이라 숫자보다 **방향**만 보세요.

- **10만 행, 데이터가 메모리에 다 들어갈 때**: auto_increment, v4, v7의 INSERT 시간은 거의 비슷했어요. 차이는 공간에서 먼저 보였어요. v4는 PK 리프 페이지가 auto_increment보다 약 1.5배 많았어요. v7은 같은 ms 안까지 순서를 맞춘 경우 auto_increment에 가까웠고, 같은 ms 안이 무작위인 경우엔 페이지가 꽤 덜 찼어요.
- **100만 행, 메모리를 일부러 작게 줄였을 때**: v4가 auto_increment·v7보다 **몇 배 느려졌어요.** v7은 auto_increment보다 조금 느린 정도였어요(키가 8바이트 더 큰 만큼).

디스크·메모리 크기에 따라 배수는 크게 달라져요. "v4 PK는 데이터가 메모리보다 커지면 급격히 느려진다"까지만 말하세요.
</Aside>

### 심화: 램포트 논리 시계

**논리 시계**(logical clock)는 실제 시각 대신 **하나씩 올라가는 카운터**로 "어느 쪽이 앞인가"만 나타내요. 몇 시인지, 몇 초 걸렸는지는 전혀 몰라요. 1978년 레슬리 램포트가 제안한 **램포트 타임스탬프**가 대표예요.

먼저 "앞선다"(happened-before, `→`)의 뜻을 정해요.

- 같은 서버 안에서 먼저 일어난 일은 나중 일보다 앞서요.
- 메시지를 **보낸** 일은 그 메시지를 **받은** 일보다 앞서요.
- a가 b보다 앞서고 b가 c보다 앞서면, a는 c보다 앞서요.
- 어느 쪽도 아니면 둘은 **동시**(concurrent)예요.

규칙은 두 개뿐이에요.

1. **규칙 1**: 각 서버는 자기 일이 하나 일어날 때마다 카운터를 1 올려요.
2. **규칙 2**: 메시지를 보낼 땐 지금 카운터 값을 같이 실어 보내요. 받은 쪽은 자기 카운터를 "받은 값보다 크게" 올려요. 흔히 `max(내 값, 받은 값) + 1`로 설명해요.

예를 들어 서버 P가 일 두 번(P=1, 2)을 하고 카운터 3을 실어 Q에게 보내요. Q는 그동안 일 한 번(Q=1)을 했어요. 메시지를 받으면 Q는 `max(1, 3) + 1 = 4`가 돼요. 그래서 "보냄(3) → 받음(4)"처럼 **앞선 일은 항상 숫자가 작아요.**

동점이면 서버 ID로 비교해요. `(카운터, 서버 ID)` 쌍으로 보면 모든 일에 빠짐없이 순서를 매길 수 있고, 그 순서는 인과관계와 어긋나지 않아요.

<Aside type="caution" title="거꾸로는 성립하지 않아요">
a가 b보다 앞서면 `C(a)`가 `C(b)`보다 작아요. 하지만 숫자가 작다고 먼저 일어난 건 **아니에요.** 위 예에서 Q의 첫 일(1)과 P의 두 번째 일(2)은 서로 아무 관계 없는 동시 사건인데 숫자는 1과 2로 달라요.
</Aside>

**한계**

- 램포트 타임스탬프는 늘 순서를 하나로 정해 버려서, 두 일이 **동시였는지 인과관계였는지 구분 못 해요.** 그 구분이 필요하면 **버전 벡터**(서버별 카운터를 묶은 목록)를 써요. 대신 램포트 쪽이 크기가 작아요.
- "누가 먼저였나"를 **나중에** 정하는 덴 좋지만, "이 아이디로 가입 승인해도 되나?"처럼 **지금 바로** 결정하려면 다른 서버들이 무엇을 하고 있는지 다 알아야 해요. 이건 합의 알고리즘의 몫이에요. Raft의 **임기**(term)도 "더 큰 값을 보면 내 값을 올리는" 논리 시계처럼 동작해요. → [합의와 Raft](../consensus-raft/)

### 심화: 그래도 시계가 필요할 때

- **시계 값은 범위로 봐야 해요.** "지금 10.3초에서 10.5초 사이일 확률이 높다"처럼요. 대부분 API는 이 오차 범위를 알려 주지 않아요. 구글 Spanner의 **TrueTime**은 예외로 `[가장 이른 시각, 가장 늦은 시각]` 두 값을 돌려줘요. Spanner는 커밋 전에 그 범위만큼 **일부러 기다려서** 순서가 겹치지 않게 하고, 기다림을 줄이려고 데이터센터마다 GPS 수신기·원자 시계를 둬요.
- **정밀한 시각은 돈이 들어요.** 유럽 금융 규제(MiFID II)는 고빈도 트레이딩 서버 시계를 UTC와 100μs 안으로 맞추라고 하는데, 이를 위해 GPS 수신기나 PTP(정밀 시간 프로토콜)가 필요해요.
- **리더 임차권(lease) 함정**: "만료 시각 - 내 현재 시각"으로 아직 내가 리더인지 확인하는 코드는, 만료 시각을 다른 서버 시계로 정했다면 시계 차이만큼 틀려요. 단조 시계로 바꿔도, 확인한 직후 GC 멈춤이나 VM 일시 정지로 스레드가 몇 초 멈추면 이미 만료된 임차권으로 일을 해 버려요. 이걸 막는 게 펜싱 토큰이에요. → [분산 락](../../redis/distributed-lock/)

### 심화: UUID와 보안

RFC 9562는 UUID를 **추측 불가능하다고 가정하지 말고**, 권한 토큰(이걸 가진 사람은 접근 가능 같은 비밀 값)으로 쓰지 말라고 해요. v7은 앞 48비트가 생성 시각이라 **언제 만들었는지가 그대로 드러나요.** 외부에 생성 시각이 보이면 안 되는 ID라면 v4가 낫고, 이때 난수는 암호학적으로 안전한 생성기로 만드는 걸 권해요.

<details>
<summary>Q. 분산 시스템에서 서버 시각을 그대로 믿으면 왜 안 되나요?</summary>

**답변(30초)**
서버 시계는 서로 조금씩 어긋나기 때문이에요. 컴퓨터 시계는 수정 발진기라 온도 등에 따라 빠르거나 느려지고, NTP로 맞춰도 네트워크 지연 때문에 수 ms에서 수십 ms, 혼잡하면 100ms 넘게 차이 나요. 차이가 크면 NTP가 강제로 맞추면서 시계가 뒤로 뛰기도 해요. 그래서 다른 서버에서 찍힌 시각끼리 비교해 순서를 정하면, 실제로 나중에 일어난 일이 더 이른 시각을 가질 수 있어요.

**꼬리질문**
- Q. NTP를 더 자주 맞추면 해결되나요? → 오차는 줄지만 네트워크 지연만큼은 남아요. 순서를 정하려면 시계 오차가 네트워크 지연보다 훨씬 작아야 해서 NTP로는 부족해요.
- Q. 시계가 어긋난 걸 어떻게 알아요? → 시계는 틀려도 티가 안 나서, 노드 간 시계 차이를 따로 모니터링하고 너무 벗어난 노드는 빼요.
</details>

<details>
<summary>Q. System.currentTimeMillis()와 System.nanoTime()의 차이는? 실행 시간은 뭘로 재나요?</summary>

**답변(30초)**
실행 시간은 `nanoTime()`으로 재요. `currentTimeMillis()`는 1970년부터 흐른 밀리초, 즉 달력 시각이라 NTP가 시계를 맞출 때 뒤로 갈 수 있어서, 차이를 재면 음수나 엉뚱한 값이 나올 수 있어요. `nanoTime()`은 단조 시계라 뒤로 가지 않고, 대신 값 하나는 의미가 없고 같은 JVM 안에서 두 값의 차이만 의미 있어요. 그래서 저장할 시각엔 `currentTimeMillis()`, 경과 시간·타임아웃엔 `nanoTime()`을 써요.

**꼬리질문**
- Q. nanoTime 값을 DB에 저장해서 다른 서버와 비교하면? → 의미 없어요. 원점이 임의라 JVM마다 달라요.
- Q. 타임아웃 비교는 어떻게 쓰나요? → `nanoTime() - start >= timeout`처럼 빼고 나서 비교해요. `start + timeout`과 비교하면 넘침 때문에 틀릴 수 있어요.
</details>

<details>
<summary>Q. auto_increment를 샤딩이나 멀티 마스터 환경에서 쓰기 어려운 이유는?</summary>

**답변(30초)**
auto_increment는 DB 한 대가 번호를 매기는 구조라서, 쓰기를 여러 DB가 나눠 받으면 DB마다 같은 번호를 매겨 전체에서 고유하지 않아요. MySQL의 `auto_increment_increment`·`offset`으로 홀짝처럼 나눌 수 있지만, 서버 수를 미리 정해야 해서 늘리기 어렵고 서버 간 순서도 안 맞아요. 그래서 각 서버가 조율 없이 만들 수 있는 UUID v7이나 Snowflake를 많이 써요.

**꼬리질문**
- Q. 중앙에서 ID를 나눠 주면요? → 가능하지만 그 발급 서버가 병목·장애 지점이 돼요. 블록 단위(1~1000, 1001~2000)로 미리 받아 두면 부담은 줄지만 순서는 대략적이에요.
- Q. ID 순번이 밖에 보이면 무슨 문제가? → 주문 수 같은 규모를 짐작당할 수 있어요.
</details>

<details>
<summary>Q. UUID v4와 v7의 차이는? PK로는 뭘 쓰겠어요?</summary>

**답변(30초)**
v4는 122비트가 전부 난수라 순서가 없고, v7은 앞 48비트가 밀리초 시각이라 정렬하면 생성 순서가 돼요. MySQL InnoDB처럼 PK 순서로 데이터를 저장하는 DB에서 v4는 아무 페이지 중간에 끼워 넣느라 페이지 분할과 빈 공간이 늘고, 데이터가 메모리보다 커지면 디스크 읽기가 많아져 INSERT가 크게 느려져요. 그래서 UUID를 PK로 써야 한다면 v7을 고르고, BINARY(16)으로 저장해요.

**꼬리질문**
- Q. v7의 단점은? → 생성 시각이 ID에 드러나고, 16바이트라 BIGINT보다 세컨더리 인덱스가 커요.
- Q. 같은 밀리초 안에서도 정렬되나요? → 기본 구조에선 뒤가 난수라 섞여요. 카운터를 넣는 구현인지 확인해야 해요.
- Q. MySQL UUID() 함수는 몇 버전이에요? → v1(시간 기반)이에요. v7 생성 함수는 MySQL 8.4 문서엔 없어서 보통 앱에서 만들어요.
</details>

<details>
<summary>Q. Snowflake ID 구조를 설명해 보세요. 시계가 뒤로 가면 어떻게 되나요?</summary>

**답변(30초)**
64비트 정수 안에 부호 1비트, 밀리초 시각 41비트, 기계 ID 10비트, 시퀀스 12비트를 넣어요. 시간이 앞이라 숫자로 정렬하면 대략 시간순이고, 서버 1024대가 각각 1ms에 4096개까지 조율 없이 만들 수 있어요. 시계가 뒤로 가면 이미 쓴 시각으로 같은 ID를 다시 만들 위험이 있어서, 보통 이전 시각보다 작으면 기다리거나 에러를 내게 구현해요.

**꼬리질문**
- Q. Snowflake ID는 완벽한 시간순인가요? → 아니요. 서버마다 시계가 달라서 대략적인 순서일 뿐, 인과 순서는 보장 못 해요.
- Q. 기계 ID는 어떻게 관리하나요? → 서버마다 겹치지 않게 배정해야 해요. 중복되면 ID 충돌 원인이 돼요.
</details>

<details>
<summary>Q. Last Write Wins(LWW)가 데이터를 잃는 상황을 설명해 보세요.</summary>

**답변(30초)**
LWW는 충돌하면 타임스탬프가 큰 쓰기만 남기는 방식인데, 타임스탬프가 각 노드 시계에서 나와서 문제예요. 예를 들어 B가 A의 값을 읽고 1을 더해 썼는데, B 쪽 노드 시계가 몇 ms 느리면 B의 쓰기가 더 작은 시각을 받아요. 그러면 다른 복제본은 A의 쓰기를 최신으로 보고 B의 쓰기를 에러 없이 버려요. 또 바로 이어서 쓴 것과 진짜 동시에 쓴 것을 구분하지 못해요.

**꼬리질문**
- Q. 대안은? → 버전 번호로 조건부 업데이트, 버전 벡터로 동시 쓰기를 찾아 병합, 한 데이터는 한 리더에서만 쓰게 라우팅하는 방법이 있어요.
- Q. 클라이언트가 타임스탬프를 붙이면? → 클라이언트 시계도 어긋나서 같은 문제예요.
</details>

<details>
<summary>Q. (심화) 램포트 논리 시계란? 규칙과 한계는?</summary>

**답변(30초)**
실제 시각 대신 증가하는 카운터로 이벤트의 앞뒤만 나타내는 시계예요. 규칙은 두 개예요. 자기 이벤트마다 카운터를 1 올리고, 메시지를 보낼 때 카운터를 실어 보내며 받은 쪽은 `max(내 값, 받은 값) + 1`로 올려요. 그러면 a가 b보다 앞서면 항상 a의 숫자가 작아요. 동점은 노드 ID로 깨서 전체 순서를 만들어요. 한계는 거꾸로가 성립하지 않아서, 숫자가 작다고 먼저 일어났다거나 두 일이 동시인지 알 수는 없다는 거예요.

**꼬리질문**
- Q. 동시인지 구분하려면? → 노드별 카운터 목록인 버전 벡터를 써요. 대신 크기가 커요.
- Q. 램포트 시계로 유일한 사용자명을 보장할 수 있나요? → 사후에 누가 먼저인지는 알지만, 지금 승인할지는 다른 노드 상황을 다 알아야 해서 합의가 필요해요.
</details>

<details>
<summary>Q. (심화) Spanner의 TrueTime은 시계 문제를 어떻게 다루나요?</summary>

**답변(30초)**
시각을 한 값이 아니라 "가장 이른 시각과 가장 늦은 시각" 범위로 돌려줘요. 두 트랜잭션의 범위가 겹치지 않으면 순서가 확실하니까, 커밋할 때 그 범위 길이만큼 일부러 기다려 겹치지 않게 만들어요. 기다리는 시간을 줄이려고 데이터센터마다 GPS 수신기와 원자 시계를 둬서 오차를 몇 ms 수준으로 줄여요.

**꼬리질문**
- Q. 일반 서버에서 따라 할 수 있나요? → 대부분 시계 API는 오차 범위를 안 알려 주고, 정밀한 시계 인프라가 비싸서 쉽지 않아요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제 이벤트(결제 요청 → 승인 → 취소)를 여러 서버가 처리하며 각자 서버 시각을 붙여 저장해요. 정산 배치가 이 시각으로 정렬했더니 가끔 "취소"가 "승인"보다 먼저 와서 정산이 틀어져요. 원인과 해결 방법은?</summary>

**상황 파악**
같은 결제 건의 이벤트를 **서로 다른 서버가 찍은 시각**으로 정렬하고 있어요. "취소는 승인을 보고 나서 일어난다"는 인과관계가 있는데도 순서가 뒤집혔다면, 서버 간 시계 차이가 이벤트 간격보다 컸다고 봐요.

**원인 후보**
1. 서버 간 시계 차이(NTP 오차 수 ms~수십 ms)가 승인과 취소 사이 간격보다 큼.
2. NTP가 시계를 강제로 맞추면서 한 서버 시계가 뒤로 뜀.
3. 밀리초 단위라 같은 시각이 찍혀서 동점일 때 순서가 무작위로 정해짐.
4. 시각을 클라이언트(앱) 기기에서 받아 씀. 사용자 기기 시계는 아예 믿을 수 없음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 결제 건마다 버전(순번)을 두고, 이벤트 저장 시 "현재 버전 + 1"을 조건부로 기록 | 시계와 무관하게 결제 건 안의 순서가 정확함 | 같은 건을 동시에 쓰면 한쪽이 실패해 재시도 필요 |
| B. 같은 결제 건의 이벤트를 한 곳(같은 파티션·같은 리더)으로 보내 그곳의 순번으로 정렬 | 순서가 자연스럽게 맞고 저장 측에서 해결 | 라우팅 설계 필요, 한 파티션에 몰리면 병목 |
| C. 취소 이벤트에 "기준이 된 승인 이벤트 ID"를 담아 인과관계를 직접 표시 | 정산이 시각 대신 관계로 판단 | 이벤트 스키마 변경, 소비 측 로직 추가 |
| D. 시계 동기화 강화·차이 모니터링 | 다른 시각 기반 기능도 개선 | 오차를 줄일 뿐 0은 못 만들어 근본 해결 아님 |

**내가 고를 방법**
A와 B를 같이 써요. 결제 건 ID를 키로 이벤트를 같은 파티션에 넣고, 결제 건마다 버전 번호를 올려 저장하면 정산은 시각이 아니라 **버전 순서**로 정렬하면 돼요. 서버 시각은 "언제쯤 일어났나"를 사람이 보는 용도로만 남겨요. 추가로 시계 차이 모니터링(D)을 걸어 다른 기능의 사고도 줄여요.

**채점 포인트**: 서버 간 시계 차이(NTP 오차)·시계 역행, 다른 서버 시각끼리 비교 금지, 인과관계 있는 이벤트는 시계 말고 순번·버전·논리 시계로, 같은 키는 같은 파티션/리더, 조건부 업데이트, 시각은 표시용, 시계 차이 모니터링.
</details>

<details>
<summary>상황: 주문 서비스를 여러 인스턴스로 늘리고 주문 DB도 샤딩하기로 했어요. 지금 주문번호는 BIGINT auto_increment예요. DB 시퀀스, UUID v7, Snowflake 중 무엇으로 바꿀지 정해 주세요.</summary>

**상황 파악**
샤딩하면 샤드마다 auto_increment가 1부터 시작해서 주문번호가 겹쳐요. 새 주문번호는 ① 전체에서 고유하고 ② 정렬하면 대략 시간순이고(최근 주문 조회, 인덱스 성능) ③ 서버를 늘려도 문제없어야 해요.

**원인 후보 (지금 방식이 안 되는 이유)**
1. auto_increment는 DB 한 대가 매기는 구조라 샤드 간 충돌.
2. `auto_increment_increment`/`offset`으로 나누면 샤드 수를 미리 정해야 해서 샤드 추가가 어려움.
3. 주문번호가 순번이라 외부에 노출되면 주문량을 짐작당함.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 중앙 DB 시퀀스(또는 블록 할당) | 8바이트, 진짜 순번, 익숙함 | 발급 DB가 병목·장애 지점, 블록 할당이면 순서가 대략적 |
| B. UUID v7 (BINARY(16)) | 조율 없이 앱 어디서나 생성, 시간순 정렬, 관리할 설정 없음 | 16바이트라 PK·세컨더리 인덱스가 커짐, 생성 시각 노출, 사람이 읽기 어려움 |
| C. Snowflake (BIGINT) | 8바이트, 조율 없이 생성, 대략 시간순, 1ms에 서버당 4096개 | 기계 ID 배정 관리 필요, 시계 역행 대응 필요, 41비트 시간 한계(약 69년) |
| (참고) UUID v4 | 가장 단순 | 무작위 삽입으로 데이터가 커지면 INSERT가 크게 느려짐 → 제외 |

**내가 고를 방법**
인스턴스 수가 많지 않고 운영 인력이 적다면 **UUID v7**을 골라요. 기계 ID 배정이나 시계 역행 처리 같은 운영 부담이 없고, 시간순이라 InnoDB 클러스터드 인덱스에서도 v4 같은 문제가 없어요. 대신 BINARY(16)으로 저장하고, 같은 ms 안에서도 단조 증가하는 생성 라이브러리인지 확인해요. 주문번호가 고객에게 보이고 BIGINT 크기가 중요하거나(기존 BIGINT 컬럼·API 호환), 이미 서버 번호를 관리할 체계(설정 서버 등)가 있다면 **Snowflake**를 골라요. 어느 쪽이든 고객에게 보여 줄 번호는 내부 PK와 분리하는 것도 검토해요.

**채점 포인트**: 샤딩 시 auto_increment 충돌, increment/offset 한계, 조율 없는 생성, 시간순 정렬과 클러스터드 인덱스(무작위 삽입 문제), PK 크기·세컨더리 인덱스, Snowflake 기계 ID 관리·시계 역행, v7 생성 시각 노출, 중앙 발급의 병목, 외부 노출 시 규모 추정.
</details>

<details>
<summary>상황: UUID v4를 PK로 쓰는 테이블이 있어요. 처음엔 괜찮았는데 데이터가 늘면서 INSERT가 점점 느려지고 디스크 읽기가 크게 늘었어요. 원인과 해결 방법은?</summary>

**상황 파악**
"처음엔 괜찮다가 데이터가 늘며 느려짐 + 디스크 **읽기** 증가"가 핵심이에요. INSERT인데 읽기가 늘었다면, 새 행을 넣을 페이지를 디스크에서 불러오고 있다는 뜻이에요. 데이터가 버퍼 풀(메모리)보다 커진 시점과 겹쳐 봐요.

**원인 후보**
1. v4는 무작위라 InnoDB 클러스터드 인덱스의 아무 페이지 중간에 끼워 넣음. 데이터가 메모리보다 커지면 그 페이지가 메모리에 없어 디스크에서 읽어 옴.
2. 무작위 삽입으로 페이지 분할이 잦고 페이지가 반쯤만 차서(순서대로면 약 15/16, 무작위면 1/2~15/16) 같은 데이터가 더 많은 페이지를 차지함.
3. PK가 CHAR(36) 문자열이면 16바이트보다도 커서 세컨더리 인덱스까지 불어남.
4. (확인용) 세컨더리 인덱스가 많거나 버퍼 풀 자체가 너무 작음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 새 PK를 UUID v7(BINARY(16))로 전환 | 앱에서 생성하는 구조 유지, 맨 끝에 붙어 삽입 위치가 모임 | 기존 데이터·참조하는 테이블 마이그레이션 필요, 생성 시각 노출 |
| B. 내부 PK는 BIGINT auto_increment(또는 Snowflake), UUID는 외부용 고유 인덱스 컬럼으로 분리 | PK가 8바이트로 작아져 모든 인덱스가 작아짐 | 외부 UUID 컬럼 인덱스는 여전히 무작위 삽입(PK보단 작은 영향), 조회 경로 정리 필요 |
| C. 버퍼 풀 늘리기 | 코드 변경 없이 바로 효과 | 데이터가 계속 늘면 다시 같은 문제, 비용 |

**내가 고를 방법**
당장은 C로 숨통을 틔우고, 근본적으로는 A나 B로 가요. 샤딩이나 여러 서버에서 ID를 만들어야 하는 구조라면 조율 없이 만들 수 있는 **A(v7)**를, DB 한 곳에 쓰고 UUID는 외부 노출용이었다면 **B**를 골라요. 한 번 재 본 예시에서도 메모리보다 큰 데이터에선 v4가 auto_increment·v7보다 몇 배 느렸고, 메모리에 다 들어갈 땐 차이가 거의 없었어요. 즉 지금 증상은 "데이터가 메모리를 넘은 순간" 드러난 거라 설명할 수 있어요. 자세한 InnoDB 구조는 [클러스터드·세컨더리·커버링 인덱스](../../db/clustered-covering/)를 참고해요.

**채점 포인트**: 클러스터드 인덱스(PK 순서 저장), 무작위 삽입·페이지 분할·채움률, 버퍼 풀보다 커질 때 디스크 읽기, PK 크기와 세컨더리 인덱스, v7·순차 키 전환, 내부 PK/외부 ID 분리, 마이그레이션 비용, MySQL `UUID()`는 v1.
</details>

## 필기 포인트

- **일 기준 시계** = 달력 시각, NTP 리셋으로 **뒤로 갈 수 있음**. **단조 시계** = 차이만 의미, 뒤로 안 감, 다른 서버끼리 비교 무의미.
- Java: 경과 시간 = `nanoTime()`, 저장할 시각 = `currentTimeMillis()`. 타임아웃은 `nanoTime() - start >= timeout`.
- **LWW** = 타임스탬프 큰 쓰기 승리 → 시계 차이로 **조용한 유실**, 동시/순차 구분 불가.
- **램포트 시계**: 이벤트마다 +1, 받으면 `max(내 값, 받은 값) + 1`. a→b면 `C(a)`가 더 작음, **역은 성립 X**. 동점은 노드 ID. 동시 판별은 **버전 벡터**.
- **UUID v4** = 122비트 난수. **v7** = 앞 48비트 Unix 밀리초 → 정렬하면 시간순. RFC 9562(2024)가 RFC 4122 대체.
- **Snowflake** = 64비트: 부호 1 + 시간 41(약 69년) + 기계 10(1024대) + 시퀀스 12(ms당 4096).
- MySQL `UUID()` = **v1**. InnoDB 순서 삽입 페이지 약 15/16, 무작위 1/2~15/16.
