:::tip[한 줄 요약]
**합의**(consensus)는 여러 서버가 "누가 리더인지", "어떤 순서로 무엇을 저장할지"에 **하나의 결론**을 내게 하는 방법이에요. **Raft**는 **과반 표**를 얻은 서버만 리더가 되고, 리더가 받은 쓰기는 **과반이 저장해야 확정(커밋)**되게 해서, 리더가 둘이 되는 **스플릿 브레인**을 막아요. 그래서 5대면 2대, 3대면 1대가 죽어도 계속 돌아가요.
:::

:::note[처음이라면 여기까지]
① 서버가 여러 대면 "누가 대장인지"를 다 같이 정해야 해요. 대장이 둘이 되면 데이터가 엇갈려요.

② Raft의 규칙은 딱 두 개예요. 과반 표를 받아야 대장(리더), 대장이 정한 일은 과반이 받아 적어야 확정.

③ 그래서 서버는 3대·5대처럼 홀수로 둬요. 4대는 3대보다 나을 게 없어요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

반장 선거를 떠올려 봐요. 반 학생 5명 중 **과반(3명)** 표를 얻어야 반장이 돼요. 한 사람은 한 번의 선거에서 한 명에게만 투표할 수 있으니, 같은 선거에서 반장이 둘 나올 수는 없어요.

반장이 "내일 체육복 챙기기"라고 정하면, 반 학생 **과반이 수첩에 받아 적어야** 그 공지가 확정돼요. 반장이 갑자기 전학 가도, 받아 적은 학생이 과반이라 새 반장 후보 중 누군가는 그 공지를 꼭 갖고 있어요.

반장이 아파서 며칠 안 나오면, 기다리다 지친 학생이 먼저 "내가 출마할게!" 하고 새 선거를 열어요. 매번 선거에는 **1기, 2기, 3기**처럼 번호를 붙여요. 아팠던 옛 반장이 돌아와 "나 1기 반장인데?" 해도, 지금은 3기라 아무도 따르지 않아요.

단, 실제로는 학생(서버)들이 "언제 출마할지"를 **각자 무작위로** 정해요. 다 같이 동시에 출마하면 표가 갈려 아무도 과반을 못 얻거든요.

## 제대로 알기

### 왜 합의가 필요한가: 스플릿 브레인

[복제](../replication/)에서 리더가 죽으면 팔로워 하나를 새 리더로 올리는 **장애 조치**(failover)를 해요. 이때 위험한 게 **스플릿 브레인**(split brain, 두 서버가 동시에 자기가 리더라고 믿는 상태)이에요. 두 리더가 각자 쓰기를 받으면 데이터가 서로 어긋나요.

그래서 "지금 리더는 누구인가"에 **모든 서버가 같은 답**을 내야 해요. 이렇게 여러 서버가 하나의 값에 동의하는 걸 **합의**라고 해요. 리더 선출 말고도, 마지막 좌석 하나를 두 사람이 동시에 예약할 때 누가 가져가는지, 같은 아이디로 동시에 가입할 때 누가 이기는지 같은 문제도 합의 문제예요.

사람이 손으로 리더를 골라도 되긴 해요. 다만 사람이 올 때까지 시스템이 멈춰 있어요. 합의 알고리즘은 이걸 **자동으로, 틀리지 않게** 해 줘요.

합의 알고리즘이 지키는 약속은 크게 두 종류예요.

| 종류 | 뜻 | 예 |
|---|---|---|
| **안전성**(safety) | 틀린 결정을 절대 안 함 | 두 서버가 다른 값으로 결정하지 않음, 한 번 정한 걸 뒤집지 않음 |
| **활동성**(liveness) | 결국엔 결정을 냄 | 살아 있는 서버는 언젠가 결론에 도달 |

결국 결정을 내리려면 **과반이 살아 있어야** 해요. 과반이 죽으면 멈추지만, 멈출지언정 **틀린 값을 쓰지는 않는** 게 합의 알고리즘의 핵심이에요.

### Raft의 역할 3가지와 임기

**Raft**는 "이해하기 쉬운 합의 알고리즘"을 목표로 만들어졌어요. 서버는 항상 셋 중 하나의 역할이에요.

| 역할 | 하는 일 | 반장 비유 |
|---|---|---|
| **리더**(leader) | 클라이언트 요청을 전부 받고, 로그를 팔로워에게 복제, 주기적으로 하트비트 전송 | 반장 |
| **팔로워**(follower) | 먼저 말 걸지 않고 리더·후보의 요청에만 응답. 클라이언트 요청이 오면 리더에게 보냄 | 일반 학생 |
| **후보**(candidate) | 리더가 없다고 보고 선거에 출마한 상태 | 출마한 학생 |

평소엔 리더 1명, 나머지는 전부 팔로워예요. 데이터는 **리더 → 팔로워** 한 방향으로만 흘러요.

**임기**(term)는 선거마다 1씩 올라가는 번호예요(1기, 2기, 3기…). 한 임기에 리더는 **최대 1명**이에요. 서버들은 메시지를 주고받을 때마다 임기 번호를 같이 보내고, 더 큰 번호를 보면 자기 번호를 올려요. 리더라도 자기 임기가 낡았다는 걸 알면 바로 팔로워로 내려가요. 낡은 임기가 붙은 요청은 거절되니, 잠깐 끊겼다 돌아온 옛 리더가 끼어들 수 없어요.

<Aside type="note" title="이름만 다른 같은 개념">
이런 번호를 일반적으로 **에포크 번호**(epoch)라고 불러요. Paxos는 투표 번호(ballot), Raft는 텀(term), ZooKeeper는 에포크라고 해요.
</Aside>

### 리더 선출: 무작위 타임아웃과 과반 투표

서버끼리 주고받는 기본 메시지는 두 개예요. 후보가 보내는 **RequestVote**(표 주세요)와, 리더가 보내는 **AppendEntries**(로그 받아 적으세요, 겸 하트비트)예요.

1. 리더는 주기적으로 **하트비트**(heartbeat, "나 살아 있어" 신호)를 보내요. 팔로워는 하트비트를 받을 때마다 타이머를 다시 시작해요.
2. 팔로워가 **선거 타임아웃**(election timeout) 동안 아무 연락도 못 받으면, 리더가 죽었다고 보고 선거를 시작해요.
3. 임기를 +1 하고 후보가 돼서, **자기에게 1표**를 주고 다른 서버 모두에게 RequestVote를 보내요.
4. 각 서버는 **한 임기에 한 명에게만**, 먼저 온 순서대로 투표해요. 단, 후보의 로그가 내 로그보다 덜 최신이면 거절해요(아래 "로그 복제와 커밋"에서 이유를 설명해요).
5. **전체의 과반** 표를 받으면 리더가 되고, 바로 하트비트를 보내 다른 서버의 출마를 막아요.
6. 아무도 과반을 못 얻으면(표 갈림, split vote) 임기만 지나가고, 다시 타임아웃을 기다려 새 선거를 해요.

**왜 타임아웃을 무작위로 하나요?** 모두 같은 시간에 타임아웃되면 동시에 출마해서 표가 계속 갈려요. 그래서 타임아웃을 일정 구간 안에서 **서버마다 무작위로** 골라요(Raft 논문 예시는 150~300ms). 그러면 대개 한 서버가 먼저 깨어나 다른 서버가 출마하기 전에 이겨요.

<Aside type="caution" title="리더가 죽으면 0초 만에 넘어가지 않아요">
새 리더가 뽑힐 때까지, 대략 **선거 타임아웃만큼은 쓰기가 안 되는 구간**이 생겨요. 아래 etcd 실험에서도 약 1.7초 걸렸어요. 앱에서 재시도를 꼭 준비해야 하는 이유예요.
</Aside>

### 로그 복제와 커밋

Raft에서 데이터는 **로그**(log, 명령을 순서대로 적은 목록)로 관리해요. 로그의 각 칸에는 **명령 + 그때의 임기 번호 + 위치(인덱스)**가 들어가요. 모든 서버가 같은 로그를 같은 순서로 실행하면 모두 같은 상태가 돼요. 이걸 **복제된 상태 머신**(replicated state machine)이라고 해요.

1. 클라이언트가 리더에게 "x=3"을 보내요.
2. 리더는 자기 로그 끝에 적고(아직 **미확정**), 팔로워 모두에게 AppendEntries로 보내요.
3. **과반**(리더 포함)이 저장하면 그 칸은 **커밋**(commit, 확정)돼요. 리더는 그제야 실제로 적용하고 클라이언트에 OK를 줘요.
4. 리더는 "몇 번 칸까지 커밋됐는지"를 다음 하트비트에 실어 보내고, 팔로워들도 그걸 보고 적용해요.
5. 느리거나 죽어 있던 팔로워에게는 OK를 준 뒤에도 계속 다시 보내요.

핵심은 **클라이언트에 OK를 주는 시점 = 과반이 저장한 시점**이라는 거예요. 모든 서버가 저장할 때까지 기다리지 않아요.

커밋된 칸은 과반에 있어요. 새 리더도 과반 표를 받아야 하니, 두 과반은 **최소 한 서버가 겹쳐요**. 여기에 "내 로그보다 덜 최신인 후보에겐 투표 안 함"이라는 규칙을 더해서, 새 리더는 **커밋된 데이터를 반드시 갖고 있게** 돼요.

반대로 **미확정** 칸은 사라질 수 있어요. 팔로워 로그가 리더와 다르면, 리더가 팔로워 로그를 자기 것으로 **덮어써요**. 리더는 자기 로그를 지우거나 고치지 않아요.

### 몇 대까지 죽어도 되나: 홀수인 이유

과반은 `⌊n/2⌋ + 1`, 견딜 수 있는 장애 수는 `⌊(n−1)/2⌋`예요(⌊ ⌋는 소수점 버림).

| 서버 수 | 과반 | 견디는 장애 |
|---|---|---|
| 1 | 1 | 0 |
| 2 | 2 | **0** |
| 3 | 2 | 1 |
| 4 | 3 | **1** |
| 5 | 3 | 2 |
| 6 | 4 | **2** |
| 7 | 4 | 3 |

- **짝수는 손해예요.** 3대와 4대 모두 1대까지만 견뎌요. 4대는 고장 날 기계만 하나 늘고, 복제할 곳이 늘어 쓰기도 느려져요.
- **2대는 1대보다 나을 게 없어요.** 과반이 2라 1대만 죽어도 멈춰요. "두 대로 이중화했으니 안전"은 착각이에요.
- **홀수면 네트워크가 반으로 갈려도 한쪽은 꼭 과반**이에요. 짝수(예: 4대가 2:2)는 양쪽 다 멈출 수 있어요.
- **많을수록 좋지도 않아요.** 저장해야 할 곳이 많아져 쓰기가 느려져요. etcd는 5대면 대부분 충분하고 7대 이하를 권장해요.

**네트워크가 갈리면?** 5대가 \{S1, S2\} / \{S3, S4, S5\}로 나뉘면, 옛 리더 S1 쪽은 2/5라 커밋을 못 해요(쓰기 멈춤). S3~S5 쪽은 새 임기로 리더를 뽑고 계속 일해요. 네트워크가 돌아오면 S1은 더 큰 임기를 보고 팔로워로 내려가고, S1 쪽의 미확정 칸은 새 리더 로그로 덮어써져요. 그래서 스플릿 브레인이 생기지 않아요.

### 실제로 돌려 본 etcd

**etcd**는 Raft로 만든 키-값 저장소예요. 쿠버네티스가 클러스터의 모든 상태(어떤 파드가 어디 떠 있어야 하는지 등)를 여기에 저장해요. 리더가 없으면 상태를 바꿀 수 없어서 새 파드 배치도 안 돼요. → [쿠버네티스 구조](../../infra/k8s-architecture/)

etcd 3대를 띄우고 직접 죽여 봤어요. 아래 수치는 **한 번 재 본 예시**라 환경마다 달라요.

| 해 본 것 | 결과 |
|---|---|
| 리더 1대를 강제 종료 | 남은 서버가 후보가 됐다가 바로 리더가 됨. 종료부터 새 리더까지 **약 1.66초**, 임기 번호 **3 → 4**. 이후 쓰기 정상 |
| 3대 중 2대 종료(1대만 남음) | 쓰기가 약 5초 뒤 `context deadline exceeded`로 **실패**. 기본 읽기도 같은 오류로 실패. 상태 확인에 `etcdserver: no leader` |
| 같은 상태에서 `--consistency=s` 읽기 | 그 서버가 가진 **마지막 값**을 돌려줌(최신이라는 보장 없음) |
| 죽인 서버 1대를 다시 켬(2/3) | 몇 초 안에 새 리더가 뽑히고 쓰기 정상 |

1.66초는 etcd 기본 선거 타임아웃 1000ms에 무작위 대기가 더해진 값과 대략 맞아요. 과반을 잃었을 때 etcd는 "옛 값이라도 쓰게 해 주기"를 하지 않고 **아예 실패**시켜요. [CAP](../cap-consistency/)으로 보면 가용성보다 일관성을 고른 거예요.

```bash
# etcd 읽기 두 종류
etcdctl get mykey                     # 기본(선형적): Raft를 거쳐 최신 값 보장
etcdctl get mykey --consistency=s     # serializable: 아무 서버나 바로 응답, 옛 값일 수 있음
```

### 2PC와 무엇이 다른가

이름이 비슷한 **2PC**(2단계 커밋, 여러 DB에 걸친 트랜잭션을 전부 커밋하거나 전부 취소하는 방법)와 자주 비교해요. 자세한 건 [분산 트랜잭션](../distributed-transactions/)에서 다뤄요.

| | 2PC | 합의(Raft) |
|---|---|---|
| 목적 | 서로 **다른 데이터**를 가진 여러 노드를 한꺼번에 커밋/취소 | **같은 데이터**를 가진 노드들이 하나의 값·순서에 동의 |
| 필요한 동의 | **전원** "예" | **과반** |
| 지휘자 | 코디네이터 고정(선출 안 함) | 리더를 투표로 뽑고, 죽으면 다시 뽑음 |
| 지휘자가 죽으면 | 참여자가 잠금을 쥔 채 복구까지 대기 | 남은 과반이 새 리더를 뽑고 계속 |

### 심화: 다른 합의 알고리즘과 FLP

- **Paxos**: 가장 유명한 합의 알고리즘이에요. 실무에선 여러 값을 연달아 합의하는 Multi-Paxos를 써요. Raft는 같은 문제를 리더 선출·로그 복제·안전성으로 나눠 이해하기 쉽게 정리한 것이지, 더 강한 걸 보장하는 건 아니에요.
- **ZAB**: ZooKeeper가 쓰는 방식이에요. 리더가 제안을 보내고 과반이 디스크에 적었다고 답하면 커밋해요. 트랜잭션 번호(zxid)의 앞 절반이 에포크, 뒤 절반이 카운터예요.
- **FLP 불가능성**: 시계·타임아웃을 전혀 못 쓰는 아주 제한된 모델에서는, 한 대라도 죽을 수 있으면 "항상 합의에 도달하는" 알고리즘이 없다는 증명이에요. Raft는 타임아웃과 무작위를 써서 이 가정 밖에서 동작해요. 그래서 운이 나쁘면 선출이 늦어질 수는 있지만(활동성), 틀린 결정은 안 해요(안전성).

### 심화: 새 리더의 커밋 규칙과 읽기

- 새 리더는 **이전 임기**의 칸이 과반에 있다는 것만 보고 커밋됐다고 판단하지 않아요. **자기 임기**의 칸이 과반에 저장될 때 그 앞 칸들까지 함께 커밋돼요. 그래서 새 리더는 임기 시작 때 빈 항목(no-op)을 하나 커밋해요.
- 리더가 로그를 거치지 않고 바로 읽어 주면, 이미 밀려난 걸 모르는 옛 리더가 낡은 값을 줄 수 있어요. 그래서 읽기 전에 과반과 하트비트를 주고받아 **아직 내가 리더인지** 확인해요. etcd의 기본(선형적) 읽기가 2대 종료 실험에서 실패한 이유도 이거예요.
- 서버를 추가·제거할 땐 옛 구성과 새 구성의 과반을 **둘 다** 요구하는 단계(joint consensus)를 거쳐서, 중간에 리더가 둘 생기지 않게 해요.

### 심화: 합의의 비용과 쓰는 곳

- 과반 투표는 일종의 **동기 복제**라 느려요. 그래서 많은 DB는 장애 때 일부 손실을 감수하고 비동기 복제를 써요.
- 장애 감지를 타임아웃에 의존해요. 네트워크 지연이 들쭉날쭉하면 리더가 죽었다고 오판해 선거가 잦아지고, 안전하긴 하지만 성능이 나빠져요. etcd는 하트비트를 서버 간 왕복 시간(RTT) 근처로, 선거 타임아웃은 RTT의 10배 이상으로 잡으라고 권장해요(기본 100ms / 1000ms).
- etcd·ZooKeeper는 범용 DB가 아니에요. "누가 리더인가", 설정값처럼 **작고 드물게 바뀌는** 데이터용이에요. 리더 선출, 잠금, 단조 증가 번호(펜싱 토큰), 변경 알림 같은 기능을 제공해요.
- Redis의 TTL 기반 락은 합의를 거치지 않아서, 정확성이 꼭 필요하면 펜싱 토큰을 함께 써야 해요. → [Redis 분산 락](../../redis/distributed-lock/)

## 면접 질문

<details>
<summary>Q. 분산 시스템에서 합의가 왜 필요한가요?</summary>

**답변(30초)**
여러 서버가 같은 결론을 내야 하기 때문이에요. 대표적으로 리더 선출이에요. 두 서버가 동시에 리더라고 믿는 스플릿 브레인이 생기면 각자 쓰기를 받아 데이터가 어긋나요. 합의 알고리즘은 과반 투표로 리더를 하나만 뽑고, 모든 서버가 같은 순서로 같은 데이터를 저장하게 해요. 사람이 수동으로 골라도 되지만 그동안 시스템이 멈추니까 자동으로 하는 거예요.

**꼬리질문**
- Q. 합의는 전원이 동의해야 하나요? → 아니요, 과반이면 돼요. 전원 동의가 필요한 건 2PC예요.
- Q. 과반이 죽으면요? → 멈춰요. 대신 틀린 값을 쓰지는 않아요.
</details>

<details>
<summary>Q. Raft의 노드 역할 3가지를 설명해 주세요.</summary>

**답변(30초)**
리더, 팔로워, 후보예요. 리더는 클라이언트 요청을 모두 받고 로그를 팔로워에게 복제하며 하트비트를 보내요. 팔로워는 먼저 말 걸지 않고 리더와 후보의 요청에만 응답해요. 팔로워가 일정 시간 하트비트를 못 받으면 후보가 되어 선거에 나가고, 과반 표를 받으면 리더가 돼요.

**꼬리질문**
- Q. 팔로워에게 쓰기 요청이 오면? → 리더에게 보내요. 쓰기는 리더만 처리해요.
</details>

<details>
<summary>Q. Raft에서 리더는 어떻게 뽑나요?</summary>

**답변(30초)**
팔로워가 선거 타임아웃 동안 하트비트를 못 받으면 임기를 1 올리고 후보가 돼요. 자기에게 투표하고 다른 서버에 투표를 요청해요. 각 서버는 한 임기에 한 명에게만 투표하니까, 과반을 받은 후보는 하나뿐이고 그 후보가 리더가 돼요. 리더는 바로 하트비트를 보내 다른 서버의 출마를 막아요.

**꼬리질문**
- Q. 아무도 과반을 못 얻으면? → 그 임기는 리더 없이 끝나고, 다시 타임아웃을 기다려 새 임기로 재선거해요.
- Q. 아무 후보에게나 투표하나요? → 아니요, 후보 로그가 내 로그보다 덜 최신이면 거절해요. 그래야 새 리더가 커밋된 데이터를 다 갖고 있어요.
</details>

<details>
<summary>Q. 선거 타임아웃을 왜 무작위로 정하나요?</summary>

**답변(30초)**
표 갈림을 막기 위해서예요. 모든 서버가 같은 시간에 타임아웃되면 동시에 출마해 표가 나뉘고, 아무도 과반을 못 얻는 일이 반복돼요. 서버마다 타임아웃을 무작위로 고르면 대개 한 서버가 먼저 출마해서 다른 서버가 깨기 전에 이기고 하트비트를 보내요. Raft 논문은 150~300ms 구간을 예로 들어요.

**꼬리질문**
- Q. 타임아웃을 아주 짧게 하면? → 선출은 빨라지지만 하트비트가 조금만 늦어도 리더가 죽었다고 오판해 불필요한 선거가 잦아져요.
</details>

<details>
<summary>Q. 합의 클러스터는 왜 3대, 5대처럼 홀수로 두나요? 4대는요?</summary>

**답변(30초)**
견딜 수 있는 장애 수가 홀수 기준으로만 늘기 때문이에요. 과반은 n/2를 버림한 값에 1을 더한 수라서, 3대와 4대 모두 1대까지, 5대와 6대 모두 2대까지만 견뎌요. 4대는 장애 내성은 3대와 같은데 고장 날 기계와 복제 대상만 늘어요. 또 홀수면 네트워크가 갈려도 한쪽은 꼭 과반이지만, 짝수는 반반으로 갈려 양쪽 다 멈출 수 있어요.

**꼬리질문**
- Q. 그럼 많을수록 좋은가요? → 아니요, 복제할 곳이 늘어 쓰기가 느려져요. etcd는 5대면 대부분 충분하고 7대 이하를 권장해요.
- Q. 2대는요? → 과반이 2라 1대만 죽어도 멈춰요. 1대보다 나을 게 없어요.
</details>

<details>
<summary>Q. Raft에서 쓰기는 언제 커밋되나요?</summary>

**답변(30초)**
리더가 자기 로그에 적은 항목을 과반 서버가 저장했을 때예요. 그 시점에 리더가 적용하고 클라이언트에 OK를 줘요. 모든 서버를 기다리지 않아요. 커밋된 항목은 과반에 있고, 새 리더도 과반 표를 받아야 하니 둘이 꼭 겹쳐서 커밋된 데이터는 리더가 바뀌어도 사라지지 않아요.

**꼬리질문**
- Q. 팔로워 로그에 있으면 커밋된 건가요? → 아니요. 과반에 안 퍼진 미확정 항목은 새 리더가 덮어쓸 수 있어요.
- Q. 팔로워는 커밋을 어떻게 아나요? → 리더가 커밋된 위치를 다음 하트비트에 실어 보내요.
</details>

<details>
<summary>Q. 네트워크 분할 때 Raft는 스플릿 브레인을 어떻게 막나요?</summary>

**답변(30초)**
과반 쪽만 커밋할 수 있기 때문이에요. 5대가 2:3으로 갈리면 2대 쪽 옛 리더는 과반을 못 모아 쓰기를 확정할 수 없어요. 3대 쪽은 새 임기로 리더를 뽑아 계속 일해요. 네트워크가 돌아오면 옛 리더는 더 큰 임기 번호를 보고 팔로워로 내려가고, 그쪽 미확정 항목은 새 리더 로그로 덮어써져요.

**꼬리질문**
- Q. 옛 리더가 갈린 동안 읽기 요청에 낡은 값을 주면요? → 그래서 선형적 읽기는 응답 전에 과반과 하트비트를 주고받아 아직 리더인지 확인해요.
</details>

<details>
<summary>Q. 2PC와 합의 알고리즘은 어떻게 다른가요?</summary>

**답변(30초)**
2PC는 서로 다른 데이터를 가진 여러 노드를 전부 커밋하거나 전부 취소하는 방법이고, 합의는 같은 데이터를 가진 노드들이 하나의 값에 동의하는 방법이에요. 2PC는 참여자 전원의 동의가 필요하고 코디네이터가 고정이라, 코디네이터가 죽으면 참여자가 잠금을 쥔 채 기다려요. 합의는 과반만 동의하면 되고, 리더가 죽으면 남은 노드가 새 리더를 뽑아 계속 진행해요.

**꼬리질문**
- Q. 2PC와 2PL은 같은 건가요? → 아니요, 2PL은 2단계 잠금이라는 전혀 다른 동시성 제어 방법이에요.
</details>

<details>
<summary>Q. (심화) FLP 불가능성이 있는데 Raft는 어떻게 합의하나요?</summary>

**답변(30초)**
FLP는 시계나 타임아웃을 전혀 못 쓰는 아주 제한된 모델에서, 한 대라도 죽을 수 있으면 항상 합의에 도달하는 결정적 알고리즘이 없다는 결과예요. Raft는 타임아웃과 무작위 선거 타이머를 써서 그 가정 밖에서 동작해요. 그래서 운이 나쁘면 선출이 계속 늦어질 수는 있지만, 틀린 결정을 내리지는 않아요.

**꼬리질문**
- Q. 그럼 모든 DB 복제를 합의로 하면 되지 않나요? → 과반 투표는 동기 복제라 느리고, 타임아웃 오판에 민감해서 성능을 위해 비동기 복제를 쓰는 DB가 많아요.
</details>

## 서술형 연습

<details>
<summary>상황: 쿠버네티스 컨트롤 플레인의 etcd를 몇 대로 구성할지 정해야 해요. 팀에서는 3대, 4대, 5대 의견이 나왔어요. 어떻게 결정하겠어요?</summary>

**상황 파악**
etcd는 쿠버네티스의 모든 상태를 담고, 과반을 잃으면 쓰기가 멈춰 새 파드 배치·배포가 안 돼요. 그래서 "몇 대가 동시에 죽어도 버텨야 하나"와 "쓰기 성능·운영 비용"을 같이 봐야 해요.

**원인 후보(고려할 요소)**
1. 견디는 장애 수: 3대·4대는 1대, 5대는 2대.
2. 쓰기 비용: 대수가 늘수록 과반 저장을 기다릴 곳이 늘어 느려짐.
3. 유지보수: 1대를 업그레이드로 내리는 동안 다른 1대가 죽는 상황.

**해결책과 트레이드오프**

| 구성 | 장점 | 단점 |
|---|---|---|
| 3대 | 비용·지연 최소, 1대 장애 견딤 | 1대 점검 중 1대 더 죽으면 정지 |
| 4대 | 없음(장애 내성은 3대와 같음) | 고장 날 기계·복제 대상만 늘어남. 2:2로 갈리면 양쪽 다 정지 |
| 5대 | 2대 장애 견딤, 1대 점검 중에도 1대 장애 허용 | 서버 비용 증가, 쓰기 지연 약간 증가 |

**내가 고를 방법**
4대는 장애 내성이 3대와 같고 단점만 있으니 먼저 뺍니다. 운영 클러스터면 5대를 골라요. 쿠버네티스 문서도 운영엔 5대를 권장하고, 업그레이드로 1대를 내린 동안에도 1대 장애를 견딜 수 있어요. 비용이 빠듯한 소규모·개발 환경이면 3대로 하되, 백업과 멤버 교체 절차를 미리 준비해요. 7대 이상은 쓰기가 느려져 고려하지 않아요.

**채점 포인트**: 과반 공식(⌊n/2⌋+1), 견디는 장애 수(3·4대=1, 5대=2), 짝수 손해(분할 시 양쪽 정지), 대수가 늘면 쓰기 느려짐, 점검 중 장애 시나리오, etcd 정지 = 쿠버네티스 상태 변경 불가, 운영 5대 권장.
</details>

<details>
<summary>상황: etcd 3대를 데이터센터 A에 2대, B에 1대로 나눠 배치했어요. 데이터센터 A 전체가 정전으로 꺼졌어요. 무슨 일이 생기고, 어떻게 바꿔야 하나요?</summary>

**상황 파악**
3대의 과반은 2대예요. A가 꺼지면 B의 1대만 남아 과반이 안 돼요. 리더를 뽑을 수 없고 쓰기가 전부 실패해요. 데이터는 B에 남아 있지만 쿠버네티스는 새 파드를 배치하거나 설정을 바꿀 수 없어요. "두 곳에 나눴으니 재해 대비가 됐다"는 착각이 원인이에요.

**원인 후보**
1. 데이터센터 2곳에는 어떻게 나눠도 한 곳이 죽으면 과반이 깨질 수 있음. 홀수면 과반을 가진 쪽이 죽을 때, 짝수(예: 2:2)면 어느 쪽이 죽어도 정지.
2. B의 1대는 혼자 리더가 될 수 없음(과반 규칙). 이건 버그가 아니라 스플릿 브레인을 막는 정상 동작.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 데이터센터를 3곳으로 늘려 1:1:1 배치 | 어느 한 곳이 통째로 죽어도 2/3 과반 유지 | 세 번째 위치 비용, 위치 간 지연이 커지면 쓰기 느려짐(타임아웃 튜닝 필요) |
| B. 5대를 2:2:1로 3곳에 배치 | 한 곳이 죽어도 과반(3) 유지, 서버 1대 추가 장애도 일부 견딤 | 서버·위치 비용 증가 |
| C. 2곳 유지 + 장애 시 사람이 백업으로 클러스터 복구 | 추가 위치 불필요 | 사람이 개입할 때까지 정지, 마지막 백업 이후 변경은 잃을 수 있음 |

**내가 고를 방법**
A나 B로 **세 번째 위치**를 둬요. 두 곳에는 어떻게 나눠도 한 곳이 통째로 죽으면 과반을 잃을 수 있으니 근본 해결이 안 돼요. 세 위치 사이 지연이 크면 하트비트와 선거 타임아웃을 왕복 시간에 맞춰 늘려서 리더가 괜히 자주 바뀌지 않게 해요. 당장 위치를 늘릴 수 없다면 C의 복구 절차를 문서화하고 정기 백업을 해 둬요.

**채점 포인트**: 3대 과반=2, 남은 1대는 리더 불가·쓰기 실패, 정상 동작(스플릿 브레인 방지)임을 설명, 2곳 배치의 한계, 3곳 분산(1:1:1 또는 2:2:1), 위치 간 지연과 타임아웃 튜닝, 수동 복구·백업.
</details>

<details>
<summary>상황: etcd(또는 Raft 기반 저장소)를 쓰는 서비스에서, 리더 서버가 죽은 직후 1~2초 동안 쓰기 요청이 실패하는 로그가 남았어요. 왜 그런지, 앱은 어떻게 대응해야 하나요?</summary>

**상황 파악**
Raft에선 리더만 쓰기를 받아요. 리더가 죽으면 팔로워가 선거 타임아웃을 기다린 뒤 새 리더를 뽑는데, 그 사이엔 쓰기를 받을 리더가 없어요. etcd 기본 선거 타임아웃이 1초라, 한 번 재 본 실험에서도 새 리더까지 약 1.7초 걸렸어요. 장애가 아니라 **설계상 생기는 짧은 공백**이에요.

**원인 후보**
1. 리더 선출 공백(선거 타임아웃 + 무작위 대기).
2. 표 갈림으로 재선거가 한 번 더 일어나 공백이 길어짐.
3. 네트워크 지연이 들쭉날쭉해 리더를 죽었다고 오판, 선거가 잦음(로그에 리더 교체가 자주 보이면 의심).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 앱에서 재시도(지수 백오프 + 지터, 최대 시간 제한) | 공백을 사용자 모르게 넘김 | 쓰기가 실제론 성공했는데 응답만 못 받았으면 **중복 실행** 위험 |
| B. A + 멱등성(요청 ID로 중복 무시, 또는 compare-and-set처럼 조건부 쓰기) | 재시도해도 결과가 한 번만 반영 | 키 설계·저장 등 구현 비용 |
| C. 선거 타임아웃을 줄임 | 공백 자체가 짧아짐 | 너무 줄이면 오판으로 리더 교체가 잦아져 오히려 불안정. 왕복 시간의 10배 이상 유지 필요 |

**내가 고를 방법**
A와 B를 같이 해요. 리더 교체는 언젠가 반드시 생기니 앱이 견디게 만드는 게 맞아요. 재시도는 백오프와 지터(무작위 간격)로 몰리지 않게 하고, 타임아웃 오류는 "실패"가 아니라 "결과 모름"일 수 있으니 멱등하게 만들어요. C는 리더 교체가 잦다는 근거(원인 3)가 있을 때 왕복 시간을 재 보고 조정해요. 무작정 줄이지 않아요.

**채점 포인트**: 리더만 쓰기 처리, 선거 타임아웃만큼 쓰기 불가 구간, 실패 원인이 설계상 정상, 재시도+백오프+지터, 타임아웃 = 결과 모름 → 멱등성 필요, 타임아웃 튜닝의 트레이드오프(오판), RTT 기반 설정.
</details>

## 필기 포인트

- 합의의 두 속성: **안전성**(틀린 결정 안 함) / **활동성**(결국 결정). 과반이 죽으면 멈추지만 안전성은 유지.
- Raft 역할: 리더·팔로워·후보. RPC: RequestVote, AppendEntries(하트비트 겸용).
- 한 임기(term)에 리더 **최대 1명**. 한 서버는 한 임기에 **한 표**.
- 선거 타임아웃 **무작위** → 표 갈림 방지. 논문 예시 150~300ms, etcd 기본 1000ms(하트비트 100ms).
- 커밋 = 리더 항목이 **과반**에 저장됨. 전원 아님.
- 과반 `⌊n/2⌋+1`, 견디는 장애 `⌊(n−1)/2⌋`. 3·4대 → 1, 5·6대 → 2. 2대 → 0.
- 2PC = 전원 동의·코디네이터 고정·블로킹. 합의 = 과반·리더 선출·복구 가능. 2PC ≠ 2PL.
- FLP: 타임아웃 없는 비동기 모델에선 항상 끝나는 결정적 합의 불가. 대표 알고리즘: Paxos, Raft, ZAB(ZooKeeper), VSR.
