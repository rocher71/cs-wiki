:::tip[한 줄 요약]
**이벤트 소싱**(event sourcing)은 "잔액 = 7만 원"처럼 현재 상태만 덮어쓰는 대신, "입금 10만 원", "출금 3만 원" 같은 **이벤트를 추가만 해서 쌓고** 현재 상태는 이벤트를 **재생**해서 계산하는 방식이에요. **CQRS**는 데이터를 **바꾸는 모델**과 **읽는 모델**을 나누는 패턴이고, 이벤트 저장소는 조회가 어려워서 둘을 함께 쓰는 경우가 많아요. 대신 복잡하고 **최종 일관성** 비용이 있어서, 결제 원장처럼 이력이 중요한 **일부에만** 써요.
:::

:::note[처음이라면 여기까지]
① 이벤트 소싱은 통장 거래내역처럼 "있었던 일"을 지우지 않고 계속 쌓는 방식이에요. 잔액은 거래내역을 더해서 구해요.

② 쌓인 기록이 너무 많아지면 중간 결과(스냅숏)를 저장해 두고 그 뒤부터만 더해요.

③ CQRS는 "쓰기용 모델"과 "조회용 모델"을 따로 두는 거예요. 이벤트 소싱 없이도 쓸 수 있어요.

④ 둘 다 복잡해서 대부분의 서비스엔 과해요. 면접에선 질문 1~3번과 "언제 쓰지 말아야 하나"부터 연습하세요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

은행 앱을 열면 잔액이 보이지만, 은행이 진짜로 믿는 건 **거래내역**이에요. 입금 10만 원, 출금 3만 원, 입금 5만 원이 순서대로 적혀 있고, 잔액은 이걸 다 더한 결과예요.

잘못 출금된 게 있으면 그 줄을 지우지 않아요. "환불 3만 원"이라는 줄을 **새로 추가**해요. 그래서 "왜 잔액이 이렇게 됐지?"라는 질문에 언제든 답할 수 있어요.

이벤트 소싱이 이 방식이에요. 보통의 DB 설계(**CRUD**, 만들기·읽기·고치기·지우기)는 잔액 칸 하나를 계속 덮어써서 이력이 남지 않아요. 이벤트 소싱은 거래내역 자체를 원본으로 저장해요.

그런데 "잔액 100만 원 이상인 고객 목록"을 뽑으려고 모든 고객의 거래내역을 매번 다 더하면 너무 느리겠죠. 그래서 조회용 표를 따로 만들어 두고, 거래가 생길 때마다 그 표를 갱신해요. 이렇게 **쓰는 쪽과 읽는 쪽을 나누는 것**이 CQRS예요.

단, 실제 은행 시스템이 모두 이벤트 소싱으로 만들어진 건 아니에요. 비유는 "원리가 같다"는 뜻이에요.

## 제대로 알기

### 상태 저장 vs 이벤트 저장

| | 상태 저장(CRUD) | 이벤트 저장(이벤트 소싱) |
|---|---|---|
| 무엇을 저장하나 | 현재 값(잔액 70,000) | 일어난 일의 목록(입금, 출금…) |
| 변경 방법 | 덮어쓰기(UPDATE) | 끝에 추가만(append-only) |
| 원본(진짜 기준) | 테이블의 현재 행 | 이벤트 저장소 |
| 과거 이력 | 따로 만들지 않으면 없음 | 자동으로 다 남음 |
| 실수 바로잡기 | 값을 고침 | **보상 이벤트**(되돌리는 이벤트)를 새로 추가 |
| 조회 | SQL로 자유롭게 | 어려움 → 보통 CQRS 읽기 모델 필요 |
| 난이도 | 익숙하고 단순 | 학습·운영 비용 큼 |

핵심 규칙은 두 가지예요.

- **이벤트는 불변**이에요. 한 번 기록하면 고치거나 지우지 않아요. 잘못됐으면 `좌석예약됨` 뒤에 `예약취소됨`처럼 **보상 이벤트**(compensating event)를 추가해요.
- **이벤트에는 업무상 의도**를 담아요. "balance 칸을 42로 바꿈" 같은 저수준 변경이 아니라 "강의 신청 취소함"처럼 **무슨 일이 있었는지**를 적어야 나중에 감사 기록이나 새 화면을 만들 때 쓸모가 있어요.

### 명령과 이벤트는 달라요

- **명령**(command)은 "출금해 줘" 같은 **요청**이에요. 잔액이 부족하면 거절될 수 있어요.
- **이벤트**(event)는 검증을 통과해 **이미 일어난 사실**이에요. 그래서 이름도 과거형("출금됨")으로 지어요.

이벤트를 받는 쪽은 이벤트를 거절할 수 없어요. 그래서 **검증은 이벤트가 되기 전**, 명령을 처리할 때 끝내야 해요.

### 왜 쓰나: 상태보다 많은 정보

- **감사 추적**: 누가 언제 무엇을 했는지 전부 남아요. "왜 이 금액이 됐나"를 설명할 수 있어요.
- **디버깅·복구**: 버그로 값이 덮어써지면 되살리기 어렵지만, 추가 전용 기록이 있으면 원인을 찾고 복구하기 쉬워요.
- **시간 여행**: 특정 시점까지만 재생하면 "지난달 1일의 잔액"을 알 수 있어요(**시간 질의**, temporal query).
- **분석용 정보**: 장바구니에 넣었다 뺀 기록은 주문엔 필요 없지만 분석엔 유용해요. 상태만 저장하면 사라져요.

이벤트 소싱은 **DDD**(도메인 주도 설계, 업무 규칙 중심으로 코드를 나누는 설계 방식) 쪽에서 나온 기법이고, 전용 DB(EventStore 등)를 써도 되고 일반 관계형 DB에 추가 전용 테이블을 만들어 구현해도 돼요.

### 재생과 스냅숏

현재 상태는 그 대상(계좌 하나, 주문 하나 같은 **엔티티**)의 이벤트를 **처음부터 순서대로 다시 적용**해서 만들어요. 이걸 **재생**(replay)이라고 해요.

```java
// 계좌의 이벤트를 처음부터 적용해 현재 잔액을 계산
long replay(List<AccountEvent> events) {
    long balance = 0;
    for (AccountEvent e : events) {
        if (e instanceof Deposited d)  balance += d.amount();
        if (e instanceof Withdrawn w)  balance -= w.amount();
    }
    return balance; // 같은 이벤트면 항상 같은 결과(결정적)
}
```

재생은 **결정적**이어야 해요. 같은 이벤트를 다시 돌리면 같은 상태가 나와야 해요. 그래서 재생 코드 안에서 현재 시각이나 난수를 쓰면 안 돼요.

이벤트가 수십만 개가 되면 재생이 느려져요. 그래서 이벤트 N개마다 그 시점의 상태 사본인 **스냅숏**(snapshot)을 저장해요. 복원할 때는 최신 스냅숏을 읽고 **그 뒤 이벤트만** 재생해요.

<Aside type="caution" title="스냅숏은 원본이 아니에요">
스냅숏은 속도를 위한 캐시일 뿐이에요. 원본은 여전히 이벤트예요. 스냅숏은 지워도 이벤트로 다시 만들 수 있지만, 이벤트를 지우고 스냅숏만 남기면 더는 이벤트 소싱이 아니에요.
</Aside>

### CQRS: 쓰기 모델과 읽기 모델 나누기

**CQRS**(Command Query Responsibility Segregation, 명령·조회 책임 분리)는 데이터를 **바꾸는 모델**(쓰기 모델)과 **읽는 모델**(읽기 모델)을 나누는 패턴이에요.

나누는 정도는 단계가 있어요.

| 단계 | 모습 | 비고 |
|---|---|---|
| 1. 코드만 분리 | 같은 DB, 쓰기용 클래스와 조회용 클래스(DTO·쿼리)를 따로 | 가장 단순한 CQRS |
| 2. 저장소 분리 | 쓰기는 관계형 DB, 읽기는 조회에 맞춘 다른 DB(문서 DB 등) | 이벤트로 읽기 DB를 동기화 |
| 3. 이벤트 소싱과 결합 | 쓰기 쪽 원본이 이벤트 저장소 | 읽기 모델은 이벤트에서 만들어 냄 |

**CQRS는 이벤트 소싱 없이도 쓸 수 있어요.** 1·2단계는 이벤트 소싱과 상관없어요. 반대로 이벤트 소싱은 거의 항상 CQRS를 동반해요. 이벤트 저장소는 "이 계좌의 이벤트 전부 주세요"처럼 **엔티티별로만** 잘 읽히고, "잔액 100만 원 이상인 고객"같은 질의를 SQL처럼 던질 수 없기 때문이에요.

읽기 모델은 이벤트를 구독해 조회용으로 미리 가공해 둔 **읽기 전용 사본**이에요. 이걸 **프로젝션**(projection) 또는 **구체화 뷰**(materialized view)라고 불러요. 화면에 맞게 **비정규화**(조인 없이 바로 보여 주도록 중복 저장)해도 괜찮아요. 원본은 이벤트라서 언제든 다시 만들 수 있으니까요.

<Aside type="note" title="CQRS = 읽기 레플리카?">
같은 말은 아니에요. 읽기 레플리카는 **같은 스키마**의 복사본이고, CQRS 읽기 모델은 조회에 맞춰 **다른 형태**로 만들 수 있어요. 다만 단순한 경우엔 쓰기 DB의 읽기 전용 복제본을 읽기 저장소로 쓰기도 해요. → [복제](../replication/)
</Aside>

### 프로젝션 재구축

원본이 이벤트라서, 읽기 모델이 버그로 틀렸거나 새 화면이 필요하면 **새 읽기 DB를 비워 놓고 이벤트를 1번부터 재생**하면 돼요. 다 만들어지면 조회를 새 DB로 돌리고 옛 것을 버려요. 기존 시스템과 나란히 돌릴 수 있어서 큰 스키마 마이그레이션보다 부담이 적어요.

주의할 점: 재생 중에 **메일 발송·결제 API 같은 외부 호출이 다시 나가면 안 돼요.** 외부 호출을 한곳(게이트웨이)으로 모아 두고, 재생 모드에서는 막아야 해요.

### 최종 일관성 비용: 쓰고 바로 목록에 안 보임

쓰기 모델과 읽기 모델이 나뉘면, 읽기 모델 갱신은 보통 **비동기**(이벤트가 저장된 뒤 따로 처리)예요. 그래서 출금하고 바로 거래내역 화면을 열면 **아직 안 보일 수 있어요.** 기다리면 맞춰지는 **최종 일관성**(eventual consistency)이에요. 복제 지연에서 본 "방금 쓴 글이 안 보임"과 같은 모양의 문제예요. → [복제 지연과 읽기 일관성](../replication-lag/)

해결 방법은 비슷해요.

- 쓰기 응답에 결과를 담아 화면에 바로 반영하기
- 쓴 본인에게는 쓰기 모델에서 읽어 주기(**자신이 쓴 내용 읽기**, read-your-writes)
- 꼭 즉시 맞아야 하는 부분은 같은 저장소·같은 트랜잭션에서 함께 갱신하기
- 프로젝션 지연을 모니터링하기

**읽기 화면이 항상 즉시 정확해야 하는 시스템**이라면 이 구조 자체가 맞지 않을 수 있어요.

### 개인정보 삭제 vs 불변 로그

"탈퇴했으니 제 개인정보를 지워 주세요"라는 요청은 "이벤트는 지우지 않는다"는 원칙과 정면으로 부딪혀요. "개인정보삭제됨" 이벤트를 추가해도 **원래 이벤트에 이름·전화번호가 그대로 남아서** 해결이 안 돼요. 필요한 건 처음부터 기록하지 않은 것처럼 만드는 거예요.

| 방법 | 어떻게 | 대가 |
|---|---|---|
| 개인정보 밖으로 빼기 | 이벤트에는 고객 ID만, 이름·연락처는 별도 저장소에 | 개인정보 저장소만 지우면 됨. 조회 때 합쳐야 함 |
| **암호화 삭제**(crypto-shredding) | 개인정보를 **사람별 키**로 암호화해 이벤트에 넣고, 삭제 요청 시 **키만 지움** | 이벤트는 남지만 그 필드는 영영 못 풂. 모든 읽기·쓰기에 암호화 비용과 키 관리 부담 |

참고로 데이터를 "진짜로" 지우는 건 원래 어려워요. 저장 엔진·파일 시스템·SSD는 제자리에 덮어쓰지 않고 새 위치에 쓰는 경우가 많고, 백업은 일부러 불변으로 만들어요. 그래서 삭제는 "아예 못 찾게 만든다"기보다 "찾기 어렵게 만든다"에 가까워요.

### 이벤트 스키마 버전 관리

이벤트는 영원히 남는 원본이라 형식(스키마)을 바꾸기 어려워요. 1년 전 이벤트도 오늘 코드로 재생할 수 있어야 하거든요.

| 전략 | 내용 |
|---|---|
| 관대한 읽기 | 모르는 필드는 무시하고, 없는 필드는 기본값으로 |
| 버전 번호 | 이벤트에 `version: 2`처럼 형식 번호를 넣음 |
| **업캐스팅**(upcasting) | 읽을 때 옛 형식을 새 형식으로 변환. 저장된 이벤트는 그대로 |
| 제자리 마이그레이션 | 저장된 이벤트를 직접 고침. **최후 수단** — 불변성과 감사 기록을 깨뜨려요 |

버그가 잘못된 이벤트를 만들었다면 코드를 고쳐도 과거 이벤트는 그대로예요. 보상 이벤트나 업캐스터로 처리해야 해요.

### 언제 쓰지 말아야 하나

이 페이지에서 가장 중요한 부분이에요. 마틴 파울러는 CQRS에 대해 "대부분의 시스템에서 **위험한 복잡성**을 더한다", "CRUD에 맞는 시스템이면 CRUD로 하라"고 경고했어요. 쓰더라도 시스템 **전체가 아니라 특정 부분**에만 쓰라고 했고, 자신이 본 사례 대부분이 좋지 않았다고 해요. Microsoft Azure 문서도 이벤트 소싱은 복잡하고 **도입하기도 되돌리기도 비싸며**, 대부분의 시스템엔 전통적인 방식으로 충분하다고 해요.

| 쓰지 않는 게 나은 경우 | 고려해 볼 만한 경우 |
|---|---|
| 감사·재생·과거 재구성이 필요 없는 단순 CRUD | 결제 원장·주문 처리처럼 **이력과 의도**가 중요한 부분 |
| 프로토타입, MVP, 수명이 짧은 서비스 | 같은 데이터로 여러 조회 화면을 만들어야 할 때 |
| 읽기 화면이 **즉시** 정확해야 하는 시스템 | 읽기가 쓰기보다 훨씬 많아 **따로 확장**해야 할 때(CQRS) |
| 거의 안 바뀌는 참조 데이터(코드표, 카탈로그) | |
| 이벤트 기반 시스템 경험이 없는 팀 | |

현실적인 권장은 **섞어 쓰기**예요. 결제 원장만 이벤트 소싱, 회원 프로필·설정은 그냥 CRUD로 둬요.

### 심화: 동시성과 중복 처리

**동시에 같은 계좌에 이벤트를 추가하면?** "읽은 뒤 스트림 버전이 그대로일 때만 추가"하는 **낙관적 동시성 제어**를 써요. 내가 버전 7을 읽고 계산했는데 그사이 누가 8번 이벤트를 넣었다면 추가를 거절하고, 다시 읽어서 재시도해요. 이벤트 소싱을 한다고 동시성 문제가 사라지지는 않아요. 여러 엔티티에 걸친 충돌은 앱이 따로 처리해야 해요.

**같은 이벤트가 두 번 오면?** 이벤트 전달은 보통 **최소 한 번**(at-least-once, 유실은 없지만 중복은 있을 수 있음)이에요. 프로젝션 핸들러가 멱등하지 않으면 잔액 집계가 두 번 반영되고 알림이 두 번 가요. **마지막으로 처리한 이벤트 순번**을 저장해 두고 그보다 작거나 같은 건 건너뛰어요.

**쓰기 DB와 이벤트 발행을 어떻게 같이?** 쓰기 저장소와 읽기 저장소가 다르면 "DB 저장"과 "이벤트 발행"을 한 트랜잭션으로 묶기 어려워요. 이때 **트랜잭셔널 아웃박스**로 원자성을 확보하고 소비자를 멱등하게 만들어요. → [아웃박스와 멱등성](../outbox-idempotency/)

### 심화: Kafka를 이벤트 저장소로 써도 될까

두 관점이 있어요.

- **써도 된다는 쪽**: 『데이터 중심 애플리케이션 설계』는 Kafka 같은 **로그 기반 메시지 브로커**로도 이벤트 소싱 방식의 시스템을 만들 수 있다고 설명해요. 이벤트를 순서대로 쌓아 두고 여러 소비자가 다시 읽을 수 있다는 점이 같으니까요.
- **대체물은 아니라는 쪽**: Azure 문서(2026)는 메시지 브로커가 이벤트 저장소를 대신할 수 없다고 해요. 보통 **"계좌 123의 이벤트만 읽기"** 같은 엔티티별 조회와 **버전 기반 낙관적 동시성**이 없기 때문이에요. 대신 이벤트를 프로젝션·다른 서비스로 **퍼뜨리는 배포 계층**으로는 좋다고 해요.

충돌이라기보다 관점 차이예요. 면접에선 "원본 저장은 엔티티별 조회와 동시성 제어가 되는 저장소에, Kafka는 전파용으로 쓰는 게 일반적이라고 알고 있다" 정도로 말하면 안전해요. → [메시지 큐와 Kafka](../message-queue-kafka/)

### 심화: 이벤트 소싱 로그 vs CDC 로그

**CDC**(Change Data Capture, DB 행 변경을 뽑아내는 기법)의 로그는 "이 행이 이렇게 바뀜"이라는 **저수준 변경**이고, 앱은 CDC가 있는지 몰라도 돼요. 이벤트 소싱의 이벤트는 앱이 **의도를 담아 직접** 기록해요.

그래서 정리 방식도 달라요. CDC 로그는 키별 최신값만 남기는 **로그 컴팩션**이 가능하지만, 이벤트 소싱은 "입금 다음 출금"이 앞 이벤트를 덮어쓰는 게 아니라서 **전체 기록이 필요**하고 컴팩션을 할 수 없어요(대신 스냅숏을 써요).

<Aside type="note" title="문서로 직접 확인하지 못한 일반 지식">
Java/Spring 쪽에서는 Axon Framework가 이벤트 소싱·CQRS 구현 프레임워크로 알려져 있어요. 이 페이지 작성 때 공식 문서로 확인하지는 않았어요.
</Aside>

## 면접 질문

<details>
<summary>Q. 이벤트 소싱이 뭔가요? CRUD와 무엇이 다른가요?</summary>

**답변(30초)**
현재 상태를 덮어쓰는 대신, 상태를 바꾼 이벤트를 순서대로 추가만 해서 저장하는 방식이에요. CRUD는 잔액 칸을 계속 덮어써서 이력이 사라지지만, 이벤트 소싱은 입금·출금 이벤트가 원본이고 잔액은 그걸 재생해 계산해요. 이벤트는 불변이라 잘못되면 지우지 않고 보상 이벤트를 추가해요. 그래서 감사 추적, 특정 시점 상태 복원, 버그 복구에 강해요.

**꼬리질문**
- Q. 이벤트 이름은 어떻게 짓나요? → 이미 일어난 사실이라 "출금됨"처럼 과거형으로, 칸 변경이 아니라 업무상 의도를 담아요.
- Q. 명령과 이벤트 차이는? → 명령은 거절될 수 있는 요청, 이벤트는 검증을 통과해 일어난 사실이에요. 검증은 이벤트가 되기 전에 해요.
</details>

<details>
<summary>Q. CQRS가 뭔가요? 이벤트 소싱이 꼭 필요한가요?</summary>

**답변(30초)**
데이터를 바꾸는 쓰기 모델과 읽는 읽기 모델을 분리하는 패턴이에요. 이벤트 소싱 없이도 쓸 수 있어요. 가장 단순하게는 같은 DB에서 쓰기용 코드와 조회용 코드만 나누고, 더 가면 읽기 전용 DB를 따로 두고 이벤트로 동기화해요. 읽기가 쓰기보다 훨씬 많아 따로 확장하거나, 조회 화면에 맞춘 형태가 필요할 때 써요.

**꼬리질문**
- Q. 읽기 레플리카랑 같은 건가요? → 레플리카는 같은 스키마 사본이고, CQRS 읽기 모델은 조회에 맞춰 다른 형태로 만들 수 있어요.
- Q. DB가 꼭 두 개여야 하나요? → 아니요. 같은 저장소에서 모델만 나눠도 CQRS예요.
</details>

<details>
<summary>Q. 이벤트 소싱과 CQRS를 왜 같이 쓰나요?</summary>

**답변(30초)**
이벤트 저장소는 엔티티별 이벤트 스트림을 읽는 데는 좋지만, 여러 엔티티를 조건으로 검색하는 건 어려워요. 그래서 이벤트를 구독해 조회용 읽기 모델, 즉 프로젝션을 따로 만들어요. 원본이 이벤트라서 프로젝션이 틀리거나 새 화면이 필요하면 이벤트를 처음부터 재생해 다시 만들 수 있어요.

**꼬리질문**
- Q. 프로젝션 재구축할 때 주의할 점은? → 재생 중에 메일·결제 같은 외부 호출이 다시 나가지 않게 막아야 해요.
</details>

<details>
<summary>Q. 이벤트가 계속 쌓이면 상태 계산이 느려지지 않나요?</summary>

**답변(30초)**
느려져요. 그래서 이벤트 N개마다 그 시점 상태를 스냅숏으로 저장하고, 복원할 때는 최신 스냅숏에서 시작해 그 뒤 이벤트만 재생해요. 스냅숏은 성능 최적화일 뿐 원본은 여전히 이벤트라, 스냅숏은 언제든 다시 만들 수 있어요.

**꼬리질문**
- Q. Kafka 로그 컴팩션처럼 오래된 이벤트를 정리하면 안 되나요? → 이벤트 소싱은 뒤 이벤트가 앞을 덮어쓰지 않아 전체 기록이 필요해서 컴팩션이 안 맞아요. 대신 스냅숏을 써요.
</details>

<details>
<summary>Q. CQRS를 쓰면 이체 직후 거래내역에 안 보인다는 문의가 올 수 있어요. 왜 그렇고 어떻게 하나요?</summary>

**답변(30초)**
읽기 모델이 이벤트를 비동기로 받아 갱신하기 때문에 잠깐 옛 값이 보이는 최종 일관성 문제예요. 쓰기 응답에 결과를 담아 화면에 바로 반영하거나, 쓴 본인에게는 쓰기 모델에서 읽어 주는 식으로 read-your-writes를 보장해요. 프로젝션 지연도 모니터링해요. 화면이 항상 즉시 정확해야 하면 같은 트랜잭션에서 함께 갱신하거나, 애초에 이 구조를 쓰지 않는 게 맞을 수 있어요.

**꼬리질문**
- Q. 프로젝션이 같은 이벤트를 두 번 받으면? → 최소 한 번 전달이라 가능해요. 처리한 이벤트 순번을 저장해 중복을 건너뛰는 멱등 처리를 해요.
</details>

<details>
<summary>Q. 같은 계좌에 동시에 출금 명령이 두 개 오면요?</summary>

**답변(30초)**
낙관적 동시성 제어를 써요. 명령 핸들러가 읽은 스트림 버전을 기억했다가, 이벤트를 추가할 때 현재 버전과 같은지 확인해요. 그사이 다른 이벤트가 추가됐으면 거절하고, 다시 읽어 잔액을 확인한 뒤 재시도해요. 그래서 잔액 부족 검사를 둘 다 통과해 마이너스가 되는 일을 막아요.

**꼬리질문**
- Q. 이벤트 소싱이면 동시성 걱정이 없지 않나요? → 아니요. 같은 엔티티엔 버전 체크가 필요하고, 여러 엔티티에 걸친 충돌은 앱이 따로 다뤄야 해요.
</details>

<details>
<summary>Q. 이벤트 형식을 바꿔야 하면 어떻게 하나요?</summary>

**답변(30초)**
이벤트는 영구 원본이라 저장된 걸 고치지 않는 게 원칙이에요. 이벤트에 버전 번호를 넣고, 읽을 때 옛 형식을 새 형식으로 바꾸는 업캐스팅을 써요. 모르는 필드는 무시하고 없는 필드는 기본값으로 채우는 관대한 읽기도 같이 해요. 저장된 이벤트를 직접 고치는 마이그레이션은 불변성과 감사 기록을 깨서 최후 수단이에요.

**꼬리질문**
- Q. 버그로 잘못된 이벤트가 이미 쌓였으면? → 코드를 고쳐도 과거 이벤트는 남아요. 보상 이벤트를 추가하거나 업캐스터로 처리해요.
</details>

<details>
<summary>Q. 회원이 개인정보 삭제를 요청하면 불변 이벤트는 어떻게 하나요?</summary>

**답변(30초)**
"삭제됨" 이벤트를 추가해도 원래 이벤트에 데이터가 남아 해결이 안 돼요. 방법은 두 가지예요. 이벤트에는 고객 ID만 넣고 개인정보는 별도 저장소에 둬서 거기만 지우거나, 개인정보를 사람별 키로 암호화해 넣고 삭제 요청 시 키만 지우는 crypto-shredding이에요. 후자는 이벤트 구조는 유지되지만 모든 읽기·쓰기에 암호화 비용과 키 관리 부담이 생겨요.

**꼬리질문**
- Q. "개인정보삭제됨" 이벤트를 추가하면 안 되나요? → 원래 이벤트에 데이터가 그대로 남아서 안 돼요. 처음부터 기록하지 않은 것처럼 만들어야 해요.
</details>

<details>
<summary>Q. 이벤트 소싱과 CQRS는 언제 쓰지 말아야 하나요?</summary>

**답변(30초)**
대부분의 시스템엔 과해요. 마틴 파울러도 CQRS가 대부분의 시스템에 위험한 복잡성을 더한다고 경고했어요. 감사·이력이 필요 없는 단순 CRUD, MVP나 수명이 짧은 서비스, 읽기가 즉시 정확해야 하는 화면, 거의 안 바뀌는 참조 데이터, 이벤트 기반 경험이 없는 팀이면 쓰지 않아요. 쓰더라도 결제 원장처럼 이력이 중요한 부분에만 적용하고 나머지는 CRUD로 둬요.

**꼬리질문**
- Q. 나중에 필요해지면 그때 도입하면 되나요? → 도입도 철회도 비싸요. 그래서 처음엔 CRUD + 이력 테이블로 시작하고, 정말 필요한 경계(바운디드 컨텍스트)에만 적용하는 게 현실적이에요.
- Q. Kafka를 이벤트 저장소로 쓰면요? → 로그 기반 브로커로 구축할 수 있다는 관점도 있지만, 엔티티별 조회와 낙관적 동시성이 보통 없어서 원본 저장소보다는 전파 계층으로 쓰는 게 일반적이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 서비스에 "주문 상태가 언제, 누구에 의해, 왜 바뀌었는지 전부 남겨야 한다"는 감사(audit) 요구가 생겼어요. 지금은 orders 테이블의 status 칸만 덮어쓰고 있어요. 어떻게 설계하겠어요?</summary>

**상황 파악**
요구사항은 "현재 상태"가 아니라 **변경 이력과 이유**예요. 지금은 덮어쓰기라 이력이 사라져요. 이력을 어디에, 무엇을 원본으로 남길지가 핵심이에요.

**원인 후보(지금 구조가 부족한 이유)**
1. `UPDATE orders SET status = ...`로 이전 값과 변경 이유가 남지 않음.
2. 애플리케이션 로그에만 남기면 보존 기간·검색·누락 보장이 안 됨.
3. 누가 바꿨는지(사용자, 관리자, 배치) 구분 정보가 없음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 이력 테이블 추가: orders는 그대로, 상태가 바뀔 때마다 `order_status_history`(주문 ID, 이전·새 상태, 사유, 행위자, 시각)를 **같은 트랜잭션**에서 INSERT | 기존 CRUD·조회 그대로, 팀이 익숙함, 도입·철회 쉬움 | 원본은 여전히 orders라 이력 누락(코드에서 빠뜨림)이 생길 수 있음. 과거 시점 상태 재구성은 제한적 |
| B. 이벤트 소싱: `주문생성됨`, `결제완료됨`, `배송시작됨`, `취소됨` 이벤트가 원본, 상태는 재생으로, 조회는 프로젝션(CQRS) | 이력이 곧 원본이라 누락이 구조적으로 없음, 의도가 남음, 시간 질의 가능 | 학습·운영 비용 큼, 조회용 프로젝션 필요, 최종 일관성, 이벤트 스키마 버전 관리, 개인정보 삭제 대응 필요 |
| C. DB 트리거나 CDC로 변경 행을 감사 테이블에 자동 복사 | 앱 코드 수정이 적고 누락이 적음 | 저수준 변경이라 **왜** 바뀌었는지(의도)가 안 남음 |

**내가 고를 방법**
요구가 "이력을 다 남기기"라면 먼저 **A**를 고르겠어요. 주문 상태 변경은 몇 가지 정해진 전이라서, 상태 변경을 한 메서드로 모으고 그 안에서 같은 트랜잭션으로 이력을 넣으면 누락도 막을 수 있어요. 팀이 익숙한 CRUD를 유지해 위험이 작아요. 다만 "과거 임의 시점의 주문 전체 상태를 재현", "같은 이력으로 여러 분석 화면" 같은 요구가 강하고, 팀이 이벤트 기반 경험이 있다면 **주문 도메인에만** B를 적용하고 회원·상품 같은 나머지는 CRUD로 둬요. 어느 쪽이든 이력에는 칸 변경이 아니라 "고객 요청으로 취소" 같은 **사유와 행위자**를 담아요.

**채점 포인트**: 상태 덮어쓰기의 한계, 이력 테이블(같은 트랜잭션)과 이벤트 소싱 비교, 이벤트 소싱의 비용(프로젝션·최종 일관성·스키마 버전·삭제 요청), 의도(사유·행위자) 기록, 부분 적용(주문만), 팀 역량 고려, CDC는 의도가 안 남음.
</details>

<details>
<summary>상황: 이벤트 소싱으로 만든 계좌 서비스에서 오래된 법인 계좌는 이벤트가 100만 개가 넘어요. 이런 계좌는 잔액 조회와 출금 처리가 몇 초씩 걸려요. 원인과 해결 방법은?</summary>

**상황 파악**
오래되고 거래가 많은 계좌만 느리다면, 요청마다 **이벤트를 처음부터 재생**해 현재 상태를 만드는 비용이 이벤트 수에 비례해 커진 거예요.

**원인 후보**
1. 스냅숏이 없어 매 요청마다 100만 개 이벤트를 읽고 재생함.
2. 잔액 **조회**까지 쓰기 모델(재생)로 처리하고 있음 — 읽기 모델(프로젝션)을 안 씀.
3. 이벤트 저장소에서 계좌별 스트림 읽기가 인덱스를 못 타 느림(확인 필요).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 스냅숏: 이벤트 N개마다 잔액·버전을 저장, 복원은 최신 스냅숏 + 이후 이벤트만 | 출금(명령) 처리 시 재생량이 N 이하로 줄어듦, 원본은 그대로 | 스냅숏 저장 공간·주기 튜닝 필요, 상태 구조가 바뀌면 스냅숏을 다시 만들어야 함 |
| B. 조회는 프로젝션으로: 이벤트를 구독해 `잔액 조회 테이블`을 갱신, 조회 API는 거기서만 읽기 | 조회가 단순 SELECT라 매우 빠르고, 읽기를 따로 확장 가능 | 최종 일관성(이체 직후 잠깐 옛 잔액), 멱등 처리·지연 모니터링 필요 |
| C. 오래된 이벤트 삭제·컴팩션 | 저장소가 가벼워짐 | 이벤트가 원본이라 감사·재생 능력을 잃음 — 사실상 이벤트 소싱 포기 |

**내가 고를 방법**
**A와 B를 함께** 써요. 출금처럼 현재 잔액으로 규칙을 검사해야 하는 명령은 쓰기 모델에서 정확해야 하므로 **스냅숏**으로 재생량을 줄여요. 단순 잔액 조회 화면은 **프로젝션**에서 읽게 해서 재생을 아예 하지 않아요. 이체 직후엔 본인 응답에 새 잔액을 담아 최종 일관성 문제를 가려요. 스냅숏은 캐시일 뿐이라 C처럼 이벤트를 지우지는 않아요. 마지막으로 원인 3(계좌별 스트림 읽기 자체가 느린지)도 확인해요.

**채점 포인트**: 재생 비용이 이벤트 수에 비례, 스냅숏(최신 스냅숏 + 이후 이벤트), 스냅숏은 원본이 아님, 조회는 CQRS 프로젝션으로 분리, 최종 일관성 대응, 명령 처리는 정확한 상태 필요, 이벤트 삭제 금지.
</details>

<details>
<summary>상황: 팀원이 새로 만드는 사내 게시판 서비스를 "확장성을 위해 CQRS + 이벤트 소싱으로 하자"고 제안했어요. 어떻게 판단하겠어요?</summary>

**상황 파악**
판단 기준은 "멋진 구조인가"가 아니라 **이 서비스의 요구가 그 비용을 정당화하는가**예요. 게시판은 글·댓글 CRUD가 대부분이고, 감사·과거 재구성 요구가 있는지부터 확인해야 해요.

**원인 후보(제안이 나온 배경과 실제 요구 확인)**
1. "나중에 커질 수 있다"는 막연한 확장성 걱정 — 실제 예상 트래픽이 사내 규모인지.
2. 글 수정 이력이 필요하다는 요구가 있는지(있다면 이력 테이블로 충분한지).
3. 팀에 이벤트 기반 시스템 운영 경험이 있는지.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 일반 CRUD(관계형 DB) + 필요하면 글 수정 이력 테이블 | 빠르게 만들고 누구나 유지보수, 조회 즉시 일관 | 이력·분석 기능은 따로 만들어야 함 |
| B. 같은 DB에서 코드만 CQRS(쓰기 서비스와 조회 쿼리 분리) | 조회 최적화 쿼리를 따로 다듬기 좋음, 비용 작음 | 구조가 약간 늘어남 |
| C. CQRS + 이벤트 소싱 | 전체 이력·재생·프로젝션 자유 | 프로젝션·최종 일관성("글 썼는데 목록에 없음")·멱등 처리·이벤트 스키마 버전·개인정보 삭제 대응까지 떠안음. 도입도 철회도 비쌈 |

**내가 고를 방법**
**A로 시작하고, 조회가 복잡해지면 B까지만** 하자고 제안하겠어요. 사내 게시판은 단순 CRUD이고, 마틴 파울러와 Azure 문서 모두 이런 경우 CQRS·이벤트 소싱이 위험한 복잡성을 더한다고 경고해요. 특히 이벤트 소싱은 "글 쓰고 목록으로 갔는데 안 보임" 같은 최종 일관성 문제를 사용자 경험에 바로 드러내는데, 게시판은 그걸 감수할 이유가 없어요. 확장성은 읽기 레플리카나 캐시로 먼저 대응할 수 있어요. 대신 팀원의 걱정을 존중해 "수정 이력·감사 요구가 생기면 이력 테이블, 정말 특정 부분에 이력이 원본이어야 하면 그 부분에만 이벤트 소싱"이라는 도입 기준을 같이 정해 둬요.

**채점 포인트**: 요구사항(감사·재생·과거 재구성) 확인, 단순 CRUD엔 과설계, Fowler·Azure 경고, 최종 일관성 사용자 경험 비용, 팀 경험·도입/철회 비용, CQRS는 이벤트 소싱 없이 단계적으로 가능, 확장성은 레플리카·캐시로 먼저, 부분 적용 기준 제시.
</details>

## 필기 포인트

- 이벤트 소싱: 원본 = **추가 전용 이벤트 로그**, 이벤트는 **불변**, 수정은 **보상 이벤트**로.
- 상태 = 이벤트 **재생**(결정적이어야 함). 느리면 **스냅숏**(원본 아님).
- **명령**은 거절 가능한 요청, **이벤트**는 일어난 사실(과거형). 검증은 이벤트 전에.
- **CQRS** = 쓰기 모델/읽기 모델 분리. **이벤트 소싱 없이도 가능**, DB 두 개 필수 아님.
- 이벤트 소싱은 조회가 어려워 보통 CQRS 동반. 읽기 모델 = **프로젝션**(재생으로 재구축 가능).
- 비용: **최종 일관성**, 멱등 처리(at-least-once), 낙관적 동시성, 이벤트 스키마 버전(업캐스팅).
- 개인정보 삭제: "삭제됨" 이벤트로는 해결 안 됨 → 외부 저장 또는 **crypto-shredding**.
- 이벤트 소싱 로그는 **로그 컴팩션 불가**(CDC 로그는 가능).
