:::tip[한 줄 요약]
**멱등**(idempotent)은 같은 요청을 여러 번 보내도 서버에 남는 결과가 한 번 보낸 것과 같은 성질이에요. HTTP에선 GET·PUT·DELETE가 멱등이고 **POST는 아니에요**. 분산 시스템에서는 "DB 저장 + 메시지 발행"을 **outbox 테이블**로 한 트랜잭션에 묶어 유실을 막고, 그 대가로 생기는 중복은 **멱등 소비자**와 **멱등 키**로 막아요.
:::

:::note[처음이라면 여기까지]
① 멱등은 "여러 번 눌러도 한 번 누른 것과 같다"예요. 엘리베이터 버튼이 멱등, 자판기 버튼은 멱등이 아니에요.

② HTTP에서 PUT(덮어쓰기)·DELETE(지우기)·GET(읽기)은 멱등이고, POST(새로 만들기)는 멱등이 아니에요. 헷갈리기 쉬우니 표로 외워 두세요.

③ "DB에 저장하고 메시지도 보내기"를 따로 하면 하나만 성공할 수 있어요. 그래서 보낼 메시지를 같은 DB에 먼저 적어 두는 게 outbox 패턴이에요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

엘리베이터에서 "5층" 버튼을 다섯 번 눌러도 엘리베이터는 5층에 한 번 서요. 처음 한 번만 효과가 있고, 나머지는 결과를 바꾸지 않아요. 이게 **멱등**이에요.

자판기 버튼은 달라요. 돈이 충분하면 누를 때마다 음료가 하나씩 더 나와요. 같은 버튼이라도 누른 횟수만큼 결과가 쌓이니까 **멱등이 아니에요**.

왜 이게 중요할까요? 인터넷은 자주 끊겨요. "결제" 버튼을 눌렀는데 화면이 멈추면, 결제가 됐는지 안 됐는지 몰라서 다시 누르게 되죠. 결제가 엘리베이터 버튼처럼 동작하면 안심하고 다시 눌러도 되지만, 자판기 버튼처럼 동작하면 돈이 두 번 빠져요.

그래서 백엔드 개발자는 "다시 보내도 괜찮은" 구조를 일부러 만들어요. 이 페이지의 outbox, 멱등 소비자, 멱등 키가 전부 그 도구예요.

단, 실제 정의는 비유보다 좁아요. 멱등은 **서버에 남는 결과**(요청이 의도한 효과)만 따져요. 응답 메시지는 매번 달라도 돼요.

## 제대로 알기

### 멱등의 정확한 정의

HTTP 명세(RFC 9110)는 이렇게 정해요. **같은 요청을 여러 번 보냈을 때 서버에 의도한 효과가 한 번 보낸 것과 같으면** 그 메서드는 멱등이에요.

여기서 두 가지를 꼭 기억하세요.

- **응답은 달라도 돼요.** 글을 DELETE하면 첫 번째는 성공(200/204), 두 번째는 "없음"(404)이 올 수 있어요. 그래도 서버 상태는 둘 다 "글 없음"이라 멱등이에요.
- **요청한 효과만 따져요.** 서버가 요청마다 접속 로그를 한 줄씩 남기는 건 상관없어요.

| 메서드 | 하는 일 | 멱등? | 안전? | 여러 번 보내면 |
|---|---|---|---|---|
| GET | 읽기 | O | O | 읽기만 하니 상태가 안 바뀜 |
| PUT | 통째로 덮어쓰기 | O | X | "이름=김토스"로 몇 번 덮어써도 결과는 같음 |
| DELETE | 지우기 | O | X | 첫 번째에 지워지고, 그 뒤엔 계속 "없음" |
| POST | 새로 만들기·처리 요청 | **X** | X | 보낼 때마다 주문·결제가 하나씩 더 생길 수 있음 |
| PATCH | 일부 수정 | 보장 안 됨 | X | "포인트 +100" 같은 수정이면 쌓임 |

**안전**(safe)은 "서버 상태를 바꿔 달라고 하지 않는 읽기 전용"이라는 뜻이에요. GET, HEAD, OPTIONS, TRACE가 안전해요. 안전한 메서드는 모두 멱등이지만, 거꾸로는 아니에요. PUT·DELETE는 상태를 바꾸니까 안전하진 않지만 멱등이에요.

### 왜 멱등을 따지나: 재시도

응답을 받기 전에 연결이 끊기면, 클라이언트는 요청이 처리됐는지 알 수 없어요. 이때 멱등 요청은 그냥 다시 보내도 결과가 같으니 **자동 재시도**해도 돼요.

비멱등 요청(POST)은 클라이언트가 함부로 자동 재시도하면 안 되고, 중간의 **프록시**(클라이언트와 서버 사이에서 요청을 대신 전달하는 서버)는 절대 자동 재시도하면 안 된다고 명세에 적혀 있어요. → [장애 대응 패턴](../../architecture/resilience/)에서 "재시도는 멱등 요청만"이라고 하는 이유예요.

<Aside type="caution" title="메서드 이름이 멱등을 보장하진 않아요">
멱등은 명세상의 약속이에요. `PUT /counter`가 호출될 때마다 +1 하도록 만들면 멱등이 깨져요(명세 위반). 반대로 POST라도 아래의 **멱등 키**를 쓰면 멱등하게 만들 수 있어요.
</Aside>

일반 연산으로 보면 `x = 5`(값을 정해 넣기)는 멱등이고 `x = x + 1`(늘리기)은 멱등이 아니에요. 늘리기 같은 연산도 **"이 연산 ID는 이미 처리했음"이라는 기록을 같이 저장**하면 멱등하게 만들 수 있어요. 이 아이디어가 이 페이지 뒷부분 전체의 핵심이에요.

### 이중 쓰기 문제

주문 서비스가 주문을 DB에 저장하고, "주문 생성됨" 이벤트를 **메시지 브로커**(Kafka처럼 서비스끼리 메시지를 전달해 주는 우체국)로 보내야 한다고 해 봐요. → [메시지 큐와 Kafka](../message-queue-kafka/)

DB와 브로커는 서로 다른 시스템이라 하나의 **트랜잭션**(여러 작업을 "전부 반영(커밋) 아니면 전부 취소(롤백)"로 묶는 단위)으로 묶이지 않아요. 둘을 묶는 **2PC**(2단계 커밋, 여러 시스템이 함께 커밋하는 프로토콜)는 대개 브로커 쪽에서 쓸 수 없거나, 쓸 수 있어도 피하는 선택이에요. 그래서 따로 쓰면(**이중 쓰기**, dual write) 둘이 어긋날 수 있어요.

| 순서 | 실패 지점 | 결과 |
|---|---|---|
| DB 커밋 → 발행 | 커밋 후 발행 전에 서버 다운, 브로커 장애 | **이벤트 유실**: 주문은 있는데 결제·배송 서비스가 모름 |
| 발행 → DB 커밋 | 발행 후 DB가 롤백 | **유령 이벤트**: 없는 주문에 대한 이벤트가 나감 |

어느 순서로 해도 한쪽만 성공하는 틈이 남아요.

### 트랜잭셔널 아웃박스

해법은 단순해요. 메시지를 바로 보내지 말고, **보낼 메시지를 업무 데이터와 같은 DB 트랜잭션에서 `outbox` 테이블에 적어 둬요.**

```sql
BEGIN;
INSERT INTO orders (id, user_id, amount) VALUES (101, 7, 30000);
-- 보낼 메시지를 같은 트랜잭션에 기록
INSERT INTO outbox (id, aggregate_type, aggregate_id, type, payload)
VALUES ('uuid-1', 'order', '101', 'OrderCreated', '{"amount":30000}');
COMMIT;  -- 둘 다 저장되거나, 둘 다 취소됨
```

그다음 **메시지 릴레이**(outbox를 읽어 브로커로 옮기는 별도 프로세스)가 새 행을 찾아 발행해요.

- 2PC가 필요 없어요. 같은 DB 안의 트랜잭션 하나면 돼요.
- **커밋된 경우에만** 메시지가 나가요. 롤백되면 outbox 행도 없으니 유령 이벤트가 없어요.
- 커밋됐으면 outbox 행이 남아 있으니, 서버가 죽어도 릴레이가 나중에 보내요. 유실이 없어요.
- 앱이 기록한 순서대로 발행할 수 있어요.

### Outbox는 "최소 한 번"이에요

릴레이가 메시지를 보낸 직후, "보냈음"을 기록하기 전에 죽으면 어떻게 될까요? 재시작한 릴레이는 그 행을 아직 안 보낸 걸로 보고 **또 보내요**.

그래서 outbox가 보장하는 건 **최소 한 번**(at-least-once, 빠짐없이 가지만 두 번 갈 수도 있음) 전달이에요. "정확히 한 번"이 아니에요. 게다가 브로커 자체도 장애 후 메시지를 다시 보내요. 그래서 **받는 쪽이 멱등해야** 해요. outbox와 멱등 소비자는 짝꿍이에요.

### 멱등 소비자

받은 메시지의 ID를 **처리 기록 테이블**에 적고, 이미 있으면 건너뛰어요.

```sql
CREATE TABLE processed_message (
  consumer_id VARCHAR(50),
  message_id  VARCHAR(100),
  PRIMARY KEY (consumer_id, message_id)  -- 같은 메시지는 한 번만 들어감
);

BEGIN;
INSERT INTO processed_message VALUES ('point-svc', 'm-1'); -- 중복이면 여기서 실패
UPDATE account SET balance = balance - 3000 WHERE id = 1;
COMMIT;
```

핵심은 두 가지예요.

1. **"ID 기록"과 "업무 변경"을 같은 트랜잭션**에 넣어요. 따로 하면 차감만 되고 기록이 안 되는 틈이 생겨요.
2. **SELECT로 먼저 확인하지 말고 유니크 제약에 맡겨요.** 두 소비자가 동시에 "없네?"를 보고 둘 다 처리할 수 있기 때문이에요. DB의 유니크 제약은 동시에 들어와도 하나만 통과시켜요.

실험 예시로 MySQL에서 한 번 돌려 보면 이래요.

| 단계 | 결과 | 잔액 |
|---|---|---|
| 처음 | — | 10000 |
| `m-1` 첫 처리(INSERT + 3000 차감, COMMIT) | 성공 | 7000 |
| 같은 `m-1` 다시 INSERT | `ERROR 1062 (23000): Duplicate entry ... for key 'processed_message.PRIMARY'` → ROLLBACK | **7000 그대로** |

`INSERT IGNORE`를 쓰면 오류 대신 "영향받은 행 0개"(`ROW_COUNT()` = 0)가 나와서, 그걸 보고 중복인지 판단할 수도 있어요.

### 결제 API의 멱등 키

메시지뿐 아니라 API 호출에서도 같은 문제가 생겨요. 앱이 결제 요청(POST)을 보냈는데 응답이 안 오면, 다시 보내야 할지 알 수 없어요.

**멱등 키**(idempotency key)는 클라이언트가 결제 시도마다 고유한 값(보통 UUID, 겹칠 일이 사실상 없는 무작위 ID)을 만들어 `Idempotency-Key` 헤더에 실어 보내는 방식이에요. 서버는 키별로 처음 처리한 결과를 저장해 두고, 같은 키가 다시 오면 **결제를 또 하지 않고 저장해 둔 응답을 그대로 돌려줘요.**

키는 **클라이언트가 만들어야** 해요. 서버가 만들면 응답을 못 받은 클라이언트는 그 키를 모르니 재시도 때 같은 키를 보낼 수 없어요.

<Aside type="note" title="표준인가요?">
`Idempotency-Key` 헤더는 IETF에서 **표준화가 진행 중인 초안**이에요(2026-11 확인 기준 아직 RFC 아님). 다만 Stripe 같은 결제 API가 이미 이 방식을 쓰고 있어요.
</Aside>

### 심화: 폴링 vs CDC(Debezium)

메시지 릴레이를 만드는 방법은 두 가지예요.

| | 폴링 발행기(polling publisher) | 트랜잭션 로그 테일링(CDC) |
|---|---|---|
| 방식 | 주기적으로 `SELECT ... FROM outbox WHERE 미발행` | DB 변경 로그(MySQL binlog, PostgreSQL WAL)를 읽어 outbox INSERT를 발행 |
| 장점 | 어떤 SQL DB에서도 됨, 이해하기 쉬움 | 테이블을 반복 조회하지 않음, 커밋된 변경을 그대로 따라감 |
| 단점 | 폴링 주기만큼 늦음, 잦은 조회가 DB 부하, 순서대로 발행하기 까다로움 | DB마다 다른 도구 필요, 운영이 낯섦, 중복 발행 회피가 까다로움 |
| 발행 완료 기록 | outbox 행에 "보냄" 표시하거나 삭제 | 로그를 어디까지 읽었는지(오프셋) 저장 |

**CDC**(Change Data Capture, DB 변경을 잡아 밖으로 흘려보내기)의 대표 도구가 **Debezium**이에요. Debezium의 Outbox Event Router는 outbox 테이블 변경을 메시지로 바꿔 줘요.

- 기본 컬럼: `id`(UUID), `aggregatetype`, `aggregateid`, `type`, `payload`
- 기본 토픽 이름: `outbox.event.` 뒤에 `aggregatetype` 값(예: `outbox.event.customers`)
- `id`가 메시지 헤더에 실려서, 소비자가 이 값으로 중복을 걸러낼 수 있어요.

어느 쪽이든 outbox 테이블은 계속 커지니, 발행된 행을 주기적으로 지우는 정리 작업이 필요해요.

### 심화: 멱등 키의 세부 규칙

**Stripe API(v1) 문서 기준**이에요.

- 모든 POST 요청에 멱등 키를 붙일 수 있어요. GET·DELETE는 원래 멱등이라 키를 보내도 효과가 없어요.
- 키는 클라이언트가 만들고(V4 UUID 권장) 최대 255자예요. 이메일 같은 민감 정보를 키로 쓰면 안 돼요.
- 처리가 시작된 첫 요청의 **상태코드와 본문을 저장**하고, 같은 키엔 그대로 돌려줘요. **500 오류였어도** 그대로 돌려줘요.
- 같은 키인데 파라미터가 다르면 오류를 돌려줘요.
- 검증 실패나 동시 요청 충돌로 처리가 아예 시작되지 않았다면 저장하지 않으니, 같은 키로 다시 시도할 수 있어요.
- 키는 **최소 24시간이 지나면** 지워질 수 있고, 지워진 뒤 같은 키는 새 요청으로 처리돼요.

**IETF 초안 기준**(표준화 진행 중)이에요.

| 상황 | 응답 |
|---|---|
| 첫 요청이 아직 처리 중인데 같은 키로 재시도 | 409 Conflict |
| 같은 키로 다른 내용(예: 금액이 다름) | 422 Unprocessable Content |
| 키가 필수인 API인데 키가 없음 | 400 Bad Request |

키를 얼마나 보관할지는 서버가 정해서 문서로 알려야 해요. 초안은 기간을 정해 두지 않아요.

### 심화: 유니크 제약에 맡겨야 하는 이유

"이미 처리했나 SELECT → 없으면 INSERT"는 앱 코드로 한 번 확인하는 방식이에요. 격리 수준이 직렬성보다 약하면, 두 트랜잭션이 동시에 "없음"을 보고 둘 다 처리할 수 있어요(쓰기 스큐·팬텀 계열 문제).

반면 관계형 DB의 유니크 제약은 약한 격리 수준에서도 정확히 지켜져요. 그래서 중복 방지의 최종 방어선은 **유니크 키**예요.

또 중요한 점은 이 ID가 **사용자 쪽에서부터 끝까지** 같이 다녀야 한다는 거예요. TCP가 패킷 중복을 걸러 주고 DB가 트랜잭션을 보장해도, 사용자가 타임아웃 후 버튼을 다시 누르면 그건 "새 요청"으로 들어와요. 처음 요청을 만든 곳에서 ID를 붙여 DB까지 들고 가야 이 재제출까지 막을 수 있어요(종단 간 논증).

<Aside type="tip" title="분산 락과 헷갈리지 마세요">
[분산 락](../../redis/distributed-lock/)은 "동시에" 실행되는 걸 막고, 멱등은 "다시" 실행돼도 결과가 같게 해요. 락이 만료된 뒤 재전달된 메시지는 락으로 못 막아요. 최종 방어는 유니크 키예요. (일반적인 설계 지식)
</Aside>

### 심화: @TransactionalEventListener(AFTER_COMMIT)의 한계

스프링의 `@TransactionalEventListener`(Spring 4.2부터)는 이벤트 리스너를 트랜잭션 단계에 묶어요. 단계는 `BEFORE_COMMIT`, `AFTER_COMMIT`(기본값), `AFTER_ROLLBACK`, `AFTER_COMPLETION`이에요.

```java
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    events.publishEvent(new OrderCreated(order.getId())); // 메모리에만 있음
}

@TransactionalEventListener // 기본 AFTER_COMMIT
public void on(OrderCreated e) {
    kafka.send("orders", e); // 여기서 실패하거나 직전에 서버가 죽으면?
}
```

- **막는 것**: 커밋된 뒤에만 실행되니, 롤백된 주문의 유령 이벤트는 안 나가요.
- **못 막는 것**: 이벤트가 메모리에만 있어요. 커밋 직후 서버가 죽거나 Kafka 발행이 실패하면 이벤트는 사라지고, 이미 끝난 커밋은 되돌릴 수 없어요. 즉 **유실 문제는 그대로**예요.
- **트랜잭션 밖에서 발행하면** 리스너가 아예 호출되지 않고 이벤트가 버려져요(`fallbackExecution = true`로 바꿀 수 있음).
- **리스너 안에서 DB를 바꾸면** 커밋되지 않는다고 Javadoc이 경고해요. 트랜잭션은 끝났는데 자원은 남아 있어서, 원래 트랜잭션에 참여한 것처럼 보이지만 반영이 안 돼요. 실무에선 `REQUIRES_NEW`로 새 트랜잭션을 여는 식으로 피해요(일반적인 회피법).

그래서 놓치면 안 되는 이벤트(결제, 정산)는 이벤트를 DB에 같이 저장하는 **outbox**로 가요. 리스너 방식은 놓쳐도 큰일이 아닌 알림 정도에 써요.

### 심화: 자주 하는 오해

- **"Kafka exactly-once 켰으니 소비자 멱등은 필요 없다"** → Kafka의 보장은 Kafka 안쪽 처리 구간 이야기예요. 외부 DB 쓰기나 외부 API 호출까지 포함한 중복은 앱이 막아야 해요.
- **"processed_message는 영원히 쌓아 둔다"** → 무한히 커져요. 메시지가 재전달될 수 있는 기간보다 넉넉히 보관하고 주기적으로 지워요(일반적인 운영 방법).

## 면접 질문

<details>
<summary>Q. 멱등성이 뭔가요? 멱등한 HTTP 메서드는 무엇이고, POST는 왜 아닌가요?</summary>

**답변(30초)**
멱등성은 같은 요청을 여러 번 보내도 서버에 남는 결과가 한 번 보낸 것과 같은 성질이에요. HTTP에선 GET, HEAD, OPTIONS 같은 읽기 메서드와 PUT, DELETE가 멱등이에요. POST는 보낼 때마다 주문이나 결제처럼 새 자원이 생길 수 있어서 멱등이 아니에요. 멱등이면 네트워크가 끊겼을 때 안심하고 재시도할 수 있어서 중요해요.

**꼬리질문**
- Q. DELETE를 두 번 하면 두 번째는 404인데 멱등인가요? → 네. 멱등은 응답이 아니라 서버 상태를 봐요. 두 번 다 "없음" 상태라 멱등이에요.
- Q. PATCH는요? → 명세상 멱등이 보장되지 않아요. "포인트 +100" 같은 수정이면 쌓이니까요.
</details>

<details>
<summary>Q. PUT과 POST의 차이를 멱등 관점에서 설명해 주세요.</summary>

**답변(30초)**
PUT은 대상을 보낸 내용으로 통째로 덮어써서, 몇 번 보내도 최종 상태가 같아 멱등이에요. POST는 서버에 처리나 생성을 요청하는 것이라 보낼 때마다 새 결과가 생길 수 있어 멱등이 아니에요. 그래서 PUT은 실패 시 자동 재시도가 가능하지만 POST는 함부로 재시도하면 중복이 생겨요. 다만 이건 명세의 약속이라, 구현이 지켜야 멱등이에요.

**꼬리질문**
- Q. POST를 멱등하게 만들 수는 없나요? → 클라이언트가 멱등 키를 보내고 서버가 키별로 결과를 저장하면 같은 키의 재요청을 한 번으로 처리할 수 있어요.
- Q. PUT인데 멱등이 깨지는 경우는? → `PUT /counter`가 +1 하도록 구현하면 깨져요. 명세 위반이에요.
</details>

<details>
<summary>Q. 안전한 메서드와 멱등 메서드는 어떻게 다른가요?</summary>

**답변(30초)**
안전은 서버 상태를 바꾸지 않는 읽기 전용이라는 뜻이고, 멱등은 여러 번 해도 결과가 같다는 뜻이에요. 안전한 메서드(GET, HEAD, OPTIONS, TRACE)는 상태를 안 바꾸니 자연히 멱등이에요. 하지만 PUT과 DELETE는 상태를 바꾸니 안전하진 않지만, 반복해도 결과가 같아 멱등이에요. 즉 안전은 멱등의 부분집합이에요.

**꼬리질문**
- Q. GET 요청마다 서버가 로그를 남기면 안전하지 않은 건가요? → 아니요. 사용자가 요청한 효과만 따지고, 서버가 스스로 남기는 로그는 상관없어요.
</details>

<details>
<summary>Q. 사용자가 결제 버튼을 두 번 누르거나, 타임아웃 후 앱이 재시도하면 중복 결제를 어떻게 막나요?</summary>

**답변(30초)**
멱등 키로 막아요. 앱이 결제 시도마다 UUID를 만들어 `Idempotency-Key` 헤더로 보내고, 서버는 키별로 처리 결과를 저장해요. 같은 키가 다시 오면 결제를 또 하지 않고 저장된 응답을 돌려줘요. 키 저장은 유니크 제약으로 해서 동시에 두 요청이 와도 하나만 처리되게 해요.

**꼬리질문**
- Q. 키는 누가 만들어요? → 클라이언트요. 응답을 못 받은 클라이언트가 재시도 때 같은 키를 보내야 하니까요.
- Q. 첫 요청이 아직 처리 중인데 같은 키가 오면요? → IETF 초안에선 409 Conflict로 거절해요. 키는 같은데 금액이 다르면 422예요.
- Q. 키는 얼마나 보관하나요? → 서버가 정해서 문서화해요. Stripe는 최소 24시간 뒤 정리될 수 있다고 안내해요.
</details>

<details>
<summary>Q. DB 저장과 메시지 발행을 함께 해야 할 때 어떤 문제가 생기고, 어떻게 해결하나요?</summary>

**답변(30초)**
DB와 브로커는 한 트랜잭션으로 묶이지 않아서 이중 쓰기 문제가 생겨요. DB 커밋 후 발행 전에 죽으면 이벤트가 유실되고, 먼저 발행하고 DB가 롤백되면 없는 데이터의 이벤트가 나가요. 해결은 트랜잭셔널 아웃박스예요. 보낼 메시지를 업무 데이터와 같은 트랜잭션에서 outbox 테이블에 저장하고, 별도 릴레이가 읽어서 발행해요. 그러면 커밋된 것만, 빠짐없이 나가요.

**꼬리질문**
- Q. 2PC로 묶으면 안 되나요? → 메시지 브로커와 DB를 2PC로 묶는 건 대개 지원되지 않거나 원치 않는 선택이에요. outbox는 같은 DB 안의 트랜잭션 하나로 끝나요.
- Q. outbox 테이블이 계속 커지면요? → 발행된 행을 지우거나 주기적으로 정리해요.
</details>

<details>
<summary>Q. Outbox 패턴을 쓰면 메시지가 정확히 한 번 전달되나요?</summary>

**답변(30초)**
아니요, 최소 한 번이에요. 릴레이가 발행한 뒤 "보냈음"을 기록하기 전에 죽으면 재시작 후 같은 메시지를 또 보내요. 브로커도 장애 후 재전달을 해요. 그래서 outbox는 유실을 막는 장치이고, 중복은 소비자가 메시지 ID로 걸러내는 멱등 소비자로 막아야 해요.

**꼬리질문**
- Q. 소비자는 무엇으로 중복을 판단하나요? → outbox 행의 id를 메시지 헤더에 실어 보내고, 그 값을 처리 기록 테이블에 저장해요.
</details>

<details>
<summary>Q. 최소 한 번 전달 환경에서 중복 메시지를 어떻게 처리하나요?</summary>

**답변(30초)**
멱등 소비자로 만들어요. 처리한 메시지 ID를 테이블에 넣는데, (소비자, 메시지 ID)를 기본 키로 둬요. ID 기록과 업무 처리를 한 트랜잭션에 넣어서, 이미 처리한 메시지면 INSERT가 키 중복으로 실패하고 롤백한 뒤 그냥 넘겨요. 처음이면 업무 처리까지 같이 커밋해요.

**꼬리질문**
- Q. 왜 SELECT로 먼저 확인하지 않나요? → 동시에 두 소비자가 "없음"을 보고 둘 다 처리할 수 있어요. 유니크 제약은 동시에 와도 하나만 통과시켜요.
- Q. ID 기록과 업무 처리를 따로 커밋하면요? → 기록만 되고 처리가 빠지거나, 처리만 되고 기록이 빠지는 틈이 생겨요.
</details>

<details>
<summary>Q. Outbox 릴레이는 어떻게 구현하나요? 폴링과 CDC를 비교해 주세요.</summary>

**답변(30초)**
폴링은 주기적으로 outbox 테이블에서 미발행 행을 조회해 발행해요. 어떤 SQL DB에서도 되고 단순하지만, 주기만큼 늦고 잦은 조회가 DB에 부하를 줘요. CDC는 MySQL binlog 같은 변경 로그를 Debezium 같은 도구로 읽어 발행해요. 조회 부하가 없고 지연이 짧지만 DB별 도구와 운영 부담이 생겨요. 트래픽이 적으면 폴링, 많으면 CDC를 고려해요.

**꼬리질문**
- Q. 둘 다 중복은 생기나요? → 네. 폴링은 발행 후 표시 전 다운, CDC는 오프셋 저장 전 다운으로 재발행돼요. 그래서 소비자 멱등은 둘 다 필요해요.
</details>

<details>
<summary>Q. @TransactionalEventListener(AFTER_COMMIT)로 Kafka에 발행하면 충분한가요?</summary>

**답변(30초)**
유령 이벤트는 막지만 유실은 못 막아요. 커밋 후에만 실행되니 롤백된 데이터의 이벤트는 안 나가요. 하지만 이벤트가 메모리에만 있어서 커밋 직후 서버가 죽거나 발행이 실패하면 사라지고, 이미 커밋된 건 되돌릴 수 없어요. 놓치면 안 되는 이벤트라면 outbox로 이벤트를 DB에 같이 저장해야 해요.

**꼬리질문**
- Q. 리스너 안에서 DB를 업데이트했는데 반영이 안 돼요. 왜죠? → AFTER_COMMIT 시점엔 트랜잭션이 이미 끝나서 변경이 커밋되지 않아요. `REQUIRES_NEW`로 새 트랜잭션을 열어야 해요.
- Q. 트랜잭션 없이 이벤트를 발행하면? → 리스너가 호출되지 않고 버려져요. `fallbackExecution = true`로 바꿀 수 있어요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제가 완료되면 "결제 완료" 이벤트를 Kafka로 보내 배송 서비스가 받아요. 그런데 가끔 결제는 DB에 완료로 남아 있는데 배송이 시작되지 않은 건이 생겨요. 주로 배포 시간대에 몰려요. 원인과 해결 방법은?</summary>

**상황 파악**
결제 데이터는 있는데 이벤트만 없어요. 배포(서버 재시작) 시간대에 몰린다는 건, DB 커밋과 이벤트 발행 사이에 서버가 내려간 경우로 보여요. 즉 **이중 쓰기로 인한 이벤트 유실**이에요.

**원인 후보**
1. 결제 커밋 후 `kafka.send()` 전에 프로세스가 종료됨(배포 재시작).
2. `@TransactionalEventListener(AFTER_COMMIT)`로 발행 중인데, 이벤트가 메모리에만 있어서 종료 시 사라짐.
3. 브로커 일시 장애로 발행이 실패했는데 재시도 없이 로그만 남기고 끝남.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 트랜잭셔널 아웃박스 + 폴링 릴레이 | 결제와 이벤트가 한 트랜잭션, 유실 없음, 어떤 DB에서나 구현 가능 | 폴링 주기만큼 지연, outbox 정리 필요, 중복 발행 가능 |
| B. 아웃박스 + CDC(Debezium) | 조회 부하 없이 지연 짧음 | Kafka Connect·Debezium 운영 부담, DB별 설정 |
| C. 발행 실패 시 재시도만 추가 | 코드 변경 최소 | 프로세스가 죽는 경우엔 재시도할 주체가 없어서 못 막음 |
| D. 정기 배치로 "결제 완료인데 배송 없음" 대사 | 기존 구조 유지, 최후의 안전망 | 늦게 발견, 근본 해결 아님 |

**내가 고를 방법**
A로 시작해요. 결제 완료 행과 outbox 행을 같은 트랜잭션에 넣으면 "결제는 됐는데 이벤트가 없는" 상태가 구조적으로 사라져요. 트래픽이 커져 폴링 부하가 문제 되면 B로 옮겨요. 어느 쪽이든 발행이 최소 한 번이라 **배송 서비스는 outbox id로 중복을 거르는 멱등 소비자**로 만들어요. D는 안전망으로 같이 둬요. C만으로는 배포 중 종료를 못 막아서 고르지 않아요.

**채점 포인트**: 이중 쓰기 진단, DB와 브로커는 한 트랜잭션 불가(2PC 회피 이유), outbox 같은 트랜잭션 저장, 릴레이(폴링/CDC) 트레이드오프, AFTER_COMMIT 리스너 한계, 최소 한 번 → 소비자 멱등, outbox 정리.
</details>

<details>
<summary>상황: 모바일 앱에서 결제 요청이 타임아웃되자 앱이 자동으로 다시 요청했고, 고객 카드에서 같은 금액이 두 번 승인됐어요. 클라이언트와 서버는 각각 무엇을 바꿔야 할까요?</summary>

**상황 파악**
첫 요청은 서버에서 실제로 처리됐는데 응답만 늦거나 끊겼어요. 앱은 실패로 보고 같은 POST를 다시 보냈고, 서버는 그걸 새 결제로 처리했어요. **비멱등 요청(POST)을 재시도해서 생긴 중복**이에요.

**원인 후보**
1. 서버가 "같은 결제 시도"를 구분할 식별자가 없음.
2. 앱의 자동 재시도가 POST에도 적용됨.
3. 사용자가 버튼을 연타해도 같은 문제가 생길 수 있음.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 멱등 키: 앱이 결제 시도마다 UUID 생성해 `Idempotency-Key`로 전송, 서버는 키별 결과 저장 후 같은 키엔 저장된 응답 반환 | 재시도·연타 모두 해결, 재시도 자체는 안전하게 허용 | 키 저장소와 보관 정책 필요, 처리 중 재요청(409)·다른 내용(422) 처리 구현 |
| B. 주문번호에 유니크 제약을 걸고 결제는 주문당 1회만 | 구현 간단, DB가 보장 | 한 주문에 부분 결제·재결제가 필요하면 안 맞음, 응답 재현은 따로 구현 |
| C. 앱의 POST 자동 재시도 끄기 | 즉시 적용 | 사용자가 다시 누르는 건 못 막음, 실패 시 사용자 경험 나쁨 |

**내가 고를 방법**
A를 골라요. **클라이언트**는 결제 화면에 들어올 때(시도 단위로) 키를 만들고, 재시도할 땐 반드시 같은 키를 보내요. **서버**는 키를 유니크 제약이 있는 테이블에 넣어 동시에 두 요청이 와도 하나만 처리하고, 처리 결과(상태코드와 본문)를 저장해 재요청에 그대로 돌려줘요. 처리 중 재요청은 409, 같은 키에 다른 금액이면 422로 거절해요. 키 보관 기간은 앱의 재시도 기간보다 길게 잡고 문서화해요. B는 주문당 결제가 1회인 구조라면 보조 방어선으로 같이 둬요.

**채점 포인트**: POST 비멱등·재시도 원인, 클라이언트가 키 생성(시도 단위), 서버 결과 저장·같은 응답 반환, 유니크 제약으로 동시 요청 방어, 처리 중(409)·파라미터 불일치(422), 키 보관 기간, IETF 초안(표준화 진행 중)·Stripe 사례.
</details>

<details>
<summary>상황: 포인트 서비스가 "결제 완료" 이벤트를 받아 포인트를 적립하는데, 같은 결제에 포인트가 두 번 적립된 고객이 나왔어요. 로그를 보니 같은 메시지 ID가 두 번 소비됐어요. 원인과 해결 방법은?</summary>

**상황 파악**
같은 메시지가 두 번 왔고 소비자가 두 번 다 처리했어요. Kafka 같은 브로커와 outbox 릴레이는 **최소 한 번 전달**이라 중복은 정상적으로 생길 수 있어요. 문제는 **소비자가 멱등하지 않은 것**이에요.

**원인 후보**
1. 포인트 적립 후 브로커에 처리 완료(오프셋 커밋/ack)를 알리기 전에 소비자가 죽거나 재배치되어 재전달됨.
2. outbox 릴레이가 발행 후 기록 전에 재시작해 같은 메시지를 다시 발행함.
3. 중복 확인을 SELECT 후 INSERT로 해서 동시 처리 시 둘 다 통과함.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `processed_message(consumer_id, message_id)` PK 테이블 + 적립과 같은 트랜잭션 | 어떤 업무에도 적용, DB가 동시 중복까지 막음 | 테이블이 계속 커져 보관·삭제 정책 필요 |
| B. 적립 내역 테이블에 `payment_id` 유니크 제약 | 테이블 추가 없음, 업무 의미가 분명 | 업무마다 따로 설계, 1:1이 아닌 업무엔 안 맞음 |
| C. "포인트 +100" 대신 "결제 X의 적립액 = 100"처럼 값을 정해 넣는 연산으로 바꾸기 | 연산 자체가 멱등 | 모든 업무를 이렇게 바꾸긴 어려움 |

**내가 고를 방법**
A를 기본으로 해요. 메시지를 받으면 트랜잭션을 열고 메시지 ID를 먼저 INSERT해요. 중복이면 키 위반으로 실패하니 롤백하고 ack만 보내요. 처음이면 같은 트랜잭션에서 적립하고 커밋해요. 실험해 보면 두 번째 INSERT가 `ERROR 1062`로 막히고 잔액은 그대로예요. 포인트처럼 결제 1건당 적립 1건인 업무는 B도 같이 걸어 이중 방어해요. 처리 기록은 재전달될 수 있는 기간보다 넉넉히 보관한 뒤 지워요. 이미 두 번 적립된 고객은 처리 기록과 적립 내역을 대조해 회수해요.

**채점 포인트**: 최소 한 번 전달(중복은 정상), ack 전 다운·리밸런싱·릴레이 재발행, 처리 ID 테이블, ID 기록과 업무 변경 같은 트랜잭션, SELECT 확인이 아니라 유니크 제약, 보관 기간, 이미 생긴 중복 보정.
</details>

## 필기 포인트

- 멱등 = 반복해도 **서버에 의도한 효과**가 같음. **응답은 달라도 됨**(DELETE 두 번째 404도 멱등).
- 멱등 메서드: GET, HEAD, OPTIONS, TRACE, **PUT, DELETE**. **POST·PATCH는 멱등 아님**(보장 없음).
- 안전 메서드: GET, HEAD, OPTIONS, TRACE. **안전 ⊂ 멱등**. PUT·DELETE는 멱등이지만 안전 아님.
- 비멱등 요청은 프록시가 자동 재시도하면 안 됨(MUST NOT).
- Outbox = 업무 데이터 + 메시지를 **같은 로컬 트랜잭션**에 저장, 릴레이가 발행. 2PC 불필요. 보장은 **최소 한 번**.
- 릴레이: 폴링 발행기 / 트랜잭션 로그 테일링(CDC, Debezium).
- 멱등 소비자: 처리한 메시지 ID + **유니크 제약**, 업무 변경과 **같은 트랜잭션**.
- `@TransactionalEventListener` 기본 단계 = `AFTER_COMMIT`. 트랜잭션 없으면 이벤트 버려짐.
