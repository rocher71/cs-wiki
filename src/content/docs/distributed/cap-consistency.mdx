:::tip[한 줄 요약]
**CAP 정리**는 "데이터를 여러 서버에 복제한 시스템에서 **네트워크가 끊겨 서버들이 갈라지면**, 항상 최신 값을 보여 주는 **일관성(C)**과 모든 요청에 답하는 **가용성(A)** 중 하나는 포기해야 한다"는 뜻이에요. "C·A·P 중 2개 고르기"가 아니에요. 분할이 없는 평소에는 **빠른 응답(지연, L)과 일관성(C)** 사이에서 고르는데, 이걸 함께 말하는 게 **PACELC**예요.
:::

:::note[처음이라면 여기까지]
① 서버를 여러 대 두면 서버끼리 연결이 끊길 수 있어요. 그때 "모르니까 답을 안 할래(C)"와 "옛날 값이라도 답할래(A)" 중 하나를 골라야 해요. 이게 CAP예요.

② "3개 중 2개를 고른다"는 흔한 설명은 틀려요. 네트워크가 끊기는 건 고르는 게 아니라 그냥 일어나는 일이에요.

③ 실무에선 데이터마다 다르게 골라요. 잔액은 정확해야 하니 C, 좋아요 수는 잠깐 틀려도 되니 A 쪽이에요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

은행 지점이 **서울점과 부산점** 두 곳 있다고 해 봐요. 두 지점은 전화선으로 장부를 계속 맞춰요. 서울에서 입금하면 바로 부산에 전화해서 "김 고객 잔액 바뀌었어요"라고 알려 줘요.

어느 날 **전화선이 끊겼어요**. 두 지점 모두 문은 열려 있어요. 서울점에서 김 고객이 돈을 뽑았는데, 부산점은 그 사실을 몰라요. 이때 부산점에 김 고객의 가족이 와서 "잔액 얼마예요?"라고 물어요.

부산점이 할 수 있는 건 두 가지뿐이에요.

- **"지금은 확인이 안 돼서 알려 드릴 수 없어요"** → 틀린 답은 안 주지만 손님을 돌려보내요. 이게 **일관성(C) 선택**이에요.
- **"제 장부로는 100만 원이에요"** → 손님은 답을 받지만 옛날 값일 수 있어요. 이게 **가용성(A) 선택**이에요.

전화선이 멀쩡할 땐 둘 다 할 수 있어요. 다만 매번 전화로 확인하고 답하면 느리고, 확인 없이 바로 답하면 빠르지만 잠깐 틀릴 수 있어요. 이 평소의 고민이 **PACELC의 뒷부분**이에요.

단, 실제로는 "지점"이 서버(노드), "전화선"이 서버 사이 네트워크예요. 그리고 고르는 단위는 은행 전체가 아니라 "잔액 조회", "광고 문구 조회"처럼 **기능마다** 달라도 돼요.

## 제대로 알기

### 왜 이런 문제가 생기나: 복제

서버 한 대가 죽어도 서비스가 돌게 하려고, 같은 데이터를 여러 서버에 **복제**(replication, 데이터 사본을 여러 곳에 두는 것)해요. → [복제](../replication/)

사본이 여러 개면 "모든 사본이 언제나 같은 값인가?"라는 질문이 생겨요. 사본끼리 맞추려면 네트워크로 연락해야 하는데, 네트워크는 느려지거나 끊길 수 있어요. CAP와 PACELC는 이 상황에서 무엇을 포기하게 되는지 정리한 말이에요.

### CAP 정리의 정확한 뜻

**CAP 정리**(CAP theorem)는 Eric Brewer가 제안하고 Gilbert와 Lynch가 증명한 결과예요. 세 글자의 뜻은 이래요.

| 글자 | 이름 | CAP에서의 정확한 뜻 |
|---|---|---|
| C | 일관성(Consistency) | **선형성**. 사본이 여러 개여도 하나뿐인 것처럼 보이고, 쓰기가 끝난 뒤 시작한 읽기는 반드시 그 값(또는 더 새 값)을 봄 |
| A | 가용성(Availability) | 죽지 않은 노드가 받은 요청은 **결국 응답**을 받아야 함. 빨라야 한다는 조건은 없음 |
| P | 분할 내성(Partition tolerance) | 서버 사이 메시지가 지연·유실되어 서버 그룹이 **갈라질 수 있음**을 전제로 함 |

**네트워크 분할**(network partition)은 서버들은 살아 있는데 서로 연락이 끊겨 그룹이 나뉜 상태예요. 은행 비유의 "전화선이 끊김"이에요.

CAP가 말하는 건 하나예요. **분할이 일어난 동안에는 C와 A를 동시에 완벽하게 지킬 수 없다.** 위 그림처럼 갈라진 쪽 노드는 최신 쓰기를 알 방법이 없으니, 답을 안 하거나(C 선택) 틀릴 위험을 안고 답하거나(A 선택) 둘 중 하나밖에 못 해요.

### 흔한 오해 1: "3개 중 2개를 고른다"

"C·A·P 중 아무거나 2개"라는 설명은 틀렸어요. Brewer 본인도 2012년 글에서 이 표현이 오해를 부른다고 했어요.

- **P는 고르는 게 아니에요.** 네트워크 분할은 원하든 말든 일어나는 장애예요. 그래서 정확한 질문은 "**분할이 났을 때** C와 A 중 무엇을 포기할까?"예요.
- **분할이 없을 땐 C와 A를 둘 다** 가질 수 있어요. CAP가 막는 건 "분할 중에 완벽한 C와 완벽한 A"라는 아주 좁은 영역뿐이에요.
- 그래서 **"CA 시스템"은 사실상 없어요.** 굳이 말하면 "분할이 절대 안 난다고 가정한" 서버 한 대나 데이터센터 하나 이야기예요. 여러 서버에 복제하는 순간 분할은 생길 수 있어요.
- C와 A는 **0 아니면 1이 아니에요.** 정도의 문제고, 시스템 전체가 아니라 **기능·데이터·사용자 단위로** 다르게 고를 수 있어요.

### 흔한 오해 2: CAP의 C는 ACID의 C와 같다

이름만 같고 뜻은 전혀 달라요.

| | CAP의 C | ACID의 C |
|---|---|---|
| 뜻 | 선형성. 여러 사본이 하나처럼 보이고 최신 값을 봄 | 트랜잭션 전후로 앱이 정한 규칙(불변식)이 지켜짐 |
| 다루는 문제 | 사본 사이의 최신성 | 데이터가 규칙에 맞는 상태인가 |

ACID는 [트랜잭션과 ACID](../../db/transaction-acid/)에서 다뤄요.

### 흔한 오해 3: "MongoDB는 CP, Cassandra는 AP"

제품 이름 하나에 CP나 AP 딱지를 붙이는 건 위험해요.

- 많은 DB가 **설정으로 일관성 수준을 조절**해요. MongoDB는 공식 문서에서 **read concern**(읽을 때 얼마나 확실한 데이터를 볼지)과 **write concern**(쓰기가 몇 개 사본에 반영돼야 성공으로 칠지)으로 일관성과 가용성 수준을 정할 수 있다고 설명해요.
- MongoDB의 기본 read concern은 `local`이에요. 나중에 롤백될 수 있는 데이터도 읽을 수 있다는 뜻이에요. 반대로 `linearizable`을 쓰면 선형적인 읽기를 할 수 있지만 primary에서만 되고 느릴 수 있어요.
- 출처마다 분류도 달라요. PACELC를 제안한 Abadi는 2012년 논문에서 MongoDB를 "PA/EC"로 분류했어요(본인도 엄밀한 정의로는 단서를 달았어요). 흔히 듣는 "MongoDB는 CP"와 다르죠.
- Kleppmann도 CP/AP 딱지는 결점이 많으니 피하라고 권해요.

그래서 면접에선 "어떤 설정·어떤 연산이냐에 따라 달라요"라고 답하는 게 정확해요.

### PACELC: 평소에는 지연 vs 일관성

**PACELC**(Abadi, 2012)는 CAP에 "평소 이야기"를 붙인 거예요. 읽는 법은 이래요.

- **P**artition이 있으면 → **A**vailability와 **C**onsistency 중 선택
- **E**lse(분할이 없으면) → **L**atency(지연, 응답 속도)와 **C**onsistency 중 선택

평소에도 고민이 생기는 이유는 복제 때문이에요. 쓰기를 받은 서버가 **다른 사본에 다 반영됐는지 확인하고 답하면** 일관성은 좋지만 느려요(EC). **자기한테만 저장하고 바로 답한 뒤 나중에 복제하면** 빠르지만 다른 사본에서 잠깐 옛 값이 보여요(EL).

Abadi의 핵심 주장은 이거예요. **분할이 없는데도 일관성을 낮춘 시스템은 CAP 때문이 아니라 속도 때문에 그렇게 한 것**이에요. 분할은 드물지만 지연은 매 요청마다 생기니까요.

| 분류(Abadi 2012, 당시 기본 설정 기준) | 시스템 예 |
|---|---|
| PA/EL (분할 땐 가용성, 평소엔 속도) | Dynamo, Cassandra, Riak |
| PC/EC (언제나 일관성) | VoltDB/H-Store, Megastore, BigTable/HBase |
| PC/EL | PNUTS |
| PA/EC | MongoDB |

이 표도 "당시 기본 설정 기준"이에요. 설정을 바꾸면 달라져요.

### 일관성 모델 사다리

"일관성"에도 강도가 여러 단계 있어요. 위로 갈수록 강하고(약속이 많고), 아래로 갈수록 약하지만 빠르고 잘 안 멈춰요.

| 강도 | 모델 | 쉬운 뜻 | 예 |
|---|---|---|---|
| 가장 강함 | **선형성**(linearizability) | 사본이 하나뿐인 것처럼 보임. 쓰기가 끝난 뒤의 읽기는 무조건 새 값 | 잔액, 재고, 아이디 중복 검사 |
| ↓ | **순차 일관성**(sequential) | 모두가 같은 하나의 순서로 연산을 봄. 단, 실시간 순서는 안 지켜도 돼서 누군가는 조금 뒤처진 값을 볼 수 있음 | |
| ↓ | **인과적 일관성**(causal) | 원인과 결과 관계가 있는 것만 순서를 지킴. 관계없는 건 사람마다 다른 순서로 보여도 됨 | 댓글보다 답글이 먼저 보이지 않게 |
| 가장 약함 | **최종적 일관성**(eventual) | 새 쓰기가 멈추면 언젠가 모든 사본이 같아짐. "언제"는 약속 안 함 | 좋아요 수, 조회수 |

인과적 일관성 예를 들어 볼게요. 단톡방에 "점심 먹을래?"라는 질문과 "응"이라는 답이 있으면, 어느 누구 화면에서도 "응"이 질문보다 먼저 보이면 안 돼요. 하지만 서로 관계없는 두 사람의 답 "응"과 "아니"는 사람마다 순서가 달라도 괜찮아요.

강한 모델은 약한 모델의 약속을 모두 포함해요. 선형적이면 인과적 순서도 자동으로 지켜져요.

### 실무: 데이터마다 다르게 고른다

| 데이터 | 틀리면? | 고르는 쪽 | 방법 예 |
|---|---|---|---|
| 계좌 잔액, 송금 | 이중 출금, 마이너스 잔액 | C(분할 땐 한쪽 쓰기 거부) | 단일 리더 또는 합의 기반 저장소 |
| 재고·좌석 예약 | 초과 판매 | 예약 연산만 C | 상품 설명·리뷰는 최종 일관성 |
| 아이디 중복 가입 | 같은 아이디 두 개 | C(유일성 검사는 선형성 필요) | |
| 좋아요 수, 조회수 | 잠깐 숫자가 다름 | A·L | 비동기 복제, 캐시, 카운터 합산 |
| 내가 쓴 글이 새로고침 후 안 보임 | 사용자 혼란 | 선형성까진 과함 | read-your-writes(쓴 직후엔 리더에서 읽기) |

좋아요 수가 A 쪽에 잘 맞는 이유가 하나 더 있어요. "더하기"는 **순서를 바꿔도 결과가 같은 연산**이라, 분할 중 양쪽에서 따로 센 걸 나중에 합쳐도 문제가 없어요. 이런 성질을 이용해 자동으로 합쳐지는 자료구조를 **CRDT**라고 불러요.

마지막 줄은 [복제 지연](../replication-lag/)에서 자세히 다뤄요.

### 심화: 선형성은 분할이 없어도 비싸다

선형성을 포기하는 이유는 대개 장애 대비가 아니라 **성능**이에요. Kleppmann은 선형성의 응답 시간이 네트워크 지연의 불확실성에 비례할 수밖에 없다는 증명(Attiya·Welch)을 소개해요. 즉 분할이 없어도 선형성은 늘 느려요. 이게 PACELC의 EL/EC 고민이에요.

같은 이유로, 멀티코어 CPU의 메모리조차 코어별 캐시 때문에 선형적이지 않아요. 이유는 역시 성능이에요.

### 심화: 선형성 vs 직렬성

이름이 비슷해서 꼬리질문으로 자주 나와요.

| | 선형성(linearizability) | 직렬성(serializability) |
|---|---|---|
| 대상 | 데이터 **하나**(키 하나) | 여러 데이터를 묶은 **트랜잭션** |
| 약속 | 최신 값을 봄(실시간 순서) | 트랜잭션들이 어떤 순서로 하나씩 실행된 것과 결과가 같음 |
| 관련 주제 | 복제·CAP | [격리 수준](../../db/isolation-levels/) |

둘 다 만족하면 **엄격한 직렬성**(strict serializability)이라고 해요. 직렬성 스냅숏 격리(SSI)는 직렬적이지만 선형적이지는 않아요.

### 심화: 어떤 복제 방식이 선형적인가

| 복제 방식 | 선형적인가 |
|---|---|
| 단일 리더 | 리더(또는 동기 팔로워)에서 읽으면 가능. 단, 비동기 복제에서 리더가 바뀔 때 커밋 유실·스플릿 브레인으로 깨질 수 있음 |
| 합의 알고리즘(ZooKeeper, etcd) | 선형적 쓰기. 읽기는 옵션을 켜야 선형적(etcd 정족수 읽기, ZooKeeper `sync()`) |
| 다중 리더 | 선형적이지 않음 |
| 리더리스(Dynamo 스타일) | 아마 아님. 마지막 쓰기 승리(LWW)를 쓰면 시계 어긋남 때문에 거의 확실히 아님 |

**스플릿 브레인**(split brain)은 리더가 둘이 되어 양쪽이 각자 쓰기를 받는 상태예요. 합의는 [합의와 Raft](../consensus-raft/)에서 다뤄요.

### 심화: "W + R > N이면 강한 일관성"인가

리더리스 복제에서 사본 N개 중 W개에 쓰고 R개에서 읽을 때, **W + R > N**이면 쓰기 그룹과 읽기 그룹이 최소 하나는 겹쳐요. 이걸 어떻게 보는지 출처마다 달라요.

- **Vogels(2008)**: W + R > N이면 강한 일관성이라고 설명했어요.
- **Kleppmann·Abadi**: 네트워크 지연 변동, 느슨한 정족수, LWW 같은 이유로 W + R > N이어도 엄밀한 **선형성**은 보장되지 않는다고 지적해요. Abadi는 R + W를 키우면 지연을 대가로 일관성이 높아지지만, Gilbert·Lynch가 정의한 수준까지는 못 간다고 해요.

면접에선 "겹치니까 **대체로** 최신 값을 읽지만, 엄밀한 선형성까지는 아니다"라고 답하는 게 안전해요.

### 심화: 가용한 모델 중 가장 강한 건 인과적 일관성

Jepsen 정리에 따르면 선형성과 순차 일관성은 분할 중에 일부 노드가 멈춰야 해요. 반면 인과적 일관성과 read-your-writes는 "같은 서버에 계속 붙어 있으면" 분할 중에도 진행할 수 있어요.

그래서 인과적 일관성은 **분할 중에도 가용하고 네트워크 지연 때문에 느려지지 않는 모델 중 가장 강한 것**으로 알려져 있어요(엄밀히는 Jepsen이 "real-time causal"을 그 상한으로 소개해요). 선형성이 필요해 보이는 많은 경우에 실제로 필요한 건 인과적 순서뿐이에요.

### 심화: Brewer가 말하는 분할 대응 3단계

1. **분할 감지**: 연락이 안 되는 걸 알아챔
2. **분할 모드**: 위험한 연산 일부만 막고 나머지는 계속 받음
3. **복구**: 연결이 돌아오면 양쪽 상태를 합치고, 그 사이 생긴 잘못은 보상 작업으로 바로잡음

Brewer는 "분할은 통신에 거는 시간 제한"이라고 표현해요. 타임아웃을 짧게 잡으면 네트워크가 그냥 느릴 때도 분할로 판단해요. 반대로 응답이 올 때까지 무한히 재시도하면 사실상 C를 고른 거예요.

## 면접 질문

<details>
<summary>Q. CAP 정리를 설명해 주세요.</summary>

**답변(30초)**
데이터를 여러 노드에 복제한 시스템에서 네트워크 분할이 생기면, 일관성과 가용성을 동시에 완벽하게 지킬 수 없다는 정리예요. 여기서 일관성은 선형성, 즉 쓰기가 끝난 뒤의 읽기는 항상 최신 값을 보는 것이고, 가용성은 살아 있는 노드가 모든 요청에 결국 응답하는 거예요. 분할된 노드는 최신 쓰기를 모르니, 응답을 거절해 일관성을 지키거나 옛 값으로 응답해 가용성을 지키는 것 중 하나만 할 수 있어요.

**꼬리질문**
- Q. 분할이 없을 땐요? → C와 A 둘 다 가질 수 있어요. 대신 지연과 일관성 사이에서 고르는데, 이게 PACELC예요.
- Q. CAP의 C와 ACID의 C는 같은가요? → 달라요. CAP의 C는 사본 사이 최신성(선형성), ACID의 C는 트랜잭션 전후로 앱의 규칙이 지켜지는 거예요.
</details>

<details>
<summary>Q. "C·A·P 중 2개를 고른다"는 설명은 맞나요?</summary>

**답변(30초)**
틀려요. 네트워크 분할은 고르는 게 아니라 언제든 일어나는 장애라서, 진짜 질문은 "분할이 났을 때 C와 A 중 무엇을 포기하나"예요. 분할이 없을 땐 둘 다 가질 수 있어요. 그래서 여러 노드에 복제하는 시스템에서 "CA 시스템"은 사실상 없어요. Brewer 본인도 이 표현이 오해를 부른다고 했고, C와 A는 0/1이 아니라 정도의 문제이며 기능마다 다르게 고를 수 있다고 했어요.

**꼬리질문**
- Q. 그럼 CA는 어디에 해당하나요? → 분할이 안 난다고 가정할 수 있는 서버 한 대나 데이터센터 하나 정도예요.
</details>

<details>
<summary>Q. 강한 일관성(선형성)과 최종적 일관성의 차이는?</summary>

**답변(30초)**
선형성은 사본이 여러 개여도 하나뿐인 것처럼 보여서, 쓰기가 끝난 뒤 시작한 읽기는 반드시 그 값을 봐요. 최종적 일관성은 쓰기가 멈추면 언젠가 모든 사본이 같아진다는 약속뿐이고, 그 사이엔 옛 값이 보일 수 있어요. 잔액·재고처럼 틀리면 안 되는 데이터는 선형성, 좋아요 수처럼 잠깐 틀려도 되는 데이터는 최종적 일관성을 써요.

**꼬리질문**
- Q. 최종적 일관성이면 "언젠가 맞으니 괜찮다"고 봐도 되나요? → 수렴 시간에 상한이 없고, 그 사이 내가 쓴 글이 안 보이는 문제가 생길 수 있어요. 필요하면 read-your-writes 같은 보장을 더해요.
- Q. 중간 단계 모델은요? → 순차 일관성(모두 같은 순서, 실시간은 아님), 인과적 일관성(원인→결과 순서만 지킴)이 있어요.
</details>

<details>
<summary>Q. PACELC는 무엇이고 CAP와 무엇이 다른가요?</summary>

**답변(30초)**
분할(P)이 있으면 가용성(A)과 일관성(C) 중에서, 그렇지 않으면(E) 지연(L)과 일관성(C) 중에서 고른다는 틀이에요. CAP는 분할 상황만 말하는데, 분할은 드물고 지연은 매 요청 생기니까 평소의 선택이 실무에선 더 중요하다는 게 핵심이에요. 예를 들어 다른 사본까지 반영을 확인하고 응답하면 EC, 로컬에만 쓰고 바로 응답하면 EL이에요.

**꼬리질문**
- Q. 분할이 없는데 왜 일관성을 낮추나요? → 성능 때문이에요. 선형성은 네트워크 지연의 불확실성만큼 응답이 느려질 수밖에 없어요.
</details>

<details>
<summary>Q. MongoDB(또는 Cassandra)는 CP인가요, AP인가요?</summary>

**답변(30초)**
한 글자로 단정하기 어려워요. MongoDB는 read concern과 write concern으로 연산마다 일관성 수준을 조절할 수 있고, 기본 read concern인 local은 롤백될 수 있는 데이터도 읽을 수 있어요. 출처마다 분류도 달라서, Abadi는 MongoDB를 PA/EC로 분류하기도 했어요. "어떤 설정과 어떤 연산이냐에 따라 달라지고, 예를 들어 결제 조회는 강하게, 피드 조회는 약하게 둔다"고 답하는 게 정확해요.

**꼬리질문**
- Q. Cassandra는요? → Abadi 분류로는 기본 설정 기준 PA/EL이지만, 읽기·쓰기 정족수를 키우면 지연을 대가로 일관성을 높일 수 있어요.
</details>

<details>
<summary>Q. (심화) 선형성과 직렬성은 어떻게 다른가요?</summary>

**답변(30초)**
선형성은 키 하나에 대한 최신성 보장이고, 직렬성은 여러 데이터를 건드리는 트랜잭션들이 하나씩 실행된 것과 같은 결과를 내는 격리 보장이에요. 선형성은 복제·CAP의 언어, 직렬성은 트랜잭션 격리 수준의 언어예요. 둘 다 만족하면 엄격한 직렬성이라고 해요.

**꼬리질문**
- Q. 직렬성을 만족하면 선형적인가요? → 아니에요. 예를 들어 직렬성 스냅숏 격리(SSI)는 선형적이지 않아요.
</details>

<details>
<summary>Q. (심화) 정족수 W + R > N이면 선형성이 보장되나요?</summary>

**답변(30초)**
견해가 갈려요. Vogels는 W + R > N이면 강한 일관성이라고 설명했어요. 하지만 Kleppmann과 Abadi는 네트워크 지연 변동, 느슨한 정족수, 마지막 쓰기 승리(LWW) 같은 이유로 엄밀한 선형성까지는 보장 못 한다고 지적해요. 그래서 "쓰기와 읽기 그룹이 겹쳐 대체로 최신 값을 읽지만 선형성은 아니다"라고 정리해요.

**꼬리질문**
- Q. 정말 선형성이 필요하면요? → 합의 알고리즘 기반 저장소(etcd, ZooKeeper)를 쓰고, 읽기도 선형 읽기 옵션을 켜요.
</details>

<details>
<summary>Q. (심화) 인과적 일관성은 왜 의미가 있나요?</summary>

**답변(30초)**
분할 중에도 가용하면서 네트워크 지연 때문에 느려지지 않는 모델 중 가장 강한 것으로 알려져 있기 때문이에요. 질문보다 답이 먼저 보이는 것 같은 이상한 일은 막아 주면서, 선형성처럼 분할 때 멈추지 않아도 돼요. 선형성이 필요해 보이는 많은 경우 실제로 필요한 건 인과적 순서뿐이에요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제와 피드(SNS 타임라인)가 있는 서비스를 여러 리전에 복제하려 해요. 리전 사이 네트워크가 끊기면 어떻게 동작해야 할까요? CP와 AP 중 무엇을 고르겠어요?</summary>

**상황 파악**
"서비스 전체를 CP냐 AP냐"로 고르는 질문처럼 보이지만, 결제와 피드는 틀렸을 때의 피해가 전혀 달라요. 결제는 잔액이 틀리면 돈이 사라지거나 두 번 나가요. 피드는 새 글이 몇 초 늦게 보여도 큰 문제가 없지만, 피드가 안 열리면 사용자는 바로 떠나요.

**원인 후보(왜 고민이 생기나)**
1. 리전 간 링크가 끊기면 각 리전은 상대방의 최신 쓰기를 모름(CAP 상황).
2. 두 리전이 각자 출금을 받으면 이중 출금·마이너스 잔액 가능.
3. 링크가 멀쩡해도 리전 간 동기 복제는 느림(PACELC의 L vs C).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 전체를 C 쪽(단일 리더·합의 저장소) | 어디서나 정확 | 분할 때 리더 반대쪽 리전은 피드까지 멈춤. 평소에도 리전 간 왕복만큼 느림 |
| B. 전체를 A 쪽(리전별로 쓰기 받고 나중에 합침) | 언제나 빠르고 안 멈춤 | 결제에서 이중 출금 위험. 충돌 해결이 어려움 |
| C. 기능별로 나눔: 결제는 C, 피드는 A·L | 피해가 큰 곳만 비용을 냄 | 저장소·설정이 두 종류라 운영이 복잡해짐 |

**내가 고를 방법**
C를 골라요. 결제·잔액은 단일 리더나 합의 기반 저장소에 두고, 분할 때 리더와 연결이 끊긴 리전에서는 결제 요청을 거절하거나 "잠시 후 다시 시도"로 안내해요(가용성 포기). 피드·좋아요 수는 리전별로 비동기 복제하고, 분할 중에도 각 리전에서 읽고 써요. 연결이 돌아오면 합치는데, 좋아요 수처럼 더하기만 하는 값은 순서와 상관없이 합칠 수 있어요. Brewer가 말한 것처럼 C/A 선택은 시스템 전체가 아니라 연산 단위로 하는 거라고 설명해요.

**채점 포인트**: 분할 시 C vs A(3개 중 2개 아님), 기능·데이터별로 다르게 선택, 결제 = 선형성 필요(이중 출금·음수 잔액), 피드 = 최종 일관성 허용, 분할 중 거절이 곧 가용성 포기, 평소 지연 비용(PACELC), 복구 후 합치기(교환 가능한 연산).
</details>

<details>
<summary>상황: "같은 게시글의 좋아요 수가 제 폰과 친구 폰에서 다르게 보여요"라는 문의가 들어왔어요. 원인과 대응을 설명해 주세요.</summary>

**상황 파악**
좋아요 수는 보통 빠른 응답과 가용성을 위해 최종적 일관성으로 운영해요. 숫자가 잠깐 다른 건 설계상 예상된 동작일 수 있어요. 먼저 "계속 다른가, 잠시 뒤 맞춰지는가"를 확인해야 해요.

**원인 후보**
1. 두 사용자가 서로 다른 복제본(팔로워)이나 다른 리전에서 읽음 → 복제 지연 동안 값이 다름.
2. 캐시 TTL이 남아 한쪽은 옛 값을 봄.
3. 계속 안 맞는다면 버그: 카운터를 "읽고 +1 해서 덮어쓰기"로 처리해 동시 요청에서 일부 좋아요가 사라짐, 또는 복제가 멈춤.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 그대로 두고 수렴 확인 | 비용 없음. 좋아요 수엔 충분 | 사용자가 잠깐 헷갈림 |
| B. 내가 누른 직후엔 내 화면에 반영(read-your-writes: 리더에서 읽거나 화면에서 바로 +1) | "눌렀는데 안 올라감" 불만 해결 | 리더 부하 증가 또는 화면과 서버 값의 잠깐 차이 |
| C. 좋아요 수를 선형적으로 읽기 | 모두 같은 숫자 | 모든 조회가 느려지고 분할 땐 조회 실패. 좋아요 수엔 과함 |

**내가 고를 방법**
먼저 몇 초에서 몇 분 안에 맞춰지는지 확인해요. 맞춰진다면 A를 유지하고, 사용자 불만이 "내가 누른 게 안 보인다"라면 B를 더해요. 계속 안 맞으면 3번 버그를 의심해서, 덮어쓰기 대신 원자적 증가나 더하기 연산으로 바꾸고 복제 상태를 점검해요. C는 좋아요 수에 비해 비용이 너무 커서 고르지 않아요.

**채점 포인트**: 최종적 일관성이라 일시적 불일치는 정상, 수렴 여부로 정상/버그 구분, 복제 지연·캐시, read-your-writes, 덮어쓰기 대신 더하기(교환 가능한 연산), 선형성은 과한 비용(PACELC의 L).
</details>

<details>
<summary>상황: 팀원이 "NoSQL은 일관성이 없으니 주문 데이터엔 절대 못 쓴다"고 주장해요. 어떻게 반박하거나 보완하겠어요?</summary>

**상황 파악**
주문 데이터는 정확해야 한다는 걱정 자체는 맞아요. 문제는 "NoSQL = 일관성 없음"이라는 단정이에요. 일관성은 있음/없음이 아니라 단계가 있고, 많은 DB가 설정으로 단계를 고를 수 있어요.

**원인 후보(왜 그런 오해가 생겼나)**
1. "Cassandra는 AP, MongoDB는 CP" 같은 딱지를 제품 전체의 성질로 받아들임.
2. 기본 설정(예: MongoDB 기본 read concern `local`)이 약하다는 걸 "그 DB는 약하다"로 일반화함.
3. 최종적 일관성을 "일관성 없음"으로 오해함. 실제로는 언젠가 수렴한다는 약한 보장이고, 그 위에 인과적 일관성 같은 단계도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 주문은 관계형 DB에 두고 트랜잭션 사용 | 팀이 익숙하고 ACID로 묶기 쉬움 | 다른 데이터와 저장소가 갈라짐 |
| B. 지금 쓰는 NoSQL에서 강한 설정 사용(예: MongoDB write concern majority, read concern majority/linearizable) | 저장소 하나로 운영 | 해당 연산이 느려짐. 설정 실수 위험, 팀이 의미를 정확히 알아야 함 |
| C. 연산별 혼합: 주문 생성·결제 상태 조회만 강하게, 주문 목록·추천은 약하게 | 필요한 곳만 비용 지불 | 연산별 설정을 문서화·검증해야 함 |

**내가 고를 방법**
"NoSQL이라서 안 된다"가 아니라 "주문의 어떤 연산에 어떤 일관성이 필요한가"로 질문을 바꿔요. 중복 주문 방지나 재고 차감처럼 유일성·불변식이 걸린 연산은 선형성 수준이 필요하고, 주문 목록 조회는 약해도 돼요. 팀이 이미 관계형 DB에 익숙하면 A가 가장 안전하고, NoSQL을 계속 쓴다면 C로 연산별 설정을 명시해요. 어느 쪽이든 공식 문서에서 설정의 정확한 보장을 확인하고 정하자고 제안해요.

**채점 포인트**: 일관성은 단계(선형성 > 순차 > 인과 > 최종), 제품 딱지보다 설정·연산 단위, read/write concern 예, 최종적 일관성 ≠ 일관성 없음, 주문 중 선형성이 필요한 연산 구분(유일성·재고), CAP의 C ≠ ACID의 C.
</details>

## 필기 포인트

- CAP: C = 선형성(원자적 일관성), A = 살아 있는 노드의 모든 요청에 결국 응답, P = 네트워크 분할. **분할 시 C와 A 중 택일**이 정확한 진술이에요.
- "CAP는 3개 중 2개를 고른다" → 틀린 보기로 자주 나와요.
- PACELC: if **P** then **A** or **C**, **E**lse **L** or **C**. 제안자는 Abadi(2012).
- 일관성 강도: 선형성 > 순차 > 인과 > 최종적.
- CAP의 P(네트워크 분할)와 샤딩의 파티셔닝(데이터 나누기)은 다른 뜻이에요. → [파티셔닝](../partitioning/)
