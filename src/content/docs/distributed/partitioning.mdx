:::tip[한 줄 요약]
**파티셔닝**(샤딩)은 한 서버에 다 못 담는 데이터를 **조각(파티션)으로 나눠 여러 서버에 나눠 담는 것**이에요. **키 범위**로 나누면 범위 조회가 쉽지만 한쪽에 몰리기 쉽고, **해시**로 나누면 고르게 퍼지지만 범위 조회가 어려워요. 서버 수가 바뀔 때 `hash % N`을 쓰면 거의 모든 키가 이사하므로, **고정 파티션 수**나 **안정 해시**(consistent hashing)처럼 일부만 옮기는 방식을 써요.
:::

:::note[처음이라면 여기까지]
① 데이터가 너무 많아지면 서버 한 대로는 못 버텨서, 데이터를 나눠 여러 서버에 담아요. 이게 파티셔닝(샤딩)이에요.

② 나누는 기준은 크게 둘이에요. "가나다순 구간"으로 나누는 **키 범위**, 그리고 키를 섞어서 나누는 **해시**예요.

③ 어느 한 서버에만 일이 몰리는 걸 **핫스팟**이라고 해요. 나누는 기준(샤드 키)을 잘 골라야 피할 수 있어요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

책이 너무 많아져서 **도서관 건물 하나로는 모자라게 된** 상황이라고 해 봐요. 그래서 건물을 여러 채 짓고 책을 나눠 두기로 해요.

첫 번째 방법은 **제목 가나다순으로 건물을 정하는 것**이에요. 1관은 "가~다", 2관은 "라~바"… 이렇게요. "ㄱ으로 시작하는 책 다 보여 주세요" 같은 요청은 1관만 가면 되니 편해요. 그런데 "가"로 시작하는 책이 유독 많거나, 신간이 전부 "가"로 시작하면 1관만 미어터져요.

두 번째 방법은 **책 번호를 정해진 규칙으로 섞어서 건물을 정하는 것**이에요. 비슷한 제목의 책도 서로 다른 건물로 흩어지니 손님이 고르게 퍼져요. 대신 "ㄱ으로 시작하는 책 전부"를 찾으려면 모든 건물을 다 돌아야 해요.

건물을 한 채 더 지을 때도 문제예요. 규칙을 잘못 만들면 **거의 모든 책을 다른 건물로 옮겨야** 해요. 좋은 규칙은 새 건물로 갈 책만 조금 옮기고 나머지는 그대로 둬요.

단, 실제로는 건물(서버)마다 같은 책의 **복사본**도 함께 두는 게 보통이에요. 나눠 담기(파티셔닝)와 여러 벌 두기([복제](../replication/))는 따로 정하는 별개의 선택이에요.

## 제대로 알기

### 파티셔닝이 왜 필요한가

데이터나 요청이 서버 한 대의 저장 공간·처리량을 넘으면 더 큰 서버를 사는 것도 한계가 있어요. 그래서 데이터를 **파티션**(partition, 데이터 조각)으로 쪼개 여러 **노드**(node, 클러스터 안의 서버 한 대)에 나눠 담아요. 레코드 하나는 정확히 한 파티션에만 속하고, 각 파티션은 작은 독립 DB처럼 움직여요. 그러면 노드를 늘리는 만큼 저장량과 처리량이 늘어나요.

같은 개념을 제품마다 다르게 불러요. 샤드(shard: MongoDB, Elasticsearch), 리전(region: HBase), 태블릿(tablet: Bigtable), vnode(Cassandra), vBucket(Couchbase)이 다 파티션이에요.

헷갈리기 쉬운 두 가지가 있어요.

| 비교 | 차이 |
|---|---|
| 파티셔닝 vs 복제 | 파티셔닝은 **서로 다른 데이터**를 나눠 담기, 복제는 **같은 데이터**를 여러 벌 두기. 보통 둘을 같이 써요(파티션마다 복사본을 여러 노드에 둠) |
| 파티셔닝 vs 네트워크 파티션 | 이름만 비슷해요. 파티셔닝은 일부러 데이터를 나누는 **설계**, 네트워크 파티션(CAP의 P)은 서버끼리 연결이 끊기는 **장애**예요 |

이름이 비슷한 기능 중에는 서버 한 대 안에서 테이블을 여러 조각으로 나누는 것도 있어요. 이 페이지에서 말하는 파티셔닝은 **여러 서버에 나누는 쪽**이에요.

### 목표: 고르게 나누기, 핫스팟 피하기

파티셔닝의 목표는 데이터와 요청을 노드에 **고르게** 퍼뜨리는 거예요. 고르지 않은 상태를 **쏠림**(skew)이라 하고, 유독 일이 몰린 파티션을 **핫스팟**(hot spot)이라 해요. 최악이면 노드 10대 중 1대만 일하고 9대는 놀아요. 그러면 나눈 의미가 없어요.

"그냥 무작위로 아무 노드에 넣으면 고르지 않나?" 싶지만, 그러면 읽을 때 어디 있는지 몰라서 모든 노드에 물어봐야 해요. 그래서 **키로 위치를 계산할 수 있는 규칙**이 필요해요. 이 키를 **샤드 키**(파티션 키)라고 불러요.

### 키 범위 파티셔닝 vs 해시 파티셔닝

**키 범위 파티셔닝**(key range partitioning)은 사전의 권처럼 **연속된 키 구간**을 파티션마다 맡겨요. 데이터가 고르지 않으면 구간 크기를 다르게 잡아도 돼요. 파티션 안에서는 키를 정렬해 두니 "11월 데이터 전부" 같은 **범위 조회**가 쉬워요.

**해시 파티셔닝**(hash partitioning)은 키를 **해시 함수**(입력을 섞어서 정해진 범위의 숫자로 바꾸는 함수)에 넣고, 나온 값의 구간마다 파티션을 맡겨요. 비슷한 키도 해시값은 멀리 흩어져서 고르게 퍼져요. 대신 키 순서가 사라져서 범위 조회는 모든 파티션에 물어봐야 해요.

| | 키 범위 | 해시 |
|---|---|---|
| 나누는 법 | 키의 연속 구간별로 | 해시값 구간별로 |
| 범위 조회 | 쉬움(필요한 파티션만) | 어려움(전체 파티션에 물어봄) |
| 고르게 퍼짐 | 접근 패턴에 따라 쏠리기 쉬움 | 고르게 퍼짐 |
| 핫스팟 위험 | 시간처럼 계속 커지는 키면 최신 구간에 몰림 | 같은 키 하나에 요청이 몰리면 여전히 생김 |
| 쓰는 곳 | Bigtable, HBase, RethinkDB, 2.4 이전 MongoDB | Cassandra, MongoDB 해시 샤딩, Riak, Voldemort 등 |

파티셔닝용 해시는 암호처럼 강할 필요는 없어요(Cassandra·MongoDB는 MD5, Voldemort는 FNV를 써요). 다만 **어느 프로세스에서 계산해도 같은 값**이 나와야 해요. 자바 `Object.hashCode()`처럼 실행할 때마다 달라질 수 있는 해시는 쓰면 안 돼요.

### 핫스팟과 그 해결

**키 범위의 핫스팟**: 센서 기록을 **시각**을 키로 키 범위 파티셔닝하면, 새 기록은 전부 "오늘" 구간에 들어가요. 오늘 파티션이 있는 노드 하나만 쓰기를 다 받고 나머지는 놀아요. 해결책은 키 앞에 **센서 이름** 같은 다른 값을 붙이는 거예요. 그러면 쓰기가 센서별로 흩어져요. 대가로 "모든 센서의 9시~10시 기록"을 보려면 센서마다 따로 범위 조회를 돌려야 해요.

**해시로도 못 막는 핫스팟**: 해시는 서로 다른 키를 흩을 뿐이에요. **같은 키**는 해시값도 늘 같아서 같은 파티션으로 가요. 유명인 계정 ID나 인기 게시글 ID 하나에 요청이 몰리면 해시를 써도 그 파티션은 뜨거워요.

대부분 DB는 이걸 알아서 고쳐 주지 않아서 **애플리케이션이 직접** 처리해요. 흔한 방법은 뜨거운 키 뒤에 두 자리 난수(00~99)를 붙여 **키 하나를 100개로 쪼개는** 거예요. 쓰기는 100개 키로 흩어져요. 대신 읽을 때 100개를 다 읽어 합쳐야 하고, 어떤 키를 쪼갰는지 따로 기록해 둬야 해요. 그래서 모든 키가 아니라 **소수의 뜨거운 키에만** 써요.

### 리밸런싱: 노드를 늘리면 데이터를 어떻게 옮기나

**리밸런싱**(rebalancing, 재균형화)은 데이터가 늘거나, 요청이 늘거나, 노드가 죽었을 때 데이터를 다른 노드로 옮기는 일이에요. 지켜야 할 건 세 가지예요.

1. 끝나고 나면 부하가 고르게 나뉘어 있을 것
2. 옮기는 동안에도 읽기·쓰기를 계속 받을 것
3. **필요한 것보다 많이 옮기지 않을 것**

#### hash % N은 왜 쓰면 안 되나

가장 쉬워 보이는 방법은 `hash(key) % N`(N은 노드 수)으로 노드를 고르는 거예요. 문제는 **N이 바뀌는 순간 거의 모든 키의 담당 노드가 바뀐다**는 거예요. 예를 들어 해시값이 7인 키는 노드 4대일 때 `7 % 4 = 3`번, 5대일 때 `7 % 5 = 2`번 노드로 가요. 새 노드로 갈 키만 옮기면 될 일을, 기존 노드끼리도 마구 주고받게 돼요.

키 1만 개, 노드 4대→5대로 한 번 재 보니 **79.6%의 키가 이사**했어요. 이론값도 약 80%예요(새 N과 옛 N에서 나머지가 우연히 같을 확률이 대략 1/5이라서, 1 − 1/5). 정말 필요한 이동은 새 노드 몫인 약 20%뿐이에요.

#### 해결 1: 고정 파티션 수

처음부터 **파티션을 노드보다 훨씬 많이** 만들어요. 예를 들어 노드 10대에 파티션 1,000개(노드당 약 100개). 노드가 추가되면 새 노드가 기존 노드들에서 **파티션 몇 개를 통째로** 가져와요.

핵심은 **키→파티션 대응은 절대 안 바뀌고, 파티션→노드 대응만 바뀐다**는 거예요. 그래서 새 노드 몫만큼만 옮겨요. 옮기는 동안엔 옛 배치로 요청을 처리해요. 성능 좋은 노드에 파티션을 더 줄 수도 있어요. Riak, Elasticsearch, Couchbase, Voldemort가 이 방식이고, [Redis Cluster](../../redis/replication-cluster/)도 키를 **해시 슬롯 16384개**로 나눠 슬롯을 노드에 나눠 주는 같은 원리예요.

단점은 처음 정한 파티션 수가 **노드 수의 상한**이 된다는 거예요. 넉넉히 잡아야 하지만, 파티션마다 관리 비용이 있어 너무 많아도 안 돼요.

#### 해결 2: 안정 해시(consistent hashing)

**안정 해시**는 노드와 키를 **같은 원형 해시 공간(링)** 위에 올려놓는 방법이에요. 키는 자기 위치에서 **시계 방향으로 가다 처음 만나는 노드**가 맡아요. 새 노드가 링에 끼어들면, 그 노드 바로 앞 구간의 키만 새 노드로 가고 나머지는 그대로예요. 1997년 Karger 등이 웹 캐시의 핫스팟을 줄이려고 제안한 방식이에요.

그런데 노드마다 링 위 점이 **1개**뿐이면 구간 길이가 들쭉날쭉해요. 그래서 물리 노드 하나를 링 위 **여러 점으로** 올리는데, 이걸 **가상 노드**(virtual node)라고 해요.

한 번 재 본 결과(키 1만 개, 노드 4대→5대)는 이래요.

| 방식 | 이동한 키 | 노드 5대일 때 노드별 키 개수 |
|---|---|---|
| hash % N | 79.6% | (고르게 나뉨, 대신 이동이 많음) |
| 안정 해시, 가상 노드 100개 | 22.5% (이론값 20%) | 1856 ~ 2250개로 고름 |
| 안정 해시, 가상 노드 1개 | 4.2% | 174 / 420 / 1301 / 3131 / 4974개로 심하게 쏠림 |

가상 노드 100개일 때 옮겨진 키는 **전부 새 노드로** 갔고, 기존 노드끼리는 주고받지 않았어요. 가상 노드 1개일 때 4.2%만 옮겨진 건 좋아서가 아니에요. 새 노드가 우연히 작은 구간을 받았을 뿐이고, 부하는 한 노드가 다른 노드의 약 28배를 맡을 만큼 깨졌어요.

### 심화: "일관성 해싱"이라는 이름의 함정

consistent hashing은 한국어로 흔히 **일관성 해싱**이라 번역돼요. 그런데 여기서 "consistent"는 **노드가 바뀌어도 키 배치가 대부분 그대로 유지된다**는 뜻이에요. [CAP의 일관성](../cap-consistency/)이나 트랜잭션 ACID의 일관성과는 **아무 관계가 없어요**. 이 페이지에서 "안정 해시"라고 부른 이유예요.

용어 혼란은 하나 더 있어요. DB 문서에서는 이 말을 그냥 "해시로 나누기"라는 뜻으로 느슨하게 쓰는 경우가 많아요. 『데이터 중심 애플리케이션 설계』는 혼동을 피하려고 "해시 파티셔닝"이라고 부르라고 권해요. 면접에서는 "노드 증감 때 옮기는 키를 최소화하는 배치 방식"이라고 정확히 말하면 돼요.

### 심화: 동적 파티셔닝과 노드 비례 파티셔닝

**동적 파티셔닝**: 파티션이 정해진 크기를 넘으면 반으로 쪼개고(HBase 기본 10GB), 작아지면 옆 파티션과 합쳐요. 파티션 수가 데이터 양을 따라가요. 함정은 빈 DB가 파티션 1개로 시작해서 **처음엔 쓰기가 노드 하나에 몰린다**는 거예요. HBase·MongoDB는 미리 쪼개 두는 **사전 분할**(pre-splitting)을 지원하지만 키 분포를 미리 알아야 해요.

**노드 비례 파티셔닝**: 노드당 파티션 수를 고정해요(Cassandra 기본 256). 새 노드가 들어오면 기존 파티션 몇 개를 무작위로 골라 반으로 쪼개 절반을 가져가요. 경계를 무작위로 고르려면 해시 파티셔닝이어야 해요. 원래 의미의 안정 해시와 가장 가까운 방식이에요.

| 전략 | 파티션 수 | 주의점 |
|---|---|---|
| 고정 파티션 수 | 처음 정한 대로 고정 | 처음 수가 노드 수 상한. 데이터가 커지면 파티션 하나가 커짐 |
| 동적 파티셔닝 | 데이터 양에 따라 늘고 줆 | 시작할 때 파티션 1개라 쏠림 |
| 노드 비례 | 노드 수에 비례 | 해시 파티셔닝이 전제 |

### 심화: 자동 리밸런싱이 위험한 이유

리밸런싱은 큰 데이터를 네트워크로 옮기는 비싼 작업이라 그동안 다른 요청이 느려질 수 있어요. 이게 **자동 장애 감지**와 합쳐지면 위험해요. 어떤 노드가 과부하로 잠깐 느려졌을 뿐인데 "죽었다"고 판단해 데이터를 옮기기 시작하면, 다른 노드와 네트워크까지 과부하가 걸려 **연쇄 장애**로 번질 수 있어요. 그래서 Couchbase·Riak·Voldemort는 시스템이 배치안을 제안하고 **사람이 확정**하게 해요.

### 심화: 보조 인덱스는 어떻게 나누나 (로컬 vs 글로벌)

**보조 인덱스**(secondary index)는 기본 키가 아닌 칼럼(예: 차 색깔)으로 찾기 위한 인덱스예요. 데이터는 기본 키로 나눴는데 "빨간 차 전부"를 찾으려면 어떻게 할까요? 방법이 두 가지예요.

| | 로컬 인덱스(문서 기준) | 글로벌 인덱스(용어 기준) |
|---|---|---|
| 인덱스 위치 | 파티션마다 **자기 데이터만** 인덱싱 | 인덱스 자체를 **값(예: color:red) 기준으로** 나눠 둠 |
| 쓰기 | 데이터가 있는 파티션 하나만 고치면 끝 | 문서 하나가 여러 인덱스 파티션을 건드려 느리고 복잡 |
| 읽기 | 모든 파티션에 물어서 합침(**스캐터/개더**) | 해당 값의 인덱스 파티션 하나만 보면 됨 |
| 약점 | 가장 느린 파티션에 끌려가 꼬리 지연(가장 느린 일부 요청의 응답 시간)이 커짐 | 보통 **비동기 갱신**이라 방금 쓴 데이터가 안 보일 수 있음 |
| 쓰는 곳 | MongoDB, Cassandra, Elasticsearch, Riak 등 | DynamoDB 글로벌 보조 인덱스 등 |

글로벌 인덱스를 항상 최신으로 맞추려면 여러 파티션을 한 번에 고치는 [분산 트랜잭션](../distributed-transactions/)이 필요해서, 현실에선 대개 비동기로 갱신해요. DynamoDB 글로벌 보조 인덱스는 보통 1초 안쪽이지만 장애 땐 더 늦어질 수 있어요. "방금 등록한 상품이 검색에 안 나와요"가 바로 이 지연이에요.

### 심화: 요청 라우팅 — 어느 노드에 물어봐야 하나

데이터가 나뉘어 있으면 "키 X는 지금 어느 노드에 있지?"를 알아야 해요. 이걸 **요청 라우팅**이라 하고, 방법은 세 가지예요.

1. **아무 노드에나 보내기**: 받은 노드가 담당이 아니면 맞는 노드로 넘겨줘요. Cassandra·Riak은 노드끼리 **가십 프로토콜**(소문 퍼지듯 서로 상태를 전달)로 배치 정보를 공유해요.
2. **라우팅 계층 두기**: 파티션 배치를 아는 중간 계층이 받아서 맞는 노드로 보내요. MongoDB의 mongos 라우터가 이 역할이에요.
3. **클라이언트가 직접**: 클라이언트가 배치표를 들고 있다가 맞는 노드로 바로 접속해요.

어느 방법이든 핵심 문제는 **배치가 바뀌었을 때 라우팅하는 쪽이 어떻게 알아채나**예요. 많은 시스템이 ZooKeeper 같은 **코디네이션 서비스**에 배치표를 저장하고, 라우터·클라이언트가 이를 구독해 변경을 통지받아요. HBase, SolrCloud가 이 방식이에요. Kafka도 예전엔 ZooKeeper를 썼지만 이후 KRaft로 의존을 없앴어요.

## 면접 질문

<details>
<summary>Q. 샤딩(파티셔닝)이 뭐고 왜 하나요? 복제와는 뭐가 다른가요?</summary>

**답변(30초)**
샤딩은 데이터를 조각으로 나눠 여러 서버에 나눠 담는 거예요. 데이터나 요청이 서버 한 대 한계를 넘을 때, 노드를 늘린 만큼 저장량과 처리량을 늘리려고 해요. 복제는 같은 데이터를 여러 벌 두는 거라 장애 대비와 읽기 분산이 목적이고, 샤딩은 서로 다른 데이터를 나눠 담는 거라 확장이 목적이에요. 실무에선 둘을 같이 써서, 파티션마다 복사본을 여러 노드에 둬요.

**꼬리질문**
- Q. 네트워크 파티션과 같은 말인가요? → 아니요. 파티셔닝은 일부러 나누는 설계, 네트워크 파티션은 서버 간 연결이 끊기는 장애예요.
- Q. 샤딩의 단점은? → 여러 샤드에 걸친 조회·조인·트랜잭션이 어려워지고, 리밸런싱과 라우팅을 관리해야 해요.
</details>

<details>
<summary>Q. 키 범위 파티셔닝과 해시 파티셔닝의 장단점을 비교해 주세요.</summary>

**답변(30초)**
키 범위는 연속된 키 구간을 파티션에 맡겨서 범위 조회가 쉽지만, 시간처럼 계속 커지는 키를 쓰면 최신 구간 하나에 쓰기가 몰려요. 해시는 키를 해시해서 고르게 흩어 주지만 키 순서가 사라져 범위 조회가 전체 파티션으로 퍼져요. 그래서 범위 조회가 중요하면 키 범위, 고른 분산이 중요하면 해시를 골라요.

**꼬리질문**
- Q. 둘을 섞을 수는 없나요? → Cassandra는 복합 키의 첫 칼럼(예: user_id)만 해시해 파티션을 정하고, 나머지 칼럼(예: 작성 시각)은 파티션 안 정렬에 써요. 그래서 한 사용자의 글을 시간순으로 범위 조회할 수 있어요.
- Q. 자바 hashCode()로 해시하면 안 되나요? → 프로세스마다 값이 달라질 수 있어서 안 돼요. 어디서 계산해도 같은 값이 나오는 해시를 써야 해요.
</details>

<details>
<summary>Q. 핫스팟이 뭐고 어떻게 해결하나요?</summary>

**답변(30초)**
핫스팟은 요청이 특정 파티션 하나에 몰리는 거예요. 원인은 두 가지예요. 시각처럼 계속 커지는 키를 키 범위로 나누면 최신 구간에 몰리고, 이건 키 앞에 센서 ID 같은 값을 붙이거나 해시로 바꿔 풀어요. 유명인 ID처럼 같은 키 하나에 몰리면 해시로도 못 막아서, 그 키 뒤에 난수를 붙여 여러 키로 쪼개요. 대신 읽을 때 쪼갠 키를 다 모아 합쳐야 해서, 소수의 뜨거운 키에만 적용해요.

**꼬리질문**
- Q. DB가 알아서 해 주지 않나요? → 대부분은 못 해서 애플리케이션이 처리해야 해요.
- Q. 읽기 핫스팟이라면? → 쓰기 분산 대신 캐시나 읽기 복제본으로 읽기를 덜어 주는 쪽을 먼저 검토할 수 있어요.
</details>

<details>
<summary>Q. 샤드 키는 어떻게 고르나요?</summary>

**답변(30초)**
두 가지를 봐요. 첫째, 데이터와 요청이 고르게 퍼지는가. 시각처럼 한쪽으로 몰리는 키나 소수 값에 몰리는 키는 피해요. 둘째, 가장 자주 하는 조회가 샤드 하나에서 끝나는가. 예를 들어 "내 주문 목록"이 핵심이면 회원 ID로 나눠야 한 샤드에서 끝나요. 이 두 기준이 부딪히면 핵심 조회를 우선하고, 나머지는 보조 인덱스나 별도 조회 저장소로 풀어요.

**꼬리질문**
- Q. 샤드 키를 나중에 바꿀 수 있나요? → 모든 데이터를 다시 나눠 옮겨야 해서 매우 비싸요. 그래서 처음에 핵심 조회 패턴을 보고 신중히 골라요.
</details>

<details>
<summary>Q. hash(key) % N으로 샤드를 고르면 왜 안 되나요?</summary>

**답변(30초)**
노드 수 N이 바뀌면 거의 모든 키의 담당 노드가 바뀌기 때문이에요. 노드 4대에서 5대로 늘리면 이론상 약 80%의 키가 이사해요. 실제로 키 1만 개로 재 보니 79.6%가 옮겨졌어요. 새 노드 몫인 20%만 옮기면 될 일을 네 배로 하는 셈이고, 캐시라면 적중률이 폭락해요. 그래서 고정 파티션 수나 안정 해시처럼 필요한 만큼만 옮기는 방식을 써요.

**꼬리질문**
- Q. 고정 파티션 수는 왜 덜 옮기나요? → 키→파티션 대응은 그대로고 파티션→노드 대응만 바뀌어서, 새 노드에 줄 파티션만 통째로 옮기면 돼요.
- Q. Redis Cluster는? → 키를 해시 슬롯 16384개로 나누고 슬롯을 노드에 배분해요. 노드를 늘리면 슬롯 일부만 옮겨요.
</details>

<details>
<summary>Q. Consistent Hashing을 설명해 주세요. 가상 노드는 왜 쓰나요?</summary>

**답변(30초)**
노드와 키를 같은 원형 해시 공간에 올려 두고, 키는 시계 방향으로 처음 만나는 노드가 맡는 방식이에요. 노드가 추가되면 그 바로 앞 구간 키만 옮겨져서 이동량이 작아요. 그런데 노드당 점이 하나면 구간 길이가 제각각이라 부하가 크게 쏠려요. 그래서 노드 하나를 여러 점으로 올리는 가상 노드를 써요. 재 보니 가상 노드 100개일 때 22.5%만 옮겨지고 부하도 고르게 나뉘었어요.

**꼬리질문**
- Q. 여기서 "일관성"은 데이터 일관성인가요? → 아니요. 노드가 바뀌어도 배치가 대부분 유지된다는 뜻이고, CAP·ACID의 일관성과는 무관해요.
- Q. 가상 노드가 1개면 어떻게 되나요? → 한 번 재 본 예시에서 노드별 키가 174개부터 4974개까지 벌어졌어요.
</details>

<details>
<summary>Q. 샤딩된 DB에서 보조 인덱스 조회는 어떻게 하나요?</summary>

**답변(30초)**
로컬 인덱스와 글로벌 인덱스 두 방식이 있어요. 로컬은 파티션마다 자기 데이터만 인덱싱해서 쓰기는 간단하지만, 읽을 땐 모든 파티션에 물어서 합쳐야 하고 가장 느린 파티션에 끌려가요. 글로벌은 인덱스 자체를 값 기준으로 나눠서 읽기는 한 파티션만 보면 되지만, 쓰기가 여러 파티션을 건드리고 보통 비동기라 방금 쓴 데이터가 잠깐 안 보일 수 있어요.

**꼬리질문**
- Q. 글로벌 인덱스를 동기로 맞추면 안 되나요? → 여러 파티션을 한 번에 고치는 분산 트랜잭션이 필요해서 느리고 복잡해요. 그래서 보통 비동기예요.
</details>

<details>
<summary>Q. 클라이언트는 데이터가 어느 노드에 있는지 어떻게 아나요?</summary>

**답변(30초)**
세 방식이 있어요. 아무 노드에 보내면 그 노드가 담당 노드로 넘겨주거나, 라우팅 계층이 받아서 보내거나, 클라이언트가 배치표를 들고 직접 가요. 어느 쪽이든 배치가 바뀐 걸 알아야 해서, 보통 ZooKeeper 같은 코디네이션 서비스에 배치표를 두고 구독하거나, Cassandra처럼 노드끼리 가십으로 퍼뜨려요.

**꼬리질문**
- Q. MongoDB는? → config server에 배치를 두고 mongos 라우터가 요청을 맞는 샤드로 보내요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 테이블이 너무 커져 샤딩하려고 해요. 샤드 키 후보는 회원 ID, 주문 ID, 주문 날짜예요. 무엇을 고르겠어요?</summary>

**상황 파악**
먼저 주문 테이블에서 가장 많이 일어나는 조회와 쓰기를 봐요. 보통 쓰기는 "주문 생성", 읽기는 "내 주문 목록(회원별 최근 주문)"과 "주문 상세"가 대부분이에요. 운영팀의 "날짜별 매출 집계"는 빈도는 낮지만 데이터를 넓게 읽어요.

**원인 후보(각 키의 위험)**
1. 주문 날짜: 키 범위로 나누면 새 주문이 모두 "오늘" 샤드에 몰려 쓰기 핫스팟이 생겨요.
2. 주문 ID 해시: 고르게 퍼지지만, "내 주문 목록"이 회원의 주문이 흩어진 모든 샤드로 퍼져요(스캐터/개더).
3. 회원 ID 해시: 한 회원의 주문이 한 샤드에 모여 "내 주문 목록"이 한 샤드에서 끝나요. 다만 주문이 아주 많은 대형 고객(법인 등)이 있으면 그 샤드가 뜨거울 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 회원 ID 해시 | 핵심 조회가 한 샤드에서 끝남, 쓰기도 고르게 | 주문 ID만으로 상세 조회 시 어느 샤드인지 모름, 대형 고객 쏠림 가능 |
| B. 주문 ID 해시 + 회원 ID 글로벌 인덱스 | 쓰기 분산 최고, 주문 상세 바로 찾음 | 인덱스가 비동기라 방금 한 주문이 목록에 늦게 보일 수 있음, 쓰기가 복잡 |
| C. 날짜 범위 | 날짜별 집계가 쉬움 | 오늘 샤드에 쓰기 집중, 서비스용 키로는 부적합 |

**내가 고를 방법**
A를 골라요. 사용자가 가장 자주 보는 화면이 한 샤드에서 끝나는 게 제일 중요해요. 주문 상세는 주문 ID 안에 회원 ID(또는 샤드 번호)를 넣어 발급하면 주문 ID만으로도 샤드를 찾을 수 있어요. 날짜별 매출 집계는 서비스 DB에서 하지 않고 분석용 저장소로 따로 보내요. 대형 고객 쏠림이 실제로 관측되면 그 고객만 키를 쪼개는 방식으로 대응해요. 노드 증설에 대비해 `hash % N` 대신 고정 파티션 수 방식으로 배치해요.

**채점 포인트**: 접근 패턴부터 분석, 날짜 범위 = 쓰기 핫스팟, 주문 ID = 회원별 조회가 스캐터/개더, 회원 ID = 핵심 조회 단일 샤드, 대형 고객 쏠림, 글로벌 인덱스의 비동기 지연, 집계는 별도 저장소, 리밸런싱 방식(mod N 회피).
</details>

<details>
<summary>상황: 유명인이 올린 게시글 하나에 좋아요·조회가 초당 수만 건 몰려, 그 게시글이 있는 샤드 하나만 CPU 100%예요. 어떻게 하겠어요?</summary>

**상황 파악**
다른 샤드는 한가한데 한 샤드만 터졌으니 전체 용량 부족이 아니라 **핫스팟**이에요. 원인은 게시글 ID 하나에 요청이 몰린 거예요. 쓰기(좋아요)와 읽기(조회) 중 무엇이 주범인지 먼저 나눠 봐요.

**원인 후보**
1. 샤드 키가 게시글 ID라 같은 키는 해시해도 늘 같은 샤드로 가요. 해시 파티셔닝으로는 못 막아요.
2. 좋아요 수를 한 행에서 계속 +1 하면 그 행에 쓰기 경합까지 겹쳐요.
3. 조회가 캐시 없이 DB로 바로 오면 읽기 부하도 그 샤드에 몰려요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 뜨거운 키 쪼개기(게시글ID_00~99) | 좋아요 쓰기가 100개 키로 흩어짐 | 좋아요 수를 읽을 때 100개를 합쳐야 함, 쪼갠 키 목록을 따로 관리 |
| B. 읽기는 캐시로 흡수 | 조회 부하를 DB에서 떼어 냄, 구현 쉬움 | 쓰기 핫스팟은 그대로, 캐시가 잠깐 옛값을 보여 줄 수 있음 |
| C. 샤드를 더 늘리기 | 간단해 보임 | 키 하나는 결국 한 샤드라 효과 없음 |

**내가 고를 방법**
읽기는 B로 캐시에서 흡수하고, 쓰기는 A로 해당 게시글의 좋아요 키만 쪼개요. 모든 게시글을 쪼개면 읽기 비용만 늘어나니, 요청량을 보고 임계치를 넘은 소수의 게시글만 쪼개고 그 목록을 기록해 둬요. 좋아요 수는 조금 늦게 맞아도 되는 값이라, 쪼갠 키를 주기적으로 합쳐 캐시에 올려 두는 식으로 읽기 비용도 줄여요. C는 원인이 "키 하나"라서 해결이 안 된다는 점을 꼭 짚어요.

**채점 포인트**: 전체 부족이 아닌 핫스팟으로 진단, 같은 키는 해시해도 같은 샤드, 키 쪼개기(난수 접미사)와 읽기 시 합산 비용, 소수 키에만 적용·목록 관리, 읽기는 캐시, 샤드 증설은 무효.
</details>

<details>
<summary>상황: 캐시 서버 4대를 hash(key) % 4로 쓰다가 1대를 추가했더니 캐시 적중률이 폭락하고 DB가 과부하에 걸렸어요. 원인과 대책은?</summary>

**상황 파악**
서버를 늘렸는데 오히려 느려졌어요. 증설 직후에 적중률이 떨어졌으니 증설 자체가 원인이에요. DB 과부하는 캐시를 못 찾은 요청이 전부 DB로 간 결과예요.

**원인 후보**
1. `hash % N`에서 N이 4→5로 바뀌면서 약 80%의 키가 다른 서버를 가리키게 됐어요. 한 번 재 본 예시에서도 79.6%가 바뀌었어요. 데이터는 옛 서버에 있는데 요청은 새 서버로 가니 대부분 캐시 미스가 나요.
2. 미스가 한꺼번에 DB로 몰려 DB가 과부하에 걸렸어요(캐시가 다시 채워질 때까지 계속).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 안정 해시 + 가상 노드 | 노드 추가 시 새 노드 몫(약 1/N)만 이동, 재 보니 22.5% | 가상 노드가 적으면 부하 쏠림, 구현·설정 필요 |
| B. 고정 슬롯(예: Redis Cluster 16384 슬롯) | 키→슬롯은 불변, 슬롯 일부만 옮김. 이동량을 운영자가 통제 | 슬롯 배치표를 관리하고 클라이언트가 알아야 함 |
| C. 그대로 두고 점진적으로 다시 채움 | 코드 변경 없음 | 다음 증설·장애 때마다 같은 사고 반복 |

**내가 고를 방법**
당장은 증설을 되돌리거나 트래픽이 적은 시간대로 미뤄 DB를 살려요. 근본 대책으로 A나 B로 바꿔요. 이미 Redis를 쓴다면 Redis Cluster의 해시 슬롯(B)이 가장 손이 덜 가고, 직접 노드를 고르는 클라이언트라면 가상 노드를 충분히 둔 안정 해시(A)를 써요. 가상 노드를 빼면 이동은 적어도 부하가 한 서버에 쏠린다는 점을 같이 말해요. 증설은 한 번에 하지 말고 단계적으로, 적중률과 DB 부하를 보며 진행해요.

**채점 포인트**: mod N에서 N 변경 → 대부분 키 재배치(약 80%), 캐시 미스 폭증 → DB 과부하 연결, 안정 해시(이동 약 1/N), 가상 노드 필요 이유(1개면 쏠림), 고정 슬롯 방식, 즉시 완화책과 근본책 구분.
</details>

## 필기 포인트

- 파티셔닝 = 샤딩. 레코드 하나는 정확히 한 파티션에 속함. 목적은 **확장성**.
- 파티셔닝(다른 데이터 나눠 담기) ≠ 복제(같은 데이터 여러 벌) ≠ 네트워크 파티션(장애).
- 키 범위: 범위 조회 유리, 시간 키면 핫스팟. 해시: 고른 분산, 범위 조회 불리.
- 같은 키에 몰리는 핫스팟은 해시로도 못 막음 → 키에 난수 붙여 쪼개기(읽기 때 합산).
- `hash % N`: N이 바뀌면 거의 모든 키 이동(4→5대면 약 80%).
- 고정 파티션 수: 키→파티션 불변, 파티션→노드만 변경. Redis Cluster 16384 해시 슬롯.
- consistent hashing의 "consistent" ≠ CAP·ACID 일관성. 가상 노드로 부하 불균형 완화.
- 로컬 인덱스 = 쓰기 쉬움·읽기 스캐터/개더. 글로벌 인덱스 = 읽기 쉬움·쓰기 복잡·보통 비동기.
- 자동 리밸런싱 + 자동 장애 감지 = 연쇄 장애 위험.
