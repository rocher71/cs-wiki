:::tip[한 줄 요약]
**복제 지연**은 레플리카(읽기용 복사본 DB)가 리더(쓰기를 받는 원본 DB)보다 **조금 늦게** 변경을 받는 현상이에요. 그래서 "방금 쓴 글이 안 보임", "새로고침마다 댓글이 보였다 사라짐" 같은 일이 생겨요. 해결은 모든 읽기를 리더로 보내는 게 아니라, **쓴 본인은 리더에서 읽게 하기**(read-your-writes), **한 사용자는 같은 레플리카에서 읽게 하기**(단조 읽기)처럼 **필요한 보장만 골라** 더하는 거예요.
:::

:::note[처음이라면 여기까지]
① 읽기를 나눠 받으려고 DB 복사본(레플리카)을 여러 대 두면, 복사본은 원본보다 조금씩 늦게 따라와요. 이게 **복제 지연**이에요.

② 그래서 글을 쓰고 바로 복사본에서 읽으면 "내 글이 없다"가 생겨요. 데이터가 사라진 게 아니라 아직 도착 안 한 거예요.

③ 흔한 해결은 "방금 쓴 사람은 잠깐 원본에서 읽게 하기"예요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

단톡방에 메시지를 보냈는데, 친구 폰에는 몇 초 늦게 뜨는 경우가 있죠. 서버(리더)에는 이미 들어갔지만, 친구 폰(레플리카)까지 전달되는 데 시간이 걸린 거예요.

이상한 건 **내 폰이 두 대**일 때예요. 폰 A로 메시지를 보내고 폰 B를 열었더니 내 메시지가 없어요. "보냈는데 왜 없지?" 하고 다시 보내면 메시지가 두 번 올라가요.

더 헷갈리는 경우도 있어요. 폰 B를 켰다 끌 때마다 다른 기지국을 거쳐 받는다고 해 봐요. 어떤 때는 친구 답장이 보이고, 다음엔 안 보였다가, 그다음엔 또 보여요. 시간이 거꾸로 가는 것처럼 느껴지죠.

DB 복제도 똑같아요. 리더가 받은 쓰기가 레플리카들에 퍼지는 데 시간이 걸리고, 레플리카마다 늦는 정도가 달라요.

단, 실제로는 단톡방과 달리 사용자가 "어느 레플리카에서 읽을지" 고르지 않아요. 서버 코드나 설정이 정하기 때문에, 이 문제는 **백엔드 개발자가 설계로 막아야** 해요.

## 제대로 알기

### 왜 레플리카에서 읽나: 읽기 확장

**리더 기반 복제**에서는 쓰기를 **리더**(leader, 원본) 한 곳만 받고, 그 변경을 **팔로워**(follower, = 레플리카, 복사본)들이 따라 적용해요. 읽기는 아무 복제본에서나 받을 수 있어요. → [복제](../replication/)

웹 서비스는 대부분 쓰기보다 읽기가 훨씬 많아요. 그래서 레플리카를 여러 대 두고 읽기를 나눠 받게 하는 **읽기 확장**(read scaling)을 많이 써요.

그런데 레플리카가 많을수록 **동기 복제**(모든 복사본이 받았다고 답해야 쓰기 완료)는 현실적이지 않아요. 한 대만 죽어도 쓰기가 멈추니까요. 그래서 읽기 확장은 사실상 **비동기 복제**(리더는 먼저 완료하고, 복사본은 뒤따라 받음)와 함께 써요. 복제 지연은 여기서 생겨요.

### 복제 지연과 최종적 일관성

비동기 레플리카는 리더보다 뒤처질 수 있어요. 그래서 같은 쿼리를 리더와 레플리카에 보내면 결과가 다를 수 있어요. 쓰기를 멈추고 기다리면 결국 레플리카가 따라잡는데, 이걸 **최종적 일관성**(eventual consistency, 지금은 어긋나도 결국 맞춰짐)이라고 해요. MySQL 레플리카처럼 비동기 복제를 쓰는 관계형 DB도 같은 성질이에요.

주의할 점은 "결국"에 **시간 상한이 없다**는 거예요. 평소엔 눈치채기 어려울 만큼 짧지만, 서버가 한계 가까이 바쁘거나 네트워크에 문제가 있으면 수 초에서 수 분까지 늘 수 있어요.

<Aside type="caution" title="복제 지연 = 데이터 유실?">
아니에요. 아직 안 넘어갔을 뿐이고, 기다리면 맞춰져요. 다만 그 사이 리더가 죽고 늦은 레플리카가 새 리더가 되면 실제로 잃을 수 있는데, 이건 [복제](../replication/)의 장애 조치(failover) 주제예요.
</Aside>

### 복제 지연이 만드는 이상 현상 3가지

| 이름 | 사용자가 겪는 일 | 지켜야 할 약속 | 대표 해결 |
|---|---|---|---|
| **자신이 쓴 내용 읽기** 위반 (read-your-writes) | 글을 쓰고 새로고침했더니 내 글이 없음 | **쓴 본인**에게는 자기 변경이 항상 보여야 함 | 내가 고칠 수 있는 데이터·쓴 직후엔 리더에서 읽기 |
| **단조 읽기** 위반 (monotonic reads) | 새로고침마다 댓글이 보였다 사라졌다 함 | 한 번 본 데이터보다 **더 옛날 데이터**를 보면 안 됨 | 사용자마다 항상 같은 레플리카에서 읽기 |
| **일관된 순서로 읽기** 위반 (consistent prefix reads) | 질문보다 대답이 먼저 보임 | A→B 순서로 쓰였으면 누구나 **A→B 순서로** 봐야 함 | 순서가 중요한 쓰기를 같은 파티션에 넣기 |

하나씩 볼게요.

**① 자신이 쓴 내용 읽기**: "새로고침해도 **내가 제출한 변경**은 항상 보인다"는 보장이에요. read-after-write consistency라고도 해요. **다른 사람**의 글은 조금 늦게 보여도 위반이 아니에요.

**② 단조 읽기**: **단조**(monotonic)는 "한 방향으로만 간다"는 뜻이에요. 새로고침할 때마다 요청이 랜덤하게 다른 레플리카로 가면, 앞선 레플리카에서 새 데이터를 봤다가 뒤처진 레플리카에서 옛 데이터를 볼 수 있어요. 이 시간 역전을 막는 보장이에요. 모든 사용자가 항상 최신을 보는 **강한 일관성**보다는 약하고, 최종적 일관성보다는 강해요.

**③ 일관된 순서로 읽기**: 데이터를 여러 **파티션**(샤드, 데이터를 나눠 담은 조각)에 나눠 담고, 파티션마다 따로 복제하면 전체 순서가 보장되지 않아요. 질문은 복제가 느린 파티션에, 대답은 빠른 파티션에 있으면 구경하는 사람에겐 대답이 먼저 보여요. → [파티셔닝](../partitioning/)

### 해결책 비교 (read-your-writes 중심)

| 방법 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| A. 내가 고칠 수 있는 데이터는 리더에서 | 내 프로필은 리더, 남의 프로필은 레플리카 | 단순 | 사용자가 고칠 수 있는 데이터가 많으면 대부분 리더로 가서 읽기 확장 효과가 사라짐 |
| B. 쓴 직후 일정 시간은 리더에서 | 서버에 "이 사용자 마지막 쓰기 시각"을 기록, N초 안이면 리더로 | 구현이 쉬움, 대부분의 읽기는 여전히 레플리카 | N을 넘는 지연엔 못 막음, 쓰기 많은 사용자는 리더 부하 |
| C. 레플리카가 따라잡을 때까지 기다리기 | 마지막 쓰기의 위치(로그 위치·GTID 같은 논리적 표시)를 기억했다가, 그만큼 반영된 레플리카에서만 읽음 | 가장 정확함 | 구현이 복잡, 기다리는 시간만큼 응답이 늦어질 수 있음 |
| D. 모든 읽기를 리더로 | 레플리카를 읽기에 안 씀 | 문제 자체가 없음 | 읽기 확장 포기 |

B의 "마지막 쓰기 시각"을 **사용자 기기에만** 저장하면 안 돼요. PC에서 프로필을 바꾸고 폰으로 보면 폰은 그 시각을 모르거든요. 이렇게 **기기가 달라도** 지켜야 하면 시각을 **서버 쪽 중앙**(세션 저장소·Redis 등)에 둬야 해요. 데이터센터가 여러 곳이면 두 기기의 요청이 같은 곳으로 간다는 보장도 없어서 리더가 있는 곳으로 보내는 처리도 필요해요.

단조 읽기는 **사용자 ID를 해시해서 레플리카를 고르는** 식으로 같은 사용자를 늘 같은 레플리카에 붙여요. 그 레플리카가 죽으면 다른 곳으로 다시 보내야 해요.

### 심화: MySQL에서 지연 확인하기

레플리카에서 `SHOW REPLICA STATUS`를 실행하면 `Seconds_Behind_Source` 값이 나와요. 레플리카의 **SQL(applier) 스레드**(받은 변경을 실제로 적용하는 일꾼)가 원본의 변경 기록(**바이너리 로그**)을 처리하는 데 **몇 초 뒤처졌는지**예요. 즉 "받는 데 늦은 시간"이 아니라 **"적용하는 데 늦은 시간"이에요.**

```sql
-- 레플리카에서 실행 (MySQL 8.4 기준)
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source: 적용이 몇 초 뒤처졌나

-- 연결이 살아 있는지는 하트비트 시각으로 확인
SELECT LAST_HEARTBEAT_TIMESTAMP
FROM performance_schema.replication_connection_status;
```

이 값을 그대로 믿으면 안 되는 이유가 MySQL 문서에 나와 있어요.

- **0이라고 다 따라잡은 게 아니에요.** 원본과의 네트워크가 끊겨도, 받는 쪽 **I/O(receiver) 스레드**가 `replica_net_timeout`이 지날 때까지 끊긴 걸 모를 수 있어요. 그동안 0으로 보일 수 있어요.
- 새 이벤트를 받는 순간 0과 큰 수 사이를 오갈 수 있어요.
- 그래서 문서는 상태 확인에 **Performance Schema 복제 테이블**을, 연결 확인에는 **하트비트**를 쓰라고 해요. 하트비트 주기(`SOURCE_HEARTBEAT_PERIOD`) 기본값은 `replica_net_timeout`의 절반이에요.

<Aside type="note" title="문서로 직접 확인하지 못한 일반 지식">
복제가 멈추면 이 값이 NULL로 나온다, 시계 차이에 영향받는다는 이야기와, 그래서 리더에 주기적으로 현재 시각을 쓰고 레플리카에서 읽어 지연을 재는 **하트비트 테이블** 방식(pt-heartbeat 같은 도구)을 쓴다는 이야기가 실무에서 많이 언급돼요. 이 페이지 작성 때 공식 문서 문장으로는 확인하지 못했으니, 면접에선 "그렇게 알고 있다" 정도로 말하세요.
</Aside>

### 심화: GTID로 "따라잡을 때까지 기다리기"

해결책 C를 MySQL로 구현하는 방법이에요. **GTID**(Global Transaction ID)는 트랜잭션마다 붙는 전역 번호예요. `WAIT_FOR_EXECUTED_GTID_SET(gtid_set, timeout)`은 레플리카가 그 GTID들을 모두 적용할 때까지 기다리고, **0이면 성공, 1이면 타임아웃**을 돌려줘요. timeout을 안 주면 끝까지 기다려요.

```sql
-- 쓰기 후 받아 둔 GTID로, 레플리카에서 최대 1초 기다림
SELECT WAIT_FOR_EXECUTED_GTID_SET('<쓰기 트랜잭션의 GTID>', 1);
-- 0 → 레플리카에서 읽기 / 1(타임아웃) → 리더에서 읽기
```

어려운 부분은 "**내** 마지막 쓰기의 GTID"를 얻는 거예요. `@@GLOBAL.gtid_executed`는 서버 전체 값이라 동시에 여러 요청이 쓰면 내 것을 특정할 수 없어요. 세션 단위로 받아오는 방법은 드라이버·설정에 따라 달라서 쓰는 환경 문서를 확인해야 해요.

<Aside type="caution" title="반동기(semi-sync) 복제로 바꾸면 끝?">
MySQL 기본은 비동기예요. 반동기 복제는 "레플리카가 받았다"까지만 기다리고 "적용했다"까지는 보장하지 않는다고 알려져 있는데, 이 페이지에선 공식 문서로 확인하지 못했어요. 완전 동기 복제는 한 대만 죽어도 쓰기가 멈추는 가용성 손해가 있어요.
</Aside>

### 심화: 스프링 읽기/쓰기 분리와 함정

스프링에선 보통 `AbstractRoutingDataSource`로 읽기/쓰기 DB를 나눠요. 커넥션을 달라는 요청(`getConnection()`)이 오면 `determineCurrentLookupKey()`가 고른 키로 실제 DB를 골라 줘요. 키가 없으면 기본 DB로 가요.

```java
public class ReplicationRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        // 지금 트랜잭션이 readOnly면 레플리카, 아니면 리더
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                ? "replica" : "primary";
    }
}
```

**함정 1: 이것만으론 전부 리더로 가요.** 스프링 트랜잭션 매니저는 트랜잭션을 시작할 때 **커넥션을 먼저 얻고**(`doBegin`), **그다음에** readOnly 표시를 스레드에 등록해요(`prepareSynchronization`). 라우팅 시점엔 readOnly가 아직 false라 늘 `primary`가 골라져요.

**해결: `LazyConnectionDataSourceProxy`로 감싸기.** 실제 커넥션 획득을 **첫 쿼리 직전**까지 미뤄 줘서, 그때는 readOnly 표시가 등록돼 있어요. Spring 6.1.2부터는 `LazyConnectionDataSourceProxy.setReadOnlyDataSource()`로 readOnly 트랜잭션용 DB를 직접 지정할 수도 있어요.

```java
@Bean @Primary
public DataSource dataSource(DataSource routingDataSource) {
    // 커넥션을 첫 쿼리 때 얻도록 미룸 → 그때 readOnly 보고 라우팅
    return new LazyConnectionDataSourceProxy(routingDataSource);
}
```

**함정 2: 라우팅이 잘 될수록 read-your-writes가 깨져요.** `@Transactional` 쓰기 메서드가 끝난 직후 `@Transactional(readOnly = true)` 조회가 레플리카로 가면, 복제 지연 때문에 방금 쓴 값이 안 보여요. 쓰기 트랜잭션 **안에서** 이어 읽는 건 같은 리더 커넥션이라 괜찮아요.

**함정 3: 전파(propagation).** 바깥이 쓰기 트랜잭션이면 안쪽 `readOnly = true` 메서드(기본 전파 REQUIRED)는 바깥 트랜잭션·커넥션에 **참여**해서 레플리카로 안 가요. 반대로 바깥이 readOnly면 안쪽 쓰기 메서드도 레플리카 커넥션을 쓰게 돼서, 레플리카가 읽기 전용이면 에러가 나요. → [@Transactional 동작 원리](../../spring/transactional/)

<details>
<summary>Q. 복제 지연이란 무엇이고, 왜 생기나요?</summary>

**답변(30초)**
레플리카가 리더의 변경을 늦게 반영해서 둘의 데이터가 잠시 어긋나는 현상이에요. 읽기를 나누려고 레플리카를 여러 대 두면, 모두 동기로 복제할 경우 한 대만 죽어도 쓰기가 멈추니까 보통 비동기 복제를 써요. 비동기라 레플리카는 뒤처질 수 있고, 기다리면 결국 맞춰지는 최종적 일관성이에요. 평소엔 짧지만 부하나 네트워크 문제가 있으면 수 초에서 수 분까지 늘 수 있어요.

**꼬리질문**
- Q. 복제 지연이면 데이터가 유실된 건가요? → 아니요, 아직 안 넘어간 것뿐이에요. 다만 그 사이 리더가 죽고 늦은 레플리카가 승격되면 유실될 수 있어요.
- Q. 동기 복제로 바꾸면 되지 않나요? → 지연 문제는 줄지만 레플리카 하나만 느리거나 죽어도 쓰기가 막혀 가용성을 잃어요.
</details>

<details>
<summary>Q. 레플리카로 읽기를 분산했더니 "방금 쓴 글이 안 보인다"는 문의가 왔어요. 원인과 해결은?</summary>

**답변(30초)**
쓰기는 리더에 했는데 바로 이어진 조회가 아직 변경을 못 받은 레플리카로 가서예요. 자신이 쓴 내용 읽기(read-your-writes) 보장이 깨진 거예요. 해결은 쓴 직후 일정 시간 동안 그 사용자의 조회를 리더로 보내거나, 내 프로필처럼 본인이 고치는 데이터는 리더에서 읽는 거예요. 더 정확히 하려면 쓰기의 GTID를 기억했다가 레플리카가 그만큼 따라잡았는지 확인하고 읽어요.

**꼬리질문**
- Q. 다른 사용자에게도 즉시 보여야 하나요? → 아니요, read-your-writes는 쓴 본인에게만 보장해요. 다른 사람에겐 늦게 보여도 돼요.
- Q. PC에서 쓰고 폰에서 보면요? → 마지막 쓰기 시각을 기기 말고 서버 쪽(세션 저장소·Redis 등)에 둬야 다른 기기도 알 수 있어요.
</details>

<details>
<summary>Q. read-your-writes, 단조 읽기, 일관된 순서로 읽기의 차이는?</summary>

**답변(30초)**
read-your-writes는 내가 쓴 건 나에게 항상 보이는 보장이에요. 단조 읽기는 한 번 본 데이터보다 옛날 데이터를 다시 보지 않는 보장이고, 새로고침마다 다른 레플리카로 가서 생기는 시간 역전을 막아요. 일관된 순서로 읽기는 A 다음 B로 쓰였으면 누구나 그 순서로 보는 보장이에요. 질문보다 대답이 먼저 보이는 걸 막고, 주로 파티션별로 따로 복제할 때 문제가 돼요.

**꼬리질문**
- Q. 단조 읽기는 어떻게 보장하나요? → 사용자 ID 해시 등으로 같은 사용자는 항상 같은 레플리카에서 읽게 해요. 그 레플리카가 죽으면 다른 곳으로 재라우팅해요.
- Q. 일관된 순서는요? → 인과관계 있는 쓰기를 같은 파티션에 넣는 방법이 있어요.
</details>

<details>
<summary>Q. "쓴 직후엔 리더에서 읽기" 방식의 단점은?</summary>

**답변(30초)**
리더 부하가 늘고, 정한 시간보다 지연이 길어지면 여전히 못 막아요. 특히 "사용자가 고칠 수 있는 데이터는 전부 리더에서" 식으로 넓게 적용하면 대부분의 읽기가 리더로 가서 레플리카를 둔 의미가 사라져요. 그래서 적용 범위를 방금 쓴 사용자, 방금 바뀐 데이터로 좁히고, 지연이 큰 레플리카는 읽기 대상에서 빼는 것도 같이 해요.

**꼬리질문**
- Q. 시간 기준 말고 더 정확한 방법은? → 마지막 쓰기의 논리적 위치(GTID)를 기억했다가, 레플리카가 거기까지 적용했는지 `WAIT_FOR_EXECUTED_GTID_SET`으로 확인하고 읽어요.
</details>

<details>
<summary>Q. MySQL에서 복제 지연은 어떻게 확인하나요? Seconds_Behind_Source를 믿어도 되나요?</summary>

**답변(30초)**
`SHOW REPLICA STATUS`의 `Seconds_Behind_Source`로 볼 수 있는데, 이건 레플리카가 받은 변경을 적용하는 게 몇 초 늦었는지예요. 그대로 믿으면 안 돼요. 네트워크가 끊겨도 타임아웃 전까진 0으로 보일 수 있고, 값이 0과 큰 수 사이를 튈 수 있어요. 그래서 Performance Schema 복제 테이블과 하트비트 시각을 같이 보고, 실무에선 리더에 주기적으로 시각을 쓰고 레플리카에서 읽어 지연을 재는 방식도 쓴다고 알고 있어요.

**꼬리질문**
- Q. 0이면 안전한가요? → 아니요. 수신 스레드가 끊김을 늦게 알아채는 동안 0일 수 있어요. 하트비트 시각도 확인해야 해요.
</details>

<details>
<summary>Q. 스프링에서 읽기/쓰기 DB를 나누는 방법과 주의점은?</summary>

**답변(30초)**
`AbstractRoutingDataSource`에서 트랜잭션이 readOnly면 레플리카, 아니면 리더를 고르게 해요. 그런데 트랜잭션 매니저가 커넥션을 먼저 얻고 나서 readOnly 표시를 등록하기 때문에, 그냥 쓰면 전부 리더로 가요. 그래서 `LazyConnectionDataSourceProxy`로 감싸 커넥션 획득을 첫 쿼리 때로 미뤄요. 또 쓰기 직후 readOnly 조회가 레플리카로 가면 방금 쓴 값이 안 보일 수 있으니, 그런 조회는 리더로 보내야 해요.

**꼬리질문**
- Q. 쓰기 트랜잭션 안에서 readOnly 메서드를 부르면? → 기본 전파 REQUIRED라 바깥 트랜잭션 커넥션(리더)을 그대로 써요.
- Q. 스프링 버전에 따라 달라진 점은? → 6.1.2부터 `LazyConnectionDataSourceProxy.setReadOnlyDataSource()`로 readOnly용 DB를 직접 지정할 수 있어요.
</details>

## 서술형 연습

<details>
<summary>상황: 커뮤니티 서비스에서 글을 쓰고 목록으로 돌아가면 방금 쓴 글이 없다는 문의가 들어와요. 몇 초 뒤 새로고침하면 보여요. 최근에 DB 레플리카를 추가해 조회를 분산했어요. 원인과 해결 방법은?</summary>

**상황 파악**
"몇 초 뒤엔 보인다"는 데이터가 사라진 게 아니라 늦게 도착한다는 뜻이에요. 레플리카 추가와 시기가 겹치므로, 글 저장은 리더에, 목록 조회는 레플리카에 가는 구조에서 생긴 **read-your-writes 위반**으로 봐요.

**원인 후보**
1. 비동기 복제라 저장 직후 레플리카에 아직 글이 반영 안 됨(복제 지연).
2. 트래픽이 몰려 레플리카 지연이 평소보다 커졌음. `Seconds_Behind_Source`만 보면 0으로 보여 놓쳤을 수 있음.
3. 조회 응답이 캐시에 남아 옛 목록을 보여 줌(같은 종류의 문제라 같이 확인).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 글 쓴 사용자는 N초 동안 조회를 리더로(마지막 쓰기 시각을 Redis 등 서버 쪽에 저장) | 구현이 쉽고, 나머지 사용자의 읽기는 계속 레플리카 | 지연이 N초를 넘으면 못 막음, 리더 부하 약간 증가 |
| B. 저장 시 GTID를 받아 두고, 조회 전 레플리카에서 `WAIT_FOR_EXECUTED_GTID_SET(gtid, 1)`, 타임아웃이면 리더로 | 지연 시간과 상관없이 정확 | 내 쓰기의 GTID를 받아 오는 방법이 환경마다 다르고 구현이 복잡, 대기만큼 응답 지연 |
| C. 저장 응답에 새 글 데이터를 담아 화면에 바로 붙이기 | DB 조회 없이 즉시 보임 | 그 화면만 해결, 다른 화면·기기에선 그대로 |

**내가 고를 방법**
먼저 A를 적용해요. 커뮤니티는 대부분 읽기이고, 글을 쓴 소수 사용자만 잠깐 리더로 보내면 읽기 확장 효과를 거의 유지하면서 문의를 없앨 수 있어요. 마지막 쓰기 시각을 서버 쪽에 두어 PC에서 쓰고 앱에서 봐도 보이게 해요. N은 측정한 평소 지연보다 넉넉하게 잡고, 하트비트로 지연을 모니터링해 N을 넘는 레플리카는 읽기 대상에서 빼요. 결제처럼 "안 보이면 다시 시도해서 중복이 생기는" 화면은 B까지 적용해요.

**채점 포인트**: read-your-writes 위반 진단, 비동기 복제·최종적 일관성, 쓴 본인에게만 보장하면 됨, 리더 라우팅(시간 기준) + 서버 쪽 저장(기기 간), GTID 대기 방식, 리더 부하 트레이드오프, 지연 모니터링(Seconds_Behind_Source 한계), 지연 큰 레플리카 제외.
</details>

<details>
<summary>상황: 게시글 상세 화면에서 새로고침할 때마다 댓글 수가 12 → 11 → 12 → 11처럼 늘었다 줄었다 해요. 댓글을 지운 사람은 없어요. 원인과 해결 방법은?</summary>

**상황 파악**
지운 사람이 없는데 숫자가 줄었다가 다시 늘어요. 한 사용자가 새 데이터를 본 뒤 옛 데이터를 보는 **시간 역전**, 즉 **단조 읽기 위반**이에요.

**원인 후보**
1. 로드밸런서나 라우팅이 요청마다 레플리카를 랜덤으로 골라, 최신인 레플리카 A와 뒤처진 레플리카 B를 번갈아 읽음.
2. 특정 레플리카 하나만 유독 지연이 큼(부하 집중, 네트워크 문제).
3. 캐시 서버 여러 대가 서로 다른 시점의 값을 갖고 있음(같은 모양의 문제라 같이 확인).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 사용자 ID 해시로 레플리카 고정 | 같은 사용자는 늘 같은 레플리카라 숫자가 거꾸로 가지 않음 | 레플리카가 죽으면 재라우팅 필요, 그 순간엔 역전 가능. 사용자가 고르게 안 퍼지면 부하 쏠림 |
| B. 지연이 큰 레플리카를 읽기 대상에서 제외 | 원인 2에 직접 효과, 전체 사용자의 체감 개선 | 지연이 작아질 뿐 0은 아니라 역전 자체를 보장하진 못함 |
| C. 댓글 수 같은 화면은 리더에서 읽기 | 항상 최신 | 인기 글이면 리더 부하가 큼 |

**내가 고를 방법**
A를 기본으로 해요. 단조 읽기는 "같은 사용자가 같은 복제본을 보면" 지켜지므로 비용 대비 효과가 커요. 레플리카 장애 시엔 다른 레플리카로 넘기는데, 이때 잠깐 역전이 생길 수 있다는 걸 받아들여요. 함께 B로 지연 모니터링을 붙여 한 레플리카만 뒤처지는 상황을 줄여요. 댓글 수는 다른 사람의 변경이라 몇 초 늦게 보이는 건 괜찮으므로 C처럼 리더로 보낼 필요까지는 없다고 판단해요.

**채점 포인트**: 단조 읽기 위반 진단(시간 역전), 랜덤 레플리카 라우팅이 원인, 사용자별 레플리카 고정(해시), 장애 시 재라우팅, 지연 큰 레플리카 제외, read-your-writes와 구분(남의 변경은 늦어도 됨), 리더 부하 트레이드오프.
</details>

<details>
<summary>상황: 스프링에서 AbstractRoutingDataSource로 readOnly면 레플리카로 가게 만들고 조회 메서드에 @Transactional(readOnly = true)를 붙였어요. 그런데 레플리카 모니터링을 보니 쿼리가 거의 안 들어와요. 원인과 해결 방법은?</summary>

**상황 파악**
라우팅 코드는 있는데 레플리카로 안 간다면, **라우팅 키를 고르는 시점**에 readOnly가 true로 안 보이고 있다는 뜻이에요.

**원인 후보**
1. 트랜잭션 매니저가 `doBegin`에서 커넥션을 먼저 얻고, 그 뒤 `prepareSynchronization`에서 readOnly를 등록함. 라우팅 시점엔 readOnly가 false라 리더로 감. `LazyConnectionDataSourceProxy`가 빠졌을 가능성이 가장 높아요.
2. 조회 메서드가 쓰기 트랜잭션 안에서 호출되어, 기본 전파 REQUIRED로 바깥 커넥션(리더)에 참여함.
3. 같은 클래스 안에서 자기 메서드를 직접 불러 프록시를 안 거쳐 `@Transactional(readOnly = true)` 자체가 적용 안 됨. → [@Transactional](../../spring/transactional/)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 라우팅 DataSource를 `LazyConnectionDataSourceProxy`로 감싸기 | 기존 라우팅 코드 그대로, 첫 쿼리 때 readOnly 보고 라우팅 | 설정이 한 겹 늘어 흐름을 이해해야 함 |
| B. Spring 6.1.2+면 `LazyConnectionDataSourceProxy.setReadOnlyDataSource()`로 레플리카 지정 | 라우팅 클래스를 직접 안 만들어도 됨 | 버전 제약, 레플리카 여러 대 분산은 따로 처리 |
| C. 서비스 구조 정리(조회를 쓰기 트랜잭션 밖으로, 자기 호출 제거) | 원인 2·3 해결 | 코드 수정 범위가 큼 |

**내가 고를 방법**

## 필기 포인트

- 읽기 확장(레플리카로 읽기 분산)은 사실상 **비동기 복제** 전제 → 복제 지연 → **최종적 일관성**(시간 상한 없음).
- **read-your-writes** = 쓴 **본인**에게만 보장. 다른 사용자는 늦어도 위반 아님.
- **단조 읽기** = 시간 역전 금지. 강한 일관성보다 약하고 최종적 일관성보다 강함. 해결: 사용자별 같은 복제본.
- **일관된 순서로 읽기** = 쓰기 순서(인과)대로 보임. 파티션별 독립 복제에서 문제.
- MySQL `Seconds_Behind_Source` = **적용** 지연. 0이어도 연결 끊김일 수 있음.
- `WAIT_FOR_EXECUTED_GTID_SET` 반환: 0 성공, 1 타임아웃.
- 스프링: 커넥션 획득 → readOnly 등록 순서 → `LazyConnectionDataSourceProxy` 필요. 6.1.2+ `setReadOnlyDataSource()`.
