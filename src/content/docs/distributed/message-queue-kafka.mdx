:::tip[한 줄 요약]
**메시지 큐**는 보내는 쪽(생산자)과 받는 쪽(소비자) 사이에서 메시지를 맡아 두는 서버예요. RabbitMQ 같은 전통 큐는 소비자가 가져가면 **지우고**, Kafka는 디스크 **로그에 남겨 두고** 소비자마다 "어디까지 읽었나"(**오프셋**)만 기록해요. Kafka의 순서 보장은 **파티션 안에서만**이고 기본 전달 보장은 **최소 한 번**(at-least-once)이라, 소비자는 같은 메시지를 두 번 받아도 괜찮게 만들어야 해요.
:::

:::note[처음이라면 여기까지]
① 메시지 큐는 "일을 맡겨 두는 우편함"이에요. 보내는 서버는 맡기고 바로 다음 일을 하고, 받는 서버는 자기 속도로 꺼내 처리해요.

② 전통 큐는 꺼내면 사라지는 편지, Kafka는 게시판 공지예요. Kafka는 읽어도 안 지우고, 읽는 쪽마다 책갈피(오프셋)만 옮겨요.

③ 같은 주문의 이벤트 순서를 지키려면 주문 ID를 **키**로 보내요. 같은 키는 같은 칸(파티션)에 들어가고, 순서는 칸 안에서만 지켜져요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

**전통 큐는 우체통**이에요. 편지를 넣으면 집배원 중 한 명이 꺼내 가요. 꺼낸 편지는 우체통에서 사라지니까, 나중에 온 집배원은 그 편지를 볼 수 없어요.

**Kafka는 게시판**이에요. 공지를 붙이면 떼지 않아요. 총무팀도 보고 인사팀도 보는데, 팀마다 **책갈피**를 갖고 "우리는 7번 공지까지 읽었다"를 따로 기록해요. 한 팀이 읽었다고 다른 팀이 못 보는 일은 없어요. 놓친 게 있으면 책갈피를 뒤로 옮겨 다시 읽을 수도 있어요.

게시판이 너무 길어지면 한 판에 다 못 붙이니까 **게시판을 여러 개**(파티션)로 나눠요. 같은 사람 관련 공지는 늘 같은 게시판에 붙이기로 정하면, 그 사람 공지는 붙인 순서대로 읽혀요. 하지만 게시판끼리는 "어느 쪽이 먼저 붙었나"를 알 수 없어요.

단, 실제 Kafka 게시판도 영원히 붙여 두진 않아요. 보관 기간(기본 7일)이 지나면 오래된 공지부터 떼요.

## 제대로 알기

### 왜 메시지 큐를 쓰나

주문이 들어오면 메일도 보내고, 포인트도 쌓고, 통계도 갱신해야 한다고 해 봐요. 주문 서버가 이걸 전부 직접 호출하면 메일 서버가 느릴 때 주문 응답도 같이 느려지고, 메일 서버가 죽으면 주문까지 실패해요.

**메시지 브로커**(message broker, = 메시지 큐)를 가운데 두면 달라져요.

- **비동기**: 주문 서버는 "브로커가 받았다"는 확인만 받고 바로 응답해요. 처리 완료는 기다리지 않아요.
- **버퍼**: 소비자가 잠깐 죽거나 느려도 메시지는 브로커에 쌓여 있다가 나중에 처리돼요. 트래픽이 몰릴 때 완충 역할도 해요.
- **느슨한 결합**: 주문 서버는 누가 이 메시지를 받는지 몰라도 돼요. 새 소비자(예: 추천 서비스)를 붙여도 주문 서버 코드는 그대로예요.

메시지를 잃지 않을 책임도 생산자·소비자에서 브로커로 옮겨 가요. 서비스 사이 통신 방식 전체 비교는 → [서비스 간 통신](../../architecture/service-communication/)

### 큐 방식 vs 로그 방식

| | 전통 큐 (RabbitMQ 등) | 로그 기반 (Kafka) |
|---|---|---|
| 소비 후 메시지 | 확인 응답(ack)을 받으면 **삭제** | **남겨 둠**, 보관 기간 지나면 삭제 |
| 소비 위치 기록 | 메시지마다 ack 상태 추적 | 파티션마다 **오프셋 숫자 하나** |
| 다시 읽기 | 불가(이미 지워짐) | 오프셋을 되돌리면 가능 |
| 순서 | 소비자 여럿 + 재전송이면 뒤바뀔 수 있음 | **파티션 안에서** 보장 |
| 병렬 처리 단위 | 메시지 하나씩 아무 소비자에게 | 파티션 하나를 소비자 한 명에게 |
| 잘 맞는 일 | 건당 처리가 무겁고 순서가 덜 중요(메일 발송 등) | 처리량이 크고 순서가 중요(이벤트 스트림) |

**확인 응답**(ack, acknowledgement)은 소비자가 "처리 끝났어요"라고 브로커에 알리는 신호예요. 전통 큐는 ack 전에 소비자 연결이 끊기면 그 메시지를 다른 소비자에게 다시 보내요. 그래서 처리는 끝났는데 ack만 못 보낸 경우엔 **두 번 처리**돼요. RabbitMQ 문서도 소비자를 중복에 견디게(멱등하게) 만들라고 권해요.

Redis에도 비슷한 기능이 있어요. Pub/Sub은 저장하지 않는 방송이고, Streams는 메모리에 저장하고 컨슈머 그룹·ACK를 써요. 비교표는 → [Redis Pub/Sub과 Streams](../../redis/pubsub-streams/)

### 토픽·파티션·오프셋

- **토픽**(topic): 메시지를 담는 이름 붙은 로그예요. 예: `orders`. 생산자·소비자가 여럿일 수 있어요.
- **이벤트**(레코드): 키, 값, 타임스탬프, (선택) 헤더로 이뤄져요.
- **파티션**(partition): 토픽을 나눈 칸이에요. 칸들은 여러 브로커(Kafka 서버)에 흩어져 있어서 한 토픽을 여러 서버가 나눠 받아요.
- **오프셋**(offset): 파티션 안 메시지마다 붙는, 0부터 하나씩 커지는 번호예요. 소비자의 "책갈피"도 이 번호예요.

소비자는 **pull** 방식이에요. 브로커가 밀어 주는 게 아니라, 소비자가 "이 파티션 몇 번 오프셋부터 줘"라고 가져가요. 그래서 오프셋을 뒤로 되돌리면 지난 메시지를 **다시 처리**할 수 있어요. 버그를 고친 뒤 어제 데이터를 다시 돌리는 게 가능한 이유예요.

### 순서는 파티션 안에서만: 같은 키 → 같은 파티션

Kafka는 **한 파티션 안에서는 쓴 순서대로** 읽힌다고 보장해요. 파티션끼리의 순서는 보장하지 않아요.

생산자가 파티션을 직접 지정하지 않으면 기본 규칙은 이래요.

- **키가 있으면**: 키의 해시값으로 파티션을 골라요. 그래서 **같은 키는 늘 같은 파티션**이에요.
- **키가 없으면**: 한 파티션에 배치(묶음)가 찰 때까지 몰아 보내다가 다른 파티션으로 바꿔요(sticky 방식). 메시지마다 돌아가며 보내려면 별도 파티셔너를 지정해야 해요.

그래서 "주문 생성 → 결제 → 취소" 순서를 지키려면 **주문 ID를 키로** 보내요. 키 없이 보내면 세 이벤트가 다른 파티션에 흩어져 취소가 먼저 처리될 수 있어요.

<Aside type="caution" title="키 = 파티션 번호가 아니에요">
키는 해시로 칸을 고를 뿐이라 **서로 다른 키가 같은 칸에 몰릴 수 있어요**(아래 실험 예시). 키 종류가 적거나 한 키에 메시지가 몰리면 한 파티션만 바쁜 **핫 파티션**이 생겨요.
</Aside>

### 컨슈머 그룹: 그룹끼리는 전부, 그룹 안에서는 나눠서

소비자 여럿을 쓰는 방법은 두 가지예요.

- **나눠 받기**(로드 밸런싱): 메시지 하나를 소비자 중 한 명만 받아요.
- **모두 받기**(팬아웃): 메시지 하나를 모든 소비자가 받아요.

Kafka의 **컨슈머 그룹**(consumer group)은 이 둘을 합친 거예요. **그룹끼리는 모두 받고, 그룹 안에서는 나눠 받아요.** 예를 들어 `email` 그룹과 `stats` 그룹은 각자 주문 이벤트를 전부 받고, `email` 그룹 안의 소비자 두 명은 파티션을 나눠 맡아요.

규칙은 하나예요. **한 파티션은 한 그룹 안에서 한 시점에 소비자 한 명만** 읽어요. 그래서 소비 위치가 "파티션마다 오프셋 숫자 하나"로 끝나요.

이 규칙의 결과도 알아 두세요.

- 그룹 안에서 동시에 일하는 소비자 수는 **파티션 수를 넘을 수 없어요.** 파티션 3개에 소비자 5명이면 2명은 놀아요.
- 한 메시지 처리가 느리면 **그 파티션 뒤 메시지가 전부 밀려요.**
- 병렬성을 늘리는 정석은 **파티션 수를 늘리는 것**이에요.

### 실험 예시: 직접 보내 보기

파티션 3개짜리 토픽 `orders`를 만들고, 키 user-A(3건), user-B(3건), user-C(2건)로 8건을 보내 본 예시예요.

| 키 | 들어간 파티션 | 파티션 안 순서 |
|---|---|---|
| user-A | 0 | a1 → a2 → a3 (보낸 순서 그대로) |
| user-B | 0 | b1 → b2 → b3 |
| user-C | 2 | c1 → c2 |

- 같은 키는 **매번 같은 파티션**이었고, 키별 순서도 유지됐어요.
- 키가 3종인데도 **A와 B가 같은 파티션에 몰리고 1번은 텅 비었어요.** 키가 적으면 고르게 안 퍼질 수 있다는 걸 보여 줘요.
- 그룹 `g-email`과 `g-stats`를 각각 처음부터 읽게 했더니 **두 그룹 모두 8건 전부**를 받았어요. 그룹별 오프셋을 조회하면 각자 따로 기록돼 있어요.
- 토픽을 만들기 전에 먼저 보냈더니 브로커가 토픽을 **파티션 1개로 자동 생성**했어요(`num.partitions` 기본값 1). 실무에서 자동 생성 토픽을 조심하는 이유예요.

### 전달 보장 3종과 오프셋 커밋 시점

**오프셋 커밋**(commit)은 소비자가 "여기까지 처리했어요"라고 책갈피를 저장하는 거예요. 소비자가 죽었다 살아나면 **마지막으로 커밋한 오프셋부터** 다시 읽어요. 그래서 **언제 커밋하느냐**가 전달 보장을 정해요.

| 보장 | 순서 | 장애 시 결과 |
|---|---|---|
| **최대 한 번**(at-most-once) | 읽기 → **커밋** → 처리 | 처리 전에 죽으면 그 메시지는 건너뜀 = **유실** 가능, 중복 없음 |
| **최소 한 번**(at-least-once) | 읽기 → 처리 → **커밋** | 커밋 전에 죽으면 다시 처리 = **중복** 가능, 유실 없음 |
| **정확히 한 번**(exactly-once) | 처리 결과 쓰기 + 커밋을 **한 트랜잭션** | 둘 다 되거나 둘 다 취소 (Kafka 안에서만) |

**Kafka 기본은 최소 한 번**이에요. 대부분의 서비스는 "유실보다 중복이 낫다"고 보고 이걸 택한 뒤, **소비자를 멱등하게**(같은 메시지를 두 번 처리해도 결과가 같게) 만들어요. 예: 처리한 이벤트 ID를 테이블에 기록하고 유니크 제약을 걸어 두 번째는 건너뛰기. → [아웃박스와 멱등 소비자](../outbox-idempotency/)

컨슈머 기본 설정은 **자동 커밋**(`enable.auto.commit=true`)이고, 5초(`auto.commit.interval.ms=5000`)마다 백그라운드로 커밋해요. 처리가 끝난 시점과 커밋 시점이 맞지 않으니, 중요한 처리는 **자동 커밋을 끄고 처리 후 직접 커밋**하는 경우가 많아요.

<Aside type="note" title="문서로 직접 확인하지 못한 일반 지식">
자동 커밋은 poll을 부를 때 직전 poll로 받은 위치까지 커밋하는 식으로 동작해서, poll 루프 안에서 처리를 다 끝내면 대체로 최소 한 번이 된다고 알려져 있어요. 이 세부 동작은 이번에 공식 문서 원문으로 확인하지 못했으니 면접에선 "그렇게 알고 있다" 정도로 말하세요.
</Aside>

### 리밸런싱

**리밸런싱**(rebalancing)은 그룹에 소비자가 들어오거나, 나가거나, 죽었을 때 파티션 담당을 다시 나누는 거예요. 배포로 소비자를 재시작할 때도 일어나요.

넘겨받은 소비자는 그 파티션의 **마지막 커밋 오프셋부터** 읽어요. 그래서 이전 담당자가 **처리는 했는데 커밋을 못 한** 메시지는 두 번 처리돼요. 배포 때 중복이 생기는 대표 원인이에요.

또 소비자가 `max.poll.interval.ms` 안에 poll을 다시 부르지 않으면 Kafka는 그 소비자가 죽었다고 보고 리밸런싱해요. 한 묶음 처리가 너무 오래 걸리면 → 쫓겨남 → 다른 소비자가 같은 메시지를 다시 받음 → 또 오래 걸림… 이 반복될 수 있어요.

### 심화: 복제와 acks, ISR, min.insync.replicas

복제는 **파티션 단위**예요. 실무에선 복제 계수 3이 흔해요. 파티션마다 **리더**가 쓰기를 받고, 나머지 복제본이 따라 적어요. → [복제](../replication/)

**ISR**(in-sync replicas)은 리더를 잘 따라오고 있는 복제본 모임이에요. `replica.lag.time.max.ms` 안에 못 따라오거나 연결이 끊기면 ISR에서 빠지고, **ISR 멤버만 새 리더가 될 수 있어요.** 메시지는 ISR 전부가 받아야 "커밋"됐다고 보고, 소비자에겐 커밋된 메시지만 보여 줘요.

생산자의 `acks` 설정은 "어디까지 받았을 때 성공으로 칠까"예요.

| acks | 성공 기준 | 위험 |
|---|---|---|
| `0` | 응답 안 기다림 | 유실돼도 모름, 재시도도 안 먹힘 |
| `1` | 리더만 기록 | 리더가 복제 전에 죽으면 유실 |
| `all`(-1), **기본값** | **현재 ISR 전부** 기록 | ISR이 1개로 줄면 사실상 acks=1 |

함정은 `all`이 "복제본 3개 전부"가 아니라 **"지금 ISR에 남은 것 전부"**라는 점이에요. 두 대가 빠져 ISR이 리더 혼자면 acks=all도 성공하고, 그 리더가 죽으면 잃어요.

이걸 막는 게 **`min.insync.replicas`**예요. acks=all일 때 ISR 수가 이 값보다 적으면 생산자는 `NotEnoughReplicas` 예외를 받아요. **쓰기를 거부해서 유실 대신 실패를 고르는** 설정이에요.

<Aside type="caution" title="min.insync.replicas 기본값은 1">
기본값 그대로면 ISR이 리더 하나만 남아도 쓰기가 성공해요. 흔한 조합은 **복제 3 + min.insync.replicas=2 + acks=all**이에요. 한 대가 죽어도 쓰기는 되고, 두 대가 죽으면 쓰기를 멈춰 유실을 막아요.
</Aside>

참고로 Kafka는 과반수 투표 대신 ISR 방식이라, 복제 f+1개로 f개 장애까지 커밋된 메시지를 지켜요(과반수 방식은 2f+1개 필요). ISR 밖의 뒤처진 복제본을 리더로 뽑을지(`unclean.leader.election.enable`)는 기본값이 "안 뽑음"으로, 일관성을 우선해요.

### 심화: 정확히 한 번은 어디까지인가

중복은 두 군데서 생겨요.

**생산 쪽 중복**: 생산자가 보냈는데 네트워크 오류로 응답을 못 받으면, 브로커에 들어갔는지 모른 채 재전송해요. 이걸 막는 게 **멱등 프로듀서**예요. 브로커가 생산자에게 ID를 주고 메시지마다 순번을 붙여 중복을 걸러요. `enable.idempotence`는 기본값 true(충돌하는 설정이 없을 때)고, acks=all, retries가 0보다 큼, `max.in.flight.requests.per.connection` 5 이하가 조건이에요. 단, 막아 주는 범위는 **한 생산자 세션, 한 파티션**이에요.

**트랜잭션**: 여러 파티션에 원자적으로 쓰고(전부 쓰이거나 전부 안 쓰임), 소비자 오프셋도 내부 토픽에 저장되니까 **결과 메시지 쓰기 + 오프셋 커밋**을 한 트랜잭션으로 묶을 수 있어요. 이게 Kafka의 exactly-once예요. 생산자에 `transactional.id`를, 소비자에 `isolation.level=read_committed`와 자동 커밋 끄기를 설정해요. `isolation.level` 기본값은 read_uncommitted라 그냥 두면 취소된 트랜잭션 메시지도 읽어요.

<Aside type="caution" title="정확히 한 번은 Kafka 안에서만">
트랜잭션이 묶어 주는 건 "Kafka에서 읽고 → Kafka에 쓰기"(Kafka Streams 포함)예요. **DB에 쓰거나 메일을 보내는 건 Kafka 트랜잭션에 안 들어가요.** 이런 부수효과는 소비자 멱등성(처리 ID 기록·유니크 키)이나, 오프셋을 결과와 같은 DB 트랜잭션에 함께 저장하는 방법으로 따로 막아야 해요. 공식 문서도 exactly-once 주장은 조건을 잘 읽으라고 경고해요. → [아웃박스와 멱등 소비자](../outbox-idempotency/)
</Aside>

### 심화: 그 밖에 알아 둘 기본값과 변화

| 항목 | 값 / 내용 |
|---|---|
| `retention.ms` | 기본 604800000 = **7일** |
| `cleanup.policy` | 기본 delete. compact로 바꾸면 키별 최신 값만 남김 |
| `auto.offset.reset` | 기본 **latest**. 커밋된 오프셋이 없는 새 그룹은 "지금 이후" 메시지부터 읽음(earliest면 처음부터) |
| 랙(lag) | 소비자가 뒤처진 정도. 보관 기간을 넘겨 뒤처지면 그 메시지는 **못 읽음** → 랙 모니터링·알림이 필수 |
| 새 리밸런스 프로토콜 | 4.0부터 정식. 브로커가 배정을 맡고 점진적이라 그룹 전체가 멈추지 않음. 클라이언트는 `group.protocol=consumer`로 켬(기본은 아직 classic) |
| KRaft | **4.0부터 ZooKeeper 제거.** 메타데이터를 컨트롤러들이 Raft 합의로 관리 → [합의와 Raft](../consensus-raft/) |
| share group | 4.2부터 정식. 파티션을 한 명에게 묶지 않고 레코드 단위로 나눠 받는 큐 방식 |

<Aside type="note" title="문서로 직접 확인하지 못한 일반 지식">
파티션 수를 나중에 늘리면 "해시 % 파티션 수" 결과가 바뀌어, 같은 키의 옛 메시지와 새 메시지가 다른 파티션에 있게 돼요. 그러면 그 키의 순서가 경계에서 깨질 수 있어요. 원리상 나오는 결론이지만 공식 문서 문장으로는 확인하지 못했어요.
</Aside>

## 면접 질문

<details>
<summary>Q. 메시지 큐를 왜 쓰나요?</summary>

**답변(30초)**
서비스 사이를 비동기로 만들고 결합을 끊으려고 써요. 주문 서버가 메일·포인트 서버를 직접 부르면 그쪽이 느리거나 죽을 때 주문도 같이 느려지거나 실패해요. 브로커에 메시지를 맡기면 주문 서버는 바로 응답하고, 소비자는 자기 속도로 처리해요. 소비자가 잠깐 죽어도 메시지가 쌓여 있다가 처리되고, 트래픽이 몰릴 때 완충도 돼요.

**꼬리질문**
- Q. 단점은요? → 처리 완료를 바로 알 수 없고, 중복·순서·유실을 따로 신경 써야 해요. 브로커라는 운영 대상도 하나 늘어요.
</details>

<details>
<summary>Q. Kafka의 토픽, 파티션, 오프셋, 컨슈머 그룹을 설명해 주세요.</summary>

**답변(30초)**
토픽은 메시지를 담는 이름 붙은 로그고, 파티션은 토픽을 나눈 칸이라 여러 브로커에 흩어져 처리량을 늘려요. 오프셋은 파티션 안 메시지 번호이자 소비자가 어디까지 읽었는지 기록하는 책갈피예요. 컨슈머 그룹은 그룹끼리는 모든 메시지를 받고, 그룹 안에서는 파티션을 나눠 맡는 단위예요. 한 파티션은 그룹 안에서 한 명만 읽어요.

**꼬리질문**
- Q. 소비자가 메시지를 읽으면 지워지나요? → 아니요, 보관 기간(기본 7일)까지 남고 오프셋만 움직여요. 그래서 오프셋을 되돌려 재처리할 수 있어요.
</details>

<details>
<summary>Q. RabbitMQ 같은 전통 큐와 Kafka는 뭐가 다른가요?</summary>

**답변(30초)**
전통 큐는 소비자가 ack하면 메시지를 지우고, 메시지마다 아무 소비자에게나 나눠 줘요. Kafka는 로그에 남겨 두고 파티션마다 오프셋 하나로 소비 위치를 관리해요. 그래서 Kafka는 재처리와 여러 그룹의 독립 소비가 쉽고, 파티션 안 순서가 보장되고 처리량이 커요. 반대로 건당 처리가 무겁고 순서가 덜 중요한 작업은 메시지 단위로 나눠 주는 전통 큐가 잘 맞아요.

**꼬리질문**
- Q. Kafka에서도 큐처럼 쓸 수 있나요? → 4.2부터 share group이 정식이라 레코드 단위로 나눠 받을 수 있어요.
</details>

<details>
<summary>Q. Kafka는 순서를 보장하나요? 주문 이벤트 순서를 지키려면?</summary>

**답변(30초)**
파티션 안에서만 보장해요. 토픽 전체 순서는 보장하지 않아요. 키를 주면 키 해시로 파티션이 정해져 같은 키는 늘 같은 파티션에 가니까, 주문 ID를 키로 보내면 한 주문의 생성·결제·취소가 순서대로 처리돼요. 토픽 전체 순서가 꼭 필요하면 파티션을 1개로 해야 하는데, 그러면 확장성을 포기해요.

**꼬리질문**
- Q. 키가 다르면 다른 파티션인가요? → 아니요, 해시라 다른 키가 같은 파티션에 몰릴 수 있어요. 키 종류가 적으면 핫 파티션이 생겨요.
- Q. 키 없이 보내면? → 기본 파티셔너가 배치 단위로 파티션을 바꿔 가며 보내서, 같은 주문 이벤트가 흩어질 수 있어요.
</details>

<details>
<summary>Q. 컨슈머를 파티션 수보다 많이 띄우면 어떻게 되나요?</summary>

**답변(30초)**
남는 컨슈머는 놀아요. 한 파티션은 그룹 안에서 한 명만 읽을 수 있어서, 그룹의 병렬성 상한은 파티션 수예요. 파티션 3개에 컨슈머 5개면 2개는 대기만 해요. 처리량을 더 늘리려면 파티션 수부터 늘려야 해요. 다만 파티션이 늘면 키→파티션 매핑이 바뀌어 순서에 영향을 줄 수 있어 처음에 넉넉히 잡는 편이에요.

**꼬리질문**
- Q. 노는 컨슈머는 쓸모가 없나요? → 다른 컨슈머가 죽으면 리밸런싱으로 파티션을 넘겨받는 예비 역할은 해요.
</details>

<details>
<summary>Q. at-most-once, at-least-once, exactly-once 차이와 오프셋 커밋 시점의 관계는?</summary>

**답변(30초)**
처리 전에 오프셋을 커밋하면 처리 중 죽었을 때 그 메시지를 건너뛰니까 최대 한 번, 즉 유실 가능이에요. 처리 후에 커밋하면 커밋 전에 죽었을 때 다시 처리하니까 최소 한 번, 즉 중복 가능이에요. Kafka 기본은 최소 한 번이에요. 정확히 한 번은 결과 쓰기와 오프셋 커밋을 한 트랜잭션으로 묶는 건데, Kafka에서 읽고 Kafka에 쓸 때만 성립해요.

**꼬리질문**
- Q. 자동 커밋이면 안전한가요? → 5초마다 커밋해서 처리 완료 시점과 안 맞아요. 중요한 처리는 자동 커밋을 끄고 처리 후 수동 커밋해요.
</details>

<details>
<summary>Q. 메시지 중복 처리는 어떻게 막나요?</summary>

**답변(30초)**
최소 한 번을 전제로 소비자를 멱등하게 만들어요. 이벤트 ID를 처리 이력 테이블에 유니크 키로 기록하고, 이미 있으면 건너뛰어요. 이 기록과 실제 처리를 같은 DB 트랜잭션에 넣어야 해요. 생산 쪽 재전송 중복은 멱등 프로듀서가 막는데, 이건 한 세션·한 파티션 범위라 소비 쪽 중복과는 별개예요.

**꼬리질문**
- Q. Kafka 트랜잭션을 쓰면 DB 중복도 막히나요? → 아니요, Kafka 트랜잭션은 Kafka 토픽 쓰기와 오프셋만 묶어요. DB는 멱등 처리나 오프셋을 DB에 같이 저장하는 방식이 필요해요.
</details>

<details>
<summary>Q. 리밸런싱이란 무엇이고, 어떤 문제를 일으키나요?</summary>

**답변(30초)**
컨슈머가 들어오거나 나가거나 죽을 때 그룹 안 파티션 담당을 다시 나누는 거예요. 배포 재시작 때도 일어나요. 넘겨받은 컨슈머는 마지막 커밋 오프셋부터 읽어서, 처리는 했는데 커밋 전이던 메시지가 중복 처리돼요. 또 처리가 오래 걸려 `max.poll.interval.ms`를 넘기면 죽은 것으로 보고 리밸런싱해서, 같은 메시지를 계속 다시 받는 반복이 생길 수 있어요.

**꼬리질문**
- Q. 줄이는 방법은? → 한 번에 가져오는 양을 줄여 poll 간격을 지키고, 종료 시 커밋 후 깔끔히 나가게 해요. 4.0부터는 브로커가 점진적으로 배정하는 새 프로토콜(`group.protocol=consumer`)도 쓸 수 있어요.
</details>

<details>
<summary>Q. acks=all이면 메시지를 절대 안 잃나요?</summary>

**답변(30초)**
아니요. acks=all은 "현재 ISR 전부"가 받았다는 뜻이라, 복제본이 빠져 ISR이 리더 하나만 남으면 사실상 acks=1이에요. 그래서 `min.insync.replicas`를 같이 써요. ISR 수가 이 값보다 적으면 쓰기를 거부해요. 기본값이 1이라 그대로 두면 소용없고, 흔한 조합은 복제 3, min.insync.replicas 2, acks=all이에요.

**꼬리질문**
- Q. 쓰기가 거부되면 장애 아닌가요? → 가용성을 내주고 내구성을 지키는 의도된 동작이에요. 유실보다 실패가 낫다는 선택이에요.
- Q. ISR이란? → 리더를 제때 따라오는 복제본 모임이고, 이들만 새 리더가 될 수 있어요.
</details>

<details>
<summary>Q. ZooKeeper는 왜 없어졌나요?</summary>

**답변(30초)**
Kafka 4.0부터 ZooKeeper 모드가 제거되고 KRaft 모드만 남았어요. 예전엔 클러스터 메타데이터를 외부 ZooKeeper가 관리했는데, 이제는 Kafka 안의 컨트롤러들이 Raft 합의로 직접 관리해요. 별도 시스템을 따로 운영하지 않아도 돼요. ZooKeeper를 쓰던 클러스터는 4.x로 올리기 전에 KRaft로 옮겨야 해요.

**꼬리질문**
- Q. Raft가 뭔가요? → 여러 서버가 리더를 뽑고 과반수 동의로 같은 기록을 유지하는 합의 알고리즘이에요. → [합의와 Raft](../consensus-raft/)
</details>

## 서술형 연습

<details>
<summary>상황: 주문 서비스가 "생성 → 결제 → 취소" 이벤트를 Kafka 토픽(파티션 6개)에 보내는데, 배송 서비스에서 가끔 취소가 결제보다 먼저 처리돼 배송이 출발해 버려요. 생산자 코드는 이벤트를 키 없이 보내고 있어요. 원인과 해결 방법은?</summary>

**상황 파악**
"가끔" 뒤바뀐다면 Kafka가 메시지를 잃은 게 아니라 **순서 보장 범위 밖**에서 처리된 거예요. Kafka 순서 보장은 파티션 안에서만인데, 키가 없으니 한 주문의 이벤트가 여러 파티션에 흩어졌을 가능성이 커요.

**원인 후보**
1. 키 미지정 → 기본 파티셔너가 배치 단위로 파티션을 바꿔, 같은 주문의 결제와 취소가 다른 파티션에 들어감. 파티션마다 다른 컨슈머가 다른 속도로 읽으니 순서가 뒤바뀜.
2. 컨슈머가 메시지를 받아 내부 스레드 풀에서 병렬 처리하면, 같은 파티션이어도 처리 순서가 섞일 수 있음.
3. 처리 실패 시 재시도 큐로 보냈다가 나중에 처리하는 구조라면 재시도된 이벤트가 뒤로 밀림.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 주문 ID를 키로 발행 | 같은 주문은 같은 파티션 → 순서 보장, 다른 주문은 계속 병렬 | 특정 키에 몰리면 핫 파티션. 나중에 파티션 수를 바꾸면 매핑이 달라짐 |
| B. 파티션 1개로 줄이기 | 토픽 전체 순서 보장 | 컨슈머 한 명만 일함, 확장성 포기 |
| C. 소비 쪽에서 상태 버전 검사(현재 상태보다 앞선 단계 이벤트는 무시·보류) | 순서가 어긋나도 잘못된 처리를 막음 | 상태 머신 로직이 복잡해짐 |

**내가 고를 방법**
A를 기본으로 해요. 순서가 필요한 단위는 "주문 하나"지 토픽 전체가 아니라서, 주문 ID 키로 충분하고 병렬성도 유지돼요. 컨슈머 안에서 병렬 처리를 한다면 같은 키는 같은 스레드에서 처리하게 맞춰요. 그리고 재시도·리밸런싱 경계에서 생길 수 있는 예외를 대비해 C처럼 "취소된 주문엔 배송 출발 금지" 같은 상태 검사를 소비 쪽에 둬요. 파티션 수는 처음부터 넉넉히 잡아 나중에 바꿀 일을 줄여요.

**채점 포인트**: 순서는 파티션 안에서만, 키 미지정 시 파티션 분산, 키 해시 → 같은 파티션, 주문 ID를 키로, 파티션 1개는 확장성 포기, 컨슈머 내부 병렬 처리 주의, 핫 파티션, 파티션 수 변경 시 매핑 변화, 소비 쪽 상태 검사.
</details>

<details>
<summary>상황: 결제 완료 이벤트를 받아 포인트를 적립하는 컨슈머를 배포했더니, 배포 시간대에 일부 사용자 포인트가 두 번 적립됐어요. 컨슈머는 메시지를 처리한 뒤 오프셋을 커밋해요. 원인과 해결 방법은?</summary>

**상황 파악**
"처리 후 커밋"은 최소 한 번 방식이라 장애·재시작 때 **중복은 원래 생길 수 있는** 구조예요. 배포 시간대에만 생겼다는 건 재시작과 리밸런싱이 계기라는 뜻이에요.

**원인 후보**
1. 컨슈머가 적립(DB 반영)까지 했는데 오프셋 커밋 전에 종료됨 → 리밸런싱으로 파티션을 넘겨받은 컨슈머가 마지막 커밋 오프셋부터 다시 읽어 같은 이벤트를 재처리.
2. 자동 커밋(5초 주기)을 쓰고 있어 마지막 커밋 이후 처리분이 재처리됨.
3. 배포 중 처리 지연으로 `max.poll.interval.ms`를 넘겨 쫓겨났고, 다른 컨슈머가 같은 묶음을 다시 처리.
4. 생산 쪽 재전송으로 이벤트 자체가 두 번 들어옴(멱등 프로듀서가 꺼져 있었거나 생산자가 재시작됨).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 멱등 소비자: 이벤트 ID를 처리 이력 테이블에 유니크 키로 넣고, 적립과 같은 DB 트랜잭션으로 처리 | 원인이 무엇이든 중복을 흡수. 가장 확실 | 테이블·조회 비용, 이력 정리 정책 필요 |
| B. 오프셋을 적립 결과와 같은 DB 트랜잭션에 저장하고, 시작할 때 DB의 오프셋부터 읽기 | 처리와 커밋이 원자적 | 오프셋 관리를 직접 해야 해서 구현 복잡 |
| C. 종료 시 처리 중인 묶음을 끝내고 커밋한 뒤 나가게(정상 종료 처리) | 배포 때 중복을 크게 줄임 | 강제 종료·장애엔 효과 없음 |
| D. Kafka 트랜잭션(exactly-once) | Kafka→Kafka 처리면 중복 없음 | 포인트 DB 쓰기는 Kafka 트랜잭션 밖이라 이 문제는 못 막음 |

**내가 고를 방법**
A를 기본으로 해요. 최소 한 번은 Kafka의 기본이고 리밸런싱·장애는 언제든 생기니, 돈이 걸린 포인트는 "두 번 와도 한 번만 반영"이 보장돼야 해요. 여기에 C를 더해 평소 배포에서 중복 자체를 줄이고, 자동 커밋은 끄고 처리 후 수동 커밋해요. D는 외부 DB까지 묶어 주지 않으니 이 문제의 해결책이 아니라고 설명해요. 이미 이중 적립된 건은 이벤트 ID 기준으로 찾아 보정해요.

**채점 포인트**: 처리 후 커밋 = 최소 한 번, 커밋 전 종료 → 재처리, 리밸런싱은 마지막 커밋 오프셋부터, 자동 커밋 주기, max.poll.interval.ms, 멱등 소비자(이벤트 ID 유니크 + 같은 트랜잭션), 오프셋을 DB에 함께 저장, 정상 종료 처리, Kafka exactly-once는 외부 DB 미포함, 이미 생긴 중복 보정.
</details>

<details>
<summary>상황: 알림 발송 컨슈머의 랙(lag)이 몇 시간째 계속 늘고 있어요. 토픽은 파티션 4개, 컨슈머도 4개예요. 원인과 해결 방법은?</summary>

**상황 파악**
랙이 계속 는다는 건 **들어오는 속도가 처리 속도보다 빠르다**는 뜻이에요. 지금은 늦게 갈 뿐이지만, 랙이 보관 기간(기본 7일)을 넘기면 그 메시지는 지워져서 **유실**로 바뀌어요.

**원인 후보**
1. 메시지 하나 처리가 느림(외부 알림 API 응답 지연 등). 한 메시지가 느리면 그 파티션 뒤 메시지가 전부 밀림.
2. 특정 파티션만 랙이 큼 → 키가 쏠려 핫 파티션이 생김.
3. 처리 시간이 `max.poll.interval.ms`를 넘겨 리밸런싱이 반복되며 같은 메시지를 계속 다시 처리.
4. 트래픽 자체가 늘어 현재 파티션 수로는 처리량이 부족함.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 컨슈머만 늘리기 | 간단 | 파티션 4개라 5번째부터는 놀기만 함. 효과 없음 |
| B. 파티션 수 늘리고 컨슈머도 늘리기 | 병렬성 상한이 올라감 | 키→파티션 매핑이 바뀌어 순서가 경계에서 깨질 수 있음. 핫 파티션 원인이면 해결 안 됨 |
| C. 처리 병목 줄이기(외부 호출 타임아웃·배치 호출, 한 번에 가져오는 양 조절) | 근본 원인 해결, 파티션 구조 유지 | 코드 수정 필요 |
| D. 순서가 중요하지 않은 작업이면 큐 방식(전통 큐 또는 share group)으로 레코드 단위 분배 | 파티션 수에 묶이지 않고 소비자를 늘릴 수 있음 | 순서 보장 포기, 운영 구조 변경 |

**내가 고를 방법**
먼저 파티션별 랙을 봐서 원인 2(쏠림)인지 1·4(전반적 느림)인지 나눠요. 쏠림이면 키 설계를 바꾸고, 전반적으로 느리면 C로 처리 시간을 줄이고 리밸런싱 반복부터 끊어요. 그래도 처리량이 모자라면 B로 파티션과 컨슈머를 같이 늘려요. A는 파티션 수가 상한이라 효과가 없다는 걸 분명히 해요. 알림은 건별 처리가 무겁고 순서가 덜 중요하니 장기적으로 D도 검토해요. 랙이 보관 기간에 닿기 전에 알림을 받도록 랙 모니터링 경보를 걸어요.

**채점 포인트**: 랙 = 유입 > 처리, 보관 기간 넘기면 유실, 컨슈머 수 상한 = 파티션 수, 파티션 늘리기와 매핑 변화, head-of-line blocking, 핫 파티션 확인(파티션별 랙), max.poll.interval.ms 리밸런싱 반복, 처리 병목 개선, 큐 방식 대안, 랙 모니터링.
</details>

## 필기 포인트

- 전통 큐: ack 후 **삭제**. 로그 기반(Kafka): **보관**, 오프셋만 이동, 재처리 가능.
- 순서 보장은 **파티션 안에서만**. 같은 키 → 같은 파티션(키 해시).
- 한 파티션은 그룹 안에서 **한 소비자만** → 그룹 병렬성 상한 = 파티션 수.
- 처리 전 커밋 = **최대 한 번**(유실), 처리 후 커밋 = **최소 한 번**(중복). Kafka 기본 = 최소 한 번.
- exactly-once = 트랜잭션 + read_committed, **Kafka→Kafka**만. 외부 DB는 멱등 소비자.
- acks 기본 **all**(= 현재 ISR 전부). `min.insync.replicas` 기본 **1** → 복제 3이면 2 권장.
- `retention.ms` 기본 7일, `auto.offset.reset` 기본 latest, `enable.auto.commit` 기본 true(5초).
- Kafka 4.0: **ZooKeeper 제거, KRaft만**. 새 리밸런스 프로토콜 정식.
