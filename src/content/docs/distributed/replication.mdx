:::tip[한 줄 요약]
**복제**(replication)는 같은 데이터를 여러 서버에 복사해 두는 거예요. 가장 흔한 **리더·팔로워** 방식에서는 쓰기를 **리더 한 대만** 받고, 팔로워들은 리더가 보내 주는 변경 기록을 **같은 순서로** 따라 적용해요. 이걸로 장애에 버티고(가용성), 읽기를 나눠 받고, 사용자와 가까운 곳에 데이터를 둘 수 있어요. 리더가 팔로워의 확인을 기다리면 **동기**(안전하지만 느림), 안 기다리면 **비동기**(빠르지만 리더가 죽으면 최근 쓰기를 잃을 수 있음)예요.
:::

:::note[처음이라면 여기까지]
① 복제는 "DB 복사본을 여러 대 두는 것"이에요. 한 대가 죽어도 서비스가 돌고, 읽기 요청을 여러 대가 나눠 받을 수 있어요.

② 쓰기는 원본(리더) 한 대만 받고, 복사본(팔로워)은 원본이 보내 주는 변경 기록을 그대로 따라 해요. 복사본에 직접 쓰면 안 돼요.

③ 원본이 복사본의 "받았어" 답장을 기다리면 안전하지만 느리고, 안 기다리면 빠르지만 원본이 갑자기 죽을 때 마지막 몇 건이 사라질 수 있어요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

팀 프로젝트 보고서 **원본 문서**가 하나 있다고 해 봐요. 팀원 여러 명이 그 **복사본**을 하나씩 들고 있어요.

원본이 든 노트북이 고장 나도 복사본이 있으니 작업이 끝나지 않아요. 교수님이 "보고서 좀 보자"고 하면 아무 팀원이나 자기 복사본을 보여 주면 돼서, 원본 가진 사람 한 명에게 질문이 몰리지 않아요. 서울 팀원과 부산 팀원이 각자 갖고 있으면 가까운 사람에게 보면 되고요.

그런데 내용을 고칠 때가 문제예요. 각자 자기 복사본을 마음대로 고치면 복사본끼리 내용이 달라져요. 그래서 **"수정은 팀장(리더) 한 명만, 나머지는 팀장이 보내 준 수정 내역을 순서대로 따라 고친다"**는 규칙을 정해요. 이게 리더·팔로워 복제예요.

팀장이 수정 내역을 보내고 "다들 받았지?" 답장을 확인한 뒤에야 "수정 완료"라고 말하면 동기, 보내기만 하고 바로 "완료"라고 말하면 비동기예요.

단, 실제로는 "팀장"이 사람이 아니라 DB 서버이고, 팀장이 갑자기 연락 두절되면 누가 새 팀장을 할지 정하는 일(장애 조치)이 생각보다 어려워요. 이건 아래에서 다뤄요.

## 제대로 알기

### 왜 복제하나

**복제**는 네트워크로 연결된 여러 서버가 같은 데이터의 복사본을 갖게 하는 거예요. 이유는 세 가지예요.

| 목적 | 무슨 뜻 | 예 |
|---|---|---|
| 가용성 | 일부 서버가 죽어도 계속 동작 | DB 서버 한 대 디스크 고장 → 다른 서버가 이어받음 |
| 읽기 확장 | 읽기 요청을 여러 서버가 나눠 처리 | 상품 조회가 몰리면 복사본을 늘려 나눠 받음 |
| 지연 시간 감소 | 사용자와 가까운 곳에 복사본을 둠 | 해외 사용자는 그 지역의 복사본에서 읽음 |

데이터가 절대 안 바뀐다면 한 번 복사하고 끝이에요. 복제가 어려운 이유는 전부 **"바뀐 내용을 어떻게 다른 서버에 퍼뜨리나"**에 있어요. 방식은 크게 세 가지예요. **단일 리더**, **다중 리더**, **리더 없음**(leaderless). 거의 모든 분산 DB가 이 셋 중 하나를 써요. 이 페이지는 가장 흔한 단일 리더를 중심으로 봐요.

흔한 오해 두 가지를 먼저 짚어 둘게요.

- **복제는 백업이 아니에요.** 실수로 `DELETE`를 날리면 그 삭제도 복사본에 그대로 퍼져요. "어제 시점으로 되돌리기"를 하려면 백업이 따로 있어야 해요.
- **복제로 늘어나는 건 읽기예요.** 단일 리더에서는 모든 쓰기가 리더 한 대로 몰려요. 쓰기가 한계라면 데이터를 쪼개는 [파티셔닝](../partitioning/)을 봐야 해요. 실제 서비스는 복제와 파티셔닝을 같이 써요.

### 단일 리더는 이렇게 돌아가요

용어부터 정리할게요. 같은 것을 부르는 이름이 여러 개예요.

| 역할 | 이 페이지 | 다른 이름 |
|---|---|---|
| 쓰기를 받는 서버 | 리더 | 마스터, 프라이머리, MySQL에선 **소스**(source) |
| 따라 하는 서버 | 팔로워 | 슬레이브, 세컨더리, 읽기 복제본, MySQL에선 **레플리카**(replica) |

MySQL은 예전 master/slave 대신 source/replica를 써요. 명령어도 `SHOW REPLICA STATUS`, `START REPLICA`, `CHANGE REPLICATION SOURCE TO`처럼 바뀌었어요. 면접에서도 primary/replica나 source/replica라고 말하는 게 좋아요.

흐름은 이래요.

1. 노드(서버) 하나를 리더로 정해요. **쓰기는 리더에게만** 보내요.
2. 리더는 먼저 자기 저장소에 기록해요.
3. 리더는 바뀐 내용을 **복제 로그**(어떤 변경이 어떤 순서로 일어났는지 적은 기록)로 팔로워들에게 보내요.
4. 팔로워들은 그 로그를 **리더와 같은 순서로** 적용해요. 순서가 같아야 결과가 같아요.
5. 읽기는 리더에게도, 아무 팔로워에게도 보낼 수 있어요. 단, 클라이언트 입장에서 팔로워는 **읽기 전용**이에요.

이 방식은 MySQL, PostgreSQL, Oracle Data Guard, SQL Server AlwaysOn, MongoDB 같은 DB에 기본으로 들어 있고, Kafka 같은 메시지 브로커도 같은 구조를 써요.

### 동기 · 비동기 · 반동기 비교

리더가 "쓰기 성공"을 클라이언트에 **언제** 알려 주느냐에 따라 나뉘어요.

| | 동기 | 비동기 | 반동기 |
|---|---|---|---|
| 리더가 기다리는 것 | 팔로워의 "받았음" 확인 | 아무것도 안 기다림 | 팔로워 **일부**(보통 1대)의 확인 |
| 쓰기 응답 속도 | 느림(팔로워 왕복만큼) | 빠름 | 중간 |
| 리더가 죽으면 | 팔로워에 최신본이 있어 안전 | 아직 안 넘어간 쓰기가 **사라질 수 있음** | 최소 2대에 최신본 |
| 팔로워가 죽으면 | 리더의 **쓰기가 전부 멈춤** | 리더는 계속 쓰기 가능 | 남은 팔로워가 답하면 계속 |
| 한 줄 정리 | 안전하지만 하나만 아파도 멈춤 | 빠르지만 유실 위험 | 둘 사이 절충 |

**동기 복제**는 팔로워도 반드시 최신이라 리더가 죽어도 데이터가 남아요. 대신 동기 팔로워 하나가 응답을 안 하면 리더가 계속 기다리느라 **쓰기 전체가 멈춰요**. 그래서 모든 팔로워를 동기로 두는 건 현실적이지 않아요.

**비동기 복제**는 리더가 보내기만 하고 바로 "성공"이라고 답해요. 팔로워가 다 죽어도 쓰기는 계속돼요. 대신 리더가 복구 못 할 만큼 망가지면, 클라이언트에게 이미 "성공"이라고 답한 쓰기도 잃을 수 있어요. 그래도 팔로워가 많거나 지역이 멀리 떨어져 있으면 널리 써요.

그래서 흔한 절충이 **"팔로워 하나만 동기, 나머지는 비동기"**예요. 이렇게 하면 최소 두 대(리더 + 동기 팔로워 1대)에 최신 데이터가 있어요. 이걸 **반동기**(semi-synchronous)라고 불러요.

보통 팔로워는 1초도 안 걸려 따라잡지만, **얼마나 걸릴지 보장은 없어요.** 장애 복구 중이거나 과부하, 네트워크 문제가 있으면 몇 분 이상 뒤처질 수도 있어요. 이때 생기는 "방금 쓴 글이 안 보임" 같은 문제는 [복제 지연](../replication-lag/)에서 다뤄요.

### MySQL에서는

- MySQL 복제는 **기본이 비동기**예요. 레플리카는 소스에 계속 붙어 있지 않아도 나중에 밀린 걸 받아 갈 수 있어요.
- **반동기**는 플러그인이라 소스·레플리카 **양쪽에** 설치하고 켜야 해요. 한쪽만 켜면 그냥 비동기로 동작해요.
- 반동기에서 소스는 클라이언트에 답하기 전에(기본 설정 `AFTER_SYNC`: 바이너리 로그를 디스크에 쓴 뒤, 스토리지 엔진에 커밋하기 전), 레플리카 **최소 1대**(개수 설정 가능, 기본 1)가 변경을 받아서 **relay log**(레플리카가 받은 변경을 적용 전에 쌓아 두는 파일)에 쓰고 **디스크에 저장했다**는 확인을 기다려요.
- 여기서 중요한 점: 레플리카가 그 변경을 **실제로 적용(커밋)했는지까지는 기다리지 않아요.** 그래서 반동기라도 레플리카에서 바로 읽으면 아직 안 보일 수 있어요.
- 정해진 시간(**타임아웃**, 기본 10초) 안에 확인을 주는 레플리카가 없으면 소스는 **조용히 비동기로 내려가요.** 레플리카가 다시 따라잡으면 반동기로 돌아와요.

### 리더가 죽으면: 장애 조치(failover)

팔로워가 죽는 건 비교적 쉬워요. 다시 살아난 팔로워가 "나 어디까지 받았더라"를 자기 로그에서 찾고, 그 뒤 것만 리더에게 다시 받으면 돼요.

리더가 죽으면 **장애 조치**(failover, 대체 서버로 넘기는 작업)가 필요해요.

1. **리더가 죽었다고 판단**해요. 확실히 알 방법이 없어서 보통 **타임아웃**을 써요. 예를 들어 30초 동안 응답이 없으면 죽은 걸로 봐요.
2. **새 리더를 골라요.** 보통 **가장 최신 데이터를 가진 팔로워**가 적합해요. 남은 노드들이 과반수로 뽑거나, 관리 노드가 지명해요. 여러 노드가 "누가 리더냐"에 합의하는 방법은 [합의와 Raft](../consensus-raft/)에서 다뤄요.
3. **모두 새 리더를 보게 해요.** 클라이언트는 쓰기를 새 리더로 보내고, 다른 팔로워도 새 리더를 따라요. 옛 리더가 살아 돌아오면 **팔로워로 내려야** 해요.

여기서 문제가 자주 터져요.

- **비동기면 데이터가 사라져요.** 새 리더가 옛 리더의 마지막 쓰기를 못 받았을 수 있어요. 흔한 처리는 그 쓰기를 그냥 버리는 거라, "성공" 응답을 받은 데이터가 없어져요.
- **다른 시스템과 엮이면 더 위험해요.** 실제로 GitHub에서, 뒤처진 MySQL 팔로워가 리더로 승격되면서 자동 증가 번호(auto_increment)가 뒤로 돌아가 **이미 쓴 기본 키를 다시 발급**한 사고가 있었어요. 그 키를 Redis에서도 쓰고 있어서 일부 개인 데이터가 다른 사용자에게 보였어요.
- **스플릿 브레인**(split brain, "뇌가 둘로 갈라짐"): 두 노드가 **둘 다 자기가 리더라고 믿고** 쓰기를 받는 상황이에요. 충돌을 정리할 장치가 없으면 데이터가 꼬이거나 사라져요. 그래서 한쪽을 강제로 끄거나 차단하는 **펜싱**(fencing)을 써요. 서버 전원을 아예 내리는 방식을 STONITH("다른 노드 머리를 쏴라")라고 불러요. 다만 펜싱을 잘못 설계하면 두 노드가 다 꺼질 수도 있어요.
- **타임아웃 길이 고르기가 어려워요.** 길면 복구가 늦고, 짧으면 잠깐 느려진 것뿐인데도 failover가 일어나 상황이 더 나빠져요. 그래서 자동 failover가 가능해도 **사람이 직접 하는 쪽을 고르는 팀**도 있어요.

### MySQL로 직접 해 보기

로컬에서 MySQL 서버 두 대(소스 1, 레플리카 1)를 띄워 확인해 본 결과예요. 수치는 한 번 재 본 예시예요.

**1) 레플리카 쓰기 막기.** 레플리카에서 `super_read_only`를 켜면 `read_only`도 같이 켜져요. 이 상태로 레플리카에 직접 `INSERT`를 하면 거부돼요.

```sql
-- 레플리카에서
SET GLOBAL super_read_only = ON;
INSERT INTO t VALUES (99);
-- ERROR 1290 (HY000): The MySQL server is running with the
-- --super-read-only option so it cannot execute this statement
```

그런데 소스에서 넣은 행은 레플리카에 **정상적으로 들어왔어요.** 복제 스레드(소스의 변경을 받아 적용하는 내부 작업)는 막지 않는다는 뜻이에요.

`read_only`와의 차이도 알아 두세요. `read_only`는 일반 사용자 쓰기만 막고 관리자 권한 계정은 통과시켜요. `super_read_only`는 **관리자까지** 막아요.

**2) 재시작하면 풀려요.** `SET GLOBAL`로 켠 `super_read_only`는 서버를 재시작하자 다시 꺼져 있었어요. 운영에서는 설정 파일에 넣거나 `SET PERSIST`(재시작 뒤에도 유지되게 저장하는 명령)로 고정해야 해요. 안 그러면 재시작 후 레플리카가 몰래 쓰기를 받는 사고가 날 수 있어요.

**3) 비동기 확인.** 레플리카의 수신을 멈춰도(`STOP REPLICA IO_THREAD`) 소스의 `INSERT`는 바로 성공했어요. 이때 `SHOW REPLICA STATUS`에서 `Replica_IO_Running: No`, `Seconds_Behind_Source: NULL`이었고, 수신을 다시 켜자 몇 초 안에 따라잡았어요.

**4) 반동기 강등과 복귀.** 실험을 빨리 하려고 타임아웃을 2초로 줄였어요.

| 상황 | INSERT 걸린 시간 | 반동기 상태 |
|---|---|---|
| 레플리카 연결됨 | 약 0.02초 | ON |
| 레플리카 수신 멈춤 | 약 2.0초(타임아웃만큼 기다림) | OFF(비동기로 강등) |
| 레플리카 다시 연결 후 다음 INSERT | 빠름 | ON(복귀) |

레플리카가 끊기면 **타임아웃만큼 기다렸다가** 성공하고, 그 뒤로는 조용히 비동기가 된다는 걸 볼 수 있어요. 기본 타임아웃(10초)이라면 그 쓰기는 10초 가까이 걸려요.

### 심화: GTID

복제에서 "레플리카가 어디까지 받았나"를 가리키는 방법은 두 가지예요.

- **바이너리 로그 파일명 + 위치**: 전통 방식. "binlog.000001 파일의 몇 번째 바이트까지"처럼 가리켜요. 리더가 바뀌면 새 리더의 파일·위치를 다시 계산해야 해서 번거로워요.
- **GTID**(Global Transaction ID): 트랜잭션마다 `서버UUID:순번` 형태의 전 세계 고유 번호를 붙여요. 파일·위치를 몰라도 "이 번호들까지 적용했다"로 알 수 있어서, **failover 때 새 소스로 갈아타기가 쉬워요.** 가장 최신 레플리카를 고를 때도 GTID 집합을 비교하면 돼요.

### 심화: 복제 로그는 무엇을 보내나

| 방식 | 보내는 것 | 장점 | 단점 |
|---|---|---|---|
| 구문(statement) 기반 | SQL 문장 그대로 | 작음 | `NOW()`, `RAND()`, 자동 증가, 트리거 때문에 복사본마다 결과가 달라질 수 있음 |
| WAL 배송 | 저장 엔진의 디스크 변경 기록(어느 블록 몇 바이트) | DB 내부 로그 재사용 | 너무 저수준이라 리더·팔로워 DB 버전이 다르면 곤란 → 무중단 업그레이드 어려움 |
| 논리적(로우 기반) | "어느 행이 어떤 값으로 바뀌었나" | 저장 엔진과 분리, 외부 시스템이 읽기 쉬움 | 변경 행이 많으면 로그가 큼 |
| 트리거 기반 | 앱 쪽 트리거·도구가 고른 변경 | 일부 데이터만, 다른 DB로도 가능 | 오버헤드·버그가 많음 |

MySQL은 옛날엔 구문 기반을 썼지만, 지금은 로우 기반이 기본이에요(혼합 모드에서는 비결정적인 문장만 로우 기반으로 바꿔요). PostgreSQL·Oracle은 WAL 배송을 써요. 로우 기반 로그는 **CDC**(Change Data Capture, DB 변경을 외부로 흘려보내는 기법)의 바탕이 돼요.

### 심화: 다중 리더와 리더 없는 복제

단일 리더의 약점은 **모든 쓰기가 리더 한 대를 거친다**는 거예요. 리더에 닿지 못하면 쓰기를 못 해요.

**다중 리더**(multi-leader, active/active)는 쓰기를 받는 노드가 여러 개예요. 각 리더가 서로의 팔로워 역할도 해요. 한 데이터센터 안에서는 복잡하기만 하고 이득이 작아서 잘 안 쓰고, **데이터센터가 여러 곳**일 때(데이터센터마다 리더 하나), 오프라인에서도 동작해야 하는 앱, 여러 명이 동시에 고치는 협업 편집에서 써요. 가장 큰 문제는 **쓰기 충돌**이에요. 같은 데이터를 두 리더에서 동시에 다르게 고치면 어느 쪽을 남길지 정하는 규칙이 필요해요. 단일 리더에선 안 생기는 문제예요.

**리더 없는 복제**(leaderless)는 모든 복제본이 쓰기를 직접 받아요. Amazon의 Dynamo 논문 이후 퍼져서 Cassandra, Riak 같은 DB가 이 방식이에요("다이나모 스타일"). 이름이 비슷한 AWS DynamoDB는 단일 리더 기반이라 헷갈리지 마세요.

- 쓰기는 복제본 n개 모두에 동시에 보내고, w개가 성공하면 성공이에요.
- 읽기도 여러 개에 동시에 보내고, **버전 번호**가 가장 큰 값을 골라요.
- 그래서 노드 하나가 죽어도 failover가 필요 없어요.
- 죽었다 돌아온 노드의 옛 값은 **읽기 복구**(읽다가 옛 값을 가진 노드를 보면 새 값을 써 줌)와 **안티 엔트로피**(백그라운드에서 복제본끼리 차이를 찾아 채움)로 맞춰요.

**정족수**(quorum, "이만큼은 동의해야 인정"하는 최소 인원)가 핵심이에요. 복제본 n개, 쓰기 성공 기준 w개, 읽기 질의 r개일 때 **w + r > n**이면 쓰기가 들어간 노드와 읽기를 보낸 노드가 **최소 한 대는 겹쳐요.** 그래서 최신 값을 읽을 거라고 기대할 수 있어요.

| 설정 | 버티는 장애 | 특징 |
|---|---|---|
| n=3, w=2, r=2 | 노드 1대 | 흔한 기본형 |
| n=5, w=3, r=3 | 노드 2대 | 더 튼튼 |
| n=3, w=3, r=1 | 쓰기는 1대만 죽어도 실패 | 읽기가 아주 많을 때 |

꼭 과반일 필요는 없고 "겹치기만" 하면 돼요. 다만 w + r > n이어도 옛 값이 보이는 경우가 있어요. 동시에 쓴 값을 시계로 정하다 시계가 어긋나 유실되거나, 읽기와 쓰기가 동시에 일어나거나, 일부 노드에만 성공한 쓰기가 되돌려지지 않는 경우 등이에요. 정족수는 **확률을 조정할 뿐 절대 보장이 아니에요.** 강한 보장이 필요하면 트랜잭션이나 [합의](../consensus-raft/)가 필요해요.

## 면접 질문

<details>
<summary>Q1. DB 복제는 왜 하나요?</summary>

**답변(30초)** 세 가지 이유예요. 첫째, 서버 일부가 죽어도 서비스가 계속 돌게 하는 가용성. 둘째, 읽기 요청을 여러 복제본이 나눠 받는 읽기 확장. 셋째, 사용자와 가까운 지역에 복제본을 둬서 응답을 빠르게 하는 거예요. 다만 단일 리더 구조에서 쓰기는 리더 한 대로 몰리기 때문에, 복제로 늘어나는 건 읽기예요.

**꼬리질문**
- Q. 복제가 있으면 백업은 필요 없나요? → 필요해요. 실수로 지운 것도 그대로 복제되니까, 특정 시점으로 되돌리려면 백업이 따로 있어야 해요.
- Q. 쓰기가 병목이면요? → 복제가 아니라 파티셔닝(샤딩)으로 데이터를 나눠야 해요.
</details>

<details>
<summary>Q2. 리더-팔로워(소스-레플리카) 복제 구조를 설명해 주세요.</summary>

**답변(30초)** 쓰기는 리더 한 대만 받아요. 리더는 자기 저장소에 기록한 뒤 변경 내용을 복제 로그로 팔로워에 보내고, 팔로워는 그걸 리더와 같은 순서로 적용해요. 읽기는 팔로워로도 보낼 수 있어서 읽기를 분산할 수 있고, 팔로워는 클라이언트 입장에선 읽기 전용이에요. MySQL에선 리더를 source, 팔로워를 replica라고 불러요.

**꼬리질문**
- Q. 왜 같은 순서로 적용해야 하나요? → 순서가 다르면 같은 변경이라도 최종 결과가 달라질 수 있어서요.
- Q. 레플리카에 실수로 쓰기가 들어가는 걸 어떻게 막나요? → `super_read_only`를 켜고, 설정 파일이나 `SET PERSIST`로 재시작 후에도 유지되게 해요. 앱에서도 쓰기 요청이 소스로만 가는지 확인해요.
</details>

<details>
<summary>Q3. 동기 복제와 비동기 복제의 차이는요?</summary>

**답변(30초)** 리더가 팔로워의 확인을 기다린 뒤 성공을 알리면 동기, 기다리지 않으면 비동기예요. 동기는 팔로워도 항상 최신이라 리더가 죽어도 데이터가 남지만, 팔로워 하나가 응답을 안 하면 쓰기가 전부 멈춰요. 비동기는 빠르고 팔로워 장애에도 쓰기가 계속되지만, 리더가 죽으면 아직 안 넘어간 쓰기를 잃을 수 있어요. 그래서 팔로워 1대만 동기로 두는 반동기를 많이 써요.

**꼬리질문**
- Q. 반동기가 보장하는 건 정확히 뭔가요? → 최소 두 대에 최신 데이터가 있다는 거예요. MySQL 기준으로는 레플리카 1대가 relay log에 받아 디스크에 쓴 것까지만 확인하고, 적용까지는 안 기다려요.
</details>

<details>
<summary>Q4. MySQL 기본 복제 방식은 뭐고, 반동기 복제에서 주의할 점은요?</summary>

**답변(30초)** MySQL은 기본이 비동기예요. 반동기는 플러그인을 소스·레플리카 양쪽에 켜야 하고, 소스는 레플리카 최소 1대가 relay log에 받아 디스크에 썼다는 확인을 기다려요. 주의할 점은 두 가지예요. 레플리카가 적용까지 했는지는 확인하지 않아서 바로 읽으면 안 보일 수 있고, 타임아웃(기본 10초) 안에 확인이 없으면 조용히 비동기로 내려간다는 거예요.

**꼬리질문**
- Q. 비동기로 내려간 걸 어떻게 아나요? → 반동기 상태 변수(소스 쪽 status가 OFF로 바뀜)를 모니터링하고 알림을 걸어야 해요.
- Q. 레플리카가 끊기면 쓰기 응답은 어떻게 되나요? → 타임아웃만큼 기다렸다가 성공해요. 그동안 쓰기 응답이 그만큼 느려져요.
</details>

<details>
<summary>Q5. 리더가 죽으면 어떻게 되나요?</summary>

**답변(30초)** 장애 조치(failover)를 해요. 먼저 타임아웃으로 리더가 죽었다고 판단하고, 가장 최신 데이터를 가진 팔로워를 새 리더로 승격한 다음, 클라이언트와 다른 팔로워가 새 리더를 보게 바꿔요. 옛 리더가 돌아오면 팔로워로 내려야 해요. 비동기라면 옛 리더에만 있던 마지막 쓰기는 사라질 수 있어요.

**꼬리질문**
- Q. 타임아웃은 짧을수록 좋나요? → 아니요. 짧으면 잠깐 느려진 것만으로도 불필요한 failover가 일어나 더 나빠질 수 있고, 길면 복구가 늦어요.
- Q. 가장 최신 레플리카는 어떻게 고르나요? → GTID를 쓰면 각 레플리카가 적용한 트랜잭션 집합을 비교해서 골라요.
</details>

<details>
<summary>Q6. 스플릿 브레인이 뭔가요? 어떻게 막나요?</summary>

**답변(30초)** 두 노드가 둘 다 자기가 리더라고 믿고 쓰기를 받는 상황이에요. 예를 들어 네트워크가 잠깐 끊겨 failover가 됐는데 옛 리더가 살아 있으면 생겨요. 그러면 데이터가 두 갈래로 갈라져서 유실·오염이 생겨요. 막으려면 옛 리더를 강제로 쓰기 불가로 만들거나 끄는 펜싱을 하고, 리더 선출을 과반 합의로 해서 리더가 동시에 둘 생기지 않게 해요.

**꼬리질문**
- Q. 왜 과반이면 막히나요? → 과반 집단은 동시에 두 개가 존재할 수 없어서, 리더를 인정받는 쪽이 하나뿐이에요. 자세한 건 Raft 같은 합의 알고리즘에서 다뤄요.
</details>

<details>
<summary>Q7. (심화) 다중 리더와 리더 없는 복제는 언제 쓰나요?</summary>

**답변(30초)** 다중 리더는 데이터센터가 여러 곳이라 각 지역에서 쓰기를 받아야 하거나, 오프라인 동작·협업 편집이 필요할 때 써요. 대신 같은 데이터를 두 곳에서 동시에 고치는 쓰기 충돌을 해결해야 해요. 리더 없는 복제는 Cassandra처럼 모든 복제본이 쓰기를 받고, 정족수 w + r > n으로 최신 값을 읽게 해요. 리더가 없으니 failover가 필요 없어요.

**꼬리질문**
- Q. n=3이면 w, r은? → 보통 w=2, r=2예요. 2+2 > 3이라 쓰기·읽기 노드가 최소 1대 겹치고, 1대 장애를 버텨요.
- Q. w + r > n이면 항상 최신 값인가요? → 아니에요. 동시 쓰기, 시계 어긋남, 일부만 성공한 쓰기 같은 예외가 있어서 확률적인 보장이에요.
</details>

## 서술형 연습

<details>
<summary>상황 1: 소스와 레플리카의 데이터가 어긋났어요. 확인해 보니 레플리카에 누군가 직접 쓴 행이 있어요.</summary>

**상황 파악**
레플리카는 소스의 변경만 따라 적용해야 하는데, 다른 경로로 쓰기가 들어가 두 서버의 데이터가 갈라졌어요. 이대로 두면 같은 키로 소스에서 온 변경과 충돌해 복제가 멈추거나, 레플리카에서 읽는 사용자가 엉뚱한 데이터를 봐요.

**원인 후보**
- 운영자가 관리자 계정으로 레플리카에 접속해 직접 고쳤다(`read_only`는 관리자 쓰기를 못 막음).
- 레플리카를 재시작했는데 `SET GLOBAL`로만 켜 둔 읽기 전용 설정이 풀렸다.
- 앱의 DB 라우팅 설정 실수로 쓰기 요청이 레플리카로 갔다.

**해결책**
1. **DB에서 막기**: 레플리카에 `super_read_only`를 켜서 관리자 쓰기까지 막아요. 복제 적용은 막지 않아요. 설정 파일이나 `SET PERSIST`로 고정해 재시작 후에도 유지되게 해요. 장점은 어떤 경로든 확실히 막힌다는 것, 단점은 레플리카에서 꼭 해야 하는 관리 작업도 잠깐 설정을 풀어야 한다는 거예요.
2. **앱에서 막기**: 쓰기 요청이 소스로만 가도록 라우팅을 점검하고, 레플리카 접속 계정에는 쓰기 권한을 주지 않아요. 장점은 실수를 일찍 발견한다는 것, 단점은 사람이 관리자 계정으로 직접 들어오는 경우는 못 막는다는 거예요.
3. **이미 어긋난 데이터**: 소스 기준으로 레플리카를 다시 만드는 게 가장 안전해요(소스 스냅숏 → 복사 → 그 시점 이후 변경을 받아 따라잡기).

**내 선택**
1번과 2번을 같이 써요. DB 단의 `super_read_only`를 영구 설정으로 두는 게 최후 방어선이고, 앱 라우팅·계정 권한은 실수를 줄이는 1차 방어선이에요. 어긋난 레플리카는 손으로 맞추지 않고 다시 만들어요.

**채점 포인트**: 레플리카는 읽기 전용이어야 하는 이유, `read_only`와 `super_read_only` 차이(관리자), 복제 적용은 막지 않음, 재시작 시 풀림 → 설정 파일·`SET PERSIST`, 앱 라우팅/계정 권한, 어긋난 레플리카는 재구축
</details>

<details>
<summary>상황 2: 소스 서버가 죽어서 레플리카를 새 소스로 승격했어요. 그런데 장애 직전 몇 초 동안 들어온 주문 몇 건이 사라졌어요.</summary>

**상황 파악**
고객은 주문 "성공" 응답을 받았는데 새 소스에는 그 주문이 없어요. 돈과 관련된 데이터라 유실 자체가 큰 문제예요.

**원인 후보**
- 복제가 **비동기**라서, 옛 소스에 커밋되고 응답까지 나간 주문이 레플리카로 넘어가기 전에 소스가 죽었다.
- 레플리카가 원래 많이 뒤처져 있었다(복제 지연이 컸다).
- 레플리카가 여러 대였는데 가장 최신이 아닌 레플리카를 승격했다.

**해결책**
1. **반동기 복제로 바꾸기**: 레플리카 최소 1대가 받아 디스크에 쓴 뒤에 성공을 알리니, 소스가 죽어도 그 레플리카에 주문이 남아요. 단점은 쓰기마다 왕복 시간이 붙어 느려지고, 레플리카가 끊기면 타임아웃 뒤 비동기로 내려가니 그 상태를 감시해야 한다는 거예요.
2. **비동기 유지 + 유실 대비**: 승격할 때 GTID로 가장 최신 레플리카를 고르고, 옛 소스의 디스크가 살아 있으면 남은 바이너리 로그에서 빠진 트랜잭션을 찾아 다시 넣어요. 결제 시스템 쪽 기록과 대조해 빠진 주문을 재처리해요. 쓰기 성능은 그대로지만 유실을 완전히 막지는 못하고 사후 복구에 손이 많이 가요.
3. **승격 절차 점검**: 뒤처진 레플리카가 승격되면 자동 증가 번호가 이미 쓴 값을 다시 발급할 수 있어요. 외부 시스템이 DB 자동 증가 키에 기대지 않게 하는 것도 함께 봐요.

**내 선택**
주문처럼 잃으면 안 되는 데이터라면 1번 반동기로 가고, 강등 여부를 모니터링·알림으로 꼭 잡아요. 쓰기 지연이 조금 늘어나는 건 주문 유실보다 싸요. 그리고 2번의 "가장 최신 레플리카 선택"은 어떤 방식이든 기본으로 해요.

**채점 포인트**: 비동기 복제의 미전송분 유실, "성공 응답 후에도 유실 가능", 반동기(1대 수신 보장)와 성능 트레이드오프, 타임아웃 시 비동기 강등 감시, GTID로 최신 레플리카 선택, 자동 증가 키 재사용 위험
</details>

<details>
<summary>상황 3: 반동기 복제를 쓰는데, 평소 수십 ms이던 쓰기 응답이 갑자기 10초 가까이 걸려요. 잠시 뒤엔 다시 빨라졌어요.</summary>

**상황 파악**
쓰기 하나가 약 10초 걸렸다가 그 뒤로 빨라졌다는 건, 반동기 기본 타임아웃(10초)과 딱 맞아요. 소스가 레플리카 확인을 기다리다 포기하고 비동기로 내려간 패턴이에요.

**원인 후보**
- 레플리카 서버가 죽었거나 재시작 중이었다.
- 소스와 레플리카 사이 네트워크가 끊기거나 매우 느렸다.
- 레플리카의 수신 스레드가 멈췄다(`Replica_IO_Running: No`).

어느 경우든 확인을 줄 레플리카가 없어서, 소스가 타임아웃만큼 기다린 뒤 비동기로 바뀌었어요. 지금은 빨라졌지만 **비동기 상태**라 이 사이 쓰기는 소스에만 있을 수 있어요.

**해결책**
1. **반동기 레플리카를 2대 이상 두기**: 확인은 1대만 있으면 되니, 한 대가 끊겨도 다른 한 대가 답해서 기다림이 안 생겨요. 서버 비용이 늘어요.
2. **타임아웃 조정**: 줄이면 장애 때 기다리는 시간이 짧아지지만, 잠깐 느린 것만으로 비동기로 자주 내려가서 반동기의 의미가 약해져요. 늘리면 그 반대예요.
3. **모니터링**: 반동기 상태(ON/OFF), 연결된 반동기 레플리카 수, 레플리카의 수신·적용 스레드 상태에 알림을 걸어요. 비동기로 내려간 동안은 유실 위험이 있다는 걸 바로 알 수 있어요.

**내 선택**
1번으로 반동기 레플리카를 2대 이상 두고 3번 모니터링을 꼭 붙여요. 타임아웃은 함부로 줄이지 않아요. 원인이 된 레플리카는 상태를 확인해 복구하고, 다시 따라잡으면 반동기로 자동 복귀하는지도 확인해요.

**채점 포인트**: 반동기 타임아웃(기본 10초)과 응답 시간의 연결, 타임아웃 후 비동기 강등·복귀, 강등 중 유실 위험, 레플리카 여러 대로 확인 여유 확보, 타임아웃 트레이드오프, 상태 모니터링
</details>

## 필기 포인트

- 단일 리더 복제에서 쓰기는 **리더만**, 팔로워는 **같은 순서로** 적용, 클라이언트 입장에서 팔로워는 읽기 전용.
- 동기: 내구성↑, 팔로워 하나 장애 시 쓰기 멈춤. 비동기: 가용성·속도↑, 리더 장애 시 유실 가능.
- MySQL 기본은 **비동기**. 반동기는 레플리카가 relay log에 **받은 것**까지 확인(적용은 X), 타임아웃 시 비동기로 강등.
- `read_only`는 관리자 통과, `super_read_only`는 관리자도 차단. 둘 다 **복제 적용은 막지 않음**.
- 복제는 백업이 아니다. 복제로 늘어나는 건 읽기다.
- 정족수: **w + r > n**이면 읽기·쓰기 집합이 겹침. n=3이면 w=r=2.
