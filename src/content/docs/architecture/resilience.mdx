:::tip[한 줄 요약]
외부 API가 느려지면 그걸 기다리는 우리 스레드·커넥션이 묶여서 **장애가 우리 서비스 전체로 번져요**(연쇄 장애). 그래서 **타임아웃**으로 기다림에 상한을 두고, **재시도**는 멱등한 요청만 **지수 백오프+지터**로 하고, **서킷브레이커**로 계속 실패하는 상대는 잠시 끊고, **벌크헤드**로 자원을 칸막이해 피해를 한곳에 가둬요.
:::

:::note[처음이라면 여기까지]
① 다른 서버를 부를 때 제일 무서운 건 "에러"보다 "응답이 안 오는 것"이에요. 기다리는 동안 우리 서버의 일꾼(스레드)이 묶여서, 결국 상관없는 기능까지 멈춰요.

② 해결 도구는 4개예요. **타임아웃**(최대 몇 초만 기다림), **재시도**(잠깐 실패면 다시 시도), **서킷브레이커**(계속 실패하면 아예 안 부름), **벌크헤드**(이 상대에겐 일꾼 몇 명까지만).

③ 재시도는 조심해야 해요. 결제처럼 두 번 하면 안 되는 요청을 막 다시 보내면 이중 결제가 나고, 다 같이 동시에 다시 보내면 장애가 더 커져요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

집에 있는 **전기 차단기**를 떠올려 봐요. 헤어드라이어 하나가 고장 나서 전기가 과하게 흐르면, 차단기가 "딸깍" 내려가서 그 회로만 끊어요. 덕분에 집 전체에 불이 나지 않고, 냉장고가 있는 다른 회로는 계속 돌아가요. 고장을 고친 뒤 차단기를 살짝 올려 보고, 괜찮으면 그대로 다시 써요.

서버도 똑같아요. 우리 서버가 부르는 **결제 대행사(PG사) API**가 고장 나서 느려졌다고 해 봐요. 차단기가 없으면 우리 서버 일꾼들이 하나둘 그 응답을 기다리느라 멈춰 서고, 결국 결제와 상관없는 "상품 보기"까지 안 돼요. 이게 **연쇄 장애**예요.

- **타임아웃**은 "전화 걸고 3초 안에 안 받으면 끊는다"예요.
- **재시도**는 "통화 중이면 조금 있다 다시 건다"예요.
- **서킷브레이커**는 차단기 그 자체예요. 자꾸 실패하면 한동안 아예 안 걸어요.
- **벌크헤드**(bulkhead, 배의 칸막이벽)는 "이 가게에 전화하는 직원은 최대 5명"처럼 자원을 나눠 두는 거예요. 배 한 칸에 물이 차도 칸막이 덕분에 배 전체는 안 가라앉아요.

단, 실제 차단기는 사람이 다시 올리지만, 소프트웨어 서킷브레이커는 정해진 시간이 지나면 **스스로 몇 건만 시험 삼아** 보내 보고 다시 붙을지 정해요.

## 제대로 알기

### 왜 필요한가: 연쇄 장애가 생기는 과정

다른 서버를 부르면(원격 호출) 실패할 수 있어요. 그런데 더 나쁜 건 **실패하지도 않고 그냥 매달려 있는 것**(hang)이에요. 응답을 기다리는 동안 우리 쪽은 스레드, 커넥션, 메모리 같은 자원을 계속 붙잡고 있거든요.

결제 대행사 응답이 30초씩 걸리기 시작하면 이렇게 번져요.

1. 주문 요청을 처리하던 **스레드**(서버의 일꾼, 요청 하나를 맡아 처리)가 결제 응답을 기다리며 멈춰요.
2. 이 호출이 **트랜잭션**(DB 작업 묶음) 안에 있으면 **DB 커넥션**(DB와 연결된 통로)도 같이 붙잡혀요.
3. 커넥션 풀이 바닥나면 다른 요청은 커넥션을 얻으려고 기다려요. HikariCP는 기본 30초(`connectionTimeout`)까지 기다리다 실패해요. → [커넥션 풀](../../db/connection-pool-query/)
4. 요청 스레드 풀까지 다 차면, 결제와 아무 상관없는 상품 조회 API도 받아 줄 일꾼이 없어 느려지거나 실패해요. → [스레드 풀](../../java/thread-pool/)

즉 **상대 한 곳이 느린 게 우리 전체 장애가 되는 것**이에요. 이 페이지의 도구들은 모두 "피해를 한곳에 가두는" 장치예요.

### 도구 4개 한눈에 비교

| 도구 | 한 줄 뜻 | 막아 주는 것 | 혼자 쓰면 생기는 한계 |
|---|---|---|---|
| 타임아웃 | 최대 N초만 기다림 | 무한 대기로 자원이 묶이는 것 | 느린 동안 매 요청이 N초씩은 여전히 묶임 |
| 재시도+백오프+지터 | 잠깐 실패면 간격을 늘리며 무작위로 다시 시도 | 일시적 실패(순간 끊김 등) | 과부하 때는 부하를 더 키움, 비멱등 요청은 중복 처리 |
| 서킷브레이커 | 실패가 많으면 한동안 아예 안 부름 | 죽은 상대를 계속 두드리는 것 | 폴백이 없으면 사용자에겐 여전히 에러 |
| 벌크헤드 | 이 상대 호출은 동시에 N개까지만 | 한 상대가 공용 스레드를 다 먹는 것 | 한도를 넘는 요청은 거절됨 |

하나만으론 부족해서 보통 함께 써요.

### 타임아웃: 기다림에 상한 두기

**모든 원격 호출에는 타임아웃을 둬요.** 왜냐하면 기본값이 "무한"인 경우가 많기 때문이에요. 예를 들어 Java의 `URLConnection`은 연결·읽기 타임아웃 기본값이 0이고, 0은 **무한 대기**로 해석돼요. 직접 안 정하면 영원히 기다릴 수 있다는 뜻이에요.

타임아웃은 두 가지로 나눠 둬요.

- **연결 타임아웃**(connect timeout): 상대 서버와 연결을 맺기까지 기다리는 시간
- **읽기(요청) 타임아웃**(read timeout): 연결된 뒤 응답이 오기까지 기다리는 시간

너무 길면 앞에서 본 연쇄 장애가 나고, 너무 짧으면 멀쩡한 요청도 실패로 처리돼서 재시도가 늘고 오히려 장애를 부를 수 있어요.

### 재시도: 다시 해 볼 때 지킬 규칙

재시도는 "내 성공 확률을 높이려고 상대 서버를 더 쓰는" 행동이에요. 가끔 일어나는 일시적 실패엔 좋지만, 상대가 **과부하**로 아픈 거라면 재시도가 부하를 더 얹어 회복을 늦춰요. 이걸 **재시도 폭풍**(retry storm)이라고 해요.

지킬 규칙은 네 가지예요.

1. **멱등한 요청만 재시도해요.** **멱등**(idempotent)은 "여러 번 해도 한 번 한 것과 결과가 같다"는 뜻이에요. 타임아웃이 났다고 상대가 처리를 안 한 게 아니에요. 결제는 이미 됐는데 응답만 늦었을 수 있어요. 그래서 결제 같은 요청은 **멱등 키**(idempotency key, 요청마다 붙이는 고유 번호. 같은 번호가 또 오면 서버가 "이미 처리함"으로 응답)가 있을 때만 다시 보내요. → [HTTP 메서드와 멱등](../../web/http-basics/)
2. **4xx는 대부분 재시도하지 않아요.** 4xx는 "요청이 잘못됐다"는 뜻이라 똑같이 다시 보내도 또 실패해요. 5xx(서버 쪽 문제)나 타임아웃이 재시도 후보예요. 단, 429(요청이 너무 많음)처럼 잠시 뒤 다시 보내면 되는 예외도 있어요.
3. **횟수와 간격에 상한을 둬요.** 실패할 때마다 기다리는 시간을 배수로 늘리는 걸 **지수 백오프**(exponential backoff)라고 해요. 간격에 상한(cap)을 두고, 최대 시도 횟수도 정해요.
4. **재시도는 한 곳에서만 해요.** 계층마다 재시도하면 곱으로 불어나요(아래 심화 참고).

### 지터: 다 같이 동시에 다시 보내지 않게

지수 백오프만 하면 문제가 하나 남아요. **같은 순간에 실패한 클라이언트들은 같은 순간에 다시 시도**해요. 모두 "100ms 뒤, 300ms 뒤…"를 똑같이 계산하니까요. 그래서 재시도가 덩어리로 몰려요.

**지터**(jitter)는 기다리는 시간에 **무작위성**을 섞어 재시도 시점을 흩뜨리는 거예요. 가장 흔히 쓰는 **Full Jitter**는 "0부터 백오프 시간 사이에서 아무 값이나 골라 기다린다"예요.

한 번 재 본 예시가 있어요. 클라이언트 100개가 동시에 실패하고, 기본 간격 100ms로 다섯 번 재시도하게 해서 시점만 비교했어요.

| | 지터 없는 지수 백오프 | Full Jitter |
|---|---|---|
| 재시도 시점 | 정확히 5개(100, 300, 700, 1500, 3100ms) | 500번이 387개의 서로 다른 ms에 흩어짐 |
| 같은 1ms에 몰린 최대 건수 | **100건** | **5건** |
| 같은 10ms에 몰린 최대 건수 | 100건 | 26건 |

이 실험은 "언제 몰리나"만 본 것이라 총 호출 수는 같아요. AWS가 한 시뮬레이션(경합하는 클라이언트 100개, 성공도 모델링)에서는 지터를 넣자 총 호출 수가 절반 넘게 줄고 끝나는 시간도 크게 줄었어요.

### 서킷브레이커: 3가지 상태

**서킷브레이커**(circuit breaker)는 외부 호출을 감싸서 실패를 지켜보다가, 실패가 기준을 넘으면 "열려서" **실제로 부르지 않고 바로 에러(또는 폴백)를 돌려주는** 장치예요. 두 가지를 지켜요. 우리 자원(스레드·커넥션)을 지키고, 아픈 상대에게 쉴 시간을 줘요.

| 상태 | 무슨 일 | 다음 상태로 가는 조건 |
|---|---|---|
| CLOSED(닫힘, 정상) | 호출을 그대로 통과시키고 성공·실패를 셈 | 실패율이 기준 이상이면 OPEN |
| OPEN(열림, 차단) | 호출을 바로 거절. 상대에게 안 감 | 정해진 대기 시간이 지나면 HALF_OPEN |
| HALF_OPEN(반열림, 시험) | 시험 호출 몇 건만 통과, 나머지는 거절 | 시험 결과가 괜찮으면 CLOSED, 나쁘면 다시 OPEN |

전기 회로라 "닫힘 = 전기가 흐름 = 정상"이에요. 문(열림 = 통과)과 반대라서 헷갈리기 쉬워요.

**HALF_OPEN이 왜 필요할까요?** OPEN에서 바로 CLOSED로 가면, 이제 막 살아난 상대에게 그동안 밀렸던 요청이 한꺼번에 쏟아져서 다시 쓰러질 수 있어요. 그래서 몇 건만 먼저 보내 보고 확인해요.

### 폴백: 끊었을 때 사용자에게 뭘 줄까

서킷브레이커는 상대를 고쳐 주지 않아요. 그냥 끊기만 하면 사용자는 여전히 에러를 봐요. 그래서 열렸을 때 대신 줄 **폴백**(fallback, 대체 응답)을 정해 둬요.

| 상황 | 폴백 예시 |
|---|---|
| 추천 상품 목록 | 캐시해 둔 이전 목록, 인기 상품 같은 기본 목록, 또는 그 영역만 숨기기 |
| 환율·시세 조회 | 조금 오래된 캐시 값(언제 값인지 표시) |
| 알림 발송 | 큐에 넣어 두고 나중에 보내기 |
| 결제 | "처리 중"으로 받고 나중에 결과 확인. 돈이 걸린 건 **모르면 성공으로 치지 않는 것**이 안전 |

기능 일부를 포기하고 핵심은 살리는 걸 **그레이스풀 디그레이데이션**(graceful degradation, 우아하게 기능 줄이기)이라고 해요.

### 벌크헤드: 자원 칸막이

**벌크헤드**는 특정 상대를 부를 수 있는 **동시 실행 수를 따로 묶어 두는** 거예요. 예를 들어 PG사 호출은 동시에 20개까지만 허용하면, PG사가 느려져도 그 20개만 묶이고 나머지 요청 스레드는 다른 기능을 계속 처리해요.

서킷브레이커와 헷갈리기 쉬워요.

- 벌크헤드: "**동시에 몇 개까지**" — 자원을 나눠서 격리
- 서킷브레이커: "**실패가 많으면 아예 안 부름**" — 빠르게 실패

### 심화: Resilience4j 서킷브레이커 기본값

**Resilience4j**는 Java에서 많이 쓰는 장애 대응 라이브러리예요. 서킷브레이커 기본값은 이래요.

| 속성 | 기본값 | 뜻 |
|---|---|---|
| failureRateThreshold | 50% | 실패율이 이 값 이상이면 OPEN |
| slowCallRateThreshold | 100% | 느린 호출 비율이 이 값 이상이면 OPEN |
| slowCallDurationThreshold | 60초 | 이보다 오래 걸리면 "느린 호출" |
| slidingWindowType | COUNT_BASED | 최근 N건으로 계산(TIME_BASED면 최근 N초) |
| slidingWindowSize | 100 | 윈도우 크기 |
| minimumNumberOfCalls | 100 | 이만큼 쌓여야 실패율 계산 시작 |
| waitDurationInOpenState | 60초 | OPEN 유지 시간 |
| permittedNumberOfCallsInHalfOpenState | 10 | HALF_OPEN 시험 호출 수 |
| automaticTransitionFromOpenToHalfOpenEnabled | false | 시간이 지나도 **다음 호출이 와야** HALF_OPEN으로 바뀜 |

OPEN일 때 들어온 호출은 `CallNotPermittedException`으로 거절돼요. 이 밖에 운영자가 수동으로 쓰는 특수 상태도 있어요. DISABLED(항상 허용), FORCED_OPEN(항상 거절), METRICS_ONLY(항상 허용하고 지표만 기록)예요.

자주 걸리는 함정 세 가지예요.

- **트래픽이 적은 API는 잘 안 열려요.** `minimumNumberOfCalls`가 100이라, 호출이 100건 쌓이기 전엔 실패율을 계산하지 않아요. 작은 값이나 TIME_BASED 윈도우로 조정해요.
- **느린 호출 기준이 기본값으론 거의 안 걸려요.** 60초 넘는 호출이 100%여야 열리니까요. 실무에선 낮춰서 써요.
- 모든 예외를 실패로 세면 안 돼요. 4xx처럼 상대 장애가 아닌 건 `ignoreExceptions`로 빼요.

설정 예시(값은 설명용이에요).

```yaml
resilience4j:
  circuitbreaker:
    instances:
      pg:                                  # PG사 호출용
        sliding-window-type: TIME_BASED    # 최근 N초 기준
        sliding-window-size: 10            # 10초
        minimum-number-of-calls: 20        # 적은 트래픽에서도 판단
        failure-rate-threshold: 50
        slow-call-duration-threshold: 2s   # 2초 넘으면 느린 호출
        slow-call-rate-threshold: 50
        wait-duration-in-open-state: 30s
  bulkhead:
    instances:
      pg:
        max-concurrent-calls: 20           # 동시에 20개까지만
```

### 심화: Retry·TimeLimiter·Bulkhead 기본값과 적용 순서

| 모듈 | 기본값 | 주의 |
|---|---|---|
| Retry | `maxAttempts` 3, `waitDuration` 500ms 고정 간격 | 3은 **첫 호출 포함 총 3번**(재시도는 2번). 지수 백오프는 `IntervalFunction`으로 따로 지정 |
| TimeLimiter | `timeoutDuration` 1초, `cancelRunningFuture` true | 비동기 호출(`CompletableFuture` 등)에 시간 제한 |
| Bulkhead(세마포어) | `maxConcurrentCalls` 25, `maxWaitDuration` 0 | 꽉 차면 바로 `BulkheadFullException` |
| Bulkhead(스레드 풀) | `queueCapacity` 100, 스레드 수는 CPU 수 기준 | 별도 스레드 풀 + 유한 큐 |

Retry 기본은 "모든 예외를 재시도"라서, 멱등하지 않은 호출에 그냥 붙이면 위험해요.

Spring Boot에서 애노테이션으로 여러 개를 붙이면 기본 적용 순서는 이래요(바깥 → 안).

```
Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( 실제 호출 ) ) ) ) )
```

Retry가 가장 바깥이에요. 순서는 `*AspectOrder` 속성으로 바꿀 수 있어요. Retry가 바깥에 있으면 서킷이 OPEN일 때 나는 `CallNotPermittedException`까지 재시도할 수 있어서, 이 예외는 재시도에서 빼라고 많이들 권해요(공식 문서 문장으로 확인한 건 아니고 실무 관행이에요).

### 심화: 재시도는 계층마다 곱해진다

재시도를 여러 층에서 하면 곱셈이 돼요. AWS 글의 예시에서는 5개 계층이 각각 3번씩 시도하면 맨 아래 DB가 받는 부하가 3×3×3×3×3 = **243배**가 돼요. 4개 계층(게이트웨이·서비스A·서비스B·DB 클라이언트)만 해도 3⁴ = 81배예요.

그래서 **재시도는 한 지점에서만** 해요. AWS는 여기에 더해 **재시도 토큰 버킷**(재시도할 때마다 토큰을 쓰고, 토큰이 떨어지면 재시도를 거의 멈추는 방식)으로 재시도 양 자체를 제한해요. 결론은 "상대가 건강해 보일 때만 재시도하고, 재시도가 도움이 안 되면 멈춘다"예요.

### 심화: 타임아웃 값 정하는 법

AWS가 권하는 방법이에요.

1. "잘못 끊어도 괜찮은 비율"을 정해요. 예: 0.1%
2. 상대 서비스 응답 시간의 그 백분위를 타임아웃으로 써요. 0.1%면 **p99.9**(1000번 중 999번은 이 시간 안에 끝남)
3. p99.9가 p50(중간값)과 거의 같으면 여유를 더 줘요. DNS 조회·TLS 연결 시간이 포함되는지도 따져요.

### 심화: 지터 공식

AWS 블로그에서 비교한 방식들이에요(원문은 그림이라, 널리 알려진 표기로 적었어요). `base`는 기본 간격, `cap`은 상한, `attempt`는 몇 번째 시도인지예요.

```
지수 백오프:        sleep = min(cap, base * 2^attempt)
Full Jitter:        sleep = random(0, min(cap, base * 2^attempt))
Equal Jitter:       t = min(cap, base * 2^attempt)
                    sleep = t/2 + random(0, t/2)
Decorrelated Jitter: sleep = min(cap, random(base, 이전sleep * 3))
```

AWS 시뮬레이션 결과로는 지터 없는 백오프가 가장 나빴고, 지터 중엔 Equal이 가장 나빴어요. Full은 Decorrelated보다 호출 수가 적고 시간은 조금 더 걸렸어요. 지터는 재시도뿐 아니라 매일 같은 시각에 도는 **크론 작업** 시작 시간에도 넣어요.

### 심화: 서킷브레이커의 단점

AWS는 서킷브레이커가 "상태(모드)"를 만들어서 테스트하기 어렵고, 회복을 오히려 늦출 수 있다고 봐요. 그래서 AWS는 앞의 토큰 버킷 재시도 제한을 대안으로 써요. 서킷브레이커를 쓴다면 임계치 튜닝, 상태 바뀔 때 로그·알림, 수동으로 열고 닫는 기능을 같이 준비해요.

<summary>Q. 외부 API에 타임아웃을 왜 꼭 설정해야 하나요?</summary>

**답변(30초)**
안 정하면 무한히 기다릴 수 있고, 그동안 우리 자원이 묶이기 때문이에요. 응답을 기다리는 동안 요청 스레드와, 트랜잭션 안이면 DB 커넥션까지 붙잡고 있어요. 상대가 느려지면 이게 쌓여서 스레드 풀·커넥션 풀이 바닥나고, 상관없는 API까지 실패하는 연쇄 장애가 나요. Java `URLConnection`도 기본값이 0, 즉 무한 대기라 직접 연결·읽기 타임아웃을 나눠서 설정해야 해요.

**꼬리질문**
- Q. 타임아웃 값은 어떻게 정하나요? → 상대 응답 시간 분포를 보고, 허용할 오탐 비율에 맞는 백분위(예: p99.9)로 정해요. 너무 짧으면 멀쩡한 요청도 끊겨서 재시도가 늘어요.
- Q. 연결 타임아웃과 읽기 타임아웃은 뭐가 다른가요? → 연결은 연결을 맺기까지, 읽기는 연결 후 응답이 오기까지 기다리는 시간이에요.
</details>

<details>
<summary>Q. 서킷브레이커가 무엇이고, 상태 전이를 설명해 주세요.</summary>

**답변(30초)**
서킷브레이커는 외부 호출의 실패를 지켜보다가 기준을 넘으면 호출을 아예 막고 바로 에러나 폴백을 돌려주는 장치예요. 평소 CLOSED에선 호출을 통과시키며 실패율을 세고, 실패율이 기준(Resilience4j 기본 50%) 이상이면 OPEN이 되어 호출을 즉시 거절해요. 대기 시간이 지나면 HALF_OPEN에서 시험 호출 몇 건만 보내 보고, 괜찮으면 CLOSED, 아니면 다시 OPEN으로 가요. 우리 자원을 지키고 상대에게 회복할 시간을 주는 게 목적이에요.

**꼬리질문**
- Q. HALF_OPEN은 왜 필요한가요? → 바로 CLOSED로 가면 막 회복한 상대에게 밀린 요청이 한꺼번에 몰려 다시 쓰러질 수 있어서, 몇 건만 시험해요.
- Q. 서킷이 열렸을 때 사용자에겐 뭘 주나요? → 폴백이요. 캐시된 이전 값, 기본값, "처리 중" 응답 후 큐로 나중에 처리, 그 기능만 숨기기 등이에요.
- Q. 트래픽이 적은 API에서 장애가 났는데 서킷이 안 열렸어요. 왜죠? → Resilience4j는 `minimumNumberOfCalls`(기본 100)만큼 호출이 쌓여야 실패율을 계산해요. 값을 줄이거나 TIME_BASED 윈도우를 써요.
</details>

<details>
<summary>Q. 재시도할 때 주의할 점은 무엇인가요?</summary>

**답변(30초)**
네 가지예요. 첫째, 멱등한 요청이나 멱등 키가 있는 요청만 재시도해요. 타임아웃이 나도 상대는 이미 처리했을 수 있어서요. 둘째, 4xx처럼 다시 해도 실패할 오류는 재시도하지 않아요. 셋째, 지수 백오프와 지터로 간격을 벌리고 흩뜨리며 최대 횟수를 둬요. 넷째, 재시도는 한 계층에서만 해요. 층마다 하면 곱으로 늘어나서 장애를 키워요.

**꼬리질문**
- Q. Resilience4j `maxAttempts=3`이면 재시도를 몇 번 하나요? → 첫 호출을 포함해 총 3번이라 재시도는 2번이에요.
- Q. Retry와 CircuitBreaker를 같이 쓰면 순서는? → Spring Boot 애노테이션 기본은 Retry가 바깥이에요. 그러면 OPEN 거절 예외까지 재시도할 수 있어서 그 예외는 재시도 대상에서 빼는 게 보통이에요.
</details>

<details>
<summary>Q. 지수 백오프와 지터는 무엇이고, 지터는 왜 필요한가요?</summary>

**답변(30초)**
지수 백오프는 실패할 때마다 재시도 간격을 배수로 늘리는 거예요. 그런데 백오프만 하면 같은 순간 실패한 클라이언트들이 같은 계산으로 같은 순간에 다시 몰려요. 지터는 대기 시간에 무작위성을 섞어 이걸 흩뜨려요. 예를 들어 100개가 동시에 실패했을 때 지터 없으면 같은 1ms에 100개가 몰렸지만, Full Jitter를 쓰면 1ms당 최대 5건 정도로 퍼졌어요.

**꼬리질문**
- Q. Full Jitter 공식은? → 0부터 `min(cap, base × 2^시도횟수)` 사이 무작위 값만큼 기다려요.
- Q. 재시도 말고 지터를 어디에 또 쓰나요? → 매일 같은 시각에 도는 크론·주기 작업 시작 시간이요. 모든 서버가 동시에 시작하지 않게 해요.
</details>

<details>
<summary>Q. 벌크헤드란 무엇이고, 서킷브레이커와 뭐가 다른가요?</summary>

**답변(30초)**
벌크헤드는 배의 칸막이처럼, 특정 외부 호출에 쓸 수 있는 동시 실행 수를 따로 떼어 두는 패턴이에요. PG사 호출을 동시에 20개로 묶어 두면, PG사가 느려져도 그 20개만 묶이고 나머지 스레드는 다른 기능을 처리해요. 서킷브레이커는 실패가 많으면 아예 안 부르는 "빠른 실패"이고, 벌크헤드는 "동시에 몇 개까지"로 자원을 격리하는 거라 목적이 달라요. 보통 둘을 함께 써요.

**꼬리질문**
- Q. Resilience4j 벌크헤드 구현은? → 세마포어 방식(기본 동시 25개, 꽉 차면 바로 거절)과 별도 고정 스레드 풀+큐 방식이 있어요.
</details>

<details>
<summary>Q. 서킷브레이커의 단점이나 한계는 무엇인가요?</summary>

**답변(30초)**
서킷브레이커는 상대를 고쳐 주지 않아요. 폴백이 없으면 사용자는 여전히 에러를 봐요. 또 상태가 생겨서 테스트가 어렵고, 임계치를 잘못 잡으면 너무 늦게 열리거나 회복을 늦출 수 있어요. 그래서 AWS는 토큰 버킷으로 재시도 양을 제한하는 방식을 대안으로 쓰기도 해요. 쓸 때는 임계치 튜닝, 상태 변경 알림, 수동 열기·닫기를 같이 준비해요.

**꼬리질문**
- Q. 모든 예외를 실패로 세면 어떻게 되나요? → 사용자 입력 오류(4xx) 같은 것까지 세면 상대가 멀쩡한데도 서킷이 열려요. 그런 예외는 제외해요.
</details>

## 서술형 연습

<details>
<summary>상황: PG사(결제 대행사) API 응답이 30초씩 걸리기 시작하더니, 결제와 상관없는 상품 조회까지 우리 서버 전체가 먹통이 됐어요. 원인과 대응을 설명하세요.</summary>

**상황 파악**
결제 외 API까지 같이 죽었다는 건 PG사 문제 자체보다 **우리 쪽 공용 자원이 고갈**됐다는 신호예요. 스레드 덤프에서 PG사 응답을 기다리는 스레드가 대부분이고, 커넥션 풀 대기(Hikari pending)가 늘어 있는지 확인해요.

**원인 후보**
- 외부 호출에 타임아웃이 없거나 너무 길어서 스레드가 30초씩 묶임
- 결제 호출이 트랜잭션 안에 있어서 DB 커넥션까지 30초씩 묶임 → 커넥션 풀 고갈 → 상품 조회도 커넥션을 못 얻음
- PG사 호출에 동시 실행 제한이 없어서 공용 요청 스레드를 다 먹음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 연결·읽기 타임아웃 설정(예: 수 초) | 가장 간단, 자원 묶임 시간에 상한 | 느린 동안은 매 요청이 그만큼씩은 여전히 묶임 |
| B. 외부 호출을 트랜잭션 밖으로 | DB 커넥션이 외부 지연에 안 묶임 | 결제 전후 DB 작업을 나눠야 해서 상태 관리가 복잡해짐 |
| C. 벌크헤드로 PG 호출 동시 수 제한 | 나머지 기능은 PG 장애와 무관하게 동작 | 한도 넘는 결제 요청은 거절됨 |
| D. 서킷브레이커 + 폴백 | 장애 동안 아예 안 불러서 빠르게 응답, PG사에 회복 시간 | 임계치 튜닝 필요, 결제 폴백("잠시 후 다시")은 사용자 경험 손해 |

**내가 고를 방법**
당장은 A와 B로 자원 묶임을 끊어요. 그다음 C로 PG 호출을 칸막이하고, D로 장애가 계속될 때 빠르게 실패시켜요. 핵심은 "PG사가 죽어도 결제만 안 되고 나머지는 살아 있게" 하는 거예요. 재시도는 이 상황에선 부하만 키우니 멱등 키가 있을 때만, 지터를 넣어 한 곳에서만 해요.

**채점 포인트**: 연쇄 장애(스레드·커넥션 풀 고갈), 타임아웃 기본값이 무한일 수 있음, 연결/읽기 타임아웃 구분, 트랜잭션 밖으로 외부 호출, 벌크헤드, 서킷브레이커 3상태, 폴백, 진단 근거(스레드 덤프·커넥션 풀 지표).
</details>

<details>
<summary>상황: 외부 API가 가끔 실패해서 재시도를 넣었는데, 그 API가 느려진 날 오히려 장애가 더 크고 길어졌어요. 왜 그럴까요?</summary>

**상황 파악**
재시도가 "일시적 실패"가 아니라 "과부하"에 걸렸어요. 상대는 이미 버거운데 우리가 요청을 몇 배로 늘려 보낸 셈이에요.

**원인 후보**
- **재시도 폭풍**: 과부하로 실패 → 재시도가 부하를 더함 → 더 실패 → 더 재시도
- **계층별 재시도의 곱**: 게이트웨이·서비스A·서비스B·DB 클라이언트가 각각 3번씩 시도하면 최악 3⁴ = 81배. AWS 예시처럼 5계층이면 243배
- **지터 없는 백오프**: 동시에 실패한 클라이언트들이 같은 순간 다시 몰려서, 상대가 회복하려는 순간마다 스파이크
- 타임아웃이 너무 짧아 멀쩡한 요청까지 실패 처리 → 재시도 증가

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 재시도를 한 계층으로 모으기 | 증폭이 곱에서 덧셈 수준으로 | 다른 계층은 일시적 실패를 그냥 위로 올려야 함 |
| B. 지수 백오프 + Full Jitter + 최대 횟수 | 몰림이 사라지고 총 호출도 줄어듦 | 성공까지 걸리는 시간이 늘 수 있음 |
| C. 재시도 토큰 버킷(재시도 양 제한) | 장애 때 재시도가 자동으로 줄어듦 | 구현·튜닝 필요 |
| D. 서킷브레이커 | 계속 실패하면 아예 안 불러서 상대가 쉴 수 있음 | 폴백 필요, 상태 관리·테스트 부담 |

**내가 고를 방법**
먼저 A로 재시도를 한 곳(예: 호출하는 서비스의 클라이언트)에만 두고, B로 백오프+지터와 최대 횟수를 넣어요. 장애가 길어질 때를 대비해 D를 붙이고, Retry가 OPEN 거절까지 재시도하지 않게 설정해요. 트래픽이 큰 서비스라면 C도 검토해요.

**채점 포인트**: 재시도는 이기적(상대 용량을 더 씀), 재시도 폭풍, 계층 곱(3^n, 243배), 한 지점에서만 재시도, 지수 백오프+지터(동시 몰림 제거), 최대 횟수, 서킷브레이커와 조합, 타임아웃이 너무 짧을 때의 부작용.
</details>

<details>
<summary>상황: 결제 요청이 타임아웃 나서 자동으로 재시도했더니, 고객 카드에서 돈이 두 번 빠졌어요. 원인과 재발 방지책은?</summary>

**상황 파악**
타임아웃은 "응답을 못 받았다"일 뿐 "상대가 처리 안 했다"가 아니에요. 첫 요청은 PG사에서 이미 승인됐는데 응답만 늦었고, 우리가 같은 결제를 새 요청으로 또 보낸 거예요.

**원인 후보**
- 결제(POST)는 멱등하지 않은데 일반 요청처럼 재시도함
- 요청에 멱등 키가 없어서 PG사가 두 요청을 다른 결제로 처리함
- 여러 계층(클라이언트 앱, 게이트웨이, 서버)이 각자 재시도함

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 멱등 키: 결제마다 고유 키를 만들어 재시도 때도 같은 키로 보냄 | 같은 키는 한 번만 처리돼 재시도가 안전해짐 | 상대 API가 멱등 키를 지원해야 함. 우리 쪽도 키 저장·만료 관리 필요 |
| B. 타임아웃 시 재시도 대신 결제 상태 조회 API로 확인 | 실제 결과를 확인하고 움직임 | 조회 API가 필요하고 확인까지 시간이 걸림. 그동안 "처리 중" 상태 관리 |
| C. 결제는 재시도 금지, 실패로 처리 | 단순, 중복 위험 없음 | 실제로는 승인됐는데 실패로 보여 줄 수 있어 대사(정산 맞추기) 작업 필요 |

**내가 고를 방법**
A를 기본으로 하고 B를 같이 써요. 결제 요청을 만들 때 멱등 키를 생성해 저장하고, 타임아웃이 나면 먼저 상태 조회로 확인한 뒤, 정말 안 된 경우에만 **같은 키로** 다시 보내요. 사용자에겐 그동안 "결제 처리 중"을 보여 줘요. 재시도는 한 계층에서만 하도록 정리해요.

**채점 포인트**: 타임아웃 ≠ 미처리, POST 비멱등, 멱등 키(같은 키 재사용), 상태 조회로 확인, "처리 중" 상태, 재시도는 한 계층에서만, 돈이 걸린 건 모르면 성공으로 치지 않기.
</details>

<details>
<summary>상황: 추천 서비스 하나가 장애가 났는데, 앱 메인 화면 전체가 에러로 떠요. 어떻게 개선하겠어요?</summary>

**상황 파악**
메인 화면에서 추천은 "있으면 좋은" 부가 기능인데, 그 하나의 실패가 화면 전체 실패로 번졌어요. 부가 기능 장애를 격리하지 못한 거예요.

**원인 후보**
- 메인 API가 추천 호출 실패(또는 타임아웃) 예외를 그대로 던져서 응답 전체가 실패
- 추천 호출에 타임아웃이 없거나 길어서 메인 API 자체가 느려지고 스레드가 묶임
- 추천 호출이 순차로 묶여 있어서, 다른 영역(배너·주문 내역)도 같이 기다림

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 짧은 타임아웃 + 실패 시 그 영역만 비우기/숨기기 | 메인 화면은 항상 뜸 | 추천 없는 화면이 노출됨 |
| B. 폴백으로 캐시된 이전 추천이나 인기 상품 목록 | 사용자는 차이를 거의 못 느낌 | 캐시가 오래되면 엉뚱한 추천, 캐시 관리 필요 |
| C. 서킷브레이커로 장애 동안 추천 호출 자체를 건너뜀 | 메인 API 응답이 빨라지고 추천 서비스도 쉼 | 임계치 튜닝, 회복 판단은 HALF_OPEN에 맡김 |
| D. 벌크헤드로 추천 호출 동시 수 제한 | 추천이 느려도 메인 API 스레드를 다 먹지 못함 | 한도 초과분은 바로 폴백 |

**내가 고를 방법**
기능을 "핵심"과 "부가"로 나누고, 추천 같은 부가 기능엔 A+B+C를 같이 걸어요. 짧은 타임아웃, 서킷브레이커, 실패 시 캐시된 인기 목록으로 폴백, 그것도 없으면 영역 숨기기 순이에요. 이게 그레이스풀 디그레이데이션이에요. 캐시 폴백을 쓸 땐 캐시가 한꺼번에 만료돼 생기는 문제도 같이 챙겨요.

**채점 포인트**: 핵심/부가 기능 구분, 폴백(캐시·기본값·숨기기), 그레이스풀 디그레이데이션, 짧은 타임아웃, 서킷브레이커, 벌크헤드, 부분 실패를 전체 실패로 만들지 않는 응답 설계.
</details>

## 필기 포인트

- 서킷브레이커 상태: **CLOSED**(정상, 통과) → **OPEN**(차단, 즉시 거절) → **HALF_OPEN**(시험 호출) → CLOSED 또는 OPEN. "닫힘 = 정상"이 함정.
- 지수 백오프 = 실패마다 간격을 배수로 늘림. 지터 = 간격에 무작위성 추가. Full Jitter = `random(0, min(cap, base × 2^n))`.
- 재시도 대상: 5xx·타임아웃. 4xx는 대부분 재시도하지 않음(429 같은 예외는 잠시 뒤 재시도). 비멱등 요청은 멱등 키 없이 재시도 금지.
- 계층별 재시도는 곱: 3번씩 5계층 = 3⁵ = 243배.
- 벌크헤드 = 동시 실행 수 격리(배의 칸막이). 서킷브레이커 = 실패 많으면 호출 차단.
- Resilience4j 기본: 실패율 50%, 윈도우 100건, 최소 100건, OPEN 60초, HALF_OPEN 시험 10건. Retry `maxAttempts` 3 = 총 3번.
