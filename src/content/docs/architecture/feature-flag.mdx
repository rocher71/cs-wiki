:::tip[한 줄 요약]
**피처 플래그**(feature flag, 피처 토글)는 코드를 다시 배포하지 않고 기능을 **켜고 끄는 스위치**예요. 이걸로 **코드 배포와 기능 출시를 분리**해서, 미완성·미공개 기능을 꺼 둔 채 운영에 올려 두고, 1% → 10% → 100%처럼 조금씩 열거나 문제가 생기면 **재배포 없이 즉시 끌 수** 있어요.
:::

:::note[처음이라면 여기까지]
① 피처 플래그는 코드 안에 넣어 둔 **전등 스위치**예요. 코드는 이미 서버에 있지만, 스위치가 꺼져 있으면 사용자에겐 안 보여요.

② 그래서 "**배포**(코드를 서버에 올리기)"와 "**출시**(사용자에게 기능 보여 주기)"를 다른 날 할 수 있어요.

③ 새 기능은 일부 사용자부터 조금씩 열고, 문제가 생기면 스위치를 내려요. 이게 롤백(옛 버전 재배포)보다 빨라요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
피처 플래그는 표준 기관이 정한 용어가 아니라서, 이 분야에서 널리 인용되는 업계 참고 글(Pete Hodgson의 "Feature Toggles", Martin Fowler의 bliki, trunkbaseddevelopment.com)과 OpenFeature 사양, Spring Boot 공식 문서를 바탕으로 했어요(2026-11 조회).
</Aside>

## 쉽게 이해하기

새로 지은 건물에 **전등을 미리 다 달아 두는** 상황을 떠올려 봐요.

전기 공사(배포)는 평일 낮에 조용히 끝내요. 전등은 달렸지만 스위치는 내려 둬요. 손님은 아무것도 못 느껴요. 개업일(출시)이 되면 공사 없이 **스위치만 올리면** 돼요.

처음엔 1층 복도 한 칸만 켜 보고, 괜찮으면 층을 늘려 가요. 어느 전등에서 스파크가 튀면 다시 공사할 필요 없이 그 스위치만 내리면 돼요. 이게 **킬 스위치**예요.

단, 실제로는 스위치가 늘어날수록 "이 스위치가 뭘 켜는 거였지?"가 헷갈려져요. 다 쓴 스위치는 떼어 내야 해요. 이걸 **토글 부채**라고 하고, 뒤에서 다뤄요.

## 제대로 알기

### 왜 필요한가: 배포 ≠ 출시

**배포**(deploy)는 새 코드를 운영 서버에 올리는 일이고, **출시**(release)는 사용자가 그 기능을 쓰게 되는 순간이에요. 플래그가 없으면 둘이 같은 순간에 일어나요. 그러면 이런 문제가 생겨요.

- 금요일 오전 10시 오픈 기능이면, 하필 그 시각에 배포해야 해요. 배포가 실패하면 오픈도 실패해요.
- 기능이 완성될 때까지 코드를 긴 **피처 브랜치**(본 코드와 따로 떨어진 작업용 사본)에 쌓아 둬야 하고, 나중에 합칠 때 충돌이 커져요.
- 문제가 생기면 옛 버전을 다시 배포(**롤백**)해야 해서 시간이 걸려요.

피처 플래그는 코드 안에 분기를 하나 두고, 그 분기를 **밖에서** 켜고 끌 수 있게 해요. 코드를 고치지 않고 동작을 바꾸는 거예요. 그래서 미완성 기능도 꺼 둔 채로 매일 main에 합칠 수 있어요. 모두가 짧은 주기로 main(트렁크)에 합치는 **트렁크 기반 개발**(trunk-based development)이 가능해지는 이유가 이거예요.

```java
// 토글 지점: 여기서 새 길/옛 길이 갈라짐
if (featureDecisions.newCheckoutEnabled(userId)) {
    return newCheckout(order);   // 새 결제 화면
}
return oldCheckout(order);       // 기존 결제 화면 (플래그 off = 기존 동작)
```

관례상 **off = 기존 동작, on = 새 동작**으로 둬요.

### 플래그는 4종류

Hodgson은 플래그를 두 기준으로 나눴어요. **얼마나 오래 사는가**(며칠 vs 몇 년), **얼마나 자주 바뀌는가**(배포마다 고정 vs 요청마다 다름)예요.

| 종류 | 용도 | 수명 | 바뀌는 빈도 |
|---|---|---|---|
| 릴리스 토글 | 미완성·미공개 기능을 꺼 둔 채 배포 | 짧음(보통 1~2주) | 한 배포 안에선 고정 |
| 실험 토글 | A/B 테스트(사용자를 나눠 다른 화면 보여 주기) | 결과가 통계적으로 나올 때까지(몇 시간~몇 주) | 요청마다(사용자별로 다름) |
| 운영 토글 | 부하·장애 때 기능 끄기, 킬 스위치 | 대부분 짧음, 일부 킬 스위치는 오래 | 재배포 없이 바로 바꿀 수 있어야 함 |
| 권한 토글 | 유료 회원·내부 직원·베타 사용자에게만 기능 제공 | 몇 년까지 | 요청마다(누구냐에 따라) |

권한 토글은 사실상 "요금제 규칙"이라 오래 살아도 괜찮아요. 반대로 릴리스 토글은 출시가 끝나면 **반드시 지워야** 하는 임시 스위치예요.

### 점진 출시: 1% → 10% → 100%

새 기능을 한 번에 전원에게 열지 않고, 조금씩 넓히는 걸 **점진 출시**(progressive rollout)라고 해요.

1. 새 코드를 플래그 off로 배포해요. 사용자는 변화 없음.
2. 내부 직원에게만 켜요. 지정한 그룹에 먼저 보여 주는 이 방식을 **샴페인 브런치**(champagne brunch, 사내에서 먼저 써 보기)라고도 불러요.
3. 무작위 1%에게 켜고 에러율·응답 시간·전환율을 봐요. 소수에게 먼저 노출하는 이 방식이 **카나리 릴리스**예요.
4. 괜찮으면 10% → 50% → 100%로 **비율 숫자만** 올려요. 재배포는 없어요.
5. 문제가 보이면 플래그 off. 즉시 기존 경로로 돌아가요.
6. 100%로 안정되면 플래그와 옛 코드를 삭제해요.

여기서 중요한 함정이 있어요. 1%를 `random() < 0.01`처럼 **요청마다** 뽑으면, 같은 사람이 새로고침할 때마다 화면이 바뀌어요. 그래서 **사용자 ID를 기준으로 고정 배정**해요. Hodgson 글은 사용자 ID를 100으로 나눈 나머지 같은 값으로 고르는 예를 들어요. 실무에서는 `hash(플래그이름 + 사용자ID) % 100 < 비율`처럼 해시를 쓰는 방식이 흔해요. 이렇게 하면 비율을 1에서 10으로 올려도 처음 켜졌던 1%는 계속 켜진 상태로 남아요.

### 킬 스위치: 재배포 없이 바로 끄기

**킬 스위치**(kill switch)는 장애 때 **핵심이 아닌 기능**을 끄는 운영 토글이에요. 예를 들어 결제 페이지의 상품 추천을 불러오는 외부 API가 느려져서 서버 **스레드**(요청 하나를 처리하는 작업자)가 다 묶이기 직전이라면, 추천을 꺼서 결제만은 살려요. 이렇게 일부 기능을 포기하고 핵심을 지키는 걸 **우아한 기능 저하**(graceful degradation)라고 해요.

킬 스위치의 조건은 하나예요. **재배포·재시작 없이 몇 초 안에** 바뀌어야 해요. 그래서 플래그 값을 어디에 두느냐가 중요해요.

| 플래그 값을 두는 곳 | 바꾸려면 | 킬 스위치로 쓸 수 있나 |
|---|---|---|
| 코드에 하드코딩 | 코드 수정 + 배포 | 아니요 |
| 환경변수·실행 인자 | 재시작(또는 재배포) | 아니요 |
| 설정 파일 | 보통 재배포 | 아니요 |
| DB + 관리 화면, 또는 etcd·Consul 같은 분산 저장소 | 화면에서 바로 변경, 서버들이 알아서 받아 감 | 예 |

여기서 **분산 저장소**는 서버 여러 대가 같은 값을 나눠 보는 공용 메모장 같은 시스템이에요. 서버가 다시 떠도 값이 남아 있고, 모든 서버가 같은 값을 봐야 해서 이런 공유 저장소가 필요해요.

### 다크 런치: 안 보이게 미리 돌려 보기

**다크 런치**(dark launching)는 새 백엔드 기능을 **실제 사용자 요청으로 실행하되, 결과는 사용자에게 보여 주지 않는** 방법이에요. 목적은 공개 전에 **부하와 성능**을 실제 트래픽으로 재 보는 거예요.

Fowler가 드는 예는 결제 화면의 상품 추천이에요. 결제 요청이 올 때마다 새 추천 엔진을 실제로 호출하지만, 결과는 화면에 그리지 않고 버려요. 그동안 응답 시간과 DB 부하만 지켜봐요. 괜찮으면 화면을 붙여 공개하고, 나쁘면 플래그로 꺼요. 사용자는 아무것도 몰라요.

옛 구현과 새 구현을 **나란히 돌려 결과를 비교**하고 사용자에게는 옛 결과만 돌려주는 방식으로도 써요.

| | 다크 런치 | 카나리 릴리스 |
|---|---|---|
| 사용자에게 보이나 | 안 보임 | 일부 사용자에게 실제로 보임 |
| 확인하는 것 | 부하·성능, 새 결과가 옛 결과와 맞는지 | 기능이 실제로 잘 쓰이는지, 에러율 |
| 잘 맞는 기능 | 기존 동작을 뒤에서 강화하는 기능(추천, 계산 로직) | 사용자가 눈으로 보고 써야 하는 기능(새 화면) |

다만 업계에서 "다크 런치"를 카나리나 부분 출시라는 뜻으로 느슨하게 쓰기도 해요. 면접에선 "사용자에게 안 보이게 돌려서 부하를 본다"는 원래 뜻으로 답하면 안전해요.

### 토글 부채: 스위치는 공짜가 아니다

플래그 하나는 if 하나지만, 쌓이면 문제가 돼요.

- 분기 조합이 늘어서 "지금 운영에서 어떤 코드가 도는지" 알기 어려워요.
- 출시가 끝났는데 안 지운 플래그 뒤에 **죽은 코드**(아무도 안 쓰는 코드)가 남아요.
- 오래된 플래그 이름을 다른 용도로 **재사용**하면, 잊힌 옛 코드가 깨어날 위험이 있어요. 관리 안 된 플래그가 큰 금전 사고로 이어진 사례도 널리 알려져 있어요.

Hodgson은 플래그를 창고 **재고**처럼 보라고 해요. 비용이 드니 적게 유지하라는 뜻이에요. 정리 규칙은 이래요.

- 릴리스 토글을 만들 때 **삭제 작업도 같이** 백로그(할 일 목록)에 넣어요.
- **만료일**을 정하고, 만료가 지나면 테스트가 실패하게 만드는 "**시한폭탄**"을 걸어요.
- 팀이 가질 수 있는 플래그 **총 개수에 상한**을 둬요.
- 출시 후 약 한 달 뒤를 **삭제 검토일**로 잡고 추적해요(trunkbaseddevelopment.com 권고).

### 심화: 플래그 판단 로직을 깔끔하게 두기

플래그를 쓰는 코드는 세 부분으로 나눠 생각해요.

- **토글 지점**(toggle point): 코드에서 실제로 분기하는 곳.
- **토글 라우터**(toggle router): 지금 어느 길이 켜졌는지 결정하는 부분. 메모리 속 표부터 분산 시스템까지 다양해요.
- **토글 컨텍스트**: 사용자 ID, 국가, 등급처럼 판단에 쓰는 요청 정보.

토글 지점마다 `flags.get("new-checkout")`를 직접 부르면, 판단 기준이 바뀔 때 모든 지점을 고쳐야 해요. 그래서 판단을 `FeatureDecisions` 같은 **전용 객체 하나에 모으고**, 이 객체를 **의존성 주입**(필요한 객체를 밖에서 넣어 주는 것)으로 받아요. 테스트할 때 가짜 결정을 넣기도 쉬워져요. 오래 사는 플래그나 분기가 많은 플래그는 if/else 대신 **전략 패턴**(같은 역할의 구현을 여러 개 두고 하나를 골라 끼우는 방식)으로 바꿔요.

### 심화: 테스트는 어떤 조합까지?

플래그가 n개면 조합은 2^n개지만 전부 테스트할 필요는 없어요. 대부분의 플래그는 서로 영향을 주지 않기 때문이에요. 보통 이렇게 해요.

- 운영에서 실제로 켜질 예정인 조합
- 새 플래그를 **전부 끈** 조합(문제가 생겨 다 껐을 때의 대비)
- 팀에 따라 전부 켠 조합

꺼져 있는 코드에도 단위 테스트는 유지해요. 언제 켜질지 모르니까요.

### 심화: 스프링에서 플래그 구현하기

스프링 부트의 `@ConditionalOnProperty`는 설정값에 따라 **빈**(스프링이 만들어 관리하는 객체)을 등록할지 말지 정해요.

```java
@Bean
@ConditionalOnProperty(name = "feature.new-checkout", havingValue = "true")
CheckoutService newCheckoutService() { return new NewCheckoutService(); }
```

이 조건은 애플리케이션이 **시작할 때**(빈을 등록하는 시점에) 평가돼요. 그래서 값을 바꾸려면 **재시작**해야 해요. 공식 문서에 "언제 평가된다"는 문장이 따로 있진 않고, 빈 등록 조건이라는 동작 원리에서 나오는 결론이에요. 즉 배포 단위로 고정되는 정적 토글이에요. 릴리스 토글로는 쓸 수 있지만, 장애 때 바로 끄는 킬 스위치로는 부족해요.

런타임에 바꾸려면 플래그 값을 DB·Redis·설정 서버·플래그 서비스 같은 외부 저장소에 두고, 짧게 캐시하면서 주기적으로 새 값을 받아 와야 해요. 코드에서는 `featureDecisions.isEnabled("new-checkout", userId)`처럼 판단 객체를 불러요.

### 심화: 플래그 서비스가 죽으면? 그리고 OpenFeature

플래그 값을 외부에서 받아 오면 "그 외부가 죽으면?"이 걱정돼요. 그래서 플래그를 물어볼 때는 항상 **기본값**을 같이 넘겨요. 실패하면 기본값을 쓰는 거예요. 기본값은 **안전한 쪽**, 보통 off(기존 동작)로 잡아요. 여기에 SDK의 로컬 캐시와 짧은 타임아웃을 더해요.

**OpenFeature**는 피처 플래그를 부르는 **벤더 중립 표준 API**예요(CNCF 인큐베이팅 프로젝트). 앱 코드는 OpenFeature API만 부르고, 실제 플래그 시스템(상용 서비스, 오픈소스, 로컬 파일)과는 **Provider**라는 번역 계층이 연결해요. 그래서 플래그 서비스를 바꿔도 앱 코드는 거의 안 고쳐요. 사양은 평가 메서드가 **플래그 키 + 기본값**을 받고, 예외를 던지지 말고 문제가 생기면 **기본값을 반환**하라고 정해요. 판단 대상(보통 사용자 ID)은 평가 컨텍스트의 **targeting key**로 넘겨요.

## 면접 질문

<details>
<summary>Q. 피처 플래그가 뭐고 왜 쓰나요?</summary>

**답변(30초)**
피처 플래그는 코드를 다시 배포하지 않고 기능을 켜고 끄는 스위치예요. 핵심은 코드 배포와 기능 출시를 분리하는 거예요. 미완성 기능도 꺼 둔 채 main에 합치고 배포할 수 있어서 트렁크 기반 개발이 가능해지고, 출시 때는 일부 사용자부터 조금씩 열어요. 문제가 생기면 롤백 대신 플래그를 꺼서 바로 기존 동작으로 돌아가요.

**꼬리질문**
- Q. 롤백과 플래그 off 중 뭐가 빠른가요? → 플래그 off예요. 재배포 없이 저장소 값만 바꾸면 서버들이 몇 초 안에 받아 가요. 단, 플래그 밖에서 생긴 문제는 롤백해야 해요.
- Q. 플래그 off는 어떤 동작이어야 하나요? → 기존 동작이어야 해요. 그래야 문제 때 끄면 안전한 쪽으로 돌아가요.
</details>

<details>
<summary>Q. 배포와 출시를 분리한다는 게 무슨 뜻인가요?</summary>

**답변(30초)**
배포는 코드를 운영 서버에 올리는 일이고, 출시는 사용자가 기능을 쓰게 되는 순간이에요. 플래그 없이는 둘이 동시에 일어나지만, 플래그를 쓰면 코드는 미리 off로 배포해 두고 출시 시점에 스위치만 켜요. 그래서 배포는 한가한 시간에 안전하게 하고, 출시는 마케팅 일정에 맞추거나 1%부터 점진적으로 할 수 있어요.

**꼬리질문**
- Q. 출시 시각에 맞춰 자동으로 켜려면? → (일반적인 운영 방법) 플래그 관리 도구에 예약 기능이 있으면 쓰거나 스케줄 작업으로 켜고, 직전에 내부 직원 대상으로 미리 켜서 확인해 둬요.
</details>

<details>
<summary>Q. 피처 플래그의 종류를 설명해 주세요.</summary>

**답변(30초)**
수명과 바뀌는 빈도로 네 가지로 나눠요. 릴리스 토글은 미완성 기능을 꺼 두는 용도로 1~2주 정도 짧게 살아요. 실험 토글은 A/B 테스트용으로 사용자마다 다른 경로를 보여 줘요. 운영 토글은 장애·부하 때 기능을 끄는 킬 스위치로, 재배포 없이 바로 바뀌어야 해요. 권한 토글은 유료 회원이나 베타 사용자에게만 기능을 주는 용도로 몇 년도 살아요.

**꼬리질문**
- Q. 이 중 반드시 지워야 하는 건? → 릴리스 토글이요. 출시가 끝나면 플래그와 옛 코드를 같이 지워요. 권한 토글은 사실상 비즈니스 규칙이라 오래 살아도 돼요.
</details>

<details>
<summary>Q. 다크 런치란 무엇이고 카나리 릴리스와 어떻게 다른가요?</summary>

**답변(30초)**
다크 런치는 새 백엔드 기능을 실제 트래픽으로 실행하되 결과를 사용자에게 보여 주지 않는 방법이에요. 공개 전에 부하와 성능을 실제 조건에서 재 보는 게 목적이에요. 카나리는 일부 사용자에게 기능을 실제로 보여 주고 반응과 에러율을 봐요. 그래서 추천·계산처럼 뒤에서 도는 기능은 다크 런치가, 새 화면처럼 사용자가 직접 써야 하는 기능은 카나리가 맞아요.

**꼬리질문**
- Q. 다크 런치 중 새 기능이 DB를 너무 쓰면? → 플래그로 바로 꺼요. 사용자에게 안 보이니 꺼도 체감 변화가 없어요.
- Q. 다크 런치로 정확도도 볼 수 있나요? → 옛 구현과 새 구현을 나란히 돌려 결과를 비교하고, 사용자에겐 옛 결과만 돌려주면 돼요.
</details>

<details>
<summary>Q. 점진 출시에서 1% 사용자는 어떻게 고르나요?</summary>

**답변(30초)**
사용자 ID를 기준으로 고정 배정해요. 요청마다 무작위로 뽑으면 같은 사람이 새로고침할 때마다 화면이 바뀌어요. 흔히 플래그 이름과 사용자 ID를 합쳐 해시한 뒤 100으로 나눈 나머지가 비율보다 작으면 켜는 식이에요. 이러면 비율을 1에서 10으로 올려도 처음 켜진 사용자는 계속 켜진 상태로 남아요.

**꼬리질문**
- Q. 왜 플래그 이름을 섞나요? → 안 섞으면 모든 플래그에서 같은 사용자들이 늘 먼저 실험 대상이 돼요.
- Q. PC와 모바일에서 화면이 다르게 보인다면? → 기기 ID로 배정했을 가능성이 커요. 로그인 사용자 ID로 배정해야 해요.
</details>

<details>
<summary>Q. 스프링에서 @ConditionalOnProperty로 피처 플래그를 만들면 충분한가요?</summary>

**답변(30초)**
릴리스 토글로는 쓸 수 있지만 킬 스위치로는 부족해요. 이 조건은 애플리케이션이 시작할 때 빈 등록 여부를 정하는 거라, 값을 바꾸려면 재시작해야 해요. 장애 때 몇 초 안에 끄려면 플래그 값을 DB나 설정 서버, 플래그 서비스 같은 외부 저장소에 두고, 짧은 캐시로 요청 시점에 읽어서 판단해야 해요.

**꼬리질문**
- Q. 매 요청 저장소를 읽으면 느리지 않나요? → 서버 메모리에 캐시하고 주기적으로 또는 변경 알림으로 갱신해요.
</details>

<details>
<summary>Q. 피처 플래그의 단점은 뭐고 어떻게 관리하나요?</summary>

**답변(30초)**
플래그가 쌓이면 분기 조합이 늘고, 안 지운 플래그 뒤에 죽은 코드가 남고, 옛 플래그를 재사용하다 잊힌 코드가 깨어날 위험도 있어요. 이걸 토글 부채라고 해요. 그래서 만들 때 삭제 작업도 같이 등록하고, 소유자와 만료일을 정하고, 만료되면 테스트가 실패하게 하고, 플래그 개수에 상한을 둬요.

**꼬리질문**
- Q. 플래그 조합을 다 테스트해야 하나요? → 아니요. 운영에서 켜질 조합과 새 플래그를 전부 끈 조합을 테스트하면 대개 충분해요.
</details>

<details>
<summary>Q. 플래그 서비스가 장애 나면 어떻게 되나요?</summary>

**답변(30초)**
평가할 때 항상 기본값을 같이 넘기고, 실패하면 기본값을 쓰게 해요. OpenFeature 사양도 평가가 예외를 던지지 말고 기본값을 반환하라고 정해요. 그래서 기본값을 안전한 쪽, 보통 기존 동작으로 잡는 게 중요해요. 여기에 SDK 로컬 캐시와 짧은 타임아웃을 더해 플래그 서비스가 느려도 본 서비스가 같이 느려지지 않게 해요.

**꼬리질문**
- Q. OpenFeature는 왜 쓰나요? → 벤더 중립 표준 API라서, 앱은 OpenFeature만 부르고 실제 플래그 서비스는 Provider로 갈아 끼워요. 서비스를 바꿔도 앱 코드는 거의 안 바뀌어요.
</details>

## 서술형 연습

<details>
<summary>상황: 마케팅팀이 금요일 오전 10시에 신규 이벤트 기능을 오픈한다고 해요. 그 시각에 맞춰 배포하는 대신, 미리 배포해 두려면 어떻게 하겠어요?</summary>

**상황 파악**
오픈 시각이 정해져 있어요. 그 시각에 배포하면 빌드·배포 실패나 예상 못 한 오류가 곧 오픈 실패가 되고, 트래픽이 몰리는 시점에 배포까지 겹쳐요. 배포와 출시를 떼어 놔야 해요.

**원인 후보(그 시각 배포가 위험한 이유)**
1. 배포 자체가 실패하거나 늦어질 수 있어요.
2. 오픈 직후 문제가 생기면 롤백(옛 버전 재배포)에 시간이 걸려요.
3. 오픈 전에 운영 환경에서 실제로 확인해 볼 기회가 없어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 금요일 10시에 맞춰 배포 | 플래그 코드가 필요 없음 | 배포 실패 = 오픈 실패, 문제 때 롤백이 느림 |
| B. 릴리스 토글로 미리 off 배포, 10시에 on | 배포는 화·수요일에 여유 있게, 오픈은 스위치만. 문제 때 즉시 off | 플래그 분기 코드와 런타임 플래그 저장소가 필요, 출시 후 삭제 작업 |
| C. B + 내부 직원 먼저 on, 오픈 때 1%→100% | 오픈 전에 운영에서 직접 확인, 오픈 직후 문제를 소수에서 발견 | 마케팅이 "모두에게 동시 공개"를 원하면 단계 시간을 아주 짧게 잡아야 함 |

**내가 고를 방법**
B를 기본으로 하고 C의 "내부 직원 먼저"를 더해요. 화요일쯤 플래그 off로 배포하고, 수·목요일엔 권한 규칙으로 내부 직원에게만 켜서 운영 데이터로 점검해요. 플래그 값은 재시작 없이 바뀌는 저장소에 두고, 기본값은 off로 잡아요. 금요일 10시에 전체 on을 하고 에러율·응답 시간을 지켜보다가 이상하면 바로 off해요. 이벤트가 끝나고 안정되면 플래그와 분기 코드를 지우는 작업을 처음부터 일정에 넣어 둬요.

**채점 포인트**: 배포와 출시 분리, 릴리스 토글, 기본값 off(off = 기존 동작), 재시작 없이 바뀌는 런타임 저장소, 내부 직원 먼저(샴페인 브런치), 오픈 후 모니터링, 롤백 대신 즉시 off, 출시 후 플래그 삭제 계획.
</details>

<details>
<summary>상황: 새 추천 알고리즘을 만들었는데 DB 쿼리가 많아 보여요. 사용자에게 공개하기 전에 실제 트래픽에서 DB에 얼마나 부하를 주는지 미리 보고 싶어요.</summary>

**상황 파악**
궁금한 건 "사용자가 좋아하나"가 아니라 "실제 트래픽에서 **부하**를 견디나"예요. 테스트 환경 부하 테스트는 실제 요청 패턴과 데이터 분포를 완전히 따라 하기 어려워요. 사용자에게는 영향이 없어야 해요.

**원인 후보(그냥 공개하면 위험한 이유)**
1. 쿼리가 많아 DB 연결이 부족해지면 추천뿐 아니라 같은 DB를 쓰는 다른 기능까지 느려져요.
2. 공개 후 문제를 발견하면 이미 사용자가 느린 화면을 겪은 뒤예요.
3. 테스트 환경 수치만으로는 운영 부하를 예측하기 어려워요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 테스트 환경에서 부하 테스트 | 운영에 영향 없음 | 실제 트래픽 패턴과 데이터를 다 재현하기 어려움 |
| B. 다크 런치: 실제 요청마다 새 알고리즘도 호출하고 결과는 버림, 부하만 측정 | 실제 조건에서 부하를 잼, 사용자에겐 안 보임, 문제면 플래그로 즉시 off | 운영 DB에 진짜 부하가 걸림, 그동안 비용(연산·DB)이 두 배 가까이 듦 |
| C. 카나리: 1% 사용자에게 새 추천을 실제로 보여 줌 | 부하와 사용자 반응을 함께 봄 | 문제 있으면 그 1%가 실제로 피해를 봄 |

**내가 고를 방법**
B를 골라요. 이 질문은 부하를 보는 거라 다크 런치가 딱 맞아요. 운영 토글로 새 알고리즘 호출을 감싸고, 처음엔 요청의 1%만 그림자 호출하다 DB 지표(쿼리 수, 응답 시간, 연결 사용률)를 보며 비율을 올려요. 새 호출은 사용자 응답을 기다리게 하지 않도록 짧은 타임아웃을 두고, 실패해도 무시해요. 지표가 기준선을 넘으면 바로 끄도록 킬 스위치 기준도 미리 정해요. 부하가 괜찮다고 확인되면, 그다음 C로 넘어가 1% 사용자에게 실제로 보여 주며 반응을 봐요.

**채점 포인트**: 다크 런치 정의(실행하되 안 보여 줌), 카나리와 구분, 플래그로 즉시 off, 그림자 호출 비율을 점진적으로 올림, DB 지표 모니터링, 사용자 응답을 막지 않게 타임아웃, 다크 런치 → 카나리 순서.
</details>

<details>
<summary>상황: 몇 년 사이 피처 플래그가 200개 넘게 쌓였어요. 어떤 플래그가 아직 쓰이는지 아무도 모르고, 코드가 if 분기투성이라 장애 원인 추적도 어려워요. 어떻게 정리하겠어요?</summary>

**상황 파악**
토글 부채가 쌓인 상태예요. 분기 조합이 늘어 운영에서 어떤 코드가 도는지 알기 어렵고, 죽은 코드와 주인 없는 플래그가 섞여 있어요. 한꺼번에 다 지우면 위험하니, 지금 있는 것을 정리하는 일과 다시 쌓이지 않게 막는 일을 나눠야 해요.

**원인 후보**
1. 만들 때 **삭제 계획**이 없었어요. 출시가 끝난 릴리스 토글이 그대로 남아요.
2. **소유자·용도 기록**이 없어서 지워도 되는지 아무도 판단 못 해요.
3. 릴리스 토글과 오래 살아도 되는 권한·킬 스위치가 **구분 없이** 섞여 있어요.
4. 판단 로직이 토글 지점마다 흩어져 있어서 지우기도 어려워요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 일괄 정리: 전수 조사 후 한 번에 삭제 | 빠르게 줄어듦 | 아직 쓰이는 걸 지울 위험, 다시 쌓이는 건 못 막음 |
| B. 규칙 도입: 만들 때 소유자·종류·만료일 필수, 삭제 작업 동시 등록, 만료 후 테스트 실패(시한폭탄), 개수 상한 | 다시 쌓이지 않음 | 개발 절차가 조금 무거워짐, 기존 200개는 그대로 |
| C. 판단을 `FeatureDecisions` 같은 객체로 모으고 오래 사는 플래그는 전략 패턴으로 | 분기가 줄고 읽기 쉬워짐 | 리팩터링 비용, 플래그 수 자체는 안 줄어듦 |

**내가 고를 방법**
B를 먼저 세우고 A를 단계적으로 해요. 먼저 200개를 종류별로 분류해요. 100% on이나 off로 오래 고정된 릴리스 토글은 삭제 후보, 권한 토글과 킬 스위치는 유지 대상으로 나누고, 각각 소유자를 정해요. 삭제 후보는 한 번에 몇 개씩, 플래그와 쓰이지 않는 쪽 코드를 같이 지우고 배포해요. 동시에 새 플래그엔 소유자·만료일을 필수로 받고, 만료가 지나면 테스트가 실패하게 하고, 팀별 개수 상한을 둬요. 옛 플래그 이름은 절대 재사용하지 않아요. 남는 오래 사는 플래그는 C로 판단 로직을 한 곳에 모아요.

**채점 포인트**: 토글 부채 인식, 종류별 분류(릴리스 vs 권한·킬 스위치), 소유자·만료일, 만들 때 삭제 작업 등록, 시한폭탄 테스트, 개수 상한, 플래그 이름 재사용 금지, 죽은 코드 같이 삭제, 판단 로직 한 곳에 모으기.
</details>

## 필기 포인트

- 피처 플래그 핵심 = **배포(deploy)와 출시(release) 분리**, 트렁크 기반 개발을 가능하게 함.
- 4종류: **릴리스**(짧음·정적), **실험**(A/B·요청마다), **운영**(킬 스위치·즉시 변경), **권한**(몇 년·요청마다).
- 관례: off = 기존 동작, on = 새 동작.
- 점진 출시는 **사용자 ID 기준 고정 배정**. 요청마다 무작위(X).
- 다크 런치 = 실행하되 **사용자에게 안 보임**(부하 측정). 카나리 = 일부에게 **실제로 보여 줌**.
- `@ConditionalOnProperty` = 시작 시 평가 → **재시작 필요**한 정적 토글. 킬 스위치로는 부족.
- OpenFeature = 벤더 중립 표준 API(CNCF), Provider로 연결, 평가 실패 시 **기본값 반환**.
- 함정: "플래그 조합을 전부 테스트해야 한다"(X), "다크 런치 = 카나리"(X).
