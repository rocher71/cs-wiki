:::tip[한 줄 요약]
**모놀리스**는 앱 전체를 **한 덩어리로 빌드·배포**하고, **마이크로서비스**(MSA)는 업무 기능별로 나눈 **작은 서비스를 각자 따로 배포**해요. MSA는 독립 배포·독립 확장·팀 자율성을 얻는 대신 네트워크·장애·데이터 일관성 같은 분산 비용을 내야 해서, 시스템과 조직이 충분히 크지 않으면 **잘 나눈 모놀리스로 시작**하는 게 맞아요.
:::

:::note[처음이라면 여기까지]
① 모놀리스는 "앱 전체를 한 번에 배포", MSA는 "기능별 작은 서비스를 각자 배포"예요. 차이의 핵심은 **배포 단위**예요.

② MSA는 따로 배포·따로 확장할 수 있는 대신, 서비스끼리 네트워크로 통신해야 해서 느려지거나 끊길 수 있고 운영할 게 많아져요.

③ 그래서 작은 팀·초기 제품은 내부를 잘 나눈 모놀리스로 시작하는 게 보통이에요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
마이크로서비스는 표준 문서가 따로 없는 설계 방식이라, 이 분야에서 널리 인용되는 업계 참고 글(Lewis & Fowler의 "Microservices", Fowler의 bliki, microservices.io)과 Spring Modulith 공식 문서를 바탕으로 했어요(2026-11 조회).

## 쉽게 이해하기

음식 장사를 **큰 식당 하나**로 할지, **푸드코트**로 할지 고르는 상황이라고 해 봐요.

**모놀리스는 큰 식당 하나**예요. 주방 하나에서 한식·중식·디저트를 다 만들어요. 재료 창고도 하나라 "짜장면 재료 좀 빌려 줘"가 바로 돼요. 대신 메뉴 하나를 바꾸려 해도 식당 전체가 잠깐 문을 닫고 다시 열어야 해요. 점심에 짜장면만 불티나게 팔려도 식당을 통째로 하나 더 차려야 해요.

**MSA는 푸드코트**예요. 가게마다 주방·창고·직원이 따로 있어요. 떡볶이 가게가 메뉴를 바꿔도 옆 가게는 그대로 장사해요. 짜장면 가게만 바쁘면 그 가게만 직원을 늘리면 돼요. 대신 "세트 메뉴" 하나를 팔려면 가게끼리 주문을 주고받아야 하고, 한 가게가 늦으면 세트 전체가 늦어요. 관리실(배포·모니터링 시스템)도 꼭 있어야 해요.

단, 실제로는 "모놀리스 = 엉망인 코드"가 아니에요. 큰 식당도 주방 안을 코너별로 잘 나눠 두면 깔끔하게 돌아가요. 이게 뒤에 나올 **모듈러 모놀리스**예요.

## 제대로 알기

### 모놀리스: 한 덩어리로 배포하는 구조

**모놀리스**(monolith, "통바위"라는 뜻)는 서버 쪽 앱 전체, 즉 요청을 받는 부분, 업무 로직, DB 접근이 **하나의 실행 단위**로 묶인 구조예요. Spring Boot라면 보통 JAR 파일 하나를 빌드해서 서버에 올리는 형태예요.

모든 기능이 같은 프로세스 안에 있어서 다른 기능을 부를 때 **메서드 호출**(같은 메모리 안에서 함수를 부르는 것)이면 끝나요. 그래서 빠르고, 흐름을 따라가며 디버깅하기 쉬워요. DB도 하나라 주문 저장과 재고 차감을 **ACID 트랜잭션**(여러 작업을 "전부 성공 아니면 전부 취소"로 묶는 기능) 하나로 묶을 수 있어요.

문제는 커졌을 때예요. 작은 수정 하나에도 전체를 다시 빌드·테스트·배포해야 하고, 여러 팀이 한 코드베이스에서 서로 일정을 맞춰야 해요.

### 마이크로서비스: 작은 서비스를 따로 배포하는 구조

**마이크로서비스 아키텍처**(Microservice Architecture, MSA)는 앱을 **작고 독립적으로 배포할 수 있는 서비스 여러 개**로 만드는 방식이에요. 서비스마다 자기 프로세스에서 돌고, **HTTP API**(네트워크로 주고받는 요청·응답 규칙)나 가벼운 메시지로 서로 통신해요. 나누는 기준은 기술 계층이 아니라 **업무 기능**(주문, 회원, 결제)이에요. 서비스마다 언어나 DB가 달라도 돼요.

같은 "주문하면 결제한다"도 모놀리스에선 메서드 호출 한 번이지만, MSA에선 **네트워크 호출**이에요. 네트워크는 느릴 수도, 끊길 수도 있어요. MSA의 어려움은 대부분 여기서 나와요. → [서비스 간 통신](../service-communication/)

### 장단점 비교

| | 모놀리스 | 마이크로서비스 |
|---|---|---|
| 배포 단위 | 앱 전체 하나 | 서비스마다 따로 |
| 기능 간 호출 | 메서드 호출(빠름, 안 끊김) | 네트워크 호출(느릴 수 있음, 실패 가능) |
| 트랜잭션 | DB 하나라 ACID로 묶기 쉬움 | 서비스별 DB라 한 트랜잭션 불가, 최종 일관성·Saga 필요 |
| 확장 | 전체를 통째로 복제 | 바쁜 서비스만 늘림 |
| 디버깅 | 한 프로세스 안이라 쉬움 | 요청이 여러 서비스를 지나가 어려움 |
| 팀 자율성 | 한 코드베이스, 배포 일정 조율 필요 | 팀별로 독립 개발·배포 |
| 기술 스택 | 하나로 고정, 업그레이드도 전체가 함께 | 서비스별로 고를 수 있음 |
| 운영 부담 | 작음 | 큼(자동 배포·모니터링·장애 대비 필수) |
| 잘 맞는 상황 | 초기 제품, 작은 팀 | 큰 시스템, 여러 팀 |

표에 나온 용어를 풀어 볼게요.

- **최종 일관성**(eventual consistency): 지금 당장은 서비스마다 데이터가 잠깐 어긋날 수 있지만, 시간이 조금 지나면 결국 맞춰지는 것.
- **보상 작업**(compensating action): 여러 서비스에 걸친 작업 중 뒤에서 실패하면, 앞에서 이미 끝난 작업을 되돌리는 작업을 따로 실행하는 것. 예: 결제 실패 시 "재고 차감 취소"를 보냄. 이런 흐름을 **Saga** 패턴이라고 해요.

몇 가지 오해를 짚어 둘게요.

- "**모놀리스는 수평 확장이 안 된다**"는 틀려요. **수평 확장**(scale-out)은 서버 대수를 늘려 처리량을 키우는 거예요. 같은 앱을 서버 여러 대(**인스턴스** 여러 개)에 띄우고 **로드밸런서**(요청을 여러 서버에 나눠 주는 장치)를 앞에 두면 돼요. 다만 필요한 부분만이 아니라 전체를 통째로 늘려야 할 뿐이에요.
- "**MSA면 성능이 좋아진다**"도 틀려요. 메서드 호출이 네트워크 호출로 바뀌니 오히려 느려질 수 있어요. MSA의 이점은 속도가 아니라 **독립 배포, 독립 확장, 팀 자율성**이에요.
- "**MSA가 최신이니 더 좋다**"도 아니에요. Fowler는 대부분의 시스템에는 잘 모듈화된 모놀리스가 맞다고 봐요.

### 모듈러 모놀리스: 배포는 하나, 안은 칸막이

**모듈러 모놀리스**(modular monolith)는 배포 단위는 하나지만 내부를 경계가 분명한 **모듈**(서로 정해진 입구로만 소통하는 코드 덩어리)로 나눈 모놀리스예요. 메서드 호출의 단순함은 지키면서, 나중에 필요하면 모듈 하나를 서비스로 떼어 낼 수 있게 준비해 두는 방식이에요.

Spring에서는 **Spring Modulith**가 이걸 도와줘요.

- `@SpringBootApplication`이 있는 패키지 바로 아래 패키지 하나하나를 모듈로 봐요(`order`, `payment` 등).
- 모듈 안의 `internal` 같은 하위 패키지는 다른 모듈이 쓰면 안 되는 내부 구현으로 취급해요.
- 그런데 자바 컴파일러는 public 클래스 사용을 막지 못해요. 그래서 테스트에서 규칙 위반을 검사해요.

```java
class ModularityTests {
  @Test
  void verifiesModularStructure() {
    // 다른 모듈의 internal 패키지를 쓰는 등 규칙 위반이 있으면 테스트 실패
    ApplicationModules.of(Application.class).verify();
  }
}
```

모듈끼리 직접 부르는 대신 **애플리케이션 이벤트**(일이 일어났다고 알리기만 하고, 관심 있는 쪽이 받아 처리하는 방식)로 소통하면 결합이 더 느슨해져요. 나중에 서비스로 뗄 때 이벤트를 메시지로 바꾸기도 쉬워요.

### 언제 MSA로 가야 할까?

Fowler는 MSA가 요구하는 추가 비용을 **Microservice Premium**(마이크로서비스 "할증료")이라고 불렀어요. 자동 배포, 모니터링, 장애 처리, 최종 일관성 같은 것들이에요. 결론은 "모놀리스로 감당이 안 될 만큼 복잡하지 않으면 MSA를 고려하지 말라"예요.

또 **MonolithFirst**(모놀리스 먼저) 글에서 두 가지를 관찰했어요. 성공한 MSA는 거의 다 커진 모놀리스를 쪼개서 시작했고, 처음부터 MSA로 만든 경우는 거의 다 큰 어려움을 겪었다는 거예요. 이유는 이래요.

- 초기에는 제품이 쓸모 있을지도 모르니 **빠른 피드백**이 중요한데, 할증료가 속도를 늦춰요.
- **서비스 경계는 처음부터 잘 긋기 어려워요.** 모놀리스 안에서 경계를 옮기는 건 리팩터링이지만, 서비스 사이 경계를 옮기는 건 훨씬 어려워요. → [서비스 경계 나누기](../service-boundary/)

도입 전 갖춰야 할 것(**Microservice Prerequisites**)으로는 네 가지를 들었어요. 서버를 몇 시간 안에 새로 띄울 수 있는 **빠른 프로비저닝**, 기술 오류와 "주문 급감" 같은 업무 이상까지 잡는 **기본 모니터링**, **빠른 배포 파이프라인**, 개발과 운영이 함께 일하는 **데브옵스 문화**예요. → [CI/CD와 GitOps](../ci-cd-gitops/)

| 이런 상황이면 | 판단 |
|---|---|
| 팀이 하나뿐이고, 제품이 아직 검증 전 | 모놀리스(가능하면 모듈러 모놀리스) |
| 업무 경계가 아직 자주 바뀜 | 모놀리스. 경계가 안정될 때까지 기다림 |
| 자동 배포·모니터링·빠른 서버 준비가 없음 | MSA 보류. 전제조건부터 갖춤 |
| 여러 팀이 한 코드베이스에서 배포 일정 때문에 자주 막힘 | MSA 검토할 만함(팀 경계 = 서비스 경계) |
| 특정 기능만 부하가 유난히 큼 | 그 기능만 떼어 내는 것부터 검토. 전체 전환과 비용 비교 |
| 기능마다 요구하는 가용성·보안 수준이 크게 다름 | 그 부분 분리 검토 |
| 팀에 MSA 운영 경험이 없음 | 처음부터 MSA는 피함 |

떼어 낼 때는 한 번에 다 바꾸지 않아요. 모놀리스 → 모듈러 모놀리스로 경계를 정리 → **가장자리 기능부터** 하나씩 서비스로 떼어 내는 순서가 흔해요. 또는 큰 서비스 두어 개로 시작해서 경계가 안정되면 잘게 나누기도 해요.

### 심화: MSA의 9가지 특징 (Lewis & Fowler, 2014)

MSA라는 말을 널리 퍼뜨린 James Lewis와 Martin Fowler의 글은 MSA에 공통으로 보이는 특징 9가지를 꼽았어요. 면접에서 "MSA가 뭐냐"는 질문에 뼈대로 쓰기 좋아요.

| 특징 | 쉽게 말하면 |
|---|---|
| 서비스 단위로 나누기 | 같은 메모리 안 라이브러리가 아니라 별도 프로세스 서비스로 나눠서, 하나씩 따로 교체·배포 |
| 업무 기능 중심 팀 | UI팀·DB팀 대신 주문팀·결제팀처럼 기능 하나를 처음부터 끝까지 맡는 팀 |
| 프로젝트가 아니라 제품 | 만든 팀이 운영까지 책임("만든 사람이 돌린다") |
| 똑똑한 끝점, 단순한 파이프 | 로직은 서비스 안에 두고, 통신은 HTTP·가벼운 메시징으로 단순하게 |
| 분산 거버넌스 | 팀마다 언어·도구를 고를 수 있음 |
| 분산 데이터 관리 | 서비스마다 자기 DB. 분산 트랜잭션 대신 최종 일관성 + 보상 작업 |
| 인프라 자동화 | 자동 테스트·자동 배포 없이는 서비스 수십 개를 못 돌림 |
| 장애 대비 설계 | 다른 서비스 호출은 언제든 실패한다고 보고 대비(모니터링, 서킷 브레이커) |
| 진화적 설계 | 함께 바뀌는 것끼리 묶어서 나눔. 경계는 점점 다듬어 감 |

여기 나온 용어 하나를 더 풀어 볼게요.

- **서킷 브레이커**(circuit breaker): 계속 실패하는 서비스로 가는 호출을 잠시 끊어서, 실패가 번지지 않게 하는 장치. 집의 누전 차단기와 비슷해요. → [장애 격리와 회복력](../resilience/)

### 심화: 콘웨이 법칙 — 팀 구조가 시스템 구조가 된다

1968년 Melvin Conway가 쓴 글에서 나온 명제예요. 요지는 "**시스템을 설계하는 조직은 자기 조직의 의사소통 구조를 닮은 설계를 만든다**"예요. 나중에 Fred Brooks가 책 『맨먼스 미신』(The Mythical Man-Month)에서 이를 인용하며 **콘웨이 법칙**(Conway's Law)이라는 이름을 붙였어요.

예를 들어 UI팀·서버팀·DB팀으로 나뉜 회사는 시스템도 UI층·서버층·DB층으로 갈라져요. 그러면 "결제 화면에 할인 표시"라는 기능 하나에도 세 팀이 회의해야 해요. Lewis & Fowler가 기술 계층별 팀 대신 **업무 기능별 팀**을 권한 근거가 이거예요.

그래서 MSA는 기술 결정이기 전에 **조직 결정**이에요. 팀이 하나뿐이면 서비스를 여러 개로 나눠도 "팀별 독립 배포"라는 이점이 거의 없어요.

### 심화: 분산 모놀리스 — 나눴는데 따로 못 움직이는 상태

**분산 모놀리스**(distributed monolith)는 서비스는 여러 개로 나눠 따로 띄웠지만, 서로 너무 단단히 묶여 있어서 **같이 바꾸고 같이 배포해야 하는** 상태를 부르는 말이에요(공식 정의가 있는 용어는 아니고 업계에서 흔히 쓰는 말이에요). 네트워크·장애 전파·디버깅 같은 분산 비용은 다 내면서 독립 배포 이점은 못 누리니, 두 구조의 단점만 모은 셈이에요.

원인은 크게 두 가지예요.

- **설계 결합**: 서비스들이 같은 DB 테이블이나 같은 데이터 클래스 라이브러리를 공유해서, 하나를 바꾸면 다른 서비스도 동시에 고쳐야 해요.
- **런타임 결합**: 주문 → 결제 → 포인트처럼 응답을 기다리는 **동기 호출**이 사슬로 이어져서, 맨 끝 하나가 느려지면 앞의 서비스들도 줄줄이 묶여요.

흔한 징후는 "배포할 때마다 여러 팀이 일정을 맞춘다", "여러 서비스가 DB 하나를 같이 쓴다", "요청 하나가 서비스 여러 개를 동기로 차례차례 거친다"예요.

**꼬리질문**
- Q. 그럼 MSA는 기술 결정인가요, 조직 결정인가요? → 조직 결정이 먼저예요. 팀 구조가 받쳐 주지 않으면 서비스를 나눠도 결국 같이 움직이게 돼요.

<details>
<summary>Q. 분산 모놀리스가 뭔가요? 어떻게 피하나요?</summary>

**답변(30초)**

**꼬리질문**
- Q. 분산 모놀리스인지 어떻게 알아보나요? → 배포 때마다 여러 팀이 일정을 맞추거나, 여러 서비스가 같은 DB 테이블을 쓰거나, 한 서비스 장애에 여러 서비스가 같이 멈추면 의심해요.
</details>

## 서술형 연습

<details>
<summary>상황: 백엔드 개발자 3명인 스타트업에서 "나중에 확장하려면 지금부터 MSA로 가야 한다"는 의견이 나왔어요. 제품은 아직 출시 전입니다. 어떻게 판단하겠어요?</summary>

**상황 파악**
팀은 3명이라 사실상 한 팀이고, 제품은 시장에서 검증되기 전이에요. "확장성"이 걱정이라지만 아직 트래픽도, 어떤 기능이 바빠질지도 몰라요. 지금 필요한 건 빠르게 만들고 고치는 속도예요.

**원인 후보(왜 MSA 의견이 나왔나 / 지금 MSA의 위험)**
1. "나중에 쪼개기 힘들 테니 처음부터"라는 걱정. 그런데 경계를 처음부터 잘 긋기 어렵고, 잘못 그은 서비스 경계는 옮기기가 훨씬 어려워요.
2. MSA의 할증료: 서비스마다 배포 파이프라인, 모니터링, 장애 대비, 서비스 간 데이터 일관성 처리가 필요해요. 3명이 이걸 다 하면 기능 개발이 멈춰요.
3. 콘웨이 법칙: 팀이 하나면 서비스를 나눠도 "팀별 독립 배포" 이점이 거의 없어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 처음부터 MSA | 나중에 분리 작업이 없음. 서비스별 확장 가능 | 운영 부담이 개발 속도를 잡아먹음. 경계를 잘못 그으면 분산 모놀리스가 됨 |
| B. 그냥 모놀리스 | 가장 빠르게 개발·배포 | 경계 없이 커지면 나중에 떼어 내기 어려움 |
| C. 모듈러 모놀리스 | 배포·트랜잭션은 단순하게, 내부는 모듈로 경계를 지켜 나중에 분리 준비 | 모듈 규칙을 지키는 수고가 들고, 서비스별 독립 확장은 아직 안 됨 |

**내가 고를 방법**
C를 골라요. 주문·결제·회원 같은 업무 기준으로 모듈을 나누고, Spring Modulith의 `verify()` 테스트로 경계를 지키고, 모듈끼리는 이벤트로 느슨하게 연결해요. 그동안 자동 배포와 모니터링 같은 MSA 전제조건을 하나씩 갖춰요. 나중에 특정 모듈 부하가 유난히 커지거나 팀이 늘어 배포가 서로 막히기 시작하면, 그 모듈부터 서비스로 떼어 내요. "확장성"은 인스턴스를 여러 대 띄우는 수평 확장으로 당분간 충분하다는 점도 같이 설명해요.

**채점 포인트**: 팀 규모·제품 단계로 상황 판단, Microservice Premium(운영 비용), MonolithFirst(성공 사례는 모놀리스에서 출발, 경계는 처음에 긋기 어려움), 콘웨이 법칙(팀 하나면 이점 작음), 모듈러 모놀리스, 전제조건(자동 배포·모니터링·데브옵스), 모놀리스도 수평 확장 가능, 분리 시점의 기준.
</details>

<details>
<summary>상황: 서비스를 주문·결제·포인트 3개로 나눴는데, 결제 쪽 기능을 하나 바꿀 때마다 세 서비스를 같은 날 함께 배포해야 해요. 왜 이런 일이 생기고 어떻게 풀겠어요?</summary>

**상황 파악**
서비스를 나눈 목적은 독립 배포인데, 실제로는 셋이 한 몸처럼 움직여요. 분산 비용은 내고 독립 배포 이점은 못 누리는 **분산 모놀리스** 상태예요.

**원인 후보**
1. **DB 공유**: 세 서비스가 같은 DB 테이블을 직접 읽고 써서, 결제 테이블 구조를 바꾸면 다른 서비스 코드도 같이 바뀌어야 해요.
2. **공유 데이터 클래스 라이브러리**: 요청·응답 클래스를 공통 라이브러리로 묶어 셋이 같이 쓰면, 필드 하나 바꿀 때 모두 새 버전으로 동시에 올려야 해요.
3. **API 호환성 미유지**: 결제 API 응답 형식을 바꾸면서 옛 형식을 지원하지 않아, 호출하는 쪽도 같은 날 바뀌어야 해요.
4. **경계를 잘못 그음**: 늘 함께 바뀌는 기능이 서로 다른 서비스로 갈라져 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. API 하위 호환 유지(필드는 추가만, 옛 형식 한동안 같이 지원) | 바로 적용 가능. 결제만 먼저 배포하고 나머지는 나중에 따라옴 | 옛 형식을 유지·정리하는 수고 |
| B. DB를 서비스별로 분리, 남의 데이터는 API·이벤트로만 접근 | 설계 결합을 근본에서 끊음 | 데이터 이전 작업이 크고, 서비스 간 데이터는 최종 일관성이 됨 |
| C. 경계 재설계(늘 같이 바뀌는 서비스는 합침) | 변경이 한 서비스 안에서 끝남 | 이미 나눈 걸 되돌리는 비용, "서비스 수"가 줄어 보임 |

**내가 고를 방법**
먼저 최근 변경 이력을 보고 "무엇 때문에 같이 배포했나"를 분류해요. 응답 형식 변경 때문이면 A로 하위 호환 규칙부터 세워요. 가장 빨리 효과가 나요. DB 공유가 원인이면 B로 테이블 소유 서비스를 하나로 정하고 나머지는 API로 접근하게 바꿔요. 분석해 보니 두 서비스가 거의 매번 함께 바뀐다면, 억지로 분리를 유지하기보다 C로 합치는 게 맞아요. 함께 바뀌는 것끼리 묶는 게 원래 MSA의 설계 원칙이에요. 적용 후엔 "단독 배포 비율"을 지표로 보며 개선됐는지 확인해요.

**채점 포인트**: 분산 모놀리스 진단, 설계 결합(공유 DB·공유 라이브러리·함께 바뀌는 변경), API 하위 호환, 서비스별 DB(Database per Service)와 최종 일관성, 경계 재설계(함께 바뀌는 것끼리 묶기), 서비스를 합치는 것도 선택지, 개선 지표.
</details>

<details>
<summary>상황: MSA로 운영 중인데, 포인트 서비스 하나가 느려지자 주문 API 전체가 타임아웃 나기 시작했어요. 장애가 왜 번졌고 어떻게 막겠어요?</summary>

**상황 파악**
주문 → 결제 → 포인트처럼 서비스가 **동기 호출**(응답이 올 때까지 기다리는 호출)로 이어져 있다고 봐요. 맨 끝 포인트가 느려지자 앞 서비스들이 응답을 기다리며 묶였어요. 이게 **런타임 결합**이고, 분산 모놀리스의 한 모습이에요.

**원인 후보**
1. **타임아웃이 없거나 너무 길어서**, 결제 서비스의 요청 처리 스레드가 포인트 응답을 하염없이 기다려요. 스레드가 다 묶이면 결제 서비스 전체가 새 요청을 못 받고, 주문도 같은 이유로 막혀요. → [프로세스와 스레드](../../java/thread-basics/)
2. **계속 실패하는 곳에 계속 호출**해서 상황을 더 나쁘게 만들어요.
3. **꼭 즉시 필요하지 않은 작업까지 동기로** 부르고 있어요. 포인트 적립은 주문 응답 전에 끝나지 않아도 되는 일이에요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 호출마다 짧은 타임아웃 + 서킷 브레이커 | 느린 서비스에 스레드가 묶이지 않고, 계속 실패하면 바로 대체 응답 | 포인트 적립이 실패한 주문을 따로 처리(재시도·보정)해야 함 |
| B. 포인트 적립을 이벤트로 비동기 처리(결제 완료 이벤트를 발행하고 포인트가 받아 처리) | 포인트가 죽어도 주문·결제는 정상. 런타임 결합 자체를 끊음 | 포인트가 조금 늦게 쌓임(최종 일관성). 메시지 브로커 운영과 중복 처리 대비 필요 |

**내가 고를 방법**
당장은 A로 결제 → 포인트 호출에 짧은 타임아웃과 서킷 브레이커를 걸어 장애가 주문까지 번지지 않게 막아요. 이어서 포인트 적립은 주문 응답에 꼭 필요하지 않으니 B로 이벤트 기반으로 바꿔요. 사용자는 몇 초 늦게 포인트를 받아도 큰 문제가 없고, 대신 주문은 포인트 장애와 상관없이 성공해요. 적용 후엔 서비스별 응답 시간과 서킷 브레이커 열림 횟수를 모니터링해요. 자세한 패턴은 [장애 격리와 회복력](../resilience/)에서 다뤄요.

**채점 포인트**: 동기 호출 사슬(런타임 결합)로 장애 전파, 스레드 고갈, 타임아웃, 서킷 브레이커, 대체 응답, 비동기 이벤트와 최종 일관성, 즉시 필요한 일과 나중에 해도 되는 일 구분, 실패 건 재처리, 모니터링.
</details>

## 필기 포인트

- 모놀리스 = **하나의 배포 단위**. 코드 품질과는 별개(모듈러 모놀리스 가능).
- MSA 핵심: **독립 배포**, 별도 프로세스, 가벼운 통신(HTTP·메시징), **업무 기능 단위**, 서비스별 데이터, 자동화.
- MSA 9가지 특징(Lewis & Fowler, 2014): 서비스 단위 컴포넌트화, 업무 기능 중심 조직, 제품(만든 팀이 운영), 똑똑한 끝점·단순한 파이프, 분산 거버넌스, 분산 데이터 관리, 인프라 자동화, 장애 대비 설계, 진화적 설계.
- 콘웨이 법칙 = 시스템 구조는 조직의 의사소통 구조를 닮음(Melvin Conway, 1968). 이름은 Fred Brooks가 붙임.
- 서비스별 DB → 한 ACID 트랜잭션 불가 → **Saga + 보상 작업, 최종 일관성**.
- 분산 모놀리스 원인: 설계 결합(공유 DB, 동시 변경) + 런타임 결합(동기 호출 사슬).
- Microservice Premium = MSA의 추가 운영 비용. MonolithFirst = 모놀리스로 시작해 나중에 분리.
- 함정: "MSA = 성능 향상"(X), "모놀리스는 수평 확장 불가"(X).
