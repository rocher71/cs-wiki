:::tip[한 줄 요약]
**동기 통신**(REST·gRPC)은 상대 서비스의 응답을 받아야 내 일이 끝나는 방식이고, **비동기 통신**(메시지 큐·이벤트)은 메시지를 중간 보관소에 맡겨 두고 바로 다음 일을 하는 방식이에요. **결과가 지금 바로 필요하면 동기**, **나중에 반영해도 되거나 여러 서비스가 반응해야 하면 비동기**를 써요. 비동기는 장애가 번지는 걸 막아 주는 대신, 데이터가 잠깐 어긋나고 메시지가 중복으로 올 수 있다는 걸 감수해야 해요.
:::

:::note[처음이라면 여기까지]
① 동기는 **전화**예요. 상대가 받아서 대답해야 통화가 끝나요. 상대가 안 받으면 나도 기다리느라 묶여요.

② 비동기는 **문자·우편함**이에요. 보내 두면 끝이고, 상대는 자기 시간에 읽어요. 상대가 지금 꺼져 있어도 괜찮아요.

③ "잔액 조회"처럼 답이 지금 필요하면 동기, "주문 완료 후 알림·포인트 적립"처럼 조금 늦어도 되면 비동기가 맞아요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
gRPC·Protocol Buffers·Apache Kafka 공식 문서와, 업계에서 널리 인용되는 참고 글(microservices.io, Martin Fowler)을 바탕으로 했어요(2026-11 조회). 공식 출처 하나로 딱 정리되지 않는 비교(예: REST vs gRPC 표)는 이 사실들을 모아 "일반적으로 그렇다"는 수준으로 정리한 거예요.
</Aside>

## 쉽게 이해하기

친구에게 내일 약속 장소를 물어봐야 한다고 해 봐요.

**전화(동기)**를 걸면 친구가 받아서 대답할 때까지 나는 수화기를 들고 기다려요. 답을 바로 들을 수 있다는 게 장점이에요. 그런데 친구가 안 받거나 말이 길어지면, 나는 그동안 아무것도 못 해요. 친구에게 물어보라고 다른 친구에게 또 전화를 거는 식으로 이어지면, 맨 끝 한 명만 늦어도 모두가 수화기를 든 채 기다려요.

**문자나 우편함(비동기)**은 보내 두면 끝이에요. 나는 바로 내 일을 하고, 친구는 폰을 켰을 때 읽어요. 친구 폰이 꺼져 있어도 문자는 사라지지 않고 기다려요. 단체방에 "나 이사했어"라고 한 번 올리면 여러 친구가 각자 알아서 주소록을 고쳐요.

단, 실제로는 문자를 보낸다고 일이 빨리 끝나는 건 아니에요. 내가 빨리 손을 놓을 뿐, 친구가 실제로 처리하는 건 나중이에요. 그리고 "문자가 두 번 갔다" 같은 일도 생겨서, 받는 쪽이 같은 메시지를 두 번 받아도 괜찮게 만들어 둬야 해요.

## 제대로 알기

### 왜 통신 방식이 중요한가

[모놀리스](../monolith-vs-msa/)에선 주문 코드가 포인트 코드를 부를 때 **메서드 호출**(같은 프로그램 안에서 함수를 부르는 것)이면 끝나요. **MSA**(마이크로서비스, 기능별로 따로 배포하는 서비스 여러 개)로 나누면 이게 **네트워크 호출**로 바뀌어요. 네트워크는 느릴 수도, 끊길 수도 있어요.

그래서 "상대를 어떻게 부를까"가 곧 "상대가 느리거나 죽었을 때 나는 어떻게 될까"를 정해요.

### 동기 통신: 응답을 받아야 일이 끝난다

**동기 통신**(synchronous)은 요청을 보내고 응답이 올 때까지 기다리는 방식이에요. 대표가 **REST**(HTTP로 JSON을 주고받는 API 스타일)와 **gRPC**예요.

- 장점: 결과를 바로 알 수 있어요. 흐름이 코드에 그대로 보여서 이해하기 쉬워요.
- 단점: 호출하는 순간 상대가 살아 있고 응답해야 해요. 상대가 느리면 나도 느려지고, 상대가 죽으면 나도 실패해요. 이걸 흔히 **시간적 결합**(temporal coupling, 같은 시간에 둘 다 살아 있어야 하는 묶임)이라고 불러요.

동기 호출이 사슬처럼 이어지면 문제가 커져요. 가용성이 99.9%인 서비스 3개를 차례로 부르면 단순 계산으로 전체는 약 99.7%로 떨어져요(0.999 × 0.999 × 0.999). 하나라도 실패하면 전체가 실패하기 때문이에요.

### 비동기 통신: 맡겨 두고 바로 다음 일

**비동기 통신**(asynchronous)은 메시지를 **메시지 브로커**(message broker, 서비스 사이에서 메시지를 받아 보관했다가 전달해 주는 중간 서버. Kafka, RabbitMQ 등)에 넣고, 응답을 기다리지 않는 방식이에요.

- 장점: 보내는 쪽과 받는 쪽이 동시에 살아 있을 필요가 없어요. 브로커가 메시지를 쌓아 두니까, 받는 서비스가 잠깐 죽어 있어도 나중에 처리할 수 있어요.
- 단점: 브로커라는 구성요소가 하나 늘고, 그 브로커도 죽지 않게 운영해야 해요. "요청하고 결과 받기" 같은 흐름은 오히려 복잡해져요.

비동기를 쓰면 함께 받아들여야 하는 것이 세 가지 있어요.

- **최종 일관성**(eventual consistency): 지금 당장은 서비스마다 데이터가 잠깐 어긋나지만, 조금 지나면 맞춰져요. 주문 직후 포인트가 몇 초 늦게 쌓이는 식이에요.
- **중복 수신**: 같은 메시지가 두 번 올 수 있어요. 받는 쪽은 **멱등**(idempotent, 같은 요청을 여러 번 처리해도 결과가 한 번 처리한 것과 같음)하게 만들어야 해요.
- **흐름이 잘 안 보임**: "주문이 끝나면 누가 뭘 하지?"가 코드 한곳에 드러나지 않아요.

### REST vs gRPC vs 메시지 큐 한눈에 보기

| | REST | gRPC | 메시지 큐·이벤트 |
|---|---|---|---|
| 방식 | 동기(요청→응답) | 동기(요청→응답, 스트리밍도 가능) | 비동기(맡기고 끝) |
| 데이터 형식 | 텍스트 JSON. 사람이 읽기 쉬움 | 바이너리 protobuf. 작음 | 정하기 나름(JSON, protobuf 등) |
| 계약(주고받는 형식 정의) | OpenAPI 등 선택 | `.proto` 파일 필수, 코드 자동 생성 | 메시지 형식을 팀끼리 약속 |
| 전송 | HTTP/1.1 또는 HTTP/2 | HTTP/2 | 브로커(Kafka 등) 경유 |
| 상대가 죽어 있으면 | 호출 실패 | 호출 실패 | 브로커에 쌓였다가 나중에 처리 |
| 주로 쓰는 곳 | 외부 공개 API, 브라우저·앱 | 내부 서비스끼리 | 여러 서비스가 반응해야 하는 일 |

위 표의 "주로 쓰는 곳"은 공식 규칙이 아니라 일반적인 경향이에요.

### gRPC: 다른 서버의 함수를 내 함수처럼

**gRPC**는 **RPC**(Remote Procedure Call, 다른 컴퓨터에 있는 함수를 내 함수처럼 부르는 것) 프레임워크예요. 서버는 기능을 구현하고, 클라이언트는 같은 이름의 메서드를 가진 **스텁**(stub, 네트워크 통신을 대신 해 주는 대리 객체)을 불러요.

순서는 이래요.

1. `.proto` 파일에 "어떤 함수가 있고, 어떤 데이터를 주고받는지"를 적어요.
2. `protoc`(protobuf 컴파일러)와 gRPC 플러그인이 클라이언트·서버 코드를 만들어 줘요.
3. 서버와 클라이언트 언어가 달라도 돼요(예: Java 서버 + Go 클라이언트).

```protobuf
// order.proto — 주문 서비스 계약
syntax = "proto3";

service OrderService {
  rpc GetOrder (OrderRequest) returns (Order);  // 요청 1개 → 응답 1개
}

message OrderRequest { int64 order_id = 1; }

message Order {
  int64 order_id = 1;  // 숫자 1, 2, 3, 4가 "필드 번호"
  int64 user_id = 2;
  string status = 3;
  int32 amount = 4;
}
```

데이터는 기본으로 **Protocol Buffers**(protobuf, 구글이 만든 바이너리 데이터 형식)로 보내요. JSON처럼 글자로 된 게 아니라 0과 1로 꽉 눌러 담은 형식이라 크기가 작아요.

### 실험: 같은 주문을 protobuf와 JSON으로

위 `Order` 메시지에 `order_id=1234567, user_id=42, status="PAID", amount=15000`을 넣고 한 번 재 봤어요.

| 형식 | 크기 |
|---|---|
| protobuf 바이너리 | 15바이트 |
| JSON `{"orderId":1234567,"userId":42,"status":"PAID","amount":15000}` | 62바이트 |

차이가 나는 이유는 protobuf 바이너리에 **필드 이름이 안 들어가기** 때문이에요. `"orderId"` 같은 글자 대신 필드 번호와 타입을 담은 1바이트짜리 꼬리표만 들어가요.

<Aside type="caution" title="몇 배 작다고 외우지 마세요">
이건 이 데이터로 한 번 재 본 예시예요. 비율은 데이터에 따라 달라요. 긴 문자열이 많은 메시지면 차이가 줄어들고, 압축한 JSON과는 비교하지 않았어요. 면접에선 "필드 이름 대신 번호를 넣어서 작다"는 이유를 말하는 게 중요해요.
</Aside>

### 이벤트 vs 커맨드

비동기로 보내는 메시지는 성격에 따라 둘로 나눠요.

| | 이벤트(event) | 커맨드(command) |
|---|---|---|
| 뜻 | "이런 일이 일어났다"는 알림 | "이걸 해라"는 요청 |
| 이름 | 과거형: `OrderCreated` | 명령형: `ChargePayment` |
| 받는 쪽 | 몇 개든 상관없음(0개도 가능) | 그 일을 할 특정 서비스 |
| 보내는 쪽의 기대 | 누가 뭘 하든 신경 안 씀 | 상대가 그 일을 해 주길 기대 |

헷갈리기 쉬운 지점이 있어요. 속으로는 "포인트 적립해 줘"를 기대하면서 이벤트인 척 보내는 경우예요. Fowler는 이걸 **"수동공격형 커맨드"**(passive-aggressive command)라고 부르며 피하라고 해요. 의도가 있으면 커맨드로 보내야 해요.

이벤트를 한 번 발행하면 포인트·알림·통계 서비스가 서로를 몰라도 각자 받아 처리할 수 있어요. 이 방식을 **발행/구독**(pub/sub)이라고 해요. 같은 아이디어를 한 프로그램 안에서 쓰는 게 [옵저버 패턴과 스프링 이벤트](../../oop/patterns-behavioral/)예요.

### 심화: gRPC 4가지 RPC 타입

<GrpcStreamingKinds />

| 타입 | 모양 | `.proto` 표기 | 예시 상황 |
|---|---|---|---|
| Unary | 요청 1 → 응답 1 | `rpc M(Req) returns (Res)` | 주문 하나 조회 |
| Server streaming | 요청 1 → 응답 여러 개 | `returns (stream Res)` | 조건에 맞는 주문 목록을 하나씩 흘려 보내기 |
| Client streaming | 요청 여러 개 → 응답 1 | `rpc M(stream Req)` | 로그를 여러 개 올리고 "몇 건 받음" 한 번 응답 |
| Bidirectional streaming | 양쪽이 각자 여러 개 | 양쪽 다 `stream` | 채팅처럼 서로 아무 때나 주고받기 |

양방향 스트리밍에서 두 방향은 서로 독립이라 순서가 섞여도 되지만, 한 방향 안에서는 보낸 순서대로 도착해요. (예시 상황 칸은 이해를 돕기 위한 예예요.)

### 심화: gRPC가 HTTP/2를 쓰는 이유

gRPC는 **HTTP/2** 위에서 돌아요. RPC 호출 하나가 HTTP/2의 **스트림**(연결 안의 독립된 통로) 하나에 대응해요. 그래서 연결 하나로 여러 호출을 동시에 처리할 수 있어요(**멀티플렉싱**). HTTP/2 자체는 [HTTP 버전별 차이](../../web/http-versions/)에서 다뤄요.

### 심화: "gRPC는 동기"의 정확한 뜻

gRPC를 동기 통신으로 분류하는 건 **요청을 보내고 응답을 받는 상호작용 방식**이라는 뜻이에요. 그런데 gRPC API는 대부분 언어에서 두 가지 스텁을 줘요.

- 동기 스텁: 응답이 올 때까지 스레드가 멈춰요(블로킹).
- 비동기 스텁: 스레드를 막지 않고 응답이 오면 알려 줘요(논블로킹).

즉 **"동기/비동기 통신"**(응답을 받아야 일이 끝나나, 아키텍처 관점)과 **"블로킹/논블로킹"**(내 스레드가 멈추나, 코드 관점)은 다른 축이에요. 비동기 스텁으로 gRPC를 불러도 상대 서버가 살아 있어야 한다는 점은 같아요.

### 심화: deadline — gRPC는 기본으로 무한정 기다린다

**deadline**은 클라이언트가 "이 호출을 언제까지 기다릴지" 정한 시각이에요. 넘으면 `DEADLINE_EXCEEDED` 에러로 끝나요.

- **gRPC는 기본으로 deadline을 정하지 않아요.** 그래서 안 정하면 응답을 무한정 기다릴 수 있어요. 공식 문서도 항상 현실적인 deadline을 정하라고 권해요.
- 서버가 다시 다른 서비스를 부를 땐 처음 클라이언트의 deadline을 이어서 지켜야 해요(**deadline 전파**). Java·Go는 기본으로 전파하고, C++은 직접 켜야 해요.
- 클라이언트와 서버는 성공 여부를 따로 판단해요. 서버는 처리를 끝냈는데 클라이언트는 deadline 초과로 실패 처리할 수 있어요. 취소해도 이미 일어난 변경은 되돌려지지 않아요. 그래서 재시도하려면 서버 쪽이 멱등해야 해요. → [장애 격리와 회복력](../resilience/)

호출마다 인증 정보 같은 키-값을 붙이는 **메타데이터**도 있어요. HTTP 헤더에 해당해요.

### 심화: protobuf 스키마를 바꿀 때 규칙

바이너리에 이름이 아니라 **필드 번호**가 들어가기 때문에 규칙도 번호 중심이에요.

- **쓰고 있는 필드 번호는 바꾸거나 재사용하지 않아요.** 필드를 지우면 번호(와 이름)를 `reserved`로 막아요.
- **새 필드 추가는 안전해요.** proto3는 모르는 필드를 읽을 때 버리지 않고 보존해요. 그래서 구버전 서비스가 신버전 메시지를 받아도 깨지지 않아요. 단, JSON으로 바꾸는 과정에선 유실될 수 있어요.
- **이름만 바꾸는 건 바이너리 기준으론 안전**하지만, JSON 변환을 쓰면 이름도 중요해져요.
- 1~15번은 1바이트, 16~2047번은 2바이트로 인코딩돼요. 자주 쓰는 필드에 1~15번을 주는 게 좋아요.

```protobuf
message Order {
  reserved 3;            // 지운 status 필드 번호는 다시 못 쓰게 막음
  reserved "status";
  int64 order_id = 1;
  int64 user_id = 2;
  int32 amount = 4;
  string state = 5;      // 새 필드는 새 번호로 추가
}
```

### 심화: 이벤트를 어떻게 설계하나

- **이벤트 알림**(event notification): "주문 생성됨, ID는 123"처럼 최소 정보만 보내요. 받는 쪽이 자세한 정보가 필요하면 원래 서비스를 다시 불러요. 결합이 느슨하지만, 전체 흐름이 코드 어디에도 드러나지 않아 파악이 어려워요.
- **상태를 실은 이벤트**(event-carried state transfer): 받는 쪽에 필요한 데이터를 이벤트에 충분히 담아요. 받는 쪽은 자기 사본을 갱신하고 원래 서비스를 부르지 않아도 돼요. 원래 서비스가 죽어도 괜찮고 빨라지지만, 데이터가 중복되고 사본이 잠깐 늦게 맞춰져요.

### 심화: Kafka는 "읽으면 사라지는 큐"가 아니다

**Kafka**에서 이벤트는 "무언가 일어났다"는 기록이에요. 보내는 쪽(**프로듀서**)과 받는 쪽(**컨슈머**)은 서로를 몰라요. 이벤트는 누가 읽어도 바로 지워지지 않고, **토픽**(이벤트를 모아 두는 이름 붙은 통로)마다 정한 보존 기간 동안 남아 있어요. 그래서 알림 서비스가 한동안 죽어 있어도, 살아난 뒤 밀린 이벤트를 읽을 수 있어요. Redis로 비슷한 일을 하는 방법은 [Redis Pub/Sub과 Streams](../../redis/pubsub-streams/)에서 비교해요.

### 심화: DB 저장과 메시지 발행은 한 번에 안 묶인다

주문을 DB에 저장하고 Kafka에 `OrderCreated`를 보내는 코드를 그냥 차례로 쓰면, 둘 중 하나만 성공하는 일이 생겨요. DB와 브로커는 서로 다른 시스템이라 한 트랜잭션으로 묶이지 않기 때문이에요(이런 상황을 흔히 **이중 쓰기**(dual write) 문제라고 불러요).

대표 해법이 **트랜잭셔널 아웃박스**(transactional outbox)예요.

1. 주문을 저장하는 **같은 DB 트랜잭션** 안에서 보낼 메시지를 `outbox` 테이블에도 저장해요. 그러면 둘은 같이 성공하거나 같이 실패해요.
2. 별도의 **메시지 릴레이**(message relay)가 `outbox` 테이블을 읽어 브로커로 보내요.
3. 릴레이가 같은 메시지를 두 번 보낼 수 있으니, 받는 쪽은 멱등해야 해요.

자세한 구현과 사가(Saga)는 분산 시스템 섹션에서 다뤄요.

<details>
<summary>Q. REST와 gRPC의 차이는 무엇이고, 왜 내부 통신에 gRPC를 쓰나요?</summary>

**답변(30초)**
REST는 보통 HTTP로 텍스트 JSON을 주고받고, gRPC는 `.proto` 파일로 계약을 정의하고 바이너리 protobuf로 HTTP/2 위에서 통신해요. gRPC는 필드 이름 대신 번호를 보내 메시지가 작고, 계약에서 코드를 자동 생성해 서비스끼리 형식이 어긋날 일이 적고, 스트리밍도 지원해요. 그래서 호출이 잦은 내부 서비스 간 통신에 많이 써요. 반대로 사람이 읽기 쉽고 어디서나 바로 부를 수 있는 REST는 외부 공개 API에 많이 써요.

**꼬리질문**
- Q. gRPC의 단점은? → 바이너리라 사람이 바로 읽기 어려워 디버깅이 불편하고, `.proto` 파일을 공유·관리하며 호환 규칙을 지켜야 해요. 브라우저에서 바로 부르기는 일반적으로 어렵다고 알려져 있어요.
- Q. protobuf가 항상 몇 배 작나요? → 데이터에 따라 달라요. 긴 문자열이 많으면 차이가 줄어요.
</details>

<details>
<summary>Q. 이벤트와 커맨드는 어떻게 다른가요?</summary>

**답변(30초)**
이벤트는 "이런 일이 일어났다"는 알림이라 과거형 이름(`OrderCreated`)을 쓰고, 받는 쪽이 누구든 무엇을 하든 보내는 쪽은 신경 쓰지 않아요. 커맨드는 "이걸 해라"는 요청이라 명령형 이름(`ChargePayment`)을 쓰고, 특정 서비스가 그 일을 해 주길 기대해요. 속으로는 행동을 기대하면서 이벤트로 보내면 흐름이 헷갈리니, 의도가 있으면 커맨드로 보내는 게 맞아요.

**꼬리질문**
- Q. 이벤트 방식의 단점은? → 결합은 느슨해지지만 "주문 후 누가 뭘 하는지"가 코드 한곳에 안 보여 흐름 파악이 어려워요. 분산 추적이나 이벤트 목록 문서로 보완해요.
</details>

<details>
<summary>Q. gRPC의 4가지 통신 방식을 설명해 주세요.</summary>

**답변(30초)**
요청 하나에 응답 하나인 Unary, 요청 하나에 응답을 여러 개 흘려 보내는 서버 스트리밍, 요청을 여러 개 보내고 응답 하나를 받는 클라이언트 스트리밍, 양쪽이 독립된 스트림으로 아무 때나 주고받는 양방향 스트리밍이 있어요. 양방향에서도 한 방향 안의 메시지 순서는 보장돼요. HTTP/2 스트림 위에서 돌기 때문에 연결 하나로 여러 호출을 동시에 처리할 수 있어요.

**꼬리질문**
- Q. 왜 HTTP/2인가요? → RPC 하나가 HTTP/2 스트림 하나라서 연결 하나에서 여러 호출을 동시에 처리(멀티플렉싱)할 수 있어요.
</details>

<details>
<summary>Q. 동기 호출에서 하위 서비스가 느려지면 어떻게 되고, 어떻게 막나요?</summary>

**답변(30초)**
호출한 쪽 스레드가 응답을 기다리며 묶이고, 그게 쌓이면 호출한 서비스도 새 요청을 못 받아 장애가 위로 번져요. gRPC는 기본으로 deadline이 없어서 안 정하면 무한정 기다릴 수도 있어요. 그래서 호출마다 현실적인 deadline이나 타임아웃을 정하고, 하위 호출까지 deadline을 전파하고, 계속 실패하면 서킷 브레이커로 끊어요. 근본적으로는 꼭 즉시 필요하지 않은 호출을 이벤트로 바꿔 동기 사슬 자체를 줄여요.

**꼬리질문**
- Q. 타임아웃 나서 재시도하면 문제는? → 서버는 이미 처리했을 수 있어요. 취소해도 이미 한 변경은 안 되돌려지니, 서버 쪽이 멱등해야 중복 처리를 막아요.
</details>

<details>
<summary>Q. protobuf 스키마를 바꿀 때 지켜야 할 규칙은?</summary>

**답변(30초)**
바이너리에는 필드 이름이 아니라 번호가 들어가서, 규칙도 번호가 핵심이에요. 쓰고 있는 필드 번호는 바꾸거나 재사용하지 않고, 필드를 지우면 그 번호와 이름을 `reserved`로 막아요. 새 필드는 새 번호로 추가하면 안전해요. proto3는 모르는 필드를 보존하기 때문에 구버전 서비스가 신버전 메시지를 받아도 깨지지 않아요.

**꼬리질문**
- Q. 필드 이름만 바꾸면? → 바이너리는 번호 기준이라 괜찮지만, JSON 변환을 쓰면 이름이 바뀌어 깨질 수 있어요.
</details>

<details>
<summary>Q. Kafka와 일반 메시지 큐의 차이는 뭔가요?</summary>

**답변(30초)**
Kafka에서 이벤트는 컨슈머가 읽어도 바로 지워지지 않고, 토픽마다 정한 보존 기간 동안 남아 있어요. 그래서 여러 컨슈머가 같은 이벤트를 각자 읽을 수 있고, 죽어 있던 서비스도 살아나서 밀린 이벤트를 처리할 수 있어요. 프로듀서와 컨슈머는 서로를 몰라서 결합이 느슨해요.

**꼬리질문**
- Q. 브로커를 쓰면 장애가 사라지나요? → 아니요. 브로커 자체가 죽으면 다 멈추니 브로커도 고가용으로 운영해야 하고, 중복 수신에 대비한 멱등 처리도 필요해요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 완료 API가 포인트 적립 → 알림 발송 → 통계 기록 서비스를 동기로 차례차례 호출해요. 주문 응답이 느리고, 알림 서비스가 죽으면 주문 자체가 실패해요. 어떻게 개선하겠어요?</summary>

**상황 파악**
주문이 끝나려면 포인트·알림·통계가 모두 응답해야 해요. 그래서 응답 시간은 각 호출 시간을 더한 만큼 길어지고, 셋 중 하나만 느리거나 죽어도 주문이 같이 느려지거나 실패해요. 그런데 이 셋은 주문 성공 여부를 바꾸지 않는 **부가 작업**이에요. 사용자에게 "주문 완료"를 보여 주는 데 꼭 필요하지 않아요.

**원인 후보**
1. **시간적 결합**: 동기 호출이라 하위 서비스가 모두 살아 있어야 주문이 끝나요. 99.9% 서비스 셋을 직렬로 부르면 단순 계산으로 약 99.7%까지 떨어져요.
2. **지연 누적**: 호출이 차례로 이어져 대기 시간이 더해져요.
3. **타임아웃 부재**: 알림이 느려지면 주문 서비스 스레드가 기다리며 묶여, 다른 주문까지 막힐 수 있어요.
4. **설계 문제**: 즉시 필요 없는 일까지 동기로 부르고 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 동기는 유지하되 타임아웃 + 서킷 브레이커, 부가 호출 실패는 무시하고 나중에 재처리 | 구조 변경이 작고 빨리 적용 | 여전히 지연이 더해지고, 실패 건을 따로 모아 재처리하는 로직이 필요 |
| B. 주문 서비스는 `OrderCreated` 이벤트만 발행, 포인트·알림·통계가 각자 구독해 처리 | 주문 응답이 부가 작업과 무관해져 빨라지고, 알림이 죽어도 주문은 성공. 새 구독자 추가도 쉬움 | 브로커 운영 부담, 포인트가 몇 초 늦게 쌓이는 최종 일관성, 중복 수신 대비 멱등 처리, 흐름 가시성 저하 |
| C. 같은 서버 안 비동기 스레드로 호출 | 브로커 없이 간단 | 서버가 재시작되면 처리 중이던 작업이 사라질 수 있고, 하위 서비스가 죽어 있으면 결국 실패 |

**내가 고를 방법**
B를 골라요. 결제·재고처럼 주문 성공을 결정하는 일은 동기로 두고, 포인트·알림·통계 같은 부가 작업만 이벤트로 분리해요. 이벤트는 "주문이 생겼다"는 사실이니 과거형 `OrderCreated`로 짓고, 각 서비스가 알아서 반응하게 해요. 브로커가 이벤트를 보관하니 알림 서비스가 잠시 죽어도 복구 후 처리돼요. 다만 DB 저장과 이벤트 발행이 어긋나지 않게 아웃박스를 쓰고, 소비자는 주문 ID 기준으로 이미 처리했는지 확인해 멱등하게 만들어요. 전환 전까지는 A의 타임아웃을 먼저 걸어 장애 번짐부터 막아요.

**채점 포인트**: 핵심 작업과 부가 작업 구분, 시간적 결합·장애 전파, 지연 누적, 이벤트 발행/구독(서로 모름), 브로커의 버퍼링(소비자 장애 시 나중에 처리), 최종 일관성, 멱등 소비자, 아웃박스(이중 쓰기 방지), 타임아웃·서킷 브레이커(단기 대응), 이벤트 이름은 과거형.
</details>

<details>
<summary>상황: 내부 MSA 서비스끼리 JSON REST로 호출량이 많아 지연과 트래픽이 커요. 팀에서 내부 호출을 gRPC로 바꾸자는 의견이 나왔어요. 어떻게 판단하겠어요?</summary>

**상황 파악**
먼저 "느린 원인이 정말 통신 형식인지"부터 확인해야 해요. 지연의 대부분이 DB 조회나 하위 서비스 대기라면 형식을 바꿔도 효과가 작아요. 호출이 아주 잦고 메시지가 크며 직렬화·전송 비용이 눈에 띌 때 gRPC 전환의 효과가 커요.

**원인 후보(현재 REST에서 비용이 생기는 지점)**
1. **메시지 크기**: JSON은 매번 필드 이름을 글자로 보내요. 데이터에 따라 다르지만, 한 번 재 본 주문 예시에선 JSON 62바이트, protobuf 15바이트였어요.
2. **연결 사용**: gRPC는 HTTP/2 스트림 위라 연결 하나로 여러 호출을 동시에 처리해요.
3. **계약 불일치**: JSON 필드명 오타·타입 불일치를 실행 중에야 발견하는 문제가 있다면, `.proto`에서 코드를 생성하는 방식이 도움이 돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. REST 유지 + 개선(응답 필드 줄이기, 압축, 호출 횟수 줄이기) | 기존 도구·디버깅 방식 그대로, 위험 작음 | 계약 자동 검증·스트리밍은 여전히 없음 |
| B. 내부 호출을 gRPC로 전환 | 작은 메시지, HTTP/2 멀티플렉싱, 계약에서 코드 생성, 스트리밍 지원, deadline 전파 | 바이너리라 디버깅 도구 학습 필요, `.proto` 공유·버전 관리와 호환 규칙(번호 재사용 금지, `reserved`) 필요, 브라우저 직접 호출은 일반적으로 추가 구성이 필요 |
| C. 호출량이 많은 몇 경로만 gRPC로 | 효과 큰 곳에만 비용을 씀, 팀이 점진적으로 익힘 | 한동안 REST와 gRPC 두 방식을 같이 운영 |

**내가 고를 방법**
먼저 측정해요. 서비스별로 지연이 어디서 나는지 보고, 직렬화·전송 비중이 큰 경로를 찾아요. 그다음 C로 호출량이 가장 많은 내부 경로 한두 개만 gRPC로 바꿔 효과를 재 봐요. 외부 공개 API는 브라우저·외부 개발자가 쓰기 쉬운 REST로 둬요. gRPC를 도입하면 기본 deadline이 없으니 모든 호출에 deadline을 정하는 규칙과, `.proto` 필드 번호를 재사용하지 않는 규칙을 처음부터 같이 정해요. 효과가 확인되면 범위를 넓혀요.

**채점 포인트**: 병목 측정 먼저, protobuf 바이너리(필드 번호, 크기 차이는 데이터 따라 다름), HTTP/2 멀티플렉싱, `.proto` 계약과 코드 생성, 스트리밍, 디버깅 어려움, 스키마 호환 규칙(번호 재사용 금지·reserved), 브라우저 제약, deadline 기본값 없음, 외부는 REST·내부는 gRPC, 점진 전환.
</details>

<details>
<summary>상황: 주문을 DB에 저장한 다음 Kafka에 "주문 생성" 이벤트를 보내는데, 가끔 DB에는 주문이 있는데 이벤트가 안 나가서 포인트가 안 쌓여요. 원인과 해결책은?</summary>

**상황 파악**
"DB 저장"과 "메시지 발행"이라는 두 작업 중 하나만 성공했어요. DB와 Kafka는 서로 다른 시스템이라 하나의 DB 트랜잭션으로 묶이지 않아요. 반대 순서로 바꿔도 "이벤트는 나갔는데 DB 저장은 롤백"이라는 반대 문제가 생겨요. 이게 흔히 말하는 **이중 쓰기** 문제예요.

**원인 후보**
1. DB 커밋 직후, 발행 직전에 서버가 죽거나 재시작됨.
2. 브로커 일시 장애나 네트워크 오류로 발행이 실패했는데 재시도가 없음.
3. 트랜잭션 안에서 발행했는데 이후 DB 커밋이 실패(반대 방향 불일치).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 발행 실패 시 재시도 | 구현이 간단 | 발행 전에 서버가 죽으면 재시도할 기회 자체가 없음. 근본 해결이 아님 |
| B. DB와 브로커를 하나의 분산 트랜잭션(2PC)으로 묶기 | 이론상 원자적 | DB나 브로커가 지원하지 않을 수 있어 현실적이지 않은 경우가 많음, 느려짐 |
| C. 트랜잭셔널 아웃박스: 같은 DB 트랜잭션에서 주문과 `outbox` 행을 함께 저장, 별도 릴레이가 읽어서 발행 | 주문이 커밋된 경우에만 이벤트가 나감. 서버가 죽어도 outbox에 남아 있어 나중에 발행됨 | outbox 테이블·릴레이 운영이 필요, 같은 이벤트가 두 번 나갈 수 있어 소비자가 멱등해야 함, 발행이 약간 늦어짐 |

**내가 고를 방법**
C를 골라요. 주문 저장과 outbox 기록을 한 로컬 트랜잭션으로 묶으면 "주문은 있는데 이벤트 기록은 없음"이 사라져요. 릴레이가 outbox를 읽어 Kafka로 보내고, 보낸 건 표시해요. 릴레이가 보낸 직후 죽으면 같은 이벤트를 다시 보낼 수 있으니, 포인트 서비스는 주문 ID로 이미 적립했는지 확인해 중복 적립을 막아요. 지금 빠진 이벤트는 DB의 주문과 포인트 내역을 대조해 한 번 보정해요. 아웃박스 구현 방식과 사가 패턴은 분산 시스템 섹션에서 자세히 다뤄요.

**채점 포인트**: 이중 쓰기(DB와 브로커는 한 트랜잭션 불가), 순서를 바꿔도 반대 문제, 2PC의 현실적 한계, 트랜잭셔널 아웃박스(같은 로컬 트랜잭션 + 메시지 릴레이), 커밋된 경우에만 발행, 중복 발행 가능 → 멱등 소비자, 누락분 보정.
</details>

## 필기 포인트

- 동기 = 응답을 받아야 끝남(REST, gRPC). 비동기 = 브로커에 맡기고 끝(Kafka, RabbitMQ).
- 동기의 약점: **시간적 결합**, 장애 전파. 비동기의 비용: 최종 일관성, 중복 수신(멱등 필요), 브로커 운영, 흐름 가시성.
- gRPC: protobuf(바이너리, 기본 IDL), `.proto`로 코드 생성, **HTTP/2** 위, RPC 하나 = HTTP/2 스트림 하나.
- gRPC 4가지: Unary(1→1), Server streaming(1→N), Client streaming(N→1), Bidirectional(N↔N, 각 방향 순서 보장).
- gRPC **기본 deadline 없음** → 항상 설정. 초과 시 `DEADLINE_EXCEEDED`.
- protobuf: 필드 번호 재사용·변경 금지, 지운 번호는 `reserved`. 1~15번은 1바이트. 새 필드 추가는 안전.
- 이벤트 = 과거형, "일어났다". 커맨드 = 명령형, "해라".
- Kafka: 읽어도 안 지워지고 보존 기간 동안 남음. 프로듀서·컨슈머는 서로 모름.
- 함정: "gRPC = 블로킹"(X, 비동기 스텁도 있음), "비동기 = 전체가 빨라짐"(X), "protobuf는 항상 4배 작다"(X, 데이터 따라 다름).
