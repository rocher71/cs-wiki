:::tip[한 줄 요약]
**12-Factor App**은 클라우드에 올려 마음대로 늘리고, 줄이고, 갈아 끼울 수 있는 웹 서비스를 만드는 **12가지 원칙**이에요. 면접에서 가장 많이 묻는 건 세 가지예요. **설정은 코드 밖**(환경변수)에 두고, 서버 프로세스는 **상태 없이**(세션은 Redis 같은 외부 저장소에) 만들고, **로그는 파일이 아니라 stdout 스트림**으로 흘려보내요.
:::

:::note[처음이라면 여기까지]
① 12-Factor는 "서버를 언제든 새로 띄우고 지워도 문제없는 앱"을 만드는 체크리스트예요.

② 12개를 다 외울 필요는 없어요. **설정 분리, 무상태 프로세스, 로그는 스트림** 세 개만 이유까지 말할 수 있으면 돼요.

③ 세 개 모두 같은 이유에서 나와요. 서버(컨테이너)는 언제든 사라지거나 복제될 수 있으니, **사라지면 안 되는 건 서버 안에 두지 않는다**는 거예요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
12factor.net 원문(마지막 갱신 2017)과 Heroku 블로그(2024-11), 개정 저장소 `twelve-factor/twelve-factor`를 바탕으로 했어요(2026-11 조회). 스프링·쿠버네티스 매핑은 이 위키의 관련 페이지와 맞췄어요.
</Aside>

## 쉽게 이해하기

**프랜차이즈 카페**를 떠올려 봐요. 본사는 매장을 하루 만에 열고, 손님이 몰리면 근처에 매장을 하나 더 내고, 장사가 안 되면 바로 닫아요. 이게 되려면 몇 가지 규칙이 필요해요.

**레시피는 본사 매뉴얼 하나**(코드는 하나)고, 매장마다 다른 **주소·와이파이 비밀번호는 매뉴얼에 적지 않고 매장 벽에 따로 붙여요**(설정 분리). 단골 적립 도장은 **매장 수첩이 아니라 본사 앱에 기록**해요(무상태). 그래야 손님이 어느 매장에 가도 도장이 이어지고, 매장 하나가 문을 닫아도 도장은 남아요. 매장 일지도 **매장 서랍에 쌓아 두지 않고 본사로 바로 전송**해요(로그는 스트림). 서랍은 꽉 차기도 하고, 매장이 없어지면 같이 사라지니까요.

단, 실제로는 12-Factor가 법이나 표준 규격은 아니에요. 클라우드에서 앱을 많이 돌려 본 경험에서 나온 **권장 원칙**이에요.

## 제대로 알기

### 12-Factor가 뭐고 왜 나왔나

**12-Factor App**은 Heroku(앱을 올리기만 하면 서버 운영을 대신 해 주는 클라우드 서비스) 공동창업자 Adam Wiggins가 2011년쯤 정리한 원칙이에요. 대상은 인터넷으로 서비스하는 웹앱(SaaS)이에요.

배경은 이래요. 클라우드에선 서버를 사람이 손으로 하나하나 관리하지 않아요. 플랫폼이 필요할 때 새로 띄우고, 남으면 지우고, 고장 나면 갈아 끼워요. 그러니 앱이 **"내가 돌던 그 서버"에 기대면 안 돼요.** 12가지 원칙은 전부 이 한 가지를 여러 각도에서 말한 거예요.

요즘으로 치면 **컨테이너와 쿠버네티스**(컨테이너 여러 개를 자동으로 띄우고 관리하는 플랫폼)에서 앱을 잘 돌리는 방법과 거의 겹쳐요. → [쿠버네티스 구조](../../infra/k8s-architecture/)

### 12개 항목 한눈에 보기

표가 길어요. 폰에선 가로로 밀어서 보세요. ★는 면접 빈출이에요.

| 번호 | 항목 | 한 줄 요지 | 스프링·K8s에서 지키는 법 | 더 읽기 |
|---|---|---|---|---|
| I | 코드베이스 | 앱 하나 = Git 저장소 하나. 같은 코드로 개발·스테이징·운영에 배포 | 공유 코드는 복붙 말고 라이브러리로 분리 | [CI/CD와 GitOps](../ci-cd-gitops/) |
| II | 의존성 | 쓰는 라이브러리를 파일에 명시. 서버에 깔려 있을 거라 기대하지 않음 | build.gradle·pom.xml에 선언, 이미지에 JDK까지 넣음 | [도커 이미지](../../infra/docker-image/) |
| III ★ | 설정 | 배포마다 다른 값(DB 주소, 비밀번호, API 키)은 코드 밖 환경변수로 | 스프링 외부 설정(환경변수가 yml을 덮어씀), K8s ConfigMap·Secret | [ConfigMap·Secret](../../infra/k8s-config/) |
| IV | 백킹 서비스 | DB·캐시·메시지 큐를 "접속 주소로 붙였다 떼는 부품"으로 취급 | `spring.datasource.url` 같은 설정만 바꿔 교체 | [ConfigMap·Secret](../../infra/k8s-config/) |
| V | 빌드·릴리스·실행 | 빌드 → (결과물+설정 = 릴리스) → 실행을 엄격히 나눔. 운영 중 코드 수정 금지 | CI가 이미지 빌드(태그 = 고유 ID), 롤백은 이전 태그로 | [CI/CD와 GitOps](../ci-cd-gitops/) |
| VI ★ | 프로세스 | 프로세스는 상태 없이. 남겨야 할 데이터는 DB·Redis로 | 세션은 Spring Session + Redis 또는 JWT, 파일은 S3 같은 저장소로 | [쿠키·세션·JWT](../../web/cookie-session-jwt/) |
| VII | 포트 바인딩 | 앱이 웹서버를 품고 직접 포트를 염(외부 WAS에 war 배포 X) | 실행 jar의 내장 Tomcat이 `server.port`(기본 8080)를 염 | [Service와 Ingress](../../infra/k8s-service-ingress/) |
| VIII | 동시성 | 처리량은 프로세스를 키우기보다 개수를 늘려서. 웹·워커처럼 역할별로 나눔 | Deployment replicas, HPA로 Pod 수 조절 | [Probe·오토스케일링](../../infra/k8s-probes-scaling/) |
| IX | 폐기 가능성 | 빨리 뜨고, 종료 신호를 받으면 하던 일 마치고 깔끔히 종료 | 스프링 graceful shutdown, K8s 유예 시간·preStop | [Probe·우아한 종료](../../infra/k8s-probes-scaling/) |
| X | 개발·운영 일치 | 개발과 운영의 시간·사람·도구 차이를 줄임. 특히 DB 종류를 똑같이 | H2 말고 Docker Compose·Testcontainers로 운영과 같은 MySQL·Redis | [도커 실행](../../infra/docker-runtime/) |
| XI ★ | 로그 | 앱은 로그 파일을 관리하지 않고 stdout으로 흘림. 수집은 플랫폼 몫 | 콘솔에 JSON 구조화 로그 → 수집기가 중앙 저장소로 | [관측성](../../infra/observability/) |
| XII | 관리 프로세스 | DB 마이그레이션 같은 일회성 작업도 같은 코드·설정으로 따로 실행 | Flyway·Liquibase, K8s Job 또는 initContainer | [무중단 DB 마이그레이션](../db-migration-zero-downtime/) |

### ★ 설정 분리 (III. Config)

**설정**(config)은 여기서 "배포할 곳마다 달라지는 값"이에요. 개발 DB 주소와 운영 DB 주소, 테스트용 API 키와 진짜 API 키처럼요.

이걸 코드에 박아 두면 두 가지 문제가 생겨요. 환경마다 코드를 고쳐서 다시 빌드해야 하고, **Git에 비밀번호가 올라가요.** 그래서 이런 값은 코드 밖, 주로 **환경변수**(운영체제가 프로세스에 넘겨주는 이름=값 쌍)로 넣어요.

판별 기준이 간단해요. **"지금 이 코드를 그대로 공개해도 비밀이 하나도 안 새나?"** 그렇다면 잘 분리된 거예요.

스프링·쿠버네티스에선 이렇게 해요.

```yaml
# application.yml — 코드에는 "어디서 읽을지"만 적어요
spring:
  datasource:
    url: ${DB_URL}            # 환경변수 DB_URL 값이 들어감
    password: ${DB_PASSWORD}  # 비밀번호는 절대 여기 직접 쓰지 않음
```

```yaml
# K8s Deployment 일부 — Secret 값을 환경변수로 넣어 줌
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef: { name: db-secret, key: password }
```

<Aside type="caution" title="오해 두 가지">
- "모든 설정을 환경변수로"가 아니에요. **배포마다 달라지는 값만**이에요. 스프링 빈을 어떻게 연결할지 같은 앱 내부 설정은 코드에 있어도 돼요.
- 환경변수나 K8s Secret에 넣었다고 안전해지는 건 아니에요. **Secret은 기본이 base64 인코딩일 뿐 암호화가 아니에요.** 운영에선 저장 암호화·권한 제한·외부 시크릿 관리를 함께 써요. → [ConfigMap·Secret](../../infra/k8s-config/)
</Aside>

### ★ 무상태 프로세스 (VI. Processes)

**상태**(state)는 "다음 요청 때도 남아 있어야 하는 데이터"예요. 로그인 세션, 장바구니, 업로드한 파일 같은 거요.

**무상태**(stateless)는 데이터를 저장하지 않는다는 뜻이 아니에요. 상태를 **프로세스 바깥**(DB, Redis, 객체 저장소)에 둔다는 뜻이에요. 그러면 아래가 가능해져요.

- **수평 확장**: 서버를 3대로 늘려도 아무 서버나 요청을 받을 수 있어요.
- **자유로운 교체**: 배포·장애로 서버가 재시작돼도 잃을 게 없어요. 쿠버네티스 Pod는 언제든 교체되니까 특히 중요해요.
- **오토스케일**: 부하에 따라 서버를 자동으로 늘리고 줄여도 사용자가 눈치채지 못해요.

스프링에선 세션을 **Spring Session + Redis**에 두거나 **JWT**(로그인 정보를 서명해서 클라이언트가 들고 다니는 토큰)를 써요. 업로드 파일은 로컬 디스크가 아니라 S3 같은 **객체 저장소**에 둬요.

**스티키 세션**(sticky session, 로드밸런서가 같은 사용자를 늘 같은 서버로 보내는 설정)은 임시방편으로 자주 쓰이지만, 12-Factor는 이걸 **명시적으로 위반**으로 봐요. 그 서버가 죽으면 세션이 날아가고, 부하가 한 서버에 쏠리고, 서버를 줄이기 어려워져요.

<Aside type="tip" title="로컬 캐시는 위반인가요?">
아니에요. 메모리 캐시(예: Caffeine)는 **없어져도 원본(DB)에서 다시 가져오면 되는 값**이면 괜찮아요. 금지되는 건 "다음 요청에도 이 서버 메모리에 그 값이 있을 거야"라고 **기대하는 것**이에요. 단, 서버마다 캐시 내용이 잠깐 다를 수 있다는 건 알고 써야 해요.
</Aside>

### ★ 로그는 스트림으로 (XI. Logs)

앱은 로그를 **어느 파일에 쓰고, 언제 쪼개고, 언제 지울지 신경 쓰지 않아요.** 그냥 **stdout**(표준 출력, 화면에 찍는 출력)으로 한 줄씩 흘려보내요. 모으고, 저장하고, 검색하는 건 **실행 환경**(로그 수집기)의 일이에요.

왜 그럴까요?

- 컨테이너는 일회용이라, 컨테이너 안 로그 파일은 **Pod가 교체되면 같이 사라져요.** 장애 원인을 찾으려는데 로그가 없는 상황이 생겨요.
- 앱이 파일을 직접 관리하면 **디스크가 꽉 차는 사고**가 나요. 로그 정리는 앱마다 하지 말고 플랫폼이 한 번에 하는 게 맞아요.
- 서버가 10대면 로그 파일도 10군데 흩어져요. 한 곳에 모아야 검색할 수 있어요.

쿠버네티스에선 stdout 출력을 노드의 수집기(Fluent Bit 등)가 모아 Loki·ELK 같은 중앙 저장소로 보내요. 스프링 부트 3.4부터는 콘솔에 **JSON 구조화 로그**를 바로 찍을 수 있어서, 필드(traceId, userId)로 검색하기 좋아요. → [관측성](../../infra/observability/)

### 나머지 항목 짧게

- **빌드·릴리스·실행(V)**: 운영 서버에 SSH로 들어가 코드를 고치면 안 돼요. 다음 배포 때 사라지고, 무엇이 돌고 있는지 아무도 몰라요. 이미지(빌드 결과) + 설정을 묶은 **릴리스는 바꾸지 않고**, 문제가 생기면 이전 릴리스로 롤백해요.
- **폐기 가능성(IX)**: 종료 신호(SIGTERM)를 받으면 새 요청은 멈추고 처리 중인 요청은 마치고 꺼져요. **Spring Boot 3.4부터 우아한 종료가 기본으로 켜져 있고**(`server.shutdown=graceful`), 단계별 최대 대기는 기본 30초예요. 쿠버네티스 쪽 순서는 [Probe·우아한 종료](../../infra/k8s-probes-scaling/)에 있어요.
- **개발·운영 일치(X)**: 개발은 H2, 운영은 MySQL이면 SQL 문법·락·인덱스 동작이 달라서 **운영에서만 터지는 버그**가 생겨요.
- **포트 바인딩(VII)**: "포트를 연다"는 사소한 얘기가 아니라, 외부 WAS(Tomcat 서버에 war 올리기) 없이 **앱 혼자 완결된다**는 뜻이에요. 실행 jar 하나로 뜨는 스프링 부트가 딱 이 모양이에요.

### 심화: 2024년 오픈소스화와 개정

12factor.net 본문은 2017년 이후 갱신되지 않았어요. **2024년 11월 Heroku가 12-Factor를 오픈소스로 전환**해 커뮤니티가 관리하게 했고, GitHub `twelve-factor/twelve-factor` 저장소에서 **개정 작업이 진행 중**이에요. 개정 FAQ에 따르면 **12개라는 개수와 범위는 유지**하면서, 낡은 표현을 정리하고 관측성·보안 같은 최신 관행을 보강하는 방향이에요. 항목 이름이 구체적으로 어떻게 바뀔지는 아직 정해진 게 없어요(2026-11 기준).

### 심화: 12-Factor가 안 맞는 곳

12-Factor는 **요청을 받아 응답하는 무상태 웹앱**을 기준으로 해요. DB 자체처럼 상태를 저장하는 게 본업인 프로그램이나 배치 작업엔 그대로 들어맞지 않는 항목이 있어요. 개정 작업도 "무상태 요청 기반 앱 예시부터" 갱신한다고 범위를 밝혔어요. 면접에서 "12-Factor의 한계"를 물으면 이 점과 "2017년 이후 오래 갱신이 없었다"는 점을 말하면 돼요.

**답변(30초)** 클라우드에서 서버를 자유롭게 늘리고 교체할 수 있는 웹앱을 만들기 위한 12가지 원칙이에요. Heroku 쪽에서 2011년쯤 정리했어요. 대표적으로 배포마다 다른 설정은 코드 밖 환경변수로 두고, 프로세스는 상태 없이 만들어 세션 같은 상태는 Redis 같은 외부 저장소에 두고, 로그는 파일 대신 stdout으로 흘려 플랫폼이 모으게 해요. 공통된 생각은 "서버는 언제든 사라질 수 있으니 중요한 건 서버 안에 두지 않는다"예요.

**꼬리질문**
- Q. 12-Factor가 표준인가요? → 아니에요. 경험에서 나온 권장 원칙이에요. 2024년에 오픈소스로 전환돼 커뮤니티가 개정 중이에요.
- Q. 쿠버네티스와는 무슨 관계예요? → 쿠버네티스가 Pod를 자유롭게 늘리고 교체하려면 앱이 이 원칙을 따라야 해요. ConfigMap·Secret(설정), replicas·HPA(동시성), SIGTERM 처리(폐기 가능성)가 그대로 대응돼요.
</details>

<details>
<summary>Q. 설정을 왜 코드와 분리하나요? 스프링·쿠버네티스에선 어떻게 하나요?</summary>

**답변(30초)** 환경마다 다른 값을 코드에 박으면 환경마다 다시 빌드해야 하고, 비밀번호가 Git에 올라가기 때문이에요. 그래서 같은 이미지를 두고 설정만 바꿔 개발·운영에 배포해요. 스프링은 application.yml에 `${DB_PASSWORD}`처럼 자리만 두고 환경변수가 값을 덮어쓰게 하고, 쿠버네티스는 ConfigMap과 Secret으로 그 환경변수를 넣어 줘요. 기준은 "코드를 공개해도 비밀이 안 새는가"예요.

**꼬리질문**
- Q. 모든 설정을 환경변수로 빼야 하나요? → 아니에요. 배포마다 달라지는 값만이에요. 빈 연결 같은 내부 설정은 코드에 있어도 돼요.
- Q. K8s Secret에 넣으면 안전한가요? → 기본은 base64 인코딩이라 누구나 되돌릴 수 있어요. 저장 암호화, 접근 권한 제한, 외부 시크릿 관리를 함께 써야 해요.
</details>

<details>
<summary>Q. 무상태(stateless) 서버가 왜 중요한가요?</summary>

**답변(30초)** 아무 서버나 아무 요청을 처리할 수 있어야 서버를 마음대로 늘리고 줄이고 교체할 수 있기 때문이에요. 세션을 서버 메모리에 두면 다른 서버로 간 요청은 로그인이 풀리고, 서버가 재시작되면 세션이 날아가요. 그래서 세션은 Redis 같은 외부 저장소나 JWT로 빼고, 파일은 객체 저장소에 둬요. 무상태는 상태가 없다는 게 아니라 상태를 프로세스 밖에 둔다는 뜻이에요.

**꼬리질문**
- Q. 세션은 Redis와 JWT 중 뭘 쓰나요? → Redis는 바로 로그아웃·차단이 되지만 Redis가 죽으면 전원 로그아웃이라 Redis를 이중화해야 해요. JWT는 저장소 조회가 없지만 만료 전 무효화가 어려워요.
- Q. 스티키 세션은 왜 안 좋나요? → 그 서버가 죽으면 세션이 사라지고, 부하가 쏠리고, 서버를 줄이기 어려워요. 12-Factor는 명시적으로 위반으로 봐요.
- Q. 로컬 캐시(Caffeine)는 무상태 위반인가요? → 잃어도 DB에서 다시 가져오면 되는 값이면 괜찮아요. 서버 간 값이 잠깐 다를 수 있다는 건 감안해요.
</details>

<details>
<summary>Q. 로그를 왜 파일이 아니라 stdout으로 남기나요?</summary>

**답변(30초)** 컨테이너는 일회용이라 안에 쓴 로그 파일은 Pod와 함께 사라지고, 앱이 파일 경로·회전·삭제까지 관리하면 디스크가 꽉 차는 사고가 나기 때문이에요. 12-Factor에선 앱은 stdout으로 흘리기만 하고, 모으고 저장하고 검색하는 건 실행 환경이 맡아요. 쿠버네티스에선 노드의 수집기가 stdout을 모아 Loki나 ELK 같은 중앙 저장소로 보내요. 서버가 여러 대여도 한곳에서 검색할 수 있어요.

**꼬리질문**
- Q. 그럼 `kubectl logs`로 보면 되지 않나요? → 노드에 잠깐 남는 것이라 회전되며 지워지고 Pod가 쫓겨나면 사라져요. 오래 보관하려면 중앙 수집이 필요해요.
- Q. 구조화 로그는 왜 쓰나요? → JSON 키-값으로 찍으면 traceId·userId 같은 필드로 검색할 수 있어요. 스프링 부트 3.4부터 지원해요.
</details>

<details>
<summary>Q. 빌드·릴리스·실행을 왜 분리하나요? 롤백과 무슨 관계예요?</summary>

**답변(30초)** 릴리스를 "빌드 결과물 + 설정"으로 묶고 바꾸지 않아야, 지금 운영에 무엇이 돌고 있는지 정확히 알고 언제든 되돌릴 수 있어서예요. CI가 jar를 이미지로 빌드해 고유 태그를 붙이고, 그 이미지와 설정이 릴리스가 돼요. 문제가 생기면 코드를 고치지 않고 이전 태그로 롤백해요. 운영 서버에 들어가 직접 고치면 다음 배포에서 사라지고 기록도 안 남아요.

**꼬리질문**
- Q. 운영 서버에서 급하게 핫픽스하면 안 되나요? → 다음 배포 때 덮여서 사라지고, 어떤 코드가 도는지 기록도 안 남아요. 고친 코드를 다시 빌드해 새 릴리스로 내보내요.
</details>

<details>
<summary>Q. 우아한 종료(graceful shutdown)가 뭐고 왜 필요한가요?</summary>

**답변(30초)** 종료 신호를 받으면 새 요청은 거절하고, 처리 중인 요청은 끝낸 뒤 꺼지는 거예요. 쿠버네티스는 배포·축소 때 Pod를 수시로 끄는데, 그냥 끊으면 처리 중이던 요청이 실패해요. Spring Boot 3.4부터는 기본으로 켜져 있고, 쿠버네티스는 SIGTERM을 보낸 뒤 유예 시간(기본 30초)이 지나면 강제로 죽여요. 트래픽 차단과 SIGTERM이 동시에 일어나서 보통 preStop sleep으로 틈을 메워요.

**꼬리질문**
- Q. 3.3 이하면요? → 기본이 `immediate`라 `server.shutdown=graceful`을 직접 넣어야 해요.
</details>

<details>
<summary>Q. 개발은 H2, 운영은 MySQL로 쓰면 뭐가 문제인가요?</summary>

**답변(30초)** SQL 문법, 락, 인덱스 동작이 DB마다 달라서 로컬 테스트는 통과했는데 운영에서만 실패하는 버그가 생겨요. 12-Factor의 개발·운영 일치 원칙은 특히 DB 같은 백킹 서비스의 종류를 환경마다 다르게 쓰지 말라고 해요. Docker Compose나 Testcontainers로 로컬에서도 운영과 같은 MySQL·Redis 버전을 띄워 테스트해요.
</details>

## 서술형 연습

<details>
<summary>상황: 트래픽이 늘어 서버를 1대에서 3대로 늘렸더니 "로그인이 자꾸 풀린다"는 문의가 쏟아집니다. 1대일 땐 문제가 없었어요. 원인과 해결책을 설명하세요.</summary>

**상황 파악**
1대일 땐 멀쩡했고 늘린 뒤에만 생겼으니, 서버 간에 **공유되지 않는 무언가**가 원인일 가능성이 커요. 로그인 상태가 풀린다는 건 세션을 못 찾는다는 뜻이에요.

**원인 후보**
- 세션이 각 서버의 **메모리**(기본 `HttpSession`)에 저장돼 있어요. 서버 A에서 로그인했는데 로드밸런서가 다음 요청을 B로 보내면 B엔 세션이 없어요.
- 배포·재시작 때도 같은 증상이 나요. 서버 메모리의 세션이 통째로 사라지니까요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 스티키 세션 | 코드 수정 없이 로드밸런서 설정만으로 바로 적용 | 서버가 죽거나 재시작되면 그 서버 사용자 전원 로그아웃. 부하 쏠림. 축소 어려움. 12-Factor 위반 |
| B. 세션을 Redis로(Spring Session) | 앱 서버가 무상태가 돼 자유롭게 늘리고 교체 가능. 강제 로그아웃도 쉬움 | 요청마다 Redis 조회. Redis가 죽으면 전원 로그아웃이라 Redis 이중화 필요 |
| C. JWT로 전환 | 저장소 조회 없이 검증. 서비스가 여러 개여도 전달 쉬움 | 만료 전 무효화가 어려움. 인증 구조를 크게 바꿔야 함 |

**내가 고를 방법과 이유**
당장 문의를 줄이려면 **A로 급한 불을 끄고**, 바로 **B로 옮기겠어요.** 기존 세션 구조를 거의 그대로 두고 저장 위치만 바꾸면 돼서 변경 범위가 작고, 앱 서버를 무상태로 만들어 앞으로 오토스케일과 무중단 배포도 가능해져요. Redis는 복제와 자동 장애 전환으로 단일 장애점이 되지 않게 해요. C는 서비스가 여러 개로 나뉘는 시점에 검토해요.

**채점 포인트**: 세션이 서버 메모리에 있음, 로드밸런서가 다른 서버로 보냄, 무상태 프로세스(12-Factor VI), 스티키 세션의 한계, Redis 세션 저장소(Spring Session), Redis 이중화, JWT 트레이드오프, 재시작·배포 때도 같은 문제
</details>

<details>
<summary>상황: 코드 리뷰 중 application.yml에 운영 DB 비밀번호가 평문으로 적혀 있고, 이미 GitHub 저장소에 몇 달 전부터 커밋돼 있는 걸 발견했어요. 어떻게 대응하겠어요?</summary>

**상황 파악**
비밀번호가 Git 이력에 남았으니 **이미 유출됐다고 가정**해야 해요. 지금 파일에서 지워도 과거 커밋에서 누구나 볼 수 있어요. 할 일은 두 갈래예요. 당장 피해를 막는 것, 그리고 다시 안 생기게 구조를 바꾸는 것이에요.

**원인 후보**
- 설정이 코드와 분리돼 있지 않아요(12-Factor III 위반). 환경마다 다른 값을 yml에 직접 적었어요.
- 커밋 전에 비밀을 걸러 내는 장치(시크릿 스캔)가 없었어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Git 이력에서 비밀번호 지우기 | 저장소에서 흔적 제거 | 이미 복제(clone)된 사본과 유출된 값은 못 지움. 이것만으로는 불충분 |
| B. 비밀번호 즉시 교체 + 접근 기록 점검 | 유출된 값을 무효화하는 유일한 확실한 방법 | 교체 순간 앱 재배포가 필요. 순서를 잘못 맞추면 짧은 장애 |
| C. 환경변수 + K8s Secret으로 이전 | 코드엔 `${DB_PASSWORD}` 자리만 남아 재발 방지. 환경마다 같은 이미지 사용 | Secret은 기본 base64라 저장 암호화·권한 제한을 따로 켜야 함 |
| D. 외부 시크릿 관리 도구 | 접근 기록·주기적 교체 등 관리가 체계적 | 도입·운영 비용이 큼 |

**내가 고를 방법과 이유**
**B를 가장 먼저** 해요. 이미 퍼진 값은 지울 수 없으니 값 자체를 바꾸는 게 핵심이고, 그동안 이상한 접속이 없었는지 DB 접근 기록도 봐요. 동시에 **C로 설정을 코드 밖으로** 옮겨 새 비밀번호는 Secret으로만 넣어요. 그다음 A로 이력을 정리하고, 커밋 단계에 시크릿 스캔을 넣어 재발을 막아요. D는 서비스와 비밀 개수가 많아지면 검토해요.

**채점 포인트**: 이미 유출된 것으로 간주, 비밀번호 교체가 최우선, 파일 삭제만으로는 이력에 남음, 설정과 코드 분리(12-Factor III), 환경변수·K8s Secret, Secret은 base64일 뿐(암호화 아님), 시크릿 스캔으로 재발 방지, 접근 기록 점검
</details>

<details>
<summary>상황: 새벽에 서버가 멈췄어요. 확인해 보니 앱이 /var/log/app/ 아래에 쓰던 로그 파일이 디스크를 100% 채워서 DB 연결·임시 파일 생성까지 실패하고 있었어요. 어떻게 해결하고 재발을 막겠어요?</summary>

**상황 파악**
직접 원인은 디스크 가득 참이고, 근본 원인은 **앱이 로그 파일을 직접 관리**하는데 정리(회전·삭제)가 제대로 안 된 거예요. 급한 건 서비스 복구, 그다음은 로그를 다루는 방식 자체를 바꾸는 거예요.

**원인 후보**
- 로그 회전 설정이 없거나, 크기·보관 개수 제한이 없음
- 에러 폭주로 평소보다 로그가 몇 배로 쏟아짐
- 앱 로그와 앱 실행에 필요한 데이터가 같은 디스크를 씀

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 오래된 로그 삭제 후 회전 설정 추가 | 빠른 복구. 기존 구조 유지 | 서버마다 설정을 관리해야 함. 서버가 늘면 로그가 흩어지고, 서버가 사라지면 로그도 사라짐 |
| B. stdout으로 출력 + 중앙 로그 수집 | 앱은 파일을 안 다뤄 디스크 사고가 원천 차단. 여러 서버 로그를 한곳에서 검색. Pod가 사라져도 로그 보존 | 수집기·저장소(Loki, ELK 등)를 구축·운영해야 함. 수집 지연·비용 |

**내가 고를 방법과 이유**
지금은 **A로 복구**해요. 오래된 로그를 지우거나 옮겨 공간을 만들고, 왜 로그가 폭증했는지(에러 반복 등)도 같이 봐요. 재발 방지는 **B로 가요.** 12-Factor의 "로그는 이벤트 스트림" 원칙대로 앱은 stdout에 JSON 구조화 로그만 찍고, 회전·보관·검색은 플랫폼(노드 수집기 → 중앙 저장소)에 맡겨요. 이러면 앱마다 회전 설정을 챙길 필요가 없고, 서버가 몇 대든 한곳에서 검색할 수 있어요. 디스크 사용량 알림도 함께 걸어 둬요.

**채점 포인트**: 디스크 가득 참이 직접 원인, 앱이 로그 파일을 직접 관리한 게 근본 원인, 즉시 복구(정리·이동), 로그 폭증 원인 확인, 로그는 stdout 스트림(12-Factor XI), 중앙 로그 수집(Fluent Bit → Loki/ELK), 구조화 로그, 디스크 사용량 모니터링
</details>
