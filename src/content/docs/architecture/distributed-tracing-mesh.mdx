:::tip[한 줄 요약]
**분산 추적**은 요청에 **trace id**를 붙여, 서비스 여러 개와 메시지 큐를 지나도 한 요청의 흐름을 한 줄로 이어 보는 기술이에요. **서비스 메시**는 서비스마다 **프록시**를 붙여 암호화(mTLS)·재시도·타임아웃·트래픽 분할·관측을 **앱 코드 밖에서** 처리하는 인프라 계층이에요. 단, 메시를 깔아도 trace id를 다음 호출로 넘기는 건 **앱의 몫**이에요.
:::

:::note[처음이라면 여기까지]
① 서비스가 여러 개면 "이 요청이 어디서 느려졌지?"를 찾기 어려워요. 그래서 요청마다 택배 송장번호 같은 **trace id**를 붙이고, 모든 서비스가 그 번호를 다음 서비스에 그대로 넘겨요.

② 번호를 한 곳이라도 안 넘기면 기록이 두 동강 나요. 메시지 큐를 지날 때도 메시지에 번호를 같이 실어야 해요.

③ **서비스 메시**는 서비스마다 "경비원"(프록시)을 붙여서 암호화·재시도·타임아웃 같은 공통 일을 대신 시키는 구조예요. 편하지만 지연·자원·운영 부담이 늘어서, 서비스가 몇 개 안 되면 안 쓰는 경우도 많아요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="먼저 보면 좋은 페이지">
trace·span이 무엇인지, `traceparent` 헤더가 어떻게 생겼는지, Spring Boot에서 어떻게 켜는지는 [관측성 기본](../../infra/observability/)에 있어요. 이 페이지는 그다음 이야기, 즉 **서비스 경계와 메시지 큐를 넘을 때**, **샘플링**, **서비스 메시**만 다뤄요.
</Aside>

## 쉽게 이해하기

택배를 떠올려 봐요. 물건 하나가 **집하장 → 물류센터 → 동네 대리점 → 집**을 거쳐요. 어디서 늦어졌는지 알 수 있는 건 상자에 **송장번호**가 붙어 있고, 거치는 곳마다 그 번호로 "몇 시 도착, 몇 시 출발"을 찍어 두기 때문이에요. 이 송장번호가 **trace id**예요. 그런데 중간 물류센터가 상자를 새 상자에 옮겨 담으면서 송장을 안 옮겨 붙이면, 그 뒤 기록은 다른 택배처럼 보여요. 추적이 끊기는 거예요.

이제 회사 건물 여러 채가 서로 서류를 주고받는다고 해 봐요. 건물마다 입구에 **경비원**이 서 있어요. 서류가 나가고 들어올 때 경비원이 봉투를 봉인(암호화)하고, 상대 건물 신분증을 확인하고, 상대가 안 받으면 다시 가져가 보고(재시도), 너무 오래 걸리면 포기하고(타임아웃), 출입 기록을 남겨요(관측). 직원(앱)은 서류 내용만 신경 쓰면 돼요. 이 경비원이 **사이드카 프록시**, 경비원 전체가 **서비스 메시**예요. 경비원들에게 규칙을 내려 주는 **본부**도 따로 있어요.

단, 실제로는 경비원이 "아까 들어온 서류 때문에 지금 이 서류가 나간다"는 사실까지는 몰라요. 그건 직원만 알아요. 그래서 송장번호를 다음 서류에 옮겨 적는 일은 **경비원이 아니라 직원(앱)**이 해야 해요.

## 제대로 알기

### 왜 MSA에서 추적이 어려운가

모놀리스에선 요청 하나가 한 프로세스 안에서 끝나서 로그 한 파일만 봐도 흐름이 보여요. MSA에선 "주문하기" 버튼 하나가 주문 → 결제 → 재고 → 알림 서비스를 차례로 지나요. 서비스마다 로그가 따로 쌓이니, 어떤 로그 줄이 같은 요청인지 이어 줄 **공통 번호**가 필요해요. 그게 trace id고, 각 서비스가 한 일 한 덩어리가 **span**이에요(정의는 [관측성 기본](../../infra/observability/) 참고).

### 컨텍스트 전파: 받은 번호를 그대로 넘기기

**컨텍스트 전파**(context propagation)는 받은 trace 정보(trace id, 지금 span id, 샘플링 여부)를 다음 호출에 그대로 실어 보내는 일이에요. 규칙은 하나예요.

- **모든 서비스가 빠짐없이** 넘겨야 해요. 한 서비스라도 빠뜨리면 그 뒤 span은 새 trace로 시작돼서 그림이 두 동강 나요.

HTTP 호출에선 표준 헤더 **`traceparent`**(W3C 표준 trace 헤더)에 담아 보내요. Spring Boot는 스프링이 만들어 준 HTTP 클라이언트를 쓰면 자동으로 넣어 주지만, 직접 `new`로 만든 클라이언트는 전파가 안 돼요. 이게 실무에서 trace가 끊기는 가장 흔한 이유예요.

### 메시지 큐를 지날 때

**메시지 큐**(Kafka 같은, 메시지를 맡아 두었다가 받는 쪽에 전해 주는 중간 창고)를 지나면 HTTP 헤더가 없어요. 그래서 **메시지 자체의 헤더**(Kafka라면 레코드 헤더)에 trace 정보를 넣어요. OpenTelemetry(분산 추적 표준 도구 모음) 규약은 보내는 쪽이 메시지마다 "이 메시지를 만든 시점의 trace 정보"(**생성 컨텍스트**, creation context)를 붙이라고 권해요.

| 역할 | span 종류 |
|---|---|
| 메시지를 만들어 보냄 | `PRODUCER` |
| 받은 메시지를 처리함 | `CONSUMER` |
| 큐에서 직접 꺼내 옴(pull 방식) | `CLIENT` |

HTTP와 다른 점이 하나 있어요. 받는 쪽 span은 보낸 쪽 span의 "자식"보다 **span link**(부모-자식이 아닌 "관련 있음" 연결)로 잇는 게 기본이에요. 소비자가 메시지 여러 개를 한 번에 처리하면 부모가 여러 개여야 하는데, span은 부모를 하나만 가질 수 있기 때문이에요. 메시지 하나만 처리할 땐 부모로 삼아도 돼요.

<Aside type="caution" title="규약 상태">
OpenTelemetry의 messaging span 규약은 2026-11 기준 아직 **Development**(개발 중) 상태예요. 이름이나 세부 규칙이 바뀔 수 있어요. 일부 속성(`error.type`, `server.address` 등)만 Stable이에요.
</Aside>

### 샘플링: 다 저장하면 너무 비싸다

요청마다 trace를 전부 저장하면 저장·전송 비용이 커요. 그래서 일부만 남기는 **샘플링**(sampling)을 해요. OpenTelemetry 문서는 대략 초당 1,000 trace가 넘으면 샘플링을 고려하라고 하고, 트래픽이 많으면 1% 이하만 남겨도 전체를 잘 대표한다고 해요.

| | Head sampling | Tail sampling |
|---|---|---|
| 언제 정하나 | trace **시작할 때**(끝을 보기 전) | span을 (거의) **다 모은 뒤** |
| 흔한 방식 | trace id 기반 확률(예: 5%) | 정책: "에러 난 trace는 항상", "느린 trace는 항상" |
| 장점 | 단순하고 가벼움 | 중요한 trace를 골라 남김 |
| 단점 | 에러 trace도 같은 확률로 버려짐 | trace를 다 모일 때까지 들고 있어야 해서 구현·운영이 어려움 |
| 어디서 | 각 서비스(SDK) | OpenTelemetry Collector(span을 모아 가공·전달하는 중계 서버)의 Tail Sampling Processor |

Head 방식은 trace id로 결정하니까 같은 trace면 모든 서비스가 같은 결정을 내려요. trace가 통째로 남거나 통째로 버려지는 거예요. 결정은 `traceparent` 끝의 sampled 플래그(`-01`)로 뒤 서비스에 전달돼요. Spring Boot 기본값 10%도 head 방식이에요.

그래서 "head 10%면 에러 trace도 10%만 남는다"는 맞는 말이에요. 에러를 빠짐없이 보고 싶으면 tail이 필요해요. 앞단에서 head로 양을 줄이고 뒤에서 tail로 골라 남기는 조합도 써요.

### 서비스 메시란

**서비스 메시**(service mesh)는 서비스 간 통신에 필요한 보안·관측·트래픽 관리 기능을 **앱 코드를 바꾸지 않고** 플랫폼 계층에서 제공하는 인프라 계층이에요. 대표 제품은 **Istio**와 **Linkerd**예요.

구조는 두 층이에요.

| 층 | 무엇 | Istio에서 하는 일 |
|---|---|---|
| **데이터 플레인**(data plane, 실제 트래픽이 지나는 층) | 서비스마다 붙은 프록시 | Istio는 **Envoy** 사이드카. 서비스 간 모든 트래픽을 가로채 재시도·서킷 브레이커·TLS·메트릭·비율 기반 분할 처리 |
| **컨트롤 플레인**(control plane, 규칙을 내려 주는 층) | 프록시들을 관리하는 서버 | **istiod**. 서비스 목록 파악, 라우팅 규칙을 프록시 설정으로 바꿔 배포, 인증서 발급 |

**사이드카**(sidecar)는 오토바이 옆에 붙는 보조석처럼, 앱 컨테이너 옆에 같은 **파드**(pod, 쿠버네티스가 컨테이너를 묶어 띄우는 가장 작은 단위)로 붙어 도는 보조 컨테이너예요. Linkerd는 Envoy 대신 Rust로 만든 가벼운 자체 프록시를 써요.

### 메시가 해 주는 것

| 기능 | 무엇을 해 주나 | Istio에서 |
|---|---|---|
| **mTLS** | 서비스끼리 서로 인증서를 확인하고 암호화 통신(앱 코드 수정 없이) | istiod가 인증 기관(CA)으로서 워크로드마다 인증서 발급 |
| **재시도** | 실패한 요청을 다시 보냄 | **기본 2번 재시도**(켜져 있음). `attempts`, `perTryTimeout`으로 조정 |
| **타임아웃** | 너무 오래 걸리면 포기 | HTTP 타임아웃 **기본 꺼짐**. 라우트별로 `timeout: 10s`처럼 설정 |
| **서킷 브레이커** | 동시 연결 수 제한, 이상한 인스턴스 빼기 | DestinationRule의 `connectionPool`, `outlierDetection` |
| **트래픽 분할** | v1에 75%, v2에 25%처럼 비율로 나눔(카나리·A/B) | VirtualService의 `weight` |
| **관측** | 서비스 간 호출의 메트릭·span을 일정한 형식으로 남김 | Envoy가 자동 기록 |

**mTLS**(mutual TLS, 상호 TLS)는 보통 TLS처럼 서버만 신분을 증명하는 게 아니라 **양쪽 모두** 인증서로 신분을 증명하는 방식이에요. "내부망이니 믿는다"가 아니라 "누구든 확인한다"는 **제로 트러스트**를 앱 수정 없이 얻는 게 메시의 큰 장점이에요.

트래픽 분할 예시를 볼게요. 결제 v2에 10%만 보내는 설정이에요.

```yaml
# VirtualService: payment로 가는 요청을 버전별로 나눔
http:
- route:
  - destination: { host: payment, subset: v1 }
    weight: 90
  - destination: { host: payment, subset: v2 }
    weight: 10   # 문제 생기면 0으로 바꿔 즉시 되돌림
  timeout: 10s   # Istio HTTP 타임아웃은 기본 꺼져 있어 직접 설정
```

subset `v1`, `v2`는 DestinationRule에서 파드 레이블(`version: v1`)로 정의해요. → [무중단 배포](../zero-downtime-deploy/)

### 라이브러리(Resilience4j) vs 메시

재시도·서킷 브레이커는 앱 안 라이브러리(Java라면 **Resilience4j**)로도, 메시로도 할 수 있어요. → [장애 격리와 회복력](../resilience/)

| 항목 | 라이브러리(Resilience4j) | 서비스 메시(Istio·Linkerd) |
|---|---|---|
| 위치 | 앱 프로세스 안 코드·설정 | 앱 밖 프록시 |
| 언어 | 언어별 라이브러리 필요 | 언어 무관 |
| 바꿀 때 | 앱 재배포 | 메시 설정만 변경 |
| 아는 것 | 비즈니스 맥락을 앎 → **fallback**(대체 응답), 메서드 단위 제어 | 요청·응답 수준만 앎 → fallback 불가 |
| 덤 | 없음 | mTLS, 트래픽 분할, 균일한 메트릭 |
| 비용 | 의존성 추가 정도 | 프록시 지연·자원·운영 |

표의 "언어", "아는 것" 비교 일부는 공식 문서보다는 업계에서 흔히 말하는 정리예요. 핵심은 **메시는 앱 속사정을 모른다**는 점이에요. Istio 문서도 메시의 장애 복구는 앱에 보이지 않게 동작하니 앱 쪽 재시도·타임아웃과 충돌할 수 있고, 앱도 실패를 스스로 처리해야 한다고 경고해요.

### 심화: 메시를 써도 추적은 앱이 이어 줘야 한다

Envoy 프록시는 지나가는 요청마다 span을 자동으로 보내요. 그런데 "결제 앱으로 **들어온** 요청 A 때문에 결제 앱이 재고로 **나가는** 요청 B를 보냈다"는 사실은 앱 안에서 일어나서 프록시가 못 봐요. 그래서 Istio 문서는 앱이 다음 헤더를 받은 그대로 다음 호출에 넘기라고 해요.

- `traceparent`, `tracestate` (W3C 표준)
- `x-request-id` (Envoy가 쓰는 요청 번호)
- Zipkin을 쓰면 B3 헤더(`x-b3-traceid` 등)

결국 Spring에서라면 관측성 설정(Micrometer Tracing)과 스프링이 만든 HTTP 클라이언트를 써야 하는 건 메시가 있어도 똑같아요.

### 심화: 앱 재시도 × 메시 재시도

둘 다 재시도를 켜 두면 곱해질 수 있어요. 예를 들어 앱이 최대 3번 시도하고, 매번 메시가 기본 2번 재시도(총 3번 시도)를 하면 최악엔 3 × 3 = **9번** 호출이 나가요. 이 곱셈은 공식 문서에 나온 수치가 아니라 설정값에서 계산한 일반적인 예시예요. 장애로 이미 힘든 서비스에 호출이 몇 배로 쏟아지는 게 문제예요.

Linkerd는 이런 폭증을 줄이려고 **멱등**(idempotent, 여러 번 해도 결과가 같은) 요청만, 그리고 **재시도 예산**(retry budget, 전체 요청 대비 재시도 비율 상한)이 남아 있을 때만 다른 인스턴스로 재시도해요.

### 심화: ambient 모드 — 사이드카 없는 메시

Istio는 사이드카 모드 외에 **ambient 모드**도 있어요. 파드에 사이드카를 넣지 않고, 노드(서버 한 대)마다 하나씩 도는 **ztunnel**이 mTLS·인증·L4(연결·암호화 수준, HTTP 내용은 안 봄) 처리를 맡고, HTTP 라우팅·재시도 같은 L7(HTTP 내용을 보고 판단하는 수준) 기능이 필요할 때만 **waypoint 프록시**(Envoy 기반)를 따로 둬요. ambient 모드는 **Istio 1.24에서 GA**(정식)가 됐어요. 복잡한 설정이 필요한 경우를 위해 사이드카 모드도 계속 지원해요.

### 심화: 도입 비용

아래는 업계에서 흔히 말하는 이야기예요. 공식 수치는 없고, Istio 소개 페이지도 오버헤드 수치는 밝히지 않아요.

- **지연**: 요청마다 보내는 쪽·받는 쪽 프록시를 한 번씩 더 거쳐요. 한 번은 작아도 호출 사슬이 길면 쌓여요.
- **자원**: 사이드카 모드는 파드마다 Envoy가 하나씩 떠서 "파드 수 × 프록시 CPU·메모리"가 들어요. ambient는 노드당 ztunnel로 이 비용을 줄이려는 거예요.
- **운영**: istiod, VirtualService·DestinationRule 같은 설정 리소스를 배워야 하고, 업그레이드 관리가 필요하고(사이드카 모드는 프록시 업그레이드에 파드 재시작이 필요), 장애 때 "앱 문제냐 메시 문제냐"를 가르는 층이 하나 늘어요.
- **언제 쓸 만한가**: 서비스가 많고 언어가 여러 개라 라이브러리로 통일하기 어렵거나, 규제상 서비스 간 mTLS가 필요할 때. 서비스 몇 개짜리 단일 언어(Spring) 팀은 라이브러리로 충분한 경우가 많아요.

### 심화: API 게이트웨이와는 뭐가 다른가

**API 게이트웨이**는 외부 → 내부로 들어오는 트래픽(남북 방향)의 입구고, **서비스 메시**는 내부 서비스 ↔ 서비스 트래픽(동서 방향)을 다뤄요. 쿠버네티스 **Gateway API**는 v1.1(2024-05)부터 메시 지원이 정식(Standard 채널)이 돼서, HTTPRoute의 `parentRef`에 Gateway 대신 **Service**를 적으면 그 서비스로 가는 내부 트래픽을 같은 API로 제어할 수 있어요. 둘이 같은 것이 된 게 아니라, 같은 API로 다룰 수 있게 된 거예요. → [API 게이트웨이와 서비스 디스커버리](../api-gateway-discovery/)

## 면접 질문

<details>
<summary>Q. MSA에서 요청 하나가 여러 서비스를 거칠 때 어떻게 추적하나요?</summary>

**답변(30초)**
분산 추적을 써요. 요청이 처음 들어올 때 trace id를 만들고, 모든 서비스가 그 번호를 `traceparent` 헤더에 실어 다음 호출로 그대로 넘겨요. 서비스마다 자기가 한 일을 span으로 기록하면, 같은 trace id의 span을 모아 요청 하나의 전체 흐름과 구간별 소요 시간을 볼 수 있어요. 핵심은 한 서비스도 빠짐없이 전파하는 거예요.

**꼬리질문**
- Q. 중간 서비스가 헤더를 안 넘기면요? → 그 뒤 span은 새 trace로 시작돼 기록이 두 동강 나요. Spring에선 `new`로 직접 만든 HTTP 클라이언트가 흔한 원인이에요.
- Q. 메시지 큐를 지나면요? → 메시지 헤더(Kafka 레코드 헤더)에 trace 정보를 넣어요. 받는 쪽 span은 보통 link로 연결해요.
</details>

<details>
<summary>Q. 서비스 메시가 뭔가요? 데이터 플레인과 컨트롤 플레인은요?</summary>

**답변(30초)**
서비스 간 통신에 필요한 mTLS, 재시도, 타임아웃, 트래픽 분할, 관측을 앱 코드 대신 인프라 계층에서 처리하는 구조예요. 데이터 플레인은 서비스마다 붙은 프록시로, 실제 트래픽을 가로채 처리해요. Istio에선 Envoy 사이드카예요. 컨트롤 플레인은 이 프록시들에 라우팅 규칙과 인증서를 내려 주는 관리 서버로, Istio에선 istiod예요.

**꼬리질문**
- Q. 사이드카 패턴의 단점은? → 파드마다 프록시가 떠서 자원이 들고, 요청마다 프록시를 두 번 더 거쳐 지연이 생기고, 운영할 게 늘어요.
- Q. ambient 모드는 왜 나왔나요? → 사이드카 없이 노드당 ztunnel로 L4(mTLS)를 처리하고 L7은 필요할 때만 waypoint로 처리해 비용을 줄이려고요. Istio 1.24에서 정식이 됐어요.
</details>

<details>
<summary>Q. Head sampling과 tail sampling의 차이는요?</summary>

**답변(30초)**
Head는 trace 시작 시점에 남길지 정해요. 보통 trace id 기반 확률이라 단순하고 가볍지만, 에러가 난 trace도 같은 확률로 버려져요. Tail은 span을 다 모은 뒤 정해서 "에러 trace는 전부, 느린 trace는 전부" 같은 정책이 가능하지만, trace를 다 모일 때까지 들고 있어야 해서 운영이 어려워요. 그래서 head로 양을 줄이고 Collector에서 tail로 골라 남기는 조합을 써요.

**꼬리질문**
- Q. Head sampling에서 서비스마다 결정이 달라지지 않나요? → trace id로 결정하고 결과를 `traceparent`의 sampled 플래그로 넘기니 trace 단위로 통째로 남거나 버려져요.
</details>

<details>
<summary>Q. 서비스 메시로 mTLS를 어떻게 자동화하나요?</summary>

**답변(30초)**
컨트롤 플레인이 인증 기관 역할을 해서 워크로드마다 인증서를 발급하고, 사이드카 프록시끼리 서로 인증서를 확인하는 상호 TLS로 통신해요. 앱은 평문으로 자기 사이드카에 보내기만 하면 되니, 코드 수정 없이 서비스 간 암호화와 상대 신원 확인을 얻어요. 내부망도 믿지 않는 제로 트러스트를 구현하는 방법이에요.

**꼬리질문**
- Q. 일반 TLS와 mTLS 차이는? → 일반 TLS는 서버만 인증서로 신분을 증명하고, mTLS는 양쪽 모두 증명해요.
</details>

<details>
<summary>Q. Resilience4j 같은 라이브러리와 메시의 재시도·서킷 브레이커, 무엇을 쓰나요? 같이 쓰면 문제는요?</summary>

**답변(30초)**
라이브러리는 앱 안에 있어서 비즈니스 맥락을 알고 fallback 같은 대체 응답을 줄 수 있지만 언어마다 따로 넣어야 해요. 메시는 언어와 무관하게 설정만으로 일괄 적용되지만 앱 속사정을 몰라 fallback은 못 해요. 둘 다 재시도를 켜면 횟수가 곱해져 장애 때 호출이 폭증할 수 있으니, 재시도는 한쪽에서만 하도록 정해요.

**꼬리질문**
- Q. Istio 재시도 기본값은? → HTTP 요청을 기본 2번 재시도해요. 반대로 HTTP 타임아웃은 기본 꺼져 있어요.
- Q. 메시가 있으면 앱의 타임아웃은 없어도 되나요? → 아니요. Istio 문서도 앱이 실패를 스스로 처리해야 한다고 해요.
</details>

<details>
<summary>Q. API 게이트웨이와 서비스 메시는 어떻게 다른가요?</summary>

**답변(30초)**
게이트웨이는 외부에서 내부로 들어오는 남북 트래픽의 입구고, 메시는 내부 서비스끼리 오가는 동서 트래픽에 mTLS·재시도·관측을 적용해요. 쿠버네티스 Gateway API v1.1부터 메시 지원이 정식이 돼서 둘을 같은 API로 설정할 수 있게 됐지만, 역할은 여전히 달라요.
</details>

## 서술형 연습

<details>
<summary>상황: Istio를 도입했는데 추적 화면에서 trace를 보니 주문 서비스에서 끊기고, 결제 쪽은 별도 trace로 보여요. "메시 깔면 추적은 자동 아니었나?" 원인과 해결을 서술하세요.</summary>

**상황 파악**
Envoy 사이드카는 서비스마다 span을 자동으로 남기고 있어요. 그런데 주문 앱으로 들어온 요청과 주문 앱이 결제로 보낸 요청이 같은 요청이라는 연결 고리가 빠졌어요. 이 연결은 앱 안에서 일어나서 프록시는 알 수 없어요.

**원인 후보**
1. 주문 앱이 받은 `traceparent`(또는 Zipkin이면 B3 헤더)를 결제 호출에 안 넘김. 특히 `new`로 직접 만든 HTTP 클라이언트를 써서 자동 전파가 안 됨.
2. 비동기 스레드로 작업을 넘기면서 trace 정보가 따라가지 않음.
3. 중간에 Kafka를 지나는데 메시지 헤더에 trace 정보를 안 넣음.
4. 서비스마다 헤더 형식이 다름(한쪽은 W3C, 한쪽은 B3).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 앱마다 Micrometer Tracing(OpenTelemetry) 설정 + 스프링이 관리하는 HTTP·메시지 클라이언트 사용 | 표준 방식. HTTP·큐 모두 자동 전파, 앱 내부 span도 생김 | 서비스마다 의존성·설정 추가, 직접 만든 클라이언트 코드 수정 필요 |
| B. 필터에서 Istio가 요구하는 헤더(`traceparent`, `tracestate`, `x-request-id`, B3)를 직접 꺼내 다음 호출에 복사 | 라이브러리 없이 최소 수정 | 헤더 목록을 손으로 관리, 비동기·큐 경로는 따로 챙겨야 하고 빠뜨리기 쉬움 |

**내가 고를 방법**
A를 골라요. 먼저 끊기는 지점(주문 → 결제)의 코드를 보고 직접 만든 클라이언트를 스프링 빈으로 바꿔요. 전파 형식은 W3C `traceparent`로 통일해요. 큐 경로도 메시지 헤더에 trace 정보가 실리는지 확인해요. 고친 뒤 테스트 요청 하나를 보내 주문 → 결제 → 알림이 한 trace id로 이어지는지 확인해요.

**채점 포인트**: 메시는 span을 자동 생성하지만 들어온 요청과 나가는 요청의 연결은 앱 책임, `traceparent`/`tracestate`·`x-request-id`·B3 헤더 전달, `new`로 만든 클라이언트·비동기 스레드·큐 헤더 누락, 전파 형식 통일, 수정 후 한 trace로 이어지는지 검증.
</details>

<details>
<summary>상황: 결제 API가 느려진 날, 결제 서비스로 들어오는 호출이 평소의 약 9배로 튀어 완전히 죽었어요. 앱엔 Resilience4j 재시도(최대 3번 시도), 메시엔 Istio 기본 재시도가 켜져 있었어요. 원인과 해결을 서술하세요.</summary>

**상황 파악**
결제가 느려 실패가 늘자, 재시도가 두 층에서 동시에 일어났어요. 이미 힘든 서비스에 요청이 몇 배로 쏟아져 회복할 틈이 없어진 상황이에요.

**원인 후보**
1. **재시도 곱셈**: 앱이 3번 시도하고, 시도마다 Istio가 기본 2번 재시도(총 3번 시도)하면 최악엔 3 × 3 = 9번이에요. (곱셈 계산은 설정값에서 나온 일반적인 예시예요.)
2. Istio의 장애 복구는 앱에 보이지 않게 동작해서, 앱 개발자가 메시 재시도가 켜진 걸 몰랐어요.
3. 재시도 간격이 짧고 상한(재시도 예산)이 없어 실패율이 오를수록 호출도 같이 늘었어요.
4. 결제 같은 **멱등하지 않은** 요청을 재시도해 중복 결제 위험도 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 재시도는 앱(Resilience4j)에서만, 메시 재시도는 해당 라우트에서 끔 | 비즈니스 맥락(멱등 여부, fallback)을 아는 쪽에서 통제 | 언어가 여러 개면 서비스마다 따로 설정해야 함 |
| B. 재시도는 메시에서만, 앱 재시도 제거 | 설정 한 곳에서 일괄 관리, 언어 무관 | 메시는 멱등 여부·fallback을 모름. 결제처럼 위험한 요청은 라우트별로 꺼야 함 |
| C. 어느 쪽이든 재시도 예산·백오프(간격 늘리기)·서킷 브레이커를 함께 | 장애 때 호출 폭증 자체를 막음 | 설정할 게 늘고, 예산을 넘긴 요청은 바로 실패 |

**내가 고를 방법**
Spring 위주 팀이라 A + C를 골라요. 결제처럼 비즈니스 판단이 필요한 호출은 앱에서 멱등 키를 붙여 재시도하고, 서킷 브레이커와 fallback을 둬요. 메시 쪽 재시도는 해당 라우트에서 끄고, 메시는 mTLS·타임아웃·관측에 집중시켜요. 팀 규칙으로 "재시도는 한 층에서만"을 문서화하고, 대시보드에서 들어오는 요청 수와 재시도 비율을 함께 봐요.

**채점 포인트**: 재시도 곱셈(앱 × 메시), Istio 기본 2번 재시도, 메시 복구가 앱에 투명해 충돌 가능, 재시도는 한 곳에서만, 멱등성(멱등 키), 재시도 예산·백오프, 서킷 브레이커, 모니터링.
</details>

<details>
<summary>상황: 서비스 5개, 전부 Spring Boot, 백엔드 4명인 팀이에요. 보안 감사에서 "서비스 간 통신 암호화"를 요구받았고, 누군가 "이참에 Istio 도입하자"고 해요. 어떻게 판단하겠어요?</summary>

**상황 파악**
꼭 필요한 건 서비스 간 암호화(와 가능하면 상대 확인)예요. 재시도·트래픽 분할 같은 나머지 메시 기능은 이미 Spring·Resilience4j로 해결하고 있을 가능성이 커요. 서비스 수와 언어가 적어 "언어 무관하게 일괄 적용"이라는 메시의 큰 장점은 덜 중요해요.

**원인 후보(무엇을 따져야 하나)**
1. 요구 범위: 암호화만인지, 상대 신원 확인(mTLS)까지인지.
2. 메시 비용: 프록시 지연, 파드마다 사이드카 자원, istiod·설정 리소스 학습, 업그레이드, 디버깅 층 추가(업계에서 흔히 말하는 비용이고 공식 수치는 없음).
3. 앞으로의 계획: 서비스나 언어가 늘어날지, 카나리 배포·균일한 메트릭 같은 다른 메시 기능이 곧 필요한지.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 앱에서 TLS(Spring 설정 + 인증서) | 새 인프라 없음, 팀이 이미 아는 기술 | 인증서 발급·관리를 직접 해야 함, 서비스마다 설정 |
| B. Istio 사이드카 모드 | mTLS 자동(istiod가 인증서 발급), 트래픽 분할·관측도 덤 | 지연·자원·운영 부담이 가장 큼. 4명 팀에 학습 비용 |
| C. Istio ambient 모드(ztunnel로 L4 mTLS만) | 사이드카 없이 mTLS, 노드당 프록시라 자원 부담이 작음. L7 기능은 필요할 때 waypoint 추가 | 그래도 메시 운영(istiod·업그레이드)은 필요. 팀에 새 개념 |

**내가 고를 방법**
감사 요구가 "암호화 + 상대 확인"이고 인증서를 손으로 관리할 여력이 없다면 C를 골라요. 사이드카 비용 없이 mTLS를 앱 수정 없이 얻고, 나중에 카나리 배포가 필요해지면 waypoint만 추가하면 돼요. 반대로 요구가 단순 암호화이고 인증서 관리 자동화를 따로 할 수 있으면 A가 가장 가벼워요. B는 서비스·언어가 늘어 L7 기능까지 전반적으로 필요해질 때 다시 검토해요. 어떤 걸 고르든 스테이징에서 지연 증가를 재 보고 결정해요.

**채점 포인트**: 요구사항(암호화 vs mTLS) 먼저 정의, 팀 규모·단일 언어라 메시 이점 작음, 메시 비용(지연·자원·운영·디버깅), 대안(앱 TLS), ambient 모드(L4만, 사이드카 없음), 기존 Resilience4j와 역할 정리, 확장 시 재검토 기준, 도입 전 측정.
</details>

## 필기 포인트

- trace id 전파: HTTP는 `traceparent` 헤더, 메시지 큐는 **메시지 헤더**. 한 곳이라도 빠지면 trace가 끊김.
- 메시징 span 종류: 보냄 `PRODUCER`, 처리 `CONSUMER`, pull로 꺼냄 `CLIENT`. 생산자–소비자는 기본 **span link**(배치 때문). 규약 상태는 **Development**.
- Head sampling = 시작 시 결정(단순, 에러 놓칠 수 있음). Tail sampling = 다 모은 뒤 결정(에러·느린 trace 선별, Collector에서, 운영 어려움).
- 서비스 메시 = **데이터 플레인**(프록시, Istio는 Envoy) + **컨트롤 플레인**(Istio는 istiod: 설정 배포·인증서 발급).
- Istio 기본값 함정: HTTP **재시도 기본 2번 켜짐**, HTTP **타임아웃 기본 꺼짐**.
- 메시가 있어도 앱이 헤더 전달(`traceparent`, `tracestate`, `x-request-id`, B3)을 해야 trace가 이어짐.
- ambient 모드 = 사이드카 없음, 노드당 ztunnel(L4) + 선택적 waypoint(L7). Istio 1.24에서 GA.
- 게이트웨이 = 남북(외부→내부), 메시 = 동서(서비스↔서비스).
