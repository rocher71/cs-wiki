:::tip[한 줄 요약]
**CI**(지속적 통합)는 코드를 메인 브랜치에 자주 합치고 합칠 때마다 **자동으로 빌드·테스트**하는 관행이고, **CD**는 그 결과물을 **언제든 운영에 내보낼 수 있는 상태**로 유지(지속적 전달)하거나 **자동으로 운영까지 내보내는**(지속적 배포) 거예요. **GitOps**는 Git에 적어 둔 "원하는 상태"를 클러스터 안의 에이전트가 **당겨와서 계속 맞추는** 배포 방식이에요.
:::

:::note[처음이라면 여기까지]
① CI는 "자주 합치고, 합칠 때마다 기계가 자동으로 검사"하는 습관이에요. 도구 이름(GitHub Actions, Jenkins)이 아니에요.

② CD는 두 가지 뜻이 있어요. 운영 반영 직전에 **사람이 버튼**을 누르면 지속적 전달, **버튼 없이 자동**이면 지속적 배포예요.

③ 이미지는 **한 번만 빌드**해서 스테이징과 운영에 똑같이 써요. 태그는 바뀔 수 있으니 바뀌지 않는 **다이제스트**(내용 지문)로 고정하는 게 안전해요.

④ GitOps는 "Git이 정답지, 클러스터가 알아서 정답지를 따라감"이에요. 롤백도 Git에서 되돌리기(revert)로 해요.

⑤ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
CI/CD는 표준 문서가 따로 없어서 Martin Fowler의 업계 참고 글을 기준으로 했고, GitHub Actions·쿠버네티스·OpenGitOps·Argo CD는 공식 문서를 따랐어요(2026-11 조회). Argo CD 기본값은 stable 문서 기준이에요.
</Aside>

## 쉽게 이해하기

과자 공장의 **컨베이어 벨트**를 떠올려 봐요.

예전엔 직원들이 각자 부품을 몇 주씩 만들다가 마지막 날 한꺼번에 조립했어요. 그러면 "내 부품이 네 부품에 안 맞네?"가 출시 직전에 터져요. **CI**는 부품을 만들 때마다 바로 벨트에 올리고, 벨트 위 **자동 검사기**가 매번 맞물리는지 확인하는 방식이에요. 문제가 작을 때 바로 잡혀요.

검사를 통과한 과자는 포장까지 끝나 **창고에 쌓여요**. 언제든 트럭에 실을 수 있지만, 실제로 내보내는 건 점장이 "출하!" 버튼을 누를 때예요. 이게 **지속적 전달**이에요. 버튼 없이 검사만 통과하면 바로 트럭에 실려 나가면 **지속적 배포**예요.

**GitOps**는 매장마다 "진열대는 이렇게 생겨야 한다"는 **설계도**를 본사(Git)에 두고, 매장 직원(에이전트)이 몇 분마다 설계도를 확인해 진열대를 맞추는 방식이에요. 누가 몰래 진열을 바꾸면 직원이 알아채요.

단, 실제로는 "검사기"를 사람이 직접 만들어야 해요. 테스트 코드가 없으면 벨트는 돌아도 아무것도 걸러지지 않아요.

## 제대로 알기

### CI: 자주 합치고, 매번 자동 검사

**CI**(Continuous Integration, 지속적 통합)는 개발자가 자기 변경을 **메인라인**(팀이 공유하는 기본 브랜치, 보통 `main`)에 **최소 하루 한 번** 합치고, 합칠 때마다 테스트가 포함된 **자동 빌드**로 검증하는 관행이에요. 목적은 "합쳤더니 안 맞는" **통합 오류를 일찍** 잡는 거예요.

Fowler가 꼽은 핵심 습관은 이래요.

- 버전 관리되는 메인라인 하나에 모든 코드가 모여요.
- 빌드는 사람 손 없이 자동으로 돌고, 빌드 안에 테스트가 들어 있어요(**스스로 테스트하는 빌드**).
- 메인라인에 커밋할 때마다 CI 서버가 빌드해요.
- **빌드가 깨지면 그걸 최우선으로 고쳐요.** 가장 빠른 방법은 보통 문제 커밋을 되돌리는 거예요.
- 빌드는 빨라야 해요. 커밋 빌드는 약 10분 안쪽이 가이드예요.
- 빌드 상태(초록불·빨간불)를 모두가 볼 수 있어야 해요.

아직 덜 만든 기능은 어떻게 매일 합칠까요? **피처 플래그**(코드는 들어가 있지만 스위치로 꺼 두는 방법)로 숨긴 채 넣어요. → [피처 플래그](../feature-flag/)

### CD: 지속적 전달 vs 지속적 배포

CD는 두 단어의 약자로 쓰여요. 차이는 딱 하나, **운영 반영이 자동이냐 사람 승인이냐**예요.

| | 지속적 통합(CI) | 지속적 전달(Continuous Delivery) | 지속적 배포(Continuous Deployment) |
|---|---|---|---|
| 한 줄 뜻 | 자주 합치고 매번 자동 빌드·테스트 | 언제든 운영에 내보낼 수 있는 상태 유지 | 통과한 변경은 자동으로 운영까지 |
| 자동화 범위 | 빌드·테스트 | 빌드부터 운영 직전까지 | 빌드부터 운영까지 전부 |
| 운영 반영 | 해당 없음 | 사람이 승인 버튼 | 버튼 없음 |
| 전제 | 자동 테스트 | CI가 되어 있음 | 지속적 전달이 되어 있음 |

지속적 전달은 "배포할 수 있지만 사업상 이유로 지금은 안 할 수도 있다"는 뜻이에요. 지속적 배포를 하려면 먼저 지속적 전달이 되어 있어야 해요.

### 배포 파이프라인: 단계마다 걸러 내는 벨트

**배포 파이프라인**(deployment pipeline)은 CD를 실제로 굴리는 장치예요. CI 위에서 실행물을 빌드하고, 자동 테스트를 돌리고, 점점 **운영과 비슷한 환경**으로 밀어 올려요. 목표는 "어떤 버전이든 어떤 환경에든 버튼 하나로 배포"예요.

1. main에 merge → 파이프라인 시작
2. 빌드(컴파일)
3. 자동 테스트(단위 → 통합). **실패하면 여기서 멈추고** 빨간불
4. 컨테이너 이미지를 빌드해 **레지스트리**(이미지 저장소)에 `app:v1.4.2` 같은 태그로 올림
5. 스테이징(운영과 비슷한 시험 환경)에 그 이미지를 배포하고 통합·E2E 테스트
6. 운영에 배포(승인 버튼 또는 자동)
7. 운영에도 **5번과 같은 이미지**를 씀. 다시 빌드하지 않아요

앞 단계일수록 빠르고 싸게, 뒤로 갈수록 느리지만 운영에 가깝게 검사해요. 어느 단계든 실패하면 그 뒤로 넘어가지 않아요.

### GitHub Actions로 보는 실제 예: 이 위키의 배포

이 위키도 GitHub Actions로 자동 배포돼요. 먼저 용어부터요.

| 용어 | 뜻 |
|---|---|
| Workflow | 저장소 안 YAML 파일로 정의한 자동화 하나(job 1개 이상) |
| Event | 워크플로를 시작시키는 일(push, PR 등) |
| Job | 같은 runner에서 도는 step 묶음. 기본은 서로 **병렬** |
| Step | job 안의 명령 하나 또는 action 하나. 순서대로 실행 |
| Action | 남이 만들어 둔 재사용 작업 단위 |
| Runner | 워크플로를 실행하는 서버. 한 번에 job 하나 |

이 위키의 `.github/workflows/deploy.yml`을 줄여 보면 이래요.

```yaml
on:
  push:
    branches: [main]      # main에 push되면 시작
  workflow_dispatch:      # 버튼으로 수동 실행도 가능
concurrency:
  group: pages            # 배포가 동시에 두 개 돌지 않게
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5    # 코드 가져오기
      - uses: withastro/action@v5    # 사이트 빌드
        with:
          node-version: 22
  deploy:
    needs: build          # build가 끝나야 시작
    runs-on: ubuntu-latest
    steps:
      - uses: actions/deploy-pages@v4  # GitHub Pages에 올리기
```

job은 원래 병렬로 돌지만 `needs: build` 때문에 deploy가 build를 기다려요. main에 push하면 사람 승인 없이 사이트가 바뀌니 **지속적 배포**의 작은 예예요. 다만 테스트 단계는 없어서 "빌드 성공"이 사실상 유일한 검사예요. 그리고 CI가 직접 배포 대상에 올리니 뒤에 나올 **push형**이에요.

### 아티팩트 불변성: 한 번 빌드해서 그대로 승격

**아티팩트**(artifact)는 빌드 결과물이에요. 컨테이너 시대엔 주로 이미지예요.

쿠버네티스 문서가 짚는 사실부터 볼게요.

- **태그**(`v1.4.2`, `latest`)는 다른 이미지를 가리키도록 **옮길 수 있어요**(가변). 같은 이름표를 다른 상자에 다시 붙일 수 있는 셈이에요.
- **다이제스트**(`@sha256:...`, 이미지 내용으로 계산한 지문)는 내용이 바뀌면 값도 바뀌어서 **불변**이에요.
- 태그만 쓰면 레지스트리에서 태그 내용이 바뀌었을 때 옛 코드 Pod와 새 코드 Pod가 섞일 수 있어요. 다이제스트로 지정하면 막을 수 있어요.
- 태그를 생략하면 `latest`로 간주돼요. 운영에서 `latest`는 피하래요. 어떤 버전이 도는지 추적하기 어렵고 제대로 롤백하기 어려워서예요.

여기에 업계에서 흔히 따르는 관행이 하나 더 있어요. **"한 번 빌드하고 여러 번 배포"**(build once, deploy many)예요. 이미지를 파이프라인에서 한 번만 만들고, **같은 다이제스트**를 스테이징 → 운영으로 **승격**(promote, 다음 환경으로 올려 보냄)해요. 환경 차이(DB 주소 등)는 이미지가 아니라 설정(ConfigMap·Secret·환경변수)으로 줘요. 그래야 "스테이징에서 테스트한 것"과 "운영에 나간 것"이 정말 같은 물건이에요. → [Docker 이미지](../../infra/docker-image/), [12-Factor App](../twelve-factor/)

### push형 vs pull형(GitOps)

배포를 "누가 클러스터에 적용하느냐"로 나눌 수 있어요. 아래 push형 설명과 보안 비교는 공식 문서 문구가 아니라 업계에서 흔히 하는 구분이에요.

| | push형(전통적인 CD) | pull형(GitOps) |
|---|---|---|
| 누가 적용하나 | CI 파이프라인이 `kubectl apply`·`helm upgrade`로 직접 | 클러스터 안 에이전트(Argo CD 등)가 Git을 당겨와서 |
| 클러스터 쓰기 권한 | CI 시스템이 들고 있어야 함 | 에이전트가 클러스터 안에 있어 CI 밖으로 덜 나감 |
| CI가 하는 일 | 테스트·빌드·배포까지 | 테스트·빌드·이미지 push + **설정 저장소의 태그 변경 커밋** |
| 손으로 바꾼 설정(드리프트) | 다음 배포 전까지 모름 | 계속 비교하니 감지, 설정에 따라 자동 복구 |
| 반영 속도 | 파이프라인이 끝나면 바로 | 에이전트 확인 주기만큼 지연(Argo CD 기본 최대 약 3분, 웹훅으로 즉시도 가능) |
| 롤백 | 이전 버전으로 파이프라인 다시 실행 등 | Git에서 revert |

### GitOps의 4원칙(OpenGitOps)

**GitOps**는 CNCF의 OpenGitOps 프로젝트가 원칙 네 가지로 정리했어요(v1.0.0).

1. **선언형**(Declarative): "이렇게 해라"(명령)가 아니라 "이런 상태여야 한다"(원하는 상태)로 적어요.
2. **버전 관리·불변**(Versioned and Immutable): 원하는 상태를 고칠 수 없고 버전이 매겨지며 전체 이력이 남는 곳에 저장해요.
3. **자동으로 당겨옴**(Pulled Automatically): 에이전트가 사람 손 없이 원하는 상태를 가져와요.
4. **지속적 조정**(Continuously Reconciled): 에이전트가 실제 상태를 계속 보면서 원하는 상태로 맞추려 해요.

원칙 문장에 "Git"이 꼭 들어가진 않아요. 저장소로 Git을 쓰는 게 대표적일 뿐이에요. 4번은 쿠버네티스 컨트롤러가 원래 하는 **조정 루프**와 같은 생각이에요. → [쿠버네티스 구조](../../infra/k8s-architecture/)

그래서 GitOps는 "Git에 YAML 넣어 두기"가 아니에요. CI가 Git의 YAML을 `kubectl apply`로 밀어 넣으면 그건 push형이에요. 핵심은 **에이전트가 당겨와서 계속 맞추는 것**이에요. 또 GitOps는 CI를 대체하지 않아요. 테스트와 이미지 빌드는 여전히 CI 몫이고, GitOps는 배포 쪽 방식이에요.

### Argo CD는 어떻게 동작하나

**Argo CD**는 쿠버네티스용 선언형 GitOps CD 도구예요. Git 저장소를 앱의 **진실의 원천**(source of truth, "정답은 여기"라고 정한 한 곳)으로 쓰고, 쿠버네티스 컨트롤러로 돌면서 실행 중인 앱을 계속 감시해요.

| 용어 | 뜻 |
|---|---|
| Application | Argo CD가 관리하는 쿠버네티스 리소스 묶음 |
| Target state | Git 파일에 적힌 원하는 상태 |
| Live state | 클러스터의 지금 상태 |
| Sync status | 둘이 같으면 `Synced`, 다르면 `OutOfSync` |
| Sync | 클러스터를 target state로 맞추는 작업 |
| Health | 앱이 정상으로 요청을 처리할 수 있는지 |

흐름은 이래요. CI가 설정 저장소에서 이미지 태그를 `v1.4.2`로 바꾸는 커밋을 해요. Argo CD가 Git을 확인하다 달라진 걸 보고 `OutOfSync`로 표시해요. **자동 동기화**(automated sync)가 켜져 있으면 바로 sync해서 `Synced`가 돼요. 그래서 CI는 Argo CD를 직접 부를 필요 없이 **Git에 커밋만** 하면 돼요.

### 심화: 기본값 함정 — self-heal과 prune은 꺼져 있다

자동 동기화를 켜도 기본값으로는 다음 두 가지를 안 해요.

- **self-heal 기본 꺼짐**: 누가 `kubectl edit`·`kubectl scale`로 클러스터를 직접 바꾸면(**드리프트**, Git과 실제가 어긋나는 것) 기본은 `OutOfSync`로 **표시만** 해요. self-heal을 켜야 다시 sync해서 Git 상태로 되돌려요.
- **prune 기본 꺼짐**: Git에서 지운 리소스를 클러스터에서 자동으로 지우지 않아요. 실수로 지웠을 때를 대비한 안전장치예요. 켜려면 `prune: true`.

```yaml
# Argo CD Application의 일부
syncPolicy:
  automated:
    prune: true     # Git에서 지운 리소스도 클러스터에서 삭제
    selfHeal: true  # 손으로 바꾼 걸 Git 상태로 되돌림
```

Git을 확인하는 주기는 `timeout.reconciliation` 기본 120초에 최대 60초의 무작위 지연이 더해져 **최대 약 3분**이에요.

### 심화: 롤백은 Git revert로

Argo CD에도 Git에 커밋됐던 설정으로 되돌리는 롤백 기능이 있어요. 그런데 **자동 동기화가 켜져 있으면 이 기능을 쓸 수 없어요.**

그래서 GitOps의 정석 롤백은 **설정 저장소에서 이전 커밋으로 `git revert`** 하는 거예요. 에이전트가 그 상태로 sync하고, "누가 언제 왜 되돌렸나"가 Git 이력에 남아요.

단, 되돌아가는 건 Git에 적힌 것(이미지 태그, 매니페스트)뿐이에요. 이번 배포에서 DB 스키마를 바꿨다면 revert로 DB는 돌아가지 않아요. → [무중단 DB 마이그레이션](../db-migration-zero-downtime/)

### 심화: 설정 저장소를 따로 두는 이유

Argo CD 문서는 매니페스트를 담은 **설정 저장소를 앱 소스 저장소와 분리**하라고 권해요.

- 레플리카 수 하나 바꿨는데 CI 전체 빌드가 도는 걸 피해요.
- 배포 이력만 깔끔하게 남아 감사하기 좋아요.
- 여러 저장소로 된 앱을 한 단위로 배포할 수 있어요.
- 코드를 쓰는 사람과 운영 배포 권한자를 나눌 수 있어요.
- CI가 같은 저장소에 매니페스트를 커밋하면 "커밋 → 빌드 → 커밋 → 빌드" 무한 루프가 생길 수 있어요.

또 kustomize·helm으로 원격 설정을 참조할 땐 `HEAD`가 아니라 Git 태그나 커밋 SHA로 고정하래요. 내 저장소가 안 바뀌어도 남의 저장소가 바뀌면 배포 내용이 달라지니까요. 이미지 다이제스트 고정과 같은 생각이에요.

### 심화: 오래 사는 피처 브랜치와 CI

Fowler는 "CI와 오래 사는 피처 브랜치는 대체로 맞지 않는다"고 봐요. 피처 브랜치에서만 CI 서버를 돌리는 건 메인라인에 자주 합치지 않으니 "반쪽 통합"이라는 거예요(기능이 하루 안에 끝나면 예외). 이건 업계 참고 글의 견해이고, 실무에선 짧게 사는 PR 브랜치에 PR마다 CI를 돌리는 방식이 흔해요.

**꼬리질문**
- Q. GitHub Actions를 쓰면 CI를 하는 건가요? → 도구는 수단이에요. 피처 브랜치를 몇 주씩 두고 CI 서버만 돌리면 자주 합친다는 핵심이 빠져요.
- Q. 빌드가 깨지면 어떻게 하나요? → 최우선으로 고쳐요. 가장 빠른 방법은 보통 문제 커밋을 되돌리는 거예요.

<details>
<summary>Q2. 지속적 전달과 지속적 배포의 차이는?</summary>

**답변(30초)** 차이는 운영 반영이 자동이냐 사람 승인이냐예요. 지속적 전달은 소프트웨어를 언제든 릴리스할 수 있는 상태로 유지하되, 운영 배포는 사람이 버튼을 눌러요. 지속적 배포는 파이프라인을 통과한 변경이 자동으로 운영까지 나가요. 지속적 배포를 하려면 지속적 전달이 먼저 되어 있어야 해요.

**꼬리질문**
- Q. 왜 지속적 배포 대신 전달을 고를까요? → 배포할 수 있어도 사업상 이유로 시점을 고르고 싶을 때가 있어서예요.
</details>

<details>
<summary>Q3. 배포 파이프라인 단계를 설명해 주세요.</summary>

**답변(30초)** merge되면 빌드, 단위·통합 테스트, 이미지 빌드와 레지스트리 push, 스테이징 배포와 E2E 테스트, 운영 배포 순으로 가요. 어느 단계든 실패하면 다음으로 넘어가지 않아요. 중요한 건 이미지를 한 번만 빌드하고 같은 이미지를 스테이징과 운영에 그대로 쓰는 거예요.

**꼬리질문**
- Q. 빌드가 40분 걸리면? → 개발자들이 커밋을 몰아서 하게 돼 CI 효과가 떨어져요. 커밋 빌드는 약 10분 안쪽이 가이드라 단계를 나누고, 독립적인 job은 병렬로 돌려요.
- Q. GitHub Actions에서 job은 순서대로 도나요? → 기본은 병렬이고, `needs`로 의존을 걸면 앞 job을 기다려요. 같은 job의 step은 순서대로 돌아요.

<details>
<summary>Q4. 환경마다 이미지를 다시 빌드하면 안 되나요? latest 태그는 왜 피하나요?</summary>

**답변(30초)** 다시 빌드하면 스테이징에서 테스트한 것과 운영에 나간 것이 달라질 수 있어요. 그래서 한 번 빌드한 같은 이미지를 승격하고 환경 차이는 설정으로 주는 게 흔한 관행이에요. latest는 어떤 버전이 도는지 추적하기 어렵고 롤백도 어려워서 피해요. 태그 자체가 옮겨 붙일 수 있는 가변 값이라, 정말 고정하려면 다이제스트로 지정해요.

**꼬리질문**
- Q. 태그와 다이제스트 차이는? → 태그는 다른 이미지를 가리키게 바꿀 수 있고, 다이제스트는 내용의 해시라 불변이에요.
</details>

<details>
<summary>Q5. GitOps란 무엇이고 push 방식과 뭐가 다른가요?</summary>

**답변(30초)** GitOps는 원하는 상태를 Git에 선언적으로 적어 두고, 클러스터 안의 에이전트가 그걸 당겨와 실제 상태와 계속 맞추는 방식이에요. push 방식은 CI가 kubectl 같은 걸로 클러스터에 직접 배포해서 CI가 클러스터 권한을 가져야 하고, 누가 손으로 바꾼 설정을 다음 배포 전까지 몰라요. GitOps에선 CI는 이미지 빌드와 설정 저장소 커밋까지만 하고, 에이전트가 드리프트를 감지하고 복구할 수 있어요.

**꼬리질문**
- Q. GitOps 4원칙은? → 선언형, 버전 관리·불변, 자동으로 당겨옴, 지속적 조정이에요.
- Q. GitOps의 단점은? → 에이전트 운영 부담, 설정 저장소 커밋 단계 추가, 확인 주기만큼 반영 지연(Argo CD 기본 최대 약 3분)이 있어요.
</details>

<details>
<summary>Q6. Argo CD에서 누가 kubectl로 설정을 바꾸면 어떻게 되나요?</summary>

**답변(30초)** Git의 target state와 클러스터의 live state가 달라지니 OutOfSync로 표시돼요. 그런데 기본값은 표시만 하고 되돌리지 않아요. self-heal을 켜 두면 드리프트를 감지했을 때 다시 sync해서 Git 상태로 되돌려요. 마찬가지로 Git에서 지운 리소스를 클러스터에서 지우는 prune도 기본은 꺼져 있어요.
</details>

<details>
<summary>Q7. GitOps에서 롤백은 어떻게 하나요?</summary>

**답변(30초)** 설정 저장소에서 문제 커밋을 git revert 하면 에이전트가 이전 상태로 sync해요. Argo CD에도 롤백 기능이 있지만 자동 동기화가 켜져 있으면 쓸 수 없어서, Git revert가 정석이에요. 되돌린 이력이 Git에 남는 것도 장점이에요. 다만 DB 스키마 변경은 Git revert로 돌아가지 않으니 마이그레이션은 따로 하위 호환을 지켜야 해요.

**꼬리질문**
- Q. 설정 저장소를 왜 앱 저장소와 나누나요? → 설정만 바꿔도 전체 빌드가 도는 걸 피하고, 배포 이력과 권한을 분리하고, CI 커밋이 다시 빌드를 부르는 무한 루프를 막으려고요.
</details>

## 서술형 연습

<details>
<summary>상황: 장애 대응 중 운영자가 kubectl scale로 레플리카를 3개에서 10개로 늘렸는데, 몇 분 뒤 다시 3개로 돌아갔어요. 또 늘려도 계속 되돌아가요. 왜 그럴까요?</summary>

**상황 파악**
누가 일부러 줄인 게 아니라면, 무언가가 "정답은 3개"라고 믿고 계속 맞추고 있다는 뜻이에요. 배포를 Argo CD 같은 GitOps 도구로 하고 있다면 가장 먼저 의심할 곳이에요.

**원인 후보**
1. **Argo CD self-heal**: Git의 매니페스트엔 `replicas: 3`이 적혀 있어요. kubectl로 바꾼 건 드리프트라 `OutOfSync`가 되고, self-heal이 켜져 있으면 다시 sync해서 3개로 되돌려요. "몇 분 뒤"라는 시간 차도 이 확인 주기와 맞아요.
2. **자동 확장 설정**: HPA(부하에 따라 Pod 수를 조절하는 기능)가 걸려 있으면 그 설정이 개수를 다시 조정할 수 있어요. → [프로브와 오토스케일링](../../infra/k8s-probes-scaling/)
3. **push형 파이프라인 재실행**: 그사이 누가 배포해서 YAML이 다시 적용됐을 수도 있어요.

먼저 Argo CD 화면에서 해당 앱이 OutOfSync → Synced로 바뀐 기록이 있는지 보면 1번인지 바로 확인돼요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 설정 저장소에서 `replicas: 10`으로 커밋 | 정석. 이력이 남고 에이전트가 반영 | 리뷰·커밋 절차와 반영 지연(기본 최대 약 3분)이 있어 급할 때 답답함 |
| B. 해당 앱의 자동 동기화(또는 self-heal)를 잠시 끄고 kubectl로 조정 | 즉시 반영 | Git과 실제가 어긋난 채로 남음. 다시 켜는 걸 잊으면 드리프트가 방치됨 |
| C. 레플리카 수를 HPA에 맡기고 Git 관리 대상에서 빼기 | 부하에 따라 자동 조절, 사람 개입 불필요 | 설정 작업이 필요하고 Git만 봐선 실제 개수를 알 수 없음 |

**내가 고를 방법**
장애 중이면 A를 바로 해요. 커밋 한 줄이고, 웹훅이 연결돼 있으면 거의 즉시 반영돼요. 정말 초 단위로 급하면 B로 잠깐 버티되, 끝나면 Git에 맞춰 커밋하고 동기화를 다시 켜는 걸 장애 대응 체크리스트에 넣어요. 장기적으론 부하에 따라 개수가 바뀌어야 하는 앱이라면 C로 가요. 핵심은 "GitOps에선 Git이 정답지라 클러스터를 직접 고치는 건 임시방편"이라는 걸 팀이 공유하는 거예요.

**채점 포인트**: 드리프트 개념, self-heal(기본은 꺼짐, 켜져 있으면 되돌림), target state vs live state, Git이 진실의 원천, Git 커밋으로 변경, 반영 지연(확인 주기·웹훅), 다른 원인(HPA·push 재배포) 배제, 임시 조치 후 Git과 다시 맞추기.
</details>

<details>
<summary>상황: 스테이징에선 잘 돌던 v1.4.2가 운영에선 다른 동작을 해요. 확인해 보니 두 환경 모두 app:v1.4.2 태그로 배포했는데 실제 이미지 내용이 달랐어요. 원인과 재발 방지책은?</summary>

**상황 파악**
같은 태그인데 내용이 다르다는 건, 그 태그가 두 시점에 서로 다른 이미지를 가리켰다는 뜻이에요. 스테이징에서 검증한 물건과 운영에 나간 물건이 달랐던 거예요.

**원인 후보**
1. **태그 재사용**: 태그는 가변이라 누군가(또는 파이프라인 재실행이) 같은 `v1.4.2`로 이미지를 다시 push했어요.
2. **환경마다 재빌드**: 운영 배포 때 이미지를 다시 빌드했고, 그사이 베이스 이미지(`latest` 등)나 의존성이 바뀌어 다른 내용이 나왔어요.
3. **태그로만 참조**: 매니페스트가 태그만 가리켜서, 노드가 언제 이미지를 받았느냐에 따라 옛 이미지와 새 이미지 Pod가 섞일 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 매니페스트에서 다이제스트(`@sha256:...`)로 지정 | 내용이 바뀌면 값도 바뀌어 확실히 고정. 섞일 일이 없음 | 사람이 읽기 어려워 태그와 함께 적거나 도구로 관리해야 함 |
| B. 불변 태그 규칙(커밋 SHA나 버전 태그, 덮어쓰기 금지)과 latest 금지 | 사람이 읽기 쉽고 추적·롤백이 쉬움 | 레지스트리·팀 규칙에 의존. 규칙이 깨지면 다시 같은 문제 |
| C. 한 번 빌드해서 같은 이미지를 승격(운영에서 재빌드 금지) | 스테이징에서 검증한 그 물건이 그대로 운영에 감 | 환경 차이를 이미지가 아니라 설정(ConfigMap·Secret·환경변수)으로 분리해야 함 |

**내가 고를 방법**
C를 기본 원칙으로 삼고 A로 고정해요. 파이프라인은 이미지를 한 번만 빌드하고, 그 다이제스트를 기록해 스테이징과 운영 매니페스트에 똑같이 넣어요. 사람이 보기 쉽게 B 규칙으로 버전 태그도 함께 붙이되, 실제 배포 기준은 다이제스트예요. 이렇게 하면 "스테이징에서 테스트한 것 = 운영에 나간 것"이 보장되고, 롤백할 때도 이전 다이제스트로 정확히 돌아갈 수 있어요.

**채점 포인트**: 태그는 가변·다이제스트는 불변, latest 지양(추적·롤백 어려움), 환경별 재빌드의 위험, 한 번 빌드·같은 아티팩트 승격(관행), 환경 차이는 설정으로, 옛·새 Pod 섞임, 롤백 정확성.
</details>

<details>
<summary>상황: 배포 후 에러율이 급증해서 설정 저장소를 git revert로 롤백했어요. 앱은 이전 버전으로 돌아왔는데 에러가 계속 나요. 이번 배포에는 컬럼 이름 변경 마이그레이션이 들어 있었어요.</summary>

**상황 파악**
GitOps 롤백은 Git에 적힌 것, 즉 이미지 태그와 매니페스트만 되돌려요. 이미 실행된 DB 스키마 변경은 그대로예요. 이전 버전 앱은 옛 컬럼 이름을 찾는데 DB엔 새 이름만 있어서 에러가 나는 거예요.

**원인 후보**
1. **하위 호환이 깨지는 마이그레이션**: 컬럼 이름을 한 번에 바꿔서 옛 코드가 쓸 수 없는 스키마가 됐어요.
2. **코드와 스키마를 한 배포에 묶음**: 앱 롤백과 DB 롤백이 따로 움직인다는 걸 고려하지 않았어요.
3. **롤백 계획 부재**: "되돌리면 DB는?"을 배포 전에 확인하는 절차가 없었어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 지금 당장 역방향 마이그레이션(컬럼 이름을 되돌림) | 이전 버전 앱이 바로 동작 | 장애 중에 운영 DB를 급히 건드리는 위험. 이름 변경 외에 데이터 변환까지 섞였다면 되돌리기 어려움 |
| B. 롤백 대신 앞으로 고치기(새 버전을 다시 배포하고 에러 원인만 수정) | 스키마는 그대로 두고 앱만 맞춤 | 원인을 찾고 고치는 데 시간이 걸려 장애가 길어짐 |
| C. 재발 방지: 마이그레이션을 하위 호환 단계로 쪼개기(새 컬럼 추가 → 양쪽에 쓰기 → 옮기기 → 옛 컬럼 제거를 여러 배포에 나눔) | 어느 단계에서 앱을 롤백해도 DB와 맞음 | 배포 횟수와 작업량이 늘어남 |

**내가 고를 방법**
지금은 에러 원인이 스키마 불일치로 확실하니, 마이그레이션 내용을 보고 A와 B 중 더 짧은 쪽을 골라요. 단순 이름 변경이었다면 이름만 되돌리는 A가 가장 빨라요. 데이터 변환까지 섞여 되돌리기 어렵다면 B가 덜 위험해요. 재발 방지는 C예요. 스키마 변경은 항상 "이전 버전 앱도 동작하는" 단계로 쪼개서, Git revert 하나로 안전하게 롤백되는 상태를 유지해요. 배포 체크리스트에 "이 배포를 되돌리면 DB는?" 항목도 넣어요. 자세한 단계는 [무중단 DB 마이그레이션](../db-migration-zero-downtime/)에서 다뤄요.

**채점 포인트**: Git revert는 매니페스트·이미지만 되돌림, DB 스키마는 별개, 하위 호환 마이그레이션(단계 분리), 역방향 마이그레이션 vs 앞으로 고치기 트레이드오프, 마이그레이션 내용 확인, 배포 전 롤백 계획.
</details>

## 필기 포인트

- CI = 메인라인에 **자주(최소 하루 한 번)** 통합 + 매번 **자동 빌드·테스트**. 도구가 아니라 관행.
- 지속적 **전달** = 언제든 릴리스 가능, 운영 반영은 **사람 승인**. 지속적 **배포** = 운영까지 **자동**. 배포는 전달을 전제로 함.
- 이미지 **태그는 가변**, **다이제스트(sha256)는 불변**. 태그 생략 시 `latest`, 운영에선 지양.
- GitHub Actions: job은 기본 **병렬**, `needs`로 순서. 같은 job의 step은 순서대로 같은 runner에서.
- OpenGitOps 4원칙: **선언형, 버전 관리·불변, 자동으로 당겨옴, 지속적 조정**.
- Argo CD: Git = 진실의 원천, target vs live 다르면 **OutOfSync**. **self-heal·prune 기본 꺼짐**. 자동 동기화 켜면 Argo CD 롤백 기능 사용 불가 → **Git revert**.
- 함정: "GitOps = Git에 YAML 보관"(X, 당겨와서 계속 조정이 핵심), "GitOps가 CI를 대체"(X).
