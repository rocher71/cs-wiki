:::tip[한 줄 요약]
서비스는 **기술 계층이 아니라 업무 기능**(바운디드 컨텍스트, 비즈니스 능력) 기준으로 나누고, **서비스마다 자기 데이터를 가져서 남의 데이터는 API로만** 가져와요. 모놀리스에서 옮길 때는 한 번에 다시 짜지 않고 **스트랭글러 패턴**으로 기능을 하나씩 떼어 내요.
:::

:::note[처음이라면 여기까지]
① 같은 "상품"이라도 카탈로그·주문·배송 팀이 신경 쓰는 정보가 달라요. 이렇게 **말뜻이 바뀌는 곳**이 서비스를 나눌 자리예요.

② 서비스마다 자기 DB(데이터 저장소)를 갖고, 다른 서비스 데이터는 그 서비스에 **API로 물어봐서** 가져와요. 남의 테이블을 직접 읽으면 안 돼요.

③ DB가 나뉘면 SQL 조인이 안 되니, 여러 서비스를 불러 합치거나 데이터를 미리 복사해 둬요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
서비스 경계는 표준 문서가 없는 설계 주제라, 업계에서 널리 참고하는 글(Martin Fowler의 bliki, Chris Richardson의 microservices.io)을 바탕으로 했어요(2026-11 조회). 커머스 "상품" 예시는 이 글들의 원칙을 쇼핑몰에 적용해 본 설명용 예시예요.
</Aside>

## 쉽게 이해하기

학교에서 "**출석부**"라는 말을 생각해 봐요. 담임 선생님에게 출석부는 "누가 오늘 왔나"예요. 보건 선생님에게는 "누가 아파서 조퇴했나"이고, 급식실에게는 "오늘 밥을 몇 명분 할까"예요. 같은 단어인데 부서마다 보는 칸이 달라요.

이걸 **하나의 거대한 출석부**로 통일하면 칸이 수십 개로 불어나요. 급식실이 칸 하나를 바꾸면 담임 선생님 양식까지 다시 찍어야 해요. 차라리 부서마다 **자기 장부**를 두고, 학생 번호만 같이 쓰는 게 편해요. 다른 부서 정보가 필요하면 그 부서에 **물어봐요**. 남의 장부를 몰래 펼쳐 고치지 않아요.

서비스 나누기도 똑같아요. 말뜻이 바뀌는 곳에서 자르고, 각자 자기 장부(DB)를 가져요.

단, 실제로는 "부서 하나 = 서비스 하나"로 딱 정해진 규칙은 없어요. 경계를 찾는 **기준**일 뿐이고, 몇 개로 묶을지는 팀 크기와 변경 빈도를 보고 정해요.

## 제대로 알기

### 왜 "어디서 자르나"가 중요한가

[모놀리스 vs 마이크로서비스](../monolith-vs-msa/)에서 봤듯이 MSA의 이점은 **서비스를 따로 바꾸고 따로 배포**하는 데 있어요. 그런데 경계를 잘못 그으면 기능 하나 고칠 때마다 여러 서비스를 같이 고쳐야 해요. 그래서 "무엇을 기준으로 자르나"가 MSA 설계의 첫 질문이에요.

흔한 실수는 **기술 계층**으로 자르는 거예요. "화면 서비스", "로직 서비스", "DB 서비스"처럼요. 이러면 기능 하나("쿠폰 추가")에 세 서비스가 다 바뀌어요. 그래서 **업무 기능** 기준으로 잘라요.

### 기준 1: 비즈니스 능력으로 나누기

**비즈니스 능력**(business capability)은 "회사가 고객에게 가치를 만들어 내려고 하는 일" 하나하나예요. 온라인 상점이라면 이런 것들이에요.

- 상품 카탈로그 관리
- 재고 관리
- 주문 관리
- 배송 관리

능력 하나마다 서비스 하나를 두는 방식이에요. 회사가 하는 일은 기술보다 잘 안 바뀌어서 구조가 안정적이에요. 팀도 "주문팀"처럼 기능 하나를 끝까지 책임지게 돼요. 출발점은 보통 회사의 **부서 구조**예요.

### 기준 2: 바운디드 컨텍스트와 서브도메인

**DDD**(Domain-Driven Design, 도메인 주도 설계)는 업무 지식을 중심으로 소프트웨어를 설계하는 방법이에요. 여기서 **도메인**은 "소프트웨어가 다루는 업무 영역"(쇼핑, 배송, 정산 등)을 뜻해요.

DDD의 핵심 도구가 **바운디드 컨텍스트**(Bounded Context, "경계가 그어진 문맥")예요. 큰 업무 모델을 여러 컨텍스트로 나누고, **각 컨텍스트 안에서는 단어 뜻이 하나로 딱 맞게** 만드는 거예요. DDD를 만든 Eric Evans는 큰 시스템 전체를 모델 하나로 통일하는 건 가능하지도 않고 비용만 크다고 봤어요.

커머스의 "상품"으로 보면 이래요.

| 컨텍스트 | "상품"이 뜻하는 것 | 가진 정보 |
|---|---|---|
| 카탈로그 | 보여 주고 검색하는 대상 | 이름, 설명, 이미지, 판매가 |
| 주문 | 주문 항목(OrderLine) | 상품ID, **주문 당시 가격**, 수량 |
| 배송 | 소포(Parcel) | 무게, 부피, 주소, 송장번호 |

주문 컨텍스트가 가격을 **따로 복사해 두는 것**(스냅숏)이 포인트예요. 나중에 카탈로그에서 판매가를 바꿔도 이미 끝난 주문 금액은 그대로여야 하니까요. 배송은 상품 이름엔 거의 관심이 없어요. 세 컨텍스트는 **상품ID만 공유**하고, 각자 필요한 필드만 자기 모델에 둬요.

Fowler는 전력회사 예를 들어요. "계량기(meter)"라는 말이 부서마다 다른 걸 가리켰대요. 말로 할 땐 대충 넘어가지만, 소프트웨어는 모호한 걸 처리하지 못해서 문제가 돼요.

**유비쿼터스 언어**(Ubiquitous Language, "어디서나 쓰는 공통 언어")는 개발자와 업무 담당자가 함께 정한 정확한 용어 사전이에요. 이 언어는 **바운디드 컨텍스트 하나 안에서만** 유효해요. 말뜻이 바뀌는 지점이 곧 컨텍스트 경계 후보예요. 경계를 만드는 가장 큰 요인은 보통 사람과 조직(어휘가 바뀌는 곳)이에요.

**서브도메인**(subdomain)은 업무 영역을 성격별로 나눈 거예요.

| 종류 | 뜻 | 어떻게 만드나 |
|---|---|---|
| 핵심(core) | 우리 회사를 차별화하는 가장 가치 있는 부분 | 직접 공들여 개발 |
| 지원(supporting) | 사업과 관련 있지만 차별화 요소는 아님 | 직접 개발 또는 외주 |
| 일반(generic) | 어느 회사나 비슷한 것 | 이미 있는 제품을 사서 씀 |

<Aside type="caution" title="바운디드 컨텍스트 = 서비스 1개?">
꼭 1:1로 대응한다고 외우지 마세요. 참고한 글들은 바운디드 컨텍스트를 **경계를 찾는 기준**으로 제시할 뿐, 하나당 서비스 하나를 규칙으로 정하지 않아요.
</Aside>

### 서비스마다 자기 DB 갖기 (Database per Service)

**Database per Service**(서비스별 데이터베이스)는 서비스의 데이터를 **그 서비스만** 읽고 쓰게 하는 규칙이에요. 다른 서비스는 그 데이터를 **API로만** 가져가요. 한 서비스의 트랜잭션은 자기 DB만 건드려요.

오해하기 쉬운 점이 있어요. **DB 서버를 서비스 수만큼 띄우라는 뜻이 아니에요.** 관계형 DB라면 세 가지 방법이 있어요.

| 방법 | 설명 | 비용 |
|---|---|---|
| 서비스별 전용 테이블 | 같은 DB에서 테이블 주인만 정함 | 가장 적음 |
| 서비스별 스키마 | 같은 DB 서버 안에 칸(스키마)을 나눔 | 적음 |
| 서비스별 DB 서버 | 서버 자체를 따로 둠 | 큼 |

앞의 두 방법은 **DB 계정과 권한**을 서비스별로 줘서 "남의 테이블은 못 읽음"을 강제할 수 있어요. 핵심은 "남의 데이터는 API로만"이에요.

장점과 단점은 이래요.

- 장점: 내 테이블 구조를 바꿔도 다른 서비스에 영향이 없어요. 서비스마다 맞는 DB를 골라도 돼요(검색은 검색엔진, 관계가 복잡하면 그래프 DB).
- 단점: 여러 서비스에 걸친 트랜잭션이 어려워요. 여러 DB를 **조인**(테이블 여러 개를 합쳐 한 번에 조회하는 SQL 기능, → [SQL 기본과 JOIN](../../db/sql-basics-join/))할 수 없어요. 운영할 DB 종류도 늘어요.

여러 서비스에 걸친 쓰기는 **Saga**(각 서비스가 자기 트랜잭션을 차례로 하고, 실패하면 되돌리는 작업을 보내는 방식)로 풀어요. 결과적으로 잠깐 어긋났다가 결국 맞춰지는 **최종 일관성**이 돼요. 자세한 건 분산 섹션에서 다뤄요.

### 공유 DB는 왜 보통 피하나

**Shared Database**(공유 데이터베이스)는 모든 서비스가 DB 하나를 같이 쓰고 서로의 테이블을 직접 읽고 쓰는 방식이에요. MSA에서는 **보통 피해야 할 방식**으로 꼽혀요(안티패턴이라고도 불려요).

장점도 있어요. 익숙한 ACID 트랜잭션을 그대로 쓰고, 운영이 단순해요. 하지만 결합이 생겨요.

- **개발할 때 결합**: 상품팀이 테이블 컬럼을 바꾸려면, 그 테이블을 읽는 주문팀·정산팀과 먼저 맞춰야 해요. 모르고 바꾸면 남의 서비스가 배포 후 깨져요.
- **실행할 때 결합**: 정산 서비스가 긴 트랜잭션으로 주문 테이블에 **잠금**(다른 쪽이 못 건드리게 잡아 두는 것)을 걸면, 주문 서비스가 멈춰요.
- DB 하나가 모든 서비스의 저장 요구를 다 맞추지 못할 수 있어요.

### 서비스 간 조인 대신 쓰는 3가지 방법

모놀리스에선 `orders JOIN members JOIN products` 한 줄이면 됐어요. DB를 나누면 이게 안 돼요. 대신 이렇게 해요.

| 방법 | 어떻게 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
| API 조합 | 게이트웨이나 화면용 서버가 주문·회원·상품 서비스를 차례로 불러 메모리에서 합침 | 항상 최신 데이터, 만들기 쉬움 | 호출이 많아 느려짐, 한 서비스가 죽으면 일부가 빔 |
| 데이터 복제 | 주문 만들 때 상품명·가격을 주문에 복사(스냅숏), 또는 이벤트를 받아 내 쪽에 사본 유지 | 내 DB만 읽어 빠름, 남이 죽어도 조회됨 | 사본이 잠깐 옛날 값일 수 있음, 저장 공간 |
| CQRS 조회 뷰 | 서비스들이 내보내는 이벤트를 모아 "내 주문 목록" 같은 조회 전용 테이블을 따로 만듦 | 화면에 딱 맞춘 빠른 조회 | 만들고 운영할 게 많음, 반영이 살짝 늦음 |

**CQRS**(Command Query Responsibility Segregation)는 "쓰는 모델과 읽는 모델을 나눈다"는 뜻이에요. **이벤트**는 "주문이 생성됐다"처럼 일이 일어났다고 알리는 메시지예요.

### 스트랭글러 패턴: 하나씩 옮기기

오래된 모놀리스를 MSA로 옮길 때, 전부 새로 짜서 어느 날 한 번에 바꾸는 건 위험해요. 다 만들 때까지 성과가 안 보이고, 그동안 기존 시스템도 계속 바뀌어요.

**스트랭글러 피그**(Strangler Fig) 패턴은 기존 시스템 **옆에** 새 기능을 만들고, 기존 기능을 **조금씩** 새 쪽으로 옮기는 방법이에요. 이름은 나무를 감싸며 자라다 결국 혼자 서는 **교살무화과**에서 왔어요.

흐름은 이래요.

1. 지금은 모든 요청이 모놀리스로 가요.
2. 앞단에 **라우터**(요청 주소를 보고 어디로 보낼지 정하는 문지기, 보통 게이트웨이 → [API 게이트웨이와 서비스 디스커버리](../api-gateway-discovery/))를 둬요.
3. 배송 기능을 새 서비스로 만들고 `/delivery/**` 요청만 새 서비스로 보내요.
4. 다른 기능도 하나씩 옮기며 모놀리스 코드를 줄여요.
5. 마지막에 모놀리스를 없애거나 작게 남겨요.

| 좋은 점 | 주의할 점 |
|---|---|
| 조금 투자하고 조금씩 성과가 보임 | 오래된 코드엔 깔끔하게 잘라 낼 **이음매**(seam, 떼어 내기 좋은 경계)가 드물어 찾는 데 공이 듦 |
| 작은 단위라 실패해도 피해가 작음 | 두 시스템이 함께 도는 동안 임시 코드가 필요하고 나중에 버려야 함 |
| 옮기면서 배움 | 팀 문화가 그대로면 새 시스템도 다시 엉킴 |

### 심화: 경계를 잘못 그었다는 신호

기능 하나 고칠 때마다 여러 서비스를 함께 배포해야 한다면 경계가 잘못됐을 가능성이 커요. 업계에선 이런 상태를 흔히 **분산 모놀리스**라고 불러요(공식 정의가 있는 용어는 아니에요). 늘 함께 바뀌는 것은 한 서비스로 묶는 게 원칙이에요. 자세한 건 [모놀리스 vs 마이크로서비스](../monolith-vs-msa/)의 분산 모놀리스 부분을 보세요.

### 심화: 컨텍스트 맵과 출처 표기

여러 컨텍스트가 같은 개념(상품, 고객)을 각자 다르게 모델링할 때, 컨텍스트끼리 어떻게 연결되는지 그린 지도를 **컨텍스트 맵**(context map)이라고 해요. 경계를 만드는 건 주로 조직이지만, 기술 차이(예: 메모리 안 모델과 관계형 DB 모델)도 경계를 만들 수 있어요.

Shared Database의 이름표는 출처 안에서도 엇갈려요. microservices.io의 개별 페이지는 "pattern"으로 분류하지만, 같은 사이트의 Database per Service 페이지에선 "anti-pattern"으로 불러요. 그래서 이 페이지는 "MSA에서 보통 피해야 할 방식"이라고 썼어요.

## 면접 질문

<details>
<summary>Q. 마이크로서비스는 무엇을 기준으로 나누나요?</summary>

**답변(30초)**
기술 계층이 아니라 업무 기능 기준으로 나눠요. 대표적으로 주문 관리·재고 관리처럼 회사가 하는 일 단위로 나누는 비즈니스 능력 방식과, DDD의 서브도메인·바운디드 컨텍스트로 나누는 방식이 있어요. 업무는 기술보다 잘 안 바뀌어서 구조가 안정적이고, 서비스 하나를 한 팀이 끝까지 맡을 수 있어요. 처음부터 완벽하긴 어려워서 조직 구조를 출발점으로 잡고 계속 다듬어요.

**꼬리질문**
- Q. 화면·로직·DB 서비스로 나누면 왜 안 되나요? → 기능 하나 바꿀 때 세 서비스가 다 바뀌어서 따로 배포하는 이점이 사라져요.
- Q. 핵심·지원·일반 서브도메인 차이는? → 핵심은 차별화 요소라 직접 공들여 만들고, 일반은 어디나 비슷하니 기성 제품을 써요.
</details>

<details>
<summary>Q. 바운디드 컨텍스트가 무엇인가요? 예를 들어 주세요.</summary>

**답변(30초)**
큰 업무 모델을 나눠서, 그 안에서는 단어 뜻이 하나로 딱 맞게 만든 경계예요. 예를 들어 쇼핑몰의 "상품"은 카탈로그에선 이름·이미지·판매가, 주문에선 상품ID·주문 당시 가격·수량, 배송에선 무게·부피예요. 이걸 클래스 하나로 통일하면 비대해지고 서로 발목을 잡아요. 그래서 컨텍스트마다 자기 모델을 두고 상품ID 같은 식별자만 공유해요.

**꼬리질문**
- Q. 유비쿼터스 언어와 관계는? → 개발자와 업무 담당자가 함께 쓰는 정확한 용어인데, 한 컨텍스트 안에서만 유효해요. 말뜻이 바뀌는 곳이 경계 후보예요.
- Q. 바운디드 컨텍스트 하나가 서비스 하나인가요? → 꼭 1:1은 아니에요. 경계를 찾는 기준이고, 실제 몇 개로 묶을지는 팀과 변경 빈도를 보고 정해요.
</details>

<details>
<summary>Q. 왜 서비스마다 DB를 따로 두나요? 단점은요?</summary>

**답변(30초)**
서비스끼리 데이터 구조로 묶이지 않게 하려고요. 내 데이터는 나만 읽고 쓰고, 남은 API로만 가져가면 내 테이블을 바꿔도 다른 서비스가 안 깨져요. 서비스마다 맞는 DB를 고를 수도 있어요. 단점은 여러 서비스에 걸친 트랜잭션과 조인이 어렵고, 운영할 DB가 늘어나는 거예요. 꼭 DB 서버를 따로 띄울 필요는 없고 스키마나 권한만 나눠도 돼요.

**꼬리질문**
- Q. 서비스 간 트랜잭션은 어떻게 하나요? → Saga로 각자 로컬 트랜잭션을 이어 가고, 실패하면 되돌리는 작업을 보내 최종 일관성을 맞춰요.
- Q. 공유 DB를 쓰면 뭐가 문제죠? → 남의 스키마 변경에 내 서비스가 깨지고(개발 시점 결합), 남의 긴 트랜잭션 잠금에 내 서비스가 멈춰요(실행 시점 결합).
</details>

<details>
<summary>Q. DB를 나누면 조인은 어떻게 하나요?</summary>

**답변(30초)**
세 가지가 있어요. 첫째 API 조합은 여러 서비스를 불러 메모리에서 합치는데, 단순하지만 호출이 늘어 느리고 한 서비스 장애에 일부가 빠져요. 둘째 데이터 복제는 주문에 상품명을 스냅숏으로 저장하거나 이벤트로 사본을 유지해서 빠르지만 값이 잠깐 옛날일 수 있어요. 셋째 CQRS는 이벤트로 조회 전용 뷰를 따로 만들어요. 화면 요구와 트래픽에 따라 골라요.

**꼬리질문**
- Q. 주문 금액은 왜 주문에 복사하나요? → 상품 가격이 나중에 바뀌어도 이미 한 주문 금액은 그대로여야 해서요. 복제가 꼼수가 아니라 업무상 맞는 모델이에요.
</details>

<details>
<summary>Q. 레거시 모놀리스를 MSA로 어떻게 옮기나요?</summary>

**답변(30초)**
한 번에 다시 짜지 않고 스트랭글러 패턴으로 하나씩 옮겨요. 앞단에 라우터를 두고, 새 서비스로 만든 기능의 요청만 그쪽으로 보내요. 이렇게 기능을 하나씩 옮기며 모놀리스를 줄여요. 작은 단위라 위험이 낮고 성과가 빨리 보여요. 대신 떼어 낼 이음매를 찾는 데 공이 들고, 두 시스템이 같이 도는 동안 임시 코드가 필요해요.

**꼬리질문**
- Q. 어떤 기능부터 옮기나요? → 다른 기능과 얽힘이 적고 경계가 분명한 기능부터요.
- Q. 데이터는요? → 옮긴 기능의 테이블은 새 서비스가 주인이 되고, 모놀리스는 그 데이터를 API로 가져가게 바꿔요.
</details>

## 서술형 연습

<details>
<summary>상황: 주문 서비스가 주문 목록을 보여 줄 때 회원 서비스의 DB 테이블을 직접 조회하고 있어요. 최근 회원팀이 컬럼 이름을 바꾸자 주문 서비스가 배포 직후 장애가 났어요. 원인과 재발 방지책을 설명해 주세요.</summary>

**상황 파악**
서비스는 나눴지만 DB는 사실상 공유하고 있어요. 회원 테이블의 주인은 회원 서비스인데, 주문 서비스가 그 구조에 직접 의존해요. 회원팀은 자기 테이블을 바꿨을 뿐인데 남의 서비스가 깨졌어요.

**원인 후보**
1. **공유 DB로 인한 개발 시점 결합**: 테이블 구조가 사실상 두 서비스 사이의 약속이 됐는데, 그 약속이 문서화도 버전 관리도 안 돼 있어요.
2. **경계를 강제하는 장치가 없음**: 주문 서비스 DB 계정이 회원 테이블 읽기 권한을 갖고 있어요.
3. 덜 보이는 위험: 주문 쪽 무거운 조회가 회원 테이블에 부하를 주거나, 반대로 회원 쪽 긴 트랜잭션 잠금에 주문이 멈출 수 있어요(실행 시점 결합).

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 회원 서비스가 회원 조회 API를 제공하고, 주문은 API로만 가져감 | 회원팀이 테이블을 바꿔도 API 계약만 지키면 됨 | 네트워크 호출이 늘어 느려지고, 회원 서비스 장애 대비가 필요 |
| B. 주문 서비스가 필요한 회원 정보(이름 등)를 이벤트로 받아 자기 쪽에 사본 유지 | 주문 조회가 빠르고 회원 서비스가 죽어도 동작 | 사본이 잠깐 옛날 값일 수 있음, 동기화 코드 필요 |
| C. 당장은 회원팀이 읽기 전용 뷰(view, 테이블을 원하는 모양으로 보여 주는 저장된 조회)를 만들어 주고 그것만 읽게 함 | 빠르게 적용 가능, 원본 테이블을 바꿔도 뷰 모양만 유지하면 됨 | 사실상 공유 DB의 변형이라, 뷰가 새 약속이 되고 잠금·부하 같은 실행 시점 결합은 그대로 남음. 근본 해결은 아님 |

**내가 고를 방법**
급한 불은 C로 끄고, 기본 방향은 A로 가요. 회원 데이터의 주인을 회원 서비스로 분명히 하고, 주문은 API 계약으로만 접근하게 해요. 그리고 DB 계정 권한을 서비스별로 나눠 남의 테이블을 아예 못 읽게 막아요. 주문 목록처럼 자주 보는 화면에서 호출이 부담되면 그 부분만 B로 사본을 둬요. 서비스별 DB라고 서버를 새로 띄울 필요는 없고, 스키마와 권한만 나눠도 돼요.

**채점 포인트**: 공유 DB(Shared Database)는 MSA에서 보통 피해야 할 방식, 개발 시점 결합(스키마 변경 영향), 실행 시점 결합(잠금), Database per Service, "남의 데이터는 API로만", API 계약, DB 권한으로 경계 강제, 데이터 복제와 최종 일관성, DB 서버를 꼭 따로 띄울 필요는 없음.
</details>

<details>
<summary>상황: 10년 된 커머스 모놀리스가 너무 커져서, 팀에서 "MSA로 처음부터 다시 짜서 한 번에 갈아타자"는 의견이 나왔어요. 어떻게 판단하겠어요?</summary>

**상황 파악**
기존 시스템은 지금도 매출을 내고 있고, 다시 짜는 동안에도 기능 요청은 계속 들어와요. 한 번에 갈아타면 새 시스템이 다 될 때까지 성과가 안 보이고, 전환 날 문제가 터지면 피해가 전체에 퍼져요.

**원인 후보(왜 한 번에 바꾸기가 위험한가)**
1. **오래 걸리고 성과가 늦음**: 몇 달~몇 년 동안 투자만 하고 결과는 마지막에야 확인돼요.
2. **움직이는 목표**: 다시 짜는 동안 기존 시스템도 바뀌어서 따라잡기가 끝나지 않아요.
3. **경계를 처음부터 잘 긋기 어려움**: 한 번에 서비스를 다 나누면 경계 실수도 한꺼번에 굳어요.
4. **조직 문제**: 팀 구조와 일하는 방식이 그대로면 새 시스템도 다시 엉켜요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 한 번에 다시 짜기 | 옛 구조에 얽매이지 않음, 공존 코드가 없음 | 성과가 늦고, 전환 위험이 한 번에 몰림 |
| B. 스트랭글러 패턴으로 하나씩 옮기기 | 위험이 작게 나뉘고 성과가 빨리 보임, 옮기며 배움 | 이음매 찾기가 어렵고, 공존용 임시 코드가 필요하며 나중에 버려야 함 |
| C. 먼저 모놀리스 안을 모듈로 정리한 뒤 B | 떼어 낼 경계가 미리 보여서 옮기기 쉬워짐 | 정리 기간만큼 분리가 늦어짐 |

**내가 고를 방법**
B를 기본으로, 얽힘이 심한 곳은 C를 섞어요. 앞단에 라우터(게이트웨이)를 두고, 배송처럼 다른 기능과 얽힘이 적고 경계가 분명한 기능부터 새 서비스로 만들어 해당 경로만 새 쪽으로 보내요. 옮긴 기능의 데이터는 새 서비스가 주인이 되게 해요. 문제가 생기면 라우팅만 되돌리면 돼서 위험도 작아요. 경계는 업무 기능과 말뜻이 바뀌는 지점을 기준으로 잡고, 팀도 그 경계에 맞춰 나눠요.

**채점 포인트**: 빅뱅 재작성의 위험(늦은 성과·움직이는 목표·전환 위험), 스트랭글러 피그, 앞단 라우터, 결합이 적은 기능부터, 이음매, 공존용 임시 코드, 데이터 소유권 이전, 조직·문화 변화, 되돌리기 쉬움.
</details>

<details>
<summary>상황: "내 주문 목록" 화면에 주문 정보와 함께 상품명, 주문한 회원 이름을 보여 줘야 해요. 주문·상품·회원 DB는 서비스별로 나뉘어 있어요. 어떻게 구현하겠어요?</summary>

**상황 파악**
모놀리스라면 세 테이블을 SQL로 조인하면 끝이지만, DB가 나뉘어 있어 조인이 안 돼요. 주문 목록은 사용자가 자주 여는 화면이라 빨라야 해요.

**원인 후보(무엇을 고려해야 하나)**
1. **데이터가 서로 다른 서비스에 있음**: 상품명은 상품 서비스, 회원 이름은 회원 서비스가 주인이에요.
2. **값의 성격이 다름**: 주문 당시 상품명·가격은 주문의 일부라 나중에 바뀌면 안 되지만, 회원 이름은 최신 값이 맞을 수도 있어요.
3. **트래픽과 장애**: 목록 하나 그릴 때마다 여러 서비스를 부르면 느려지고, 한 서비스가 죽으면 화면 일부가 비어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. API 조합: 게이트웨이나 화면용 서버가 주문 목록을 받고, 상품·회원 서비스를 불러 합침 | 항상 최신 값, 만들기 쉬움 | 호출이 늘어 느림, 한 서비스 장애에 일부가 빔 |
| B. 데이터 복제: 주문 만들 때 상품명·가격을 주문에 스냅숏으로 저장, 회원 이름은 이벤트로 받아 사본 유지 | 주문 DB만 읽어 빠르고, 다른 서비스가 죽어도 조회됨 | 사본이 잠깐 옛날 값일 수 있음, 동기화 코드 필요 |
| C. CQRS 조회 뷰: 이벤트를 모아 "내 주문 목록" 전용 테이블을 따로 만듦 | 화면에 딱 맞춘 빠른 조회 | 만들고 운영할 게 많음, 반영이 살짝 늦음 |

**내가 고를 방법**
상품명·가격은 B의 스냅숏으로 해요. 주문 당시 값이 남아야 하는 건 업무상 맞는 모델이라 고민할 필요가 없어요. 회원 이름은 처음엔 A로 회원 서비스에 회원 ID 목록을 한 번에 보내 여러 명을 묻는 방식(한 명씩 N번 부르지 않게)으로 붙이고, 회원 서비스가 응답하지 않으면 이름 칸만 비워 두고 목록은 보여 줘요. 트래픽이 커져 호출이 부담되면 B의 이벤트 사본이나 C의 조회 뷰로 옮겨요. 이때 이름이 바뀐 직후 잠깐 옛 이름이 보일 수 있다는 점은 업무 담당자와 합의해요.

**채점 포인트**: 서비스 간 SQL 조인 불가, API 조합(지연·부분 실패), 데이터 복제(스냅숏·이벤트 사본), CQRS 조회 뷰, 최종 일관성, 주문 당시 가격은 주문 컨텍스트의 데이터, 장애 시 부분 응답, 트래픽에 따른 단계적 선택.
</details>

## 필기 포인트

- 서비스 분해 기준: **비즈니스 능력**, **서브도메인**(핵심·지원·일반). 기술 계층으로 나누지 않음.
- **바운디드 컨텍스트**: DDD 전략 설계의 중심. 컨텍스트마다 자기 모델, 관계는 **컨텍스트 맵**으로.
- **유비쿼터스 언어**: 개발자와 업무 전문가가 함께 만든 정밀한 용어. 한 바운디드 컨텍스트 안에서 유효.
- **Database per Service**: 내 데이터는 나만, 남은 API로만. 전용 테이블·스키마·DB 서버 중 선택.
- 서비스별 DB 단점: 서비스 간 트랜잭션(→ Saga, 최종 일관성), 조인(→ API 조합, CQRS).
- **Shared Database**: 로컬 ACID·운영 단순 vs 개발 시점·실행 시점 결합. MSA에선 보통 피함.
- **스트랭글러 피그**: 옆에 새로 만들고 기능을 점진적으로 옮김. 앞단 라우터.
- 함정: "서비스별 DB = DB 서버를 서비스 수만큼"(X).
