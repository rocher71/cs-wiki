:::tip[한 줄 요약]
**API 게이트웨이**는 모든 외부 요청이 들어오는 **하나의 입구**로, 인증·처리율 제한·라우팅·응답 합치기를 한곳에서 처리해요. **서비스 디스커버리**는 수시로 바뀌는 서비스 주소를 **이름으로 찾게 해 주는 주소록**이고, 쿠버네티스에서는 **Service와 DNS**가 이 역할을 대신해 줘요.
:::

:::note[처음이라면 여기까지]
① 서비스가 여러 개로 쪼개지면 앱이 주소를 다 알아야 하고, 로그인 확인 같은 공통 일을 서비스마다 반복하게 돼요. 그래서 **입구를 하나(게이트웨이)** 두고 공통 일을 거기서 해요.

② 서비스 서버는 껐다 켤 때마다 주소(IP)가 바뀌어요. 그래서 "주문 서비스 어디 있어?"를 물어볼 **주소록(디스커버리)**이 필요해요.

③ 게이트웨이는 모든 요청이 지나가서, 죽으면 전부 멈춰요. 그래서 꼭 **여러 대**로 띄워요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

큰 회사 건물에 손님이 찾아온다고 해 봐요.

**API 게이트웨이는 1층 안내 데스크**예요. 손님은 층마다 돌아다니지 않고 안내 데스크로만 가요. 데스크 직원이 출입증을 확인하고(인증), 너무 자주 들락거리는 사람은 잠깐 막고(처리율 제한), "주문 문의는 5층으로"처럼 알맞은 부서로 보내요(라우팅). 손님은 건물 안이 어떻게 나뉘어 있는지 몰라도 돼요.

**서비스 디스커버리는 사내 전화번호 안내**예요. 부서는 자리를 자주 옮겨요. 그래서 "주문팀 번호"를 외워 두지 않고, 필요할 때마다 안내에 물어봐요. 부서가 이사하면 안내 목록만 고치면 돼요.

단, 실제로는 안내 데스크가 하나뿐이면 그 직원이 쓰러지는 순간 건물 출입이 다 막혀요. 그래서 실제 게이트웨이는 같은 일을 하는 여러 대를 나란히 띄워요.

## 제대로 알기

### 왜 API 게이트웨이가 필요할까?

MSA에서는 주문·회원·상품이 각자 다른 서비스예요. 게이트웨이가 없으면 이런 일이 생겨요.

- 모바일 앱이 서비스마다 주소를 따로 알아야 하고, 홈 화면 하나 그리는 데 서버를 여러 번 왕복해요.
- 서비스가 쪼개지거나 합쳐지면 앱도 바뀌어야 해요.
- "로그인한 사용자인가?" 확인 코드를 서비스마다 똑같이 넣어야 해요.

**API 게이트웨이**(API Gateway)는 모든 클라이언트가 들어오는 **단일 진입점**이에요. 바깥에서는 `api.shop.com` 하나만 보이고, 안쪽이 어떻게 나뉘었는지, 서버가 몇 대인지는 숨겨져요.

### 게이트웨이가 하는 일

| 하는 일 | 쉽게 말하면 | 예 |
|---|---|---|
| 라우팅(프록시) | 요청을 알맞은 서비스로 넘겨줌 | `/orders/**` → 주문 서비스 |
| 응답 조합 | 여러 서비스를 불러 결과를 합쳐 한 번에 돌려줌 | 홈 화면용 `/home` → 회원·주문·추천을 불러 합침 |
| 인증 | 토큰이 진짜인지, 만료됐는지 확인 | JWT 서명 검증, 실패면 401 |
| 처리율 제한 | 한 사용자가 너무 많이 부르면 잠깐 막음 | 초당 10회 넘으면 429 |
| 프로토콜 변환 | 바깥용 형식과 내부 형식을 바꿔 줌 | 바깥은 HTTP/JSON, 안쪽은 다른 프로토콜 |
| 클라이언트별 API | 앱·웹에 맞춘 응답 제공 | 앱엔 필드를 줄여서 응답 |

용어를 풀어 볼게요.

- **프록시**(proxy): 요청을 대신 받아서 뒤쪽 서버에 넘겨 주는 중간 서버. → [로드밸런서와 프록시](../../web/load-balancer-proxy/)
- **JWT**(JSON Web Token): 서버가 서명해서 준 로그인 증표. 서명을 확인하면 위조 여부를 알 수 있어요. → [쿠키·세션·JWT](../../web/cookie-session-jwt/)
- **처리율 제한**(rate limiting): 정해진 시간에 허용할 요청 수를 정해 두고 넘치면 거절하는 것. 거절할 땐 보통 **429 Too Many Requests**를 돌려줘요.

### 장점과 단점

| | 내용 |
|---|---|
| 장점 | 클라이언트가 서비스 구조·서버 위치를 몰라도 됨. 왕복 횟수가 줄어듦. 클라이언트 코드가 단순해짐. 인증 같은 공통 일을 한곳에 모음 |
| 단점 | 만들고·배포하고·관리할 부품이 하나 더 생김. 요청이 한 단계 더 거쳐서 응답이 조금 느려짐(보통 아주 작음) |
| 주의 | 모든 요청이 지나가서 **단일 장애점**(SPOF, 여기 하나가 죽으면 전체가 멈추는 곳)이자 병목이 될 수 있음 |

"게이트웨이 = 로드밸런서"는 아니에요. **로드밸런서**는 같은 서비스의 서버 여러 대에 요청을 나누는 게 핵심이고, 게이트웨이는 **어느 서비스로 보낼지** 정하고 인증·처리율 제한 같은 API 관리를 해요. 게이트웨이 안에서도 서버를 고를 때 로드밸런싱 기능을 써요.

### BFF: 화면 종류마다 게이트웨이 따로

**BFF**(Backends for Frontends, "프런트엔드를 위한 백엔드")는 게이트웨이를 하나만 두지 않고 **클라이언트 종류마다 따로** 두는 방식이에요. 웹용 BFF, 모바일 앱용 BFF, 외부 파트너용 게이트웨이처럼요.

앱 화면은 작아서 필드가 적게 필요하고, 웹은 한 화면에 더 많은 정보를 보여 줘요. 게이트웨이 하나가 둘 다 맞추려 하면 조건문이 쌓이고, 여러 팀이 한 게이트웨이를 고치느라 서로 막혀요. BFF로 나누면 앱팀은 앱 BFF만, 웹팀은 웹 BFF만 고치면 돼요.

흔히 하는 실수는 게이트웨이에 업무 로직(할인 계산 같은 것)을 넣는 거예요. 그러면 모든 팀이 게이트웨이를 고쳐야 해서 게이트웨이가 다시 모놀리스가 돼요. 게이트웨이는 **얇게**, 화면 맞춤 조합은 BFF로 빼는 게 보통이에요. → [모놀리스 vs 마이크로서비스](../monolith-vs-msa/)

### 서비스 디스커버리가 필요한 이유

컨테이너나 가상 서버는 다시 뜰 때마다 **IP 주소가 바뀌고**, 트래픽에 따라 서버 수가 자동으로 늘었다 줄었다 해요(**오토스케일링**). 그래서 "주문 서비스 주소"를 코드나 설정 파일에 고정해 둘 수 없어요.

**서비스 디스커버리**(service discovery)는 서비스 이름으로 지금 살아 있는 서버 주소를 찾는 방법이에요. 핵심 부품은 **서비스 레지스트리**(service registry)로, 서비스별 서버 목록과 주소를 담은 DB예요. 서버는 켜질 때 등록하고 꺼질 때 빠져요. Netflix **Eureka**, **Consul**, ZooKeeper, etcd가 대표적이고, 쿠버네티스와 AWS ELB는 레지스트리가 **내장**돼 있어요.

### 디스커버리 두 방식 비교

| | 클라이언트 사이드 | 서버 사이드 |
|---|---|---|
| 누가 주소를 고르나 | 호출하는 쪽이 레지스트리에서 목록을 받아 **직접** 고름 | 호출하는 쪽은 고정 주소의 **라우터**로 보내고, 라우터가 고름 |
| 호출하는 쪽이 아는 것 | 서버 목록 전체 | 라우터 주소(또는 서비스 이름) 하나 |
| 예 | Spring Cloud + Eureka, Spring Cloud LoadBalancer | 쿠버네티스 Service, AWS ELB |
| 장점 | 부품과 거치는 단계가 적음 | 호출하는 쪽 코드가 단순함. 클라우드가 기본 제공하기도 함 |
| 단점 | 호출하는 쪽이 레지스트리에 묶임. 언어·프레임워크마다 찾는 로직이 필요 | 직접 운영하면 라우터를 설치·이중화해야 함. 거치는 단계가 하나 더 |

여기서 "클라이언트"는 브라우저나 앱이 아니에요. **다른 서비스나 API 게이트웨이**처럼 호출하는 쪽 서버예요.

### 쿠버네티스에서는 Service DNS가 대신해요

쿠버네티스 위에서는 Eureka 같은 레지스트리를 따로 두지 않고 **Service 이름으로 호출**하는 경우가 흔해요. 플랫폼이 디스커버리를 해 주기 때문이에요.

1. Pod(쿠버네티스에서 컨테이너가 도는 단위)가 준비되면(Ready), 쿠버네티스가 **대신** 그 Pod를 서비스의 서버 목록(EndpointSlice)에 넣어요. Pod는 스스로 등록하지 않아요.
2. 주문 Pod가 `http://payment/pay`처럼 이름으로 부르면, 클러스터 DNS가 결제 Service의 고정 가상 주소(**ClusterIP**)를 알려 줘요.
3. 노드에 있는 **kube-proxy** 규칙이 그 요청을 결제 Pod 하나로 넘겨요. 주문 Pod는 결제 Pod 목록을 전혀 몰라요.

즉 쿠버네티스 Service는 **서버 사이드 디스커버리**예요. 자세한 동작은 → [쿠버네티스 Service와 Ingress](../../infra/k8s-service-ingress/)

### 심화: 등록 방식 — 셀프 등록 vs 3rd party 등록

| | 셀프 등록 | 3rd party 등록 |
|---|---|---|
| 누가 등록하나 | 서비스 자신. 켜질 때 등록, 주기적으로 "살아 있어요" 신호(**하트비트**), 꺼질 때 해제 | 별도 등록기가 대신 등록·해제 |
| 예 | Eureka 클라이언트 | 쿠버네티스, AWS Auto Scaling 그룹 |
| 장점 | 자기 상태를 알아서 "시작 중", "사용 가능"처럼 자세히 알릴 수 있음 | 서비스 코드가 단순함 |
| 단점 | 레지스트리에 묶임. 살아는 있는데 요청을 못 받는 상태면 스스로 빠지지 못함 | 등록기는 겉 상태(켜졌나/꺼졌나)만 앎. 헬스체크로 보완 |

쿠버네티스는 3rd party 등록이고, **readiness probe**(요청 받을 준비가 됐는지 검사)가 헬스체크 역할을 해요.

레지스트리가 죽으면 어떻게 될까요? 호출하는 쪽이 목록을 캐시해 두기 때문에 당장은 동작해요. 하지만 시간이 지나면 목록이 낡아지니 레지스트리도 **고가용성**(여러 대로 띄워 하나가 죽어도 버티게 함)으로 운영해야 해요.

### 심화: Spring Cloud Gateway 동작

Spring 진영의 대표 게이트웨이예요. 용어 세 개만 알면 돼요.

- **Route**: 게이트웨이 설정의 기본 단위. ID, 보낼 곳(URI), 조건(predicate) 묶음, 필터 묶음으로 이뤄져요. 조건이 모두 맞으면 이 route를 써요.
- **Predicate**: 요청이 이 route에 맞는지 판단하는 조건. 경로·헤더·파라미터 등 무엇이든 쓸 수 있어요.
- **Filter**: 뒤쪽 서비스로 보내기 **전과 후**에 요청·응답을 고치는 단계.

요청 하나는 "route 매칭 → pre 필터(인증, 처리율 제한) → 서비스로 전달 → post 필터 → 응답" 순으로 흘러요.

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order
          uri: lb://order-service     # lb = 서비스 이름으로 서버를 골라 줌
          predicates:
            - Path=/orders/**          # 이 경로면 이 route
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10  # 초당 10개씩 토큰 채움
                redis-rate-limiter.burstCapacity: 20  # 순간 최대 20개까지
```

- `lb://order-service`처럼 쓰면 Spring Cloud LoadBalancer가 서비스 이름을 실제 주소로 바꿔요. 살아 있는 서버가 없으면 기본으로 **503**을 돌려줘요. 이때 게이트웨이가 클라이언트 사이드 디스커버리의 "클라이언트"예요.
- **RequestRateLimiter**의 기본 구현은 Redis를 쓰는 **토큰 버킷** 방식이에요. 막히면 **429**를 돌려줘요. 누구 기준으로 셀지는 `KeyResolver`가 정하고, 기본값은 로그인 사용자 이름이에요. 키가 비어 있으면 기본으로 거절해요. Redis를 쓰는 건 게이트웨이가 여러 대여도 카운터를 **공유**하려는 게 보통 이유예요. → [Redis 실전 활용](../../redis/redis-practice/)
- 예전 자료에 나오는 Ribbon은 유지보수 모드로 빠졌고, 지금 Spring Cloud는 Spring Cloud LoadBalancer를 써요(업계 통념, 버전별로 확인 필요).

### 심화: Ingress·Gateway API와 API 게이트웨이의 차이

- **Ingress**: 클러스터 밖 HTTP 요청을 호스트·경로 기준으로 Service에 보내는 규칙. TLS 종료도 해요. 컨트롤러가 있어야 동작하고, 지금은 기능이 고정(frozen)돼서 Gateway API를 권해요.
- **Gateway API**: Ingress의 후속 표준. 헤더 조건이나 비율 나눠 보내기를 표준으로 표현할 수 있어요.
- **API 게이트웨이**: 위 같은 "어디로 보낼지" 규칙 위에 인증·처리율 제한·응답 조합·사용량 관리 같은 **API 관리 기능**을 얹은 것으로 흔히 구분해요. 실제 제품들은 둘 다 하기도 해서 경계가 흐려요.

흔한 구성은 "클라우드 로드밸런서 → Ingress/Gateway(외부 진입, TLS) → Spring Cloud Gateway 같은 앱 게이트웨이 → 각 서비스"예요. 게이트웨이는 **바깥→안** 트래픽을 맡고, 서비스끼리 주고받는 트래픽은 서비스 메시가 맡는다고 흔히 나눠요. → [분산 추적과 서비스 메시](../distributed-tracing-mesh/)

### 심화: 게이트웨이에서 인증할 때 주의점

- 게이트웨이는 JWT의 **서명, 만료 시각(exp), 발급자(iss), 대상(aud)**을 확인하고, 통과한 요청만 안으로 보내요. 허용할 서명 알고리즘은 고정해야 해요(`alg: none` 같은 공격 방지).
- RS256 같은 **비대칭 서명**이면 게이트웨이는 **공개키만** 있으면 검증할 수 있어서, 인증 서버의 비밀키를 여기저기 나눠 줄 필요가 없어요.
- 게이트웨이가 검증 후 사용자 ID를 `X-User-Id` 같은 내부 헤더로 넘기는 방식이 흔해요. 이때 **바깥에서 같은 이름의 헤더를 보내면 게이트웨이가 지우고 덮어써야** 해요. 안 그러면 누구나 남의 ID를 적어 보낼 수 있어요.
- 내부 서비스가 게이트웨이를 거치지 않고 바깥에서 직접 닿으면 위 방어가 무너져요. 네트워크 정책으로 막아야 해요.
- "이 주문이 이 사용자 것인가" 같은 **인가**는 업무 지식이 필요해서 보통 각 서비스에서 해요.

## 면접 질문

<details>
<summary>Q. API 게이트웨이가 무엇이고 왜 쓰나요?</summary>

**답변(30초)**
모든 클라이언트 요청이 들어오는 단일 진입점이에요. MSA에서 서비스가 여러 개로 나뉘면 클라이언트가 서비스 주소를 다 알아야 하고, 인증 같은 공통 로직이 서비스마다 중복돼요. 게이트웨이를 두면 클라이언트는 주소 하나만 알면 되고, 게이트웨이가 경로에 따라 알맞은 서비스로 라우팅하면서 인증, 처리율 제한, 여러 서비스 응답 조합을 한곳에서 처리해요.

**꼬리질문**
- Q. 로드밸런서와 뭐가 다른가요? → 로드밸런서는 같은 서비스 서버들에 요청을 나누는 게 핵심이고, 게이트웨이는 어느 서비스로 보낼지 정하고 API 관리 기능을 해요. 게이트웨이 내부에서도 로드밸런싱을 써요.
- Q. 단점은요? → 운영할 부품이 하나 늘고, 요청이 한 단계 더 거쳐 조금 느려지고, 모든 요청이 지나가서 단일 장애점이 될 수 있어요.
</details>

<details>
<summary>Q. 서비스 디스커버리가 왜 필요한가요?</summary>

**답변(30초)**
컨테이너 환경에서는 서버가 재시작될 때마다 IP가 바뀌고, 오토스케일링으로 서버 수도 계속 변해서 주소를 고정해 둘 수 없기 때문이에요. 그래서 서비스 레지스트리에 서비스 이름과 살아 있는 서버 주소를 등록해 두고, 호출할 때 이름으로 찾아요. Eureka나 Consul 같은 레지스트리를 따로 두기도 하고, 쿠버네티스는 이 기능이 내장돼 있어요.

**꼬리질문**
- Q. 레지스트리가 죽으면요? → 호출자가 목록을 캐시해서 당장은 동작하지만 점점 낡은 정보가 되므로, 레지스트리도 여러 대로 고가용성 있게 운영해야 해요.
</details>

<details>
<summary>Q. BFF 패턴이란 무엇이고 언제 쓰나요?</summary>

**답변(30초)**
Backends for Frontends의 줄임말로, 웹·모바일·외부 파트너처럼 클라이언트 종류마다 게이트웨이를 따로 두는 패턴이에요. 화면마다 필요한 데이터가 달라서 게이트웨이 하나로 다 맞추면 분기 코드가 쌓이고 여러 팀이 같은 게이트웨이를 고치느라 막혀요. BFF로 나누면 각 클라이언트 팀이 자기 BFF에서 필요한 만큼만 조합해 응답할 수 있어요.

**꼬리질문**
- Q. BFF의 단점은? → 보통 꼽는 건 게이트웨이가 여러 개라 운영할 게 늘고, 공통 로직이 BFF마다 중복될 수 있다는 점이에요(업계 통념). 인증 같은 공통 처리는 앞단 게이트웨이나 공통 라이브러리로 빼는 게 흔해요.
</details>

<details>
<summary>Q. 클라이언트 사이드와 서버 사이드 디스커버리의 차이는?</summary>

**답변(30초)**
누가 서버를 고르느냐의 차이예요. 클라이언트 사이드는 호출하는 쪽이 레지스트리에서 목록을 받아 직접 하나를 골라요. Eureka와 Spring Cloud LoadBalancer가 예이고, 거치는 단계가 적지만 호출하는 쪽이 레지스트리에 묶이고 언어마다 로직이 필요해요. 서버 사이드는 호출하는 쪽이 고정된 라우터로만 보내고 라우터가 골라요. 쿠버네티스 Service와 AWS ELB가 예이고, 호출자 코드는 단순하지만 라우터를 운영해야 하고 단계가 하나 늘어요.

**꼬리질문**
- Q. 여기서 "클라이언트"는 브라우저인가요? → 아니에요. 다른 서비스나 API 게이트웨이처럼 호출하는 서버예요.
</details>

<details>
<summary>Q. 쿠버네티스에서는 서비스 디스커버리를 어떻게 하나요? Eureka가 필요한가요?</summary>

**답변(30초)**
쿠버네티스는 Service와 클러스터 DNS로 디스커버리를 내장하고 있어서 Eureka가 필수는 아니에요. Pod가 Ready가 되면 쿠버네티스가 대신 Service의 서버 목록에 넣고, 호출자는 Service 이름으로 부르면 DNS가 ClusterIP를 알려 주고 kube-proxy가 Pod 하나로 넘겨요. 서버 사이드 디스커버리와 3rd party 등록을 플랫폼이 해 주는 셈이에요.

**꼬리질문**
- Q. 그래도 Eureka를 유지할 때는? → 기존 코드와 클라이언트 쪽 로드밸런싱 정책을 그대로 쓰고 싶거나, 쿠버네티스 밖 서버와 섞여 있을 때예요. 대신 운영할 부품이 하나 더 남아요.
- Q. Headless Service는? → ClusterIP 없이 DNS가 Pod IP 목록을 직접 돌려줘서, 호출자가 고르는 클라이언트 사이드에 가까워져요.
</details>

<details>
<summary>Q. Ingress와 API 게이트웨이는 같은 건가요?</summary>

**답변(30초)**
겹치지만 같다고 보진 않아요. Ingress나 Gateway API는 외부 HTTP를 호스트·경로 기준으로 Service에 보내는 쿠버네티스 표준 규칙이에요. API 게이트웨이는 그 위에 인증, 처리율 제한, 응답 조합, 사용량 관리 같은 API 관리 기능을 얹은 것으로 흔히 구분해요. 실제 제품은 둘 다 하기도 해서, 클라우드 LB, Ingress, 앱 게이트웨이를 차례로 두는 구성도 흔해요.

**꼬리질문**
- Q. 게이트웨이와 서비스 메시는? → 게이트웨이는 바깥에서 안으로 오는 트래픽, 서비스 메시는 서비스끼리 주고받는 트래픽을 주로 맡아요.
</details>

<details>
<summary>Q. 게이트웨이에서 인증하면 내부 서비스는 무엇을 믿나요?</summary>

**답변(30초)**
게이트웨이가 JWT의 서명, 만료, 발급자를 검증하고 사용자 ID를 내부 헤더로 넘기면, 서비스는 그 헤더를 믿어요. 이게 안전하려면 두 가지가 지켜져야 해요. 바깥에서 들어온 같은 이름의 헤더를 게이트웨이가 지우고 덮어써야 하고, 내부 서비스가 게이트웨이를 거치지 않고 바깥에 노출되면 안 돼요. 보안을 더 겹으로 하려면 서비스도 토큰을 다시 검증하고, 인가는 각 서비스에서 해요.

**꼬리질문**
- Q. 서비스마다 다시 검증하면 비용이 크지 않나요? → 비대칭 서명이면 공개키로 로컬에서 검증해 비용이 크지 않아요. 대신 검증 로직이 중복돼요. 보안 요구 수준에 따라 골라요.
</details>

<details>
<summary>Q. Spring Cloud Gateway에서 처리율 제한은 어떻게 하나요?</summary>

**답변(30초)**
RequestRateLimiter 필터를 route에 붙여요. 기본 구현인 RedisRateLimiter는 토큰 버킷 방식으로, replenishRate는 초당 채워지는 토큰 수, burstCapacity는 순간 최대 허용량이에요. 누구 기준으로 셀지는 KeyResolver로 정하고, 한도를 넘으면 429를 돌려줘요. Redis에 카운터를 두니까 게이트웨이를 여러 대 띄워도 같은 한도를 공유해요.

**꼬리질문**
- Q. 키를 IP로 하면 문제는? → 회사·통신사 공유 IP 뒤의 여러 사용자가 한 묶음으로 막힐 수 있어요. 로그인 사용자는 사용자 ID로 세는 게 나아요.
- Q. Redis가 죽으면? → 그때 다 통과시킬지(fail-open), 다 막을지(fail-closed)를 정해 둬야 해요. 동작은 구현·버전마다 확인이 필요해요.
</details>

## 서술형 연습

<details>
<summary>상황: MSA로 서비스 8개를 운영하는데, 모든 서비스가 각자 JWT 검증 코드를 복사해 갖고 있어요. 검증 규칙을 하나 바꾸려면 8개를 다 고쳐 배포해야 해요. 어떻게 개선하겠어요?</summary>

**상황 파악**
인증이라는 공통 관심사가 서비스마다 흩어져 있어요. 규칙 하나 바꾸는 데 8번 배포가 필요하고, 한 서비스라도 깜빡하면 그 서비스만 약한 검증으로 남아 보안 구멍이 돼요.

**원인 후보**
1. 들어오는 입구가 하나로 정리되지 않아 각 서비스가 직접 외부 요청을 받아요.
2. 검증 코드를 공통 라이브러리 없이 복사해서, 버전이 서비스마다 달라요.
3. 서비스가 외부에 직접 노출돼 있어서 각자 검증할 수밖에 없는 구조예요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 공통 인증 라이브러리로 통일 | 구조 변경이 작음. 서비스마다 스스로 검증해 보안이 겹으로 유지됨 | 규칙 바꿀 때 여전히 8개 서비스가 라이브러리를 올려 배포해야 함. 언어가 다르면 여러 벌 필요 |
| B. 게이트웨이에서 JWT 검증, 서비스는 내부 헤더(`X-User-Id`)만 읽음 | 검증 규칙을 한곳에서 바꿈. 서비스 코드가 단순해짐 | 게이트웨이가 뚫리거나 우회되면 끝. 외부에서 보낸 같은 헤더를 반드시 지워야 함 |
| C. B + 서비스는 공개키로 가볍게 재검증(제로 트러스트) | 게이트웨이 우회·헤더 위조에도 버팀 | 검증이 두 번이라 중복 비용, 서비스에도 검증 코드가 남음 |

**내가 고를 방법**
B를 기본으로 하되 안전장치를 같이 걸어요. 게이트웨이에서 서명·만료·발급자·대상을 검증하고 허용 알고리즘을 고정해요. 검증 후 사용자 ID를 내부 헤더로 넘길 때, **바깥에서 들어온 같은 이름의 헤더는 먼저 지우고 덮어써요.** 그리고 네트워크 정책으로 서비스가 게이트웨이를 거치지 않고는 바깥에서 닿지 않게 막아요. 결제처럼 민감한 서비스는 C처럼 공개키로 토큰을 한 번 더 확인해요. "이 주문이 이 사용자 것인가" 같은 인가는 업무 지식이 필요하니 계속 각 서비스에서 해요.

**채점 포인트**: 공통 관심사를 게이트웨이로 모으기, JWT 검증 항목(서명·exp·iss·aud, 알고리즘 고정), 내부 헤더 위조 방지(외부 헤더 제거·덮어쓰기), 게이트웨이 우회 차단(네트워크 정책), 인증과 인가 구분(인가는 서비스), 중복 검증 트레이드오프, 비대칭 서명이면 공개키만 필요.
</details>

<details>
<summary>상황: 게이트웨이를 한 대로 운영하다가 그 서버가 죽자 모든 서비스가 동시에 접속 불가가 됐어요. 어떻게 재발을 막겠어요?</summary>

**상황 파악**
뒤쪽 서비스는 멀쩡했는데 입구 하나가 막혀 전체 장애가 났어요. 게이트웨이가 **단일 장애점**이었던 거예요. 모든 요청이 지나가니 병목이 될 위험도 같이 있어요.

**원인 후보**
1. 게이트웨이가 한 대뿐이라 대신 받아 줄 서버가 없었어요.
2. 게이트웨이가 상태(세션, 처리율 카운터)를 자기 메모리에 들고 있어서 여러 대로 늘리기 어려웠을 수 있어요.
3. 게이트웨이에 무거운 로직이 들어가 있거나, 느린 뒤쪽 서비스 하나 때문에 게이트웨이의 연결·스레드가 다 묶였을 수 있어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 게이트웨이를 여러 대로 띄우고 앞에 L4 로드밸런서(쿠버네티스면 replicas 2 이상 + 오토스케일링) | 한 대가 죽어도 나머지가 받음. 트래픽 늘면 대수 증가 | 서버 비용. 상태를 공유해야 함 |
| B. 게이트웨이를 무상태로: 세션·처리율 카운터는 Redis 같은 외부 저장소로 | 아무 대나 요청을 받을 수 있어 확장·교체가 쉬움 | Redis가 새 의존성이 됨. Redis 장애 시 통과/차단 정책을 정해야 함 |
| C. 게이트웨이를 얇게 + 뒤쪽 호출에 타임아웃·서킷 브레이커, 클라이언트별로 BFF 분리 | 느린 서비스 하나가 게이트웨이를 마비시키지 못함. 장애 범위가 클라이언트별로 좁아짐 | 설정·운영할 게 늘어남. 게이트웨이가 여러 개면 관리 부담 |

**내가 고를 방법**
A와 B를 함께 해요. 둘은 짝이에요. 무상태가 돼야 여러 대로 늘리는 게 의미가 있어요. 게이트웨이를 최소 두 대 이상, 가능하면 서로 다른 노드·가용 영역에 띄우고 오토스케일링을 걸어요. 처리율 카운터는 Redis로 옮겨 모든 게이트웨이가 같은 한도를 보게 해요. 이어서 C로 게이트웨이에 들어간 업무 로직을 빼고, 뒤쪽 호출마다 타임아웃과 서킷 브레이커를 걸어요. 배포할 때도 한 대씩 교체하는 무중단 배포로 바꿔요. 모니터링으로는 게이트웨이별 응답 시간과 5xx 비율, 대수 대비 CPU를 봐요.

**채점 포인트**: 단일 장애점(SPOF) 진단, 다중 인스턴스 + 앞단 로드밸런서, 오토스케일링, 무상태화(외부 저장소로 상태 이동), Redis 장애 시 정책, 게이트웨이에 업무 로직 금지, 타임아웃·서킷 브레이커, BFF로 장애 범위 축소, 무중단 배포, 모니터링.
</details>

<details>
<summary>상황: 모바일 앱과 웹이 같은 API를 쓰는데, 앱은 필드 몇 개만 필요하고 웹은 훨씬 많은 정보를 한 화면에 보여 줘요. API에 옵션 파라미터가 계속 늘고, 앱은 홈 화면 하나에 API를 여러 번 불러 느려요. 어떻게 하겠어요?</summary>

**상황 파악**
클라이언트마다 필요한 데이터 모양이 다른데 API는 하나라, 양쪽 요구를 다 맞추느라 API가 복잡해졌어요. 앱은 모바일 네트워크에서 여러 번 왕복하니 더 느려요.

**원인 후보**
1. 범용 API 하나로 모든 클라이언트를 맞추려 해요.
2. 화면 하나에 필요한 데이터가 여러 서비스에 흩어져 있는데, 합치는 일을 클라이언트가 해요.
3. 앱팀과 웹팀이 같은 API를 고치느라 서로 기다려요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 게이트웨이 하나에 응답 조합 기능 추가(`/home`이 여러 서비스를 불러 합침) | 왕복 횟수가 줄어듦. 부품이 늘지 않음 | 게이트웨이에 클라이언트별 분기가 쌓여 복잡해지고, 여러 팀이 게이트웨이를 고치느라 병목 |
| B. BFF: 앱용 BFF와 웹용 BFF를 따로 둠 | 각 팀이 자기 화면에 딱 맞는 API를 독립적으로 바꿈. 앱 BFF는 필요한 필드만 줌 | 운영할 게이트웨이가 늘고, 공통 로직이 BFF마다 중복될 수 있음(업계 통념) |
| C. 클라이언트가 원하는 필드를 쿼리로 고르는 방식(GraphQL 같은 것) | API 하나로 다양한 모양 지원 | 새 기술 도입 비용, 무거운 쿼리 제어가 필요 |

**내가 고를 방법**
클라이언트 팀이 나뉘어 있고 화면 요구가 계속 갈라질 거라면 B를 골라요. 앱 BFF는 홈 화면용 API 하나에서 회원·주문·추천 서비스를 **병렬로** 불러 앱에 필요한 필드만 합쳐 줘요. 이때 한 서비스가 느려 전체 응답이 끌려가지 않게, 호출마다 타임아웃을 걸고 추천처럼 없어도 되는 데이터는 빈 값으로 대체해 부분 응답을 줘요. 인증·처리율 제한 같은 공통 일은 BFF 앞의 공통 게이트웨이에 두고, BFF에는 화면 조합만 둬요. 업무 로직은 계속 각 서비스에 둬요. 팀이 하나뿐이고 화면 차이가 작다면 A로 시작해도 충분해요.

**채점 포인트**: 클라이언트별 요구 차이 진단, 왕복 횟수(모바일 지연), 응답 조합, BFF 정의와 팀 독립성, BFF 단점(운영 증가·중복), 병렬 호출·타임아웃·부분 응답, 공통 기능은 앞단 게이트웨이, BFF에 업무 로직 금지, 팀 규모에 따른 선택.
</details>

## 필기 포인트

- API 게이트웨이 = **단일 진입점**. 라우팅, 응답 조합, 인증, 처리율 제한, 프로토콜 변환.
- 단점: 부품 하나 추가, 네트워크 단계 추가. 단일 장애점 → 다중 인스턴스·무상태로 대응.
- BFF = 클라이언트 종류마다 게이트웨이를 따로.
- 서비스 레지스트리 예: Eureka, Consul, ZooKeeper, etcd. 쿠버네티스·AWS ELB는 내장.
- 클라이언트 사이드(호출자가 직접 고름, Eureka) vs 서버 사이드(라우터가 고름, 쿠버네티스 Service·AWS ELB).
- 셀프 등록(서비스가 직접, 하트비트) vs 3rd party 등록(등록기가 대신, 쿠버네티스).
- 처리율 제한 초과 = **429**. Spring Cloud Gateway `lb://`에서 서버 못 찾으면 기본 **503**.
- 함정: "디스커버리의 클라이언트 = 브라우저"(X), "쿠버네티스에도 Eureka 필수"(X), "게이트웨이 = 로드밸런서"(X).
