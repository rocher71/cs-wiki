:::tip[한 줄 요약]
무중단 배포 중에는 **옛 버전 앱과 새 버전 앱이 같은 DB를 동시에** 써요. 그래서 컬럼 이름 변경·삭제 같은 스키마 변경은 한 번에 하지 않고 **expand(새 것 추가) → migrate(앱을 새 것으로 옮김) → contract(옛 것 제거)** 순서로 여러 번의 배포에 나눠요. 그리고 ALTER 자체가 빨라도 **메타데이터 락**에 줄을 서면 서비스 전체가 멈출 수 있어서 `lock_wait_timeout`을 짧게 걸어요.
:::

:::note[처음이라면 여기까지]
① 서버를 끄지 않고 배포하면, 잠깐 동안 옛 앱과 새 앱이 **같은 DB**를 함께 써요. 그래서 컬럼 이름을 확 바꾸면 아직 떠 있는 옛 앱이 바로 에러가 나요.

② 해결책은 "새 컬럼을 먼저 **추가**하고, 앱을 새 컬럼으로 **옮기고**, 아무도 안 쓰게 된 옛 컬럼을 **나중에 지우는**" 것이에요. 이걸 **expand-contract**라고 불러요.

③ ALTER 문이 0.001초짜리여도, 앞에 오래 열린 트랜잭션이 있으면 ALTER가 기다리고, 그 뒤 평범한 조회까지 전부 줄을 서요. 그래서 "기다리는 시간 상한"을 짧게 걸어요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
DB 기능은 **MySQL 8.4 공식 문서(InnoDB)** 기준이에요. 실험은 노트북에 띄운 MySQL 9.x로 한 번 재 본 예시라서, 숫자 자체보다 **"행 수가 늘면 어떻게 변하나"라는 비례 관계**만 보면 돼요. 마이그레이션 도구는 Flyway·Spring Boot 공식 문서를 봤어요(2026-11 조회).
</Aside>

## 쉽게 이해하기

**영업 중인 가게의 간판을 바꾸는 상황**이라고 해 봐요. 가게 이름이 "김밥천국"에서 "김밥나라"로 바뀌어요.

옛 간판을 밤사이 떼고 새 간판을 달면 어떨까요? 옛 이름으로 적힌 배달앱 주소, 단골 손님의 기억, 전단지가 아직 남아 있어요. 그 사람들은 "가게가 없어졌네?" 하고 돌아가요.

그래서 똑똑한 가게는 이렇게 해요. ① 새 간판을 **옛 간판 옆에 함께** 달아요. ② 영수증·전단지에 두 이름을 같이 적어요. ③ 배달앱·지도 정보를 하나씩 새 이름으로 고쳐요. ④ 이제 아무도 옛 이름으로 찾아오지 않는 걸 확인한 뒤에야 **옛 간판을 떼요.**

DB도 똑같아요. 옛 앱(옛 이름으로 찾아오는 손님)이 남아 있는 동안은 옛 컬럼을 없애면 안 돼요. 새 것을 먼저 **넓혀서(expand)** 함께 두고, 다 옮긴 뒤에 **줄여요(contract).**

단, 실제로는 간판을 다는 작업(ALTER) 자체도 문제가 될 수 있어요. 공사하는 동안 잠깐 가게 문을 막아야 하는데, 안에 오래 앉아 있는 손님 한 명 때문에 공사가 시작을 못 하고, 그 사이 밖에 손님 줄이 길게 늘어설 수 있어요. 뒤에 나올 **메타데이터 락** 이야기예요.

## 제대로 알기

### 왜 필요한가: 두 버전이 동시에 돈다

**무중단 배포**(서비스를 멈추지 않고 새 버전으로 바꾸는 배포)는 보통 서버를 한 대씩 바꾸는 **롤링 배포**나, 새 환경을 옆에 띄우고 전환하는 **블루그린 배포**로 해요. → [무중단 배포](../zero-downtime-deploy/)

어느 방식이든 **잠깐은 옛 버전 앱과 새 버전 앱이 같은 DB를 함께** 써요. 그리고 배포가 잘못되면 옛 버전으로 **롤백**(이전 버전으로 되돌리기)할 수도 있어야 해요.

그래서 스키마 변경은 이 조건을 지켜야 해요.

- **옛 앱도, 새 앱도 깨지지 않을 것.** 컬럼을 바로 RENAME·DROP 하면 아직 떠 있는 옛 앱의 쿼리가 즉시 에러가 나요.
- **앱을 되돌려도 DB와 맞을 것.** DB는 보통 앱처럼 쉽게 되돌릴 수 없어요.

여기서 많이 하는 오해가 있어요. MySQL 8.4에서 `RENAME COLUMN`은 순식간에 끝나는 INSTANT 작업이에요. 하지만 **DB가 무중단이라고 앱이 무중단인 건 아니에요.** 이름이 바뀐 순간 옛 앱이 옛 이름으로 보낸 쿼리는 실패해요. 무중단은 DB 기능이 아니라 **앱 배포 순서**의 문제예요.

### expand-contract: 넓혔다가 줄이기

**병행 변경**(Parallel Change)은 Danilo Sato가 2014년 Martin Fowler의 블로그(bliki)에 정리한 패턴이고, 다른 이름이 **expand and contract**예요. 세 단계로 나눠요.

| 단계 | 하는 일 | 특징 |
|---|---|---|
| **expand**(넓히기) | 옛 방식과 새 방식을 **둘 다** 지원하게 만든다 | 아무것도 깨지지 않음 |
| **migrate**(옮기기) | 쓰는 쪽을 하나씩 새 방식으로 옮긴다 | 보통 가장 오래 걸림, 옛·새가 함께 있는 전환기 |
| **contract**(줄이기) | 옛 방식을 아무도 안 쓰면 제거한다 | 되돌리기 어려운 마지막 단계 |

핵심은 **한 번의 배포가 아니라 여러 번의 배포**(보통 3~4회)로 쪼갠다는 점이에요. 각 단계가 **바로 앞 버전과 호환**되니까, 어느 시점에 배포를 되돌려도 서비스가 깨지지 않아요.

### 컬럼 이름 변경 6단계 (`name` → `full_name`)

업계에서 흔히 쓰는 순서예요. 위 그림과 같이 보면 돼요.

| # | 작업 | DB 컬럼 | 앱 쓰기 | 앱 읽기 | 구분 |
|---|---|---|---|---|---|
| 1 | `full_name` 컬럼 추가(NULL 허용) | name, full_name | name | name | expand (DDL 배포) |
| 2 | 앱 v2: **이중 쓰기** | name, full_name | 둘 다 | name | migrate |
| 3 | **백필**: 옛 행을 작은 배치로 채움 | name, full_name | 둘 다 | name | migrate |
| 4 | 앱 v3: **읽기 전환** | name, full_name | 둘 다 | full_name | migrate |
| 5 | 앱 v4: 옛 컬럼 쓰기 중단 | name, full_name | full_name | full_name | migrate (롤백 경계) |
| 6 | `name` 컬럼 삭제 | full_name | full_name | full_name | contract (DDL 배포) |

용어를 풀어 볼게요.

- **이중 쓰기**(dual write): 저장할 때 옛 컬럼과 새 컬럼에 같은 값을 둘 다 넣는 것.
- **백필**(backfill): 새 컬럼이 생기기 전에 있던 옛 행들의 빈 칸을 채워 넣는 작업.

각 단계에서 왜 안전한지 짚어 볼게요.

- **1단계**에서 NULL 허용으로 추가하니 옛 앱의 INSERT가 실패하지 않아요.
- **3단계** 백필은 옛 앱 v1이 모두 내려간 뒤(이제 모든 쓰기가 full_name도 채울 때) 시작해요. 한 방에 하지 않고 PK 범위로 1,000~5,000행씩 나눠요(아래 SQL). 한 번에 전체를 UPDATE하면 트랜잭션이 길어져서 락을 오래 쥐고, 복제 서버가 늦게 따라오고, 다음 DDL이 그 트랜잭션 때문에 기다리게 돼요.
- **4단계**까지는 옛 컬럼도 계속 최신으로 쓰이고 있어요. 문제가 생기면 이 배포만 되돌리면 돼요.
- **5단계**부터는 옛 컬럼이 갱신되지 않아요. 이때 name을 읽는 v2 이하로 되돌리면 옛 컬럼이 낡은 값을 보여 줘요. 그래서 여기가 **롤백 경계**예요. 충분히 지켜본 뒤 넘어가요.
- **6단계**는 옛 버전 앱이 **하나도 안 떠 있고** 안정된 걸 확인한 뒤에 해요.

```sql
-- 3단계 백필: id 범위를 조금씩 옮겨 가며 반복 실행
UPDATE users
SET full_name = name
WHERE id BETWEEN 1 AND 5000
  AND full_name IS NULL;  -- 아직 안 채운 행만
```

같은 원리가 다른 변경에도 쓰여요.

- **컬럼 삭제만** 할 때: 먼저 코드에서 그 컬럼 사용을 없애서 배포 → 그다음 DROP. 순서가 반대면 옛 앱이 에러가 나요.
- **NOT NULL 컬럼 추가**: DEFAULT를 주거나, NULL 허용으로 추가 → 백필 → 앱 전환 → 마지막에 NOT NULL 제약 추가.

### DDL은 세 가지 방식으로 돈다 (MySQL InnoDB)

**DDL**(Data Definition Language)은 테이블 구조를 바꾸는 SQL이에요(`CREATE`, `ALTER`, `DROP`). MySQL InnoDB의 **온라인 DDL**은 ALTER를 세 가지 **알고리즘**(처리 방식) 중 하나로 실행해요.

| 알고리즘 | 하는 일 | 테이블 다시 만들기 | 작업 중 쓰기(DML) |
|---|---|---|---|
| **INSTANT** | 테이블 정보(메타데이터)만 고침 | 안 함 | 가능 |
| **INPLACE** | 엔진 안에서 처리, 경우에 따라 재빌드 | 경우에 따라 | 대부분 가능 |
| **COPY** | 새 테이블을 만들어 행을 전부 복사 | 함 | **불가** |

**DML**(Data Manipulation Language)은 데이터를 다루는 SQL(`SELECT`, `INSERT`, `UPDATE`, `DELETE`)이에요. COPY는 복사하는 동안 쓰기를 막아서, 큰 테이블이면 그 시간만큼 서비스가 멈춰요.

작업별로 어떤 방식이 되는지는 MySQL 8.4 문서 기준으로 이래요("조건부"는 제약이 있다는 뜻).

| 작업 | INSTANT | INPLACE | 재빌드 | 작업 중 쓰기 |
|---|---|---|---|---|
| 컬럼 추가 | 가능(조건부) | 가능 | 안 함(조건부) | 가능(조건부) |
| 컬럼 삭제 | 가능(조건부) | 가능 | 함 | 가능 |
| 컬럼 이름 변경 | 가능(조건부) | 가능 | 안 함 | 가능(조건부) |
| 컬럼 순서 변경 | 불가 | 가능 | 함 | 가능 |
| 컬럼 타입 변경 | 불가 | 불가 | 함 | **불가** |
| VARCHAR 길이 늘리기 | 불가 | 가능 | 안 함 | 가능 |
| 보조 인덱스 추가 | 불가 | 가능 | 안 함 | 가능 |

"재빌드" 열은 INPLACE로 실행할 때 기준이에요. INSTANT로 실행되면 재빌드하지 않아요.

표에서 가져갈 것은 두 가지예요.

- 컬럼 추가·삭제·이름 변경은 대부분 **INSTANT로 거의 즉시** 끝나요.
- **컬럼 타입 변경**(예: INT → BIGINT)은 COPY만 돼요. 큰 테이블이면 쓰기가 오래 막혀요.

### 실험: INSTANT는 행 수와 무관, COPY는 행 수에 비례

노트북에서 회원 테이블(id, email, age, created_at)을 10만 행, 100만 행으로 만들어 한 번 재 봤어요.

| 작업 | 10만 행 | 100만 행 |
|---|---|---|
| 컬럼 추가 (INSTANT) | 약 1.3ms | 약 3.5ms |
| 컬럼 이름 변경 (INSTANT) | 약 1.0ms | - |
| 컬럼 삭제 (INSTANT) | 약 2.1ms | - |
| 타입 변경 (COPY) | 약 0.26초 | 약 0.96초 |

- **INSTANT**는 행이 10배가 돼도 몇 ms 그대로예요. 테이블 정보만 고치니까요.
- **COPY**는 행이 10배가 되니 시간도 몇 배로 늘었어요. 행을 전부 복사하니까 **행 수에 비례**해요.
- 노트북의 작은 테이블이라 1초 안에 끝났지만, 운영 테이블이 수억 행·수백 GB면 같은 비례로 **분~시간 단위**가 되고, COPY는 그동안 쓰기를 막아요.

### 함정: 1ms짜리 ALTER가 서비스를 11초 멈춘다 (메타데이터 락)

**메타데이터 락**(MDL, Metadata Lock)은 "이 테이블 구조를 지금 누가 쓰고 있다"는 표시예요. 평범한 SELECT·INSERT도 실행되는 동안, 그리고 **그 트랜잭션이 끝날 때까지** 공유 MDL을 쥐고 있어요. ALTER는 마지막에 테이블 정의를 바꿔 끼울 때 아주 잠깐 **배타 MDL**(혼자만 쓰는 락)이 필요해요.

문제는 MySQL의 줄서기 규칙이에요. **배타 MDL을 기다리는 요청이 있으면, 그 뒤에 온 평범한 쿼리도 함께 기다려요.** 그래서 이런 일이 생겨요.

1. 세션 A가 트랜잭션을 열고 조회한 뒤 **커밋을 안 하고** 있어요(공유 MDL 보유).
2. 세션 B가 INSTANT ALTER를 보내요. 배타 MDL이 필요해서 A 뒤에서 기다려요.
3. 세션 C(단건 SELECT), D(INSERT)가 와요. B 뒤에서 기다려요.
4. 상태를 보면 B, C, D 모두 `Waiting for table metadata lock`이에요.

실험에서는 A가 약 12초 동안 트랜잭션을 열어 두게 했어요. 결과는 이랬어요.

| 세션 | 원래 걸리는 시간 | 실제 걸린 시간 |
|---|---|---|
| B: ALTER (INSTANT) | 약 1ms | **약 11초** |
| C: PK로 한 행 SELECT | 거의 즉시 | **약 10초** |
| D: INSERT | 거의 즉시 | **약 10초** |

A가 커밋하자마자 전부 한꺼번에 풀렸어요. 운영이라면 이 10초 동안 이 테이블을 쓰는 API 요청이 전부 쌓이고, **커넥션 풀**(DB 연결을 미리 만들어 두고 돌려 쓰는 묶음)이 바닥나서 다른 API까지 멈출 수 있어요. → [커넥션 풀](../../db/connection-pool-query/)

"INSTANT니까 안전하다", "온라인 DDL이니까 락이 없다"는 둘 다 틀려요. 온라인 DDL의 `LOCK=NONE`은 "작업 중 DML을 허용한다"는 뜻이지 MDL이 없다는 뜻이 아니에요.

### 대책: 기다리는 시간에 상한 걸기

`lock_wait_timeout`은 MDL을 얼마나 기다릴지 정하는 설정인데, 기본값이 **31536000초, 즉 1년**이에요. 즉 기본 상태에선 ALTER가 사실상 끝없이 기다리고, 그동안 뒤 쿼리도 계속 막혀요.

그래서 DDL을 실행하는 세션에만 짧게 걸어요.

```sql
-- 이 세션(DDL 실행용)에서만 2초까지만 기다림
SET SESSION lock_wait_timeout = 2;
ALTER TABLE member ADD COLUMN x INT NULL, ALGORITHM=INSTANT;
-- 2초 안에 락을 못 얻으면 ERROR 1205 (Lock wait timeout exceeded)
-- ALTER만 포기하고, 줄 서 있던 서비스 쿼리는 바로 진행됨 → 잠시 뒤 재시도
```

실험에서도 같은 상황에 2초를 걸었더니 ALTER만 2초 뒤 포기했고 서비스 쿼리는 영향이 없었어요. 함께 쓰는 실무 습관은 이래요(업계 관행).

- 배포 전에 `information_schema.innodb_trx`나 `SHOW PROCESSLIST`로 **오래 열린 트랜잭션**이 있는지 확인해요.
- 트래픽이 적은 시간에 실행하고, 실패하면 재시도해요.
- 커밋 안 한 DB 콘솔 세션, 오래 도는 배치를 정리해요.

락 자체가 처음이라면 → [DB 락](../../db/locks/), [트랜잭션과 ACID](../../db/transaction-acid/)

### 마이그레이션 도구: Flyway로 버전 관리하기

**마이그레이션**(migration)은 "DB 스키마를 바꾸는 SQL 한 묶음"이에요. 사람이 손으로 서버마다 ALTER를 치면 어디에 뭘 적용했는지 헷갈려서, 코드처럼 버전을 붙여 관리해요. 대표 도구가 **Flyway**예요.

- 각 마이그레이션은 **버전·설명·체크섬**을 가지고, 버전 순서대로 **정확히 한 번** 적용돼요.
- 적용 기록은 DB 안의 `flyway_schema_history` 테이블에 남아요.
- 파일 이름은 `V<버전>__<이름>.sql` 꼴이에요(밑줄 2개). 예: `V1__init.sql`, `V2_1__add_full_name.sql`.

```text
src/main/resources/db/migration/
├── V1__init.sql
├── V2__add_full_name.sql      -- 1단계: ADD COLUMN full_name
└── V3__drop_name.sql          -- 6단계: 옛 앱이 다 사라진 뒤 별도 배포로
```

Spring Boot에서는 Flyway를 의존성에 넣으면 **앱이 시작할 때 자동으로** 마이그레이션이 실행돼요. 기본 위치는 `classpath:db/migration`이고, MySQL이면 `flyway-mysql` 모듈도 필요해요.

**체크섬**(checksum)은 파일 내용으로 계산한 지문 같은 값이에요. 이미 적용된 파일을 고치면 저장된 지문과 달라져서 다음 실행 때 검증(validate)이 실패해요. 원칙은 **적용된 파일은 고치지 말고 새 버전 파일을 추가하기**예요.

비슷한 도구로 **Liquibase**도 있어요. 변경을 changeset 단위(XML/YAML/SQL 등)로 관리해요.

### 심화: INSTANT의 제약과 VARCHAR 경계

- **INSTANT 컬럼 추가가 안 되는 경우**: `ROW_FORMAT=COMPRESSED` 테이블, FULLTEXT 인덱스가 있는 테이블, 임시 테이블. 같은 ALTER 안에 INSTANT가 안 되는 작업을 섞어도 안 돼요.
- **행 버전 한도**: INSTANT로 컬럼을 추가·삭제할 때마다 테이블의 행 버전이 하나씩 늘어요(`INFORMATION_SCHEMA.INNODB_TABLES.TOTAL_ROW_VERSIONS`). 한도는 64개(MySQL 9.1.0부터 255개)이고, 닿으면 INSTANT가 에러가 나서 재빌드해야 해요. 재빌드나 `OPTIMIZE TABLE`을 하면 0으로 돌아가요.
- **INPLACE로 컬럼 추가**하면 테이블이 재빌드돼요. AUTO_INCREMENT 컬럼 추가는 작업 중 쓰기가 막혀요.
- **외래키로 참조되는 컬럼 이름 변경**은 INPLACE만 돼요.
- **VARCHAR 길이의 함정**: 값 길이를 0~255바이트면 1바이트, 256바이트 이상이면 2바이트로 저장해요. 그래서 255바이트 이하 → 256바이트 이상으로 넘어가는 변경은 INPLACE가 안 되고 COPY가 필요해요. 줄이는 것도 INPLACE가 안 돼요. 바이트 수는 문자셋에 달려 있어서, utf8mb4(글자당 최대 4바이트)면 `VARCHAR(63)`=252바이트, `VARCHAR(64)`=256바이트예요. 실험에서도 63 → 64는 INPLACE가 거부됐고, 이미 2바이트 구간인 100 → 200 → 300은 INPLACE로 됐어요.

### 심화: ALGORITHM·LOCK을 명시하는 안전장치

ALTER에 `ALGORITHM`과 `LOCK`을 적어 두면, 그 조건으로 못 할 때 **실행하지 않고 바로 에러**를 내요. "모르고 COPY로 돌아서 쓰기가 막히는" 사고를 미리 막는 장치예요.

| LOCK 값 | 작업 중 허용 |
|---|---|
| NONE | 조회 + 쓰기 |
| SHARED | 조회만 |
| EXCLUSIVE | 둘 다 막음 |
| DEFAULT | 가능한 최대 동시성(생략과 같음) |

```sql
-- 타입 변경을 INPLACE로 시도 → 실행 대신 즉시 에러
ALTER TABLE member MODIFY age BIGINT, ALGORITHM=INPLACE;
-- ERROR 1846: Cannot change column type INPLACE. Try ALGORITHM=COPY.

-- COPY인데 쓰기를 허용하라고 하면 → 역시 즉시 에러
ALTER TABLE member MODIFY age BIGINT, ALGORITHM=COPY, LOCK=NONE;
-- COPY algorithm requires a lock. Try LOCK=SHARED.
```

### 심화: 온라인 DDL의 3단계와 그 밖의 한계

MySQL 문서는 온라인 DDL을 세 단계로 설명해요.

1. **초기화**: 공유(업그레이드 가능한) MDL을 잡아요.
2. **실행**: 필요하면 잠깐 배타 MDL을 잡아요.
3. **커밋**: 테이블 정의를 바꿔 끼울 때 **반드시 배타 MDL로 올려요**(짧게).

그래서 어떤 알고리즘이든 앞에 긴 트랜잭션이 있으면 막혀요. 보조 인덱스를 만드는 동안에도 읽기·쓰기는 되지만, 그 테이블을 쓰던 트랜잭션이 다 끝나야 문장이 끝나요.

그 밖의 한계도 있어요.

- **복제 지연**: 소스 DB에서 긴 DDL이 끝난 뒤 **레플리카**(복제본 DB)에서 다시 실행돼요. 그동안의 변경은 레플리카 DDL이 끝나야 반영돼요.
- 온라인 DDL에는 **일시정지·속도 조절 기능이 없어요.** 실패하면 되돌리는 비용도 클 수 있어요.
- `ON ... CASCADE`, `ON ... SET NULL` 외래키가 있으면 `LOCK=NONE`이 안 돼요.

그래서 큰 테이블의 타입 변경처럼 COPY가 필요한 작업에는 **gh-ost**, **pt-online-schema-change** 같은 외부 도구를 쓰는 경우가 많아요(그림자 테이블에 복사하면서 변경분을 따라가다가 마지막에 테이블을 바꿔 끼우는 방식).

### 심화: 롤백은 어떻게? Flyway undo와 roll-forward

- Flyway에는 **undo 마이그레이션**(`U` 접두사 파일로 같은 버전의 V를 되돌림)이 있지만 **유료 에디션 기능**이에요. 반복 마이그레이션(`R__`)은 undo가 없어요.
- 이미 적용된 파일을 고쳐서 체크섬 에러가 났다면: 실수면 파일을 원래대로 되돌리고, 의도한 변경이면 `repair` 명령으로 기록을 갱신해요.
- 실무에서는 undo 대신 **되돌리는 내용을 담은 새 V 파일을 추가**(roll-forward, 앞으로 고쳐 나가기)하고, 애초에 **expand-contract로 롤백이 필요 없게** 설계하는 경우가 많아요.
- Liquibase는 addColumn·renameColumn 같은 변경은 rollback을 자동으로 만들 수 있지만, dropColumn·dropTable·데이터 insert·직접 쓴 SQL은 rollback을 직접 적어야 해요. 지운 데이터는 자동으로 되살릴 수 없으니까요.

## 면접 질문

<details>
<summary>Q. 무중단 배포를 할 때 DB 스키마 변경이 왜 문제가 되나요?</summary>

**답변(30초)**
배포하는 동안 옛 버전 앱과 새 버전 앱이 같은 DB를 함께 쓰기 때문이에요. 롤링 배포든 블루그린이든 잠깐은 두 버전이 공존하고, 롤백할 수도 있어야 해요. 그래서 컬럼을 바로 RENAME이나 DROP 하면 아직 떠 있는 옛 앱의 쿼리가 즉시 실패해요. 스키마 변경은 옛 코드와 새 코드 모두와 호환되는 형태로, 여러 번의 배포에 나눠서 해야 해요.

**꼬리질문**
- Q. MySQL에서 RENAME COLUMN은 INSTANT라 즉시 끝나는데 괜찮지 않나요? → DB는 무중단이어도 옛 앱이 옛 이름으로 쿼리하는 순간 에러예요. 무중단은 DB 기능이 아니라 배포 순서의 문제예요.
- Q. 컬럼 삭제는 어떤 순서로 하나요? → 먼저 코드에서 그 컬럼 사용을 없애 배포하고, 옛 앱이 다 내려간 뒤 DROP 해요.
</details>

<details>
<summary>Q. expand-contract(병행 변경) 패턴이 뭔가요?</summary>

**답변(30초)**
바꾸고 싶은 것을 한 번에 바꾸지 않고 세 단계로 나누는 패턴이에요. expand에서 옛 방식과 새 방식을 둘 다 지원하게 넓히고, migrate에서 쓰는 쪽을 하나씩 새 방식으로 옮기고, contract에서 아무도 안 쓰는 옛 방식을 제거해요. 각 단계가 바로 앞 버전과 호환되니 어느 시점에 배포를 되돌려도 서비스가 깨지지 않아요. 대표 적용처가 DB 스키마 변경이에요.

**꼬리질문**
- Q. 가장 오래 걸리는 단계는? → migrate예요. 옛 스키마와 새 스키마가 함께 있는 전환기라서, 이중 쓰기·백필·읽기 전환을 점진적으로 해요.
- Q. 단점은? → 배포가 3~4번으로 늘고, 이중 쓰기 코드와 임시 컬럼을 한동안 유지해야 해요. 마지막 contract를 잊으면 쓰레기 컬럼이 남아요.
</details>

<details>
<summary>Q. 운영 중인 서비스에서 컬럼 이름을 바꾸려면 어떻게 하나요?</summary>

**답변(30초)**
expand-contract로 여섯 단계에 나눠요. 새 컬럼을 NULL 허용으로 추가하고, 앱이 옛·새 컬럼에 이중 쓰기를 하게 배포해요. 그다음 옛 행을 작은 배치로 백필하고, 읽기를 새 컬럼으로 전환해요. 이후 옛 컬럼 쓰기를 멈추고, 옛 앱이 하나도 없을 때 옛 컬럼을 삭제해요. 읽기 전환까지는 옛 컬럼도 최신이라 언제든 롤백할 수 있고, 옛 컬럼 쓰기를 멈추는 순간이 롤백 경계예요.

**꼬리질문**
- Q. 백필은 왜 나눠서 하나요? → 한 번에 UPDATE하면 트랜잭션이 길어져 락을 오래 쥐고, 복제가 늦어지고, 다음 DDL이 메타데이터 락에 막혀요. PK 범위로 몇천 행씩 나눠요.
- Q. 백필 도중 새로 가입한 회원은요? → 이미 이중 쓰기 중이라 새 행은 full_name이 채워져 있어요. 백필은 `full_name IS NULL`인 옛 행만 골라 채우면 돼요.
</details>

<details>
<summary>Q. MySQL 온라인 DDL의 INSTANT, INPLACE, COPY 차이는요?</summary>

**답변(30초)**
INSTANT는 테이블 메타데이터만 바꿔서 행 수와 상관없이 거의 즉시 끝나요. 컬럼 추가·삭제·이름 변경이 대표적이에요. INPLACE는 테이블을 복사하지 않고 엔진 안에서 처리하는데, 경우에 따라 재빌드하고 대부분 작업 중 쓰기를 허용해요. COPY는 새 테이블에 행을 전부 복사해서 행 수에 비례해 오래 걸리고 그동안 쓰기가 막혀요. 컬럼 타입 변경이 COPY예요.

**꼬리질문**
- Q. 원하는 알고리즘이 안 되는 걸 미리 알 수 있나요? → ALTER에 ALGORITHM과 LOCK을 명시하면, 그 조건으로 못 할 때 실행 대신 즉시 에러가 나요.
- Q. VARCHAR 길이 늘리기는 항상 INPLACE인가요? → 아니요. 길이 저장이 255바이트 이하는 1바이트, 256바이트 이상은 2바이트라, 그 경계를 넘으면 COPY예요. utf8mb4면 VARCHAR(63)→(64)가 경계예요.
- Q. 대용량 테이블 INT→BIGINT는? → COPY라 쓰기가 오래 막혀요. 새 컬럼 + 이중 쓰기 + 백필로 expand-contract 하거나 gh-ost, pt-online-schema-change 같은 도구를 써요.
</details>

<details>
<summary>Q. 큰 테이블도 아닌데 컬럼 하나 추가했더니 서비스가 몇 초 멈췄어요. 원인이 뭘까요?</summary>

**답변(30초)**
메타데이터 락 줄서기일 가능성이 커요. ALTER는 INSTANT라도 마지막에 잠깐 배타 메타데이터 락이 필요한데, 앞에 커밋 안 한 긴 트랜잭션이 공유 락을 쥐고 있으면 ALTER가 기다려요. 그리고 기다리는 배타 락 요청 뒤에 온 평범한 SELECT·INSERT도 전부 줄을 서요. 대책은 DDL 세션에 lock_wait_timeout을 짧게 걸고 실패하면 재시도하는 것, 그리고 배포 전에 긴 트랜잭션을 확인하는 거예요.

**꼬리질문**
- Q. 어떻게 확인하나요? → PROCESSLIST에서 상태가 `Waiting for table metadata lock`인 세션들이 보이고, `information_schema.innodb_trx`에서 오래 열린 트랜잭션을 찾아요.
- Q. lock_wait_timeout 기본값은? → 31536000초, 1년이에요. 기본값 그대로면 사실상 무한정 기다려요.
- Q. LOCK=NONE이면 락이 없는 거 아닌가요? → 작업 중 DML을 허용한다는 뜻이지 메타데이터 락이 없다는 뜻이 아니에요.
</details>

<details>
<summary>Q. 마이그레이션 롤백은 어떻게 하나요? Flyway에서 이미 적용된 파일을 고치면요?</summary>

**답변(30초)**
Flyway는 버전 순서대로 각 파일을 한 번만 적용하고, 체크섬을 기록해 둬요. 적용된 파일을 고치면 체크섬이 달라져 다음 검증에서 실패하니, 원칙은 고치지 말고 새 버전 파일을 추가하는 거예요. undo 마이그레이션은 유료 기능이라, 보통은 되돌리는 내용을 새 V 파일로 추가하는 roll-forward를 쓰고, 애초에 expand-contract로 앱만 되돌려도 되게 설계해요.

**꼬리질문**
- Q. 체크섬 에러가 났는데 의도한 수정이었다면? → `repair`로 기록을 갱신해요. 실수라면 파일을 원래대로 되돌려요.
- Q. Spring Boot에서 Flyway는 언제 실행되나요? → 앱이 시작할 때 자동으로 돌아요. 파드가 여러 개면 여러 곳에서 동시에 시작되는 구조를 점검해야 해요.
</details>

## 서술형 연습

<details>
<summary>상황: 회원 테이블의 name 컬럼을 full_name으로 바꾸라는 요구가 왔어요. 서비스는 롤링 배포로 무중단 운영 중입니다. 어떻게 진행하겠어요?</summary>

**상황 파악**
롤링 배포라 배포 중에는 옛 파드(name을 씀)와 새 파드(full_name을 씀)가 같은 DB를 함께 써요. 배포가 잘못되면 옛 버전으로 롤백도 할 수 있어야 해요. 회원 테이블은 행이 많고 거의 모든 API가 읽는 테이블이에요.

**원인 후보(단순 RENAME이 위험한 이유)**
1. `RENAME COLUMN`은 DB에선 즉시 끝나지만, 그 순간 옛 파드의 `SELECT name` 쿼리가 전부 에러가 나요.
2. 앱 배포와 DDL을 동시에 하려 해도 "DDL 후 앱 교체" 사이, 또는 롤백 시 앱과 스키마가 어긋나요.
3. 대량 백필을 한 방에 하면 긴 트랜잭션이 락과 복제 지연을 만들어요.

**해결책**
1. **expand-contract 6단계**: full_name 추가(NULL 허용) → 이중 쓰기 배포 → 배치 백필 → 읽기 전환 배포 → 옛 컬럼 쓰기 중단 배포 → name 삭제.
   - 장점: 각 단계가 앞 버전과 호환돼 언제 되돌려도 안전해요. 읽기 전환까지는 옛 컬럼도 최신이에요.
   - 단점: 배포가 4번 이상, 몇 주가 걸릴 수 있고 이중 쓰기 코드를 한동안 유지해야 해요.
2. **점검 시간에 서비스를 내리고 RENAME + 앱 교체**.
   - 장점: 간단하고 빨라요.
   - 단점: 무중단 요구를 어겨요. 롤백할 때도 다시 점검 시간이 필요해요.
3. **이름은 그대로 두고 코드에서만 매핑**(엔티티 필드 이름만 fullName, 컬럼은 name).
   - 장점: DB 변경이 아예 없어요.
   - 단점: DB와 코드 이름이 계속 어긋나서 헷갈려요. "왜 바꿔야 하나"에 따라 충분할 수도 있어요.

**내가 고를 방법과 이유**
먼저 3번으로 충분한지 물어볼 거예요(이름만 문제라면 비용이 0이니까요). 컬럼 자체를 바꿔야 한다면 1번을 골라요. 무중단이 요구 조건이고, 각 단계가 독립적으로 롤백 가능하기 때문이에요. 백필은 PK 범위로 몇천 행씩 나누고, 각 DDL은 `ALGORITHM=INSTANT`와 짧은 `lock_wait_timeout`을 걸어 실행해요. 5단계(옛 컬럼 쓰기 중단)는 롤백 경계라 충분히 지켜본 뒤 넘어가고, name 삭제는 옛 파드가 하나도 없는 걸 확인한 뒤 별도 배포로 해요.

**채점 포인트**: 옛/새 앱 공존, expand-migrate-contract, NULL 허용 추가, 이중 쓰기, 배치 백필, 읽기 전환, 롤백 경계, 옛 앱 종료 후 DROP, 여러 번의 배포
</details>

<details>
<summary>상황: 배포 때 "컬럼 하나 추가" 마이그레이션이 돌았는데, 회원 API가 약 10초 동안 전부 타임아웃 나고 커넥션 풀이 고갈됐어요. 테이블은 크지 않고, ALTER는 INSTANT였어요. 원인과 대책은?</summary>

**상황 파악**
INSTANT ALTER는 행 수와 무관하게 몇 ms면 끝나요. 그런데 10초가 걸렸고, ALTER와 상관없는 단순 조회까지 멈췄어요. 즉 작업 자체가 느린 게 아니라 **무언가를 기다린** 거예요.

**원인 후보**
1. **메타데이터 락 줄서기**(가장 유력): 커밋 안 한 콘솔 세션이나 오래 도는 배치 트랜잭션이 이 테이블의 공유 MDL을 쥐고 있었어요. ALTER는 커밋 단계에서 배타 MDL이 필요해 기다리고, 그 뒤에 온 SELECT·INSERT가 전부 ALTER 뒤에 줄을 섰어요. 상태는 `Waiting for table metadata lock`. `lock_wait_timeout` 기본값이 1년이라 ALTER가 포기하지도 않아요.
2. 생각보다 무거운 DDL: INSTANT가 안 되는 조건(FULLTEXT 인덱스, 행 버전 한도 등)이라 실제로는 재빌드가 돌았을 수 있어요. 다만 ALGORITHM=INSTANT를 명시했다면 이 경우엔 에러가 났을 거예요.
3. 앱 시작 시 자동 마이그레이션(Spring Boot + Flyway)이 여러 파드에서 동시에 시작되는 구조라 DDL이 겹쳤을 수 있어요.

**해결책**
1. **DDL 세션에 `lock_wait_timeout`을 짧게(예: 2~5초) + 재시도**
   - 장점: 락을 못 얻으면 ALTER만 포기하고 서비스 쿼리는 바로 진행돼요. 피해가 최대 몇 초로 묶여요.
   - 단점: 긴 트랜잭션이 계속 있으면 ALTER가 계속 실패해요. 재시도 로직이 필요해요.
2. **배포 전 긴 트랜잭션 점검·정리**: `information_schema.innodb_trx`, `SHOW PROCESSLIST`로 오래 열린 트랜잭션을 찾아 끝내고, 트래픽 적은 시간에 실행.
   - 장점: 원인 자체를 없애요.
   - 단점: 사람 손이 들고, 점검과 실행 사이에 새 긴 트랜잭션이 생길 수 있어요.
3. **마이그레이션을 앱 시작과 분리**: 앱 기동 시 자동 실행 대신 배포 파이프라인의 별도 단계에서 한 번만 실행.
   - 장점: 실행 시점과 횟수를 통제할 수 있어요.
   - 단점: 파이프라인이 복잡해지고, 앱과 스키마 순서를 사람이 챙겨야 해요.

**내가 고를 방법과 이유**
1번을 기본 안전장치로 항상 걸어요. 메타데이터 락은 "언제 긴 트랜잭션이 있을지" 예측할 수 없어서, 최악을 몇 초로 묶는 게 가장 확실하기 때문이에요. 여기에 2번 점검을 배포 체크리스트에 넣고, 콘솔에서 트랜잭션을 열어 두지 않는 습관과 긴 배치를 쪼개는 걸 같이 해요. 여러 파드가 동시에 마이그레이션을 돌리는 구조라면 3번도 검토해요.

**채점 포인트**: 메타데이터 락(MDL), 배타 락 대기 뒤 쿼리까지 대기, 긴/미커밋 트랜잭션, `Waiting for table metadata lock`, lock_wait_timeout 기본 1년, 짧은 타임아웃 + 재시도, innodb_trx/PROCESSLIST 점검, INSTANT여도 MDL 필요
</details>

<details>
<summary>상황: 새 버전 배포 후 장애가 나서 앱을 옛 버전으로 롤백했어요. 그런데 마이그레이션은 이미 적용돼서 옛 앱이 계속 에러를 냅니다. 어떻게 해야 하고, 다음엔 어떻게 막을까요?</summary>

**상황 파악**
앱은 이미지 하나 바꾸면 되돌아가지만, DB 스키마와 데이터는 그대로 남아 있어요. 새 버전과 함께 나간 마이그레이션이 옛 앱과 호환되지 않는 변경(컬럼 삭제·이름 변경, 기본값 없는 NOT NULL 추가 등)이었기 때문에 옛 앱이 깨진 거예요.

**원인 후보**
1. 한 번의 배포에 "앱 변경 + 옛 앱이 못 견디는 스키마 변경"을 함께 넣었어요.
2. NOT NULL 컬럼을 기본값 없이 추가해서 옛 앱의 INSERT가 실패해요.
3. 옛 컬럼을 삭제했거나 이름을 바꿔서 옛 앱의 조회가 실패해요.

**해결책**
1. **지금 당장: roll-forward**. 옛 앱이 견딜 수 있게 스키마를 앞으로 고치는 새 마이그레이션 파일을 추가해요(예: NOT NULL 제약을 풀거나 DEFAULT 추가, 지운 컬럼 다시 추가).
   - 장점: Flyway 버전 기록이 깔끔하게 이어지고 무료판에서도 돼요.
   - 단점: 삭제된 컬럼의 데이터는 백업 없이는 되살릴 수 없어요.
2. **Flyway undo 마이그레이션**
   - 장점: 버전 단위로 되돌리는 절차가 정해져 있어요.
   - 단점: 유료 에디션 기능이고, 데이터 삭제는 undo로도 되살릴 수 없어요.
3. **적용된 V 파일을 고쳐서 다시 배포**
   - 이건 안 돼요. 체크섬이 달라져 검증에서 실패해요.

**재발 방지**
- **expand-contract로 "롤백 가능한 마이그레이션"만 앱과 함께 내보내기**: 새 버전과 함께 나가는 변경은 추가(expand)만 하고, 삭제·제약 강화(contract)는 옛 앱이 완전히 사라지고 안정된 뒤 별도 배포로 해요. 그러면 앱만 되돌려도 DB와 호환돼요.
- 컬럼 추가는 NULL 허용이나 DEFAULT를 줘서 옛 앱의 INSERT가 깨지지 않게 해요.
- 배포 전에 "이 마이그레이션 적용 후 옛 버전 앱이 정상 동작하는가"를 체크해요.

**내가 고를 방법과 이유**
지금은 1번 roll-forward로 옛 앱이 동작하게 복구할 거예요. 기록이 꼬이지 않고 도구 에디션과 상관없이 할 수 있기 때문이에요. 근본적으로는 expand-contract로 "앱 롤백만으로 충분한 상태"를 만들어 DB 롤백이 필요 없게 하는 게 답이에요. DB 데이터는 앱처럼 쉽게 되돌릴 수 없으니까요.

**채점 포인트**: 앱과 DB 롤백의 비대칭, 옛 앱과 호환되는 스키마(expand만 먼저), contract는 별도 배포, roll-forward(새 V 파일), undo는 유료 기능, 적용 파일 수정 금지(체크섬), NULL 허용/DEFAULT, 삭제 데이터는 복구 불가
</details>

## 필기 포인트

- **expand → migrate → contract** = 병행 변경(Parallel Change). 한 번이 아니라 여러 번의 배포.
- 컬럼 이름 변경 6단계: 새 컬럼 추가 → 이중 쓰기 → 백필 → 읽기 전환 → 옛 컬럼 쓰기 중단(롤백 경계) → 옛 컬럼 삭제.
- MySQL InnoDB 온라인 DDL: **INSTANT**(메타데이터만), **INPLACE**(엔진 내부, 대부분 DML 허용), **COPY**(행 복사, DML 불가).
- 컬럼 추가·삭제·이름 변경 = INSTANT 가능 / 컬럼 타입 변경 = COPY만.
- VARCHAR 길이 저장 1바이트(0~255B) ↔ 2바이트(256B~). 경계를 넘거나 줄이면 INPLACE 불가.
- 온라인 DDL도 메타데이터 락은 잡음. 대기 중인 배타 MDL 뒤의 쿼리도 대기. `lock_wait_timeout` 기본 31536000초(1년).
- Flyway: `V<버전>__<이름>.sql`, `flyway_schema_history`, 체크섬 불일치 → 파일 되돌리기 또는 repair. undo는 유료 기능.
- 함정: "INSTANT면 무조건 안전"(X), "LOCK=NONE = 락 없음"(X), "DB에서 RENAME이 즉시면 무중단"(X).
