:::tip[한 줄 요약]
**무중단 배포**는 새 버전을 올리는 동안에도 사용자 요청이 끊기지 않게 하는 방법이에요. **롤링**은 서버를 몇 대씩 차례로 바꾸고, **블루그린**은 똑같은 환경 두 벌을 두고 트래픽을 통째로 넘기고, **카나리**는 일부 사용자에게만 먼저 내보내 지표를 보고 넓혀요. 셋 다 옛 버전과 새 버전이 함께 도는 순간이 있어서 **API·DB 하위 호환**이 꼭 필요해요.
:::

:::note[처음이라면 여기까지]
① 롤링은 "한 대씩 바꾸기", 블루그린은 "옆에 새 환경 차려 놓고 한 번에 넘기기", 카나리는 "일부만 먼저 보내 보기"예요.

② 롤백(되돌리기)은 블루그린이 가장 빠르고, 자원은 롤링이 가장 적게 들고, 문제를 일으켜도 피해 범위가 가장 작은 건 카나리예요.

③ A/B 테스트는 배포 전략이 아니라 "어느 쪽이 더 잘 팔리나"를 보는 실험이에요.

④ 면접에선 질문 1~3번부터 연습하세요. "심화:"가 붙은 소제목은 나중에 읽어도 돼요.
:::

<Aside type="note" title="이 페이지의 기준">
쿠버네티스 공식 문서, Argo Rollouts 공식 문서, AWS CodeDeploy 문서, Martin Fowler 사이트의 업계 참고 글(BlueGreenDeployment, CanaryRelease)을 바탕으로 했어요(2026-11 조회). 세션 처리처럼 공식 문장으로 확인하지 못한 부분은 "일반적인 원칙"이라고 따로 밝혔어요.
</Aside>

## 쉽게 이해하기

손님이 계속 드나드는 식당을 **문 닫지 않고 리모델링**해야 한다고 해 봐요.

**롤링**은 **테이블을 한 개씩 바꾸는** 방법이에요. 테이블 하나를 새것으로 바꾸는 동안 나머지 테이블에서 계속 손님을 받아요. 여분 공간이 조금만 있으면 돼요. 대신 공사 중에는 헌 테이블과 새 테이블이 섞여 있고, 다시 옛날 걸로 돌리려면 또 한 개씩 바꿔야 해요.

**블루그린**은 **바로 옆에 똑같은 새 매장을 차려 두는** 방법이에요. 새 매장 준비가 끝나면 입구 안내판을 새 매장 쪽으로 돌려요. 문제가 생기면 안내판만 다시 돌리면 끝이에요. 대신 매장 두 개 값이 들고, 안내판을 돌리는 순간 모든 손님이 새 매장으로 가요.

**카나리**는 **단골 몇 명만 먼저 새 메뉴를 맛보게** 하는 방법이에요. 반응이 괜찮으면 조금씩 더 많은 손님에게 내놓고, 탈이 나면 그 몇 명만 원래 메뉴로 돌려요.

단, 실제로는 매장이 두 개여도 **창고(DB)는 하나를 같이 쓰는** 경우가 대부분이에요. 그래서 새 매장이 창고 정리 방식을 바꿔 버리면 옛 매장으로 돌아갔을 때 물건을 못 찾아요. 이게 뒤에 나올 "DB **하위 호환**"(새 버전이 바꾼 뒤에도 옛 버전이 그대로 읽고 쓸 수 있게 하는 것) 문제예요.

## 제대로 알기

### 왜 무중단 배포가 필요한가

가장 단순한 배포는 "옛 서버를 전부 내리고 새 서버를 띄우는" 방식이에요. 쿠버네티스에선 이걸 `Recreate` 전략이라고 불러요. 옛 **Pod**(쿠버네티스에서 앱이 실제로 돌아가는 가장 작은 단위)를 모두 끈 뒤에 새 Pod를 만들기 때문에, 그 사이엔 아무도 요청을 받지 못해요. 이게 **다운타임**이에요.

무중단 배포 전략들은 이 공백을 없애는 방법이고, 차이는 결국 하나예요. **"새 버전에 트래픽을 언제, 얼마나 보내느냐"**예요.

### 롤링 업데이트: 몇 대씩 차례로 교체

**롤링 업데이트**(rolling update)는 서버를 몇 대씩 새 버전으로 바꿔 나가는 방식이에요. 쿠버네티스 **Deployment**(Pod 여러 개를 원하는 개수·버전으로 유지해 주는 관리자)의 기본 전략이 바로 이거예요.

- 옛 버전 묶음을 조금씩 줄이고, 새 버전 묶음을 조금씩 늘려요.
- 여분 서버가 조금만 있으면 돼서 **자원이 가장 적게** 들어요.
- 되돌릴 때(`kubectl rollout undo`)도 같은 교체 과정을 **거꾸로 다시** 해야 해서, 즉시 돌아가지 않고 교체 시간만큼 걸려요.
- 교체하는 동안 v1과 v2가 **같은 주소 뒤에서 동시에** 요청을 받아요.

몇 대씩 바꿀지 정하는 `maxSurge`·`maxUnavailable` 설정과 Pod 교체 과정은 [Pod와 Deployment](../../infra/k8s-pod-deployment/)에서 자세히 다뤄요.

<Aside type="caution" title="롤링이면 무조건 무중단?">
아니에요. 새 Pod가 요청 받을 준비가 됐는지 확인하는 **readiness probe**와, 꺼지는 Pod가 처리 중인 요청을 끝내고 내려가는 **우아한 종료**(graceful shutdown)가 없으면 교체 중에 요청이 실패할 수 있어요. → [프로브와 오토스케일링](../../infra/k8s-probes-scaling/)
</Aside>

### 블루그린: 환경 두 벌을 통째로 스위치

**블루그린 배포**(blue-green deployment)는 거의 똑같은 운영 환경을 **두 벌**(blue, green) 두고, 그중 하나만 실제 손님을 받게 하는 방식이에요.

1. 지금은 Blue(v1)가 라이브예요.
2. 쉬고 있는 Green에 v2를 올리고 최종 테스트를 해요.
3. **라우터**(요청을 어느 서버로 보낼지 정하는 장치, 로드밸런서 같은 것)가 모든 요청을 Green으로 넘겨요.
4. Blue는 바로 지우지 않고 **롤백 대비**로 남겨 둬요.

장점은 **롤백이 가장 빠르다**는 거예요. 이전 환경이 그대로 살아 있으니 라우터만 되돌리면 돼요. 단점은 전환하는 동안 **전체 용량을 두 벌** 들고 있어야 한다는 것, 그리고 스위치를 누르는 순간 **사용자 100%가 새 버전**을 만난다는 거예요.

다 쓴 환경은 "라이브 → 롤백 대기 → 다음 릴리스 준비" 순으로 돌아가며 써요. 업계에선 Netflix가 쓰던 이름인 **레드블랙**(red-black)이라고 부르기도 해요.

### 카나리: 일부에게 먼저, 지표 보고 넓히기

**카나리 릴리스**(canary release)는 새 버전을 **소수 사용자에게 먼저** 내보내고, 문제가 없다는 확신이 쌓이면 전체로 넓히는 방식이에요. 옛날 광부들이 유독가스를 먼저 알아채려고 탄광에 카나리아를 데려간 데서 이름이 왔어요.

- 누구에게 먼저 보낼지는 무작위, 사내 직원 먼저, 지역별 등으로 정해요.
- 예를 들어 5% → 25% → 100%처럼 단계마다 **에러율**, **p99 지연**(가장 느린 1% 요청의 응답 시간) 같은 지표를 보고 넘어가요.
- 문제가 생기면 그 소수 사용자만 옛 버전으로 돌려보내요. 피해 범위가 가장 작아요.
- 대신 두 버전이 **오래** 함께 돌아서 관리가 복잡해요. 동시에 도는 버전 수는 최소로 유지해요.

사용자 폰에 설치되는 앱은 업데이트 시점을 서버가 정할 수 없어서 이 방식이 어려워요. 카나리는 서버 쪽 배포에 잘 맞아요.

### 한눈에 비교

| | 롤링 | 블루그린 | 카나리 | A/B 테스트 |
|---|---|---|---|---|
| 롤백 속도 | 느림(교체를 거꾸로 다시) | 가장 빠름(라우터만 되돌림) | 빠름(새 버전 비율을 0으로) | 해당 없음(실험 종료) |
| 필요 자원 | 적음(여분 몇 대) | 많음(전환 중 두 벌) | 중간(카나리 몇 대) | 실험 플랫폼·플래그 |
| 위험 노출 범위 | 바뀐 비율만큼 점점 커짐 | 전환 순간 100% | 처음엔 소수(예: 5%) | 실험군만 |
| 두 버전 동시 실행 | 예(교체 내내) | 짧게(옛 환경이 롤백 대비로 살아 있음) | 예(오래) | 예(일부러) |
| DB 하위 호환 | 필요 | 필요(롤백 시 옛 버전이 새 데이터를 읽음) | 필요 | 같은 배포본 안에서 나누면 배포 문제는 아님 |

<Aside type="caution" title="자주 틀리는 것">
"블루그린은 두 버전이 동시에 안 도니까 DB 걱정이 없다"는 틀려요. 보통 DB는 하나를 같이 쓰고, 롤백하면 v2가 쓴 데이터를 v1이 읽어야 해요. 그래서 블루그린도 DB 하위 호환이 필요해요.
</Aside>

### A/B 테스트는 배포 전략이 아니라 실험

**A/B 테스트**도 "트래픽 일부를 다른 버전으로" 보낸다는 점은 카나리와 비슷해요. 하지만 목적이 달라요.

- **카나리**: 새 버전이 **고장 났는지**를 분·시간 단위로 빨리 잡는 게 목적이에요.
- **A/B**: "새 버튼이 **더 잘 팔리나**" 같은 가설을 검증하는 **제품 실험**이에요. 통계적으로 믿을 만한 결과가 나오려면 며칠이 걸려요.

둘을 섞으면 결과가 왜곡될 수 있어요. 보통 A/B는 같은 배포본 안에서 **피처 플래그**(코드 안의 기능 스위치)나 실험 플랫폼으로 사용자를 나누고, **같은 사용자는 계속 같은 그룹**에 머물게 해요(일반적인 운영 방식). → [피처 플래그](../feature-flag/)

### 어떤 걸 고를까

| 이런 상황이면 | 고를 만한 전략 |
|---|---|
| 노드 자원이 빠듯하고 사내용 서비스 | 롤링 |
| 롤백이 몇 초 안에 돼야 하고 자원 여유가 있음 | 블루그린 |
| 결제처럼 장애 피해가 크고 지표로 판단할 수 있음 | 카나리 + 자동 분석 |
| "어느 쪽이 더 효과 좋은가"를 알고 싶음 | 배포 전략이 아니라 A/B 실험 |

### 심화: 쿠버네티스 기본 기능으로 카나리 하기

별도 도구 없이도 **라벨**(Pod에 붙이는 이름표)로 흉내 낼 수 있어요.

- stable용, canary용 Deployment를 두 개 만들어요.
- 둘 다 공통 라벨 `app: my-app`을 달고, 구분용으로 `track: stable` / `track: canary`를 달아요.
- **Service**(Pod 묶음 앞에 놓인 고정 주소)는 공통 라벨만 보고 양쪽에 요청을 나눠 줘요.
- 비율은 Pod 개수로 맞춰요. 예를 들어 stable 9개, canary 1개면 대략 10%가 카나리로 가요.

한계가 분명해요. 비율이 **Pod 개수 단위**라서 1%를 맞추려면 Pod가 100개 필요해요. "사내 직원만", "이 헤더가 붙은 요청만" 같은 지정도 안 돼요. 이런 건 Ingress, 서비스 메시(Istio 등) 같은 트래픽 라우팅 도구나 Argo Rollouts가 필요해요.

또 쿠버네티스 Deployment는 배포가 정해진 시간(`progressDeadlineSeconds`, 기본 600초) 안에 안 끝나도 **자동으로 롤백하지 않아요**. 실패 상태만 기록해요. 자동 롤백은 Argo Rollouts나 AWS CodeDeploy 같은 도구가 해 줘요.

### 심화: Argo Rollouts로 카나리·블루그린

**Argo Rollouts**는 쿠버네티스에 카나리·블루그린을 더해 주는 도구예요. Deployment 대신 `Rollout`이라는 리소스를 써요.

**카나리**는 `steps`에 단계를 적어요.

```yaml
strategy:
  canary:
    steps:
    - setWeight: 5            # 새 버전으로 5% 보내기
    - pause: {duration: 10m}  # 10분 기다렸다가 자동 진행
    - setWeight: 25
    - pause: {}               # 사람이 promote 할 때까지 무기한 대기
    - setWeight: 100
```

트래픽 라우팅 도구를 연결하지 않으면 비율은 Pod 개수로 근사돼요(Pod 10개에 10%면 카나리 1개).

**자동 분석**은 `AnalysisTemplate`에 "어떤 지표를, 얼마마다, 어떤 기준으로" 볼지 적어요.

```yaml
kind: AnalysisTemplate
spec:
  metrics:
  - name: success-rate
    interval: 5m                        # 5분마다 조회
    successCondition: result[0] >= 0.95 # 성공률 95% 이상이면 통과
    failureLimit: 3                     # (예시 값) 이보다 많이 실패하면 중단
    provider:
      prometheus:
        query: ...                      # HTTP 성공률을 구하는 쿼리
```

실패 횟수가 `failureLimit`를 넘으면 Rollout이 멈추고 카나리 비율을 0으로 되돌린 뒤 `Degraded` 상태가 돼요. 사람이 밤새 지켜보지 않아도 나쁜 버전이 자동으로 빠지는 거예요.

**블루그린**은 Service 두 개로 해요.

- `activeService`(필수): 실제 손님 트래픽이 가는 곳.
- `previewService`(선택): 승격 전에 새 버전을 미리 테스트하는 곳.
- 승격하면 컨트롤러가 activeService가 가리키는 대상을 새 버전으로 바꿔 트래픽을 넘겨요.
- `autoPromotionEnabled`(기본 true)를 false로 두면 사람이 승인할 때까지 기다려요.
- `scaleDownDelaySeconds`(기본 30초): 전환 직후 옛 버전을 바로 줄이지 않고 잠깐 남겨 둬요. 각 노드의 라우팅 규칙이 바뀌는 데 시간이 걸리기 때문이에요.
- `prePromotionAnalysis`로 전환 전에 자동 검증도 할 수 있어요.

### 심화: AWS CodeDeploy의 트래픽 전환 방식

AWS CodeDeploy도 ECS·Lambda 배포에 미리 정의된 방식을 줘요. `ECSCanary10Percent5Minutes`는 처음 10%를 보내고 5분 뒤 나머지 90%를 넘겨요. `ECSLinear10PercentEvery1Minutes`는 1분마다 10%씩 늘려요. `ECSAllAtOnce`는 한 번에 넘겨요. EC2는 대체 환경에 배포한 뒤 트래픽을 옮기는 블루/그린을 지원해요.

### 심화: 배포 중 세션이 끊기는 문제

로그인 정보 같은 **세션**을 서버 메모리에 들고 있으면, 롤링·카나리 중엔 요청마다 v1·v2 서버를 오가며 로그인이 풀릴 수 있고, 블루그린 전환 때는 옛 환경의 메모리 세션이 통째로 사라져요. 그래서 보통 세션을 Redis 같은 **외부 저장소로 빼서** 어느 서버가 받아도 같은 세션을 보게 해요. 카나리에선 한 사용자가 계속 같은 버전으로 가도록 고정하기도 해요(일반적인 원칙).

<details>
<summary>Q. 무중단 배포 방식 세 가지를 설명해 주세요.</summary>

**답변(30초)**
롤링, 블루그린, 카나리가 있어요. 롤링은 서버를 몇 대씩 새 버전으로 바꾸는 방식으로, 자원이 적게 들고 쿠버네티스 기본 전략이에요. 블루그린은 같은 환경을 두 벌 두고 라우터를 한 번에 새 쪽으로 넘기는 방식이라 롤백이 가장 빠르지만 자원이 두 배 들어요. 카나리는 일부 사용자에게만 먼저 내보내고 지표를 보며 비율을 늘리는 방식이라 문제가 생겨도 피해 범위가 작아요.

**꼬리질문**
- Q. 가장 단순한 배포는요? → 옛 서버를 다 내리고 새로 띄우는 Recreate예요. 그 사이 다운타임이 생겨요.
- Q. 롤링이면 다운타임이 0인가요? → readiness probe와 우아한 종료가 없으면 교체 중 요청이 실패할 수 있어요.
</details>

<details>
<summary>Q. 블루그린과 카나리는 각각 언제 쓰나요?</summary>

**답변(30초)**
롤백이 즉시 돼야 하고 자원 여유가 있으면 블루그린, 장애 피해가 커서 노출 범위를 최소로 하고 싶으면 카나리를 써요. 블루그린은 라우터만 되돌리면 되지만, 전환 순간 사용자 100%가 새 버전을 만나요. 카나리는 5%, 25%처럼 조금씩 넓히며 에러율을 확인하니 문제를 소수에게서 잡을 수 있어요. 대신 두 버전이 오래 같이 돌아서 운영이 더 복잡해요.

**꼬리질문**
- Q. 블루그린의 비용 문제는? → 전환 중엔 전체 용량을 두 벌 들고 있어야 해요.
- Q. 카나리 대상은 어떻게 고르나요? → 무작위, 사내 직원 먼저, 지역별 등으로 골라요.
</details>

<details>
<summary>Q. 카나리 배포와 A/B 테스트는 뭐가 다른가요?</summary>

**답변(30초)**
트래픽을 나눈다는 기술은 비슷하지만 목적이 달라요. 카나리는 새 버전이 고장 났는지를 분·시간 단위로 빨리 잡는 배포 방법이고, A/B는 어느 안이 전환율이 더 높은지 가설을 검증하는 실험이라 통계적으로 의미 있는 결과까지 며칠이 걸려요. 그래서 A/B는 보통 피처 플래그나 실험 플랫폼으로 같은 사용자를 같은 그룹에 고정해서 진행하고, 둘을 섞으면 결과가 왜곡될 수 있어요.

**꼬리질문**
- Q. 왜 같은 사용자를 같은 그룹에 고정하나요? → 한 사람이 A·B를 번갈아 보면 어느 안의 효과인지 알 수 없어요.
</details>

<details>
<summary>Q. 무중단 배포할 때 DB 스키마 변경은 어떻게 하나요?</summary>

**답변(30초)**
**스키마**(테이블·컬럼 구조) 변경을 앱 배포와 분리해요. 먼저 옛 앱과 새 앱이 둘 다 동작하는 스키마로 바꾸고, 그다음 새 앱을 배포하고, 안정되면 옛 버전 지원을 지워요. 이걸 확장-축소(expand-contract)라고 해요. 롤링·카나리는 두 버전이 동시에 돌고, 블루그린도 롤백하면 옛 버전이 새 데이터를 읽어야 해서 어느 전략이든 필요해요.

**꼬리질문**
- Q. 컬럼 이름을 바꾸려면? → 새 컬럼 추가 → 양쪽에 쓰기 → 새 앱 배포 → 옛 컬럼 제거 순으로 나눠요. 자세한 건 [무중단 DB 마이그레이션](../db-migration-zero-downtime/)에서 다뤄요.
</details>

<details>
<summary>Q. 롤백은 어떻게 하고, 자동 롤백 기준은 뭘로 잡나요?</summary>

**답변(30초)**
전략마다 달라요. 롤링은 rollout undo로 교체를 거꾸로 해서 시간이 걸리고, 블루그린은 라우터만 되돌려 즉시, 카나리는 새 버전 비율을 0으로 돌려요. 자동 롤백은 쿠버네티스 Deployment가 해 주지 않아서 Argo Rollouts 같은 도구를 써요. 에러율, HTTP 성공률, p99 지연 같은 지표를 주기적으로 보고, 기준 아래로 정해진 횟수 넘게 떨어지면 자동으로 중단·복귀하게 해요.

**꼬리질문**
- Q. 기술 지표만 보면 되나요? → 주문 수처럼 비즈니스 지표도 봐요. IMVU라는 회사는 비즈니스 지표가 통계적으로 의미 있게 나빠지면 자동 롤백했어요.
- Q. Deployment가 진행 기한을 넘기면? → ProgressDeadlineExceeded 상태만 남기고 자동 롤백은 안 해요.
</details>

<details>
<summary>Q. 쿠버네티스에서 카나리 배포는 어떻게 구현하나요?</summary>

**답변(30초)**
기본 기능만 쓰면 stable·canary Deployment 두 개에 공통 라벨을 달고, Service가 공통 라벨로 양쪽에 트래픽을 보내게 해요. 비율은 Pod 개수로 맞춰서, 9대 1이면 대략 10%예요. 다만 Pod 개수 단위라 정밀한 비율이나 헤더 기반 지정이 안 돼서, 실무에선 Argo Rollouts의 setWeight·pause 단계와 AnalysisTemplate 자동 분석, 또는 서비스 메시 같은 트래픽 라우팅을 같이 써요.

**꼬리질문**
- Q. 라벨 방식으로 1%를 보내려면? → Pod가 100개 필요해요. 그래서 트래픽 라우팅 도구가 필요해요.
</details>

## 서술형 연습

<details>
<summary>상황: 결제 서비스의 새 버전을 배포해야 해요. 장애가 나면 바로 돈 문제가 생깁니다. 어떤 배포 전략을 고르겠어요?</summary>

**상황 파악**
결제는 장애 한 번이 곧 금전 손실과 신뢰 하락이에요. 그래서 목표는 두 가지예요. 문제가 생겨도 **영향받는 사용자를 최소로** 하고, **빨리 알아채서 빨리 되돌리는** 거예요.

**원인 후보(배포에서 생길 수 있는 위험)**
1. 새 버전 버그로 결제 실패율이 올라감.
2. 성능 저하로 응답이 느려져 타임아웃.
3. 테스트 환경에선 안 보이고 실제 트래픽에서만 드러나는 문제.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 롤링 | 자원 적게 듦, 설정 간단 | 롤백이 느림. 문제를 자동으로 판단하지 않아 사람이 보고 멈춰야 함 |
| B. 블루그린 | 라우터만 되돌리면 즉시 롤백 | 전환 순간 사용자 100%가 새 버전에 노출. 자원 두 벌 |
| C. 카나리 + 자동 분석 | 처음엔 5%만 노출. 지표가 나쁘면 자동으로 0%로 복귀 | 두 버전이 오래 공존해 API·DB 호환 필요, 설정·모니터링 준비 필요 |

**내가 고를 방법**
C를 골라요. Argo Rollouts로 5% → 25% → 100% 단계를 두고, 단계마다 AnalysisTemplate으로 결제 성공률·에러율·p99 지연을 봐요. 기준을 정해진 횟수 넘게 못 넘으면 자동으로 카나리 비율을 0으로 되돌려요. 마지막 100% 직전에는 사람이 승인하는 `pause`를 둬요. 기술 지표만이 아니라 결제 완료 건수 같은 비즈니스 지표도 같이 보고, 새 버전은 옛 버전과 API·DB가 호환되게 만들어 둬요. 블루그린의 즉시 롤백이 아쉽다면, 카나리 비율을 0으로 돌리는 것도 충분히 빠르다는 점을 근거로 들어요.

**채점 포인트**: 위험 노출 범위 최소화, 카나리 단계적 확대, 자동 분석(성공률·에러율·지연)과 자동 중단, 비즈니스 지표, 블루그린의 100% 노출·2배 자원 트레이드오프, 두 버전 공존에 따른 API·DB 호환, 수동 승인 단계.
</details>

<details>
<summary>상황: 블루그린으로 배포하고 10분 뒤 버그를 발견해 Blue로 롤백했어요. 그런데 그 10분 동안 새 버전이 저장한 주문 데이터를 옛 버전이 읽지 못해 에러가 납니다. 왜 그렇고 어떻게 막겠어요?</summary>

**상황 파악**
라우터는 바로 되돌렸지만, **DB는 Blue와 Green이 하나를 같이** 쓰고 있었어요. 그 10분 동안 v2가 쓴 데이터가 DB에 남아 있고, v1은 그 모양을 이해하지 못해요. "블루그린은 롤백이 쉽다"는 건 앱 얘기지, 데이터까지 되돌려 주진 않아요.

**원인 후보**
1. v2 배포에 **스키마 변경이 같이** 들어갔어요(컬럼 이름 변경, 새 필수 컬럼, 값 형식 변경 등).
2. 옛 버전이 모르는 새 값(예: 새 주문 상태 코드)을 v2가 저장했어요.
3. 전환 직후 새 환경에서 처리된 거래를 롤백 때 어떻게 할지 계획이 없었어요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 스키마 변경을 앱 배포와 분리(확장-축소): 옛·새 앱이 모두 읽을 수 있는 스키마를 먼저 배포 → 새 앱 → 안정 후 옛 지원 제거 | 언제든 v1로 돌아가도 데이터를 읽을 수 있음 | 배포가 여러 번으로 나뉘고, 한동안 옛 컬럼·새 컬럼을 같이 관리 |
| B. 전환 직전 잠깐 읽기 전용 모드로 두기 | 전환 중 새로 쓰이는 데이터를 줄여 롤백이 단순 | 그동안 주문을 못 받아 사실상 짧은 중단 |
| C. 문제 데이터를 사후에 수작업·스크립트로 변환 | 이미 터진 상황 복구에 필요 | 느리고 실수 위험, 재발 방지는 안 됨 |

**내가 고를 방법**
지금 장애는 C로 v2가 쓴 데이터를 v1이 읽을 수 있게 변환해 복구하고, 재발 방지는 A로 해요. 규칙은 "새 앱은 옛 스키마에서도 돌고, 옛 앱은 새 스키마에서도 돈다"예요. 이렇게 하면 블루그린이든 카나리든 롤백할 때 데이터 걱정이 없어요. 쓰기가 많지 않은 서비스라면 B도 고려하지만, 결제·주문처럼 멈추면 안 되는 서비스엔 A가 맞아요. 자세한 단계는 [무중단 DB 마이그레이션](../db-migration-zero-downtime/)에서 다뤄요.

**채점 포인트**: 블루그린도 DB는 공유, 롤백은 앱만 되돌림, 하위 호환(옛 앱이 새 데이터를 읽어야 함), 스키마 변경과 앱 배포 분리, 확장-축소(expand-contract), 전환 중 거래 처리(읽기 전용 모드 등), 단기 복구와 재발 방지 구분.
</details>

<details>
<summary>상황: 롤링 업데이트 중에 일부 사용자만 에러가 나요. 배포가 끝나자 에러가 사라졌어요. 원인과 대책은?</summary>

**상황 파악**
"배포 중에만, 일부 사용자만"이 핵심 단서예요. 롤링 중엔 v1과 v2 Pod가 같은 Service 뒤에서 **동시에** 요청을 받아요. 배포가 끝나 v2만 남자 에러가 사라졌으니, 두 버전이 섞인 상태에서만 생기는 문제일 가능성이 커요.

**원인 후보**
1. **API 호환 깨짐**: v2가 응답 형식이나 요청 필드를 바꿨는데, 같은 사용자의 다음 요청이 v1으로 가면 v1이 이해하지 못해요(또는 반대).
2. **DB 스키마 호환 깨짐**: v2가 바꾼 스키마를 v1 Pod가 못 읽어요.
3. **세션을 서버 메모리에 저장**: 요청마다 다른 Pod로 가면서 로그인이 풀려요.
4. **준비 안 된 Pod로 트래픽**: readiness probe가 없거나 우아한 종료가 없어 막 뜬 Pod나 꺼지는 Pod가 요청을 받아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. API·DB 하위 호환 규칙(필드는 추가만, 옛 형식 한동안 지원, 스키마는 확장-축소) | 근본 원인 제거, 어느 전략에도 통함 | 옛 형식을 정리하는 수고 |
| B. 세션을 Redis 같은 외부 저장소로 | 어느 Pod가 받아도 같은 세션 | 외부 저장소 운영 필요 |
| C. readiness probe·우아한 종료 설정 | 준비 안 된·꺼지는 Pod로 가는 요청 차단 | 설정·종료 대기 시간 조정 필요 |
| D. 사용자를 한 버전에 고정(sticky) | 한 사용자가 버전을 오가지 않음 | 부하가 고르게 안 나뉘고, 호환 문제를 숨길 뿐 |

**내가 고를 방법**
먼저 에러 로그를 Pod 버전별로 나눠 봐서 원인을 좁혀요. 응답 형식이나 스키마 문제면 A가 기본 해법이에요. 두 버전이 공존하는 건 롤링의 본질이라 피할 수 없으니, 호환을 지키는 게 맞아요. 로그인 풀림이면 B, 배포 시작·끝에 몰린 에러면 C를 같이 적용해요. D는 임시방편이라 쓰더라도 A를 대신하진 않아요.

**채점 포인트**: 롤링 중 v1·v2 동시 서비스, API 하위 호환, DB 스키마 호환(확장-축소), 세션 외부화, readiness probe·우아한 종료, 버전별 로그로 원인 좁히기, sticky의 한계.
</details>

<details>
<summary>상황: 새 기능 코드는 수요일에 배포해 두고, 실제로 사용자에게 보이는 건 금요일 이벤트 시작 시각에 맞추고 싶어요. 어떻게 하겠어요?</summary>

**상황 파악**
요구사항은 **"배포"**(코드를 서버에 올리는 일)와 **"출시"**(사용자에게 기능을 보여 주는 일)를 다른 시점에 하자는 거예요. 배포 전략(롤링·블루그린·카나리)은 "새 코드를 언제 서버에 올리나"만 다뤄서, 이것만으로는 금요일 정각 공개를 맞추기 어려워요.

**원인 후보(그냥 금요일에 배포하면 생기는 문제)**
1. 이벤트 직전 배포는 위험해요. 배포 문제와 이벤트 트래픽이 겹쳐요.
2. 배포에는 시간이 걸려서 정확히 정각에 맞추기 어려워요(롤링은 교체 시간만큼).
3. 문제가 생기면 롤백도 배포 단위라, 기능만 빠르게 끄기 어려워요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 금요일 정각에 배포 | 별도 장치 없음 | 위험한 시점에 배포, 정각 맞추기 어려움, 끄려면 롤백 |
| B. 피처 플래그: 수요일에 기능을 꺼 둔 채 배포 → 금요일에 플래그만 켬 | 배포는 여유 있게, 공개는 정각에. 문제 시 플래그만 끄면 즉시 숨김 | 플래그 관리가 필요하고, 다 쓴 플래그는 코드에서 지워야 함 |
| C. 블루그린으로 금요일에 스위치 | 전환 자체는 빠름 | 자원 두 벌을 이틀 들고 있어야 하고, 기능 하나 때문에 환경 전체를 바꿈 |

**내가 고를 방법**
B를 골라요. 수요일에 평소처럼 롤링이나 카나리로 배포하되 새 기능은 플래그로 꺼 둬요. 그사이 사내 직원에게만 플래그를 켜서 미리 확인할 수도 있어요. 금요일 정각엔 플래그만 켜고, 문제가 생기면 코드 롤백 없이 플래그를 꺼요. 이벤트가 끝나 기능이 안정되면 플래그 코드는 지워요. 자세한 건 [피처 플래그](../feature-flag/)에서 다뤄요.

**채점 포인트**: 배포와 출시(릴리스) 분리, 피처 플래그, 플래그 끄기로 즉시 대응(코드 롤백 불필요), 배포 전략은 코드 올리는 시점만 다룸, 사내 먼저 켜기, 다 쓴 플래그 정리.
</details>

## 필기 포인트

- 쿠버네티스 Deployment 기본 전략 = **RollingUpdate**. 다른 하나는 **Recreate**(전부 끄고 새로 띄움, 다운타임 있음).
- 롤백 속도: 블루그린(라우터 되돌림) > 카나리(비율 0) > 롤링(역방향 교체).
- 자원: 롤링(여분 조금) < 카나리 < 블루그린(전환 중 두 벌).
- 카나리 이름 유래 = 탄광의 카나리아. 다른 이름: phased rollout, incremental rollout.
- 쿠버네티스 Deployment는 실패해도 **자동 롤백 안 함**(ProgressDeadlineExceeded 상태만).
- 블루그린 = 레드블랙이라고도 함.
- 함정: "블루그린은 DB 호환 불필요"(X), "카나리 = A/B 테스트"(X), "rollout undo는 즉시"(X), "롤링이면 무조건 무중단"(X).
