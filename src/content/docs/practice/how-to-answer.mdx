:::tip[한 줄 요약]
장애·문제 해결 서술형은 "정답 원인"을 맞히는 문제가 아니라 **생각 순서**를 보는 문제예요. **상황 정리 → 원인 후보 여러 개 → 확인 방법 → 즉시 완화 → 근본 해결과 트레이드오프 → 재발 방지**, 이 6단을 채우면 원인을 100% 몰라도 좋은 답안이 돼요.
:::

:::note[이 섹션 안내]
이 섹션은 개념 설명이 아니라 **연습장**이에요. 페이지마다 실무에서 흔한 상황(재고가 음수, API가 느림, 서버가 죽음…)을 주고, 생각 순서와 모범 답안을 보여 줘요.

모든 페이지가 이 페이지의 **6단 구조**로 풀려 있어요. 먼저 여기서 뼈대를 익히고, 아래 [유형별 페이지](#유형별-페이지)로 넘어가세요.

문제는 모두 연습용으로 지어낸 **실무 상황형 서술형**이에요. 특정 회사의 실제 기출이 아니에요. 개념(락, 인덱스, GC 등)은 다른 섹션에 있으니 링크를 따라가면 돼요.
:::

:::note[처음이라면 여기까지]
① 답안은 **6칸짜리 빈칸 채우기**라고 생각하세요. 상황 정리 / 원인 후보 / 확인 방법 / 즉시 완화 / 근본 해결 / 재발 방지.

② 원인은 **하나로 찍지 말고 2~3개 후보**를 쓰고, "이걸 보면 가려진다"는 확인 방법을 붙여요.

③ 원인을 찾기 전에 **사용자 피해부터 멈추는 한 줄**(롤백, 기능 끄기)을 꼭 넣어요.

④ 해결책은 **2개 이상** 쓰고 각각의 단점을 말한 뒤 하나를 골라요. 이것만 지켜도 감점의 대부분을 피해요.
:::

## 쉽게 이해하기

응급실 의사를 떠올려 보세요. 환자가 "배가 아파요" 하고 들어왔어요.

좋은 의사는 바로 수술하지 않아요. 먼저 **증상을 듣고**(언제부터, 어디가, 얼마나), 위험하면 **응급 처치**로 상태부터 안정시켜요. 그다음 "맹장염일 수도, 장염일 수도, 결석일 수도" 하고 **후보를 여러 개** 떠올린 뒤, 피검사·CT 같은 **검사**로 하나씩 지워요. 그렇게 **진단**이 나오면 **치료**를 하는데, 수술과 약물 중 무엇이 나은지 환자 상황에 맞춰 골라요. 마지막으로 "기름진 음식 줄이세요" 같은 **재발 방지** 안내를 해요.

서술형 답안도 똑같아요. 증상 듣기 = 상황 정리, 후보 떠올리기 = 원인 가설, 검사 = 지표·로그 확인, 응급 처치 = 즉시 완화, 치료 = 근본 해결, 생활 습관 안내 = 재발 방지예요.

단, 실제 장애 대응에서는 의사와 순서가 조금 달라요. 답안에 쓰는 순서는 "가설 → 확인 → 완화"지만, 현장에서는 **완화를 가장 먼저** 하는 경우가 많아요. 원인이 다 밝혀질 때까지 사용자가 기다려 줄 수 없으니까요. 그래서 답안에도 "원인 확인보다 먼저 이걸 한다"고 순서를 적어 주면 좋아요.

## 제대로 알기

### 왜 구조가 필요한가

서술형 채점자는 "원인을 맞혔나"만 보지 않아요. 실무에서는 원인을 처음부터 아는 경우가 드물기 때문이에요. 그래서 이런 걸 봐요.

- 증상에서 **범위를 좁혀 가는 순서**가 있는가
- 추측과 확인된 사실을 **구분**하는가
- 사용자 피해를 **먼저** 생각하는가
- 해결책마다 **대가(트레이드오프, 얻는 것과 잃는 것)**를 아는가

구조 없이 아는 걸 다 쏟아 내면, 맞는 말이 있어도 이 네 가지가 안 보여요. 6단 구조는 이 네 가지를 자연스럽게 드러내는 틀이에요.

### 답안 6단 구조

| 단 | 쓸 내용 | 핵심 질문 | 분량 감각 |
|---|---|---|---|
| 1. 상황 정리·영향 범위 | 문제에 주어진 단서를 내 말로 다시 정리 | 무엇이, 언제부터, 누구에게, 어디까지? | 2~3줄 |
| 2. 가설(원인 후보) | 원인 후보 2~3개, 가능성 높은 순 | 이 증상을 설명할 수 있는 건 뭐뭐가 있나? | 번호 목록 2~3개 |
| 3. 확인 방법 | 후보를 가려 줄 지표·로그·도구 | 무엇을 보면 후보 하나가 지워지나? | 2~4줄 |
| 4. 즉시 완화 | 원인을 몰라도 피해를 멈추는 조치 | 지금 당장 사용자 피해를 어떻게 멈추나? | 1~2줄 |
| 5. 근본 해결·트레이드오프 | 해결책 2개 이상 + 장단점 + 내가 고른 것과 이유 | 무엇을 얻고 무엇을 잃나? 그래서 무엇을? | 작은 표 1개 + 2~3줄 |
| 6. 재발 방지 | 다음엔 먼저 알거나 아예 안 생기게 | 같은 일이 또 생기면 어떻게 더 빨리 알까? | 1~2줄 |

각 단을 조금 더 풀면 이래요.

**1. 상황 정리·영향 범위**
문제를 그대로 베끼지 말고, 단서가 가리키는 방향을 한 문장으로 써요. 예: "한 API만 느리고 배포가 없었으니, 공용 자원보다 그 API의 쿼리를 먼저 의심해요." 이 한 문장이 있으면 이후 가설이 왜 그 순서인지 설명이 돼요. **영향 범위**(피해가 어디까지 번졌나)도 여기서 짚어요. 일부 사용자인지 전체인지, 한 서버인지 전부인지에 따라 의심할 곳이 달라져요.

**2. 가설(원인 후보)**
원인 후보를 2~3개 쓰고, 가능성이 높은 것부터 놓아요. 가능성이 낮은 후보도 "이건 다른 API도 영향받았을 테니 우선순위 낮음"처럼 이유를 달아 두면 좋은 점수를 받아요. 지우는 이유까지 보여 주는 거니까요.

**3. 확인 방법**
"로그를 본다"로 끝내지 말고, **무슨 값이 어떻게 나오면 어떤 후보가 맞는지**를 써요. 예: "`tomcat.threads.busy`가 최대치에 붙어 있으면 스레드 고갈", "스레드 덤프에서 같은 외부 호출 지점에 스레드가 몰려 있으면 타임아웃 없는 호출". 도구 이름 + 볼 값 + 판단 기준, 이 세 가지가 한 세트예요.

**4. 즉시 완화**
**완화**(mitigation, 원인은 그대로 두고 피해만 줄이는 조치)는 원인 확정 전에 할 수 있는 일이에요. 최근 배포와 시점이 겹치면 롤백, 특정 기능이 문제면 기능 끄기(기능 플래그), 특정 서버가 문제면 트래픽에서 빼기가 대표적이에요. 완화하기 전에 **증거(스레드 덤프, 힙 덤프)를 먼저 남긴다**는 한 줄을 넣으면 더 좋아요. 재시작하면 증거가 사라지니까요. 자세한 흐름은 [장애 대응·롤백·포스트모템](../incident-response/)에 있어요.

**5. 근본 해결·트레이드오프**
해결책은 최소 2개를 비교해요. 하나만 쓰면 "왜 그게 최선인지"를 보여 줄 방법이 없어요. 작은 표(방법 / 장점 / 단점)를 그리고, 마지막에 "저는 A를 고르겠어요. 이 상황은 ~라서 A의 단점이 덜 아프기 때문이에요"처럼 **상황에 기댄 이유**를 써요. "A가 제일 좋아서"는 이유가 아니에요.

**6. 재발 방지**
고친 걸로 끝내지 않고 "다음에는 어떻게 더 빨리 알아챌까, 아예 안 생기게 할까"를 써요. 알림(지표가 기준을 넘으면 울리게), 테스트(동시성 테스트, 장애 주입 테스트), 리뷰 체크리스트, 포스트모템 정도면 충분해요.

<Aside type="tip" title="외우는 문장">
"먼저 상황을 정리하면 ~예요. 원인 후보는 ①②③이고, ~을 보면 가릴 수 있어요. 원인 확인과 별개로 지금은 ~로 피해부터 막아요. 근본 해결은 A와 B가 있는데, ~라서 A를 골라요. 재발 방지로 ~를 둬요."
</Aside>

### 나쁜 답 vs 좋은 답

같은 문제를 두고 두 답안을 비교해 볼게요. 문제는 [외부 API 장애 대응](../external-api-failure/)의 상황 1이에요.

> 메인 페이지에 붙은 상품 추천 API(외부 서비스)가 장애로 응답이 10초 넘게 걸리기 시작하더니, 추천과 상관없는 주문 API까지 타임아웃이 나며 서비스 전체가 멈췄어요.

**나쁜 답**

> 외부 API 장애가 원인입니다. 서버를 증설하고, 서킷브레이커와 Resilience4j를 적용하고, 모니터링을 강화하겠습니다. 추천 업체에도 연락하겠습니다.

틀린 단어는 없는데 점수가 낮아요. 이유를 하나씩 보면 이래요.

| 문제점 | 왜 감점인가 |
|---|---|
| "외부 API 장애가 원인" | 문제에 이미 적힌 말이에요. **왜 상관없는 주문까지** 죽었는지가 핵심인데 설명이 없어요. |
| 서버 증설 | 늘린 서버의 스레드도 똑같이 추천 호출에 묶여요. 원인과 안 맞는 해결이에요. |
| 서킷브레이커, Resilience4j | 이름만 있어요. 무엇을 막는지, 열렸을 때 사용자에게 뭘 보여 줄지 없어요. 게다가 Resilience4j는 서킷브레이커 같은 패턴을 구현한 라이브러리 이름이라, 패턴과 도구를 나란히 쓴 것뿐이에요. |
| 모니터링 강화 | 어떤 값을 볼지 없어요. |
| 즉시 완화 없음 | 서비스 전체가 멈춘 상황인데 지금 당장 무엇을 할지 빠졌어요. |
| 트레이드오프 없음 | 왜 그 방법인지, 대가는 뭔지 없어요. |

**좋은 답**

> **상황 정리**: 주문은 추천을 안 쓰는데 같이 멈췄으니, 추천 호출이 **공용 자원(요청 스레드 풀, DB 커넥션 풀)을 다 붙잡은** 연쇄 장애로 봐요.
>
> **원인 후보**: ① 추천 호출에 타임아웃이 없거나 너무 김 ② 추천 호출이 트랜잭션 안에 있어 DB 커넥션까지 묶음 ③ 추천과 주문이 같은 스레드 풀을 칸막이 없이 공유.
>
> **확인 방법**: `tomcat.threads.busy`가 최대치에 붙었는지, 스레드 덤프에서 추천 호출 지점(소켓 읽기)에 스레드가 몰렸는지, `hikaricp.connections.pending`이 쌓였는지 봐요. 셋 다 맞으면 ①②가 겹친 거예요.
>
> **즉시 완화**: 원인 확인과 별개로 지금 기능 플래그로 추천 영역을 꺼서 주문부터 살려요. 끄기 전에 스레드 덤프를 몇 장 떠 둬요.
>
> **근본 해결**: 짧은 타임아웃(변경 작지만 상대가 계속 죽으면 짧은 대기가 반복), 서킷브레이커 + 인기 상품 폴백(죽은 동안 아예 안 불러 스레드가 안 묶이지만 실패율 기준 튜닝 필요), 벌크헤드(추천 동시 호출 상한, 넘치면 즉시 폴백). 타임아웃을 기본으로 깔고 서킷과 벌크헤드를 같이 붙여요. 추천은 틀려도 손해가 작은 데이터라 폴백으로 대체해도 괜찮기 때문이에요. 트랜잭션 안에 있었다면 밖으로 빼요.
>
> **재발 방지**: 외부 API별 지연·에러율 알림을 두고, 스테이징에서 추천 API를 일부러 늦추는 장애 주입 테스트를 해요.

나쁜 답에 있던 "서킷브레이커"는 좋은 답에도 있어요. 차이는 **왜 필요한지, 무엇을 얻고 잃는지, 다른 것과 어떻게 엮는지**가 붙었느냐예요. 개념 설명은 [외부 API 장애 대응](../external-api-failure/)과 [장애 격리 패턴](../../architecture/resilience/)에 있어요.

### 감점 패턴

이 섹션 페이지들의 "흔한 감점 답안"을 모아 보면 다섯 가지로 묶여요.

| 감점 패턴 | 예 | 고치는 법 |
|---|---|---|
| 도구 이름만 나열 | "APM, 로그, EXPLAIN으로 확인하겠습니다" | 도구 + 볼 값 + 판단 기준. "EXPLAIN에서 `type=ALL`이면 전체 읽기" |
| 원인 하나로 단정 | "인덱스가 없어서입니다" | 후보 2~3개 + 각각을 가리는 확인 방법 |
| 완화 없이 원인부터 | 서비스가 멈췄는데 분석 얘기만 함 | "원인 확인과 별개로 지금은 ~로 막는다" 한 줄 |
| 트레이드오프 없음 | "Redis를 쓰겠습니다" | 해결책 2개 이상, 각각의 단점, 상황에 기댄 선택 이유 |
| 재발 방지 없음 | 고치고 끝 | 알림·테스트·체크리스트 중 하나라도 |

자주 나오는 "만능 오답"도 있어요. 원인과 안 맞는데 습관처럼 쓰는 해결책이에요.

- **서버를 늘린다**: DB 쿼리가 느리거나, 외부 API에 스레드가 묶였거나, 교착상태면 늘린 서버도 똑같이 막혀요.
- **메모리(힙)를 늘린다**: 누수라면 죽는 시점만 늦춰요([메모리 누수·OOM·GC 폭주](../memory-oom/)).
- **재시작한다**: 증상은 사라지지만 증거(덤프)도 같이 사라져요. 재시작 전에 덤프를 떠야 해요.
- **synchronized를 붙인다**: 서버가 여러 대면 소용없어요([동시성: 재고·포인트·중복 요청](../concurrency-stock-points/)).

### 모르는 부분 다루기

문제에 처음 보는 기술이 나오거나, 원인이 확신이 안 설 때가 있어요. 이때 빈칸으로 두거나 아는 척 단정하는 게 가장 나빠요. 대신 **"확인하겠다" + 어떻게**를 써요.

- 나쁜 예: "정확한 원인은 추가 확인이 필요합니다."
- 좋은 예: "이 부분은 확신이 없어요. 배포 시각과 에러 시작 시각이 겹치는지, 새 버전 서버에서만 에러가 나는지 보면 배포 문제인지 가릴 수 있어요. 겹치면 롤백부터 하겠어요."

요령은 세 가지예요.

1. **모르는 건 모른다고 표시**하고, 아는 범위(공통 원리)로 가설을 세워요. 처음 보는 기술이라도 "줄이 밀린다 → 처리 속도보다 들어오는 속도가 빠르다"처럼 일반 원리로 접근할 수 있어요.
2. **확인 방법을 구체적으로** 붙여요. 무엇을 보면 내 가설이 맞는지 틀린지 갈리는지.
3. **틀려도 안전한 완화**를 고려해요. 원인을 몰라도 롤백, 기능 끄기, 트래픽 빼기는 할 수 있어요.

### 분량 감각

시간·분량 제한은 회사와 전형마다 다를 수 있으니 안내를 따르세요. 일반적인 감각은 이래요.

- 6단이 **모두** 있는 게 한 단을 길게 쓰는 것보다 나아요. 시간이 모자라면 각 단을 한두 줄로 줄이더라도 6칸을 다 채워요.
- 가장 공들일 곳은 **5단(근본 해결·트레이드오프)**이에요. 작은 표 하나와 선택 이유 두세 줄.
- 개념 설명은 한 줄이면 돼요. "갱신 손실(두 요청이 같은 값을 읽고 덮어써서 하나가 사라지는 문제)"처럼 괄호로 짧게 풀고 넘어가요. 교과서처럼 길게 설명하면 정작 판단이 묻혀요.
- 숫자가 있으면 써요. "Tomcat 기본 스레드 200개", "p99 응답 시간(가장 느린 1%를 뺀 나머지가 이 안에 끝나는 시간)" 같은 구체적인 값이 "많아요", "느려요"보다 훨씬 설득력 있어요. 단, 확신 없는 숫자는 지어내지 말고 "기본값 확인 필요"라고 써요.

### 심화: 문제 유형마다 6단이 어떻게 달라지나

뼈대는 같아도 단마다 무게가 달라요.

| 유형 | 무게가 실리는 단 | 이유 |
|---|---|---|
| 데이터가 틀어짐(동시성) | 2·5단 | 원인이 코드 구조라 완화보다 해결책 비교가 핵심. 틀어진 데이터 보정도 써야 해요 |
| 느림(쿼리·외부 API) | 3단 | "어디서 시간을 쓰는지" 판별이 답의 절반 |
| 서버가 죽음(메모리·장애) | 4단 | 피해 차단과 증거 확보 순서가 중요 |
| 원인 불명(로그 추적) | 1·3단 | 공통점 찾기와 증거 모으는 방법이 핵심 |
| 큰 작업 설계(트래픽·마이그레이션) | 5·6단 | 사전 준비와 되돌릴 수 있는지가 핵심 |

설계 면접(새 시스템을 그려 보라는 문제)은 순서가 달라요. 요구사항 묻기 → 규모 추정 → 설계 순으로 가요. 그쪽은 [시스템 설계 면접 푸는 법](../../system-design/design-approach/)을 보세요.

## 면접 질문

<details>
<summary>Q. 서비스에 장애가 나면 무엇부터 하나요?</summary>

**답변(30초)** 원인을 찾기 전에 사용자 피해부터 멈춰요. 먼저 무엇이 언제부터 어디까지 영향받는지 확인하고 팀에 알려요. 최근 배포와 시점이 겹치면 롤백하고, 특정 기능이 문제면 기능 플래그로 꺼요. 피해가 멈춘 게 지표로 확인되면 그다음에 원인을 찾고, 끝나면 포스트모템으로 재발 방지책을 정해요.

**꼬리질문**
- Q. 롤백했는데 원인을 어떻게 찾나요? → 롤백 전에 떠 둔 덤프·로그와, 배포 차이(diff)를 봐요. 그래서 완화 전에 증거부터 남겨요.
- Q. 롤백이 안 되는 경우는요? → DB 스키마를 바꿨거나 데이터를 이미 바꿨으면 코드만 되돌려도 안 맞을 수 있어요. 그땐 기능 끄기나 수정 배포로 가요.
</details>

<details>
<summary>Q. 원인을 모르는 문제가 나오면 어떻게 답하나요?</summary>

**답변(30초)** 모른다고 단정하거나 빈칸으로 두지 않고, 가설과 확인 방법으로 답해요. 증상을 설명할 수 있는 후보를 두세 개 세우고, 어떤 지표나 로그를 보면 후보가 지워지는지 적어요. 그리고 원인과 상관없이 할 수 있는 완화(롤백, 기능 끄기)를 같이 말해요.

**꼬리질문**
- Q. 후보가 너무 많으면요? → 영향 범위로 좁혀요. 전체가 느리면 공용 자원, 한 API만이면 그 코드, 한 서버만이면 그 서버의 상태나 입력을 먼저 봐요.
</details>

<details>
<summary>Q. 완화와 근본 해결은 어떻게 다른가요?</summary>

**답변(30초)** 완화는 원인은 그대로 두고 피해만 멈추는 조치예요. 롤백, 기능 끄기, 문제 서버를 트래픽에서 빼기 같은 거예요. 근본 해결은 원인 자체를 고쳐서 같은 조건이 와도 안 터지게 하는 거예요. 타임아웃 추가, 쿼리 수정, 락 방식 변경 같은 거예요. 장애 중엔 완화가 먼저고, 근본 해결은 원인이 확인된 뒤에 해요.

**꼬리질문**
- Q. 재시작은 완화인가요? → 네, 잠깐 증상을 없애는 완화예요. 다만 증거가 사라지고 원인이 남아 있으면 다시 터지니, 덤프를 먼저 뜨고 근본 해결과 짝지어야 해요.
</details>

<details>
<summary>Q. 서술형에서 해결책을 왜 여러 개 쓰라고 하나요?</summary>

**답변(30초)** 하나만 쓰면 왜 그게 최선인지 보여 줄 수 없기 때문이에요. 해결책마다 얻는 것과 잃는 것이 있어서, 두세 개를 비교하고 "이 상황에선 이 단점이 덜 아프니까 이걸 고른다"고 써야 판단력이 드러나요. 예를 들어 재고 차감이면 조건부 UPDATE, 비관적 락, 낙관적 락을 충돌 빈도로 비교해 골라요.

**꼬리질문**
- Q. 다 좋아 보이면 어떻게 고르나요? → 상황의 제약을 봐요. 충돌이 잦은가, 정확성이 돈과 관련 있나, 지금 당장 바꿀 수 있는 범위인가. 그 제약에서 단점이 가장 덜 아픈 걸 골라요.
</details>

## 서술형 연습

아래 상황은 답안 **구조 자체**를 연습하려고 지어낸 짧은 문제예요. 정답 원인보다 6칸을 다 채우는 데 집중하세요.

<details>
<summary>연습 1: 배포 30분 뒤부터 로그인 API의 5xx 에러(서버 쪽 오류) 비율이 평소 1% 미만에서 20%로 올랐어요. 다른 API는 정상이에요. 6단 구조로 짧게 답해 보세요.</summary>

**상황 정리**
로그인 API 하나만, 배포 직후부터 에러가 늘었어요. 시점이 겹치니 **이번 배포의 변경**을 가장 먼저 의심해요. 다른 API는 정상이라 서버 전체 자원 문제일 가능성은 낮아요.

**원인 후보**
1. 새 코드의 로그인 로직 버그
2. 새 버전에서 쓰는 설정값·환경 변수 누락
3. 로그인이 의존하는 다른 서비스나 DB 쪽 문제가 우연히 같은 시간에 생김(가능성 낮음, 시점만 보고 단정하지 않으려고 남겨 둠)

**확인 방법**
에러 시작 시각이 배포 완료 시각과 맞는지, 새 버전 서버에서만 에러가 나는지(버전별 에러율), 에러 로그의 예외 종류와 스택 트레이스, 배포 차이(diff)에 로그인 관련 변경이 있는지 봐요.

**즉시 완화**
시점이 겹치면 원인 확정 전에 **이전 버전으로 롤백**해요. 롤백 뒤 에러율이 평소로 내려오는지 지표로 확인해요. 단, DB 스키마를 바꾼 배포라면 코드만 되돌려도 안 맞을 수 있어서 먼저 확인해요.

**근본 해결과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 원인 고친 뒤 재배포 | 새 기능을 살림 | 원인 파악 시간이 걸림 |
| B. 문제 기능만 플래그로 끄고 나머지 배포 유지 | 다른 변경은 살림 | 플래그가 미리 있어야 함 |

롤백으로 피해를 멈췄으니 A로 가요. 원인을 확인하고 테스트를 추가한 뒤 다시 배포해요.

**재발 방지**
일부 서버에만 먼저 배포하는 카나리 배포와 에러율 기준 알림을 둬서, 20%까지 가기 전에 알아채고 자동으로 멈추게 해요.

**채점 포인트**: 배포 시점 상관 → 변경 의심, 버전별 에러율로 확인, 원인 확정 전 롤백, 롤백 후 지표 확인, 스키마 변경 시 롤백 주의, 카나리·알림.

**흔한 감점 답안**: 로그부터 한참 분석하고 롤백은 안 함, "서버를 늘린다"(한 API만의 문제), 시점이 겹친다는 이유만으로 확인 없이 "배포 버그"라고 단정.
</details>

<details>
<summary>연습 2: 아래 나쁜 답을 6단 구조의 좋은 답으로 고쳐 보세요. 문제는 "새 버전 배포 뒤로 며칠마다 서버가 느려지다 죽고, 재시작하면 멀쩡해요"이고, 나쁜 답은 "메모리가 부족하니 서버 메모리를 늘리고, 주기적으로 재시작하겠습니다"예요.</summary>

**나쁜 답의 문제**
메모리가 "부족"한지 "새는지" 가리지 않았어요. 늘리기와 재시작 둘 다 완화일 뿐 원인이 그대로라, 죽는 간격만 바뀌어요. 확인 방법·트레이드오프·재발 방지가 없어요.

**고친 답**

**상황 정리**: 시간이 지날수록 나빠지고 재시작하면 회복되니, 무언가 계속 쌓이는 **메모리 누수**를 먼저 의심해요. 새 버전 배포 뒤부터라 이번 변경과 관련 있을 가능성이 커요.

**원인 후보**: ① 크기 제한 없는 캐시·컬렉션에 계속 쌓임 ② 정리 안 된 ThreadLocal이나 무제한 큐 ③ 누수가 아니라 트래픽 증가로 힙이 그냥 작음(이 경우 재시작 직후에도 빨리 차야 해서 가능성 낮음).

**확인 방법**: GC 후 남는 메모리(바닥선)가 톱니처럼 제자리인지, 계단처럼 계속 오르는지 봐요. 오르면 누수예요. 클래스별 객체 수 표(히스토그램)를 시간 간격을 두고 여러 번 떠서 늘어나는 객체를 찾고, 힙 덤프에서 그 객체를 붙잡은 쪽을 따라가요.

**즉시 완화**: 다음에 죽기 전에 OOM 시 자동 힙 덤프 옵션을 켜 두고, 새 버전과 관련이 확인되면 이전 버전으로 롤백해요. 재시작이 필요하면 덤프를 먼저 떠요.

**근본 해결**: 원인 객체를 붙잡은 코드를 고쳐요. 캐시라면 크기 제한·만료를 넣거나(로컬에서 빠르지만 서버마다 값이 다를 수 있음), 외부 캐시로 옮겨요(일관성은 낫지만 네트워크 비용). 상황에 따라 골라요.

**재발 방지**: 바닥선 추세에 알림을 걸고, 캐시·컬렉션을 추가할 땐 크기 제한을 리뷰 체크 항목으로 둬요.

자세한 도구와 판단은 [메모리 누수·OOM·GC 폭주](../memory-oom/)에 있어요.

**채점 포인트**: 부족 vs 누수 구분, 바닥선 추세로 확인, 재시작 전 덤프 확보, 늘리기·재시작은 완화일 뿐이라는 인식, 해결책 비교, 알림.

**흔한 감점 답안**: 나쁜 답의 문장만 다듬음(구조는 그대로), "GC 알고리즘을 바꾼다"(살아 있는 객체는 어떤 GC도 못 치움).
</details>
