:::tip[한 줄 요약]
메모리 장애는 **"누가 죽였나"부터** 가려요. 앱 로그에 `OutOfMemoryError`가 있으면 JVM이 던진 것이고, 로그 없이 **Exit 137 / OOMKilled**면 컨테이너 한도를 넘어 커널이 죽인 거예요. JVM OOM이면 GC 후 남는 양(바닥선)이 **계단처럼 계속 오르는지**로 누수인지 보고, **힙 덤프**로 누가 객체를 붙잡고 있는지 찾아 코드를 고쳐요. 힙만 늘리는 건 장애를 미룰 뿐이에요.
:::

:::note[처음이라면 여기까지]
① 자바에도 메모리 누수가 있어요. GC는 "아무도 안 쓰는 객체"만 치워요. 어딘가에서 참조를 계속 들고 있으면 못 치워요.

② 누수의 흔한 증상 순서는 "점점 느려짐 → CPU 높음 → 죽고 재시작"이에요. 느려지는 이유는 GC가 쉬지 않고 돌기 때문이에요.

③ 진단 순서는 **에러 메시지로 종류 구분 → 메모리 그래프 모양 보기 → 힙 덤프로 범인 찾기** 세 단계예요.

④ 면접에선 서술형 1~3번부터 연습하세요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

방에 택배 상자를 매일 들여놓는다고 해 봐요. 다 뜯은 상자는 청소할 때 버려요. 그런데 "언젠가 쓸지 몰라" 하고 **포스트잇을 붙여 둔 상자**는 청소하는 사람이 못 버려요.

처음엔 티가 안 나요. 며칠 지나면 방이 좁아지고, 청소하는 사람은 방이 꽉 찰 때마다 불려 와요. 청소 시간이 길어지는데 버릴 건 거의 없어요. 그동안 방 주인은 아무것도 못 해요. 결국 문이 안 닫힐 만큼 차면 끝이에요.

여기서 방은 **힙**(heap, 자바 객체가 사는 메모리), 청소는 **GC**(가비지 컬렉션, 안 쓰는 객체를 자동으로 치우는 일), 포스트잇은 **참조**(객체를 가리키는 변수)예요. 포스트잇이 남은 상자가 계속 쌓이는 게 **메모리 누수**, 문이 안 닫히는 순간이 **OOM**(OutOfMemoryError, 메모리 부족 에러), 청소부가 쉬지 않고 불려 다니는 상태가 **GC 폭주**예요.

방을 두 배로 넓히면 어떻게 될까요? 꽉 차는 날이 두 배 늦어질 뿐, 결국 또 차요. 포스트잇을 떼는 게 진짜 해결이에요.

단, 실제로는 누수가 아니어도 OOM이 나요. 한 번에 상자 1만 개가 들어오면(대량 조회) 방이 깨끗해도 넘쳐요. 그래서 "계속 쌓이는지"를 먼저 봐야 해요.

GC 자체가 처음이라면 → [JVM 구조와 GC](../../java/jvm-gc/)를 먼저 읽어 보세요. 이 페이지는 GC 원리를 다시 설명하지 않고 **장애를 푸는 순서**에 집중해요.

## 이 유형을 푸는 순서

서술형 답안 기본 틀(→ [서술형 답안 쓰는 법](../how-to-answer/))을 메모리 장애에 맞추면 이렇게 돼요.

1. **증상 확인**: 응답이 점점 느려지나? CPU가 높은데 트래픽은 평소와 같나(→ GC가 CPU를 먹는 중)? 프로세스가 죽고 재시작되나? 배포 후 며칠 지나서 생기나(→ 시간에 비례해 쌓이는 것)?
2. **영향 범위**: 서버 한 대만인가, 전부인가? 같은 버전이 깔린 서버가 다 비슷한 주기로 죽으면 코드 문제일 가능성이 커요.
3. **누가 죽였나 구분**: 앱 로그에 `OutOfMemoryError: ...`가 있나, 아니면 로그 없이 Exit 137(`OOMKilled`)인가? 둘은 원인과 보는 곳이 완전히 달라요.
4. **어느 OOM인지 메시지로 구분**: `Java heap space`인지 `Metaspace`인지 등. 아래 표를 보세요.
5. **그래프 모양 보기**: GC 로그나 힙 사용량 그래프에서 **GC 직후 바닥선**이 일정한지(톱니), 계속 오르는지(계단).
6. **즉시 완화**: 재시작·인스턴스 교체·롤백으로 서비스를 살려요. 단, **재시작 전에 덤프부터** 확보해요. 재시작하면 증거가 사라져요.
7. **원인 찾기**: 클래스 히스토그램을 시간차로 여러 번 → 힙 덤프 → 가장 많은 메모리를 붙잡은 객체(지배 객체) → 그 객체를 붙잡은 경로(GC Root) → 코드.
8. **근본 해결과 재발 방지**: 코드 수정(크기 제한 캐시, `remove()`, 크기 제한 큐, 페이징) + 힙 사용률·GC 시간 알림 + 덤프 옵션 상시 켜기.

## 제대로 알기

### OOM 메시지 종류

`OutOfMemoryError` 뒤에 붙는 메시지가 "어느 칸이 찼는지" 알려줘요. 진단의 첫 단계는 이걸 읽는 거예요.

| 메시지 | 무엇이 찼나 | 먼저 의심할 것 |
|---|---|---|
| `Java heap space` | 힙에 새 객체를 둘 자리가 없음 | 힙이 그냥 작음 / 누수 / 한 번에 대량 로딩 |
| `GC overhead limit exceeded` | GC에 시간 대부분(약 98%)을 쓰고도 거의(2% 미만) 못 비우는 상태가 반복 | 살아 있는 데이터가 힙에 겨우 들어가는 상태. 주로 **Parallel GC**에서 보는 메시지(G1 기본 환경에선 보통 `Java heap space`로 나옴) |
| `Metaspace` | 클래스 정보 저장 공간 | 클래스로더 누수(재배포 반복), 프록시·동적 클래스 무한 생성 |
| `Compressed class space` | 압축된 클래스 포인터 공간 | Metaspace와 비슷 |
| `Requested array size exceeds VM limit` | 힙 여유와 무관, 배열 하나가 VM 한계보다 큼 | 크기 계산 버그 |
| `Direct buffer memory` | 힙 **밖**의 다이렉트 버퍼 | Netty·NIO 클라이언트의 버퍼 해제 누락 (공식 문서에서 이 문구 확인 못함) |
| `unable to create native thread` | 힙이 아니라, OS가 스레드를 더 안 만들어 줌(스레드 수 한도 또는 네이티브 메모리 부족) | 스레드 무한 생성, 스레드 수 한도 (공식 문서에서 이 문구 확인 못함) |

메시지별 GC 쪽 설명은 → [JVM 구조와 GC의 OOM 메시지 표](../../java/jvm-gc/)에도 있어요.

`Metaspace`는 기본 한도(`MaxMetaspaceSize`)가 **무제한**이에요. "무제한이니 안 터진다"가 아니라, 한도가 없으니 결국 컴퓨터(또는 컨테이너)의 메모리를 다 먹어요.

### JVM OOM과 컨테이너 OOMKilled(137)는 다르다

| | JVM `OutOfMemoryError` | 컨테이너 `OOMKilled` |
|---|---|---|
| 누가 | JVM이 스스로 던짐 | Linux 커널(OOM killer)이 프로세스를 강제 종료 |
| 기준 | 힙(`-Xmx`)이나 Metaspace 등 JVM 내부 한도 | 컨테이너 메모리 limit(힙 + 힙 밖 전부) |
| 흔적 | 앱 로그에 스택트레이스, 덤프 옵션 켜면 `.hprof` | 앱 로그엔 아무것도 없음, 덤프도 없음 |
| 확인 | 앱 로그 | `kubectl describe pod` → `Reason: OOMKilled`, `Exit Code: 137` |

137은 128 + 9, 즉 **SIGKILL**(거부할 수 없는 강제 종료 신호)로 죽었다는 뜻이에요. JVM은 예외를 던질 틈도 없이 꺼져서 `HeapDumpOnOutOfMemoryError`도 소용이 없어요. 137 자체와 `docker inspect`로 확인하는 법은 → [컨테이너 vs VM](../../infra/container-vs-vm/), limits 설정은 → [ConfigMap·Secret·리소스 관리](../../infra/k8s-config/)에 있어요.

컨테이너 메모리는 힙만이 아니에요.

```text
컨테이너 메모리 사용량 ≈ 힙(-Xmx 이하)
                      + Metaspace(클래스 정보)
                      + 스레드 수 × 스레드 스택(-Xss, Linux x64 기본 1MB)
                      + 코드 캐시 + 다이렉트 버퍼 + GC 자체 구조 ...
```

그래서 `-Xmx`를 limit과 똑같이 주면 힙 밖 몫이 없어서 힙이 멀쩡해도 OOMKilled가 나요.

### 컨테이너에서 힙 크기는 어떻게 정해지나

- JVM은 Linux에서 **컨테이너 인식**(`UseContainerSupport`)이 기본으로 켜져 있어요. 컨테이너 메모리 limit을 "이 컴퓨터의 메모리"로 봐요.
- `-Xmx`를 안 주면 기본 최대 힙은 그 메모리의 **25%**(`MaxRAMPercentage` 기본값)예요. limit 2GiB면 힙은 약 512MB예요.
- 흔한 실수는 오히려 반대예요. limit은 넉넉한데 힙이 25%라 `Java heap space`가 나요.
- 실무에선 `-XX:MaxRAMPercentage`를 50~75% 정도로 올려 쓰는 경우가 많아요(관례, 정답 수치는 아님). 남는 몫은 힙 밖 메모리용이에요.

### 그래프 모양: 톱니 vs 계단

힙 사용량 그래프(Actuator/Micrometer 지표나 GC 로그)를 보면 두 모양이 있어요. 지표 수집은 → [관측성](../../infra/observability/)

- **정상(톱니)**: 요청이 오면 오르고, GC가 돌면 뚝 떨어져요. **GC 직후 바닥선이 거의 일정**해요.
- **누수(계단)**: 톱니는 있는데 GC가 돌 때마다 **바닥선이 조금씩 올라가요.** 안정된 부하에서도 계속 오르면 누수 신호예요.
- **순간 대량 로딩**: 바닥선은 평소대로인데 특정 시점에 확 치솟아 OOM이 나요. 누수가 아니라 한 요청이 너무 많이 올린 거예요.

GC 로그는 `-Xlog:gc`(간단히) 또는 `-Xlog:gc*:파일명`(자세히, 파일로)으로 켜요. 로그에서 `Pause Full`이 자꾸 찍히는데 `30M->29M`처럼 전후가 거의 같으면, 청소해도 버릴 게 없다는 뜻이에요.

### 확인 명령

`<pid>`는 자바 프로세스 번호예요. `jcmd -l`로 목록을 보고, 메인 클래스 이름 일부로도 지정할 수 있어요. 컨테이너 안의 JVM은 밖에서 안 보이니 `kubectl exec`로 들어가서 실행해요.

| 명령 | 보여주는 것 | 운영 영향 |
|---|---|---|
| `jcmd <pid> GC.heap_info` | 힙 전체·사용량, Metaspace 사용량 개요 | 중간 |
| `jcmd <pid> GC.class_histogram` | 클래스별 객체 수·바이트 순위 | **높음** — 실행 순간 Full GC가 일어남(실험 확인) |
| `jcmd <pid> GC.heap_dump 파일명` | 힙 전체를 `.hprof` 파일로 | **높음** — Full GC 요청, 파일이 힙 크기만큼 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 나는 순간 자동으로 덤프 | 평소엔 비용 없음, **기본은 꺼짐** |
| `-XX:HeapDumpPath=경로` | 덤프 저장 위치(`%p`는 PID로 바뀜) | 컨테이너면 재시작해도 남는 볼륨에 |
| `kubectl describe pod` | `OOMKilled`, `Exit Code: 137`, `Restart Count` | 없음 |

히스토그램은 **한 번만 보면 잘 몰라요.** `byte[]`(`[B`)나 `String`은 원래 늘 상위권이라서요. 몇 분 간격으로 여러 번 떠서 **계속 늘어나는 클래스**를 찾아요. 히스토그램은 "무엇이" 쌓이는지 보여주고, "누가 붙잡고 있는지"는 힙 덤프를 Eclipse MAT 같은 도구로 열어 **GC Root까지의 경로**로 확인해요.

공식 문서는 `jmap -histo`보다 `jcmd`를 권장해요.

### 실험: 작은 힙에서 누수 재현해 보기

`static` 리스트에 100KB 배열을 20ms마다 넣기만 하고 절대 비우지 않는 7줄짜리 프로그램을, 힙 32MB(`-Xmx32m`)로 돌려 봤어요. GC 로그를 정리하면 이래요(실험 예시, 시각·경로는 생략).

```text
GC(0)  Pause Young (Normal) (G1 Evacuation Pause)        14M->14M(32M)
GC(1)  Pause Full (Heap Inspection Initiated GC)         16M->16M(32M)   ← 히스토그램 실행 순간
GC(5)  Pause Young (Concurrent Start) (G1 Evacuation Pause) 20M->20M(32M)
...    To-space exhausted
GC(22) Pause Full (G1 Compaction Pause)                  30M->30M(32M)
GC(24) Pause Full (G1 Compaction Pause)                  30M->29M(32M)
java.lang.OutOfMemoryError: Java heap space
Dumping heap to ./java_pid<pid>.hprof ...
```

읽는 법이에요.

1. **Young GC 전후가 같아요**(`14M->14M`, `20M->20M`). 전부 살아 있어서 하나도 못 버렸어요. 바닥선이 계단처럼 올라가요.
2. **`To-space exhausted`**: GC가 살아남은 객체를 옮겨 둘 빈칸이 없어요.
3. **Full GC가 연달아 돌아요**(한 번 실행에서 `Pause Full` 12줄). 그래도 `30M->29M`, 거의 못 비워요. 이 구간이 **GC 폭주**예요.
4. 결국 `Java heap space`, 그리고 옵션을 켜 둬서 덤프가 저장돼요. 덤프 크기는 약 33MB로 **힙 크기와 비슷**했어요.

같은 시점 `GC.class_histogram` 1위는 `[B`(byte[])였어요. 약 7,900개, 16MB로 2위(String, 0.18MB)와 비교가 안 됐어요.

32MB 힙이라 Full GC가 1ms 안팎이었지만, 운영 힙(수 GB)에선 한 번에 수백 ms~초 단위가 될 수 있어요. 그 시간 동안 앱이 멈추니 응답이 느려지고 CPU는 GC가 다 써요.

<Aside type="caution" title="OOM 뒤의 JVM은 믿지 마세요">
실험에서 OOM 직후 예외를 처리하는 도중에도 또 OOM이 났어요. OOM을 `catch`해서 계속 돌리면 반쯤 고장 난 상태로 요청을 받아요. 실무에선 덤프를 남기고 **죽은 뒤 재시작**되게 하는 편이 안전해요(`-XX:+ExitOnOutOfMemoryError`, 기본 꺼짐).
</Aside>

### 흔한 누수 원인

| 원인 | 왜 쌓이나 | 고치는 법 |
|---|---|---|
| `static` Map/List 캐시 | 넣기만 하고 지우지 않음. static은 앱이 끝날 때까지 살아 있음 | 크기 제한·만료(TTL)가 있는 캐시(Caffeine 등) |
| ThreadLocal 미정리 | 스레드 풀의 스레드는 안 죽어서, `remove()` 안 하면 값이 계속 남음. 다음 요청에 남의 정보가 보이는 버그도 생김 | `finally`에서 `remove()` |
| 무제한 큐 | `Executors.newFixedThreadPool`의 작업 큐는 크기 제한이 없음. 처리가 느려지면 작업이 끝없이 쌓임 | `ThreadPoolExecutor` + 크기 제한 큐 + 거절 정책 → [스레드 풀](../../java/thread-pool/) |
| 리스너·콜백 해제 누락 | 등록만 하고 해제 안 하면 목록이 계속 커짐 | 해제 짝 맞추기 |
| 클래스로더 누수 | 재배포 때 옛 클래스들이 안 풀림 | `Metaspace` OOM으로 나타남 |
| (누수 아님) 대량 로딩 | 수십만 행 `findAll()`, 파일 통째로 읽기 | 페이징·스트리밍·청크 처리 |

### 심화: 운영 중 덤프·히스토그램의 비용

- `GC.class_histogram`과 `GC.heap_dump`는 공식 문서에서 영향도 **High**예요. 기본 옵션이면 Full GC(앱 전체 멈춤)를 일으켜요. 트래픽을 받는 인스턴스는 로드밸런서에서 빼고 떠요.
- 덤프 파일은 힙 크기만큼 커요. 힙 8GB면 덤프도 수 GB라 **디스크 여유**를 먼저 봐요. 컨테이너 안 임시 디스크에 쓰면 재시작 때 사라지니 볼륨을 붙여요.
- 덤프에는 힙에 있던 **모든 데이터**가 들어 있어요. 사용자 개인정보, 토큰, 비밀번호가 그대로 있을 수 있어요. 운영 데이터처럼 접근 권한을 제한하고, 분석 후 지워요.
- 더 가벼운 대안: **JFR**(Java Flight Recorder, JVM 내장 기록기)의 `OldObjectSample` 이벤트로 오래 살아남는 객체와 그 출처를 볼 수 있어요. 힙 덤프보다 부담이 적어요.

### 심화: 힙 밖 메모리 추적

OOMKilled인데 힙은 멀쩡하다면 힙 밖을 봐야 해요. `-XX:NativeMemoryTracking=summary`로 켜고 `jcmd <pid> VM.native_memory baseline`을 찍은 뒤, 시간이 지나 `jcmd <pid> VM.native_memory summary.diff`로 어느 영역(스레드, 클래스, 내부 등)이 늘었는지 비교해요. 켜 두면 5~10% 정도 느려질 수 있어서 상시보다는 진단용이에요.

다이렉트 버퍼 한도는 `-XX:MaxDirectMemorySize`로 정해요(안 주면 JVM이 자동으로 정함).

## 면접 질문

<details>
<summary>Q. 자바는 GC가 있는데도 메모리 누수가 생기나요?</summary>

**답변(30초)** 네, 생겨요. GC는 어디에서도 참조하지 않는 객체만 치우기 때문에, 더 이상 안 쓰는데 참조가 남아 있으면 못 치워요. 대표적인 예가 넣기만 하고 지우지 않는 static Map 캐시, 스레드 풀에서 remove하지 않은 ThreadLocal, 크기 제한 없는 작업 큐예요. 이런 객체가 시간이 지나며 쌓이면 GC 후에도 사용량이 계속 올라가다 OOM이 나요.

**꼬리질문**
- Q. 그럼 static을 쓰면 안 되나요? → static 자체가 문제가 아니라, 계속 커지는데 크기 제한·삭제가 없는 컬렉션이 문제예요.
- Q. ThreadLocal은 왜 스레드 풀에서 특히 위험해요? → 풀의 스레드는 요청이 끝나도 안 죽어서 값이 계속 남고, 다음 요청에 이전 사용자 정보가 보일 수도 있어요.
</details>

<details>
<summary>Q. OutOfMemoryError가 나면 무엇부터 보나요?</summary>

**답변(30초)** 에러 메시지부터 봐요. `Java heap space`면 힙, `Metaspace`면 클래스 정보 영역, `unable to create native thread`면 힙이 아니라 스레드 수 한도나 네이티브 메모리 문제라서 보는 곳이 달라요. 힙이면 GC 로그나 힙 그래프에서 GC 후 바닥선이 계속 오르는지 보고, 오르면 누수로 보고 힙 덤프를 분석해요. 그래서 평소에 `HeapDumpOnOutOfMemoryError`를 켜 둬요.

**꼬리질문**
- Q. 그 옵션은 기본으로 켜져 있나요? → 아니요, 기본은 꺼져 있어요. 덤프 경로도 `HeapDumpPath`로 정해 둬요.
- Q. 힙 덤프에서 무엇을 보나요? → 메모리를 가장 많이 붙잡은 객체와, 그 객체를 붙잡은 참조 경로(GC Root)를 따라가 코드 위치를 찾아요.
</details>

<details>
<summary>Q. 메모리 누수와 그냥 힙이 작은 것은 어떻게 구분하나요?</summary>

**답변(30초)** GC 직후 남는 양, 즉 바닥선의 추세로 구분해요. 트래픽이 일정한데 바닥선이 계단처럼 계속 올라가면 누수예요. 바닥선은 일정하고 피크만 한도에 닿거나 특정 요청 직후 치솟으면 용량 부족이나 대량 로딩이에요. 누수면 힙을 늘려도 장애 간격만 길어지고, 용량 부족이면 힙을 늘리거나 조회를 나누는 게 맞아요.

**꼬리질문**
- Q. 히스토그램 한 번으로는 왜 부족해요? → byte[]·String은 원래 늘 상위라서, 시간차로 여러 번 떠서 계속 늘어나는 클래스를 봐야 해요.
</details>

<details>
<summary>Q. GC 로그에 Full GC가 계속 찍혀요. 무슨 상황인가요?</summary>

**답변(30초)** 힙이 거의 차서 GC가 공간을 확보하려고 계속 돌지만 살아 있는 객체가 많아 거의 못 비우는 상태예요. Full GC 동안 앱이 멈추니 응답이 느려지고 CPU는 GC가 다 써요. OOM 직전 단계라 보면 돼요. 즉시 그 인스턴스를 트래픽에서 빼고 덤프를 확보한 뒤, 바닥선이 오른 원인을 찾아요.

**꼬리질문**
- Q. 로그에서 뭘 보면 확신할 수 있죠? → `Pause Full`의 전후 용량이 거의 같은지(`30M->29M`)를 봐요. 거의 못 비우면 살아 있는 데이터가 힙을 채운 거예요.
</details>

<details>
<summary>Q. 쿠버네티스에서 Pod가 OOMKilled, Exit 137로 재시작돼요. Java OOM과 뭐가 다른가요?</summary>

**답변(30초)** 137은 커널이 SIGKILL로 죽였다는 뜻이고, 컨테이너 메모리 limit을 넘어서예요. JVM이 던지는 OutOfMemoryError가 아니어서 앱 로그에도 안 남고 힙 덤프도 안 생겨요. 컨테이너 메모리는 힙에 Metaspace, 스레드 스택, 다이렉트 버퍼가 더해진 거라, `-Xmx`를 limit에 꽉 맞췄거나 힙 밖 메모리가 늘었는지를 봐요. 확인은 `kubectl describe pod`의 Reason과 Exit Code로 해요.

**꼬리질문**
- Q. 컨테이너에서 기본 힙은 얼마예요? → 컨테이너 limit의 25%(`MaxRAMPercentage` 기본값)예요. 보통 50~75% 정도로 올려 쓰고 나머지는 힙 밖 몫으로 둬요.
- Q. 힙 밖 메모리는 어떻게 봐요? → NativeMemoryTracking을 켜고 `jcmd VM.native_memory`로 시간차 비교를 해요.
</details>

<details>
<summary>Q. 운영 중인 서버에서 힙 덤프를 떠도 되나요?</summary>

**답변(30초)** 뜰 수는 있지만 비용을 알고 떠야 해요. 덤프는 기본적으로 Full GC를 일으켜 앱이 멈추고, 파일이 힙 크기만큼이라 디스크가 넉넉해야 해요. 또 힙 안의 개인정보·토큰이 그대로 들어 있어 보안 관리가 필요해요. 그래서 그 인스턴스를 로드밸런서에서 빼고 뜨고, 평소엔 OOM 때 자동 덤프 옵션을 켜 두는 편이 나아요.

**꼬리질문**
- Q. 더 가벼운 방법은요? → 클래스 히스토그램(이것도 Full GC는 있음)이나 JFR의 OldObjectSample로 먼저 좁혀 볼 수 있어요.
</details>

## 서술형 연습

모두 연습용으로 만든 가상 상황이에요.

<details>
<summary>상황 1: 새 버전을 배포하고 나서, 며칠이 지나면 응답이 점점 느려지다가 서버가 죽고 재시작돼요. 재시작 직후엔 멀쩡해요. 어떻게 접근할까요?</summary>

**상황 파악**
"며칠 지나면", "재시작하면 멀쩡"은 시간에 비례해 무언가 쌓인다는 신호예요. 느려지는 건 힙이 차면서 GC가 자주, 길게 돌기 때문일 가능성이 커요. 새 버전 배포 이후부터라면 그 배포에 들어간 코드 변경이 1순위 용의자예요.

**원인 후보**
1. 메모리 누수: static 캐시, ThreadLocal 미정리, 리스너 해제 누락 등 새 코드가 참조를 붙잡음
2. 힙이 새 버전의 정상 사용량에 비해 작음(누수 아님)
3. 메모리가 아닌 다른 자원(커넥션·스레드)이 쌓임

**확인 순서**
1. 앱 로그에서 죽을 때 `OutOfMemoryError` 메시지가 있는지, 있으면 어떤 종류인지 봐요. 로그가 없고 Exit 137이면 컨테이너 한도 쪽(상황 2)으로 가요.
2. 힙 사용량 그래프를 배포 전후로 비교해요. GC 후 바닥선이 계단처럼 오르면 누수(1번), 일정하면 용량 문제(2번)예요.
3. 누수라면 `GC.class_histogram`을 몇 시간 간격으로 떠서 계속 늘어나는 클래스를 찾고, 힙 덤프를 MAT로 열어 그 객체를 붙잡은 경로를 따라가요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 이전 버전으로 롤백 | 즉시 증상 해소, 원인이 배포라는 것도 확인됨 | 새 기능도 같이 빠짐 |
| B. 주기적 재시작(예약) | 코드 수정 없이 버팀 | 원인이 그대로, 트래픽이 늘면 주기가 짧아짐 |
| C. 힙 덤프 분석 후 코드 수정 | 근본 해결 | 분석에 시간이 걸림, 덤프 확보가 먼저 필요 |

**내가 고를 방법**
먼저 다음 장애 때 증거가 남도록 `HeapDumpOnOutOfMemoryError`와 덤프 경로(볼륨)를 켜 둬요. 당장 서비스가 불안하면 A로 롤백해 안정시키고, 롤백 전에 증상이 있는 인스턴스 하나를 트래픽에서 빼서 덤프를 떠 둬요. 그다음 C로 지배 객체와 GC Root 경로를 찾아 코드를 고쳐요(예: 캐시에 크기 제한, ThreadLocal `remove()`). B는 고칠 때까지의 임시방편으로만 써요. 재발 방지로 GC 후 힙 사용률과 GC 시간 비율에 알림을 걸어요.

**채점 포인트**: 시간 비례 증상 → 누수 의심, OOM 메시지 확인, 바닥선 추세(톱니 vs 계단), 재시작 전 덤프 확보, HeapDumpOnOutOfMemoryError(기본 꺼짐), 히스토그램 여러 번 비교, 덤프의 GC Root 경로, 롤백(즉시 완화)과 코드 수정(근본) 분리, 알림.

**흔한 감점 답안**: "재시작 스케줄을 걸면 된다"로 끝냄, "힙을 늘린다"만 말함, 덤프 없이 재시작해서 증거를 날림.
</details>

<details>
<summary>상황 2: 쿠버네티스 Pod가 몇 시간마다 재시작돼요. kubectl describe를 보니 OOMKilled, Exit Code 137인데, 앱 로그에는 OutOfMemoryError가 한 줄도 없고 힙 덤프도 안 남아요.</summary>

**상황 파악**
137은 SIGKILL이고 Reason이 OOMKilled면 컨테이너 메모리 limit을 넘어 커널이 죽인 거예요. JVM은 예외를 던질 기회가 없었으니 로그와 덤프가 없는 게 자연스러워요. 즉 "JVM 힙"이 아니라 "프로세스 전체 메모리"가 limit을 넘었어요.

**원인 후보**
1. `-Xmx`(또는 MaxRAMPercentage)를 limit에 너무 가깝게 줘서 힙 밖 몫이 없음
2. 힙 밖 메모리 증가: 스레드 수 폭증(스레드마다 스택), 다이렉트 버퍼(Netty 등) 해제 누락, Metaspace 증가
3. limit 자체가 앱의 정상 사용량보다 작음

**확인 순서**
1. 실행 옵션에서 `-Xmx`·`MaxRAMPercentage`와 Pod limit을 비교해요.
2. 컨테이너 메모리 그래프와 JVM 힙 그래프를 겹쳐 봐요. 힙은 평평한데 컨테이너 메모리만 오르면 힙 밖이에요.
3. 스레드 수 지표를 봐요. 힙 밖이 의심되면 `-XX:NativeMemoryTracking=summary`를 켜고 `jcmd VM.native_memory`로 baseline 대비 어느 영역이 늘었는지 비교해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 힙 비율을 낮춤(예: MaxRAMPercentage를 limit의 50~75%) | 힙 밖 몫 확보, 바로 적용 | 힙이 줄어 `Java heap space` 위험이 생길 수 있음 |
| B. limit 상향 | 즉시 안정 | 비용 증가, 힙 밖 누수라면 시간만 미룸 |
| C. 힙 밖 원인 제거(스레드 풀 상한, 버퍼 해제, 클래스 생성 줄이기) | 근본 해결 | NMT 분석 필요, 시간이 걸림 |

**내가 고를 방법**
먼저 limit과 힙 설정을 비교해요. `-Xmx`가 limit과 거의 같다면 A가 1순위예요. 힙 밖 몫이 확보되는지 확인하고, 그래도 컨테이너 메모리가 시간에 따라 계속 오르면 힙 밖 누수로 보고 NMT로 영역을 찾아 C로 고쳐요. B는 C를 하는 동안 서비스를 안정시키는 임시 조치로만 써요. 이 상황에서 `HeapDumpOnOutOfMemoryError`는 도움이 안 된다는 것도 짚어요(JVM OOM이 아니니까요).

**채점 포인트**: 137 = 128 + 9(SIGKILL), OOMKilled ≠ JVM OOM, 그래서 로그·덤프 없음, 컨테이너 메모리 = 힙 + 힙 밖(Metaspace·스레드 스택·다이렉트 버퍼), Xmx vs limit 비교, MaxRAMPercentage(기본 25%), 힙 그래프와 컨테이너 그래프 비교, NMT, limit 상향의 한계.

**흔한 감점 답안**: "Java 힙이 부족하니 -Xmx를 올린다"(오히려 더 자주 죽음), 힙 덤프를 분석하겠다고 함(안 생김).
</details>

<details>
<summary>상황 3: OOM이 자꾸 나서 힙을 2GB에서 4GB로 두 배 늘렸어요. 그랬더니 장애가 사흘마다에서 엿새마다로 바뀌었을 뿐, 여전히 죽어요.</summary>

**상황 파악**
힙을 두 배로 했더니 장애 간격도 정확히 두 배가 됐어요. 이건 메모리가 일정한 속도로 쌓이고 있다는 강한 증거예요. 힙 크기가 아니라 **쌓이는 속도**가 문제라서, 힙을 늘리는 방법은 이 장애를 고칠 수 없어요.

**원인 후보**
1. 요청량에 비례해 쌓이는 누수(캐시에 키가 계속 추가됨, 요청마다 리스너 등록 등)
2. 무제한 큐에 처리 못 한 작업이 쌓임(소비가 생산을 못 따라감)
3. 시간 기반으로 쌓이는 데이터(만료 안 되는 세션·토큰 보관)

**확인 순서**
1. 힙 그래프에서 GC 후 바닥선의 기울기를 봐요. 2GB, 4GB 둘 다 같은 기울기로 오른다면 누수 확정이에요.
2. 히스토그램을 시간차로 떠서 개수가 꾸준히 느는 클래스를 찾아요.
3. 힙 덤프에서 그 객체를 붙잡은 컬렉션(예: static `HashMap`, 큐)을 찾아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 힙을 더 늘림 | 간격이 더 길어짐 | 근본 해결 아님, 힙이 크면 Full GC 한 번이 더 길어짐 |
| B. 누수 지점 코드 수정 | 근본 해결 | 원인 분석 필요 |
| C. 큐·캐시에 상한을 두고 넘치면 거절/제거 | 누수의 피해를 막는 안전장치 | 거절된 작업 처리 정책 필요 |

**내가 고를 방법**
A는 이미 효과가 없다는 게 증명됐어요. 오히려 힙이 커질수록 GC 폭주 구간의 멈춤도 길어져요. 힙 덤프로 쌓이는 객체를 찾아 B로 고쳐요. 동시에 같은 종류의 실수가 다시 나와도 OOM까지 가지 않게, 캐시는 크기 제한 캐시로 바꾸고 작업 큐는 크기 제한 큐와 거절 정책을 둬요(C). 바닥선 기울기를 알림으로 걸어 두면 다음 누수는 장애 전에 잡을 수 있어요.

**채점 포인트**: 간격 비례 = 일정 속도로 쌓임 = 누수, 힙 증설은 시간만 미룸, 큰 힙의 Full GC 비용, 바닥선 기울기, 히스토그램 추세, 덤프로 붙잡은 컬렉션 찾기, 크기 제한 캐시·큐, 추세 알림.

**흔한 감점 답안**: "8GB로 더 늘린다", "GC 알고리즘을 바꾼다"(살아 있는 객체는 어떤 GC도 못 치움).
</details>

<details>
<summary>상황 4: 메모리가 계속 오르는 서버가 있어요. 원인을 찾으려고 운영 중인 서버에서 바로 힙 덤프를 뜨려고 해요. 괜찮을까요? 주의할 점은?</summary>

**상황 파악**
힙 덤프는 누수 분석에 가장 중요한 자료라 뜨는 것 자체는 맞아요. 하지만 운영 서버에서는 세 가지 비용이 있어요. 멈춤(성능), 용량(디스크), 개인정보(보안)예요.

**원인 후보(위험 요소)**
1. **멈춤**: `jcmd GC.heap_dump`는 기본적으로 Full GC를 요청하고, 힙 전체를 쓰는 동안 앱이 응답을 못 해요. 히스토그램도 실행 순간 Full GC가 일어나요(실험에서 `Heap Inspection Initiated GC` 확인).
2. **용량**: 덤프 크기 ≈ 힙 사용량이에요. 힙 8GB면 수 GB 파일이 생겨 디스크가 차면 다른 장애가 날 수 있어요.
3. **개인정보**: 힙에 있던 사용자 정보, 세션, 토큰, 비밀번호가 그대로 파일에 담겨요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 인스턴스를 로드밸런서에서 빼고 `jcmd GC.heap_dump` | 사용자 영향 없음, 지금 상태 그대로 확보 | 남은 인스턴스에 부하가 몰림, 수동 작업 |
| B. `HeapDumpOnOutOfMemoryError`로 OOM 때 자동 | 가장 결정적인 순간을 확보, 평소 비용 없음 | 다음 장애까지 기다려야 함, 경로·디스크 준비 필요 |
| C. 히스토그램·JFR로 먼저 좁히기 | 덤프보다 가볍고 파일 작음 | "누가 붙잡나"까지는 덤프보다 약함, 히스토그램도 Full GC는 있음 |

**내가 고를 방법**
우선 C로 시간차 히스토그램을 떠서 의심 클래스를 좁혀요. 덤프가 필요하면 A로 해당 인스턴스를 트래픽에서 빼고, 디스크 여유를 확인한 뒤 압축 옵션(`-gz`)으로 떠요. 동시에 B를 상시 켜고 덤프 경로를 재시작해도 남는 볼륨으로 둬요. 덤프 파일은 운영 데이터처럼 다뤄요. 접근 권한을 제한하고, 외부(개인 PC, 공용 채널)로 옮기지 않고, 분석이 끝나면 지워요.

**채점 포인트**: 덤프는 필요하지만 비용 있음, Full GC(STW)·영향도 High, 트래픽에서 제외 후 수행, 파일 크기 ≈ 힙, 디스크·볼륨, 개인정보·토큰 포함 → 접근 통제·삭제, OOM 자동 덤프 상시, 히스토그램·JFR로 먼저 좁히기.

**흔한 감점 답안**: "덤프는 가벼우니 그냥 뜬다", 개인정보 언급 없음, 덤프 파일을 슬랙에 올려 공유.
</details>

<details>
<summary>상황 5: 상품 조회가 느려서 HashMap에 결과를 담는 로컬 캐시를 만들었어요. 응답은 빨라졌는데, 2주 뒤부터 OOM이 나기 시작했어요.</summary>

**상황 파악**
캐시를 만든 시점과 OOM 시점이 2주 차이라는 건, 캐시가 조금씩 커지다 힙을 다 채웠다는 뜻이에요. 그냥 `HashMap`은 크기 제한도, 만료도 없어서 한 번 들어간 키는 앱이 끝날 때까지 안 빠져요. 상품 ID·검색 조건처럼 키 종류가 많으면 끝없이 커져요.

**원인 후보**
1. 캐시에 크기 제한·만료가 없음(가장 유력)
2. 키가 예상보다 다양함(검색어·페이지 번호까지 키에 포함)
3. 키 객체의 `equals`/`hashCode`가 잘못돼 같은 키가 다른 키로 계속 추가됨 → [equals와 hashCode](../../java/equals-hashcode/)
4. 여러 스레드가 동시에 쓰는 `HashMap`(동시성 문제도 따로 있음)

**확인 순서**
힙 덤프에서 가장 큰 지배 객체가 그 캐시 `HashMap`인지, 엔트리 수가 얼마인지 봐요. 키 분포를 보면 2번, 같은 내용의 키가 중복돼 있으면 3번이에요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 크기 제한 + 만료가 있는 로컬 캐시(Caffeine 등) | 메모리 상한 보장, 코드 변경 작음 | 서버마다 캐시가 달라 데이터 불일치 가능, 히트율이 조금 떨어질 수 있음 |
| B. Redis 같은 외부 캐시로 이동 | 서버 힙과 분리, 서버끼리 공유 | 네트워크 왕복 비용, 운영할 시스템이 늘어남 → [캐시 패턴](../../redis/cache-patterns/) |
| C. 캐시를 빼고 쿼리·인덱스 개선 | 캐시 불일치 문제 자체가 없음 | 원래 느린 이유가 남아 있으면 효과 제한 → [느린 쿼리](../slow-query/) |

**내가 고를 방법**
당장은 A로 바꿔요. 최대 개수(또는 용량)와 만료 시간을 정해 메모리 상한을 확실히 두고, 히트율 지표를 같이 봐요. 데이터가 서버 간에 꼭 같아야 하거나 캐시가 커서 힙을 많이 먹으면 B로 가요. 그리고 캐시가 원래 느린 쿼리를 가리고 있는 거라면 C도 같이 봐요. "캐시는 반드시 상한과 만료를 정한다"를 팀 규칙으로 두면 재발을 막을 수 있어요.

**채점 포인트**: 무제한 HashMap = 누수, 시간 지연 후 OOM, 덤프에서 지배 객체 확인, 크기 제한·만료(TTL·eviction), 로컬 vs 외부 캐시 트레이드오프(일관성·네트워크), 키 설계·equals/hashCode, 히트율 모니터링, 원인 쿼리 개선.

**흔한 감점 답안**: "힙을 늘린다", "주기적으로 `clear()`한다"(한순간 캐시가 비어 DB에 요청이 몰림).
</details>
