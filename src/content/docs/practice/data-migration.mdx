:::tip[한 줄 요약]
수천만 행은 **한 문장으로 바꾸지 않아요.** ① PK 범위로 잘게 나눠(청크) 청크마다 커밋 → ② 청크 사이에 쉬거나 레플리카(원본을 복사해 두는 읽기용 DB) 지연을 보며 속도 조절 → ③ 진행 위치를 저장하고 다시 돌려도 결과가 같게(멱등) → ④ 행 수·범위별 체크섬·샘플 비교로 검증. 목적은 "빨리 끝내기"가 아니라 **서비스 요청이 기다리는 시간을 잘게 쪼개는 것**이에요.
:::

:::note[처음이라면 여기까지]
① 큰 UPDATE 한 문장은 끝날 때까지 바꾼 행 전부를 잠그고 있어요. 그동안 같은 행을 고치려는 서비스 요청은 줄을 서요.

② 그래서 1만 행 정도씩 나눠서 바꾸고 바로바로 커밋해요. 다음 범위는 OFFSET이 아니라 **"마지막으로 처리한 id 다음부터"**로 찾아요.

③ 배치는 중간에 죽을 수 있어요. 다시 돌려도 값이 두 번 더해지지 않게, 어디까지 했는지 기록해 둬요.

④ 서술형은 상황 1·4번부터 연습하세요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

이사를 한다고 해 봐요. 짐 전부를 한 번에 들고 나가려 하면 현관이 막혀요. 그동안 다른 가족은 드나들 수도 없어요. 그러다 중간에 넘어지면 짐을 전부 다시 집 안으로 들여놔야 해요.

그래서 짐을 **상자 단위**로 나눠 옮겨요. 상자 하나 옮기고 나면 현관이 잠깐 비어서 가족이 지나갈 수 있어요. 벽에 "12번 상자까지 옮김"이라고 적어 두면, 점심 먹고 와서도 13번부터 이어서 하면 돼요. 다 옮긴 뒤에는 목록과 상자 수를 맞춰 보고, 몇 개는 열어서 내용물도 확인해요.

DB에선 짐이 행, 상자가 **청크**(chunk, 한 번에 처리하는 행 묶음), 현관이 **락**(lock, 다른 트랜잭션이 같은 행을 못 고치게 막는 잠금), 벽의 메모가 **진행 위치**(마지막으로 처리한 id)예요.

단, 실제로는 상자로 나눈다고 이사가 빨리 끝나진 않아요. 쉬는 틈을 주면 오히려 더 오래 걸려요. 대신 **다른 사람이 기다리는 시간**이 확 줄어요.

## 이 유형을 푸는 순서

"대량 데이터를 바꿔야 한다" 또는 "배치가 문제를 일으킨다"는 상황을 받으면 아래 순서를 답안 뼈대로 써요. 답안 쓰는 일반 구조는 [서술형 답안 쓰는 법](../how-to-answer/)에 있어요.

| 단계 | 할 일 | 이 주제에서 구체적으로 |
|---|---|---|
| 1. 증상 확인 | 무엇이 언제부터 | 배치 시간대와 겹치는 락 대기·1205 에러, 레플리카 지연, 배치 진행률 |
| 2. 영향 범위 | 누가 피해를 보나 | 같은 테이블을 쓰는 API, 레플리카에서 읽는 API, 다른 배치 |
| 3. 즉시 완화 | 일단 피해를 멈춤 | 배치 중지 스위치, 속도 낮추기. 큰 트랜잭션 `KILL`은 롤백 비용 확인 후 |
| 4. 원인 찾기 | 숫자로 확인 | `innodb_trx`(잠근 행 수·시작 시각), `Seconds_Behind_Source`, `History list length`, EXPLAIN |
| 5. 근본 해결 | 배치 구조 바꾸기 | PK 키셋 청크 + 청크마다 커밋, 속도 조절, 멱등 + 진행 위치 저장 |
| 6. 재발 방지 | 다음엔 먼저 알기 | 배치 표준 템플릿, 지연·락 대기 알림, 검증 단계 필수화 |

### 증상별 원인 후보와 확인 도구

| 증상 | 원인 후보 | 확인 도구 | 처방 |
|---|---|---|---|
| 배치 도는 동안 같은 테이블 쓰기 API가 멈추거나 50초 뒤 `ERROR 1205` | 큰 트랜잭션이 락을 오래 쥠, 인덱스 없는 조건으로 넓게 잠금 | `information_schema.innodb_trx`의 `trx_rows_locked`·`trx_started`, `data_lock_waits` | PK 범위 청크 + 청크마다 커밋 |

| 오래 걸려 `KILL`했더니 DB가 더 느려짐 | 대량 롤백이 원작업보다 오래 걸림 | `innodb_trx`의 롤백 중 상태 | 처음부터 작은 문장 여러 개로 |
| 전체 조회가 점점 느려지고 언두가 쌓임 | 긴 트랜잭션이 purge를 막음 | `SHOW ENGINE INNODB STATUS`의 `History list length` | 트랜잭션 짧게 |

## 제대로 알기

### 한 문장 UPDATE가 위험한 이유

`UPDATE member SET grade = ...` 한 줄은 짧아 보여도, 행이 5천만 개면 트랜잭션 하나가 5천만 행을 바꾸는 거예요. autocommit이어도 마찬가지예요. **트랜잭션 크기 = 커밋 사이에 바꾼 양**이에요. MySQL 8.4 문서 기준으로 이런 문제가 생겨요.

1. **락을 끝까지 쥐어요.** InnoDB는 UPDATE가 훑은 행에 락을 걸고, 락은 커밋이나 롤백 때 한꺼번에 풀려요. 조건이 인덱스를 못 타서 전체를 훑으면 테이블 모든 행이 잠기고 INSERT까지 막혀요. 같은 행을 고치려는 요청은 기다리다 `innodb_lock_wait_timeout`(기본 50초)을 넘기면 `ERROR 1205`로 실패해요.
2. **언두 로그가 쌓여요.** **언두 로그**(undo log, 바꾸기 전 값을 적어 둔 기록)는 롤백에도 쓰이고, 다른 트랜잭션이 옛 값을 읽을 때(MVCC)도 쓰여요. 긴 트랜잭션이 있으면 옛 기록을 못 지워서(purge가 막혀서) `History list length`가 커지고, 그 행을 읽는 다른 쿼리도 옛 버전을 재구성하느라 느려져요.
3. **실패하면 롤백도 오래 걸려요.** 대량 변경의 롤백은 원래 작업보다 몇 배 오래 걸릴 수 있어요. 프로세스를 죽여도 재시작 때 롤백이 다시 시작돼요.
4. **복제가 밀려요.** 바이너리 로그(binlog, 레플리카에 보낼 변경 기록)는 트랜잭션 전체를 **커밋 때 한 덩어리로** 기록해요. 레플리카는 커밋 뒤에야 받기 시작하고, 그 큰 덩어리를 적용하는 동안 뒤 트랜잭션이 줄을 서요. 트랜잭션 크기에는 `max_binlog_cache_size`라는 상한도 있어서 넘으면 실패하고 롤백돼요.

문서의 권고도 같아요. 주기적으로 커밋하고, 큰 UPDATE·DELETE 하나를 적은 행을 다루는 여러 문장으로 나누라고 해요.

### 실험: 한 문장 vs 청크

100만 행 테이블에서 같은 컬럼을 세 방식으로 바꾸면서, 다른 세션이 단건 UPDATE를 계속 날려 **기다린 시간**을 쟀어요. 아래 숫자는 한 번 재 본 실험 예시예요.

| 방식 | 전체 시간 | 다른 세션 최대 대기 |
|---|---|---|
| 한 문장 `UPDATE mig SET grade='X'` | 약 2초 | 약 2초 (전체 시간과 거의 같음) |
| PK 범위 1만 행 청크 × 100번, 청크마다 커밋 | 2.38초 | 0.11초 |
| 위와 같고 청크 사이 20ms 쉼 | 4.71초 | 0.03초 |

부하가 없을 때 같은 단건 UPDATE의 최대값은 0.02초였어요. 청크 + 쉼이면 거의 평소 수준이에요.

**읽는 법**: 청크로 나눠도 전체 시간은 줄지 않아요. 쉬면 오히려 2배가 돼요. 대신 다른 요청의 최대 대기가 2초 → 0.1초 → 0.03초로 줄어요. 락을 쥐는 단위가 "전체"에서 "청크 하나"로 작아졌기 때문이에요.

한 문장 실행 1초 뒤 `innodb_trx`를 보니 잠근 행(`trx_rows_locked`)이 약 50만 개였고, 끝날 때까지 늘기만 했어요. 이 실험은 100만 행이라 2초였지만, 수천만 행이면 같은 비율로 수십 초~분이 되어 50초 타임아웃을 넘을 수 있어요.

### 다음 범위 찾기: OFFSET 말고 키셋

청크를 나누는 방법은 두 가지예요.

```sql
-- OFFSET: 앞의 k행을 다 읽고 버린 뒤 N행
SELECT ... FROM mig ORDER BY id LIMIT 10000 OFFSET 980000;

-- 키셋: 마지막 id 다음부터 바로 N행 (PK 범위 스캔)
SELECT ... FROM mig WHERE id > 980000 ORDER BY id LIMIT 10000;
```

같은 1만 행을 읽는데 결과가 이렇게 달랐어요(EXPLAIN ANALYZE, 실험 예시).

| 쿼리 | 걸린 시간 | 읽은 행 |
|---|---|---|
| `LIMIT 10000 OFFSET 10` | 1.07ms | 10,010 |
| `LIMIT 10000 OFFSET 980000` | 88ms | 990,000 |
| `WHERE id > 980000 LIMIT 10000` | 1.33ms | 10,000 |

OFFSET은 뒤 페이지일수록 앞을 다 읽고 버려서 약 80배 느렸어요. 전체로 보면 청크 수가 늘수록 제곱으로 늘어나요. **키셋**(keyset, "마지막으로 본 키 다음부터" 찾는 방식)은 몇 번째 청크든 비용이 같아요.

OFFSET은 정확성 문제도 있어요. 처리 중에 행이 추가·삭제되거나, `WHERE processed = 0`처럼 처리하면 대상에서 빠지는 조건과 같이 쓰면 경계가 밀려서 행을 건너뛰거나 두 번 처리해요.

키셋 방식은 두 가지 모양이 있어요.

- `WHERE id > :last ORDER BY id LIMIT N`: 항상 N행씩. 매번 마지막 id를 받아 둬야 해요.
- `WHERE id BETWEEN :s AND :s + N - 1`: 고정 범위. id에 구멍이 많으면 빈 청크가 생기지만 해롭지는 않아요.

둘 다 "다음 시작점"이 숫자 하나라서 진행 위치로 저장하기 좋아요. 청크 조건은 꼭 **PK나 인덱스 범위**여야 해요. 그래야 잠그는 범위도 그 청크로 좁아져요.

### 청크 크기와 속도 조절

청크가 너무 크면 위의 긴 트랜잭션 문제가 돌아와요. 너무 작으면 커밋마다 로그를 디스크에 쓰는 비용이 쌓여서 그게 처리량의 상한이 돼요. MySQL 문서도 "초당 수천 번 커밋"과 "몇 시간에 한 번 커밋" 둘 다 문제라고 해요. 실무에선 1천~1만 행 사이에서 시작해요.

행 수보다 **청크 하나가 걸리는 시간**을 기준으로 정하는 게 더 안정적이에요. pt-online-schema-change가 이렇게 해요. 한 번 복사가 약 0.5초(`--chunk-time` 기본값) 걸리도록 청크 크기를 자동으로 조절해요.

속도 조절(throttling)은 두 가지를 같이 써요.

- **청크 사이에 잠깐 쉬기.** 그 틈에 서비스 트랜잭션이 락·CPU·I/O를 가져가요. 실험에서 20ms만 쉬어도 최대 대기가 0.11초 → 0.03초로 줄었어요.
- **복제 지연을 보며 멈추기.** 청크마다(또는 몇 청크마다) 레플리카의 `Seconds_Behind_Source`를 확인해서 기준(예: 1초)을 넘으면 멈췄다가, 따라잡으면 재개해요. pt-online-schema-change는 `--max-lag`(기본 1초)를 넘으면 복사를 멈춰요.

그 밖에 트래픽 적은 시간대에 돌리고, p99 응답 시간·락 대기·`History list length`를 보며 사람이 누를 수 있는 **중지 스위치**를 둬요.

### 다시 돌려도 안전한(멱등) 배치

배치는 배포, OOM, 네트워크 끊김으로 중간에 죽어요. 그래서 두 가지가 필요해요. **처음부터 다시 돌려도 결과가 같을 것**(멱등, idempotent)과 **멈춘 곳부터 이어갈 수 있을 것**이에요.

멱등을 만드는 방법이에요.

1. **덮어쓰기형 SET.** `SET grade = 계산값`은 두 번 해도 같아요. `SET point = point + 100` 같은 누적형은 두 번 하면 두 배가 돼요.
2. **처리 대상 조건.** `AND grade IS NULL`을 걸면 이미 한 행은 건너뛰어요. 이 조건이 인덱스를 안 타도 PK 범위로 스캔이 제한돼서 괜찮아요.
3. **INSERT 이관이면 유니크 키 + "있으면 건너뛰기".** `INSERT IGNORE`나 `INSERT ... ON DUPLICATE KEY UPDATE`로 같은 행이 두 번 들어가지 않게 해요.
4. **진행 위치를 청크와 같은 트랜잭션에 저장.** 마지막 처리 id를 별도 테이블에 적고 청크와 함께 커밋해요.

```sql
START TRANSACTION;
UPDATE member SET grade = /* 계산식 */ 'GOLD'
 WHERE id > 1200000 AND id <= 1210000   -- 키셋 범위
   AND grade IS NULL;                     -- 처리 대상만
UPDATE backfill_progress SET last_id = 1210000 WHERE job = 'grade';
COMMIT;                                   -- 둘이 함께 반영
```

4번이 왜 같은 트랜잭션이어야 할까요? 청크는 커밋됐는데 위치 저장 전에 죽으면 그 청크를 한 번 더 하게 돼요(멱등이면 괜찮아요). 반대로 위치만 먼저 저장되고 청크가 실패하면 **그 청크를 영영 건너뛰어요.** 이건 데이터 누락이에요.

### 검증: 행 수만으로는 부족하다

값이 틀려도 행 수는 같을 수 있어요. 그래서 여러 겹으로 확인해요.

1. **행 수 비교.** 전체와 id 범위별 `COUNT(*)`.
2. **범위별 체크섬·합계 비교.** 예: id 범위마다 `SUM(CRC32(CONCAT_WS('|', col1, col2, ...)))`를 양쪽에서 계산해 비교해요. 다른 범위만 더 잘게 쪼개 찾아요.
3. **샘플 행 직접 비교.** 무작위 id 몇백 개를 양쪽에서 읽어 값을 비교해요.
4. **섀도 읽기.** 읽기를 새 곳으로 바꾸기 전 일정 기간, 양쪽을 다 읽어 결과를 비교하고 다르면 로그를 남겨요.

<Aside type="caution" title="CHECKSUM TABLE은 운영 대형 테이블에 조심">
`CHECKSUM TABLE`은 테이블 전체 체크섬을 한 번에 주지만, 도는 동안 InnoDB 테이블에 **읽기 락**을 걸어(그동안 쓰기가 막혀요) 모든 행을 하나씩 읽어요. InnoDB는 빠른 `QUICK` 방식도 지원하지 않아요. 값이 행 포맷(행을 디스크에 저장하는 형식)에 따라 달라서, 행 포맷이 다르거나 버전 업그레이드로 저장 형식이 바뀐 테이블끼리는 비교할 수 없어요. 해시라서 값이 같아도 100% 같다는 보장은 아니에요(다르면 거의 확실히 달라요). 운영 대형 테이블은 범위별 비교가 현실적이에요.
</Aside>

### 심화: 이중 쓰기와 백필이 부딪힐 때

새 테이블·컬럼으로 옮기는 동안에도 서비스 쓰기는 계속 들어와요. 그래서 **이중 쓰기**(새로 들어오는 데이터를 옛 곳과 새 곳에 같이 쓰기)와 **백필**(이미 있던 데이터 채우기)이 같이 돌아요. 단계 순서는 [무중단 DB 마이그레이션](../../architecture/db-migration-zero-downtime/)의 expand-contract에 있어요.

문제는 같은 행을 두고 경합할 때예요. 백필이 옛 값을 앱으로 읽어 온 뒤 새 곳에 쓰는 사이, 서비스가 그 행을 바꾸고 이중 쓰기로 새 곳에 최신 값을 넣었다고 해 봐요. 그다음 백필이 쓰면 **최신 값을 옛 값으로 덮어요.**

막는 방법이에요(실무 관행).

- 컬럼 백필이면 `UPDATE ... SET new = f(old) WHERE id BETWEEN ...` **한 문장으로 DB 안에서** 처리해요. 읽기와 쓰기가 행 락 안에서 한 번에 일어나요.
- 테이블 이관이면 `INSERT IGNORE`로 "이미 있으면 건너뛰기"를 해요. 이중 쓰기가 먼저 넣은 최신 값을 백필이 덮지 않아요.

### 심화: Spring Batch는 무엇을 대신해 주나

Spring Batch(6.1 문서 기준)는 위에서 손으로 짠 루프를 프레임워크로 만든 거예요.

- **청크 처리**(chunk-oriented processing): `ItemReader`가 항목을 하나씩 읽고, 필요하면 `ItemProcessor`가 가공해요. 읽은 수가 commit interval에 닿으면 그 묶음을 `ItemWriter`가 한 번에 쓰고 커밋해요. **청크 하나 = 트랜잭션 하나**예요.
- **JobRepository**: Job·JobInstance(Job + 식별 파라미터, 논리적 실행 1회)·JobExecution(실행 시도 1회)·StepExecution·ExecutionContext(프레임워크가 저장하는 키-값 상태)를 DB에 저장해요.
- **재시작**: 같은 식별 파라미터로 다시 실행하면 JobExecution은 새로 생기지만 JobInstance는 그대로라 "멈춘 곳부터" 가요. 리더가 위치를 ExecutionContext에 넣으면 커밋할 때마다 저장되고, 재시작 때 그 위치로 건너뛰어요. 같은 JobInstance가 실행 중인데 또 실행하면 `JobExecutionAlreadyRunningException`, `preventRestart()`로 막은 Job을 재시작하면 `JobRestartException`이 나요.
- **DB 리더 두 종류**: `JdbcCursorItemReader`는 SQL 한 번 + 열린 결과에서 한 행씩 전진해요. `JdbcPagingItemReader`는 페이지마다 쿼리를 따로 날리고 `sortKey`가 필수예요. 실행 사이 누락을 막으려면 sortKey에 유니크 제약이 있어야 해요. 키셋 방식의 전제와 같아요.

<Aside type="caution" title="Spring Batch를 써도 멱등은 직접 챙겨요">
프레임워크는 **커밋된 청크까지만** 위치를 저장해요. 실패한 청크는 롤백 후 다시 처리돼요. writer가 `+N` 같은 누적형이거나 외부 API·파일에 쓰면 두 번 반영될 수 있어서, writer 쪽 멱등은 여전히 필요해요.
</Aside>

성공한 JobInstance를 같은 파라미터로 다시 돌릴 때 어떤 예외가 나는지, 6.x의 Step 빌더 정확한 시그니처는 이번에 문서로 확인하지 못했어요. 면접에선 개념(청크 = 트랜잭션, JobRepository가 상태 저장, 재시작은 마지막 커밋 위치부터)으로 답하면 충분해요.

### 심화: 온라인 스키마 변경 도구 한 줄씩

- **gh-ost**(GitHub): 트리거 없이 같은 모양의 고스트 테이블에 복사하고, 진행 중 변경은 binlog를 읽어 따라 반영한 뒤 마지막에 테이블을 바꿔치기(cut-over)해요.
- **pt-online-schema-change**(Percona): 복사 테이블에 ALTER를 적용하고 청크로 복사해요. 진행 중 변경은 원본의 **트리거**가 복사본에 반영하고, 끝나면 `RENAME TABLE`로 원자적으로 교체해요. 청크 시간·복제 지연으로 속도를 자동 조절해요.

둘 다 이 페이지의 원칙(청크 + 속도 조절 + 진행 중 변경 따라잡기)을 도구로 만든 거예요.

## 면접 질문

<details>
<summary>Q. 큰 테이블을 UPDATE 한 문장으로 바꾸면 어떤 문제가 생기나요?</summary>

**답변(30초)** 트랜잭션 하나가 모든 행을 바꾸는 거라 끝날 때까지 락을 쥐어서, 같은 행을 고치려는 서비스 요청이 기다리다 50초 뒤 1205로 실패할 수 있어요. 언두 로그가 쌓여 다른 조회도 느려지고, 실패하면 롤백이 원작업보다 오래 걸려요. binlog에 커밋 때 한 덩어리로 기록돼서 레플리카 지연도 커져요. 그래서 PK 범위 청크로 나눠 청크마다 커밋해요.

**꼬리질문**
- Q. autocommit이면 괜찮지 않나요? → 문장 하나가 100만 행이면 트랜잭션도 100만 행이에요. 트랜잭션 크기는 커밋 사이 변경량이에요.
- Q. 청크로 나누면 빨라지나요? → 아니요. 실험에서 약 2초 vs 2.38초로 비슷했고 쉬면 4.71초였어요. 대신 다른 세션 최대 대기가 약 2초에서 0.03초로 줄었어요.
</details>

<details>
<summary>Q. 배치에서 OFFSET 대신 무엇으로 페이지를 나누나요? 왜요?</summary>

**답변(30초)** `WHERE id > 마지막id ORDER BY id LIMIT N` 같은 키셋 방식을 써요. OFFSET은 앞의 행을 다 읽고 버려서 뒤로 갈수록 느려져요. 실험에서 OFFSET 980000은 99만 행을 읽어 88ms, 키셋은 1만 행만 읽어 1.3ms였어요. 처리하면서 대상이 바뀌면 OFFSET은 행을 건너뛰기도 해요. 키셋은 다음 시작점이 숫자 하나라 진행 위치 저장에도 좋아요.

**꼬리질문**
- Q. Spring Batch에선요? → `JdbcPagingItemReader`의 sortKey가 이 역할이고, 누락을 막으려면 유니크해야 해요.
</details>

<details>
<summary>Q. 청크 크기는 어떻게 정하나요?</summary>

**답변(30초)** 너무 크면 긴 트랜잭션 문제가 돌아오고, 너무 작으면 커밋마다 로그 flush 비용이 처리량 상한이 돼요. 보통 1천~1만 행에서 시작하고, 행 수보다 **청크 하나가 걸리는 시간**(예: 0.5초 이하)을 기준으로 맞춰요. pt-online-schema-change가 그렇게 청크 크기를 자동 조절해요. 운영 지표를 보면서 조정해요.

**꼬리질문**
- Q. 속도는 어떻게 조절하나요? → 청크 사이에 쉬고, 레플리카 지연이 기준(예: 1초)을 넘으면 멈췄다가 재개해요.
</details>

<details>
<summary>Q. 배치가 중간에 죽었어요. 어떻게 다시 돌리나요?</summary>

**답변(30초)** 처음부터 다시 돌려도 결과가 같게(멱등) 설계해 두고, 저장된 진행 위치부터 이어가요. 멱등은 덮어쓰기형 SET, `IS NULL` 같은 대상 조건, INSERT면 유니크 키와 INSERT IGNORE로 만들어요. 진행 위치는 청크와 같은 트랜잭션에 커밋해야, 위치만 앞서 저장돼 청크를 건너뛰는 일이 없어요.

**꼬리질문**
- Q. Spring Batch는 자동으로 해 주나요? → 재시작 위치는 JobRepository·ExecutionContext가 관리하지만, 실패한 청크는 다시 처리되니 writer 멱등은 직접 챙겨야 해요.
</details>

<details>
<summary>Q. 마이그레이션이 정확히 됐는지 어떻게 검증하나요?</summary>

**답변(30초)** 행 수만 보면 값 오류를 못 잡아요. 전체·범위별 COUNT, id 범위별 체크섬(CRC32 합 등) 비교, 샘플 행 직접 비교, 읽기 전환 전 섀도 읽기 순으로 겹겹이 확인해요. `CHECKSUM TABLE`은 읽기 락을 걸고 전체를 읽으며 행 포맷·버전이 다르면 비교가 안 돼서, 운영 대형 테이블엔 범위별 비교를 써요.

**꼬리질문**
- Q. 이중 쓰기 중에 백필하면 뭐가 위험해요? → 백필이 읽어 온 옛 값으로 이중 쓰기가 넣은 최신 값을 덮을 수 있어요. DB 안 한 문장 UPDATE나 INSERT IGNORE로 막아요.
</details>

## 서술형 연습

아래 상황은 모두 실무 상황형 연습용으로 지어낸 것이에요. 실제 기출 문제가 아니에요.

<details>
<summary>상황 1: 회원 3천만 명의 `grade` 컬럼 값을 새 기준으로 일괄 변경해야 해요. 팀원이 운영 DB에 `UPDATE member SET grade = ...` 한 줄을 돌리자고 해요. 어떻게 계획하겠어요?</summary>

**상황 파악**
서비스는 계속 돌고 있고, 회원 테이블은 로그인·주문 등에서 계속 쓰여요. 한 문장이면 3천만 행이 트랜잭션 하나가 돼요. 목표는 "빨리 끝내기"가 아니라 **서비스 영향 없이 정확하게 끝내기**예요.

**한 문장의 문제(원인 후보)**
1. 끝날 때까지 바꾼 행의 락을 쥠 → 같은 회원 행을 고치는 요청이 기다리다 50초 뒤 1205
2. 언두 로그 누적, purge 막힘 → 다른 조회도 느려짐
3. 중간 실패나 `KILL` 시 롤백이 원작업보다 오래 걸림
4. binlog에 커밋 때 한 덩어리 → 레플리카가 한참 밀림, binlog 캐시 상한 초과 위험

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 한 문장 UPDATE | 코드 간단, 원자적 | 위 4가지 위험 전부 |
| B. PK 키셋 청크(1천~1만 행) + 청크마다 커밋 + 쉬기 | 락을 청크 단위로만 쥠, 서비스 대기 짧음 | 전체가 원자적이지 않음(중간 상태 존재), 총 시간 늘어남 |
| C. B + 복제 지연 감시 + 진행 위치 저장 | 레플리카 보호, 중간에 죽어도 이어감 | 배치 코드·진행 테이블 관리 |
| D. 트래픽 적은 시간대에만 실행 | 영향 더 줄임 | 기간이 길어짐 |

**내가 고를 방법**
C를 기본으로 하고 D를 더해요. 순서는 이래요.

1. 스테이징에서 청크 크기를 정해요. 청크 하나가 0.5초 이하로 끝나는 크기로요.
2. `WHERE id > :last AND id <= :last + N`에 "아직 새 기준으로 안 바뀐 행만" 고르는 대상 조건을 더하고, 덮어쓰기형 SET으로 써요.
3. 진행 위치를 청크와 같은 트랜잭션에 저장해요.
4. 청크 사이에 쉬고, `Seconds_Behind_Source`가 1초를 넘으면 멈춰요. 중지 스위치를 둬요.
5. 끝나면 범위별 COUNT·체크섬·샘플로 검증해요.

근거로, 100만 행 실험에서 한 문장은 다른 세션 최대 대기가 약 2초(문장이 끝날 때까지)였고 청크 + 20ms 쉼은 0.03초였어요(실험 예시). 3천만 행이면 한 문장 쪽은 50초 타임아웃을 넘길 수 있어요.

**채점 포인트**: 트랜잭션 크기 = 커밋 사이 변경량, 락 보유·1205, 언두/purge, 롤백 비용, binlog·복제 지연, PK 키셋 청크, 청크 크기 기준(시간), 속도 조절, 멱등·진행 위치, 검증, 실험 수치.

**흔한 감점 답안**: "새벽에 한 문장으로 돌린다"(시간만 옮김), "청크로 나누면 빨라진다"(목적을 잘못 앎), OFFSET으로 청크를 나눔, 검증 단계 없음.
</details>

<details>
<summary>상황 2: 새벽 백필 배치를 돌리자 레플리카 지연이 수십 초로 치솟았어요. 고객센터에 "방금 바꾼 주소가 안 바뀌었어요" 문의가 몰려요. 조회 API는 레플리카에서 읽어요.</summary>

**상황 파악**
쓰기는 소스(원본)에 반영됐지만, 조회는 레플리카에서 하니 사용자에겐 옛 데이터가 보여요. 배치 시작과 지연 급증이 겹치니 **백필이 복제를 밀어낸 것**을 먼저 의심해요.

**원인 후보**
1. 청크가 너무 크거나 한 문장이라, 커밋 때 큰 덩어리가 레플리카로 가서 적용하는 동안 뒤 변경이 밀림
2. 청크는 작지만 쉬지 않고 계속 돌아 레플리카 적용 속도를 넘어섬
3. 레플리카 자체 부하(무거운 조회)가 겹침

**확인 순서**
`SHOW REPLICA STATUS`의 `Seconds_Behind_Source` 추이와 배치 진행 로그의 시각을 맞춰 봐요 → 소스 `innodb_trx`에서 배치 트랜잭션 크기(`trx_rows_modified`) 확인 → 배치를 잠깐 멈췄을 때 지연이 줄어드는지 확인. `Seconds_Behind_Source`는 0과 큰 값을 오갈 수 있어서 추이로 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 즉시 배치 중지 또는 속도 낮춤 | 지연이 바로 줄기 시작 | 백필 기간이 길어짐 |
| B. 방금 쓴 사용자의 조회만 소스로 보냄(read-your-writes) | 문의의 직접 원인 해결 | 라우팅 로직 필요, 소스 부하 증가 |
| C. 지연 기준 스로틀(기준 초과 시 멈춤, 따라잡으면 재개) | 재발 방지, 자동 | 배치 코드 변경, 기준값 튜닝 |
| D. 청크 줄이기 + 청크 사이 쉬기 | 덩어리가 작아져 적용이 고르게 됨 | 총 시간 증가 |

**내가 고를 방법**
즉시는 A로 배치를 멈춰 지연을 줄이고, 필요하면 B로 해당 조회를 소스로 돌려요. 재개할 땐 C + D로 바꿔요. pt-online-schema-change처럼 레플리카 지연이 1초를 넘으면 멈추는 방식이에요. 진행 위치를 저장해 뒀다면 멈춘 곳부터 이어가요. 재발 방지로 지연 알림을 걸고, 배치 템플릿에 지연 감시를 기본으로 넣어요. read-your-writes는 [복제 지연](../../distributed/replication-lag/)에 있어요.

**채점 포인트**: 레플리카 읽기 → 옛 데이터, 큰 트랜잭션은 커밋 후 한 덩어리로 전달, Seconds_Behind_Source(한계 포함), 즉시 중지, read-your-writes, 지연 기준 스로틀(max-lag), 청크·쉬기, 진행 위치로 재개.

**흔한 감점 답안**: "레플리카를 늘린다"(각 레플리카가 같은 변경을 적용해야 해서 지연이 안 풀림), 원인 확인 없이 캐시 탓, 배치를 그대로 두고 조회만 전부 소스로 돌림(소스 과부하).
</details>

<details>
<summary>상황 3: 포인트 지급 백필 배치가 70% 지점에서 배포 때문에 죽었어요. 처음부터 다시 돌렸더니 일부 회원 포인트가 두 배가 됐어요. 왜 그렇고, 어떻게 고치나요?</summary>

**상황 파악**
"처음부터 다시"가 안전하려면 배치가 멱등이어야 해요. 두 배가 됐다면 이미 처리한 행을 한 번 더 처리했고, 그 처리가 누적형이었다는 뜻이에요.

**원인 후보**
1. `SET point = point + 100` 같은 누적형 SET
2. 처리 여부를 가리는 대상 조건이 없음
3. 진행 위치를 저장하지 않았거나, 청크와 다른 트랜잭션에 저장해 실제 위치와 어긋남

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 덮어쓰기형으로 변경(지급 결과 값을 계산해 SET) | 몇 번 돌려도 같음 | 계산식이 원본 값에 의존하면 별도 기준 컬럼 필요 |
| B. 처리 기록 남기기(지급 이력 테이블 + 유니크 키, INSERT IGNORE) | 중복 지급을 DB가 막음, 감사 기록 | 테이블 추가 |
| C. 진행 위치를 청크와 같은 트랜잭션에 저장 | 멈춘 곳부터 정확히 이어감 | 진행 테이블 관리 |
| D. Spring Batch 재시작 | 위치 관리를 프레임워크가 함 | 실패한 청크는 다시 처리돼서 writer 멱등은 여전히 필요 |

**내가 고를 방법**
먼저 두 배가 된 회원을 찾아 바로잡아요. 지급 이력이나 진행 기록으로 중복 구간을 특정해요. 고칠 땐 B + C를 해요. 포인트처럼 누적이 본질인 값은 덮어쓰기형으로 바꾸기 어려워서, "이 회원에게 이 지급을 했는가"를 유니크 키로 기록하는 게 가장 확실해요. 위치는 청크와 같은 트랜잭션에 커밋해서, 위치만 앞서 저장돼 청크를 건너뛰는 일도 막아요. Spring Batch를 쓰더라도 writer는 멱등으로 짜요. 멱등 키 개념은 [아웃박스·멱등성](../../distributed/outbox-idempotency/)에 있어요.

**채점 포인트**: 멱등 정의, 누적형 SET의 위험, 대상 조건, 유니크 키 + INSERT IGNORE, 진행 위치는 같은 트랜잭션(이유: 건너뜀 vs 재처리), Spring Batch 재시작 범위와 한계, 피해 데이터 복구.

**흔한 감점 답안**: "실패하면 전체 롤백 후 처음부터"(대량 롤백 비용, 근본 원인 그대로), "Spring Batch를 쓰면 자동으로 해결"(writer 멱등 누락), 피해 복구 언급 없음.
</details>

<details>
<summary>상황 4: 1억 행 정산 배치가 `ORDER BY id LIMIT 10000 OFFSET ?`로 페이지를 넘기며 돌아요. 처음엔 빠른데 뒤로 갈수록 느려져서 아침 업무 시작 전까지 안 끝나요.</summary>

**상황 파악**
같은 크기(1만 행)를 처리하는데 뒤로 갈수록 느려진다면, 한 페이지를 가져오는 비용이 **위치에 비례**한다는 뜻이에요. OFFSET 페이징의 전형적인 모양이에요.

**원인**
`OFFSET k`는 앞의 k행을 다 읽고 버린 뒤 N행을 돌려줘요. 페이지가 뒤로 갈수록 버리는 양이 늘어 전체로는 제곱으로 늘어요. 실험(100만 행)에서 OFFSET 980000은 99만 행을 읽어 88ms, OFFSET 10은 1.07ms였어요. 1억 행이면 차이가 훨씬 커져요. 또 배치가 `WHERE settled = 0`처럼 처리하면 빠지는 조건과 OFFSET을 같이 쓰면, 처리할 때마다 앞 행이 빠져 경계가 밀리면서 행을 건너뛰어요.

**확인 순서**
배치 로그에서 페이지 번호별 소요 시간이 선형으로 느는지 → 뒤쪽 OFFSET 쿼리를 스테이징에서 EXPLAIN ANALYZE로 돌려 읽은 행 수가 OFFSET + N에 가까운지 → 처리 누락 건수 확인.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 키셋 `WHERE id > :last ORDER BY id LIMIT N` | 위치와 무관하게 일정(실험 1.33ms, 1만 행만 읽음), 진행 위치 저장 쉬움 | 마지막 id를 이어 받아야 함, 정렬 키가 유니크해야 함 |
| B. 고정 PK 범위 `BETWEEN :s AND :s + N - 1` | 병렬로 범위를 나눠 돌리기 쉬움 | id 구멍이 많으면 빈 청크 |
| C. 커서 리더(한 번 쿼리 후 결과를 한 행씩) | 쿼리 한 번 | 연결을 오래 쥐고, 긴 읽기는 purge를 막을 수 있음 |
| D. 서버·DB 스펙 증설 | 즉시 조금 빨라짐 | 제곱 증가는 그대로 |

**내가 고를 방법**
A를 골라요. 실험에서 같은 1만 행을 읽는데 88ms → 1.33ms(약 80배)였고, 몇 번째 청크든 비용이 같아요. 마지막 id를 진행 위치로 저장하면 중간에 죽어도 이어갈 수 있어요. 더 빨라야 하면 B로 범위를 나눠 병렬로 돌리되, DB 부하를 보며 동시 수를 정해요. Spring Batch면 `JdbcPagingItemReader`의 sortKey를 유니크한 PK로 둬요. 처리 누락이 있었다면 대상 조건으로 남은 행을 다시 확인해요.

**채점 포인트**: OFFSET은 앞 행을 읽고 버림, 뒤로 갈수록 느림(제곱), 실험 수치, 대상 조건 + OFFSET의 건너뛰기 버그, 키셋, 정렬 키 유니크, 진행 위치, 커서 방식의 긴 연결 주의.

**흔한 감점 답안**: "인덱스를 추가한다"(id는 이미 PK 인덱스, 실험에서도 인덱스 스캔이었음), "페이지 크기를 키운다"(버리는 양은 그대로), 스펙 증설만 말함.
</details>

<details>
<summary>상황 5: 서비스를 멈추지 않고 주문 테이블을 새 스키마의 `orders_v2`로 이관했어요. 읽기를 새 테이블로 바꾸기 전에, 데이터가 맞는지 어떻게 확인하겠어요?</summary>

**상황 파악**
이관 중에도 주문은 계속 들어왔으니, 백필(옛 데이터)과 이중 쓰기(새 데이터)가 섞여 있어요. 확인해야 할 건 두 가지예요. **빠진 행이 없는지**와 **값이 같은지**예요. 읽기를 바꾼 뒤에 틀린 걸 발견하면 사용자에게 바로 보여요.

**틀어질 수 있는 지점(원인 후보)**
1. 백필 청크 누락(진행 위치가 앞서 저장됨, OFFSET 경계 밀림)
2. 백필이 이중 쓰기로 들어온 최신 값을 옛 값으로 덮음
3. 변환 로직 버그(타입·NULL·시간대 처리)
4. 이중 쓰기 일부 실패

**해결책과 트레이드오프**

| 방법 | 잡는 것 | 한계 |
|---|---|---|
| A. 전체·id 범위별 `COUNT(*)` | 누락·중복 행 | 값 오류는 못 잡음 |
| B. id 범위별 체크섬 비교(`SUM(CRC32(CONCAT_WS(...)))`) | 값 차이 위치를 범위로 좁힘 | 스키마가 다르면 비교할 컬럼을 맞춰 변환해야 함 |
| C. `CHECKSUM TABLE` | 한 번에 전체 비교 | 읽기 락 + 전체 읽기, 같은 구조·버전끼리만, 스키마가 바뀌면 못 씀 |
| D. 샘플 행 직접 비교 | 변환 로직 버그 | 표본이라 드문 오류는 놓칠 수 있음 |
| E. 섀도 읽기(양쪽 읽어 비교·로그) | 실제 트래픽 기준 차이, 이중 쓰기 실패 | 읽기 부하 2배, 기간 필요 |

**내가 고를 방법**
A → B → D → E 순서로 겹겹이 해요. 범위별 COUNT로 누락을 먼저 보고, 체크섬이 다른 범위만 더 잘게 쪼개 찾아요. 변환 로직은 샘플로 확인하고, 마지막으로 일정 기간 섀도 읽기로 실제 요청에서 차이가 0인지 봐요. C는 스키마가 달라서 못 쓰고, 운영 대형 테이블에 읽기 락을 거는 것도 피해요. 이관 중에 덮어쓰기 문제를 막으려면 백필을 INSERT IGNORE로 해서 이중 쓰기가 먼저 넣은 행을 건드리지 않게 해요. 읽기 전환 뒤에도 옛 테이블 쓰기를 바로 끊지 않아 되돌릴 길을 남겨요. 단계 전체는 [무중단 DB 마이그레이션](../../architecture/db-migration-zero-downtime/)의 expand-contract와 이어져요.

**채점 포인트**: 백필 + 이중 쓰기 공존, COUNT만으론 부족, 범위별 체크섬으로 좁히기, CHECKSUM TABLE의 락·버전·스키마 한계, 샘플 비교, 섀도 읽기, 덮어쓰기 경합(INSERT IGNORE), 전환 후 되돌릴 길.

**흔한 감점 답안**: "COUNT가 같으면 끝", "CHECKSUM TABLE 한 번 돌린다"(스키마가 다르고 운영 락), 검증 없이 읽기 전환, 롤백 계획 없음.
</details>
