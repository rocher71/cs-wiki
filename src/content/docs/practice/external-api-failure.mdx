:::tip[한 줄 요약]
외부 API가 느려지면 **그 응답을 기다리는 우리 서버의 스레드와 DB 커넥션이 하나씩 묶여 바닥나고**, 같은 자원을 쓰는 상관없는 API까지 같이 멈춰요. 그래서 **① 타임아웃으로 기다림에 상한 → ② 서킷브레이커로 아픈 곳은 아예 안 부르기 → ③ 벌크헤드로 묶일 수 있는 자원 수 제한 → ④ 폴백으로 대신 줄 응답 → ⑤ 꼭 즉시 필요 없으면 비동기로 빼기** 순서로 막아요.
:::

:::note[처음이라면 여기까지]
① 외부 API가 느리면 우리 서버도 그 시간만큼 일꾼(스레드)을 붙잡고 기다려요. 일꾼이 다 묶이면 다른 손님도 못 받아요. 이게 **연쇄 장애**예요.

② Java `HttpClient`처럼 **타임아웃을 안 주면 영원히 기다리는** HTTP 클라이언트가 있어요. 타임아웃은 "꼭 직접 설정하는 것"이라고 기억하세요.

③ 타임아웃은 상대를 빠르게 하는 게 아니라 **내 일꾼을 빨리 돌려받는 장치**예요. 한 번 재 본 실험에서 정상 요청이 10초 걸리던 게 타임아웃 1초를 주니 1초로 줄었어요.

④ 서술형은 상황 1·2번부터 연습하세요. 서킷브레이커·재시도 개념은 [장애 격리 패턴](../../architecture/resilience/)에 있어요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

은행 창구에 직원이 10명 있어요. 손님 중 몇 명이 "거래처에 확인 전화 좀 해 주세요"라고 해요.

그런데 그 거래처가 오늘 전화를 안 받아요. 직원은 수화기를 들고 신호음만 들으며 기다려요. 손님이 계속 같은 부탁을 하니 직원 10명이 **전부** 수화기를 든 채 멈춰요. 그냥 통장 정리하러 온 손님도 창구가 비지 않으니 번호표만 쥐고 기다려요. 거래처 하나 때문에 은행 전체가 멈춘 거예요.

고치는 방법은 상식적이에요.

- "신호가 30초 가면 끊는다" → **타임아웃**
- "그 거래처는 지금 안 받으니 한동안 전화 걸지 말자" → **서킷브레이커**
- "그 거래처 전화는 2번 창구 두 명만 건다" → **벌크헤드**
- "확인이 안 되니 일단 '확인 중'이라고 안내한다" → **폴백**
- "확인되면 문자로 알려 드릴게요" → **비동기화**

단, 실제 서버에선 직원(스레드)이 10명이 아니라 기본 200명이고, 기다리는 동안 DB 커넥션 같은 다른 자원까지 같이 쥐고 있을 수 있어요. 그래서 실제로는 200명보다 훨씬 먼저 바닥나는 자원이 있어요(아래 연쇄 장애 참고).

## 이 유형을 푸는 순서

"외부 API 때문에 서비스가 이상해요" 유형은 아래 순서를 답안 뼈대로 써요. 답안 쓰는 일반 구조는 [서술형 답안 쓰는 법](../how-to-answer/)에 있어요.

| 단계 | 할 일 | 이 주제에서 구체적으로 |
|---|---|---|
| 1. 증상 확인 | 무엇이, 언제부터, 얼마나 | p99 응답 시간, 5xx 비율, 특정 시간대에만인지 |
| 2. 영향 범위 | 외부 API를 **안 쓰는** API도 느린가 | 같이 느리면 공용 자원(스레드·커넥션 풀) 고갈 신호 |
| 3. 즉시 완화 | 피해부터 멈춤 | 해당 기능 끄기(기능 플래그), 서킷 수동 OPEN, 타임아웃 낮춰 재배포, 폴백 |
| 4. 원인 찾기 | 어디서 기다리는지 숫자로 | 스레드 덤프, Tomcat 스레드·Hikari 지표, 외부 호출별 지연 지표 |
| 5. 근본 해결 | 다시 번지지 않게 | 타임아웃·서킷브레이커·벌크헤드, 외부 호출을 트랜잭션 밖으로, 비동기화 |
| 6. 재발 방지 | 다음엔 먼저 알기 | 외부 API별 지연·에러 대시보드와 알림, 장애 주입 테스트, 계약에 SLA |

### 증상별 원인 후보와 확인 도구

| 증상 | 의심할 것 | 확인 도구 |
|---|---|---|
| 외부 API를 안 쓰는 API까지 같이 느림 | 요청 스레드 풀 고갈 | Actuator/Micrometer `tomcat.threads.busy`가 최대치(기본 200)에 붙음, 스레드 덤프 |
| 스레드 덤프에 소켓 읽기에서 멈춘 스레드가 잔뜩 | 타임아웃 없는(또는 너무 긴) 외부 호출 | `jcmd <pid> Thread.print` 또는 `jstack`으로 같은 호출 지점에 몰린 스레드 찾기 |
| 응답이 최대 30초까지 늘어지다 `Connection is not available` | 트랜잭션 안에서 외부 호출 → DB 커넥션까지 묶임 | `hikaricp.connections.active`·`pending` |
| 외부 API가 회복됐는데도 한동안 에러 | 재시도 폭풍, 큐에 쌓인 대기 작업 | 외부 호출 횟수 지표(평소 대비 몇 배인지), 큐 길이 |

스레드 덤프 읽는 법은 [로그·지표로 원인 추적](../debugging-with-logs/), 커넥션 풀은 [커넥션 풀과 쿼리](../../db/connection-pool-query/)에 있어요.

## 제대로 알기

### 왜 외부 API 하나가 서비스 전체를 죽이나

Spring MVC 같은 서블릿 방식에서는 **요청 하나가 응답을 끝낼 때까지 스레드 하나를 붙잡아요.** 외부 API를 동기로 부르면 응답이 올 때까지 그 스레드는 아무 일도 못 하고 기다려요. 스레드 풀 구조는 [스레드 풀](../../java/thread-pool/)에 있어요.

Spring Boot 내장 Tomcat 기본값은 이래요.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `server.tomcat.threads.max` | 200 | 요청을 처리하는 스레드 최대 개수 |
| `server.tomcat.accept-count` | 100 | 스레드가 전부 바쁠 때 들어온 연결이 기다리는 대기열 길이 |
| `server.tomcat.max-connections` | 8192 | 동시에 받아 둘 수 있는 연결 수 |

연쇄는 이렇게 일어나요.

1. 외부 API가 10초씩 늦어져요.
2. 그 API를 부르는 요청 스레드가 하나씩 "대기"로 묶여요.
3. 200개가 다 차면 새 요청은 대기열(100)에서 기다리고, 대기열도 차면 연결이 거절돼요.
4. 외부 API와 **상관없는** 상품 조회도 같은 스레드 풀을 쓰니 같이 느려지거나 실패해요.

이렇게 느린 상대 하나를 여러 호출자가 기다리다 호출자 자원이 고갈되고 장애가 번지는 걸 **연쇄 장애**(cascading failure)라고 해요.

**더 빨리 바닥나는 자원: DB 커넥션.** 외부 호출이 `@Transactional` 안에 있으면 응답을 기다리는 동안 DB 커넥션도 쥐고 있어요. HikariCP 기본 `maximumPoolSize`는 **10**이라 스레드(200)보다 커넥션(10)이 훨씬 먼저 바닥나요. 다른 요청은 커넥션을 `connectionTimeout`(기본 30초)까지 기다리다 예외가 나요. 그래서 **외부 호출은 트랜잭션 밖으로** 빼는 게 기본이에요.

**"스레드를 늘리면 되지 않나요?"** 기다리는 스레드만 늘고, 병목은 커넥션 풀이나 외부 API의 동시 처리 한도로 옮겨가요. 근본은 기다림에 상한(타임아웃)을 두고 자원을 격리(벌크헤드)하는 거예요.

### 함정: 타임아웃 기본값이 "무한"인 클라이언트

타임아웃은 두 종류예요.

- **연결 타임아웃**(connect timeout): 상대와 연결을 맺기까지 기다리는 한도
- **읽기/요청 타임아웃**(read/request timeout): 연결된 뒤 응답을 기다리는 한도

장애 때 흔한 건 "연결은 바로 되는데 응답이 안 오는" 경우예요. 그래서 연결 타임아웃만으로는 부족하고 읽기/요청 타임아웃을 **따로** 줘야 해요.

공식 문서로 확인한 기본 동작이에요.

| 클라이언트 | 설정 안 하면 | 근거 |
|---|---|---|
| Java 11+ `java.net.http.HttpClient` 요청 타임아웃 (`HttpRequest.Builder.timeout`) | **영원히 기다림** | Javadoc에 "설정 안 하면 무한 Duration과 같다, 즉 영원히 블록"이라고 적혀 있음 |
| 같은 클라이언트의 연결 타임아웃 (`HttpClient.Builder.connectTimeout`) | 기본값을 문서에 따로 적지 않음 | 새 연결을 맺을 때만 적용, 응답 대기는 못 막음 |
| JDK `URLConnection` connect/read 타임아웃 | 기본 0 = **무한** | Javadoc |
| Spring `SimpleClientHttpRequestFactory` (`HttpURLConnection` 기반) | 시스템 기본(위의 0 = 무한) | Javadoc: 기본은 시스템 기본, 0은 무한 |
| Spring 6.1+ `JdkClientHttpRequestFactory` (`HttpClient` 기반) | `setReadTimeout` 기본은 시스템 기본, 0은 무한 | 연결 타임아웃은 이 팩토리에 없어서 넘겨주는 `HttpClient`에 설정 |

Java `HttpClient`는 시간이 넘으면 `send`가 `HttpTimeoutException`을 던져요. 그래서 이렇게 써요.

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(1))   // 연결 맺기 한도
        .build();
HttpRequest req = HttpRequest.newBuilder(uri)
        .timeout(Duration.ofSeconds(1))          // 응답 기다리기 한도 — 없으면 영원히 대기
        .build();
```

**Spring Boot에서 전역으로 주기.** Boot 4.x 문서 기준 `spring.http.clients.connect-timeout`, `spring.http.clients.read-timeout` 속성이 있어요. Boot 3.5 문서에서는 `s` 없는 `spring.http.client.*`였으니 쓰는 버전 문서를 확인하세요. 설정 안 하면 밑단 HTTP 클라이언트 자체 기본값을 따라요.

<Aside type="caution" title="함정: 직접 만든 인스턴스엔 속성이 안 먹어요">
Boot가 자동 구성한 `RestClient.Builder`·`RestTemplateBuilder`를 **주입받아** 만들어야 위 속성이 적용돼요. `RestClient.create()`나 `new RestTemplate()`처럼 직접 만들면 자동 구성을 건너뛰어서 속성으로 준 타임아웃이 적용되지 않아요. 코드 곳곳에서 직접 만들고 있다면 공용 Bean 하나로 모으는 게 먼저예요.
</Aside>

참고로 Boot의 자동 구성은 클래스패스에 있는 HTTP 클라이언트를 Apache HttpClient → Jetty → Reactor Netty → JDK HttpClient → Simple(`HttpURLConnection`) 순서로 골라요. 그래서 "우리 서비스가 실제로 어떤 클라이언트를 쓰는지"도 기본값 판단에 필요해요.

### 실험: 타임아웃 하나로 정상 요청이 10배 빨라졌다

작은 Java 프로그램으로 재현해 봤어요(JDK 17, 한 번 재 본 실험 예시).

- 가짜 외부 서버: `/slow`는 10초 뒤 응답, `/fast`는 즉시 응답
- 우리 서버 역할: 스레드 10개짜리 풀(`Executors.newFixedThreadPool(10)`) + Java `HttpClient`
- 느린 호출 10건을 먼저 넣고, 이어서 정상 호출 10건을 넣은 뒤 **정상 10건이 다 끝난 시점**을 쟀어요.

| 설정 | 정상 요청 10건 완료까지 | 무슨 일이 있었나 |
|---|---|---|
| 타임아웃 없음 | **10066ms** | 느린 호출 10건이 스레드 10개를 다 잡아서 정상 작업이 큐에서 10초 기다림 |
| `HttpRequest.timeout(1초)` | **1007ms** | 느린 호출이 1초 만에 `HttpTimeoutException`으로 끝나고 스레드를 반납 |

```java
// 클라이언트 쪽 핵심만
var b = HttpRequest.newBuilder(URI.create("http://127.0.0.1:" + port + path));
if (timeout != null) b.timeout(timeout);   // 없으면 무한 대기
client.send(b.build(), HttpResponse.BodyHandlers.discarding());
// pool = newFixedThreadPool(10); slow 10건 submit → fast 10건 submit
```

정상 요청이 느려진 건 **정상 요청 자체가 느려서가 아니라 스레드를 못 받아서**예요. 타임아웃은 상대를 빠르게 하지 않아요. 내 자원을 돌려받는 장치예요.

그런데 1초 타임아웃도 여전히 호출마다 스레드를 1초씩 묶어요. 외부 API가 계속 죽어 있으면 1초짜리 대기가 끝없이 반복돼요. 그래서 서킷브레이커와 벌크헤드가 더 필요해요.

### 대응 조합: 어떤 순서로 얹나

개념과 기본값은 [장애 격리 패턴](../../architecture/resilience/)에 있어요. 여기서는 "장애 상황에서 무엇부터 얹는가" 순서로 정리해요.

| 순서 | 도구 | 막는 것 | 한 줄 요약 |
|---|---|---|---|
| 1 | 타임아웃 | 무한 대기 | 기다림에 상한. 없으면 나머지가 다 소용없음 |
| 2 | 서킷브레이커 | 죽은 상대를 계속 부르기 | 실패율(기본 50%)이나 느린 호출 비율이 넘으면 OPEN → 안 부르고 바로 실패 |
| 3 | 벌크헤드 | 한 외부 API가 자원 전부 차지 | 외부 API별 동시 호출 수 상한, 넘으면 즉시 거절 |
| 4 | 폴백 | 사용자에게 에러 화면 | 끊었을 때 대신 줄 응답(캐시·기본값·숨김·명확한 실패) |
| 5 | 비동기화 | 요청 경로가 외부를 기다림 | 즉시 결과가 필요 없으면 큐·아웃박스로 빼기 |

재시도는 이 표에 일부러 안 넣었어요. **멱등한 요청만**, 한 계층에서만, 지수 백오프와 지터를 섞어서 써요. 멱등은 "여러 번 해도 한 번 한 것과 결과가 같다"는 뜻이에요. → [아웃박스와 멱등성](../../distributed/outbox-idempotency/)

벌크헤드와 서킷브레이커는 헷갈리기 쉬워요. 벌크헤드는 "**동시에 몇 개까지**"(자원 격리), 서킷브레이커는 "**실패가 많으면 아예 안 부름**"(빠른 실패)이에요. 경쟁 관계가 아니라 같이 써요.

<Aside type="note" title="도입 순서와 감싸는 순서는 달라요">
위 표는 "무엇부터 챙기나" 순서예요. Resilience4j를 Spring Boot 애노테이션으로 붙이면 실제로 감싸는 기본 순서는 바깥부터 `Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( 호출 ) ) ) ) )`예요.
</Aside>

### 심화: 타임아웃 예산

호출이 여러 단계로 이어지면 **위쪽 타임아웃이 아래쪽 (타임아웃 × 시도 횟수 + 백오프 대기)의 합보다 커야** 의미가 있어요. 공식 수치가 있는 규칙은 아니고 설계 원칙이에요.

- 좋은 예: 게이트웨이 3초 → 우리 서버 → 외부 API 타임아웃 1초 × 최대 2회 + 백오프 0.2초 ≈ 2.2초. 3초 안에 들어와요.
- 나쁜 예: 게이트웨이 2초인데 우리 서버가 외부 API를 2초 × 3회 시도. 게이트웨이는 2초에 이미 504를 돌려줬는데, 서버는 최대 6초 넘게 아무도 안 받을 응답을 위해 계속 일해요.

타임아웃 값 자체는 상대 서비스 응답 시간의 높은 백분위(예: p99.9)를 기준으로 정해요. 너무 길면 자원 낭비, 너무 짧으면 멀쩡한 요청까지 끊겨 재시도가 늘어요. 남은 시간을 아래로 넘겨주는 방식(gRPC의 deadline 전파)도 있어요.

### 심화: 벌크헤드로 계산해 보기

**벌크헤드**(bulkhead, 배의 격벽)는 배 안을 칸막이로 나눠 한 칸에 물이 차도 배 전체가 가라앉지 않게 하는 구조에서 따온 이름이에요.

Resilience4j 기본값은 두 가지 구현이 달라요.

| 구현 | 기본값 | 꽉 차면 |
|---|---|---|
| SemaphoreBulkhead | `maxConcurrentCalls` 25, `maxWaitDuration` 0 | 기다리지 않고 바로 `BulkheadFullException` |
| FixedThreadPoolBulkhead | `maxThreadPoolSize` CPU 수, `coreThreadPoolSize` CPU 수 - 1, `queueCapacity` 100 | 큐까지 차면 `BulkheadFullException` |

계산 예: Tomcat 스레드 200개, 외부 API A에 세마포어 벌크헤드 25. A가 완전히 멈춰도 A 때문에 묶이는 스레드는 **최대 25개**예요. 나머지 175개는 다른 요청을 처리해요. 26번째 A 호출은 기다리지 않고 바로 거절돼서 폴백으로 가요.

외부 API마다 별도 스레드 풀을 두는 것도 벌크헤드예요. 단 `Executors.newFixedThreadPool`은 **큐 길이에 제한이 없어서**, 외부 API가 느려지면 대기 작업이 끝없이 쌓여 메모리 부족(OOM)까지 갈 수 있어요. 유한 큐와 거절 정책을 같이 써요. → [스레드 풀](../../java/thread-pool/), [메모리 누수·OOM](../memory-oom/)

### 심화: 폴백 고르기

폴백은 "이 데이터가 틀리거나 늦으면 **누가 손해를 보나**"로 골라요(정합성과 가용성 중 어느 쪽이 중요한지). 아래 분류는 공식 규칙이 아니라 실무에서 흔히 쓰는 정리예요.

| 폴백 | 어울리는 데이터 | 예 |
|---|---|---|
| 캐시 값(조금 오래된 값) | 조금 늦어도 괜찮은 것 | 상품 추천, 날씨, 환율(기준 시각 표시) |
| 기본값 | 대충이라도 보여 주면 되는 것 | 추천 실패 → 인기 상품 고정 목록, 배송 예정일 → "확인 중" |
| 나중에 처리 | 지금 안 돼도 언젠가 되면 되는 것 | 알림 발송, 포인트 적립 → 큐·아웃박스에 넣고 성공 응답 |
| 기능 숨김 | 없어도 핵심 흐름이 되는 것 | 리뷰 위젯·추천 영역을 빼고 주문은 살림 |
| 명확한 실패 | **돈이 걸린 것** | 결제·송금 → 가짜 성공 금지, "처리 중" + 상태 조회 |

결제처럼 결과가 중요한 외부 호출은 [결제 시스템 설계](../../system-design/payment-system/)를 같이 보세요. **타임아웃이 곧 "처리 안 됨"이 아니에요.** 상대는 처리했는데 응답만 늦었을 수 있어서, 다시 보내기 전에 상태를 조회하거나 멱등 키를 써야 이중 결제를 막아요.

### 심화: 비동기화와 가상 스레드

**비동기화.** 사용자가 바로 결과를 볼 필요가 없는 호출(알림, 정산 연동, 외부 동기화)은 요청 처리 경로에서 빼서 메시지 큐나 아웃박스로 넘겨요. 그러면 외부 지연이 요청 스레드를 묶지 않아요. 나중에 다시 처리할 때 같은 일이 두 번 되지 않게 멱등해야 해요. → [메시지 큐와 Kafka](../../distributed/message-queue-kafka/)

`CompletableFuture.supplyAsync`에 Executor를 안 넘기면 공용 ForkJoinPool(코어 수 - 1개)을 써서, 블로킹 외부 호출 몇 개에 금방 고갈돼요. I/O 전용 Executor를 넘기고 `orTimeout`(Java 9+)으로 시간 제한을 걸어요.

**가상 스레드로 바꾸면 해결될까?** Java 21 가상 스레드(`spring.threads.virtual.enabled=true`)는 스레드 고갈은 크게 줄여 줘요. 이때 `server.tomcat.threads.max`는 효과가 없어요. 하지만 외부 API가 느린 건 그대로이고, 병목이 커넥션 풀과 외부 API 동시 처리 한도로 옮겨가요. 그래서 타임아웃과 세마포어 벌크헤드는 여전히 필요해요. → [가상 스레드](../../java/virtual-threads/)

## 면접 질문

<details>
<summary>Q. 외부 API 하나가 느려졌는데 왜 상관없는 API까지 느려지나요?</summary>

**답변(30초)** 요청 스레드와 커넥션을 같이 쓰기 때문이에요. 서블릿 방식에서는 요청 하나가 응답을 끝낼 때까지 스레드 하나를 붙잡는데, 외부 API를 동기로 부르면 응답이 올 때까지 그 스레드가 묶여요. 이런 스레드가 Tomcat 기본 200개를 다 채우면 외부 API와 상관없는 요청도 대기열에서 기다리다 실패해요. 이걸 연쇄 장애라고 해요.

**꼬리질문**
- Q. 트랜잭션 안에서 외부 API를 부르면요? → DB 커넥션까지 쥐고 기다려서, Hikari 기본 10개가 스레드 200개보다 훨씬 먼저 바닥나요. 외부 호출은 트랜잭션 밖으로 빼요.
- Q. 스레드 풀을 늘리면요? → 기다리는 스레드만 늘고 병목이 커넥션 풀이나 외부 API 한도로 옮겨가요. 타임아웃과 격리가 근본이에요.
</details>

<details>
<summary>Q. 외부 API를 부를 때 타임아웃을 안 주면 어떻게 되나요?</summary>

**답변(30초)** 클라이언트에 따라 영원히 기다릴 수 있어요. Java `HttpClient`는 요청 타임아웃을 설정하지 않으면 무한으로 블록한다고 Javadoc에 적혀 있고, `HttpURLConnection` 기반인 Spring `SimpleClientHttpRequestFactory`도 기본이 시스템 기본값(`URLConnection` 기본 0, 즉 무한)이에요. 그리고 연결 타임아웃과 읽기 타임아웃은 따로라서, 연결만 제한하면 "연결은 됐는데 응답이 안 오는" 장애를 못 막아요. 그래서 둘 다 직접 설정해요.

**꼬리질문**
- Q. Spring Boot 속성으로 타임아웃을 줬는데 안 먹어요. → `RestClient.create()`나 `new RestTemplate()`처럼 직접 만들면 자동 구성을 건너뛰어요. 주입받은 Builder로 만들어야 해요.
- Q. 타임아웃이 나면 상대는 처리 안 한 건가요? → 아니에요. 처리했는데 응답만 늦었을 수 있어요. 결제는 재시도 전에 상태 조회나 멱등 키가 필요해요.
</details>

<details>
<summary>Q. 벌크헤드와 서킷브레이커는 뭐가 다르고, 왜 같이 쓰나요?</summary>

**답변(30초)** 벌크헤드는 외부 API별로 동시에 쓸 수 있는 자원 수를 제한하는 칸막이고, 서킷브레이커는 실패가 많으면 아예 호출하지 않고 바로 실패시키는 차단기예요. 벌크헤드가 있으면 API A가 죽어도 A가 묶을 수 있는 스레드가 예를 들어 25개로 끝나요. 서킷이 열리면 그 25개조차 안 묶이고 바로 폴백으로 가요. 하나는 피해 범위를, 하나는 피해 시간을 줄여서 같이 써요.

**꼬리질문**
- Q. 서킷이 열린 다음엔 어떻게 닫히나요? → 정해진 시간이 지나면 HALF_OPEN으로 시험 호출을 몇 개 보내 보고, 성공하면 CLOSED로 돌아가요. → [장애 격리 패턴](../../architecture/resilience/)
- Q. 별도 스레드 풀로 격리할 때 주의점은? → `newFixedThreadPool`은 큐가 무제한이라 대기 작업이 쌓여 OOM까지 갈 수 있어요. 유한 큐와 거절 정책을 둬요.
</details>

<details>
<summary>Q. 타임아웃 값과 재시도 횟수는 어떻게 정하나요?</summary>

**답변(30초)** 타임아웃은 상대 응답 시간의 높은 백분위, 예를 들어 p99.9를 기준으로 잡아요. 그리고 호출 체인 전체로 봐서 위쪽 타임아웃이 아래쪽 "타임아웃 × 시도 횟수 + 백오프"의 합보다 크게 맞춰요. 게이트웨이가 3초면 외부 API는 1초씩 최대 2번에 백오프 0.2초 정도로 2.2초 안에 끝나게 해요. 재시도는 멱등한 요청만, 한 계층에서만 해요.

**꼬리질문**
- Q. 반대로 아래쪽이 더 길면요? → 위쪽은 이미 포기하고 에러를 돌려줬는데 아래쪽은 계속 일하고 재시도까지 해서 자원만 낭비해요.
- Q. 가상 스레드를 쓰면 타임아웃이 필요 없나요? → 스레드 고갈은 줄지만 외부 지연·커넥션 풀은 그대로라 여전히 필요해요.
</details>

## 서술형 연습

아래 상황은 모두 실무 상황형 연습용으로 지어낸 것이에요. 실제 기출 문제가 아니에요.

<details>
<summary>상황 1: 메인 페이지에 붙은 상품 추천 API(외부 서비스)가 장애로 응답이 10초 넘게 걸리기 시작하더니, 추천과 상관없는 주문 API까지 타임아웃이 나며 서비스 전체가 멈췄어요.</summary>

**상황 파악**
주문은 추천을 안 쓰는데 같이 죽었어요. 외부 API 하나 때문에 **공용 자원(요청 스레드 풀, DB 커넥션 풀)이 고갈**된 연쇄 장애일 가능성이 커요. 추천 호출이 스레드를 하나씩 붙잡고 기다리는 동안 Tomcat 스레드(기본 200)가 다 차서, 주문 요청도 대기열에서 기다리다 실패한 모양이에요.

**원인 후보**
1. 추천 API 호출에 타임아웃이 없거나 너무 김(Java `HttpClient`·`HttpURLConnection` 계열은 기본이 무한)
2. 추천 호출이 트랜잭션 안에 있어 DB 커넥션까지 묶음 → 주문의 DB 작업이 커넥션을 못 받음
3. 추천 호출과 주문 처리가 같은 스레드 풀을 아무 칸막이 없이 공유

**확인 순서**
`tomcat.threads.busy`가 최대치인지 → 스레드 덤프에서 추천 API 호출 지점(소켓 읽기)에 스레드가 몰려 있는지 → `hikaricp.connections.pending`이 쌓였는지 → 추천 호출 지연 지표가 장애 시작 시각과 맞는지.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 즉시: 추천 영역 끄기(기능 플래그) | 바로 피해 차단, 핵심(주문) 살림 | 추천 매출 일부 포기, 플래그가 미리 있어야 함 |
| B. 추천 호출에 짧은 타임아웃 | 스레드가 빨리 풀림, 코드 변경 작음 | 상대가 계속 죽어 있으면 짧은 대기가 반복됨 |
| C. 서킷브레이커 + 폴백(인기 상품 목록) | 죽은 동안 아예 안 불러 스레드가 안 묶임, 화면은 유지 | 설정값(실패율·대기 시간) 튜닝 필요 |
| D. 벌크헤드(추천 동시 호출 상한) | 추천이 아무리 죽어도 묶이는 스레드 수가 정해짐 | 상한을 넘는 요청은 즉시 폴백 |

**내가 고를 방법**
지금은 A로 추천 영역을 꺼서 주문부터 살려요. 그다음 B(타임아웃)를 기본으로 깔고, C와 D를 같이 붙여요. 추천은 틀려도 손해가 작은 데이터라 폴백은 인기 상품 목록이나 영역 숨김이 적당해요. 추천 호출이 트랜잭션 안에 있었다면 밖으로 빼요. 재발 방지로 외부 API별 지연·에러율 대시보드와 알림을 두고, 스테이징에서 추천 API를 일부러 늦추는 장애 주입 테스트를 해요.

**채점 포인트**: 공용 자원 고갈(스레드·커넥션) 설명, Tomcat 200·Hikari 10 같은 숫자, 즉시 완화(기능 끄기), 타임아웃이 1순위, 서킷·벌크헤드로 격리, 폴백 내용, 트랜잭션 밖으로, 재발 방지.

**흔한 감점 답안**: "서버를 늘린다"(늘린 서버도 똑같이 묶임), "스레드 풀을 1000으로 늘린다"(병목이 커넥션으로 옮겨갈 뿐), "추천 회사에 연락한다"로 끝냄(우리 쪽 격리가 없음).
</details>

<details>
<summary>상황 2: 연동 중인 외부 API가 보통은 200ms 안에 응답하는데, 가끔 30초가 걸려요. 지금은 타임아웃이 설정돼 있지 않아요. 타임아웃을 몇 초로 잡을지 근거와 함께 설명하세요. 앞단 게이트웨이 타임아웃은 3초예요.</summary>

**상황 파악**
"가끔 30초"를 그대로 기다리면 그동안 스레드가 묶여 상황 1 같은 연쇄 장애가 날 수 있어요. 그렇다고 아무 숫자나 정하면 멀쩡한 요청을 끊거나, 게이트웨이보다 길어서 의미가 없어요. 근거는 두 가지예요. **상대의 실제 응답 시간 분포**와 **우리 위쪽의 타임아웃 예산**이에요.

**원인 후보(왜 가끔 30초인가)**
1. 상대 쪽 일시적 과부하·GC·느린 쿼리
2. 특정 요청 유형만 무거움(조회 범위가 큰 요청)
3. 연결은 되는데 응답이 늦는 경우 → 연결 타임아웃만으론 못 막음

**정하는 순서**
1. 외부 호출 지연 지표에서 p50·p99·p99.9를 봐요. "잘못 끊어도 괜찮은 비율"을 정하고(예: 0.1%), 그 백분위(p99.9)를 출발점으로 삼아요.
2. 예산 안에 넣어요. 게이트웨이 3초 안에 우리 처리 시간과 재시도까지 들어가야 해요. 예: 외부 1초 × 최대 2회 + 백오프 0.2초 ≈ 2.2초.
3. 연결 타임아웃과 읽기/요청 타임아웃을 **둘 다** 설정해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 짧게(예: 1초, p99.9 근처) | 스레드가 빨리 풀림, 예산 안에 재시도 여유 | 30초짜리 요청은 전부 실패 처리 → 폴백 필요 |
| B. 길게(예: 30초) | 느린 요청도 결국 성공 | 게이트웨이(3초)가 먼저 끊어 사용자는 어차피 실패, 서버만 30초 낭비 |
| C. 짧은 타임아웃 + 오래 걸려도 꼭 필요한 건 비동기로 분리 | 요청 경로는 빠르고, 결과도 결국 받음 | 상태 관리·조회 API가 추가됨(상황 5) |

**내가 고를 방법**
A를 기본으로 해요. B는 게이트웨이가 3초에 끊는 순간 의미가 없어요. 사용자는 실패를 보는데 서버만 계속 기다리는 "헛일"이 돼요. 그 결과가 오래 걸려도 꼭 필요하다면 C로 비동기 처리를 붙여요. 값은 한 번 정하고 끝이 아니라, 지연 분포가 바뀌면 다시 봐요. 그리고 타임아웃만으로는 상대가 계속 죽어 있을 때 1초 대기가 반복되니 서킷브레이커를 같이 둬요. 코드에서 `RestClient.create()`나 `new RestTemplate()`로 직접 만들고 있으면 Boot 타임아웃 속성이 안 먹으니 주입받은 Builder로 바꿔요.

**채점 포인트**: 기본값이 무한일 수 있다는 인식, 백분위(p99.9) 근거, 타임아웃 예산(위 > 아래 × 횟수 + 백오프), 연결 vs 읽기 타임아웃, 게이트웨이보다 긴 값의 무의미함, 끊긴 요청의 폴백·비동기, 서킷과 같이.

**흔한 감점 답안**: "30초 걸리니 31초로 준다", 근거 없이 "보통 3초"라고만 씀, 연결 타임아웃만 설정, 타임아웃 후 무조건 재시도.
</details>

<details>
<summary>상황 3: 외부 쿠폰 조회 API에 서킷브레이커를 붙였어요. 장애가 나서 서킷이 열렸는데, 사용자에게는 무엇을 보여 줘야 할까요? 같은 서비스의 결제 승인 API도 서킷이 열렸다면 달라지나요?</summary>

**상황 파악**
서킷이 열리면 외부를 부르지 않고 바로 실패해요. 이때 그냥 500 에러를 내면 서킷브레이커의 절반만 한 거예요. **대신 줄 응답(폴백)**을 데이터 종류에 맞게 정해야 해요. 기준은 "틀리거나 늦으면 누가 손해를 보나"예요.

**원인 후보(폴백을 다르게 해야 하는 이유)**
1. 쿠폰 조회: 없어도 주문은 가능, 조금 오래된 정보도 큰 문제는 아님
2. 결제 승인: 결과가 틀리면 돈이 사라지거나 두 번 빠짐 → 정합성이 우선

**해결책과 트레이드오프**

| 폴백 | 장점 | 단점 |
|---|---|---|
| A. 캐시된 마지막 쿠폰 목록 | 사용자 경험 유지 | 만료된 쿠폰이 보일 수 있음 → 결제 시점 재검증 필요 |
| B. 쿠폰 영역 숨김 + "쿠폰은 잠시 후 사용할 수 있어요" 안내 | 핵심 흐름(주문) 유지, 틀린 정보 없음 | 쿠폰 쓰려던 사용자는 이탈 가능 |
| C. 결제: 가짜 성공 금지, "처리 중" + 상태 조회 | 이중 결제·누락 방지 | 사용자가 결과를 늦게 앎, 상태 조회 설계 필요 |
| D. 결제: 명확한 실패 + "잠시 후 다시 시도" | 단순, 정합성 안전 | 결제 전환율 손해 |

**내가 고를 방법**
쿠폰은 B를 기본으로, 캐시가 있으면 A를 쓰되 결제 직전에 쿠폰 유효성을 다시 확인해요. 결제는 성공처럼 보이는 폴백은 절대 안 돼요. 승인 요청을 이미 보냈다면 타임아웃이어도 상대가 처리했을 수 있으니 C로 "처리 중"을 보여 주고 상태 조회로 확정해요. 아직 보내지도 못했으면(서킷 OPEN으로 바로 거절) D로 명확하게 실패를 알려요. 결제 흐름은 [결제 시스템 설계](../../system-design/payment-system/)와 이어져요.

**채점 포인트**: 서킷 OPEN = 호출 없이 즉시 실패, 폴백 종류(캐시·기본값·숨김·나중에 처리·명확한 실패), 데이터별 판단 기준(정합성 vs 가용성), 돈은 가짜 성공 금지, 타임아웃 ≠ 미처리, 캐시 폴백의 재검증.

**흔한 감점 답안**: "에러 페이지를 보여 준다"로 끝냄, 결제도 "일단 성공 처리하고 나중에 맞춘다", 모든 기능에 같은 폴백.
</details>

<details>
<summary>상황 4: 외부 API가 가끔 실패해서 재시도를 3번 넣었어요. 그런데 다음 장애 때 외부 서비스가 더 오래 죽어 있었고, 상대 회사에서 "장애 동안 평소의 몇 배 요청이 들어왔다"고 연락이 왔어요.</summary>

**상황 파악**
재시도는 "내 성공 확률을 높이려고 상대를 더 쓰는" 행동이에요. 상대가 일시적 오류가 아니라 **과부하**로 아팠다면, 재시도가 부하를 더 얹어 회복을 늦춰요. 이게 **재시도 폭풍**(retry storm)이에요.

**원인 후보**
1. 재시도 간격이 고정이거나 지터가 없어 실패한 요청들이 같은 순간에 한꺼번에 다시 감
2. 여러 계층(게이트웨이·우리 서버·HTTP 클라이언트)에서 각각 재시도해 곱으로 불어남(3번씩 2개 층이면 9배)
3. 멱등하지 않은 요청, 4xx 같은 다시 해도 실패할 요청까지 재시도
4. 서킷브레이커가 없어 상대가 죽어 있는 동안에도 계속 재시도. Retry가 서킷 바깥에 있으면 서킷이 거절한 예외까지 재시도할 수 있음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 지수 백오프 + 지터(무작위 간격) | 재시도 시점이 흩어져 몰림 감소 | 개별 요청의 완료 시간이 늘어남 |
| B. 재시도는 한 계층에서만, 횟수 축소 | 곱셈 증폭 제거 | 계층 간 합의·설정 정리 필요 |
| C. 재시도 예산(토큰 버킷 등으로 재시도 비율 제한) | 장애 때 재시도 양 자체가 줄어듦 | 구현·튜닝 필요 |
| D. 서킷브레이커와 같이 | 상대가 죽어 있으면 아예 안 부름 | 서킷이 거절한 예외는 재시도 대상에서 빼야 함 |

**내가 고를 방법**
A·B·D를 같이 해요. 재시도는 HTTP 클라이언트 한 곳에서만, 5xx·타임아웃에만, 멱등한 요청에만 해요. 지수 백오프에 지터를 섞고, 서킷이 열리면 재시도를 멈춰요. 트래픽이 큰 서비스면 C로 재시도 비율 상한까지 둬요. 횟수를 정할 땐 타임아웃 예산 안에 들어오는지도 확인해요. Resilience4j Retry `maxAttempts` 기본 3은 **첫 호출 포함**이라 재시도는 2번이라는 점도 헷갈리지 않게 해요. 자세한 공식과 실험은 [장애 격리 패턴](../../architecture/resilience/)에 있어요.

**채점 포인트**: 재시도 폭풍 정의, 과부하 vs 일시적 오류 구분, 지수 백오프 + 지터, 계층별 곱셈 증폭, 한 계층에서만, 멱등·5xx만, 재시도 예산, 서킷과 조합.

**흔한 감점 답안**: "재시도 횟수를 5번으로 늘린다", "간격을 1초로 고정한다"(동시에 몰림), 결제 같은 비멱등 요청도 그냥 재시도.
</details>

<details>
<summary>상황 5: 외부 신용 심사 API는 응답에 수십 초가 걸리기도 하지만, 그 결과 없이는 대출 신청을 진행할 수 없어요. 타임아웃을 짧게 잡으면 심사가 계속 실패하고, 길게 잡으면 서버 스레드가 묶여요.</summary>

**상황 파악**
"오래 걸려도 꼭 필요한 결과"예요. 폴백으로 기본값을 줄 수도 없고(심사 결과를 지어낼 수 없음), 요청 스레드로 수십 초를 기다리면 상황 1의 연쇄 장애가 나요. 해법은 **기다리는 일을 요청 처리 경로 밖으로 빼는 것**이에요.

**원인 후보(왜 동기로는 안 되나)**
1. 동기 호출은 응답이 올 때까지 요청 스레드(트랜잭션 안이면 커넥션까지)를 묶음
2. 앞단 게이트웨이·앱의 타임아웃이 외부 처리 시간보다 짧아 사용자는 어차피 실패를 봄
3. 타임아웃 후 재요청하면 심사가 중복으로 들어갈 수 있음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 비동기 + 상태 조회: 신청을 "접수됨"으로 저장하고 작업 번호를 바로 돌려줌 → 큐·아웃박스로 심사 요청 → 앱은 상태 조회 API로 확인, 완료되면 알림 | 요청 스레드가 안 묶임, 결과도 결국 받음 | 상태 테이블·조회 API·알림 등 구성 요소 증가, 사용자는 결과를 나중에 봄 |
| B. 별도 I/O 전용 스레드 풀(벌크헤드)에서 비동기 호출 + 긴 타임아웃 | 기존 구조를 덜 바꿈 | 그 풀은 여전히 묶임, 결과를 사용자에게 돌려줄 방법은 결국 필요 |
| C. 가상 스레드로 전환 | 스레드 고갈 완화 | 외부 지연 자체는 그대로, 병목이 커넥션·외부 동시성 한도로 이동 |

**내가 고를 방법**
A를 골라요. 사용자가 결과를 "즉시" 볼 필요는 없고 "확실히" 받는 게 중요하니까요. 신청 저장과 심사 요청 메시지를 한 트랜잭션에 함께 기록하는 아웃박스로 "신청은 됐는데 심사 요청이 빠지는" 상황을 막아요. 메시지가 다시 처리될 수 있으니 신청 번호를 멱등 키로 써서 심사가 두 번 들어가지 않게 해요([아웃박스와 멱등성](../../distributed/outbox-idempotency/)). 심사 호출을 하는 워커에도 타임아웃·서킷브레이커는 그대로 둬요. 오래 응답이 없는 건은 상태를 조회해 확정하고, 일정 시간이 지나면 "심사 지연" 상태로 바꿔 사용자에게 알려요. B·C는 스레드 문제만 완화하고 "사용자에게 결과를 어떻게 돌려주나"는 못 풀어서 보조 수단이에요.

**채점 포인트**: 오래 걸리는데 꼭 필요한 결과 → 요청 경로에서 분리, 접수·작업 번호·상태 조회, 큐/아웃박스, 멱등 키로 중복 방지, 워커에도 타임아웃·서킷, 지연 상태 처리, 가상 스레드의 한계.

**흔한 감점 답안**: "타임아웃을 60초로 늘린다", "가상 스레드로 바꾸면 끝", 비동기로 빼고 중복 처리·실패 처리를 언급 안 함.
</details>
