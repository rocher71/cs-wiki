:::tip[한 줄 요약]
"API가 느려요"를 받으면 **① DB 구간이 느린지 확인 → ② 슬로우 쿼리 로그와 digest 집계로 범인 쿼리 찾기 → ③ EXPLAIN ANALYZE로 왜 느린지 읽기 → ④ 인덱스 못 탐 / 데이터 많음 / N+1 / 락 대기 / 커넥션 풀 고갈 중 어느 갈래인지 판별** 순서로 좁혀 가요. 원인마다 고치는 방법이 완전히 달라서, 판별이 답안의 절반이에요.
:::

:::note[처음이라면 여기까지]
① "느리다"의 원인은 하나가 아니에요. 쿼리 하나가 오래 걸릴 수도, 빠른 쿼리가 너무 많이 나갈 수도, DB에 들어가기 전 줄을 서고 있을 수도 있어요.

② 그래서 바로 "인덱스 추가!"라고 답하면 감점이에요. 먼저 **어디서** 시간이 쓰이는지 숫자로 확인해요.

③ 가장 흔한 범인은 **인덱스가 있는데도 못 쓰는 쿼리**예요. 예: `DATE(created_at) = '2025-06-01'`처럼 컬럼에 함수를 씌우면 인덱스를 못 타요.

④ 서술형은 1·2번부터 연습하세요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

도서관에서 "2025년 6월 1일에 들어온 책"을 찾는다고 해 봐요.

사서에게는 입고 날짜순으로 정리된 **색인 카드**가 있어요. 카드에서 6월 1일 칸만 펼치면 바로 찾아요. 이게 **인덱스**(index, 정렬해 둔 찾아보기 목록)를 타는 경우예요.

그런데 요청서에 "입고 시각을 '날짜만' 잘라서 6월 1일인 책"이라고 적혀 있으면, 사서는 카드를 못 쓰고 서가의 책 50만 권을 한 권씩 꺼내 날짜를 잘라 보며 비교해요. 결과는 똑같은데 시간은 수십 배가 걸려요.

도서관이 느린 이유는 이것 말고도 있어요. 책 한 권씩 따로따로 100번 대출 신청하는 손님(N+1), 창구가 10개뿐이라 줄이 길어진 상황(커넥션 풀 고갈), 누가 책을 빌려 놓고 반납 안 해서 다음 사람이 기다리는 상황(락 대기)이에요. 그래서 "느려요"를 들으면 **어떤 종류의 느림인지**부터 가려야 해요.

단, 실제 DB는 사서처럼 매번 판단을 새로 하지 않아요. **옵티마이저**(optimizer, 쿼리를 어떻게 실행할지 정하는 DB 안의 계획 담당)가 조건 모양과 데이터 양을 보고 실행 계획을 골라요.

## 이 유형을 푸는 순서

서술형에서 "느린 API"를 받으면 아래 순서를 그대로 답안 뼈대로 써요. 답안 쓰는 일반 구조는 [서술형 답안 쓰는 법](../how-to-answer/)에 있어요.

| 단계 | 할 일 | 이 주제에서 구체적으로 |
|---|---|---|
| 1. 증상 확인 | 어떤 API가, 언제부터, 얼마나 | p50·p99 응답 시간, 에러율, 특정 API만인지 전체인지 |
| 2. 영향 범위 | 누가 피해를 보나 | 전체 API가 같이 느리면 공용 자원(커넥션 풀·락) 의심, 한 API만이면 그 쿼리 의심 |
| 3. 즉시 완화 | 일단 피해를 멈춤 | 문제 기능 끄기, 막는 트랜잭션 `KILL`(롤백 영향 고려), 배치 중단 |
| 4. 원인 찾기 | 숫자로 갈래 판별 | APM 구간 → 슬로우 로그·digest → EXPLAIN ANALYZE → 락·풀 지표 |
| 5. 근본 해결 | 갈래별 처방 | 조건 재작성·인덱스, fetch join, 트랜잭션 짧게, 배치 청크 |
| 6. 재발 방지 | 다음엔 먼저 알기 | 슬로우 로그 기준 낮추기, 풀·락 대기 알림, 배포 전 EXPLAIN 리뷰 |

### 1단계: 정말 DB 때문인가

APM이나 요청 로그에서 응답 시간을 구간별로 나눠 봐요. DB 호출 구간이 대부분을 차지하는지, 아니면 외부 API 호출·직렬화 같은 다른 곳인지 먼저 갈라요. DB가 아니면 이 페이지가 아니라 [외부 API 장애 대응](../external-api-failure/)이나 [로그·지표로 원인 추적](../debugging-with-logs/) 쪽이에요.

### 2단계: 범인 쿼리 찾기

**슬로우 쿼리 로그**(slow query log, 오래 걸린 쿼리를 파일에 남기는 기능)부터 떠올리지만, 함정이 두 개 있어요.

- MySQL에선 **기본으로 꺼져 있고**(`slow_query_log=OFF`), 기준 시간 `long_query_time`이 기본 **10초**예요. 그대로 두면 1초짜리 쿼리 수천 번은 로그에 하나도 안 남아요. 실무에선 1초, 0.5초처럼 낮춰 써요.
- 로그는 쿼리 한 건씩 적혀서 "어떤 모양의 쿼리가 시간을 제일 많이 먹나" 순위가 바로 안 보여요.

그래서 **digest 집계**를 같이 봐요. `performance_schema.events_statements_summary_by_digest`는 값만 다른 쿼리를 `?`로 바꿔 한 줄로 묶고, 실행 횟수(`COUNT_STAR`)와 누적 시간(`SUM_TIMER_WAIT`), 읽은 행 수를 쌓아요. 사람이 읽기 좋게 만든 뷰 `sys.statement_analysis`는 **총 시간 내림차순**으로 보여 줘요.

순위는 **총 시간 = 횟수 × 평균**으로 봐요. 평균 1ms라도 수십만 번 불리면 1등이 될 수 있어요. N+1이 이렇게 드러나요.

로그 한 줄에서 볼 숫자는 이거예요. 한 번 재 본 예시예요.

```text
# Query_time: 0.039695  Lock_time: 0.000001 Rows_sent: 1  Rows_examined: 500000
SELECT COUNT(*), SUM(amount) FROM orders WHERE DATE(created_at)='2025-06-02';
```

`Rows_sent`(돌려준 행)는 1인데 `Rows_examined`(읽은 행)는 50만이에요. **많이 읽고 조금 돌려준다** = 인덱스를 못 쓰고 있다는 강한 신호예요.

### 3단계: EXPLAIN ANALYZE로 이유 읽기

`EXPLAIN ANALYZE`는 쿼리를 **실제로 실행**하고, 예상치 옆에 실측 `(actual time=첫 행..끝 rows=N loops=L)`을 붙여 줘요. 자세한 읽는 법은 [EXPLAIN 읽기](../../db/explain/)에 있어요. 여기서는 세 가지만 봐요.

- 가장 안쪽(들여쓰기가 깊은) 줄이 먼저 실행돼요.
- **실제 rows가 큰 줄**, **끝 시간이 갑자기 커지는 줄**을 찾아요.
- `loops`가 1보다 크면 time과 rows는 **1회 평균**이에요. 총량은 loops를 곱해야 해요.

### 4단계: 증상으로 원인 갈래 판별

| 증상(숫자) | 원인 갈래 | 확인 도구 | 처방 |
|---|---|---|---|
| `Rows_examined` ≫ `Rows_sent`, EXPLAIN `type=ALL` | 인덱스 못 탐: 컬럼에 함수·형변환, 앞 `%` LIKE, 복합 인덱스 왼쪽 컬럼 누락 | 슬로우 로그, EXPLAIN ANALYZE | 컬럼 가공 없는 조건으로 재작성, 인덱스 추가·순서 조정 |
| 같은 쿼리가 데이터 늘수록 점점 느려짐 | 데이터 많음(풀 스캔 비용이 행 수에 비례) | digest의 평균 시간 추이, `SUM_ROWS_EXAMINED` | 인덱스, 조회 범위 제한, 페이징 |
| 슬로우 로그는 비었는데 API는 느림, 같은 모양 쿼리 `COUNT_STAR` 폭증 | N+1 | digest 표, SQL 로그 | fetch join, `@EntityGraph`, batch size |
| 쿼리는 빠른데 응답이 최대 30초까지 늘어짐, 이어서 `Connection is not available` | 커넥션 풀 고갈 | Hikari 메트릭(active·pending), `leakDetectionThreshold` | 커넥션 쥐는 시간 줄이기(트랜잭션 안 외부 호출 제거) |
| 특정 UPDATE가 멈춰 있다가 `ERROR 1205` | 락 대기 | `innodb_trx`, `data_lock_waits`, `sys.innodb_lock_waits` | 막는 트랜잭션 종료, 트랜잭션 짧게, 조건 컬럼 인덱스 |

개념은 각 페이지에 있어요. [인덱스와 B-Tree](../../db/index-btree/), [복합 인덱스](../../db/composite-index/), [JPA N+1](../../spring/jpa-n-plus-one/), [커넥션 풀과 쿼리](../../db/connection-pool-query/), [락](../../db/locks/).

## 제대로 알기

### 실험: DATE()를 씌우면 50배 느려진다

50만 행 `orders` 테이블에 `created_at` 인덱스(`idx_created`)를 걸고, 하루치(1,440행)를 두 가지 방법으로 세어 봤어요. 결과(개수·합계)는 둘이 똑같았어요. 아래 숫자는 한 번 재 본 실험 예시예요.

| 조건 | 실행 방식 | 읽은 행 | 걸린 시간 |
|---|---|---|---|
| `WHERE DATE(created_at) = '2025-06-01'` | `Table scan`(전체 읽기), `type=ALL`, `possible_keys=NULL` | 500,000 | 45.8ms |
| `WHERE created_at >= '2025-06-01' AND created_at < '2025-06-02'` | `Index range scan using idx_created`, `type=range` | 1,440 | 0.70ms |

반복 측정에서도 약 38ms 대 0.8ms로 **약 50배** 차이가 났어요. 함수 쪽 EXPLAIN ANALYZE는 이렇게 읽혀요.

```text
-> Aggregate ... (actual time=45.8..45.8 rows=1 loops=1)
    -> Filter: (cast(orders.created_at as date) = '2025-06-01') ... (actual time=20.2..45.8 rows=1440 loops=1)
        -> Table scan on orders ... (actual time=0.107..35.6 rows=500000 loops=1)
```

안쪽 줄부터 보면 50만 행을 다 읽고(`rows=500000`), 필터에서 1,440행만 남겨요. 버린 행이 99% 이상이에요.

**왜 그럴까요?** 인덱스는 `created_at` **원래 값**의 순서로 정렬돼 있어요. `DATE()`로 가공한 값은 그 순서를 쓸 수 없어서, 모든 행에 함수를 계산해 비교해야 해요. 옵티마이저도 조건을 `cast(created_at as date)`로 바꿔 보여 줘요. 문자열 컬럼을 숫자와 비교하는 형변환도 같은 이유로 인덱스를 못 타요.

**고치는 방법**

1. **컬럼을 가공하지 않는 범위 조건으로 다시 쓰기.** 1순위예요. `>= 당일 AND < 다음날`(반 열린 구간)로 쓰면 경계 실수가 없어요.
2. **함수 결과에 인덱스 걸기.** MySQL 8.0 이후 버전에는 `DATE(created_at)` 같은 식에 인덱스를 거는 함수 기반 인덱스가 있어요. 생성 컬럼(계산된 값을 저장하는 컬럼)에 인덱스를 거는 방법도 있어요. 둘 다 쓰기할 때 인덱스를 하나 더 갱신하는 비용이 들어요.

`BETWEEN '2025-06-01' AND '2025-06-01 23:59:59'`로 바꾸는 답은 흔한 함정이에요. 컬럼이 소수점 이하 초까지 저장하면(`DATETIME(6)`) `23:59:59.5` 같은 값을 놓쳐요.

### 커넥션 풀 고갈은 "에러보다 지연이 먼저"

Spring Boot 기본 풀인 HikariCP는 `maximumPoolSize` 기본 **10**개예요. 빈 커넥션이 없으면 요청 스레드는 `connectionTimeout`(기본 **30초**)까지 **기다려요**. 그래도 못 받으면 이런 예외가 나요.

```text
SQLTransientConnectionException:
{풀 이름} - Connection is not available, request timed out after 30000ms
```

메시지 뒤에는 total·active·idle·waiting 커넥션 수가 붙어요. 그래서 첫 증상은 에러가 아니라 **응답이 최대 30초까지 늘어지는 것**이고, 그다음에 이 예외가 쏟아져요.

이때 DB CPU는 한가할 수 있어요. 쿼리는 빠른데 **커넥션을 오래 쥐는 코드**가 있기 때문이에요.

- 트랜잭션 안에서 외부 API를 호출함(응답 올 때까지 커넥션을 쥐고 있음)
- 느린 쿼리 몇 개가 커넥션 10개를 다 차지함
- 락 대기 중인 요청이 커넥션을 쥔 채 멈춤

확인은 Actuator/Micrometer의 `hikaricp.connections.active`, `hikaricp.connections.pending` 지표로 해요. `leakDetectionThreshold`(기본 0 = 꺼짐)를 켜면 오래 안 돌아온 커넥션을 빌려 간 코드의 스택을 로그로 남겨 줘요.

**풀만 키우면 안 되는 이유**: DB가 동시에 처리하는 쿼리와 락 경합이 늘어서 오히려 더 느려질 수 있어요(HikariCP 문서 "About Pool Sizing"). 커넥션을 쥐는 **시간**을 줄이는 게 먼저예요.

### 심화: 락 대기, 누가 막고 있나 찾기

세션 A가 트랜잭션 안에서 `id=1` 행을 UPDATE하고 커밋하지 않은 채 다른 일을 하면, 같은 행을 UPDATE하려는 세션 B는 기다려요.

<LockWaitChain />

찾는 순서는 이래요.

1. `SHOW PROCESSLIST`로 지금 도는 문장과 `TIME`(초)을 봐요. 오래 멈춘 UPDATE가 보여도 상태만으로 락 대기라고 확정하긴 어려워요.
2. `information_schema.innodb_trx`에서 `trx_state`가 **LOCK WAIT**인 트랜잭션(기다리는 쪽)과, `trx_started`가 한참 전인 **RUNNING** 트랜잭션(범인 후보)을 찾아요.
3. `performance_schema.data_lock_waits`는 한 줄이 "요청한 쪽이 막는 쪽을 기다린다"는 관계예요. `REQUESTING_*`이 기다리는 쪽, `BLOCKING_*`이 막는 쪽이에요. 락 상세는 `data_locks`와 조인해요.
4. `sys.innodb_lock_waits`는 이걸 한 줄로 요약하고, 바로 쓸 수 있는 `KILL QUERY n` / `KILL n` 문장까지 만들어 줘요.

한 번 재 본 예시에서 `data_lock_waits`는 `요청 trx 1571 → 막는 trx 1570`으로 나왔고, 기다리던 B는 결국 이렇게 끝났어요.

```text
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

기다리는 한도는 `innodb_lock_wait_timeout`, 기본 **50초**예요. 1205는 기본적으로 **그 문장만** 롤백하고 트랜잭션은 열린 채로 둬요. 트랜잭션 전체를 롤백하는 데드락(1213)과 달라요.

<Aside type="caution" title="함정: blocking_query는 락을 잡은 쿼리가 아니에요">
`sys.innodb_lock_waits`의 `blocking_query`는 막는 세션이 **지금 실행 중인 문장**이에요. 세션이 놀고 있으면 NULL이에요. 실험에서 락을 잡은 건 `UPDATE ... WHERE id=1`이었는데, blocking_query에는 `SELECT SLEEP(8)`이 보였어요. "트랜잭션을 열어 두고 외부 호출이나 다른 일을 하는 코드"가 전형적인 범인이라, 화면에 UPDATE가 안 보여도 그 세션이 원인일 수 있어요. `trx_started`와 앱 로그로 무슨 코드였는지 추적해요.
</Aside>

**`KILL`은 공짜가 아니에요.** 그 트랜잭션은 롤백돼서 그동안 한 변경이 사라지고, 큰 트랜잭션이면 롤백 자체가 오래 걸려요. 즉시 완화일 뿐이고, 근본 해결은 트랜잭션을 짧게, 외부 호출은 트랜잭션 밖으로, 조건 컬럼에 인덱스예요.

### 심화: 인덱스 없는 UPDATE는 느리고 넓게 잠근다

InnoDB는 UPDATE할 때 **훑은 행**에 락을 걸어요. 조건 컬럼에 인덱스가 없으면 많은 행을 훑으니 그만큼 넓게 잠가요. [락](../../db/locks/) 페이지 실험에선 1행을 고치는데 레코드 락이 1,003개 걸렸어요. 그래서 "느린 쿼리"와 "락 대기"가 한 원인에서 같이 터지고, 대기하는 요청들이 커넥션을 쥔 채 멈추면 "풀 고갈"까지 이어져요. 세 갈래가 연쇄되는 전형적인 모양이에요.

### 심화: 도구를 쓸 때 주의할 점

- `EXPLAIN ANALYZE`는 **실제로 실행**해요. 운영 DB에서 무거운 쿼리나 UPDATE·DELETE에 함부로 돌리면 안 돼요. 운영에선 일반 `EXPLAIN` 먼저, ANALYZE는 복제본이나 스테이징에서 해요.
- digest 표 타이머 값의 단위는 피코초(1조분의 1초)예요. 1e12로 나누면 초예요.
- digest 표는 `TRUNCATE TABLE`로 비울 수 있어요. 배포 직전에 비우고 배포 후 다시 보면 "새로 생긴 무거운 쿼리"를 비교하기 좋아요.
- `log_queries_not_using_indexes`(기본 꺼짐)를 켜면 인덱스를 안 쓴 쿼리도 슬로우 로그에 남아요. `long_query_time`은 `SET GLOBAL`로 바꿀 수 있고, **새 연결부터** 적용돼요.

## 면접 질문

<details>
<summary>Q. 느린 쿼리를 어떻게 찾나요?</summary>

**답변(30초)** 슬로우 쿼리 로그와 performance_schema의 digest 집계를 같이 봐요. 슬로우 로그는 기본 꺼짐에 기준 10초라서 1초 이하로 낮춰 켜고, `Rows_examined`가 `Rows_sent`보다 훨씬 큰 쿼리를 먼저 봐요. 로그는 한 건씩이라, 같은 모양 쿼리를 묶은 digest 표(또는 `sys.statement_analysis`)에서 총 시간 순으로 순위를 봐요. 찾은 쿼리는 EXPLAIN ANALYZE로 원인을 확인해요.

**꼬리질문**
- Q. 왜 평균 말고 총 시간으로 보나요? → 평균 1ms라도 수십만 번 불리면 DB 시간을 제일 많이 먹어요. N+1이 이렇게 숨어요.
- Q. 슬로우 로그가 비었으면 DB 문제가 아닌가요? → 아니에요. 기준이 높거나, 빠른 쿼리가 많이 나가거나(N+1), 커넥션 대기 시간은 슬로우 로그에 안 남아요.
</details>

<details>
<summary>Q. 인덱스가 있는데 안 타는 경우를 예로 들어 주세요.</summary>

**답변(30초)** 조건에서 컬럼을 가공하면 인덱스를 못 타요. 예를 들어 `DATE(created_at) = '2025-06-01'`은 인덱스가 원래 값 순서로 정렬돼 있어서 쓸 수 없고 전체 행을 읽어요. 실험에서 50만 행을 다 읽어 45.8ms가 걸렸고, `created_at >= 당일 AND < 다음날`로 바꾸니 1,440행만 읽어 0.70ms였어요. 형변환, 앞에 `%`가 붙은 LIKE, 복합 인덱스의 왼쪽 컬럼을 빼먹은 조건도 같은 종류예요.

**꼬리질문**
- Q. 꼭 함수를 써야 하면요? → 함수 기반 인덱스나 생성 컬럼+인덱스가 있지만, 쓰기마다 인덱스를 더 갱신하는 비용이 있어서 조건 재작성이 1순위예요.
- Q. BETWEEN으로 23:59:59까지 쓰면요? → 소수점 이하 초를 저장하는 컬럼이면 경계 값을 놓쳐요. 반 열린 구간이 안전해요.
</details>

<details>
<summary>Q. "Connection is not available, request timed out after 30000ms"가 나오면 무엇을 의심하나요?</summary>

**답변(30초)** HikariCP 커넥션 풀이 고갈돼서 30초(기본 connectionTimeout) 동안 커넥션을 못 받은 거예요. 풀 크기보다 **커넥션을 오래 쥐는 코드**를 먼저 의심해요. 트랜잭션 안의 외부 API 호출, 느린 쿼리, 락 대기 중인 요청이 대표적이에요. active·pending 지표와 leakDetectionThreshold로 어떤 코드가 오래 쥐는지 찾아요.

**꼬리질문**
- Q. 풀을 늘리면 안 되나요? → 임시로는 될 수 있지만 DB 동시 실행과 락 경합이 늘어 더 느려질 수 있어요. 점유 시간을 줄이는 게 근본이에요.
</details>

<details>
<summary>Q. 어떤 UPDATE가 멈춰 있어요. 누가 막는지 어떻게 찾고, 찾은 뒤엔 어떻게 하나요?</summary>

**답변(30초)** `innodb_trx`에서 LOCK WAIT 트랜잭션과 오래된 RUNNING 트랜잭션을 보고, `performance_schema.data_lock_waits`나 `sys.innodb_lock_waits`로 막는 쪽 스레드를 찾아요. 급하면 `KILL`하지만 그 트랜잭션이 롤백되니 영향을 확인하고 해요. 근본적으로는 트랜잭션을 짧게 하고, 외부 호출을 트랜잭션 밖으로 빼고, 조건 컬럼에 인덱스를 둬요.

**꼬리질문**
- Q. blocking_query가 NULL이거나 엉뚱한 쿼리면요? → 그 컬럼은 막는 세션이 "지금" 실행 중인 문장이라, 락을 잡고 놀고 있으면 NULL이에요. `trx_started`와 앱 로그로 추적해요.
- Q. 1205와 1213은 뭐가 달라요? → 1205는 락 대기 타임아웃으로 기본적으로 문장만 롤백, 1213은 데드락으로 트랜잭션 전체를 롤백해요.
</details>

## 서술형 연습

아래 상황은 모두 실무 상황형 연습용으로 지어낸 것이에요. 실제 기출 문제가 아니에요.

<details>
<summary>상황 1: 주문이 쌓이면서 "일별 매출" API만 점점 느려지더니, 오늘은 응답이 수 초 걸려요. 다른 API는 정상이에요. 배포한 것도 없어요.</summary>

**상황 파악**
한 API만 느리고 배포도 없으니 공용 자원(풀·락)보다 **그 API의 쿼리**가 데이터 증가를 못 버티는 쪽을 먼저 의심해요. 데이터가 적을 땐 전체 읽기도 빨라서 티가 안 났다가, 행 수가 늘면서 시간이 같이 늘어난 모양이에요.

**원인 후보**
1. 조건이 인덱스를 못 타서 전체 행을 읽음(컬럼 가공, 형변환, 인덱스 없음)
2. 조회 범위가 너무 넓음(기간 제한·페이징 없음)
3. 같은 시간대에 다른 작업이 테이블을 잠금(이 경우 다른 API도 영향받았을 가능성이 커서 우선순위 낮음)

**확인 순서**
APM에서 DB 구간 비중 확인 → 슬로우 로그 기준을 낮춰 해당 쿼리의 `Rows_examined`가 전체 행 수에 가까운지 확인 → digest 표에서 이 쿼리의 평균 시간과 읽은 행 수 → 스테이징에서 `EXPLAIN ANALYZE`로 `Table scan`, `type=ALL`인지 확인.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 조건을 인덱스 탈 수 있게 재작성 | 코드 수정만으로 끝, 쓰기 비용 없음 | 같은 패턴 쿼리를 다 찾아 고쳐야 함 |
| B. 필요한 컬럼에 인덱스 추가 | 비슷한 쿼리도 같이 빨라짐 | 쓰기마다 인덱스 갱신, 큰 테이블이면 인덱스 생성 작업 부담 |
| C. 일별 합계를 미리 계산해 두는 집계 테이블 | 조회가 가장 빠름 | 배치·갱신 로직, 실시간성 떨어짐 |

**내가 고를 방법**
EXPLAIN으로 원인이 확인되면 A(필요하면 B)를 먼저 해요. 수정 전후 EXPLAIN ANALYZE의 읽은 행 수와 시간을 비교해 효과를 숫자로 보여 줘요. 데이터가 더 커져 A·B로도 부족하면 C를 검토해요. 재발 방지로 슬로우 로그 기준을 낮추고, 쿼리 리뷰 때 EXPLAIN을 보는 체크리스트를 둬요.

**채점 포인트**: 한 API만 → 해당 쿼리 의심, 데이터 증가와 풀 스캔 비용, Rows_examined vs Rows_sent, digest/총 시간, EXPLAIN ANALYZE(운영에서 주의), 전후 수치 비교, 재발 방지.

**흔한 감점 답안**: "서버를 늘린다"(DB 쿼리 문제는 앱 서버를 늘려도 안 풀림), 확인 없이 "인덱스 추가"만 씀, 원인 확인 도구를 하나도 안 말함.
</details>

<details>
<summary>상황 2: 아래 쿼리가 슬로우 로그 상위에 있어요. created_at에는 인덱스가 있어요. 왜 느리고 어떻게 고치나요? `SELECT COUNT(*), SUM(amount) FROM orders WHERE DATE(created_at) = ?`</summary>

**상황 파악**
인덱스가 있는데도 느리다면 "인덱스를 못 쓰는 조건"을 의심해요. 슬로우 로그에서 `Rows_sent: 1`, `Rows_examined`가 전체 행 수라면 거의 확실해요.

**원인**
인덱스는 `created_at` 원래 값 순서로 정렬돼 있어요. `DATE()`를 씌우면 그 순서를 쓸 수 없어서 모든 행에 함수를 계산해 비교해요. EXPLAIN에서 `type=ALL`, `possible_keys=NULL`로 보이고, EXPLAIN ANALYZE에서 `Table scan`이 50만 행을 읽은 뒤 `Filter`가 1,440행만 남겨요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `created_at >= :day AND created_at < :nextDay`로 재작성 | 기존 인덱스 그대로 사용, 추가 비용 없음 | 호출 코드에서 다음 날 값을 계산해야 함 |
| B. 함수 기반 인덱스 | 쿼리를 안 바꿔도 됨 | 인덱스 하나 더, 쓰기 비용, 같은 식을 정확히 써야 탐 |
| C. 날짜만 담는 생성 컬럼 + 인덱스 | 다른 쿼리에서도 재사용 | 스키마 변경, 저장 공간·쓰기 비용 |

**내가 고를 방법**
A를 골라요. 실험에서 같은 결과를 내면서 45.8ms가 0.70ms로 약 50배 빨라졌고, 읽은 행이 50만에서 1,440으로 줄었어요(실험 예시). 경계는 `BETWEEN ... 23:59:59`가 아니라 반 열린 구간으로 써서 소수점 초 값을 놓치지 않게 해요. 수정 후 EXPLAIN에서 `type=range`, `key=idx_created`를 확인해요.

**채점 포인트**: 컬럼 가공 → 인덱스 정렬 순서 못 씀, EXPLAIN 근거(ALL/range), 범위 조건 재작성, 반 열린 구간, 대안과 쓰기 비용, 전후 수치.

**흔한 감점 답안**: "인덱스를 하나 더 만든다"(이미 있음, 원인 설명 없음), `BETWEEN` 23:59:59로 고침, 형변환·LIKE 같은 같은 계열 함정을 모름.
</details>

<details>
<summary>상황 3: 이벤트로 트래픽이 늘자 전체 API가 30초씩 걸리다가 "Connection is not available, request timed out after 30000ms" 에러가 폭증했어요. DB CPU는 20%로 한가해요. 팀원이 풀 크기를 10에서 100으로 늘리자고 해요.</summary>

**상황 파악**
DB는 한가한데 앱이 커넥션을 못 받고 있어요. 30초는 HikariCP 기본 connectionTimeout과 같아요. 쿼리 실행이 아니라 **커넥션을 오래 쥐는 것**이 문제일 가능성이 커요. 전체 API가 같이 느린 건 커넥션 풀이 공용 자원이라서예요.

**원인 후보**
1. 트랜잭션 안에서 외부 API(결제·알림 등)를 호출해 응답 올 때까지 커넥션을 쥠
2. 이벤트 관련 느린 쿼리 몇 개가 커넥션을 오래 차지
3. 락 대기 중인 요청들이 커넥션을 쥔 채 멈춤
4. 커넥션을 반납하지 않는 코드(누수)

**확인 순서**
`hikaricp.connections.active`가 최대치에 붙어 있고 `pending`이 쌓이는지 → `leakDetectionThreshold`를 켜서 오래 쥔 커넥션의 스택 확인 → 스레드 덤프에서 요청 스레드가 어디서 기다리는지 → DB 쪽 PROCESSLIST·`innodb_trx`로 오래 열린 트랜잭션 확인.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 풀 크기 증설 | 설정만 바꿔 즉시 적용 | 원인이 그대로면 금방 다시 고갈, DB 동시 실행·락 경합 증가로 더 느려질 수 있음 |
| B. 외부 호출을 트랜잭션 밖으로, 트랜잭션 짧게 | 근본 해결, 같은 풀로 더 많이 처리 | 코드 구조 변경, 외부 호출과 DB 반영 사이 정합성 설계 필요 |
| C. 느린 쿼리 수정 | 점유 시간 직접 감소 | 원인 쿼리 찾기에 시간 필요 |
| D. 문제 기능 끄기·요청 제한 | 즉시 피해 차단 | 기능 일부 포기 |

**내가 고를 방법**
즉시는 D로 피해를 줄이고, 풀 증설은 하더라도 소폭·임시로만 해요. 지표로 원인을 확인한 뒤 B 또는 C로 점유 시간을 줄이는 게 본 해결이에요. 재발 방지로 pending 커넥션 수와 대기 시간에 알림을 걸고, 외부 API 호출에 타임아웃을 둬요.

**채점 포인트**: 30초 = connectionTimeout 기본값, DB 한가 → 점유 시간 문제, 풀 크기만 늘리면 안 되는 이유, 트랜잭션 안 외부 호출, active/pending 지표, leakDetectionThreshold, 재발 방지 알림.

**흔한 감점 답안**: "풀을 100으로 늘린다"로 끝냄, "DB 서버 스펙을 올린다"(DB는 한가함), connectionTimeout을 늘려 에러만 늦춤.
</details>

<details>
<summary>상황 4: 매일 새벽 정산 배치가 돌 때마다 주문 상태 변경 API가 50초쯤 멈췄다가 "ERROR 1205 Lock wait timeout exceeded"로 실패해요. 배치가 끝나면 정상이에요.</summary>

**상황 파악**
50초는 `innodb_lock_wait_timeout` 기본값과 같아요. 주문 API가 **배치가 잡은 락**을 기다리다 포기한 거예요. 배치 시간에만 생기니 배치 쿼리의 락 범위와 트랜잭션 길이를 의심해요.

**원인 후보**
1. 배치가 큰 범위를 한 트랜잭션으로 UPDATE해서 끝날 때까지 락을 쥠
2. 배치 UPDATE 조건 컬럼에 인덱스가 없어 훑은 행 전체를 잠금(실제로 바꿀 행보다 훨씬 넓게)
3. 배치가 트랜잭션을 연 채 외부 호출·다른 처리를 함

**확인 순서**
배치 시간에 `innodb_trx`에서 LOCK WAIT(주문 API)와 오래된 RUNNING(배치)을 확인 → `data_lock_waits`로 막는 트랜잭션이 배치인지 확인 → `data_locks`로 잠근 범위 확인 → 배치 쿼리 EXPLAIN으로 인덱스 사용 여부 확인. `sys.innodb_lock_waits`의 blocking_query는 배치가 "지금" 하는 문장이라 락 잡은 UPDATE와 다를 수 있음에 주의해요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 배치를 PK 범위로 잘게 나눠(청크) 청크마다 커밋 | 락을 짧게 쥠, 주문 API가 사이사이 진행 | 전체가 원자적이지 않음, 중간 실패 시 이어서 돌릴 수 있게(멱등) 설계 필요 |
| B. 배치 조건 컬럼에 인덱스 | 잠그는 행 수 자체가 줄고 배치도 빨라짐 | 인덱스 추가 비용 |
| C. 배치를 트래픽 적은 시간으로 이동 | 간단 | 문제를 피할 뿐, 데이터가 늘면 다시 겹침 |
| D. 주문 API에서 1205 재시도 | 일부 요청 구제 | 50초를 기다린 뒤라 사용자 경험은 이미 나쁨 |

**내가 고를 방법**
B와 A를 같이 해요. 인덱스로 잠그는 범위를 줄이고, 청크 커밋으로 락 쥐는 시간을 줄여요. 청크 크기는 한 번 실행이 짧게 끝나는 크기로 테스트해 정해요. 지금 당장 막혀 있으면 배치 트랜잭션을 `KILL`할 수 있지만, 롤백되면서 그동안 변경이 사라지고 롤백도 오래 걸릴 수 있어 영향을 먼저 확인해요. 대규모 배치 설계는 [대용량 데이터 마이그레이션·배치](../data-migration/)와 이어져요.

**채점 포인트**: 50초 = lock wait timeout 기본값, 1205 의미(기본은 문장만 롤백), 막는 트랜잭션 찾기(innodb_trx, data_lock_waits), blocking_query 함정, 인덱스 없는 UPDATE의 넓은 락, 청크 커밋, 멱등 재실행, KILL의 롤백 비용.

**흔한 감점 답안**: "lock wait timeout을 늘린다"(더 오래 기다릴 뿐), 1205를 데드락이라고 함, 배치를 한 트랜잭션으로 유지한 채 시간만 옮김.
</details>

<details>
<summary>상황 5: 게시글 목록 API(한 페이지 100개)가 3초 걸려요. 슬로우 로그에는 아무것도 없어요. SQL 로그를 켜 보니 목록 조회 한 번에 쿼리가 101번 나가요.</summary>

**상황 파악**
쿼리 하나하나는 빨라서 슬로우 로그엔 안 남지만, 101번이 순서대로 나가니 합치면 느려요. 목록 1번 + 게시글마다 작성자 조회 100번, 전형적인 **N+1**이에요. digest 표를 보면 `... WHERE id = ?` 같은 같은 모양 쿼리의 `COUNT_STAR`가 비정상적으로 커요.

**원인 후보**
1. JPA 지연 로딩 연관(작성자 등)을 목록 반복문이나 응답 변환에서 하나씩 건드림
2. 즉시 로딩으로 설정했어도 JPQL 목록 조회 후 연관을 따로 불러옴

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. fetch join | 쿼리 1번으로 함께 조회 | 컬렉션 연관을 fetch join하면 페이징을 DB에서 못 하는 문제가 있음 |
| B. `@EntityGraph` | 메서드마다 함께 불러올 연관 지정 | 결국 조인이라 A와 같은 한계 |
| C. batch size(`IN`으로 묶어 조회) | 페이징과 함께 쓰기 좋음, 쿼리 1 + 몇 번 | 완전히 1번은 아님 |
| D. 필요한 컬럼만 DTO로 조회 | 가장 가벼움 | 엔티티 재사용성 떨어짐, 쿼리 직접 작성 |

**내가 고를 방법**
작성자처럼 다대일 연관이면 A로 1번에 가져와요. 댓글 같은 컬렉션이고 페이징이 필요하면 C를 써요. 수정 후 SQL 로그에서 쿼리 수가 줄었는지, 응답 시간이 줄었는지 숫자로 확인해요. 재발 방지로 테스트에서 요청당 쿼리 수를 확인하거나 digest 표에서 실행 횟수 상위를 주기적으로 봐요. 개념은 [JPA N+1](../../spring/jpa-n-plus-one/)에 있어요.

**채점 포인트**: 슬로우 로그에 안 잡히는 이유, 총 시간 = 횟수 × 평균, digest COUNT_STAR, N+1 정의(1 + N), fetch join·EntityGraph·batch size·DTO, 페이징 주의, 전후 쿼리 수 비교.

**흔한 감점 답안**: "즉시 로딩(EAGER)으로 바꾼다"(N+1이 사라지지 않을 수 있고 다른 곳까지 무거워짐), "캐시를 붙인다"로 원인을 덮음, 슬로우 로그가 비었으니 DB 문제가 아니라고 함.
</details>
