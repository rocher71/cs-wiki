:::tip[한 줄 요약]
원인을 모를 땐 **① 지표로 "언제·어느 서버"를 좁히고 → ② traceId로 요청 하나의 로그를 서비스 끝까지 따라가고 → ③ 멈춤이나 CPU 100%는 스레드 덤프로 스레드가 지금 뭘 하는지 직접 봐요.** 그러려면 로그가 처음부터 JSON 구조화 로그에 traceId가 찍혀 있고, 개인정보는 가려져 있어야 해요.
:::

:::note[처음이라면 여기까지]
① 로그는 "현장 기록", 지표는 "맥박·체온", 트레이스는 "동선"이에요. 셋을 맞춰 봐야 원인이 보여요.

② 서버가 여러 대면 로그가 흩어져요. 요청마다 붙는 번호 **traceId**로 검색하면 한 요청의 기록만 한 줄로 모여요.

③ 서버가 멈췄을 땐 **스레드 덤프**(thread dump, 지금 이 순간 모든 스레드가 어디서 뭘 하는지 찍은 사진)를 떠요. 멈췄는데 CPU가 한가하면 서로 기다리는 중(교착상태·대기), CPU가 100%면 어딘가 계속 도는 중이에요.

④ 서술형은 상황 1·2부터 연습하세요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

탐정이 사건을 푼다고 해 봐요.

**현장 기록**(로그)에는 "몇 시에 누가 무엇을 했다"가 적혀 있어요. **맥박·체온**(지표)은 "몇 시부터 이상했다"를 숫자로 알려 줘요. **동선**(트레이스)은 한 사람이 어느 방을 거쳐 갔는지 보여 줘요.

기록이 "누가 뭔가 했음"처럼 대충 적혀 있으면 아무리 많아도 소용없어요. 그래서 좋은 기록은 항목이 정해진 서식(구조화 로그)이고, 사건마다 같은 **사건 번호**(traceId)가 붙어 있어요.

용의자가 아무 말도 안 하고 서 있으면(서버 무응답) 탐정은 그 순간을 사진으로 찍어요. 이게 스레드 덤프예요. 사진 속에서 두 사람이 서로의 열쇠를 쥔 채 상대가 먼저 주길 기다리고 있으면 교착상태예요.

단, 실제로는 탐정 한 명이 다 기억하지 않아요. 로그는 로그 수집기에, 지표는 지표 저장소에 따로 쌓이고, traceId가 그 둘을 잇는 고리예요. 세 신호 자체의 개념은 [관측성](../../infra/observability/), 서비스 사이로 번호를 넘기는 원리는 [분산 추적과 서비스 메시](../../architecture/distributed-tracing-mesh/)에 있어요.

## 이 유형을 푸는 순서

"원인을 모르겠다"류 문제는 아래 순서를 답안 뼈대로 써요. 답안 쓰는 일반 구조는 [서술형 답안 쓰는 법](../how-to-answer/)에 있어요.

| 단계 | 할 일 | 이 주제에서 구체적으로 |
|---|---|---|
| 1. 증상 확인 | 무엇이, 언제부터 | 에러율·응답 시간 그래프, 어떤 API·어떤 에러 코드 |
| 2. 영향 범위 | 누가, 몇 명이 | 전체인지, 한 인스턴스·한 사용자군·한 앱 버전인지 |
| 3. 즉시 완화 | 피해 멈추기 | 이상한 인스턴스를 트래픽에서 빼기(빼기 전 덤프 확보), 최근 배포 롤백 |
| 4. 원인 찾기 | 좁혀 가기 | 지표로 시간·인스턴스 → 로그로 실패 건 → traceId로 요청 하나 → 필요하면 스레드 덤프 |
| 5. 근본 해결 | 코드·설정 수정 | 락 순서, 무한 루프, 타임아웃, 마스킹 |
| 6. 재발 방지 | 다음엔 바로 보이게 | 구조화 로그·traceId 표준화, 레벨 규칙, 알림, 마스킹 규칙 |

### 증상별 원인 후보와 확인 도구

| 증상 | 먼저 의심할 것 | 확인 도구 |
|---|---|---|
| 일부 요청만 가끔 실패 | 특정 인스턴스·입력·시간대에 몰린 문제 | 구조화 로그를 필드별로 묶어 세기, traceId로 한 건 추적 |
| 응답 없음 + CPU 낮음 | 교착상태, 락·커넥션 풀 대기, 타임아웃 없는 외부 호출 | `jcmd <pid> Thread.print`, 스레드 상태 |
| 응답 느림 + CPU 100% | 무한 루프·무거운 연산, 또는 GC | `top -H -p <pid>` → 스레드 ID 16진수 → 덤프의 `nid` |
| 로그는 많은데 못 찾음 | 평문 로그, 상관 ID 없음, 레벨 남발 | 구조화 로그, `traceId` MDC, 레벨 규칙 |
| 로그에 민감정보 | 요청 객체 통째 로깅, `toString()` | 마스킹 배포, 저장된 사본 정리 |

GC가 CPU를 먹는 경우는 [메모리 누수·OOM·GC 폭주](../memory-oom/), 외부 호출 대기는 [외부 API 장애 대응](../external-api-failure/), 장애 공유·롤백 절차는 [장애 대응·롤백·포스트모템](../incident-response/)에 있어요.

## 제대로 알기

### 좋은 로그 ① 구조화 로그: 한 줄에 JSON 하나

**구조화 로그**(structured log, 로그 한 줄을 정해진 필드가 있는 데이터로 남기는 방식)는 "주문 실패 user=7 order=1234" 같은 문장 대신 JSON 객체를 한 줄에 하나씩 찍어요.

왜 필요할까요? 평문은 사람이 읽기엔 좋지만, "실패한 요청 500건을 인스턴스별로 세 줘" 같은 질문에 답하려면 정규식으로 긁어야 해요. JSON이면 로그 검색 도구에서 필드로 바로 거르고 묶어 셀 수 있어요. 재현 안 되는 버그를 잡을 때 이게 결정적이에요.

Spring Boot는 **3.4부터** 구조화 로그를 내장 지원해요. 그 전에는 logstash-logback-encoder 같은 외부 라이브러리로 했어요.

```properties
# 콘솔 로그를 JSON으로 (ecs, logstash, gelf 중 하나)
logging.structured.format.console=ecs
# 파일 로그도 따로 지정 가능
logging.structured.format.file=logstash
```

- `ecs`: Elastic Common Schema 형식
- `logstash`: Logstash 형식
- `gelf`: Graylog Extended Log Format 형식
- 직접 만든 포맷터 클래스 이름을 넣을 수도 있어요.

ECS로 찍으면 대략 이런 모양이에요(값은 줄임).

```json
{"@timestamp":"...","log":{"level":"INFO","logger":"org.example.Application"},"service":{"name":"simple"},"message":"...","ecs":{"version":"8.11"}}
```

세 형식(ECS·Logstash·GELF) 모두 **MDC**(Mapped Diagnostic Context, 지금 스레드에 붙여 두는 "이 요청의 꼬리표" 저장소)에 든 키를 JSON 필드로 자동으로 넣어 줘요. 그래서 traceId 같은 값을 MDC에 넣으면 따로 손대지 않아도 모든 줄에 찍혀요.

### 좋은 로그 ② 요청마다 traceId

Spring Boot에 **Micrometer Tracing**(요청마다 추적 번호를 만들고 넘겨 주는 라이브러리)을 붙이면, 추적 번호를 MDC의 `traceId`, `spanId` 키에 넣어 줘요. Spring Boot는 이 둘로 **상관 ID**(correlation ID, 같은 요청에서 나온 로그를 묶는 번호)를 만들어 로그 줄에 자동으로 찍어요. 형식은 `logging.pattern.correlation`으로 바꿀 수 있어요.

이게 있으면 "요청 하나 따라가기"가 검색 한 번이에요. 사용자 신고의 주문번호로 로그 한 줄을 찾고, 그 줄의 traceId로 다시 검색하면 여러 서비스의 로그가 시간순으로 모여요.

<Aside type="caution" title="스레드가 바뀌면 traceId가 사라질 수 있어요">
MDC는 스레드에 붙는 저장소예요. `@Async`, 직접 만든 스레드 풀, `CompletableFuture`로 일을 넘기면 새 스레드에는 꼬리표가 없어서 그 뒤 로그에 traceId가 비어요. 컨텍스트를 복사해 넘기는 장치(Micrometer의 context-propagation, `TaskDecorator`)가 필요해요. 외부 호출에 번호를 넘기려면 자동 구성된 `RestClient.Builder`·`WebClient.Builder`를 써야 한다는 점은 [관측성](../../infra/observability/)에 있어요.
</Aside>

### 좋은 로그 ③ 레벨 기준

레벨 이름(TRACE, DEBUG, INFO, WARN, ERROR)은 정해져 있지만 **언제 무엇을 쓸지는 표준이 없고 팀 규칙**이에요. 흔히 쓰는 기준은 이래요. Spring Boot 기본 출력은 INFO 이상이에요.

| 레벨 | 언제 | 예 |
|---|---|---|
| ERROR | 사람이 조치해야 하는 실패 | 결제 요청 실패, 데이터 불일치 |
| WARN | 스스로 회복했지만 지켜볼 것 | 재시도 후 성공, 폴백 동작 |
| INFO | 업무 이벤트·상태 변화 | 주문 생성, 배치 시작·종료 |
| DEBUG | 개발·장애 조사용 상세값 | 요청 파라미터, 분기 결과(운영 기본 꺼둠) |

흔한 실수 두 가지예요.

- 같은 예외를 컨트롤러·서비스·저장소에서 모두 ERROR로 찍기. 알림이 세 배로 울리고 검색이 어지러워요. **처리하는 한 곳에서만** 찍어요.
- 입력 검증 실패(400) 같은 **예상된 실패**를 ERROR로 찍기. 진짜 장애가 묻혀요.

### 좋은 로그 ④ 남기면 안 되는 것

OWASP Logging Cheat Sheet는 아래를 로그에 그대로 남기지 말고 지우거나, 가리거나(마스킹), 해시하거나, 암호화하라고 해요.

- 세션 ID, 액세스 토큰, 비밀번호, 암호화 키, DB 접속 문자열
- 카드·계좌 정보
- 주민등록번호 같은 정부 식별자, 건강 정보 같은 민감 개인정보

세션을 추적해야 하면 원본 대신 해시값을 남겨요. (일반 원칙) 한국 개인정보보호법도 개인정보에 접근 통제·암호화 같은 안전 조치를 요구하고, 금융권은 카드·계좌번호 노출에 특히 엄격해요(조항 세부는 여기서 다루지 않아요).

마스킹은 **찍는 순간** 하는 게 안전해요. 로그 포맷터에서 가리거나, DTO의 `toString()`에서 민감 필드를 빼요. 수집한 뒤에 지우면 이미 복제·백업된 사본이 남아요.

### 스레드 덤프 뜨고 읽기

**스레드 덤프**는 JVM 안 모든 스레드의 현재 상태와 호출 스택을 찍은 사진이에요. 서버가 멈췄거나 CPU를 이상하게 쓸 때 "지금 무엇을 하고 있나"를 직접 보는 도구예요.

뜨는 방법은 세 가지예요.

- `jcmd <pid> Thread.print`: Oracle이 권장하는 방법이에요.
- `jstack <pid>`: 오래 쓰여 온 도구지만 Oracle 문서에선 실험적 도구로 분류하고 jcmd를 권해요. `-l`을 붙이면 `java.util.concurrent` 락 정보도 나와요.
- `kill -3 <pid>`(SIGQUIT 신호): JVM이 표준 출력에 덤프를 찍어요. 프로세스는 죽지 않아요.

덤프의 스레드 한 덩어리 첫 줄에는 스레드 이름, 우선순위, `tid`(JVM 안 스레드 구조체 주소), **`nid`(OS가 붙인 스레드 번호, 16진수)**, 상태가 있어요. 그 아래 `java.lang.Thread.State:` 줄과 호출 스택이 이어져요.

상태는 네 가지를 구분하면 돼요(Java 17 `Thread.State` 기준).

| 상태 | 뜻 | 대표 원인 |
|---|---|---|
| RUNNABLE | JVM에선 실행 중 | 계산 중, **또는 소켓 읽기처럼 OS 자원을 기다리는 중** |
| BLOCKED | 모니터 락(`synchronized`)을 기다림 | 다른 스레드가 `synchronized` 블록을 쥐고 있음 |
| WAITING | 시간 제한 없이 다른 스레드를 기다림 | `Object.wait()`, `Thread.join()`, `LockSupport.park()` |
| TIMED_WAITING | 시간 제한 있는 대기 | `Thread.sleep(ms)`, `wait(ms)`, `parkNanos` |

이 상태는 JVM이 보는 상태라 OS의 스레드 상태와 꼭 일치하지는 않아요.

### 실험: 교착상태는 덤프에 이렇게 보여요

두 스레드가 락 두 개를 **반대 순서**로 잡는 작은 프로그램을 띄웠어요. `order-worker`는 A→B, `payment-worker`는 B→A 순서로 잡고, 사이에 0.2초 쉬어요. 2초 뒤 `jcmd <pid> Thread.print`로 뜬 덤프에서 두 스레드 부분만 발췌했어요(로컬 JDK 17로 한 번 재 본 예시, 주소는 실행마다 달라요).

```text
"order-worker" #14 prio=5 os_prio=31 cpu=0.17ms elapsed=2.15s tid=0x000000013f843000 nid=0x7203 waiting for monitor entry  [0x000000017253e000]
   java.lang.Thread.State: BLOCKED (on object monitor)
	at Deadlock.lambda$main$0(Deadlock.java:5)
	- waiting to lock <0x000000061fc1afb0> (a java.lang.Object)
	- locked <0x000000061fc1afa0> (a java.lang.Object)

"payment-worker" #15 prio=5 os_prio=31 cpu=0.12ms elapsed=2.15s tid=0x000000013f839800 nid=0x6403 waiting for monitor entry  [0x000000017274a000]
   java.lang.Thread.State: BLOCKED (on object monitor)
	at Deadlock.lambda$main$1(Deadlock.java:6)
	- waiting to lock <0x000000061fc1afa0> (a java.lang.Object)
	- locked <0x000000061fc1afb0> (a java.lang.Object)

Found one Java-level deadlock:
=============================
"order-worker":
  waiting to lock monitor 0x0000600001bb0000 (object 0x000000061fc1afb0, a java.lang.Object),
  which is held by "payment-worker"

"payment-worker":
  waiting to lock monitor 0x0000600001bb4000 (object 0x000000061fc1afa0, a java.lang.Object),
  which is held by "order-worker"
...
Found 1 deadlock.
```

읽는 순서는 이래요.

1. **맨 아래부터 봐요.** HotSpot JVM은 덤프를 찍은 뒤 교착상태 탐지를 돌려서, 있으면 `Found one Java-level deadlock`을 붙여 줘요. `synchronized`와 `java.util.concurrent` 락 둘 다 대상이에요.
2. **`locked`와 `waiting to lock`을 짝지어요.** order-worker는 `...afa0`을 쥐고 `...afb0`을 기다리고, payment-worker는 정반대예요. 서로가 서로를 기다리는 원이에요.
3. **`cpu=` 값을 봐요.** 두 스레드 모두 0.2ms도 안 썼어요. 교착상태는 "멈췄는데 CPU는 한가한" 모양이에요.
4. **스택의 줄 번호**(`Deadlock.java:5`, `:6`)가 락을 잡는 코드 위치예요. 여기를 고쳐요.

JVM의 `synchronized` 교착상태는 **스스로 풀리지 않아요.** JVM은 탐지해서 알려 줄 뿐이라 재시작 전까지 그 스레드들은 영영 멈춰 있어요. DB(InnoDB)는 교착상태를 감지하면 한쪽 트랜잭션을 롤백해서 풀어 주는 것과 달라요. 고치는 방법은 락 잡는 순서를 전체 코드에서 통일하기, `tryLock(시간)`으로 기다림에 상한 두기, 락 범위 줄이기예요. 개념은 [동기화](../../java/synchronization/)에 있어요.

### CPU 100%: 어떤 스레드가 먹고 있나 (Linux 기준)

교착상태와 반대로 CPU가 꽉 차 있으면 **계속 도는 스레드**를 의심해요. 순서는 이래요(숫자는 설명용 가짜 값).

1. `top`으로 java 프로세스가 CPU를 다 쓰는지 확인해요.
2. `top -H -p <pid>`로 그 프로세스의 **스레드별** CPU를 봐요. 예: 스레드 ID 12345가 99%.
3. 그 번호를 16진수로 바꿔요. `printf '%x' 12345` → `3039`.
4. `jcmd <pid> Thread.print`로 덤프를 떠서 `nid=0x3039`인 스레드를 찾아요.
5. 덤프를 **몇 초 간격으로 2~3번** 떠서, 매번 RUNNABLE이고 같은 메서드에 있는지 봐요. 그렇다면 그 코드가 범인이에요(무한 while, 무거운 정규식 등).

<Aside type="note" title="macOS에선 이대로 안 맞아요">
`top -H`의 스레드 ID와 덤프 `nid`를 16진수로 맞추는 방법은 Linux HotSpot 기준이에요. 운영 서버(대부분 Linux 컨테이너)에서 쓰는 방법이고, macOS 노트북에선 번호가 대응하지 않아요.
</Aside>

CPU를 먹는 스레드가 `GC Thread`류면 코드 루프가 아니라 메모리 문제예요. GC 로그와 힙을 봐요([메모리 누수·OOM·GC 폭주](../memory-oom/)).

### 재현 안 되는 버그: 실패들의 공통점 찾기

"가끔만 실패해요"는 한 건을 아무리 들여다봐도 안 풀릴 때가 많아요. 대신 **실패한 요청 여러 건을 모아 축별로 쪼개 세요.** 한 축에 몰리면 그게 단서예요.

| 축 | 쪼개 보는 것 | 몰리면 의심할 것 |
|---|---|---|
| 시간 | 분·시 단위 분포 | 정각 배치, 크론, 트래픽 피크, 배포 시각 |
| 인스턴스 | 파드·노드·버전별 | 한 대만 다른 설정·버전, 노드 문제 |
| 사용자·입력 | 앱 버전, 국가, 특정 데이터 | 특정 입력값 처리 버그, 구버전 앱 |
| 의존성 | DB 복제본, 외부 API, 카드사 | 특정 의존 대상의 지연·오류 |

구조화 로그면 이 쪼개기가 필드별로 묶어 세기 한 번이에요. 순서는 **지표 → 로그 → 트레이스**예요. 에러율 그래프로 시간대·인스턴스를 좁히고, 그 구간 ERROR 로그를 traceId로 열어 트레이스에서 어느 구간인지 봐요.

Google SRE 책의 문제 해결 장도 같은 흐름을 권해요. 먼저 피해를 줄이고, 관찰한 데이터로 가설을 세워 검증하고, **최근 변경**(배포·설정)이 흔한 원인이니 그 시각과 대조하라고 해요. 다만 시각이 겹친다고 원인이라고 단정하면 안 돼요. 상관관계는 가설일 뿐이라, 되돌려 보거나 재현해서 확인해요.

### 심화: 덤프 읽을 때 흔한 착각

- **"BLOCKED가 없으니 락 문제가 아니다" → 틀려요.** BLOCKED는 `synchronized` 대기만이에요. `ReentrantLock`이나 커넥션 풀(HikariCP) 대기는 내부적으로 `LockSupport.park`라서 **WAITING/TIMED_WAITING**으로 보여요.
- **"RUNNABLE이면 CPU를 쓰는 중" → 아닐 수 있어요.** 타임아웃 없는 외부 호출로 소켓 읽기에서 막힌 스레드도 RUNNABLE이에요. 그래서 CPU 문제는 `top -H`의 실제 수치와 같이 봐요.
- **덤프 한 장으로 결론 내기 → 위험해요.** 순간 사진이라 우연히 그 자리에 있었을 수 있어요. 여러 장에서 계속 같은 자리에 있어야 범인이에요.
- 덤프에는 Reference Handler, Finalizer, Signal Dispatcher 같은 JVM 내부 스레드도 섞여 있어요. 요청을 처리하는 스레드(Tomcat이면 `http-nio-` 로 시작하는 이름)부터 봐요.

### 심화: 증거가 부족할 때

- 문제 경로에 traceId와 핵심 입력(마스킹한 값)을 담은 로그를 **추가해 배포**해요. 다음 발생 때 증거가 남아요.
- 특정 패키지만 잠깐 DEBUG로 올려요. Spring Boot Actuator의 `loggers` 엔드포인트에 `POST /actuator/loggers/com.example` + `{"configuredLevel":"debug"}`를 보내면 재시작 없이 레벨이 바뀌어요(엔드포인트는 기본으로 HTTP에 노출되지 않으니 `management.endpoints.web.exposure.include`로 열고, 외부엔 막아 둬요). 조사가 끝나면 `{}`를 보내 꼭 되돌려요. DEBUG를 계속 켜 두면 로그 비용이 늘고 민감정보가 찍힐 위험도 커져요.

### 심화: 로그 주입

사용자 입력에 줄바꿈 문자(CR/LF)를 넣어 가짜 로그 줄을 만드는 공격이 있어요. OWASP는 JSON 같은 구조화 형식으로 남기고 값을 이스케이프하라고 해요. `log.info("user={}", name)` 같은 파라미터 방식만으로는 줄바꿈 주입을 못 막는다고 짚어요. 구조화 로그가 검색뿐 아니라 보안에도 이로운 이유예요.

## 면접 질문

<details>
<summary>Q. 로그 레벨은 어떻게 나눠 쓰나요?</summary>

**답변(30초)** ERROR는 사람이 조치해야 하는 실패, WARN은 스스로 회복했지만 지켜볼 일, INFO는 주문 생성 같은 업무 이벤트, DEBUG는 조사용 상세값으로 운영에선 꺼 둬요. 레벨 이름은 정해져 있지만 사용 기준은 팀 규칙이라 미리 합의해 둬요. 특히 같은 예외를 여러 계층에서 중복으로 ERROR 찍지 않고, 400 같은 예상된 실패는 ERROR로 올리지 않아요.

**꼬리질문**
- Q. 왜 중복 로깅이 문제인가요? → 알림이 부풀고, 한 사건이 여러 건처럼 보여 검색이 어려워요. 처리하는 한 곳에서만 찍어요.
- Q. 운영에서 DEBUG를 켜 둬도 되나요? → 조사할 때 특정 패키지만 잠깐 켜고 되돌려요. 계속 켜면 비용과 민감정보 노출 위험이 커요.
</details>

<details>
<summary>Q. 구조화 로그가 뭐고 왜 쓰나요?</summary>

**답변(30초)** 로그 한 줄을 문장이 아니라 필드가 있는 JSON으로 남기는 방식이에요. 필드로 바로 거르고 묶어 셀 수 있어서 "실패 요청을 인스턴스별로 세기" 같은 분석이 쉬워지고, 줄바꿈을 이용한 로그 주입도 막기 좋아요. Spring Boot 3.4부터 `logging.structured.format.console=ecs`처럼 설정 한 줄로 켤 수 있고, MDC 값도 필드로 자동으로 들어가요.

**꼬리질문**
- Q. 3.4 이전엔 못 했나요? → logstash-logback-encoder 같은 외부 라이브러리로 했어요. 3.4부터 내장된 거예요.
- Q. 지표 레이블에 userId를 넣는 것과 뭐가 다른가요? → 지표는 레이블 조합마다 시계열이 생겨 값 종류가 많으면 비싸지만, 로그 필드는 값 종류가 많아도 괜찮아요.
</details>

<details>
<summary>Q. 서버 여러 대에 흩어진 로그에서 요청 하나를 어떻게 찾나요?</summary>

**답변(30초)** 요청마다 붙는 traceId로 찾아요. Micrometer Tracing을 쓰면 traceId·spanId가 MDC에 들어가고 Spring Boot가 로그 줄마다 상관 ID로 찍어 줘요. 서비스 사이엔 헤더로 같은 번호가 넘어가니, 로그 수집기에서 traceId 하나로 검색하면 모든 서비스의 기록이 시간순으로 모여요. 사용자 신고엔 traceId가 없으니 주문번호 같은 업무 키로 한 줄을 먼저 찾고 거기서 traceId를 얻어요.

**꼬리질문**
- Q. `@Async`를 쓰는 구간에서 traceId가 비어 있어요. 왜죠? → MDC가 스레드에 붙어 있어서 새 스레드로 안 넘어가요. context-propagation이나 `TaskDecorator`로 복사해요.
- Q. 번호를 헤더로 넘기는 표준은요? → W3C `traceparent`예요. 자세한 건 분산 추적 페이지 내용이에요.
</details>

<details>
<summary>Q. 서버가 응답이 없을 때 스레드 덤프로 무엇을 보나요?</summary>

**답변(30초)** `jcmd <pid> Thread.print`로 덤프를 떠서 요청 처리 스레드들의 상태를 봐요. 맨 아래 `Found one Java-level deadlock`이 있으면 교착상태라 `locked`/`waiting to lock` 짝으로 원을 확인해요. 없으면 전부 같은 락에 BLOCKED인지, 커넥션 풀 대기로 WAITING인지, 외부 호출 소켓 읽기에서 RUNNABLE인지로 갈래를 나눠요. 한 장으로 단정하지 않고 몇 장 떠서 비교해요.

**꼬리질문**
- Q. BLOCKED와 WAITING 차이는요? → BLOCKED는 `synchronized` 모니터 대기만이고, `ReentrantLock`·커넥션 풀 대기는 park라서 WAITING/TIMED_WAITING이에요.
- Q. 교착상태면 CPU는 어떤가요? → 거의 0이에요. 서로 기다리기만 해요. 실험에서도 두 스레드 CPU가 0.2ms 미만이었어요.
- Q. JVM 교착상태는 DB처럼 자동으로 풀리나요? → 아니에요. JVM은 탐지만 하고, 재시작 전까지 안 풀려요.
</details>

<details>
<summary>Q. CPU가 100%일 때 원인 스레드를 어떻게 찾나요?</summary>

**답변(30초)** Linux 기준으로 `top -H -p <pid>`로 스레드별 CPU를 보고, 제일 높은 스레드 ID를 `printf '%x'`로 16진수로 바꿔요. 스레드 덤프에서 같은 값의 `nid`를 찾으면 그 스레드의 스택이 나와요. 덤프를 몇 초 간격으로 여러 번 떠서 매번 RUNNABLE로 같은 메서드에 있으면 그 코드가 원인이에요. GC 스레드가 상위면 메모리 쪽을 봐요.

**꼬리질문**
- Q. 덤프를 왜 여러 번 뜨나요? → 순간 사진이라 우연일 수 있어요. 계속 같은 자리에 있어야 범인이에요.
- Q. jstack과 jcmd 중 뭘 쓰나요? → 둘 다 되지만 Oracle은 jcmd `Thread.print`를 권해요.
</details>

## 서술형 연습

아래 상황은 모두 실무 상황형 연습용으로 지어낸 것이에요. 실제 기출 문제가 아니에요.

<details>
<summary>상황 1: 특정 사용자 몇 명만 주문할 때 가끔 500 에러가 나요. 다른 사용자는 정상이고, 로컬에선 재현이 안 돼요. 고객센터가 주문번호 몇 개를 전달했어요.</summary>

**상황 파악**
전체가 아니라 일부 사용자만, 가끔이에요. 서버 전체 문제보다 **특정 입력·인스턴스·의존 대상**에 걸린 문제일 가능성이 커요. 재현이 안 되니 운영 기록에서 증거를 찾아야 해요.

**원인 후보**
1. 그 사용자들의 데이터에만 있는 값(빈 필드, 긴 문자열, 특정 결제수단)을 처리 못 함
2. 여러 인스턴스 중 한 대만 설정·버전이 다름
3. 특정 외부 의존 대상(특정 카드사·DB 복제본)의 오류

**확인 순서**
전달받은 주문번호로 로그를 검색해 실패 줄을 찾고 traceId를 얻어요 → traceId로 전체 검색해 주문·결제·외부 호출 로그를 시간순으로 봐요 → 트레이스에서 실패한 구간과 예외 스택을 확인해요 → 한 건으로 끝내지 않고, 같은 에러의 다른 실패 건을 모아 인스턴스·앱 버전·결제수단별로 묶어 세요. 한 축에 몰리면 그 축의 차이를 봐요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. traceId로 찾은 원인 코드 수정 | 근본 해결 | 원인이 확인돼야 가능 |
| B. 증거가 부족하면 해당 경로에 traceId+핵심 입력(마스킹) 로그를 추가 배포 | 다음 발생 때 바로 원인 확인 | 다시 터질 때까지 기다려야 함 |
| C. 특정 인스턴스에 몰리면 그 인스턴스를 빼고 재배포 | 빠른 완화 | 원인을 모르면 재발 |

**내가 고를 방법**
먼저 traceId로 한 건을 끝까지 따라가 실패 구간을 확정하고, 실패 건들을 축별로 묶어 공통점을 확인해요. 원인이 보이면 A로 고치고 그 입력을 테스트 케이스로 남겨요. 증거가 부족하면 B로 로그를 보강해요. 인스턴스 쏠림이면 C로 먼저 완화해요. 재발 방지로 이 경로의 에러율 알림을 걸어요.

**채점 포인트**: 일부·가끔 → 공통점 찾기, 업무 키 → traceId → 서비스 간 흐름, 트레이스로 실패 구간, 축별 묶어 세기(인스턴스·버전·입력), 로그 보강 시 마스킹, 재현 테스트.

**흔한 감점 답안**: "로컬에서 재현될 때까지 시도한다"로 끝냄, 실패 한 건만 보고 결론, 서버 증설(일부 사용자 문제와 무관).
</details>

<details>
<summary>상황 2: 주문 서버가 갑자기 요청에 응답을 안 해요. 헬스체크도 타임아웃이에요. 그런데 CPU 사용률은 2%로 거의 놀고 있어요.</summary>

**상황 파악**
일은 안 하는데 CPU는 한가하니, 스레드들이 **무언가를 기다리고 있는** 모양이에요. 계산이 많아서 느린 게 아니에요.

**원인 후보**
1. 교착상태: 두 스레드가 서로의 락을 기다림
2. 공용 자원 대기: 커넥션 풀 고갈, 한 락을 모든 요청이 기다림
3. 타임아웃 없는 외부 호출: 응답 안 오는 서버를 요청 스레드들이 계속 기다림

**확인 순서**
트래픽에서 빼거나 재시작하기 **전에** `jcmd <pid> Thread.print`로 덤프를 몇 초 간격으로 2~3장 떠요(재시작하면 증거가 사라져요). 맨 아래 `Found one Java-level deadlock`이 있으면 1번이에요. 없으면 요청 스레드(`http-nio-`)를 봐요. 전부 같은 객체에 BLOCKED면 한 락 경합, `HikariPool` 근처에서 TIMED_WAITING이면 커넥션 풀 대기, 소켓 읽기에서 RUNNABLE이면 외부 호출 대기예요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 덤프 확보 후 재시작 | 즉시 복구 | 원인이 남아 있으면 재발 |
| B. 교착상태면 락 획득 순서 통일 또는 `tryLock(시간)` | 근본 해결 | 락 쓰는 코드를 전부 점검해야 함 |
| C. 외부 호출·풀 대기면 타임아웃 설정, 트랜잭션 안 외부 호출 제거 | 한 의존 대상 장애가 전체로 번지지 않음 | 타임아웃 값 조정 필요, 실패 처리 코드 추가 |

**내가 고를 방법**
덤프부터 확보하고 A로 복구해요. JVM 교착상태는 스스로 안 풀리니 재시작이 유일한 즉시 조치예요. 덤프로 갈래를 확인한 뒤 B나 C로 고쳐요. 재발 방지로 요청 스레드 수·풀 대기 수 알림을 걸고, 멈춤 감지 시 덤프를 자동으로 남기는 절차를 둬요.

**채점 포인트**: CPU 낮음 → 대기, 재시작 전 덤프 확보, 덤프 여러 장, `Found one Java-level deadlock`, locked/waiting to lock 원형, BLOCKED vs WAITING(풀·ReentrantLock은 WAITING), 소켓 읽기는 RUNNABLE, JVM 교착상태는 자동 해제 안 됨, 락 순서·tryLock·타임아웃.

**흔한 감점 답안**: 덤프 없이 바로 재시작, "CPU가 낮으니 서버는 문제없다", "BLOCKED가 없으니 락 문제가 아니다", 서버 증설(대기 원인이 그대로라 새 서버도 똑같이 멈춤).
</details>

<details>
<summary>상황 3: 배포 후 파드 하나만 CPU 100%가 30분째예요. 그 파드로 간 요청만 느려요. 나머지 파드는 정상이에요.</summary>

**상황 파악**
한 파드만, 배포 직후, CPU 꽉 참이에요. **특정 입력이 그 파드에 들어가 무한 루프나 무거운 연산에 빠졌거나**, GC가 계속 돌고 있을 가능성이 커요.

**원인 후보**
1. 특정 요청 입력이 무한 루프·무거운 정규식을 일으킴
2. 메모리 부족으로 GC가 쉬지 않고 돎
3. 그 파드만 설정이 다름(가능성 낮지만 확인)

**확인 순서**
먼저 덤프를 뜰 준비를 하고 그 파드를 트래픽에서 빼요(빼고 나서도 루프는 계속 돌 수 있어 증거가 남아요). `top -H -p <pid>`로 CPU를 먹는 스레드 ID를 보고, `printf '%x'`로 16진수로 바꿔 덤프의 `nid`와 맞춰요. 덤프를 몇 초 간격으로 2~3장 떠서 그 스레드가 매번 RUNNABLE로 같은 메서드에 있는지 봐요. 상위 스레드가 `GC Thread`류면 GC 로그와 힙을 봐요. 그 스레드가 처리하던 요청의 traceId·입력을 로그에서 찾아요.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 파드를 빼고 재시작 | 즉시 완화 | 같은 입력이 오면 다른 파드도 같은 상태가 됨 |
| B. 배포 롤백 | 배포가 원인이면 확실 | 다른 변경도 같이 되돌아감 |
| C. 원인 코드 수정(루프 종료 조건, 정규식 단순화, 입력 길이 제한) | 근본 해결 | 원인 확인에 시간 필요 |

**내가 고를 방법**
덤프를 확보한 뒤 A로 완화해요. 배포 직후라 같은 입력이 퍼지면 전체로 번질 수 있으니, 같은 현상이 다른 파드에 보이면 바로 B로 롤백해요. 덤프의 코드 줄로 원인을 확정해 C로 고치고, 그 입력을 테스트로 남겨요. 재발 방지로 파드별 CPU 알림을 걸어요.

**채점 포인트**: 한 파드 → 특정 입력·상태 의심, 트래픽에서 빼기, `top -H` → 16진수 → `nid`, 덤프 여러 장에서 계속 RUNNABLE, GC 스레드면 메모리 쪽, traceId로 그 요청 찾기, 배포 직후면 롤백 판단, Linux 기준이라는 전제.

**흔한 감점 답안**: 파드를 그냥 재시작하고 끝(증거 없음), 덤프 한 장으로 단정, CPU 100%를 교착상태라고 함(교착상태는 CPU가 낮아요), 오토스케일로 파드만 늘림.
</details>

<details>
<summary>상황 4: 장애가 났는데 로그는 하루 수천만 줄이나 있어요. 그런데 평문이고, 요청을 묶을 번호가 없고, 정상 흐름도 ERROR로 찍혀 있어서 원인을 못 찾았어요. 앞으로 어떻게 바꾸겠어요?</summary>

**상황 파악**
로그 **양**이 아니라 **형식**이 문제예요. 평문이라 필드로 거르고 셀 수 없고, 요청 번호가 없어 한 요청을 못 따라가고, 레벨이 엉망이라 진짜 에러가 묻혀요.

**원인 후보**
1. 평문 로그: 집계·필터가 정규식 의존
2. 상관 ID 없음: 서버·서비스를 넘어 요청을 못 묶음
3. 레벨 기준 없음: 예상된 실패·중복 로깅이 ERROR를 덮음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 구조화 로그 도입(Spring Boot 3.4+ `logging.structured.format.console`) | 필드로 바로 집계·필터, 로그 주입 방어 | 기존 대시보드·검색 쿼리 수정, 로그 크기 다소 증가 |
| B. Micrometer Tracing으로 traceId를 MDC에 넣고 모든 로그에 찍기 | 요청 하나를 검색 한 번으로 추적 | 비동기 구간은 컨텍스트 전파 따로 처리, 외부 호출은 자동 구성 클라이언트 사용 |
| C. 레벨 규칙 합의(ERROR=조치 필요, 한 곳에서만, 400은 ERROR 아님) | 알림이 믿을 만해짐 | 팀 합의와 코드 정리 비용 |

**내가 고를 방법**
셋 다 필요해요. 효과가 가장 큰 B(traceId)를 먼저 넣고, 이어서 A로 형식을 바꾸고, C는 리뷰 규칙으로 정착시켜요. 비동기 구간에서 traceId가 비는지 꼭 확인해요. 바꾸면서 민감정보 마스킹 규칙도 같이 넣어요. 재발 방지로 ERROR 비율 알림을 걸고, 장애 회고 때 "이번에 로그로 바로 찾았나"를 점검 항목으로 둬요.

**채점 포인트**: 양보다 형식, 구조화 로그(JSON·필드 집계), traceId MDC·상관 ID, 비동기 컨텍스트 전파, 레벨 기준과 중복 로깅 금지, 마스킹 같이 도입, 지표→로그→트레이스 연결.

**흔한 감점 답안**: "로그를 더 많이 남긴다"(이미 많음), "DEBUG로 올린다"(양만 늘고 위험), 도구(로그 수집기)만 바꾸고 형식은 그대로.
</details>

<details>
<summary>상황 5: 로그 검색 중 결제 요청 로그에 카드번호와 주민등록번호가 평문으로 찍혀 있는 걸 발견했어요. 몇 달 전 배포부터 그랬던 것 같아요.</summary>

**상황 파악**
보안 사고예요. 코드만 고친다고 끝나지 않아요. **이미 쌓인 로그와 그 사본**(로그 수집기, 백업, 다른 팀이 받아 간 것)이 남아 있고, 그동안 누가 접근했는지도 확인해야 해요.

**원인 후보**
1. 요청 객체를 통째로 로깅(`log.info("req={}", request)`)
2. DTO의 `toString()`이 모든 필드를 출력
3. 예외 메시지나 외부 API 응답 본문에 민감값이 섞여 찍힘

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 즉시: 해당 로그 줄 제거·마스킹 핫픽스 배포 | 새로 쌓이는 걸 바로 막음 | 이미 쌓인 건 그대로 |
| B. 이미 쌓인 로그·수집기·백업 사본 찾아 삭제 또는 마스킹, 접근 권한 점검 | 노출 범위 축소 | 사본 위치 파악이 어렵고, 장애 조사용 로그도 같이 잃을 수 있음 |
| C. 재발 방지: 로그 포맷터에서 패턴 마스킹, DTO `toString()`에서 민감 필드 제외, 리뷰·정적 검사 규칙, 보존 기간 단축 | 같은 실수가 다시 나와도 걸러짐 | 포맷터 마스킹은 정규식 비용, 패턴 누락 가능 |

**내가 고를 방법**
A를 바로 하면서 그 로그에 접근할 수 있는 사람을 먼저 좁혀요. 보안·법무 담당에 바로 공유해 보고 절차를 따르고, 노출 범위 조사에 필요한 기록을 어떻게 보존할지 그쪽과 정한 뒤 B로 사본을 정리하고 접근 기록을 확인해요. 근본적으로는 찍는 순간 가리는 C가 핵심이에요. 수집 후 지우는 방식은 이미 복제된 사본이 남아서 불완전해요. 꼭 필요한 추적은 원본 대신 키를 둔 해시(HMAC, 번호는 경우의 수가 적어 그냥 해시는 되돌려 찾기 쉬워요)나 끝 4자리만 남겨요. 로그 보존 기간을 정해 오래된 로그가 자동으로 지워지게 해요.

**채점 포인트**: 즉시 차단 배포, 이미 쌓인 사본(수집기·백업) 정리, 접근 권한·기록 점검, 보안 담당 공유, 찍는 순간 마스킹(포맷터·toString), 해시·부분 마스킹, 보존 기간, 리뷰 규칙. OWASP가 꼽는 제외 대상(토큰·비밀번호·카드·계좌·정부 식별자).

**흔한 감점 답안**: 코드만 고치고 쌓인 로그는 방치, 로그 수집기에서만 지움(백업·원본 남음), 숨기고 공유 안 함, "로그를 아예 안 남긴다"(장애 조사가 불가능해짐).
</details>
