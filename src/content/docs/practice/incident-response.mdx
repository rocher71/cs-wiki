:::tip[한 줄 요약]
장애 대응의 첫 목표는 원인 규명이 아니라 **피해를 멈추는 것(완화)**이에요. 알리고 역할을 나눈 뒤, 최근 배포와 겹치면 **되돌리고(롤백)** 기능 문제면 **꺼요**. 지표로 복구를 확인한 뒤에 원인을 찾고, **비난 없는 포스트모템**으로 같은 일이 구조적으로 다시 안 생기게 해요.
:::

:::note[처음이라면 여기까지]
① 장애가 나면 "왜 그런지"보다 "사용자 피해를 어떻게 멈추지"가 먼저예요. 원인을 다 몰라도 "어디가 문제인지"만 알면 멈출 수 있어요.

② 가장 빠른 멈춤 수단은 방금 한 변경을 되돌리기(롤백)나, 문제 기능만 끄기(피처 플래그)예요.

③ 혼자 조용히 고치지 말고 먼저 알려요. 누가 지휘하고 누가 시스템을 만지는지 정해야 사고가 안 커져요.

④ 끝나면 보고서(포스트모템)를 써요. "누가 실수했다"가 아니라 "그 실수가 가능했던 구조"를 고치는 게 목적이에요. 서술형은 1·2번부터 풀어 보세요.
:::

## 쉽게 이해하기

건물에 불이 났다고 해 봐요.

소방관은 도착하자마자 "왜 불이 났지?"를 조사하지 않아요. 먼저 사람을 대피시키고 불을 꺼요. 원인 조사는 불이 꺼진 뒤에 해요.

현장에는 지휘관이 한 명 있어요. 지휘관은 직접 호스를 들지 않고, 누가 어디를 맡을지 정하고 상황을 바깥에 알려요. 각자 판단으로 아무 문이나 열면 불길이 더 번질 수 있으니까요.

불이 꺼지면 보고서를 써요. "경비원이 졸았다"로 끝내면 다음 경비원도 졸 수 있어요. 그래서 "화재 경보기가 왜 안 울렸나, 방화문은 왜 열려 있었나"처럼 **구조**를 고쳐요.

서비스 장애도 똑같아요. 완화(불 끄기) → 원인(조사) → 포스트모템(구조 개선) 순서예요.

단, 실제로는 불 끄는 도구(롤백, 기능 끄기)가 늘 통하지는 않아요. DB 구조를 바꾼 배포는 되돌리기 어려워서, 배포 전에 "되돌릴 수 있게" 준비해 둬야 해요. 아래 표에서 다뤄요.

## 이 유형을 푸는 순서

서술형에서 장애 상황이 나오면 이 순서로 답을 짜요. 각 단계에서 스스로 던질 질문을 같이 적었어요.

<IncidentTimeline />

1. **탐지**: 알림(에러율, 응답 지연)이나 고객 문의로 알아채요. 사용자가 실제로 겪는 **증상**인지 먼저 봐요.
2. **공유·역할**: 사고로 선언하고, 지휘자를 정하고, 채널을 열고, 첫 공지를 해요.
3. **영향 평가**: 어떤 기능이, 몇 % 사용자에게, 언제부터 문제인지. 그리고 **직전에 바뀐 것**(배포, 설정, 플래그, 트래픽)을 확인해요.
4. **완화**: 원인을 몰라도 쓸 수 있는 수단으로 피해부터 멈춰요. 장애 시작이 배포 시점과 겹치면 먼저 그 배포를 되돌려요.
5. **복구 확인**: 지표가 평소 수준으로 돌아왔는지 숫자로 확인하고 공지를 업데이트해요.
6. **원인 분석**: 완화하면서 남겨 둔 로그·지표·덤프로 근본 원인을 찾아요.
7. **포스트모템**: 타임라인, 영향, 원인, 재발 방지 액션 아이템을 비난 없이 적고 리뷰받아요.

Google SRE 책도 우선순위를 피해 멈추기 → 서비스 복구 → 원인 분석용 증거 보존 순으로 들어요. SRE Workbook은 원인이 일찍 밝혀진 경우가 아니면 **영향을 먼저 멈추고 원인은 나중에** 찾으라고 하고, 장애가 배포 시점과 겹치면 최근 릴리스를 롤백하라고 제안해요.

<Aside type="caution" title="답안에서 자주 빠뜨리는 것">
3번 "직전에 뭐가 바뀌었나"와 5번 "정말 멈췄나 숫자로 확인"이에요. 롤백만 하고 확인 없이 끝내는 답은 감점돼요.
</Aside>

## 제대로 알기

### 탐지: 무엇을 보고 알아채나

지표의 자세한 개념은 [관측성](../../infra/observability/)에 있어요. 여기선 장애 대응에 필요한 만큼만 정리해요.

| 방법 | 무엇을 보나 | 관점 | 장애 때 쓰임 | 출처 |
|---|---|---|---|---|
| 4 골든 시그널 | Latency(지연), Traffic(요청량), Errors(에러), Saturation(포화도: 가장 빠듯한 자원이 얼마나 찼나) | 사용자가 보는 서비스 | 알림(호출) 기준 | Google SRE 책 6장 |
| RED | 서비스마다 Rate(초당 요청), Errors(실패 요청 수), Duration(처리 시간) | 요청·사용자 경험 | "어느 서비스가 아픈가" | Tom Wilkie 발표, Grafana 블로그(2018) |
| USE | 자원마다 Utilization(바쁜 시간 비율), Saturation(밀린 일), Errors(에러) | 기계·자원(CPU, 디스크, 스레드 풀, 커넥션 풀 등) | "어느 자원이 병목인가" 체크리스트 | Brendan Gregg |

장애 대응에서 기억할 점 몇 가지예요.

- **증상과 원인을 구분해요.** "HTTP 500이 늘었다"는 증상, "DB가 연결을 거부한다"는 원인이에요. 알림은 증상에 걸어요. 사용자가 실제로 겪는 것이니까요.
- **평균만 보면 안 돼요.** 평균 응답이 100ms여도 1%는 5초일 수 있어요. p99(느린 쪽 1% 경계값)를 봐요.
- **에러 응답의 지연은 따로 봐요.** 빨리 실패하는 요청이 섞이면 평균 지연이 오히려 좋아 보일 수 있어요.
- RED에는 RFC 같은 공식 명세가 없어요. 면접에서 "표준"이라고 말하지 않아요.

### 공유와 역할: 혼자 고치지 않기

Google SRE 책 14장은 관리 안 된 사고가 망가지는 패턴 세 가지를 들어요.

1. 기술 문제에만 몰두해서 완화와 큰 그림을 놓침
2. 소통 부족: 누가 뭘 하는지 모르고, 윗선은 계속 상황을 물어봄
3. **프리랜싱**: 지휘자에게 알리지 않고 혼자 시스템을 바꿔 상황을 악화시킴

그래서 역할을 나눠요.

| 역할 | 하는 일 |
|---|---|
| Incident Commander(IC, 지휘자) | 전체 상황 파악, 사람 모으고 일 나누기, 장애물 치우기. 아무에게도 안 맡긴 역할은 IC가 맡음 |
| Operations(운영) | 실제로 시스템을 바꾸는 사람. 사고 중엔 이 역할만 시스템을 변경 |
| Communication(소통) | 바깥 창구, 정해진 주기로 상황 공지, 사고 문서 관리 |
| Planning(계획) | 버그 등록, 교대 준비, 나중에 되돌려야 할 임시 변경 기록 |

작은 팀이면 한 사람이 여러 역할을 겸해도 돼요. 중요한 건 "지금 누가 지휘하나"가 모두에게 분명한 거예요. 그 밖의 원칙은 정해진 지휘소(공유 채널), 실시간으로 함께 고치는 사고 상태 문서, 명시적 인수인계(받는 쪽이 "받았다"고 할 때까지 기다리고 모두에게 알림)예요.

**언제 사고로 선언하나**: 다른 팀이 함께 고쳐야 할 때, 고객에게 보이는 장애일 때, 집중해서 1시간 봐도 안 풀릴 때. 하나라도 해당하면 선언해요. SRE 책은 늦게보다 **일찍** 선언하는 쪽을 권해요.

### 완화 수단: 언제 쓰고 언제 못 쓰나

SRE Workbook은 롤백·트래픽 빼기 같은 **범용 완화**(generic mitigation, 원인과 상관없이 쓸 수 있는 수단)가 투박하고 부작용이 있을 수 있지만 빠르다고 해요. 원인을 다 이해할 필요 없이 "어디가 문제인지"만 알면 돼요.

| 수단 | 언제 쓰나 | 언제 못 쓰나 / 주의 | 더 보기 |
|---|---|---|---|
| 롤백(이전 버전으로 되돌리기) | 장애 시작이 배포 직후와 겹칠 때 | 코드만 돌아가요. DB 스키마·데이터, 이미 나간 결제·메시지, 캐시에 쓴 새 형식 데이터는 그대로예요. 원인이 배포가 아니면 효과 없음 | [무중단 배포](../../architecture/zero-downtime-deploy/) |
| 피처 플래그 끄기(킬 스위치) | 새 기능 하나가 문제일 때 | 플래그로 감싸 둔 기능만 가능. 재배포가 없어 롤백보다 빠를 수 있음 | [피처 플래그](../../architecture/feature-flag/) |
| 트래픽 차단·우회(드레인) | 특정 서버·지역·외부 연동만 문제일 때 | 남은 쪽이 늘어난 트래픽을 감당 못 하면 같이 무너짐 | [회복성](../../architecture/resilience/) |
| 스케일아웃(서버 늘리기) | 순수한 과부하일 때 | 병목이 DB·외부 API면 서버를 늘려도 그쪽 부담만 커짐. 버그로 인한 에러엔 효과 없음 | [트래픽 급증 대응](../traffic-spike/) |
| 캐시·응답 단순화 | 읽기 부하가 몰릴 때 | 오래된 데이터를 보여줘도 되는 화면만. 결제·잔액처럼 정확해야 하는 곳은 불가 | |

쿠버네티스에서는 `kubectl rollout undo`라는 명령으로 Deployment를 이전 리비전으로 되돌릴 수 있어요. 세부 옵션은 [쿠버네티스 공식 문서](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-back-a-deployment)를 확인하세요.

### 롤백이 안 되는 경우: DB 스키마

배포에 "컬럼 이름 바꾸기"나 "컬럼 삭제" 같은 스키마 변경이 들어 있으면, 앱만 옛 버전으로 돌려도 옛 앱이 새 테이블 구조에서 에러를 낼 수 있어요. 스키마는 되돌리기가 훨씬 어렵고, 지운 데이터는 안 돌아와요.

그래서 스키마 변경은 **expand → migrate → contract**로 나눠요. 먼저 새 컬럼을 **추가만** 하고(expand), 데이터를 옮기고(migrate), 옛 컬럼은 한참 뒤에 지워요(contract). 각 단계에서 옛 버전 앱이 여전히 돌아가야 앱 롤백이 가능해요. 자세한 건 [무중단 DB 마이그레이션](../../architecture/db-migration-zero-downtime/)에 있어요.

롤백이 안 되면 남는 선택지는 **롤포워드**(고친 버전을 빨리 새로 배포, 핫픽스라고도 해요)나 기능 끄기예요.

### 포스트모템: 무엇을 쓰나

**포스트모템**(postmortem)은 사고의 영향, 완화·해결 조치, 근본 원인, 재발 방지 조치를 적은 기록이에요.

언제 쓰나(기준은 사고 **전에** 정해 둬요):
- 기준 이상 사용자에게 보인 장애나 성능 저하
- 데이터 손실(양과 상관없이)
- 온콜(당번)이 롤백·트래픽 우회 같은 개입을 했을 때
- 해결 시간이 기준을 넘었을 때
- 모니터링이 못 잡고 사람이 직접 발견했을 때

| 구성 요소 | 내용 |
|---|---|
| 요약·영향 | 어떤 기능이, 몇 명에게, 얼마 동안 |
| 타임라인 | 탐지·선언·완화·복구 시각 (사고 상태 문서를 재사용) |
| 근본 원인·기여 요인 | 기술 원인 + "왜 테스트·리뷰·모니터링이 못 막았나" |
| 잘된 점 / 아쉬운 점 | 대응 과정 자체에 대한 회고 |
| 액션 아이템 | 담당자와 기한이 있는 구체적 개선. 우선순위 표시 |

**비난 없는**(blameless) 포스트모템은 개인이나 팀을 탓하지 않고 기여 원인을 찾아요. 관련자 모두 선의였고, 당시 가진 정보로 맞다고 생각한 행동을 했다고 가정해요. 의료·항공에서 온 문화예요. 탓하기 시작하면 사람들이 문제를 숨기니까요. 사람은 못 고쳐도 시스템과 절차는 고칠 수 있다는 생각이에요. 그렇다고 개선점을 흐리게 쓰는 건 아니에요.

다 쓰면 시니어가 검토해요(핵심 데이터가 있나, 원인을 충분히 깊게 팠나, 액션 아이템이 적절한가). 그 뒤 사용자를 식별할 정보는 빼고 넓게 공유하고 보관해요. SRE 책은 리뷰 안 된 포스트모템은 없는 것과 같다는 취지로 말해요.

### 심화: 공개 장애 보고서 두 개

아래는 회사가 직접 공개한 보고서를 요약한 거예요. 서술형에서 "실제 사례로는"이라고 한 줄 붙이면 좋아요.

**Cloudflare, 2019-07-02** (공식 블로그 보고서, 2019-07-12)

- 무슨 일: WAF(웹 방화벽) 관리형 규칙에 추가한 정규식이 과도한 백트래킹(정규식 엔진이 경우의 수를 계속 되짚는 현상)으로 HTTP 처리 CPU를 다 써 버려서 502 에러가 났어요.
- 타임라인(UTC): 13:42 배포 → 약 13:45 첫 알림 → 14:00 공격이 아니라 WAF가 원인임을 특정 → 14:07 WAF 전역 끄기 → 14:09 정상화(27분) → 14:52 규칙을 고쳐 WAF 다시 켬.
- 왜 퍼졌나: 단계적 배포 없이 전 세계에 동시 배포, CPU 보호 장치가 몇 주 전 리팩터링에서 실수로 빠짐, 테스트가 CPU 사용량을 안 봄.
- 대응을 늦춘 것: 자사 인증 서비스도 같이 장애라 내부 도구 접속이 막혔고, 상태 페이지 업데이트가 늦었음.
- 후속: CPU 보호 복구, 실행 시간이 보장되는 정규식 엔진으로 이전, 규칙 변경도 단계적 배포, 테스트에 성능 측정 추가 등.
- 교훈: **원인 수정(14:52)보다 기능 끄기(14:07)가 먼저**였어요. 그리고 장애 대응 도구가 장애 대상에 의존하면 대응이 느려져요.

**GitLab.com, 2017-01-31** (공식 블로그 포스트모템, 2017-02-10)

- 무슨 일: 복제 지연으로 레플리카(복제 DB)를 다시 만들던 중, 엔지니어가 secondary에서 지우려던 데이터 디렉터리를 **primary**에서 지워 약 300GB가 삭제됐어요.
- 백업이 사실상 없었어요: 덤프 도구 버전이 DB 버전과 안 맞아 백업이 실패하고 있었고, 실패 알림 메일은 메일 설정 문제로 거부돼 아무도 몰랐어요. 디스크 스냅샷도 안 쓰고 있었어요.
- 복구: 약 6시간 전 스테이징용으로 떠 둔 스냅샷으로 복구했고, 약 18시간 서비스가 멈췄어요. 그 사이 DB 변경(프로젝트·댓글 등)이 손실됐어요. Git 저장소 자체는 무관했어요. 복구 과정을 공개 문서와 라이브 방송으로 공유했어요.
- 후속: 스냅샷 주기화, 백업 복원 자동 테스트, 시점 복구, 백업 모니터링, 서버 구분 명확화(프롬프트 등), 복제 작업 절차서, 데이터 내구성 책임자 지정. 앞으로의 사고 보고서에서는 엔지니어 이름을 가리기로 했어요.
- 교훈: **복원해 보지 않은 백업은 백업이 아니에요.** 알림이 실패하는 것도 모니터링해야 해요. 그리고 고칠 대상은 "실수한 사람"이 아니라 "primary와 secondary를 헷갈리게 만든 환경"이에요.

### 심화: 미리 준비할 것

SRE Workbook은 사고 전에 소통 채널 합의, 정기 업데이트·종료 공지 방식, 연락처 목록, 사고 기준 정의, 공지 템플릿, 정기 훈련과 회고를 준비해 두라고 해요. SRE 책은 절차 문서화, 역할 순환, 훈련(장애 복구 테스트·롤플레이)도 들어요. 서술형의 "재발 방지" 칸에 쓰기 좋은 재료예요.

<summary>Q. 운영 중 장애가 나면 무엇부터 하나요?</summary>

**답변(30초)** 원인 찾기보다 피해 멈추기가 먼저예요. 먼저 사고로 알리고 지휘할 사람을 정한 뒤, 어떤 기능이 몇 % 사용자에게 언제부터 문제인지와 직전 변경을 확인해요. 최근 배포와 겹치면 롤백하고, 특정 기능이면 플래그로 꺼요. 에러율·지연이 평소로 돌아온 걸 지표로 확인한 다음, 남겨 둔 로그로 원인을 찾고 포스트모템을 써요.

**꼬리질문**
- Q. 원인을 모르는데 롤백해도 되나요? → 완화엔 "어디가 문제인지"만 알면 돼요. 배포와 시점이 겹치면 되돌리는 게 가장 빠르고, 효과가 없으면 배포가 원인이 아니라는 정보도 얻어요.
- Q. 롤백이 안 되는 경우는? → 되돌릴 수 없는 스키마 변경이 들어간 배포, 이미 외부로 나간 결제·메시지 같은 부수효과가 있을 때예요.
</details>

<details>
<summary>Q. 골든 시그널, RED, USE는 어떻게 다른가요?</summary>

**답변(30초)** 골든 시그널은 지연·트래픽·에러·포화도 네 가지로, 사용자가 보는 서비스 상태를 봐요. RED는 서비스마다 요청 수·실패·처리 시간을 보는 요청 관점이고, USE는 CPU·디스크·커넥션 풀 같은 자원마다 사용률·포화·에러를 보는 자원 관점이에요. 알림은 증상 쪽(골든 시그널·RED)에 걸고, 병목 자원을 찾을 땐 USE를 체크리스트로 써요.

**꼬리질문**
- Q. 평균 응답 시간으로 알림을 걸면? → 꼬리 지연을 가려요. p99 같은 백분위를 봐요.
</details>

<details>
<summary>Q. 비난 없는 포스트모템이 뭔가요? 책임은 안 묻나요?</summary>

**답변(30초)** 개인을 탓하지 않고, 그 실수가 가능했던 시스템과 절차를 찾아 고치는 포스트모템이에요. 모두 선의로 당시 정보 안에서 판단했다고 가정해요. 탓하면 사람들이 문제를 숨겨서 다음 사고를 못 막아요. 책임을 안 묻는 게 아니라, 담당자와 기한이 있는 구체적 개선 항목으로 책임을 남겨요.

**꼬리질문**
- Q. Incident Commander는 왜 직접 안 고치나요? → 고치는 데 빠지면 전체 상황과 소통을 놓쳐요. 시스템 변경은 Operations 역할로 모아야 서로 모르는 변경이 겹치지 않아요.

## 서술형 연습

아래는 연습용 가상 상황이에요. 실제 기출 문제가 아니에요. 쉬운 것부터 어려운 순서예요.

<details>
<summary>상황 1: 금요일 오후 주문 서비스 새 버전을 배포했어요. 10분 뒤 주문 API의 5xx 비율이 평소 1%에서 15%로, p99 응답 시간이 3배로 뛰었어요. 무엇을 어떤 순서로 하나요?</summary>

**상황 파악**
증상(5xx, p99 상승)이 배포 직후에 시작됐어요. 시점이 겹치니 배포가 가장 유력한 후보예요. 주문은 매출과 직결되니 원인 분석보다 피해를 멈추는 게 먼저예요.

**원인 후보**
1. 새 버전 코드 버그(새 쿼리, 바뀐 로직)
2. 새 버전의 설정 변경(타임아웃, 커넥션 풀 크기 등)
3. 우연히 같은 시각에 일어난 다른 변경(외부 API, DB, 트래픽)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 즉시 이전 버전으로 롤백 | 원인 몰라도 가장 빠름. 효과 없으면 "배포가 원인 아님"도 알게 됨 | 새 기능도 같이 빠짐. 스키마 변경이 있으면 위험 |
| B. 새 기능만 플래그로 끄기 | 재배포 없이 빠름, 나머지 변경은 유지 | 플래그로 감싼 기능일 때만 가능, 원인이 그 기능이 아니면 효과 없음 |
| C. 원인 찾아 핫픽스 배포 | 근본 수정 | 찾고 고치고 배포하는 동안 계속 15% 실패 |

**내가 고를 방법**
먼저 팀 채널에 사고를 선언하고 지휘자를 정해요. 배포에 되돌릴 수 없는 스키마 변경이 없는지만 빠르게 확인한 뒤 A로 롤백해요(플래그로 감싼 새 기능이 명확한 원인이면 B가 더 빨라요). 롤백 전에 에러 로그 샘플과 지표 화면은 남겨 둬요. 롤백 후 5xx 비율과 p99가 평소 수준으로 돌아왔는지 확인하고 공지를 업데이트해요. 그다음 남긴 로그로 원인을 찾아 테스트를 추가한 수정 버전을 다시 배포하고, 포스트모템에 "왜 배포 전에 못 잡았나"(테스트, 카나리 배포 여부)를 액션 아이템으로 남겨요.

**채점 포인트**: 완화 먼저, 사고 선언·공유, 배포 시점과의 상관, 롤백 전 스키마 변경 확인, 증거 보존, 지표로 복구 확인, 원인 분석은 나중, 재발 방지(카나리·테스트).

**흔한 감점 답안**: "로그를 보고 원인을 찾아서 고친다"로 시작하는 답. 고치는 동안 사용자 15%가 계속 실패해요. 롤백하고 확인 없이 끝내는 답도 감점이에요.
</details>

<details>
<summary>상황 2: 배포 직후 결제 화면 에러가 늘어서 롤백했어요. 그런데 롤백 후 20분이 지나도 에러율이 그대로예요. 다음에 무엇을 하나요?</summary>

**상황 파악**
롤백으로 안 멈췄다는 건 **원인이 배포가 아닐 가능성**이 크다는 뜻이에요. 시점이 우연히 겹쳤거나, 배포가 남긴 흔적(데이터, 캐시)이 코드를 되돌려도 남아 있는 거예요. 롤백이 실패한 게 아니라 후보 하나를 지운 거예요.

**원인 후보**
1. 외부 의존성 장애: PG(결제대행사)나 외부 API가 느려지거나 에러
2. 배포가 남긴 데이터: 새 버전이 DB나 캐시에 새 형식 데이터를 써서 옛 버전이 못 읽음(롤백은 코드만 되돌림)
3. 인프라·자원: DB 커넥션 풀 고갈, 디스크 꽉 참, 인증서 만료
4. 트래픽 변화: 같은 시각 이벤트·봇 트래픽 급증

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 외부 의존성 지표·상태 페이지 확인 후 서킷 브레이커·대체 경로 | 외부 원인이면 우리 쪽 피해를 줄임 | 결제는 대체가 어려워 "잠시 결제 불가" 안내가 필요할 수 있음 |
| B. 새 형식으로 쓰인 캐시·데이터 정리(캐시 비우기, 데이터 보정) | 배포 흔적이 원인이면 해결 | 캐시를 한꺼번에 비우면 DB에 부하가 몰림, 데이터 보정은 신중해야 함 |
| C. 자원 지표(USE)로 병목 찾아 증설·정리 | 자원 문제면 직접 해결 | 원인 확인 전 증설은 엉뚱한 곳일 수 있음 |

**내가 고를 방법**
먼저 지휘자에게 "롤백 효과 없음, 배포 외 원인 조사로 전환"을 공유해요. 에러 로그를 에러 종류별로 묶어 어디서 실패하는지 봐요. 외부 호출 타임아웃이 대부분이면 A(PG 상태 확인, 서킷 브레이커로 빠르게 실패시키고 사용자 안내), 역직렬화·형식 에러면 B, 커넥션 대기면 C로 가요. 이 경우 포스트모템엔 "롤백 후 확인으로 원인을 빨리 좁혔다"는 잘된 점과, 외부 의존성 대시보드가 없어 늦었다면 그 보강을 액션 아이템으로 남겨요.

**채점 포인트**: 롤백 효과 없음 = 원인 후보 제거, 롤백은 코드만 되돌림(데이터·캐시·외부 상태는 남음), 외부 의존성 확인, 에러 종류별 분류, 상황 공유 갱신, 캐시 일괄 삭제의 부작용.

**흔한 감점 답안**: "롤백이 덜 됐나 보다"며 계속 재배포만 반복하거나, 더 이전 버전으로 계속 되돌리는 답. 증거 없이 같은 수단을 반복해요.
</details>

<details>
<summary>상황 3: 새벽 3시, 당번인 당신에게 알림이 왔어요. 로그인 API 에러율이 급증했고 아직 아무도 깨어 있지 않아요. 처음 15분 동안 무엇을 하나요?</summary>

**상황 파악**
혼자서 탐지·지휘·조치를 다 해야 해요. 가장 위험한 건 혼자 조용히 이것저것 바꾸다가 무엇을 바꿨는지 모르게 되는 거예요. 로그인은 모든 기능의 입구라 영향이 커요.

**원인 후보**
1. 최근 배포·설정 변경(야간 배치나 자동 배포 포함)
2. 인증에 쓰는 외부 서비스나 DB·캐시 장애
3. 인증서·비밀키 만료 같은 시간 기반 문제
4. 비정상 트래픽(크리덴셜 스터핑 같은 공격)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 혼자 원인을 끝까지 파고들기 | 아무도 안 깨움 | 큰 그림을 놓치고, 혼자 판단이 틀리면 악화. 기록도 안 남음 |
| B. 짧게 영향 확인 후 사고 선언·에스컬레이션, 범용 완화부터 | 판단 공유, 기록이 남음, 도움을 빨리 받음 | 동료를 깨우는 비용 |

**내가 고를 방법**
B예요. 0~5분: 증상이 진짜인지(사용자 쪽 에러율, 고객 문의) 확인하고 영향 범위와 시작 시각을 봐요. 5~10분: 기준(고객에게 보이는 장애)에 해당하니 사고를 선언하고, 채널에 첫 공지를 남기고, 정해진 에스컬레이션 대상에게 연락해요. 사고 문서에 시각별로 본 것과 한 일을 적기 시작해요. 10~15분: 시작 시각 직전 변경이 있으면 롤백, 특정 서버·지역만 이상하면 트래픽을 빼는 등 범용 완화를 해요. 실행한 변경은 전부 문서에 적어요. 동료가 오면 지금까지 상황을 넘기고 지휘 역할을 명시적으로 인수인계해요.

**채점 포인트**: 증상 확인, 영향 범위, 일찍 선언·에스컬레이션, 사고 문서에 타임라인 기록, 직전 변경 확인, 범용 완화, 변경 기록, 명시적 인수인계, 혼자 과부하면 도움 요청.

**흔한 감점 답안**: "아침까지 혼자 원인을 찾아본다", "일단 서버를 다 재시작한다"(증거가 사라지고, 왜 고쳐졌는지 모름).
</details>

<details>
<summary>상황 4: 배포에 "users 테이블의 name 컬럼을 full_name으로 이름 변경"하는 마이그레이션이 포함돼 있었어요. 배포 직후 일부 API가 에러를 내요. 앱만 롤백하면 옛 앱이 name 컬럼을 못 찾아요. 어떻게 하나요?</summary>

**상황 파악**
스키마가 이미 바뀌어서 앱 롤백이 곧 또 다른 장애예요. 옛 앱은 `name`을, 새 앱은 `full_name`을 기대해요. "롤백 먼저"가 그대로 통하지 않는 경우예요.

**원인 후보**
1. 새 앱의 일부 코드가 아직 `name`을 참조(이름 변경 누락)
2. 이름 변경 중 테이블 잠금으로 쿼리 대기
3. 다른 서비스·배치가 같은 테이블의 `name`을 직접 읽음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 롤포워드: 남은 참조를 고친 핫픽스 배포 | 스키마를 안 건드림 | 고치고 배포하는 동안 에러 지속, 급하게 만든 수정이 또 버그일 수 있음 |
| B. 스키마를 되돌린 뒤(full_name → name) 앱 롤백 | 원래 상태로 복귀 | 운영 중 두 번째 스키마 변경이라 잠금·실수 위험, 그 사이 쓴 데이터 확인 필요 |
| C. 문제 기능만 플래그로 끄기 | 빠름 | 해당 기능이 플래그로 감싸져 있을 때만 |

**내가 고를 방법**
에러가 나는 API와 원인을 먼저 좁혀요. 참조 누락처럼 고칠 곳이 명확하고 작으면 A, 그 기능이 플래그로 감싸져 있으면 C로 먼저 끄고 A를 해요. 다른 서비스까지 깨졌고 영향이 크면, DB 담당자와 함께 B를 신중히 진행해요. 포스트모템의 핵심 액션 아이템은 "이름 변경 같은 파괴적 스키마 변경은 expand → migrate → contract로 나눈다"예요. 새 컬럼 추가 → 양쪽에 쓰기 → 읽기 전환 → 옛 컬럼은 나중에 삭제하면, 어느 단계에서든 앱 롤백이 가능해요.

**채점 포인트**: 롤백은 코드만 되돌림, 옛 앱과 새 스키마의 호환성, 롤포워드·플래그 대안, 스키마 되돌리기의 위험, 다른 서비스 영향 확인, expand-contract, "배포 전에 롤백 가능성을 설계한다"는 재발 방지.

**흔한 감점 답안**: "바로 롤백한다"(옛 앱도 깨짐), "DB를 백업에서 복원한다"(그 사이 쓴 데이터까지 날아감, 과한 수단).
</details>

<details>
<summary>상황 5: 신입 엔지니어가 운영 DB에서 WHERE 조건이 빠진 UPDATE를 실행해 주문 상태가 대량으로 바뀌었어요. 복구는 끝났고, 포스트모템 초안 회의에서 누군가 "원인: 담당자 부주의"라고 쓰고 마무리하자고 해요. 어떻게 답하나요?</summary>

**상황 파악**
"담당자 부주의"는 원인이 아니라 결과를 다시 적은 거예요. 같은 구조라면 다음 사람도 같은 실수를 할 수 있어요. 게다가 사람을 탓하면 다음부터 실수를 숨기게 돼서 탐지가 더 늦어져요.

**원인 후보(기여 요인)**
1. 운영 DB에 개인 계정으로 직접 쓰기 권한이 있음
2. 운영·개발 접속 환경이 구분이 안 됨(프롬프트·색 구분 없음)
3. 대량 변경 전 확인 절차(리뷰, 영향 행 수 확인, 트랜잭션 안에서 실행)가 없음
4. 복구 절차가 미리 연습되지 않아 복구가 오래 걸림
5. 알림이 이상을 못 잡고 고객 문의로 알았다면 모니터링 공백

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. "담당자 부주의" + 주의 교육 | 빨리 끝남 | 구조가 그대로라 재발, 숨기는 문화 |
| B. 비난 없는 형식으로 기여 요인과 액션 아이템 | 재발 방지, 정보가 잘 모임 | 시간이 더 들고, 권한 축소는 일하기 불편해짐 |

**내가 고를 방법**
B를 제안하고 원인 문장을 이렇게 고쳐요. "운영 DB에 리뷰 없이 직접 쓰기 실행이 가능했고, 영향 행 수 확인 절차가 없었다." 이름은 빼요(GitLab도 2017년 데이터 삭제 사고 포스트모템에서 앞으로는 엔지니어 이름을 가리겠다고 밝혔어요). 액션 아이템은 담당자와 기한을 붙여 적어요. 운영 DB 쓰기 권한 분리, 변경 쿼리 리뷰 절차, 운영 접속 화면 구분, 백업 복원 정기 훈련, 대량 변경 감지 알림. 마지막으로 시니어 리뷰를 받고 팀 전체에 공유해요. 비난이 없다는 건 책임이 없다는 게 아니라, 책임을 "구조를 고치는 일"로 남긴다는 뜻이라고 덧붙여요.

**채점 포인트**: blameless 정의, 개인 → 시스템·절차, 기여 요인 여러 개, 구체적 액션 아이템(담당자·기한), 권한 분리·확인 절차·환경 구분, 복원 훈련, 포스트모템 리뷰·공유, 비난이 문제 은폐를 낳는다는 이유.

**흔한 감점 답안**: "그냥 넘어가자"(개선 없음)나 "신입에게 운영 권한을 주지 말자"만 쓰는 답. 경력자도 같은 실수를 할 수 있는 구조라는 점을 놓쳐요.
</details>
