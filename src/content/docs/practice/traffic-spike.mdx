:::tip[한 줄 요약]
트래픽이 갑자기 몰리면 **① 병목이 어디인지(앱 CPU·스레드 / DB 커넥션 / 외부 API / 캐시) 가르고 → ② 서버를 늘리되 그것만 믿지 않고 → ③ 입장 제한·부가 기능 끄기·캐시로 핵심 기능을 지킨 뒤 → ④ 다음 이벤트는 사전 스케일아웃과 부하 테스트로 대비**해요. 자동 확장(HPA)은 초 단위 급증에는 늦고, DB가 병목이면 서버를 늘릴수록 더 나빠질 수 있어요.
:::

:::note[처음이라면 여기까지]
① 서버를 자동으로 늘리는 기능이 있어도, 늘어난 서버가 일을 시작하기까지 **수십 초~수 분**이 걸려요. 그 사이에 이미 터질 수 있어요.

② 앱 서버를 늘려도 **DB는 하나**인 경우가 많아요. 서버마다 DB 연결을 10개씩 잡으면, 서버를 3배로 늘리는 순간 DB가 받을 수 있는 연결 수를 넘어요.

③ 그래서 급할 땐 "덜 중요한 기능 끄기", "한꺼번에 못 들어오게 줄 세우기"로 **결제·주문 같은 핵심만 살리는 것**이 정답에 가까워요.

④ 서술형은 1·2번부터 연습하세요. "심화:" 소제목은 나중에 읽어도 돼요.
:::

## 쉽게 이해하기

평소 손님 20명이 오던 식당에 갑자기 단체 손님 200명이 들이닥쳤다고 해 봐요.

사장님이 제일 먼저 떠올리는 건 "직원 더 부르기"예요. 이게 **스케일아웃**(scale-out, 서버 대수를 늘리는 것)이에요. 그런데 쉬는 직원에게 전화해서 출근하고, 앞치마 입고, 메뉴 익히기까지 시간이 걸려요. 그동안 손님은 이미 화가 나서 나가요.

더 큰 문제는 **주방이 하나**라는 거예요. 홀 직원을 10명 더 불러도 주문서가 주방 한 곳에 몰리면 요리는 그대로 느려요. 오히려 주방 앞이 북적여서 더 엉망이 돼요. 이 주방이 백엔드의 **DB**예요.

그래서 노련한 사장님은 다른 방법을 같이 써요. 오늘은 손이 많이 가는 메뉴를 빼고 **간단한 메뉴만 받기**(부가 기능 끄기), 입구에서 **번호표 나눠 주기**(대기열), 미리 만들어 둔 반찬 내기(캐시)예요. 그리고 다음 단체 예약이 잡히면 **전날 미리 직원을 불러 두고** 재료를 손질해 둬요(사전 스케일아웃, 캐시 워밍).

단, 실제 서버는 사람처럼 "눈치껏" 손님을 거절하지 않아요. 무엇을 끄고 누구를 기다리게 할지는 **미리 코드와 설정으로 만들어 둬야** 그 순간에 쓸 수 있어요.

## 이 유형을 푸는 순서

서술형에서 "트래픽이 몰려서 장애가 났다"를 받으면 아래 순서를 답안 뼈대로 써요. 답안 쓰는 일반 구조는 [서술형 답안 쓰는 법](../how-to-answer/)에 있어요.

| 단계 | 할 일 | 이 주제에서 구체적으로 |
|---|---|---|
| 1. 증상 확인 | 얼마나 몰렸고 무엇이 깨졌나 | 초당 요청 수(RPS), p99 응답 시간, 에러율(503·타임아웃), 자원 포화 지표 |
| 2. 영향 범위 | 전체인가 일부인가 | 전체 API가 같이 느리면 공용 자원(DB·커넥션 풀·스레드), 특정 API만이면 그 기능의 의존성 |
| 3. 병목 찾기 | 어디가 먼저 찼나 | 앱 CPU·스레드 / DB 커넥션·DB CPU / 외부 API 응답 / 캐시 적중률 |
| 4. 즉시 완화 | 핵심 기능부터 살리기 | 수동 스케일아웃, 캐시 TTL 늘리기, 레이트 리밋·대기열, 부가 기능 끄기, 배치 멈추기 |
| 5. 근본 해결 | 같은 양이 와도 버티게 | 쿼리·인덱스, 캐시 설계, 읽기 레플리카, 무거운 작업 비동기화(큐) |
| 6. 재발 방지 | 다음엔 미리 | 부하 테스트, 사전 스케일 계획, 용량 알람, 끌 기능 목록과 킬 스위치 |

핵심은 3단계예요. **병목이 어디냐에 따라 "서버 늘리기"가 약이 되기도, 독이 되기도** 해요.

### 증상으로 병목 가르기

| 증상 | 의심 | 확인 도구 |
|---|---|---|
| 앱 CPU 100%, 응답 느림 | 앱 서버 용량 부족 | `kubectl top pods`, `kubectl describe hpa`(이벤트) |
| 앱 CPU는 여유, 응답 느림 | DB 커넥션 대기 또는 외부 API가 느림 | 커넥션 풀 지표(active·pending), Actuator/Micrometer |
| DB가 "Too many connections" | 파드 수 × 풀 크기가 DB 최대 연결 수 초과 | `SHOW VARIABLES LIKE 'max_connections'`, `SHOW STATUS LIKE 'Threads_connected'` |
| 파드가 계속 재시작 | liveness 검사가 과부하로 실패 | `kubectl describe pod`(Events), `kubectl get pods`의 RESTARTS |
| HPA가 늘렸는데 새 파드가 Pending | 노드(서버 자리) 부족 | `kubectl describe pod`의 Events(FailedScheduling) |
| 캐시 만료 순간 DB 급증 | 캐시 스탬피드·핫키 | 캐시 적중률, DB 초당 쿼리 수 그래프 |

`Threads_connected`, `FailedScheduling` 같은 이름은 일반적으로 쓰이는 것이고, 환경마다 보는 화면이 다를 수 있어요. 캐시 스탬피드(인기 키가 동시에 만료돼 요청이 한꺼번에 DB로 가는 현상)는 [캐시 문제](../../redis/cache-problems/)에 있어요.

### 즉시 쓸 수 있는 카드

| 카드 | 효과 | 대가(트레이드오프) | 자세히 |
|---|---|---|---|
| 수동 스케일아웃(replica 직접 올리기) | 앱 CPU가 병목이면 가장 직접적 | 준비 시간이 걸림, DB가 병목이면 역효과 | [프로브와 오토스케일링](../../infra/k8s-probes-scaling/) |
| 캐시 TTL 늘리기 | DB로 가는 읽기를 바로 줄임 | 오래된 값이 보임(가격·재고는 주의) | [캐시·CDN 확장](../../system-design/cache-cdn-scale/) |
| 레이트 리밋 | 들어오는 양 자체를 상한으로 묶음 | 일부 사용자는 429 에러를 봄 | [처리율 제한기](../../system-design/rate-limiter/) |
| 부가 기능 끄기(킬 스위치) | 추천·랭킹·리뷰 집계 같은 부하를 통째로 제거 | 기능이 잠시 사라짐, 미리 플래그가 있어야 가능 | [피처 플래그](../../architecture/feature-flag/) |
| 대기열(번호표) | 시스템이 감당할 만큼만 입장시킴 | 사용자가 기다림, 대기열 자체도 만들어 둬야 함 | [대기열 시스템](../../system-design/waiting-queue/) |
| 읽기 레플리카로 분산 | 읽기 부하를 여러 DB로 나눔 | 복제 지연(방금 쓴 값이 안 보임), 쓰기는 분산 안 됨, 당장 새로 만들긴 어려움 | [커넥션 풀과 쿼리](../../db/connection-pool-query/) |
| 배치·비핵심 작업 멈추기 | 같은 DB를 쓰는 다른 부하 제거 | 정산·통계가 늦어짐 | - |

<Aside type="caution">
읽기 레플리카는 "평소에 이미 있어야" 급할 때 쓸 수 있는 카드예요. 장애 중에 새로 만드는 건 즉시 완화가 아니라 근본 해결 쪽이에요. 그리고 MySQL 복제에서 **쓰기는 원본(소스)에서만** 해요. 레플리카로는 쓰기 부하를 못 나눠요.
</Aside>

## 제대로 알기

### HPA가 급증에 늦는 이유

**HPA**(Horizontal Pod Autoscaler, 부하를 보고 파드 수를 자동으로 늘리고 줄이는 쿠버네티스 기능)는 켜 두면 안심이 되지만, 반응까지 시간이 쌓여요. 기본 동작은 [프로브와 오토스케일링](../../infra/k8s-probes-scaling/)에 있고, 여기선 "왜 늦나"만 봐요.

| 지연 구간 | 기본값(공식 문서) | 의미 |
|---|---|---|
| 메트릭 수집 | Metrics Server가 15초마다 수집 | 부하가 올라도 HPA가 보는 숫자는 최대 십수 초 전 값 |
| HPA 판단 | `--horizontal-pod-autoscaler-sync-period` 15s | 15초마다 한 번 "몇 개가 필요한지" 다시 계산 |
| 한 번에 늘리는 폭 | 15초마다 "현재의 100%" 또는 "4개" 중 큰 쪽까지 | 2개였다면 15초 뒤 최대 6개. 한 번에 무한정 안 늘어남 |
| 새 파드 준비 | 정해진 값 없음 | 스케줄링 → 이미지 받기 → JVM·Spring 기동 → readiness 통과해야 트래픽을 받음 |
| 노드가 모자랄 때 | 정해진 값 없음 | 새 파드가 Pending. 노드 증설은 별도 기능(Cluster Autoscaler) 몫이라 더 느림(일반 지식) |

계산식은 `원하는 파드 수 = 올림(현재 파드 수 × 현재 지표 / 목표 지표)`예요. 비율이 1에서 10% 이내면(tolerance 0.1) 움직이지 않아요.

결론은 이거예요. HPA는 **몇 분에 걸쳐 서서히 오르는 부하**에는 잘 맞지만, 티켓 오픈·푸시 발송 직후처럼 **몇 초 만에 10배 뛰는 부하**에는 늦어요. 날짜가 정해진 이벤트라면 **미리 최소 파드 수(minReplicas)를 올려 두는 사전 스케일아웃**이 정석이에요.

### 앱을 늘리면 DB 커넥션이 먼저 터진다

앱 서버(파드)는 각자 **커넥션 풀**(connection pool, DB 연결을 미리 열어 두고 돌려 쓰는 통)을 가져요. 그래서 DB가 받는 연결 수는 이렇게 계산해요.

`총 커넥션 = 파드 수 × 파드당 풀 크기 (+ 배치·관리 도구)`

MySQL 8.4의 `max_connections`(동시에 받을 수 있는 최대 연결 수) 기본값은 **151**이에요. HikariCP의 풀 크기(`maximumPoolSize`) 기본값은 **10**이에요. 이 두 기본값으로 계산해 봐요.

| 파드 수 | 풀 크기 | 총 커넥션 | max_connections 151 대비 |
|---|---|---|---|
| 10 | 10 | 100 | 여유 있음 |
| 15 | 10 | 150 | 거의 꽉 참(관리 도구 하나만 붙어도 넘음) |
| 30 | 10 | 300 | **2배 초과** — 새 파드는 DB 연결 실패 |

<DbConnectionBudgetBars />

연결이 거절되지 않더라도 문제는 남아요. DB가 한 번에 효율적으로 처리할 수 있는 쿼리 수는 **DB 서버의 CPU 코어 수**에 묶여 있어요. HikariCP 위키가 풀 크기 출발점으로 `(코어 수 × 2) + 디스크 수`를 제안하는 이유예요. 연결을 300개 열어 줘도 DB는 그만큼 빨라지지 않고, 오히려 서로 CPU와 락을 다투며 다 같이 느려져요.

그래서 DB가 병목일 때의 답은 "앱 더 늘리기"가 아니라 **DB 앞에서 요청을 줄이는 것**이에요.

- **캐시**: Redis·로컬 캐시·CDN이 읽기를 DB 앞에서 받아 줌
- **읽기 레플리카**: 읽기를 여러 DB로 나눔(쓰기는 원본만)
- **입장 제한**: 레이트 리밋·대기열로 DB까지 가는 동시 요청 수 자체를 묶음

### 심화: 과부하를 버티는 두 가지 전략 (Google SRE)

Google SRE 책의 "Handling Overload"와 "Addressing Cascading Failures" 장이 이 주제의 고전이에요. 핵심 용어 두 개만 가져와요.

| | 로드 셰딩(load shedding) | 우아한 성능 저하(graceful degradation) |
|---|---|---|
| 뜻 | 과부하에 가까워지면 **요청 일부를 버려서** 서버를 살려 두는 것 | 요청은 받되 **하는 일을 줄이는 것** |
| 예 | 일부 요청에 바로 503·429 응답 | 추천 대신 고정 목록, 실시간 계산 대신 캐시된 값 |
| 사용자 체감 | 일부는 실패를 봄 | 다 성공하지만 품질이 낮아짐 |

SRE 책이 강조하는 점은 이래요.

- **빨리 거절하는 게 처리하는 것보다 싸요.** 다만 "과부하면 모든 트래픽을 끊는다"는 흔한 실수예요.
- 요청에 **중요도**를 매겨 낮은 것부터 버려요. Google은 `CRITICAL_PLUS`, `CRITICAL`, `SHEDDABLE_PLUS`, `SHEDDABLE` 4단계를 써요. 실무로 옮기면 결제·주문은 살리고 추천·랭킹·리뷰 집계부터 끄는 거예요.
- 성능 저하 모드는 **미리 만들고 테스트해 둬야** 실제로 쓸 수 있어요.
- 용량은 초당 요청 수보다 **실제 자원(CPU 등)**으로 재는 게 나아요. 요청마다 비용이 달라서예요.

### 심화: 연쇄 장애가 생기는 고리

**연쇄 장애**(cascading failure)는 한 곳의 문제가 되먹임으로 점점 커지는 장애예요. 가장 흔한 원인이 과부하예요.

1. 서버 하나가 과부하로 죽으면 남은 서버로 부하가 몰려 차례로 죽어요.
2. CPU가 모자라면 모든 요청이 느려지고, 느린 요청이 메모리·스레드를 오래 붙잡아요. Java에선 CPU 부족 → GC 증가 → CPU 더 부족의 악순환이 생겨요.
3. **liveness 검사가 DB를 보고 있으면** 과부하 때 검사가 실패해 파드가 재시작돼요. 재시작 중엔 남은 파드가 더 바빠져서 또 실패해요. Spring Boot 문서도 liveness가 외부 시스템에 의존하면 연쇄 장애가 날 수 있다고 경고해요.
4. **재시도가 부하를 곱해요.** 3계층이 각각 3번씩 재시도하면 맨 아래 DB에는 요청 하나가 최대 64번(4 × 4 × 4) 도착할 수 있어요.

끊는 방법도 SRE 책에 정리돼 있어요. 트래픽을 크게 줄였다가 회복되면 천천히 올리기, 성능 저하 모드 켜기, 배치 끄기, 헬스 체크 실패로 인한 재시작 연쇄 멈추기, 재시도는 지수 백오프+지터·횟수 제한·"과부하니 재시도 말 것" 응답으로 묶기예요. 재시도·서킷 브레이커는 [외부 API 장애 대응](../external-api-failure/)과 [회복성 패턴](../../architecture/resilience/)에 더 있어요.

### 심화: 새로 뜬 서버는 처음엔 느리다

새 프로세스는 기동 직후 느려요. JIT 컴파일(자주 쓰는 코드를 기계어로 바꿔 빠르게 하는 것)이 아직 안 됐고, 커넥션 풀과 로컬 캐시가 비어 있어서예요. SRE 책도 캐시가 비면 모든 요청이 비싸진다고 적어요. 그래서 새 서버나 빈 캐시에는 **부하를 천천히 올려 데우는 것**이 좋아요.

HPA도 이걸 고려해요. 파드 시작 후 30초(`initial-readiness-delay`) 안의 readiness 변화는 초기 상태로 취급하고, 아직 Ready가 아닌 파드는 계산에서 사용량 0%로 가정해 늘리는 폭을 보수적으로 줄여요. 시작 후 5분(`cpu-initialization-period`) 동안은 CPU 샘플을 건너뛸 수 있어요.

반대로 스케일 다운은 기본 **5분 안정화**가 있어요. 최근 5분 권고값 중 가장 높은 값 아래로는 안 줄여요. 급증 뒤 바로 줄였다가 다음 파도에 또 늦는 걸 막는 의도된 설계예요.

### 심화: 이벤트 전에 준비할 것

SRE 책은 "깨질 때까지 부하 테스트하고, 부하가 정상으로 돌아왔을 때 어떻게 회복하는지도 테스트하라"고 해요. 많이 쓰는 도구는 이래요.

- **Grafana k6**: 오픈소스 성능 테스트 도구, 시나리오를 JavaScript로 써요.
- **nGrinder**: 네이버가 만든 스트레스 테스트 플랫폼. 스크립트 작성·실행·모니터링·결과 리포트를 한곳에서 해요.
- **Apache JMeter**: 순수 Java 프로그램. 서버에 무거운 부하를 흉내 내 성능을 재요.

부하 테스트 다음엔 캐시를 미리 채워 두는 **캐시 워밍**(인기 상품·메인 페이지 데이터를 이벤트 전에 적재)과 TTL에 무작위 값을 더해 동시 만료를 막는 것까지 챙겨요. 자세한 건 [캐시·CDN 확장](../../system-design/cache-cdn-scale/)에 있어요.

## 면접 질문

<details>
<summary>Q. 트래픽이 갑자기 10배 늘면 무엇부터 하나요?</summary>

**답변(30초)** 먼저 병목이 어디인지 봐요. 앱 CPU인지, DB 커넥션인지, 외부 API인지에 따라 대응이 달라서예요. 앱 CPU가 병목이면 파드를 수동으로 늘리고, DB가 병목이면 캐시 TTL을 늘리거나 레이트 리밋·대기열로 DB까지 가는 요청을 줄여요. 동시에 추천·랭킹 같은 부가 기능을 피처 플래그로 꺼서 결제·주문 같은 핵심 기능에 자원을 몰아줘요. 안정되면 원인을 찾고 부하 테스트로 재발을 막아요.

**꼬리질문**
- Q. 왜 바로 서버부터 늘리지 않나요? → 새 서버가 준비되기까지 시간이 걸리고, DB가 병목이면 서버를 늘릴수록 DB 연결이 늘어 더 나빠질 수 있어서요.
- Q. 무엇을 먼저 끄나요? → 매출·핵심 흐름에 영향이 없는 부가 기능부터요. 결제·주문은 마지막까지 지켜요.
</details>

<details>
<summary>Q. 스케일 업과 스케일 아웃의 차이, 왜 보통 스케일 아웃을 하나요?</summary>

**답변(30초)** 스케일 업은 서버 한 대의 CPU·메모리를 키우는 것이고, 스케일 아웃은 서버 대수를 늘리는 거예요. 스케일 업은 한 대의 성능 한계가 있고, 바꾸는 동안 멈출 수 있어요. 스케일 아웃은 대수를 계속 늘릴 수 있고 한 대가 죽어도 나머지가 버텨요. 다만 서버가 상태(세션 등)를 갖지 않아야 하고, 뒤의 DB는 여전히 하나일 수 있다는 점을 같이 봐야 해요.

**꼬리질문**
- Q. DB는 왜 스케일 아웃이 어렵나요? → 쓰기는 한 곳(원본)에서 해야 일관성이 지켜져서예요. 읽기는 레플리카로 나눌 수 있지만 쓰기는 샤딩 같은 큰 설계 변경이 필요해요.
</details>

<details>
<summary>Q. HPA를 켜 두면 급증을 막을 수 있나요?</summary>

**답변(30초)** 서서히 오르는 부하는 막지만, 초 단위 급증에는 늦어요. 메트릭이 15초마다 수집되고, HPA가 15초마다 판단하고, 한 번에 늘리는 폭도 제한돼 있어요. 그 뒤에도 새 파드가 이미지를 받고 JVM을 띄우고 readiness를 통과해야 트래픽을 받아요. 그래서 예정된 이벤트는 minReplicas를 미리 올리는 사전 스케일아웃을 하고, 예상 못 한 급증엔 레이트 리밋·대기열로 앞단에서 버텨요.

**꼬리질문**
- Q. 노드가 모자라면요? → 새 파드가 Pending에 머물러요. 노드를 늘리는 건 Cluster Autoscaler 몫이라 더 오래 걸려요.
- Q. 급증이 끝났는데 왜 파드가 안 줄어요? → 기본 5분 스케일 다운 안정화 때문이에요. 다음 파도에 다시 늦지 않게 하려는 의도예요.
</details>

<details>
<summary>Q. 서버를 늘렸더니 오히려 더 느려졌어요. 왜 그럴까요?</summary>

**답변(30초)** 병목이 앱이 아니라 DB였을 가능성이 커요. 파드마다 커넥션 풀을 가지니 파드를 늘리면 DB 연결 수가 곱으로 늘어요. 풀 10에 파드 30개면 300개로 MySQL 기본 max_connections 151을 넘어요. 넘지 않더라도 DB가 동시에 처리할 수 있는 양은 코어 수에 묶여 있어서, 연결만 늘면 서로 경합해 다 같이 느려져요. 그래서 캐시·레플리카·입장 제한으로 DB에 가는 요청을 줄이고, 풀 크기는 파드 수와 함께 계산해요.

**꼬리질문**
- Q. 그럼 풀 크기를 줄이면 되나요? → 파드당 풀을 줄여 총합을 DB 한도 안에 맞추는 건 맞아요. 다만 그것만으로 처리량이 늘진 않아서 DB 앞의 부하 자체를 줄여야 해요.
</details>

<details>
<summary>Q. 로드 셰딩과 우아한 성능 저하는 어떻게 다른가요?</summary>

**답변(30초)** 로드 셰딩은 요청 일부를 버려서 서버를 살리는 거고, 우아한 성능 저하는 요청은 받되 하는 일을 줄이는 거예요. 예를 들어 일부 요청에 바로 503을 주는 게 셰딩이고, 추천 대신 고정 목록을 보여 주는 게 성능 저하예요. 둘 다 버릴 순서, 즉 요청 중요도를 미리 정해 두고 테스트해 둬야 실제로 쓸 수 있어요.

**꼬리질문**
- Q. 과부하면 모든 요청을 막으면 되지 않나요? → 그러면 핵심 기능까지 죽어요. 중요도 낮은 것부터 버리는 게 원칙이에요.
</details>

<details>
<summary>Q. 과부하 때 재시도가 왜 장애를 키우나요?</summary>

**답변(30초)** 실패한 요청을 다시 보내면 이미 바쁜 서버에 요청이 더 쌓여요. 여러 계층이 각자 재시도하면 곱으로 늘어서, 3계층이 3번씩 재시도하면 맨 아래에는 최대 64배가 도착할 수 있어요. 그래서 지수 백오프와 지터로 간격을 벌리고, 요청당 재시도 횟수와 전체 재시도 비율을 제한하고, 서버는 "과부하니 재시도하지 말라"는 응답을 줘요.

**꼬리질문**
- Q. 재시도를 어느 계층에서 하나요? → 한 계층에서만 하는 게 좋아요. 여러 계층이 다 하면 곱이 돼요.
</details>

## 서술형 연습

아래 상황은 모두 실무 상황형 연습용으로 지어낸 것이에요. 실제 기출 문제가 아니에요.

<details>
<summary>상황 1: 오후 1시 할인 이벤트를 시작한 지 1분 만에 API 대부분이 503을 돌려줘요. 앱 파드 CPU는 95%를 넘었어요. 무엇을 어떤 순서로 하겠어요?</summary>

**상황 파악**
시작 직후 1분 만이니 서서히 오른 부하가 아니라 **순간 급증**이에요. 앱 CPU가 95%라 1차 병목은 앱 서버예요. 다만 DB나 외부 API도 같이 차 있는지 확인해야 "서버 늘리기"가 맞는 약인지 알 수 있어요.

**원인 후보**
1. 앱 파드 수가 순간 요청을 감당 못 함(HPA가 아직 반응 전)
2. 이벤트 페이지의 무거운 부가 기능(추천·실시간 랭킹)이 CPU를 먹음
3. 앱 CPU 과부하로 liveness 실패 → 재시작 → 남은 파드 더 과부하

**확인 순서**
RPS·에러율·p99로 급증 시점 확인 → `kubectl top pods`로 CPU, `kubectl get pods`로 RESTARTS → `kubectl describe hpa`로 HPA가 늘리고 있는지 → 커넥션 풀 pending·DB CPU로 DB가 아직 여유 있는지.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. replica 수동 상향(HPA 기다리지 않기) | 앱 CPU 병목에 직접 효과 | 준비까지 시간 걸림, 파드×풀이 DB 한도를 넘는지 먼저 계산해야 함 |
| B. 부가 기능 킬 스위치로 끄기 | 몇 초 안에 부하 감소, 배포 불필요 | 기능이 사라짐, 플래그가 미리 있어야 함 |
| C. 레이트 리밋·대기열로 입장 제한 | 시스템이 감당할 양만 받음 | 일부 사용자는 기다리거나 429를 봄 |

**내가 고를 방법**
B를 가장 먼저 해요. 효과가 가장 빠르고 되돌리기도 쉬워요. 동시에 A로 replica를 올리되, 파드 수 × 풀 크기가 DB `max_connections` 안인지 계산하고 올려요. 그래도 버거우면 C로 입장을 묶어요. 재시작이 반복되면 liveness가 외부 의존성을 보는지 확인해요. 재발 방지로 다음 이벤트부터는 시작 전에 minReplicas를 올리고, 이벤트 규모로 부하 테스트를 해요.

**채점 포인트**: 순간 급증 vs 서서히 증가 구분, HPA 반응 지연, 병목 확인 후 스케일아웃, 파드×풀 vs DB 한도, 기능 끄기·입장 제한, 핵심 기능 우선, 사전 스케일아웃·부하 테스트로 재발 방지.

**흔한 감점 답안**: "HPA가 있으니 기다린다", "서버를 늘린다" 한 줄로 끝, DB 영향 확인 없음, 즉시 완화와 근본 해결 구분 없음.
</details>

<details>
<summary>상황 2: HPA를 CPU 70% 목표로 켜 뒀는데, 푸시 알림 발송 직후 몰린 트래픽을 못 버티고 3분간 장애가 났어요. 장애가 끝날 무렵에야 파드가 늘어나 있었어요. 왜 그랬고, 어떻게 하겠어요?</summary>

**상황 파악**
HPA가 고장 난 게 아니라 **설계상 반응이 느린** 상황이에요. 푸시 발송 직후처럼 몇 초 만에 뛰는 부하는 HPA가 따라가기 전에 기존 파드를 넘어서요.

**원인 후보**
1. 지연이 쌓임: 메트릭 수집(15초 주기) + HPA 판단(15초 주기) + 한 번에 늘리는 폭 제한(15초마다 현재의 100% 또는 4개 중 큰 쪽)
2. 새 파드 준비 시간: 스케줄링, 이미지 받기, JVM·Spring 기동, readiness 통과. 기동 직후엔 캐시·JIT가 비어 느림
3. 노드가 모자라 새 파드가 Pending → 노드 증설까지 더 대기
4. 아직 Ready가 아닌 파드는 계산에서 0% 사용으로 가정돼 증가 폭이 보수적으로 줄어듦

**확인 순서**
`kubectl describe hpa` 이벤트에서 스케일 결정 시각 확인 → 새 파드의 생성·Ready 시각 비교 → Pending이 있었다면 Events의 FailedScheduling → 이미지 크기·애플리케이션 기동 시간 측정.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 예정된 발송 전 minReplicas 상향(사전 스케일아웃) | 가장 확실, 발송 시각을 우리가 앎 | 그 시간만큼 서버 비용, 끝나고 되돌리는 절차 필요 |
| B. 기동 시간 줄이기(이미지 경량화, 초기화 최소화) | 모든 스케일 상황에 도움 | 효과에 한계, 개발 비용 |
| C. 노드 여유 확보 | Pending 대기 제거 | 노는 노드 비용 |
| D. 푸시를 나눠 보내기 + 앞단 레이트 리밋 | 급증 자체를 완만하게 | 늦게 받는 사용자 생김, 마케팅과 협의 필요 |

**내가 고를 방법**
발송 시각을 아는 이벤트라 A가 1순위예요. 발송 몇 분 전에 파드와 노드를 미리 올리고 끝나면 내려요. 여기에 D로 발송을 몇 묶음으로 나눠 급증 모양을 완만하게 만들어요. B·C는 장기 과제로 둬요. HPA는 끄지 않고, 예상보다 더 몰릴 때의 안전망으로 남겨요.

**채점 포인트**: HPA 지연 구간(수집·판단·늘리는 폭·준비 시간) 설명, 노드 부족 Pending, 콜드 스타트, 사전 스케일아웃, 급증 모양 바꾸기(분산 발송·리밋), HPA는 안전망으로 유지.

**흔한 감점 답안**: "CPU 목표를 50%로 낮춘다"만 씀(반응 지연은 그대로), "HPA가 고장 났다", 준비 시간·노드 부족을 언급 안 함.
</details>

<details>
<summary>상황 3: 트래픽이 몰려서 앱 파드를 10개에서 30개로 늘렸어요. 그런데 직후부터 DB에서 "Too many connections" 에러가 나고, 원래 정상이던 API까지 전부 느려졌어요. 파드당 커넥션 풀은 10, DB는 MySQL 기본 설정이에요.</summary>

**상황 파악**
늘린 직후 DB 에러가 났으니 **스케일아웃 자체가 원인**이에요. 파드당 풀 10 × 30 = 300개 연결이 필요한데, MySQL 기본 `max_connections`는 151이에요. 10개일 땐 100개라 여유가 있었어요.

**원인 후보**
1. 총 커넥션(300)이 DB 한도(151)를 넘어 새 연결이 거절됨
2. 연결을 받은 파드들도 DB CPU·락을 서로 다퉈 쿼리가 다 느려짐
3. 연결 못 받은 요청이 풀에서 최대 30초(HikariCP 기본 connectionTimeout) 기다리며 요청 스레드를 묶음 → 전체 API 지연

**확인 순서**
`SHOW VARIABLES LIKE 'max_connections'`와 `SHOW STATUS LIKE 'Threads_connected'`로 한도와 현재 수 → 풀 지표(active·pending) → DB CPU → 배치·관리 도구가 쓰는 연결까지 합산.

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 파드 수를 DB 한도 안으로 되돌리거나 파드당 풀을 줄임(예: 30개 × 4) | 즉시 에러 멈춤 | 처리량은 그대로, 앱 병목이 다시 생길 수 있음 |
| B. `max_connections` 올리기 | 설정만 바꿈 | 연결마다 DB 메모리 사용, DB 처리량은 코어 수에 묶여 오히려 경합 증가 |
| C. 캐시 TTL 늘리기·읽기 레플리카·입장 제한으로 DB 부하 줄이기 | DB 병목의 근본 대응 | 데이터 신선도, 복제 지연, 대기 UX |

**내가 고를 방법**
먼저 A로 총 커넥션을 151 아래(관리용 여유 포함)로 맞춰 에러를 멈춰요. B는 DB 자원이 남는 걸 확인했을 때만 조금 올려요. 그다음 C로 DB까지 가는 요청을 줄여요. 앞으로는 "최대 파드 수 × 풀 크기 + 기타 연결 ≤ DB 한도"를 HPA maxReplicas와 풀 설정에 같이 반영해요.

**채점 포인트**: 파드 수 × 풀 = 총 커넥션 계산(300 > 151), 스케일아웃이 원인일 수 있다는 인식, DB 처리량은 코어 수에 묶임, max_connections 증설의 한계, 캐시·레플리카·입장 제한, maxReplicas와 풀 크기 함께 설계.

**흔한 감점 답안**: "max_connections를 1000으로 올린다"만 씀, "파드를 더 늘린다", 계산 없이 막연히 "DB가 느리다".
</details>

<details>
<summary>상황 4: 다음 달 한정 수량 특가 이벤트를 해요. 평소의 50배 트래픽이 예상돼요. 백엔드 담당으로서 사전 준비 계획을 세워 주세요.</summary>

**상황 파악**
날짜와 규모를 아는 이벤트라 **대부분을 미리 막을 수 있어요**. 목표는 "50배가 와도 결제·주문은 정상, 나머지는 줄을 서거나 품질을 낮춰서라도 버팀"이에요.

**원인 후보(터질 수 있는 지점)**
1. 앱 파드·노드 부족, HPA 반응 지연
2. DB 커넥션 총합 초과, 인기 상품 행에 쓰기 집중(재고 차감)
3. 캐시가 비어 있거나 동시 만료(스탬피드)
4. 외부 API(결제·알림)의 처리 한도
5. 재시도 폭증, liveness 연쇄 재시작

**준비 계획**
1. **피크 추정**: 평소 RPS × 50, API별 비율(상품 조회 vs 주문)로 나눠요.
2. **부하 테스트**: k6·nGrinder·JMeter 중 하나로 이벤트 시나리오를 만들어 깨질 때까지 올려요. 어디가 먼저 깨지는지(대개 DB·외부 API)와 부하가 빠진 뒤 회복되는지도 봐요.
3. **사전 스케일아웃**: 이벤트 전에 minReplicas와 노드를 미리 올려요.
4. **DB 커넥션 계산**: 최대 파드 수 × 풀 크기 + 기타 ≤ `max_connections`.
5. **캐시 워밍**: 이벤트 상품·메인 페이지 데이터를 미리 적재하고 TTL에 무작위 값을 더해 동시 만료를 막아요.
6. **입장 제한**: 대기열로 감당 가능한 인원만 입장, API별 레이트 리밋.
7. **끌 기능 목록과 킬 스위치**: 추천·리뷰 집계·실시간 랭킹 순으로 끌 순서를 정하고 플래그를 미리 배포해요.
8. **재고 차감 동시성**: 조건부 UPDATE나 Redis 원자 연산으로 초과 판매를 막아요([동시성: 재고·포인트](../concurrency-stock-points/)).
9. **관측·대응**: 대시보드·알람, 당일 담당자, 롤백·기능 끄기 절차를 미리 적어 둬요.

**트레이드오프**

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 넉넉한 사전 스케일아웃 | 안정성 | 이벤트 전후 서버 비용 |
| 대기열 | DB·결제 보호, 공정한 순서 | 사용자 대기, 대기열 구축 비용 |
| 캐시 TTL 길게 | DB 부하 감소 | 재고·가격 표시가 늦게 바뀜(최종 판정은 DB에서) |

**채점 포인트**: 피크 추정, 부하 테스트(도구 이름, 회복까지 테스트), 사전 스케일아웃·노드 확보, 커넥션 총합 계산, 캐시 워밍·TTL 지터, 대기열·리밋, 킬 스위치와 끌 순서, 재고 동시성, 모니터링·당일 대응 절차, 비용·UX 트레이드오프.

**흔한 감점 답안**: "서버를 50배로 늘린다"(DB·외부 API가 안 늘어남), 부하 테스트 없이 감으로 준비, 재고 초과 판매를 언급 안 함.
</details>

<details>
<summary>상황 5: 쇼핑 앱에 트래픽이 몰려 이대로면 전체가 멈출 것 같아요. 기능은 상품 조회, 장바구니, 주문·결제, 상품 추천, 리뷰, 실시간 인기 랭킹, 최근 본 상품이 있어요. 무엇부터 포기하고 무엇을 끝까지 지키겠어요?</summary>

**상황 파악**
모든 기능을 다 살릴 자원이 없으니 **버릴 순서**를 정하는 문제예요. 기준은 매출과 신뢰에 직결되는지, 꺼도 사용자가 목적을 이룰 수 있는지, 그 기능이 얼마나 비싼지(DB·CPU)예요.

**우선순위(예시)**

| 순위 | 기능 | 처리 |
|---|---|---|
| 끝까지 지킴 | 주문·결제 | 자원 우선 배정, 이것만은 정확해야 함 |
| 지킴(품질 낮춰도 됨) | 상품 조회, 장바구니 | 캐시 TTL 늘려 DB 보호, 상세 정보 일부 생략 가능 |
| 품질 낮춤 | 상품 추천 | 개인화 대신 미리 만든 고정 목록(우아한 성능 저하) |
| 먼저 끔 | 실시간 인기 랭킹, 리뷰 작성·집계, 최근 본 상품 | 킬 스위치로 끄거나 마지막 캐시 값 표시 |

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 기능별 킬 스위치로 낮은 순위부터 끄기 | 몇 초 안에 효과, 핵심은 그대로 | 플래그가 미리 있어야 함, 일부 기능 사라짐 |
| B. 우아한 성능 저하(고정 추천, 캐시 값) | 화면은 유지, 사용자 체감 작음 | 성능 저하 모드를 미리 만들고 테스트해야 함 |
| C. 요청 중요도별 로드 셰딩(낮은 중요도 요청부터 거절) | 자동으로 핵심 보호 | 요청마다 중요도 표시가 필요, 설계 비용 |

**내가 고를 방법**
지금 당장은 A와 B예요. 랭킹·리뷰 집계·최근 본 상품을 끄고, 추천은 고정 목록으로 바꿔요. 주문·결제는 레이트 리밋에서 별도 한도를 두거나 대기열로 입장시켜 보호해요. 장기적으로는 C처럼 요청에 중요도를 붙여(Google SRE의 CRITICAL·SHEDDABLE 같은 구분) 과부하 때 자동으로 낮은 것부터 버리게 해요. 끄는 순서와 플래그는 장애 전에 문서로 정해 두고 훈련해요.

**채점 포인트**: 버릴 기준(매출·필수 여부·비용), 핵심(주문·결제) 끝까지 보호, 끄기 vs 품질 낮추기 구분, 킬 스위치·피처 플래그, 로드 셰딩과 요청 중요도, 사전에 정해 두고 테스트, "전부 막기"는 실수.

**흔한 감점 답안**: "모든 요청을 막고 점검 페이지를 띄운다"(핵심까지 죽음), 우선순위 기준 없이 나열만, 미리 준비해야 쓸 수 있다는 점을 빠뜨림.
</details>
