:::tip[한 줄 요약]
여러 요청이 같은 잔액·재고를 **동시에 읽고 각자 계산해 덮어쓰면** 에러 하나 없이 차감이 사라져요(갱신 손실). 단순 차감은 **조건부 UPDATE**, 읽고 복잡하게 검증해야 하면 **비관적 락(FOR UPDATE)**, 충돌이 드물면 **낙관적 락(@Version)**을 고르고, 같은 요청이 두 번 오는 문제는 락이 아니라 **멱등 키 + 유니크 제약**으로 막아요.
:::

:::note[처음이라면 여기까지]
① "잔액 읽기 → 앱에서 빼기 → 결과 저장"을 따로따로 하면, 그 사이에 다른 요청이 끼어들어 한쪽 차감이 사라져요. 에러가 안 나서 더 위험해요.

② 가장 쉬운 해결은 읽기와 빼기를 DB에 **한 문장**으로 맡기는 거예요. `balance = balance - 10 WHERE balance >= 10` 이렇게요.

③ `synchronized`는 서버 한 대 안에서만 통해요. 서버가 여러 대면 DB에서 막아야 해요.

④ "버튼 두 번 누름"은 동시성과 다른 문제예요. 락은 순서만 정해 줄 뿐 두 번 다 실행해요. 요청마다 고유 번호를 붙이고 DB가 중복을 거절하게 해요. 서술형은 1·2번부터 풀어 보세요.
:::

## 쉽게 이해하기

가족이 같이 쓰는 공용 통장 하나가 있다고 해 봐요. 잔액은 1,000원이에요.

엄마와 아빠가 같은 순간에 각자 앱을 열어요. 둘 다 "1,000원 있네"를 봐요. 엄마는 10원을 쓰고 "남은 돈 990원"이라고 장부에 적어요. 아빠도 10원을 쓰고 자기가 본 1,000원에서 계산해 "990원"이라고 적어요. 20원이 나갔는데 장부엔 990원이 남아요. 엄마의 10원이 장부에서 **사라진** 거예요.

해결책은 몇 가지예요.

- 은행 창구에 "지금 잔액에서 10원 빼 주세요, 모자라면 거절하고요"라고 **한 번에** 부탁하기(조건부 UPDATE)
- 통장을 쓰는 동안 **들고 가서** 다른 사람이 못 보게 하기(비관적 락)
- 적을 때 "내가 본 장부 쪽수가 아직 그대로면 적고, 누가 먼저 적었으면 처음부터 다시"(낙관적 락)

그리고 아빠가 실수로 같은 결제를 두 번 눌렀다면? 이건 줄을 세워도 두 번 다 빠져요. 영수증 번호를 보고 "이 번호는 이미 처리했어요"라고 거절해야 해요(멱등 키).

단, 실제로는 "통장을 들고 간다"는 것도 DB 안에서 행 하나에 표시를 거는 거라, 서버가 몇 대든 DB 한 곳에서 줄이 세워져요. 앱 서버 안의 자물쇠(`synchronized`)와는 달라요.

## 그림으로 보기

<LostUpdateVsConditional />

같은 실험을 실제로 돌려 본 결과예요. 잔액 1,000원 계좌에 "10원 차감" 요청 100건을 동시에 보냈어요. 기대하는 최종 잔액은 0원이에요.

| 방법 | 최종 잔액 | 사라진 차감 | 에러 | 비고 |
|---|---|---|---|---|
| 일반 SELECT 후 UPDATE | 690 / 290 / 320 (3번 실행) | **69 / 29 / 32건** | 0건 | 돌릴 때마다 손실 수가 달라요 |
| 같은 방법 + 읽기와 쓰기 사이 20ms 지연 | 930 | **93건** | 0건 | 틈이 길수록 손실이 커져요 |
| 조건부 UPDATE | 0 | 0 | 0건 | 100건 모두 affected rows 1 |
| `SELECT ... FOR UPDATE` + 20ms 지연 | 0 | 0 | 0건 | 한 줄로 대기 → 적어도 100 × 20ms = 2초 |
| 낙관적 락(version) | 0 | 0 | 0건 | 대신 **재시도 804번**, 한 요청은 33번 시도 |

중복 요청도 따로 재 봤어요. 같은 요청 번호(`request_id`)로 INSERT 100건을 동시에 보내니, 유니크 제약 덕분에 **1건만 들어가고 99건은 `Duplicate entry` 에러**로 거절됐어요.

<Aside type="note" title="실험 예시라는 점">
로컬 임시 MySQL 서버(InnoDB, 기본 격리 수준 REPEATABLE READ)에서 mysql 명령줄 프로세스 100개를 병렬로 띄워 한 번 재 본 예시예요. 실제 앱(커넥션 풀, JPA)과는 타이밍이 달라서 손실 "개수"는 의미가 없고, **"에러 없이 사라진다"**는 경향만 보면 돼요.
</Aside>

가장 무서운 점은 첫 줄이에요. 에러가 0건이라 로그만 봐서는 아무 일도 없어 보여요. 나중에 정산이나 고객 문의로 발견돼요.

## 이 유형을 푸는 순서

"재고가 음수가 됐다", "포인트가 안 맞는다", "쿠폰이 초과 발급됐다" 같은 문제가 나오면 이 순서로 답을 짜요.

<ConcurrencyDecisionFlow />

1. **공유 자원과 경쟁 구간 찾기**: 여러 요청이 동시에 고치는 데이터는 무엇이고(포인트 잔액 한 행, 상품 재고 한 행), 코드에서 "읽기 → 판단 → 쓰기"가 떨어져 있는 구간은 어디인가요? 보통 `findById → if 검사 → set` 같은 모양이에요.
2. **조건 확인**: 서버는 몇 대인가요? 같은 행에 충돌이 얼마나 자주 나나요(인기 상품, 선착순)? 정확성이 얼마나 중요한가요(돈이면 최상)?
3. **방법 고르기**: 아래 비교표에서 고르고, **왜 다른 걸 안 골랐는지**까지 써요.
4. **실패 처리**: 차감이 안 됐을 때(잔액 부족, 품절, 락 대기 초과, 버전 충돌) 무엇을 응답하나요? 재시도한다면 어디서, 몇 번까지?
5. **중복 요청 막기**: 더블 클릭·네트워크 재시도로 같은 요청이 두 번 오면? 멱등 키와 유니크 제약을 따로 챙겨요.
6. **재발 방지**: 동시 요청 테스트(스레드 100개를 한꺼번에 출발시키기)로 재현하고, 잔액·재고를 주문 기록과 맞춰 보는 점검을 둬요.

<Aside type="caution" title="답안에서 자주 빠뜨리는 것">
4번 "실패하면 어떻게 하나"와 5번 "같은 요청 두 번"이에요. "락을 건다"로 끝나는 답은 방향은 맞지만 점수가 낮아요. 어떤 락을, 왜, 실패하면 어떻게까지 써야 해요.
</Aside>

## 제대로 알기

### 방법 비교: 언제 쓰고 언제 못 쓰나

| 방법 | 언제 쓰나 | 못 쓰거나 조심할 때 |
|---|---|---|
| **조건부 UPDATE** | 잔액·재고 단순 차감, 선착순. 한 행·한 문장으로 끝나는 경우 | 여러 테이블에 걸친 복잡한 규칙은 한 문장으로 못 씀 |
| **비관적 락** `FOR UPDATE` | 읽은 값으로 복잡하게 검증한 뒤 써야 하고, 충돌이 잦을 때 | 기다리는 동안 커넥션을 쥠. 락 안에서 외부 API를 부르면 줄이 길어짐. 여러 행을 다른 순서로 잠그면 데드락 |
| **낙관적 락** `@Version` | 게시글·설정 수정처럼 충돌이 드문 데이터 | 한 행에 몰리면(인기 상품) 재시도 폭증 |
| **유니크 제약** | 더블 클릭, 재시도, 1인 1쿠폰 | 동시 차감 문제는 못 풂(중복만 막음) |
| **Redis 분산 락** | DB 밖 자원(외부 API, 여러 DB에 걸친 작업)을 서버 여러 대가 순서대로 써야 할 때 | 락 만료·Redis 장애 때 두 서버가 동시에 락을 가질 수 있음. 최종 정확성은 DB에 남겨야 함 |
| `synchronized` | 서버 1대·트랜잭션 밖의 메모리 자원 정도 | 서버 여러 대면 안 됨. `@Transactional` 메서드에 붙여도 깨짐 |

판단 기준을 한 번 더 표로 보면 이래요. 정답표가 아니라 **보통 이렇게 판단한다**는 일반론이에요.

| 방법 | 충돌이 잦을 때 | 서버 여러 대 | 성능 | 잘 맞는 상황 |
|---|---|---|---|---|
| 조건부 UPDATE | 좋음(대기 짧음) | 됨 | 보통 가장 좋음 | 단순 차감, 선착순 |
| 비관적 락 | 좋음(줄 서기) | 됨 | 대기·커넥션 점유 | 읽고 검증 후 쓰기, 충돌 잦은 돈 |
| 낙관적 락 | 나쁨(재시도 폭증) | 됨 | 충돌 적으면 가벼움 | 충돌 드문 엔티티 |
| 유니크 제약 | 해당 없음 | 됨 | 좋음 | 중복 요청, 1인 1회 |
| Redis 분산 락 | 줄 서기 | 됨 | 네트워크 왕복 추가 | DB 밖 자원 |
| `synchronized` | 해당 없음 | **안 됨** | 빠름 | 거의 안 씀 |

### 조건부 UPDATE: 읽기와 쓰기를 한 문장으로

```sql
-- 잔액이 충분할 때만 10 차감. DB가 '지금 값' 기준으로 검사하고 뺀다
UPDATE account
SET balance = balance - 10
WHERE id = 1 AND balance >= 10;
-- 바뀐 행이 1이면 성공, 0이면 잔액 부족 → 실패 응답
```

UPDATE는 찾은 행에 **배타 락**(다른 쓰기를 못 하게 하는 잠금)을 걸고, 다른 트랜잭션이 마지막으로 커밋한 최신 값으로 조건을 따져요. 그래서 읽기와 쓰기 사이에 틈이 없어요.

성공 여부는 **affected rows**(이 문장으로 영향받은 행 수)로 판단해요. 실험에서 잔액을 500원으로 두고 같은 100건을 보내니 **1이 50건, 0이 50건**이었고 잔액은 음수 없이 0으로 끝났어요. 0이 나온 50건에는 "잔액 부족"을 응답하면 돼요.

### 비관적 락: 줄 세우고 하나씩

```sql
START TRANSACTION;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;  -- 이 행을 잠그고 최신 값 읽기
-- 앱에서 잔액·한도·쿠폰 등 복잡한 검증
UPDATE account SET balance = ? WHERE id = 1;
COMMIT;  -- 여기서 락이 풀린다
```

`FOR UPDATE`로 읽은 행은 다른 트랜잭션이 고치거나 `FOR UPDATE`로 읽지 못하고 기다려요. 락은 **커밋·롤백할 때** 풀려요. 그래서 반드시 트랜잭션 안에서 써야 해요. Spring Data JPA에서는 리포지토리 메서드에 `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 붙이면 Hibernate가 MySQL에선 `SELECT ... FOR UPDATE`로 바꿔 실행해요.

비용은 **기다림**이에요. 실험처럼 20ms짜리 작업 100건이 한 줄로 서면 적어도 2초(100 × 20ms)가 걸려요. 락을 쥔 채 외부 API를 부르면 그 시간만큼 모두가 기다려요.

### 낙관적 락: 일단 하고, 겹치면 다시

```java
@Entity
class Account {
    @Id Long id;
    int balance;
    @Version Long version;  // Hibernate가 직접 올림. 코드에서 바꾸지 않는다
}
// 실제 SQL: UPDATE account SET balance=?, version=v+1 WHERE id=? AND version=v
// 바뀐 행이 0이면 그 사이 누가 고친 것 → 예외
```

잠그지 않고 읽은 뒤, 쓸 때 "내가 읽은 버전이 아직 그대로면" 저장해요. 누가 먼저 바꿨으면 바뀐 행이 0이 되고 `OptimisticLockException`이 나요. Spring에선 `ObjectOptimisticLockingFailureException`으로 바뀌어 올라와요.

충돌이 드물면 가장 가볍지만, 한 행에 몰리면 재시도가 폭발해요. 실험에서 100건을 성공시키는 데 **총 904번** 시도했어요.

### 유니크 제약: 같은 요청 두 번 막기

```sql
CREATE TABLE point_use (
  request_id VARCHAR(64) NOT NULL UNIQUE,  -- 클라이언트가 만든 요청 번호(멱등 키)
  user_id BIGINT, amount INT, result VARCHAR(20)
);
-- 처리 전에 먼저 INSERT. 같은 번호가 또 오면 Duplicate entry → 이전 결과를 돌려준다
```

**멱등**(같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질)을 만드는 장치예요. "먼저 조회해서 없으면 INSERT"는 조회와 INSERT 사이에 틈이 있어서 둘 다 통과할 수 있어요. 유니크 제약은 DB가 인덱스에서 보장하니 서버가 몇 대든 틈이 없어요. "1인 1쿠폰"도 같은 원리로 `UNIQUE(user_id, coupon_id)`를 걸어요. → [멱등 키와 아웃박스](../../distributed/outbox-idempotency/)

### 심화: REPEATABLE READ인데 왜 갱신 손실이 나나

"MySQL 기본 격리 수준이 REPEATABLE READ(RR)니까 안전하다"는 오해가 많아요. 실험도 RR에서 돌렸는데 차감이 사라졌어요.

- InnoDB의 일반 SELECT는 **락을 걸지 않는 읽기**예요. 트랜잭션에서 처음 읽은 시점의 사진(스냅샷)을 보여 줄 뿐이에요.
- RR의 스냅샷은 SELECT에만 적용되고, UPDATE는 다른 트랜잭션이 커밋한 **최신 행**을 대상으로 동작해요.
- 그래서 RR은 "내가 읽은 값이 계속 같아 보이게" 해 줄 뿐, "남이 못 바꾸게" 막지 않아요. 읽은 값으로 계산해서 `SET balance = 990`을 쓰면 남의 변경을 덮어써요.

READ COMMITTED로 낮춰도 읽기와 쓰기 사이 틈은 그대로예요. 그렇다고 SERIALIZABLE로 올리면 InnoDB가 일반 SELECT를 공유 락 읽기(`FOR SHARE`)로 바꿔서, 두 트랜잭션이 공유 락을 쥔 채 서로 UPDATE하려다 **데드락**이 나요. 한쪽이 롤백돼 손실은 막히지만, 실패한 요청을 다시 해야 하고 동시성이 크게 떨어져요. 전역 격리 수준이 아니라 이 쿼리에 맞는 락을 골라야 해요. → [트랜잭션 격리 수준](../../db/isolation-levels/)

### 심화: synchronized + @Transactional 함정

서버 1대인데도 `@Transactional` 메서드에 `synchronized`를 붙이면 깨질 수 있어요.

Spring의 `@Transactional`은 **프록시**(진짜 객체 앞에 서서 호출을 대신 받는 대리 객체)가 메서드 호출을 감싸서 트랜잭션을 시작하고 커밋해요. `synchronized`는 진짜 메서드에 걸려요. 그래서 순서가 이렇게 돼요.

```
[프록시: 트랜잭션 시작]
    [락 획득 → 잔액 읽기·차감 → 락 해제]
        ← 틈: 다음 스레드가 들어와 아직 커밋 안 된 '이전 값'을 읽음
[프록시: 커밋]
```

락이 풀린 뒤 커밋되기 전 틈에 다음 요청이 옛 값을 읽어요. 이건 Spring 문서가 직접 적은 내용은 아니고, "프록시가 메서드 호출 전후로 트랜잭션을 돈다"는 문서 설명에서 따라 나오는 결론이에요. 락을 트랜잭션 바깥 메서드(다른 빈)로 빼면 틈은 메워지지만, 여전히 서버 1대에서만 통해요. → [@Transactional 동작 원리](../../spring/transactional/), [자바 동기화](../../java/synchronization/)

### 심화: 낙관적 락 재시도는 트랜잭션 바깥에서

- 버전 충돌 예외가 나면 그 트랜잭션은 **롤백 표시**가 돼요. 같은 트랜잭션 안에서 catch해서 다시 시도해도 커밋할 수 없어요.
- 그래서 재시도는 `@Transactional` 메서드를 **바깥에서** 다시 부르는 식으로, 매번 새 트랜잭션에서 다시 읽고 해요.
- JPA는 쓰기를 트랜잭션 끝까지 미룰 수 있어서 예외가 **커밋 시점**에야 날 수도 있어요. 메서드 안에서 직접 잡아야 하면 `flush()`로 쓰기를 앞당겨요.
- 재시도는 횟수 제한을 둬요. 실험에선 최대 50번으로 뒀는데 한 요청이 33번까지 갔어요.
- JPQL 벌크 UPDATE는 `@Version` 값을 자동으로 올리지 않아요. 벌크 문으로 바꿀 땐 버전도 직접 올려야 해요.

### 심화: JDBC affected rows 함정

MySQL에서 UPDATE의 affected rows는 기본적으로 **실제로 값이 바뀐 행 수**예요. 그런데 MySQL Connector/J(자바용 MySQL 드라이버)는 `useAffectedRows` 기본값이 `false`라서, JDBC `executeUpdate()`가 **WHERE에 맞은 행 수**를 돌려줘요.

`balance = balance - 10`처럼 값이 항상 바뀌는 UPDATE에선 둘이 같아서 문제없어요. 하지만 "이미 `USED`인 쿠폰을 `USED`로" 바꾸는 UPDATE의 반환값으로 성공을 판정하면, 값은 안 바뀌었는데 1이 나와 착각할 수 있어요. 이럴 땐 WHERE에 `status = 'UNUSED'`처럼 바뀌기 전 상태를 조건으로 넣어요.

### 심화: 분산 락과 Redis 앞단 차감

Redis 분산 락(`SET key 토큰 NX PX 만료시간`)은 서버 여러 대가 DB 밖 자원을 순서대로 쓰게 할 때 써요. 단 락이 만료된 뒤 두 서버가 동시에 락을 가진다고 믿는 순간이 생길 수 있어서, redis.io도 펜싱 토큰을 권해요. 그래서 **최종 정확성은 DB 조건부 UPDATE나 유니크 제약에 남겨요**. → [Redis 분산 락](../../redis/distributed-lock/)

DB가 못 버틸 만큼 몰리는 선착순은 Redis에서 재고를 먼저 깎아 대부분을 걸러내고, 통과한 요청만 DB 조건부 UPDATE로 확정하는 2단 구조를 써요. → [대기열 설계](../../system-design/waiting-queue/)

## 면접 질문

<details>
<summary>Q. 갱신 손실(lost update)이 뭔가요?</summary>

**답변(30초)** 두 요청이 같은 값을 읽고 각자 계산해서 덮어써, 한쪽 변경이 사라지는 현상이에요. 잔액 1,000에 두 요청이 동시에 10씩 빼면, 둘 다 1,000을 읽고 990을 써서 최종 990이 돼요. 기대값 980에서 10이 사라진 거예요. 에러가 안 나서 정산이나 고객 문의로 늦게 발견되는 게 특징이에요.

**꼬리질문**
- Q. 왜 에러가 안 나나요? → 두 UPDATE 모두 정상 실행이라서요. DB 입장에선 순서대로 두 번 쓴 것뿐이에요.
- Q. 어떻게 재현하나요? → 스레드 100개를 한꺼번에 출발시켜 같은 행을 차감하고 최종 값을 기대값과 비교해요.
</details>

<details>
<summary>Q. 재고 차감 동시성 문제를 어떻게 해결하나요?</summary>

**답변(30초)** 단순 차감이면 조건부 UPDATE를 먼저 고려해요. `stock = stock - 1 WHERE stock > 0`처럼 DB가 최신 값 기준으로 검사·차감하게 하고 affected rows가 0이면 품절로 응답해요. 여러 테이블을 읽고 복잡하게 검증해야 하면 `FOR UPDATE` 비관적 락을, 충돌이 드문 데이터면 `@Version` 낙관적 락을 써요. 서버가 여러 대일 수 있으니 `synchronized` 같은 앱 내부 락은 쓰지 않아요.

**꼬리질문**
- Q. 조건부 UPDATE의 한계는? → 한 행·한 문장으로 표현되는 규칙에만 써요. 복잡하면 락이 필요해요.
- Q. 트래픽이 아주 크면? → Redis에서 앞단 차감으로 걸러내고 DB에서 최종 확정해요.
</details>

<details>
<summary>Q. 비관적 락과 낙관적 락은 어떻게 고르나요?</summary>

**답변(30초)** 충돌 빈도로 골라요. 비관적 락은 읽을 때부터 행을 잠가 줄을 세우니 충돌이 잦은 곳에 맞지만 대기와 커넥션 점유가 비용이에요. 낙관적 락은 잠그지 않고 쓸 때 버전으로 충돌을 감지하니 충돌이 드물면 가볍지만, 한 행에 몰리면 재시도가 폭증해요. 실험에서 100건에 904번 시도가 필요했어요.

**꼬리질문**
- Q. 낙관적 락은 DB 락을 전혀 안 쓰나요? → 버전 조건 UPDATE를 실행하는 순간엔 행 락을 잡아요. 읽고 고민하는 동안 잠그지 않을 뿐이에요.
- Q. 충돌 시 재시도는 어디서? → 트랜잭션 바깥에서 새 트랜잭션으로, 횟수 제한을 두고요.
</details>

<details>
<summary>Q. synchronized로 해결하면 안 되나요?</summary>

**답변(30초)** 두 가지 이유로 안 돼요. 첫째, `synchronized`는 한 JVM 안의 스레드만 막아서 서버가 두 대 이상이면 각자 자기 락을 가져요. 둘째, 서버가 한 대여도 `@Transactional` 메서드에 붙이면 락 해제가 커밋보다 먼저라, 그 틈에 다음 요청이 커밋 전 값을 읽어요. 그래서 실무에선 DB에서 막아요.

**꼬리질문**
- Q. 둘째 문제는 어떻게 메우나요? → 락을 트랜잭션 바깥(다른 빈)에서 잡으면 되지만 여전히 서버 1대 한정이라 쓸 이유가 적어요.
</details>

<details>
<summary>Q. MySQL 기본 격리 수준이 REPEATABLE READ인데 왜 갱신 손실이 나나요?</summary>

**답변(30초)** RR의 스냅샷은 읽기용이지 락이 아니기 때문이에요. InnoDB의 일반 SELECT는 락 없이 스냅샷을 읽어서 다른 트랜잭션이 같은 행을 고칠 수 있어요. 앱에서 계산한 값을 그대로 쓰면 남의 변경을 덮어써요. 막으려면 조건부 UPDATE나 `FOR UPDATE` 같은 잠금 읽기를 써야 해요.

**꼬리질문**
- Q. SERIALIZABLE로 올리면? → InnoDB가 일반 SELECT를 공유 락 읽기로 바꿔서, 두 트랜잭션이 서로 UPDATE하려다 데드락이 나요. 한쪽이 롤백돼 손실은 막지만 재시도가 필요하고 동시성이 크게 떨어져요.
</details>

<details>
<summary>Q. 결제 버튼을 두 번 누르면 어떻게 막나요?</summary>

**답변(30초)** 멱등 키로 막아요. 클라이언트가 요청마다 고유 번호를 만들어 보내고, 서버는 처리 전에 그 번호를 유니크 제약이 걸린 테이블에 INSERT해요. 같은 번호가 또 오면 중복 에러가 나니 처리하지 않고 이전 결과를 돌려줘요. 락은 순서만 정해 줄 뿐 두 요청을 다 실행하기 때문에 따로 필요해요.

**꼬리질문**
- Q. 앱에서 "먼저 조회해서 없으면 처리"는 왜 안 되나요? → 조회와 INSERT 사이 틈으로 둘 다 통과할 수 있어요. DB 유니크 제약은 서버가 몇 대든 틈이 없어요.
- Q. 첫 요청이 아직 처리 중일 때 두 번째가 오면? → 처리 중 상태를 기록해 두고 "처리 중" 응답이나 대기 후 결과 반환을 해요.
</details>

## 서술형 연습

아래는 연습용 가상 상황이에요. 실제 기출 문제가 아니에요. 쉬운 것부터 어려운 순서예요.

<details>
<summary>상황 1: 포인트 사용 API에서 이벤트 날 잔액이 음수인 계정과, 쓴 만큼 안 빠진 계정이 함께 발견됐어요. 코드는 findById로 잔액을 읽고, 잔액이 충분하면 setBalance(잔액 - 사용액)을 해요(JPA 변경 감지로 저장). 에러 로그는 없어요. 원인과 해결을 써 주세요.</summary>

**상황 파악**
공유 자원은 사용자 포인트 잔액 한 행이에요. "읽기(findById) → 앱에서 검사·계산 → 저장"이 떨어져 있고, 이벤트 날 같은 사용자의 요청이 겹칠 때만 나타나요. 에러가 없다는 건 "실패"가 아니라 "덮어쓰기"라는 신호예요.

**원인 후보**
1. 갱신 손실: 두 요청이 같은 잔액을 읽고 각자 계산해 덮어씀 → 차감 누락
2. 검사와 차감 사이 틈: 둘 다 "잔액 충분"을 보고 통과 → 합치면 잔액보다 많이 씀 → 음수
3. "RR이니 안전하다"는 가정: 일반 SELECT는 락이 없어서 막아 주지 않아요

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 조건부 UPDATE `balance = balance - ? WHERE id = ? AND balance >= ?` | 틈이 없음, 대기 짧음, 서버 대수 무관 | 규칙이 복잡해지면 한 문장으로 못 씀. 변경 감지 대신 직접 쿼리 |
| B. `@Lock(PESSIMISTIC_WRITE)`로 읽기 | 기존 코드 구조 유지, 복잡한 검증 가능 | 같은 사용자 요청이 줄 섬, 트랜잭션이 길면 커넥션 점유 |
| C. `@Version` 낙관적 락 | 평소엔 가벼움 | 충돌 시 재시도 설계 필요 |

**내가 고를 방법**
포인트 차감은 "잔액 확인 + 차감"이 한 행으로 끝나니 A를 골라요. affected rows가 0이면 "잔액 부족"으로 응답해요. 사용 내역 기록 같은 다른 작업은 같은 트랜잭션에 넣어요. 규칙이 늘어 한 문장으로 못 쓰게 되면 B로 바꿔요. 재발 방지로 스레드 100개를 한꺼번에 출발시키는 동시성 테스트를 넣고, 잔액을 사용 내역 합계와 맞춰 보는 점검으로 이미 틀어진 계정을 찾아 보정해요.

**채점 포인트**: 갱신 손실 용어, 읽기-쓰기 틈 지적, RR이어도 난다, 조건부 UPDATE + affected rows 0 처리, 대안 1개 이상과 비교, 동시성 테스트, 틀어진 데이터 보정.

**흔한 감점 답안**: "트랜잭션을 건다"(이미 트랜잭션 안이라도 일어나요), "격리 수준을 SERIALIZABLE로 올린다"(데드락), "synchronized를 붙인다"(서버 여러 대·프록시 문제).
</details>

<details>
<summary>상황 2: 서버 1대일 땐 포인트 차감 메서드에 synchronized를 붙여 문제가 없었어요. 트래픽이 늘어 서버를 3대로 늘리자 잔액 불일치가 다시 생겼어요. 왜 그런지, 어떻게 고치는지 써 주세요.</summary>

**상황 파악**
변한 건 서버 대수뿐이에요. `synchronized`는 한 JVM 안에서만 줄을 세우니, 서버 3대면 자물쇠도 3개라 서로를 막지 못해요.

**원인 후보**
1. 서버마다 따로인 락: 서버 A와 B의 요청이 동시에 같은 행을 읽고 덮어씀
2. 사실 1대일 때도 안전하지 않았을 가능성: `@Transactional` 메서드에 `synchronized`를 붙였다면 락 해제 후 커밋 전 틈이 있어요. 트래픽이 적어 안 드러났을 뿐일 수 있어요(프록시 구조에서 나오는 결론이에요)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 조건부 UPDATE | DB 한 곳에서 줄 서니 서버 대수 무관, 추가 인프라 없음 | 단순 차감에만 |
| B. 비관적 락 `FOR UPDATE` | 복잡한 검증 가능, 서버 대수 무관 | 대기·커넥션 점유 |
| C. Redis 분산 락 | DB 밖 자원까지 직렬화 가능 | Redis 왕복·장애 지점 추가, 만료 시 두 서버가 동시에 가질 수 있음 |

**내가 고를 방법**
A를 골라요. 데이터가 DB 한 행에 있으니 DB에서 막는 게 가장 단순하고, 분산 락은 Redis라는 새 장애 지점을 더하면서도 결국 DB 쪽 보호가 또 필요해요. `synchronized`는 지워요. 남겨 두면 서버 1대 안에서 불필요하게 줄만 세워요. 분산 락은 외부 API 호출처럼 DB로 막을 수 없는 자원이 생길 때 검토해요.

**채점 포인트**: JVM 단위 락이라는 설명, 서버 대수 무관한 DB 수준 해결, `@Transactional` + `synchronized` 틈 언급, 분산 락을 고르지 않은 이유(또는 고른다면 펜싱·DB 최종 보호).

**흔한 감점 답안**: "Redis 분산 락을 건다"로만 끝내는 답. 왜 DB 락이 아닌지, 락 만료 땐 어떻게 되는지 빠지면 감점이에요.
</details>

<details>
<summary>상황 3: 인기 상품 재고에 @Version 낙관적 락을 적용했더니 ObjectOptimisticLockingFailureException이 초당 수백 건 나고, 사용자 대부분이 "구매 실패"를 봐요. 원인과 개선을 써 주세요.</summary>

**상황 파악**
재고는 상품당 한 행이고, 인기 상품은 그 한 행에 요청이 몰려요. 낙관적 락은 "충돌이 드물다"를 전제로 한 방법이라 전제가 깨졌어요.

**원인 후보**
1. 충돌 빈도가 높은 곳에 낙관적 락: 동시에 읽은 요청 중 하나만 성공하고 나머지는 전부 버전 충돌
2. 재시도가 없거나, 있어도 같은 트랜잭션 안에서 시도: 예외 후 트랜잭션은 롤백 표시라 커밋 불가
3. 재시도가 있다면 무제한·즉시 재시도: 다시 몰려서 또 충돌(실험에서 100건 성공에 904번 시도, 한 요청이 33번)

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 조건부 UPDATE로 교체 | 실패는 "진짜 품절"일 때만, 재시도 불필요 | 변경 감지 대신 직접 쿼리 작성 |
| B. 비관적 락으로 교체 | 실패 없이 줄 서서 처리 | 대기 시간·커넥션 점유, 몰리면 응답 지연 |
| C. 낙관적 락 유지 + 재시도 개선(트랜잭션 밖, 횟수 제한, 간격 두기) | 코드 변경 적음 | 몰릴수록 시도 횟수 증가, DB 부하 |

**내가 고를 방법**
재고 차감은 한 행 한 문장으로 끝나니 A로 바꿔요. affected rows 0일 때만 "품절"이라 사용자에게 정확한 메시지를 줄 수 있어요. 낙관적 락은 상품 설명 수정처럼 충돌이 드문 곳에 남겨요. 당장 A를 배포하기 어렵다면 C로 급한 불을 끄되, 재시도는 `@Transactional` 메서드 바깥에서 새 트랜잭션으로, 횟수 제한을 둬요. 트래픽이 DB가 못 버틸 수준이면 Redis 앞단 차감이나 대기열을 더해요.

**채점 포인트**: 낙관적 락의 전제(충돌 드묾), 충돌 잦은 곳엔 부적합, 재시도는 트랜잭션 밖·횟수 제한, 롤백 표시, 대안 비교, 낙관적 락이 맞는 곳 구분.

**흔한 감점 답안**: "재시도를 넣는다"만 쓰는 답. 어디서, 몇 번, 왜 그 자리인지 없으면 감점이고, 같은 트랜잭션 안에서 catch해 재시도하는 답은 틀려요.
</details>

<details>
<summary>상황 4: 결제 버튼을 빠르게 두 번 누른 사용자의 포인트가 두 번 차감됐어요. 포인트 차감에는 이미 조건부 UPDATE를 쓰고 있어요. 원인과 해결을 써 주세요.</summary>

**상황 파악**
조건부 UPDATE가 있으니 잔액이 틀어지진 않았어요. 문제는 **같은 의도의 요청이 두 번 들어와서 두 번 다 정당하게 처리된 것**이에요. 동시성(누가 먼저냐)이 아니라 중복(같은 요청이 몇 번이냐) 문제예요.

**원인 후보**
1. 더블 클릭: 화면에서 버튼을 막지 않음
2. 네트워크 재시도: 첫 요청은 처리됐는데 응답이 늦어 앱이 다시 보냄
3. 서버에 "이 요청은 이미 처리했다"를 판단할 기준이 없음

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 화면에서 버튼 비활성화 | 쉬움, 대부분의 더블 클릭 막음 | 네트워크 재시도·API 직접 호출은 못 막음. 보조 수단 |
| B. 멱등 키 + `UNIQUE(request_id)` | 서버 대수 무관, 재시도까지 막음, 이전 결과 재응답 가능 | 키 생성 규칙·결과 저장·만료 정책 설계 필요 |
| C. 앱에서 "최근 같은 요청 있었나" 조회 후 처리 | 테이블 변경 적음 | 조회와 처리 사이 틈으로 둘 다 통과 가능 |

**내가 고를 방법**
B를 기본으로 하고 A를 함께 써요. 클라이언트가 결제 시도마다 UUID를 만들어 보내고, 재시도할 때도 같은 값을 보내요. 서버는 포인트 차감 전에 `point_use(request_id UNIQUE)`에 "처리 중"으로 INSERT해 먼저 커밋하고, 차감과 결과 저장은 그다음 한 트랜잭션으로 묶어요. 처리 중에 멈춘 키는 만료 시간을 두고 정리해요. 같은 키가 또 오면 중복 에러가 나니 저장된 결과를 그대로 돌려주고, 아직 처리 중이면 "처리 중"(예: 409 Conflict)을 응답해요. 실험에서도 같은 키로 100건을 동시에 넣으니 1건만 들어갔어요. C는 틈이 있어서 고르지 않아요.

**채점 포인트**: 동시성과 중복의 구분, 락으로는 못 막는다, 멱등 키(클라이언트 생성, 재시도 때 같은 값), DB 유니크 제약, 이전 결과 재응답, 처리 중 상태, 화면 방어는 보조.

**흔한 감점 답안**: "버튼을 비활성화한다"만 쓰는 답(재시도를 못 막음), "락을 건다"(두 번 다 실행됨), "Redis에 키가 있는지 확인 후 처리"(확인-처리 틈).
</details>

<details>
<summary>상황 5: 선착순 쿠폰 1만 장을 오후 2시에 풀어요. 10만 명이 몰릴 것으로 예상하고, 1인 1장 제한이 있어요. 서버는 여러 대예요. DB 락만으로 할지, Redis를 쓸지 설계를 써 주세요.</summary>

**상황 파악**
공유 자원은 쿠폰 재고 한 행이에요. 10만 요청이 몇 초 안에 그 한 행으로 몰려요. 요구사항은 세 가지예요. ① 1만 장을 넘지 않기 ② 1인 1장 ③ DB가 버티기.

**원인 후보(깨질 수 있는 지점)**
1. 초과 발급: 재고 확인과 차감 사이 틈
2. 한 사람이 여러 장: 같은 사용자의 동시 요청·재시도
3. DB 과부하: 한 행에 10만 건이 줄 서면 대기가 길어지고 커넥션 풀이 바닥남

**해결책과 트레이드오프**

| 방법 | 장점 | 단점 |
|---|---|---|
| A. DB만: 조건부 UPDATE `stock = stock - 1 WHERE stock > 0` + `UNIQUE(user_id, coupon_id)` | 단순, 정확, 추가 인프라 없음 | 10만 건이 한 행에서 줄 섬 → 응답 지연, 커넥션 고갈 위험 |
| B. Redis 앞단 차감(Lua로 "남았으면 빼기"를 한 번에) + DB 최종 확정 | 대부분을 Redis에서 빠르게 거절, DB엔 약 1만 건만 | Redis와 DB 수가 어긋날 수 있어 맞춰 보기 필요, 구조 복잡 |
| C. 대기열로 입장 속도 조절 + A | DB가 버틸 만큼만 들여보냄 | 대기열 구축 비용, 사용자가 기다림 |

**내가 고를 방법**
B를 고르고, 필요하면 C를 앞에 둬요. Redis에서 Lua 스크립트로 재고를 깎아 1만 명만 통과시키고, 나머지 9만 명은 바로 "마감"을 받아요. 통과한 요청만 DB에 `UNIQUE(user_id, coupon_id)` INSERT와 조건부 UPDATE로 최종 확정해요. 그래서 Redis가 잘못돼도 DB가 초과 발급과 중복을 막는 마지막 보루가 돼요. Redis에서 깎았는데 DB 확정이 실패한 건은 되돌리고, 끝난 뒤 Redis 수와 DB 발급 수를 맞춰 봐요. 예상 트래픽이 이보다 작아 DB가 버틸 수 있다면 A만으로 충분하니 부하 테스트로 정해요. Redis 분산 락으로 한 명씩 줄 세우는 방식은 10만 명이 락을 기다리게 돼서 고르지 않아요. → [대기열 설계](../../system-design/waiting-queue/)

**채점 포인트**: 한 행 몰림(핫스팟) 인식, 정확성은 DB(조건부 UPDATE + 유니크 제약), Redis 원자적 차감(GET 후 DECR 금지), 실패 시 되돌리기·정합성 확인, 1인 1장 = 유니크 제약, 부하 테스트로 결정, 분산 락을 안 고른 이유.

**흔한 감점 답안**: "Redis 분산 락을 건다"(전원이 줄 서서 느림), "Redis로만 처리"(최종 기록·정합성 없음), "synchronized"(서버 여러 대).
</details>
